### Copying Collection e Reference Counting

Dois algoritmos complementares com filosofias opostas: Copying Collection move objetos para eliminar fragmentação; Reference Counting os libera imediatamente mas falha com ciclos.

---

## Copying Collection

Divide o espaço em duas metades (semi-spaces). Apenas uma metade está ativa por vez:

```
FASE 1 — Scan:
  Percorre objetos vivos no espaço ativo (From-space)

FASE 2 — Copy:
  Copia cada objeto vivo para o espaço inativo (To-space)
  Atualiza referências para novos endereços
  Objetos mortos simplesmente ficam para trás (não precisam ser "liberados")

FASE 3 — Swap:
  To-space vira o novo From-space
  From-space antigo é completamente descartado
```

**Na JVM — Eden e Survivor Spaces:**
```
Eden [A B C D E F] → Minor GC →  Survivor S1 [A C E]  (B, D, F morreram)
S0 [G H] → Minor GC → S1 também recebe [G H] se ainda vivos
Eden limpo para nova alocação
```

**Vantagens:**
- Zero fragmentação — objetos sempre compactados no To-space
- Rápido para Young Generation onde a maioria morre (pouco a copiar)

**Desvantagem:**
- Usa apenas 50% do espaço disponível (metade sempre vazia)
- Lento se muitos objetos sobrevivem (copia muito)

## Reference Counting

Cada objeto mantém um contador de quantas referências apontam para ele:

```java
Pessoa p = new Pessoa();   // contador = 1
Pessoa q = p;              // contador = 2
p = null;                  // contador = 1
q = null;                  // contador = 0 → objeto coletado IMEDIATAMENTE
```

**Vantagem:** Coleta imediata — sem pausas de GC, sem varredura periódica.

**Problema fatal: ciclos de referência**

```python
# Python (usa reference counting)
class No:
    def __init__(self): self.proximo = None

a = No()
b = No()
a.proximo = b   # b.contador = 1
b.proximo = a   # a.contador = 1

a = None        # a.contador = 1 (ainda referenciado por b.proximo)
b = None        # b.contador = 1 (ainda referenciado por a.proximo)

# Ambos têm contador = 1 mas são inacessíveis — LEAK com reference counting puro
```

O Python resolve isso com o **Cyclic Garbage Collector** — um algoritmo separado que detecta ciclos periodicamente. Mas é mais lento e menos previsível.

---

## Comparação

| Algoritmo | Coleta imediata | Lida com ciclos | Fragmentação | Overhead |
|-----------|----------------|-----------------|-------------|---------|
| Reference Counting | Sim | Não (precisa detector) | Nenhuma | Constante por operação |
| Copying Collection | Não (periódica) | Sim | Nenhuma | Por evento de GC |
| Mark-and-Sweep | Não | Sim | Alta | Por evento de GC |

## 🧩 Quiz de Fixação

1. Por que Copying Collection é eficiente para o Young Generation mas não para o Old?
2. O que é um ciclo de referência e por que Reference Counting não o detecta?
3. Por que Python tem dois mecanismos de GC (reference counting + cycle detector)?

**Respostas:**
1) No Young, a maioria dos objetos morre — pouco a copiar, processo rápido. No Old, muitos objetos sobrevivem — copiar todos a cada coleta seria extremamente caro.
2) Ciclo de referência é quando A→B→A (ou cadeia maior). O contador de ambos nunca chega a zero mesmo com ambos inacessíveis — cada um mantém o outro "vivo" artificialmente.
3) Reference counting é rápido e garante coleta imediata para objetos sem ciclos (a maioria). O cycle detector é o fallback para ciclos, rodando periodicamente. Combinar os dois dá coleta rápida no caso comum com tratamento correto do caso difícil.
