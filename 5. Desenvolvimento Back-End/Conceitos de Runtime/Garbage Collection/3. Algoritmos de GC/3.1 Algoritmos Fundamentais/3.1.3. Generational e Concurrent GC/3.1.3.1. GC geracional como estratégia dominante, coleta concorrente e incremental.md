### GC Geracional e Concurrent — As Estratégias Dominantes

Os algoritmos fundamentais (Mark-Sweep, Copying) são blocos de construção. Os coletores modernos os combinam em duas estratégias macro que dominam os runtimes de produção: geracional e concurrent.

---

## GC Geracional — combinando algoritmos por região

O GC geracional não é um algoritmo único — é uma **estratégia de aplicar algoritmos diferentes em regiões diferentes** do heap com base na "idade" dos objetos:

```
Young Generation → Copying Collection
  (maioria morre jovem → copiar apenas os vivos é barato)

Old Generation → Mark-and-Compact ou Mark-and-Sweep
  (poucos objetos, mas vivem muito → compactação periódica)
```

**Por que funciona tão bem:**
- 95%+ das coletas são Minor GCs (Young only) — rápidas e frequentes
- Old GCs são raras — objetos lá são realmente de longa duração
- Cada região usa o algoritmo mais eficiente para seu perfil de objetos

---

## GC Concorrente — eliminar pausas longas

O problema histórico do GC: **Stop-the-World**. A aplicação para para o GC varrer. Em heaps grandes, isso significa segundos de pausa.

A solução: executar a maior parte do trabalho de GC **enquanto a aplicação roda**:

```
Timeline sem concurrent GC:
  App ──────────────── STW (2s) ──────────────── App continua

Timeline com concurrent GC (ex: G1, ZGC):
  App ──── STW(<5ms) ──── App+GC simultâneos ──── STW(<5ms) ──── App
```

**Fases típicas de um coletor concurrent:**

| Fase | Concurrent? | O que faz |
|------|------------|----------|
| Initial Mark | STW (curto) | Marca objetos diretamente alcançados pelas GC Roots |
| Concurrent Mark | Sim | Percorre o grafo de referências enquanto app roda |
| Remark | STW (curto) | Captura mudanças feitas durante o Concurrent Mark |
| Concurrent Sweep/Compact | Sim | Limpa e reorganiza memória enquanto app roda |

---

## GC Incremental

Uma variação do concurrent: ao invés de fazer todo o trabalho em paralelo, divide em **fatias pequenas** intercaladas com a execução:

```
App ── GC(5ms) ── App ── GC(5ms) ── App ── GC(5ms) ── App
```

Resultado: pausas curtas e previsíveis em vez de uma pausa longa e rara. Comum em ambientes interativos (V8 do browser, jogos).

---

## Resumo das estratégias modernas

| Estratégia | Coletores | Caso de uso |
|-----------|----------|-------------|
| Geracional + Parallel | ParallelGC (Java), CLR padrão | Alta throughput, pausas toleráveis |
| Geracional + Concurrent | G1 GC (Java padrão desde JDK 9) | Equilíbrio throughput/latência |
| Geracional + Concurrent low-latency | ZGC, Shenandoah | SLA < 10ms de pausa |
| Reference Counting + Cyclic | CPython | Scripts, processos de vida curta |
| Incremental | V8 (JavaScript) | Browser/Node.js com UI responsiva |

## 🧩 Quiz de Fixação

1. Por que o Young Generation usa Copying Collection e não Mark-and-Compact?
2. O que o "Remark" STW faz no ciclo de um coletor concurrent?
3. Qual a diferença prática entre GC concurrent e GC incremental?

**Respostas:**
1) Copying Collection é mais eficiente quando a maioria dos objetos morre — no Young, 95%+ morrem, então há pouco a copiar. Mark-and-Compact percorre e move tudo, sendo mais caro para regiões com muita rotatividade.
2) O Concurrent Mark roda enquanto a aplicação modifica objetos — ao terminar, o grafo pode estar desatualizado. O Remark STW re-escaneia as mudanças feitas durante o Concurrent Mark para garantir que nenhum objeto vivo seja perdido.
3) Concurrent: o GC roda em threads separadas simultaneamente com a aplicação — ambos acontecem ao mesmo tempo. Incremental: o GC é dividido em pequenas fatias que se alternam com a execução da aplicação — não simultâneos, mas interleaved. Incremental garante mais previsibilidade; concurrent é mais eficiente em CPUs multi-core.
