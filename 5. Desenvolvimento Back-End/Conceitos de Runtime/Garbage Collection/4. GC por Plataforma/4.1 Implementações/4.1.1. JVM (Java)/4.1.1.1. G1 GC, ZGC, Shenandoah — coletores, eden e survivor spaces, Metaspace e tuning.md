### GC na JVM (Java)

A JVM é a plataforma com o ecossistema de GC mais rico — oferece múltiplos coletores selecionáveis, cada um otimizado para um perfil diferente de aplicação.

---

## Coletores disponíveis

| Coletor | Padrão desde | Foco | Pausa típica |
|---------|-------------|------|-------------|
| **Serial GC** | JDK 1 | Single-core, baixo footprint | Alta (ms–s) |
| **Parallel GC** | JDK 5 | Throughput máximo | Alta (ms–s) |
| **CMS** | JDK 6 (deprecado JDK 9) | Baixa latência (substituído) | Média |
| **G1 GC** | JDK 9 (padrão) | Equilíbrio throughput/latência | 10–200ms configurável |
| **ZGC** | JDK 15 (production) | Latência mínima, heaps enormes | < 1ms |
| **Shenandoah** | JDK 15 | Latência mínima (Red Hat) | < 10ms |

---

## Organização de memória na JVM

```
Young Generation:
  ├── Eden Space       (alocação inicial de todos os objetos)
  ├── Survivor S0      (objetos que sobreviveram ao Minor GC)
  └── Survivor S1      (alternado com S0 a cada Minor GC)

Old Generation:
  └── Tenured Space    (objetos promovidos após N Minor GCs)

Metaspace (Java 8+, fora do heap):
  └── Metadados de classes, bytecode, method tables
      (substituiu PermGen — sem mais OutOfMemoryError: PermGen space)
```

---

## G1 GC — o padrão moderno

G1 (Garbage First) divide o heap em **regiões de tamanho uniforme** (1MB–32MB):

```
Heap: [E][E][S][O][O][E][H][O][S][E][O][O]
       ↑   ↑   ↑       ↑
    Eden Survivor Old  Humongous (objetos grandes)
```

G1 coleta primeiro as regiões com mais lixo (daí "Garbage First"). Permite pausas configuráveis:

```bash
-XX:MaxGCPauseMillis=200   # target de 200ms de pausa máxima
```

---

## ZGC — ultra baixa latência

ZGC mantém pausas abaixo de **1ms independente do tamanho do heap** (funciona com heaps de terabytes):

```bash
java -XX:+UseZGC -Xmx16g MeuServico
```

Técnicas que permitem isso:
- **Colored pointers**: informação do GC embutida nos ponteiros — sem precisar parar a aplicação para escanear
- **Load barriers**: código inserido pelo JIT que mantém o grafo consistente sem STW
- Toda compactação e marcação são feitas concorrentemente

---

## Tuning básico

```bash
# Heap size
-Xms2g -Xmx8g          # heap mínimo 2GB, máximo 8GB

# Escolha de coletor
-XX:+UseG1GC            # G1 (padrão no JDK 9+)
-XX:+UseZGC             # ZGC (ultra baixa latência)
-XX:+UseShenandoahGC    # Shenandoah

# G1 tuning
-XX:MaxGCPauseMillis=100           # pausa máxima alvo
-XX:G1HeapRegionSize=16m           # tamanho das regiões
-XX:InitiatingHeapOccupancyPercent=45  # quando iniciar coleta concurrent

# Logging de GC
-Xlog:gc*:file=gc.log:time,uptime:filecount=5,filesize=10m
```

## 🧩 Quiz de Fixação

1. Por que o G1 GC substituiu o CMS como padrão?
2. O que é Metaspace e por que substituiu o PermGen?
3. Em que situação você escolheria ZGC em vez de G1?

**Respostas:**
1) G1 é mais previsível (tempo de pausa configurável), não sofre de fragmentação do Old Generation como o CMS, e lida melhor com heaps grandes. O CMS tinha bugs difíceis de resolver e foi deprecado no JDK 9.
2) Metaspace armazena metadados de classes fora do heap Java (na memória nativa). O PermGen era dentro do heap com tamanho fixo — causava `OutOfMemoryError: PermGen space` em aplicações com muitas classes. Metaspace cresce dinamicamente.
3) ZGC é a escolha quando SLA exige pausas abaixo de 1ms (sistemas financeiros, jogos em tempo real, APIs com latência P99 crítica), especialmente com heaps grandes (8GB+) onde G1 pode ter pausas de centenas de ms.
