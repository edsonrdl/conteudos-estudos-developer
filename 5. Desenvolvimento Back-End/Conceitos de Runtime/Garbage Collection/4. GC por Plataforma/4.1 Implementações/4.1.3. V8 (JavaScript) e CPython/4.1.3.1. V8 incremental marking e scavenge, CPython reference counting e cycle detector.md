### GC no V8 (JavaScript) e CPython (Python)

Duas plataformas com abordagens bem diferentes: V8 usa GC geracional com coleta incremental adaptada para ambientes de browser/Node.js; CPython usa reference counting como mecanismo primário.

---

## V8 — JavaScript (Chrome, Node.js)

O V8 implementa um GC geracional com foco em latência previsível — fundamental para não travar a UI do browser.

**Divisão do heap:**

```
Young Generation (New Space):
  ├── From-space   (alocação ativa)
  └── To-space     (destino do Scavenge)

Old Generation (Old Space):
  ├── Old Space    (objetos promovidos)
  ├── Code Space   (código JIT compilado)
  └── Large Object Space (objetos grandes)
```

**Scavenge (Minor GC no V8):**
- Copying Collection no New Space
- Muito frequente e muito rápido (New Space é pequeno: ~1-8MB)
- Objetos que sobrevivem 2 Scavenges → promovidos para Old Space

**Mark-Compact (Major GC no V8):**
- Coleta o Old Space
- **Incremental marking**: divide a marcação em fatias de ~1ms intercaladas com JavaScript
- **Concurrent sweeping**: limpeza em thread separada, não bloqueia JS

```
Timeline no browser:
  JS frame(16ms) ── GC(1ms) ── JS frame(16ms) ── GC(1ms) ── ...
  → GC é invisível para o usuário (dentro do budget de 60fps)
```

## CPython — Python

CPython combina dois mecanismos:

### Reference Counting (primário)

```python
x = [1, 2, 3]    # lista: refcount = 1
y = x             # lista: refcount = 2
x = None          # lista: refcount = 1
y = None          # lista: refcount = 0 → DESTRUÍDA IMEDIATAMENTE
```

**Vantagem:** Objetos destruídos instantaneamente ao perder todas as referências — sem pausa de GC, memória liberada no momento exato.

**Desvantagem:** Ciclos de referência não são coletados pelo reference counting:

```python
a = []
b = []
a.append(b)   # b.refcount = 2 (variável b + referência em a)
b.append(a)   # a.refcount = 2 (variável a + referência em b)
del a         # a.refcount = 1 (ainda referenciado por b[0])
del b         # b.refcount = 1 (ainda referenciado por a[0])
# Ambos inacessíveis mas refcount > 0 — LEAK
```

### Cycle Detector (secundário)

O módulo `gc` do CPython roda periodicamente para detectar e coletar ciclos:

```python
import gc
gc.collect()           # força coleta de ciclos manualmente
gc.disable()           # desabilita (se sua aplicação não cria ciclos)
gc.get_threshold()     # (700, 10, 10) — thresholds por geração
```

**GIL e implicações para GC:**
O Global Interpreter Lock (GIL) do CPython garante que apenas uma thread Python executa por vez — simplifica o reference counting (sem race conditions nos contadores) mas limita paralelismo.

## Comparação

| | V8 | CPython |
|--|-----|---------|
| Mecanismo primário | Geracional + incremental marking | Reference counting |
| Coleta de ciclos | Sim (Mark-Compact) | Sim (cycle detector periódico) |
| Coleta imediata | Não | Sim (sem ciclos) |
| Pausas | < 1ms (incremental) | Mínimas (exceto durante cycle detection) |
| Ideal para | Ambientes com restrição de latência de frame | Scripts, processos de vida curta |

## 🧩 Quiz de Fixação

1. Por que o V8 divide a marcação (incremental marking) em fatias de ~1ms?
2. O `del` em Python libera memória imediatamente?
3. Por que `gc.disable()` pode ser seguro em alguns programas Python?

**Respostas:**
1) Para não bloquear o event loop do JavaScript — o browser precisa renderizar frames a 60fps (~16ms cada). Uma pausa de GC de 50ms causaria frame drops visíveis. Fatias de 1ms mantêm o GC invisível para o usuário.
2) `del` decrementa o refcount. Se o refcount chegar a zero, sim — o objeto é destruído imediatamente. Se há outras referências (ou ciclos), a memória não é liberada.
3) Se o programa cria apenas estruturas acíclicas (sem objetos que se referenciam mutuamente), o reference counting é suficiente para gerenciar toda a memória. O cycle detector é desnecessário e seu overhead pode ser eliminado com `gc.disable()`.
