### Latência vs Throughput — Trade-offs do GC

Todo GC é uma negociação entre três dimensões que não podem ser maximizadas simultaneamente: **throughput**, **latência** e **footprint** (uso de memória).

---

## O triângulo impossível

```
         Throughput
        (% de CPU na app)
             ▲
             │
             │   Você pode ter dois dos três
             │
  Footprint ──────────── Latência
(memória usada)    (tempo de pausa)
```

| Prioridade | Coletor típico | Sacrifício |
|-----------|---------------|-----------|
| **Throughput máximo** | Parallel GC | Pausas longas |
| **Latência mínima** | ZGC, Shenandoah | Mais CPU e memória |
| **Footprint mínimo** | Serial GC | Throughput e latência |
| **Equilíbrio** | G1 GC | Nem o melhor em nenhum dos três |

---

## Heap sizing — a decisão mais impactante

```
Heap pequeno:
  + Menor uso de memória
  + Full GC mais rápido (menos para varrer)
  - GC muito frequente (heap enche rápido)
  - Maior % de CPU gasto em GC

Heap grande:
  + GC menos frequente
  + Maior throughput (app roda mais sem interrupções)
  - Full GC pode ser lento (muito para varrer)
  - Maior consumo de memória
```

**Regra prática para Java/G1:**
```bash
# Tamanho mínimo = 2x o uso de heap em steady state
# Exemplo: app usa ~2GB em repouso → Xmx4g a 6g

java -Xms2g -Xmx6g -XX:+UseG1GC -XX:MaxGCPauseMillis=100 MinhaApp
```

## Análise de GC logs

GC logs são a principal ferramenta de diagnóstico de problemas de GC:

```bash
# Java — habilitar log de GC
-Xlog:gc*:file=gc.log:time,uptime:filecount=5,filesize=20m
```

**O que procurar nos logs:**

```
# Minor GC frequente → Young Generation pequeno
[0.235s][info][gc] GC(1) Pause Young (Normal) 156M->12M(512M) 4.521ms

# Major GC crescendo → objetos sendo promovidos em excesso
[12.451s][info][gc] GC(47) Pause Young (Concurrent Start) 480M->460M(512M) 8.2ms

# Full GC → situação crítica
[45.2s][info][gc] GC(89) Pause Full (Allocation Failure) 511M->220M(512M) 4521ms
                                                                             ↑ 4.5 segundos!
```

**Ferramentas de análise:**
- **GCEasy.io** — análise visual de GC logs online
- **JVM MXBeans** — métricas de GC em tempo real via JMX/Micrometer
- **async-profiler** — profiler de baixo overhead que inclui eventos de GC

---

## Métricas para monitorar em produção

```
gc.pause.duration    → duração das pausas (P50, P95, P99)
gc.memory.used       → uso de heap ao longo do tempo
gc.collection.count  → frequência de coletas por tipo
jvm.gc.overhead      → % de CPU gasto em GC (alerta se > 5%)
```

## 🧩 Quiz de Fixação

1. Se uma aplicação precisa de throughput máximo e pode tolerar pausas de 1s, qual coletor JVM escolher?
2. O que indica `jvm.gc.overhead` acima de 5%?
3. Como determinar se o heap está subdimensionado?

**Respostas:**
1) Parallel GC (`-XX:+UseParallelGC`) — maximiza throughput usando todas as CPUs para GC, a custo de pausas maiores. Ideal para batch processing, jobs offline.
2) O GC está consumindo mais de 5% do tempo total de CPU da JVM — a aplicação gasta mais tempo coletando do que processando. A JVM também lança `OutOfMemoryError: GC overhead limit exceeded` ao atingir 98%.
3) Analisando os GC logs: se Minor GCs são muito frequentes (< 1s entre coletas), o heap está subdimensionado. Se o heap usage após cada coleta não cai muito (GC recovering pouca memória), há objetos de vida longa demais no Young ou vazamento lógico.
