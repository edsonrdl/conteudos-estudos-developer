### Sistemas Low-Latency e Alternativas ao GC

Em sistemas onde pausas de GC de qualquer duração são inaceitáveis — trading de alta frequência, simulações em tempo real, jogos AAA, roteadores de pacotes — o próprio GC se torna o inimigo. As estratégias a seguir eliminam ou contornam o GC completamente.

---

## 1. Object Pooling — reutilizar em vez de alocar

A ideia central: alocar objetos uma vez na inicialização e reutilizá-los indefinidamente. Zero alocações novas = zero pressão no GC.

```java
// Pool de objetos de mensagem para um sistema de mensageria
public class MessagePool {
    private final Queue<Message> pool = new ArrayDeque<>(1000);

    public MessagePool(int size) {
        for (int i = 0; i < size; i++) {
            pool.add(new Message());  // alocação única no boot
        }
    }

    public Message acquire() {
        Message m = pool.poll();
        if (m == null) throw new RuntimeException("Pool exhausted");
        return m;
    }

    public void release(Message m) {
        m.reset();        // limpar estado
        pool.offer(m);    // devolver ao pool
    }
}

// Uso: zero alocações no hot path
Message msg = pool.acquire();
try {
    msg.setPayload(data);
    processMessage(msg);
} finally {
    pool.release(msg);  // nunca vira lixo para o GC
}
```

**Usado em:** Chronicle, Aeron, Disruptor (LMAX), engines de jogos (Unity, Unreal).

## 2. Off-Heap Memory — fora do alcance do GC

Java permite alocar memória diretamente na memória nativa (fora do heap gerenciado), invisível para o GC:

```java
// DirectByteBuffer — memória off-heap
ByteBuffer buffer = ByteBuffer.allocateDirect(1024 * 1024 * 100); // 100MB off-heap
// GC nunca varre esse buffer — zero pausa relacionada a ele

// Acesso via Unsafe (usado por frameworks como Netty, Cassandra, Kafka)
import sun.misc.Unsafe;
long address = unsafe.allocateMemory(1024);
unsafe.putLong(address, 42L);
long value = unsafe.getLong(address);
unsafe.freeMemory(address);  // responsabilidade manual!
```

**Bibliotecas que facilitam off-heap:**
- **Chronicle Map** — estruturas de dados off-heap com persistência
- **MapDB** — banco de dados off-heap para Java
- **Netty** — buffers de rede gerenciados off-heap com reference counting próprio

## 3. Linguagens sem GC — Rust e C++

Para sistemas onde latência determinística é requisito fundamental, linguagens com gerenciamento manual/ownership eliminam o problema na raiz:

```rust
// Rust: ownership garante liberação determinística sem GC
fn processar_pacote(dados: Vec<u8>) -> Resultado {
    let pacote = Pacote::from_bytes(dados);  // alocado
    let resultado = analisar(&pacote);
    resultado  // pacote é dropado aqui — liberação imediata e determinística
    // Sem GC, sem pausa, sem surpresas
}

// Pool manual em Rust com alocador customizado
use std::alloc::{GlobalAlloc, Layout};

// Sistemas como Tokio usam alocadores de arena para zero-copy networking
```

**Por que Rust para low-latency:**
- Sem runtime de GC
- Liberação determinística via ownership
- Zero-cost abstractions
- Usado em: Cloudflare Workers, Discord (migrou de Go para Rust para reduzir latência), Firefox

## 4. Epsilon GC — GC que não coleta

Java 11+ inclui o **Epsilon GC**: um GC que aloca memória mas nunca coleta. Útil para:

```bash
# Testes de performance sem overhead de GC
java -XX:+UseEpsilonGC -Xmx4g MeuApp

# Quando usar:
# - Benchmarks onde GC distorceria os resultados
# - Aplicações de vida muito curta (batch jobs rápidos)
# - Análise de consumo real de memória (OOM = você vê o leak)
```

Quando o heap enche com Epsilon GC, a JVM encerra — é intencional.

---

## 5. Azul Zing / C4 — GC com pausas verdadeiramente zero

Para quem precisa de Java mas sem pausas, a JVM comercial **Zing** da Azul implementa o **C4 (Continuously Concurrent Compacting Collector)**:

```
C4 vs ZGC:
  ZGC:  < 1ms de pausa (mas ainda tem pausa)
  C4:   pausas verdadeiramente zero — compactação 100% concurrent
  
Usado em: Goldman Sachs, Nasdaq, sistemas de trading HFT em Java
```

---

## Decisão de arquitetura

```
Latência aceitável > 1ms  →  ZGC ou Shenandoah (JVM padrão)
Latência < 1ms, Java obrigatório  →  Object pooling + off-heap + Azul Zing
Latência determinística absoluta  →  Rust, C++, ou Ada
Batch job efêmero  →  Epsilon GC (sem overhead nenhum)
```

## 🧩 Quiz de Fixação

1. Por que object pooling reduz pressão no GC e não apenas "esconde" o problema?
2. Qual a diferença fundamental entre DirectByteBuffer e um array Java normal em relação ao GC?
3. Em que situação o Epsilon GC é uma escolha legítima de produção?

**Respostas:**
1) Object pooling elimina alocações novas no hot path — objetos do pool existem desde a inicialização e nunca se tornam lixo. O GC não tem nada para coletar porque nenhum objeto novo é criado. Não é esconder: é genuinamente não criar lixo.
2) Arrays Java ficam no heap gerenciado — o GC os vasculha, move (durante compactação) e coleta. `DirectByteBuffer` aloca na memória nativa fora do heap — o GC nunca o vê, nunca pausa por causa dele. A desvantagem é que liberação depende do finalizador ou de chamada explícita.
3) Para jobs de vida muito curta onde a aplicação termina antes de precisar de coleta (scripts de inicialização, ferramentas CLI rápidas), e para benchmarks onde a presença do GC distorceria os resultados que se quer medir.
