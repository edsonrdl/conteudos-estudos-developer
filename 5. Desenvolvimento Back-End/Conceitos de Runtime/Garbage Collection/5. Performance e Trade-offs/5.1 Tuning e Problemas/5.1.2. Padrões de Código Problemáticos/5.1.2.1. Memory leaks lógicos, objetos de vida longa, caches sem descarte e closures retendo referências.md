### Padrões de Código Problemáticos para o GC

O GC elimina erros de gerenciamento manual, mas não protege contra padrões de código que mantêm objetos vivos além do necessário. Esses "memory leaks lógicos" são a causa mais comum de degradação de performance em aplicações de longa duração.

---

## 1. Coleções estáticas sem política de descarte

```java
// PROBLEMA: HashMap estático que só cresce
public class SessionManager {
    private static final Map<String, UserSession> sessions = new HashMap<>();

    public void criarSessao(String token, UserSession session) {
        sessions.put(token, session);  // nunca remove
    }
}
// sessions é GC Root (variável estática)
// Todos os UserSession são eternamente alcançáveis
// Heap cresce indefinidamente → eventual OutOfMemoryError
```

**Solução:** `WeakHashMap` (chaves são coletadas quando não há mais referências externas) ou cache com TTL/tamanho máximo (Caffeine, Guava Cache).

---

## 2. Listeners e callbacks não removidos

```java
// PROBLEMA: componente registra listener mas nunca remove
button.addActionListener(e -> {
    // closure captura 'this' — referência ao componente pai
    this.processarClique();
});
// button → listener → this (componente pai)
// Mesmo após o componente "sumir", o button ainda o referencia
```

**Padrão clássico em:** Swing/JavaFX, Android Activities, event buses (EventBus, RxJava sem dispose).

**Solução:** sempre remover listeners ao destruir o componente (`removeActionListener`, `dispose()`, `unsubscribe()`).

---

## 3. Closures em JavaScript retendo contexto

```javascript
// PROBLEMA: closure retém referência ao DOM inteiro
function configurarBotao() {
    const elementoGrande = document.getElementById('tabela-enorme'); // 10MB de DOM

    document.getElementById('btn').addEventListener('click', () => {
        console.log('clicado');
        // 'elementoGrande' está em closure mas nunca é usado
        // O GC não pode coletar elementoGrande enquanto o listener existir
    });
}
```

**Solução:** não capturar o que não é necessário, ou capturar apenas o dado mínimo.

---

## 4. Cache sem limite ou expiração

```python
# PROBLEMA: cache que cresce ilimitadamente
cache = {}

def get_dados(id):
    if id not in cache:
        cache[id] = buscar_do_banco(id)  # nunca expira, nunca remove
    return cache[id]
```

**Solução:** `functools.lru_cache` com `maxsize`, ou bibliotecas de cache com TTL.

---

## 5. ThreadLocal não limpo

```java
// PROBLEMA: ThreadLocal em thread pool (threads são reutilizadas)
private static ThreadLocal<List<String>> buffer = new ThreadLocal<>();

void processar() {
    buffer.set(new ArrayList<>());
    // ... usa buffer ...
    // esquecer de chamar buffer.remove() ao finalizar
}
// A thread volta para o pool com o ThreadLocal ainda preenchido
// Próxima requisição pode ver dados da anterior
// Referência nunca é coletada enquanto a thread existir
```

**Solução:** sempre `buffer.remove()` no finally.

## Diagnóstico de memory leaks lógicos

```
Sintoma: heap usage cresce lentamente mas consistentemente ao longo do tempo
         mesmo após GCs completos

Ferramenta (Java): heap dump + análise com Eclipse MAT ou VisualVM
  jmap -dump:live,format=b,file=heapdump.hprof <pid>
  → procurar por instâncias acumuladas de uma mesma classe

Ferramenta (Node.js): --inspect + Chrome DevTools Memory tab
  → tirar snapshots ao longo do tempo, comparar o que cresceu
```

## 🧩 Quiz de Fixação

1. Por que `WeakHashMap` resolve o problema do cache estático?
2. Por que ThreadLocal em thread pools é especialmente perigoso?
3. Como diferenciar um memory leak lógico de um heap subdimensionado?

**Respostas:**
1) As chaves do `WeakHashMap` são referências fracas — o GC pode coletá-las quando não há mais referências fortes para elas. A entrada do map some automaticamente, liberando o valor associado.
2) Em thread pools, as threads nunca morrem — são reutilizadas. Um ThreadLocal associado a uma thread permanece até a thread morrer ou até `remove()` ser chamado. Entre requisições, o dado fica "pendurado" na thread, nunca coletado, e pode ser acidentalmente acessado pela próxima requisição.
3) Memory leak lógico: heap uso cresce continuamente mesmo sem aumento de carga — cada ciclo de GC recupera menos memória que o anterior. Heap subdimensionado: uso oscila próximo ao máximo mas se estabiliza, e GCs frequentes conseguem recuperar memória — a aplicação sobrevive mas com GC excessivo.
