### GC — Conceito e Problema que Resolve

O Garbage Collector (GC) é o componente do runtime responsável por liberar automaticamente a memória de objetos que o programa não usa mais. Ele resolve um problema fundamental que existia antes de sua adoção: o gerenciamento manual de memória era frágil, complexo e fonte constante de bugs críticos.

---

## O problema antes do GC

Em linguagens como C e C++, o programador aloca e libera memória manualmente:

```c
Pessoa* p = malloc(sizeof(Pessoa));   // aloca
// ... usa p ...
free(p);                               // libera — OBRIGATÓRIO
```

Esse modelo gerava quatro categorias de erros graves:

| Erro | O que acontece |
|------|---------------|
| **Memory leak** | `free()` esquecido — objeto ocupa memória para sempre |
| **Dangling pointer** | Ponteiro usado após o `free()` — acessa memória inválida |
| **Double free** | `free()` chamado duas vezes — corrompe o heap |
| **Use-after-free** | Objeto usado depois de liberado — comportamento indefinido |

Em sistemas grandes (APIs com milhares de requisições, microservices, frameworks com objetos em cascata), garantir que cada objeto fosse liberado exatamente uma vez, no momento certo, tornou-se inviável.

---

## O que o GC faz

O GC assume a responsabilidade de liberar memória automaticamente. O desenvolvedor cria objetos livremente — o runtime decide quando coletá-los:

```java
// Java — sem free(), sem delete()
Pessoa p = new Pessoa("Ana");
processarPessoa(p);
// quando p sai de escopo e não há mais referências,
// o GC a coletará automaticamente
```

O GC executa três funções centrais:
1. **Rastrear** todos os objetos criados no heap
2. **Determinar** quais ainda são alcançáveis (em uso) e quais não são
3. **Liberar** a memória dos inacessíveis

---

## O que o GC elimina vs o que não elimina

| Elimina | Não elimina |
|---------|------------|
| Dangling pointers | Memory leaks **lógicos** (objeto referenciado mas nunca usado) |
| Double free | Alocação excessiva |
| Use-after-free | Objetos retidos por caches mal projetados |
| Maioria dos memory leaks reais | GC não corrige mau design |

**Memory leak lógico** — o erro mais comum em código GC-managed:
```java
List<Evento> historico = new ArrayList<>();

void registrar(Evento e) {
    historico.add(e);  // nunca remove — lista cresce infinitamente
    // o GC não pode coletar: os objetos ainda são alcançáveis
}
```
O GC só coleta objetos *inacessíveis*. Se o código mantém referências desnecessárias, o GC não pode ajudar.

---

## Impacto no design de software

Com o GC, padrões que seriam perigosos sem ele tornaram-se seguros e idiomáticos:

- **Imutabilidade** — criar novos objetos em vez de modificar existentes
- **Objetos efêmeros** — DTOs, records, value objects descartados rapidamente
- **Pipelines funcionais** — `stream().map().filter().collect()` cria dezenas de objetos intermediários
- **Arquiteturas orientadas a eventos** — mensagens criadas e descartadas em alta frequência

## 🧩 Quiz de Fixação

1. O que é um dangling pointer e como o GC o previne?
2. Por que memory leaks ainda ocorrem em linguagens com GC?
3. O GC elimina a necessidade de pensar em memória?

**Respostas:**
1) Dangling pointer é um ponteiro que referencia memória já liberada. Com GC, o runtime só libera memória quando não há mais referências — nunca enquanto o ponteiro existir.
2) Memory leaks lógicos ocorrem quando o código mantém referências a objetos que não serão mais usados (listas que crescem, caches sem expiração). O GC só coleta inacessíveis — se há referência, o objeto está "vivo" para o GC.
3) Não. O GC elimina erros de ciclo de vida (free/delete), mas entender heap sizing, padrões de alocação, gerações e tuning é essencial para sistemas de alta performance.
