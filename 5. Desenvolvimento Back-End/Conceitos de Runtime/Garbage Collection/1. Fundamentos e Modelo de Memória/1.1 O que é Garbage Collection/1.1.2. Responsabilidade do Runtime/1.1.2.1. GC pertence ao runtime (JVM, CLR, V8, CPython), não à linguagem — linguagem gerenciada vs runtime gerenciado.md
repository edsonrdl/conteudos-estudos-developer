### GC Pertence ao Runtime, Não à Linguagem

O equívoco mais comum: "Java tem GC", "Python tem GC". A afirmação é tecnicamente imprecisa. O GC pertence ao **runtime** — a máquina virtual ou engine de execução. A linguagem apenas define a sintaxe e regras; o runtime implementa o mecanismo de memória.

---

## Por que o GC é do runtime

```
Linguagem → define REGRAS (sintaxe, escopo, tipos, como criar objetos)
Runtime   → define EXECUÇÃO (heap, GC, threads, JIT, otimizações)
```

A prova: duas linguagens distintas podem compartilhar o mesmo GC.

| Linguagens | Runtime compartilhado | GC |
|-----------|----------------------|-----|
| Java, Kotlin, Scala | JVM (HotSpot, OpenJ9, GraalVM) | G1, ZGC, Shenandoah... |
| C#, F#, VB.NET | CLR (.NET) | GC geracional da CLR |
| JavaScript, TypeScript | V8, SpiderMonkey, JavaScriptCore | Incremental marking |
| Python (padrão) | CPython | Reference counting + cycle detector |

Se você rodar o mesmo código Python no CPython vs PyPy, o comportamento de memória será diferente — mesma linguagem, runtime diferente, GC diferente.

---

## O que cada um controla

**A linguagem define:**
- Como objetos são criados (`new`, literais, fábricas)
- Escopo e visibilidade de variáveis
- Se variáveis são por valor ou por referência
- Regras de tipagem

**A linguagem NÃO define:**
- Como o heap é estruturado internamente
- Qual algoritmo de GC é usado
- Quando o GC entra em ação
- Quantas threads paralelas de GC existem
- Como fragmentação é tratada
- Como o grafo de referências é rastreado

---

## Linguagem gerenciada vs Runtime gerenciado

| Conceito | Definição |
|---------|-----------|
| **Linguagem gerenciada** | Código não executa diretamente na CPU — passa por um ambiente intermediário. O desenvolvedor não controla ponteiros, alocação ou desalocação diretamente. Exemplos: Java, C#, Python, JS |
| **Runtime gerenciado** | O ambiente que realmente executa o código e gerencia memória, threads, segurança e otimizações. Exemplos: JVM, CLR, V8, CPython |

> Uma linguagem é "gerenciada" porque seu runtime assume a responsabilidade pelo gerenciamento de memória — incluindo o GC.

**Contraexemplo:** C e C++ são linguagens **não gerenciadas** — código compila direto para o binário nativo, sem runtime intermediário, sem GC automático.

---

## Implicação prática

Qualquer mudança no runtime afeta diretamente:
- Ritmo e duração das coletas
- Tamanho padrão do heap
- Pausas Stop-the-World
- Comportamento de performance da aplicação

Por isso, engenheiros de performance estudam o **runtime**, não apenas a linguagem. Saber que "Java usa G1 GC por padrão a partir do JDK 9" é conhecimento de runtime, não de linguagem.

## 🧩 Quiz de Fixação

1. Por que dizer "Python tem GC" é tecnicamente impreciso?
2. Java e Kotlin têm GCs diferentes?
3. O que muda no comportamento de memória ao trocar de JVM (HotSpot → OpenJ9)?

**Respostas:**
1) O GC pertence ao CPython (runtime), não à linguagem Python. Rodando em PyPy, o mesmo código Python terá um GC diferente.
2) Não. Ambos compilam para bytecode JVM e usam exatamente o mesmo GC — o da JVM que estiver rodando.
3) O comportamento do GC pode mudar completamente — OpenJ9 tem estratégias de heap diferentes do HotSpot. A linguagem Java é a mesma; o que muda é o runtime e suas políticas de coleta.
