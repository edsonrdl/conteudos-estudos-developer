### Stack, Heap e Alocação

A memória de uma aplicação é dividida em regiões com propósitos distintos. Entender onde cada dado reside explica o comportamento do GC e o custo de alocação.

---

## Stack vs Heap

```
┌─────────────────┐    ┌──────────────────────────────┐
│     STACK       │    │           HEAP               │
│                 │    │                              │
│ método doWork() │    │  ┌────────────┐              │
│  ref p ────────────────>│  Pessoa    │              │
│  int x = 5      │    │  │ nome: "Ana"│              │
│                 │    │  └────────────┘              │
│ método main()   │    │                              │
│  ref pedido ───────────>│  Pedido    │              │
│                 │    │  └────────────┘              │
└─────────────────┘    └──────────────────────────────┘
  Liberada ao sair        Gerenciada pelo GC
  do escopo do método
```

| Característica | Stack | Heap |
|---------------|-------|------|
| O que armazena | Frames de execução, variáveis locais primitivas, referências | Objetos criados com `new` |
| Ciclo de vida | Vinculado ao escopo do método — liberado automaticamente ao retornar | Controlado pelo GC |
| Compartilhamento | Privada por thread | Compartilhada entre todas as threads |
| Tamanho | Pequeno e fixo (~512KB–8MB) | Grande e configurável (-Xmx) |
| Velocidade de alocação | Muito rápida (só move o stack pointer) | Mais custosa (GC overhead) |

---

## Variáveis primitivas vs referências

```java
void calcular() {
    int x = 42;                // primitivo — mora na stack, liberado ao retornar
    String nome = "Ana";       // referência na stack, objeto String no heap
    Pedido p = new Pedido();   // referência na stack, objeto Pedido no heap
}
// ao retornar: x, nome e p desaparecem da stack
// os objetos String e Pedido no heap ficam até o GC coletar
```

A **referência** (o endereço de memória) fica na stack. O **objeto** fica no heap. Quando a referência sai de escopo, o objeto no heap pode se tornar inacessível — mas não é liberado instantaneamente.

---

## Escape Analysis

Runtimes modernos (JVM HotSpot, CLR, V8) fazem **Escape Analysis** — analisam se um objeto "escapa" do método onde foi criado:

```java
// Objeto NÃO escapa — só usado localmente
void processar() {
    Point p = new Point(1, 2);  // JVM pode alocar na stack em vez do heap
    return p.x + p.y;           // p não vai para fora do método
}

// Objeto ESCAPA — retornado para o chamador
Point criarPonto() {
    return new Point(1, 2);     // precisa ir para o heap (sobrevive ao método)
}
```

Quando o objeto não escapa, o runtime pode alocá-lo na **stack** (ou registradores), eliminando completamente o overhead do GC para aquele objeto.

---

## Impacto prático para desenvolvedores

- **Objetos de curta duração** (criados e descartados no mesmo método) são ideais — Escape Analysis os mantém na stack
- **Alocação excessiva no heap** gera mais pressão no GC → mais coletas → mais pausas
- **Objetos grandes passados por referência** (em vez de copiados) reduzem alocação

## 🧩 Quiz de Fixação

1. Uma variável local `int x = 5` é gerenciada pelo GC?
2. O que acontece com o objeto no heap quando a referência local sai de escopo?
3. O que é Escape Analysis e qual seu benefício?

**Respostas:**
1) Não. Primitivos em variáveis locais ficam na stack e são liberados automaticamente quando o método retorna — sem intervenção do GC.
2) O objeto não é imediatamente liberado. Ele permanece no heap até o GC rodar e determinar que não há mais GC Roots alcançando aquele objeto.
3) Escape Analysis é a análise do runtime para determinar se um objeto criado em um método "escapa" para fora dele (retornado, passado para outra thread, armazenado em campo). Se não escapa, o runtime pode alocá-lo na stack, eliminando o overhead do GC para esse objeto.
