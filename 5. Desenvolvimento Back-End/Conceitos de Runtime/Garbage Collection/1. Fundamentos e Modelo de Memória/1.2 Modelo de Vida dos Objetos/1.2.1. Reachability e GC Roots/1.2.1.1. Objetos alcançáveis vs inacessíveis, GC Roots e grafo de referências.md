### Reachability — Como o GC Decide o que Coletar

O GC não adivinham se um objeto ainda será usado — ele usa **análise de alcançabilidade (reachability analysis)**. Um objeto é coletável se e somente se não há nenhum caminho de uma GC Root até ele.

---

## GC Roots — o ponto de partida

**GC Roots** são os pontos de entrada do grafo de referências — tudo que está definitivamente "vivo" na aplicação:

| GC Root | Exemplos |
|---------|---------|
| Stack frames ativos | Variáveis locais de métodos em execução |
| Variáveis estáticas | `static final Cache INSTANCE = new Cache()` |
| Threads ativas | Objetos referenciados por threads em execução |
| Referências JNI/nativas | Objetos passados para código nativo (C/C++) |
| Referências internas do runtime | Objetos do classloader, classes carregadas |

O GC começa por essas raízes e percorre o grafo de referências. Tudo alcançável a partir delas está **vivo**. O restante é elegível para coleta.

---

## O grafo de referências

```
GC Roots
   │
   ├── Objeto A (vivo)
   │     ├── Objeto B (vivo — alcançado via A)
   │     └── Objeto C (vivo — alcançado via A)
   │           └── Objeto D (vivo — alcançado via C)
   │
   └── Objeto E (vivo)

   Objeto F ──→ Objeto G    ← INACESSÍVEIS: nenhuma GC Root aponta para eles
```

F e G são coletáveis mesmo que apontem um para o outro — o que importa é acessibilidade a partir das roots, não existência de referências entre si.

---

## Exemplos práticos

```java
// 1. Objeto vivo
String nome = "Ana";   // 'nome' é GC Root (variável local)
// → objeto String "Ana" está vivo

// 2. Objeto torna-se inacessível
nome = null;           // referência perdida
// → objeto String "Ana" não tem mais GC Root apontando para ele
// → elegível para coleta

// 3. Cadeia de objetos
Pedido pedido = new Pedido();
pedido.cliente = new Cliente();
pedido.itens = List.of(new Item(), new Item());

pedido = null;
// → Pedido, Cliente e ambos os Items tornam-se inacessíveis juntos
// → toda a cadeia é coletada
```

## Memory leak lógico — quando o grafo não mente

```java
static List<Request> auditLog = new ArrayList<>();

void handleRequest(Request req) {
    auditLog.add(req);   // variável estática = GC Root permanente
    process(req);
    // req nunca é removido de auditLog
    // GC não pode coletar: auditLog (root) → req (vivo)
}
```

`auditLog` é uma GC Root (variável estática). Todos os objetos `Request` adicionados são eternamente alcançáveis — o GC não os coletará mesmo que nunca sejam lidos novamente. Isso é um **memory leak lógico**.

---

## 🧩 Quiz de Fixação

1. Um objeto tem 3 referências de outros objetos apontando para ele, mas nenhuma GC Root. Ele é coletado?
2. Dois objetos se referenciam mutuamente mas são inacessíveis por qualquer GC Root. Serão coletados?
3. Por que variáveis estáticas são GC Roots problemáticas?

**Respostas:**
1) Sim. O que determina a coleta é a alcançabilidade a partir de GC Roots — não o número de referências entre objetos. Sem caminho de uma root, o objeto é inacessível e coletável.
2) Sim (exceto em Reference Counting puro como Python — que precisa do cycle detector). Mark-and-sweep e algoritmos de tracejamento encontram que não há caminho de root para eles e os coletam.
3) Variáveis estáticas existem durante toda a vida da aplicação. Qualquer objeto alcançado a partir delas nunca será coletado — mesmo que nunca mais seja usado. São a causa mais comum de memory leaks lógicos em caches estáticos e singletons mal projetados.
