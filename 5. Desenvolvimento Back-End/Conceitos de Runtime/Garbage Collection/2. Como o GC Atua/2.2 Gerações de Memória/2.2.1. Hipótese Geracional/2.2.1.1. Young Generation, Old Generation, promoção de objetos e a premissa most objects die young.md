### Hipótese Geracional

A maioria dos coletores modernos é **geracional** — dividem o heap por "idade" dos objetos. Essa estratégia é fundamentada em uma observação empírica amplamente verificada sobre o comportamento de programas reais.

---

## A hipótese

> **"Most objects die young"** — a grande maioria dos objetos tem vida curtíssima.

Em uma API REST típica:
- Um DTO criado durante o parsing de uma requisição dura milissegundos
- Um objeto de resposta é criado, serializado e descartado
- Iteradores, streams, builders — criados e mortos no mesmo método

Essa realidade levou ao design geracional: **colete frequentemente onde os objetos morrem rápido, e raramente onde ficam os de longa duração**.

---

## Estrutura do heap geracional

```
┌────────────────────────────────────────────────────────────┐
│                    YOUNG GENERATION                        │
│  ┌─────────────┐  ┌──────────────┐  ┌──────────────┐      │
│  │    Eden     │  │  Survivor S0 │  │  Survivor S1 │      │
│  │  (alocação) │  │              │  │              │      │
│  └─────────────┘  └──────────────┘  └──────────────┘      │
├────────────────────────────────────────────────────────────┤
│                    OLD GENERATION                          │
│         (objetos que sobreviveram múltiplas coletas)       │
├────────────────────────────────────────────────────────────┤
│                    METASPACE (Java 8+)                     │
│         (metadados de classes, fora do heap principal)     │
└────────────────────────────────────────────────────────────┘
```

---

## O ciclo de vida de um objeto

```
1. Objeto criado → vai para Eden
2. Minor GC ocorre:
   - Objetos mortos em Eden → descartados
   - Objetos vivos → copiados para Survivor S0
3. Próximo Minor GC:
   - Objetos vivos em S0 → copiados para S1 (age +1)
4. Após N sobrevivências (tenuring threshold padrão = 15):
   - Objeto promovido para Old Generation
5. Old coletada muito menos frequentemente
```

---

## Por que essa divisão é eficiente

| Sem divisão geracional | Com divisão geracional |
|----------------------|----------------------|
| Cada GC varre o heap inteiro | Minor GC varre só Young (~20% do heap) |
| Pausas longas e frequentes | Pausas curtas e frequentes + raras longas |

---

## Problema: promoção prematura

Se o Young Generation é muito pequeno, objetos morrem no Old em vez do Young — enchem o Old, causando Major GCs desnecessários:

```
[GC (Allocation Failure)]     → Minor GC normal
[Full GC (Promotion Failed)]  → objeto não coube no Old durante promoção
```

## 🧩 Quiz de Fixação

1. Por que Minor GC é muito mais frequente que Major GC?
2. O que acontece com um objeto que sobrevive ao tenuring threshold?
3. O que é promoção prematura e por que é problemática?

**Respostas:**
1) O Young Generation enche rapidamente (todos os novos objetos vão para ali) e é pequeno — satura com frequência. O Old só recebe objetos promovidos, cresce lentamente.
2) É promovido para a Old Generation — passa a ser coletado com muito menos frequência, ocupando espaço por mais tempo.
3) Promoção prematura ocorre quando o Young é tão pequeno que objetos de curta duração são promovidos antes de morrer. O Old fica cheio de objetos temporários, causando Major GCs frequentes que deveriam ser raros.
