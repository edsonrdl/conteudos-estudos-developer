### Quando o GC é Acionado

O GC não roda em intervalos fixos — ele é acionado por eventos específicos ligados ao estado da memória. Entender esses gatilhos explica por que aplicações têm picos de latência inesperados.

---

## Gatilhos principais

| Gatilho | O que acontece |
|---------|---------------|
| **Saturação do Young Generation (Eden)** | Espaço de objetos novos encheu → Minor GC disparado |
| **Promoção excessiva para Old Generation** | Muitos objetos sobrevivem ao Young GC → pressão no Old → Major GC |
| **Heap próximo do limite** | JVM/CLR detecta que o heap está quase cheio → Full GC |
| **Falha de alocação** | Tentativa de alocar objeto mas não há espaço → GC de emergência |
| **Chamada explícita** | `System.gc()` (Java) / `GC.Collect()` (.NET) — hint, não garantia |

---

## O fluxo de alocação

```
new Objeto() chamado
      ↓
Tentativa de alocar no Eden (Young Generation)
      ↓
Eden tem espaço?
  ├── SIM → aloca ali, continua
  └── NÃO → dispara Minor GC
            ↓
        Objetos vivos movidos para Survivor Space
        Objetos que sobrevivem N coletas → promovidos para Old Generation
            ↓
        Old Generation ficou muito cheia?
          ├── NÃO → execução continua
          └── SIM → Major GC ou Full GC
```

---

## Pressão de memória

**Pressão de memória** é o estado em que o runtime está alocando objetos mais rápido do que o GC consegue limpar. Sintomas:

```
CPU do GC: 40%+ → GC está trabalhando demais
Heap usage: oscila entre 90-100% → pouco espaço livre entre coletas
Tempo entre GCs: muito curto (< 1s) → objetos sendo criados e mortos em rajadas
```

Em microservices Java com alta carga, uma API que cria muitos DTOs por requisição pode gerar centenas de Minor GCs por minuto — cada um com uma pausa de alguns milissegundos.

---

## Heap sizing e o impacto nos gatilhos

```
# JVM: heap pequeno → GC frequente, pausas curtas
java -Xms256m -Xmx512m MinApp

# JVM: heap grande → GC raro, pausas longas (mais para varrer)
java -Xms4g -Xmx8g AppServidor
```

O tamanho do heap não elimina o GC — apenas muda a frequência e duração das coletas. Heap muito grande com Full GC pode causar pausas de vários segundos.

## 🧩 Quiz de Fixação

1. O GC roda em intervalos de tempo fixos (ex: a cada 30 segundos)?
2. O que é "pressão de memória" e como ela afeta a aplicação?
3. Chamar `System.gc()` garante que o GC vai rodar?

**Respostas:**
1) Não. O GC é acionado por eventos de alocação e esgotamento de espaço — não por timers. Em aplicações com pouca alocação, o GC pode não rodar por minutos.
2) Pressão de memória é o estado em que a taxa de alocação supera a capacidade do GC de limpar. Resulta em GCs cada vez mais frequentes, alta CPU do GC e potencialmente em Full GC bloqueante.
3) Não. `System.gc()` é uma sugestão ao runtime — a JVM pode ignorá-la. É considerado má prática em produção pois pode forçar Full GC desnecessário.
