### Tipos de Coleta — Minor, Major e Full GC

Não existe um único tipo de coleta. Os runtimes modernos dividem o heap em regiões e coletam cada região com estratégias e frequências diferentes.

---

## Os três tipos

| Tipo | Região afetada | Frequência | Duração típica | Pausa |
|------|---------------|-----------|----------------|-------|
| **Minor GC** | Young Generation (Eden + Survivors) | Alta (segundos a minutos) | Milissegundos | Curta |
| **Major GC** | Old Generation | Baixa | Dezenas a centenas de ms | Média/longa |
| **Full GC** | Heap inteiro (Young + Old + Metaspace) | Rara (idealmente) | Centenas de ms a segundos | Longa |

---

## Minor GC — o mais comum

```
Eden Space [████████████ cheio]
      ↓
Minor GC dispara
      ↓
Objetos vivos copiados para Survivor Space S1
Objetos mortos descartados (a maioria — "most objects die young")
Eden limpo
      ↓
Objetos que sobrevivem N minor GCs → promovidos para Old Generation
```

**Características:**
- Muito rápido porque só examina uma fração do heap
- Pausa é proporcional ao número de objetos **vivos** no Young (não ao número de mortos)
- Quanto mais objetos de curta duração, melhor — morrem antes de ser promovidos

---

## Major GC — coleta do Old

Ocorre quando a Old Generation está pressurizada. Objetos no Old sobreviveram várias coletas — são poucos, mas grandes ou de vida longa:

```
Casos comuns de objetos no Old Generation:
- Cache em memória
- Sessões de usuário
- Objetos de configuração
- Pools de conexão
- Entidades JPA carregadas
```

**Características:**
- Mais lento que Minor (Old é maior, tem mais para varrer)
- Alguns coletores (G1, ZGC) fazem Major GC concorrentemente — pausa mínima
- CMS (deprecado) e Parallel GC param a aplicação completamente

---

## Full GC — o mais temido

Um Full GC varre **todo o heap** de uma vez. Causas comuns:

```
1. Heap 100% cheio — não há mais onde alocar
2. Promoção falhou — Old Generation sem espaço para receber do Young
3. Metaspace cheio — classes não conseguem ser carregadas
4. System.gc() chamado explicitamente
5. Heap muito fragmentado — compactação necessária
```

**Impacto:** Em aplicações Java com heap de 8GB, um Full GC pode levar **vários segundos** de pausa — para todos os threads da aplicação.

```
Linha do tempo durante Full GC:
  t=0ms   → requisição chega
  t=1ms   → Full GC dispara, STW inicia
  t=4500ms→ Full GC termina, STW encerra
  t=4501ms→ requisição finalmente processada
  → timeout de 4.5s para o cliente
```

---

## Como evitar Full GC

- Heap corretamente dimensionado (não muito cheio, não superdimensionado)
- Evitar objetos de vida longa desnecessários (caches sem expiração)
- Escolher um coletor de baixa pausa (G1, ZGC, Shenandoah para Java)
- Monitorar `gc.log` para detectar padrões de promoção excessiva

---

## 🧩 Quiz de Fixação

1. Por que Minor GC é rápido mesmo sendo frequente?
2. O que provoca promoção de objetos para Old Generation?
3. Por que Full GC é especialmente problemático em serviços web?

**Respostas:**
1) Porque examina apenas o Young Generation (pequeno) e a maioria dos objetos ali já morreu — pouco trabalho de varredura e cópia.
2) Objetos que sobrevivem a um número configurável de Minor GCs são promovidos para Old Generation. Objetos alocados grandes demais para o Eden também vão direto para Old.
3) Durante um Full GC, o runtime para todas as threads de aplicação (STW). Requisições HTTP em andamento ficam suspensas, causando timeouts para os clientes — impacto visível e direto na disponibilidade.
