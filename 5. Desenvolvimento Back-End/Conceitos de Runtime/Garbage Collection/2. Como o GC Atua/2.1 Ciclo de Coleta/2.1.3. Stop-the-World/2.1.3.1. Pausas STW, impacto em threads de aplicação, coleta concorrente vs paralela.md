### Stop-the-World (STW)

Stop-the-World é o mecanismo pelo qual o runtime **pausa todas as threads de aplicação** para que o GC possa operar em um estado consistente do heap. É a principal fonte de latência introduzida pelo GC.

---

## Por que o STW existe

O GC precisa analisar o grafo de referências do heap. Se threads de aplicação continuassem modificando objetos durante a coleta, o grafo estaria em constante mutação — o GC poderia:
- Marcar como morto um objeto que outra thread está prestes a usar
- Perder referências criadas depois do início da varredura
- Calcular incorretamente a alcançabilidade

Para garantir consistência, o runtime força um **safe point** — um momento onde todas as threads chegam a um estado seguro e param.

---

## O impacto

```
Thread 1 (requisição HTTP): processando requisição do usuário
Thread 2 (outra requisição): também processando
Thread 3 (GC): ativa

STW event:
  → Thread 1: para imediatamente no safe point
  → Thread 2: para imediatamente no safe point
  → GC coleta: faz seu trabalho
  → STW termina: threads 1 e 2 retomam

Para o usuário:
  → requisição levou 150ms a mais sem motivo aparente
  → é o STW do GC
```

---

## Paralelo vs Concorrente vs STW puro

| Modo | O que significa | Pausa |
|------|----------------|-------|
| **Serial** | GC roda em 1 thread, aplicação para | STW completa |
| **Parallel** | GC usa múltiplas threads, mas aplicação ainda para | STW completa, mas mais rápida |
| **Concurrent** | GC roda junto com a aplicação (a maioria do trabalho) | STW muito curta (só fases críticas) |
| **Incremental** | GC divide o trabalho em pequenas fatias intercaladas com a aplicação | Pausas curtas e previsíveis |

**Coletores modernos de baixa pausa** (G1, ZGC, Shenandoah, .NET GC em Server mode) fazem a maior parte do trabalho de forma **concorrente** — apenas fases muito curtas exigem STW:

```
ZGC (Java):
  Pausa STW típica: < 1ms
  (independente do tamanho do heap)

G1 GC (Java):
  Pausa STW típica: 10–200ms (configurável via -XX:MaxGCPauseMillis)

Parallel GC (Java, old):
  Pausa STW: pode ser segundos em heaps grandes
```

---

## Safe points

O runtime não para as threads em qualquer instrução — espera que cheguem a um **safe point**: um ponto no código onde o estado da thread é bem-definido e pode ser inspecionado com segurança (ex: entre bytecodes Java, entre instruções JIT).

Se uma thread está em um loop longo sem safe points, a STW pode demorar mais para iniciar — chamado de **safe point bias**.

## 🧩 Quiz de Fixação

1. Por que o GC não pode rodar completamente concorrente sem nenhuma pausa?
2. Qual a diferença entre GC paralelo e GC concorrente?
3. Por que ZGC é preferido para sistemas com SLA de baixa latência?

**Respostas:**
1) Algumas fases (como o "initial mark" e "remark") precisam de uma visão consistente do heap — não podem tolerar modificações simultâneas pelas threads da aplicação. Essas fases precisam de STW, mesmo que brevíssimo.
2) Paralelo: usa múltiplas threads de GC mas ainda para a aplicação (STW). Concorrente: o GC trabalha ao mesmo tempo que a aplicação, minimizando ou eliminando pausas longas.
3) ZGC mantém pausas STW abaixo de 1ms independente do tamanho do heap (mesmo em heaps de terabytes). Sistemas com SLAs de latência de milissegundos não podem tolerar pausas de dezenas ou centenas de ms do G1 ou Parallel GC.
