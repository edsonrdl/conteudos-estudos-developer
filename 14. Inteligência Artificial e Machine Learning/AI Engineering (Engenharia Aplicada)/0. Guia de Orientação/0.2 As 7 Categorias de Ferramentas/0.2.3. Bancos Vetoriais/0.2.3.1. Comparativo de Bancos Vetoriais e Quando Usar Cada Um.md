### Comparativo de Bancos Vetoriais e Quando Usar Cada Um

Depois do LLM (0.2.1.1) e do framework de orquestração (0.2.2.1), a terceira peça essencial do quebra-cabeça é onde guardar o conhecimento que o sistema vai consultar. Essa é a 4ª responsabilidade do diagrama de 0.1.1.1: o **Banco Vetorial**, a "memória de longo prazo" do sistema.

---

## O papel do banco vetorial: memória pesquisável por significado

**Analogia:** um banco de dados relacional tradicional (como o MySQL ou o PostgreSQL puro) é como um arquivo organizado por etiquetas exatas — você encontra rapidamente "o contrato número 4521", mas não consegue perguntar "me mostre contratos parecidos com esse aqui, mesmo que não usem as mesmas palavras". Um banco vetorial resolve exatamente esse segundo tipo de busca: ele guarda embeddings (vetores numéricos que representam o *significado* de um texto, gerados pela etapa de Embedding do pipeline) e permite encontrar os vetores mais **semanticamente próximos** de uma consulta, mesmo que as palavras exatas sejam diferentes.

```
Busca tradicional (por palavra-chave exata):
  "cancelamento de contrato" → só encontra documentos que
                                 contêm literalmente essas palavras

Busca vetorial (por significado):
  "cancelamento de contrato" → encontra também documentos que
                                 falam em "rescisão", "término
                                 antecipado do acordo", mesmo sem
                                 nenhuma palavra em comum
```

## Comparativo dos principais bancos vetoriais

| Banco | Ponto forte | Quando usar |
|---|---|---|
| Qdrant | Boa performance, filtros avançados, código aberto | Produção em geral — opção popular no mercado atual |
| Pinecone | Totalmente gerenciado (serverless) | Quando não se quer administrar infraestrutura própria |
| Weaviate | Busca híbrida nativa, API em GraphQL | Projetos com necessidades de busca mais complexas |
| Milvus | Escala massiva (bilhões de vetores) | Big data, empresas com volume muito grande de dados |
| Chroma | Simplicidade, fácil uso local | Prototipagem, projetos pequenos, aprendizado |
| PGVector | Extensão de vetores para quem já usa PostgreSQL | Infraestrutura já existente em Postgres |

## O critério mais importante: gerenciado vs. autogerenciado

Além das diferenças técnicas de performance e recursos, a decisão mais impactante na prática costuma ser operacional: quem vai manter esse banco de dados rodando, escalando e sendo monitorado?

```
┌─────────────────────────────────────────────────────┐
│  GERENCIADO (ex: Pinecone)                              │
│                                                          │
│  Vantagem: zero esforço de infraestrutura — só           │
│            consumir a API                                │
│  Custo: pagamento recorrente ao provedor,                │
│         menos controle sobre a infraestrutura            │
└─────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────┐
│  AUTOGERENCIADO (ex: Qdrant, Milvus, Chroma, PGVector)   │
│                                                          │
│  Vantagem: controle total, sem dependência de um          │
│            provedor externo, custo previsível             │
│  Custo: exige que o time opere, escale e monitore          │
│         a própria infraestrutura                          │
└─────────────────────────────────────────────────────┘
```

Essa decisão é similar à escolha entre um LLM open-source local e um LLM via API (vista em 0.2.1.1) — a mesma lógica de "quem paga com dinheiro" vs. "quem paga com esforço de engenharia" se repete aqui.

## Um caso especial: PGVector, quando a infraestrutura já existe

O PGVector merece destaque separado por resolver um problema de adoção específico: times que já operam um banco PostgreSQL em produção podem adicionar capacidade de busca vetorial **sem introduzir um novo sistema de banco de dados** na infraestrutura. Isso reduz drasticamente a complexidade operacional de um primeiro experimento com RAG, mesmo que, em escalas muito grandes, um banco vetorial dedicado (Qdrant, Milvus) tenda a performar melhor.

| Cenário | Recomendação |
|---|---|
| Já opera PostgreSQL e quer testar RAG rapidamente | PGVector — menor fricção de adoção |
| Volume de vetores muito grande (dezenas de milhões+) e performance é crítica | Um banco vetorial dedicado (Qdrant, Milvus) |
| Aprendizado e prototipagem local | Chroma — simplicidade acima de tudo |
| Não quer operar infraestrutura própria | Pinecone (ou equivalente gerenciado) |

## Quando usar cada um e limitações

**Quando priorizar simplicidade (Chroma):**
- Fase de aprendizado ou prova de conceito, onde o objetivo é validar a ideia de RAG rapidamente, sem se preocupar ainda com escala ou infraestrutura de produção.

**Quando priorizar controle e performance (Qdrant, Milvus):**
- Sistemas em produção com volume real de usuários, onde filtros avançados de busca e desempenho em escala já são requisitos concretos, não hipotéticos.

**Quando priorizar zero esforço operacional (Pinecone):**
- Times pequenos ou sem experiência em operar infraestrutura de banco de dados, onde o custo adicional do serviço gerenciado compensa o tempo de engenharia economizado.

**Limitações:**
- **A escolha do banco vetorial raramente é a decisão mais impactante na qualidade do RAG**: escolher entre Qdrant e Pinecone importa menos, para a qualidade final das respostas, do que a qualidade do chunking (Domínio 2) e do modelo de embedding usado (0.2.6.1) — um erro comum é gastar tempo demais comparando bancos vetoriais e pouco tempo refinando essas outras etapas.
- **Migrar de banco vetorial depois de um sistema já em produção tem custo real**: exige reprocessar (reindexar) toda a base de vetores existente, o que pode ser demorado e custoso para bases muito grandes — vale escolher com alguma folga de escala desde o início, se o crescimento do projeto já é previsível.
- **"Escala massiva" é relativo**: a maioria dos projetos nunca chega perto do volume de dados que justificaria a complexidade adicional de um banco como Milvus — escolher a ferramenta certa para o tamanho real do problema, não para um cenário hipotético de escala extrema, evita complexidade desnecessária.

## 🧩 Quiz de Fixação

1. Qual é a diferença fundamental entre uma busca por palavra-chave exata (banco de dados tradicional) e uma busca vetorial semântica?
2. Por que o PGVector costuma ser uma boa escolha para um primeiro experimento de RAG em uma empresa que já usa PostgreSQL, mesmo que não seja a opção de melhor performance em escala massiva?
3. Por que a escolha entre Qdrant e Pinecone costuma ter menos impacto na qualidade final das respostas de um sistema RAG do que a escolha do modelo de embedding ou da estratégia de chunking?

**Respostas:**
1) Uma busca por palavra-chave exata encontra apenas documentos que contêm literalmente os termos usados na consulta, exigindo que o vocabulário da pergunta coincida com o vocabulário do documento. Uma busca vetorial semântica compara o *significado* representado nos embeddings da consulta e dos documentos, permitindo encontrar conteúdo relevante mesmo quando as palavras exatas são diferentes — por exemplo, encontrando documentos sobre "rescisão contratual" ao buscar por "cancelamento de contrato".
2) Porque o PGVector permite adicionar capacidade de busca vetorial a um banco de dados PostgreSQL que a empresa já opera e já sabe administrar, evitando a necessidade de introduzir e aprender a operar um novo sistema de banco de dados dedicado só para validar a ideia de RAG. Essa redução de fricção operacional costuma valer mais, numa fase inicial de experimentação, do que o ganho de performance que um banco vetorial dedicado ofereceria em escalas muito grandes — que o projeto talvez nunca alcance.
3) Porque a qualidade final das respostas de um sistema RAG depende principalmente de o sistema conseguir recuperar os trechos de texto certos e relevantes — e isso é determinado majoritariamente por como o texto foi dividido em chunks (Domínio 2) e pela qualidade do modelo de embedding usado para representar o significado desses chunks (0.2.6.1). O banco vetorial é responsável por armazenar e buscar esses vetores de forma eficiente, mas não influencia diretamente a qualidade semântica da representação ou da divisão do conteúdo — diferenças de banco vetorial afetam principalmente performance e custo operacional, não a relevância do que é recuperado.
