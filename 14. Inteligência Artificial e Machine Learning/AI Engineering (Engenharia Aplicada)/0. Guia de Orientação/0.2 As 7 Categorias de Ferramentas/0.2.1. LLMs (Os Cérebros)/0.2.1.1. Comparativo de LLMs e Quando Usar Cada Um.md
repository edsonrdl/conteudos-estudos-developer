### Comparativo de LLMs e Quando Usar Cada Um

A primeira das 7 responsabilidades mapeadas em 0.1.1.1 que vale detalhar é o próprio **LLM** — a peça que recebe texto, "pensa" e devolve texto. É natural começar por aqui: é a categoria mais visível e mais discutida do ecossistema, mas também a mais sujeita a decisões precipitadas ("vou usar o modelo mais famoso") em vez de decisões baseadas no problema real a resolver.

---

## O papel do LLM dentro do sistema

**Analogia:** se o sistema de IA inteiro fosse uma empresa de consultoria, o LLM seria o consultor sênior que efetivamente analisa a informação reunida e escreve o parecer final. Ele não é quem coleta os documentos (isso é Extração), não é quem organiza o arquivo da empresa (Banco Vetorial), e não é quem decide qual documento trazer para a reunião (Retrieval) — ele é quem, recebendo tudo isso pronto, produz o raciocínio e a resposta.

Um princípio fundamental que orienta toda a escolha de LLM: **um LLM não sabe o que aconteceu depois do fim do seu treinamento**. Ele não tem acesso a fatos novos, dados privados da empresa, ou eventos recentes — por isso, sistemas reais quase sempre combinam o LLM com RAG (Domínio 2), que injeta esse conhecimento externo no momento da consulta.

## Comparativo dos principais LLMs

| Modelo | Ponto forte | Quando usar |
|---|---|---|
| GPT-4o / o3 (OpenAI) | Raciocínio geral, forte integração com o ecossistema OpenAI | Tarefas complexas, geração e revisão de código |
| Claude (Anthropic) | Contexto longo, forte aderência a instruções detalhadas | Documentos extensos, análise cuidadosa, tarefas que exigem seguir regras precisas |
| Gemini (Google) | Contexto muito extenso, multimodalidade nativa | Vídeos, áudio, documentos muito grandes |
| Llama / DeepSeek | Open-source, pode rodar localmente | Privacidade de dados, eliminação de custo por chamada de API |
| Mistral / Qwen | Eficiência computacional, forte suporte multilíngue | Aplicações voltadas a mercados europeus/asiáticos |
| Phi / Gemma | Modelos pequenos, mas com boa qualidade | Dispositivos de borda (edge), mobile, IoT |
| Cohere | Especializado em recuperação e busca corporativa | Sistemas RAG de uso empresarial |

## Os quatro critérios que realmente deveriam guiar a escolha

Em vez de escolher um LLM pela popularidade do nome, a prática de Engenharia de IA Aplicada recomenda avaliar quatro dimensões concretas:

```
┌─────────────────────────────────────────────────────────┐
│  1. CAPACIDADE DE RACIOCÍNIO                                │
│     A tarefa exige lógica complexa, matemática, planejamento?│
│     → favorece modelos de raciocínio mais fortes             │
│                                                              │
│  2. TAMANHO DE CONTEXTO NECESSÁRIO                           │
│     Preciso processar documentos grandes de uma vez?         │
│     → favorece modelos com janela de contexto ampla          │
│                                                              │
│  3. CUSTO E LATÊNCIA                                          │
│     Quantas chamadas por dia? Qual a tolerância de espera?    │
│     → favorece modelos menores/mais baratos quando possível  │
│                                                              │
│  4. PRIVACIDADE E SOBERANIA DE DADOS                          │
│     Os dados podem sair da infraestrutura da empresa?         │
│     → favorece modelos open-source rodando localmente        │
└─────────────────────────────────────────────────────────┘
```

Um erro comum é escolher, por exemplo, o modelo com maior janela de contexto do mercado para uma tarefa que processa mensagens curtas de chat — pagando por uma capacidade que nunca será usada, enquanto um modelo mais barato e mais rápido resolveria o mesmo problema igualmente bem.

## Por que raramente existe "o melhor LLM", apenas "o LLM certo para esta tarefa"

Um sistema de IA maduro em produção frequentemente usa **mais de um LLM ao mesmo tempo**, cada um para uma responsabilidade diferente — essa é, inclusive, a ideia central por trás do LLM Routing e Cascading, que será aprofundado no Domínio 7 (LLMOps):

```
Pergunta do usuário
        │
        ▼
  Classificador de complexidade
        │
   ┌────┴────┐
   ▼         ▼
Pergunta    Pergunta
 simples     complexa
   │           │
   ▼           ▼
Modelo       Modelo
barato/      poderoso/
rápido       mais caro
(ex: modelo  (ex: modelo
 pequeno)     de raciocínio)
```

Essa mistura de modelos — um mais barato para tarefas simples, um mais caro para tarefas que realmente exigem — é uma das formas mais eficazes de controlar custo em sistemas de IA que atendem alto volume de usuários, sem sacrificar qualidade nas tarefas que de fato precisam de mais capacidade.

## Quando usar cada categoria e limitações

**Quando faz sentido usar um modelo proprietário via API (GPT, Claude, Gemini):**
- Times pequenos que não querem/podem operar infraestrutura de GPU própria.
- Tarefas que se beneficiam diretamente do estado da arte em capacidade de raciocínio.
- Produtos onde o custo por chamada de API ainda é pequeno comparado ao valor gerado por resposta.

**Quando faz sentido usar um modelo open-source local (Llama, Mistral, Phi):**
- Requisitos regulatórios ou contratuais que impedem enviar dados sensíveis para uma API de terceiros.
- Volume de chamadas alto o suficiente para que o custo de infraestrutura própria compense o custo por chamada de uma API paga.
- Aplicações em dispositivos com conectividade limitada ou que precisam funcionar offline (edge, IoT).

**Limitações:**
- **O "melhor" modelo muda com muita frequência**: este ecossistema evolui rápido o suficiente para que qualquer tabela comparativa fique desatualizada em poucos meses — o critério de decisão (as quatro dimensões acima) é mais durável do que qualquer ranking específico de modelos.
- **Modelos maiores nem sempre produzem melhores resultados para uma tarefa específica**: um modelo pequeno bem ajustado (via prompt bem escrito ou fine-tuning, Domínio 6) pode superar um modelo genérico muito maior em uma tarefa estreita e bem definida.
- **Trocar de modelo não é sempre trivial**: prompts otimizados para o comportamento específico de um modelo podem se comportar de forma diferente em outro — mudar de fornecedor de LLM geralmente exige reavaliar (e às vezes reescrever) prompts e reexecutar a avaliação sistemática (Domínio 7) antes de ir para produção.

## 🧩 Quiz de Fixação

1. Por que a afirmação "LLMs não sabem o que aconteceu depois do treinamento deles" é uma das razões centrais para a existência do RAG?
2. Quais são as quatro dimensões recomendadas para escolher um LLM, em vez de escolher pelo nome mais popular do momento?
3. Por que um sistema de IA em produção pode se beneficiar de usar mais de um LLM diferente ao mesmo tempo, em vez de um único modelo para todas as tarefas?

**Respostas:**
1) Porque o conhecimento de um LLM está congelado no momento em que seu treinamento foi concluído — ele não tem acesso automático a fatos novos, eventos recentes ou dados privados de uma empresa específica. O RAG resolve exatamente essa limitação, buscando informação externa e atualizada no momento da consulta e injetando-a no contexto da pergunta, permitindo que o modelo responda com base em conhecimento que ele nunca "viu" durante o treinamento.
2) As quatro dimensões são: capacidade de raciocínio necessária para a tarefa (lógica complexa vs. tarefas simples), tamanho de contexto necessário (documentos grandes vs. mensagens curtas), custo e latência tolerável (volume de chamadas e tempo de resposta aceitável), e privacidade/soberania de dados (se os dados podem ou não sair da infraestrutura da empresa). Avaliar essas dimensões concretas evita pagar por capacidades que a tarefa não precisa, ou escolher um modelo inadequado só por popularidade.
3) Porque diferentes tarefas dentro do mesmo sistema têm exigências muito diferentes de capacidade e custo — perguntas simples podem ser respondidas igualmente bem por um modelo pequeno e barato, enquanto perguntas complexas se beneficiam de um modelo mais poderoso (e mais caro). Rotear cada pergunta para o modelo mais apropriado (uma prática chamada LLM Routing, aprofundada no Domínio 7) permite controlar custos em escala, sem sacrificar qualidade nas tarefas que realmente exigem mais capacidade de raciocínio.
