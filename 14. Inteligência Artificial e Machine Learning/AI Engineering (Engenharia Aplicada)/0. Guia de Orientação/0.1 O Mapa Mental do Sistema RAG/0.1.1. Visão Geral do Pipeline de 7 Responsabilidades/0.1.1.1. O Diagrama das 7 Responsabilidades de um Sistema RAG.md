### O Diagrama das 7 Responsabilidades de um Sistema RAG

Antes de mergulhar em qualquer técnica específica de RAG, Agentes ou LLMOps, este glossário abre com um domínio de orientação — a pergunta mais comum de quem está começando em Engenharia de IA Aplicada não é "como funciona o Chain-of-Thought", é **"qual ferramenta eu uso para quê, e como elas se encaixam?"**. Este primeiro arquivo responde isso com um mapa mental único.

---

## O problema: dezenas de ferramentas, nenhum mapa

Quem começa a estudar construção de sistemas de IA em produção rapidamente esbarra em uma lista assustadora de nomes — LangChain, LlamaIndex, Qdrant, Pinecone, Docling, Ragas, CrewAI, LangGraph — sem nenhuma indicação clara de **onde**, no fluxo de um sistema real, cada uma dessas ferramentas entra. O resultado é confusão: alguém pode achar que LangChain e Qdrant são "concorrentes" (não são — resolvem problemas completamente diferentes) ou que Docling substitui o LangChain (também não — um extrai texto de documentos, o outro orquestra o fluxo inteiro).

**Analogia:** pense em uma linha de produção de uma fábrica de automóveis. Ninguém confunde a máquina que estampa a lataria com a esteira que transporta as peças, mesmo que as duas sejam "máquinas da fábrica" — cada uma tem uma responsabilidade fixa na linha de montagem, e entender o processo completo exige saber a ordem em que as responsabilidades acontecem, não apenas conhecer cada máquina isoladamente. Um sistema de IA em produção tem exatamente esse tipo de linha de montagem — só que trabalhando com texto em vez de metal.

---

## O diagrama: 7 responsabilidades, em sequência

Um sistema de IA em produção — mais especificamente, um sistema que usa RAG (Retrieval-Augmented Generation, que veremos em profundidade no Domínio 2) — pode ser dividido em exatamente **7 responsabilidades distintas**, cada uma resolvida por uma categoria diferente de ferramenta:

```
[DADOS BRUTOS] → Extração → Chunking → Embedding → [BANCO VETORIAL]
                                                           │
                                                           ▼
[USUÁRIO] → Pergunta → Framework → LLM ← Retrieval ← [BUSCA]
                                    │
                              [RESPOSTA]
                                    │
                             [AVALIAÇÃO / OBSERVABILIDADE]
```

Cada seta nesse diagrama representa uma transformação de dados, e cada caixa representa uma responsabilidade que, na prática, é resolvida por uma ferramenta especializada diferente:

| # | Responsabilidade | O que acontece | Categoria de ferramenta (aprofundada em 0.2) |
|---|---|---|---|
| 1 | **Extração** | Dados brutos (PDFs, sites, planilhas) viram texto limpo | Ferramentas de extração (Crawl4AI, Docling, LlamaParse...) |
| 2 | **Chunking** | O texto extraído é dividido em pedaços menores e gerenciáveis | Parte da lógica do framework de orquestração ou de bibliotecas dedicadas |
| 3 | **Embedding** | Cada pedaço de texto é convertido em um vetor numérico | Modelos de embedding (OpenAI, Voyage AI, SBERT...) |
| 4 | **Banco Vetorial** | Os vetores são armazenados de forma pesquisável | Bancos vetoriais (Qdrant, Pinecone, Weaviate...) |
| 5 | **Framework** | Orquestra o fluxo inteiro: recebe a pergunta, busca, monta o prompt | Frameworks de orquestração (LangChain, LlamaIndex...) |
| 6 | **LLM** | Recebe a pergunta + os trechos recuperados e gera a resposta final | Os modelos de linguagem em si (GPT, Claude, Gemini...) |
| 7 | **Avaliação** | Mede, de forma sistemática, se as respostas geradas são boas | Ferramentas de avaliação (Ragas, DeepEval, Giskard...) |

---

## Por que separar em exatamente essas 7 partes

A divisão não é arbitrária — ela reflete uma regra prática valiosa: **cada uma dessas responsabilidades pode ser trocada de ferramenta de forma independente das outras**, desde que a interface entre elas seja respeitada. Trocar o banco vetorial de Chroma para Qdrant não deveria exigir reescrever a lógica de extração de dados; trocar o LLM de GPT-4o para Claude não deveria exigir refazer o pipeline de chunking.

```
Extração ──► Chunking ──► Embedding ──► Banco Vetorial ──► Framework ──► LLM ──► Avaliação
   │              │             │              │                │           │         │
   ▼              ▼             ▼              ▼                ▼           ▼         ▼
Docling,      lógica do     OpenAI,         Qdrant,          LangChain,   GPT-4o,   Ragas,
LlamaParse,   framework/    Voyage,         Pinecone,        LlamaIndex   Claude,   DeepEval,
Crawl4AI...   bibliotecas   SBERT...        Weaviate...                  Gemini... Giskard...
              dedicadas

Cada bloco pode ser substituído isoladamente, contanto que a
"interface" entre os blocos (formato de dado esperado) seja mantida.
```

Isso é, na prática, o mesmo princípio de separação de responsabilidades que aparece em arquitetura de software tradicional (cada componente com uma única razão para mudar) — aplicado à construção de sistemas de IA.

---

## O fluxo em duas fases: Ingestão (offline) e Consulta (online)

Um detalhe frequentemente confuso para quem está começando: as 7 responsabilidades não acontecem todas ao mesmo tempo, para cada pergunta do usuário. Elas se dividem em duas fases com ritmos completamente diferentes:

```
FASE DE INGESTÃO (offline, acontece uma vez, ou periodicamente)
────────────────────────────────────────────────────────────────
[DADOS BRUTOS] → Extração → Chunking → Embedding → [BANCO VETORIAL]

   Executada quando novos documentos chegam. Pode levar minutos
   ou horas para uma base de documentos grande. NÃO acontece a
   cada pergunta do usuário.


FASE DE CONSULTA (online, acontece a cada pergunta do usuário)
────────────────────────────────────────────────────────────────
[USUÁRIO] → Pergunta → Framework → LLM ← Retrieval ← [BUSCA]
                              │
                        [RESPOSTA]

   Executada em tempo real, a cada pergunta. Precisa ser rápida
   (segundos, não minutos) — o banco vetorial já está pronto e
   populado pela fase de ingestão.
```

A **Avaliação** (7ª responsabilidade) normalmente roda de forma separada das duas — tanto durante o desenvolvimento (validando mudanças antes de ir para produção) quanto de forma contínua, amostrando conversas reais já ocorridas, como veremos em profundidade no Domínio 7 (LLMOps).

## Quando esse mapa mental é mais útil, e suas limitações

**Quando usar esse mapa mental:**
- Ao avaliar uma nova ferramenta desconhecida — a primeira pergunta a fazer é "em qual das 7 responsabilidades essa ferramenta se encaixa?", o que já elimina boa parte da confusão inicial.
- Ao montar a arquitetura de um novo sistema de IA do zero — desenhar as 7 caixas primeiro, e só depois escolher a ferramenta específica para cada uma, evita a armadilha de escolher uma ferramenta "porque é popular" sem saber exatamente que responsabilidade ela cobre.
- Ao debugar um sistema com problemas — isolar em qual das 7 etapas o problema está acontecendo (resposta ruim porque o chunking cortou informação no meio? porque o embedding não capturou o significado certo? porque o LLM alucinou apesar do contexto correto?) direciona a investigação.

**Limitações do modelo:**
- **Nem todo sistema de IA usa RAG**: sistemas que dependem só de fine-tuning (Domínio 6) ou que fazem tarefas sem necessidade de busca em uma base de conhecimento (um simples chatbot conversacional, por exemplo) não passam por todas essas 7 etapas — o diagrama é específico para sistemas com recuperação de informação.
- **Sistemas agênticos (Domínio 4) adicionam complexidade além dessas 7 caixas**: um agente que usa ferramentas, planeja múltiplos passos e coordena outros agentes tem responsabilidades adicionais (orquestração, memória, verificação) que este diagrama simplificado não cobre — ele é o ponto de partida, não o mapa completo do glossário inteiro.
- **As fronteiras entre as caixas nem sempre são tão nítidas na prática**: alguns frameworks (como o LlamaIndex) oferecem funcionalidades que cobrem múltiplas responsabilidades ao mesmo tempo (chunking + embedding + orquestração, por exemplo) — o diagrama ajuda a entender conceitualmente, mas a implementação real às vezes combina responsabilidades numa única biblioteca.

## 🧩 Quiz de Fixação

1. Por que a fase de Ingestão (Extração → Chunking → Embedding → Banco Vetorial) roda separadamente e com ritmo diferente da fase de Consulta (Framework → LLM → Resposta)?
2. Se um desenvolvedor quer trocar o banco vetorial do sistema de Chroma para Qdrant, por que essa troca, em teoria, não deveria exigir mudanças na etapa de Extração de dados?
3. Diante de um sistema RAG que está devolvendo respostas incompletas, como o mapa das 7 responsabilidades ajuda a direcionar a investigação do problema?

**Respostas:**
1) Porque elas têm propósitos e volumes de trabalho completamente diferentes: a fase de Ingestão processa a base de documentos inteira (que pode ser grande) e não precisa ser instantânea, já que só acontece quando novos dados chegam — pode levar minutos ou horas sem problema. Já a fase de Consulta acontece a cada pergunta feita por um usuário em tempo real, e por isso precisa ser rápida (segundos) — ela não reprocessa os documentos, apenas consulta o banco vetorial que a fase de Ingestão já deixou pronto.
2) Porque, seguindo o princípio de separação de responsabilidades do diagrama, cada uma das 7 etapas deveria poder ser trocada de forma isolada, desde que a "interface" entre elas seja respeitada — no caso do banco vetorial, isso significa que ele continua recebendo os mesmos vetores gerados pela etapa de Embedding. A etapa de Extração de dados lida com um problema completamente anterior e diferente (transformar documentos brutos em texto limpo), sem nenhuma dependência de qual banco vetorial será usado depois.
3) O mapa permite isolar sistematicamente em qual das 7 etapas o problema provavelmente está ocorrendo: a resposta incompleta pode ser causada por um chunking que cortou informação relevante no meio de um pedaço (etapa de Chunking), por um embedding que não capturou bem o significado da pergunta (etapa de Embedding), por uma busca que não recuperou os trechos certos (etapa de Banco Vetorial/Retrieval), ou pelo próprio LLM ignorando parte do contexto fornecido (etapa do LLM). Em vez de tentar adivinhar a causa olhando só a resposta final, o mapa direciona a investigação para verificar cada etapa isoladamente.
