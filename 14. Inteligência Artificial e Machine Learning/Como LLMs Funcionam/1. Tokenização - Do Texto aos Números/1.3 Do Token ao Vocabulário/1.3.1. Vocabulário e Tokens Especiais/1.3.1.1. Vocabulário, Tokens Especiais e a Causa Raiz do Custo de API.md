### Vocabulário, Tokens Especiais e a Causa Raiz do Custo de API

Com BPE, WordPiece e SentencePiece explicados (1.2.1.1, 1.2.2.1), este arquivo fecha o Domínio 1 mostrando o que sobra ao final do treino de um tokenizador: um vocabulário fixo, incluindo tokens que não representam texto nenhum.

---

## O vocabulário final

O conjunto final de todos os tokens possíveis, após o algoritmo de fusão (BPE, WordPiece ou Unigram) terminar, é o **vocabulário** do modelo. Um exemplo real: o tokenizador `cl100k_base`, usado por modelos da OpenAI, tem **100.256 tokens** no seu vocabulário — um número fixo, decidido no momento em que o tokenizador foi treinado, e que não muda depois (mesmo que o modelo continue evoluindo).

```
Vocabulário do tokenizador (tamanho fixo)
┌─────────────────────────────────────────┐
│  ID 0:      "!"                          │
│  ID 1:      "\""                         │
│  ...                                     │
│  ID 4521:   " gato"                      │
│  ...                                     │
│  ID 100255: <|endoftext|>                │
└─────────────────────────────────────────┘

Cada token do texto de entrada é mapeado para um desses IDs.
Um token fora desse conjunto simplesmente não existe para o modelo.
```

---

## Tokens especiais: IDs que não são texto

Além dos tokens que representam pedaços de texto real, todo vocabulário reserva **tokens especiais** — símbolos que controlam a estrutura da conversa ou o comportamento do modelo, não o conteúdo:

| Token especial | Papel |
|---|---|
| `<\|endoftext\|>` | Sinaliza o fim de uma geração — o modelo "aprende" a produzir esse token quando termina de responder |
| `<\|pad\|>` | Token de preenchimento, usado para igualar o tamanho de sequências diferentes durante o treinamento em lote |
| `<\|system\|>`, `<\|user\|>`, `<\|assistant\|>` | Delimitam papéis dentro de uma conversa de chat, permitindo ao modelo distinguir "isto foi dito pelo sistema" de "isto foi dito pelo usuário" |

Esses tokens especiais são parte do vocabulário como qualquer outro — cada um tem um ID numérico — mas nunca aparecem como texto visível para quem lê a conversa; eles existem para estruturar a entrada de forma que o modelo entenda os limites entre instruções, pergunta do usuário e resposta.

---

## Por que isso é a causa raiz do custo de API

Cada token — seja uma subpalavra de texto real ou um token especial — consome espaço no **orçamento total de tokens** de uma requisição a um LLM. Isso conecta diretamente com três conceitos tratados em profundidade do lado aplicado deste guia:

| Conceito aplicado | Por que a mecânica de tokenização o explica |
|---|---|
| **Custo por token (input/output)** | APIs de LLM cobram por token processado — a contagem de tokens de um texto é decidida exatamente pelo algoritmo de tokenização (Domínio 1.2), não pelo número de caracteres ou palavras |
| **Context Window (limite de contexto)** | O limite de "quantos tokens cabem" em uma conversa é um limite sobre a sequência de IDs que o modelo processa de uma vez — mais tokens especiais e subpalavras consomem esse orçamento mais rápido |
| **Compressão de prompt (ex: LLMLingua)** | Técnicas de compressão de prompt funcionam removendo ou reescrevendo texto para reduzir a **contagem de tokens** resultante, sem perder o significado essencial |

---

## Erro comum: estimar custo por caracteres, não por tokens

Um erro frequente é assumir que dois textos de tamanho parecido em caracteres terão custo de API parecido. Isso não é verdade: um texto em português com muitos acentos e uma pontuação incomum pode gerar mais tokens que um texto equivalente em inglês, porque o vocabulário do tokenizador foi treinado com uma distribuição de idiomas que nem sempre favorece igualmente todas as línguas.

## 🧩 Quiz de Fixação

1. O que diferencia um "token especial" de um token comum de texto, dentro do vocabulário de um tokenizador?
2. Por que o tamanho do vocabulário de um tokenizador (como os 100.256 tokens do `cl100k_base`) é fixo, e não muda com o tempo mesmo que o modelo continue sendo atualizado?
3. Por que estimar o custo de uma requisição de API contando caracteres, em vez de tokens, pode levar a estimativas erradas?

**Respostas:**
1) Um token especial não representa um pedaço de texto legível — ele é um símbolo de controle, usado para marcar estrutura (fim de geração, preenchimento, delimitação de papéis em uma conversa). Um token comum representa uma subpalavra real que, combinada com outros tokens, reconstrói o texto visível. Ambos têm um ID numérico no vocabulário, mas cumprem papéis completamente diferentes.
2) Porque o vocabulário é definido durante o **treinamento do tokenizador**, um processo separado (e geralmente anterior) ao treinamento do modelo de linguagem em si. Uma vez que esse vocabulário é fixado, ele se torna parte da "interface" do modelo — mudar o vocabulário exigiria retreinar ou pelo menos reajustar o modelo inteiro, então na prática ele permanece fixo durante toda a vida útil daquela versão do modelo.
3) Porque a contagem de tokens não tem uma relação fixa com o número de caracteres — ela depende de quais subpalavras aquele texto específico gera, de acordo com o vocabulário do tokenizador. Um texto com muitos acentos, palavras raras ou de um idioma menos representado no treinamento do tokenizador pode gerar significativamente mais tokens do que um texto de tamanho parecido em caracteres, mas em um idioma ou vocabulário mais "eficiente" para aquele tokenizador específico.
