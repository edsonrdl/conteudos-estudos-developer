### Boas Práticas de Instrumentação: Onde e Quando Medir

O arquivo anterior (2.1.1.1) definiu o que é um SLI e quais famílias de métrica costumam servir de base para ele. Mas a fórmula "eventos bons / eventos totais" só produz um número confiável se a **instrumentação** — o ponto exato de onde o dado é coletado, e a janela de tempo sobre a qual ele é calculado — for escolhida com cuidado. Dois times medindo "a mesma" disponibilidade de formas diferentes podem chegar a números completamente diferentes, e só um deles reflete o que o usuário realmente vive.

---

## Onde medir: do lado do servidor ou do lado do cliente

A decisão mais importante de instrumentação é **onde**, na jornada de uma requisição, o dado é coletado. Existem, no mínimo, três pontos possíveis, cada um mais próximo — ou mais distante — da experiência real do usuário.

```
Usuário ──► Rede ──► Load Balancer ──► Servidor de Aplicação ──► Banco de Dados
   │                        │                    │
   │                        │                    │
   ▼                        ▼                    ▼
[medição no             [medição no          [medição no
 cliente/browser]        Load Balancer]       Servidor de App]

  MAIS PRÓXIMO                                  MAIS DISTANTE
  da experiência real                           da experiência real
  do usuário                                    do usuário
```

**Analogia:** imagine medir a satisfação de clientes de um restaurante perguntando ao garçom "como você acha que os clientes estão se sentindo?" versus entregar uma pesquisa de satisfação real para cada cliente preencher ao sair. O garçom (o servidor de aplicação) tem uma visão, mas filtrada pela sua própria posição — ele não vê o tempo que o cliente esperou na fila da porta, nem a demora para conseguir estacionar. A pesquisa entregue diretamente ao cliente (medição no lado do cliente) captura a experiência completa, "de ponta a ponta".

### Medição no servidor de aplicação

É a forma mais comum e mais fácil de implementar — o próprio código da aplicação (ou um middleware/interceptor) registra o tempo de início e fim de cada requisição, e se ela terminou com sucesso ou erro.

```python
# Exemplo simplificado de middleware que registra o SLI no servidor
import time

async def sli_middleware(request, call_next):
    start = time.monotonic()
    response = await call_next(request)
    duration = time.monotonic() - start

    metrics.record_request(
        status_code=response.status_code,
        duration_seconds=duration,
        endpoint=request.url.path
    )
    return response
```

**Limitação:** essa medição só captura o tempo **a partir do momento em que a requisição chega ao servidor**. Ela não enxerga o tempo de rede entre o usuário e o servidor, nem problemas de DNS, nem lentidão do lado do cliente (um JavaScript pesado demorando para renderizar a resposta, por exemplo).

### Medição no cliente (Real User Monitoring — RUM)

Instrumenta o próprio código que roda no navegador ou aplicativo do usuário, medindo o tempo desde que a requisição foi disparada até que a resposta foi de fato recebida e processada pelo cliente.

```javascript
// Exemplo simplificado de RUM no navegador
const start = performance.now();

fetch('/api/produtos')
  .then(response => {
    const duration = performance.now() - start;
    enviarMetrica({
      endpoint: '/api/produtos',
      duration_ms: duration,
      status: response.status
    });
    return response.json();
  });
```

Essa abordagem captura a experiência **completa**, incluindo latência de rede, DNS, TLS handshake — tudo que o usuário de fato espera. É mais fiel à realidade, mas mais complexa de implementar e de agregar (dados vêm de milhares de dispositivos diferentes, com condições de rede variadas).

### Medição no Load Balancer / API Gateway

Um meio-termo: captura tempo de rede a partir do ponto de entrada da infraestrutura (mais próximo do usuário que o servidor de aplicação, mas ainda não é o cliente real). Muito usada porque a maioria dos Load Balancers e API Gateways já expõe essas métricas nativamente, sem exigir código adicional na aplicação.

---

## Comparativo dos pontos de medição

| Ponto de medição | O que captura | O que NÃO captura | Complexidade de implementar |
|---|---|---|---|
| Servidor de aplicação | Tempo de processamento interno, erros de negócio | Latência de rede, DNS, tempo do lado do cliente | Baixa — geralmente um middleware simples |
| Load Balancer / Gateway | Tempo de rede interno + processamento do backend | Latência entre o usuário final e a borda da infraestrutura | Baixa — geralmente já vem pronto na ferramenta |
| Cliente (RUM) | Experiência completa e real do usuário, ponta a ponta | Nada relevante para a experiência — é a visão mais completa | Alta — requer instrumentação no frontend/app e agregação de dados variados |

## Quando medir: a janela de tempo

A segunda decisão crucial é **sobre qual período** o SLI é calculado. A mesma métrica, olhada em janelas diferentes, conta histórias diferentes:

```
Janela de 5 minutos:       ████░░░░░░  (reage rápido, mas ruidosa —
                                          um pico breve derruba o número)

Janela de 1 hora:          ██████░░░░  (equilíbrio comum para dashboards
                                          operacionais)

Janela de 30 dias:         ████████░░  (estável, usada para calcular
                                          o SLO e o Error Budget do período)
```

| Janela | Vantagem | Desvantagem | Uso típico |
|---|---|---|---|
| Curta (1-5 min) | Detecta problemas quase em tempo real | Muito ruidosa — picos breves e normais podem parecer incidentes | Alertas operacionais imediatos |
| Média (1 hora) | Bom equilíbrio entre reatividade e estabilidade | Ainda sensível a picos de tráfego pontuais | Dashboards de monitoramento do dia a dia |
| Longa (7-30 dias) | Estável, reflete tendência real, base confiável para metas | Reage devagar — um problema sério recente pode ainda não aparecer significativamente | Cálculo do SLO e do Error Budget (ver 2.2.1.1 e 2.2.2.1) |

A prática recomendada — e que veremos se repetir quando chegarmos a Multiwindow Multi-burn-rate Alerting (4.2.1.1) — é **usar janelas diferentes para propósitos diferentes**: uma janela curta para alertar a equipe de plantão sobre um problema acontecendo agora, e uma janela longa (geralmente alinhada ao período do SLO, como 30 dias) para avaliar se a meta de confiabilidade do trimestre está sendo cumprida.

## Erro comum: medir "sucesso" de forma otimista demais

Um erro sutil e frequente é considerar como "sucesso" qualquer resposta que não seja um erro técnico explícito — por exemplo, contar uma resposta HTTP `200 OK` como sucesso mesmo quando o corpo da resposta contém um erro de negócio (`{"status": "error", "message": "saldo insuficiente"}`). Se o SLI só olha o código HTTP e ignora o conteúdo semântico da resposta, o sistema pode reportar 99.99% de "disponibilidade" enquanto uma parcela relevante dos usuários está, na prática, recebendo respostas de erro disfarçadas de sucesso técnico.

| Abordagem ingênua | Abordagem correta |
|---|---|
| "Sucesso" = qualquer resposta HTTP 2xx | "Sucesso" = resposta HTTP 2xx **e** ausência de erro de negócio inesperado no corpo da resposta |
| SLI de disponibilidade parece ótimo, mas esconde falhas reais | SLI reflete com mais fidelidade o que o usuário efetivamente experimentou |

## Quando usar cada estratégia e limitações

**Quando priorizar medição no servidor:**
- Fase inicial de adoção de SLIs, onde implementar rápido e obter visibilidade básica importa mais que capturar cada detalhe da experiência do usuário.
- Serviços internos (API-to-API), onde não existe "cliente humano" com navegador — só faz sentido medir no ponto onde a requisição é processada.

**Quando priorizar RUM (medição no cliente):**
- Aplicações web/mobile voltadas ao usuário final, onde a experiência de ponta a ponta (incluindo rede e renderização) é o que realmente importa para o negócio.
- Quando já existem reclamações de "lentidão" que não aparecem nas métricas do servidor — geralmente sinal de que o problema está na rede ou no cliente, não no backend.

**Limitações:**
- **RUM tem amostragem e variabilidade**: dados de milhares de dispositivos com condições de rede muito diferentes (um usuário em fibra óptica, outro em 3G) tornam a agregação mais complexa — normalmente se usa percentis (como já visto em 2.1.1.1) em vez de médias, e às vezes se segmenta por tipo de conexão ou região.
- **Escolher a janela errada distorce decisões**: usar uma janela muito curta para decidir se um SLO trimestral foi cumprido gera decisões precipitadas baseadas em ruído; usar uma janela muito longa para alertar a equipe de plantão significa que um incidente sério pode demorar demais para disparar um alerta.
- **Instrumentação excessiva tem custo**: capturar métricas detalhadas demais, em todos os pontos possíveis, tem custo de armazenamento e processamento — a prática recomendada é instrumentar prioritariamente os SLIs que de fato alimentam um SLO definido, não "medir tudo por precaução".

## 🧩 Quiz de Fixação

1. Por que medir a latência apenas no servidor de aplicação pode subestimar o tempo real que o usuário percebe?
2. Por que a prática recomendada é usar janelas de tempo diferentes para alertas operacionais e para o cálculo do SLO/Error Budget, em vez de uma única janela para tudo?
3. Qual é o problema de considerar toda resposta HTTP `200 OK` como "sucesso" para fins de cálculo de um SLI de disponibilidade?

**Respostas:**
1) Porque a medição no servidor de aplicação só captura o tempo a partir do momento em que a requisição chega ao servidor — ela não enxerga a latência de rede entre o usuário e o servidor, o tempo de resolução de DNS, o handshake TLS, nem o tempo que o cliente (navegador ou aplicativo) leva para processar e renderizar a resposta recebida. Um usuário com conexão lenta pode ter uma experiência ruim mesmo que o servidor responda rapidamente, e essa medição não capturaria esse problema.
2) Porque cada propósito exige um trade-off diferente entre reatividade e estabilidade: uma janela curta (poucos minutos) é ruidosa, mas reage quase em tempo real, o que é essencial para alertar uma equipe de plantão sobre um problema acontecendo agora. Uma janela longa (semanas) é mais estável e reflete a tendência real de confiabilidade ao longo do tempo, o que é necessário para avaliar de forma justa se uma meta de SLO trimestral está sendo cumprida — usar a janela errada em cada contexto geraria alertas tardios demais ou decisões de negócio baseadas em ruído de curto prazo.
3) O problema é que uma resposta pode ter o código HTTP `200 OK` (tecnicamente bem-sucedida do ponto de vista do protocolo) mas conter, no corpo da resposta, um erro de negócio (por exemplo, uma operação rejeitada por regra de negócio). Se o SLI conta essa resposta como "sucesso" só por causa do código HTTP, o número reportado de disponibilidade fica artificialmente otimista, escondendo uma parcela real de usuários que, na prática, não conseguiram completar o que vieram fazer — o SLI deixa de refletir fielmente a experiência do usuário.
