### Ferramentas na Prática: Prometheus, Grafana e Google Cloud SLO Monitoring

Depois de entender a teoria completa da cadeia SLI/SLO/SLA (3.1.1.1), este arquivo mostra como isso é efetivamente implementado com ferramentas reais de observabilidade — do lado open-source (Prometheus + Grafana) e do lado gerenciado por um provedor de nuvem (Google Cloud SLO Monitoring).

---

## A arquitetura geral de implementação

Independentemente da ferramenta escolhida, a implementação prática de SLI/SLO segue sempre o mesmo fluxo de dados:

```
┌───────────────┐      ┌───────────────┐      ┌────────────────┐      ┌──────────────┐
│  Aplicação      │ ──►  │  Coletor de     │ ──►  │  Banco de Séries  │ ──►  │  Dashboard /   │
│  instrumentada   │      │  Métricas         │      │  Temporais         │      │  Alertas         │
│  (expõe /metrics)│      │  (Prometheus)     │      │  (armazena o        │      │  (Grafana /     │
│                  │      │                   │      │   histórico de SLI) │      │   Alertmanager) │
└───────────────┘      └───────────────┘      └────────────────┘      └──────────────┘
```

A aplicação expõe métricas brutas (contadores de requisições, histogramas de latência); uma ferramenta coleta e armazena essas métricas ao longo do tempo; e, por cima desse histórico, se calculam os SLIs, se comparam contra os SLOs, e se disparam alertas quando necessário.

## Prometheus: instrumentando e coletando os SLIs

O Prometheus é a ferramenta open-source mais usada para coletar métricas no formato de séries temporais. A aplicação expõe um endpoint HTTP (geralmente `/metrics`) e o Prometheus periodicamente "puxa" (scrape) esses dados.

```python
# Exemplo em Python com a biblioteca prometheus_client
from prometheus_client import Counter, Histogram

REQUEST_COUNT = Counter(
    'http_requests_total',
    'Total de requisições HTTP',
    ['method', 'endpoint', 'status']
)

REQUEST_LATENCY = Histogram(
    'http_request_duration_seconds',
    'Duração das requisições HTTP',
    ['method', 'endpoint'],
    buckets=[0.05, 0.1, 0.2, 0.3, 0.5, 1.0, 2.0, 5.0]
)

@app.middleware("http")
async def instrument_requests(request, call_next):
    with REQUEST_LATENCY.labels(request.method, request.url.path).time():
        response = await call_next(request)
    REQUEST_COUNT.labels(request.method, request.url.path, response.status_code).inc()
    return response
```

A partir dessas métricas brutas, o SLI de disponibilidade e o SLI de latência (p95) podem ser calculados usando **PromQL**, a linguagem de consulta do Prometheus:

```promql
# SLI de disponibilidade: proporção de requisições SEM erro 5xx, na última hora
sum(rate(http_requests_total{status!~"5.."}[1h]))
/
sum(rate(http_requests_total[1h]))

# SLI de latência: percentual de requisições respondidas em até 300ms, na última hora
histogram_quantile(0.95, rate(http_request_duration_seconds_bucket[1h])) < 0.3
```

A primeira consulta soma a taxa de requisições sem erro e divide pela taxa total — exatamente a fórmula de SLI vista em 2.1.1.1 (eventos bons / eventos totais). A segunda usa `histogram_quantile` para calcular o p95 de latência a partir dos "buckets" do histograma definido na instrumentação.

## Grafana: visualizando SLO e Error Budget

O Grafana consome os dados armazenados pelo Prometheus (ou outras fontes) e constrói dashboards visuais. Um dashboard típico de SLO mostra, lado a lado:

```
┌─────────────────────────────────────────────────────────┐
│  SLO: Disponibilidade ≥ 99.9% (janela de 30 dias)            │
│                                                              │
│  SLI atual:        99.94%   ████████████████████████░░       │
│  Error Budget:      60% restante   (25,9 de 43,2 min)         │
│                                                              │
│  ┌──────────────────────────────────────────────────┐     │
│  │  Gráfico: consumo do Error Budget ao longo do mês    │     │
│  │  100% ┤                                              │     │
│  │   75% ┤          ╭──╮                                │     │
│  │   50% ┤ ╭────────╯  ╰──╮                             │     │
│  │   25% ┤─╯               ╰───────────────             │     │
│  │    0% └────────────────────────────────────► tempo    │     │
│  └──────────────────────────────────────────────────┘     │
└─────────────────────────────────────────────────────────┘
```

Esse tipo de painel é o que os papéis descritos em 3.1.1.1 (engenheiro de plantão, tech lead) consultam no dia a dia — ele transforma os números abstratos de SLI/SLO/Error Budget em uma visão imediata e compartilhada do "quanto de risco ainda temos disponível este mês".

## Google Cloud SLO Monitoring: a versão gerenciada

Provedores de nuvem como o Google Cloud oferecem um recurso nativo (Cloud Monitoring SLO) que abstrai boa parte da configuração manual de PromQL, permitindo definir o SLO diretamente em uma interface declarativa (ou via API/Terraform):

```yaml
# Exemplo simplificado de definição de SLO via Terraform no Google Cloud
resource "google_monitoring_slo" "availability_slo" {
  service      = google_monitoring_service.meu_servico.service_id
  display_name = "Disponibilidade - 99.9% em 30 dias"

  goal                = 0.999
  rolling_period_days = 30

  request_based_sli {
    good_total_ratio {
      good_service_filter  = "metric.type=\"loadbalancing.googleapis.com/https/request_count\" AND metric.labels.response_code_class=\"200\""
      total_service_filter = "metric.type=\"loadbalancing.googleapis.com/https/request_count\""
    }
  }
}
```

A vantagem dessa abordagem gerenciada é que o provedor já cuida de calcular o Error Budget automaticamente, exibir os dashboards e integrar diretamente com o sistema de alertas da própria plataforma — reduzindo a quantidade de PromQL customizado que a equipe precisa manter.

## Comparativo entre as abordagens

| Aspecto | Prometheus + Grafana (open-source) | Google Cloud SLO Monitoring (gerenciado) |
|---|---|---|
| Controle sobre a instrumentação | Total — a equipe define métricas, buckets, labels | Depende de métricas já expostas pela infraestrutura do provedor |
| Curva de aprendizado | Mais alta — exige aprender PromQL e configurar dashboards manualmente | Mais baixa — configuração declarativa, cálculo de Error Budget automático |
| Portabilidade | Alta — funciona em qualquer infraestrutura (on-premise, multi-cloud) | Atrelado ao provedor de nuvem específico |
| Custo operacional | Exige manter e escalar a própria infraestrutura de monitoramento | Custo embutido no provedor, sem infraestrutura própria para manter |
| Flexibilidade de SLIs customizados | Muito alta — qualquer métrica exposta pode virar um SLI | Depende do que o provedor já expõe nativamente, ou de métricas customizadas enviadas manualmente |

---

## Quando usar cada abordagem e limitações

**Quando usar Prometheus + Grafana:**
- Ambientes multi-cloud, on-premise ou híbridos, onde não existe um único provedor de nuvem centralizando a infraestrutura.
- Equipes que já têm expertise em observabilidade open-source e valorizam controle total sobre a instrumentação e as consultas.
- SLIs muito customizados, específicos do domínio de negócio, que não se encaixam bem em métricas de infraestrutura padrão de um provedor.

**Quando usar uma solução gerenciada (Google Cloud SLO Monitoring ou equivalentes de outros provedores):**
- Equipes menores, sem capacidade dedicada para operar e manter uma stack de observabilidade própria.
- Sistemas já fortemente integrados a um único provedor de nuvem, onde as métricas de infraestrutura relevantes já são nativamente expostas.
- Quando o cálculo automático de Error Budget e a integração pronta com alertas (aprofundado em 4.2.1.1) economizam tempo de engenharia significativo.

**Limitações:**
- **Ferramentas não substituem a disciplina de definição de SLI/SLO**: nenhuma ferramenta escolhe, por conta própria, qual é o SLI relevante ou qual deveria ser o SLO — isso continua sendo uma decisão humana baseada em dados (2.2.1.1), independentemente da ferramenta usada para implementar.
- **Métricas mal instrumentadas geram dashboards enganosos**: um painel bonito no Grafana, alimentado por um SLI mal definido (por exemplo, contando erro 4xx como falha do sistema, ver 2.1.1.2), só vai exibir um número impreciso de forma mais visualmente convincente.
- **Soluções gerenciadas têm menos flexibilidade para SLIs muito específicos do negócio**: métricas como "porcentagem de pedidos processados com sucesso end-to-end", que exigem lógica de negócio customizada, geralmente são mais fáceis de implementar com instrumentação própria (Prometheus) do que dentro dos limites de uma ferramenta gerenciada genérica.

## 🧩 Quiz de Fixação

1. Na consulta PromQL de disponibilidade (`sum(rate(http_requests_total{status!~"5.."}[1h])) / sum(rate(http_requests_total[1h]))`), o que cada uma das duas partes da divisão representa, e como isso se relaciona com a fórmula de SLI vista em 2.1.1.1?
2. Qual é a principal vantagem prática de usar uma solução gerenciada como o Google Cloud SLO Monitoring em vez de configurar tudo manualmente com Prometheus e Grafana?
3. Por que um dashboard bem construído no Grafana não é suficiente, por si só, para garantir que a organização está medindo confiabilidade de forma correta?

**Respostas:**
1) A parte do numerador (`sum(rate(http_requests_total{status!~"5.."}[1h]))`) soma a taxa de requisições que NÃO tiveram erro 5xx (os "eventos bons") na última hora; a parte do denominador (`sum(rate(http_requests_total[1h]))`) soma a taxa de todas as requisições (os "eventos totais") no mesmo período. Essa divisão implementa exatamente a fórmula de SLI vista em 2.1.1.1 — eventos bons dividido por eventos totais —, calculada de forma contínua e automatizada a partir dos dados coletados pelo Prometheus.
2) A principal vantagem é que a solução gerenciada já cuida automaticamente do cálculo do Error Budget e da integração com o sistema de alertas da própria plataforma, reduzindo a quantidade de consultas PromQL customizadas e configuração manual que a equipe precisaria construir e manter por conta própria — trocando controle e flexibilidade por menor esforço operacional.
3) Porque um dashboard só é tão confiável quanto os dados que ele exibe — se o SLI subjacente foi mal definido (por exemplo, contando respostas de erro de negócio como sucesso técnico, como discutido em 2.1.1.2) ou se o SLO não tem base em dados históricos reais (2.2.1.1), o dashboard vai apresentar esses números incorretos de forma visualmente convincente, dando uma falsa sensação de confiabilidade bem medida quando, na verdade, o problema está na escolha e definição das métricas, não na ferramenta de visualização.
