### O que é SMTP — fluxo de envio, comandos, relay e portas

SMTP (Simple Mail Transfer Protocol, RFC 5321) é o protocolo responsável pelo **envio** de e-mails. Define como mensagens são roteadas e entregues entre servidores de e-mail através da internet. Enquanto IMAP e POP3 lidam com a **leitura** de e-mails pelo usuário final, SMTP é usado em dois contextos: pelo cliente de e-mail para enviar ao servidor de saída, e entre servidores de e-mail para rotear mensagens até o destino.

---

## Arquitetura do sistema de e-mail

```
Fluxo completo de um e-mail: joao@gmail.com → maria@empresa.com

1. João compõe e clica "Enviar" no Gmail
   
2. Cliente Gmail → SMTP Google (smtp.gmail.com:587)
   "Envie este e-mail"
   
3. SMTP Google (MTA sender) → consulta DNS MX de empresa.com
   "Para onde devo entregar e-mail de empresa.com?"
   DNS MX: mail.empresa.com (10) → IP 203.0.113.5
   
4. SMTP Google → SMTP empresa.com:25 (MTA receiver)
   Entrega o e-mail diretamente ao servidor da empresa
   
5. Servidor da empresa armazena o e-mail no mailbox de Maria
   (em formato Maildir ou mbox)
   
6. Maria abre o Outlook, que conecta via IMAP a mail.empresa.com
   e baixa o e-mail para leitura

Siglas:
  MUA: Mail User Agent (cliente do usuário: Gmail, Outlook, Thunderbird)
  MTA: Mail Transfer Agent (servidor SMTP que roteia: Postfix, Sendmail)
  MDA: Mail Delivery Agent (entrega no mailbox: Dovecot, Procmail)
  MSA: Mail Submission Agent (recebe do cliente: porta 587)
```

## Comandos SMTP

Uma sessão SMTP é uma conversa de texto entre cliente e servidor — legível por humanos:

```
Conexão estabelecida:
  Servidor: 220 mail.empresa.com ESMTP Postfix (Ubuntu)

Cliente: EHLO meu-servidor.com
  → Apresentação estendida (ESMTP) com hostname do remetente
  → HELO = versão antiga sem extensões
  
Servidor:
  250-mail.empresa.com
  250-PIPELINING
  250-SIZE 52428800          ← tamanho máximo de mensagem (50 MB)
  250-STARTTLS               ← suporte a TLS
  250-AUTH PLAIN LOGIN       ← métodos de autenticação
  250 8BITMIME               ← suporte a UTF-8

Cliente: STARTTLS
  → Negociar TLS neste canal (STARTTLS upgrade)
  Servidor: 220 Go ahead
  [TLS handshake — tudo a seguir é criptografado]

Cliente: AUTH LOGIN
  Servidor: 334 VXNlcm5hbWU6  (base64 "Username:")
  Cliente: am9hbw==           (base64 "joao")
  Servidor: 334 UGFzc3dvcmQ6  (base64 "Password:")
  Cliente: c2VuaGExMjM=       (base64 "senha123")
  Servidor: 235 Authentication successful

Cliente: MAIL FROM:<joao@gmail.com>
  → Envelope sender (pode ser diferente do From: no cabeçalho!)
  Servidor: 250 Ok

Cliente: RCPT TO:<maria@empresa.com>
  → Destinatário (pode ter múltiplos RCPT TO)
  Servidor: 250 Ok

Cliente: RCPT TO:<backup@empresa.com>
  → Segundo destinatário (BCC pode ser feito aqui sem aparecer no cabeçalho)
  Servidor: 250 Ok

Cliente: DATA
  Servidor: 354 End data with <CR><LF>.<CR><LF>
  
  [Corpo da mensagem — headers + body]
  From: João Silva <joao@gmail.com>
  To: Maria Santos <maria@empresa.com>
  Subject: Relatório de Janeiro
  Date: Mon, 15 Jan 2024 10:30:00 +0000
  Message-ID: <abc123@gmail.com>
  MIME-Version: 1.0
  Content-Type: text/plain; charset=utf-8
  
  Olá Maria,
  
  Segue o relatório de janeiro.
  
  Abraços,
  João
  .           ← linha com apenas ponto = fim da mensagem
  
  Servidor: 250 Ok: queued as XYZ123

Cliente: QUIT
  Servidor: 221 Bye
```

## Envelope vs Cabeçalhos — distinção crítica

```
SMTP Envelope (não aparece no e-mail):
  MAIL FROM: joao@gmail.com      ← Return-Path (bounces vão para cá)
  RCPT TO: maria@empresa.com     ← destinatário real de entrega

Cabeçalhos da mensagem (visíveis no e-mail):
  From: João Silva <joao@gmail.com>    ← exibido pelo cliente de e-mail
  To: Maria Santos <maria@empresa.com>
  Cc: pedro@empresa.com
  Bcc: (omitido no cabeçalho, mas RCPT TO na envelope)

Por que isso importa:
  O MAIL FROM (envelope) é usado para bounces e verificações SPF
  O From: (header) é o que o usuário vê
  Um spammer pode colocar From: ceo@empresa.com no header
  mas o MAIL FROM real é spammer@evil.com
  → SPF verifica o MAIL FROM (envelope), não o From: do header
  → DMARC alinha o From: do header com o domínio autenticado
```

## Códigos de resposta SMTP

```
2xx — Sucesso:
  211: System status
  214: Help message
  220: Service ready (banner inicial)
  221: Service closing
  235: Authentication successful
  250: Requested mail action okay, completed
  251: User not local; will forward
  354: Start mail input (resposta ao DATA)

4xx — Erros temporários (tentar novamente):
  421: Service not available (tente mais tarde)
  450: Mailbox unavailable (temporariamente ocupado)
  451: Requested action aborted: local error in processing
  452: Too many recipients / Insuficient system storage

5xx — Erros permanentes (não tentar novamente):
  500: Syntax error, command unrecognized
  501: Syntax error in parameters
  503: Bad sequence of commands
  530: Authentication required
  535: Authentication credentials invalid
  550: User unknown / Mailbox unavailable / Policy rejection
  551: User not local
  552: Storage allocation exceeded
  553: Mailbox name not allowed
  554: Transaction failed (spam, blacklist)
  
Importante:
  4xx: servidor de envio deve tentar novamente (filas SMTP)
  5xx: bounce definitivo (notificar remetente que e-mail não foi entregue)
```

## Relay SMTP — como o e-mail é roteado

```
Relay = um servidor SMTP que aceita e encaminha e-mails para outro servidor

Tipos de relay:

1. Open Relay (proibido na internet moderna):
   Aceita e-mails de QUALQUER remetente para QUALQUER destinatário
   → Usado por spammers para enviar e-mail anônimo
   → Servidores configurados assim são imediatamente bloqueados em blacklists
   
2. Closed Relay (correto):
   Aceita e-mails apenas de:
   a. Usuários autenticados (SMTP AUTH) para qualquer destino
   b. Rede interna (IP autorizado) para qualquer destino
   
3. MX Record relay:
   Aceita e-mails de qualquer servidor para @empresa.com (domínio local)
   Rejeita e-mails para outros domínios (evita ser usado como relay)

Verificando se um servidor é open relay:
  telnet mail.servidor.com 25
  EHLO teste.com
  MAIL FROM:<fake@ninguem.com>
  RCPT TO:<qualquer@gmail.com>
  → 250: OPEN RELAY! Servidor aceita qualquer destino
  → 550 Relay access denied: correto, não é open relay
```

## Portas SMTP — 25, 465 e 587

```
Porta 25 — SMTP entre servidores (MTA to MTA):
  Uso: comunicação entre servidores de e-mail na internet
  Autenticação: geralmente não requerida (baseada em IP/DNS)
  TLS: STARTTLS opcional
  
  BLOQUEADA para uso de usuário final:
  → ISPs bloqueiam saída na porta 25 de IPs residenciais
  → Previne que máquinas infectadas enviem spam diretamente
  → Apenas servidores com IP fixo/dedicado usam porta 25

Porta 465 — SMTPS (legado, mas voltou):
  Uso: cliente → servidor de saída (submission) com TLS implícito
  TLS: conecta diretamente em TLS (como HTTPS)
  Autenticação: obrigatória
  
  História: definida informalmente, depois removida de RFCs, depois reintroduzida
  Status atual: amplamente suportada como alternativa segura à 587

Porta 587 — Mail Submission (recomendada):
  Uso: cliente → servidor de saída (MSA)
  TLS: STARTTLS upgrade
  Autenticação: obrigatória (SMTP AUTH)
  Status: porta oficial para envio de e-mail por usuários (RFC 6409)
  
  Recomendada para:
    → Configuração de clientes de e-mail (Outlook, Thunderbird)
    → APIs de envio (código da aplicação)
    → Serviços como Gmail, SendGrid, AWS SES

Resumo de uso:
  Servidor recebendo e-mail externo: porta 25
  Usuário/app enviando e-mail: porta 587 (preferido) ou 465
```

## ESMTP — Extended SMTP

```
ESMTP (RFC 5321) estende o SMTP original com:
  EHLO em vez de HELO: anuncia suporte a extensões
  
  Extensões comuns:
  STARTTLS:   negociar TLS na conexão existente
  AUTH:       autenticação (PLAIN, LOGIN, CRAM-MD5, XOAUTH2)
  SIZE:       anunciar tamanho máximo aceito de mensagem
  8BITMIME:   suporte a UTF-8 no corpo do e-mail
  PIPELINING: enviar múltiplos comandos sem esperar resposta (performance)
  CHUNKING:   enviar mensagens grandes em pedaços (BDAT)
  DSN:        Delivery Status Notifications (bounce reports detalhados)
  SMTPUTF8:   endereços de e-mail com caracteres Unicode (joão@empresa.com)
```

## Enviando e-mail via código

```python
# Python — smtplib com STARTTLS e autenticação
import smtplib
from email.mime.multipart import MIMEMultipart
from email.mime.text import MIMEText
from email.mime.application import MIMEApplication

def enviar_email(destinatario: str, assunto: str, corpo: str, anexo: str = None):
    # Construir a mensagem
    msg = MIMEMultipart()
    msg['From'] = 'joao@empresa.com'
    msg['To'] = destinatario
    msg['Subject'] = assunto
    msg['Message-ID'] = '<' + str(uuid.uuid4()) + '@empresa.com>'
    
    # Corpo em texto e HTML
    msg.attach(MIMEText(corpo, 'plain', 'utf-8'))
    msg.attach(MIMEText(f'<html><body>{corpo}</body></html>', 'html', 'utf-8'))
    
    # Anexo opcional
    if anexo:
        with open(anexo, 'rb') as f:
            attachment = MIMEApplication(f.read(), Name=os.path.basename(anexo))
            attachment['Content-Disposition'] = f'attachment; filename="{os.path.basename(anexo)}"'
            msg.attach(attachment)
    
    # Enviar via SMTP com STARTTLS (porta 587)
    with smtplib.SMTP('smtp.empresa.com', 587) as servidor:
        servidor.ehlo()
        servidor.starttls()        # upgrade para TLS
        servidor.ehlo()            # re-identificar após TLS
        servidor.login('joao@empresa.com', 'senha_de_app')
        servidor.send_message(msg)
    
    print(f"E-mail enviado para {destinatario}")

# Para produção: usar variáveis de ambiente para credenciais
# SMTP_HOST, SMTP_PORT, SMTP_USER, SMTP_PASSWORD
```

## Filas SMTP e tratamento de erros

```
SMTP confiável usa filas para lidar com falhas temporárias:

Servidor de envio (Postfix/Sendmail):
  1. Mensagem entra na fila
  2. Tenta entregar imediatamente
  3. Se falhar com 4xx (temporário): tentar novamente
     → 5 min → 30 min → 4h → 8h → 24h (exemplo de backoff)
  4. Se ainda falhar após X dias: gerar NDR (Non-Delivery Report)
     e notificar o remetente
  5. Se falhar com 5xx (permanente): gerar NDR imediatamente

Bounce e NDR:
  → Enviado para o MAIL FROM (Return-Path) original
  → Contém o código de erro e a mensagem de diagnóstico
  → "550 User unknown" → e-mail não existe → limpar da lista

Soft bounce vs Hard bounce:
  Soft bounce (4xx): temporário — manter e tentar novamente
  Hard bounce (5xx): permanente — remover da lista de e-mails
```

## Erros comuns e armadilhas

**MAIL FROM vs From: header:** não são a mesma coisa. MAIL FROM é o envelope usado para bounces e SPF. From: no header é o que o usuário vê. Enviar e-mail transacional com MAIL FROM incorreto quebra SPF e faz bounces irem para o lugar errado.

**Usar porta 25 de IP residencial:** ISPs bloqueiam. Use sempre porta 587 ou 465 com autenticação para envio de aplicação.

**Não implementar retry com backoff:** aplicações que enviam e-mail diretamente (sem fila) e recebem 4xx precisam implementar retry. Apenas jogar a mensagem fora em caso de falha temporária resulta em perda de e-mails.

## 🧩 Quiz de Fixação

1. Uma aplicação envia e-mail com `From: noreply@empresa.com` mas o `MAIL FROM` no envelope SMTP é `app@servidor-compartilhado.com`. Por que isso causa problemas de entregabilidade e como corrigir?

2. Um servidor SMTP retorna `421 Service temporarily unavailable` para uma mensagem. O cliente SMTP descarta a mensagem imediatamente. Qual é o erro e qual seria o comportamento correto?

3. Por que ISPs bloqueiam a porta 25 de saída em IPs residenciais, e como usuários/aplicações em redes residenciais devem configurar o envio de e-mail?

**Respostas:**

1) O `MAIL FROM` (envelope) é o que o SPF verifica: "o servidor enviando tem permissão para enviar e-mail de `app@servidor-compartilhado.com`?". Se o SPF de `servidor-compartilhado.com` não autoriza o IP de envio, ou se `empresa.com` tem DMARC, a mensagem pode ser rejeitada ou marcada como spam. Além disso, bounces (erros de entrega) vão para `app@servidor-compartilhado.com`, não para `noreply@empresa.com` — o remetente real nunca fica sabendo de falhas de entrega. **Correção:** o `MAIL FROM` deve usar um domínio que o servidor tem autorização SPF para enviar, alinhado com o `From:` header (para DMARC passar). Use `MAIL FROM: noreply@empresa.com` e configure o SPF de `empresa.com` para autorizar o IP/servidor de envio.

2) O erro é **descartar a mensagem após um código 4xx**. Códigos 4xx são erros **temporários** — o servidor de destino está temporariamente indisponível mas poderá receber o e-mail mais tarde. O comportamento correto é colocar a mensagem em fila e tentar novamente com backoff exponencial: 5 min, 30 min, 4h, 8h, 24h, etc. Apenas código 5xx (permanente) justifica gerar um bounce imediato. Um sistema de envio que descarta mensagens em 4xx perderá e-mails legítimos toda vez que o servidor de destino tiver instabilidade temporária.

3) ISPs bloqueiam a porta 25 de saída para prevenir que máquinas infectadas por malware (botnets) enviem spam diretamente para servidores de destino na internet. Um computador doméstico comprometido poderia enviar milhões de spams sem passar por nenhum gateway de e-mail rastreável. **Como configurar envio:** usuários e aplicações em redes residenciais (ou qualquer rede sem IP dedicado de servidor) devem usar: (a) o servidor SMTP do ISP ou do provedor de e-mail (Gmail: smtp.gmail.com:587, Office 365: smtp.office365.com:587); (b) um serviço de envio transacional (SendGrid, AWS SES, Mailgun) via porta 587 ou 465 com autenticação; (c) nunca tentar conectar diretamente na porta 25 de servidores externos — será bloqueado tanto pelo ISP quanto pelas blacklists de IP residencial.
