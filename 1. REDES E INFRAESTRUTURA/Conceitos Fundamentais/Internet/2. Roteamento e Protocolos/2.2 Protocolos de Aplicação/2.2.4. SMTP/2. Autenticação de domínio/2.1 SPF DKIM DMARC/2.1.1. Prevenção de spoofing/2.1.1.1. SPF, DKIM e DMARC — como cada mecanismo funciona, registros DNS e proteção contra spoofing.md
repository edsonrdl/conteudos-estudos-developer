### SPF, DKIM e DMARC — autenticação de domínio e proteção contra spoofing

Qualquer pessoa pode enviar um e-mail com `From: ceo@empresa.com` no header — o SMTP original não tem verificação de identidade. SPF, DKIM e DMARC são três mecanismos complementares que, juntos, permitem que servidores de destino verifiquem se um e-mail que diz ser de `empresa.com` foi realmente autorizado pelo proprietário do domínio. Entender cada um e como se complementam é essencial para garantir entregabilidade e proteger a reputação do domínio.

---

## O problema — spoofing de e-mail

```
Sem autenticação de domínio:

1. Atacante envia:
   MAIL FROM: <spoofed@evil.com>       ← envelope (oculto)
   
   Cabeçalho da mensagem:
   From: CEO João Silva <ceo@empresa.com>   ← o que Maria vê!
   To: maria@empresa.com
   Subject: Urgente: Transferência bancária
   
2. Maria vê um e-mail do CEO solicitando transferência
   O e-mail parece legítimo — usa o nome e domínio da empresa
   
3. Maria não tem como saber que veio de evil.com

SPF, DKIM e DMARC resolvem isso de formas diferentes:
  SPF:   "Quais servidores têm permissão para enviar e-mail de empresa.com?"
  DKIM:  "Este e-mail foi assinado digitalmente pela chave de empresa.com?"
  DMARC: "O que fazer se SPF ou DKIM falhar? Bloquear? Quarentena? Reportar?"
```

---

## SPF — Sender Policy Framework

SPF permite que o proprietário do domínio publique quais servidores IP têm autorização para enviar e-mails de seu domínio. O servidor receptor consulta o DNS do domínio do `MAIL FROM` e verifica se o IP de origem está autorizado.

### Registro SPF no DNS

```
Tipo: TXT
Nome: empresa.com (ou _spf.empresa.com para include)
Valor: v=spf1 <mecanismos> <qualificador_padrão>

Exemplo básico:
  v=spf1 mx ip4:203.0.113.0/24 include:sendgrid.net -all

Análise:
  v=spf1               → versão SPF 1
  mx                   → IPs do registro MX de empresa.com também podem enviar
  ip4:203.0.113.0/24   → range de IPs autorizado
  include:sendgrid.net → incluir a política SPF de sendgrid.net
  -all                 → tudo mais = FAIL (bloquear)
```

### Mecanismos SPF

```
all         → Corresponde a qualquer IP (geralmente no final)
ip4:<cidr>  → IPv4 ou range: ip4:203.0.113.5, ip4:203.0.113.0/24
ip6:<cidr>  → IPv6: ip6:2001:db8::/32
a           → IPs do registro A de empresa.com
mx          → IPs dos registros MX de empresa.com
include:<domínio> → Herdar SPF de outro domínio (ex: sendgrid.net, mailchimp.com)
exists:<domínio>  → Lookup DNS customizado (avançado, raro)
ptr:<domínio>     → Verificação reversa DNS (lenta, não recomendada)

Qualificadores (prefixo):
  + (padrão, implícito) → PASS — autorizado
  - → FAIL — não autorizado (bloquear)
  ~ → SOFTFAIL — não autorizado mas aceitar (marcar como spam)
  ? → NEUTRAL — sem política
```

### Resultado da verificação SPF

```
PASS:     IP está na lista → e-mail provavelmente legítimo
FAIL:     IP NÃO está na lista (-all) → bloquear ou marcar como spam
SOFTFAIL: IP NÃO está (~all) → aceitar mas suspeitar
NEUTRAL:  Sem política (?all)
NONE:     Nenhum registro SPF encontrado
PERMERROR: Erro permanente na política (ex: mais de 10 lookups DNS)
TEMPERROR: Erro temporário (DNS indisponível — tentar novamente)
```

### Limitação do SPF — 10 lookups DNS

```
SPF tem limite de 10 lookups DNS durante a avaliação:
  include:, a:, mx:, exists:, ptr: cada um contam

Erro comum:
  v=spf1 include:sendgrid.net include:mailchimp.com include:salesforce.com ...
  
  Se a soma de lookups recursivos passar de 10: PERMERROR
  → Todos os e-mails falham SPF!

Solução:
  → Usar ferramentas como dmarcanalyzer.com para contar lookups
  → Consolidar via serviço de "SPF flattening" (converte includes em IPs)
  → Ou usar subdomínios: marketing.empresa.com para Mailchimp, 
    vendas.empresa.com para Salesforce
```

## DKIM — DomainKeys Identified Mail

DKIM usa criptografia de chave pública para assinar digitalmente partes do e-mail. O servidor remetente assina o e-mail com uma chave privada; o servidor receptor verifica a assinatura com a chave pública publicada no DNS. Se a assinatura é válida, o e-mail não foi modificado em trânsito e foi enviado pelo dono do domínio.

### Como DKIM funciona

```
Servidor remetente (assina):
  1. Seleciona headers a incluir na assinatura:
     From:, To:, Subject:, Date:, Message-ID:, Content-Type:
  
  2. Hash do corpo do e-mail (SHA-256)
  
  3. Assina com chave privada RSA/Ed25519:
     signature = RSA_sign(private_key, hash(selected_headers + body_hash))
  
  4. Adiciona header DKIM-Signature ao e-mail:
     DKIM-Signature: v=1; a=rsa-sha256; c=relaxed/relaxed;
       d=empresa.com; s=selector1; t=1705312800;
       bh=BASE64_DO_HASH_DO_BODY;
       h=From:To:Subject:Date;
       b=BASE64_DA_ASSINATURA

Servidor receptor (verifica):
  1. Lê DKIM-Signature: extrai d= (domínio) e s= (seletor)
  2. Consulta DNS: selector1._domainkey.empresa.com
  3. Obtém chave pública RSA
  4. Verifica assinatura: RSA_verify(public_key, assinatura, headers + body_hash)
  5. Se válida: DKIM PASS — e-mail não foi modificado e foi autorizado
```

### Registro DKIM no DNS

```
Tipo: TXT
Nome: selector1._domainkey.empresa.com
Valor: v=DKIM1; k=rsa; p=MIGfMA0GCSqGSIb3DQEBAQUAA4GNADCBiQKBgQC...

Componentes:
  v=DKIM1           → versão
  k=rsa             → algoritmo da chave (rsa ou ed25519)
  p=<chave_publica> → chave pública em base64
  t=s               → (opcional) modo estrito — sem subdomínios
  s=email           → (opcional) uso apenas para e-mail

Seletor (selector):
  Permite múltiplas chaves DKIM para o mesmo domínio:
  selector1._domainkey.empresa.com → chave atual
  selector2._domainkey.empresa.com → nova chave (rotação)
  mailchimp._domainkey.empresa.com → chave do Mailchimp
  
  Rotação de chaves sem downtime:
  1. Criar selector2 com nova chave
  2. Atualizar servidor para assinar com selector2
  3. Após propagação DNS: desativar selector1
```

### Campos do DKIM-Signature

```
DKIM-Signature: v=1; a=rsa-sha256; c=relaxed/relaxed;
  d=empresa.com;     ← domínio que assinou
  s=selector1;       ← seletor para lookup da chave pública
  t=1705312800;      ← timestamp (Unix epoch)
  x=1705399200;      ← expiração da assinatura (opcional)
  bh=BASE64...;      ← hash do body
  h=From:To:Subject:Date:Message-ID:Content-Type; ← headers assinados
  b=BASE64...        ← assinatura em si

c= (canonicalização):
  relaxed/relaxed: tolera pequenas modificações (espaços, quebras de linha)
  simple/simple:   mais estrito — qualquer mudança invalida a assinatura
  
  Maioria usa relaxed/relaxed: e-mails frequentemente passam por
  sistemas que adicionam trailers, mudam quebras de linha, etc.
```

## DMARC — Domain-based Message Authentication, Reporting and Conformance

DMARC une SPF e DKIM definindo:
1. **Política:** o que fazer quando SPF e/ou DKIM falham
2. **Alinhamento:** o From: header deve estar alinhado com o domínio autenticado
3. **Relatórios:** receber relatórios de servidores sobre autenticação

### O conceito de alinhamento

```
DMARC verifica ALINHAMENTO — o From: header deve bater com o domínio autenticado:

E-mail enviado via Mailchimp para newsletter.empresa.com:
  From: noreply@empresa.com              ← header visível
  MAIL FROM: bounce@mailchimp.com        ← envelope SPF
  DKIM-Signature: d=empresa.com          ← assinado por empresa.com

SPF check: bounce@mailchimp.com → IP do Mailchimp → PASS (para mailchimp.com)
DKIM check: d=empresa.com → assinatura válida → PASS
DMARC alinhamento:
  SPF domain (mailchimp.com) vs From: (empresa.com) → NÃO alinhado
  DKIM domain (empresa.com) vs From: (empresa.com) → ALINHADO ✓
  → DMARC: PASS (basta um mecanismo alinhado)

SPF spoofing sem DMARC:
  MAIL FROM: spf-autorizado@empresa.com → SPF PASS
  From: ceo@empresa.com                 → Não verificado pelo SPF
  → Spoofing passa no SPF mas DMARC exige alinhamento:
    SPF domain (empresa.com) vs From: (empresa.com) → ALINHADO
    Mas o servidor do atacante não tem permissão SPF para empresa.com → SPF FAIL
    → DMARC FAIL
```

### Registro DMARC no DNS

```
Tipo: TXT
Nome: _dmarc.empresa.com
Valor: v=DMARC1; p=reject; rua=mailto:dmarc@empresa.com; ruf=mailto:forensics@empresa.com; pct=100

Análise:
  v=DMARC1     → versão DMARC 1
  p=reject     → política: reject | quarantine | none
  rua=mailto:  → relatórios agregados (diários)
  ruf=mailto:  → relatórios forenses (por mensagem — dados sensíveis)
  pct=100      → % de e-mails sujeitos à política (útil para rollout gradual)
  sp=none      → política para subdomínios (se diferente de p=)
  adkim=r      → alinhamento DKIM: r=relaxed, s=strict
  aspf=r       → alinhamento SPF: r=relaxed, s=strict
```

### Políticas DMARC

```
p=none (monitoramento apenas):
  → Aplicar nenhuma ação — apenas coletar relatórios
  → Ponto de partida: ver como os e-mails estão se saindo sem bloquear nada
  → Riscos: spoofing ainda passa, mas você aprende quem está enviando

p=quarantine (quarentena):
  → E-mails que falham vão para spam/quarentena
  → Passo intermediário de migração

p=reject (bloqueio):
  → E-mails que falham são rejeitados na entrega
  → Proteção máxima — spoofers não conseguem entrar na caixa de entrada
  → Implementar após validar que TODOS os sistemas legítimos passam DMARC

Rollout gradual:
  Mês 1: p=none — monitorar relatórios
  Mês 2: p=quarantine; pct=10 — 10% em quarentena
  Mês 3: p=quarantine; pct=50 → pct=100
  Mês 4: p=reject; pct=10 → pct=100
```

### Relatórios DMARC (RUA)

```
Relatório RUA — Relatório Agregado (XML diário):
  Quem está enviando e-mail com seu domínio:
  - IPs remetentes
  - Quantidade de e-mails por IP
  - Resultado SPF, DKIM, DMARC para cada fonte
  
  Exemplo (simplificado):
  <feedback>
    <date_range>2024-01-15 a 2024-01-15</date_range>
    <record>
      <source_ip>198.51.100.50</source_ip>
      <count>1</count>
      <policy_evaluated>
        <dkim>fail</dkim>
        <spf>fail</spf>
      </policy_evaluated>
    </record>
    <record>
      <source_ip>149.72.173.42</source_ip>  ← sendgrid.net
      <count>2834</count>
      <policy_evaluated>
        <dkim>pass</dkim>
        <spf>pass</spf>
      </policy_evaluated>
    </record>
  </feedback>

Ferramentas para visualizar relatórios DMARC:
  → dmarcanalyzer.com
  → postmarkapp.com/dmarc
  → dmarcian.com
  → Google Postmaster Tools (para domínios com alto volume para Gmail)
```

## Os três mecanismos juntos — visão integrada

```
E-mail chega para verificação:

1. SPF: "O IP 198.51.100.50 está autorizado a enviar de empresa.com?"
   Consulta TXT de empresa.com → v=spf1 ... -all
   IP encontrado? → PASS | FAIL | SOFTFAIL

2. DKIM: "A assinatura d=empresa.com, s=selector1 é válida?"
   Consulta TXT selector1._domainkey.empresa.com → chave pública
   Verifica assinatura → PASS | FAIL | NONE

3. DMARC: "SPF e DKIM estão alinhados com o From: do header?"
   Consulta TXT _dmarc.empresa.com → v=DMARC1; p=reject; ...
   
   Se qualquer mecanismo (SPF ou DKIM) PASS E ALINHADO:
     → DMARC PASS → e-mail entregue normalmente
   
   Se ambos falham ou não estão alinhados:
     → p=none:       entrega + coleta no relatório
     → p=quarantine: vai para spam
     → p=reject:     rejeitado (bounce 550)

Proteção completa:
  SPF protege contra uso não-autorizado de domínio no envelope
  DKIM protege contra modificação em trânsito e valida identidade do remetente
  DMARC alinha os dois com o From: visível e define a política de execução
```

## Erros comuns e armadilhas

**SPF com `-all` mas esquecendo de incluir todos os remetentes:** se o Mailchimp, SendGrid ou qualquer serviço de terceiro enviar e-mail do domínio sem estar no SPF, os e-mails legítimos falham. Antes de mudar para `-all`, verificar TODOS os sistemas que enviam e-mail pelo domínio.

**DMARC `p=none` deixado assim por anos:** o modo de monitoramento é útil para diagnóstico inicial, mas não protege nada. Migrar gradualmente para `quarantine` e `reject` após entender os relatórios.

**Esquecer de incluir IPs de relay interno:** servidores internos que encaminham e-mails (anti-virus, DLP, systems que geram notificações) precisam estar no SPF ou assinar com DKIM.

**DKIM com cabeçalhos críticos não assinados:** não assinar o `From:` header permite que atacantes modifiquem o remetente sem invalidar a assinatura. Sempre incluir `From:, To:, Subject:, Date:, Message-ID:` na lista `h=`.

## 🧩 Quiz de Fixação

1. Uma empresa tem SPF configurado (`v=spf1 include:sendgrid.net -all`) e DMARC com `p=reject`. Um funcionário usa o servidor SMTP interno (IP 203.0.113.50) para enviar e-mail corporativo, mas esse IP não está no SPF. O que acontece e como corrigir sem afetar o SendGrid?

2. Um atacante envia e-mail com `From: ceo@empresa.com` usando um servidor na Europa que não está no SPF de empresa.com. A empresa tem DMARC `p=reject`. O atacante configura um DKIM válido para o próprio domínio do atacante (`d=evil.com`). O DMARC passa?

3. Uma empresa recebe relatório DMARC mostrando que 500 e-mails/dia chegam com o domínio deles no From, vindo de IPs de um provedor de marketing que eles não reconhecem. O que esse relatório indica e quais são as ações possíveis?

**Respostas:**

1) O e-mail do servidor interno falha o SPF (`-all` significa que qualquer IP não listado é FAIL). Com DMARC `p=reject`, o servidor de destino rejeita o e-mail. **Correção:** adicionar o IP interno ao SPF: `v=spf1 ip4:203.0.113.50 include:sendgrid.net -all`. Verificar também se o servidor interno assina com DKIM (idealmente todos os remetentes deveriam assinar). Alternativa: redirecionar o envio interno pelo SendGrid (todos os e-mails passam pelo mesmo caminho autorizado).

2) **Não passa DMARC.** Para o DMARC passar, é necessário que pelo menos um mecanismo (SPF ou DKIM) PASSE E ESTEJA ALINHADO com o From: header. Analisando: (a) SPF: o IP europeu do atacante não está no SPF de `empresa.com` → SPF FAIL; (b) DKIM: o atacante assinou com `d=evil.com` → verificação criptográfica pode passar para evil.com, mas o alinhamento falha porque DKIM domain (`evil.com`) ≠ From: domain (`empresa.com`) → DKIM PASS mas não alinhado; (c) DMARC: nenhum mecanismo passou E estava alinhado → DMARC FAIL → com `p=reject`, o e-mail é rejeitado. Este é exatamente o cenário que DMARC foi projetado para bloquear: a distinção entre a identidade técnica de envio e a identidade visual no From: header.

3) O relatório indica que **alguém está usando o domínio da empresa em e-mails** — pode ser: (a) um provedor de marketing contratado por outro time sem o conhecimento da TI (Shadow IT); (b) um ex-prestador de serviços que ainda tem configuração apontando para o domínio; (c) um atacante fazendo spoofing em larga escala. **Ações possíveis:** (a) investigar internamente quem contratou esse provedor de marketing; (b) se for legítimo: adicionar o provedor ao SPF e configurar DKIM para o domínio; (c) se for spoofing: manter o DMARC `p=reject` (vai bloquear) e opcionalmente contatar o provedor hospedeiro para reportar o abuso; (d) independente da causa: analisar o relatório completo (quais e-mails, para quem, com qual conteúdo) usando as ferramentas DMARC para entender o padrão.
