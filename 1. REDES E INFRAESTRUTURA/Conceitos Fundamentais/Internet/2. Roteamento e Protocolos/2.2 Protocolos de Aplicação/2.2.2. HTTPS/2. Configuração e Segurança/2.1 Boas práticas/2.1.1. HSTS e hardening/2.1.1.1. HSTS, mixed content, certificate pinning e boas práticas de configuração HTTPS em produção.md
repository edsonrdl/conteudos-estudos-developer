### HSTS, mixed content, certificate pinning e boas práticas de configuração HTTPS

Ter HTTPS habilitado é o ponto de partida — configurá-lo corretamente é o que realmente importa para segurança. HSTS garante que conexões HTTP nunca ocorram, mesmo que o usuário tente. Mixed content quebra as garantias do HTTPS quando recursos inseguros são carregados. Certificate Pinning (e sua evolução) previne ataques com certificados legítimos mas mal-intencionados. Este arquivo consolida as práticas essenciais para HTTPS seguro em produção.

---

## HSTS — HTTP Strict Transport Security

HSTS é um header de resposta que instrui o browser a **sempre** usar HTTPS para o domínio, nunca HTTP — por um período definido. Após receber o header, o browser faz o upgrade HTTP→HTTPS automaticamente, antes de enviar qualquer dado pela rede.

> HSTS foi coberto em profundidade no contexto de security headers em [[1. REDES E INFRAESTRUTURA/Conceitos Fundamentais/Internet/2. Roteamento e Protocolos/2.2 Protocolos de Aplicação/2.2.1. HTTP/3. Estrutura da Resposta/3.2 Response Headers/3.2.1. Cabeçalhos de resposta/3.2.1.3. Headers de segurança — CORS, CSP, HSTS, X-Frame-Options, X-Content-Type-Options|3.2.1.3 — Headers de segurança]]. Este arquivo foca nos aspectos de configuração prática e problemas comuns.

```
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
```

### Problemas comuns com HSTS

```
Problema 1 — Subdomínio sem HTTPS com includeSubDomains:
  Você ativou:
  Strict-Transport-Security: max-age=31536000; includeSubDomains
  
  Mas staging.empresa.com não tem certificado HTTPS.
  → staging.empresa.com fica inacessível por 1 ano!
  → Browser força HTTPS, encontra certificado inválido, bloqueia
  
  Solução antes de ativar includeSubDomains:
    curl -I https://subdominio.empresa.com  (para cada subdomínio)
    Certifique-se que TODOS respondem com HTTPS válido

Problema 2 — Dificuldade de reverter HSTS:
  Se você definiu max-age=31536000 e precisa voltar para HTTP temporariamente:
  → Não tem como "reverter" para os usuários que já receberam o header
  → O máximo que pode fazer: enviar max-age=0 (zera o HSTS)
  → Mas isso só funciona se o usuário conseguir acessar o site via HTTPS
    para receber o novo header
  
  Solução: começar com max-age curto e aumentar gradualmente
  
  Fase 1: max-age=300 (5 minutos) — testar
  Fase 2: max-age=86400 (1 dia) — validar
  Fase 3: max-age=604800 (1 semana) — confirmar
  Fase 4: max-age=2592000 (30 dias) — estabilizar
  Fase 5: max-age=31536000; includeSubDomains (produção)
  Fase 6: max-age=31536000; includeSubDomains; preload (preload list)

Problema 3 — First visit vulnerability:
  HSTS só se aplica APÓS a primeira visita HTTPS.
  Se o usuário NUNCA visitou o site: browser não sabe sobre o HSTS.
  
  Atacante pode interceptar a primeira visita HTTP:
  Usuário: http://banco.com
  Atacante (MITM): serve versão HTTP falsa
  
  Solução: HSTS Preload List
```

### HSTS Preload List

```
A Preload List é uma lista hardcoded nos browsers contendo domínios
que SEMPRE devem usar HTTPS — mesmo na primeira visita.

Requisitos para entrar na lista:
  1. max-age >= 31536000 (1 ano)
  2. includeSubDomains presente
  3. preload presente
  4. Todos os subdomínios têm HTTPS válido
  5. Redirect HTTP → HTTPS funciona

Como submeter: https://hstspreload.org

Aviso IMPORTANTE:
  A Preload List é PERMANENTE e muito difícil de remover.
  Remoção leva meses para propagar para todos os browsers.
  NUNCA submeta um domínio sem ter HTTPS estável para todos os subdomínios.
  
  → Pense muito antes de submeter
  → Submeta apenas se CERTAMENTE nunca precisará de HTTP nesse domínio
```

## Mixed Content — o risco de recursos HTTP em páginas HTTPS

Mixed content ocorre quando uma página HTTPS carrega recursos via HTTP. Isso quebra as garantias de segurança do HTTPS: o atacante pode interceptar o recurso HTTP e:
- Modificar um script JS para injetar código malicioso
- Alterar uma imagem (para phishing visual)
- Capturar dados de formulários

```
Tipos de mixed content:

Active Mixed Content (bloqueado por browsers modernos):
  → Scripts: <script src="http://cdn.exemplo.com/lib.js">
  → Stylesheets: <link rel="stylesheet" href="http://...">
  → iframes: <iframe src="http://...">
  → XHR/fetch: fetch('http://api.exemplo.com/dados')
  
  Um script HTTP pode controlar completamente a página HTTPS
  → Browser bloqueia automaticamente (não carrega)

Passive Mixed Content (aviso nos browsers):
  → Imagens: <img src="http://cdn.exemplo.com/foto.jpg">
  → Vídeos: <video src="http://...">
  → Áudio: <audio src="http://...">
  
  Menos perigoso: não pode executar código
  → Browser exibe aviso (cadeado amarelo/quebrado)
  → Chrome 79+: também bloqueia imagens

Upgrade-Insecure-Requests:
  → Header de requisição que pede ao servidor para redirecionar HTTP→HTTPS
  → O browser envia automaticamente em páginas HTTPS
  → Upgrade-Insecure-Requests: 1
  
Content-Security-Policy: upgrade-insecure-requests
  → Instrui o browser a fazer upgrade automático de sub-recursos HTTP→HTTPS
  → Antes de bloquear, tenta acessar via HTTPS
  → Se HTTPS não existir: bloqueia
```

### Detectando e corrigindo mixed content

```bash
# Ferramentas para encontrar mixed content:

# 1. Browser DevTools — Console mostra warnings de mixed content

# 2. Lighthouse (Chrome DevTools)
#    → Audit → Mixed Content

# 3. curl para verificar recursos
curl -I http://cdn.exemplo.com/lib.js
# Se retorna 301 → https://... : vai funcionar com upgrade-insecure-requests
# Se retorna 200 HTTP: precisa forçar HTTPS no HTML

# 4. Ferramenta de linha de comando: mixed-content-scanner
npx mixed-content-scanner https://meusite.com

# Correção no HTML:
# ANTES: <script src="http://cdn.exemplo.com/lib.js">
# DEPOIS: <script src="https://cdn.exemplo.com/lib.js">
# OU:     <script src="//cdn.exemplo.com/lib.js">  ← protocol-relative (usa o mesmo scheme)
```

```python
# CSP para forçar upgrade de recursos HTTP para HTTPS
response.headers["Content-Security-Policy"] = "upgrade-insecure-requests"
# Instrui o browser a tentar HTTPS antes de HTTP para todos os recursos
```

## Certificate Transparency — auditoria pública de certificados

Certificate Transparency (CT) é um sistema de logs públicos onde todas as CAs devem registrar os certificados que emitem. Isso permite detectar certificados emitidos fraudulentamente.

```
Por que CT foi criado:
  2011: DigiNotar (CA holandesa) foi comprometida
  Atacante emitiu certificados falsos para google.com, gmail.com, etc.
  Com certificados válidos: MITM perfeito — browsers não detectavam
  
  CT resolve isso:
  1. CAs devem registrar TODOS os certificados em logs públicos
  2. Browsers verificam se o certificado está em pelo menos 2 logs
  3. Qualquer certificado não-logado é rejeitado
  4. Você pode monitorar logs para detectar certs emitidos sem sua permissão

Headers relacionados:
  Certificate Transparency via SCT (Signed Certificate Timestamp)
  → Incluído no certificado pelo CT log
  → Ou enviado via TLS extension

Monitoramento proativo:
  → crt.sh — buscar certificados emitidos para seu domínio
  → certspotter.com — alertas para novos certificados
```

## Certificate Pinning — confiança explícita em certificados específicos

Certificate Pinning é a prática de hardcodar quais certificados/chaves públicas são válidos para um domínio específico — rejeitando qualquer outro certificado, mesmo que seja emitido por uma CA confiável.

```
Problema que resolve:
  Uma CA maliciosa (ou comprometida) emite certificado válido para seu domínio
  → Browser confia (a CA está na lista de confiança)
  → Atacante faz MITM com certificado "legítimo"
  → Certificate Pinning rejeita: "não é o certificado que esperamos"

Onde é usado:
  → Apps mobile (iOS e Android)
  → Software desktop crítico
  → Raramente em browsers (por isso HPKP foi removido)
```

### HPKP — o padrão que falhou (removido)

```
HTTP Public Key Pinning (HPKP):
  O servidor enviava header com fingerprints de chaves aceitas:
  Public-Key-Pins: pin-sha256="abc="; pin-sha256="def="; max-age=5184000
  
  Problema catastrófico:
  → Se você perde a chave privada OU a CA não pode emitir com essa chave:
    Todos os browsers que receberam o pin ficam bloqueados por max-age
  → Ransomware: atacante que comprometia o servidor podia setar pinos falsos
    → Proprietário do site não conseguia mais servir o site por meses!
  
  HPKP foi removido de todos os browsers modernos (2018-2020)
```

### Pinning moderno em apps mobile

```swift
// iOS — URLSession com certificate pinning
class PinnedDelegate: NSObject, URLSessionDelegate {
    func urlSession(_ session: URLSession,
                    didReceive challenge: URLAuthenticationChallenge,
                    completionHandler: @escaping (URLSession.AuthChallengeDisposition, URLCredential?) -> Void) {
        
        guard let serverTrust = challenge.protectionSpace.serverTrust,
              let certificate = SecTrustGetCertificateAtIndex(serverTrust, 0) else {
            completionHandler(.cancelAuthenticationChallenge, nil)
            return
        }
        
        // Comparar com o certificado/chave pública esperada
        let serverCertData = SecCertificateCopyData(certificate) as Data
        let pinnedCertData = loadPinnedCertificate()
        
        if serverCertData == pinnedCertData {
            completionHandler(.useCredential, URLCredential(trust: serverTrust))
        } else {
            completionHandler(.cancelAuthenticationChallenge, nil)  // rejeitar!
        }
    }
}
```

### Pinning por chave pública (mais resiliente que por certificado)

```python
# Pinning por hash da chave pública (não do certificado inteiro)
# Vantagem: você pode renovar o certificado sem atualizar o pin
# Desde que use a mesma chave privada (ou uma pre-pinned backup key)

import ssl
import hashlib
import base64
from urllib.request import urlopen

PINNED_KEYS = {
    # SHA-256 do SubjectPublicKeyInfo (SPKI) esperado
    "YLh1dUR9y6Kja30RrAn7JKnbQG/uEtLMkBgFF2Fuihg="  # chave atual
    "X3pGTSOuJeEVw989IJ/cEtXUEmy52zs1TZQrU06KUKg="  # backup key
}

def verificar_pin(hostname: str) -> bool:
    ctx = ssl.create_default_context()
    with ctx.wrap_socket(socket.socket(), server_hostname=hostname) as s:
        s.connect((hostname, 443))
        cert_der = s.getpeercert(binary_form=True)
    
    # Extrair SPKI e calcular hash
    # (em produção: usar cryptography library para extrair SPKI corretamente)
    spki_hash = base64.b64encode(hashlib.sha256(cert_der).digest()).decode()
    return spki_hash in PINNED_KEYS
```

## Configuração de TLS hardening

```nginx
# Nginx — configuração TLS segura para produção

ssl_protocols TLSv1.2 TLSv1.3;           # apenas versões seguras
ssl_prefer_server_ciphers off;             # TLS 1.3 não usa (melhor assim)

# Cipher suites para TLS 1.2 (TLS 1.3 define os próprios automaticamente)
ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305;

# Session tickets e caching
ssl_session_timeout 1d;
ssl_session_cache shared:SSL:10m;
ssl_session_tickets off;                   # Forward Secrecy requer isso

# OCSP Stapling — servidor inclui resposta OCSP no handshake
ssl_stapling on;
ssl_stapling_verify on;
ssl_trusted_certificate /path/to/chain.pem;
resolver 8.8.8.8 8.8.4.4 valid=300s;     # DNS para OCSP

# Headers de segurança
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
add_header X-Content-Type-Options nosniff always;
add_header X-Frame-Options DENY always;
add_header Content-Security-Policy "upgrade-insecure-requests; default-src 'self'" always;
```

## Erros comuns e armadilhas

**Não renovar certificados antes do vencimento:** Let's Encrypt tem 90 dias. Configure alertas para 30 e 7 dias antes do vencimento. Certbot renova automaticamente mas falhas de configuração acontecem — monitorar com uptime services ou scripts.

**Servir certificado sem a cadeia intermediária:** o cliente pode não ter o certificado intermediário em cache. Sem ele, alguns clientes (especialmente móveis) recebem `ERR_CERT_AUTHORITY_INVALID`. O arquivo do servidor deve incluir o certificado do domínio + todos os intermediários (full chain).

**Mixed content de recursos de terceiros:** CDNs, fontes, analytics. Google Fonts, por exemplo, tem HTTPS — mas URLs antigas podem ser `http://`. Verificar e atualizar todos os URLs de terceiros para HTTPS.

**Certificate Pinning em apps sem backup pin:** se você fizer pinning de apenas um certificado e ele expirar antes de você atualizar o app: o app fica inutilizável até o usuário atualizar. Sempre fazer pinning em 2+ chaves públicas (atual + backup).

## 🧩 Quiz de Fixação

1. Um site entra na HSTS Preload List com `max-age=31536000; includeSubDomains`. Seis meses depois, a empresa decide criar o subdomínio `legacy.empresa.com` que só funciona em HTTP (sistema legado sem suporte a TLS). O que acontece e quais são as opções?

2. Uma página HTTPS carrega um script de `http://analytics.terceiro.com/tracker.js`. O browser bloqueia o script (active mixed content). O desenvolvedor adiciona `Content-Security-Policy: upgrade-insecure-requests` e `analytics.terceiro.com` suporta HTTPS. O script agora carrega? O que o header faz exatamente?

3. Um app mobile bancário usa certificate pinning com a chave pública atual (`pin-atual`). O banco renova o certificado mas mantém a mesma chave privada. O app continua funcionando? E se o banco trocar para uma nova chave privada (novo par de chaves RSA)?

**Respostas:**

1) **O que acontece:** browsers de usuários que receberam o HSTS (ou que têm o domínio na Preload List) forçam HTTPS para `legacy.empresa.com`. Como não há TLS, o subdomínio fica completamente inacessível para esses usuários. **Opções:** (a) **Adicionar TLS ao legacy.empresa.com** — usar um reverse proxy (nginx) na frente do sistema legado que termina TLS e repassa HTTP internamente. O sistema legado não precisa suportar TLS diretamente; (b) **Usar um subdomínio fora do escopo:** se o legacy precisar ser HTTP, usar um domínio completamente diferente (ex: `legacy-empresa.net`) que não está sob o `empresa.com` com HSTS/includeSubDomains; (c) **Remover da Preload List:** processo demorado (meses), e apenas afeta novos usuários/instalações — usuários atuais continuam com o pin na cache por `max-age` segundos. A lição: nunca submeter à Preload List sem certificeza de que TODOS os subdomínios terão HTTPS para sempre.

2) **Sim, o script carrega** (assumindo que `analytics.terceiro.com` suporta HTTPS). O header `Content-Security-Policy: upgrade-insecure-requests` instrui o browser a automaticamente fazer upgrade de URLs HTTP para HTTPS para todos os sub-recursos da página antes de tentar carregá-los. Então: `http://analytics.terceiro.com/tracker.js` → browser tenta `https://analytics.terceiro.com/tracker.js` → se HTTPS responde com sucesso: script é carregado normalmente. Se HTTPS não existe no terceiro: o recurso é bloqueado (não cai de volta para HTTP). O header é uma forma de corrigir mixed content sem modificar o HTML — útil quando você tem muitos recursos hardcoded com HTTP e o servidor destino tem HTTPS disponível.

3) **Mesma chave privada, novo certificado:** o app **continua funcionando**. O pinning é na **chave pública** (derivada da chave privada) — não no certificado em si. Renovar o certificado mantém a mesma chave privada → mesma chave pública → mesmo pin → app aceita. **Nova chave privada (novo par RSA):** o app **para de funcionar** para todos os usuários com a versão atual instalada. A nova chave pública não bate com o pin hardcoded no app. O banco precisaria: (a) ter o pin da nova chave no app (backup pin) antes de trocar; (b) ou publicar uma nova versão do app com o pin atualizado E garantir que todos os usuários atualizem antes da troca de chave. Este é o risco principal do certificate pinning: atualizações de chave exigem coordenação precisa entre app e servidor. A solução padrão é sempre ter dois pins — chave atual e chave de backup (próxima geração) — nunca apenas um.
