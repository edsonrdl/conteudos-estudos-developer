### Como o HTTPS protege o HTTP — TLS sobre TCP, handshake, certificados e cadeia de confiança

HTTPS não é um protocolo diferente do HTTP — é o HTTP rodando sobre uma camada de segurança chamada **TLS** (Transport Layer Security). O TLS resolve três problemas fundamentais do HTTP puro: **confidencialidade** (ninguém pode ler os dados em trânsito), **integridade** (ninguém pode modificar os dados) e **autenticidade** (você está realmente falando com quem pensa estar). Entender como o TLS funciona explica por que HTTPS é seguro e o que acontece quando um certificado é inválido.

---

## O problema que o HTTPS resolve

```
HTTP puro (texto claro na rede):

Browser → [café Wi-Fi] → Roteador → ISP → Servidor
          ↑
          Qualquer pessoa na mesma rede Wi-Fi pode capturar:
          GET /login HTTP/1.1
          Host: banco.com
          Cookie: session=abc123
          Body: {"senha": "minha_senha_secreta"}

Ataques possíveis com HTTP:
  Eavesdropping: leitura dos dados (senhas, tokens, dados pessoais)
  Man-in-the-Middle: modificar a resposta do servidor em trânsito
  → Trocar o conteúdo de uma página bancária para roubar credenciais
  → Injetar scripts maliciosos no HTML retornado pelo servidor
  Session hijacking: roubar cookies de sessão
```

```
HTTPS (dados criptografados):

Browser → [dados cifrados] → Roteador → [dados cifrados] → ISP → Servidor

O Wi-Fi captura:
  [lixo binário cifrado — ilegível sem a chave privada do servidor]

O que o atacante vê:
  IP de destino: 93.184.216.34 (pode resolver para banco.com via DNS)
  Porta: 443
  Tamanho aproximado dos pacotes
  Timing dos pacotes
  
  NÃO vê: URLs, headers, cookies, senhas, qualquer conteúdo
```

## O que é TLS

TLS (Transport Layer Security) é o sucessor do SSL (Secure Sockets Layer). SSL foi descontinuado por vulnerabilidades — hoje "SSL" no mercado geralmente significa TLS. As versões modernas:

```
SSL 2.0 (1995): descontinuado — vulnerável
SSL 3.0 (1996): descontinuado — POODLE attack
TLS 1.0 (1999): descontinuado (2021 pela RFC)
TLS 1.1 (2006): descontinuado (2021 pela RFC)
TLS 1.2 (2008): ainda amplamente usado, aceitável
TLS 1.3 (2018): atual — mais rápido e seguro

TLS 1.3 melhorias sobre 1.2:
  → Handshake em 1 RTT (vs 2 RTTs no 1.2)
  → 0-RTT para reconexões
  → Algoritmos fracos removidos (RSA key exchange, RC4, SHA-1)
  → Forward Secrecy obrigatório
```

## TLS Handshake — como a conexão segura é estabelecida

O handshake é o processo de negociação que acontece antes de qualquer dado HTTP ser transmitido. Durante o handshake, cliente e servidor:
1. Verificam a identidade do servidor (via certificado)
2. Negociam algoritmos de criptografia
3. Estabelecem chaves simétricas compartilhadas para a sessão

### TLS 1.3 Handshake (1-RTT)

```
Cliente                                    Servidor
  │                                           │
  │─── ClientHello ─────────────────────────▶│
  │   • Versões TLS suportadas (TLS 1.3)     │
  │   • Cipher suites suportadas             │
  │   • Key shares (chaves públicas ECDH)    │
  │   • Extensions (SNI, ALPN, etc.)         │
  │                                           │
  │◀── ServerHello + Certificate + Finished ─│
  │   • Versão escolhida: TLS 1.3            │
  │   • Cipher suite escolhida               │
  │   • Key share do servidor (ECDH)         │
  │   • Certificado do servidor              │
  │   • Finished (MAC dos handshake messages)│
  │                                           │
  │─── Finished ────────────────────────────▶│
  │   • Confirmação que handshake foi ok      │
  │                                           │
  │─── GET /api/dados HTTP/1.1 ─────────────▶│ ← dados HTTP cifrados
  │◀── HTTP/1.1 200 OK ──────────────────────│

Total: 1 RTT (antes do primeiro dado HTTP)
vs TLS 1.2: 2 RTTs
```

### O que acontece em cada passo

**ClientHello — o browser anuncia capacidades:**
```
Enviado:
  - Versões TLS suportadas: [TLS 1.3, TLS 1.2]
  - Cipher suites: [TLS_AES_256_GCM_SHA384, TLS_CHACHA20_POLY1305_SHA256, ...]
  - Key shares: chaves públicas para ECDH (troca de chaves Diffie-Hellman)
  - SNI (Server Name Indication): "api.banco.com"
    → Permite que um servidor hospede múltiplos certificados no mesmo IP
  - ALPN (Application-Layer Protocol Negotiation): "h2, http/1.1"
    → Negocia HTTP/2 ou HTTP/1.1
```

**ServerHello + Certificate — servidor responde:**
```
Enviado:
  - Versão escolhida: TLS 1.3
  - Cipher suite escolhida: TLS_AES_256_GCM_SHA384
  - Key share: chave pública ECDH do servidor
  - Certificate: certificado X.509 do servidor
  - CertificateVerify: prova que o servidor tem a chave privada
  - Finished: MAC para verificar integridade do handshake

Neste ponto:
  Cliente e servidor derivam as mesmas chaves simétricas
  usando o Diffie-Hellman (sem nunca transmitir a chave)
```

## Criptografia no TLS — como os dados são protegidos

### Diffie-Hellman — como duas partes criam uma chave secreta compartilhada sem transmiti-la

```
Analogia com cores:

1. Ambos começam com cor pública: amarelo
2. Cliente escolhe segredo: vermelho; envia mistura: amarelo+vermelho = laranja
3. Servidor escolhe segredo: azul; envia mistura: amarelo+azul = verde
4. Cliente: pega verde + vermelho = marrom (segredo compartilhado)
5. Servidor: pega laranja + azul = marrom (mesmo segredo!)

Na rede, apenas laranaja e verde foram transmitidos.
Ninguém que interceptou sabe o vermelho, o azul nem o marrom.
```

Em TLS, usa-se ECDH (Elliptic Curve Diffie-Hellman) — mesmo princípio mas com curvas elípticas (mais eficiente).

### Criptografia simétrica para os dados

```
Após o handshake: ambos têm a mesma chave simétrica (AES-256, ChaCha20)

Criptografia simétrica:
  → Muito mais rápida que assimétrica
  → Mesma chave para criptografar e descriptografar
  → AES-256-GCM: padrão atual (256-bit key, GCM mode)
  
  Dados HTTP → AES-256 encrypt → [lixo cifrado na rede] → AES-256 decrypt → Dados HTTP

Por que não usar criptografia assimétrica para os dados?
  → RSA/ECDSA são ~1000x mais lentos que AES
  → Usados apenas para o handshake e autenticação (onde performance não é crítica)
  → Dados em trânsito: criptografia simétrica (velocidade)
```

### Forward Secrecy — segurança do passado

```
Forward Secrecy (Sigilo de Encaminhamento):
  Mesmo que a chave privada do servidor seja comprometida amanhã,
  conversas passadas não podem ser decifradas.

Por que isso importa:
  Ataque prático:
    Governo/atacante captura todo o tráfego HTTPS de um banco por 5 anos
    Depois obtém a chave privada do banco (roubo, court order, vulnerabilidade)
    
    Sem Forward Secrecy (RSA key exchange):
      → Pode descriptografar TODOS os 5 anos de tráfego capturado
    
    Com Forward Secrecy (ECDH ephemeral):
      → Cada sessão tem chaves efêmeras únicas
      → Comprometer a chave privada hoje não ajuda a decifrar o passado
      → As chaves efêmeras de cada sessão foram destruídas após o uso

TLS 1.3: Forward Secrecy OBRIGATÓRIO (usa sempre ECDHE)
TLS 1.2: opcional, mas deve ser configurado (cipher suites ECDHE_*)
```

## Certificados X.509 — como o servidor prova sua identidade

Um certificado é como uma "identidade digital" emitida por uma entidade confiável (CA). Contém:

```
Campos de um certificado X.509:
  Subject:          CN=api.banco.com, O=Banco ABC, C=BR
                    ↑ para quem é    ↑ organização ↑ país
  
  Subject Alt Names: api.banco.com, *.banco.com, banco.com
                    ↑ domínios válidos para este certificado
  
  Issuer:           CN=Let's Encrypt R3, O=Let's Encrypt
                    ↑ quem emitiu (CA)
  
  Valid From:       2024-01-15 00:00:00 UTC
  Valid Until:      2024-04-15 23:59:59 UTC  ← 90 dias (Let's Encrypt)
  
  Public Key:       [chave pública RSA 2048-bit ou EC P-256]
                    ↑ o servidor tem a chave privada correspondente
  
  Signature:        [assinatura digital da CA]
                    ↑ prova que a CA verificou esse certificado
  
  Serial Number:    abc123...
  Fingerprint:      SHA-256: de:ad:be:ef:...
```

### Como o browser valida o certificado

```
1. Recebe o certificado do servidor

2. Verifica a assinatura:
   "A CA Let's Encrypt assinou este certificado?
    Vou verificar com a chave pública da Let's Encrypt"
   
3. Verifica a cadeia de certificados (chain of trust):
   Certificado do servidor
     ↑ assinado por
   Certificado intermediário (Let's Encrypt R3)
     ↑ assinado por
   Certificado raiz (ISRG Root X1)
     ↑ confiado pelo OS/browser (hardcoded)

4. Verifica se o domínio no certificado bate:
   Você está em: api.banco.com
   Certificado diz: CN=api.banco.com ✓
   (ou wildcard: *.banco.com ✓)

5. Verifica a validade:
   Certificado válido até: 2024-04-15
   Data atual: 2024-01-20
   ✓ Ainda válido

6. Verifica revogação (OCSP ou CRL):
   "Este certificado foi revogado antes de expirar?"
   → OCSP: Online Certificate Status Protocol
   → CRL: Certificate Revocation List

Qualquer verificação falhar → alerta de segurança ao usuário
```

### A cadeia de confiança (Chain of Trust)

```
Raiz de confiança:

┌─────────────────────────────────────────────────────────┐
│              Root CA (Certificado Raiz)                 │
│  ISRG Root X1 (Let's Encrypt) / DigiCert / Comodo      │
│  → Hardcoded no OS e browsers como "confiável"          │
│  → Autoassinados (ninguém acima deles para assinar)     │
│  → Validade: 20+ anos                                   │
│  → Chave privada em hardware HSM offline, ultra-segura  │
└──────────────────────┬──────────────────────────────────┘
                       │ assina
┌──────────────────────▼──────────────────────────────────┐
│         Intermediate CA (Certificado Intermediário)     │
│  Let's Encrypt R3 / DigiCert Global CA                  │
│  → Assinado pela Root CA                               │
│  → Validade: 2-5 anos                                  │
│  → Emissor real de certificados do usuário final       │
│  → Chave privada online (necessária para emitir)       │
└──────────────────────┬──────────────────────────────────┘
                       │ assina
┌──────────────────────▼──────────────────────────────────┐
│           End-Entity Certificate (Seu certificado)     │
│  api.banco.com                                          │
│  → Assinado pela Intermediate CA                       │
│  → Validade: 90 dias (Let's Encrypt) a 1 ano          │
│  → Chave privada no seu servidor                       │
└─────────────────────────────────────────────────────────┘

Por que o certificado raiz não emite diretamente?
  → Segurança por isolamento: a chave da Root CA fica offline
  → Se uma Intermediate CA for comprometida: apenas revogar ela
  → Root CA permanece intacta
```

## Tipos de certificados

```
DV (Domain Validation) — mais comum:
  → Prova apenas que você controla o domínio
  → Verificação automática (DNS ou arquivo HTTP)
  → Emissão em minutos
  → Let's Encrypt: gratuito, 90 dias
  → Custo: grátis a $10/ano
  → Adequado para: APIs, sites em geral

OV (Organization Validation):
  → Prova que a organização existe (verificação manual da CA)
  → Emissão em 1-3 dias
  → Custo: $50-500/ano
  → Exibe: O=Empresa ABC no certificado
  → Adequado para: empresas que querem mostrar identidade

EV (Extended Validation) — mais rigoroso:
  → Verificação detalhada da organização (física, jurídica)
  → Emissão em dias a semanas
  → Custo: $200-1000/ano
  → Browsers modernos não exibem mais a "barra verde" para EV
  → Adequado para: bancos, e-commerces grandes
  
Wildcard:
  → *.empresa.com cobre todos os subdomínios imediatos
  → NÃO cobre sub.sub.empresa.com (apenas um nível)
  → Let's Encrypt fornece wildcards via DNS challenge

SAN (Subject Alternative Names):
  → Um único certificado para múltiplos domínios
  → empresa.com, www.empresa.com, api.empresa.com no mesmo cert
```

## O que acontece em diferentes falhas de certificado

```
ERR_CERT_DATE_INVALID (certificado expirado):
  → O certificado está vencido
  → Browser bloqueia com aviso vermelho
  → Solução: renovar o certificado

ERR_CERT_COMMON_NAME_INVALID (domínio não bate):
  → Você está em api.banco.com mas o certificado é para banco.com
  → Possível: misconfiguration, ou ataque MITM com certificado falso
  → Browser bloqueia

ERR_CERT_AUTHORITY_INVALID (CA não confiável):
  → Certificado auto-assinado (não emitido por CA confiável)
  → Frequente em ambientes de desenvolvimento/teste
  → Browser bloqueia (pode ser ignorado manualmente em dev)

NET::ERR_CERT_REVOKED (certificado revogado):
  → A CA revogou o certificado antes de expirar
  → Motivo: chave privada comprometida, domínio vendido, erro na emissão
  → Browser bloqueia definitivamente (sem como ignorar)
```

## Verificando HTTPS na prática

```bash
# Verificar certificado de um domínio
openssl s_client -connect api.banco.com:443 -servername api.banco.com < /dev/null

# Ver apenas as datas de validade
echo | openssl s_client -connect api.banco.com:443 2>/dev/null | \
  openssl x509 -noout -dates

# Ver todos os SANs (domínios cobertos)
echo | openssl s_client -connect api.banco.com:443 2>/dev/null | \
  openssl x509 -noout -text | grep -A1 "Subject Alternative"

# Ver a cadeia de certificados
echo | openssl s_client -showcerts -connect api.banco.com:443 2>/dev/null | \
  grep -E "subject=|issuer="

# Verificar qual versão TLS e cipher suite estão sendo usados
curl -v --tlsv1.3 https://api.banco.com 2>&1 | grep -E "TLS|cipher"
```

## Erros comuns e armadilhas

**Confundir SSL e TLS:** SSL foi descontinuado. "SSL certificate" hoje em dia significa certificado TLS. Quando alguém fala em "instalar SSL", quer dizer TLS.

**Deixar TLS 1.0/1.1 habilitado:** versões antigas têm vulnerabilidades conhecidas (BEAST, POODLE). Configurar servidores para aceitar apenas TLS 1.2+ (mínimo) ou TLS 1.3 (ideal).

**Certificado expirado:** Let's Encrypt tem validade de 90 dias. Sem renovação automática (Certbot, ACME), o certificado expira e o site fica inacessível. Configurar renovação automática antes de colocar em produção.

**Mixed content:** página HTTPS carregando recursos via HTTP (imagens, scripts). O browser bloqueia os recursos HTTP — a proteção do HTTPS é quebrada por qualquer elemento não-seguro. Verificar que TODOS os recursos usam HTTPS.

## 🧩 Quiz de Fixação

1. Por que o Diffie-Hellman permite que cliente e servidor estabeleçam uma chave secreta compartilhada sem nunca transmiti-la pela rede — e por que isso é essencial para o Forward Secrecy?

2. Um certificado TLS tem no campo SAN: `*.empresa.com, empresa.com`. Um usuário acessa `api.dev.empresa.com` (dois subdomínios de profundidade). O certificado é válido para esse acesso?

3. Uma empresa tem seu certificado TLS revogado pela CA após descobrir que a chave privada foi comprometida. Usuários que visitaram o site ontem (antes da revogação) ficaram com sessões ativas. Essas sessões são seguras? E sessões iniciadas após a revogação?

**Respostas:**

1) O Diffie-Hellman usa propriedades matemáticas de álgebra modular (ou curvas elípticas no ECDH) onde é computacionalmente fácil calcular `g^a mod p` mas extremamente difícil inverter — dado `g^a mod p`, encontrar `a` (problema do logaritmo discreto). Cliente e servidor trocam seus valores públicos (`g^a mod p` e `g^b mod p`) pela rede abertamente, mas ambos podem calcular `g^ab mod p` — que é o segredo compartilhado — sem transmiti-lo. **Forward Secrecy:** quando o DH usa chaves **efêmeras** (novas para cada sessão), mesmo que um atacante capture todo o tráfego E depois obtenha a chave privada do servidor, ele não consegue decifrar sessões passadas — as chaves efêmeras foram descartadas após o uso e nunca eram a chave privada do servidor.

2) **Não é válido.** O wildcard `*.empresa.com` cobre apenas **um nível** de subdomínio: `api.empresa.com`, `www.empresa.com`, `admin.empresa.com`. O domínio `api.dev.empresa.com` tem dois níveis abaixo de `empresa.com` — o wildcard não se aplica. Um wildcard `*.empresa.com` literalmente significa "um segmento de qualquer caractere antes de `.empresa.com`". Para cobrir `api.dev.empresa.com`, seria necessário um certificado wildcard `*.dev.empresa.com` ou um certificado com SAN explícito para `api.dev.empresa.com`.

3) **Sessões antigas (antes da revogação) com tráfego já capturado:** dependem do Forward Secrecy. Se TLS 1.3 ou TLS 1.2 com ECDHE estava sendo usado: as chaves de sessão eram efêmeras e foram descartadas — um atacante que comprometeu a chave privada **não consegue** decifrar tráfego passado capturado. Se estava usando cipher suites sem Forward Secrecy (RSA key exchange no TLS 1.2): o tráfego passado pode ser decifrado com a chave privada comprometida. **Sessões novas após a revogação:** browsers que verificam OCSP/CRL em tempo real recebem resposta "revogado" e bloqueiam a conexão. Porém, OCSP pode ser cacheado ou ter falhas de verificação ("soft fail") — alguns browsers conectam mesmo sem OCSP resposta. OCSP Stapling (servidor inclui a resposta OCSP no handshake) melhora isso. Na prática: certificado revogado + chave comprometida = emergência — além de revogar, o servidor deve ser imediatamente isolado e uma nova chave/certificado emitidos.
