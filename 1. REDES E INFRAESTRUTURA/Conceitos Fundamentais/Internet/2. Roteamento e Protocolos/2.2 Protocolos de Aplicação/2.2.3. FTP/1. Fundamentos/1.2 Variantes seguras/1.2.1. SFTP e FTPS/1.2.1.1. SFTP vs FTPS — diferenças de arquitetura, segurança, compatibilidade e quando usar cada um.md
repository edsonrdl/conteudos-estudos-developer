### SFTP vs FTPS — diferenças de arquitetura, segurança, compatibilidade e quando usar

SFTP e FTPS resolvem o mesmo problema (FTP inseguro) de formas completamente diferentes. Apesar dos nomes semelhantes, são protocolos com arquiteturas opostas: FTPS é "FTP com TLS" (extensão do FTP), enquanto SFTP é "SSH File Transfer Protocol" (protocolo completamente diferente que roda sobre SSH). A escolha entre eles depende da infraestrutura existente, dos requisitos de firewall e da compatibilidade com clientes e servidores.

---

## FTPS — FTP over TLS

FTPS (FTP Secure) adiciona criptografia TLS ao FTP existente, mantendo a mesma arquitetura de dois canais e os mesmos comandos.

### Dois modos de FTPS

```
FTPS Explicit (FTPES) — padrão recomendado:
  1. Cliente conecta na porta 21 (FTP normal)
  2. Cliente envia: AUTH TLS  ← "quero negociar TLS"
  3. Servidor responde: 234 AUTH TLS OK
  4. TLS handshake acontece no canal de controle
  5. Após TLS: tudo no canal de controle é criptografado
  6. Canal de dados: criptografado via PBSZ/PROT C ou PROT P
  
  Vantagem: usa porta padrão (21), pode ser usada em modo não-criptografado
             por clientes antigos que não entendem AUTH TLS
  Porta: 21

FTPS Implicit — legado (evitar):
  1. Cliente conecta na porta 990 diretamente com TLS
  2. TLS handshake imediato (sem negociação)
  3. Toda comunicação já começa criptografada
  
  Desvantagem: porta não-padrão, sem fallback para FTP puro
  Porta: 990 (controle), 989 (dados)
```

### Comandos FTPS específicos

```
AUTH TLS     → negociar TLS no canal de controle (Explicit mode)
AUTH SSL     → negado — SSL depreciado, não usar
PBSZ 0       → Protection Buffer Size (deve ser 0 para TLS)
PROT P       → Protection Level Private (criptografar canal de dados)
PROT C       → Protection Level Clear (dados sem criptografia — inseguro!)
CCC          → Clear Command Channel (voltar canal de controle para texto puro)
```

### Problema do FTPS com firewall e NAT

```
FTPS herda o problema do FTP com firewalls/NAT:

Canal de dados PASV com FTPS:
  PASV → "227 Entering Passive Mode (192,168,1,1,196,150)"
  
  Firewall statefull que inspeciona FTP (por porta 21):
    → Lê o IP:porta no PASV
    → Abre automaticamente a porta de dados no firewall
    → Funciona!
  
  Firewall com FTPS criptografado:
    → O conteúdo do PASV está criptografado
    → Firewall não consegue ler o IP:porta
    → NÃO abre a porta de dados automaticamente
    → Canal de dados bloqueado!
  
  Solução:
    1. Configurar range de portas passivas fixo no servidor FTPS
    2. Abrir esse range no firewall manualmente
    3. OU usar EPSV ALL com o IP do servidor em vez de IP interno
```

## SFTP — SSH File Transfer Protocol

SFTP é um **protocolo completamente diferente** do FTP — não é uma extensão. Roda sobre SSH (Secure Shell) e usa apenas **uma conexão TCP** na porta 22. Tudo (autenticação, comandos e dados) é transmitido criptografado pelo mesmo canal SSH.

```
SFTP — arquitetura simples:

1. Cliente conecta em: servidor:22 (SSH)
2. Autenticação SSH (senha ou chave pública)
3. Cliente solicita subsistema: sftp
4. Tudo transmitido em binário criptografado por um único canal TCP

NÃO tem:
  → Canal de controle separado
  → Canal de dados separado
  → Modo ativo/passivo
  → Problemas com NAT/firewall (apenas porta 22)
  
Tem:
  → Criptografia completa (TLS/AES via SSH)
  → Autenticação por senha OU chave pública SSH
  → Checksums de integridade em cada operação
  → Operações atômicas (renomear, criar, deletar)
```

### Comandos SFTP

```
Conectar:
  sftp usuario@servidor.com
  sftp -P 2222 usuario@servidor.com  ← porta customizada

Navegação:
  pwd       → diretório remoto atual
  cd /path  → mudar diretório remoto
  lpwd      → diretório LOCAL atual
  lcd       → mudar diretório LOCAL
  ls -la    → listar remoto
  lls       → listar local

Transferência:
  get arquivo.txt           → baixar arquivo
  get -r /diretório/        → baixar diretório recursivo
  put arquivo.txt           → enviar arquivo
  put -r /diretório/        → enviar diretório recursivo
  
  mget *.csv               → baixar múltiplos (wildcard)
  mput *.log               → enviar múltiplos (wildcard)

Gerenciamento de arquivos:
  mkdir novo_dir            → criar diretório
  rmdir velho_dir           → remover diretório
  rm arquivo.txt            → remover arquivo
  rename antigo novo        → renomear
  chmod 755 arquivo.sh      → permissões (sistemas Unix)
  chown user arquivo        → proprietário

Informações:
  df -h                     → espaço em disco
  stat arquivo.txt          → metadados do arquivo
  
Sair:
  exit / quit / bye
```

### Autenticação por chave pública SSH (mais segura)

```bash
# Gerar par de chaves SSH
ssh-keygen -t ed25519 -C "deploy@empresa.com" -f ~/.ssh/sftp_key
# Cria: ~/.ssh/sftp_key (privada) e ~/.ssh/sftp_key.pub (pública)

# Copiar chave pública para o servidor
ssh-copy-id -i ~/.ssh/sftp_key.pub usuario@servidor.com
# Ou manualmente adicionar ao servidor:
# cat sftp_key.pub >> /home/usuario/.ssh/authorized_keys

# Conectar com chave (sem senha)
sftp -i ~/.ssh/sftp_key usuario@servidor.com

# Configurar no ~/.ssh/config para simplificar:
Host sftp-producao
  HostName servidor.com
  User deploy
  IdentityFile ~/.ssh/sftp_key
  Port 22

# Usar simplesmente:
sftp sftp-producao
```

### SFTP em scripts e automação

```python
# Python — paramiko para SFTP automatizado
import paramiko

def transferir_arquivo(host, usuario, chave_privada, arquivo_local, caminho_remoto):
    """Upload via SFTP com autenticação por chave."""
    
    # Carregar chave privada
    chave = paramiko.Ed25519Key.from_private_key_file(chave_privada)
    
    # Conectar via SSH
    cliente_ssh = paramiko.SSHClient()
    cliente_ssh.set_missing_host_key_policy(paramiko.AutoAddPolicy())
    # Na produção: usar RejectPolicy e verificar host keys!
    
    cliente_ssh.connect(
        hostname=host,
        username=usuario,
        pkey=chave
    )
    
    # Abrir cliente SFTP
    sftp = cliente_ssh.open_sftp()
    
    try:
        sftp.put(arquivo_local, caminho_remoto)
        print(f"Arquivo enviado: {arquivo_local} → {caminho_remoto}")
        
        # Verificar integridade via stat
        stat = sftp.stat(caminho_remoto)
        print(f"Tamanho no servidor: {stat.st_size} bytes")
    finally:
        sftp.close()
        cliente_ssh.close()

# Uso:
transferir_arquivo(
    host="servidor.empresa.com",
    usuario="deploy",
    chave_privada="/home/usuario/.ssh/sftp_key",
    arquivo_local="/tmp/backup_20240115.tar.gz",
    caminho_remoto="/backups/backup_20240115.tar.gz"
)
```

```bash
# Bash — SFTP não-interativo com comandos em batch
sftp -i ~/.ssh/sftp_key usuario@servidor.com <<EOF
cd /uploads
put relatorio.csv
ls -la
bye
EOF

# rsync sobre SSH (mais eficiente para sincronização)
rsync -avz -e "ssh -i ~/.ssh/sftp_key" \
  /local/dados/ \
  usuario@servidor.com:/remoto/dados/
# rsync: só transfere arquivos que mudaram (delta)
```

## Comparativo SFTP vs FTPS

```
┌─────────────────────────┬────────────────────────────┬────────────────────────────┐
│ Aspecto                 │ SFTP                       │ FTPS                       │
├─────────────────────────┼────────────────────────────┼────────────────────────────┤
│ Base                    │ SSH (protocolo diferente)  │ FTP + TLS (extensão)       │
│ Porta padrão            │ 22 (SSH)                   │ 21 (Explicit) / 990 (Impl.)│
│ Canais TCP              │ 1 (tudo no SSH)            │ 2 (controle + dados)       │
│ Compatibilidade NAT     │ Excelente (1 porta)        │ Problemática (multi-porta) │
│ Compatibilidade firewall│ Simples (porta 22)         │ Complexa (range de portas) │
│ Autenticação            │ Senha ou chave pública SSH │ Usuário/senha via TLS      │
│ Criptografia            │ SSH (AES, ChaCha20)        │ TLS (AES, etc.)            │
│ Verificação de servidor │ Host key (fingerprint SSH) │ Certificado X.509          │
│ PKI necessária          │ Não (host keys simples)    │ Sim (certificados CA)      │
│ Suporte legado          │ Pode precisar instalar     │ FTP legado já existe       │
│ Clientes disponíveis    │ Muitos (FileZilla, WinSCP) │ Muitos (FileZilla, WinSCP) │
│ Compatibilidade Windows │ Requer servidor SSH/SFTP   │ IIS tem suporte nativo     │
│ Chave pública SSH       │ Suporte nativo             │ Não (usa certificados TLS) │
│ Quando usar             │ Maioria dos casos novos    │ Integração com FTP legado  │
└─────────────────────────┴────────────────────────────┴────────────────────────────┘
```

## SCP — alternativa simples ao SFTP

SCP (Secure Copy Protocol) também roda sobre SSH e é mais simples que SFTP para operações básicas:

```bash
# SCP — copiar arquivos via SSH
# Upload
scp arquivo.txt usuario@servidor.com:/destino/

# Download
scp usuario@servidor.com:/origem/arquivo.txt ./local/

# Diretório recursivo
scp -r /pasta-local/ usuario@servidor.com:/pasta-remota/

# Com porta customizada
scp -P 2222 arquivo.txt usuario@servidor.com:/destino/

# Com chave privada
scp -i ~/.ssh/sftp_key arquivo.txt usuario@servidor.com:/destino/

# SCP vs SFTP:
# SCP: mais simples, sem navegação interativa, não suporta renomear remotamente
# SFTP: mais completo, navegação interativa, mais operações de arquivo
```

## Quando usar cada um

```
SFTP — escolha padrão para casos novos:
  ✓ Automatização de transferências (CI/CD, scripts de backup)
  ✓ Acesso de usuários via GUI (FileZilla, WinSCP)
  ✓ Ambientes Linux/Unix (SSH já está disponível)
  ✓ Quando quer autenticação por chave pública sem PKI complexa
  ✓ Quando NAT e firewall são restrições (só porta 22)
  ✓ Quando não há FTP legado para manter compatibilidade

FTPS — quando há restrições específicas:
  ✓ Integração com sistemas legados que já usam FTP (só precisa adicionar TLS)
  ✓ Ambientes Windows com IIS (FTPS tem suporte nativo)
  ✓ Compliance que especifica TLS (FTPS usa TLS certificado por CA)
  ✓ Quando parceiros externos já têm clientes FTPS configurados
  ✓ Quando certificados X.509 são obrigatórios (vs host keys SSH)

Evitar ambos — usar alternativas modernas:
  → HTTPS + REST API (para integração entre sistemas)
  → rsync (para sincronização eficiente de diretórios)
  → S3/Cloud Storage (para arquivos em nuvem)
  → Git LFS (para arquivos grandes em repositórios)
```

## Erros comuns e armadilhas

**Confundir SFTP com FTPS:** são protocolos diferentes. Um cliente/servidor SFTP não se conecta a um servidor FTPS e vice-versa. Verificar sempre qual protocolo o servidor oferece.

**Não verificar host key SSH no SFTP:** `AutoAddPolicy()` no paramiko aceita qualquer servidor — incluindo um atacante. Em produção, verificar o fingerprint do host key na primeira conexão e rejeitar mudanças inesperadas.

**FTPS sem criptografar o canal de dados:** usar `PROT C` (Clear) no canal de dados torna o FTPS sem sentido — as credenciais ficam criptografadas mas os arquivos não. Sempre usar `PROT P` (Protected).

**Permissões de arquivo SFTP:** ao enviar arquivos, as permissões do arquivo no servidor podem não ser as esperadas (dependem do umask do servidor). Verificar permissões após upload com `sftp> stat arquivo`.

## 🧩 Quiz de Fixação

1. Um sistema de pagamentos precisa receber arquivos de lotes de transações de 50 parceiros diferentes. O time quer usar SFTP. Um parceiro reclama que não consegue se conectar porque a porta 22 está bloqueada no firewall dele. Quais são as opções para resolver sem comprometer a segurança?

2. Uma empresa usa FTPS Explicit (porta 21) para receber arquivos de parceiros. O firewall da empresa inspeciona FTP mas não consegue ler os dados do canal de dados (bloqueado). Por que isso acontece e como resolver?

3. Um script Python usa `paramiko.AutoAddPolicy()` para aceitar conexões SFTP automaticamente. Por que isso é um risco de segurança em produção e como implementar verificação de host key corretamente?

**Respostas:**

1) Opções sem comprometer segurança: (a) **Mudar a porta do servidor SFTP:** configurar o servidor SSH/SFTP para também escutar na porta 443 (HTTPS) ou 8080 — portas geralmente abertas em firewalls corporativos. Desvantagem: pode conflitar com outros serviços; (b) **Oferecer HTTPS como alternativa:** criar uma API REST com upload via HTTPS — mais moderna e não tem problemas de firewall; (c) **VPN ou túnel dedicado:** parceiro conecta via VPN, usando IP privado onde porta 22 não é bloqueada; (d) **Contatar o parceiro para abrir a porta 22 de saída:** a maioria dos firewalls corporativos modernos permite saída em portas comuns, incluindo 22 — pode ser configuração específica do parceiro que pode ser alterada. A melhor solução a longo prazo é oferecer HTTPS/S3 como alternativa ao SFTP, pois HTTPS raramente é bloqueado.

2) O problema é que com FTPS, o canal de controle (porta 21) fica criptografado após o `AUTH TLS`. O firewall stateful que normalmente "ajuda" o FTP — lendo os endereços IP/porta no PASV/PORT para abrir automaticamente a conexão de dados — não consegue mais ler esses valores (estão cifrados). Resultado: a porta de dados não é aberta automaticamente no firewall. **Como resolver:** (a) configurar um range fixo de portas passivas no servidor FTPS (ex: `PassivePortRange 50000-51000`); (b) abrir esse range no firewall da empresa; (c) **OU** usar `EPSV ALL` com IP público do servidor para evitar que o firewall precise abrir dinamicamente. O firewall não precisa mais "ler" o PASV — apenas o range fixo precisa estar aberto.

3) `AutoAddPolicy()` aceita automaticamente qualquer host key, incluindo a de um servidor falso criado por um atacante (Man-in-the-Middle). Se um DNS poisoning ou ataque de rota redirecionar a conexão para um servidor malicioso, o script aceitará sem questionar, entregando arquivos e credenciais ao atacante. **Implementação correta:**
```python
import paramiko

# Na primeira conexão: registrar o fingerprint do host key
ssh = paramiko.SSHClient()
ssh.load_system_host_keys()  # usa ~/.ssh/known_hosts
ssh.load_host_keys('/app/known_hosts')  # ou arquivo customizado

# RejectPolicy: rejeita hosts desconhecidos
ssh.set_missing_host_key_policy(paramiko.RejectPolicy())

# Na primeira conexão com host desconhecido: WarningPolicy e verificar manualmente
# ssh.set_missing_host_key_policy(paramiko.WarningPolicy())

# Alternativa: verificar o fingerprint explicitamente
def verificar_host(hostname, key):
    import base64, hashlib
    fingerprint = base64.b64encode(hashlib.md5(key.asbytes()).digest()).decode()
    expected = "xx:xx:xx:xx..."  # fingerprint esperado
    if fingerprint != expected:
        raise paramiko.BadHostKeyException(hostname, key, None)
```
O processo correto: na primeira conexão manual, verificar o fingerprint do servidor, adicioná-lo ao `known_hosts`, e depois usar `RejectPolicy` — qualquer mudança inesperada no host key dispara um erro, alertando sobre possível MITM.
