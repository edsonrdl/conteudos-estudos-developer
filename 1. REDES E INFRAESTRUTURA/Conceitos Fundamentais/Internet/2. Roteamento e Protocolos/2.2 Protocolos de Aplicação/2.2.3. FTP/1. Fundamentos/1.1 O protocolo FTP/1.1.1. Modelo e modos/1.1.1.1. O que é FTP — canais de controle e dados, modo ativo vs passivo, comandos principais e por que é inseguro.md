### O que é FTP — canais de controle e dados, modos ativo/passivo, comandos e insegurança

FTP (File Transfer Protocol) é um dos protocolos mais antigos da internet (RFC 959, 1985), projetado especificamente para transferência de arquivos entre cliente e servidor. Sua arquitetura com dois canais TCP separados — um para controle e um para dados — cria comportamentos distintos que ainda hoje causam problemas em firewalls e NAT. É considerado inseguro por transmitir credenciais e dados em texto puro, mas ainda persiste em sistemas legados e ambientes internos isolados.

---

## Arquitetura de dois canais

A característica mais incomum do FTP é usar **duas conexões TCP separadas**:

```
Canal de Controle (porta 21):
  → Conexão persistente durante toda a sessão
  → Transmite: comandos (USER, PASS, LIST, RETR, STOR...)
  → Transmite: respostas de status (200 OK, 530 Login incorrect...)
  → Permanece aberta mesmo quando não há transferência em andamento

Canal de Dados (porta 20 ou efêmera):
  → Criado apenas quando necessário (LIST, RETR, STOR, etc.)
  → Transmite: conteúdo dos arquivos, listagem de diretórios
  → Fechado após cada transferência
  → Quem abre a conexão depende do modo (ativo vs passivo)
```

```
Exemplo de sessão FTP no canal de controle (texto puro!):

Cliente → Servidor:
  USER joao
  PASS minha_senha_em_texto_puro   ← senha legível na rede!
  CWD /documentos
  PASV                             ← solicitar modo passivo
  RETR relatorio.pdf               ← baixar arquivo
  QUIT

Servidor → Cliente:
  220 Welcome to FTP Server
  331 Password required for joao
  230 User joao logged in          ← autenticado
  250 CWD command successful
  227 Entering Passive Mode (192,168,1,1,196,150)  ← IP:PORT para dados
  150 Opening data connection
  226 Transfer complete
  221 Goodbye
```

## Modo Ativo vs Modo Passivo

A diferença fundamental entre os dois modos está em **quem inicia a conexão de dados**.

### Modo Ativo (PORT) — servidor conecta no cliente

```
Fluxo do Modo Ativo:

1. Cliente → Servidor:21  (canal de controle)
   PORT 192,168,1,100,200,50   ← "me conecte no IP 192.168.1.100, porta 51250"

2. Servidor:20 → Cliente:51250  (canal de dados)
   O SERVIDOR inicia a conexão de VOLTA para o cliente

Problema com NAT/Firewall:
  Cliente está atrás de NAT:
    IP interno: 192.168.1.100
    IP público: 203.0.113.10
  
  Cliente envia: PORT 192,168,1,100,200,50  ← IP PRIVADO (não roteável!)
  Servidor tenta conectar em: 192.168.1.100:51250
  → Falha! O servidor não consegue alcançar o IP privado do cliente
  
  Mesmo com IP público: firewall do cliente bloqueia conexões de entrada
  na porta 51250 (porta efêmera não-permitida)
  
  → Modo ativo raramente funciona em redes modernas com NAT/firewall
```

### Modo Passivo (PASV) — cliente conecta no servidor

```
Fluxo do Modo Passivo:

1. Cliente → Servidor:21
   PASV   ← "abra uma porta para eu me conectar"

2. Servidor → Cliente:21
   227 Entering Passive Mode (192,168,1,1,196,150)
   → Servidor abre porta 50326 e aguarda conexão
   → Formato: h1,h2,h3,h4,p1,p2  onde porta = p1*256 + p2
   → 196*256 + 150 = 50326

3. Cliente → Servidor:50326  (cliente inicia o canal de dados)
   → Cliente faz a conexão de saída (que firewalls geralmente permitem)

Por que funciona melhor com NAT:
  O cliente sempre faz conexões de SAÍDA (tanto controle quanto dados)
  Firewalls permitem conexões de saída por padrão
  O servidor precisa ter a porta 50326 acessível (mas é controlável)
  
  Configurar range de portas passivas no servidor:
  PassivePortRange 50000-51000   ← apenas essas portas passivas
  Abrir no firewall: TCP 50000-51000 inbound no servidor FTP
```

### EPSV — Extended Passive Mode (IPv6)

```
Para IPv6, o formato antigo (192,168,1,1,196,150) não funciona.
O modo EPSV usa formato diferente:

EPSV
→ 229 Entering Extended Passive Mode (|||50326|)
→ Apenas a porta — cliente usa o mesmo IP do canal de controle
```

## Comandos FTP principais

```
Autenticação:
  USER <login>     → enviar nome de usuário
  PASS <senha>     → enviar senha (texto puro!)
  QUIT             → encerrar sessão

Navegação:
  PWD              → mostrar diretório atual (Print Working Directory)
  CWD <dir>        → mudar de diretório (Change Working Directory)
  CDUP             → subir um nível (Change to Parent Directory)
  MKD <dir>        → criar diretório
  RMD <dir>        → remover diretório

Listagem:
  LIST [path]      → listar arquivos (formato verbose, legível por humanos)
  NLST [path]      → listar apenas nomes de arquivos
  STAT             → informações do servidor ou arquivo

Transferência:
  RETR <arquivo>   → baixar arquivo do servidor (retrieve)
  STOR <arquivo>   → enviar arquivo para o servidor (store)
  APPE <arquivo>   → anexar ao arquivo existente
  DELE <arquivo>   → deletar arquivo
  RNFR <nome>      → renomear de (rename from)
  RNTO <nome>      → renomear para (rename to)

Modo e tipo:
  TYPE A           → modo ASCII (converte quebras de linha — texto)
  TYPE I           → modo Binário (raw bytes — imagens, executáveis, archives)
  PASV             → modo passivo
  PORT h,h,h,h,p,p → modo ativo (informar IP:porta do cliente)

Misc:
  NOOP             → no-operation (manter conexão viva)
  SYST             → informação do sistema operacional do servidor
  FEAT             → listar features suportadas (RFC 2389)
  SIZE <arquivo>   → tamanho do arquivo em bytes
```

## Códigos de resposta FTP

```
1xx — Resposta positiva preliminar (ação em progresso):
  125: Data connection already open; Transfer starting
  150: File status okay; Opening data connection

2xx — Resposta positiva de conclusão:
  200: Command okay
  220: Service ready for new user  ← banner de boas-vindas
  226: Closing data connection; File transfer successful
  227: Entering Passive Mode       ← resposta ao PASV
  230: User logged in              ← autenticação bem-sucedida
  250: Requested file action okay  ← CWD, DELE, etc.
  331: User name okay, need password
  257: "path" created              ← MKD bem-sucedido

4xx — Erro transitório (tente novamente):
  421: Service not available
  425: Can't open data connection
  450: File unavailable (busy)

5xx — Erro permanente:
  500: Syntax error, command unrecognized
  530: Not logged in / Login incorrect
  550: File unavailable (not found, no access)
  553: File name not allowed
```

## Por que FTP é inseguro

```
Problema 1 — Credenciais em texto puro:
  USER joao
  PASS minha_senha_123
  
  Qualquer sniffer de rede (tcpdump, Wireshark) captura username e senha
  Em uma rede não-confiável: comprometimento imediato

Problema 2 — Dados em texto puro:
  Arquivos transferidos sem criptografia
  → Documentos confidenciais, configurações, bases de dados: todos legíveis

Problema 3 — Sem verificação de integridade:
  Não há garantia que o arquivo chegou sem alteração
  → Man-in-the-middle pode modificar o arquivo em trânsito

Problema 4 — Sem autenticação do servidor:
  Cliente não verifica que está falando com o servidor legítimo
  → Ataque de spoofing: servidor falso aceita credenciais

Problema 5 — Vulnerabilidades conhecidas:
  FTP bounce attack (PORT abuse): usar um servidor FTP como proxy para escanear outros hosts
  Brute force: sem rate limiting nativo
  Anonymous FTP: muitos servidores permitem login anônimo sem senha
  
Contextos onde FTP AINDA pode ser aceitável:
  → Redes totalmente isoladas (air-gapped, sem internet)
  → Sistemas legados que não suportam SFTP/FTPS e não podem ser atualizados
  → Dados públicos não-sensíveis em FTP anônimo (ex: mirrors de software open-source)
  
Em qualquer outro contexto: usar SFTP ou FTPS
```

## FTP anônimo

```
Muitos servidores FTP públicos permitem acesso sem senha:

USER anonymous
PASS qualquer-email@exemplo.com   ← convenção histórica (email como senha)
ou
PASS anonymous

Uso legítimo:
  → Mirrors de distribuições Linux
  → Repositórios de software open-source
  → Arquivos públicos de organizações

Risco:
  → Servidor mal-configurado expõe arquivos internos
  → Diretório de upload permite hospedar conteúdo malicioso
```

## Erros comuns e armadilhas

**Modo ativo falha atrás de NAT:** praticamente universal hoje. Sempre configurar clientes FTP para modo passivo (PASV) por padrão.

**TYPE I obrigatório para binários:** sem `TYPE I`, o FTP converte quebras de linha (`\r\n` ↔ `\n`) para arquivos no modo ASCII. Isso corrompe arquivos binários (imagens, executáveis, ZIPs). Sempre usar modo binário (`TYPE I`) para transferir qualquer coisa que não seja texto puro.

**Firewall bloqueando range passivo:** se o servidor não configurar `PassivePortRange` e o firewall não abrir essas portas, PASV também falha. Configurar um range específico (ex: 50000-51000) e abrir no firewall.

## 🧩 Quiz de Fixação

1. Por que o modo ativo FTP (PORT) quase sempre falha em ambientes modernos com NAT, enquanto o modo passivo (PASV) funciona com mais frequência?

2. Um desenvolvedor transfere um arquivo executável via FTP sem mudar o tipo. O arquivo parece transferido com sucesso (226 Transfer complete), mas ao executar no destino ele falha. Qual é a causa provável e como corrigir?

3. Uma empresa usa FTP interno para transferir backups entre servidores na mesma rede privada (LAN). O analista de segurança recomenda migrar para SFTP. A empresa argumenta que "é rede interna, não tem risco". Quais cenários de ameaça real existem mesmo em rede interna que justificam a migração?

**Respostas:**

1) No modo ativo, **o servidor inicia a conexão de dados** de volta para o cliente (porta 20 do servidor → porta efêmera do cliente). O problema é duplo: (a) o cliente geralmente está atrás de NAT e envia seu IP privado (ex: 192.168.1.100) no comando PORT — o servidor na internet não consegue rotear para esse IP privado; (b) mesmo com IP público correto, o firewall/NAT do cliente bloqueia conexões de **entrada** na porta efêmera (como 51250) pois não foram abertas explicitamente. No modo passivo, é o **cliente quem inicia ambas as conexões** (controle e dados) — conexões de saída, que firewalls permitem por padrão. O servidor abre uma porta específica e o cliente conecta nela.

2) O problema é que a transferência foi feita no modo padrão **ASCII** (`TYPE A`). No modo ASCII, o FTP converte automaticamente quebras de linha entre formatos de SO (`\r\n` do Windows ↔ `\n` do Unix). Para um arquivo executável binário, essa conversão corrompe bytes — o bit pattern do executável é alterado, tornando-o inválido. **Correção:** antes de transferir, executar `TYPE I` (ou `BIN`) no cliente FTP para mudar para modo binário (raw bytes, sem conversão). A maioria dos clientes FTP gráficos modernos usa binário por padrão, mas clientes de linha de comando podem defaultar para ASCII.

3) Ameaças reais em rede interna: (a) **Funcionário malicioso:** qualquer máquina na mesma LAN com acesso ao switch pode capturar tráfego FTP em texto puro — credenciais e arquivos de backup — usando um sniffer como Wireshark; (b) **Malware lateral:** se uma máquina da rede for comprometida, o malware pode monitorar o tráfego FTP e exfiltrar dados de backup (que geralmente contêm dados sensíveis de toda a empresa); (c) **Segmentação de rede inadequada:** muitas "redes internas" não são realmente isoladas — VLANs mal configuradas, acesso de visitantes Wi-Fi, dispositivos IoT na mesma rede; (d) **Compliance:** regulações como PCI DSS, HIPAA e LGPD exigem criptografia de dados em trânsito mesmo em redes internas para dados sensíveis. A premissa "rede interna = sem risco" é um dos erros de segurança mais comuns — a maioria dos incidentes de segurança tem origem interna ou lateral.
