### O que é HTTP — modelo request/response, stateless, conexões TCP e papel na web

HTTP (HyperText Transfer Protocol) é o protocolo de comunicação da camada de aplicação que define como mensagens são trocadas entre um **cliente** (browser, app mobile, CLI, serviço backend) e um **servidor** (web server, API). É o fundamento de toda a Web e da grande maioria das APIs modernas. Entender o HTTP não é opcional para um desenvolvedor — é o alfabeto com o qual a internet escreve.

---

## O modelo Request/Response

HTTP funciona em um ciclo simples e rígido: o cliente **sempre inicia** enviando uma requisição; o servidor **sempre responde** com uma resposta. Nunca o contrário (em HTTP tradicional — WebSocket é diferente).

```
Ciclo fundamental HTTP:

Cliente                              Servidor
  │                                     │
  │──── REQUEST ────────────────────▶   │
  │   Método: GET                       │
  │   URL: /api/usuarios/123            │
  │   Headers: Authorization, Accept    │
  │   Body: (vazio no GET)              │
  │                                     │ processa
  │                                     │ consulta banco
  │                                     │ serializa resposta
  │   ◀──── RESPONSE ────────────────  │
  │   Status: 200 OK                    │
  │   Headers: Content-Type, Cache-...  │
  │   Body: {"id": 123, "nome": "..."}  │
  │                                     │
```

Uma requisição HTTP tem **4 componentes**:
1. **Request Line** — método + URL + versão HTTP
2. **Headers** — metadados da requisição (quem sou, o que aceito, autenticação)
3. **Blank Line** — separador obrigatório entre headers e body
4. **Body** (opcional) — dados enviados ao servidor

Uma resposta HTTP tem **3 componentes**:
1. **Status Line** — versão HTTP + código de status + mensagem
2. **Headers** — metadados da resposta (tipo do conteúdo, cache, cookies)
3. **Body** (opcional) — dados retornados pelo servidor

```
Exemplo real de requisição HTTP em texto puro:

POST /api/login HTTP/1.1
Host: api.meusite.com
Content-Type: application/json
Authorization: Bearer eyJ...
Accept: application/json
Content-Length: 45

{"email": "user@exemplo.com", "senha": "123"}
```

```
Resposta correspondente:

HTTP/1.1 200 OK
Content-Type: application/json
Set-Cookie: session=abc123; HttpOnly; Secure
Cache-Control: no-store
Content-Length: 87

{"token": "eyJ...", "expira_em": "2024-01-16T10:00:00Z", "usuario": "user@exemplo.com"}
```

## Stateless — o que significa e por que importa

HTTP é **stateless** (sem estado): cada requisição é completamente independente da anterior. O servidor não guarda nenhuma memória de interações passadas com o cliente. Se você faz 100 requisições para o mesmo endpoint, o servidor trata cada uma como se fosse a primeira.

```
Stateless em prática:

Requisição 1: GET /usuario/perfil
  Servidor: "Quem é esse cliente? Não sei. Precisa se autenticar."

Requisição 2: POST /login + credenciais → token retornado
  Servidor: "OK, autenticado. Aqui está seu token."
  Servidor depois: "Não lembro nada disso."

Requisição 3: GET /usuario/perfil + Authorization: Bearer <token>
  Servidor: "Recebo um token. Vou validar... OK, é o usuário X."
  (sem o token, seria igual à Requisição 1)
```

**O stateless não é uma limitação — é um design intencional:**
- Facilita escalar horizontalmente (qualquer servidor pode atender qualquer requisição, sem sessão presa a um servidor específico)
- Torna o sistema mais resiliente (servidor reiniciado não perde estado de clientes)
- Simplifica o cache (requisições idênticas sempre produzem o mesmo resultado se os dados não mudaram)

### Como o estado é mantido então?

Se HTTP é stateless, como um site sabe que você está logado?

```
Mecanismos para simular estado em HTTP stateless:

1. Cookies:
   Servidor → Set-Cookie: session=abc123
   Cliente armazena e reenvia → Cookie: session=abc123
   Servidor valida o cookie a cada requisição

2. Tokens (JWT, OAuth):
   Servidor → retorna token no body
   Cliente armazena (localStorage, memória) e reenvia → Authorization: Bearer <token>
   Servidor valida o token a cada requisição

3. Query Parameters (menos seguro, evitar para auth):
   GET /dashboard?token=abc123
```

## HTTP sobre TCP

HTTP opera sobre o **TCP** na camada de transporte. Antes de qualquer requisição HTTP, uma conexão TCP precisa ser estabelecida:

```
Fluxo completo — do zero até a resposta HTTP:

1. Resolução DNS:
   Cliente: "Qual é o IP de api.meusite.com?"
   DNS: "É 93.184.216.34"

2. TCP Handshake (3-way):
   Cliente → SYN → Servidor
   Cliente ← SYN-ACK ← Servidor
   Cliente → ACK → Servidor
   (conexão estabelecida — ~1 RTT)

3. TLS Handshake (se HTTPS):
   Negociação de chaves e certificados
   (~1-2 RTTs adicionais)

4. HTTP Request:
   Cliente → GET /api/dados HTTP/1.1 ... → Servidor

5. HTTP Response:
   Cliente ← 200 OK ... ← Servidor

6. Conexão TCP fechada (ou mantida para reutilização — keep-alive)
```

### Custo de uma nova conexão TCP

Estabelecer uma conexão TCP tem custo de latência — pelo menos 1 RTT (Round Trip Time) antes da primeira requisição chegar ao servidor:

```
RTT de ~100ms (cliente → servidor):
  TCP Handshake: 100ms
  TLS Handshake: 200ms (2 RTTs)
  HTTP Request:  100ms
  HTTP Response: 100ms (dados chegando)
  Total: ~500ms só de overhead de conexão

Para mitigar isso:
  → HTTP/1.1 keep-alive: reutiliza a conexão TCP para múltiplas requisições
  → HTTP/2: múltiplas requisições na mesma conexão TCP (multiplexing)
  → HTTP/3: usa QUIC (sobre UDP) — elimina o custo do TCP handshake
```

## HTTP vs HTTPS

HTTP e HTTPS diferem apenas pela camada de segurança:

```
HTTP:
  Cliente → [TCP] → Servidor
  Dados em texto puro na rede
  Qualquer interceptador lê tudo

HTTPS:
  Cliente → [TCP] → [TLS] → Servidor
  Dados criptografados na rede
  Interceptador vê apenas ruído criptografado
```

HTTP na porta **80** (padrão), HTTPS na porta **443** (padrão). Ambas são apenas convenções — qualquer porta funciona se configurada corretamente.

## Papel do HTTP na web moderna

```
HTTP está em tudo:
  ✓ Navegadores carregando páginas HTML, CSS, JS
  ✓ APIs REST entre frontend e backend
  ✓ APIs entre microserviços (HTTP/gRPC sobre HTTP/2)
  ✓ Webhooks (servidor A chama servidor B via HTTP)
  ✓ Downloads e uploads de arquivos
  ✓ Streaming de vídeo (HLS/DASH usam HTTP)
  ✓ Server-Sent Events (SSE — streaming de dados do servidor)
  ✓ GraphQL (geralmente sobre HTTP POST)
  ✓ WebRTC signaling (negociação via HTTP)

O que NÃO é HTTP:
  ✗ WebSocket (usa HTTP para o handshake inicial, depois muda de protocolo)
  ✗ Streaming de vídeo ao vivo em baixa latência (RTMP, SRT)
  ✗ Jogos em tempo real (UDP direto ou WebRTC)
  ✗ Transferência de arquivos (FTP — embora HTTP também possa fazer isso)
```

## Erros comuns e armadilhas

**Assumir que HTTP mantém estado:** muitos bugs de autenticação vêm de código que assume que o servidor "lembra" do login anterior. Cada requisição precisa enviar as credenciais/token — o servidor não guarda contexto entre elas.

**Confundir HTTP com HTML:** HTTP é o protocolo de transporte; HTML é um tipo de conteúdo. HTTP pode transportar JSON, imagens, vídeo, binários — qualquer coisa. A confusão vem de que browsers usam HTTP para buscar HTML por padrão.

**Usar HTTP em produção (sem S):** qualquer dado sensível trafegado em HTTP puro é legível por qualquer ponto intermediário na rede. Em 2024, HTTPS é obrigatório para qualquer aplicação em produção — incluindo APIs internas que trafegam entre serviços.

## 🧩 Quiz de Fixação

1. HTTP é descrito como "stateless". Por que isso não significa que aplicações web não podem ter estado (ex: usuário logado), e como o estado é implementado sobre um protocolo stateless?

2. Por que o primeiro carregamento de uma página HTTPS pode ser significativamente mais lento que os subsequentes, e quais mecanismos do HTTP moderno reduzem esse overhead?

3. Um desenvolvedor backend recebe uma requisição e quer saber: (a) qual usuário está fazendo a requisição, (b) em qual formato os dados foram enviados, (c) qual formato o cliente aceita na resposta. Onde no protocolo HTTP cada uma dessas informações está tipicamente localizada?

**Respostas:**

1) O stateless significa apenas que o **servidor** não guarda memória entre requisições — não que a aplicação não pode ter estado. O estado é implementado no **cliente** (que guarda um token/cookie) e reenviado em cada requisição. O servidor valida esse estado a cada requisição de forma independente. Assim, o "estado" vive no token: quando o cliente envia `Authorization: Bearer eyJ...`, o servidor decodifica o JWT e extrai quem é o usuário — reconstruindo o "estado" a partir do token, sem ter memorizado nada. Stateless + tokens = escalabilidade horizontal sem sessões presas a servidores específicos.

2) O primeiro carregamento requer: (1) resolução DNS (~50-100ms), (2) TCP handshake (~1 RTT = 50-200ms dependendo da distância), (3) TLS handshake (~1-2 RTTs adicionais = 100-400ms), e só então a primeira requisição HTTP. Subsequentes reutilizam a conexão existente (HTTP keep-alive) ou a conexão já estabelecida (HTTP/2 multiplexing), eliminando o overhead de TCP e TLS. Mecanismos que reduzem isso: **HTTP/2 connection reuse** (uma conexão serve múltiplas requisições em paralelo), **TLS Session Resumption** (reutiliza parâmetros TLS de sessões anteriores, reduzindo handshake a 0 RTTs), **HTTP/3 com QUIC** (elimina o TCP handshake combinando com o TLS em um único RTT), e **DNS caching** (evita re-resolver o domínio).

3) (a) **Quem é o usuário:** tipicamente no header `Authorization` (ex: `Authorization: Bearer eyJ...` para JWT, ou `Authorization: Basic dXNlcjpwYXNz` para Basic Auth), ou no header `Cookie` se a autenticação usa sessão por cookie. (b) **Formato dos dados enviados:** no header `Content-Type` da requisição (ex: `Content-Type: application/json` ou `Content-Type: multipart/form-data; boundary=...`). (c) **Formato aceito na resposta:** no header `Accept` da requisição (ex: `Accept: application/json` ou `Accept: text/html,application/json;q=0.9,*/*;q=0.8` com preferências ponderadas).
