### HTTP/1.1 vs HTTP/2 vs HTTP/3 — conexões, multiplexing, header compression e QUIC

Cada versão do HTTP resolve problemas de performance da versão anterior, mantendo a semântica do protocolo intacta — os métodos, status codes e headers continuam os mesmos. O que muda é **como** as mensagens são transportadas: do texto puro em conexões serializadas (HTTP/1.1) ao binário multiplexado (HTTP/2) ao UDP com QUIC (HTTP/3).

---

## HTTP/1.1 — o padrão que durou décadas (1997–hoje)

HTTP/1.1 foi uma evolução enorme sobre o HTTP/1.0, introduzindo **conexões persistentes** (keep-alive) e **pipelining**. Mesmo assim, carrega limitações estruturais que só versões posteriores resolveram.

### Características do HTTP/1.1

```
Formato: texto puro (ASCII legível por humanos)

GET /index.html HTTP/1.1
Host: www.exemplo.com
Connection: keep-alive
Accept: text/html

(linha em branco)
```

**Conexões persistentes (keep-alive):**
```
HTTP/1.0 (sem keep-alive):
  Conexão TCP → Requisição 1 → Resposta 1 → Fecha TCP
  Nova Conexão TCP → Requisição 2 → Resposta 2 → Fecha TCP
  (3-way handshake para CADA requisição)

HTTP/1.1 (com keep-alive):
  Conexão TCP → Req 1 → Resp 1 → Req 2 → Resp 2 → Req N → Resp N → Fecha TCP
  (1 handshake para N requisições)
```

### Head-of-Line Blocking (HOL Blocking) — o problema central

```
Pipelining HTTP/1.1 (sequencial dentro de 1 conexão):

Conexão TCP única:
  ──Req1──▶──Req2──▶──Req3──▶
  ◀─Resp1──◀─Resp2──◀─Resp3─

Problema: Req2 espera Resp1 antes de poder ser processada
          Se Resp1 demora (arquivo grande, banco lento):
          Req2 e Req3 ficam bloqueadas esperando

Resultado na prática:
  Browsers abrem 6 conexões TCP paralelas por domínio para contornar o HOL
  → 6 handshakes TCP simultâneos
  → 6 fluxos de dados paralelos
  → Complexidade de gerenciamento no servidor
```

### Problemas do HTTP/1.1

```
1. HOL Blocking:     uma resposta lenta bloqueia as seguintes
2. Headers repetidos: cada requisição reenvia os mesmos headers
                      (User-Agent, Accept, Authorization, Cookie...)
                      sem compressão — puro overhead
3. Sem priorização:  todas as requisições têm o mesmo peso
4. Sem server push:  servidor só responde, nunca inicia
```

## HTTP/2 — binário, multiplexado e comprimido (2015)

HTTP/2 (baseado no SPDY do Google) é uma reescrita do transporte mantendo a semântica HTTP idêntica. O mesmo código de aplicação funciona em HTTP/1.1 e HTTP/2 — a diferença é invisível para a aplicação.

### Frames binários — tudo é binário agora

```
HTTP/1.1 (texto):
  GET /api/dados HTTP/1.1\r\n
  Host: api.exemplo.com\r\n
  ...

HTTP/2 (binário):
  [HEADERS Frame]  [DATA Frame]  [SETTINGS Frame]
  binário compacto, não legível diretamente
  mas muito mais eficiente para parsing e transmissão
```

### Multiplexing — o fim do HOL Blocking na camada HTTP

```
HTTP/2 — streams paralelos na MESMA conexão TCP:

                    Conexão TCP única
  ┌─────────────────────────────────────────────────────┐
  │                                                     │
  │  Stream 1: [HEADERS: GET /api/dados]                │
  │             [DATA: resposta dados]                  │
  │                                                     │
  │  Stream 3: [HEADERS: GET /imagem.jpg]               │
  │             [DATA: chunk 1][DATA: chunk 2][DATA: 3] │
  │                                                     │
  │  Stream 5: [HEADERS: POST /login]                   │
  │             [DATA: body][HEADERS: 200 OK]           │
  │                                                     │
  └─────────────────────────────────────────────────────┘

Streams são intercalados — bytes de stream 1, 3 e 5 se misturam
no nível TCP mas são reassemblados pelo HTTP/2 corretamente

Resultado:
  → Imagem grande não bloqueia resposta da API
  → 1 conexão TCP substitui as 6 paralelas do HTTP/1.1
  → Menor uso de memória no servidor (menos sockets)
```

### HPACK — compressão de headers

```
HTTP/1.1 — headers repetidos em cada requisição:

Req 1: User-Agent: Mozilla/5.0 (Windows NT 10.0) Chrome/120
       Accept: text/html,application/json;q=0.9
       Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6Ikp...
       Cookie: session=abc123; preferences=dark_mode

Req 2 (mesma sessão, mesmo contexto):
       User-Agent: Mozilla/5.0 (Windows NT 10.0) Chrome/120  ← IDÊNTICO
       Accept: text/html,application/json;q=0.9               ← IDÊNTICO
       Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6Ikp... ← IDÊNTICO
       Cookie: session=abc123; preferences=dark_mode           ← IDÊNTICO

Total headers Req 1 + Req 2: ~800 bytes enviados duas vezes = ~1.600 bytes

HTTP/2 com HPACK (compressão):
  Req 1: [índice 1] [índice 2] [índice 3] [índice 4]  → ~200 bytes
  Req 2: [ref 1] [ref 2] [ref 3] [ref 4]              → ~20 bytes
  (apenas referências ao dicionário — não repete o valor)

  Economia: até 90% no tamanho dos headers em sessões estabelecidas
```

### Server Push — envio proativo

```
Sem Server Push:
  Browser: GET /index.html
  Servidor: responde com HTML
  Browser parseia HTML, descobre que precisa de styles.css e app.js
  Browser: GET /styles.css  (nova requisição)
  Browser: GET /app.js      (nova requisição)
  Total: 3 round trips

Com HTTP/2 Server Push:
  Browser: GET /index.html
  Servidor: responde com HTML + faz PUSH de styles.css + PUSH de app.js
  Browser já tem os recursos quando o HTML é parseado
  Total: 1 round trip

Na prática: Server Push teve adoção limitada e foi removido no HTTP/3
O problema: o servidor não sabe o que o browser já tem em cache
→ Empurra recursos desnecessários, desperdiçando banda
→ Substituído por <link rel="preload"> e Early Hints (103)
```

### HTTP/2 ainda tem um problema: TCP HOL Blocking

```
HTTP/2 resolve HOL blocking na camada HTTP (multiplexing)
MAS o TCP ainda sofre HOL blocking na camada de transporte:

  Se um pacote TCP é perdido:
  Todo o fluxo TCP aguarda a retransmissão
  → Todos os streams HTTP/2 na mesma conexão ficam parados
  → Em redes com alta perda de pacotes, HTTP/2 pode ser pior que HTTP/1.1
     (HTTP/1.1 com 6 conexões: perda em 1 não afeta as outras 5)

Este é o problema que HTTP/3 resolve.
```

## HTTP/3 — sobre UDP com QUIC (2022)

HTTP/3 muda o transporte de TCP para **QUIC** (Quick UDP Internet Connections), um protocolo desenvolvido pelo Google e padronizado pelo IETF. O resultado: multiplexing sem HOL blocking mesmo em redes com perda de pacotes, e conexões muito mais rápidas.

### QUIC — o que muda fundamentalmente

```
HTTP/1.1 e HTTP/2:
  Aplicação (HTTP) → TCP → IP → Rede

HTTP/3:
  Aplicação (HTTP) → QUIC → UDP → IP → Rede

Por que UDP? UDP não tem as garantias de entrega do TCP —
mas o QUIC implementa suas próprias garantias de forma mais inteligente:
  ✓ Controle de congestionamento
  ✓ Retransmissão de pacotes perdidos
  ✓ Ordenação de dados
  ✗ HOL Blocking em nível de stream (streams são independentes!)
```

### 0-RTT e 1-RTT — conexões mais rápidas

```
HTTP/2 (TCP + TLS):
  TCP Handshake:  1 RTT (SYN → SYN-ACK → ACK)
  TLS Handshake:  1-2 RTTs
  Primeira requisição: 2-3 RTTs de overhead

HTTP/3 (QUIC):
  Primeira conexão: 1 RTT (QUIC combina TCP+TLS em um único handshake)
  Conexão resumida: 0-RTT (cliente usa parâmetros de sessão anterior)
                    → Dados enviados JUNTO com o handshake!

Resultado prático:
  HTTP/2 primeira carga: ~300ms de overhead (30ms RTT × 3)
  HTTP/3 primeira carga: ~30ms de overhead (30ms RTT × 1)
  HTTP/3 conexão resumida: ~0ms de overhead
```

### Connection Migration — mobilidade sem reconexão

```
HTTP/2 (TCP):
  Você está no Wi-Fi, fazendo download grande
  Você muda para 4G
  → Conexão TCP é quebrada (IP muda)
  → Download reinicia do zero

HTTP/3 (QUIC):
  Você está no Wi-Fi, fazendo download grande
  Você muda para 4G
  → QUIC usa Connection ID (não depende de IP/porta)
  → Download continua de onde parou
  → Zero interrupção visível ao usuário

Caso de uso: streaming de vídeo, downloads longos em dispositivos móveis
```

## Como verificar qual versão está sendo usada

```bash
# curl — ver a versão HTTP usada na resposta
curl -I --http2 https://www.google.com
# Mostra: HTTP/2 200

curl -I --http3 https://www.cloudflare.com
# Mostra: HTTP/3 200

# Chrome DevTools:
# Network → clique na requisição → Protocol
# h1 = HTTP/1.1, h2 = HTTP/2, h3 = HTTP/3

# Verificar se um servidor suporta HTTP/2
curl -I --http2 https://api.meusite.com 2>&1 | grep "HTTP/"

# Verificar headers de resposta com versão
curl -sv https://exemplo.com 2>&1 | grep "< HTTP"
```

## Quando cada versão é usada na prática

```
HTTP/1.1:
  → APIs internas em rede local (latência < 1ms — overhead não importa)
  → Clientes legados que não suportam HTTP/2
  → Debugging simples (texto puro = fácil de ler)
  → Ainda dominante em muitos ambientes corporativos

HTTP/2:
  → APIs públicas modernas (AWS, Google, GitHub — todos usam HTTP/2)
  → Sites com muitos recursos (CSS, JS, imagens)
  → Mobile apps com conexões instáveis (multiplexing reduz o impacto)
  → Padrão atual para a maioria das APIs REST modernas

HTTP/3:
  → CDNs (Cloudflare, Fastly — adoção alta)
  → Streaming de vídeo e áudio
  → Jogos com latência crítica
  → Aplicações mobile com troca frequente de rede
  → Crescendo rapidamente: Google, Meta, Cloudflare já usam
```

## 🧩 Quiz de Fixação

1. Um site carrega 20 recursos (CSS, JS, imagens). Em HTTP/1.1, browsers abrem até 6 conexões paralelas por domínio. Em HTTP/2, apenas 1 conexão é usada. Por que o HTTP/2 não é simplesmente "mais lento" por usar menos conexões?

2. Um servidor HTTP/2 está em uma rede com 2% de perda de pacotes. Um usuário percebe que a performance é pior que esperado, às vezes pior que HTTP/1.1. Qual é a causa e por que HTTP/3 resolveria isso?

3. O que é 0-RTT no HTTP/3 e qual é o risco de segurança associado a ele?

**Respostas:**

1) Com HTTP/1.1 e 6 conexões, cada conexão carrega apenas 1 recurso por vez (HOL blocking dentro da conexão). Com HTTP/2 e 1 conexão, todos os 20 recursos são enviados **em paralelo** na mesma conexão via multiplexing — cada recurso em seu próprio stream. O HTTP/2 não serializa; ele intercala bytes de todos os 20 streams simultaneamente. Além disso, HTTP/2 usa HPACK para comprimir headers (economizando ~80% em sessões estabelecidas) e evita o overhead de 6 handshakes TCP. O resultado é frequentemente mais rápido que HTTP/1.1, não mais lento — especialmente em redes de alta latência onde o custo de setup das conexões TCP é significativo.

2) A causa é o **TCP HOL Blocking**. HTTP/2 resolveu o HOL blocking na camada HTTP (via multiplexing de streams), mas todos os streams ainda compartilham uma única conexão TCP. Com 2% de perda de pacotes, o TCP frequentemente perde um pacote e bloqueia **todos** os streams enquanto espera a retransmissão — em HTTP/1.1 com 6 conexões, uma perda em uma conexão não afeta as outras 5. HTTP/3 resolve isso porque o QUIC opera sobre UDP e trata cada stream de forma independente: a perda de um pacote do stream X não bloqueia os streams Y e Z. Cada stream tem sua própria fila de retransmissão — eliminando o HOL blocking mesmo no nível de transporte.

3) O **0-RTT** permite que o cliente envie dados HTTP **junto com** o primeiro pacote do handshake QUIC, usando parâmetros de segurança de uma sessão anterior (session tickets). Isso elimina completamente o overhead de conexão para reconexões. O risco é a vulnerabilidade a **replay attacks**: um atacante que intercepta o pacote 0-RTT pode reenviar o mesmo pacote para o servidor mais tarde, fazendo com que a requisição seja processada novamente. Isso é problemático para requisições não-idempotentes (ex: `POST /pagamento` — o pagamento seria cobrado duas vezes). A mitigação padrão é limitar 0-RTT a requisições idempotentes (GET, HEAD) e rejeitar 0-RTT para POST com efeitos colaterais. Servidores podem também usar tokens anti-replay, mas com custo de complexidade.
