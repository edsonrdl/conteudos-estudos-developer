### URL completa — scheme, host, port, path, query string e fragment

A URL (Uniform Resource Locator) é o endereço de um recurso na internet. Cada parte tem um significado preciso e regras específicas de formatação. Entender a anatomia completa de uma URL é fundamental para trabalhar com APIs, debugar requisições, configurar servidores e evitar erros de parsing.

---

## Anatomia completa de uma URL

```
https://usuario:senha@api.empresa.com:8443/v2/produtos/123/avaliacoes?status=aprovado&page=2&limit=10#resultados

│       │              │               │    │                         │                               │
│       │              │               │    │                         │                               └─ Fragment
│       │              │               │    │                         └─ Query String
│       │              │               │    └─ Path
│       │              │               └─ Port
│       │              └─ Host
│       └─ User Info (raro em HTTP)
└─ Scheme
```

---

## 1. Scheme (Protocolo)

O scheme define o protocolo a ser usado para acessar o recurso.

```
https://exemplo.com
│
└─ Scheme

Schemes comuns:
  https   → HTTP sobre TLS (padrão para web)
  http    → HTTP sem criptografia (evitar em produção)
  ftp     → File Transfer Protocol
  ftps    → FTP sobre TLS
  sftp    → SSH File Transfer Protocol
  ws      → WebSocket
  wss     → WebSocket sobre TLS
  mailto  → Endereço de e-mail
  file    → Arquivo local (file:///home/user/doc.pdf)
  data    → Dados inline (data:image/png;base64,...)
  jdbc    → Conexão com banco de dados Java

Regras:
  → Sempre seguido de "://"
  → Case-insensitive (HTTPS == https), mas convencionalmente minúsculo
  → Obrigatório em URLs absolutas
```

---

## 2. User Info (Autenticação na URL — evitar)

```
ftp://usuario:senha@ftp.empresa.com

Formato: scheme://usuario:senha@host
                    │      │
                    │      └─ Senha em texto puro na URL!
                    └─ Nome de usuário

Por que evitar:
  → Credenciais expostas em logs de servidor, histórico do browser, Referer header
  → Extremamente inseguro — qualquer sistema que logge a URL vê as credenciais
  → Correto apenas para FTP legado ou conexões de banco local para dev
  → Em APIs HTTP: use Authorization header em vez disso
```

---

## 3. Host

O host identifica o servidor que possui o recurso. Pode ser um domínio ou um endereço IP.

```
https://api.empresa.com/dados
        │
        └─ Host

Formatos possíveis:
  api.empresa.com          → Nome de domínio (FQDN)
  empresa.com              → Domínio raiz
  sub.api.empresa.com      → Subdomínio
  localhost                → Loopback local
  192.168.1.10             → IPv4 direto
  [2001:db8::1]            → IPv6 (obrigatório entre colchetes!)
  example.internal         → Domínio interno (DNS privado)

Componentes de um domínio:
  sub.api.empresa.com.br
  │   │   │       │  └─ ccTLD (country code Top-Level Domain)
  │   │   │       └─ TLD (Top-Level Domain)
  │   │   └─ Domínio de segundo nível (SLD)
  │   └─ Subdomínio
  └─ Subsubdomínio

O host é resolvido para um IP via DNS antes de estabelecer a conexão.
```

---

## 4. Port (Porta)

A porta identifica qual serviço no servidor deve receber a conexão.

```
https://api.empresa.com:8443/dados
                        │
                        └─ Port

Portas padrão (omitidas quando usadas):
  http  → 80     (https://exemplo.com == https://exemplo.com:80)
  https → 443    (https://exemplo.com == https://exemplo.com:443)
  ftp   → 21
  ftps  → 990
  ssh   → 22
  smtp  → 25, 465 (TLS), 587 (STARTTLS)
  imap  → 143, 993 (TLS)
  pop3  → 110, 995 (TLS)
  mysql → 3306
  postgres → 5432
  redis → 6379
  mongodb → 27017

Portas customizadas (explícitas na URL):
  https://api.empresa.com:8443/endpoint   → API em porta não-padrão
  http://localhost:3000                    → App local de desenvolvimento
  http://localhost:5432                   → Nunca — postgres não fala HTTP!
                                            (mas URI de conexão sim: postgresql://host:5432/db)

Range de portas:
  0-1023:     Well-known ports (requerem root no Linux)
  1024-49151: Registered ports (convenções de serviços)
  49152-65535: Dynamic/private (conexões efêmeras do cliente)
```

---

## 5. Path (Caminho)

O path identifica o recurso específico dentro do servidor, seguindo uma hierarquia similar a um sistema de arquivos.

```
https://api.empresa.com/v2/produtos/123/avaliacoes
                        │
                        └─ Path: /v2/produtos/123/avaliacoes

Estrutura típica em APIs REST:
  /v2                      → Versão da API
  /v2/produtos             → Coleção de recursos
  /v2/produtos/123         → Recurso específico (ID 123)
  /v2/produtos/123/avaliacoes → Sub-recurso (avaliacoes do produto 123)

Path Parameters vs Query Parameters:
  /produtos/123            → Path param (identifica O recurso)
  /produtos?id=123         → Query param (filtra recursos — evitar para ID)

  Regra prática:
  Path param: faz parte da identidade do recurso
              /usuarios/{id}    → qual usuário específico
              /pedidos/{id}/itens → itens de um pedido específico
  
  Query param: filtra, pagina, ordena uma coleção
              /usuarios?role=admin&page=2

Caracteres especiais no path:
  / → separador de segmentos (reservado)
  . → ponto (permitido, mas .. tem semântica especial)
  ~ → tilde (permitido)
  - _ → hífen e underscore (permitidos e recomendados)
  
  Espaços e caracteres especiais DEVEM ser percent-encoded:
  /produtos/camiseta azul → ERRADO
  /produtos/camiseta%20azul → CORRETO
  /produtos/camiseta-azul → MELHOR (sem encoding necessário)

Case sensitivity:
  Depende do servidor/SO:
  Linux (ext4): /Produto != /produto (case-sensitive)
  Windows (NTFS): /Produto == /produto (case-insensitive)
  Convenção em APIs: lowercase com hífens (/meus-pedidos, não /MeusPedidos)
```

## 6. Query String

A query string contém pares chave=valor para filtrar, paginar, configurar ou passar parâmetros sem alterar a identidade do recurso.

```
https://api.empresa.com/produtos?status=ativo&page=2&limit=10&ordenar=preco_asc
                                 │
                                 └─ Query String

Anatomia:
  ?           → Inicia a query string
  chave=valor → Par chave-valor
  &           → Separa múltiplos pares

Exemplos por tipo de uso:

Filtragem:
  /produtos?categoria=eletronicos&marca=samsung&preco_max=5000

Paginação:
  /usuarios?page=3&per_page=20
  /usuarios?offset=40&limit=20
  /usuarios?cursor=eyJpZCI6NDJ9  (cursor-based pagination)

Ordenação:
  /produtos?sort=preco&order=asc
  /produtos?ordenar=nome_desc

Busca:
  /produtos?q=notebook+gamer
  /produtos?search=notebook%20gamer

Seleção de campos (sparse fieldsets):
  /usuarios/123?fields=id,nome,email  (não retorna outros campos)

Inclusão de relacionamentos:
  /pedidos/456?include=itens,cliente

Formato da resposta:
  /relatorio?format=csv
  /dados?lang=pt-BR
```

### Encoding da query string

```
Caracteres que DEVEM ser percent-encoded na query string:

Espaço:  " " → %20 ou + (apenas em query strings, não em path)
&:       %26 (quando faz parte de um valor, não separador)
=:       %3D (quando faz parte de um valor)
+:       %2B (quando é literal, não encoding de espaço)
#:       %23 (# inicia o fragment — encoded dentro da query)
?:       %3F (? inicia query — encoded dentro de valor)

Exemplo com valor que contém &:
  URL: /busca?q=café & bolo
  ERRADO: /busca?q=café & bolo   → parser lê "q=café " e " bolo" como segundo param
  CORRETO: /busca?q=caf%C3%A9%20%26%20bolo  → valor literal "café & bolo"

Encoding em código:
  # Python
  from urllib.parse import urlencode, quote
  params = {'q': 'café & bolo', 'page': 2}
  urlencode(params)  # → 'q=caf%C3%A9+%26+bolo&page=2'
  
  # JavaScript
  new URLSearchParams({'q': 'café & bolo', 'page': 2}).toString()
  # → 'q=caf%C3%A9+%26+bolo&page=2'
  
  # Go
  url.Values{'q': {'café & bolo'}, 'page': {'2'}}.Encode()
```

## 7. Fragment (Fragmento)

O fragment identifica uma âncora dentro do documento retornado. É processado **exclusivamente pelo cliente** — nunca é enviado ao servidor.

```
https://docs.empresa.com/api/referencia#autenticacao
                                        │
                                        └─ Fragment: autenticacao

O navegador:
  1. Requisita: GET /api/referencia HTTP/1.1 (SEM o #autenticacao)
  2. Recebe a página completa
  3. Rola até o elemento com id="autenticacao"

O servidor NUNCA vê o fragment — é processamento 100% client-side.

Usos comuns:
  #secao-2          → âncora HTML (<h2 id="secao-2">)
  #top              → scroll para o topo
  #/rota/spa        → roteamento em Single Page Applications (React Router, Vue Router)
  #access_token=... → OAuth implicit flow retorna token no fragment (deprecado)
                      (seguro pois não vai ao servidor, mas inseguro no histórico do browser)

Em SPAs (Single Page Applications):
  https://app.com/#/dashboard    → Hash routing (rota processada pelo JS)
  https://app.com/dashboard      → History API (rota real, requer suporte do servidor)
```

## URI vs URL vs URN

```
URI (Uniform Resource Identifier):
  Identificador genérico de qualquer recurso
  Superconjunto que inclui URL e URN

URL (Uniform Resource Locator):
  URI que especifica ONDE o recurso está (inclui o mecanismo de acesso)
  https://exemplo.com/recurso → é uma URL (e portanto também uma URI)

URN (Uniform Resource Name):
  URI que identifica o recurso pelo NOME, sem localização
  urn:isbn:978-3-16-148410-0 → ISBN de um livro (identifica, não localiza)
  urn:uuid:6ba7b810-9dad-11d1-80b4-00c04fd430c8 → UUID

Na prática:
  Programadores usam "URL" para quase tudo
  "URI" aparece em RFCs, specs HTTP e contexts mais técnicos
  A distinção raramente importa no dia a dia
```

## Construindo e parseando URLs em código

```python
# Python — construir URL com segurança
from urllib.parse import urlencode, urlunparse, quote

base = "https"
host = "api.empresa.com"
path = f"/v2/produtos/{produto_id}/avaliacoes"
params = {
    "status": "aprovado",
    "page": page,
    "limit": 10
}

url = f"{base}://{host}{path}?{urlencode(params)}"
# → https://api.empresa.com/v2/produtos/123/avaliacoes?status=aprovado&page=2&limit=10

# Python — parsear URL
from urllib.parse import urlparse, parse_qs

url = "https://api.empresa.com:8443/v2/produtos?status=ativo&page=2#top"
parsed = urlparse(url)

print(parsed.scheme)    # https
print(parsed.netloc)    # api.empresa.com:8443
print(parsed.hostname)  # api.empresa.com
print(parsed.port)      # 8443
print(parsed.path)      # /v2/produtos
print(parsed.query)     # status=ativo&page=2
print(parsed.fragment)  # top

params = parse_qs(parsed.query)
print(params)  # {'status': ['ativo'], 'page': ['2']}
```

```javascript
// JavaScript — URL API nativa
const url = new URL('https://api.empresa.com:8443/v2/produtos?status=ativo&page=2#top');

console.log(url.protocol);  // "https:"
console.log(url.hostname);  // "api.empresa.com"
console.log(url.port);      // "8443"
console.log(url.pathname);  // "/v2/produtos"
console.log(url.search);    // "?status=ativo&page=2"
console.log(url.hash);      // "#top"

// Acessar parâmetros individualmente
url.searchParams.get('status');  // "ativo"
url.searchParams.get('page');    // "2"

// Construir URL com parâmetros
const novaUrl = new URL('https://api.empresa.com/produtos');
novaUrl.searchParams.set('categoria', 'eletrônicos');
novaUrl.searchParams.set('page', '1');
console.log(novaUrl.toString());
// → https://api.empresa.com/produtos?categoria=eletr%C3%B4nicos&page=1
```

## Erros comuns e armadilhas

**Concatenar strings para construir URLs:** `baseUrl + "/produto/" + id + "?page=" + page` quebra quando `id` contém caracteres especiais ou quando `baseUrl` tem barra no final. Sempre usar bibliotecas de URL ou template strings com encoding.

**Confundir path parameters com query parameters para ID de recurso:** `/produtos?id=123` é semanticamente errado — o ID faz parte da identidade do recurso e deve estar no path (`/produtos/123`). Query params são para filtros e modificadores.

**Fragment no servidor:** tentar logar ou processar server-side o fragment `#secao` de uma URL é impossível — o browser nunca envia o fragment ao servidor. Para passar dados ao servidor que não apareçam na URL, use headers ou body.

**Não fazer encoding de valores de query parameters:** `?nome=João Silva` (com espaço) causa erros de parsing em alguns servidores. Sempre usar `encodeURIComponent()` (JavaScript) ou `quote()` (Python) para valores de parâmetros.

## 🧩 Quiz de Fixação

1. Uma URL de produção é `https://api.empresa.com/produtos?categoria=cafés & chás`. Quais problemas existem nessa URL e como corrigir?

2. Um desenvolvedor frontend usa `window.location.hash` para ler `#access_token=eyJ...` retornado por um servidor OAuth. Por que o servidor nunca vê esse token no hash, e qual é o benefício de segurança disso?

3. Qual é a diferença prática entre `/usuarios/123` e `/usuarios?id=123` do ponto de vista REST, e como isso afeta caching, logs e semântica da API?

**Respostas:**

1) **Problemas:** (a) o espaço entre `cafés` e `&` não está encoded — o parser vai interpretar `categoria=cafés ` (com espaço final) como o valor e ` chás` como um segundo parâmetro vazio; (b) o `&` dentro do valor ("cafés & chás") é interpretado como separador de parâmetros, não como parte do valor; (c) o `é` em "cafés" e o `á` em "chás" são caracteres não-ASCII que devem ser percent-encoded. **Correção:** `https://api.empresa.com/produtos?categoria=caf%C3%A9s%20%26%20ch%C3%A1s` — ou melhor ainda, reformular o design da API para usar IDs/slugs em vez de nomes com caracteres especiais: `?categoria=cafes-e-chas`.

2) O fragment (`#...`) é processado exclusivamente pelo browser — nunca é incluído nas requisições HTTP enviadas ao servidor. Quando o servidor OAuth redireciona para `https://app.com/callback#access_token=eyJ...`, o browser acessa `GET /callback` sem o fragment. O JavaScript da página lê o token via `window.location.hash`. O **benefício de segurança**: o token não aparece nos logs do servidor da aplicação (access logs, nginx/apache logs), nos logs de proxies intermediários, nem é enviado no header `Referer` se o usuário navegar para outra página. O token fica apenas no browser. A desvantagem (por isso o fluxo foi deprecado no OAuth 2.1): o token ainda aparece no histórico do browser e pode ser lido por scripts JavaScript maliciosos na mesma página — o fluxo PKCE com código de autorização é mais seguro.

3) **`/usuarios/123` (path parameter):** semanticamente, "o usuário 123 é o recurso identificado por esta URL". Caches HTTP podem armazenar essa URL como chave única, CDNs roteiam por path, logs mostram exatamente qual recurso foi acessado. É a forma REST correta — o ID faz parte da identidade do recurso. **`/usuarios?id=123` (query parameter):** semanticamente, "filtre a coleção de usuários por id=123". Caches tratam query strings diferentemente (menos agressivamente). Alguns proxies/CDNs ignoram query params para caching. Logs mostram `/usuarios` para todas as requisições de usuários individuais, dificultando análise. Do ponto de vista REST e da semântica HTTP, IDs pertencem ao path — query params são para filtros, paginação e modificadores que não alteram a identidade do recurso.
