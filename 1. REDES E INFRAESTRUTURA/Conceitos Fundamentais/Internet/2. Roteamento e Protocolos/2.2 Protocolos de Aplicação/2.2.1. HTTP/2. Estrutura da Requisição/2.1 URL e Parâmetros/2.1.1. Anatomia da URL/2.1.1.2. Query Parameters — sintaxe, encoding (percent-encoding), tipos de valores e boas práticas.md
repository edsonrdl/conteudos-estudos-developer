### Query Parameters — sintaxe, percent-encoding, tipos de valores e boas práticas

Os query parameters (parâmetros de consulta) são a forma padrão de passar dados adicionais em uma URL sem fazer parte da identidade do recurso. Aparecem após o `?` na URL e permitem filtrar, paginar, ordenar, configurar e customizar o comportamento de uma requisição GET sem alterar o endpoint. Dominar query parameters inclui saber encodar valores corretamente, estruturar parâmetros complexos e evitar armadilhas comuns de design de API.

---

## Sintaxe básica

```
https://api.exemplo.com/produtos?chave1=valor1&chave2=valor2&chave3=valor3
                                 │             │
                                 │             └─ segundo par (separado por &)
                                 └─ primeiro par chave=valor

Regras fundamentais:
  ?    → inicia a query string (apenas 1 por URL)
  =    → separa chave de valor
  &    → separa múltiplos pares
  #    → encerra a query string (inicia o fragment)

Casos especiais:
  Chave sem valor:    ?ativo        → chave "ativo" com valor vazio/undefined
  Valor vazio:        ?ativo=        → chave "ativo" com valor "" (string vazia)
  Mesmo chave várias: ?tag=js&tag=python&tag=go → array de valores
```

---

## Percent-encoding — a regra de ouro

Qualquer caractere que não seja "seguro" na URL deve ser **percent-encoded**: substituído por `%` seguido do código hexadecimal do byte UTF-8.

### Caracteres permitidos sem encoding

```
Unreserved characters (RFC 3986) — podem ser usados diretamente:
  A-Z a-z 0-9 - _ . ~

Caracteres reservados — têm significado especial na URL:
  : / ? # [ ] @ ! $ & ' ( ) * + , ; =
  
  Quando parte de um VALOR (não separador), DEVEM ser encoded.
  Quando atuando como SEPARADORES (& = ? #), NÃO se encoded.
```

### Tabela de encoding dos mais comuns

```
Caractere   Encoded     Quando encontrar
──────────────────────────────────────────────
Espaço       %20 ou +   Em valores de parâmetro
!            %21        Em valores
"            %22        Em valores
#            %23        Quando faz parte do valor (não o # do fragment)
$            %24        Em valores
%            %25        Quando é literal (não percent-encoding)
&            %26        Quando faz parte do valor (não separador)
'            %27        Em valores
(            %28        Em valores
)            %29        Em valores
*            %2A        Em valores
+            %2B        Quando é literal (+ é encoding de espaço em query)
,            %2C        Em valores
/            %2F        Em valores de path param
:            %3A        Em valores
;            %3B        Em valores
<            %3C        Em valores
=            %3D        Quando faz parte do valor (não separador)
>            %3E        Em valores
?            %3F        Quando faz parte do valor (não início da query)
@            %40        Em valores
[            %5B        Em valores (arrays)
\            %5C        Em valores
]            %5D        Em valores (arrays)
^            %5E        Em valores
`            %60        Em valores
{            %7B        Em valores (JSON)
|            %7C        Em valores
}            %7D        Em valores (JSON)
~            %7E        Pode ser usado direto (unreserved)

Caracteres Unicode (não-ASCII):
  é  → %C3%A9   (UTF-8: C3 A9)
  ã  → %C3%A3   (UTF-8: C3 A3)
  ç  → %C3%A7   (UTF-8: C3 A7)
  中 → %E4%B8%AD (UTF-8: E4 B8 AD)
```

### Espaço: `%20` vs `+`

```
Duas formas de encodar espaço em query strings:
  %20  →  padrão RFC 3986 (URL encoding)
  +    →  application/x-www-form-urlencoded (HTML forms)

Ambas são aceitas na maioria dos servidores, mas:
  Em PATH: use %20 (+ é literal no path)
  Em QUERY: ambos funcionam, %20 é mais explícito e correto

Armadilha:
  "café+" decodificado como:
    URL encoding: "café+"   (+ é literal)
    Form encoding: "café "  (+ é espaço)
  
  Sempre especifique qual padrão está usando!
```

### Encoding em código

```python
# Python
from urllib.parse import quote, quote_plus, urlencode

# quote: encoda tudo exceto unreserved + /
quote("café & bolo")          # 'caf%C3%A9%20%26%20bolo'
quote("café & bolo", safe='') # 'caf%C3%A9%20%26%20bolo' (safe='' = encoda tudo)

# quote_plus: igual ao quote mas espaço vira +
quote_plus("café & bolo")     # 'caf%C3%A9+%26+bolo'

# urlencode: ideal para dicionários de parâmetros
params = {'q': 'café & bolo', 'page': 2, 'limit': 10}
urlencode(params)              # 'q=caf%C3%A9+%26+bolo&page=2&limit=10'
urlencode(params, quote_via=quote)  # usa %20 em vez de +
```

```javascript
// JavaScript
encodeURIComponent("café & bolo")  // "caf%C3%A9%20%26%20bolo"
// encodeURIComponent encoda TUDO exceto: A-Z a-z 0-9 - _ . ! ~ * ' ( )

// Para construir query strings completas:
new URLSearchParams({'q': 'café & bolo', 'page': '2'}).toString()
// → "q=caf%C3%A9+%26+bolo&page=2"  (usa + para espaço)

// Para decodar:
decodeURIComponent("caf%C3%A9%20%26%20bolo")  // "café & bolo"
```

```go
// Go
import "net/url"

params := url.Values{}
params.Set("q", "café & bolo")
params.Set("page", "2")
params.Encode()  // → "page=2&q=caf%C3%A9+%26+bolo"
```

## Tipos de valores e padrões de uso

### Strings simples

```
/produtos?nome=notebook
/usuarios?email=user@exemplo.com
/busca?q=machine+learning  (q é convenção para search query)
```

### Números e booleanos

```
/produtos?preco_min=100&preco_max=5000
/pedidos?page=3&limit=20
/usuarios?ativo=true&verificado=false

Atenção: query params são SEMPRE strings na URL
  ?ativo=true   → string "true", não boolean
  ?page=3       → string "3", não número
  O servidor deve fazer o parse/coerção dos tipos
```

### Datas e timestamps

```
Formatos comuns para datas em query params:
  ISO 8601 (recomendado):
    /eventos?inicio=2024-01-15&fim=2024-03-31
    /logs?de=2024-01-15T08:00:00Z&ate=2024-01-15T20:00:00Z

  Unix timestamp:
    /eventos?inicio=1705276800&fim=1711843200

  Formato legível (menos preciso):
    /relatorios?mes=2024-01  (ano-mês)

Armadilha com +00:00 em timestamps ISO:
  2024-01-15T08:00:00+00:00
  O + DEVE ser encoded: 2024-01-15T08%3A00%3A00%2B00%3A00
  Ou usar Z em vez de +00:00: 2024-01-15T08:00:00Z (mais seguro)
```

### Arrays — múltiplos valores

```
Não existe padrão único. As convenções mais comuns:

1. Repetição da chave (mais compatível, RFC recomendada):
   /produtos?tag=javascript&tag=python&tag=go
   
   PHP/Java: $_GET['tag'] = ['javascript', 'python', 'go']
   Python:   parse_qs(query)['tag'] = ['javascript', 'python', 'go']
   Express:  req.query.tag = ['javascript', 'python', 'go']

2. Colchetes com índice (PHP/Laravel style):
   /produtos?tag[0]=javascript&tag[1]=python&tag[2]=go

3. Colchetes sem índice (jQuery/axios style):
   /produtos?tag[]=javascript&tag[]=python&tag[]=go

4. Valores separados por vírgula (uma string, não array real):
   /produtos?tags=javascript,python,go
   /produtos?ids=1,2,3,4,5
   (o servidor faz o split por vírgula)

5. JSON encodado (péssima prática — evitar):
   /produtos?tags=%5B%22javascript%22%2C%22python%22%5D
   (["javascript","python"] encodado — difícil de ler e debugar)

Recomendação: usar repetição de chave (#1) para arrays simples
              Documentar claramente qual convenção a API usa
```

### Objetos e dados estruturados

```
Query params não são projetados para objetos complexos.
Para filtros complexos, usar:

1. Parâmetros separados (preferido para casos simples):
   /produtos?preco_min=100&preco_max=5000&categoria=eletronicos

2. Notação de ponto (alguns frameworks):
   /produtos?filtro.preco.min=100&filtro.preco.max=5000

3. JSON no parâmetro (extremo — usar com moderação):
   /relatorio?config={"formato":"pdf","timezone":"America/Sao_Paulo"}
   (deve ser percent-encoded)
   
4. Para filtros muito complexos: usar POST com body JSON
   É tecnicamente incorreto semânticamente (GET é para buscar)
   mas amplamente praticado em GraphQL e algumas APIs de busca
```

## Parâmetros de sistema e convenções amplamente adotadas

```
Paginação:
  ?page=1&per_page=20        (page-based — simples, amplamente usada)
  ?offset=0&limit=20         (offset-based — precisa para SQL direto)
  ?cursor=eyJpZCI6NDJ9       (cursor-based — melhor para grandes datasets)
  ?after=abc123&first=20     (Relay spec — GraphQL)

Ordenação:
  ?sort=campo&order=asc|desc    (dois params separados)
  ?sort=+nome,-data_criacao     (prefixos +/- para direção)
  ?orderBy=nome_asc             (campo+direção concatenados)

Busca:
  ?q=termo          (q é convenção universal para busca)
  ?search=termo     (alternativa verbosa)
  ?keyword=termo    (menos comum)

Seleção de campos (sparse fieldsets — JSON:API spec):
  ?fields[usuarios]=id,nome,email
  ?fields=id,nome,email

Inclusão de relacionamentos:
  ?include=pedidos,enderecos   (comma-separated)
  ?expand=autor,tags           (alternativa)

Filtros (JSON:API spec):
  ?filter[nome]=João&filter[ativo]=true

Locale e formato:
  ?lang=pt-BR&timezone=America/Sao_Paulo
  ?format=json|csv|xml
  ?currency=BRL

Versão (alternativa ao path versioning):
  ?version=2   (menos comum — path versioning é preferido)

Callback (JSONP — legado, não usar):
  ?callback=meuCallback   (JSONP para cross-origin — substituído por CORS)

Debug/desenvolvimento:
  ?debug=true
  ?pretty=true   (formata o JSON com indentação)
  ?dry_run=true  (simula sem persistir)
```

## Boas práticas de design

```
✓ Use snake_case ou kebab-case consistentemente:
  ?preco_minimo=100    (snake_case — mais comum em APIs)
  ?preco-minimo=100    (kebab-case — alternativa)
  ✗ ?precoMinimo=100  (camelCase — evitar, menos legível em URLs)

✓ Nomes descritivos e em inglês (para APIs públicas):
  ?min_price=100&max_price=5000
  ✗ ?pmin=100&pmax=5000  (abreviações obscuras)

✓ Valores booleanos explícitos:
  ?active=true&verified=false
  ✗ ?active=1&verified=0  (ambíguo — é booleano ou número?)
  ✗ ?active  (sem valor — comportamento undefined em muitos parsers)

✓ Documentar o comportamento de parâmetros ausentes:
  Se ?page não for fornecido: default para page=1
  Se ?limit não for fornecido: default para limit=20 (ou qual?)
  Se ?sort não for fornecido: qual é a ordem padrão?

✗ Nunca usar query params para dados sensíveis:
  ✗ ?password=123456  → aparece em logs, histórico, Referer
  ✗ ?token=eyJ...     → mesmo problema
  Use Authorization header para tokens

✓ Limite o tamanho:
  Browsers e servidores têm limites (tipicamente 2.000-8.000 caracteres total na URL)
  Para filtros muito complexos: considere POST com body JSON
```

```python
    tags: List[str] = Query(default=[])  # ?tags=js&tags=python
):
    # FastAPI faz parse, validação e coerção de tipos automaticamente
    ...
```

```javascript
// Express (Node.js) — manual
app.get('/produtos', (req, res) => {
  const {
    page = '1',
    limit = '20',
    sort = 'nome',
    order = 'asc',
    tags  // undefined se não fornecido, string se 1, array se vários
  } = req.query;

  const limitNum = Math.min(parseInt(limit, 10), 100);

    ? Array.isArray(tags) ? tags : [tags]

    return res.status(400).json({ erro: 'page deve ser inteiro >= 1' });
  }
```

## Erros comuns e armadilhas

**Logar URLs com dados sensíveis:** query params aparecem em access logs de servidores (nginx, apache, CloudWatch), em headers `Referer` quando o usuário navega para outro site, e no histórico do browser. Nunca passar tokens, senhas ou PII em query params.

**Não fazer encoding de valores:** `?nome=José Silva` (com acento e espaço) pode funcionar em alguns browsers que fazem encoding automático, mas é comportamento undefined. Sempre encodar explicitamente valores ao construir URLs programaticamente.

**Confundir `null` com valor ausente:** `?ativo=null` envia a string `"null"`, não ausência de valor. Para indicar "sem filtro", omita o parâmetro completamente — não envie `null` como string.

**Arrays com chave única sem documentação:** `/produtos?tag=js,python` vs `/produtos?tag=js&tag=python` têm comportamentos completamente diferentes. Documentar e manter consistência é crítico.

## 🧩 Quiz de Fixação

1. Uma API recebe a URL `/busca?q=café+bolo&data=2024-01-15T08:00:00+03:00`. Quais problemas de encoding existem e como corrigir?

2. Um endpoint de listagem aceita `/usuarios?roles=admin&roles=editor&roles=viewer`. Em Python com `urllib.parse.parse_qs`, qual é o valor de `params['roles']`? Em Express.js, qual é o valor de `req.query.roles`?

3. Um desenvolvedor precisa passar um filtro complexo para uma API GET: `{ "preco": { "min": 100, "max": 5000 }, "categorias": ["eletronicos", "informatica"] }`. Quais são as três abordagens possíveis, e qual é a mais recomendada?

**Respostas:**

1) **Problema 1:** `café` — o `é` (U+00E9) deve ser percent-encoded como `%C3%A9`. Usando `+` para espaço: `caf%C3%A9+bolo` está correto. **Problema 2:** `2024-01-15T08:00:00+03:00` — o `+` no timezone é crítico. Em query strings, `+` significa espaço. A URL envia a data como `2024-01-15T08:00:00 03:00` (com espaço), não com `+03:00`. O `+` deve ser encoded como `%2B`: `2024-01-15T08%3A00%3A00%2B03%3A00`. Melhor ainda: usar `Z` (UTC) ou `%2B` consistentemente. **URL correta:** `/busca?q=caf%C3%A9+bolo&data=2024-01-15T08%3A00%3A00%2B03%3A00`.

2) **Python `parse_qs`:** `params['roles']` = `['admin', 'editor', 'viewer']` — `parse_qs` agrupa valores de chaves repetidas em uma lista automaticamente. **Express.js:** `req.query.roles` = `['admin', 'editor', 'viewer']` quando há 3 valores, mas se houver apenas 1 (ex: `?roles=admin`), `req.query.roles` = `'admin'` (string, não array!). Esse comportamento inconsistente do Express é a razão pelo qual código Node.js deve sempre normalizar: `const rolesArray = Array.isArray(req.query.roles) ? req.query.roles : [req.query.roles].filter(Boolean)`.

3) **Abordagem 1 — Parâmetros separados (recomendada):** `/usuarios?preco_min=100&preco_max=5000&categoria=eletronicos&categoria=informatica` — legível, compatível com todos os frameworks, fácil de documentar e testar. **Abordagem 2 — Notação de ponto:** `/usuarios?filtro.preco.min=100&filtro.preco.max=5000&filtro.categoria[]=eletronicos` — funciona em alguns frameworks (Spring, Laravel) mas não é padrão universal. **Abordagem 3 — POST com body JSON:** tecnicamente viola a semântica REST (GET é para buscar, não tem body), mas é amplamente praticado para filtros complexos (Elasticsearch Query DSL, GraphQL). Aceito quando os filtros são tão complexos que query params se tornam ilegíveis. **Recomendação:** usar Abordagem 1 para APIs REST padrão — é o mais simples, mais interoperável e não tem problemas de encoding ou limite de tamanho de URL para casos típicos.
