### Headers de cache condicional — Cache-Control, If-Modified-Since, If-None-Match e ETag

O cache HTTP é um dos mecanismos de performance mais poderosos da web — mas também um dos mais incompreendidos. Quando funciona corretamente, elimina completamente requisições ao servidor para recursos não modificados. Quando mal configurado, serve dados desatualizados ou invalida o cache prematuramente. Os headers de cache operam em dois níveis: **expiração** (por quanto tempo um recurso é válido sem verificar) e **validação** (verificar se o recurso mudou sem baixar novamente).

---

## Os dois modelos de cache HTTP

```
Modelo 1 — Expiração (Freshness):
  "Este recurso é válido por X tempo, não precisa verificar"
  
  Cliente: GET /logo.png
  Servidor: 200 OK + Cache-Control: max-age=31536000  (1 ano)
  
  Próxima requisição em 6 meses:
  → Cliente serve direto do cache local
  → Servidor NUNCA é consultado
  → 0 bytes de rede, 0 latência

Modelo 2 — Validação (Conditional):
  "Este recurso pode ter mudado. Posso verificar sem baixar novamente?"
  
  Cliente: GET /api/dados + If-None-Match: "abc123"
  Servidor: 304 Not Modified (sem body)
  
  → Apenas headers são transferidos (dezenas de bytes, não kilobytes)
  → Cliente usa o que está em cache
  → Muito mais eficiente que baixar tudo de novo
```

## Cache-Control — o header principal

`Cache-Control` é o mecanismo moderno de controle de cache, substituindo o antigo `Expires`. Pode aparecer tanto na requisição quanto na resposta.

### Cache-Control na RESPOSTA (do servidor)

```
Cache-Control: max-age=3600
               │
               └─ recurso é "fresh" por 3600 segundos (1 hora)
                  cliente pode usar o cache sem verificar por 1h

Diretivas mais importantes:

max-age=<seconds>
  → Tempo em segundos que o recurso é válido
  → Conta a partir do momento que foi recebido
  → max-age=0: deve revalidar sempre antes de usar
  → max-age=31536000: 1 ano (para assets com hash no nome)

s-maxage=<seconds>
  → Igual ao max-age, mas apenas para caches compartilhados (CDNs, proxies)
  → Ignora max-age para CDNs se s-maxage estiver presente
  → Cache-Control: max-age=60, s-maxage=3600
    → browser: 60s; CDN: 3600s

no-cache
  → CONFUSO: NÃO significa "não cachear"!
  → Significa: "sempre revalidar antes de usar"
  → O recurso pode ser armazenado, mas deve ser validado (If-None-Match/If-Modified-Since)
  → Ideal para: HTML de páginas (pode cachear mas verificar se mudou)

no-store
  → NÃO armazenar de forma alguma — nem em memória, nem em disco
  → Cada requisição vai ao servidor
  → Ideal para: dados sensíveis (extratos bancários, dados de sessão)

private
  → Apenas caches do cliente (browser) podem armazenar
  → CDNs e proxies compartilhados NÃO devem cachear
  → Ideal para: respostas personalizadas por usuário

public
  → Qualquer cache pode armazenar (browsers E CDNs)
  → Ideal para: assets estáticos, conteúdo público

must-revalidate
  → Após expirar (max-age), deve revalidar antes de usar
  → Sem isso: alguns caches podem usar recursos expirados em caso de falha de rede
  → Mais rigoroso que no-cache

stale-while-revalidate=<seconds>
  → Serve o recurso desatualizado enquanto busca a versão nova em background
  → Cache-Control: max-age=60, stale-while-revalidate=300
    → Até 60s: fresh, sem verificar
    → 60-360s: serve o stale imediatamente, revalida em background
    → Após 360s: deve esperar pela revalidação
  → Resultado: zero latência percebida pelo usuário durante revalidação

stale-if-error=<seconds>
  → Se o servidor estiver indisponível, usar cache desatualizado por X segundos
  → Resiliência: melhor dar resposta antiga do que erro
```

### Combinações comuns e para que servem

```
Recurso                    Cache-Control                           Por quê
──────────────────────────────────────────────────────────────────────────────────
HTML de página             no-cache                                Sempre verificar se mudou
                                                                   mas pode cachear
                                                                   
Assets com hash            max-age=31536000, immutable             Hash no nome garante
(app.abc123.js)                                                    unicidade — nunca muda
                                                                   
API REST (dados públicos)  max-age=60, s-maxage=300                Browser 1min, CDN 5min
                           stale-while-revalidate=60
                           
API REST (dados privados)  private, no-cache                       Por usuário, sempre validar

Dados sensíveis            no-store, no-cache                      Nunca armazenar

Assets estáticos genéricos max-age=86400, public                   1 dia (sem hash no nome)

Streaming/SSE              no-store                                Dados em tempo real
```

```
immutable:
  → Indica que o recurso NUNCA mudará durante o max-age
  → Browser não faz revalidação mesmo ao pressionar Ctrl+F5
  → Use apenas com hashed file names (garante que o nome muda junto com o conteúdo)
  → Cache-Control: max-age=31536000, immutable
```

### Cache-Control na REQUISIÇÃO (do cliente)

```
no-cache
  → "Quero uma resposta fresh — não me dê cache do proxy"
  → Força validação mesmo que o proxy tenha resposta em cache
  → Equivale ao Ctrl+Shift+R no browser

no-store
  → "Por favor, não guarde essa resposta"
  → Menos comum na requisição

max-age=0
  → Equivalente prático a no-cache na requisição

max-stale=<seconds>
  → "Aceito resposta desatualizada por até X segundos"
  → Útil quando servidor está lento e é aceitável dado velho

min-fresh=<seconds>
  → "Só aceito resposta com pelo menos X segundos de freshness restante"

only-if-cached
  → "Só responda se você tem em cache. Não vá ao servidor."
  → Se não tiver cache: 504 Gateway Timeout
  → Útil para offline-first
```

## ETag — impressão digital do recurso

`ETag` (Entity Tag) é um identificador único de uma versão específica de um recurso. É como um hash do conteúdo — se o conteúdo mudar, o ETag muda; se não mudar, o ETag é o mesmo.

```
Resposta do servidor com ETag:
  HTTP/1.1 200 OK
  ETag: "abc123def456"
  Cache-Control: no-cache
  Content-Type: application/json
  
  {"usuarios": [...]}

Próxima requisição (usando o ETag armazenado):
  GET /api/usuarios
  If-None-Match: "abc123def456"

Se não mudou:
  HTTP/1.1 304 Not Modified
  ETag: "abc123def456"
  (sem body — zero bytes de dados!)

Se mudou:
  HTTP/1.1 200 OK
  ETag: "xyz789uvw"
  
  {"usuarios": [...novos dados...]}
```

### ETag strong vs weak

```
Strong ETag: "abc123"
  → Idêntico byte a byte — mesmo conteúdo = mesmo ETag
  → Usado para comparação precisa
  → Modificação de qualquer byte muda o ETag

Weak ETag: W/"abc123"
  → Semanticamente equivalente mas não necessariamente byte a byte
  → "Este recurso é essencialmente o mesmo, mesmo que alguns bytes difiram"
  → Útil para: compressão dinâmica (gzip de um arquivo pode ter timestamps diferentes)
              respostas com partes geradas (server date, session IDs)
```

### Gerando ETags em código

```python
# FastAPI — ETag baseado em hash do conteúdo
import hashlib
import json
from fastapi import Request
from fastapi.responses import Response, JSONResponse

@app.get("/api/produtos")
async def listar_produtos(request: Request):
    produtos = db.get_produtos()
    content = json.dumps(produtos, ensure_ascii=False, sort_keys=True)
    
    # Gerar ETag como MD5 do conteúdo
    etag = f'"{hashlib.md5(content.encode()).hexdigest()}"'
    
    # Verificar se o cliente tem a versão atual
    if request.headers.get("If-None-Match") == etag:
        return Response(status_code=304, headers={"ETag": etag})
    
    return JSONResponse(
        content=produtos,
        headers={
            "ETag": etag,
            "Cache-Control": "no-cache"  # sempre verificar, mas pode cachear
        }
    )
```

```python
# Alternativa: ETag baseado em timestamp/versão (mais eficiente)
@app.get("/api/produtos")
async def listar_produtos(request: Request):
    ultima_modificacao = db.get_ultima_modificacao_produtos()
    etag = f'"{ultima_modificacao.timestamp():.0f}"'
    
    if request.headers.get("If-None-Match") == etag:
        return Response(status_code=304, headers={"ETag": etag})
    
    produtos = db.get_produtos()
    return JSONResponse(
        content=produtos,
        headers={"ETag": etag, "Cache-Control": "no-cache"}
    )
```

## If-Modified-Since — revalidação por data

Alternativa ao ETag baseada em timestamp. O cliente envia a data em que recebeu o recurso; o servidor responde com 304 se não houve modificação desde então.

```
Primeira requisição:
  GET /noticias HTTP/1.1

Resposta:
  HTTP/1.1 200 OK
  Last-Modified: Mon, 15 Jan 2024 10:00:00 GMT
  Cache-Control: max-age=300
  
  [conteúdo das notícias]

Após 5 minutos (cache expirou):
  GET /noticias HTTP/1.1
  If-Modified-Since: Mon, 15 Jan 2024 10:00:00 GMT

Se não houve nova notícia:
  HTTP/1.1 304 Not Modified
  Last-Modified: Mon, 15 Jan 2024 10:00:00 GMT
  (zero bytes de conteúdo)

Se houve nova notícia:
  HTTP/1.1 200 OK
  Last-Modified: Mon, 15 Jan 2024 12:30:00 GMT
  
  [novas notícias]
```

### Limitações do If-Modified-Since

```
Precisão de 1 segundo:
  Se o servidor atualiza o recurso duas vezes no mesmo segundo,
  If-Modified-Since não detecta a segunda atualização

Manipulação de arquivos:
  Copiar um arquivo reseta o Last-Modified mesmo sem mudança de conteúdo
  → Falso positivo: servidor diz "mudou" mas conteúdo é o mesmo

Recursos dinâmicos:
  Difícil determinar "quando foi modificado" para dados de banco
  → ETag (hash do conteúdo) é mais confiável

Recomendação: usar ETag em vez de (ou além de) Last-Modified
```

## If-None-Match vs If-Match — usos diferentes

```
If-None-Match: "abc123"
  → "Responda apenas SE o ETag NÃO é mais abc123"
  → Usado em GET para revalidação de cache
  → "Só me mande de volta se mudou"

If-Match: "abc123"
  → "Execute a operação APENAS SE o ETag AINDA é abc123"
  → Usado em PUT/PATCH/DELETE para otimistic locking
  → "Só modifique se não houve mudança concorrente"

Exemplo de optimistic locking:
  1. Cliente lê o produto: GET /produtos/123
     Resposta: ETag: "v5", {preco: 2999}
  
  2. Cliente decide mudar o preço
  
  3. Outro cliente também mudou o preço nesse meio tempo (preco: 3500, ETag: "v6")
  
  4. Primeiro cliente envia:
     PATCH /produtos/123
     If-Match: "v5"            ← "só mude se ainda for v5"
     Body: {"preco": 2799}
  
  5. Servidor verifica: ETag atual é "v6", não "v5"
     HTTP/1.1 412 Precondition Failed
     
     → Conflito detectado! Primeiro cliente sabe que o produto foi alterado
     → Pode buscar a versão atual e reconsiderar a mudança
```

## Fluxo completo de cache HTTP

```
Primeira requisição:
  Browser → GET /produtos/123 → Servidor
  Servidor → 200 OK + ETag: "v5" + Cache-Control: no-cache + body

Browser armazena: URL, ETag, Last-Modified, body

Segunda requisição (Ctrl+F5 ou Cache-Control: no-cache na req):
  Browser → GET /produtos/123 + If-None-Match: "v5" → Servidor
  
  Se não mudou: Servidor → 304 Not Modified (sem body)
  → Browser usa body armazenado: 0 bytes de conteúdo transferido!
  
  Se mudou: Servidor → 200 OK + ETag: "v6" + body atualizado
  → Browser atualiza o cache

Terceira requisição (recurso com max-age=3600 ainda fresh):
  Browser nem consulta o servidor
  → Serve diretamente do cache local: 0 bytes, 0 latência, 0 requisições
```

## Headers de cache na requisição — resumo

```
If-None-Match: "etag-value"
  → Usado com: GET, HEAD
  → Revalida: servidor retorna 304 se recurso não mudou

If-Modified-Since: <HTTP-date>
  → Usado com: GET, HEAD
  → Revalida por data: servidor retorna 304 se não houve modificação

If-Match: "etag-value"
  → Usado com: PUT, PATCH, DELETE
  → Optimistic locking: operação falha com 412 se recurso mudou

If-Unmodified-Since: <HTTP-date>
  → Usado com: PUT, PATCH, DELETE, Range requests
  → Alternativa ao If-Match por data

Cache-Control: no-cache
  → Força revalidação — não usa cache sem verificar
  → Usado principalmente na requisição para forçar fresh response

Cache-Control: only-if-cached
  → Apenas usa cache; se não tiver → 504 Gateway Timeout
```

## Erros comuns e armadilhas

**`no-cache` não significa "não cachear":** é o erro mais comum. `no-cache` significa "revalidar sempre antes de usar". Para realmente proibir qualquer cache: `no-store`.

**Não incluir ETag em APIs mutáveis:** sem ETag, cada requisição baixa o conteúdo completo mesmo que não tenha mudado. Para APIs com dados que mudam raramente mas são frequentemente consultados, ETag pode reduzir 80%+ do tráfego de dados.

**Assets estáticos sem `immutable`:** sem `immutable`, browsers fazem revalidação ao pressionar F5 mesmo com `max-age=31536000`. Adicionar `immutable` a assets com hash no nome (que nunca mudam) elimina essa revalidação desnecessária.

**ETags diferentes em servidores de um cluster:** se 3 servidores geram ETags de formas ligeiramente diferentes (ex: incluindo timestamp de servidor), o mesmo recurso tem ETags diferentes dependendo de qual servidor respondeu → revalidações falsas constantemente. ETags devem ser baseadas no conteúdo, não no servidor.

## 🧩 Quiz de Fixação

1. Um arquivo CSS está sendo servido com `Cache-Control: max-age=86400` (1 dia). O time faz um deploy com mudanças no CSS às 14h. Usuários que visitaram o site antes das 14h ficam com o CSS desatualizado por até 24h. Como resolver isso sem reduzir o max-age (que prejudicaria a performance)?

2. Uma API retorna dados de um dashboard que muda a cada 30 segundos. O header correto para balancear performance (não consultar o servidor desnecessariamente) e atualidade (dados não muito velhos) seria qual combinação de Cache-Control?

3. Dois usuários editam o mesmo produto simultaneamente: Usuário A carrega (ETag: "v3"), Usuário B carrega (ETag: "v3"), Usuário B salva primeiro (ETag vira "v4"), Usuário A tenta salvar. O que acontece com `If-Match: "v3"` na requisição de Usuário A, e qual é o comportamento esperado da aplicação?

**Respostas:**

1) A solução é **cache busting com hashed filenames**: em vez de servir `styles.css`, o build system gera `styles.abc123.css` (hash do conteúdo no nome). O HTML referencia `styles.abc123.css`. No próximo deploy, o conteúdo muda → hash muda → nome muda → `styles.xyz789.css`. O browser sempre busca o arquivo novo porque o nome é diferente. O arquivo antigo (`styles.abc123.css`) ainda fica em cache por 1 ano — sem problema, pois ninguém mais o referencia. Com `Cache-Control: max-age=31536000, immutable` para os arquivos com hash: performance máxima (1 ano em cache, sem verificação) + sempre atualizado (novo deploy = novo hash = novo arquivo).

2) A combinação ideal é: `Cache-Control: max-age=30, stale-while-revalidate=30`. Explicação: `max-age=30` → dados são "fresh" por 30 segundos (alinhado com o ciclo de atualização). `stale-while-revalidate=30` → quando o cache expira (30s), o sistema serve imediatamente o dado desatualizado enquanto busca a versão nova em background. O usuário vê resposta instantânea (zero latência) e na próxima requisição já tem os dados atualizados. Sem o `stale-while-revalidate`, a cada 30s o usuário esperaria a revalidação. Com ele, a revalidação acontece em background e o usuário nunca espera.

3) O servidor recebe `PATCH /produtos/123` com `If-Match: "v3"`, mas o ETag atual é `"v4"` (porque Usuário B já modificou). O servidor retorna **412 Precondition Failed** — a condição `If-Match: "v3"` não é satisfeita (o recurso não é mais "v3"). **Comportamento esperado da aplicação:** (a) detectar o 412 no cliente de Usuário A; (b) buscar a versão atual do produto (`GET /produtos/123` → retorna "v4" com as mudanças de Usuário B); (c) apresentar para Usuário A: "Este produto foi modificado por outro usuário. Aqui estão as mudanças. Deseja mesclar ou substituir?"; (d) se Usuário A confirmar suas mudanças sobre a versão atual, reenvia com `If-Match: "v4"`. Isso é **optimistic locking** — não bloqueia edições concorrentes, mas detecta conflitos e permite resolução manual, sem perder dados de nenhum usuário.
