### Headers de autenticação e autorização — Authorization, Cookie e API-Key

Autenticação e autorização em HTTP acontecem quase exclusivamente via headers. O header `Authorization` é o canal padrão, com dois esquemas amplamente usados (Bearer e Basic). Cookies têm seu próprio header e são o mecanismo de sessão da web tradicional. APIs modernas adicionam headers customizados (`X-Api-Key`, `X-Access-Token`) para casos de uso específicos. Cada abordagem tem trade-offs distintos de segurança, compatibilidade e conveniência.

---

## Authorization — o header padrão

```
Authorization: <scheme> <credentials>

Formato:
  scheme      → identifica o mecanismo de autenticação
  credentials → dados de autenticação no formato do scheme

Exemplos:
  Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
  Authorization: Basic dXNlcjpzZW5oYQ==
  Authorization: Digest username="user", realm="api.exemplo.com"...
  Authorization: AWS4-HMAC-SHA256 Credential=AKIAIOSFODNN7EXAMPLE...
  Authorization: ApiKey abc123def456
```

---

## Bearer Token — o padrão moderno

O esquema **Bearer** ("portador") significa: "quem tem este token tem acesso". É o padrão da indústria para autenticação em APIs REST modernas, especialmente com OAuth 2.0 e JWT.

```
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJ1c2VyXzEyMyIsIm5hbWUiOiJKb8OjbyBTaWx2YSIsImlhdCI6MTcwNTMxMjgwMCwiZXhwIjoxNzA1MzE2NDAwfQ.signature
                │
                └─ "Bearer" + espaço + token
```

### JWT (JSON Web Token) — o formato mais comum para Bearer

```
Um JWT tem 3 partes separadas por ponto (.):

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9   → Header (base64url)
.eyJzdWIiOiJ1c2VyXzEyMyIsIm5hbWUiOiJKb8OjbyJ9  → Payload (base64url)
.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV    → Signature

Decodificado:

Header:
{
  "alg": "HS256",   → algoritmo de assinatura
  "typ": "JWT"
}

Payload (claims):
{
  "sub": "user_123",          → subject (ID do usuário)
  "name": "João Silva",       → claim customizado
  "email": "joao@email.com",  → claim customizado
  "role": "admin",            → claim customizado
  "iat": 1705312800,          → issued at (quando foi emitido)
  "exp": 1705316400,          → expiration (quando expira)
  "iss": "auth.empresa.com",  → issuer (quem emitiu)
  "aud": "api.empresa.com"    → audience (para quem é)
}

Signature:
HMACSHA256(base64url(header) + "." + base64url(payload), secret)
```

```
Como o servidor valida um JWT:

1. Extrair o token do header Authorization: Bearer <token>
2. Dividir em header.payload.signature
3. Verificar a assinatura (usando a chave secreta ou chave pública)
4. Verificar que exp > now() (não expirou)
5. Verificar iss (emissor confiável)
6. Extrair sub/role/etc do payload para autorização

Se a assinatura for válida: o conteúdo do payload é confiável
Importante: JWT payload é BASE64 (não criptografado) — nunca coloque senhas!
```

### Fluxo OAuth 2.0 com Bearer Token

```
1. Usuário faz login:
   POST /auth/login
   Body: {"email": "user@email.com", "senha": "123456"}
   
   Resposta: {"access_token": "eyJ...", "refresh_token": "...", "expires_in": 3600}

2. Usar o token nas requisições:
   GET /api/perfil
   Authorization: Bearer eyJ...
   
   Servidor valida o JWT e responde com os dados do usuário

3. Quando o access_token expira (depois de 1h):
   POST /auth/refresh
   Authorization: Bearer <refresh_token>
   
   Resposta: {"access_token": "novo_token_eyJ...", "expires_in": 3600}
```

### Bearer em código

```python
# Python (requests)
import requests

token = "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."

response = requests.get(
    "https://api.exemplo.com/perfil",
    headers={"Authorization": f"Bearer {token}"}
)

# Com session (reutiliza o header em todas as requisições)
session = requests.Session()
session.headers.update({"Authorization": f"Bearer {token}"})
response = session.get("https://api.exemplo.com/pedidos")
```

```javascript
// JavaScript (fetch)
const token = localStorage.getItem('access_token');

const response = await fetch('https://api.exemplo.com/perfil', {
  headers: {
    'Authorization': `Bearer ${token}`,
    'Content-Type': 'application/json'
  }
});

// Axios com interceptor — adiciona token automaticamente
axios.interceptors.request.use(config => {
  const token = localStorage.getItem('access_token');
  if (token) {
    config.headers.Authorization = `Bearer ${token}`;
  }
  return config;
});
```

## Basic Authentication

O esquema **Basic** envia username:senha codificados em Base64. É simples mas deve ser usado **apenas sobre HTTPS** — Base64 não é criptografia (é reversível trivialmente).

```
Authorization: Basic dXNlcjpzZW5oYQ==
                      │
                      └─ base64("user:senha") = "dXNlcjpzZW5oYQ=="

Decodificação:
  atob("dXNlcjpzZW5oYQ==") === "user:senha"
  
  echo "dXNlcjpzZW5oYQ==" | base64 --decode
  # user:senha
```

### Quando usar Basic Auth

```
✓ APIs internas entre serviços com HTTPS
✓ CI/CD pipelines acessando repositórios (ex: GitHub packages)
✓ Ferramentas de monitoramento e dashboards internos
✓ Ambientes de desenvolvimento para simplicidade
✓ APIs que precisam suportar clientes legados sem Bearer

✗ APIs públicas com muitos usuários (sem rotação de senha fácil)
✗ Qualquer comunicação sem TLS (expõe credenciais)
✗ APIs mobile (senha armazenada no dispositivo = risco)
```

```bash
# curl com Basic Auth
curl -u usuario:senha https://api.exemplo.com/dados
# curl codifica automaticamente em base64

# Equivalente manual:
curl -H "Authorization: Basic $(echo -n 'usuario:senha' | base64)" \
  https://api.exemplo.com/dados
```

```python
# Python
import requests

response = requests.get(
    "https://api.exemplo.com/dados",
    auth=("usuario", "senha")  # requests faz o Basic Auth automaticamente
)
```

### 401 e WWW-Authenticate — desafio de autenticação

```
Quando Basic Auth é requerido e o header está ausente/errado:

HTTP/1.1 401 Unauthorized
WWW-Authenticate: Basic realm="API de Produção"
                         │
                         └─ realm: nome do "domínio protegido"
                            browsers mostram uma caixa de login com esse nome

O header WWW-Authenticate diz ao cliente:
  → Qual esquema usar (Basic, Bearer, Digest...)
  → Parâmetros adicionais (realm, scope para OAuth...)

Para Bearer (OAuth 2.0):
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="api.empresa.com", error="invalid_token",
                  error_description="Token expirado ou inválido"
```

## Cookie — sessões baseadas em cookie

O header `Cookie` é o mecanismo clássico de sessão da web. Diferente do `Authorization`, cookies são **gerenciados automaticamente pelo browser** e enviados em todas as requisições para o mesmo domínio.

```
Cookie: session=abc123; preferencia=dark_mode; csrf_token=xyz789
        │                │                     │
        └─ sessão        └─ preferência        └─ CSRF token

Múltiplos cookies separados por "; " (ponto e vírgula + espaço)
```

### Como um cookie chega ao browser

```
1. Servidor envia Set-Cookie na resposta:
   HTTP/1.1 200 OK
   Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=86400

2. Browser armazena o cookie para o domínio

3. Nas requisições seguintes para o mesmo domínio:
   GET /perfil HTTP/1.1
   Cookie: session=abc123
   (enviado automaticamente pelo browser — o JavaScript não precisa fazer nada)
```

### Atributos do Set-Cookie que controlam o comportamento

```
Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Strict; Path=/api; Domain=.empresa.com; Max-Age=86400

HttpOnly:
  → JavaScript NÃO pode ler este cookie (document.cookie não o vê)
  → Proteção contra XSS: mesmo que JS malicioso injete código, não rouha a sessão
  → Use sempre para cookies de sessão/autenticação

Secure:
  → Cookie só é enviado em conexões HTTPS
  → Em HTTP: cookie não é incluído no header Cookie
  → Use sempre em produção

SameSite:
  Strict: cookie só enviado para requisições do mesmo site (aba atual)
          → Maior segurança contra CSRF, mas quebra links de outros sites
  Lax:    enviado em navegação de links mas não em POST cross-site
          → Equilíbrio — padrão moderno dos browsers
  None:   enviado em qualquer contexto cross-site
          → Requer Secure; usado para widgets embarcados (ex: chat de suporte)

Path:
  → Cookie só enviado em requisições para este path e seus sub-paths
  Path=/api → enviado para /api/usuarios, /api/pedidos, mas NÃO para /assets/

Domain:
  .empresa.com → enviado para empresa.com E todos os subdomínios
  api.empresa.com → apenas para api.empresa.com (sem subdomínios)

Max-Age (preferível a Expires):
  86400 → expira em 86.400 segundos (1 dia)
  0     → deletar o cookie imediatamente
  Sem Max-Age/Expires: cookie de sessão (deletado ao fechar o browser)
```

### Cookie vs Bearer Token — comparativo

```
┌───────────────────────┬────────────────────────────┬────────────────────────────┐
│ Aspecto               │ Cookie (HttpOnly)           │ Bearer Token (localStorage)│
├───────────────────────┼────────────────────────────┼────────────────────────────┤
│ XSS risk              │ Baixo (HttpOnly)            │ Alto (JS pode ler)         │
│ CSRF risk             │ Alto (sem mitigação)        │ Baixo (não enviado auto)   │
│ Storage               │ Browser automático          │ localStorage/memory/cookie │
│ Mobile apps           │ Inconveniente               │ Natural (Authorization)    │
│ Cross-domain          │ Restrito (SameSite)         │ Funciona facilmente        │
│ Logout                │ Invalidar sessão no servidor│ Expirar o token            │
│ Stateless             │ Não (sessão no servidor)    │ Sim (JWT = stateless)      │
│ Revogação             │ Fácil (deletar sessão)      │ Difícil (JWT não revogável)│
└───────────────────────┴────────────────────────────┴────────────────────────────┘

Recomendação atual (2024):
  → Web apps: cookies HttpOnly + SameSite (proteção XSS) + CSRF token
  → APIs consumidas por mobile/third-party: Bearer JWT
  → APIs internas entre serviços: Bearer JWT ou Basic Auth (HTTPS)
```

## API Keys — headers customizados

API Keys são tokens estáticos de longa duração usados principalmente para autenticar serviços (não usuários). Não há um header padrão — cada API escolhe o nome.

### Padrões mais comuns

```
1. Header X-Api-Key (mais comum):
   X-Api-Key: abc123def456ghi789

2. Header Authorization com scheme customizado:
   Authorization: ApiKey abc123def456ghi789
   Authorization: Token abc123def456ghi789

3. Header customizado do serviço:
   X-Auth-Token: abc123      (Stripe legado)
   Stripe-Key: sk_live_...   (hipotético)
   X-RapidAPI-Key: abc123    (RapidAPI)
   api-key: abc123           (Azure OpenAI)

4. Query parameter (evitar — aparece em logs):
   ?api_key=abc123  ← EVITAR em produção (fica em logs de servidor)
   ?apiKey=abc123   ← idem

Exemplos reais:
  # OpenAI
  Authorization: Bearer sk-proj-abc123...
  
  # Stripe
  Authorization: Bearer sk_live_abc123...
  
  # Mailchimp
  Authorization: Bearer abc123-us10
  
  # AWS (Signature v4 — muito mais complexo)
  Authorization: AWS4-HMAC-SHA256 Credential=AKIAIOSFODNN7/...
```

### Diferença entre API Key e Bearer Token de usuário

```
API Key:
  → Identifica uma APLICAÇÃO (não um usuário)
  → Longa duração (meses/anos) — não expira frequentemente
  → Gerada no console do serviço, armazenada como secret
  → Exemplo: sk_live_abc123 do Stripe para o seu backend chamar o Stripe

Bearer JWT de usuário:
  → Identifica um USUÁRIO específico
  → Curta duração (minutos a horas)
  → Emitido após login, armazenado temporariamente no cliente
  → Exemplo: token que o seu frontend usa para chamar sua própria API

Erro comum: armazenar API Keys de serviços externos no frontend
  ✗ Chave OpenAI hardcoded no código React → vazamento
  ✓ Frontend → seu backend → backend usa a API Key para chamar OpenAI
```

### Segurança de API Keys

```
✓ Armazenar em variáveis de ambiente / secrets manager:
  OPENAI_API_KEY=sk-proj-...    (nunca no código)

✓ Diferentes keys para diferentes ambientes:
  sk_test_... para dev/staging
  sk_live_... para produção

✓ Rotação periódica:
  Gerar nova key → atualizar em todos os serviços → revogar antiga

✓ Escopo limitado (principle of least privilege):
  Key de leitura ≠ Key de escrita ≠ Key de admin

✓ Monitorar uso da key:
  Alertas para uso anormal (muitas requisições, IPs inesperados)

✗ Nunca:
  → Commitar keys no git (mesmo repositório privado)
  → Passar keys em query params
  → Logar requests com o header Authorization completo
  → Compartilhar uma key entre múltiplos serviços/equipes
```

## Autenticação server-side — o que fazer ao receber os headers

```python
# FastAPI — extraindo e validando Bearer JWT
from fastapi import Depends, HTTPException, Header
from jose import JWTError, jwt

SECRET_KEY = "sua-chave-secreta"
ALGORITHM = "HS256"

async def get_current_user(authorization: str = Header(...)):
    scheme, _, token = authorization.partition(" ")
    
    if scheme.lower() != "bearer":
        raise HTTPException(status_code=401, detail="Scheme inválido")
    
    try:
        payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
        user_id: str = payload.get("sub")
        if user_id is None:
            raise HTTPException(status_code=401, detail="Token inválido")
        return user_id
    except JWTError:
        raise HTTPException(
            status_code=401,
            detail="Token inválido ou expirado",
            headers={"WWW-Authenticate": "Bearer"}
        )

@app.get("/perfil")
async def meu_perfil(user_id: str = Depends(get_current_user)):
    return {"user_id": user_id}
```

## Erros comuns e armadilhas

**"Bearer" com maiúscula vs minúscula:** a spec diz que o scheme é case-insensitive, mas muitos servidores validam literalmente `"Bearer"` com B maiúsculo. Sempre usar exatamente `Authorization: Bearer <token>`.

**Armazenar JWT em localStorage:** JavaScript pode ler, então scripts XSS também podem. Para máxima segurança: usar cookies HttpOnly para o access token (browser gerencia, JS não acessa). Para APIs que requerem Bearer via JavaScript: aceitar o trade-off e focar em prevenção de XSS (CSP, sanitização).

**JWT sem verificação de expiração:** o JWT pode ser válido em assinatura mas expirado. Sempre verificar `exp` claim. Muitas bibliotecas fazem isso automaticamente, mas bibliotecas legadas ou uso manual podem esquecer.

**API Key na query string:** `?api_key=abc123` aparece em logs de nginx/apache, no Referer header, em ferramentas de analytics. Em produção, sempre usar header para API Keys.

## 🧩 Quiz de Fixação

1. Um JWT com payload `{"sub": "user_123", "role": "admin", "exp": 9999999999}` é enviado em `Authorization: Bearer eyJ...`. O servidor valida a assinatura e ela está correta. O atacante conseguiu o JWT de um usuário admin e vai tentar usá-lo amanhã. O servidor pode revogar esse JWT antes de `exp`? Quais são as opções?

2. Um cookie de sessão tem os atributos: `HttpOnly; Secure; SameSite=None; Domain=.empresa.com`. Um script malicioso injetado via XSS tenta roubar o cookie com `document.cookie`. O que acontece? E uma requisição CSRF de outro site consegue usar o cookie?

3. Por que usar `Authorization: Bearer <api_key>` em vez de `X-Api-Key: <api_key>` é considerado melhor prática para API Keys, mesmo que ambos funcionem tecnicamente?

**Respostas:**

1) **JWTs não são revoáveis nativamente** — a assinatura válida é suficiente para o servidor confiar neles até `exp`. Para revogar antes do prazo, as opções são: (a) **Blocklist/denylist:** manter no Redis ou banco a lista de JTI (JWT ID, claim `jti`) revogados. A cada requisição, verificar se o `jti` está na blocklist. Custo: uma consulta extra por requisição; (b) **Access tokens de curta duração:** se o access token expira em 15 minutos, o dano máximo de um token roubado é 15 minutos. Usar refresh tokens de longa duração para emitir novos access tokens; (c) **Refresh token rotation:** ao revogar a sessão, invalidar o refresh token — o usuário não consegue mais renovar o access token expirado; (d) **Mudar a chave de assinatura:** todos os tokens emitidos anteriormente tornam-se inválidos de uma vez — drástico, quebra todos os usuários. Para o cenário descrito, a melhor combinação é: access tokens com `exp` curto + blocklist para emergências.

2) **XSS tentando roubar com `document.cookie`:** **falha completamente** — `HttpOnly` impede que qualquer JavaScript acesse o cookie. `document.cookie` simplesmente não inclui cookies HttpOnly. O script malicioso não vê o cookie de sessão. **Requisição CSRF de outro site:** **consegue** — `SameSite=None` significa que o cookie é enviado em requisições cross-site (incluindo cross-origin). O atacante pode fazer um formulário em `site-malicioso.com` que envia um POST para `empresa.com` e o browser incluirá o cookie de sessão automaticamente. Para mitigar: usar `SameSite=Strict` ou `SameSite=Lax` (que bloqueia POSTs cross-site) combinado com CSRF token no body das requisições que modificam estado.

3) **Motivos para preferir `Authorization: Bearer`:** (a) **Padrão da indústria** — proxies, WAFs, APM tools e gateways de API reconhecem e processam o header `Authorization` de forma padronizada. Um WAF pode logar, inspecionar e mascarar automaticamente o valor do `Authorization`; headers customizados `X-Api-Key` podem não receber o mesmo tratamento; (b) **Consistência** — clientes que já enviam `Authorization: Bearer` para tokens de usuário usam o mesmo mecanismo para API Keys; (c) **Bibliotecas e frameworks** — middlewares de autenticação tipicamente extraem `Authorization` automaticamente; `X-Api-Key` requer configuração customizada; (d) **Spec compliance** — RFC 7235 define `Authorization` como o header de autenticação HTTP; não há RFC para `X-Api-Key`. Na prática, ambos funcionam — mas `Authorization: Bearer` é mais interoperável.
