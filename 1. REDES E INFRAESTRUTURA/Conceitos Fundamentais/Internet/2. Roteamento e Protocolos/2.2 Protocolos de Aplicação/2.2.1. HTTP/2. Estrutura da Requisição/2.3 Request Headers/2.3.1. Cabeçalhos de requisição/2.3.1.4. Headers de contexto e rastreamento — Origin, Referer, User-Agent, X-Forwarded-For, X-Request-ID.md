### Headers de contexto e rastreamento — Origin, Referer, User-Agent, X-Forwarded-For e X-Request-ID

Os headers de contexto carregam informações sobre o ambiente da requisição — de onde ela veio, quem a enviou, por onde passou e como rastreá-la. São essenciais para segurança (CORS, CSRF protection), analytics, debugging distribuído e rate limiting. Alguns são enviados automaticamente pelo browser; outros são adicionados por proxies e load balancers; outros são definidos pelo desenvolvedor para observabilidade.

---

## Origin — de onde veio a requisição

`Origin` identifica a origem (scheme + host + porta) de onde a requisição foi iniciada. É o header central do mecanismo CORS e da proteção contra CSRF.

```
Origin: https://app.meusite.com
        │       │
        │       └─ Host (sem path, sem query, sem fragment)
        └─ Scheme

Formato: scheme://host[:port]
  → SEM path, query ou fragment (diferente do Referer)
  → Apenas as três partes que definem a "origem" no modelo de segurança web
```

### Quando o browser envia Origin

```
Enviado em:
  → Requisições cross-origin (origem diferente do destino)
  → Requisições POST/PUT/PATCH/DELETE (mesmo em same-origin — em muitos browsers)
  → WebSocket handshakes
  → fetch() e XMLHttpRequest cross-origin

NÃO enviado em:
  → Navegação direta por link (GET de outra página)
  → Recursos carregados por <img>, <script>, <link> (apenas Referer)
  → Quando o usuário digita a URL diretamente
```

### Origin na proteção CSRF

```
CSRF (Cross-Site Request Forgery):
  Site malicioso (https://evil.com) tenta fazer o browser do usuário
  enviar uma requisição autenticada para https://banco.com/transferir

O browser envia automaticamente:
  POST /transferir HTTP/1.1
  Host: banco.com
  Origin: https://evil.com  ← browser inclui a origem real
  Cookie: session=abc123    ← cookie de sessão enviado automaticamente

O servidor pode verificar:
  if (origin !== "https://app.banco.com") → rejeitar (403 Forbidden)

Proteção simples e eficaz:
  O servidor sabe de onde veio a requisição
  Sites maliciosos não conseguem falsificar o Origin (browser protege)
```

```python
# FastAPI — validação de Origin para CSRF
from fastapi import Request, HTTPException

ALLOWED_ORIGINS = {"https://app.empresa.com", "https://admin.empresa.com"}

@app.middleware("http")
async def csrf_protection(request: Request, call_next):
    if request.method in ("POST", "PUT", "PATCH", "DELETE"):
        origin = request.headers.get("Origin")
        if origin and origin not in ALLOWED_ORIGINS:
            raise HTTPException(status_code=403, detail="Origin não autorizada")
    return await call_next(request)
```

## Referer — de qual página o usuário veio

`Referer` (sim, com erro de ortografia — "referrer" correto, mas o header foi padronizado com typo) informa a URL completa da página que originou a requisição.

```
Referer: https://www.google.com/search?q=produto+notebook

Diferença do Origin:
  Origin:  https://www.google.com            (apenas scheme+host)
  Referer: https://www.google.com/search?q=... (URL completa com path e query)
```

### Casos de uso do Referer

```
Analytics e tracking:
  Saber de qual site os usuários chegam (tráfego orgânico, social, email)
  
  Referer: https://www.google.com/... → tráfego orgânico Google
  Referer: https://t.co/abc123       → tráfego do Twitter
  Sem Referer                        → tráfego direto (ou bloqueado por política)

Proteção contra hotlinking:
  Servidor de imagens verifica se o Referer é do próprio site:
  Referer: https://outro-site.com → bloquear (não serve imagem para outros sites)
  Referer: https://meusite.com    → permitir
  
  # Nginx anti-hotlinking
  location ~* \.(jpg|jpeg|png|gif)$ {
    valid_referers none blocked meusite.com *.meusite.com;
    if ($invalid_referer) { return 403; }
  }

Debug e analytics:
  Entender o funil de navegação
  Qual página levou o usuário a completar uma compra
```

### Referer-Policy — controlar o que é enviado

Por questões de privacidade, o `Referrer-Policy` header controla quanto do Referer é enviado:

```
Referrer-Policy: no-referrer
  → Nunca envia o Referer

Referrer-Policy: no-referrer-when-downgrade
  → Envia Referer em HTTPS→HTTPS e HTTP→HTTP
  → NÃO envia em HTTPS→HTTP (evita vazar URL segura)
  → Padrão histórico

Referrer-Policy: origin
  → Envia apenas a origem (scheme+host), sem path/query
  → https://meusite.com/compra?produto=123 → Referer: https://meusite.com

Referrer-Policy: same-origin
  → Envia Referer completo apenas para o mesmo site
  → Para outros sites: não envia nada

Referrer-Policy: strict-origin-when-cross-origin (padrão moderno)
  → Same-origin: Referer completo
  → Cross-origin HTTPS→HTTPS: apenas a origem
  → HTTPS→HTTP: nada

Referrer-Policy: unsafe-url
  → Sempre envia o Referer completo (inseguro — expõe URLs privadas)
```

## User-Agent — quem está fazendo a requisição

`User-Agent` identifica o cliente HTTP — browser, bot, app, CLI. Historicamente usado para feature detection e analytics; hoje frequentemente usado para bot detection.

```
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36
            (KHTML, like Gecko) Chrome/120.0.0.0 Safari/537.36

Componentes (herança histórica — todos os browsers fingem ser Mozilla):
  Mozilla/5.0         → legado (todos os browsers enviam isso)
  (Windows NT 10.0; Win64; x64) → sistema operacional
  AppleWebKit/537.36  → engine de renderização
  Chrome/120.0.0.0    → browser real
  Safari/537.36       → legado (Chrome finge ser Safari para compatibilidade)
```

### User-Agents de serviços e ferramentas

```
curl:
  User-Agent: curl/8.4.0

Python requests:
  User-Agent: python-requests/2.31.0

Googlebot:
  User-Agent: Mozilla/5.0 (compatible; Googlebot/2.1; +http://www.google.com/bot.html)

AWS SDK Python:
  User-Agent: Boto3/1.34.0 Python/3.12.0 Linux/5.15.0

GitHub Actions:
  User-Agent: github-actions/2.0

Postman:
  User-Agent: PostmanRuntime/7.36.0
```

### Usos práticos do User-Agent

```
1. Analytics — entender o breakdown de browsers/OS dos usuários

2. Bot detection — identificar scrapers, crawlers maliciosos:
   Se User-Agent for vazio: provavelmente um bot mal configurado
   Se User-Agent for de ferramenta conhecida: depende do contexto

3. Feature delivery — servir conteúdo otimizado:
   Mobile User-Agent → servir imagens menores, layout mobile
   (melhor prática: usar CSS responsivo em vez de User-Agent detection)

4. Conditional rendering legacy:
   if (userAgent.includes("MSIE")) → IE compatibility mode
   (hoje: usar feature detection via JavaScript em vez de UA sniffing)

5. Rate limiting diferenciado:
   Bots legítimos (Googlebot): rate limit mais permissivo
   Bots desconhecidos: rate limit mais restritivo
```

```python
# Extraindo informações do User-Agent com user-agents library
from user_agents import parse

ua_string = request.headers.get("User-Agent", "")
ua = parse(ua_string)

print(f"Browser: {ua.browser.family} {ua.browser.version_string}")
print(f"OS: {ua.os.family} {ua.os.version_string}")
print(f"Device: {ua.device.family}")
print(f"É bot: {ua.is_bot}")
print(f"É mobile: {ua.is_mobile}")
```

## X-Forwarded-For — IP real atrás de proxies

Quando uma requisição passa por proxies, load balancers ou CDNs, o IP de origem da requisição TCP é o do último proxy — não o IP real do cliente. `X-Forwarded-For` preserva o IP original ao longo da cadeia de proxies.

```
Sem proxy:
  Cliente (203.0.113.10) → Servidor
  request.remote_addr = 203.0.113.10 ← IP real

Com proxy:
  Cliente (203.0.113.10) → Proxy (10.0.1.1) → Servidor
  request.remote_addr = 10.0.1.1 ← IP do proxy, não do cliente!
  X-Forwarded-For: 203.0.113.10  ← IP real preservado pelo proxy

Com múltiplos proxies:
  Cliente → Proxy A → Proxy B → Servidor
  X-Forwarded-For: 203.0.113.10, 10.0.1.1
                   │              │
                   └─ IP original │
                                  └─ IP do Proxy A (adicionado por Proxy B)
  
  Leitura: o IP mais à ESQUERDA é o IP original do cliente
```

### Headers relacionados

```
X-Forwarded-For: 203.0.113.10                    (IP original do cliente)
X-Forwarded-Host: api.meusite.com                (Host original)
X-Forwarded-Proto: https                         (Protocolo original)
X-Real-IP: 203.0.113.10                         (Nginx — alternativa ao X-Forwarded-For)
Forwarded: for=203.0.113.10; proto=https         (RFC 7239 — padrão formal, menos usado)
```

### Segurança — nunca confiar cegamente no X-Forwarded-For

```
O problema: um cliente malicioso pode manipular X-Forwarded-For:

curl -H "X-Forwarded-For: 1.2.3.4" https://api.meusite.com
→ Servidor recebe: X-Forwarded-For: 1.2.3.4
→ Server pensa que o cliente tem IP 1.2.3.4 (falso!)

Consequências:
  → Bypass de rate limiting por IP
  → Bypass de geolocation-based access control
  → Falsificação de auditoria

Solução correta: confiar apenas nos proxies que você controla

# Nginx — remover X-Forwarded-For do cliente, adicionar o real
proxy_set_header X-Forwarded-For $remote_addr;  # sobrescreve com IP real

# Se há múltiplos proxies confiáveis:
# Usar o último IP da lista que NÃO seja de um proxy confiável
TRUSTED_PROXIES = {"10.0.1.1", "10.0.1.2"}  # seus load balancers

def get_real_ip(request):
    xff = request.headers.get("X-Forwarded-For", "")
    if not xff:
        return request.remote_addr
    
    ips = [ip.strip() for ip in xff.split(",")]
    # Pegar o último IP que não é de proxy confiável
    for ip in reversed(ips):
        if ip not in TRUSTED_PROXIES:
            return ip
    return request.remote_addr
```

## X-Request-ID — rastreamento distribuído

`X-Request-ID` (também `X-Correlation-ID` ou `Request-ID`) é um identificador único para cada requisição. Permite rastrear uma requisição através de múltiplos serviços em uma arquitetura distribuída.

```
Sem X-Request-ID — investigando um erro:
  Log de serviço A: "Erro ao processar usuário 123" (14:32:05.123)
  Log de serviço B: "Falha na consulta ao banco" (14:32:05.124)
  Log de serviço C: "Timeout chamando serviço de pagamento" (14:32:05.125)
  
  São logs do MESMO request? De requests diferentes? Impossível saber!

Com X-Request-ID:
  Log A: "req_id=abc-123 - Erro ao processar usuário 123"
  Log B: "req_id=abc-123 - Falha na consulta ao banco"
  Log C: "req_id=abc-123 - Timeout chamando serviço de pagamento"
  
  Buscar "abc-123" em todos os logs → contexto completo da requisição!
```

### Fluxo do X-Request-ID em microserviços

```
Cliente (browser/app):
  POST /pedidos
  X-Request-ID: cli-req-abc123          ← pode gerar no cliente

API Gateway:
  → Recebe X-Request-ID do cliente
  → Ou gera um novo se não existir
  → Propaga para todos os serviços downstream

Serviço de Pedidos:
  POST /pedidos + X-Request-ID: cli-req-abc123
  → Loga todas as ações com esse ID
  → Chama Serviço de Estoque com o MESMO X-Request-ID

Serviço de Estoque:
  GET /estoque/123 + X-Request-ID: cli-req-abc123
  → Loga com o mesmo ID

Serviço de Pagamento:
  POST /cobrar + X-Request-ID: cli-req-abc123
  → Loga com o mesmo ID

Resultado: buscar "cli-req-abc123" em Elasticsearch/Splunk/Datadog
           mostra o trace completo de toda a operação
```

### Implementação do X-Request-ID

```python
# FastAPI — middleware para X-Request-ID
import uuid
from fastapi import Request
import logging

logger = logging.getLogger(__name__)

@app.middleware("http")
async def request_id_middleware(request: Request, call_next):
    # Aceitar do cliente ou gerar novo
    request_id = request.headers.get("X-Request-ID") or str(uuid.uuid4())
    
    # Adicionar ao contexto de logging
    # (em produção: usar contextvars para threading-safe logging)
    
    response = await call_next(request)
    
    # Ecoar no response para o cliente rastrear também
    response.headers["X-Request-ID"] = request_id
    
    logger.info(f"request_id={request_id} method={request.method} "
                f"path={request.url.path} status={response.status_code}")
    
    return response
```

```python
# Propagar para serviços downstream (httpx)
import httpx

async def chamar_servico_estoque(produto_id: int, request_id: str):
    async with httpx.AsyncClient() as client:
        response = await client.get(
            f"http://servico-estoque/estoque/{produto_id}",
            headers={"X-Request-ID": request_id}  # propaga o mesmo ID
        )
    return response.json()
```

## Outros headers de contexto relevantes

```
Host (obrigatório em HTTP/1.1):
  Host: api.empresa.com:8443
  → Identifica o servidor de destino (necessário para virtual hosting)
  → Obrigatório: sem ele, HTTP/1.1 retorna 400 Bad Request

Content-Length:
  Content-Length: 1234
  → Tamanho em bytes do body
  → Obrigatório em requisições com body em HTTP/1.1
  → HTTP/2 usa framing — Content-Length é opcional mas recomendado

Transfer-Encoding:
  Transfer-Encoding: chunked
  → Corpo enviado em "chunks" de tamanho variável
  → Usado quando o tamanho total não é conhecido antecipadamente
  → Incompatível com Content-Length (um ou outro)

Connection:
  Connection: keep-alive    ← HTTP/1.1: manter a conexão TCP aberta
  Connection: close         ← fechar após esta requisição
  → HTTP/2: esse header não é usado (multiplexing é nativo)
```

## Erros comuns e armadilhas

**Confiar cegamente no X-Forwarded-For para rate limiting:** um atacante pode enviar `X-Forwarded-For: 1.1.1.1` repetidamente com IPs diferentes para contornar rate limits. Use apenas o IP TCP real do proxy confiável mais próximo.

**Logar o Referer completo sem consideração de privacidade:** a URL completa do Referer pode conter tokens, IDs de sessão ou dados pessoais nos query params (`?reset_token=abc123`). Antes de logar, verificar se há dados sensíveis ou mascarar a query string.

**Não propagar X-Request-ID entre microserviços:** o ID é gerado no gateway mas não é passado adiante. Cada serviço gera seu próprio ID → impossível correlacionar logs. Criar um middleware padronizado que propaga automaticamente.

**Usar User-Agent para feature detection em vez de feature detection JS:** `navigator.userAgent` é facilmente falsificável e muda com cada versão do browser. Para saber se o browser suporta uma feature, usar `if ('IntersectionObserver' in window)` — direto e confiável.

## 🧩 Quiz de Fixação

1. Uma API de pagamentos usa `X-Forwarded-For` para rate limiting: máximo de 10 requisições por minuto por IP. Um atacante envia: `X-Forwarded-For: 1.2.3.4` na primeira requisição, `X-Forwarded-For: 5.6.7.8` na segunda, etc. O rate limiting funciona? Como corrigir?

2. Um servidor de imagens usa `Referer` para anti-hotlinking: bloqueia se o Referer não for do próprio domínio. Um usuário abre a URL da imagem diretamente na aba do browser (sem navegar de outra página). O que acontece com o Referer nesse caso, e a imagem seria bloqueada?

3. Três microserviços (API Gateway → Pedidos → Pagamento) precisam correlacionar logs. O time decide que cada serviço gera seu próprio UUID para X-Request-ID em vez de propagar o mesmo. Qual é o problema e como o observability fica comprometido?

**Respostas:**

1) O rate limiting **não funciona** — o atacante está forjando o `X-Forwarded-For` com IPs diferentes a cada requisição, fazendo o servidor acreditar que são clientes diferentes. O IP real do atacante (que vem na conexão TCP) está sendo ignorado. **Correção:** para rate limiting, usar **o IP da conexão TCP (`request.remote_addr`)** — que não pode ser falsificado pelo cliente, pois é determinado pela conexão de rede, não por headers. Se há proxies confiáveis na frente (load balancer, nginx), configurar esses proxies para sobrescrever `X-Forwarded-For` com o IP real antes de chegar na aplicação (`proxy_set_header X-Forwarded-For $remote_addr`), e usar apenas o IP que esses proxies confiáveis reportam — não o que o cliente enviou.

2) Quando o usuário abre uma URL de imagem diretamente no browser (digita na barra de endereços ou cola), o browser **não envia o header Referer** (ou envia vazio). O servidor recebe uma requisição sem Referer. O anti-hotlinking que bloqueia "Referer não for do próprio domínio" precisa tratar esse caso: **sem Referer = acesso direto = permitir**. Só bloquear quando o Referer está presente E é de outro domínio. Se o servidor bloqueasse requisições sem Referer, o usuário que abre a imagem diretamente (caso legítimo muito comum) seria bloqueado — criando péssima experiência. A regra correta é: `if (referer exists AND referer.origin !== "meusite.com") → block`.

3) **Problema principal:** cada serviço tem um UUID diferente, sem conexão entre eles. Para investigar um erro que envolveu os 3 serviços, o engenheiro precisa: (a) encontrar o log do API Gateway com o erro (UUID: aaa-111); (b) tentar descobrir qual requisição no Pedidos corresponde ao mesmo usuário/ação no mesmo timestamp (UUID: bbb-222 — sem conexão com aaa-111); (c) repetir para Pagamento (UUID: ccc-333). **O observability fica completamente comprometido:** correlação entre logs só é possível por tentativas manuais usando timestamp + dados de negócio (usuário, pedido ID) — processo demorado e propenso a erros. Em produção com dezenas de requisições simultâneas no mesmo segundo, a correlação manual é praticamente impossível. A solução é o API Gateway gerar 1 UUID → propagá-lo via `X-Request-ID` para todos os serviços downstream → cada serviço loga usando o mesmo ID recebido → qualquer log do sistema pode ser correlacionado com uma busca única.
