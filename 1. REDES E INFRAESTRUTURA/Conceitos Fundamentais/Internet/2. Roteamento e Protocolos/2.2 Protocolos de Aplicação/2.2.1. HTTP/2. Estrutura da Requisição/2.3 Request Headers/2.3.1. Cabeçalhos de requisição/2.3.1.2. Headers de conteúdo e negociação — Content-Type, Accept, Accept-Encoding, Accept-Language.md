### Headers de conteúdo e negociação — Content-Type, Accept, Accept-Encoding, Accept-Language

Os headers de conteúdo e negociação formam um sistema de comunicação bilateral entre cliente e servidor: o cliente declara o que está enviando (`Content-Type`) e o que consegue processar (`Accept`, `Accept-Encoding`, `Accept-Language`); o servidor responde no formato mais adequado ao cliente. Esse mecanismo — chamado **content negotiation** — permite que uma mesma URL sirva JSON para APIs, HTML para browsers e CSV para relatórios, sem duplicar endpoints.

---

## Content-Type — o que estou enviando

`Content-Type` descreve o tipo e o formato do body da requisição. É obrigatório em qualquer requisição com body (POST, PUT, PATCH). Sem ele, o servidor não sabe como interpretar os dados recebidos.

```
Content-Type: <type>/<subtype>; <parâmetros>

Exemplos:
  Content-Type: application/json
  Content-Type: application/json; charset=utf-8
  Content-Type: multipart/form-data; boundary=----WebKitFormBoundary7MA4YWx
  Content-Type: application/x-www-form-urlencoded
  Content-Type: text/plain; charset=utf-8
  Content-Type: application/xml
  Content-Type: application/octet-stream
```

### Os tipos MIME mais usados em HTTP

```
Tipo              MIME Type                        Quando usar
──────────────────────────────────────────────────────────────────
JSON              application/json                  APIs REST modernas (padrão)
Form URL encoded  application/x-www-form-urlencoded Formulários HTML tradicionais
Multipart         multipart/form-data               Upload de arquivos
Plain text        text/plain                        Texto simples, logs
HTML              text/html                         Páginas web
XML               application/xml ou text/xml       APIs SOAP, configs legadas
Binary stream     application/octet-stream          Arquivos binários genéricos
PDF               application/pdf                   Documentos PDF
ZIP               application/zip                   Arquivos comprimidos
CSV               text/csv                          Exportações tabulares
JPEG              image/jpeg                        Imagens JPEG
PNG               image/png                         Imagens PNG
MP4               video/mp4                         Vídeos
GraphQL           application/graphql               Queries GraphQL
MessagePack       application/msgpack               Alternativa binária ao JSON
Protobuf          application/x-protobuf            gRPC / Protocol Buffers
NDJSON            application/x-ndjson             Streaming JSON (uma linha por objeto)
```

### Parâmetro charset

```
Content-Type: text/plain; charset=utf-8
Content-Type: text/html; charset=ISO-8859-1

charset define a codificação de caracteres do body.

Para application/json:
  charset é tecnicamente desnecessário (JSON mandato UTF-8 por padrão)
  mas muitas APIs enviam "application/json; charset=utf-8" por clareza

Para text/* (text/plain, text/html, text/csv):
  charset=utf-8 é altamente recomendado para evitar ambiguidade

Se charset ausente em text/*:
  Padrão histórico: ISO-8859-1 (Latin-1)
  Browsers modernos: tentam detectar automaticamente
```

### Content-Type na requisição vs na resposta

```
Na REQUISIÇÃO (client → server):
  Informa como o servidor deve interpretar o body enviado
  
  POST /produtos
  Content-Type: application/json
  Body: {"nome": "Notebook", "preco": 2999}

Na RESPOSTA (server → client):
  Informa como o cliente deve interpretar o body recebido
  (este é um response header — detalhado no arquivo 3.2.1.1)
  
  HTTP/1.1 200 OK
  Content-Type: application/json
  Body: {"id": 123, "nome": "Notebook", "preco": 2999}
```

## Accept — o que quero receber

`Accept` diz ao servidor em quais formatos o cliente consegue processar a resposta. Permite que o mesmo endpoint retorne JSON para APIs, HTML para browsers ou CSV para ferramentas de BI.

```
Accept: <type>/<subtype>[; q=<quality>], ...

Exemplos:
  Accept: application/json                    → apenas JSON
  Accept: text/html                           → apenas HTML
  Accept: */*                                 → qualquer formato (default browsers)
  Accept: application/json, text/plain; q=0.9 → prefere JSON, aceita texto
  Accept: text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8
```

### Quality Factor (q) — preferências ponderadas

```
O parâmetro q (quality factor) vai de 0.0 a 1.0 (padrão 1.0):
  q=1.0 → preferência máxima (equivale a não especificar q)
  q=0.9 → segunda preferência
  q=0.5 → aceita mas prefere outros
  q=0.0 → não aceita (nunca use — melhor omitir o tipo)

Exemplo real — header Accept de um browser Chrome:
  text/html,application/xhtml+xml,application/xml;q=0.9,image/avif,image/webp,*/*;q=0.8

Interpretação:
  1. text/html                  (q=1.0) ← primeira escolha
  2. application/xhtml+xml      (q=1.0) ← segunda (empate com HTML)
  3. image/avif                 (q=1.0)
  4. image/webp                 (q=1.0)
  5. application/xml            (q=0.9)
  6. */* (qualquer coisa)       (q=0.8) ← fallback
```

### Content Negotiation na prática

```python
# FastAPI — servir JSON ou CSV baseado no Accept
from fastapi import Request
from fastapi.responses import JSONResponse, Response
import csv
import io

@app.get("/relatorio")
async def relatorio(request: Request):
    dados = [{"nome": "Produto A", "vendas": 150}, {"nome": "Produto B", "vendas": 89}]
    
    accept = request.headers.get("Accept", "application/json")
    
    if "text/csv" in accept:
        output = io.StringIO()
        writer = csv.DictWriter(output, fieldnames=["nome", "vendas"])
        writer.writeheader()
        writer.writerows(dados)
        return Response(
            content=output.getvalue(),
            media_type="text/csv",
            headers={"Content-Disposition": "attachment; filename=relatorio.csv"}
        )
    
    return JSONResponse(dados)
```

```bash
# curl — solicitar formatos diferentes do mesmo endpoint
curl -H "Accept: application/json" https://api.exemplo.com/relatorio
curl -H "Accept: text/csv" https://api.exemplo.com/relatorio
curl -H "Accept: application/xml" https://api.exemplo.com/relatorio
```

### Quando o servidor não suporta o Accept solicitado

```
HTTP/1.1 406 Not Acceptable
Content-Type: application/json

{
  "erro": "Formato não suportado",
  "formatos_aceitos": ["application/json", "text/csv"]
}

406 Not Acceptable: servidor não consegue produzir resposta no formato pedido
415 Unsupported Media Type: servidor não consegue processar o Content-Type enviado
```

## Accept-Encoding — compressão de dados

`Accept-Encoding` indica quais algoritmos de compressão o cliente suporta para o body da resposta. Compressão reduz drasticamente o volume de dados transferidos (tipicamente 60-80% para JSON/HTML/CSS).

```
Accept-Encoding: gzip, deflate, br, zstd
                 │     │        │   │
                 │     │        │   └─ Zstandard (mais novo e eficiente)
                 │     │        └─ Brotli (melhor compressão que gzip)
                 │     └─ DEFLATE (zlib)
                 └─ gzip (mais universal)
```

### Algoritmos de compressão HTTP

```
gzip:
  → Mais compatível — suportado por praticamente tudo
  → Baseado em DEFLATE com header gzip
  → Compressão: ~70% para JSON típico
  → Ideal para: compatibilidade máxima

Brotli (br):
  → Melhor compressão que gzip (~15-25% menor)
  → Mais lento para comprimir (mas decompressão rápida)
  → Suportado: browsers modernos, não suportado por algumas ferramentas CLI antigas
  → Requer HTTPS (browsers só suportam br em HTTPS)
  → Ideal para: sites modernos, CDNs

Zstandard (zstd):
  → Meta, 2023
  → Compressão equivalente ao Brotli, decompressão mais rápida
  → Suporte ainda crescendo
  → Ideal para: APIs de alto volume, streaming

deflate:
  → Algoritmo base do gzip (sem o header gzip)
  → Evitar — implementações inconsistentes entre servidores/clientes

identity:
  → Sem compressão
  → Accept-Encoding: identity → "não quero compressão"
```

### Ganho real de compressão

```
Arquivo JSON típico de API (resposta de listagem):
  Sem compressão:    48.200 bytes (~47 KB)
  Com gzip:          8.140 bytes (~8 KB)   → 83% menor
  Com brotli:        6.820 bytes (~6.7 KB) → 86% menor

HTML de uma página:
  Sem compressão:   120.000 bytes (~117 KB)
  Com gzip:          32.000 bytes (~31 KB)  → 73% menor
  Com brotli:        27.000 bytes (~26 KB)  → 78% menor

JavaScript bundle (React app):
  Sem compressão:   250.000 bytes (~244 KB)
  Com gzip:          78.000 bytes (~76 KB)  → 69% menor
  Com brotli:        65.000 bytes (~63 KB)  → 74% menor
```

### Como o servidor responde à compressão

```
Requisição:
  GET /api/produtos HTTP/1.1
  Accept-Encoding: gzip, br

Resposta comprimida:
  HTTP/1.1 200 OK
  Content-Encoding: gzip      ← informa o algoritmo usado
  Vary: Accept-Encoding        ← essencial para caches (ver abaixo)
  Content-Length: 8140         ← tamanho APÓS compressão

  [bytes comprimidos]

O cliente descomprime automaticamente (browsers, requests, axios)
```

### Vary: Accept-Encoding — essencial para cache

```
Se o servidor servir versões comprimidas e não-comprimidas do mesmo recurso
sem o header Vary: Accept-Encoding, um proxy/CDN pode cachear a versão gzip
e servi-la para um cliente que não suporta gzip → erro de decompressão.

Vary: Accept-Encoding
→ "O cache deve armazenar versões separadas para cada Accept-Encoding"
→ Sem isso: possíveis bugs em CDNs e proxies
```

## Accept-Language — idioma preferido

`Accept-Language` comunica ao servidor em quais idiomas e regiões o cliente prefere receber o conteúdo.

```
Accept-Language: pt-BR, pt;q=0.9, en-US;q=0.8, en;q=0.7, *;q=0.5

Interpretação:
  1. pt-BR (Português Brasil)   ← primeira escolha
  2. pt (Português genérico)    ← segunda
  3. en-US (Inglês EUA)         ← terceira
  4. en (Inglês genérico)       ← quarta
  5. * (qualquer idioma)        ← fallback
```

### Formato de locale

```
Estrutura: language[-region][-script][-extension]
  pt      → Português (genérico)
  pt-BR   → Português do Brasil
  pt-PT   → Português de Portugal
  en      → Inglês (genérico)
  en-US   → Inglês dos EUA
  en-GB   → Inglês do Reino Unido
  zh-CN   → Chinês Simplificado (China)
  zh-TW   → Chinês Tradicional (Taiwan)
  es-419  → Espanhol América Latina

Casos especiais:
  *       → qualquer idioma (fallback universal)
  q=0     → idioma não aceito (raramente usado)
```

### Uso em APIs — internacionalização (i18n)

```python
# FastAPI — retornar mensagens no idioma do cliente
from fastapi import Request

MESSAGES = {
    "pt-BR": {"erro_nao_encontrado": "Produto não encontrado"},
    "en-US": {"erro_nao_encontrado": "Product not found"},
    "es":    {"erro_nao_encontrado": "Producto no encontrado"},
}

def get_locale(request: Request) -> str:
    accept_lang = request.headers.get("Accept-Language", "en-US")
    # Pegar o primeiro idioma (mais preferido)
    preferred = accept_lang.split(",")[0].split(";")[0].strip()
    return preferred if preferred in MESSAGES else "en-US"

@app.get("/produtos/{id}")
async def get_produto(id: int, request: Request):
    locale = get_locale(request)
    produto = db.get(id)
    if not produto:
        raise HTTPException(
            status_code=404,
            detail=MESSAGES[locale]["erro_nao_encontrado"]
        )
    return produto
```

### Accept-Language vs URL para i18n

```
Via header Accept-Language:
  GET /produtos          + Accept-Language: pt-BR → resposta em português
  GET /produtos          + Accept-Language: en-US → resposta em inglês
  
  Prós: URL limpa, sem redundância
  Contras: difícil de compartilhar links (URL idêntica mas conteúdo diferente)
           SEO ruim (Google prefere URLs com idioma explícito)

Via URL (mais comum para sites):
  GET /pt-br/produtos    → sempre português
  GET /en/products       → sempre inglês
  
  Prós: URL canônica por idioma, melhor para SEO e compartilhamento
  Contras: duplicação de conteúdo para SEO, mais rotas para gerenciar

Recomendação:
  → APIs: Accept-Language (stateless, sem alterar URLs)
  → Sites/SPAs: URL com locale + Accept-Language como fallback
```

## Resumo — negociação de conteúdo completa

```
Requisição HTTP completa com todos os headers de negociação:

GET /relatorio HTTP/1.1
Host: api.empresa.com
Authorization: Bearer eyJ...
Accept: application/json, text/csv;q=0.9                → prefere JSON
Accept-Encoding: br, gzip;q=0.9, deflate;q=0.8          → prefere Brotli
Accept-Language: pt-BR, pt;q=0.9, en;q=0.7              → prefere pt-BR
Accept-Charset: utf-8, iso-8859-1;q=0.5                 → prefere UTF-8 (raro hoje)

Resposta ideal do servidor:
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8   → JSON em UTF-8
Content-Encoding: br                             → comprimido com Brotli
Content-Language: pt-BR                         → resposta em português
Vary: Accept, Accept-Encoding, Accept-Language   → cache por combinação
```

## Erros comuns e armadilhas

**POST sem Content-Type:** o servidor recebe o body mas não sabe o formato. Muitos frameworks retornam 400 Bad Request ou 415 Unsupported Media Type. Sempre incluir `Content-Type` em requisições com body.

**Content-Type: application/json sem charset:** tecnicamente JSON é sempre UTF-8, mas servidores legados podem tratar errado. Para máxima compatibilidade: `Content-Type: application/json; charset=utf-8`.

**Accept-Encoding: gzip sem Vary: Accept-Encoding no servidor:** proxies e CDNs podem cachear a versão errada. Verificar que o servidor inclui `Vary: Accept-Encoding` nas respostas comprimidas.

**Ignorar Accept-Language:** APIs que retornam mensagens de erro em inglês para usuários que enviaram `Accept-Language: pt-BR` criam má experiência. Mesmo que não haja tradução completa, mensagens de erro devem ser internacionalizáveis.

## 🧩 Quiz de Fixação

1. Um cliente envia `Accept: application/json;q=0.8, text/xml;q=0.9, */*;q=0.5`. O servidor suporta JSON e HTML. Qual formato deve usar na resposta e por quê?

2. Um servidor comprime todas as respostas com gzip mas não inclui o header `Vary: Accept-Encoding`. Um CDN cacheia a resposta de `GET /api/dados`. O próximo cliente que não suporta gzip (sem `Accept-Encoding` na requisição) recebe a resposta do cache. O que acontece?

3. Uma API REST internacional recebe `Accept-Language: zh-CN, zh;q=0.9, en-US;q=0.8`. A API suporta apenas `en-US` e `pt-BR`. Qual idioma deve usar na resposta e como implementar o fallback corretamente?

**Respostas:**

1) O servidor deve retornar **XML** (`text/xml`). Analisando as preferências: `text/xml;q=0.9` (segunda preferência do cliente, mas o servidor suporta XML) vs `application/json;q=0.8` (terceira preferência, e o servidor suporta JSON) vs `text/html` (suportado pelo servidor, mas não listado no Accept — exceto via `*/*;q=0.5`). Entre os formatos que o servidor suporta E o cliente aceita explicitamente: XML com q=0.9 > JSON com q=0.8. O wildcard `*/*;q=0.5` cobre HTML (q=0.5) mas é menor que JSON (q=0.8) e XML (q=0.9). Portanto: XML com q=0.9 vence. Na prática, muitos servidores simplificam e não implementam negociação complexa — servem JSON por padrão a menos que `Accept: text/html` seja enviado.

2) **O CDN cacheia a resposta comprimida em gzip** (com `Content-Encoding: gzip` no payload). Quando um cliente sem `Accept-Encoding: gzip` requisita o mesmo recurso, o CDN serve do cache — a resposta comprimida. O cliente recebe bytes gzip que não sabe descomprimir → **erro de decompressão ou dados corrompidos**. Com `Vary: Accept-Encoding`, o CDN manteria duas entradas de cache: uma para clientes que aceitam gzip e outra para os que não aceitam, servindo a versão correta para cada tipo de cliente.

3) O idioma correto é **en-US**. Processo de fallback: (1) verificar `zh-CN` — não suportado; (2) verificar `zh` (genérico) — não suportado; (3) verificar `en-US` — **suportado** → usar. O `pt-BR` não é relevante pois `en-US` (q=0.8) foi encontrado antes. **Implementação correta do fallback:**
```python
def resolve_language(accept_lang: str, supported: list) -> str:
    # Parsear e ordenar por q value
    langs = []
    for lang_item in accept_lang.split(','):
        parts = lang_item.strip().split(';')
        lang = parts[0].strip()
        q = 1.0
        for p in parts[1:]:
            if p.strip().startswith('q='):
                q = float(p.split('=')[1])
        langs.append((lang, q))
    
    langs.sort(key=lambda x: x[1], reverse=True)
    
    # Tentar match exato, depois match por prefixo
    for lang, _ in langs:
        if lang in supported:
            return lang
        # Fallback: prefixo (zh-CN → zh)
        prefix = lang.split('-')[0]
        for sup in supported:
            if sup.startswith(prefix):
                return sup
    
    return supported[0]  # default: primeiro suportado
```
