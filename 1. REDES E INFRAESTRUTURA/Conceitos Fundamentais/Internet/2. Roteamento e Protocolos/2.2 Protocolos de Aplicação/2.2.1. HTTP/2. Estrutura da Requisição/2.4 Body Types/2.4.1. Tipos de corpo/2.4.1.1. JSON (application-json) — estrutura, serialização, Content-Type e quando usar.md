### JSON (application/json) — estrutura, serialização, Content-Type e quando usar

JSON (JavaScript Object Notation) é o formato de body dominante nas APIs modernas. Leve, legível por humanos e suportado nativamente por virtualmente toda linguagem de programação, tornou-se o padrão de facto para troca de dados em APIs REST. Entender sua estrutura, regras de serialização e as sutilezas do `Content-Type` é fundamental para construir e consumir APIs corretamente.

---

## Estrutura do JSON

JSON define apenas 6 tipos de valores primitivos e 2 tipos de estrutura:

```
Tipos primitivos:
  string:  "texto entre aspas duplas"
  number:  42, 3.14, -7, 1e10  (sem diferença int/float no JSON)
  boolean: true, false          (minúsculas — diferente de outras linguagens)
  null:    null                 (minúsculo)

Tipos compostos:
  object:  {"chave": valor, "outra": valor2}  (chaves DEVEM ser strings)
  array:   [valor1, valor2, valor3]

Regras:
  → Aspas: SEMPRE aspas duplas ("), nunca simples (')
  → Vírgulas: entre elementos, mas NÃO após o último
  → Comentários: NÃO existem em JSON puro
  → Trailing comma: inválido {"a": 1, "b": 2,}  ← o último , é erro
```

## Content-Type para JSON

```
Requisição (enviando JSON ao servidor):
  Content-Type: application/json
  Content-Type: application/json; charset=utf-8

Resposta (servidor retornando JSON):
  Content-Type: application/json
  Content-Type: application/json; charset=utf-8

Variantes específicas (menos comuns):
  application/vnd.api+json         → JSON:API specification
  application/graphql-response+json → GraphQL responses
  application/merge-patch+json      → JSON Merge Patch (RFC 7396)
  application/json-patch+json       → JSON Patch (RFC 6902)
  application/problem+json          → RFC 7807 — respostas de erro padronizadas
```

### Por que `charset=utf-8` é opcional no JSON

```
RFC 8259 (a spec JSON atual) mandata que JSON SEMPRE seja UTF-8:
  "JSON text exchanged between systems that are not part of a closed
  ecosystem MUST be encoded using UTF-8"

Portanto:
  Content-Type: application/json            → UTF-8 implícito (correto)
  Content-Type: application/json; charset=utf-8 → explícito (não faz mal)

Na prática:
  Muitas APIs e frameworks incluem charset=utf-8 por clareza
  Alguns linters/validators são mais estritos e preferem sem charset
  Para interoperabilidade máxima: incluir charset=utf-8
```

## Serialização — como tipos são convertidos para JSON

Diferentes linguagens e tipos precisam de atenção especial ao serializar para JSON.

### Datas e timestamps

```
JSON não tem tipo nativo de data — são sempre strings:

Formatos mais comuns:
  ISO 8601 (recomendado):
    "2024-01-15T10:30:00Z"           → UTC
    "2024-01-15T10:30:00+03:00"      → com timezone offset
    "2024-01-15"                     → apenas data (sem hora)

  Unix timestamp (inteiro):
    1705312200                       → segundos desde 1970-01-01T00:00:00Z
    1705312200000                    → milissegundos (JavaScript Date.now())

  Formatos legados (evitar em APIs novas):
    "15/01/2024"                     → ambíguo (BR vs EUA)
    "Jan 15, 2024"                   → não padronizado
    "2024-01-15 10:30:00"            → sem timezone (ambíguo)

Recomendação: sempre usar ISO 8601 com timezone explícito
  "2024-01-15T10:30:00Z" (Z = UTC = melhor)
  "2024-01-15T07:30:00-03:00" (offset explícito = correto mas mais verboso)
```

### Números e precisão

```
JSON number não distingue int de float:
  42     → pode ser int ou float (depende do parser)
  42.0   → explicitamente float
  1e10   → notação científica (válida)

PERIGO — números grandes (floating point):
  JSON número: 9007199254740993        ← maior que Number.MAX_SAFE_INTEGER
  
  JavaScript: JSON.parse('{"id": 9007199254740993}').id
  → 9007199254740992                   ← PERDA DE PRECISÃO!
  
  Por quê: JavaScript usa double (64-bit float) para todos os números
           Integers > 2^53 não têm representação exata
  
  Soluções:
  1. Enviar IDs grandes como STRING: {"id": "9007199254740993"}
  2. Usar bibliotecas que suportam BigInt: json-bigint (Node.js)
  3. Usar BigDecimal/Long (Java) com serialização customizada
  
  Problema real: Twitter mudou IDs de int para string nos tweets exatamente
                 por esse motivo (tweet_id_str vs tweet_id)
```

### Null vs campo ausente

```
Diferença semântica:
  {"nome": null}       → campo existe, mas o valor é nulo/desconhecido
  {}                   → campo não existe/não foi informado

Na prática (PUT/PATCH):
  PATCH com {"nome": null}     → explicitamente setar nome como nulo
  PATCH com {}                 → não alterar o nome

Boas práticas:
  → Documentar claramente o que null significa em cada campo
  → Em GET responses: omitir campos opcionais não preenchidos OU retornar null
    Ser consistente — nunca misturar os dois padrões
  → Para operações de patch: preferir campos ausentes = sem alteração
    e null = setar como nulo
```

### Serialização em diferentes linguagens

```python
# Python — json module
import json
from datetime import datetime, timezone
from decimal import Decimal

dados = {
    "nome": "João",
    "data": datetime.now(timezone.utc),  # TypeError sem custom encoder
    "preco": Decimal("19.99")            # TypeError sem custom encoder
}

# Custom encoder para tipos não-nativos
class CustomEncoder(json.JSONEncoder):
    def default(self, obj):
        if isinstance(obj, datetime):
            return obj.isoformat()
        if isinstance(obj, Decimal):
            return float(obj)  # ou str(obj) para precisão exata
        return super().default(obj)

json_string = json.dumps(dados, cls=CustomEncoder, ensure_ascii=False)
# ensure_ascii=False → preserva caracteres Unicode (ã, é, ç)

# Parsing
dados_dict = json.loads(json_string)
```

```javascript
// JavaScript — JSON nativo
const dados = {
  nome: "João",
  data: new Date(),           // Date → string ISO automaticamente
  valor: 19.99               // number (cuidado com precisão)
};

// Serialização
const jsonString = JSON.stringify(dados);
const jsonPretty = JSON.stringify(dados, null, 2);  // indentado com 2 espaços

// Parsing
const obj = JSON.parse(jsonString);

// Revivers para transformar strings de volta em tipos específicos
const objComDatas = JSON.parse(jsonString, (key, value) => {
  if (typeof value === 'string' && /\d{4}-\d{2}-\d{2}T/.test(value)) {
    return new Date(value);  // converte ISO strings de volta para Date
  }
  return value;
});
```

```go
// Go — encoding/json
type Produto struct {
    ID        int64     `json:"id"`
```

## Boas práticas de design com JSON

### Convenção de nomes (naming conventions)

```
snake_case (recomendado para APIs REST):
  {"nome_completo": "João", "data_nascimento": "1990-01-15"}
  Mais comum em Python, Ruby, Go, bancos de dados

camelCase (comum em JavaScript/Java):
  {"nomeCompleto": "João", "dataNascimento": "1990-01-15"}
  Mais natural para clientes JavaScript

PascalCase (C#/.NET):
  {"NomeCompleto": "João", "DataNascimento": "1990-01-15"}
  Evitar em APIs públicas — não é idiomático

Regra prática:
  → APIs consumidas principalmente por JS frontend: camelCase
  → APIs Python: snake_case
  → APIs públicas: documentar e ser consistente (misturar é pior que escolher qualquer um)
```

### Estrutura de erros padronizada (RFC 7807)

```json
// Problem+JSON — formato padronizado para respostas de erro
// Content-Type: application/problem+json

{
  "type": "https://api.empresa.com/erros/recurso-nao-encontrado",
  "title": "Produto não encontrado",
  "status": 404,
  "detail": "Produto com ID 123 não existe no catálogo",
  "instance": "/produtos/123",
  "trace_id": "req-abc-123"
}

// Alternativa comum (não padronizada mas amplamente usada):
{
  "error": "NOT_FOUND",
  "message": "Produto com ID 123 não encontrado",
  "code": 404,
  "timestamp": "2024-01-15T10:30:00Z"
}
```

```json
// Content-Type: application/vnd.empresa.produto.v2+json
```

## Quando NÃO usar JSON

```
JSON é inadequado quando:

Performance extrema:
  JSON é texto — parsing e serialização têm custo de CPU
  Para alto volume entre serviços: usar Protocol Buffers (protobuf) ou MessagePack
  protobuf: ~10x menor, ~6x mais rápido para serializar
  msgpack: ~2x menor que JSON, ainda legível em binário

Dados binários (imagens, arquivos):
  JSON não suporta binário nativamente
  Base64 encoding aumenta o tamanho em ~33%
  Para binários: multipart/form-data ou envio direto (application/octet-stream)

Streaming de dados:
  JSON tradicional = um único objeto → necessário parsear tudo antes de processar
  Para streaming: NDJSON (Newline Delimited JSON) — uma linha por objeto
  Content-Type: application/x-ndjson
  {"evento": "login", "user": "123"}\n
  {"evento": "compra", "user": "456"}\n

Dados tabulares grandes:
  JSON tem overhead de chaves repetidas em arrays de objetos
  Para CSVs grandes: usar CSV (text/csv) — muito mais compacto

Documentos com hierarquia profunda e XML legado:
  SOAP, RSS, Atom — XML é o formato esperado
  application/xml ou text/xml
```

## Erros comuns e armadilhas

**Trailing comma:** `{"a": 1, "b": 2,}` é JSON inválido, embora JavaScript aceite. Muitos parsers strict rejeitam.

**Comentários em JSON:** JSON puro não suporta comentários. Para configurações que precisam de comentários, usar JSON5 ou JSONC (extensões, não padrão) ou YAML.

**Aspas simples:** `{'nome': 'João'}` é inválido em JSON. Sempre aspas duplas.

**Numbers como strings quando necessário:** IDs de banco de dados que excedem `Number.MAX_SAFE_INTEGER` (>2^53) devem ser strings em JSON para clientes JavaScript. IDs do Twitter/snowflake são exemplos reais.

**Não validar o Content-Type:** ao receber uma requisição POST, verificar sempre que `Content-Type: application/json` está presente antes de parsear o body. Corpo sem Content-Type pode ser qualquer coisa.

## 🧩 Quiz de Fixação

1. Uma API retorna `{"preco": 19.99}`. Um cliente JavaScript parseia isso com `JSON.parse()` e obtém `19.989999999999998`. Por que isso acontece e quais são as duas abordagens para lidar com valores monetários em JSON?

2. Uma API REST usa campos opcionais: quando um usuário não tem foto de perfil, a API retorna às vezes `{"foto": null}` e às vezes omite o campo `foto` completamente. Por que essa inconsistência é problemática e como os clientes deveriam lidar com ela?

3. Um serviço Python recebe um JSON com uma data `"data_pedido": "2024-01-15T10:30:00Z"` e precisa calcular há quantos dias o pedido foi feito. Como converter a string ISO para um objeto datetime em Python, e por que nunca usar `datetime.fromisoformat()` diretamente sem tratar o 'Z'?

**Respostas:**

1) O problema é a **representação de ponto flutuante** (IEEE 754 double precision). `19.99` não tem representação exata em binário — o valor armazenado é a aproximação mais próxima, que em decimal é `19.989999999999998`. **Abordagem 1 — Enviar como string:** `{"preco": "19.99"}` — o cliente parseia a string para um tipo decimal de alta precisão. Desvantagem: perde a semântica de número no JSON, precisa conversão explícita. **Abordagem 2 — Usar inteiros em centavos (mais comum e recomendado):** `{"preco_centavos": 1999}` — armazena e transfere como inteiro (sem problema de float), divide por 100 para exibição. É a abordagem do Stripe, Adyen e da maioria das APIs financeiras sérias. Nunca fazer operações matemáticas em JSON numbers para valores monetários sem antes converter para Decimal (Python) ou BigDecimal (Java).

2) A inconsistência cria um contrato de API ambíguo: clientes não sabem se devem checar `"foto" in response` OU `response.foto !== null` OU ambos. Código como `if (user.foto)` pode funcionar às vezes e falhar outras vezes dependendo de qual formato o servidor retornou. Causa bugs difíceis de reproduzir. **Como os clientes devem lidar:** com defensive programming — `const foto = user?.foto ?? null` (JavaScript) ou `user.get("foto")` (Python) tratando ambos os casos como "sem foto". **O correto:** a API deve escolher UMA convenção e seguir sempre. A recomendação mais comum é: **sempre incluir o campo, com valor null quando não preenchido** — isso torna o schema previsível e a validação mais simples (o cliente sempre sabe quais campos existem).

3) Em Python 3.11+, `datetime.fromisoformat("2024-01-15T10:30:00Z")` funciona (Z é suportado). Em Python 3.10 e anteriores, `fromisoformat()` não aceita o sufixo "Z" e lança `ValueError`. **Abordagem correta e compatível:**
```python
from datetime import datetime, timezone, timedelta

def parse_iso_date(s: str) -> datetime:
    # Substituir Z por +00:00 para compatibilidade
    s = s.replace("Z", "+00:00")
    return datetime.fromisoformat(s)  # retorna datetime com tzinfo=UTC

# Calcular dias
data_pedido = parse_iso_date("2024-01-15T10:30:00Z")
agora = datetime.now(timezone.utc)
dias = (agora - data_pedido).days

# Alternativa com dateutil (mais robusta):
from dateutil import parser
data_pedido = parser.parse("2024-01-15T10:30:00Z")  # aceita qualquer formato ISO
```
**Por que o `Z` é problemático:** `Z` é a notação padrão para UTC em ISO 8601, mas o Python implementou suporte a ele apenas no 3.11. Sempre usar `replace("Z", "+00:00")` para garantir compatibilidade em todos os ambientes.
