### Plain text, XML e binary — outros content-types, casos de uso e comparativo

JSON domina as APIs modernas, mas o ecossistema HTTP é muito mais amplo. `text/plain` é usado para logs, webhooks e respostas simples. XML persiste em sistemas corporativos legados, SOAP e feeds RSS. Dados binários (`application/octet-stream`, `image/*`, `audio/*`) são essenciais para qualquer transferência de arquivo. Entender quando cada formato é adequado — e como lidar com ele — completa o quadro dos body types HTTP.

---

## text/plain — texto puro sem estrutura

O tipo mais simples: apenas texto sem nenhuma formatação ou estrutura definida.

```
Content-Type: text/plain
Content-Type: text/plain; charset=utf-8

Casos de uso:
  → Respostas simples de APIs (health checks, versão, ping)
  → Logs e mensagens de debug
  → Webhooks que enviam texto puro
  → Mensagens de erro legíveis por humanos (em alguns sistemas legados)
  → Exportação de dados em CSV/TSV simplificados
  → Callbacks de verificação (ex: Google Search Console: "google-site-verification=abc123")
```

### Health checks e endpoints de diagnóstico

```python
# FastAPI — health check com text/plain
from fastapi.responses import PlainTextResponse

@app.get("/health")
async def health():
    return PlainTextResponse("OK")

@app.get("/version")
async def version():

```

```
Requisição:  GET /health
Resposta:
  HTTP/1.1 200 OK
  Content-Type: text/plain; charset=utf-8
  Content-Length: 2

  OK
```

# FastAPI — receber body como texto puro

async def webhook_texto(request: Request):

## text/csv — dados tabulares

CSV (Comma-Separated Values) não é um padrão bem definido, mas é universalmente compreendido e adequado para exportações de dados tabulares.

```
Content-Type: text/csv; charset=utf-8
Content-Disposition: attachment; filename="relatorio-janeiro.csv"
```

```
Formato CSV básico:
  id,nome,email,valor,data
  1,João Silva,joao@email.com,1500.50,2024-01-15
  2,Maria Santos,maria@email.com,2300.00,2024-01-16
  3,Pedro Costa,pedro@email.com,800.75,2024-01-17
```

```python
# FastAPI — exportar CSV
import csv
import io
from fastapi.responses import StreamingResponse

@app.get("/relatorio/csv")
async def exportar_csv():
    dados = db.get_vendas_janeiro()
    
    output = io.StringIO()
    writer = csv.DictWriter(
        output,
        fieldnames=["id", "nome", "email", "valor", "data"],
        extrasaction="ignore"
    )
    writer.writeheader()
    writer.writerows(dados)
    
    output.seek(0)
    return StreamingResponse(
        iter([output.getvalue()]),
        media_type="text/csv",
        headers={
            "Content-Disposition": "attachment; filename=relatorio-janeiro.csv"
        }
    )
```

## application/xml e text/xml — dados estruturados em XML

XML (eXtensible Markup Language) foi o formato dominante antes do JSON. Ainda é obrigatório em contextos específicos.

```
Content-Type: application/xml
Content-Type: text/xml
Content-Type: application/soap+xml; charset=utf-8
```

### Diferença entre application/xml e text/xml

```
text/xml:         tratado como texto (charset padrão: US-ASCII!)
                  legado — pode causar problemas de encoding com UTF-8
                  
application/xml:  tratado como dados binários
                  charset padrão: UTF-8 (conforme RFC)
                  preferido para novos sistemas

Recomendação: sempre usar application/xml com charset=utf-8
```

### Estrutura XML

```xml
<!-- Exemplo de XML em resposta de API -->
<?xml version="1.0" encoding="UTF-8"?>
<produto xmlns="https://api.empresa.com/schema/v1">
  <id>123</id>
  <nome>Notebook Dell XPS</nome>
  <preco moeda="BRL">4999.90</preco>
  <ativo>true</ativo>
  <categorias>
    <categoria>Eletrônicos</categoria>
    <categoria>Computadores</categoria>
  </categorias>
  <criado_em>2024-01-15T10:30:00Z</criado_em>
</produto>
```

### Onde XML ainda é obrigatório

```
1. SOAP Web Services (sistemas corporativos legados):
   → SAP, Oracle, sistemas bancários antigos
   → Content-Type: application/soap+xml

2. Feeds RSS e Atom:
   → RSS 2.0 e Atom 1.0 são XML puro
   → Content-Type: application/rss+xml | application/atom+xml

3. Configurações e metadados:
   → Android Manifest: AndroidManifest.xml
   → Maven POM: pom.xml
   → Spring Bean: applicationContext.xml

4. Protocolos de pagamento (Brasil):
   → NFe (Nota Fiscal Eletrônica) é XML assinado digitalmente
   → PAF-ECF, SPED, outros sistemas fiscais

5. Microsoft Office:
   → DOCX, XLSX, PPTX são ZIPs com XML dentro
   → OOXML (Office Open XML)
   
6. SVG (Scalable Vector Graphics):
   → Content-Type: image/svg+xml
   → XML para gráficos vetoriais
```

## application/octet-stream — binário genérico

`application/octet-stream` é o Content-Type genérico para "qualquer sequência de bytes". Usado quando o tipo específico é desconhecido ou quando o servidor quer forçar o download.

```
Content-Type: application/octet-stream
Content-Disposition: attachment; filename="backup.tar.gz"
```

```
Casos de uso:
  → Download de arquivos de tipo desconhecido
  → Forçar download em vez de exibição no browser
  → Upload de arquivos sem tipo específico
  → Dados binários proprietários
  → Streaming de dados binários
```

### Content-Disposition — controlar download vs exibição

```
Content-Disposition: inline; filename="relatorio.pdf"
  → Browser tenta EXIBIR o arquivo (se souber como)
  → PDF: abre no viewer do browser
  → JPEG: exibe no browser
  
Content-Disposition: attachment; filename="relatorio.pdf"
  → Browser FORÇA DOWNLOAD — caixa de diálogo "Salvar como"
  → Independente do Content-Type
  → Sugere o nome de arquivo "relatorio.pdf"

Sem Content-Disposition:
  → Browser decide baseado no Content-Type
  → image/jpeg: exibe inline
  → application/octet-stream: faz download (comportamento padrão)
```

### Tipos binários específicos

```
Imagens:
  image/jpeg      → JPEG
  image/png       → PNG
  image/gif       → GIF
  image/webp      → WebP (melhor compressão)
  image/avif      → AVIF (melhor ainda)
  image/svg+xml   → SVG (vetorial, XML)

Documentos:
  application/pdf                          → PDF
  application/msword                       → .doc
  application/vnd.openxmlformats-officedocument.wordprocessingml.document → .docx
  application/vnd.ms-excel                 → .xls
  application/vnd.openxmlformats-officedocument.spreadsheetml.sheet → .xlsx

Comprimidos:
  application/zip                → ZIP
  application/gzip               → GZIP
  application/x-tar              → TAR
  application/x-7z-compressed    → 7-Zip

Áudio/Vídeo:
  audio/mpeg    → MP3
  audio/ogg     → OGG
  video/mp4     → MP4
  video/webm    → WebM

APIs binárias de alto desempenho:
  application/x-protobuf    → Protocol Buffers (gRPC)
  application/msgpack       → MessagePack
  application/cbor          → CBOR (Concise Binary Object Representation)
```

### Download de arquivo no servidor

```python
# FastAPI — servir arquivo para download
from fastapi.responses import FileResponse

@app.get("/relatorio/download")
async def download_relatorio(id: int):
    caminho = f"/tmp/relatorio_{id}.pdf"
    
    if not os.path.exists(caminho):
        raise HTTPException(404, "Relatório não encontrado")
    
    return FileResponse(
        path=caminho,
        media_type="application/pdf",
        filename=f"relatorio-{id}.pdf",  # sugere nome para download
        # filename= → adiciona Content-Disposition: attachment automaticamente
    )

# Streaming de arquivo grande (sem carregar tudo em memória)
@app.get("/arquivos/{nome}")
async def download_arquivo(nome: str):
    caminho = f"/arquivos/{nome}"
    
    async def iterfile():
        async with aiofiles.open(caminho, "rb") as f:
            while chunk := await f.read(64 * 1024):  # 64 KB chunks
                yield chunk
    
    return StreamingResponse(
        iterfile(),
        media_type="application/octet-stream",
        headers={"Content-Disposition": f"attachment; filename={nome}"}
    )
```

## Formatos binários de alta performance

Para APIs com alto volume de dados, JSON pode ser substituído por formatos binários:

### Protocol Buffers (protobuf)

```
Vantagens sobre JSON:
  → 3-10x menor em tamanho
  → 5-10x mais rápido para serializar/deserializar
  → Schema fortemente tipado (.proto file)
  → Backward/forward compatible

Custo:
  → Não é legível por humanos (binário)
  → Requer geração de código a partir do .proto
  → Debugging mais complexo

Usado por: gRPC, Kubernetes, Google internamente
Content-Type: application/x-protobuf ou application/grpc+proto
```

```protobuf
// produto.proto
syntax = "proto3";

message Produto {
  int32 id = 1;
  string nome = 2;
  double preco = 3;
  bool ativo = 4;
  repeated string categorias = 5;
}
```

### MessagePack

```
Posição intermediária entre JSON e protobuf:
  → ~2x menor que JSON
  → ~2x mais rápido que JSON
  → SEM schema — estrutura dinâmica como JSON
  → Legível como JSON (com ferramenta)

Ideal quando:
  → Alta performance sem querer gerenciar schemas .proto
  → Substituir JSON em APIs internas de alto volume

Content-Type: application/msgpack
```

## Segurança — validação de Content-Type

```python
# Nunca confiar no Content-Type sem validar o conteúdo real

import magic  # python-magic — detecta tipo pelo conteúdo (não pela extensão)

@app.post("/upload/imagem")
async def upload_imagem(imagem: UploadFile = File(...)):
    conteudo = await imagem.read()
    
    # Verificar tipo pelo CONTEÚDO (magic bytes), não pelo Content-Type declarado
    tipo_real = magic.from_buffer(conteudo, mime=True)
    
    tipos_permitidos = {"image/jpeg", "image/png", "image/webp"}
    if tipo_real not in tipos_permitidos:
        raise HTTPException(
            400,
            f"Tipo de arquivo inválido: {tipo_real}. Permitidos: {tipos_permitidos}"
        )
    
    # Verificar tamanho
    if len(conteudo) > 10 * 1024 * 1024:  # 10 MB
        raise HTTPException(400, "Arquivo muito grande (máximo 10 MB)")
    
    # Salvar
    ...
```

```
Por que validar pelo conteúdo e não pelo Content-Type?

Um atacante pode enviar:
  Content-Type: image/jpeg
  Body: [arquivo PHP malicioso]

Se o servidor salva o arquivo e o executa como imagem:
  → Remote Code Execution (RCE) — vulnerabilidade crítica

Defesa:
  1. Validar Content-Type (primeira linha de defesa)
  2. Verificar magic bytes do arquivo (defesa real)
  3. Sanitizar e reprocessar imagens (ex: re-encode com Pillow)
  4. Servir arquivos de upload de domínio/bucket separado
  5. Nunca executar conteúdo de upload
```

## Erros comuns e armadilhas

**Usar `text/xml` em vez de `application/xml`:** `text/xml` tem charset padrão US-ASCII — caracteres UTF-8 como acentos são interpretados incorretamente. Sempre usar `application/xml; charset=utf-8`.

**Confiar no Content-Type declarado para segurança:** um cliente pode declarar qualquer Content-Type. Para uploads de arquivo, sempre verificar os magic bytes (primeiros bytes do arquivo) com `python-magic` ou equivalente.

**Não definir `Content-Disposition` para downloads:** sem esse header, o browser decide como exibir o arquivo. `application/pdf` sem `Content-Disposition: attachment` abre no viewer do browser em vez de fazer download — pode ser indesejado.

**Usar `application/octet-stream` para tudo:** um tipo genérico faz com que browsers, proxies e ferramentas não saibam como processar o conteúdo. Use o tipo específico (`image/jpeg`, `application/pdf`) quando conhecido.

## 🧩 Quiz de Fixação

1. Uma API retorna uma imagem JPEG com `Content-Type: application/octet-stream`. Um browser que recebe essa resposta vai exibir a imagem ou fazer download? E se fosse `Content-Type: image/jpeg`? O que muda?

2. Um sistema de upload recebe um arquivo com `Content-Type: image/png` declarado pelo cliente. O servidor salva diretamente sem verificar o conteúdo. Um atacante envia um arquivo PHP disfarçado como PNG. Se o servidor servir esse arquivo com `Content-Type: image/png`, há risco? E se servir com execução de PHP?

3. Uma empresa usa SOAP XML para integrar com um parceiro legado. A requisição SOAP chegou mas o servidor retorna 415 Unsupported Media Type. O desenvolvedor está enviando `Content-Type: application/xml`. Qual pode ser o Content-Type correto para SOAP e como verificar?

**Respostas:**

1) Com `Content-Type: application/octet-stream`: o browser **forçará o download** — caixa de diálogo "Salvar como" aparece. Browsers tratam `octet-stream` como binário desconhecido e sempre baixam. Com `Content-Type: image/jpeg`: o browser **exibe a imagem inline** diretamente na aba, sem perguntar — pois reconhece o tipo e sabe renderizá-lo. O que muda: o browser usa o Content-Type para decidir como processar. Para forçar download de uma imagem, usar `Content-Disposition: attachment` junto com `image/jpeg` sobrepõe o comportamento inline.

2) **Sem execução PHP (servir como estático):** baixo risco direto — o browser recebe `Content-Type: image/png` e tenta renderizar como imagem, resultando em imagem corrompida mas sem execução de código. **Com execução PHP (servidor interpretando o arquivo):** risco crítico de **Remote Code Execution (RCE)**. O arquivo PHP com extensão `.png` seria executado pelo servidor PHP como código, permitindo ao atacante rodar qualquer comando no servidor (ler arquivos, deletar dados, criar backdoors). A defesa é em camadas: (a) verificar magic bytes do arquivo (PNG começa com `\x89PNG`, não com `<?php`); (b) reprocessar imagens com Pillow/ImageMagick (reencoding elimina código embutido); (c) servir uploads de um bucket/domínio separado que nunca executa código; (d) renomear arquivos ao salvar (remove extensão .php original).

3) O Content-Type correto para SOAP é **`application/soap+xml`** (SOAP 1.2) ou **`text/xml`** (SOAP 1.1, legado). Muitos serviços SOAP legados aceitam apenas `text/xml` — o padrão SOAP 1.1 (RFC 2026) usa `text/xml`. SOAP 1.2 modernizou para `application/soap+xml`. **Como verificar:** consultar o WSDL (Web Services Description Language) do parceiro para identificar a versão SOAP usada, ou verificar a documentação do serviço. Também é possível tentar: `Content-Type: text/xml; charset=utf-8` para SOAP 1.1 e `Content-Type: application/soap+xml; charset=utf-8` para SOAP 1.2. O SOAPAction header também pode ser necessário em SOAP 1.1: `SOAPAction: "https://parceiro.com/acao"`.
