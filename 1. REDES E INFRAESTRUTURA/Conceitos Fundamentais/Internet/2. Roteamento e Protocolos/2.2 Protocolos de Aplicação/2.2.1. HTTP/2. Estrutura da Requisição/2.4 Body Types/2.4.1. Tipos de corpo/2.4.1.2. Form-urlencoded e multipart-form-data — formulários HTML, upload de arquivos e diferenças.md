### Form-urlencoded e multipart/form-data — formulários HTML, upload de arquivos e diferenças

`application/x-www-form-urlencoded` e `multipart/form-data` são os dois formatos nativos de submissão de formulários HTML — existem desde os primórdios da web. Enquanto JSON domina as APIs modernas, esses formatos ainda são essenciais: formulários HTML usam `form-urlencoded` por padrão, e qualquer upload de arquivo exige `multipart/form-data`. Entender a estrutura interna de cada um explica limitações, comportamentos e quando escolher um sobre o outro.

---

## application/x-www-form-urlencoded

O formato mais antigo de envio de dados de formulários. Os pares chave=valor são encodados exatamente como query parameters, mas no body da requisição em vez da URL.

### Estrutura

```
Content-Type: application/x-www-form-urlencoded
Body:

nome=Jo%C3%A3o+Silva&email=joao%40empresa.com&idade=30&ativo=true
│                    │                        │         │
└─ nome=João Silva   └─ email=joao@empresa.com└─ inteiro└─ boolean (como string)

Regras:
  → Pares: chave=valor
  → Separados por: &
  → Encoding: mesmo do query string (percent-encoding)
  → Espaços: + ou %20
  → Caracteres especiais: percent-encoded
  → Sem suporte a arquivos binários
  → Sem suporte a campos aninhados nativamente
```

### Como um formulário HTML gera form-urlencoded

```html
<!-- HTML form — action POST sem enctype = form-urlencoded por padrão -->
<form method="POST" action="/login">
  <input type="text" name="email" value="joao@empresa.com">
  <input type="password" name="senha" value="minha_senha">
  <input type="checkbox" name="lembrar" value="sim" checked>
  <button type="submit">Entrar</button>
</form>

<!-- Requisição gerada pelo browser: -->
POST /login HTTP/1.1
Content-Type: application/x-www-form-urlencoded
Content-Length: 54

email=joao%40empresa.com&senha=minha_senha&lembrar=sim
```

### Enviando form-urlencoded programaticamente

```python
# Python — requests
import requests

response = requests.post(
    "https://api.exemplo.com/login",
    data={  # usar 'data=' para form-urlencoded, não 'json='
        "email": "joao@empresa.com",
        "senha": "minha_senha",
        "lembrar": "sim"
    }
    # requests define automaticamente:
    # Content-Type: application/x-www-form-urlencoded
)
```

```javascript
// JavaScript — URLSearchParams
const params = new URLSearchParams({
  email: 'joao@empresa.com',
  senha: 'minha_senha',
  lembrar: 'sim'
});

const response = await fetch('https://api.exemplo.com/login', {
  method: 'POST',
  headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
  body: params.toString()
  // → "email=joao%40empresa.com&senha=minha_senha&lembrar=sim"
});
```

### Recebendo form-urlencoded no servidor

```python
# FastAPI
from fastapi import Form

@app.post("/login")
async def login(
    email: str = Form(...),
    senha: str = Form(...),
    lembrar: str = Form(default="nao")
):
    # FastAPI parseia automaticamente o body form-urlencoded
    return {"email": email, "lembrar": lembrar}
```

```javascript
// Express
app.use(express.urlencoded({ extended: true }));

app.post('/login', (req, res) => {
  const { email, senha, lembrar } = req.body;
  // extended: true → suporte a arrays e objetos aninhados via qs library
});
```

### Limitações do form-urlencoded

```
✗ Não suporta arquivos binários
  → dados binários precisam de base64, o que aumenta o tamanho em ~33%
  → Para arquivos: usar multipart/form-data

✗ Não suporta estruturas aninhadas nativamente:
  Workaround PHP/jQuery: campo[subchave]=valor
  → Não é padrão HTTP — cada framework implementa diferente

✗ Ineficiente para dados grandes:
  Encoding com % aumenta tamanho (cada byte especial = 3 chars)
  → Para grandes volumes de texto: considerar JSON ou multipart

✓ Simples e universal:
  Todos os browsers, todos os servidores, sem config adicional
  
✓ Ideal para:
  Formulários de login simples
  Dados de formulário sem arquivos
  Webhooks de provedores legados (Stripe, Twilio usam form-urlencoded)
```

## multipart/form-data

`multipart/form-data` permite enviar múltiplos "partes" em uma única requisição — cada parte pode ter seu próprio Content-Type, tornando possível enviar texto e arquivos binários juntos.

### Estrutura interna — o boundary

```
Content-Type: multipart/form-data; boundary=----WebKitFormBoundary7MA4YWxkTrZu0gW

Body (texto puro representando o que é enviado):

------WebKitFormBoundary7MA4YWxkTrZu0gW
Content-Disposition: form-data; name="nome"

João Silva
------WebKitFormBoundary7MA4YWxkTrZu0gW
Content-Disposition: form-data; name="email"

joao@empresa.com
------WebKitFormBoundary7MA4YWxkTrZu0gW
Content-Disposition: form-data; name="foto"; filename="avatar.jpg"
Content-Type: image/jpeg

[bytes binários da imagem JPEG aqui]
------WebKitFormBoundary7MA4YWxkTrZu0gW--
                                        ↑
                                        Dois traços finais indicam o fim
```

### O boundary

```
O boundary é uma string delimitadora que separa as partes:
  → Gerado aleatoriamente pelo browser/client para cada requisição
  → Deve ser uma string que NÃO aparece no conteúdo enviado
  → O servidor usa o boundary para separar as partes
  → Definido no Content-Type: multipart/form-data; boundary=<string>

Por que aleatório?
  Se o boundary fosse fixo ("---separator") e um arquivo contivesse
  essa string, o parser quebraria o arquivo no meio
  → Geradores escolhem strings longas e aleatórias para evitar colisões
```

### Como um formulário HTML gera multipart

```html
<!-- enctype="multipart/form-data" é obrigatório para upload de arquivos -->
<form method="POST" action="/perfil" enctype="multipart/form-data">
  <input type="text" name="nome" value="João Silva">
  <input type="email" name="email" value="joao@empresa.com">
  <input type="file" name="foto" accept="image/*">
  <button type="submit">Salvar</button>
</form>
```

### Enviando multipart programaticamente

```python
# Python — requests com arquivo
import requests

# Upload de arquivo de disco
with open("avatar.jpg", "rb") as foto:
    response = requests.post(
        "https://api.exemplo.com/perfil",
        files={
            "foto": ("avatar.jpg", foto, "image/jpeg")
            #        ↑ filename   ↑ file obj  ↑ content-type
        },
        data={
            "nome": "João Silva",
            "email": "joao@empresa.com"
        }
        # requests define automaticamente boundary e Content-Type: multipart/form-data
    )

# Upload de bytes em memória (sem arquivo em disco)
import io
from PIL import Image

# Processar imagem em memória e enviar
img = Image.open("original.jpg")
img_thumb = img.resize((200, 200))
buffer = io.BytesIO()
img_thumb.save(buffer, format="JPEG")
buffer.seek(0)

response = requests.post(
    "https://api.exemplo.com/imagens",
    files={"imagem": ("thumbnail.jpg", buffer, "image/jpeg")},
    data={"descricao": "Thumbnail do produto"}
)
```

```javascript
// JavaScript — FormData API
const formData = new FormData();
formData.append('nome', 'João Silva');
formData.append('email', 'joao@empresa.com');

// Arquivo do input file do DOM
const fileInput = document.getElementById('foto');
formData.append('foto', fileInput.files[0]);

// Arquivo criado em memória (Blob)
const conteudo = new Blob(['Hello World'], { type: 'text/plain' });
formData.append('documento', conteudo, 'arquivo.txt');

const response = await fetch('https://api.exemplo.com/perfil', {
  method: 'POST',
  body: formData
  // NÃO definir Content-Type manualmente — o browser define com o boundary correto!
  // Se você define 'Content-Type: multipart/form-data', o boundary não é incluído
  // → o servidor não consegue parsear → erro!
});
```

### Recebendo multipart no servidor

```python
# FastAPI — upload de arquivo
from fastapi import File, UploadFile, Form
from typing import Optional

@app.post("/perfil")
async def atualizar_perfil(
    nome: str = Form(...),
    email: str = Form(...),
    foto: Optional[UploadFile] = File(None)
):
    if foto:
        # Verificar tipo do arquivo
        if not foto.content_type.startswith("image/"):
            raise HTTPException(400, "Apenas imagens são aceitas")
        
        # Verificar tamanho (em memória)
        conteudo = await foto.read()
        if len(conteudo) > 5 * 1024 * 1024:  # 5 MB
            raise HTTPException(400, "Imagem deve ter menos de 5 MB")
        
        # Salvar no S3 ou disco
        caminho = f"uploads/{foto.filename}"
        with open(caminho, "wb") as f:
            f.write(conteudo)
    
    return {"nome": nome, "email": email, "foto_salva": foto.filename if foto else None}
```

```python
# FastAPI — múltiplos arquivos
from typing import List

@app.post("/galeria")
async def upload_galeria(
    descricao: str = Form(...),
    imagens: List[UploadFile] = File(...)
):
    urls = []
    for imagem in imagens:
        conteudo = await imagem.read()
        url = s3.upload(conteudo, imagem.filename, imagem.content_type)
        urls.append(url)

```

```javascript
// Express com multer
const multer = require('multer');
const upload = multer({
  storage: multer.memoryStorage(),  // ou multer.diskStorage()
  limits: { fileSize: 5 * 1024 * 1024 },  // 5 MB
  fileFilter: (req, file, cb) => {
    if (file.mimetype.startsWith('image/')) cb(null, true);
    else cb(new Error('Apenas imagens'), false);
  }
});

// Único arquivo
app.post('/perfil', upload.single('foto'), (req, res) => {
  const { nome, email } = req.body;
  const foto = req.file;  // { fieldname, originalname, buffer, mimetype, size }
  res.json({ nome, foto: foto?.originalname });
});

// Múltiplos arquivos
app.post('/galeria', upload.array('imagens', 10), (req, res) => {
  const arquivos = req.files;  // Array de arquivos
  res.json({ count: arquivos.length });
});
```

## Enviando JSON junto com arquivo — o dilema

Uma limitação comum: precisar enviar dados estruturados (JSON) junto com um arquivo. As opções:

### Opção 1 — Partes separadas no multipart

```python
# Enviar JSON como uma parte e arquivo como outra
import requests
import json

dados = {"nome": "Produto A", "preco": 99.90, "categorias": ["A", "B"]}

response = requests.post(
    "https://api.exemplo.com/produtos",
    files={
        "dados": (None, json.dumps(dados), "application/json"),
        "imagem": ("produto.jpg", open("produto.jpg", "rb"), "image/jpeg")
    }
)
```

```
Body gerado:
  --boundary
  Content-Disposition: form-data; name="dados"
  Content-Type: application/json
  
  {"nome": "Produto A", "preco": 99.90, "categorias": ["A", "B"]}
  --boundary
  Content-Disposition: form-data; name="imagem"; filename="produto.jpg"
  Content-Type: image/jpeg
  
  [bytes da imagem]
  --boundary--
```

### Opção 2 — JSON nos campos de formulário + arquivo no file field

```python
# Cada campo JSON como campo separado (perde tipagem de array/objeto)
response = requests.post(
    "https://api.exemplo.com/produtos",
    data={
        "nome": "Produto A",
        "preco": "99.90",
        "categorias": ["A", "B"]  # array → ?categorias=A&categorias=B
    },
    files={"imagem": open("produto.jpg", "rb")}
)
```

### Opção 3 — URL para upload separado (recomendada para arquivos grandes)

```
1. POST /produtos + JSON body → cria o produto, retorna product_id
2. POST /produtos/{id}/imagens + multipart → faz upload da imagem
   OU
   GET /upload-url → recebe pre-signed URL do S3
   PUT <presigned_url> + arquivo → upload direto para S3
```

## Comparativo form-urlencoded vs multipart vs JSON

```
┌────────────────────────┬─────────────────┬─────────────────┬──────────────────┐
│ Característica         │ form-urlencoded │ multipart       │ JSON             │
├────────────────────────┼─────────────────┼─────────────────┼──────────────────┤
│ Arquivo binário        │ Não             │ Sim             │ Não (base64 ok)  │
│ Múltiplos arquivos     │ Não             │ Sim             │ Não              │
│ Estrutura aninhada     │ Limitada        │ Limitada        │ Nativa           │
│ Arrays                 │ Com workarounds │ Com workarounds │ Nativo           │
│ Suporte nativo HTML    │ Sim (padrão)    │ Sim (com enctype)│ Não (JS req.)  │
│ Legibilidade           │ Média           │ Baixa           │ Alta             │
│ Tamanho (texto puro)   │ Compacto        │ Maior (headers) │ Similar          │
│ Tamanho (com arquivo)  │ N/A             │ Eficiente       │ +33% (base64)    │
│ Parsing complexidade   │ Simples         │ Moderada        │ Simples          │
│ Quando usar            │ Forms simples   │ Uploads         │ APIs REST        │
└────────────────────────┴─────────────────┴─────────────────┴──────────────────┘
```

## Erros comuns e armadilhas

**Definir `Content-Type: multipart/form-data` manualmente em JavaScript:** ao usar `FormData`, o browser precisa gerar o boundary e incluí-lo no Content-Type. Se você define o Content-Type manualmente, o boundary é omitido → o servidor não consegue parsear o body.

**Não validar o tipo e tamanho do arquivo no servidor:** confiar apenas na extensão do arquivo nome (`.jpg`) é insuficiente — verificar o MIME type real e o tamanho antes de processar ou salvar.

**Usar form-urlencoded para dados com estruturas complexas:** `categorias[0]=A&categorias[1]=B` funciona em alguns frameworks mas é frágil e inconsistente. Para dados estruturados com arrays e objetos: usar JSON.

**Não usar `enctype="multipart/form-data"` no form HTML:** sem esse atributo, o browser usa form-urlencoded mesmo com `<input type="file">` — o arquivo é enviado como string (nome do arquivo), não como bytes binários.

## 🧩 Quiz de Fixação

1. Um formulário HTML tem `method="POST"` e `enctype="multipart/form-data"`, com campos: `nome` (text), `email` (text) e `documento` (file). O usuário preenche tudo e clica em Enviar. Descreva a estrutura exata do body HTTP gerado.

2. Um desenvolvedor tenta fazer upload de arquivo em JavaScript com:
   ```javascript
   const formData = new FormData();
   formData.append('arquivo', file);
   fetch('/upload', {
     method: 'POST',
     headers: { 'Content-Type': 'multipart/form-data' },
     body: formData
   });
   ```
   O servidor retorna erro 400. O que está errado?

3. Uma API precisa receber: (a) metadados JSON complexos com arrays aninhados, (b) uma imagem JPEG. Qual é a abordagem mais adequada considerando legibilidade do código cliente e simplicidade do servidor?

**Respostas:**

1) O body HTTP gerado pelo browser seria:
```
POST /endpoint HTTP/1.1
Content-Type: multipart/form-data; boundary=----WebKitFormBoundaryXYZ123

------WebKitFormBoundaryXYZ123
Content-Disposition: form-data; name="nome"

[valor do campo nome]
------WebKitFormBoundaryXYZ123
Content-Disposition: form-data; name="email"

[valor do campo email]
------WebKitFormBoundaryXYZ123
Content-Disposition: form-data; name="documento"; filename="arquivo.pdf"
Content-Type: application/pdf

[bytes binários do arquivo PDF]
------WebKitFormBoundaryXYZ123--
```
Cada campo é uma "parte" separada pelo boundary. O campo de arquivo inclui `filename` no Content-Disposition e seu `Content-Type` real. O boundary final tem dois traços extras (`--`) para indicar o fim do multipart.

2) O problema é que o desenvolvedor definiu `Content-Type: multipart/form-data` manualmente, **sem o boundary**. O header correto deveria ser `Content-Type: multipart/form-data; boundary=----SomeBoundaryString`, mas o boundary é gerado pelo browser/FormData automaticamente. Ao sobrescrever o Content-Type manualmente, o boundary é omitido, e o servidor recebe `Content-Type: multipart/form-data` sem saber como separar as partes → erro de parsing → 400. **Correção:** remover completamente a linha `headers: { 'Content-Type': 'multipart/form-data' }` — ao usar `FormData` como body, o browser define o Content-Type correto com boundary automaticamente.

3) A abordagem mais adequada é **multipart com duas partes**: uma parte JSON (com `Content-Type: application/json`) para os metadados e uma parte imagem (com `Content-Type: image/jpeg`) para o arquivo. No servidor, a parte JSON é parseada como objeto completo com arrays aninhados, e a parte imagem é lida como bytes binários — sem perda de estrutura nem overhead de base64. Alternativamente (especialmente para arquivos grandes), a **Opção 3 de dois requests** é mais robusta: primeiro `POST /endpoint` com apenas o JSON para criar o recurso e obter o ID; depois `POST /endpoint/{id}/imagem` ou uma pre-signed URL do S3 para o upload do arquivo. Essa separação permite: retentativas independentes (se o JSON criou mas o upload falhou, só refazer o upload), upload direto para S3 sem passar pelo backend (mais eficiente), e progress tracking mais granular.
