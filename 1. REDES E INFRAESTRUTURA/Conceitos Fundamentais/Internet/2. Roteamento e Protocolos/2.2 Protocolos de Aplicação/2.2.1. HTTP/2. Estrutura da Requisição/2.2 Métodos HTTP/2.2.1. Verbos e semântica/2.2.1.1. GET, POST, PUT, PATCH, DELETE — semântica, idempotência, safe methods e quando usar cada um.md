### GET, POST, PUT, PATCH, DELETE — semântica, idempotência e quando usar

Os métodos HTTP (verbos) definem a **intenção** da requisição — o que o cliente quer fazer com o recurso. Escolher o método errado não apenas viola a semântica REST, mas quebra caching, idempotência e o comportamento esperado por middlewares, proxies e frameworks. Cada método tem propriedades técnicas precisas que determinam como pode ser usado com segurança.

---

## Duas propriedades fundamentais

Antes dos métodos, dois conceitos definem seu comportamento:

### Safe (Seguro)

Um método é **safe** se não modifica o estado do servidor. O cliente pode chamar quantas vezes quiser sem efeitos colaterais.

```
Safe methods: GET, HEAD, OPTIONS
Não-safe:     POST, PUT, PATCH, DELETE

Implicação:
  → Browsers podem fazer prefetch de links (GET) sem perguntar ao usuário
  → Crawlers podem indexar URLs GET sem risco de modificar dados
  → Ao clicar "voltar" no browser: GET é re-executado, POST mostra aviso
    "Tem certeza que deseja reenviar o formulário?"
```

### Idempotente

Uma operação é **idempotente** se executá-la N vezes produz o mesmo resultado que executar 1 vez.

```
Idempotente:     GET, HEAD, OPTIONS, PUT, DELETE
Não-idempotente: POST, PATCH (em geral)

Analogia:
  Idempotente: ligar o interruptor quando a luz JÁ está ligada → sem efeito
  Não-idempotente: adicionar R$10 à conta → cada chamada modifica o estado

Implicação prática:
  Clientes podem RETRY automaticamente métodos idempotentes após falha de rede
  Retry de POST pode criar recursos duplicados!
  
  Timeout em DELETE /usuarios/123:
  → Pode ter sido executado ou não
  → Retry é seguro (se executou: idempotente; se não: executa agora)
  
  Timeout em POST /pedidos:
  → Pode ter sido executado ou não
  → Retry PODE criar pedido duplicado!
  → Solução: Idempotency-Key header (ver abaixo)
```

## GET — buscar um recurso

```
Propósito:   Recuperar dados sem modificar nada
Safe:        Sim
Idempotente: Sim
Body:        Não deve ter (tecnicamente permitido, mas sem semântica definida)
Cacheable:   Sim (é a base do caching HTTP)
```

### Usos corretos

```
GET /produtos                        → listar todos os produtos
GET /produtos/123                    → buscar produto com ID 123
GET /usuarios/456/pedidos            → listar pedidos do usuário 456
GET /relatorios/vendas?mes=2024-01   → relatório com query params
GET /busca?q=notebook+gamer          → busca
```

### Usos incorretos

```
❌ GET /deletar-usuario/123          → GET não modifica estado
❌ GET /login (com credenciais na URL) → dados sensíveis em query params
❌ GET /processar-pagamento          → GET não deve ter efeitos colaterais

Por que não usar GET com body para filtros complexos?
  Tecnicamente a RFC permite body no GET, mas:
  → Muitos proxies/firewalls descartam o body de requisições GET
  → Frameworks frequentemente ignoram o body em GET
  → Se necessário: usar POST com body (documentado como "busca complexa")
```

### Caching com GET

```
GET é cacheável por padrão:
  GET /produtos/123 → 200 OK, Cache-Control: max-age=3600
  
  Próxima requisição em 30 min:
  → Browser/proxy serve do cache sem ir ao servidor
  → Servidor nunca recebe a segunda requisição

Invalidade o cache:
  PUT/PATCH/DELETE no mesmo recurso invalida o cache
  (proxies e CDNs respeitam isso automaticamente)
```

## POST — criar um recurso ou processar dados

```
Propósito:   Criar novo recurso ou submeter dados para processamento
Safe:        Não
Idempotente: NÃO (cada POST pode criar algo novo)
Body:        Sim (o recurso ou dados a processar)
Cacheable:   Raramente (com headers específicos)
```

### Usos corretos

```
POST /produtos                    → criar novo produto (retorna 201 Created)
POST /usuarios                    → criar nova conta
POST /pedidos                     → submeter novo pedido
POST /login                       → autenticar (retorna token)
POST /emails/enviar               → enviar e-mail (ação sem recurso)
POST /pagamentos/processar        → processar pagamento (operação)
POST /busca/avancada              → busca com filtros complexos (body JSON)
POST /relatorios/gerar            → iniciar geração assíncrona
```

### POST não é idempotente — o problema de retry

```
Cenário:
  POST /pedidos  → timeout (não sabe se chegou ao servidor)
  POST /pedidos  → retry → cria SEGUNDO pedido!

Solução: Idempotency-Key
  POST /pedidos
  Idempotency-Key: a1b2c3d4-uuid-gerado-pelo-cliente

  Servidor:
  1. Verifica se já processou essa chave
  2. Se sim: retorna a resposta original (sem reprocessar)
  3. Se não: processa e armazena a chave + resposta

  Retry com mesma chave:
  POST /pedidos + Idempotency-Key: a1b2c3d4...
  → Servidor retorna resposta original (sem criar duplicata)

Usado por: Stripe, Adyen, PayPal, AWS
```

### POST vs GET para ações

```
Ações que modificam estado SEMPRE devem ser POST (ou PUT/PATCH/DELETE):
  ✓ POST /usuarios/123/bloquear
  ✓ POST /pedidos/456/cancelar
  ✓ POST /arquivos/789/mover

  ❌ GET /usuarios/123/bloquear
     Crawler/prefetch pode bloquear usuários acidentalmente!
```

## PUT — substituir um recurso completamente

```
Propósito:   Substituir TOTALMENTE um recurso existente (ou criar se não existir)
Safe:        Não
Idempotente: SIM (PUT com os mesmos dados sempre resulta no mesmo estado)
Body:        Sim (representação COMPLETA do recurso)
Cacheable:   Não
```

### Usos corretos

```
PUT /produtos/123
Body: {"id": 123, "nome": "Notebook", "preco": 2999, "ativo": true, "categoria": "informatica"}
→ Substitui o produto 123 inteiramente com esses dados
→ Campos não enviados no body podem ser removidos/zerados!

PUT /configuracoes/perfil
Body: {"tema": "dark", "idioma": "pt-BR", "notificacoes": true, ...}
→ Substitui toda a configuração do perfil
```

### PUT é COMPLETO — principal diferença do PATCH

```
Produto 123 no banco:
  {id: 123, nome: "Notebook Dell", preco: 2999.90, ativo: true, categoria: "informatica"}

PUT /produtos/123 com body:
  {"id": 123, "nome": "Notebook Dell", "preco": 3499.90}
  (sem ativo e sem categoria)

Resultado após PUT:
  {id: 123, nome: "Notebook Dell", preco: 3499.90, ativo: null, categoria: null}
  ↑ ativo e categoria REMOVIDOS porque não foram enviados!

Para atualizar apenas o preço: use PATCH, não PUT
```

### PUT pode criar (upsert)

```
Se o recurso não existe:
  PUT /configuracoes/usuario/789
  Body: {...}
  
  Comportamento esperado:
  → Recurso existe: substitui → 200 OK
  → Recurso não existe: cria → 201 Created
  
  O cliente controla o ID (diferente do POST onde o servidor gera o ID)
  PUT /artigos/slug-do-artigo → cliente define o slug como identificador
```

## PATCH — atualizar parcialmente um recurso

```
Propósito:   Atualizar PARCIALMENTE um recurso (apenas os campos enviados)
Safe:        Não
Idempotente: Depende da implementação (pode ou não ser)
Body:        Sim (apenas os campos a modificar)
Cacheable:   Não
```

### Usos corretos

```
PATCH /produtos/123
Body: {"preco": 3499.90}
→ Atualiza APENAS o preço. Nome, ativo, categoria permanecem intactos.

PATCH /usuarios/456
Body: {"email": "novo@email.com"}
→ Atualiza apenas o email.

PATCH /configuracoes/perfil
Body: {"tema": "light"}
→ Atualiza apenas o tema. Outros settings permanecem.
```

### PATCH não é sempre idempotente

```
PATCH idempotente (substitui valor):
  PATCH /produto/123 + {"preco": 3499.90}
  → Executar N vezes: preço sempre fica 3499.90 ✓ idempotente

PATCH não-idempotente (operação incremental):
  PATCH /produto/123 + {"incrementar_estoque": 10}
  → Primeira vez: estoque += 10
  → Segunda vez: estoque += 10 novamente ✗ não-idempotente!
  
  Para operações incrementais sem idempotência: documentar claramente
  e usar Idempotency-Key se retry for necessário
```

### JSON Patch — padrão formal para PATCH

```
RFC 6902 define JSON Patch — operações declarativas sobre documentos JSON:

PATCH /usuarios/123
Content-Type: application/json-patch+json

[
  {"op": "replace", "path": "/email", "value": "novo@email.com"},
  {"op": "add",     "path": "/telefone", "value": "+55 11 9999-9999"},
  {"op": "remove",  "path": "/foto_antiga"},
  {"op": "move",    "from": "/nome_temp", "path": "/nome"},
  {"op": "test",    "path": "/versao", "value": 5}  → falha se versão != 5
]

Operações: add, remove, replace, move, copy, test
→ Mais expressivo que PATCH simples mas raramente usado na prática
→ Útil quando o documento tem estrutura profunda e complex
```

## DELETE — remover um recurso

```
Propósito:   Remover um recurso
Safe:        Não
Idempotente: SIM (deletar o que já foi deletado = mesmo estado: ausente)
Body:        Geralmente não tem, mas é permitido
Cacheable:   Não
```

### Usos corretos

```
DELETE /produtos/123          → remove produto 123
DELETE /usuarios/456/sessoes  → encerra todas as sessões do usuário
DELETE /pedidos/789           → cancela/remove pedido
DELETE /arquivos/abc.pdf      → remove arquivo
```

### DELETE é idempotente — mas o status code pode variar

```
Primeira chamada:
  DELETE /produtos/123 → 204 No Content (deletado com sucesso)

Segunda chamada (mesmo recurso já deletado):
  DELETE /produtos/123 → 404 Not Found (não existe mais)
  OU
  DELETE /produtos/123 → 204 No Content (idempotente — resultado final é o mesmo)

A spec HTTP diz que ambos 204 e 404 são corretos na segunda chamada.
O importante: o ESTADO final é o mesmo (recurso ausente) = idempotente.
```

### Soft delete vs Hard delete

```
Hard delete (remoção física):
  DELETE /usuarios/123
  → Remove do banco permanentemente
  → 204 No Content

Soft delete (remoção lógica):
  DELETE /usuarios/123
  → Define ativo=false ou deleted_at=now() no banco
  → Dados preservados para auditoria, recuperação
  → 204 No Content (mesma interface, comportamento diferente internamente)

  Para reativar:
  PATCH /usuarios/123 + {"ativo": true}  ou  POST /usuarios/123/restaurar
```

## Mapeamento CRUD → HTTP

```
Operação    HTTP Method    URL                      Status esperado
──────────────────────────────────────────────────────────────────
Create      POST           /produtos                201 Created
Read (all)  GET            /produtos                200 OK
Read (one)  GET            /produtos/123            200 OK | 404 Not Found
Update full PUT            /produtos/123            200 OK | 204 No Content
Update part PATCH          /produtos/123            200 OK | 204 No Content
Delete      DELETE         /produtos/123            204 No Content | 404

Alternativas para operações especiais:
  Busca complexa:     POST /produtos/busca (body com filtros)
  Ação sobre recurso: POST /pedidos/123/cancelar
  Estado booleano:    PATCH /usuarios/123 + {"ativo": false}
                      OU: DELETE /usuarios/123/sessao-ativa
```

## Erros comuns e armadilhas

**Usar POST para tudo:** o erro mais comum em APIs. `POST /listar-usuarios`, `POST /buscar-produto`. Quebra caching, bookmarking e semântica REST.

**Usar GET para modificações:** `GET /admin/deletar-usuario?id=123` — qualquer crawler, prefetch ou monitoramento pode deletar usuários involuntariamente.

**Confundir PUT com PATCH:** enviar apenas `{"preco": 3499}` via PUT remove todos os outros campos do recurso. Se a intenção é atualização parcial, use PATCH.

**Não implementar Idempotency-Key em POST críticos:** pagamentos, criação de pedidos, envio de e-mails — qualquer POST que não possa ser duplicado deve suportar Idempotency-Key.

## 🧩 Quiz de Fixação

1. Um time decide implementar `PUT /usuarios/123` que aceita apenas os campos modificados (comportamento parcial). Por que isso viola a semântica do PUT e qual problema prático pode causar para clientes que seguem a spec corretamente?

2. `DELETE /pedidos/456` é executado com sucesso (204). O cliente perde a conexão antes de receber a resposta e faz retry. O servidor retorna 404. Do ponto de vista da idempotência, o resultado final está correto. Qual é a melhor resposta que o servidor deveria retornar no retry para evitar confusão no cliente?

3. Uma API de pagamentos recebe `POST /cobrancas` que pode criar uma cobrança duplicada em caso de retry. O cliente implementa retry com backoff exponencial. Como o Idempotency-Key resolve esse problema, e onde o servidor deve armazenar o mapeamento de chaves para garantir que funcione corretamente?

**Respostas:**

1) **Violação:** PUT significa "substitua o recurso inteiramente com o que estou enviando". Um cliente que segue a spec vai enviar TODOS os campos do recurso (como faria em uma substituição completa). Se o servidor silenciosamente ignora campos ausentes (comportamento PATCH), o cliente pensa que atualizou completamente mas na verdade fez uma atualização parcial. **Problema prático:** um cliente que faz `GET /usuarios/123` → modifica 1 campo → `PUT /usuarios/123 [body completo]` espera sobrescrever o recurso. Se o servidor tratar como PATCH internamente, pode haver inconsistências quando múltiplos campos são críticos. A solução correta é implementar PUT com semântica correta (substituição total) e expor PATCH separadamente para atualizações parciais.

2) **Melhor resposta: 204 No Content** (não 404). Do ponto de vista da idempotência, o resultado final — o pedido não existe — é o mesmo independente de quantas vezes o DELETE foi chamado. Retornar 404 no retry faz o cliente pensar que houve um erro, quando na verdade a operação foi bem-sucedida (o recurso foi deletado na primeira chamada). 204 no retry comunica "a operação foi processada com sucesso e não há conteúdo para retornar" — o que é verdadeiro. Alguns times preferem 200 com `{"status": "deletado"}` para maior clareza, mas 204 é semanticamente correto e mais simples.

3) **Como funciona:** o cliente gera um UUID único antes de enviar a primeira requisição (`Idempotency-Key: uuid-v4-gerado-localmente`). O servidor, ao receber: (1) verifica se já existe uma entrada para essa chave no storage de idempotência; (2) se não existe: processa a cobrança, armazena `{chave: uuid, resposta: {status: 201, body: {...}}, expira_em: now()+24h}`; (3) se existe: retorna a resposta armazenada sem reprocessar. **Onde armazenar:** em um storage durável separado do banco principal — Redis com TTL (tipicamente 24h-7 dias) é a escolha comum. **Atenção:** não pode estar em memória local (perde em restart) nem apenas no banco de cobranças (operação não-atômica). O ideal é uma transação atômica: criar a cobrança E salvar a chave de idempotência juntos — se qualquer parte falhar, ambas rollbackam, garantindo que não existam chaves sem cobrança correspondente ou cobranças sem chave.
