### HEAD, OPTIONS, CONNECT e TRACE — métodos auxiliares, CORS preflight e casos de uso

Além dos cinco métodos principais (GET, POST, PUT, PATCH, DELETE), o HTTP define quatro métodos auxiliares que resolvem problemas específicos: verificar recursos sem baixá-los, descobrir capacidades do servidor, estabelecer túneis e diagnosticar roteamento. O mais relevante no desenvolvimento moderno é o **OPTIONS** — ele é a base do mecanismo CORS que todo desenvolvedor frontend inevitavelmente encontra.

---

## HEAD — GET sem body

```
Propósito:   Igual ao GET, mas o servidor retorna apenas os headers (sem body)
Safe:        Sim
Idempotente: Sim
Body:        Não (nem na requisição nem na resposta)
Cacheable:   Sim
```

O servidor processa a requisição exatamente como um GET mas omite o body da resposta. Os headers retornados devem ser idênticos ao que um GET retornaria.

### Casos de uso práticos

**1. Verificar se um recurso existe sem baixar o conteúdo:**
```bash
# Verificar se um arquivo existe no S3 sem baixá-lo (pode ter GBs)
curl -I https://bucket.s3.amazonaws.com/arquivo-grande.zip
# HTTP/2 200 OK
# Content-Length: 2147483648   ← 2 GB, mas não foi baixado
# ETag: "abc123def456"
# Last-Modified: Mon, 15 Jan 2024 10:00:00 GMT

curl -I https://bucket.s3.amazonaws.com/nao-existe.txt
# HTTP/2 404 Not Found
# (nenhum byte de body baixado)
```

**2. Verificar se o cache está atualizado:**
```bash
# Verificar ETag/Last-Modified sem baixar o recurso
curl -I https://cdn.exemplo.com/app.bundle.js
# ETag: "v2.1.0-hash"
# Last-Modified: Fri, 12 Jan 2024 08:00:00 GMT

# Se o ETag for diferente do que está em cache: baixar com GET
# Se for igual: usar o cache local
```

**3. Verificar tamanho antes de download:**
```python
import requests

def verificar_tamanho(url: str) -> int:
    response = requests.head(url)
    tamanho = int(response.headers.get('Content-Length', 0))
    print(f"Arquivo: {tamanho / 1024 / 1024:.1f} MB")
    return tamanho

# Decide se vai baixar baseado no tamanho
if verificar_tamanho("https://cdn.exemplo.com/video.mp4") < 100 * 1024 * 1024:
    requests.get("https://cdn.exemplo.com/video.mp4")
```

**4. Monitoramento de disponibilidade (health checks):**
```bash
# Health check sem tráfego de dados — mais eficiente que GET
# Usado por load balancers, monitoramento (Pingdom, Datadog)
curl -o /dev/null -s -w "%{http_code}" -X HEAD https://api.meusite.com/health
# 200 (sem baixar body)
```

### Quando o HEAD falha

```
Armadilha: alguns servidores mal configurados:
  HEAD /recurso → 405 Method Not Allowed
  
  Causa: desenvolvedor não registrou HEAD explicitamente
  (frameworks geralmente registram HEAD automaticamente para rotas GET)
  
  Verificar: se GET funciona mas HEAD não, é bug de configuração
```

## OPTIONS — descobrir capacidades e CORS preflight

```
Propósito:   Descobrir quais métodos e headers o servidor aceita para um recurso
Safe:        Sim
Idempotente: Sim
Body:        Pode ter (raramente usado na prática)
Cacheable:   Sim (com headers adequados)
```

### Caso 1 — Descoberta de capacidades

```bash
# O que este endpoint aceita?
curl -X OPTIONS https://api.exemplo.com/produtos/123 -v

# Resposta:
# HTTP/2 204 No Content
# Allow: GET, POST, PUT, PATCH, DELETE, HEAD, OPTIONS
# Accept-Patch: application/json-patch+json
```

### Caso 2 — CORS Preflight (o mais importante)

CORS (Cross-Origin Resource Sharing) é o mecanismo que permite (ou bloqueia) que JavaScript em `https://meusite.com` faça requisições para `https://api.outraempresa.com`. O browser envia automaticamente uma requisição OPTIONS antes de certas requisições cross-origin — isso é o **preflight**.

```
O problema que CORS resolve:

Browser em https://meusite.com
JavaScript tenta: fetch("https://api.banco.com/transferir", {method: "POST", body: ...})

SEM CORS: o browser bloquearia para proteger o usuário
  → Um site malicioso não pode fazer transferências bancárias em nome do usuário
  → A política Same-Origin impede requisições cross-origin por padrão

COM CORS (se api.banco.com autorizar meusite.com):
  → O servidor declara explicitamente quem pode acessá-lo
  → Browser permite a requisição
```

### Quando o browser envia preflight OPTIONS

```
O browser envia OPTIONS automaticamente quando a requisição cross-origin:
  → Usa métodos diferentes de: GET, POST, HEAD
  → Usa headers além de: Accept, Accept-Language, Content-Language, Content-Type
  → Tem Content-Type diferente de:
      application/x-www-form-urlencoded
      multipart/form-data
      text/plain

Requisições "simples" (sem preflight):
  fetch("https://api.com/dados")  → GET com headers básicos → sem preflight

Requisições "não-simples" (COM preflight):
  fetch("https://api.com/dados", {
    method: "DELETE",                           → método não-simples
    headers: {"Authorization": "Bearer eyJ..."} → header não-simples
  })
```

### Fluxo completo de CORS preflight

```
1. JavaScript em https://app.meusite.com faz:
   DELETE /usuarios/123 com Authorization header

2. Browser intercepta e envia OPTIONS PRIMEIRO:
   OPTIONS /usuarios/123 HTTP/1.1
   Host: api.empresa.com
   Origin: https://app.meusite.com
   Access-Control-Request-Method: DELETE
   Access-Control-Request-Headers: Authorization

3. Servidor responde ao OPTIONS:
   HTTP/1.1 204 No Content
   Access-Control-Allow-Origin: https://app.meusite.com
   Access-Control-Allow-Methods: GET, POST, PUT, PATCH, DELETE
   Access-Control-Allow-Headers: Authorization, Content-Type
   Access-Control-Max-Age: 86400  ← cache o preflight por 24 horas
   Vary: Origin

4. Browser verifica a resposta:
   ✓ Origin permitida?  → sim (Allow-Origin)
   ✓ Método permitido?  → sim (DELETE está em Allow-Methods)
   ✓ Header permitido?  → sim (Authorization está em Allow-Headers)
   → Envia a requisição DELETE real

5. DELETE /usuarios/123 HTTP/1.1
   Host: api.empresa.com
   Origin: https://app.meusite.com
   Authorization: Bearer eyJ...

6. Servidor responde ao DELETE com headers CORS também:
   HTTP/1.1 204 No Content
   Access-Control-Allow-Origin: https://app.meusite.com
```

### Headers CORS na resposta do OPTIONS

```
Access-Control-Allow-Origin:
  *                             → qualquer origem (sem credenciais)
  https://app.meusite.com       → apenas essa origem específica
  null                          → nunca usar em produção

Access-Control-Allow-Methods:
  GET, POST, PUT, PATCH, DELETE, OPTIONS

Access-Control-Allow-Headers:
  Authorization, Content-Type, X-Request-ID, X-Api-Key

Access-Control-Allow-Credentials:
  true  → permite enviar cookies e headers de autenticação
         (requer Allow-Origin específico — não pode ser *)

Access-Control-Max-Age:
  86400  → browser pode cachear o preflight por 86.400 segundos (1 dia)
           sem Max-Age: browser refaz preflight a cada requisição!

Access-Control-Expose-Headers:
  X-Total-Count, X-Rate-Limit-Remaining
  → headers que o JavaScript pode acessar (por padrão só headers "simples")
```

### Configurando CORS no servidor

```python
# FastAPI
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://app.meusite.com", "https://admin.meusite.com"],
    allow_credentials=True,
    allow_methods=["GET", "POST", "PUT", "PATCH", "DELETE"],
    allow_headers=["Authorization", "Content-Type", "X-Request-ID"],
    max_age=86400,
)
```

```javascript
// Express (Node.js)
const cors = require('cors');

app.use(cors({
  origin: ['https://app.meusite.com', 'https://admin.meusite.com'],
  credentials: true,
  methods: ['GET', 'POST', 'PUT', 'PATCH', 'DELETE'],
  allowedHeaders: ['Authorization', 'Content-Type', 'X-Request-ID'],
  maxAge: 86400
}));
```

```nginx
# Nginx — responder OPTIONS diretamente sem bater no backend
location /api/ {
    if ($request_method = OPTIONS) {
        add_header Access-Control-Allow-Origin $http_origin;
        add_header Access-Control-Allow-Methods "GET, POST, PUT, PATCH, DELETE, OPTIONS";
        add_header Access-Control-Allow-Headers "Authorization, Content-Type";
        add_header Access-Control-Max-Age 86400;
        add_header Content-Length 0;
        return 204;
    }
    
    add_header Access-Control-Allow-Origin $http_origin;
    proxy_pass http://backend;
}
```

## CONNECT — estabelecer túnel TCP

```
Propósito:   Estabelecer um túnel TCP através de um proxy HTTP
Safe:        Não
Idempotente: Não
Body:        Não
Cacheable:   Não
```

CONNECT é usado por proxies HTTP para estabelecer um túnel TCP bidirecional. É o mecanismo pelo qual seu browser acessa sites HTTPS através de um proxy corporativo.

```
Sem CONNECT (proxy não consegue ver HTTPS):
  Browser → Proxy → Servidor HTTPS
  Proxy tentaria descriptografar o HTTPS → erro de certificado

Com CONNECT (proxy cria túnel):
  1. Browser → Proxy: CONNECT api.banco.com:443 HTTP/1.1
  
  2. Proxy conecta ao servidor de destino:
     Proxy → api.banco.com:443 (TCP)
  
  3. Proxy responde ao browser:
     HTTP/1.1 200 Connection Established
  
  4. A partir daí, proxy apenas repassa bytes:
     Browser ←→ [bytes criptografados TLS] ←→ api.banco.com
     O proxy não consegue ver o conteúdo (TLS entre browser e servidor)

Uso prático:
  → Proxies corporativos que precisam inspecionar HTTPS:
    Instalam um certificado raiz na máquina do usuário
    O proxy faz "man in the middle" legítimo para inspecção de segurança
  
  → WebSockets através de proxies HTTP:
    WebSocket usa CONNECT para estabelecer o túnel persistente
```

```bash
# CONNECT via curl (raramente usado diretamente)
curl -x http://proxy:3128 https://api.banco.com/endpoint
# curl usa CONNECT automaticamente para HTTPS através de proxy
```

## TRACE — diagnóstico de roteamento

```
Propósito:   O servidor ecoa de volta a requisição recebida — diagnóstico de roteamento
Safe:        Sim
Idempotente: Sim
Body:        Não
Cacheable:   Não
```

TRACE faz o servidor devolver a requisição exatamente como a recebeu, incluindo qualquer modificação feita por proxies intermediários. Funciona como um `traceroute` em nível HTTP.

```
Browser → Proxy A → Proxy B → Servidor

TRACE /diagnostico HTTP/1.1
Host: api.exemplo.com
X-Custom-Header: teste

Servidor responde com o que recebeu (após proxies modificarem):
HTTP/1.1 200 OK
Content-Type: message/http

TRACE /diagnostico HTTP/1.1
Host: api.exemplo.com
X-Custom-Header: teste
Via: 1.1 proxy-a.empresa.com, 1.1 proxy-b.provider.com   ← adicionado pelos proxies
X-Forwarded-For: 203.0.113.10                              ← adicionado pelo proxy A
```

### Por que TRACE está desabilitado na maioria dos servidores

```
Vulnerabilidade XST (Cross-Site Tracing):
  1. Usuário visita site malicioso
  2. JavaScript faz TRACE para um servidor que tenha cookie do usuário
  3. Resposta do TRACE inclui os headers enviados, incluindo Cookie
  4. JavaScript lê os cookies mesmo que HttpOnly!
  
  HttpOnly era suposto impedir JavaScript de ler cookies diretamente
  TRACE tornava isso possível indiretamente

Mitigação: desabilitar TRACE no servidor (padrão em nginx, Apache modernos)
Hoje: browsers modernos também bloqueiam TRACE via JavaScript
      mas é boa prática manter desabilitado

# Nginx: negar TRACE
if ($request_method = TRACE) {
    return 405;
}

# Apache: desabilitar TRACE
TraceEnable off
```

## Erros comuns e armadilhas

**Não cachear respostas OPTIONS:** sem `Access-Control-Max-Age`, o browser faz um preflight OPTIONS antes de CADA requisição cross-origin. Para uma SPA com 50 chamadas de API por página, isso dobra o número de requisições. Sempre configurar `max-age=86400` (ou similar).

**Usar `Access-Control-Allow-Origin: *` com `credentials: true`:** essa combinação é inválida — o browser rejeita. Para enviar cookies/Authorization em requisições cross-origin, a origem deve ser específica (não `*`).

**Não implementar HEAD para rotas GET:** frameworks como Express registram HEAD automaticamente para rotas GET, mas servidores customizados frequentemente esquecem. Monitoramento e CDNs usam HEAD — um 405 aqui pode sinalizar "recurso indisponível" erroneamente.

## 🧩 Quiz de Fixação

1. Uma SPA em `https://app.meusite.com` faz 30 chamadas de API por segundo para `https://api.meusite.com`. O time detecta que metade das chamadas são OPTIONS que nunca chegam ao backend. Qual é a causa e como resolver com 1 linha de configuração?

2. Por que `Access-Control-Allow-Origin: *` funciona para uma API pública (leitura de dados meteorológicos), mas não pode ser usado quando a API precisa receber cookies de sessão do usuário?

3. Um monitor de disponibilidade faz `HEAD /health` a cada 30 segundos. O servidor retorna 405 Method Not Allowed. O monitor marca o serviço como "down". O servidor aceita GET normalmente. Qual é o bug e qual é a causa mais provável?

**Respostas:**

1) A causa é a ausência de `Access-Control-Max-Age` na resposta do OPTIONS — o browser está fazendo preflight antes de CADA requisição cross-origin. Com 30 chamadas/segundo, são 30 OPTIONS + 30 requisições reais = 60 requisições/segundo. **Solução:** adicionar `Access-Control-Max-Age: 86400` na resposta do OPTIONS (ou no middleware CORS). Com isso, o browser faz apenas 1 preflight por dia por rota, eliminando 15 OPTIONS/segundo na prática. Em FastAPI: `CORSMiddleware(..., max_age=86400)`. Em nginx: `add_header Access-Control-Max-Age 86400` no bloco que responde ao OPTIONS.

2) `Access-Control-Allow-Origin: *` indica "qualquer origem pode acessar". Para requisições sem credenciais (sem cookies, sem Authorization), isso é seguro — o servidor não tem como identificar o usuário de qualquer forma. Mas quando a API precisa receber credenciais (`credentials: true` no `fetch`), o browser exige que a resposta tenha `Access-Control-Allow-Credentials: true` E que `Access-Control-Allow-Origin` seja uma origem específica (não `*`). A razão de segurança: se `*` fosse permitido com credenciais, qualquer site malicioso em qualquer origem poderia fazer requisições autenticadas em nome do usuário (usando os cookies/tokens do usuário sem o usuário saber) — exatamente o ataque de CSRF que CORS foi projetado para prevenir.

3) **Bug:** o servidor não tem a rota HEAD registrada (ou está explicitamente bloqueando). **Causa mais provável:** o desenvolvedor usou um framework ou registrou apenas `GET /health` sem registrar `HEAD /health`, e o framework não adicionou HEAD automaticamente. Em algumas configurações de nginx ou frameworks web, HEAD não é adicionado automaticamente. **Correção:** (a) se usando nginx como proxy: adicionar `if ($request_method = HEAD) { return 200; }` ou configurar o backend para aceitar HEAD; (b) se usando um framework como Express: verificar que está usando `app.get('/health', ...)` — o Express registra HEAD automaticamente para rotas GET. Se o problema persistir, pode ser que um middleware esteja bloqueando explicitamente. O monitor não está errado — HEAD 405 é uma falha real de configuração, pois HEAD é um método HTTP padrão que qualquer endpoint GET deve suportar.
