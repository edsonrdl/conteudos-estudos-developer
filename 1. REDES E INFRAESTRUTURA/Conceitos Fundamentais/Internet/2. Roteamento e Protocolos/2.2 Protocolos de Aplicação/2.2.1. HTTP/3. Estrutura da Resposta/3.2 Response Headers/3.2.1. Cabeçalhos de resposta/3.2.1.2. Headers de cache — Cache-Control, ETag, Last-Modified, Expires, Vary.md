### Headers de cache da resposta — Cache-Control, ETag, Last-Modified, Expires e Vary

Os headers de cache da resposta são a forma como o servidor instrui clientes e proxies sobre como e por quanto tempo armazenar e reutilizar a resposta. Uma estratégia de cache bem configurada pode eliminar 80%+ das requisições ao servidor para ativos estáticos e reduzir significativamente a latência percebida. Este arquivo cobre o lado da **resposta** — o que o servidor envia para controlar o comportamento de cache.

## Cache-Control na resposta — instruindo clientes e CDNs

`Cache-Control` na resposta é o mecanismo principal para controlar o cache. O servidor declara explicitamente como sua resposta pode ser armazenada e por quanto tempo.

### Diretivas de expiração

```
max-age=<seconds>
  → Tempo em segundos que a resposta é "fresh" (válida sem revalidar)
  → Conta a partir do momento que o cliente recebeu a resposta
  
  Cache-Control: max-age=3600
  → Válido por 1 hora a partir do recebimento

s-maxage=<seconds>
  → Igual ao max-age, mas APENAS para caches compartilhados (CDNs, proxies)
  → Sobrescreve max-age para CDNs se presente
  
  Cache-Control: max-age=60, s-maxage=3600
  → Browser: 1 minuto
  → CDN: 1 hora
  
  Caso de uso: dados que mudam frequentemente para usuários individuais
               mas podem ser cacheados por mais tempo em CDN (dados públicos)
```

### Diretivas de armazenamento

```
public
  → Qualquer cache pode armazenar (browsers, CDNs, proxies)
  → Mesmo respostas com Authorization header podem ser cacheadas
  
  Cache-Control: public, max-age=86400
  → CDN pode cachear — ideal para assets estáticos públicos

private
  → Apenas caches do cliente final (browser) podem armazenar
  → CDNs e proxies compartilhados NÃO devem cachear
  
  Cache-Control: private, max-age=300
  → Dados personalizados por usuário: só o browser daquele usuário guarda

no-cache
  → PODE ser armazenado, mas SEMPRE revalidar antes de usar
  → "Guarda, mas sempre pergunta se ainda é válido"
  
  Cache-Control: no-cache
  → Cada requisição vai ao servidor para validar (via ETag/Last-Modified)
  → 304 Not Modified = usa o cache
  → 200 OK = cache foi invalidado, usa nova versão

no-store
  → NÃO armazenar em nenhum lugar — nem no browser, nem em CDN
  → Cada requisição faz uma busca completa ao servidor
  
  Cache-Control: no-store
  → Para dados ultra-sensíveis: extratos bancários, dados de sessão
  → "Nunca guarda nada"

must-revalidate
  → Após expirar (max-age esgotado), DEVE revalidar antes de usar
  → Sem isso: alguns caches "tolerantes" podem usar resposta expirada offline
  
  Cache-Control: max-age=3600, must-revalidate
  → Mais rigoroso que apenas max-age

proxy-revalidate
  → Igual ao must-revalidate, mas apenas para caches compartilhados (CDNs)
  → Browsers podem ser mais tolerantes; CDNs devem revalidar estritamente

immutable
  → O recurso NUNCA muda durante o max-age
  → Browser não faz revalidação mesmo com F5 ou Ctrl+R
  → Válido SOMENTE com max-age
  
  Cache-Control: max-age=31536000, immutable
  → Para assets com hash no nome: app.abc123.js, styles.xyz789.css
  → Força download de nova versão apenas quando o nome do arquivo muda
```

### stale-while-revalidate e stale-if-error

```
stale-while-revalidate=<seconds>
  → Serve a resposta "velha" imediatamente enquanto busca a nova em background
  → Zero latência percebida durante revalidação
  
  Cache-Control: max-age=60, stale-while-revalidate=600
  
  Timeline:
    0-60s:   fresh, serve do cache sem verificar
    60-660s: "stale" mas ainda serve imediatamente + busca nova versão em background
    660s+:   deve aguardar revalidação (não mais stale-while-revalidate)

stale-if-error=<seconds>
  → Se o servidor retornar 5xx, serve a resposta em cache mesmo expirada
  → Resiliência: melhor dar resposta velha do que nada
  
  Cache-Control: max-age=60, stale-if-error=86400
  → Se servidor falhar: servir do cache por até 24h
```

### Combinações por tipo de recurso

```
Assets com hash no nome (app.abc123.js, logo.xyz789.png):
  Cache-Control: public, max-age=31536000, immutable
  → 1 ano em cache, nunca revalida (o hash garante unicidade)
  → Quando o arquivo muda: o nome muda (novo hash) → novo arquivo = novo cache

HTML de páginas:
  Cache-Control: no-cache
  → Sempre verifica se mudou (via ETag), mas pode usar cache se 304
  → Balanceia: HTML precisa ser atual, mas evita download desnecessário

APIs com dados públicos (feeds, catálogos):
  Cache-Control: public, max-age=60, s-maxage=300, stale-while-revalidate=60
  → Browser: 1 min fresh, depois revalida
  → CDN: 5 min fresh
  → stale-while-revalidate: zero latência durante revalidação

APIs com dados privados por usuário:
  Cache-Control: private, no-cache
  → Só browser guarda (private), sempre valida antes de usar (no-cache)

Dados ultra-sensíveis (extratos, dados médicos):
  Cache-Control: no-store, no-cache
  → Nunca guarda absolutamente nada
  → Cada requisição vai ao servidor

Imagens sem hash (favicon.ico, imagens sem versionamento):
  Cache-Control: public, max-age=86400
  → 1 dia em cache (equilíbrio entre performance e atualidade)
```

## ETag — versão do recurso

`ETag` é um identificador opaco que representa uma versão específica do recurso. Quando o cliente tem o recurso em cache com um ETag, ele pode verificar se o recurso mudou sem baixar tudo novamente.

```
HTTP/1.1 200 OK
ETag: "abc123def456"
Cache-Control: no-cache

Body: {"usuarios": [...]}

Próxima requisição (cliente envia If-None-Match):
  GET /api/usuarios
  If-None-Match: "abc123def456"

Se não mudou:
  HTTP/1.1 304 Not Modified
  ETag: "abc123def456"
  (sem body — economiza toda a largura de banda do conteúdo)

Se mudou:
  HTTP/1.1 200 OK
  ETag: "xyz789uvw"
  Body: {"usuarios": [...novo conteúdo...]}
```

### ETag strong vs weak

```
Strong ETag: "abc123"
  → Byte-a-byte idêntico — qualquer diferença = ETag diferente
  → Pode ser usado para range requests (verificar partes específicas)
  → Gerado por: hash MD5/SHA do conteúdo, número de versão

Weak ETag: W/"abc123"
  → Semanticamente equivalente — conteúdo "essencialmente o mesmo"
  → Usado quando: compressão dinâmica (gzip pode variar), timestamps na resposta
  → NÃO pode ser usado para range requests
  
  Exemplo: resposta com timestamp de geração:
    {"data": "2024-01-15T10:30:00Z", "usuarios": [...]}
    {"data": "2024-01-15T10:30:01Z", "usuarios": [...]}  ← 1 segundo depois, mesmos dados
    → Strong ETag diferente (timestamp mudou)
    → Weak ETag igual (conteúdo relevante é o mesmo)
```

### Gerando ETags no servidor

```python
# Python — ETag como MD5 do conteúdo
import hashlib
import json
from fastapi import Request
from fastapi.responses import Response, JSONResponse

@app.get("/api/produtos")
async def listar_produtos(request: Request):
    produtos = await db.get_produtos()
    
    # Gerar ETag determinístico a partir do conteúdo
    conteudo = json.dumps(produtos, sort_keys=True, ensure_ascii=False)
    etag = f'"{hashlib.md5(conteudo.encode()).hexdigest()}"'
    
    # Verificar If-None-Match
    if request.headers.get("If-None-Match") == etag:
        return Response(
            status_code=304,
            headers={
                "ETag": etag,
                "Cache-Control": "no-cache"
            }
        )
    
    return JSONResponse(
        content=produtos,
        headers={
            "ETag": etag,
            "Cache-Control": "no-cache"
        }
    )

# Alternativa eficiente: ETag baseado em versão/timestamp (sem carregar dados)
@app.get("/api/produtos")
async def listar_produtos_v2(request: Request):
    # Versão leve: pegar apenas o timestamp da última modificação
    ultima_mod = await db.get_ultima_modificacao_produtos()
    etag = f'"{int(ultima_mod.timestamp())}"'
    
    if request.headers.get("If-None-Match") == etag:
        return Response(status_code=304, headers={"ETag": etag})
    
    # Só busca os dados completos se necessário
    produtos = await db.get_produtos()
    return JSONResponse(content=produtos, headers={"ETag": etag})
```

## Last-Modified — timestamp de modificação

`Last-Modified` indica quando o recurso foi modificado pela última vez. É a alternativa baseada em data ao ETag.

```
HTTP/1.1 200 OK
Last-Modified: Mon, 15 Jan 2024 10:00:00 GMT
Cache-Control: public, max-age=300

Próxima requisição (após max-age expirar):
  GET /recurso
  If-Modified-Since: Mon, 15 Jan 2024 10:00:00 GMT

Se não mudou desde então:
  HTTP/1.1 304 Not Modified
  Last-Modified: Mon, 15 Jan 2024 10:00:00 GMT

Se mudou:
  HTTP/1.1 200 OK
  Last-Modified: Mon, 15 Jan 2024 15:30:00 GMT
  Body: [conteúdo atualizado]
```

### Formato da data HTTP

```
Last-Modified usa o formato RFC 7231 (IMF-fixdate):
  Mon, 15 Jan 2024 10:00:00 GMT    ← correto (sempre GMT/UTC)
  2024-01-15T10:00:00Z             ← formato ISO (NÃO é correto para esse header)
  
  # Python — gerar data no formato HTTP correto
  from email.utils import formatdate
  from datetime import datetime, timezone
  
  dt = datetime(2024, 1, 15, 10, 0, 0, tzinfo=timezone.utc)
  last_modified = formatdate(dt.timestamp(), usegmt=True)
  # → "Mon, 15 Jan 2024 10:00:00 GMT"
```

### ETag vs Last-Modified — qual usar

```
Use ETag quando:
  ✓ Conteúdo gerado dinamicamente (banco de dados)
  ✓ Precisão de 1 segundo não é suficiente (atualizações rápidas)
  ✓ Arquivos que são copiados/movidos (Last-Modified muda sem mudança de conteúdo)
  ✓ Comparação precisa byte-a-byte necessária

Use Last-Modified quando:
  ✓ Arquivos estáticos no sistema de arquivos (mtime natural)
  ✓ Recursos que raramente são atualizados mais de uma vez por segundo
  ✓ Simplicidade é prioridade

Use ambos (recomendado para recursos importantes):
  ETag: "abc123"
  Last-Modified: Mon, 15 Jan 2024 10:00:00 GMT
  
  Clientes enviam ambos (If-None-Match + If-Modified-Since)
  Servidor usa o mais preciso (ETag tem precedência por ser mais confiável)
```

## Expires — data de expiração absoluta (legado)

`Expires` é o predecessor do `Cache-Control: max-age` — define uma data absoluta de expiração. É considerado legado mas ainda amplamente suportado.

```
Expires: Mon, 22 Jan 2024 10:00:00 GMT

→ Cache válido até esse momento específico
→ Após essa data: revalidar antes de usar

Problema com Expires:
  → Depende do relógio do servidor E do cliente estarem sincronizados
  → Se o cliente está com horário errado: comportamento imprevisível
  → max-age é relativo (em segundos) — sem esse problema

Cache-Control: max-age sobrescreve Expires:
  Se ambos estiverem presentes: max-age tem precedência
  Expires é útil apenas para compatibilidade com clientes HTTP/1.0 muito antigos

Expires = 0 ou data no passado:
  Indica que o recurso já expirou → deve revalidar imediatamente
  Equivalente a Cache-Control: no-cache
```

```python
# Python — gerar Expires no formato correto (legado)
from email.utils import formatdate
from datetime import datetime, timezone, timedelta

expira_em = datetime.now(timezone.utc) + timedelta(hours=24)
expires_header = formatdate(expira_em.timestamp(), usegmt=True)
# → "Tue, 16 Jan 2024 10:00:00 GMT"
```

## Vary — variações do mesmo recurso

`Vary` instrui caches a armazenar versões separadas da mesma URL para diferentes valores de headers. Sem `Vary`, um cache pode servir a versão errada de um recurso.

```
Vary: Accept-Encoding
  → "Esta resposta pode ser diferente dependendo do Accept-Encoding"
  → Cache deve armazenar versão gzip e versão não-comprimida separadamente

Vary: Accept-Language
  → "Esta resposta pode ser diferente por idioma"
  → CDN mantém versão em pt-BR e en-US separadas para a mesma URL

Vary: Accept
  → "Servidor serve JSON ou XML dependendo do Accept"
  → Cache mantém versão JSON e versão XML separadas

Vary: *
  → "Esta resposta pode variar por qualquer header"
  → EVITAR — efetivamente desativa o cache em CDNs (cada request é único)

Vary: Authorization
  → Cache trata como não-cacheável por padrão
  → Pois Authorization varia por usuário
```

### O problema sem Vary

```
Sem Vary: Accept-Encoding:

1. Cliente A (suporta gzip): GET /api/dados + Accept-Encoding: gzip
   CDN não tem em cache → vai ao servidor
   Servidor retorna: Content-Encoding: gzip + body comprimido
   CDN armazena: [bytes gzip]

2. Cliente B (sem gzip): GET /api/dados (sem Accept-Encoding)
   CDN tem em cache → serve do cache
   CDN serve: [bytes gzip] para um cliente que NÃO suporta gzip!
   → Cliente B recebe dados corrompidos (lixo binário)

Com Vary: Accept-Encoding:

1. Cliente A: CDN armazena versão gzip sob chave "/api/dados + gzip"
2. Cliente B: CDN não tem "/api/dados + sem encoding" → vai ao servidor
   Servidor retorna: sem compressão
   CDN armazena versão não-comprimida sob chave "/api/dados + sem encoding"
3. Cada cliente recebe a versão correta para seu Accept-Encoding
```

### Vary e performance de cache

```
Vary com muitos headers = mais versões do cache = menor hit rate:

Vary: Accept-Encoding          ← 2-3 versões (gzip, br, identity)
Vary: Accept-Language          ← N versões (uma por idioma)
Vary: Accept-Encoding, Accept-Language ← N × 3 versões!

Para CDNs:
  Muitas variações = menor taxa de cache hit = mais requisições ao origem
  
Boas práticas:
  → Incluir Vary apenas quando a resposta REALMENTE varia por aquele header
  → Accept-Encoding: sempre incluir se usar compressão condicional
  → Accept-Language: incluir se o servidor faz i18n na resposta
  → Accept: incluir se o servidor faz content negotiation (JSON vs XML)
```

## Age — quanto tempo está no cache

`Age` é um header de resposta adicionado por proxies/CDNs indicando há quantos segundos o recurso está no cache do proxy:

```
HTTP/1.1 200 OK
Cache-Control: max-age=300
Age: 120

→ O recurso tem 300s de validade
→ Está no cache do CDN há 120s
→ Frescura restante para o cliente: 300 - 120 = 180s
→ O cliente pode usar por mais 180s sem revalidar

Age = 0: acabou de ser buscado do servidor de origem
Age = max-age: resposta expirou no cache do proxy
```

## Configuração completa de cache por tipo de recurso

```nginx
# Nginx — configuração de cache por tipo de arquivo

# HTML — sem cache, sempre revalida
location ~* \.html$ {
    add_header Cache-Control "no-cache";
    add_header ETag $upstream_http_etag;
    add_header Last-Modified $upstream_http_last_modified;
}

# Assets com hash no nome — cache longo
location ~* \.(js|css)$ {
    if ($uri ~* "\.[a-f0-9]{8,}\.(js|css)$") {
        add_header Cache-Control "public, max-age=31536000, immutable";
    }
}

# Imagens sem hash
location ~* \.(jpg|jpeg|png|gif|webp|avif|svg)$ {
    add_header Cache-Control "public, max-age=86400, stale-while-revalidate=3600";
    add_header Vary "Accept-Encoding";
}

# API JSON pública
location /api/public/ {
    add_header Cache-Control "public, max-age=60, s-maxage=300, stale-while-revalidate=60";
    add_header Vary "Accept-Encoding, Accept-Language";
    add_header ETag $upstream_http_etag;
}

# API privada
location /api/private/ {
    add_header Cache-Control "private, no-cache";
    add_header Pragma "no-cache";  # compatibilidade HTTP/1.0
}
```

## Erros comuns e armadilhas

**`Cache-Control: no-cache` não impede caching:** esse é o erro mais comum. `no-cache` significa "revalidar sempre antes de usar" — o recurso PODE ser armazenado. Para realmente proibir armazenamento: `no-store`.

**Sem `Vary: Accept-Encoding` em respostas comprimidas:** um CDN pode servir a versão gzip para um cliente sem suporte a gzip → dados corrompidos. Sempre incluir `Vary: Accept-Encoding` quando a compressão é condicional.

**ETags inconsistentes em clusters:** se 3 servidores backend geram ETags diferentes para o mesmo conteúdo (ex: incluindo o ID do servidor na ETag), um cliente que faz round-robin entre servidores sempre recebe ETag diferente → nunca obtém 304 → cache nunca é aproveitado.

**`immutable` em assets sem versionamento por nome:** se `logo.png` tem `Cache-Control: immutable, max-age=31536000` e você atualiza o logo, os usuários ficam com a versão antiga por 1 ano inteiro. `immutable` só é seguro com assets cujo nome inclui um hash do conteúdo.

## 🧩 Quiz de Fixação

1. Uma CDN armazena em cache `GET /api/noticias` com `Cache-Control: max-age=300`. Após 240 segundos, um usuário faz a requisição. A CDN serve do cache e inclui `Age: 240`. O browser recebe esse header. Por quanto tempo mais o browser pode usar esse recurso sem revalidar?

2. Uma API retorna `Cache-Control: public, max-age=3600` sem `Vary: Accept-Language`. O servidor serve a mesma URL em português para `Accept-Language: pt-BR` e em inglês para `Accept-Language: en-US`. Um CDN cacheia a versão em português. O próximo usuário com `Accept-Language: en-US` recebe qual idioma e por quê?

3. Um asset JavaScript tem `Cache-Control: public, max-age=31536000, immutable`. O time faz deploy de uma nova versão do JavaScript. Os usuários que visitaram o site antes do deploy ainda terão o arquivo antigo em cache por 1 ano? Como o time deveria estruturar o deploy para evitar isso?

**Respostas:**

1) O recurso tem `max-age=300` (válido por 300 segundos). A CDN o armazenou e já faz `Age: 240` segundos que está no cache. O browser calcula a frescura restante como `max-age - Age = 300 - 240 = 60 segundos`. O browser pode usar o recurso por mais **60 segundos** sem revalidar. Após isso, o browser enviará uma requisição condicional (`If-None-Match` ou `If-Modified-Since`) para verificar se o recurso mudou. O `Age` header é crucial para que o browser saiba que o recurso já "envelhececu" na CDN e deve ser tratado como tendo apenas 60s de validade restante, não os 300s completos.

2) O usuário com `en-US` **recebe a versão em português**. Sem `Vary: Accept-Language`, o CDN não sabe que a resposta varia por idioma — ele tem apenas uma entrada de cache para a URL `/api/noticias`, que é a versão em português (a primeira que foi cacheada). Para o CDN, todas as requisições para `/api/noticias` são iguais e devem receber a mesma resposta em cache. **Como corrigir:** adicionar `Vary: Accept-Language` na resposta. Isso instrui o CDN a manter versões separadas da resposta para cada `Accept-Language` distinto — `/api/noticias [pt-BR]` e `/api/noticias [en-US]` são tratadas como entradas de cache separadas.

3) **Sim e não** — a resposta depende do nome do arquivo. Se o arquivo se chama simplesmente `app.js`, os usuários com `app.js` em cache usarão a versão antiga por 1 ano (o `immutable` impede qualquer revalidação). **Como estruturar corretamente:** usar **content-based hashing** no nome do arquivo. O build system (Webpack, Vite, etc.) gera nomes como `app.abc12345.js` baseados no hash do conteúdo. Quando o código muda, o hash muda: `app.xyz98765.js`. O HTML é atualizado para referenciar o novo nome. O `immutable + max-age=31536000` é seguro porque: (a) usuários com `app.abc12345.js` em cache nunca precisam revalidar (correto — esse arquivo nunca muda); (b) após o deploy, o HTML aponta para `app.xyz98765.js` — arquivo diferente, sem entrada de cache, baixado normalmente. Os arquivos antigos ficam em cache mas não são mais referenciados — eventualmente expiram ou são limpos pelo browser.
