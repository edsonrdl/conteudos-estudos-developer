### Headers de sessão e navegação — Set-Cookie, Location e WWW-Authenticate

Os headers de sessão e navegação controlam como o browser persiste estado (cookies), para onde redirecionar o usuário (Location) e como autenticar quando o acesso é negado (WWW-Authenticate). São os headers que fecham o ciclo de interação entre servidor e browser para fluxos de autenticação, sessão e navegação.

---

## Set-Cookie — gerenciamento de sessão

`Set-Cookie` é o header com o qual o servidor instrui o browser a armazenar um cookie. O browser então envia esse cookie automaticamente em todas as requisições subsequentes para o mesmo domínio (conforme os atributos configurados).

```
Set-Cookie: <nome>=<valor>; <atributos>

Exemplos:
  Set-Cookie: session_id=abc123def456; HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=86400
  Set-Cookie: preferencia_tema=dark; SameSite=Lax; Max-Age=31536000
  Set-Cookie: csrf_token=xyz789; SameSite=Strict; Path=/
```

### Atributos de segurança

#### HttpOnly — proteção contra XSS

```
Set-Cookie: session_id=abc123; HttpOnly

→ JavaScript NÃO pode ler este cookie
→ document.cookie não inclui cookies HttpOnly
→ Mesmo se XSS injetar código malicioso: não consegue roubar o session_id

Sem HttpOnly:
  document.cookie → "session_id=abc123; outro_cookie=xyz"
  Qualquer script na página (incluindo injetado) lê tudo

Com HttpOnly:
  document.cookie → "outro_cookie=xyz"
  session_id não aparece → script malicioso não consegue roubar

OBRIGATÓRIO para:
  → Cookies de sessão
  → Cookies de autenticação (tokens de sessão)
  → Qualquer cookie que não precise ser lido por JavaScript
```

#### Secure — apenas HTTPS

```
Set-Cookie: session_id=abc123; Secure

→ Cookie só é enviado em conexões HTTPS
→ Em HTTP: o header Cookie não inclui este cookie
→ Sem Secure: cookie enviado em texto puro via HTTP → interceptável

OBRIGATÓRIO para:
  → Qualquer cookie em ambiente de produção
  → Combine sempre com HttpOnly para cookies de autenticação
```

#### SameSite — proteção contra CSRF

```
SameSite=Strict
  → Cookie só é enviado quando a origem da requisição É o mesmo site
  → Navegação de outro site para o seu: cookie NÃO é enviado
  
  Fluxo:
    1. Usuário está em evil.com
    2. JavaScript em evil.com faz fetch para banco.com
    3. SameSite=Strict: banco.com NÃO recebe o cookie de sessão
    → Ataque CSRF falha!
    
  Lado negativo:
    Usuário clica em link em email para banco.com
    → O cookie de sessão NÃO é enviado (novo link = "outro site")
    → Usuário precisa logar novamente
    → Experiência ruim para logins via link

SameSite=Lax (padrão moderno dos browsers se não especificado)
  → Cookie enviado em navegações de nível superior (top-level navigation)
  → Cookie NÃO enviado em requisições cross-site de sub-recursos
  
  Permite:
    → Clicar em links de emails → cookie enviado (navegação top-level)
    → Formulários GET de outros sites → cookie enviado
  
  Bloqueia:
    → POSTs de forms de outros sites → cookie NÃO enviado
    → fetch/XHR de outros sites → cookie NÃO enviado
    → Iframes de outros sites → cookie NÃO enviado
  
  Equilíbrio: boa proteção CSRF + boa experiência de usuário

SameSite=None
  → Cookie enviado em qualquer contexto cross-site
  → REQUER Secure (browsers bloqueiam None sem Secure)
  
  Quando usar:
    → Widgets embarcados que precisam de autenticação
    → APIs chamadas de outros domínios com credentials
    → Serviços que funcionam como iframe em sites de parceiros
    
  Set-Cookie: embed_token=abc; SameSite=None; Secure
```

### Atributos de escopo

#### Domain — em quais domínios o cookie é enviado

```
Set-Cookie: session=abc; Domain=empresa.com
  → Enviado para: empresa.com E todos os subdomínios (*.empresa.com)
  → api.empresa.com, admin.empresa.com, www.empresa.com — todos recebem

Set-Cookie: session=abc; Domain=api.empresa.com
  → Apenas para api.empresa.com (não para outros subdomínios)

Sem Domain:
  → Apenas para o domínio exato que enviou o cookie
  → Não para subdomínios
  
Segurança:
  Domain=empresa.com com muitos subdomínios:
  → Subdomínio comprometido (ex: cdn.empresa.com) pode ler/enviar o cookie
  → Prefira Domain específico ou sem Domain quando possível
```

#### Path — em quais URLs o cookie é enviado

```
Set-Cookie: admin_token=abc; Path=/admin
  → Cookie enviado apenas para: /admin, /admin/usuarios, /admin/config...
  → NÃO enviado para: /, /api, /produtos

Set-Cookie: session=abc; Path=/
  → Cookie enviado para TODOS os paths
  → Padrão quando Path não é especificado

Uso: isolar cookies por área da aplicação
  → Cookie de sessão de /app/ não enviado para /static/
  → Cookie de /admin/ não enviado para o site público
```

#### Expiração — quando o cookie é deletado

```
Max-Age=<seconds>
  → Expiração relativa em segundos a partir de agora
  → Preferido sobre Expires
  
  Max-Age=86400  → 1 dia
  Max-Age=604800 → 1 semana
  Max-Age=31536000 → 1 ano
  Max-Age=0      → deletar imediatamente (logout)
  Max-Age=-1     → cookie de sessão (deletado ao fechar browser)

Expires=<date>
  → Expiração absoluta no formato HTTP date
  → Problema: depende do relógio do cliente estar correto
  → Use Max-Age quando possível
  
  Expires=Thu, 01 Jan 2099 00:00:00 GMT → "nunca expira"
  Expires=Thu, 01 Jan 1970 00:00:00 GMT → deletar imediatamente

Sem Max-Age e sem Expires:
  → Cookie de sessão (session cookie)
  → Deletado quando o browser é fechado
  → Não persiste entre sessões
```

### Múltiplos cookies em uma resposta

```
Cada Set-Cookie define UM cookie:

HTTP/1.1 200 OK
Set-Cookie: session_id=abc123; HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=86400
Set-Cookie: csrf_token=xyz789; SameSite=Strict; Path=/; Max-Age=86400
Set-Cookie: preferencia=dark; SameSite=Lax; Max-Age=31536000

→ Browser armazena 3 cookies separados
→ Nas próximas requisições:
  Cookie: session_id=abc123; csrf_token=xyz789; preferencia=dark
```

### Login e logout com cookies

```python
# FastAPI — login com cookie de sessão
from fastapi import Response, Request
from fastapi.responses import JSONResponse

@app.post("/auth/login")
async def login(credenciais: Credenciais, response: Response):
    usuario = autenticar(credenciais.email, credenciais.senha)
    if not usuario:
        raise HTTPException(401, "Credenciais inválidas")
    
    session_id = criar_sessao(usuario.id)
    csrf_token = gerar_csrf_token()
    
    response.set_cookie(
        key="session_id",
        value=session_id,
        max_age=86400,      # 1 dia
        httponly=True,      # JS não lê
        secure=True,        # HTTPS apenas
        samesite="strict",  # proteção CSRF
        path="/"
    )
    response.set_cookie(
        key="csrf_token",
        value=csrf_token,
        max_age=86400,
        httponly=False,     # JS PRECISA ler para enviar no header
        secure=True,
        samesite="strict",
        path="/"
    )
    
    return {"usuario": usuario.nome, "message": "Login realizado"}

@app.post("/auth/logout")
async def logout(response: Response, request: Request):
    session_id = request.cookies.get("session_id")
    if session_id:
        invalidar_sessao(session_id)
    
    # Deletar os cookies
    response.delete_cookie("session_id")
    response.delete_cookie("csrf_token")
    # Equivalente: set_cookie(..., max_age=0)
    
    return {"message": "Logout realizado"}
```

### Padrão de double-submit CSRF com cookie

```
Proteção CSRF com dois cookies:
  1. session_id: HttpOnly, SameSite=Strict → JS não lê, apenas browser envia
  2. csrf_token: sem HttpOnly, SameSite=Strict → JS lê e envia no header

Fluxo:
  Login: servidor gera ambos os cookies
  
  Requisição mutante (POST):
  Browser envia automaticamente: Cookie: session_id=...; csrf_token=xyz
  JS lê e adiciona header: X-CSRF-Token: xyz
  
  Servidor verifica:
  1. session_id válido (autenticação)
  2. X-CSRF-Token header == csrf_token cookie
     → Se iguais: requisição legítima (apenas o próprio site pode ler e enviar o cookie)
     → Se diferentes: possível CSRF → rejeitar

Por que funciona:
  Atacante de evil.com NÃO consegue ler o csrf_token cookie (SameSite=Strict)
  Então não pode incluir o X-CSRF-Token header correto
  → Servidor detecta a discrepância → rejeita
```

## Location — redirecionamento e criação de recursos

`Location` é usado em dois contextos distintos:

### 1. Redirecionamentos (3xx)

```
HTTP/1.1 301 Moved Permanently
Location: https://nova-url.com/recurso

HTTP/1.1 302 Found
Location: /login?redirect=/painel

HTTP/1.1 307 Temporary Redirect
Location: https://api.v2.empresa.com/endpoint

O browser:
  → Lê o Location header
  → Faz uma nova requisição para a URL indicada
  → Automaticamente (sem ação do usuário)
  → GET para 301/302/303; mesmo método para 307/308

Valores absolutos vs relativos:
  Absoluto: https://www.empresa.com/novo-caminho  → mais seguro e explícito
  Relativo: /novo-caminho                          → relativo ao servidor atual
             novo-caminho                           → relativo ao path atual (evitar)
```

### 2. Criação de recursos (201 Created)

```
HTTP/1.1 201 Created
Location: /api/produtos/456
Content-Type: application/json

{"id": 456, "nome": "Notebook", "criado_em": "2024-01-15T10:00:00Z"}

O Location indica onde encontrar o recurso recém-criado:
  → Cliente pode imediatamente fazer GET /api/produtos/456
  → Não precisa saber como montar a URL do novo recurso
  → Segue o princípio HATEOAS do REST
```

### Open Redirect — vulnerabilidade no Location

```
Aplicação com redirect baseado em input:
  GET /login?redirect=/painel → após login, redireciona para /painel
  
Ataque:
  GET /login?redirect=https://evil.com
  
  Se o servidor não valida o destino:
  HTTP/1.1 302 Found
  Location: https://evil.com  ← usuário redirecionado para site malicioso!
  
  Phishing: usuário confia no domínio da empresa, clica no link legítimo
  → é redirecionado para site de phishing

Prevenção:
  1. Só permitir redirects para URLs relativas (/path, não http://...)
  2. Whitelist de domínios permitidos
  3. Nunca usar input do usuário diretamente no Location header

# Python — validação de redirect
from urllib.parse import urlparse

def redirect_seguro(url: str, base_domain: str = "empresa.com") -> str:
    parsed = urlparse(url)
    
    # URL relativa: sempre seguro
    if not parsed.scheme and not parsed.netloc:
        return url
    
    # URL absoluta: verificar domínio
    if parsed.netloc and (parsed.netloc == base_domain or 
                          parsed.netloc.endswith(f".{base_domain}")):
        return url
    
    # Destino não confiável: redirecionar para home
    return "/"
```

## WWW-Authenticate — desafio de autenticação

`WWW-Authenticate` é enviado junto com `401 Unauthorized` para informar ao cliente qual esquema de autenticação usar e como proceder.

```
HTTP/1.1 401 Unauthorized
WWW-Authenticate: <scheme> <parâmetros>

Exemplos:
  WWW-Authenticate: Basic realm="API Interna"
  WWW-Authenticate: Bearer realm="api.empresa.com"
  WWW-Authenticate: Bearer realm="api.empresa.com", error="invalid_token", error_description="Token expirado"
  WWW-Authenticate: Digest realm="api.empresa.com", qop="auth", nonce="abc123"
```

### Schemes comuns

```
Basic:
  WWW-Authenticate: Basic realm="Nome do Domínio Protegido"
  
  Browser exibe caixa de login nativa com o realm como título
  Usuário envia: Authorization: Basic base64(usuario:senha)

Bearer (OAuth 2.0 / JWT):
  WWW-Authenticate: Bearer realm="api.empresa.com"
  
  Sem mais informação: "precisa de token Bearer"
  
  Com erro específico:
  WWW-Authenticate: Bearer realm="api.empresa.com",
    error="invalid_token",
    error_description="Token expirado — renovar com refresh_token",
    error_uri="https://docs.empresa.com/auth/token-expired"

Negotiate (Kerberos / NTLM):
  WWW-Authenticate: Negotiate
  WWW-Authenticate: NTLM
  
  Ambientes corporativos com Active Directory
  Autenticação transparente (SSO) para usuários na rede interna
```

### WWW-Authenticate com múltiplos schemes

```
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="api.empresa.com", error="invalid_token"
WWW-Authenticate: Basic realm="api.empresa.com"

→ O servidor suporta Bearer OU Basic
→ O cliente pode escolher qual usar
→ Bearer é geralmente tentado primeiro (mais seguro)
```

### Proxy-Authenticate — autenticação em proxies

```
HTTP/1.1 407 Proxy Authentication Required
Proxy-Authenticate: Basic realm="Proxy Corporativo"

→ O proxy (não o servidor final) requer autenticação
→ Cliente responde com: Proxy-Authorization: Basic base64(user:senha)
→ Diferente de 401: é o proxy que precisa ser autenticado, não o servidor
```

## Sumário — headers de sessão e navegação por contexto

```
Fluxo de LOGIN:
  POST /login + credenciais
  ↓
  HTTP/1.1 200 OK
  Set-Cookie: session_id=abc; HttpOnly; Secure; SameSite=Strict; Max-Age=86400
  Set-Cookie: csrf_token=xyz; Secure; SameSite=Strict; Max-Age=86400
  
Fluxo de RECURSO CRIADO:
  POST /api/produtos + body
  ↓
  HTTP/1.1 201 Created
  Location: /api/produtos/456
  
Fluxo de REDIRECT:
  GET /pagina-antiga
  ↓
  HTTP/1.1 301 Moved Permanently
  Location: /nova-pagina
  
Fluxo de AUTENTICAÇÃO NECESSÁRIA:
  GET /api/dados (sem token)
  ↓
  HTTP/1.1 401 Unauthorized
  WWW-Authenticate: Bearer realm="api.empresa.com", error="missing_token"
  
Fluxo de LOGOUT:
  POST /logout
  ↓
  HTTP/1.1 200 OK
  Set-Cookie: session_id=; Max-Age=0; Path=/
  Set-Cookie: csrf_token=; Max-Age=0; Path=/
```

## Erros comuns e armadilhas

**Cookie sem HttpOnly para dados de sessão:** qualquer XSS na página pode roubar o session_id via `document.cookie`. HttpOnly é não-negociável para cookies de autenticação.

**SameSite sem Secure em produção:** `SameSite=None` sem `Secure` é rejeitado por browsers modernos — o cookie simplesmente não é enviado. Sempre combine `SameSite=None; Secure`.

**Location com redirect não validado:** usar parâmetros de URL como destino de redirect sem validação cria Open Redirect — permite phishing usando a reputação do seu domínio.

**Não enviar WWW-Authenticate no 401:** sem esse header, o cliente não sabe como autenticar. Muitos clientes HTTP automáticos precisam do `WWW-Authenticate` para iniciar o fluxo de autenticação corretamente.

**Cookies compartilhados entre subdomínios inadvertidamente:** `Domain=empresa.com` faz o cookie ir para todos os subdomínios. Um subdomínio de terceiro (`parceiro.empresa.com`) receberia o session_id — indesejado.

## 🧩 Quiz de Fixação

1. Um site usa `Set-Cookie: session_id=abc123; SameSite=Lax`. Um usuário recebe um e-mail com link `https://banco.com/painel`. Ao clicar, o cookie de sessão é enviado? E se o e-mail tiver um formulário POST que aponta para `https://banco.com/transferir`?

2. Uma API REST retorna `201 Created` com `Location: /api/pedidos/789` mas sem body. O cliente recebe o 201. Quais são as opções disponíveis para o cliente obter os dados do pedido criado, e qual é a mais eficiente?

3. Por que o padrão de double-submit CSRF (session_id com HttpOnly + csrf_token sem HttpOnly) funciona mesmo sem verificação server-side do Referer/Origin, e qual é o único cenário onde ainda seria vulnerável?

**Respostas:**

1) **Clicando no link (GET navegação top-level):** o cookie com `SameSite=Lax` **É enviado**. `Lax` permite que cookies sejam enviados em navegações de nível superior (o usuário está navegando para o site), incluindo cliques em links de e-mails, bookmarks ou digitando a URL. O browser interpreta "clicar em link" como navegação legítima do usuário. **Formulário POST de outro domínio:** o cookie com `SameSite=Lax` **NÃO é enviado**. `Lax` bloqueia POSTs cross-site (e outros métodos não-GET em contextos cross-origin como iframes). Um formulário no e-mail fazendo POST para banco.com seria um CSRF clássico — e `Lax` protege exatamente contra isso.

2) O cliente tem três opções: (a) **Fazer GET imediatamente** com a URL do Location: `GET /api/pedidos/789` → recebe os dados completos. É o padrão REST e a mais semântica; (b) **O servidor pode retornar o body no 201** — a RFC permite body no 201. Retornar o pedido criado diretamente no body do 201 elimina a segunda requisição — é a mais **eficiente** (1 round trip em vez de 2); (c) **Ignorar o Location** e assumir o ID da resposta pelo padrão da API (frágil, não recomendado). A opção mais comum em produção é (b): retornar os dados no body do 201 E o Location header — o cliente tem os dados imediatamente e também sabe a URL canônica do recurso para referência futura.

3) O padrão funciona sem verificação de Referer/Origin porque: o `csrf_token` está num cookie com `SameSite=Strict` (ou Lax) — sites de outras origens não conseguem ler esse cookie via JavaScript. Portanto, um atacante em `evil.com` não pode obter o valor do `csrf_token` para incluí-lo no header `X-CSRF-Token`. A proteção independe do Referer/Origin porque está baseada na **incapacidade do atacante de ler o cookie** — não em verificar de onde a requisição veio. **O único cenário vulnerável:** **XSS no próprio domínio**. Se um atacante conseguir injetar JavaScript em qualquer página de `banco.com`, ele pode ler o `csrf_token` cookie (que não tem HttpOnly) via `document.cookie` e fazer requisições autenticadas com o token correto. Por isso o double-submit CSRF só é uma camada — deve ser combinado com proteção robusta contra XSS (CSP, sanitização de input, Content-Type validation).
