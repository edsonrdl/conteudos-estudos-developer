### Headers de conteúdo da resposta — Content-Type, Content-Length, Content-Encoding, Transfer-Encoding

Os headers de conteúdo da resposta descrevem o body que o servidor está retornando: o que é, qual o tamanho, se está comprimido e como foi transmitido. São os headers que o cliente lê para saber como interpretar e descomprimir os bytes recebidos — erros aqui resultam em dados corrompidos ou parsing incorreto.

---

## Content-Type — o que é o body

Na resposta, `Content-Type` informa ao cliente como interpretar o body recebido. O cliente usa essa informação para: escolher o parser correto, exibir ou processar o conteúdo adequadamente.

```
Content-Type: <type>/<subtype>[; parâmetros]

Exemplos em respostas:
  Content-Type: application/json; charset=utf-8
  Content-Type: text/html; charset=utf-8
  Content-Type: image/jpeg
  Content-Type: application/pdf
  Content-Type: text/csv; charset=utf-8
  Content-Type: application/octet-stream
```

### Regras de sniffing — quando o browser ignora o Content-Type

```
MIME Sniffing:
  Browsers antigos "adivinhavam" o tipo do conteúdo quando Content-Type
  estava ausente ou parecia incorreto.
  
  Problema de segurança:
    Servidor retorna: Content-Type: text/plain
    Body contém: <script>alert('xss')</script>
    Browser sniffa: "parece HTML!" → executa o script → XSS!

Prevenção:
  X-Content-Type-Options: nosniff
  → Instrui o browser a NÃO fazer sniffing — respeitar o Content-Type declarado
  → Deve ser incluído em TODAS as respostas de APIs

  Sem nosniff: browser pode executar conteúdo "inocente" como HTML/JS
  Com nosniff: browser rejeita conteúdo com Content-Type incorreto
```

### Content-Type em diferentes tipos de resposta

```python
# FastAPI — configurando Content-Type correto por tipo de resposta
from fastapi.responses import (
    JSONResponse,       # application/json
    HTMLResponse,       # text/html
    PlainTextResponse,  # text/plain
    FileResponse,       # infere do arquivo (image/jpeg, application/pdf, etc.)
    StreamingResponse,  # configura manualmente
    Response            # controle total
)

# JSON (padrão do FastAPI)
@app.get("/api/dados")
async def dados():
    return {"resultado": "ok"}  # Content-Type: application/json

# HTML
@app.get("/pagina")
async def pagina():
    return HTMLResponse("<html><body>Olá!</body></html>")

# Arquivo com Content-Type específico
@app.get("/imagem")
async def imagem():
    return FileResponse("foto.jpg", media_type="image/jpeg")

# Content-Type customizado
@app.get("/proto")
async def proto():
    dados = produto.SerializeToString()  # protobuf serializado
    return Response(content=dados, media_type="application/x-protobuf")
```

## Content-Length — tamanho do body

`Content-Length` especifica o tamanho exato do body em bytes. Permite ao cliente:
- Saber quanto dado esperar
- Mostrar barra de progresso de download
- Detectar se a resposta foi truncada
- Reutilizar conexão TCP (sabe quando a resposta termina)

```
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 247

{"id": 1, "nome": "Produto A", ...}  ← exatamente 247 bytes
```

### Quando Content-Length pode estar ausente

```
1. Respostas com Transfer-Encoding: chunked:
   O tamanho é desconhecido antecipadamente (streaming)
   → Não se usa Content-Length com chunked

2. Respostas 1xx, 204, 304:
   Sem body → Content-Length não se aplica (ou deve ser 0)

3. Conexões HTTP/1.0:
   O servidor fecha a conexão para indicar fim do body
   → Content-Length não é obrigatório mas recomendado

4. HTTP/2:
   Usa framing — o tamanho de cada frame é conhecido
   Content-Length ainda pode ser usado mas não é crítico para framing
```

### Content-Length e segurança

```
Content-Length incorreto pode causar:

Truncation attack (Content-Length menor que o body real):
  Content-Length: 10
  Body: {"ok": true, "dados_confidenciais": "..."}  ← 50 bytes reais
  
  Cliente lê apenas 10 bytes: {"ok": tru
  Resto do body: e, "dados_confidenciais..."} → ignorado ou misturado na próxima resposta
  
  Em conexões persistentes: os bytes excedentes são interpretados como a próxima resposta
  → Possível HTTP Response Splitting

Validação:
  Servidores e proxies devem verificar que Content-Length bate com o body real
  Clientes devem verificar que receberam exatamente Content-Length bytes
```

### Calculando Content-Length

```python
# Python — calcular Content-Length de um body JSON
import json

dados = {"id": 123, "nome": "Produto A", "preco": 2999.90}
body = json.dumps(dados, ensure_ascii=False).encode("utf-8")

headers = {
    "Content-Type": "application/json; charset=utf-8",
    "Content-Length": str(len(body))  # número de BYTES, não caracteres!
}

# Atenção: len("café") == 4 chars, mas len("café".encode("utf-8")) == 5 bytes!
# Content-Length sempre em bytes
```

## Content-Encoding — compressão do body

`Content-Encoding` indica qual transformação foi aplicada ao body antes de transmitir. O cliente deve reverter essa transformação (descomprimir) para obter o conteúdo original.

```
Content-Encoding: gzip
Content-Encoding: br
Content-Encoding: zstd
Content-Encoding: deflate
Content-Encoding: identity  ← sem transformação (valor padrão)
```

### Fluxo de compressão

```
Servidor (antes de enviar):
  Body original: {"usuarios": [...]}  →  48.200 bytes
  Comprimir com gzip                  →   8.140 bytes (83% menor)
  
  Resposta:
    Content-Encoding: gzip
    Content-Length: 8140        ← tamanho COMPRIMIDO
    Body: [bytes gzip]

Cliente (ao receber):
  Lê Content-Encoding: gzip
  Descomprime os bytes recebidos
  Obtém: {"usuarios": [...]}  →  48.200 bytes (original)

O Content-Length reflete o tamanho APÓS compressão (tamanho na rede)
O tamanho antes da compressão só é conhecido após descomprimir
```

### Content-Encoding vs Accept-Encoding

```
Na REQUISIÇÃO (o que o cliente suporta):
  Accept-Encoding: br, gzip;q=0.9, deflate;q=0.8
  → "Consigo processar Brotli (preferido), gzip, deflate"

Na RESPOSTA (o que o servidor aplicou):
  Content-Encoding: gzip
  → "Apliquei gzip neste body"

O servidor escolhe o algoritmo baseado no Accept-Encoding do cliente
Se o cliente não enviou Accept-Encoding: servidor não comprime (ou usa identity)
```

### Compressão múltipla (raro mas possível)

```
Content-Encoding: gzip, deflate
→ Body foi primeiro deflate, depois gzip
→ Cliente deve descomprimir na ordem inversa: primeiro ungzip, depois inflate
→ Na prática: usar apenas uma compressão é suficiente e mais simples
```

### Configurando compressão no servidor

```python
# FastAPI — middleware de compressão automática
from fastapi.middleware.gzip import GZipMiddleware

app.add_middleware(
    GZipMiddleware,
    minimum_size=1000  # só comprimir respostas > 1000 bytes
    # Responses menores: overhead de compressão > ganho
)
```

```nginx
# Nginx — compressão automática
gzip on;
gzip_min_length 1000;
gzip_types application/json text/plain text/html text/css application/javascript;
gzip_vary on;  # adiciona Vary: Accept-Encoding (importante para cache)

# Brotli (módulo extra)
brotli on;
brotli_min_length 1000;
brotli_types application/json text/plain text/html text/css application/javascript;
```

### Por que Content-Encoding importa para Content-Length

```
Sem compressão:
  Content-Length: 48200   ← tamanho do body na rede

Com gzip:
  Content-Encoding: gzip
  Content-Length: 8140    ← tamanho COMPRIMIDO na rede
  
  Após descomprimir: 48200 bytes (o "tamanho real" não está no header!)

Se um proxy remover Content-Encoding mas não recomprimir:
  Remove gzip, serve bytes descomprimidos
  Mas mantém: Content-Length: 8140 (INCORRETO — não bate com os 48200 reais)
  → Cliente para de ler após 8140 bytes, corpo truncado!
  
  Boas práticas de proxy: sempre atualizar Content-Length ao modificar o encoding
```

## Transfer-Encoding — como o body é transmitido

`Transfer-Encoding` descreve como o body é transmitido na rede — diferente do `Content-Encoding` que descreve uma transformação semântica do conteúdo.

```
Diferença fundamental:
  Content-Encoding: transformação do CONTEÚDO
    → Compressão que está no arquivo "armazenado"
    → Se baixar, salvar e abrir: arquivo está comprimido
    
  Transfer-Encoding: transformação da TRANSMISSÃO
    → Apenas para a transferência — removido antes de salvar
    → Se salvar o body: Transfer-Encoding já foi revertido

Transfer-Encoding: chunked    ← o mais importante
Transfer-Encoding: compress   ← legado/obsoleto
Transfer-Encoding: gzip       ← compressão de transmissão (raro)
Transfer-Encoding: identity   ← sem transformação
```

### chunked — streaming sem Content-Length

`Transfer-Encoding: chunked` permite enviar o body em pedaços (chunks) quando o tamanho total não é conhecido antecipadamente. Essencial para streaming.

```
Formato de chunks:
  [tamanho do chunk em hexadecimal]\r\n
  [bytes do chunk]\r\n
  [próximo chunk...]
  0\r\n         ← chunk de tamanho 0 indica fim
  \r\n

Exemplo real de resposta chunked:

HTTP/1.1 200 OK
Content-Type: application/json
Transfer-Encoding: chunked

7\r\n         ← próximo chunk tem 7 bytes
{"id": \r\n
5\r\n         ← próximo chunk tem 5 bytes
"123"}\r\n
0\r\n         ← fim (chunk vazio)
\r\n
```

### Quando usar chunked

```
Casos de uso:
  1. Streaming de dados em tempo real:
     → Logs em tempo real
     → Resultados de uma query longa
     → Progresso de geração de relatório
  
  2. Respostas geradas dinamicamente:
     → Servidor começa a enviar antes de processar tudo
     → Reduz Time-To-First-Byte (TTFB)
  
  3. Server-Sent Events (SSE):
     → Eventos contínuos do servidor
     → Transfer-Encoding: chunked com Content-Type: text/event-stream
  
  4. Download de arquivo gerado dinamicamente:
     → Gerar PDF on-the-fly sem saber o tamanho final
```

```python
# FastAPI — streaming com Transfer-Encoding: chunked automático
from fastapi.responses import StreamingResponse
import asyncio

async def gerar_dados_streaming():
    for i in range(100):
        yield f'{{"item": {i}, "processado": true}}\n'
        await asyncio.sleep(0.1)  # simula processamento

@app.get("/dados/stream")
async def stream_dados():
    return StreamingResponse(
        gerar_dados_streaming(),
        media_type="application/x-ndjson"
        # FastAPI define Transfer-Encoding: chunked automaticamente
        # quando usa um generator (sem Content-Length definido)
    )
```

### Trailers HTTP — headers após o body

Com chunked, é possível enviar headers após o body (trailers):

```
HTTP/1.1 200 OK
Transfer-Encoding: chunked
Trailer: X-Checksum        ← anuncia que X-Checksum virá após o body

[chunks do body]
0\r\n
X-Checksum: abc123def456  ← header enviado APÓS o body completo
\r\n

Casos de uso:
  → Checksum de integridade calculado durante streaming
  → Tempo de processamento (só disponível após processar tudo)
  → Assinatura digital do conteúdo (só após gerar tudo)
```

## Interact between headers

```
Regras de combinação:

Content-Length + Transfer-Encoding: chunked
  → INVÁLIDO em HTTP/1.1 — mutuamente exclusivos
  → Se ambos estiverem presentes: Transfer-Encoding tem precedência
  → HTTP/2: não tem chunked (usa framing nativo)

Content-Encoding + Transfer-Encoding
  → VÁLIDO — podem coexistir
  → Ex: body comprimido com gzip (Content-Encoding)
        transmitido em chunks (Transfer-Encoding: chunked)
  
  Ordem de aplicação (servidor):
    1. Comprimir body (Content-Encoding: gzip)
    2. Dividir em chunks (Transfer-Encoding: chunked)
    3. Enviar
  
  Ordem de remoção (cliente):
    1. Remontar chunks (reverter Transfer-Encoding)
    2. Descomprimir (reverter Content-Encoding)
    3. Usar o conteúdo

Vary: Accept-Encoding
  → Deve estar presente quando o servidor serve versões comprimidas/não-comprimidas
  → Informa ao cache que respostas diferentes podem existir por Accept-Encoding
```

```
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8   ← o que é (tipo)
Content-Encoding: gzip                           ← como foi comprimido
Content-Length: 8140                             ← bytes na rede (após compressão)
Transfer-Encoding: chunked                       ← como está sendo transmitido
Vary: Accept-Encoding                            ← para cache (versões múltiplas)
X-Content-Type-Options: nosniff                 ← não fazer sniffing

[8140 bytes comprimidos, em chunks]

Cliente faz:
  1. Remonta chunks (Transfer-Encoding)
  2. Descomprime gzip (Content-Encoding)
  3. Parseia JSON (Content-Type: application/json)
  4. Interpreta como UTF-8 (charset=utf-8)
```

## Erros comuns e armadilhas

**Content-Length em bytes, não em caracteres:** `"café"` tem 4 caracteres mas 5 bytes em UTF-8. Sempre calcular `Content-Length` a partir de `len(body.encode("utf-8"))`, nunca de `len(texto)`.

**Content-Length incorreto em respostas comprimidas:** após habilitar compressão no nginx, o Content-Length deve refletir o tamanho comprimido. Se o servidor calcula Content-Length antes de comprimir e depois comprime, o valor será errado — causando truncamento ou padding no cliente.

**Não incluir `Vary: Accept-Encoding`:** sem esse header, um CDN pode cachear a versão gzip e servi-la para um cliente que não suporta gzip → erro de decompressão. Sempre incluir `Vary: Accept-Encoding` quando a compressão é condicional.

**Usar `Transfer-Encoding: chunked` e `Content-Length` juntos:** são mutuamente exclusivos em HTTP/1.1. A maioria dos servidores remove Content-Length ao usar chunked, mas código manual pode falhar nisso.

## 🧩 Quiz de Fixação

1. Uma resposta tem `Content-Encoding: gzip` e `Content-Length: 8140`. Após descomprimir, o body tem 48.200 bytes. Um proxy remove o `Content-Encoding: gzip` (descomprime) mas mantém `Content-Length: 8140`. O que acontece no cliente?

2. Uma API de streaming usa `Transfer-Encoding: chunked` para enviar eventos em tempo real. Um cliente que não suporta chunked (HTTP/1.0 legado) tenta receber a resposta. O que acontece e como o servidor pode lidar com isso?

3. `Content-Type: text/plain` é retornado por um servidor para um arquivo que na verdade contém HTML com `<script>`. Um browser moderno com `X-Content-Type-Options: nosniff` recebe essa resposta. O script é executado? E sem o `nosniff`?

**Respostas:**

1) O cliente recebe bytes descomprimidos (48.200 bytes) mas `Content-Length: 8140` diz "espere apenas 8140 bytes". O cliente lê 8140 bytes e acredita que a resposta terminou — os 40.060 bytes restantes ficam no buffer TCP. Em conexões persistentes (keep-alive), esses bytes excedentes são misturados com a próxima resposta → **HTTP Response Splitting** — o cliente processa dados corrompidos. Em conexões não-persistentes, os bytes são simplesmente truncados, resultando em JSON/HTML cortado no meio. O proxy deveria ou (a) descomprimir e remover `Content-Encoding: gzip` **e** atualizar `Content-Length: 48200`, ou (b) manter a compressão intacta sem alterar os headers.

2) Clientes HTTP/1.0 não entendem `Transfer-Encoding: chunked` (foi introduzido no HTTP/1.1). O cliente HTTP/1.0 receberia os bytes brutos incluindo os tamanhos dos chunks no formato hexadecimal, interpretando tudo como conteúdo — o resultado seria dados corrompidos com o "lixo" dos tamanhos de chunk. **Como o servidor pode lidar:** verificar o header da requisição — `HTTP/1.0` vs `HTTP/1.1`. Para clientes HTTP/1.0: não usar chunked, gerar o conteúdo completo antes de enviar e incluir `Content-Length`. Para clientes HTTP/1.1+: usar chunked normalmente. Na prática, clientes HTTP/1.0 puros são extremamente raros hoje — a maioria dos cenários reais envolve proxies ou ferramentas que devem suportar HTTP/1.1.

3) **Com `X-Content-Type-Options: nosniff`:** o browser **não executa** o script. O `nosniff` instrui o browser a respeitar o `Content-Type: text/plain` declarado e não tentar inferir outro tipo. O browser exibe o conteúdo como texto literal — incluindo as tags HTML e a tag `<script>` como texto visível. **Sem `nosniff`:** o browser antigo faz MIME sniffing — analisa o conteúdo, detecta padrões HTML (`<script>`, `<html>`, etc.), decide "isso é HTML!" e renderiza/executa o conteúdo. O script `<script>alert('xss')</script>` seria executado → **Cross-Site Scripting (XSS)**. Essa é exatamente a vulnerabilidade que `X-Content-Type-Options: nosniff` previne — garantir que o browser trate o conteúdo apenas como o tipo declarado, impedindo execução acidental de código.
