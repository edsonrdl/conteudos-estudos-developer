### Códigos de Status HTTP — 1xx, 2xx, 3xx, 4xx e 5xx

O código de status HTTP é a primeira informação que o servidor comunica ao cliente — ele define o resultado da requisição antes mesmo do body ser lido. Usar o código errado viola a semântica HTTP, quebra caches, confunde clientes e dificulta debugging. Este arquivo é uma referência completa de todos os códigos relevantes com o contexto exato de quando usar cada um.

---

## Estrutura da Status Line

```
HTTP/1.1 404 Not Found
│         │   │
│         │   └─ Reason Phrase (texto legível — informativo, pode ser customizado)
│         └─ Status Code (3 dígitos — a parte que importa para máquinas)
└─ Versão HTTP

Grupos por primeiro dígito:
  1xx → Informativos (requisição recebida, continua processando)
  2xx → Sucesso (requisição recebida, entendida e aceita)
  3xx → Redirecionamento (ação adicional necessária)
  4xx → Erro do cliente (requisição contém erro)
  5xx → Erro do servidor (servidor falhou em processar requisição válida)
```

---

## 1xx — Informativos

Raramente usados diretamente em APIs. O browser ou HTTP client lida automaticamente.

```
100 Continue
  → Servidor recebeu os headers da requisição e autoriza o cliente a enviar o body
  → Usado com: Expect: 100-continue (verificar se servidor aceita antes de enviar body grande)
  → Prático: cliente envia headers de autenticação primeiro; só envia o body se autorizado

101 Switching Protocols
  → Servidor aceita mudar de protocolo (conforme pedido pelo header Upgrade)
  → Uso mais comum: upgrade de HTTP para WebSocket
  
  Handshake WebSocket:
  Client → GET /chat + Upgrade: websocket
  Server → 101 Switching Protocols + Upgrade: websocket
  (a partir daí, a conexão é WebSocket, não mais HTTP)

102 Processing (WebDAV)
  → Servidor recebeu e está processando — evita timeout em operações longas
  → Raramente usado fora de WebDAV

103 Early Hints
  → Servidor envia headers de resource hints antes da resposta final
  → Permite que o browser pré-carregue recursos enquanto o servidor ainda processa
  
  HTTP/1.1 103 Early Hints
  Link: </styles.css>; rel=preload; as=style
  Link: </app.js>; rel=preload; as=script
  
  (depois, quando o HTML fica pronto:)
  HTTP/1.1 200 OK
  → Browser já começou a baixar styles.css e app.js
```

## 2xx — Sucesso

### 200 OK — o mais comum

```
200 OK
  → Requisição foi bem-sucedida
  → Body contém o resultado
  → Usado em: GET (recurso retornado), PUT (recurso atualizado), PATCH (aplicado)

GET /usuarios/123        → 200 OK + body com dados do usuário
PUT /usuarios/123        → 200 OK + body com usuário atualizado (ou 204 sem body)
POST /login              → 200 OK + body com token de autenticação
POST /busca              → 200 OK + body com resultados da busca
```

### 201 Created — recurso criado

```
201 Created
  → Requisição resultou em criação de novo recurso
  → Deve incluir Location header apontando para o novo recurso
  → Body: opcionalmente retorna o recurso criado

POST /produtos
Body: {"nome": "Notebook"}

HTTP/1.1 201 Created
Location: /produtos/456
Content-Type: application/json

{"id": 456, "nome": "Notebook", "criado_em": "2024-01-15T10:00:00Z"}

Erro comum: retornar 200 em vez de 201 para criações
  → 201 comunica explicitamente "um novo recurso foi criado"
  → Permite que o cliente saiba que um ID foi gerado
```

### 202 Accepted — aceito para processamento assíncrono

```
202 Accepted
  → Requisição foi aceita mas processamento ainda não foi concluído
  → Não implica que o processamento será concluído (pode falhar)
  → Ideal para: tarefas em background, processamento assíncrono

POST /relatorios/gerar
HTTP/1.1 202 Accepted
Location: /relatorios/jobs/789
Content-Type: application/json

{"job_id": "789", "status": "queued", "polling_url": "/relatorios/jobs/789"}

O cliente pode consultar /relatorios/jobs/789 periodicamente para saber o status
```

### 204 No Content — sucesso sem body

```
204 No Content
  → Requisição foi bem-sucedida, sem conteúdo para retornar
  → Não deve ter body (body seria ignorado pelo client)
  → Usado em: DELETE (recurso removido), PATCH (sem necessidade de retornar), 
              PUT (sem necessidade de retornar o recurso inteiro)

DELETE /produtos/123     → 204 No Content (deletado com sucesso)
PATCH /configuracoes     → 204 No Content (atualizado, sem necessidade de retornar)
PUT /cache/invalidar     → 204 No Content (ação executada)

Diferença de 200 vs 204:
  200: "sucesso, aqui estão os dados"
  204: "sucesso, não há dados para retornar"
```

### 206 Partial Content — download parcial

```
206 Partial Content
  → Servidor está retornando apenas parte do recurso (conforme pedido)
  → Gerado em resposta ao header Range: bytes=0-1023
  → Usado em: downloads resumíveis, streaming de vídeo

Requisição:
  GET /video.mp4
  Range: bytes=0-1048575  ← solicita primeiros 1 MB

Resposta:
  HTTP/1.1 206 Partial Content
  Content-Range: bytes 0-1048575/52428800  ← 0-1MB de 50MB total
  Content-Length: 1048576
  Accept-Ranges: bytes
  
  [primeiros 1 MB do vídeo]

Suporte a retomada de download:
  Download de 500 MB interrompido na metade:
  → Range: bytes=262144000-  ← retomar do byte 250 MB
  → Servidor retorna os 250 MB restantes com 206
```

## 3xx — Redirecionamentos

### 301 Moved Permanently

```
301 Moved Permanently
  → Recurso foi movido permanentemente para nova URL
  → Browsers e clientes DEVEM atualizar bookmarks/links
  → Search engines transferem "link juice" para nova URL
  → Método original pode mudar para GET no redirect (comportamento antigo de alguns browsers)

HTTP/1.1 301 Moved Permanently
Location: https://nova-url.com/recurso

Usos:
  → Migração de domínio (http://old.com → https://new.com)
  → Reestruturação de URLs (/produtos/123 → /loja/produtos/123)
  → Redirecionamento HTTP → HTTPS
```

### 302 Found (temporário)

```
302 Found
  → Recurso foi movido TEMPORARIAMENTE para outra URL
  → Browsers não atualizam bookmarks
  → Historicamente: método pode mudar para GET no redirect

HTTP/1.1 302 Found
Location: /login?redirect=/painel

Usos:
  → Redirecionamento após login
  → Redirecionamento condicional temporário
  → A/B testing (redireciona para variante temporariamente)
  
Problema histórico do 302:
  POST /formulario → 302 → GET /resultado
  Alguns browsers antigos mudavam POST para GET (correto)
  Outros não mudavam (enviavam POST para nova URL — incorreto)
  → Levou à criação do 303 e 307 para clareza
```

### 303 See Other

```
303 See Other
  → Após processar a requisição, o cliente deve buscar a resposta em outra URL
  → SEMPRE usa GET para a nova URL (independente do método original)
  → Padrão para POST/Redirect/GET (PRG)

POST /pedidos (cria pedido)
→ 303 See Other
→ Location: /pedidos/456

Client: GET /pedidos/456  (com GET — nunca reenvia o POST)
→ 200 OK + dados do pedido

Por que PRG importa:
  Sem PRG: usuário atualiza a página → reenvia o POST → cria pedido duplicado!
  Com PRG: atualizar a página apenas faz GET /pedidos/456 → sem duplicata
```

### 304 Not Modified — cache válido

```
304 Not Modified
  → Recurso não foi modificado desde a versão em cache do cliente
  → Resposta sem body (zero bytes de conteúdo)
  → O cliente usa o body da versão em cache

Requisição:
  GET /api/produtos
  If-None-Match: "abc123"

Resposta quando não mudou:
  HTTP/1.1 304 Not Modified
  ETag: "abc123"
  Cache-Control: no-cache
  (sem body — economiza banda)

Cliente: usa o body que já tem em cache
```

### 307 Temporary Redirect

```
307 Temporary Redirect
  → Redirecionamento temporário, como o 302
  → DIFERENÇA: preserva o método HTTP original (POST continua POST)
  → Cliente não deve assumir que a URL vai mudar permanentemente

POST /api/v1/produto → 307 → Location: /api/v2/produto
Cliente: POST /api/v2/produto (mantém POST)

Vs 302: alguns clientes antigos mudavam POST→GET em 302
307 garante que POST permanece POST
```

### 308 Permanent Redirect

```
308 Permanent Redirect
  → Redirecionamento permanente, como o 301
  → DIFERENÇA: preserva o método HTTP original
  → Mais recente e explícito que 301

POST /api/old/produto → 308 → Location: /api/new/produto
Cliente: POST /api/new/produto (mantém POST, permanentemente)

Resumo dos redirecionamentos:
  Temporário + muda método:  302 (legado)
  Temporário + mantém método: 307 (prefira esse)
  Permanente + muda método:  301 (para GET→GET é ok)
  Permanente + mantém método: 308 (mais preciso que 301 para não-GET)
```

## 4xx — Erros do cliente

### 400 Bad Request

```
400 Bad Request
  → A requisição é malformada ou contém dados inválidos
  → Erro de sintaxe, parâmetro obrigatório ausente, tipo errado

Quando usar:
  → JSON inválido no body
  → Campo obrigatório ausente
  → Tipo inválido (string onde era esperado número)
  → Formato inválido (data "32/01/2024")
  → Parâmetro de query inválido

Resposta bem estruturada:
HTTP/1.1 400 Bad Request
{
  "erro": "VALIDAÇÃO_FALHOU",
  "mensagem": "Dados da requisição inválidos",
  "detalhes": [
    {"campo": "email", "motivo": "formato de email inválido"},
    {"campo": "preco", "motivo": "deve ser um número positivo"}
  ]
}
```

### 401 Unauthorized — não autenticado

```
401 Unauthorized
  (nome confuso — deveria ser "Unauthenticated")
  → Requisição não autenticada — credenciais ausentes ou inválidas
  → Deve incluir WWW-Authenticate indicando como autenticar

HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="api.empresa.com"

{
  "erro": "NÃO_AUTENTICADO",
  "mensagem": "Token de autenticação ausente ou inválido"
}

Quando usar (NÃO confundir com 403):
  → Token ausente no header Authorization
  → Token expirado
  → Credenciais básicas incorretas
  → "Não sei quem você é"

401 vs 403:
  401: "Não sei quem você é" → faça login
  403: "Sei quem você é, mas não tem permissão" → acesso negado
```

### 403 Forbidden — não autorizado

```
403 Forbidden
  → Cliente autenticado, mas sem permissão para o recurso/ação
  → Não importa reautenticar — a resposta será sempre 403

HTTP/1.1 403 Forbidden
{
  "erro": "ACESSO_NEGADO",
  "mensagem": "Você não tem permissão para deletar produtos"
}

Quando usar:
  → Usuário autenticado tentando acessar recurso de outro usuário
  → Role insuficiente (usuário comum tentando acessar rota admin)
  → Recurso bloqueado por política (IP bloqueado, conta suspensa)
  → "Sei quem você é, mas não pode fazer isso"

Nota: alguns sistemas retornam 404 em vez de 403 para recursos privados
  → "Segurança por obscuridade": não revelar que o recurso existe
  → Ex: GitHub retorna 404 para repositórios privados mesmo quando autenticado
```

### 404 Not Found

```
404 Not Found
  → Recurso não encontrado no servidor
  → Não indica se o recurso existiu anteriormente ou nunca existiu

GET /produtos/999  → 404 (produto não existe)
GET /usuarios/abc  → 404 (ID formato inválido — alguns retornam 400 aqui)

Debates comuns:
  404 vs 400 para ID inválido:
    GET /produtos/abc  → 400 (ID deve ser número — erro de formato)
    GET /produtos/999  → 404 (ID válido mas produto não existe)
    
  404 vs 403 para recursos privados:
    404: não revela que o recurso existe (mais seguro)
    403: revela existência mas nega acesso (mais informativo)
```

### 405 Method Not Allowed

```
405 Method Not Allowed
  → Método HTTP não suportado pelo endpoint
  → Deve incluir Allow header com métodos suportados

DELETE /configuracoes  → o endpoint não suporta DELETE
HTTP/1.1 405 Method Not Allowed
Allow: GET, POST, PUT

Comum em:
  → Tentar DELETE em recurso imutável
  → GET em endpoint que só aceita POST
  → Endpoint de webhook que só aceita POST
```

### 409 Conflict

```
409 Conflict
  → Requisição conflita com o estado atual do recurso
  → Usado quando a request é válida mas não pode ser processada

Exemplos:
  POST /usuarios com email já cadastrado → 409 (email duplicado)
  PUT /produto/123 com ETag desatualizado → 409 ou 412
  DELETE /categoria/5 que tem produtos → 409 (violação de integridade)
  POST /transferencia (saldo insuficiente) → 409 (alguns usam 422)

HTTP/1.1 409 Conflict
{
  "erro": "CONFLITO",
  "mensagem": "Email joao@email.com já cadastrado",
  "campo": "email"
}
```

### 410 Gone

```
410 Gone
  → Recurso existiu, mas foi permanentemente removido
  → Diferente do 404: indica que não voltará

GET /noticias/2015/artigo-antigo → 410 Gone
(o artigo existia, foi deletado, nunca voltará)

vs 404:
  404: recurso não encontrado (nunca existiu OU foi deletado OU URL errada)
  410: recurso foi deletado permanentemente (definitivamente não voltará)

SEO: search engines removem 410 dos índices mais agressivamente que 404
```

### 422 Unprocessable Entity

```
422 Unprocessable Entity
  → Sintaxe correta, mas semântica inválida — lógica de negócio falhou

Diferença 400 vs 422:
  400: formato inválido (JSON malformado, campo ausente, tipo errado)
  422: formato válido, mas dados violam regras de negócio

Exemplos de 422:
  → Transferência bancária com valor maior que saldo (regra de negócio)
  → Data de nascimento no futuro (semanticamente inválida)
  → Cadastro com CPF inválido (checksum falhou, não é formato)
  → Pedido com produto sem estoque

HTTP/1.1 422 Unprocessable Entity
{
  "erro": "ENTIDADE_NÃO_PROCESSÁVEL",
  "mensagem": "CPF 123.456.789-00 é inválido (dígito verificador incorreto)"
}

Nota: há debate na comunidade sobre 400 vs 422 — o importante é ser consistente
```

### 429 Too Many Requests

```
429 Too Many Requests
  → Rate limiting: cliente excedeu o número de requisições permitidas
  → Deve incluir Retry-After indicando quando pode tentar novamente

HTTP/1.1 429 Too Many Requests
Retry-After: 60
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1705312860

{
  "erro": "MUITAS_REQUISIÇÕES",
  "mensagem": "Limite de 100 requisições/minuto excedido",
  "retry_after_seconds": 60
}

Headers de rate limit (convenção amplamente adotada):
  X-RateLimit-Limit:     total de requests permitidos no período
  X-RateLimit-Remaining: requests restantes no período atual
  X-RateLimit-Reset:     Unix timestamp de quando o limite reseta
```

## 5xx — Erros do servidor

Indício de problema no servidor — o cliente enviou uma requisição válida mas o servidor falhou.

### 500 Internal Server Error

```
500 Internal Server Error
  → Erro genérico: algo deu errado no servidor sem categoria específica
  → Não deve expor stack trace ou detalhes internos em produção

HTTP/1.1 500 Internal Server Error
{
  "erro": "ERRO_INTERNO",
  "mensagem": "Erro interno do servidor",
  "request_id": "req-abc-123"  ← para correlacionar com logs internos
}

Boas práticas:
  → Logar o stack trace internamente (com request_id)
  → Retornar apenas mensagem genérica ao cliente
  → Nunca expor: nome de tabelas, queries SQL, paths de arquivo, versões de libs
```

### 502 Bad Gateway

```
502 Bad Gateway
  → Servidor atuando como gateway/proxy recebeu resposta inválida do upstream

Cenário típico:
  Browser → Nginx → App Server
  App Server retorna resposta malformada ou está travado
  Nginx não consegue processar → 502 para o browser

Outros cenários:
  → Load balancer não consegue conectar ao backend
  → Resposta do upstream veio corrompida
  → Backend reiniciando durante deploy
```

### 503 Service Unavailable

```
503 Service Unavailable
  → Servidor temporariamente indisponível
  → Manutenção planejada ou sobrecarga temporária
  → Deve incluir Retry-After quando possível

HTTP/1.1 503 Service Unavailable
Retry-After: 3600
{
  "erro": "SERVIÇO_INDISPONÍVEL",
  "mensagem": "Manutenção programada das 02:00 às 04:00",
  "retry_after": "2024-01-16T04:00:00Z"
}

Diferença 500 vs 503:
  500: algo quebrou (inesperado)
  503: serviço deliberadamente indisponível (manutenção, sobrecarga)
```

### 504 Gateway Timeout

```
504 Gateway Timeout
  → Gateway/proxy não recebeu resposta do upstream a tempo

Cenário:
  Browser → Nginx (timeout: 30s) → App Server
  App Server demorou mais de 30s → Nginx retorna 504

Causas comuns:
  → Query lenta no banco de dados
  → Chamada a serviço externo lenta
  → Deadlock no processamento
  → Recursos esgotados (CPU, memória)

504 vs 503:
  503: servidor indisponível (não está rodando)
  504: servidor rodando, mas resposta demorou demais (timeout)
```

## 🧩 Quiz de Fixação

1. Uma API de e-commerce recebe `POST /pedidos` com dados válidos, mas o usuário não tem saldo suficiente. Qual status code retornar — 400, 409 ou 422 — e justifique?

2. Um endpoint `GET /usuarios/123` existe e o usuário 123 existe, mas o cliente autenticado não tem permissão para ver dados de outros usuários. Qual status retornar: 403 ou 404? Há um caso legítimo para usar 404 aqui?

3. `DELETE /produtos/50` é executado com sucesso. O mesmo cliente faz `DELETE /produtos/50` novamente. Qual status code deve ser retornado na segunda chamada: 204 ou 404? Ambos são aceitáveis?

**Respostas:**

1) **422 Unprocessable Entity** é o mais semanticamente correto. O body da requisição está bem-formado (JSON válido, todos os campos obrigatórios presentes, tipos corretos) — não é um 400. O problema é uma regra de negócio: "saldo insuficiente para essa transação". O servidor entende a requisição completamente mas não pode processá-la porque viola uma restrição de domínio. 409 seria aceitável se entendido como "conflito com o estado atual da conta" (saldo = estado), mas 422 é mais preciso para falhas de validação de lógica de negócio. Alguns times usam 400 para tudo que o servidor rejeita — o importante é ser consistente e documentar.

2) **Depende da política de segurança da aplicação:** (a) **403 Forbidden** — semanticamente correto: o cliente está autenticado, o recurso existe, mas o acesso é negado. Comunica claramente "você não tem permissão". (b) **404 Not Found** — técnica de "security by obscurity": não revelar que o recurso existe evita que um atacante enumere IDs válidos ("se retorna 403, o usuário 123 existe"). GitHub faz isso com repositórios privados: retorna 404 mesmo para repos que existem mas o usuário não tem acesso. **Qual usar:** para APIs públicas com dados sensíveis (endereços, dados pessoais de outros usuários), 404 é defensivamente melhor. Para APIs internas ou admin panels onde a existência do recurso não é informação sensível, 403 é mais informativo.

3) **Ambos são aceitáveis**, e há argumentos para cada um. **204 (recomendado por idempotência):** DELETE é idempotente — o estado final (produto 50 não existe) é o mesmo independente de quantas vezes foi chamado. Retornar 204 no segundo DELETE é correto semanticamente: "a operação de deletar foi processada e o resultado desejado foi atingido". **404 (também aceitável):** o produto não existe mais — uma busca retornaria 404, então o DELETE também pode retornar 404 para consistência. **Na prática:** a RFC HTTP diz que DELETE idempotente deve resultar no mesmo estado final, mas o código de resposta pode variar. Muitas APIs retornam 404 no segundo DELETE — o cliente deve tratar isso como sucesso (o produto não existe = objetivo alcançado). Para clientes que fazem retry de DELETE, 204 no segundo chamado é mais seguro para evitar tratamento incorreto do 404 como erro.
