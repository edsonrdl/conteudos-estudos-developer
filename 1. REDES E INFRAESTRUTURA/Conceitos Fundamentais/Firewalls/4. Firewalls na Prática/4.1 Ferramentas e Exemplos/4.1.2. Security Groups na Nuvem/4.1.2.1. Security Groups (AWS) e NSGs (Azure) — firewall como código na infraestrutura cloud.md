### Security Groups (AWS) e NSGs (Azure) — firewall na nuvem

Security Groups e Network Security Groups são a implementação de firewall nos principais provedores cloud. São stateful, gerenciados pelo provedor e configuráveis como código — parte fundamental do modelo de segurança em nuvem.

---

## Security Groups — AWS

Associado a instâncias EC2, Load Balancers, RDS e outros recursos. Age como firewall virtual no nível do recurso.

### Características

- **Stateful:** respostas a conexões permitidas são automaticamente autorizadas.
- **Default deny:** sem regra de entrada = nada entra; sem regra de saída = tudo sai (padrão).
- **Whitelist only:** só permite — não tem regras de DENY explícito.
- **Múltiplos por instância:** uma EC2 pode ter vários Security Groups simultaneamente.

### Exemplo de configuração

```hcl
# Terraform — Security Group para servidor web
resource "aws_security_group" "web" {
  name = "web-server-sg"

  ingress {
    from_port   = 443
    to_port     = 443
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]  # HTTPS público
  }

  ingress {
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = ["203.0.113.0/32"]  # SSH só do IP do admin
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]  # saída liberada
  }
}
```

## NSG — Network Security Groups (Azure)

Similar ao Security Group, mas pode ser associado a **subnets** ou **interfaces de rede** individualmente.

```
NSG tem regras com prioridade numérica (100–4096):
  Prioridade 100: ALLOW  TCP  *  :443  (menor número = maior prioridade)
  Prioridade 200: ALLOW  TCP  203.0.113.0/32  :22
  Prioridade 4096: DENY  *   *   *  (regra padrão implícita)
```

---

## Security Group vs NACL (AWS)

| | Security Group | Network ACL |
|---|---|---|
| Nível | Instância/recurso | Subnet inteira |
| Estado | Stateful | Stateless |
| Regras | Só ALLOW | ALLOW e DENY |
| Avaliação | Todas as regras | Em ordem (1ª que bater) |
| Uso | Controle granular por recurso | Bloqueio em nível de subnet |

## Firewall como Código

Tanto Security Groups quanto NSGs são recursos de infraestrutura — devem ser gerenciados com IaC:

```
Benefícios:
  ├── Versionamento (git) das regras de firewall
  ├── Code review de mudanças de segurança
  ├── Ambientes idênticos (dev/staging/prod)
  └── Auditoria: quem mudou o quê e quando
```

Ferramentas: Terraform, AWS CloudFormation, Pulumi, Bicep (Azure).

## 🧩 Quiz de Fixação

1. Por que Security Groups são stateful mas NACLs (AWS) são stateless?
2. Uma EC2 tem Security Group que permite entrada na 443. A saída está bloqueada. A instância consegue responder às requisições HTTPS?
3. Qual a vantagem de gerenciar Security Groups com Terraform em vez de pela console AWS?

**Respostas:**
1) São implementações diferentes: Security Groups rastreiam estado de conexão (retorno automático); NACLs processam cada pacote independentemente — precisam de regras de entrada e saída explícitas.
2) Sim — Security Groups são stateful. A resposta a uma conexão de entrada permitida é automaticamente autorizada, independente das regras de saída.
3) As regras ficam no controle de versão (git), possibilitando histórico de mudanças, code review, rollback e garantia de consistência entre ambientes — eliminando configurações manuais não rastreadas.
