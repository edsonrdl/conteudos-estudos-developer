### Terminação SSL no proxy e mTLS

A terminação SSL (SSL termination) e o mTLS (mutual TLS) são dois padrões complementares de segurança gerenciados no reverse proxy. O primeiro centraliza a criptografia; o segundo adiciona autenticação bidirecional.

---

## SSL Termination — terminação no proxy

O reverse proxy decifra o HTTPS e encaminha o tráfego internamente (HTTP ou HTTPS re-cifrado):

```
                    ┌─────────────────────────────────┐
                    │        Rede interna              │
Cliente ──HTTPS──► [Proxy]  ──HTTP──►  Backend A       │
   443 ssl          │        ──HTTP──►  Backend B       │
                    │        ──HTTP──►  Backend C       │
                    └─────────────────────────────────┘
                         ↑
            TLS termina aqui — tráfego interno
            em HTTP (rede privada, considerada segura)
```

**Vantagens:**
- Certificados gerenciados em **um único ponto**.
- Backends sem overhead de CPU com criptografia.
- Renovação de certificados sem tocar nos servidores.

**Re-encryption (SSL passthrough vs re-encrypt):**

| Modo | Comportamento |
|---|---|
| **Passthrough** | Proxy não decifra — encaminha TLS opaco ao backend |
| **Termination** | Proxy decifra → HTTP interno |
| **Re-encryption** | Proxy decifra → novo TLS até o backend |

Re-encryption é usada quando a rede interna também precisa ser cifrada (compliance, zero trust).

---

## mTLS — Mutual TLS (autenticação mútua)

No TLS padrão, apenas o **servidor** apresenta certificado (o cliente verifica o servidor). No mTLS, **ambos** apresentam certificados:

```
TLS padrão:
  Cliente verifica: "este é mesmo o servidor legítimo?" → sim → conecta
  Servidor não verifica o cliente → qualquer um pode conectar

mTLS:
  Cliente verifica o servidor ✓
  Servidor verifica o cliente ✓
  Se o cliente não tiver certificado válido → conexão recusada
```

---

## mTLS no reverse proxy — casos de uso

### API entre serviços (service mesh)

```
Serviço A ──mTLS──► Proxy Sidecar A ══mTLS══ Proxy Sidecar B ──mTLS──► Serviço B
```

Em arquiteturas com Istio/Envoy, cada serviço tem um sidecar proxy que faz mTLS automaticamente — garantindo que apenas serviços autorizados se comuniquem.

### API corporativa (B2B)

```
Parceiro Externo (com cert. emitido pela nossa CA)
        │
     ──mTLS──► [Reverse Proxy / API Gateway]
                     │
                  valida o certificado do cliente
                  roteia para backend se válido
```

## Configuração mTLS no Nginx

```nginx
server {
    listen 443 ssl;
    server_name api.empresa.com;

    ssl_certificate      /etc/ssl/server.crt;
    ssl_certificate_key  /etc/ssl/server.key;

    # mTLS — exige certificado do cliente
    ssl_client_certificate /etc/ssl/ca.crt;   # CA que assinou certs dos clientes
    ssl_verify_client on;                      # rejeita sem certificado válido
    ssl_verify_depth 2;

    location / {
        proxy_pass http://backend;
        proxy_set_header X-Client-Cert $ssl_client_escaped_cert;
        proxy_set_header X-Client-DN   $ssl_client_s_dn;
    }
}
```

## 🧩 Quiz de Fixação

1. Qual a diferença entre SSL passthrough e SSL termination no reverse proxy?
2. O que o mTLS adiciona em relação ao TLS padrão?
3. Por que service meshes como Istio usam mTLS entre todos os serviços?

**Respostas:**
1) No passthrough, o proxy encaminha o TLS sem decifrar — o backend gerencia o certificado. Na termination, o proxy decifra e encaminha HTTP (ou re-cifra) — centralizando o gerenciamento de certificados.
2) Autenticação bidirecional — além do cliente verificar o servidor (TLS padrão), o servidor também verifica o cliente via certificado. Apenas clientes com certificado válido emitido pela CA confiável conseguem conectar.
3) Para garantir identidade de todos os serviços — sem mTLS, qualquer processo na rede interna poderia se comunicar com qualquer serviço. Com mTLS, cada serviço precisa de certificado válido, implementando zero trust na comunicação interna.
