### Proxy transparente vs explícito

A diferença entre proxy transparente e explícito está em **quem sabe que o proxy existe**. No explícito, o cliente é configurado para usá-lo. No transparente, o tráfego é interceptado sem que o cliente precise de qualquer configuração.

---

## Proxy Explícito (ou Tradicional)

O cliente é configurado manualmente para enviar requisições ao proxy:

```
Configuração no navegador:
  Proxy HTTP: 192.168.1.100
  Porta: 3128

Fluxo:
  Cliente ──CONNECT 192.168.1.100:3128──► Proxy
  Proxy ──────────────────────────────► Destino
```

**Características:**
- Cliente sabe que o proxy existe.
- Pode ser configurado por GPO (Windows), MDM ou manualmente.
- Aplicações que não suportam proxy o ignoram (bypass).
- Fácil de contornar (usuário desabilita nas configurações).

**Quando usar:** ambientes corporativos onde todos os dispositivos são gerenciados.

---

## Proxy Transparente (Intercepting Proxy)

O tráfego é redirecionado para o proxy por regras de rede (iptables, roteador) sem qualquer configuração no cliente:

```
Fluxo normal que o cliente "acha" que faz:
  Cliente ──────────────────────────────► google.com

O que realmente acontece:
  Cliente ──► [Roteador redireciona porta 80/443] ──► Proxy ──► google.com
```

**Como é implementado:**
```bash
# iptables redireciona todo HTTP para o proxy (porta 3128)
iptables -t nat -A PREROUTING -p tcp --dport 80 -j REDIRECT --to-port 3128
```

**Características:**
- Cliente não precisa ser configurado — funciona em qualquer dispositivo.
- Impossível de contornar sem acesso às configurações de rede.
- Para HTTPS: requer SSL inspection (instalar CA no cliente) ou apenas ver o SNI sem decifrar.
- Ideal para redes de convidados, hotéis, aeroportos.

---

## Comparativo

| Aspecto | Proxy Explícito | Proxy Transparente |
|---|---|---|
| Configuração no cliente | Necessária | Não necessária |
| O cliente sabe? | Sim | Não |
| Pode ser contornado? | Sim (desabilita nas configs) | Não (nível de rede) |
| HTTPS inspection | Mais simples | Requer CA instalada ou SNI apenas |
| Funciona com qualquer app | Não (app precisa suportar proxy) | Sim |

---

## HTTPS no proxy transparente — o problema

HTTPS cifra o conteúdo **e** oculta a URL (só o domínio via SNI fica visível). Para inspecionar:

```
Opção 1 — Apenas SNI (sem decifrar):
  Proxy vê: destino = google.com
  Proxy não vê: qual URL exata, qual conteúdo

Opção 2 — SSL Inspection (MITM legítimo):
  CA do proxy instalada nos clientes
  Proxy decifra, inspeciona, re-cifra
  Proxy vê tudo — mas é intrusivo
```

## 🧩 Quiz de Fixação

1. Por que um proxy transparente é mais difícil de contornar que um explícito?
2. O que é SNI e por que é relevante para proxies transparentes com HTTPS?
3. Em qual cenário faz sentido usar proxy explícito em vez de transparente?

**Respostas:**
1) O redirecionamento acontece no nível da rede (roteador/firewall) — o cliente não tem configuração para desabilitar.
2) SNI (Server Name Indication) é a extensão do TLS que expõe o domínio destino mesmo em conexões cifradas — o proxy transparente consegue ver o destino (mas não o conteúdo) sem decifrar o HTTPS.
3) Quando os dispositivos são todos gerenciados pela empresa e se quer que as aplicações saibam que estão usando proxy (autenticação, configurações específicas por app).
