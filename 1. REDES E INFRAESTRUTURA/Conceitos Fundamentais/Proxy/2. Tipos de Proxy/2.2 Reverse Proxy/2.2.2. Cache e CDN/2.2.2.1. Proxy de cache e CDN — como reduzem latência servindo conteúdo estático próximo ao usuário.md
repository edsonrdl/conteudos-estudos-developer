### Proxy de cache e CDN — latência e distribuição de conteúdo

O proxy de cache armazena respostas para reutilização — evitando requisições repetidas ao servidor de origem. A CDN leva esse conceito ao extremo, distribuindo o cache em servidores geograficamente próximos aos usuários.

---

## Como o cache de proxy funciona

```
1ª requisição (cache miss):
  Cliente ──► Proxy Cache ──► Servidor de Origem
                  ↑
         Armazena a resposta

2ª requisição (cache hit):
  Cliente ──► Proxy Cache ──► responde do cache (sem ir ao servidor)
```

**O que é armazenado:** imagens, CSS, JS, vídeos, respostas de API — qualquer conteúdo com headers de cache adequados.

---

## Headers HTTP que controlam o cache

| Header | Função | Exemplo |
|---|---|---|
| `Cache-Control` | Define política de cache | `max-age=3600`, `no-cache`, `private` |
| `ETag` | Identificador único da versão do recurso | `"abc123"` |
| `Last-Modified` | Data da última modificação | `Wed, 01 Jan 2025 00:00:00 GMT` |
| `Expires` | Data de expiração absoluta | `Thu, 02 Jan 2025 00:00:00 GMT` |

```
Cache-Control: public, max-age=86400   → pode ser cacheado por 24h
Cache-Control: private, no-store       → não cache (dados do usuário)
Cache-Control: no-cache                → revalida sempre antes de usar
```

---

## CDN — Content Delivery Network

A CDN é uma rede de reverse proxies com cache distribuídos geograficamente (PoPs — Points of Presence):

```
Servidor de Origem (São Paulo)
        │
   CDN distribui para:
   ├── PoP São Paulo    ← usuário BR acessa daqui (~5ms)
   ├── PoP Nova York    ← usuário EUA acessa daqui (~10ms)
   ├── PoP Frankfurt    ← usuário EU acessa daqui (~8ms)
   └── PoP Tóquio       ← usuário JP acessa daqui (~6ms)

Sem CDN: usuário JP acessa São Paulo (~250ms)
Com CDN: usuário JP acessa Tóquio (~6ms)
```

---

## O que a CDN faz além de cache

| Função | Benefício |
|---|---|
| **Proximidade geográfica** | Reduz latência drasticamente |
| **Absorção de DDoS** | Distribui o ataque por toda a rede CDN |
| **Compressão** | Gzip/Brotli automático |
| **HTTP/2 e HTTP/3** | Edge otimizado mesmo que o origin seja HTTP/1.1 |
| **WAF integrado** | Cloudflare, Akamai oferecem WAF no edge |
| **Failover** | Se o origin cair, CDN serve do cache |

---

## Cache hit ratio — a métrica-chave

```
Hit ratio = requisições servidas do cache / total de requisições

Hit ratio de 90%:
  Apenas 10% dos requests chegam ao servidor de origem
  → 90% de redução de carga no backend
  → 90% das respostas com latência de edge (muito menor)
```

## 🧩 Quiz de Fixação

1. O que é cache hit ratio e por que é importante?
2. Por que conteúdo com `Cache-Control: private` não deve ser armazenado por CDNs?
3. Além de reduzir latência, qual outra vantagem significativa as CDNs oferecem?

**Respostas:**
1) É a proporção de requisições respondidas diretamente do cache — quanto maior, menor a carga no servidor de origem e menor a latência para os usuários.
2) `private` indica que o conteúdo é específico de um usuário (ex: dados de conta) — cacheá-lo na CDN compartilharia dados privados com outros usuários que fizessem a mesma requisição.
3) Proteção contra DDoS — ao distribuir o tráfego por centenas de PoPs ao redor do mundo, ataques volumétricos são absorvidos pela rede CDN sem atingir o servidor de origem.
