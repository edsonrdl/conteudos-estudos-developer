### Reverse proxy como load balancer, terminação SSL e API Gateway

O reverse proxy é a peça central de infraestrutura moderna. Além de simplesmente encaminhar requisições, centraliza funções críticas que seriam complexas e redundantes se implementadas em cada servidor individualmente.

---

## Load Balancing — distribuição de carga

O reverse proxy distribui requisições entre múltiplos servidores backend:

```
                    ┌──► Servidor A (192.168.1.10)
Internet ──► Nginx ─┼──► Servidor B (192.168.1.11)
                    └──► Servidor C (192.168.1.12)
```

### Algoritmos de balanceamento

| Algoritmo | Como funciona | Melhor para |
|---|---|---|
| **Round Robin** | Rotaciona entre servidores em ordem | Servidores homogêneos |
| **Least Connections** | Envia para o servidor com menos conexões ativas | Requisições de duração variável |
| **IP Hash** | Mesmo cliente sempre vai ao mesmo servidor | Sessões com estado (sticky sessions) |
| **Weighted** | Servidores com mais capacidade recebem mais tráfego | Servidores heterogêneos |

---

## Terminação SSL/TLS

O reverse proxy decifra HTTPS e encaminha HTTP (ou HTTPS re-cifrado) para os backends:

```
Cliente ──HTTPS──► [Reverse Proxy] ──HTTP──► Servidores backend
                        ↑
                  Gerencia todos os certificados TLS
                  Uma renovação → todos protegidos
```

**Vantagens:**
- Certificados gerenciados em um único ponto.
- Servidores backend não precisam lidar com criptografia (reduz CPU).
- Renovação automática centralizada (ex: Certbot + Nginx).

---

## API Gateway — reverse proxy inteligente

O API Gateway é um reverse proxy com funcionalidades adicionais para APIs:

```
Internet ──► [API Gateway] ──► /users    → Serviço Users
                           ──► /orders   → Serviço Orders
                           ──► /products → Serviço Products
```

**Funcionalidades típicas:**

| Função | Descrição |
|---|---|
| **Roteamento** | Direciona por path, host, método HTTP |
| **Autenticação** | Valida JWT, API keys antes de encaminhar |
| **Rate limiting** | Limita requisições por cliente/IP |
| **Transformação** | Modifica headers, body da requisição/resposta |
| **Observabilidade** | Logs, métricas, tracing centralizados |

Exemplos: Kong, AWS API Gateway, Nginx, Traefik, Envoy.

## Configuração Nginx — exemplo real

```nginx
upstream backend {
    least_conn;                    # algoritmo least connections
    server 192.168.1.10:8080;
    server 192.168.1.11:8080;
    server 192.168.1.12:8080 weight=2;  # recebe o dobro de tráfego
}

server {
    listen 443 ssl;
    server_name api.empresa.com;

    ssl_certificate     /etc/ssl/empresa.crt;
    ssl_certificate_key /etc/ssl/empresa.key;

    location / {
        proxy_pass http://upstream_backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

## 🧩 Quiz de Fixação

1. Por que o algoritmo IP Hash é útil para aplicações com sessões?
2. Qual a vantagem de fazer terminação SSL no reverse proxy em vez de em cada servidor backend?
3. O que diferencia um API Gateway de um reverse proxy simples?

**Respostas:**
1) Garante que o mesmo cliente sempre chegue ao mesmo servidor backend — necessário quando a sessão do usuário está armazenada localmente no servidor (sem sessão distribuída).
2) Centraliza o gerenciamento de certificados em um único ponto — renovação, configuração de cipher suites e atualizações de segurança TLS são feitas uma vez para todos os backends.
3) O API Gateway adiciona autenticação, rate limiting, transformação de requests/responses e observabilidade — o reverse proxy simples apenas encaminha e balanceia, sem lógica de negócio sobre as requisições.
