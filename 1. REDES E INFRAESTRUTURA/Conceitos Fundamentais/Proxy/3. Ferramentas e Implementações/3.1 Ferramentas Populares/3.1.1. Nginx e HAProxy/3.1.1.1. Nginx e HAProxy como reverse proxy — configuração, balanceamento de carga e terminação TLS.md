### Nginx e HAProxy como reverse proxy

Nginx e HAProxy são as duas ferramentas open source mais usadas como reverse proxy em produção. Cada uma tem pontos fortes distintos e casos de uso ideais.

---

## Nginx

Servidor web e reverse proxy de alta performance. Excelente para servir conteúdo estático e proxy de aplicações HTTP.

### Configuração como reverse proxy

```nginx
# /etc/nginx/conf.d/app.conf

upstream app_servers {
    server 10.0.0.1:3000;
    server 10.0.0.2:3000;
    server 10.0.0.3:3000;
    keepalive 32;              # conexões persistentes com backend
}

server {
    listen 80;
    server_name app.empresa.com;
    return 301 https://$host$request_uri;   # força HTTPS
}

server {
    listen 443 ssl http2;
    server_name app.empresa.com;

    ssl_certificate     /etc/letsencrypt/live/app.empresa.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/app.empresa.com/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;

    location / {
        proxy_pass         http://app_servers;
        proxy_http_version 1.1;
        proxy_set_header   Upgrade $http_upgrade;
        proxy_set_header   Connection keep-alive;
        proxy_set_header   Host $host;
        proxy_set_header   X-Real-IP $remote_addr;
        proxy_set_header   X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
    }

    location /static/ {
        root /var/www;          # serve estático direto — sem ir ao backend
        expires 30d;
        add_header Cache-Control "public, immutable";
    }
}
```

## HAProxy

Focado exclusivamente em proxy e load balancing — não serve arquivos estáticos. Extremamente eficiente para TCP e HTTP, com health checks avançados.

```
# /etc/haproxy/haproxy.cfg

frontend http_front
    bind *:80
    redirect scheme https code 301 if !{ ssl_fc }

frontend https_front
    bind *:443 ssl crt /etc/ssl/empresa.pem
    default_backend app_back

backend app_back
    balance leastconn
    option httpchk GET /health    # health check no endpoint /health
    server app1 10.0.0.1:3000 check inter 2s rise 2 fall 3
    server app2 10.0.0.2:3000 check inter 2s rise 2 fall 3
    server app3 10.0.0.3:3000 check inter 2s rise 2 fall 3 backup
```

## Nginx vs HAProxy

| Aspecto | Nginx | HAProxy |
|---|---|---|
| Conteúdo estático | Excelente (nativo) | Não faz |
| Load balancing HTTP | Muito bom | Excelente |
| Load balancing TCP | Bom (stream module) | Excelente |
| Health checks | Básico (versão free) | Avançado (nativo) |
| Dashboard de status | Limitado | HAProxy Stats page |
| Websockets | Suporte nativo | Suporte nativo |
| Configuração | Flexível | Muito clara |

---

## Quando usar cada um

| Cenário | Escolha |
|---|---|
| Servidor web + reverse proxy + cache | Nginx |
| Load balancer puro de alta performance | HAProxy |
| Proxy TCP (banco de dados, etc.) | HAProxy |
| Muita mistura de conteúdo estático e dinâmico | Nginx |
| Visibilidade de health e stats em tempo real | HAProxy |

## 🧩 Quiz de Fixação

1. Por que o header `X-Forwarded-For` é importante ao usar Nginx como reverse proxy?
2. O que o parâmetro `fall 3` faz na configuração do HAProxy?
3. Em qual cenário seria melhor usar HAProxy em vez de Nginx como load balancer?

**Respostas:**
1) O backend recebe o IP do Nginx, não do cliente real. `X-Forwarded-For` preserva o IP original do cliente — essencial para logs, rate limiting e geolocalização.
2) Marca o servidor como DOWN (fora de rotação) após 3 health checks consecutivos falhando — o HAProxy para de enviar tráfego para aquele servidor.
3) Quando se precisa de load balancing TCP (ex.: banco de dados, Redis, SMTP) ou quando health checks avançados e visibilidade em tempo real (stats page) são prioritários.
