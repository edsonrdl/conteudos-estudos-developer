### TCP — Transmission Control Protocol

O TCP é um protocolo **orientado à conexão**: antes de transmitir qualquer dado, os dois lados precisam se sincronizar. Isso garante entrega completa, em ordem e sem duplicatas — ao custo de um overhead de controle maior que o UDP.

---

## Características do TCP

| Característica | Descrição |
| -------------- | --------- |
| Orientado à conexão | Handshake obrigatório antes de transmitir |
| Entrega garantida | Retransmite pacotes perdidos automaticamente |
| Ordenação | Reordena pacotes que chegam fora de sequência |
| Controle de fluxo | Ajusta velocidade de envio à capacidade do receptor |
| Controle de congestionamento | Evita saturar a rede com tráfego excessivo |
| Full-duplex | Comunicação bidirecional simultânea |

---

## Three-Way Handshake — Estabelecimento de Conexão

O TCP usa 3 passos para sincronizar os dois lados antes de qualquer dado ser enviado:

```
Cliente                    Servidor
   |   — SYN (seq=x) —>      |   "Quero me conectar, meu seq inicial é X"
   |   <— SYN-ACK (seq=y, ack=x+1) —   |   "Ok, meu seq é Y, confirmo o teu X"
   |   — ACK (ack=y+1) —>    |   "Confirmado, iniciando"
   |        CONECTADO         |
```

**Por que 3 passos e não 2?**  
Com apenas 2 passos, o cliente não confirmaria que recebeu o SYN-ACK do servidor. O 3º passo (ACK final) garante que **ambos os lados** confirmaram a sincronização — evitando conexões fantasma onde um lado acha que está conectado e o outro não.

**Campos sincronizados no handshake:**
- **Sequence Number (ISN):** número inicial aleatório de cada lado — evita confusão com conexões antigas
- **Window Size:** capacidade do buffer de cada lado — define o controle de fluxo
- **MSS (Maximum Segment Size):** tamanho máximo de segmento que cada lado aceita

---

## Four-Way Handshake — Encerramento de Conexão

O encerramento requer 4 passos porque cada direção é encerrada **independentemente**:

```
Cliente                    Servidor
   |   — FIN —>               |   "Terminei de enviar"
   |   <— ACK —               |   "Recebi, mas ainda posso enviar"
   |   <— FIN —               |   "Terminei de enviar também"
   |   — ACK —>               |   "Confirmado"
   |        FECHADO           |
```

O cliente entra em estado **TIME_WAIT** por 2×MSL (Maximum Segment Lifetime, ~60s) antes de fechar definitivamente — garantindo que qualquer ACK atrasado ainda em trânsito seja absorvido.

---

## Controle de Fluxo — Sliding Window

O TCP não espera confirmação de cada pacote individualmente. Ele usa uma **janela deslizante** que define quantos bytes podem estar "em voo" ao mesmo tempo:

```
Receptor anuncia window size = 8000 bytes
Remetente pode enviar até 8000 bytes sem ACK

Após ACK de 4000 bytes:
→ Janela desliza: mais 4000 bytes podem ser enviados
```

Se o receptor ficar sem buffer, anuncia `window size = 0` — o remetente para de enviar e aguarda um **Window Update**.

---

## Controle de Congestionamento

Quando há perda de pacotes (indicador de congestionamento na rede), o TCP reage:

| Algoritmo | O que faz |
| --------- | --------- |
| **Slow Start** | Começa com janela pequena e dobra a cada RTT até atingir o limiar |
| **Congestion Avoidance** | Após o limiar, cresce linearmente (1 MSS por RTT) |
| **Fast Retransmit** | Ao receber 3 ACKs duplicados, retransmite imediatamente sem esperar timeout |
| **Fast Recovery** | Reduz a janela pela metade (não reinicia do zero) após perda detectada por duplicatas |

**Algoritmos modernos:** CUBIC (padrão Linux), BBR (Google — baseado em largura de banda medida).

---

## Quando usar TCP

- Transferência de arquivos (FTP, SFTP, S3)
- Navegação web (HTTP/HTTPS)
- Acesso remoto (SSH)
- Bancos de dados (MySQL, PostgreSQL, Redis)
- Email (SMTP, IMAP, POP3)
- Qualquer dado que **não pode ser perdido**
