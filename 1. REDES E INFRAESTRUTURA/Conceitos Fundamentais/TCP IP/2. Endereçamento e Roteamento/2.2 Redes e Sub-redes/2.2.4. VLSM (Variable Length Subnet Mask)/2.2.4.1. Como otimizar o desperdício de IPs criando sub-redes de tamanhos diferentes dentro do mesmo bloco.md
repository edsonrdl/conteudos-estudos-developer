### VLSM — Variable Length Subnet Mask

Até aqui, o subnetting criava sub-redes do **mesmo tamanho** (FLSM — Fixed Length). O problema: diferentes partes da rede têm necessidades completamente diferentes de hosts.

- Uma LAN com 50 servidores precisa de `/26` (62 hosts)
- Um link ponto-a-ponto entre roteadores precisa de apenas 2 hosts → `/30`

Com FLSM, você usaria `/26` para tudo — desperdiçando 60 endereços em cada link. O **VLSM** resolve isso permitindo criar sub-redes de **tamanhos diferentes** dentro do mesmo bloco.

**Analogia:** cortar um bolo em fatias de tamanhos diferentes conforme a fome de cada pessoa — em vez de fatias iguais que sobram para uns e faltam para outros.

---

## Regra de ouro do VLSM

> Sempre aloque a **maior sub-rede primeiro**, depois as menores — do maior para o menor.

Isso evita sobreposição de blocos e garante que os endereços maiores fiquem em posições naturalmente alinhadas.

---

## Exemplo Prático — Rede `200.1.1.0/24`

**Requisitos:**
| Segmento | Hosts necessários |
| -------- | ----------------- |
| Loja NY | 28 hosts |
| Loja LA | 12 hosts |
| Link Roteador 1–2 | 2 hosts |
| Link Roteador 2–3 | 2 hosts |

**Alocação (maior → menor):**

**1. Loja NY — 28 hosts → `/27` (30 hosts úteis)**
- Rede: `200.1.1.0/27`
- Hosts: `200.1.1.1` a `200.1.1.30`
- Broadcast: `200.1.1.31`

**2. Loja LA — 12 hosts → `/28` (14 hosts úteis)**
- Rede: `200.1.1.32/28`
- Hosts: `200.1.1.33` a `200.1.1.46`
- Broadcast: `200.1.1.47`

**3. Link R1–R2 — 2 hosts → `/30` (2 hosts úteis)**
- Rede: `200.1.1.48/30`
- Hosts: `200.1.1.49` e `200.1.1.50`
- Broadcast: `200.1.1.51`

**4. Link R2–R3 — 2 hosts → `/30`**
- Rede: `200.1.1.52/30`
- Hosts: `200.1.1.53` e `200.1.1.54`
- Broadcast: `200.1.1.55`

**Espaço usado:** `.0` a `.55` (56 endereços)  
**Espaço livre:** `.56` a `.255` (200 endereços para crescimento futuro)

---

## Comparação — FLSM vs VLSM

| Critério | FLSM | VLSM |
| -------- | ---- | ---- |
| Tamanho das sub-redes | Igual para todas | Variável por necessidade |
| Desperdício de IPs | Alto (especialmente em links P2P) | Mínimo |
| Complexidade de planejamento | Simples | Requer ordenação cuidadosa |
| Uso atual | Raramente usado | Padrão na indústria |

## VLSM na Cloud — impacto no Kubernetes

Na AWS e Azure, cada sub-rede perde 5 IPs (não 2) para serviços da plataforma. Em clusters Kubernetes onde **cada Pod consome um IP real da sub-rede**:

- Uma `/28` (16 IPs totais) entrega apenas **11 IPs utilizáveis** após os 5 reservados
- Com 2 nodes, restam apenas 9 IPs para Pods — limitando o autoscaling

**Regra prática para cloud:** use blocos maiores (`/24` ou `/22`) nos segmentos de workload para garantir escala. Aplique sub-redes menores apenas em segmentos de infraestrutura com crescimento previsível.
