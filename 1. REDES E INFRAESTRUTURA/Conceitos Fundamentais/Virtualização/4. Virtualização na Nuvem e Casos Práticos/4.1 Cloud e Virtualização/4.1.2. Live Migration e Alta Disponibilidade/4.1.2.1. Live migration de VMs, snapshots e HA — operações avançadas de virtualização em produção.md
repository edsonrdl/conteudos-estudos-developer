### Live migration, snapshots e HA — operações avançadas em produção

As operações avançadas de virtualização são o que tornam a infraestrutura resiliente e operável sem janelas de manutenção. Live migration, snapshots e HA são pilares do modelo de uptime moderno.

---

## Live Migration — mover VMs sem downtime

A live migration transfere uma VM em execução de um host físico para outro, sem interromper o serviço.

```
Host A (sobrecarga)          Host B (com capacidade)
  └── VM (rodando)  ──────►  └── VM (rodando)
                   migração
                   sem parar

Do ponto de vista da aplicação: nada aconteceu.
Do ponto de vista da rede: IP permanece o mesmo.
```

### Como funciona (simplificado)

```
1. Pré-cópia de memória:
   Copia páginas de RAM da VM para o host destino (enquanto VM ainda roda)
   Repete para páginas modificadas durante a cópia (dirty pages)

2. Stop-and-copy:
   Pausa a VM por milissegundos
   Copia as últimas páginas modificadas

3. Retomada no destino:
   VM continua no host B a partir do estado exato onde parou
   Host A libera os recursos
```

**Tempo de downtime real:** 10-100 milissegundos (imperceptível).

### Nomes por plataforma

| Plataforma | Nome |
|---|---|
| VMware | vMotion |
| Hyper-V | Live Migration |
| KVM/libvirt | virsh migrate |
| AWS | instância não migra entre hosts (reinicia em novo host) |

## Snapshots — captura de estado

Um snapshot captura o estado completo de uma VM em um momento específico:

```
VM em execução
    │
    ├─── Snapshot 1 (antes da atualização de SO)
    │
    │    [SO atualizado... deu erro]
    │
    └─── Reverter para Snapshot 1 → VM volta ao estado anterior
```

**O que um snapshot captura:**
- Estado da memória RAM (opcional — aumenta tamanho)
- Estado do disco (todas as alterações desde o snapshot base)
- Configuração da VM

**Atenção — snapshots não são backup:**

```
Snapshot:
  ├── Armazenado no mesmo datastore da VM
  ├── Se o datastore falhar, snapshot e VM são perdidos juntos
  └── Muitos snapshots degradam performance (chain longa)

Backup real:
  ├── Cópia em local separado (off-site, outro storage)
  └── Pode restaurar mesmo se o storage original falhar
```

## HA — High Availability

Em clusters com HA, o hypervisor monitora os hosts e reinicia VMs automaticamente em caso de falha:

```
Cluster HA (3 hosts):
  Host A: VM1, VM2, VM3  ← falha (hardware crash)
       ↓
  HA detecta falha em ~30 segundos
       ↓
  Host B: reinicia VM1, VM2
  Host C: reinicia VM3
       ↓
  Downtime total: 60-120 segundos (reboot das VMs)
```

### HA vs Fault Tolerance

| | HA | FT (Fault Tolerance) |
|---|---|---|
| Mecanismo | Reinicia em outro host após falha | VM espelho sincronizada em tempo real |
| Downtime | 60-120 segundos | Zero (failover instantâneo) |
| Overhead | Baixo | Alto (CPU/RAM dobrado) |
| Uso | Workloads gerais | Sistemas críticos (financeiro, saúde) |

## 🧩 Quiz de Fixação

1. Por que a live migration pausa a VM por apenas milissegundos em vez de minutos?
2. Por que snapshots não substituem backups?
3. Qual a diferença de downtime entre HA e Fault Tolerance em caso de falha de host?

**Respostas:**
1) A maior parte da memória é copiada enquanto a VM ainda roda (pré-cópia). A VM só é pausada para copiar as últimas páginas modificadas durante a cópia — que são poucas, levando apenas milissegundos.
2) Snapshots ficam no mesmo storage da VM — se o storage falhar, ambos são perdidos. Backup real fica em local separado, permitindo recuperação mesmo em falha total do storage original.
3) HA reinicia as VMs no host alternativo — gera downtime de 60-120 segundos (tempo de reboot). FT mantém VM espelho sincronizada — failover instantâneo, sem downtime perceptível.
