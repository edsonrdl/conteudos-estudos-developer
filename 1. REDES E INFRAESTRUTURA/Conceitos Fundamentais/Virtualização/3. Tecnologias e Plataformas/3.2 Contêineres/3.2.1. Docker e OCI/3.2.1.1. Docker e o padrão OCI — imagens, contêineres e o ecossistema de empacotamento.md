### Docker e o padrão OCI — imagens, contêineres e empacotamento

Docker popularizou os contêineres ao tornar seu uso simples e portável. O padrão OCI (Open Container Initiative) garantiu que o ecossistema não ficasse preso a um único fornecedor.

---

## O que o Docker fez de diferente

Antes do Docker, contêineres Linux (LXC) existiam mas eram complexos de usar. O Docker trouxe:

```
1. Dockerfile → definição declarativa da imagem
2. Docker Hub  → registro público de imagens
3. docker CLI  → interface simples para build, run, push, pull
4. Layers      → camadas reutilizáveis que aceleram build e download
```

---

## Imagem vs Contêiner

```
Imagem:     template imutável — "a receita"
              ├── Camada base (ubuntu:22.04)
              ├── Camada de dependências (apt install nodejs)
              └── Camada da aplicação (COPY app/ .)

Contêiner:  instância em execução da imagem — "o bolo assado"
              └── Camada de escrita (read-write layer) sobre a imagem
```

Múltiplos contêineres podem rodar da mesma imagem, cada um com sua camada de escrita independente.

---

## Dockerfile — construindo imagens

```dockerfile
# Imagem base
FROM node:20-alpine

# Diretório de trabalho
WORKDIR /app

# Copia dependências primeiro (aproveita cache de layers)
COPY package*.json ./
RUN npm ci --only=production

# Copia o código
COPY src/ ./src/

# Usuário não-root (segurança)
USER node

# Porta exposta
EXPOSE 3000

# Comando padrão
CMD ["node", "src/index.js"]
```

---

## Comandos essenciais

```bash
# Build da imagem
docker build -t minha-app:1.0 .

# Rodar contêiner
docker run -d \
  --name api \
  -p 8080:3000 \
  -e DATABASE_URL=postgres://... \
  --memory="512m" \
  --cpus="0.5" \
  minha-app:1.0

# Ver contêineres rodando
docker ps

# Logs
docker logs -f api

# Entrar no contêiner
docker exec -it api sh

# Parar e remover
docker stop api && docker rm api
```

## OCI — Open Container Initiative

Criada em 2015 (Linux Foundation), define padrões abertos para:

| Especificação | O que padroniza |
|---|---|
| **OCI Image Spec** | Formato da imagem de contêiner |
| **OCI Runtime Spec** | Como executar um contêiner (runc é a implementação de referência) |
| **OCI Distribution Spec** | API de registro de imagens (Docker Hub, ECR, GCR) |

```
Antes do OCI: imagens Docker só rodavam com Docker
Depois do OCI: imagem OCI roda em Docker, Podman, containerd, CRI-O...
```

---

## Docker vs containerd vs Podman

| | Docker | containerd | Podman |
|---|---|---|---|
| Daemon | Sim (dockerd) | Sim | Não (daemonless) |
| OCI compatível | Sim | Sim | Sim |
| Kubernetes | Via shim (não mais nativo) | Nativo (padrão) | Sim |
| Root necessário | Por padrão | Sim | Não (rootless) |
| Uso principal | Desenvolvimento | Produção/K8s | Segurança, RHEL |

## 🧩 Quiz de Fixação

1. O que são layers (camadas) em uma imagem Docker e por que são vantajosas?
2. O que o padrão OCI resolveu no ecossistema de contêineres?
3. Por que o Kubernetes abandonou o Docker como runtime padrão?

**Respostas:**
1) São camadas imutáveis empilhadas que formam a imagem. Vantajosas porque são cacheadas — se apenas o código da aplicação muda, as camadas de dependências não precisam ser baixadas/reconstruídas novamente.
2) Padronizou o formato de imagem e a interface de execução — garantindo portabilidade entre diferentes runtimes (Docker, containerd, Podman) sem lock-in de fornecedor.
3) O Kubernetes precisava de uma interface padronizada (CRI — Container Runtime Interface) para se comunicar com runtimes. O Docker não implementava o CRI diretamente, exigindo um shim intermediário (dockershim). O containerd e CRI-O implementam CRI nativamente, sendo mais eficientes.
