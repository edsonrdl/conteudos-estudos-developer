### Máquinas virtuais — isolamento completo, overhead e casos de uso

Uma máquina virtual (VM) é um ambiente computacional completo e isolado, com seu próprio SO, kernel, bibliotecas e aplicações — rodando sobre hardware virtualizado pelo hypervisor.

---

## Anatomia de uma VM

```
┌─────────────────────────────────────┐
│          Aplicação                  │
├─────────────────────────────────────┤
│    Bibliotecas / Runtime            │
├─────────────────────────────────────┤
│    Sistema Operacional (Guest OS)   │  ← kernel próprio
├─────────────────────────────────────┤
│    Hardware Virtual                 │  ← vCPU, vRAM, vDisk, vNIC
├─────────────────────────────────────┤
│         Hypervisor                  │
├─────────────────────────────────────┤
│         Hardware Físico             │
└─────────────────────────────────────┘
```

Cada VM enxerga um computador completo — não sabe que o hardware é virtual.

---

## Componentes de uma VM

| Componente | Virtual | Físico correspondente |
|---|---|---|
| vCPU | Núcleos lógicos alocados | Cores do processador físico |
| vRAM | Memória reservada | RAM do host |
| vDisk | Arquivo de imagem (VMDK, QCOW2, VHD) | Disco físico ou SAN |
| vNIC | Interface de rede virtual | NIC física (via switch virtual) |
| BIOS/UEFI | Emulado pelo hypervisor | Firmware físico |

---

## Isolamento — a principal vantagem

O isolamento é total por design:

```
VM 1 (comprometida por malware)
  → não acessa memória da VM 2
  → não acessa disco da VM 3
  → hypervisor isola completamente

Exceção: vulnerabilidades de VM escape (raras, críticas quando ocorrem)
```

Isso permite rodar workloads de diferentes clientes no mesmo hardware físico — base do modelo multitenancy das nuvens públicas.

---

## Overhead das VMs

Cada VM carrega um SO completo:

```
VM mínima (Ubuntu Server):
  ├── Kernel Linux: ~100MB RAM
  ├── Processos do sistema: ~200MB RAM
  ├── Imagem de disco mínima: ~2GB
  └── Tempo de boot: 30-60 segundos

→ Overhead significativo para workloads simples
→ Justificado quando isolamento forte é necessário
```

## Casos de uso em produção

| Cenário | Por que VM e não contêiner |
|---|---|
| **Diferentes SOs** | VM Windows + VM Linux no mesmo host físico |
| **Isolamento de segurança** | Clientes diferentes (multitenancy), compliance |
| **Kernels diferentes** | Aplicação legada que exige kernel específico |
| **Desktop virtualizado (VDI)** | Usuário precisa de desktop completo remoto |
| **Testes de SO** | Instalar/destruir SOs sem risco ao host |
| **Serviços com estado complexo** | Banco de dados que precisa de recursos dedicados garantidos |

---

## Operações fundamentais com VMs

| Operação | Descrição |
|---|---|
| **Snapshot** | Captura o estado completo da VM em um momento |
| **Clone** | Cria cópia independente da VM |
| **Live Migration** | Move VM entre hosts físicos sem downtime |
| **Suspend/Resume** | Pausa e retoma preservando estado de memória |
| **Template** | VM base para criar novas VMs rapidamente |

## 🧩 Quiz de Fixação

1. Por que VMs são preferidas a contêineres em ambientes multitenancy de nuvem pública?
2. O que é VM escape e por que é crítico?
3. Qual a diferença entre snapshot e clone de uma VM?

**Respostas:**
1) O isolamento das VMs é por hardware virtualizado (hypervisor) — muito mais forte que o isolamento por namespace dos contêineres. Dois clientes diferentes em VMs separadas não têm como interferir um com o outro.
2) VM escape é uma vulnerabilidade que permite que código rodando dentro da VM acesse o hypervisor ou outras VMs — compromete o isolamento fundamental. É raro mas crítico pois quebra o modelo de segurança inteiro.
3) Snapshot captura o estado em um ponto no tempo (pode reverter para ele) — a VM original continua existindo. Clone cria uma cópia completamente independente — uma nova VM separada.
