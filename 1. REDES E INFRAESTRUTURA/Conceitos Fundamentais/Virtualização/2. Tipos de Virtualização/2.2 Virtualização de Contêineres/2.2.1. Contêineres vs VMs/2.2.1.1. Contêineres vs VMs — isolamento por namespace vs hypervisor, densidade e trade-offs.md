### Contêineres vs VMs — isolamento, densidade e trade-offs

Contêineres e VMs são as duas formas dominantes de virtualizar workloads. Diferem fundamentalmente no nível de isolamento e no que compartilham com o host — o que determina densidade, performance e casos de uso ideais.

---

## A diferença fundamental

```
MÁQUINAS VIRTUAIS:
┌──────────┬──────────┬──────────┐
│  App A   │  App B   │  App C   │
│  Libs    │  Libs    │  Libs    │
│  OS      │  OS      │  OS      │  ← cada VM tem seu próprio kernel
│  Kernel  │  Kernel  │  Kernel  │
├──────────┴──────────┴──────────┤
│         Hypervisor             │
├────────────────────────────────┤
│         Hardware Físico        │
└────────────────────────────────┘

CONTÊINERES:
┌──────────┬──────────┬──────────┐
│  App A   │  App B   │  App C   │
│  Libs    │  Libs    │  Libs    │
├──────────┴──────────┴──────────┤
│    Kernel do Host (compartilhado)  │  ← um só kernel para todos
├────────────────────────────────────┤
│         Hardware Físico            │
└────────────────────────────────────┘
```

---

## Como o contêiner isola sem VM

O kernel Linux oferece dois mecanismos que o Docker e outros runtimes usam:

| Mecanismo | O que faz |
|---|---|
| **Namespaces** | Isolamento: cada contêiner tem sua visão de PID, rede, filesystem, usuários |
| **cgroups** | Limites: CPU, RAM, I/O máximo por contêiner |

```
Contêiner A vê:  PIDs 1, 2, 3...  (na verdade PIDs 5432, 5433... no host)
Contêiner B vê:  PIDs 1, 2, 3...  (na verdade PIDs 6100, 6101... no host)
Host vê:         todos os PIDs reais
```

---

## Comparativo direto

| Aspecto | VM | Contêiner |
|---|---|---|
| **Isolamento** | Forte (hypervisor) | Moderado (kernel compartilhado) |
| **Boot time** | 30-60 segundos | Milissegundos |
| **Tamanho** | GB (SO completo) | MB (só a app + libs) |
| **Densidade** | Dezenas por host | Centenas/milhares por host |
| **Overhead** | Alto (kernel próprio) | Mínimo |
| **SO guest** | Qualquer SO | Apenas Linux (no host Linux) |
| **Portabilidade** | Baixa (imagem grande) | Alta (imagem pequena) |
| **Segurança** | VM escape (raro) | Kernel compartilhado (risco maior) |

---

## Quando usar cada um

| Cenário | Escolha |
|---|---|
| Multitenancy com clientes diferentes | VM |
| Microserviços e APIs | Contêiner |
| Aplicação legada com SO específico | VM |
| CI/CD pipeline (build/test rápido) | Contêiner |
| Compliance rigoroso (PCI, HIPAA) | VM |
| Alta densidade de workloads leves | Contêiner |
| Desktop remoto | VM |

---

## O melhor dos dois mundos — VMs + Contêineres

Em produção, frequentemente se usa ambos:

```
Host físico
  └── VM (isolamento forte para o cliente)
        └── Contêineres (alta densidade dentro da VM)
              ├── Contêiner: API
              ├── Contêiner: Worker
              └── Contêiner: Cache
```

Kubernetes em nuvem pública roda pods (contêineres) dentro de VMs (nodes) — aproveitando isolamento de VM e eficiência de contêiner simultaneamente.

## 🧩 Quiz de Fixação

1. Por que contêineres iniciam em milissegundos enquanto VMs levam dezenas de segundos?
2. Qual o risco de segurança inerente ao kernel compartilhado dos contêineres?
3. Por que Kubernetes em nuvem pública usa VMs como nodes em vez de rodar contêineres diretamente no bare-metal?

**Respostas:**
1) Contêineres não inicializam um SO — apenas criam namespaces e cgroups em um kernel já rodando. VMs precisam fazer boot completo do kernel guest, inicializar drivers e serviços do SO.
2) Uma vulnerabilidade de kernel explorada dentro de um contêiner pode comprometer todos os outros contêineres e o host — o kernel é compartilhado. Em VMs, o kernel é isolado por hypervisor.
3) Para isolamento entre clientes (multitenancy) — cada cliente tem VMs separadas, garantindo que uma falha ou comprometimento não afete outros. Contêineres dentro da VM ainda têm alta densidade.
