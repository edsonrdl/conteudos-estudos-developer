### Estrutura por Microsserviço e Integration Events

Até aqui, tratamos a Clean Architecture como se existisse um único sistema, com uma única fronteira de camadas. Em um cenário de microsserviços, essa pergunta muda de forma: não é mais "como organizar as camadas de um sistema", e sim "como organizar as camadas **de cada serviço**, e como esses serviços conversam entre si sem que um viole a autonomia do outro".

---

## Cada microsserviço é uma Clean Architecture completa, isolada

A resposta mais simples — e a mais correta na maioria dos casos — é que **cada microsserviço replica a estrutura de quatro camadas internamente**, como se fosse uma aplicação independente. Não existe um "Domain" compartilhado entre serviços, nem uma camada de Application global: cada serviço tem seu próprio núcleo, sua própria fronteira, sua própria Regra da Dependência.

**Analogia:** pense em um conjunto de países independentes, cada um com sua própria constituição, seu próprio governo e suas próprias leis internas — mas que se relacionam entre si através de tratados e embaixadas (não através de um governo mundial único). O microsserviço de Pedidos tem sua própria "constituição" (sua Clean Architecture interna); o microsserviço de Pagamentos tem a dele. Eles não compartilham Entities nem Use Cases — apenas concordam em como trocar mensagens entre as "embaixadas" (os eventos de integração).

```
/microservice-order/
├── Domain/           # Entities específicas do domínio Order
├── Application/      # Use cases do contexto Order
├── Infrastructure/   # Adapters para este serviço
└── API/             # Interface REST/GraphQL

/microservice-payment/
├── Domain/          # Entities de Payment
├── Application/     # Use cases de pagamento
├── Infrastructure/  # Integração com gateways
└── API/            # API de pagamento
```

O ganho central dessa replicação — que a princípio pode parecer duplicação de esforço — é a **autonomia**: o serviço de Order pode escolher Java/Spring, o de Payment pode escolher Python/FastAPI, cada um pode evoluir seu próprio modelo de domínio sem esperar aprovação do outro time, e um deploy do serviço de Payment nunca exige recompilar ou re-testar o serviço de Order.

| Sem essa separação (Domain/Use Cases compartilhados) | Com Clean Architecture isolada por serviço |
|---|---|
| Um `Order` compartilhado precisa satisfazer as regras de negócio de Pedidos **e** de Pagamentos ao mesmo tempo | Cada serviço define sua própria visão de `Order` (ou do conceito equivalente), só com os dados que lhe interessam |
| Mudar uma regra de Pagamento pode exigir recompilar o serviço de Pedidos | Cada serviço é implantado, versionado e escalado de forma independente |
| Acoplamento de tecnologia — todos os serviços precisam da mesma stack | Cada serviço escolhe a tecnologia mais adequada ao seu próprio problema |

## Como os serviços conversam: Integration Events, não chamadas diretas de Domain

Se cada serviço tem seu próprio Domain isolado, como o serviço de Pagamentos sabe que um pedido foi processado e precisa reservar estoque? A resposta, alinhada ao que já vimos em Domain Events (4.2.1.1), é: **Integration Events** — a versão "entre serviços" do mesmo conceito.

A diferença de nomenclatura importa: um **Domain Event** comunica um fato dentro das fronteiras de um único serviço (ex: entre Entity e Use Case, como vimos em 4.2.1.1); um **Integration Event** comunica esse mesmo tipo de fato **para fora** do serviço, via um broker de mensageria (Kafka, RabbitMQ, SNS/SQS), para que outros serviços possam reagir.

```csharp
// Publicação de Integration Events
public class OrderProcessedIntegrationEvent : IntegrationEvent
{
    public Guid OrderId { get; }
    public decimal TotalAmount { get; }
    public List<OrderItem> Items { get; }

    public OrderProcessedIntegrationEvent(Guid orderId, decimal totalAmount, List<OrderItem> items)
    {
        OrderId = orderId;
        TotalAmount = totalAmount;
        Items = items;
    }
}

// Handler em outro microserviço
[EventHandler]
public class UpdateInventoryOnOrderProcessedHandler : IIntegrationEventHandler<OrderProcessedIntegrationEvent>
{
    private readonly IInventoryService _inventoryService;

    public async Task Handle(OrderProcessedIntegrationEvent @event)
    {
        foreach (var item in @event.Items)
        {
            await _inventoryService.ReserveItemAsync(item.ProductId, item.Quantity);
        }
    }
}
```

Repare que `OrderProcessedIntegrationEvent` é publicado pelo microsserviço `order`, mas o `UpdateInventoryOnOrderProcessedHandler` vive **dentro do microsserviço de estoque** (`inventory`), não no de pedidos. O serviço de Pedidos nunca importa nada do serviço de Estoque — ele apenas publica o evento em um broker; é o serviço de Estoque quem decide se está interessado nesse tipo de evento e se inscreve para recebê-lo.

## Fluxo completo entre dois microsserviços

```
┌────────────────────────────────┐
│   MICROSSERVIÇO: ORDER            │
│                                    │
│   OrderUseCase.ProcessOrder()      │
│         │                          │
│         ▼                          │
│   Domain: Order.Process()           │  ← regra de negócio interna, isolada
│         │                          │
│         ▼                          │
│   publica OrderProcessedIntegrationEvent
└──────────────┬───────────────────┘
               │
               ▼
     ┌───────────────────┐
     │  Broker de Mensageria │   (Kafka / RabbitMQ / SNS+SQS)
     └──────────┬──────────┘
                │  entrega o evento para quem se inscreveu
                ▼
┌────────────────────────────────┐
│   MICROSSERVIÇO: INVENTORY        │
│                                    │
│   UpdateInventoryOnOrderProcessedHandler.Handle()
│         │                          │
│         ▼                          │
│   Domain: Inventory.Reserve()       │  ← regra de negócio PRÓPRIA do
│                                    │     serviço de estoque, não do de pedidos
└────────────────────────────────┘
```

Note que o serviço de Inventory **não confia cegamente** nos dados do evento como se fossem sua própria fonte de verdade — ele traduz o evento recebido (`OrderProcessedIntegrationEvent`) em uma chamada ao seu próprio Domain (`Inventory.Reserve()`), que aplica as regras de negócio específicas de estoque (ex: verificar se há quantidade suficiente). Isso é a mesma ideia de Anti-Corruption Layer que veremos em Strangler Fig (5.3.1.1): cada serviço protege seu próprio modelo de domínio das particularidades do formato de dados de outro serviço.

## Diferença entre Domain Event e Integration Event

| Aspecto | Domain Event (visto em 4.2.1.1) | Integration Event |
|---|---|---|
| Escopo | Dentro de um único serviço/processo | Entre serviços diferentes |
| Mecanismo de transporte | Lista em memória, mediator interno (ex: MediatR) | Broker de mensageria externo (Kafka, RabbitMQ, SNS/SQS) |
| Quem consome | Handlers dentro do mesmo serviço | Handlers em outros serviços, possivelmente escritos em outra linguagem |
| Formato do payload | Pode referenciar tipos internos do domínio livremente | Precisa ser um contrato estável e serializável (JSON/Avro/Protobuf), já que outro serviço vai deserializar |
| Consistência | Geralmente forte, dentro da mesma transação | Sempre eventual — há um delay entre publicação e processamento |

## Quando usar e limitações

**Quando usar Clean Architecture isolada por microsserviço:**
- Quando os serviços já são organizacionalmente independentes (times diferentes, ciclos de deploy diferentes) — a arquitetura replicada reforça essa independência técnica.
- Quando cada serviço tem um domínio de negócio genuinamente distinto (Pedidos, Pagamentos, Estoque são bounded contexts diferentes, não apenas divisões técnicas arbitrárias).

**Limitações e armadilhas:**
- **Duplicação de conceitos é esperada, não um bug**: o conceito de "Pedido" pode existir, de formas diferentes, tanto no serviço de Order quanto no de Payment (cada um só com os dados que lhe interessam) — tentar unificar isso numa única Entity compartilhada reintroduz o acoplamento que os microsserviços tentam evitar.
- **Consistência eventual é inevitável**: entre o momento em que `OrderProcessedIntegrationEvent` é publicado e o momento em que o Inventory processa esse evento, existe uma janela onde os dois serviços estão temporariamente "desincronizados" — o restante do sistema (e a UI) precisa saber lidar com isso.
- **Quebra de contrato do evento é uma mudança de API pública**: como `OrderProcessedIntegrationEvent` é consumido por outros serviços que talvez você nem controle, mudar seu formato (remover um campo, por exemplo) é uma mudança *breaking*, que exige o mesmo cuidado de versionamento de uma API REST pública.
- **Granularidade errada gera "distributed monolith"**: se os serviços forem divididos por camada técnica (um serviço "Domain", outro "Infrastructure") em vez de por bounded context de negócio, o resultado é pior que um monolito — a mesma quantidade de acoplamento, mas com a latência e a complexidade operacional de uma rede distribuída.

## 🧩 Quiz de Fixação

1. Por que cada microsserviço mantém sua própria implementação completa de Clean Architecture, em vez de compartilhar um único Domain entre todos os serviços?
2. Qual a diferença fundamental entre um Domain Event (4.2.1.1) e um Integration Event, e por que essa distinção importa na hora de decidir o formato do payload?
3. Por que o `UpdateInventoryOnOrderProcessedHandler`, ao receber o evento, chama `Inventory.Reserve()` em vez de simplesmente confiar nos dados do evento e atualizar o estoque diretamente?

**Respostas:**
1) Porque compartilhar um único Domain entre serviços reintroduziria o acoplamento que a arquitetura de microsserviços busca eliminar — uma mudança de regra de negócio em um serviço exigiria coordenar e recompilar todos os outros que dependem do mesmo Domain. Ao manter cada serviço com sua própria Clean Architecture isolada, cada time ganha autonomia real: pode escolher sua própria tecnologia, evoluir seu próprio modelo de domínio e fazer deploy independentemente dos demais.
2) Um Domain Event vive inteiramente dentro de um único serviço/processo — é publicado e consumido na mesma aplicação, geralmente através de uma lista em memória ou um mediator interno, podendo referenciar tipos internos do domínio livremente. Um Integration Event atravessa a fronteira de rede entre serviços diferentes, via um broker de mensageria — por isso seu payload precisa ser um contrato estável e serializável (JSON, Avro, Protobuf), já que será deserializado por outro serviço, possivelmente escrito em outra linguagem, que não tem acesso aos tipos internos do domínio que o publicou.
3) Porque o serviço de Inventory tem seu próprio modelo de domínio e suas próprias regras de negócio (por exemplo, verificar se há quantidade suficiente disponível antes de reservar). Se ele simplesmente confiasse cegamente nos dados do evento e atualizasse o estoque diretamente, estaria abrindo mão de validar suas próprias invariantes de negócio, além de acoplar sua estrutura interna ao formato exato do evento publicado por outro serviço. Traduzir o evento em uma chamada ao próprio Domain (`Inventory.Reserve()`) preserva a autonomia e a integridade das regras de negócio de cada serviço.
