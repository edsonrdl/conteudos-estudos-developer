### Estudo de Caso: Maven Multi-módulo com Temporal Workflow

Os arquivos anteriores mostraram a Clean Architecture "espalhada" entre microsserviços independentes (5.1.1.1). Este arquivo mostra a outra ponta do espectro: um **monolito modular** — uma única aplicação, um único deploy, mas com as quatro camadas da Clean Architecture fisicamente separadas em módulos Maven distintos, cada um com suas próprias regras de dependência impostas pelo próprio build. O exemplo é um sistema real (aqui chamado StateNode) que orquestra fluxos jurídicos dinâmicos usando o motor de workflow Temporal, mantido completamente isolado na camada de Infraestrutura.

---

## Por que um monolito modular, e não vários microsserviços

**Analogia:** um monolito modular é como um apartamento bem planejado, com cômodos separados por paredes reais (não apenas por móveis) — cozinha, quarto e sala são fisicamente isolados, cada um com sua função clara, mas todos fazem parte do mesmo imóvel, com uma única entrada e uma única conta de energia. Já um conjunto de microsserviços seria como várias casas separadas em terrenos diferentes — mais autonomia entre elas, mas também mais custo de coordenação (cada uma com seu próprio portão, sua própria manutenção).

Um monolito modular bem-feito entrega boa parte do isolamento arquitetural dos microsserviços (times não pisam no código uns dos outros, dependências são controladas) sem o custo operacional de rede distribuída, versionamento de contratos entre serviços e consistência eventual — trade-off que costuma valer a pena quando o domínio ainda não tem fronteiras de negócio claras o suficiente para justificar serviços separados, ou quando o time é pequeno demais para operar múltiplos deploys independentes.

## A estrutura de módulos Maven

```
statenode/
├── pom.xml                              ← PAI (agregador — só declara os módulos filhos)
│
├── statenode-core/
│   └── domain/
│       ├── entities/       ← Processo, ProcessoSchema, WorkflowBlueprint
│       ├── valueobjects/   ← Contexto, SlotPayload, TipoSlot, StatusProcesso
│       ├── events/         ← SlotPreenchidoEvent, WorkflowIniciadoEvent...
│       ├── exceptions/     ← SchemaVioladoException, ProcessoException...
│       └── gateways/       ← IProcessoRepository, IWorkflowEnginePort (Ports)
│
├── statenode-application/
│   └── application/
│       └── usecases/
│           ├── CriarProcesso/       (Interactor, InputPort, OutputPort)
│           ├── PreencherSlot/
│           ├── IniciarWorkflow/
│           └── ValidarBlueprint/
│
├── statenode-infrastructure/
│   └── infrastructure/
│       ├── persistence/     ← JPA Entities, Repositories, Adapters
│       ├── temporal/        ← Workflow e Activities do Temporal
│       ├── events/          ← Publisher e Listeners de eventos
│       └── adapters/        ← TemporalWorkflowEngineAdapter (implementa o Port)
│
└── statenode-webapi/
    ├── StateNodeApplication.java   (ponto de entrada Spring Boot)
    ├── webapi/
    │   ├── entrypoints/     ← ProcessoController
    │   └── dtos/            ← CriarProcessoRequest, PreencherSlotRequest
    └── config/               ← TemporalConfig, JacksonConfig
```

Cada uma dessas quatro pastas de segundo nível (`statenode-core`, `statenode-application`, `statenode-infrastructure`, `statenode-webapi`) **não é uma pasta comum — é um módulo Maven próprio, com seu próprio `pom.xml`**. Essa é a diferença central entre isso e uma simples convenção de pastas dentro de um único módulo: o Maven, no momento do build, **recusa compilar** se um módulo declarar uma dependência não autorizada em seu `pom.xml`.

## A Regra da Dependência imposta pelo build, não só pela disciplina

```
statenode-webapi ──depende de──► statenode-application ──depende de──► statenode-core
      │                                                                       ▲
      └──depende de── statenode-infrastructure ──depende de──────────────────┘

statenode-core NÃO declara dependência em NENHUM outro módulo.
```

O `pom.xml` de `statenode-core` simplesmente **não lista** `statenode-infrastructure` nem `statenode-application` como dependência. Isso significa que, mesmo que um desenvolvedor tente escrever `import br.com.statenode.infrastructure.temporal.DynamicLegalWorkflow;` dentro de uma classe do módulo `core`, **o código nem compila** — o Maven não encontra a classe, porque o classpath do módulo `core` nunca inclui o jar de `infrastructure`.

Essa é uma vantagem prática sobre depender apenas de um Architecture Test (visto em 4.4.2.1): o Architecture Test roda como parte da suíte de testes, então uma violação só é detectada quando alguém roda os testes; a separação em módulos Maven é **estrutural**, então a violação nem chega a compilar. As duas abordagens não são excludentes — muitos projetos usam módulos Maven **e** Architecture Tests, como defesa em profundidade.

## O Port do motor de workflow: isolando o Temporal do domínio

O ponto mais interessante do exemplo é como o **Temporal** (motor de execução de workflows de longa duração) é mantido fora do domínio. Em vez de a Entity `Processo` ou os Use Cases chamarem a API do Temporal diretamente, existe um Port — `IWorkflowEnginePort` — definido dentro de `statenode-core` (perto do domínio), e a implementação concreta usando Temporal fica isolada em `statenode-infrastructure`:

```java
// statenode-core/domain/gateways/IWorkflowEnginePort.java
public interface IWorkflowEnginePort {
    void iniciarWorkflow(WorkflowBlueprint blueprint, Contexto contextoInicial);
    void avancarSlot(ProcessoId processoId, SlotPayload payload);
}

// statenode-infrastructure/infrastructure/adapters/TemporalWorkflowEngineAdapter.java
@Component
public class TemporalWorkflowEngineAdapter implements IWorkflowEnginePort {
    private final WorkflowClient temporalClient;

    @Override
    public void iniciarWorkflow(WorkflowBlueprint blueprint, Contexto contextoInicial) {
        DynamicLegalWorkflow workflow = temporalClient.newWorkflowStub(
            DynamicLegalWorkflow.class,
            WorkflowOptions.newBuilder()
                .setTaskQueue("legal-workflows")
                .build()
        );
        WorkflowClient.start(workflow::executar, blueprint, contextoInicial);
    }

    @Override
    public void avancarSlot(ProcessoId processoId, SlotPayload payload) {
        DynamicLegalWorkflow workflow = temporalClient.newWorkflowStub(
            DynamicLegalWorkflow.class, processoId.toString()
        );
        workflow.preencherSlot(payload);
    }
}
```

Por que isso importa tanto? O Temporal é um motor de workflow poderoso, mas é uma decisão de infraestrutura — assim como o banco de dados. Se, daqui a dois anos, o time decidir migrar para outro orquestrador (Camunda, AWS Step Functions, ou um motor próprio), a única coisa que muda é a implementação de `TemporalWorkflowEngineAdapter` dentro de `statenode-infrastructure`. Nem `statenode-core` nem `statenode-application` precisam saber que essa migração aconteceu — porque eles nunca conheceram o Temporal, apenas a interface `IWorkflowEnginePort`.

## Use Cases organizados por pasta própria: Interactor, InputPort, OutputPort

Repare que, dentro de `statenode-application/usecases/`, cada caso de uso (`CriarProcesso`, `PreencherSlot`, `IniciarWorkflow`, `ValidarBlueprint`) tem sua própria pasta, contendo três arquivos:

| Arquivo | Papel |
|---|---|
| `InputPort.java` | Interface que define o que o Use Case aceita como entrada (o "contrato de chamada") |
| `OutputPort.java` | Interface que define como o resultado é comunicado de volta (permite múltiplas formas de apresentar o resultado, sem o Use Case saber qual) |
| `Interactor.java` | A implementação real do Use Case — a classe que orquestra Entities, Gateways e produz o resultado através do `OutputPort` |

```java
// statenode-application/usecases/CriarProcesso/InputPort.java
public interface InputPort {
    void criar(CriarProcessoInput input);
}

// statenode-application/usecases/CriarProcesso/OutputPort.java
public interface OutputPort {
    void sucesso(ProcessoId processoId);
    void falha(String motivo);
}

// statenode-application/usecases/CriarProcesso/Interactor.java
public class Interactor implements InputPort {
    private final IProcessoRepository processoRepository;
    private final IWorkflowEnginePort workflowEngine;
    private final OutputPort outputPort;

    @Override
    public void criar(CriarProcessoInput input) {
        var schema = ProcessoSchema.carregar(input.getSchemaId());
        var processo = Processo.iniciar(schema, input.getContextoInicial());

        processoRepository.salvar(processo);
        workflowEngine.iniciarWorkflow(schema.getBlueprint(), processo.getContexto());

        outputPort.sucesso(processo.getId());
    }
}
```

Esse padrão (`InputPort`/`OutputPort`/`Interactor`) é a forma **mais literal e original** de implementar Use Cases, exatamente como descrito no livro original de Robert C. Martin — cada camada de fora (o Controller REST em `statenode-webapi`, por exemplo) implementa um `OutputPort` específico para o seu formato de resposta (JSON, por exemplo), sem que o `Interactor` precise saber nada sobre HTTP.

## O fluxo de eventos dentro do monolito

```
Processo (Entity, em statenode-core)
    │
    ├── ao preencher slot ──► registra SlotPreenchidoEvent (Domain Event)
    │
    ▼
SpringEventPublisherAdapter (statenode-infrastructure/events/)
    │  usa o mecanismo de eventos do próprio Spring (ApplicationEventPublisher)
    ▼
SlotPreenchidoListener (statenode-infrastructure/events/listeners/)
    │
    └──► pode disparar uma Activity do Temporal, notificar, etc.
```

Aqui, como tudo roda no mesmo processo (é um monolito, não microsserviços), os Domain Events não precisam de um broker externo como Kafka — o próprio `ApplicationEventPublisher` do Spring, que é apenas um mecanismo de publish/subscribe em memória, já é suficiente. Isso é uma vantagem prática do monolito modular: a mesma ideia de Domain Events (vista em 4.2.1.1) funciona, mas com infraestrutura muito mais simples que a de Integration Events entre microsserviços (vista em 5.1.1.1).

## Comparativo: Monolito Modular (Maven multi-módulo) vs. Microsserviços

| Aspecto | Monolito Modular (este exemplo) | Microsserviços (5.1.1.1) |
|---|---|---|
| Imposição da Regra da Dependência | Estrutural — o build falha se violada | Depende de disciplina + Architecture Tests dentro de cada serviço |
| Deploy | Único, todos os módulos juntos | Independente, por serviço |
| Comunicação entre "partes" | Chamada de método direta (mesma JVM) | Rede — HTTP, mensageria |
| Consistência | Forte, transacional (mesmo banco/processo) | Eventual, via Integration Events |
| Custo operacional | Baixo — um único processo para rodar e monitorar | Alto — múltiplos deploys, service discovery, observabilidade distribuída |
| Quando escalar horizontalmente | O monolito inteiro escala junto (menos granular) | Cada serviço escala independentemente conforme sua própria demanda |

## Quando usar e limitações

**Quando usar esse modelo (monolito modular multi-módulo):**
- Quando o time ainda é pequeno ou médio, e o custo operacional de microsserviços (observabilidade distribuída, versionamento de contratos, infraestrutura de mensageria) não se paga ainda.
- Quando as fronteiras de bounded context do domínio ainda não estão maduras o suficiente para virar serviços separados — o monolito modular serve como um passo intermediário, e a extração futura para microsserviços fica mais fácil justamente porque os módulos já são bem isolados.
- Quando forte consistência transacional entre partes do sistema é um requisito frequente (mais fácil garantir dentro de um único banco/processo do que entre serviços distribuídos).

**Limitações:**
- **Escalabilidade é sempre do processo inteiro**: não é possível escalar apenas o módulo de `infrastructure` (por exemplo, se ele estiver sob mais carga) sem escalar toda a aplicação junto.
- **Um bug em um módulo pode, em teoria, derrubar o processo inteiro** — diferente de microsserviços, onde uma falha em um serviço não necessariamente derruba os demais (embora isso também dependa de boas práticas de isolamento de falhas dentro do próprio monolito).
- **A disciplina de módulos Maven exige manutenção**: se os `pom.xml` não forem revisados com cuidado, é possível (por engano) adicionar uma dependência de `core` para `infrastructure` sem perceber — o ideal é reforçar isso também com um Architecture Test, como defesa em profundidade.

## 🧩 Quiz de Fixação

1. Qual é a diferença prática entre usar módulos Maven separados para impor a Regra da Dependência e usar apenas um Architecture Test (visto em 4.4.2.1) dentro de um único módulo?
2. Por que o `TemporalWorkflowEngineAdapter` vive em `statenode-infrastructure` e implementa uma interface (`IWorkflowEnginePort`) definida em `statenode-core`, em vez de o `Interactor` do Use Case chamar a API do Temporal diretamente?
3. Por que, nesse monolito modular, os Domain Events podem ser transportados pelo `ApplicationEventPublisher` do Spring (em memória), enquanto os Integration Events entre microsserviços (5.1.1.1) exigem um broker externo como Kafka?

**Respostas:**
1) Com módulos Maven separados, a violação da Regra da Dependência impede o próprio código de compilar — se `statenode-core` tentasse importar algo de `statenode-infrastructure`, o build falharia porque essa dependência nunca foi declarada no `pom.xml` do módulo `core`. Já um Architecture Test roda como parte da suíte de testes: ele detecta a violação, mas só depois que o código já compilou e os testes foram executados — é uma barreira mais tardia. As duas abordagens se complementam: módulos Maven barram estruturalmente, Architecture Tests reforçam a checagem mesmo dentro de um único módulo.
2) Porque o Temporal é uma decisão de infraestrutura, não uma regra de negócio — se a implementação do Use Case chamasse a API do Temporal diretamente, o módulo `statenode-application` (ou até `statenode-core`) passaria a depender de uma biblioteca de infraestrutura específica, violando a Regra da Dependência. Ao depender apenas da interface `IWorkflowEnginePort`, o Use Case (`Interactor`) permanece livre de qualquer conhecimento sobre Temporal — se o motor de workflow for trocado no futuro, só a implementação em `statenode-infrastructure` precisa mudar.
3) Porque, no monolito modular, todos os módulos rodam no mesmo processo e na mesma JVM — não há fronteira de rede a atravessar, então um mecanismo de publish/subscribe em memória, como o `ApplicationEventPublisher` do Spring, é suficiente e muito mais simples de operar. Já entre microsserviços, cada serviço roda em um processo (e possivelmente uma máquina) diferente, então o evento precisa atravessar a rede para chegar a outro serviço — isso exige um broker de mensageria externo (Kafka, RabbitMQ), capaz de entregar a mensagem de forma confiável entre processos distintos.
