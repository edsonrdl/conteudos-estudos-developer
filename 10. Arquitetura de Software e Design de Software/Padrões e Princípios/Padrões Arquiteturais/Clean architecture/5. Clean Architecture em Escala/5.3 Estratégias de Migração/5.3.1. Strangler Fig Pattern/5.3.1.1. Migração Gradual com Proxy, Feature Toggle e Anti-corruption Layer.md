### Migração Gradual com Proxy, Feature Toggle e Anti-corruption Layer

Nem todo sistema em Clean Architecture nasce assim. Na prática, a situação mais comum é o oposto: existe um sistema legado, sem camadas claras, com anos de acoplamento acumulado, e a pergunta não é "como projetar do zero", mas "como migrar sem reescrever tudo de uma vez e sem parar o sistema por meses". O Strangler Fig Pattern é a resposta mais estabelecida para esse problema.

---

## A analogia que dá nome ao padrão

O nome vem literalmente de uma planta: o **cipó-estrangulador** (strangler fig) cresce ao redor de uma árvore hospedeira, envolvendo-a pouco a pouco. Com o tempo, o cipó forma sua própria estrutura completa, capaz de se sustentar sozinho — e a árvore original, agora completamente envolvida e privada de luz, morre e apodrece por dentro, deixando de pé apenas a estrutura do cipó, que ocupou seu lugar gradualmente, sem nunca ter havido um momento de "substituição total de uma vez".

É exatamente essa a estratégia: em vez de um "Big Bang" (parar tudo, reescrever o sistema inteiro, trocar de uma vez), o sistema novo (em Clean Architecture) **cresce ao redor** do sistema legado, assumindo uma responsabilidade de cada vez, até que o legado possa ser desligado com segurança — sem nunca ter existido um período de "sistema fora do ar para reescrita".

---

## O mecanismo central: um Proxy que decide quem atende cada requisição

O componente que torna a migração gradual possível é um **Proxy** — uma camada fina, posicionada na frente tanto do sistema legado quanto do novo sistema, que decide, para cada requisição, qual dos dois deve processá-la.

```java
@Component
public class PaymentServiceProxy {
    private final LegacyPaymentService legacyService;
    private final ModernPaymentService modernService;
    private final FeatureToggle featureToggle;

    public PaymentResult processPayment(PaymentRequest request) {
        // Determinar qual implementação usar
        if (featureToggle.isModernPaymentEnabled(request.getCustomerId())) {
            return modernService.processPayment(request);
        } else {
            // Anti-corruption layer para sistema legacy
            LegacyPaymentData legacyData = PaymentDataTranslator.toLegacy(request);
            LegacyPaymentResponse response = legacyService.processPayment(legacyData);
            return PaymentDataTranslator.toModern(response);
        }
    }
}
```

Esse `PaymentServiceProxy` é o "portão" pelo qual toda requisição de pagamento passa. Repare em duas decisões de design cruciais:

1. **O `FeatureToggle` decide o roteamento por cliente** (`request.getCustomerId()`), não globalmente. Isso permite migrar 1% dos clientes primeiro, observar o comportamento em produção, e só então aumentar gradualmente esse percentual — em vez de trocar 100% dos usuários de uma vez.
2. **Quando o legado ainda atende, os dados passam por um Anti-Corruption Layer** (`PaymentDataTranslator`) — o formato de dados do sistema legado nunca vaza para o resto da aplicação nova; ele é traduzido para o formato moderno antes de retornar.

---

## O fluxo completo do Proxy

```
                         Requisição de pagamento chega
                                    │
                                    ▼
                         ┌─────────────────────┐
                         │  PaymentServiceProxy  │
                         └──────────┬───────────┘
                                    │
                    featureToggle.isModernPaymentEnabled(clienteId)?
                                    │
                  ┌─────────────────┴─────────────────┐
                  │ SIM                                │ NÃO
                  ▼                                     ▼
      ┌─────────────────────┐              ┌─────────────────────────┐
      │  ModernPaymentService  │              │  LegacyPaymentService     │
      │  (Clean Architecture)  │              │  (sistema legado)          │
      └─────────────────────┘              └───────────┬─────────────┘
                  │                                     │
                  │                          PaymentDataTranslator
                  │                          (Anti-Corruption Layer)
                  │                                     │
                  ▼                                     ▼
         PaymentResult (formato moderno)      PaymentResult (formato moderno,
                                               já traduzido do legado)
```

O ponto crucial desse desenho: **quem chama o `PaymentServiceProxy` nunca sabe se a resposta veio do sistema novo ou do legado** — ambos os caminhos produzem o mesmo `PaymentResult`, no mesmo formato. Isso é o que permite que o roteamento mude, cliente por cliente, sem que nenhum consumidor externo precise ser alterado.

---

## Por que o Anti-Corruption Layer é obrigatório, não opcional

Sem o `PaymentDataTranslator`, o formato de dados do sistema legado (`LegacyPaymentData`, `LegacyPaymentResponse`) vazaria diretamente para dentro do sistema novo — e, com ele, todas as inconsistências, nomes de campos estranhos e decisões de modelagem antigas que motivaram a migração em primeiro lugar. O Anti-Corruption Layer atua como uma membrana de tradução: tudo que entra e sai do sistema legado passa por ela, garantindo que o modelo de domínio novo (Clean Architecture) nunca precise conhecer o formato antigo.

Essa é a mesma ideia já vista em 5.1.1.1, quando o serviço de Inventory traduzia o `OrderProcessedIntegrationEvent` para o seu próprio modelo de domínio, em vez de confiar cegamente no formato recebido — aqui, a fonte "não confiável" (do ponto de vista do novo domínio) é o próprio sistema legado.

## Migração em fases

O Strangler Fig raramente acontece "camada por camada" de uma vez — na prática, costuma ser sequenciado assim:

| Fase | Duração típica | O que acontece |
|---|---|---|
| **1. Assessment** | 2-4 semanas | Mapear a arquitetura atual e suas dependências, identificar bounded contexts, definir a estratégia de dados (banco compartilhado? banco próprio para o novo sistema?) |
| **2. Infrastructure** | 2-3 semanas | Preparar o novo ambiente, implementar as primeiras Anti-Corruption Layers, configurar os pipelines de CI/CD do sistema novo |
| **3. Core Domain** | 4-8 semanas | Migrar as Entities e Value Objects para o novo modelo de domínio, implementar Domain Services, escrever testes de domínio puros |
| **4. Application Layer** | 3-6 semanas | Migrar os Use Cases, implementar Command/Query Handlers, escrever testes de aplicação |

Note que o Proxy e o Feature Toggle entram em cena logo na Fase 2 — é o que permite que as fases seguintes (3 e 4) aconteçam **em produção, com tráfego real**, de forma incremental, em vez de exigir que tudo esteja pronto antes de qualquer usuário real tocar no sistema novo.

## Comparativo: Big Bang Rewrite vs. Strangler Fig

| Aspecto | Big Bang Rewrite | Strangler Fig Pattern |
|---|---|---|
| Risco de falha total | Alto — se o sistema novo tiver um problema não previsto, não há "plano B" fácil | Baixo — o Feature Toggle permite reverter clientes específicos para o legado a qualquer momento |
| Tempo até o primeiro valor em produção | Longo — só entrega valor quando tudo estiver pronto | Curto — cada fatia migrada já entrega valor, mesmo com o legado ainda rodando |
| Complexidade operacional durante a transição | Baixa (só um sistema rodando de cada vez) | Mais alta (dois sistemas coexistindo, Proxy e ACL para manter) |
| Adequado para sistemas críticos 24/7 | Raramente — a janela de corte é arriscada | Sim — não exige downtime nem corte único |
| Feedback real de produção durante a migração | Só no final | Contínuo, desde a primeira fatia migrada |

## Quando usar e limitações

**Quando usar:**
- Sistemas legados críticos, que não podem ficar fora do ar durante a migração.
- Quando o time quer validar a nova arquitetura com tráfego real e usuários reais antes de migrar 100% da base.
- Quando a migração é grande o suficiente (meses) para que os riscos de um Big Bang sejam inaceitáveis.

**Limitações:**
- **Custo de manter dois sistemas coexistindo**: enquanto a migração não termina, o time precisa dar suporte tanto ao sistema legado quanto ao novo — incluindo corrigir bugs no legado, mesmo sabendo que ele será desligado.
- **O Proxy e o Anti-Corruption Layer são código extra e temporário**: eles não fazem parte do sistema final — precisam ser removidos ao fim da migração, e esquecer de removê-los deixa uma camada de indireção desnecessária para sempre.
- **Sincronização de dados é o ponto mais difícil**: se o sistema legado e o novo sistema acessam bases de dados diferentes durante a transição, manter os dois sincronizados (para que um cliente migrado e outro não migrado vejam dados consistentes) costuma ser a parte mais arriscada de todo o processo — exige planejamento cuidadoso na Fase 1 (Assessment).
- **Não é atalho para adiar decisões de arquitetura**: o Strangler Fig reduz o risco de a migração dar errado de uma vez, mas não elimina a necessidade de um bom design para o sistema novo — migrar gradualmente para uma arquitetura mal pensada só distribui o problema ao longo do tempo, em vez de resolvê-lo.

## 🧩 Quiz de Fixação

1. Por que o padrão se chama "Strangler Fig" (cipó-estrangulador), e o que essa analogia representa na prática da migração?
2. No `PaymentServiceProxy`, por que o roteamento é decidido por `request.getCustomerId()` (por cliente) em vez de uma variável global que afeta todos os usuários de uma vez?
3. O que aconteceria se o `PaymentDataTranslator` (Anti-Corruption Layer) fosse removido, e o `ModernPaymentService` passasse a receber diretamente os objetos `LegacyPaymentData` do sistema antigo?

**Respostas:**
1) O nome vem da planta cipó-estrangulador, que cresce envolvendo uma árvore hospedeira aos poucos, até formar sua própria estrutura completa e independente — momento em que a árvore original, sem mais luz, morre por dentro. Na migração de software, isso representa o sistema novo crescendo gradualmente ao redor do sistema legado, assumindo responsabilidades uma de cada vez, até que o legado possa ser desligado com segurança — sem nunca existir um único momento de corte total ("Big Bang").
2) Porque roteamento por cliente permite uma migração incremental e reversível: o time pode migrar um pequeno percentual de clientes primeiro, observar o comportamento em produção com tráfego real, e só então aumentar gradualmente esse percentual. Uma variável global que afeta todos os usuários de uma vez eliminaria essa gradualidade, tornando a migração equivalente a um Big Bang (todos migram ao mesmo tempo), perdendo justamente a vantagem de risco reduzido que o Strangler Fig oferece.
3) O modelo de domínio moderno (`ModernPaymentService` e tudo que dependesse dele) passaria a conhecer diretamente o formato de dados do sistema legado — reintroduzindo, dentro do sistema novo, as mesmas inconsistências, nomenclaturas estranhas e decisões de modelagem antigas que motivaram a migração. Isso "contaminaria" o novo domínio com o formato do legado, tornando a arquitetura nova tão acoplada ao sistema antigo quanto o próprio legado era — exatamente o problema que o Anti-Corruption Layer existe para evitar.
