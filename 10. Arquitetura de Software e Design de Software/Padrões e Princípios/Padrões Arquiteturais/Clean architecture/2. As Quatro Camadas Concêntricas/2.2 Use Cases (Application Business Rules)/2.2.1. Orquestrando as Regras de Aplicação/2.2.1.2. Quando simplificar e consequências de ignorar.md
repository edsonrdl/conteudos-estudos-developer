### Use Cases — quando simplificar e consequências de ignorar

O arquivo anterior (2.2.1.1) definiu o que são os Use Cases e mostrou exemplos em e-commerce, sistema bancário e controle de estoque. Este arquivo trata da mesma pergunta prática feita para as Entities (2.1.1.2), agora aplicada à camada de Use Cases: quando vale a pena simplificar, e o que se perde ao misturar essa camada com outras.

---

## Quando a camada é necessária

Na maioria dos sistemas, **vale a pena ter uma camada de Use Cases explícita** sempre que há lógica de aplicação não trivial. Se há várias etapas ou regras a cumprir em uma operação, ou integração entre várias partes — verificar estoque, depois pagamento, depois atualizar banco — essa camada traz muito valor: organiza o código e facilita testar as operações sem precisar de interface gráfica ou banco real.

---

## Quando pode ser evitada ou simplificada

Em **aplicações extremamente simples**, pode-se argumentar que a criação de classes de Use Case separadas acrescenta complexidade desnecessária. Em um CRUD básico onde cada operação é "salvar X no banco" sem outras regras, alguns desenvolvedores optam por implementar essa lógica diretamente no controlador ou em um serviço anêmico, sem criar uma classe de `UseCase` específica.

Em contextos de **startup ou MVP**, onde a prioridade é entregar rápido, seguir à risca todas as camadas pode parecer burocrático demais para algo simples. Imagine um caso de uso trivial como "Login de Usuário": implementando com todas as camadas, seriam necessárias uma interface de repositório de usuário, um Use Case `FazerLoginUseCase`, uma Entity `Usuario`, um adaptador para o banco e outro para a interface — muitas classes para uma funcionalidade que poderia ser apenas verificar usuário e senha no banco.

```
Login de Usuário — duas abordagens

SIMPLIFICADA (aceitável para MVP):        COM USE CASE EXPLÍCITO (produção):
Controller                                 Controller
  └─ chama ORM diretamente                   └─ chama FazerLoginUseCase
     e valida senha ali mesmo                     └─ usa UsuarioRepository (interface)
                                                        └─ Adapter implementa com o ORM
1 classe, resolve rápido                   4-5 classes, testável e reutilizável
```

Nesses cenários, é possível **simplificar temporariamente** — por exemplo, chamando o repositório (ou ORM) diretamente no controlador de login e contendo a lógica ali mesmo. Ainda assim, mesmo em sistemas pequenos, deve-se ter cuidado: abrir mão da camada de Use Cases pode levar a controladores muito carregados de lógica, dificultando a expansão futura. É comum que projetos inicialmente simples sofram refatorações para introduzir Use Cases conforme a complexidade aumenta — evitar essa camada só é aceitável como **concessão temporária** em prol da velocidade, não como boa prática para se manter a longo prazo.

---

## Consequências de ignorar ou misturar essa camada

Fundir a camada de Use Cases com outras — colocar toda a lógica de aplicação dentro de um controller web, ou dentro de um serviço de acesso a dados — traz problemas concretos:

| Problema | Como se manifesta |
|---|---|
| **Perda de organização clara do fluxo** | Um controller que faz validações, acessos a banco e chamadas a serviços externos tudo de uma vez fica difícil de entender e testar — testá-lo exige simular requisições HTTP e banco de dados, em vez de simplesmente chamar um método de Use Case em memória |
| **Componentes "inchados"** | Controllers viram classes enormes — o antipadrão **"Fat Controller"** — ou regras de negócio acabam escritas em scripts SQL |
| **Dificuldade de reutilização** | A lógica de cálculo de parcelas de um empréstimo, por exemplo, enterrada em um bean do Spring acoplado à web, não vira um componente limpo reutilizável em outra aplicação ou ferramenta batch |
| **Violação da Regra da Dependência** | Se o fluxo de negócio depende diretamente de detalhes externos (um `JdbcTemplate` do Spring, a construção manual de uma resposta JSON), alterações nesses detalhes se propagam para a lógica — o sistema fica mais frágil a mudanças tecnológicas |
| **Duplicação de regra de negócio** | Sem uma classe central representando o Use Case, é comum ver a mesma regra implementada de forma ligeiramente diferente em dois lugares distintos do sistema |

Conforme o projeto cresce, as funcionalidades podem começar a **se embaralhar**, dificultando identificar onde está cada regra — um cenário propício ao "código espaguete". Em resumo, ignorar a camada de Use Cases leva a um código menos mantenível e escalável. Por outro lado, ao manter Use Cases bem definidos, a tendência é que o projeto permaneça coeso e compreensível à medida que cresce, mesmo com muitas funcionalidades.

## 🧩 Quiz de Fixação

1. No exemplo do "Login de Usuário", por que a abordagem simplificada (sem Use Case explícito) pode ser uma escolha razoável em um MVP, mas arriscada se mantida em produção por muito tempo?
2. O que caracteriza o antipadrão "Fat Controller", e qual é a causa raiz que normalmente leva a esse problema?
3. Explique como a ausência de uma camada de Use Cases pode levar à duplicação de uma mesma regra de negócio em diferentes partes do sistema.

**Respostas:**
1) É razoável em um MVP porque a prioridade é validar uma hipótese de negócio rapidamente, e o overhead de criar múltiplas classes (interface de repositório, Use Case, Entity, adapters) pode não se justificar nesse momento. É arriscado mantê-la em produção porque, conforme o sistema cresce, a lógica de autenticação tende a se espalhar ou a ficar acoplada ao controller, dificultando testes, reuso e futuras mudanças de infraestrutura.
2) O "Fat Controller" é um controller que acumula validações, acesso a banco de dados e chamadas a serviços externos, tudo misturado em uma única classe enorme. A causa raiz é a ausência de uma camada de Use Cases que deveria concentrar essa orquestração — sem ela, toda a responsabilidade acaba recaindo sobre o componente de entrada (o Controller).
3) Sem uma classe central (o Use Case) representando uma regra de negócio específica, diferentes desenvolvedores — ou o mesmo desenvolvedor em momentos diferentes — tendem a reimplementar a mesma lógica em pontos distintos do sistema sempre que precisam dela, já que não existe um único lugar óbvio para reutilizá-la. Isso aumenta o risco de as duas implementações divergirem ao longo do tempo.
