### Use Cases — o que são, responsabilidades e exemplos práticos

Com as Entities mapeadas (2.1.1.1, 2.1.1.2), este arquivo avança para a segunda camada concêntrica: os Use Cases. Se as Entities são as regras de negócio atemporais, os Use Cases são o "roteiro" que usa essas regras para realizar algo concreto que o sistema precisa fazer.

---

## O que são: os fluxos de operação da aplicação

A camada de Use Cases — também chamada de **Aplicação** ou **Interactors** em alguns contextos — contém as **regras de negócio específicas da aplicação**: os fluxos de operações que o sistema deve realizar para satisfazer os requisitos. Enquanto as Entities trazem regras gerais e atemporais, os Use Cases definem **como essas regras são utilizadas para atingir um objetivo concreto** dentro do sistema automatizado.

Cada Use Case representa uma **ação ou funcionalidade** do sistema do ponto de vista do usuário ou do negócio — "Efetuar Compra", "Realizar Login", "Gerar Relatório de Vendas", "Processar Empréstimo". Ele orquestra as Entities e coordena a sequência de passos necessária para completar uma tarefa com valor de negócio, implementando **todas as regras de aplicação** daquele processo, do input ao output.

**Importante:** Use Cases não são o mesmo que "casos de uso" da UML ou descrições de requisitos — aqui não se trata de documentação, mas de **componentes de software reais** que realizam funcionalidades. Se o requisito diz "usuário faz login", na arquitetura existe uma classe (ou método) `FazerLoginUseCase` que implementa a lógica de autenticação de fato.

| Elemento (visão resumida) | Descrição |
|---|---|
| **Regras de negócio da aplicação** | Como os dados fluem entre Entities para cumprir um objetivo |
| **Orquestração** | Coordena chamadas para Entities e interfaces externas |
| **Políticas específicas** | Regras que podem mudar conforme a aplicação evolui (diferente das Entities, mais estáveis) |

---

## Responsabilidades: coordenar sem conhecer o mundo externo

Os Use Cases coordenam o **fluxo de dados entre as Entities e as camadas externas**, aplicando as regras de negócio da aplicação em si. Eles pegam uma solicitação externa (vinda de um controlador, por exemplo), interagem com as Entities necessárias para cumprir a solicitação, aplicam lógicas de decisão ou validação adicionais, e produzem uma resposta.

**Não** é função do Use Case se preocupar com *como* os dados chegam ou para onde vão (formato JSON, interface gráfica, banco de dados) — essas são preocupações de outras camadas. Idealmente, um Use Case lida com **objetos de negócio e interfaces abstratas** para obter ou persistir informações, de forma que possa ser executado em isolamento. Por isso, os Use Cases não devem depender de classes de UI, de banco de dados ou de frameworks — eles dependem apenas de **interfaces** que representam essas funcionalidades externas, invertendo a direção da dependência (o mesmo Princípio de Inversão de Dependência visto em 1.2.1.1).

Um papel adicional importante: os Use Cases **protegem as Entities**. Mudanças nesta camada não devem afetar as Entities em si (não se muda a definição de `Cliente` ou `Pedido` porque um processo mudou), e mudanças em detalhes externos (UI, banco) não devem afetar os Use Cases internamente. A única razão válida para mudar um Use Case é uma alteração na lógica de operação do sistema — nunca uma mudança de ferramenta ou detalhe de infraestrutura.

## Exemplos práticos em diferentes domínios

**E-commerce:** "Adicionar item ao carrinho", "Fechar Pedido", "Processar Pagamento". No caso de **Fechar Pedido**: verifica se o carrinho não está vazio, calcula o valor total com frete e descontos, assegura estoque disponível para cada produto, cria o pedido (Entity `Pedido`), debita os estoques correspondentes (chamando métodos das Entities `Produto`/`Estoque`), e solicita à camada de persistência que salve o pedido. Se alguma validação falhar, cancela a operação e retorna um erro apropriado — todas as decisões e sequências desse processo ficam concentradas no Use Case, e a interface externa apenas dispara essa orquestração.

**Sistema bancário:** um Use Case "Aprovar Empréstimo" verifica os dados do cliente e sua pontuação de crédito, aplica as regras de aprovação (renda compatível, crédito acima de determinado score), calcula os termos do empréstimo, e grava a aprovação ou reprovação. Esse Use Case interage com Entities como `PropostaDeEmprestimo` e `Cliente`, e pode usar um serviço externo de análise de crédito via interface — sem conhecer os detalhes daquele serviço.

**Controle de estoque:** um Use Case "Registrar Entrada de Produto" recebe a notificação de que um lote chegou, atualiza as quantidades em estoque (via Entity `Estoque`), verifica se havia pedidos pendentes daquele produto, e registra a entrada em um histórico.

Em todos os casos, o Use Case define **um fluxo completo de interação**: recebe uma entrada, orquestra Entities e serviços para cumprir as regras do negócio naquele contexto específico, e produz uma saída.

## 🧩 Quiz de Fixação

1. Qual é a diferença entre o papel de uma Entity e o papel de um Use Case, usando o exemplo do Use Case "Fechar Pedido"?
2. Por que um Use Case não deve depender diretamente de uma classe de UI ou de banco de dados, e o que ele usa no lugar disso?
3. O que significa dizer que os Use Cases "protegem as Entities", e qual é a única razão válida para alterar um Use Case?

**Respostas:**
1) A Entity (`Pedido`, `Produto`, `Estoque`) carrega as regras de negócio gerais e estáveis, como "não é possível ter estoque negativo". O Use Case "Fechar Pedido" orquestra várias dessas Entities em uma sequência específica de passos — verificar carrinho, checar estoque, calcular total, criar o pedido, debitar estoque, persistir — para realizar um objetivo concreto do sistema, sem redefinir nenhuma das regras que já vivem nas Entities.
2) Porque essa dependência direta acoplaria a lógica de aplicação a um detalhe técnico específico, violando a Regra da Dependência (1.2.1.1) e impedindo que o Use Case seja testado ou reutilizado isoladamente. No lugar disso, o Use Case depende apenas de interfaces abstratas que representam essas capacidades externas, e a implementação concreta é fornecida por uma camada mais externa.
3) Significa que mudanças na camada de Use Cases (ajustar o fluxo de um processo) não devem exigir alterar a definição das Entities, e mudanças em detalhes externos (trocar a UI ou o banco) não devem afetar a lógica interna dos Use Cases. A única razão válida para alterar um Use Case é uma mudança real na lógica de operação do sistema — por exemplo, adicionar uma nova etapa de validação ao processo de pedido — nunca uma mudança de ferramenta ou tecnologia.
