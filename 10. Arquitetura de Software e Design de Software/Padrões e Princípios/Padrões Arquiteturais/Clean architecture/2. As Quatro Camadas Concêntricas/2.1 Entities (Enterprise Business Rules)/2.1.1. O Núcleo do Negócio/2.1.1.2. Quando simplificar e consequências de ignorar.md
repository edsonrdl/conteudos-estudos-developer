### Entities — quando simplificar e consequências de ignorar

O arquivo anterior (2.1.1.1) definiu o que são as Entities e mostrou exemplos em diferentes domínios. Este arquivo trata da pergunta que todo time real enfrenta: vale a pena criar essa camada em **todo** projeto, ou existem casos legítimos de simplificação — e o que se paga quando essa camada é ignorada por engano.

---

## Quando a camada é necessária

Praticamente **qualquer sistema que possua lógica de negócio significativa necessita de uma camada de Entities** bem definida. Sempre que há regras complexas ou dados que precisam manter consistência independente de detalhes externos, é recomendável encapsulá-los em Entities. Essa camada ajuda a **centralizar a lógica** de negócio e facilita o reuso dessas regras em diferentes partes do sistema — ou até em sistemas diferentes dentro do mesmo domínio da empresa.

---

## Quando pode ser evitada ou simplificada

Em **aplicações muito simples ou em protótipos iniciais**, às vezes não se percebe uma separação explícita de Entities. Se a aplicação é essencialmente um CRUD simples (cria, lê, atualiza, deleta dados) **sem regras de negócio além das validações básicas**, pode parecer desnecessário ter uma camada separada — as "entidades" acabam sendo apenas estruturas de dados (classes ou tabelas do banco) sem comportamento.

Nesses casos, alguns times optam por **simplificar**: não criam classes de domínio ricas e deixam a lógica trivial espalhada em scripts SQL ou no código da interface. Essa abordagem pode agilizar protótipos, pois **evita a sobrecarga inicial** de modelar um domínio complexo quando ele não existe.

Entretanto, deve-se ter cautela: abrir mão da camada de Entities significa que as regras — mesmo as simples — podem acabar distribuídas em lugares inadequados, como validações de integridade feitas diretamente no controlador web ou no banco de dados via *triggers*. Essa simplicidade inicial pode cobrar seu preço adiante, se o sistema crescer ou as regras aumentarem de complexidade.

| Cenário | Decisão recomendada |
|---|---|
| Sistema com regras de negócio complexas, exceções, invariantes | Criar Entities ricas desde o início |
| CRUD simples sem nenhuma regra além de validação de formato | Simplificar é aceitável — mas com consciência do risco |
| Protótipo/MVP que valida uma hipótese e pode ser descartado | Simplificar é razoável — velocidade de validação pesa mais |
| Sistema que já demonstrou crescimento de complexidade | Investir em Entities ricas antes que a dívida técnica se acumule |

---

## Consequências de ignorar ou misturar essa camada

Se as Entities não forem claramente definidas e a lógica de negócio for empurrada para outras camadas — como adaptadores, ou até dentro de consultas de banco — perde-se a **separação de preocupações** fundamental. As regras de negócio ficam **espalhadas** e fortemente acopladas a detalhes de implementação, tornando o código frágil a mudanças.

Por exemplo, se validações importantes ficam apenas no nível de interface (UI) ou banco, uma mudança na UI (substituir uma interface web por uma API) ou no banco de dados pode fazer com que a equipe esqueça de reimplementar alguma regra, introduzindo bugs. Além disso, sem Entities bem definidas, diferentes partes do sistema podem duplicar lógica — violando o princípio DRY — ou implementar regras de formas inconsistentes.

```
Regra de negócio sem Entity definida
         │
         ▼
Regra é implementada em múltiplos lugares
(Controller A, Controller B, trigger de banco)
         │
         ▼
Uma mudança na regra exige encontrar e
atualizar TODOS os lugares — fácil esquecer um
         │
         ▼
Inconsistência: a regra "vale" em um lugar
do sistema e "não vale" em outro
```

A longo prazo, isso resulta em um código confuso e difícil de manter — conforme o sistema cresce, fica mais propenso a se tornar um "código espaguete" sem estrutura clara. Misturar a lógica de negócio com detalhes externos também reduz a **estabilidade** do núcleo: alterações em tecnologias externas (mudança de um framework web, ajustes no esquema do banco de dados) podem forçar modificações em regras de negócio que deveriam ser independentes.

Em resumo, ignorar a camada de Entities sacrifica a ideia de ter um núcleo de negócio **limpo** — sem dependências externas — dificultando testes isolados e a evolução segura do sistema.

## 🧩 Quiz de Fixação

1. Em que tipo de cenário simplificar ou omitir a camada de Entities é considerado uma decisão aceitável, e por quê?
2. Por que a ausência de Entities bem definidas tende a gerar duplicação de regras de negócio em diferentes partes do sistema?
3. Explique como uma mudança aparentemente inofensiva na UI (trocar web por API) pode introduzir um bug quando as regras de negócio não estão centralizadas em Entities.

**Respostas:**
1) É aceitável em CRUDs muito simples, sem regras de negócio além de validações básicas de formato, ou em protótipos/MVPs cujo objetivo é validar uma hipótese rapidamente e que têm chance real de serem descartados. Nesses casos, o custo de modelar um domínio rico supera o benefício, já que não há complexidade de negócio real a proteger.
2) Porque, sem um local único e centralizado (a Entity) para encapsular uma regra, diferentes desenvolvedores tendem a reimplementar a mesma verificação em pontos distintos do sistema (um Controller, uma trigger de banco, um script) sempre que precisam daquela regra, já que não existe um método reutilizável para chamar.
3) Se uma validação de negócio (por exemplo, "pedido não pode ter itens sem preço") estiver implementada apenas dentro do Controller web, e não dentro de uma Entity, trocar essa interface web por uma API não replicaria automaticamente essa validação — a nova API precisaria reimplementar a regra manualmente, e é fácil esquecer de fazê-lo, permitindo que dados inválidos entrem no sistema pela nova via.
