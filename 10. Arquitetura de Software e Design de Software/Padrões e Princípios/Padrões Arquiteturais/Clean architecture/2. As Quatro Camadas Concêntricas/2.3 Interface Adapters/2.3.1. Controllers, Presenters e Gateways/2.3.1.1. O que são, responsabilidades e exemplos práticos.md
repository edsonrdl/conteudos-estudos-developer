### Interface Adapters — o que são, responsabilidades e exemplos práticos

Com Entities (2.1) e Use Cases (2.2) mapeados, este arquivo avança para a terceira camada concêntrica: os Interface Adapters. Se as duas primeiras camadas formam o núcleo protegido, esta é a camada que efetivamente conversa com o mundo — a fronteira de tradução entre o "dentro" e o "fora".

---

## O que são: o tradutor entre o núcleo e o mundo externo

A camada de Interface Adapters serve como um **"tradutor" ou ponte** entre as camadas internas de negócio e as camadas externas, garantindo que cada lado possa operar no formato de dados ou protocolo que lhe é mais conveniente. Em essência, os adapters convertem os dados **do formato usado internamente** (pelos Use Cases e Entities) para o formato esperado por algum agente externo — uma resposta HTTP, uma linha de banco de dados, uma mensagem para outro sistema — e vice-versa.

Isso permite que as camadas de negócio permaneçam **isoladas dos detalhes de implementação** de interfaces, bancos ou serviços externos. A ideia é que **nenhuma lógica de negócio saiba "falar a língua" do mundo externo** — essa tradução fica inteiramente a cargo dos adapters. Em termos práticos, essa camada implementa o mesmo padrão de Ports and Adapters visto no glossário da [[10. Arquitetura de Software e Design de Software/Padrões e Princípios/Padrões Arquiteturais/Hexagonal/0 Hexagonal (Glossário )|Arquitetura Hexagonal]]: os Use Cases definem portas (interfaces) de entrada e saída, e os adapters são as implementações concretas dessas portas para tecnologias específicas.

---

## Os três tipos de componentes desta camada

| Componente | Papel | Direção |
|---|---|---|
| **Controllers** | Recebem entradas externas (requisições HTTP, cliques, comandos de CLI) e as transformam em chamadas aos Use Cases correspondentes | Entrada (mundo externo → núcleo) |
| **Presenters** | Pegam a resposta bruta de um Use Case (dados puros, objetos de domínio) e formatam-na para a forma exigida pela interface — formatar datas, valores, montar JSON/HTML | Saída (núcleo → mundo externo) |
| **Gateways** | Conectam a aplicação a uma fonte de dados externa (banco, sistema de arquivos, serviço externo), convertendo objetos de domínio para a estrutura de dados daquela fonte e vice-versa | Ambas (implementam as Secondary Ports definidas pelos Use Cases) |

Cada adaptador de interface **implementa um lado da comunicação**: ou o lado de entrada (adaptando algo externo para uma chamada interna) ou o lado de saída (adaptando um resultado interno para um formato externo). Um detalhe importante: **toda lógica de acesso a dados ou formatação de apresentação fica restrita a esta camada** — se o sistema usa SQL, todas as queries SQL estão aqui, e nada dentro de Use Cases ou Entities deve ter comandos SQL ou dependência de classes de acesso a dados. Da mesma forma, toda construção de HTTP, JSON ou HTML fica nos Controllers e Presenters, nunca dentro dos Use Cases.

## Exemplos práticos em diferentes domínios

**E-commerce com API REST:** um Controller REST para "Fechar Pedido" mapeia um endpoint (`POST /pedidos`), recebe um JSON, extrai os dados (itens, endereço), monta um objeto de request e chama o Use Case `FecharPedido`. Um Presenter (ou o próprio Controller) formata o resultado — um objeto de confirmação com número do pedido e data — em uma resposta JSON/HTTP. Um Gateway `PedidoRepositoryImpl` implementa a interface `PedidoRepository` (definida pelo Use Case) usando JPA/Hibernate, convertendo o objeto `Pedido` em entidades JPA ou comandos SQL — o Use Case apenas invoca `pedidoRepository.salvar(pedido)`, sem saber que existe SQL ou JPA por trás.

**Integração com serviço de pagamento externo:** um adaptador sabe chamar a API do provedor de pagamento (via HTTP ou SDK) e traduz a resposta em um resultado que o Use Case entende — "pagamento efetuado" ou uma exceção de pagamento recusado. O Use Case `FecharPedido` solicita "realizar pagamento" através de uma interface (uma Secondary Port), e o adaptador implementa essa interface usando o serviço real, sem que o Use Case conheça API keys ou formatos de JSON do provedor.

**Sistema bancário:** adaptadores para um Controller web ou desktop, para um sistema legado (o Use Case chama uma interface `CoreBankingService`, e o adaptador implementa chamando um serviço SOAP legado), ou para um caixa eletrônico (um evento "cartão inserido" vira uma chamada ao Use Case `AutenticarCartao`).

**Controle de estoque:** um leitor de código de barras (hardware) tem seu driver traduzido por um adaptador em uma entrada para o Use Case de dar baixa no estoque; ou um componente que lê um arquivo CSV de fornecimento e transforma em objetos de entrada para o Use Case de atualizar estoque.

Em todos os domínios, os Interface Adapters são os **meios de comunicação**: recebem algo em um formato e convertem para outro. A analogia mais usada é a de **"adaptadores de tomada"** — a camada funciona como aquele plugue que adapta um formato de tomada diferente, permitindo conectar o aparelho (o núcleo) à fonte de energia (o sistema externo) de forma compatível.

## 🧩 Quiz de Fixação

1. Qual é a diferença de direção entre um Controller e um Presenter, dentro da camada de Interface Adapters?
2. Por que toda query SQL de um sistema deve ficar restrita à camada de Interface Adapters (no Gateway), e nunca dentro de um Use Case ou de uma Entity?
3. No exemplo do serviço de pagamento externo, como o Use Case `FecharPedido` consegue "solicitar um pagamento" sem conhecer a API do provedor?

**Respostas:**
1) O Controller lida com a direção de entrada — recebe algo do mundo externo (uma requisição HTTP, um comando) e o traduz para uma chamada ao Use Case. O Presenter lida com a direção de saída — pega o resultado bruto produzido pelo Use Case e o formata no formato que a interface externa espera (JSON, HTML, texto formatado).
2) Porque manter o SQL (ou qualquer outro código de acesso a dados) restrito aos Gateways garante que as camadas internas (Use Cases e Entities) não conheçam detalhes de persistência — se essas queries estivessem espalhadas pelo núcleo, trocar de tecnologia de banco exigiria alterar a lógica de negócio, violando a Regra da Dependência (1.2.1.1).
3) Porque o Use Case depende apenas de uma interface abstrata (uma Secondary Port) que representa a capacidade "realizar pagamento", sem nenhuma referência à tecnologia concreta. O adaptador de pagamento implementa essa interface por trás das cenas, cuidando de API keys, formatos de requisição e detalhes do provedor — o Use Case apenas invoca o método da interface e recebe de volta um resultado já traduzido para o vocabulário do domínio.
