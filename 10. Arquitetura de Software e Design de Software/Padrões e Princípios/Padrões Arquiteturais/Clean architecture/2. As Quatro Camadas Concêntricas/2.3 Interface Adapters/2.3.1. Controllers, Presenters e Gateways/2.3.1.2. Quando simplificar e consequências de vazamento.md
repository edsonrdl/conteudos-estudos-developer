### Interface Adapters — quando simplificar e consequências de deixar formatos vazarem

O arquivo anterior (2.3.1.1) definiu Controllers, Presenters e Gateways. Este fecha o subtópico com a mesma pergunta prática já feita para Entities e Use Cases: quando vale a pena simplificar essa camada, e o que acontece quando um formato externo "vaza" para dentro do núcleo.

---

## Quando a camada é (quase) sempre necessária

**Quase sempre haverá alguma forma de adaptador**, pois todo sistema real precisa interagir com o mundo externo — ter uma interface de entrada/saída, persistir dados. A questão real não é "ter ou não ter" adaptadores, mas **quando precisamos explicitá-los e separá-los bem, e quando podemos simplificar**.

Em sistemas seguindo estritamente a Clean Architecture, mesmo havendo apenas uma interface (por exemplo, só uma aplicação web), criam-se adaptadores para ela — Controllers e Presenters separados — visando manter a independência do núcleo. Essa disciplina é necessária em sistemas complexos, com múltiplas formas de interface (web, mobile, APIs públicas), ou onde se quer de fato ter a opção de trocar tecnologia de interface ou banco com impacto mínimo.

---

## Quando pode ser evitada ou simplificada

Em **aplicações pequenas ou cenários muito controlados**, a camada de adapters explícita pode trazer sobrecarga desproporcional. Um microsserviço muito simples que apenas lê de um banco e retorna um resultado, sem muita lógica, pode achar exagero criar DTOs, mapeadores e interfaces de repositório separadas — nesse caso, é possível usar diretamente as entidades do ORM no Use Case ou retornar objetos do banco diretamente, pulando a formalidade dos adapters.

Isso de fato simplifica o desenvolvimento a curto prazo (menos classes, menos código de conversão). Em microsserviços especificamente, a busca por mantê-los pequenos pode levar a decisões de design menos "cerimoniosas" — aplicar toda a estratificação da Clean Architecture dentro de um serviço muito pequeno pode ser complexidade extra desnecessária.

| Quando simplificar é defensável | Quando NÃO é defensável |
|---|---|
| Script interno que lê um arquivo e grava no banco, sem expectativa de crescer | Sistema com múltiplas interfaces (web, mobile, API pública) já previstas |
| Protótipo onde velocidade de desenvolvimento é crítica | Sistema onde trocar de banco ou tecnologia de interface é um requisito real |
| Microsserviço deliberadamente minúsculo e de escopo fechado | Sistemas de porte moderado a grande, com vida útil longa |

Ao simplificar, a equipe **reduz o encapsulamento** em prol de velocidade — mas deve ficar claro que isso **sacrifica flexibilidade**: se, com o tempo, for preciso mudar algo (ler de outro formato, adicionar outra interface), a ausência da camada isolada vai cobrar seu preço. Evitar adapters só é defensável em código descartável ou muito pequeno; em sistemas moderados a grandes, a camada é essencial.

---

## Consequências de ignorar ou misturar essa camada

Não usar Interface Adapters — ou misturar suas responsabilidades com as dos Use Cases — resulta em acoplamento forte entre o núcleo da aplicação e os detalhes externos. Isso se manifesta de algumas formas específicas:

**Formato de dados externo "vazando" para dentro:** o Use Case passa ou recebe diretamente estruturas de JSON, tipos do framework web, ou estruturas de banco (um `ResultSet` SQL, um modelo de ORM) em suas funções. Sempre que o formato externo mudar, o Use Case quebra, violando a independência prometida pela arquitetura.

```java
// ERRADO — Use Case recebe um objeto do framework web diretamente
public class FecharPedidoUseCase {
    public void executar(HttpServletRequest request) {
        // se a lógica for reutilizada num teste ou noutra interface (CLI),
        // ela não funciona, porque exige um HttpServletRequest específico
    }
}

// CORRETO — Use Case depende apenas de um objeto do vocabulário do domínio
public class FecharPedidoUseCase {
    public ResultadoPedido executar(FecharPedidoInput input) {
        // input é um objeto de domínio simples, sem dependência de framework
    }
}
```

**Regras de negócio poluídas por código de conversão:** sem Presenters, é comum ver métodos de Use Case ou Entity cheios de formatação de datas e concatenação de strings para gerar saída — o que desvia do foco principal e torna a testagem mais difícil (testar um método que já devolve HTML ou JSON complica comparar resultados).

**Violação da Regra da Dependência:** se o Use Case grava dados chamando diretamente uma API SQL, trocar SQL por um banco NoSQL exige alterar a lógica do Use Case em diversos pontos, arriscando quebrar outras coisas. Na Clean Architecture ideal, essa troca exigiria apenas criar um novo Gateway implementando a interface de persistência, **sem tocar nas regras de negócio** — ignorar os adapters elimina exatamente essa proteção (a mesma discutida em 1.2.1.1).

**Impacto na testabilidade:** sem adapters bem definidos, testar um Use Case pode exigir um banco de dados real (se ele contém SQL diretamente) ou simular componentes externos complicados. Com adapters bem definidos, é possível usar *doubles* (mocks, stubs) das interfaces para testar o núcleo facilmente.

```
Sem Interface Adapters                    Com Interface Adapters
     │                                          │
     ▼                                          ▼
Use Case conhece HTTP/SQL/JSON          Use Case conhece só o vocabulário
     │                                    de domínio (interfaces abstratas)
     ▼                                          │
Mudança externa quebra o núcleo                 ▼
     │                                    Mudança externa afeta só o Adapter
     ▼                                          │
Teste exige infraestrutura real                 ▼
                                          Teste usa um double da interface
```

Em resumo, misturar ou pular a camada de Interface Adapters faz o sistema perder modularidade: um detalhe externo passa a ter poder de impacto sobre as regras de negócio, aumentando o acoplamento e diminuindo a facilidade de mudança. Pode economizar esforço no curto prazo, mas arrisca tornar o sistema rígido e frágil no longo prazo.

## 🧩 Quiz de Fixação

1. Em que tipo de sistema simplificar a camada de Interface Adapters — usando diretamente entidades do ORM no Use Case, por exemplo — costuma ser uma decisão razoável?
2. Dê um exemplo concreto de "vazamento de formato externo" para dentro de um Use Case, e explique por que isso quebra a promessa de independência da arquitetura.
3. Por que a ausência de Interface Adapters bem definidos torna a testabilidade de um Use Case mais difícil?

**Respostas:**
1) É razoável em sistemas pequenos, únicos e sem expectativa de crescer — como um script interno simples, um protótipo onde velocidade de desenvolvimento é crítica, ou um microsserviço deliberadamente minúsculo e de escopo fechado. Nesses casos, o custo de manter Gateways e DTOs separados supera o benefício, já que a chance de precisar trocar de tecnologia ou adicionar novas interfaces é baixa.
2) Um exemplo é um Use Case que recebe diretamente um objeto `HttpServletRequest` do framework web como parâmetro. Isso quebra a promessa de independência porque, se o formato de entrada mudar (por exemplo, adicionar uma interface de linha de comando), a lógica de negócio dentro do Use Case não pode ser reaproveitada sem reescrevê-la, já que ela está fisicamente acoplada ao tipo específico do framework.
3) Porque, sem um Gateway isolando o acesso a dados (por exemplo, se o Use Case contém SQL diretamente), testar a lógica de negócio exige subir um banco de dados real ou simular componentes externos complexos. Com um Gateway bem definido implementando uma interface abstrata, é possível substituir essa implementação por um double (mock ou stub) durante os testes, verificando a lógica do Use Case isoladamente, sem qualquer infraestrutura real.
