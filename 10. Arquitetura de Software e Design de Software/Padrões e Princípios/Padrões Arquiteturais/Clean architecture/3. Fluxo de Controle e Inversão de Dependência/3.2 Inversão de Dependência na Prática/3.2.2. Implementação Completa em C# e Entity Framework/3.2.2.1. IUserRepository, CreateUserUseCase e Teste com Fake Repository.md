### IUserRepository, CreateUserUseCase e Teste com Fake Repository

O arquivo anterior (3.2.1.1) mostrou a Inversão de Dependência em Java com Spring. Este fecha o Domínio 3 com o mesmo princípio implementado em C# e Entity Framework — e, principalmente, mostra o benefício mais tangível de tudo isso: testar a regra de negócio sem nenhum banco de dados real.

---

## 1. Camada de Domínio — a abstração vive aqui

Esta é a camada mais interna e de **alto nível**. Ela define a regra de negócio e os contratos de que precisa, sem saber como serão implementados:

| Arquivo | Conteúdo | Propósito |
|---|---|---|
| `IUserRepository.cs` | `public interface IUserRepository { ... }` | **Contrato:** define o que precisa ser feito (`Save`, `Get`). A Infraestrutura terá que seguir este contrato. |
| `User.cs` | `public class User { ... }` | A Entidade de Domínio. |

```csharp
// Camada de Domínio (Camada Interna)

// A Interface (Abstração) VIVE AQUI
// O Domínio diz: "Eu preciso de um objeto que saiba salvar e buscar usuários."
public interface IUserRepository
{
    void Save(User user);
    User GetByEmail(string email);
}

// A Entidade de Domínio
public class User
{
    public string Name { get; set; }
    public string Email { get; set; }
    // ... lógica de domínio
}
```

---

## 2. Camada de Aplicação — depende só da abstração

Esta camada de alto nível contém a orquestração e as regras de negócio. Ela depende **apenas** de `IUserRepository` (a interface do Domínio):

```csharp
// Camada de Aplicação (Use Case)

public class CreateUserUseCase
{
    // O Use Case depende da ABSTRAÇÃO (IUserRepository)
    private readonly IUserRepository _userRepository;

    // Injeção de Dependência: recebe uma IMPLEMENTAÇÃO de IUserRepository.
    // Não importa se é SQL, MongoDB, ou um Fake para teste.
    public CreateUserUseCase(IUserRepository userRepository)
    {
        _userRepository = userRepository;
    }

    public void Execute(User user)
    {
        // 1. Regra de negócio: não pode ter e-mail duplicado.
        if (_userRepository.GetByEmail(user.Email) != null)
        {
            throw new Exception("Erro: Usuário já existe.");
        }

        // 2. Usa o contrato (Save) para persistir o objeto.
        _userRepository.Save(user);
    }
}
```

Note a frase-chave no comentário: "não importa se é SQL, MongoDB, ou um Fake para teste" — o Use Case literalmente não tem como saber, e não precisa saber.

---

## 3. Camada de Infraestrutura — a única que implementa a interface

Esta é a camada mais externa e de **baixo nível**. Contém os detalhes tecnológicos e é a única que implementa a interface do Domínio:

```csharp
// Camada de Infraestrutura (Camada Externa)

// A Implementação CONCRETA VIVE AQUI
// Ela inverte a dependência: a Infraestrutura depende do Domínio (a interface).
public class SqlUserRepository : IUserRepository
{
    private readonly DbContext _dbContext; // Detalhe de baixo nível (Entity Framework)

    public SqlUserRepository(DbContext dbContext)
    {
        _dbContext = dbContext;
    }

    // A Infraestrutura PREENCHE o contrato do Domínio.
    public void Save(User user)
    {
        _dbContext.Users.Add(user);
        _dbContext.SaveChanges();
    }

    public User GetByEmail(string email)
    {
        return _dbContext.Users.FirstOrDefault(u => u.Email == email);
    }
}
```

| Camada | Tipo | Depende de | Direção da seta |
|---|---|---|---|
| Infraestrutura (`SqlUserRepository`) | Baixo Nível | Domínio (`IUserRepository`) | **Aponta para dentro** (correto) |
| Aplicação (`CreateUserUseCase`) | Alto Nível | Domínio (`IUserRepository`) | **Aponta para dentro** (correto) |

O `CreateUserUseCase` está totalmente **desacoplado** da tecnologia de banco de dados (`SqlUserRepository`) — ele conhece apenas `IUserRepository`.

## O benefício prático: testar sem banco de dados real

O maior ganho de toda essa estrutura é a testabilidade. Para testar `CreateUserUseCase`, não é preciso um banco de dados real — basta criar um `FakeUserRepository` na camada de teste, implementando a mesma interface:

```csharp
// Camada de Teste

// Implementação Fake/Mock para teste (em memória)
public class FakeUserRepository : IUserRepository
{
    private readonly List<User> _store = new List<User>();

    public void Save(User user) { _store.Add(user); }
    public User GetByEmail(string email) {
        return _store.FirstOrDefault(u => u.Email == email);
    }
}

[Fact] // Teste de unidade
public void Deve_Falhar_AoCriarUsuarioExistente()
{
    // ARRANGE: injetamos o FAKE Repository
    var fakeRepo = new FakeUserRepository();
    fakeRepo.Save(new User { Email = "teste@email.com" });

    var useCase = new CreateUserUseCase(fakeRepo); // Depende apenas da Interface

    // ACT & ASSERT: testamos apenas a lógica de negócio do Use Case
    var novoUsuario = new User { Email = "teste@email.com" };

    // O teste valida que a regra de negócio (não duplicar e-mail) foi cumprida.
    Assert.Throws<Exception>(() => useCase.Execute(novoUsuario));
}
```

Esse teste roda em milissegundos, sem conexão de rede, sem servidor de banco de dados, sem `DbContext` real — porque `FakeUserRepository` é apenas uma lista em memória que satisfaz o mesmo contrato `IUserRepository` que `SqlUserRepository` satisfaz. Ao fazer o Domínio definir o contrato, garante-se que a lógica de negócio essencial (o Use Case) nunca precise de um detalhe externo (a Infraestrutura) para funcionar ou ser testada.

## 🧩 Quiz de Fixação

1. No teste `Deve_Falhar_AoCriarUsuarioExistente`, por que é possível verificar a regra de negócio "não duplicar e-mail" sem nunca ter tocado em um banco de dados real?
2. Comparando `SqlUserRepository` e `FakeUserRepository`, o que os dois têm em comum que permite trocar um pelo outro sem alterar `CreateUserUseCase`?
3. Por que a frase do comentário no código "não importa se é SQL, MongoDB, ou um Fake para teste" resume o benefício central da Inversão de Dependência?

**Respostas:**
1) Porque a regra de negócio "não pode ter e-mail duplicado" está inteiramente dentro de `CreateUserUseCase.Execute()`, que depende apenas da interface `IUserRepository` — não de uma implementação específica. Ao injetar `FakeUserRepository` (uma lista em memória) no lugar de `SqlUserRepository`, o teste consegue verificar a mesma lógica de negócio sem precisar de infraestrutura real.
2) Ambos implementam a mesma interface `IUserRepository`, fornecendo os métodos `Save` e `GetByEmail` com a mesma assinatura. Por dependerem apenas dessa abstração comum, `CreateUserUseCase` pode receber qualquer uma das duas implementações via injeção de dependência, sem que uma linha de código do Use Case precise mudar.
3) Porque resume exatamente a inversão de dependência na prática: a camada de Aplicação nunca decide qual tecnologia de persistência será usada — ela apenas declara o que precisa (a interface) e recebe, de fora, qualquer implementação que satisfaça esse contrato. Isso vale tanto para trocar de banco de dados em produção quanto para substituir a implementação real por uma versão de teste.
