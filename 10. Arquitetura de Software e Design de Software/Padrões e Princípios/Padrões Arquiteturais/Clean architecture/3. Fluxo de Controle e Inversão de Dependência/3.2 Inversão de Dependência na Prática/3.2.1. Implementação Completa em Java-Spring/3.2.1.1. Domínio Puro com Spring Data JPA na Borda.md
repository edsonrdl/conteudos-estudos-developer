### Domínio Puro com Spring Data JPA na Borda

O arquivo anterior (3.1.1.1) mostrou o fluxo de controle em teoria. Este arquivo mostra a Inversão de Dependência funcionando em um caso real e completo, em Java com Spring Data JPA, provando com código que o Domínio e a Aplicação nunca precisam saber que o Spring existe.

---

## A premissa: Spring só aparece na borda

Para este exemplo, o Spring Framework é usado apenas nas camadas de **Infraestrutura** e **Apresentação** — Domínio e Aplicação permanecem puros, sem nenhum import de Spring ou JPA.

---

## 1. Camada de Domínio (`com.app.domain`) — pura

Esta camada não conhece Spring nem JPA. A Entity `Pagamento` (regras de negócio) e a interface `PagamentoRepository` (o contrato que o domínio exige) vivem aqui:

```java
// PACOTE: com.app.domain
public interface PagamentoRepository {
    // Métodos de contrato que o Use Case precisa
    Pagamento getById(String id);
    void save(Pagamento pagamento);
}
```

Repare que essa interface fala inteiramente o vocabulário do domínio — `Pagamento`, `getById`, `save` — sem nenhuma menção a JPA, SQL ou Spring.

---

## 2. Camada de Aplicação (`com.app.application`) — pura

O Use Case `ProcessarPagamentoUseCase` depende **apenas** da interface `PagamentoRepository`. Ele não muda em nada, independentemente de qual tecnologia de persistência será usada por trás — ele só usa o contrato.

---

## 3. Camada de Infraestrutura (`com.app.infrastructure`) — onde os frameworks entram

Esta é a camada que introduz Spring e JPA de fato, com três peças:

**A) Model de persistência** — uma classe separada da Entity de domínio, para não sujar `Pagamento` com anotações de banco:

```java
// PACOTE: com.app.infrastructure.model
import javax.persistence.Entity;
import javax.persistence.Id;
import javax.persistence.Table;

@Entity
@Table(name = "pagamentos")
public class PagamentoJpaModel {
    @Id
    private String id;
    private double valor;
    private String status; // Mapeado para String/Enum no DB
}
```

**B) Repositório de baixo nível do Spring Data**, que o próprio Spring implementa automaticamente:

```java
// PACOTE: com.app.infrastructure.repository
import org.springframework.data.jpa.repository.JpaRepository;
import com.app.infrastructure.model.PagamentoJpaModel;

public interface PagamentoJpaRepository extends JpaRepository<PagamentoJpaModel, String> {
    // O Spring implementa automaticamente
}
```

**C) O Adaptador de Repositório — a ponte onde a Inversão de Dependência acontece de fato:**

```java
package com.app.infrastructure.adapter;

import com.app.domain.Pagamento;
import com.app.domain.PagamentoRepository; // Implementa a Interface do DOMÍNIO!
import com.app.infrastructure.repository.PagamentoJpaRepository;
import com.app.infrastructure.model.PagamentoJpaModel;
import org.springframework.stereotype.Component;

@Component // Bean Spring — detalhe de infraestrutura
public class PagamentoRepositoryAdapter implements PagamentoRepository {

    private final PagamentoJpaRepository jpaRepository;

    public PagamentoRepositoryAdapter(PagamentoJpaRepository jpaRepository) {
        this.jpaRepository = jpaRepository;
    }

    // MAPPER: converte Entidade de Domínio para Model JPA e vice-versa
    private PagamentoJpaModel toJpaModel(Pagamento domain) {
        PagamentoJpaModel model = new PagamentoJpaModel();
        model.setId(domain.getId());
        model.setValor(domain.getValor());
        model.setStatus(domain.getStatus().name());
        return model;
    }

    private Pagamento toDomain(PagamentoJpaModel model) {
        return new Pagamento(model.getId(), model.getValor()); // Simplificado
    }

    @Override
    public Pagamento getById(String id) {
        return jpaRepository.findById(id).map(this::toDomain).orElse(null);
    }

    @Override
    public void save(Pagamento pagamento) {
        PagamentoJpaModel model = toJpaModel(pagamento);
        jpaRepository.save(model);
    }
}
```

## 4. Camada de Apresentação (`com.app.presentation`) — entrada/saída

```java
package com.app.presentation;

import com.app.application.ProcessarPagamentoUseCase;
import com.app.domain.Pagamento;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class PagamentoController {

    private final ProcessarPagamentoUseCase useCase;

    public PagamentoController(ProcessarPagamentoUseCase useCase) {
        this.useCase = useCase;
    }

    public static class PagamentoRequest {
        public String pagamentoId;
        public double valor;
        public String numeroCartao;
    }

    @PostMapping("/pagamentos")
    public Pagamento processar(@RequestBody PagamentoRequest request) {
        ProcessarPagamentoUseCase.Request useCaseRequest = new ProcessarPagamentoUseCase.Request();
        useCaseRequest.pagamentoId = request.pagamentoId;
        useCaseRequest.valor = request.valor;
        useCaseRequest.numeroCartao = request.numeroCartao;

        return useCase.execute(useCaseRequest); // Regra de negócio pura
    }
}
```

## O fluxo completo de dependência (inversão garantida)

```
PagamentoController (Apresentação)
        │ depende de
        ▼
ProcessarPagamentoUseCase (Aplicação)
        │ depende de
        ▼
PagamentoRepository — interface (Domínio)
        ▲ implementa
        │
PagamentoRepositoryAdapter (Infraestrutura)
        │ usa
        ▼
PagamentoJpaRepository — ferramenta de baixo nível (Spring Data/JPA)
```

1. `PagamentoController` (Apresentação) → depende de `ProcessarPagamentoUseCase` (Aplicação).
2. `ProcessarPagamentoUseCase` (Aplicação) → depende de `PagamentoRepository` (interface do Domínio).
3. `PagamentoRepositoryAdapter` (Infraestrutura) → **implementa** `PagamentoRepository` (interface do Domínio).
4. `PagamentoRepositoryAdapter` (Infraestrutura) → **usa** `PagamentoJpaRepository` (ferramenta de baixo nível/JPA).

O segredo está no Adaptador de Repositório: é a classe na Infraestrutura que atua como tradutor e ponte, garantindo que o Use Case — a camada de alto valor — nunca precise saber que o Spring Data JPA existe.

## 🧩 Quiz de Fixação

1. Por que a classe `PagamentoJpaModel` existe separadamente da Entity de domínio `Pagamento`, em vez de simplesmente anotar `Pagamento` com `@Entity`?
2. Na cadeia de dependências do exemplo, quem implementa `PagamentoRepository`, e quem apenas depende dele como uma abstração?
3. Se amanhã o projeto decidisse trocar Spring Data JPA por MongoDB, quais classes precisariam mudar, e quais permaneceriam intactas?

**Respostas:**
1) Porque anotar `Pagamento` diretamente com `@Entity` acoplaria a Entity de domínio à tecnologia JPA, violando a Regra da Dependência (1.2.1.1). Ao manter `PagamentoJpaModel` como uma classe separada, apenas ela carrega as anotações técnicas, e o `PagamentoRepositoryAdapter` faz a tradução (mapper) entre os dois mundos.
2) `PagamentoRepositoryAdapter`, na camada de Infraestrutura, implementa a interface `PagamentoRepository`. `ProcessarPagamentoUseCase`, na camada de Aplicação, apenas depende dessa interface como uma abstração, sem conhecer qual implementação concreta está por trás.
3) Apenas as classes da camada de Infraestrutura precisariam mudar: `PagamentoJpaModel`, `PagamentoJpaRepository` e `PagamentoRepositoryAdapter` seriam substituídas por equivalentes usando o driver do MongoDB, mantendo a mesma assinatura de `PagamentoRepository`. O Domínio (`Pagamento`, `PagamentoRepository`) e a Aplicação (`ProcessarPagamentoUseCase`) permaneceriam completamente intactos.
