### O Fluxo Completo de uma Requisição

Com as quatro camadas concêntricas totalmente mapeadas no Domínio 2, este arquivo abre o Domínio 3 juntando as peças: como uma requisição realmente atravessa Controller, Use Case e Presenter, e por que essa travessia usa portas de entrada e saída específicas em vez de uma chamada direta.

---

## As cinco etapas do fluxo de controle

```
1. Controller recebe a requisição externa
        │
        ▼
2. Use Case Input Port define a interface de entrada
        │
        ▼
3. Use Case Interactor executa a lógica de negócio
        │
        ▼
4. Use Case Output Port define a interface de saída
        │
        ▼
5. Presenter formata os dados para apresentação
```

Cada uma dessas cinco etapas corresponde a um conceito já detalhado no Domínio 2:

| Etapa | Conceito | Arquivo de referência |
|---|---|---|
| 1 | Controller (Interface Adapter de entrada) | 2.3.1.1 |
| 2 | Use Case Input Port | Interface que o Controller chama, implementada pelo Interactor |
| 3 | Use Case Interactor | O próprio Use Case, executando a orquestração (2.2.1.1) |
| 4 | Use Case Output Port | Interface que o Interactor chama para devolver o resultado |
| 5 | Presenter (Interface Adapter de saída) | 2.3.1.1 |

---

## Por que existem duas portas (Input e Output), e não uma chamada direta

Um detalhe que passa despercebido na primeira leitura: o Interactor não devolve o resultado diretamente ao Controller através de um `return` simples — ele **chama** a Use Case Output Port, que é implementada pelo Presenter. Essa aparente complicação extra existe por um motivo preciso: manter a Regra da Dependência (1.2.1.1) também na direção de saída.

```
SEM Output Port (dependência na direção errada):

Controller ──chama──► Interactor ──return──► Controller
                          │
                          └─ o Interactor "sabe" qual formato o
                             Controller espera de volta (acoplamento)

COM Output Port (dependência sempre para dentro):

Controller ──chama──► Input Port ──► Interactor ──chama──► Output Port ◄──implementa── Presenter
                                                                                            │
                                                                                            └─ o Presenter decide como
                                                                                               apresentar o resultado
```

Se o Interactor simplesmente retornasse um valor, ele precisaria conhecer o formato de saída esperado (JSON? HTML? um ViewModel específico?) — uma dependência do núcleo em direção à periferia. Com a Output Port, o Interactor apenas invoca um método abstrato (`apresentar(resultado)`), e é o Presenter — uma peça da camada de Interface Adapters — quem decide como formatar aquilo. O Interactor nunca sabe se o resultado vai virar um JSON, um HTML ou uma linha de log.

---

## Exemplo prático: fechando o ciclo com código

```java
// Use Case Input Port — interface de entrada, implementada pelo Interactor
public interface FecharPedidoInputPort {
    void executar(FecharPedidoRequest request);
}

// Use Case Output Port — interface de saída, implementada pelo Presenter
public interface FecharPedidoOutputPort {
    void apresentarSucesso(PedidoConfirmado confirmacao);
    void apresentarErro(String motivo);
}

// Use Case Interactor — a lógica de negócio em si
public class FecharPedidoInteractor implements FecharPedidoInputPort {
    private final PedidoRepository pedidoRepository; // Gateway
    private final FecharPedidoOutputPort outputPort;  // Output Port

    @Override
    public void executar(FecharPedidoRequest request) {
        Pedido pedido = pedidoRepository.buscarPorId(request.getPedidoId());

        if (pedido.getItens().isEmpty()) {
            outputPort.apresentarErro("Pedido vazio");
            return;
        }

        pedido.finalizar();
        pedidoRepository.salvar(pedido);
        outputPort.apresentarSucesso(new PedidoConfirmado(pedido.getId(), pedido.getData()));
    }
}

// Controller — recebe a requisição HTTP e aciona o Input Port
@RestController
public class PedidoController {
    private final FecharPedidoInputPort inputPort;

    @PostMapping("/pedidos/fechar")
    public void fechar(@RequestBody FecharPedidoRequest request) {
        inputPort.executar(request); // não recebe retorno diretamente daqui
    }
}

// Presenter — implementa a Output Port e decide o formato final
public class FecharPedidoPresenterHttp implements FecharPedidoOutputPort {
    private ResponseEntity<?> resposta;

    @Override
    public void apresentarSucesso(PedidoConfirmado confirmacao) {
        resposta = ResponseEntity.ok(new PedidoResponseJson(confirmacao));
    }

    @Override
    public void apresentarErro(String motivo) {
        resposta = ResponseEntity.badRequest().body(motivo);
    }
}
```

Note que o `PedidoController` nem precisa saber que existe um Presenter separado nesse desenho — ele só conhece a Input Port. Quem orquestra a ligação entre Interactor e Presenter concreto é a camada de Frameworks & Drivers (2.4), no momento da inicialização (injeção de dependência), exatamente como visto em 2.4.1.1.

## Simplificação comum na prática

Muitos projetos reais simplificam esse fluxo, fazendo o Interactor **retornar** um objeto de saída diretamente (em vez de chamar uma Output Port), e deixando o próprio Controller formatar a resposta. Isso é o que aconteceu nos exemplos de 2.2.1.1 e 2.3.1.1 deste guia — uma simplificação pragmática amplamente aceita, desde que a regra principal seja respeitada: **o Interactor nunca deve conhecer o formato final de apresentação** (JSON, HTML), apenas devolver um objeto de domínio ou DTO simples, deixando a formatação de fato a cargo do Controller ou de um Presenter explícito.

| Abordagem | Rigor | Uso mais comum |
|---|---|---|
| Output Port explícita (Presenter separado) | Mais fiel ao desenho original de Uncle Bob | Sistemas grandes, múltiplas formas de apresentação do mesmo resultado |
| Interactor retorna um objeto de domínio/DTO simples | Simplificação pragmática, ainda respeita a Regra da Dependência | A maioria dos projetos reais em produção |

## 🧩 Quiz de Fixação

1. Por que o Interactor chama uma Output Port em vez de simplesmente usar `return` para devolver o resultado ao Controller, no desenho original de Uncle Bob?
2. No exemplo de código, por que o `PedidoController` não precisa saber que existe uma classe `FecharPedidoPresenterHttp`?
3. Qual é a regra mínima que precisa ser respeitada mesmo quando um projeto simplifica o fluxo e faz o Interactor retornar um valor diretamente?

**Respostas:**
1) Porque, se o Interactor retornasse diretamente um valor, ele precisaria conhecer o formato de saída esperado pelo chamador (JSON, HTML, um ViewModel específico) — o que criaria uma dependência do núcleo (Use Case) em direção à periferia (formato de apresentação), violando a Regra da Dependência. Chamando uma Output Port abstrata, o Interactor delega a decisão de formatação para quem implementa essa interface (o Presenter), sem nunca conhecer os detalhes concretos.
2) Porque o Controller depende apenas da Input Port (a interface que ele chama para acionar o Use Case) — ele nunca interage diretamente com o Presenter ou com a Output Port. A ligação entre o Interactor e o Presenter concreto é feita pela camada de Frameworks & Drivers, na inicialização do sistema, mantendo o Controller isolado desse detalhe.
3) A regra mínima é que o Interactor nunca deve conhecer o formato final de apresentação (JSON, HTML, etc.) — ele deve devolver, no máximo, um objeto de domínio simples ou um DTO neutro, deixando a formatação de fato a cargo do Controller ou de um Presenter explícito. Mesmo simplificando a estrutura de portas, essa fronteira de responsabilidade precisa continuar existindo.
