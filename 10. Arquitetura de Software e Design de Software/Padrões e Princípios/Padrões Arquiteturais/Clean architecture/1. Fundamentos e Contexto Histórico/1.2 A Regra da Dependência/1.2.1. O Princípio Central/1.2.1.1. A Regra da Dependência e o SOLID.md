### A Regra da Dependência e o SOLID

O arquivo anterior (1.1.1.1) mostrou de onde vem a Clean Architecture e o que ela promete entregar. Este arquivo define a regra única que sustenta todas essas promessas — a Regra da Dependência — e mostra por que ela nada mais é do que o Princípio de Inversão de Dependência do SOLID aplicado à escala de uma arquitetura inteira.

---

## O enunciado da regra

**Pela Regra da Dependência, cada seta de dependência de código sempre aponta das camadas externas para as internas — nada nas camadas internas conhece ou depende diretamente de algo das camadas mais externas.** Uma classe em uma camada interna nunca deve importar, referenciar ou conhecer qualquer coisa de uma camada mais externa.

```
┌──────────────────────────────────────────────┐
│           Frameworks & Drivers                │
│  ┌──────────────────────────────────────┐    │
│  │       Interface Adapters               │    │
│  │  ┌──────────────────────────────┐    │    │
│  │  │        Use Cases               │    │    │
│  │  │  ┌──────────────────────┐    │    │    │
│  │  │  │      Entities          │    │    │    │
│  │  │  └──────────────────────┘    │    │    │
│  │  └──────────────────────────────┘    │    │
│  └──────────────────────────────────────┘    │
└──────────────────────────────────────────────┘

         Dependências sempre apontam PARA DENTRO
```

Isso garante que decisões de tecnologia (banco de dados, interface, frameworks) **não afetem o núcleo de regras de negócio**, e — igualmente importante — que o núcleo de regras de negócio nunca force uma mudança de tecnologia externa. O sistema fica mais resiliente a mudanças em ambas as direções, e mais fácil de testar em isolamento.

---

## Por que isso é literalmente o "D" do SOLID

O Princípio de Inversão de Dependência (Dependency Inversion Principle) diz: "módulos de alto nível não devem depender de módulos de baixo nível; ambos devem depender de abstrações." Na Clean Architecture, essa frase se traduz diretamente:

| Termo do SOLID | Equivalente na Clean Architecture |
|---|---|
| Módulo de alto nível | Entities e Use Cases (as camadas internas, que carregam as políticas de negócio) |
| Módulo de baixo nível | Interface Adapters e Frameworks & Drivers (as camadas externas, com os detalhes técnicos) |
| Abstração da qual ambos dependem | As interfaces (Ports/Gateways) definidas pelas camadas internas |

A diferença entre aplicar o DIP em uma única classe e aplicá-lo como a Regra da Dependência de uma arquitetura inteira é apenas de **escala**: em vez de inverter a dependência entre duas classes isoladas, a Clean Architecture aplica esse mesmo raciocínio a cada fronteira entre as quatro camadas concêntricas, de forma sistemática e obrigatória.

---

## Os quatro princípios fundamentais derivados da regra

A partir dessa única regra, quatro propriedades práticas emergem — e servem como checklist para saber se uma implementação está realmente seguindo a Clean Architecture:

| Princípio | O que garante |
|---|---|
| **Dependência unidirecional** | Camadas internas nunca dependem das externas — a seta de código só aponta para dentro |
| **Independência de frameworks** | O núcleo (Entities, Use Cases) não conhece tecnologias específicas — nenhuma anotação, nenhuma classe de biblioteca externa |
| **Testabilidade** | Camadas internas podem ser testadas isoladamente, sem subir banco de dados, servidor web ou qualquer infraestrutura |
| **Flexibilidade** | Tecnologias externas podem ser substituídas (banco, framework, UI) sem afetar o núcleo de regras de negócio |

Esses quatro princípios serão vistos em ação, camada por camada, ao longo do Domínio 2 deste guia — cada camada concêntrica existe justamente para sustentar essas quatro garantias.

---

## O que acontece quando a regra é violada

Um exemplo simples e comum de violação: uma classe `Pedido` (Entity, camada mais interna) importando uma anotação `@Entity` do JPA (um detalhe de Frameworks & Drivers, a camada mais externa). Mesmo sem nenhuma chamada explícita de método, essa dependência já existe — `Pedido` não compila nem funciona sem a biblioteca JPA no classpath, o que significa que a seta de dependência **saiu** do núcleo, na direção errada.

| Sintoma da violação | Consequência |
|---|---|
| Entity anotada com `@Entity`/`@Table` | O núcleo do sistema depende de uma decisão de persistência que deveria ser um detalhe substituível |
| Use Case recebendo um objeto `HttpServletRequest` | A lógica de aplicação depende do protocolo de transporte, tornando-a impossível de reutilizar em um contexto não-web |
| Entity lançando uma exceção de uma biblioteca externa (`SQLException`) | O tratamento de erro do núcleo fica amarrado a uma tecnologia específica |

Esses cenários serão retomados, com correções de código concretas, nos arquivos de "quando evitar/consequências" de cada camada, no Domínio 2.

## 🧩 Quiz de Fixação

1. Qual é o enunciado da Regra da Dependência, e em que direção as setas de dependência de código devem sempre apontar?
2. Como a Regra da Dependência se relaciona diretamente com o Princípio de Inversão de Dependência (o "D" do SOLID)?
3. Por que uma Entity anotada com `@Entity` do JPA é considerada uma violação da Regra da Dependência, mesmo que nenhuma linha de código dentro da classe chame explicitamente uma API do JPA?

**Respostas:**
1) A Regra da Dependência estabelece que o código-fonte só pode depender de elementos de camadas mais internas — nunca de camadas mais externas. As setas de dependência sempre apontam das camadas externas (Frameworks & Drivers) em direção às camadas internas (Entities), nunca o contrário.
2) A Regra da Dependência é a aplicação do Princípio de Inversão de Dependência na escala de uma arquitetura inteira: assim como o DIP diz que módulos de alto nível não devem depender de módulos de baixo nível (ambos devem depender de abstrações), a Clean Architecture faz com que as camadas internas (Entities, Use Cases) nunca dependam das camadas externas (Interface Adapters, Frameworks & Drivers), e a comunicação entre elas acontece através de interfaces/abstrações definidas pelas camadas internas.
3) Porque a anotação `@Entity` faz a classe depender diretamente da biblioteca JPA para sequer compilar e funcionar corretamente — mesmo sem uma chamada de método explícita, essa é uma dependência real e direta de uma camada externa (Frameworks & Drivers) dentro de uma camada interna (Entities), violando a direção obrigatória da Regra da Dependência.
