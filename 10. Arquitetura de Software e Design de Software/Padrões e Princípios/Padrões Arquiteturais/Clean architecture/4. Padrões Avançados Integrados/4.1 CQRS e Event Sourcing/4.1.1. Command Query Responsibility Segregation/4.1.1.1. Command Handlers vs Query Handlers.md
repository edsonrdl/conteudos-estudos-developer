### Command Handlers vs Query Handlers

Com as três primeiras camadas e o fluxo de dependência bem estabelecidos (Domínios 1-3), este arquivo abre o Domínio 4 mostrando como um padrão externo à Clean Architecture — o CQRS — se encaixa naturalmente dentro da camada de Use Cases.

---

## O que é CQRS e por que se encaixa na Clean Architecture

CQRS (Command Query Responsibility Segregation) separa operações de leitura e escrita em modelos distintos, **permitindo otimização independente e escalabilidade diferenciada** para cada um. Commands alteram estado sem retornar dados; Queries retornam dados sem modificar estado.

Esse padrão não é exclusivo da Clean Architecture — já apareceu como uma prática comum dentro da camada de Use Cases desde os primeiros exemplos deste guia (2.2.1.1). O que o CQRS formaliza é uma divisão explícita: em vez de um único Use Case genérico que às vezes lê e às vezes escreve, cada operação vira um **Handler** dedicado, seguindo apenas uma das duas responsabilidades.

---

## Implementação prática em C#

```csharp
// Command Handler — escreve, não retorna dados de negócio
public class CreateOrderCommandHandler : IRequestHandler<CreateOrderCommand, Guid>
{
    private readonly IOrderRepository _repository;
    private readonly IEventPublisher _eventPublisher;

    public async Task<Guid> Handle(CreateOrderCommand command, CancellationToken cancellationToken)
    {
        var order = Order.Create(command.CustomerId, command.Items);
        await _repository.AddAsync(order);

        // Publicar eventos de domínio (aprofundado em 4.2.1)
        await _eventPublisher.PublishAsync(order.DomainEvents);
        return order.Id;
    }
}

// Query Handler — lê, não modifica estado
public class GetOrderQueryHandler : IRequestHandler<GetOrderQuery, OrderDto>
{
    private readonly IOrderReadRepository _readRepository;

    public async Task<OrderDto> Handle(GetOrderQuery query, CancellationToken cancellationToken)
    {
        return await _readRepository.GetOrderProjectionAsync(query.OrderId);
    }
}
```

Repare em três detalhes que conectam diretamente com os domínios anteriores:

1. **`CreateOrderCommandHandler` depende de `IOrderRepository`** — uma interface (Secondary Port, na linguagem já vista no glossário da [[10. Arquitetura de Software e Design de Software/Padrões e Princípios/Padrões Arquiteturais/Hexagonal/0 Hexagonal (Glossário )|Arquitetura Hexagonal]]), nunca de uma implementação concreta — a mesma Inversão de Dependência vista em 3.2.1.1 e 3.2.2.1.
2. **`GetOrderQueryHandler` usa `IOrderReadRepository`, uma interface separada** — o modelo de leitura pode ser uma projeção otimizada (uma view materializada, uma tabela desnormalizada), diferente do modelo usado para escrever.
3. **Cada Handler tem uma única razão para existir** — o Command Handler nunca faz consultas complexas de exibição, e o Query Handler nunca altera estado. Isso é uma aplicação direta do Princípio de Responsabilidade Única (SRP) na camada de Use Cases.

## Onde cada peça vive nas quatro camadas concêntricas

| Peça | Camada |
|---|---|
| `CreateOrderCommand`, `GetOrderQuery` | Use Cases (representam a intenção, como visto em 2.2.1.1) |
| `CreateOrderCommandHandler`, `GetOrderQueryHandler` | Use Cases (o "Interactor" que executa a lógica) |
| `IOrderRepository`, `IOrderReadRepository` | Interfaces definidas pelo Domínio/Use Cases, implementadas na Infraestrutura |
| `OrderDto` | Objeto de transporte que atravessa a fronteira para o Presenter/Controller (2.3.1.1) |

---

## Por que separar modelos de leitura e escrita, na prática

| Sem CQRS (modelo único) | Com CQRS (modelos separados) |
|---|---|
| Uma única entidade precisa servir tanto para validar regras de negócio (escrita) quanto para exibir dados otimizados (leitura) | O modelo de escrita foca em invariantes e regras; o modelo de leitura foca em performance e formato de exibição |
| Consultas complexas de tela forçam a Entity a carregar dados que não fazem parte de sua responsabilidade de negócio | Queries podem ler diretamente de uma projeção/view, sem reconstruir o Aggregate completo |
| Escalar leitura e escrita juntos, mesmo com cargas de uso muito diferentes | Leitura e escrita podem escalar de forma independente (por exemplo, réplicas de leitura) |

## 🧩 Quiz de Fixação

1. Por que `CreateOrderCommandHandler` e `GetOrderQueryHandler` usam interfaces de repositório diferentes (`IOrderRepository` e `IOrderReadRepository`), em vez de compartilhar a mesma?
2. Qual princípio do SOLID o CQRS aplica diretamente ao separar Command Handlers de Query Handlers?
3. Em qual camada da Clean Architecture vivem os Handlers de Command e Query, e por que eles não pertencem à camada de Interface Adapters?

**Respostas:**
1) Porque as necessidades de escrita e leitura costumam ser diferentes: a escrita precisa carregar o Aggregate completo para validar invariantes de negócio, enquanto a leitura pode se beneficiar de uma projeção otimizada e desnormalizada, focada apenas em exibir dados rapidamente. Separar as interfaces permite que cada lado evolua e seja otimizado de forma independente.
2) O Princípio da Responsabilidade Única (Single Responsibility Principle, o "S" do SOLID) — cada Handler tem uma única razão para mudar: o Command Handler muda se a regra de escrita mudar, e o Query Handler muda se a forma de exibição dos dados mudar, nunca os dois ao mesmo tempo pela mesma causa.
3) Eles vivem na camada de Use Cases, porque são eles quem orquestram o fluxo — buscam dados via Secondary Ports, aplicam ou consultam regras de negócio, e retornam um resultado. Não pertencem aos Interface Adapters porque não fazem tradução de formato externo (HTTP, JSON) — essa tradução continua sendo responsabilidade do Controller, que apenas invoca o Handler correspondente.
