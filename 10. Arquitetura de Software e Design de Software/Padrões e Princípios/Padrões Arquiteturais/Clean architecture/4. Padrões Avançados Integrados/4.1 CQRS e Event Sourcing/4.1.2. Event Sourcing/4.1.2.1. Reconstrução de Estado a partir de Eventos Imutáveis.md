### Reconstrução de Estado a partir de Eventos Imutáveis

O arquivo anterior (4.1.1.1) mostrou o CQRS separando leitura e escrita. Este arquivo cobre outro padrão que se encaixa naturalmente dentro da camada de Entities: o Event Sourcing, uma forma radicalmente diferente de guardar o estado de um Aggregate.

---

## O que é Event Sourcing

Event Sourcing captura todas as mudanças de estado como uma sequência de **eventos imutáveis**. Em vez de guardar o estado atual de um objeto diretamente (uma linha em uma tabela `pedidos` com o valor mais recente de cada coluna), o sistema guarda **cada evento que já aconteceu** com aquele objeto — e o estado atual é **derivado** reproduzindo esses eventos em ordem.

Isso proporciona três benefícios que um modelo de estado tradicional não oferece facilmente: **auditoria completa** (todo evento fica registrado para sempre), **capacidade de reconstrução temporal** (é possível saber exatamente qual era o estado do Aggregate em qualquer momento do passado) e **debugging avançado** (reproduzir os eventos um a um revela exatamente a sequência que levou a um estado problemático).

---

## Estrutura de implementação

```java
public class OrderAggregate {
    private UUID id;
    private List<OrderItem> items = new ArrayList<>();
    private OrderStatus status;
    private List<DomainEvent> changes = new ArrayList<>();

    public void createOrder(UUID customerId, List<OrderItem> items) {
        OrderCreatedEvent event = new OrderCreatedEvent(UUID.randomUUID(), customerId, items);
        applyEvent(event);
        changes.add(event); // guarda o evento para ser persistido depois
    }

    private void applyEvent(OrderCreatedEvent event) {
        this.id = event.getOrderId();
        this.items = event.getItems();
        this.status = OrderStatus.CREATED;
    }

    // Reconstruir estado a partir de eventos históricos
    public static OrderAggregate fromEvents(List<DomainEvent> events) {
        OrderAggregate aggregate = new OrderAggregate();
        events.forEach(aggregate::applyEvent);
        return aggregate;
    }
}
```

O método `fromEvents` é o coração do padrão: em vez de um `Repository` fazer um `SELECT * FROM pedidos WHERE id = ?` e montar o objeto diretamente das colunas, ele busca **todos os eventos** associados àquele `id` (em ordem cronológica) e os reaplica um a um, através de `applyEvent`, até reconstruir o estado atual do zero.

```
Modelo tradicional (estado direto)          Event Sourcing (estado derivado)

Tabela "pedidos"                            Tabela "eventos"
┌────┬────────┬──────────┐                  ┌────┬─────────────────────┬──────────┐
│ id │ status │  total   │                  │ id │ tipo_evento         │ payload  │
├────┼────────┼──────────┤                  ├────┼─────────────────────┼──────────┤
│ 42 │ PAGO   │ 150.00   │                  │ 42 │ OrderCreatedEvent   │ {...}    │
└────┴────────┴──────────┘                  │ 42 │ ItemAddedEvent      │ {...}    │
                                             │ 42 │ PaymentReceivedEvent│ {...}    │
Uma linha = o estado atual                  └────┴─────────────────────┴──────────┘
(o histórico se perdeu)                     Estado atual = reproduzir os 3 eventos em ordem
```

## Onde o Event Sourcing vive nas camadas concêntricas

| Peça | Camada | Papel |
|---|---|---|
| `OrderAggregate`, `OrderCreatedEvent` | Entities | O Aggregate e seus eventos são regras de negócio puras — nenhuma dependência de banco |
| `fromEvents(List<DomainEvent>)` | Entities | Lógica de reconstrução, ainda dentro do domínio, sem saber como os eventos foram persistidos |
| Um "Event Store" que persiste e recupera a lista de eventos por `id` | Interface Adapters + Frameworks & Drivers | O Gateway que sabe gravar/ler eventos de um banco específico (aprofundado em domínio futuro sobre persistência de eventos) |

A regra de dependência (1.2.1.1) se mantém: `OrderAggregate` não sabe como os eventos chegam até ele — apenas recebe uma `List<DomainEvent>` já carregada e sabe reconstruir o estado a partir dela. Quem busca essa lista no banco é responsabilidade de uma camada mais externa.

---

## Trade-off central: o que se ganha e o que custa

| Ganho | Custo |
|---|---|
| Auditoria completa e nativa — todo evento fica registrado para sempre | Consultas de leitura simples (como "todos os pedidos pagos") ficam mais difíceis sem um modelo de leitura complementar |
| Reconstrução do estado em qualquer ponto do passado (útil para depuração e conformidade regulatória) | Reconstruir um Aggregate com um histórico muito longo de eventos pode ficar lento sem otimizações (snapshots) |
| Naturalmente compatível com CQRS — os eventos alimentam projeções de leitura otimizadas | Maior complexidade conceitual e operacional do que simplesmente atualizar uma linha em uma tabela |

Por esse motivo, Event Sourcing costuma aparecer combinado com CQRS (visto em 4.1.1.1): os mesmos eventos que reconstroem o Aggregate para escrita também alimentam projeções de leitura otimizadas, resolvendo o principal ponto fraco do padrão.

## 🧩 Quiz de Fixação

1. Qual é a diferença fundamental entre o modelo tradicional de persistência (uma linha por registro) e o Event Sourcing, em termos do que é efetivamente armazenado?
2. No método `fromEvents`, por que o `OrderAggregate` não precisa saber de onde vieram os eventos (banco relacional, banco de documentos, um arquivo)?
3. Por que Event Sourcing costuma ser combinado com CQRS na prática, em vez de usado isoladamente?

**Respostas:**
1) No modelo tradicional, apenas o estado atual é armazenado — cada atualização sobrescreve os valores anteriores, e o histórico de como se chegou àquele estado se perde. No Event Sourcing, cada mudança de estado é armazenada como um evento imutável e permanente, e o estado atual é sempre derivado (calculado) a partir da sequência completa de eventos.
2) Porque o método `fromEvents` recebe apenas uma `List<DomainEvent>` já pronta como parâmetro — a responsabilidade de buscar esses eventos em algum mecanismo de armazenamento (um Event Store, um banco relacional, etc.) pertence a uma camada mais externa (Interface Adapters/Frameworks & Drivers). O Aggregate, na camada de Entities, só sabe reaplicar eventos que já recebeu, mantendo a Regra da Dependência intacta.
3) Porque o Event Sourcing, sozinho, torna consultas de leitura mais difíceis — reconstruir o estado de um Aggregate a cada consulta simples seria ineficiente. Combinando com CQRS, os mesmos eventos gerados pela escrita são usados para alimentar projeções de leitura otimizadas e já prontas para consulta, resolvendo justamente essa limitação.
