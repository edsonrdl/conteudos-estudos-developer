### Testes de Domínio Puros vs Testes de Aplicação com Mocks

Um dos maiores ganhos práticos da Clean Architecture é a testabilidade — mas esse ganho só se realiza se os testes forem escritos de forma coerente com as camadas que estão testando. Testar a Entity da mesma forma que se testa o Use Case (ou vice-versa) desperdiça exatamente a separação que a arquitetura foi desenhada para proporcionar. Este arquivo detalha como testar cada camada de forma apropriada ao seu nível de responsabilidade.

---

## Por que a estratégia de teste muda por camada

**Analogia:** pense em testar um carro. Para testar se o motor funciona corretamente, você o coloca numa bancada de testes isolada — sem rodas, sem carroceria, sem sistema elétrico do painel — e mede rotação, torque, consumo. Você não precisa do carro inteiro montado para saber se o motor está com defeito. Mas para testar se o painel exibe a velocidade correta quando o carro acelera, você precisa de outra coisa: um "motor simulado" (um mock) que produza sinais de RPM controlados, para verificar se o painel reage certo — sem precisar de um motor de verdade rodando.

A **Entity** é o motor: um componente isolado, sem dependências externas, que deve ser testável sozinho, sem infraestrutura nenhuma. O **Use Case** é o painel: ele não faz a lógica de negócio sozinho, ele orquestra colaboradores (repositórios, gateways, publishers) — e testá-lo bem significa simular esses colaboradores, não usá-los de verdade.

---

## Testes de Domain Layer: puros, sem dependências

Uma Entity bem projetada não depende de banco de dados, de frameworks ou de qualquer infraestrutura — portanto, testá-la não deveria exigir nenhuma dessas coisas. Um teste de Entity instancia o objeto diretamente, chama um método, e verifica o resultado ou a exceção lançada. Nenhum mock é necessário, porque não há nenhuma dependência externa a substituir.

```csharp
[Test]
public void Account_Withdraw_ShouldThrowException_WhenInsufficientFunds()
{
    // Arrange
    var account = new Account(AccountId.New(), Money.Of(100));
    var withdrawAmount = Money.Of(150);

    // Act & Assert
    Assert.Throws<InsufficientFundsException>(() =>
        account.Withdraw(withdrawAmount)
    );
}
```

Repare no que **não existe** neste teste: não há banco de dados, não há `Setup()` de mock, não há `async/await` esperando uma chamada de rede. É apenas `new Account(...)` seguido de uma chamada de método e uma asserção. Esse tipo de teste roda em milissegundos e não pode quebrar por motivos externos (rede instável, banco fora do ar) — só quebra se a regra de negócio realmente mudou ou se há um bug real na Entity.

```
┌─────────────────────────────────────┐
│   TESTE DE DOMAIN LAYER               │
│                                        │
│   var account = new Account(...)      │  ← instancia direta, sem framework
│   account.Withdraw(amount)            │  ← chama método real
│   Assert...                           │  ← verifica resultado/exceção
│                                        │
│   Nenhuma dependência externa.        │
│   Nenhum mock necessário.             │
└─────────────────────────────────────┘
```

## Testes de Application Layer: com mocks/doubles

O Use Case, por outro lado, **depende** de colaboradores externos — repositórios, publishers de eventos, gateways de pagamento — através de interfaces (Ports). Testar o Use Case de forma isolada significa **substituir cada uma dessas dependências por um mock** (ou outro tipo de test double), controlando exatamente o que cada uma retorna, para poder verificar se o Use Case orquestra a lógica corretamente.

```csharp
[Test]
public async Task TransferMoney_ShouldSucceed_WhenAccountsExistAndHaveFunds()
{
    // Arrange
    var sourceAccount = new Account(sourceAccountId, Money.Of(500));
    var targetAccount = new Account(targetAccountId, Money.Of(100));

    _accountRepository.GetByIdAsync(sourceAccountId).Returns(sourceAccount);
    _accountRepository.GetByIdAsync(targetAccountId).Returns(targetAccount);

    var command = new TransferMoneyCommand(sourceAccountId, targetAccountId, Money.Of(200));

    // Act
    var result = await _transferMoneyHandler.Handle(command, CancellationToken.None);

    // Assert
    result.IsSuccess.Should().BeTrue();
    await _accountRepository.Received(2).SaveAsync(Arg.Any<Account>());
}
```

Aqui, `_accountRepository` é um mock (usando NSubstitute, no exemplo) — não é um banco de dados real. O teste configura o mock para devolver contas específicas quando consultado (`GetByIdAsync(...).Returns(...)`), executa o Use Case, e depois verifica **duas coisas diferentes**:

1. **O resultado da operação** (`result.IsSuccess.Should().BeTrue()`) — a regra de negócio foi aplicada corretamente?
2. **A interação com o colaborador** (`_accountRepository.Received(2).SaveAsync(...)`) — o Use Case realmente chamou o repositório para persistir as duas contas alteradas?

Esse segundo tipo de asserção — verificar *como* um colaborador foi chamado, não apenas o resultado final — só faz sentido em testes de Use Case. Numa Entity pura, não existiria "colaborador" a verificar.

```
┌───────────────────────────────────────────────────┐
│   TESTE DE APPLICATION LAYER                        │
│                                                       │
│   mock(_accountRepository)                           │  ← substitui dependência real
│         .GetByIdAsync(id).Returns(account)            │  ← controla o que ela retorna
│                                                       │
│   handler.Handle(command)                             │  ← executa o Use Case real
│                                                       │
│   Assert result.IsSuccess                             │  ← verifica o resultado
│   Assert repository.Received(2).SaveAsync(...)        │  ← verifica a interação
└───────────────────────────────────────────────────┘
```

## Comparativo direto

| Aspecto | Testes de Domain Layer | Testes de Application Layer |
|---|---|---|
| O que é testado | A Entity/Value Object isoladamente | O Use Case orquestrando colaboradores |
| Dependências externas | Nenhuma | Substituídas por mocks/doubles |
| Velocidade de execução | Muito rápida (microssegundos a milissegundos) | Rápida, mas um pouco mais lenta (setup de mocks) |
| O que se verifica | Resultado do método / exceção lançada | Resultado final **e** como os colaboradores foram chamados |
| Causa mais comum de falha | Regra de negócio quebrada de verdade | Regra de negócio quebrada, ou mock configurado incorretamente |
| Fragilidade a mudanças de infraestrutura | Nenhuma (não depende de nada externo) | Baixa, mas pode quebrar se a assinatura do Port mudar |

## Erro comum: testar o Use Case como se fosse um teste de integração

Um erro frequente é substituir os mocks por implementações reais (banco de dados de verdade, gateway de pagamento real) dentro do teste do Use Case, achando que isso "testa mais". O problema é que isso transforma um teste de unidade — que deveria rodar em milissegundos, isolado — em um teste de integração, lento e frágil a fatores externos (conexão de rede, estado do banco). Testes de integração continuam tendo valor, mas são uma categoria **diferente**, com objetivo diferente: verificar se o Adapter concreto (ex: implementação JPA do repositório) realmente conversa bem com o banco de dados real — não se a lógica do Use Case está correta.

| Tipo de teste | Testa | Usa dependências reais? |
|---|---|---|
| Teste de unidade da Entity | Regra de negócio pura | Não — nunca precisa |
| Teste de unidade do Use Case | Orquestração da lógica de aplicação | Não — usa mocks dos Ports |
| Teste de integração do Adapter | Se a implementação concreta (JPA, HTTP client) funciona contra o sistema real | Sim — banco de dados/API reais (geralmente em container de teste) |

## Quando usar e limitações

**Quando usar testes de domínio puros:**
- Sempre que uma Entity ou Value Object tiver qualquer lógica não trivial (validações, cálculos, transições de estado).
- Como primeira linha de defesa — são os testes mais baratos de escrever e mais rápidos de rodar, então devem cobrir a maior parte das regras de negócio.

**Quando usar testes de aplicação com mocks:**
- Para verificar que o Use Case orquestra corretamente múltiplos colaboradores (ex: chama o repositório certo, publica o evento certo, na ordem certa).
- Para testar caminhos de erro que dependem do comportamento de um colaborador (ex: "o que acontece se o repositório não encontrar a conta?").

**Limitações e armadilhas:**
- **Mocks excessivos escondem bugs de integração real**: um teste de Use Case 100% mockado nunca vai pegar um problema real de mapeamento entre a Entity e a tabela do banco — para isso, testes de integração do Adapter continuam necessários.
- **Verificar interação demais em vez de comportamento**: testes que verificam `Received(1).MethodX()` para todo método chamado, em vez de focar no resultado observável, tendem a quebrar toda vez que o Use Case é refatorado internamente, mesmo sem mudança de comportamento — prefira verificar apenas as interações que realmente importam para o contrato do Use Case (ex: "a conta foi salva" importa; "o repositório foi chamado exatamente nesta ordem interna" geralmente não).
- **Confundir teste de Use Case com teste de Controller**: o teste de Use Case não deve envolver HTTP, serialização JSON ou roteamento — isso pertence à camada de Interface Adapters, testada separadamente.

## 🧩 Quiz de Fixação

1. Por que o teste de `Account.Withdraw` não usa nenhum mock, enquanto o teste de `TransferMoneyHandler` usa um mock para `_accountRepository`?
2. No teste do Use Case, por que a asserção `_accountRepository.Received(2).SaveAsync(...)` é tão importante quanto `result.IsSuccess.Should().BeTrue()`?
3. Qual é o problema de substituir os mocks de um teste de Use Case por implementações reais (banco de dados de verdade), achando que isso deixa o teste "mais completo"?

**Respostas:**
1) Porque `Account` é uma Entity — não tem nenhuma dependência externa, então pode ser instanciada e testada diretamente. Já `TransferMoneyHandler` é um Use Case que depende de um repositório (`IAccountRepository`) para buscar e salvar contas; para testar o Use Case isoladamente, sem depender de um banco de dados real, essa dependência precisa ser substituída por um mock controlado pelo teste.
2) Porque um teste de Use Case precisa verificar não só o resultado final da operação, mas também se o Use Case de fato orquestrou seus colaboradores corretamente. Se `result.IsSuccess` fosse `true` mas o repositório nunca tivesse sido chamado para salvar as contas alteradas, a transferência pareceria bem-sucedida no teste, mas as mudanças nunca seriam persistidas de verdade em produção — por isso verificar a interação com o mock é essencial para capturar esse tipo de bug.
3) Isso transforma um teste de unidade (rápido, isolado, determinístico) em um teste de integração (mais lento, dependente de infraestrutura externa, sujeito a falhas por motivos alheios à lógica de negócio, como rede instável ou banco de dados fora do ar). Além disso, mistura duas responsabilidades de teste diferentes: verificar se a lógica de orquestração do Use Case está correta (que deveria ser rápido e isolado) e verificar se a implementação concreta do repositório realmente funciona contra um banco real (que é responsabilidade de um teste de integração do Adapter, uma categoria separada).
