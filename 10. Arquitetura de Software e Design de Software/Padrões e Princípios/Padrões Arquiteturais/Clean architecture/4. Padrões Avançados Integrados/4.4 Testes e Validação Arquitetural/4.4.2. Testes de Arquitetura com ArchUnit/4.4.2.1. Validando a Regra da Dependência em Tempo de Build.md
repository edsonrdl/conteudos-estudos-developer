### Validando a Regra da Dependência em Tempo de Build

O arquivo anterior (4.4.1.1) tratou de testes que verificam **comportamento** — se a lógica de negócio produz o resultado certo. Este arquivo trata de um tipo de teste diferente: testes que verificam **estrutura** — se o código está organizado nas camadas corretas, respeitando a direção de dependência que sustenta toda a Clean Architecture. Sem esse tipo de verificação automatizada, a Regra da Dependência sobrevive apenas na disciplina dos desenvolvedores e na atenção do revisor de código — o que, em times grandes e sob prazo apertado, tende a falhar silenciosamente.

---

## O problema: a Regra da Dependência não se impõe sozinha

Nada no compilador de Java, C# ou TypeScript impede, por padrão, que uma classe dentro do pacote `domain` importe uma classe do pacote `infrastructure`. A linguagem permite. O `import` compila. Os testes de negócio continuam passando. E, ainda assim, a arquitetura foi violada: a partir desse ponto, a Entity mais protegida do sistema depende de um detalhe de banco de dados, e trocar essa tecnologia de infraestrutura deixa de ser trivial.

**Analogia:** pense na Regra da Dependência como uma regra de trânsito — "só se pode virar à direita nesta rua". Uma placa de sinalização (a documentação, o code review) *pede* para os motoristas obedecerem, mas não impede fisicamente ninguém de virar à esquerda. Um Architecture Test é como uma barreira física ou uma câmera com multa automática: transforma a regra de "esperança de que todos obedeçam" em algo verificado e aplicado mecanicamente, toda vez que o código passa pelo pipeline de build.

---

## Como funciona um Architecture Test

Um Architecture Test não executa a lógica de negócio — ele **analisa a estrutura estática do código compilado** (classes, namespaces/pacotes, referências entre eles) e verifica se essa estrutura obedece a regras declaradas. Se uma classe do domínio importar algo da infraestrutura, o teste falha, exatamente como falharia um teste comum — só que em vez de verificar um `Assert.AreEqual`, ele verifica uma regra de dependência entre pacotes.

```csharp
[Test]
public void Domain_ShouldNotDependOn_ApplicationOrInfrastructure()
{
    var result = Types.InCurrentDomain()
        .That()
        .ResideInNamespace("MyApp.Domain")
        .ShouldNot()
        .HaveDependencyOnAny("MyApp.Application", "MyApp.Infrastructure")
        .GetResult();

    Assert.IsTrue(result.IsSuccessful,
        $"Domain layer has forbidden dependencies: {string.Join(", ", result.FailingTypes)}");
}
```

Esse teste (no estilo de bibliotecas como o ArchUnitNET, para .NET) declara, em código executável: "nenhuma classe no namespace `MyApp.Domain` pode ter dependência em `MyApp.Application` ou `MyApp.Infrastructure`". Se um desenvolvedor, por engano ou pressa, adicionar `using MyApp.Infrastructure.Persistence;` dentro de uma classe de `MyApp.Domain`, esse teste falha no próximo build — antes mesmo de chegar a um Pull Request revisado por humanos.

---

## O exemplo canônico: ArchUnit (Java)

A biblioteca mais conhecida para esse tipo de teste é a **ArchUnit**, no ecossistema Java, com uma DSL fluente especificamente desenhada para expressar arquiteturas em camadas:

```java
@ArchTest
static final ArchRule layered_architecture = layeredArchitecture()
    .layer("Controllers").definedBy("..controller..")
    .layer("UseCases").definedBy("..usecase..")
    .layer("Domain").definedBy("..domain..")

    .whereLayer("Controllers").mayNotBeAccessedByAnyLayer()
    .whereLayer("UseCases").mayOnlyBeAccessedByLayers("Controllers")
    .whereLayer("Domain").mayOnlyBeAccessedByLayers("UseCases");
```

Esse teste declara a arquitetura inteira de uma vez, de forma declarativa:
- `Controllers` não pode ser acessado por **nenhuma** outra camada (ele é o ponto de entrada, não deveria ser importado por ninguém).
- `UseCases` só pode ser acessado por `Controllers` (nem `Domain` nem qualquer outra coisa deveria chamar um Use Case diretamente, pulando o Controller).
- `Domain` só pode ser acessado por `UseCases` (reforçando que nada além da camada de aplicação chama diretamente uma Entity).

Rodar esse `@ArchTest` como parte da suíte de testes normal (JUnit, no caso do ArchUnit) significa que **qualquer violação da Regra da Dependência quebra o build**, do mesmo jeito que um teste de negócio quebrado quebraria.

## Onde isso se encaixa no pipeline

```
┌──────────────────────────────────────────────────────────┐
│  Pull Request aberto                                       │
└───────────────┬─────────────────────────────────────────┘
                 │
                 ▼
┌──────────────────────────────────────────────────────────┐
│  Pipeline de CI                                             │
│                                                               │
│   1. Testes de Domain Layer (puros)         ─── passa        │
│   2. Testes de Application Layer (mocks)    ─── passa        │
│   3. Architecture Tests (ArchUnit)          ─── FALHA         │
│         └─► "Domain layer has forbidden                     │
│              dependency on Infrastructure"                  │
│                                                               │
│  Build quebra ANTES do merge — violação nunca chega          │
│  a produção, mesmo que a lógica de negócio estivesse OK.     │
└──────────────────────────────────────────────────────────┘
```

O ponto central: um Architecture Test não substitui os testes de comportamento (Domain/Application) — ele adiciona uma **terceira categoria**, que verifica algo que nenhum teste de comportamento consegue capturar: a lógica pode estar perfeitamente correta e, ainda assim, a arquitetura pode estar sendo violada silenciosamente.

---

## Comparativo: revisão manual vs. Architecture Tests automatizados

| Aspecto | Revisão manual de código (code review) | Architecture Tests automatizados |
|---|---|---|
| Consistência | Depende da atenção e experiência de quem revisa | Sempre aplica a mesma regra, sem exceção |
| Velocidade de feedback | Minutos a horas (depende de disponibilidade do revisor) | Segundos, no próprio build |
| Escala com o time | Piora conforme o time cresce (mais PRs, menos atenção por PR) | Não degrada — a regra roda igual, não importa quantos PRs existam |
| Cobre violações sutis | Fácil deixar passar um `import` indevido em meio a um PR grande | Detecta qualquer violação, por menor que seja, de forma mecânica |
| Custo de manutenção | Baixo custo inicial, alto custo de atenção contínua | Custo inicial de escrever as regras; depois, manutenção baixa |

## Quando usar e limitações

**Quando usar:**
- Em qualquer projeto de médio a grande porte onde a Regra da Dependência é central para o design (Clean Architecture, Hexagonal, Onion) e o time tem mais de 2-3 desenvolvedores — a partir daí, depender só de disciplina humana se torna arriscado.
- Como parte obrigatória do pipeline de CI, junto com os testes de unidade — não como uma verificação opcional ou manual.
- Para documentar a arquitetura de forma executável: um novo desenvolvedor pode ler as regras do ArchUnit e entender instantaneamente quais dependências são proibidas, sem precisar de um documento de arquitetura separado (que facilmente fica desatualizado).

**Limitações:**
- **Falso senso de segurança**: um Architecture Test garante que a *estrutura* de pacotes/namespaces está correta, mas não garante que o *design* dentro de cada camada seja bom — uma Entity anêmica (sem comportamento, só getters/setters) passa perfeitamente em qualquer Architecture Test, mesmo sendo um anti-padrão.
- **Precisa ser mantido junto com a arquitetura**: se o projeto introduzir uma nova camada ou pacote, as regras do ArchUnit precisam ser atualizadas — regras desatualizadas tanto podem barrar código legítimo quanto deixar passar violações que uma regra mais específica pegaria.
- **Não substitui entendimento arquitetural do time**: a ferramenta aplica regras que alguém precisa ter definido corretamente primeiro; um time sem entendimento da Regra da Dependência pode escrever regras de ArchUnit frouxas demais e ter uma falsa sensação de proteção.

## 🧩 Quiz de Fixação

1. Por que um teste de negócio (Domain/Application) pode passar perfeitamente mesmo quando a Regra da Dependência foi violada, e por que isso exige uma categoria de teste separada?
2. No exemplo em Java com ArchUnit, o que significa a regra `.whereLayer("UseCases").mayOnlyBeAccessedByLayers("Controllers")`, e que tipo de violação ela impediria?
3. Por que um Architecture Test que passa 100% não é garantia de que o design das camadas internamente está bom?

**Respostas:**
1) Porque testes de Domain e Application verificam *comportamento* — se o resultado de uma operação está correto — não *estrutura* — de onde vêm as dependências de cada classe. É perfeitamente possível uma Entity calcular tudo certinho mesmo importando uma classe de infraestrutura por engano; o teste de comportamento não teria como perceber isso, porque ele nunca inspeciona os `imports`/`usings` do arquivo. Por isso é necessária uma categoria de teste separada, que analisa a estrutura estática do código, não sua execução.
2) Significa que a camada `UseCases` só pode ser referenciada (importada, chamada) pela camada `Controllers` — nenhuma outra camada tem permissão de acessar um Use Case diretamente. Isso impediria, por exemplo, que uma Entity do `Domain` chamasse um Use Case diretamente (inversão errada de quem depende de quem) ou que um componente de infraestrutura pulasse a camada de Controllers e chamasse um Use Case sem passar pela camada de entrada apropriada.
3) Porque o Architecture Test verifica apenas a direção e a existência de dependências entre pacotes/namespaces — ele não avalia a qualidade do código dentro de cada camada. Uma Entity pode estar tecnicamente no pacote `domain`, sem nenhuma dependência proibida, e ainda assim ser um Anemic Domain Model (só getters/setters, sem nenhuma regra de negócio) — um anti-padrão que nenhuma regra estrutural de ArchUnit é capaz de detectar, porque isso é uma questão de qualidade de design, não de estrutura de dependências.
