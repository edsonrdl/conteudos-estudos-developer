### Saga Pattern — Transações Distribuídas com Compensação

O arquivo anterior (4.2.1.1) mostrou como um Use Case reage a um fato já ocorrido dentro do mesmo processo, através de Domain Events. Mas e quando uma operação de negócio precisa coordenar múltiplos passos que **não podem ser revertidos por uma transação de banco de dados única** — por exemplo, porque cada passo acontece em um serviço, banco ou processo diferente? É esse o problema que o Saga Pattern resolve.

---

## O problema: transações que atravessam fronteiras

Numa aplicação monolítica com um único banco de dados, uma operação como "finalizar pedido" pode ser envolvida numa transação ACID: se qualquer passo falhar, um `ROLLBACK` desfaz tudo automaticamente. Mas em um cenário distribuído — múltiplos microsserviços, cada um com seu próprio banco — não existe um `ROLLBACK` que atravesse serviços.

A solução tradicional para isso seria o **Two-Phase Commit (2PC)**: um coordenador pergunta a todos os participantes "você está pronto para commitar?" e só efetiva a transação se todos responderem que sim. O problema do 2PC é que ele exige que todos os participantes fiquem **bloqueados**, aguardando a decisão final — isso não escala bem, é frágil a falhas de rede e é incompatível com a maioria dos brokers de mensageria e serviços de terceiros.

O Saga Pattern resolve o mesmo problema de outra forma: em vez de uma transação distribuída bloqueante, a operação é dividida em uma **sequência de transações locais**, cada uma completa e commitada isoladamente. Se um passo falhar no meio do caminho, em vez de um rollback automático, a saga executa **ações de compensação** — transações locais que desfazem, do ponto de vista de negócio, o efeito dos passos anteriores já commitados.

**Analogia:** pense em uma viagem com múltiplas reservas independentes — hotel, passagem aérea e aluguel de carro, cada uma feita com uma empresa diferente. Não existe um "cancelamento único" que desfaça as três de uma vez, porque não há uma transação global entre essas empresas. Se o aluguel do carro falhar depois que hotel e passagem já foram confirmados, a solução não é mágica: é **cancelar manualmente** o hotel e a passagem já reservados (as compensações), uma a uma.

---

## Sequência de passos locais e compensações

```
Fluxo feliz (todos os passos completam):

  ValidarPedido ──► ProcessarPagamento ──► ReservarEstoque ──► ConfirmarPedido
       ✓                    ✓                    ✓                  ✓


Fluxo com falha (ReservarEstoque falha):

  ValidarPedido ──► ProcessarPagamento ──► ReservarEstoque
       ✓                    ✓                  ✗ FALHOU
                                                   │
                     ┌─────────────────────────────┘
                     ▼
         Compensação na ordem REVERSA dos passos já commitados:

  EstornarPagamento ◄── (compensa ProcessarPagamento)
       ✓
  (ValidarPedido normalmente não precisa de compensação —
   é uma leitura/checagem, não uma escrita com efeito colateral)
```

Cada passo da saga tem, tipicamente, dois métodos: a ação direta (`Execute`) e sua compensação (`Compensate`). Nem todo passo precisa de compensação — um passo somente de leitura, como validar se o pedido existe, normalmente não altera estado e não precisa ser desfeito.

---

## Implementação: Saga Orquestrada

Existem duas formas principais de coordenar uma saga: **orquestração** (um componente central comanda cada passo, sabendo a sequência completa) e **coreografia** (cada serviço reage a eventos publicados pelos outros, sem um coordenador central). A orquestração é mais fácil de entender e depurar por ter o fluxo explícito em um único lugar; a coreografia é mais desacoplada, mas o fluxo fica implícito, espalhado entre os handlers de evento de cada serviço.

O exemplo abaixo usa orquestração — o padrão mais comum para começar:

```csharp
public class OrderProcessingSaga
{
    private readonly List<ISagaStep> _steps;

    public OrderProcessingSaga()
    {
        _steps = new List<ISagaStep>
        {
            new ValidateOrderStep(),
            new ProcessPaymentStep(),
            new ReserveInventoryStep(),
            new ConfirmOrderStep()
        };
    }

    public async Task<bool> ProcessOrderAsync(ProcessOrderCommand command)
    {
        var sagaId = Guid.NewGuid();
        var context = new SagaContext(sagaId, command);
        var executedSteps = new Stack<ISagaStep>();

        try
        {
            foreach (var step in _steps)
            {
                await step.ExecuteAsync(context);
                executedSteps.Push(step); // só empilha depois de confirmar sucesso
            }

            return true;
        }
        catch (SagaStepException ex)
        {
            // Compensar apenas os passos que de fato foram executados,
            // na ordem inversa em que aconteceram
            while (executedSteps.Count > 0)
            {
                var stepToCompensate = executedSteps.Pop();
                await stepToCompensate.CompensateAsync(context);
            }

            return false;
        }
    }
}

public interface ISagaStep
{
    Task ExecuteAsync(SagaContext context);
    Task CompensateAsync(SagaContext context);
}

public class ProcessPaymentStep : ISagaStep
{
    private readonly IPaymentGateway _paymentGateway;

    public async Task ExecuteAsync(SagaContext context)
    {
        var result = await _paymentGateway.ChargeAsync(context.PaymentInfo);
        if (!result.Success)
            throw new SagaStepException(nameof(ProcessPaymentStep), result.ErrorMessage);

        context.PaymentTransactionId = result.TransactionId; // guarda dado necessário à compensação
    }

    public async Task CompensateAsync(SagaContext context)
    {
        // Ação de compensação: estornar o valor já cobrado
        await _paymentGateway.RefundAsync(context.PaymentTransactionId);
    }
}
```

Repare em dois pontos importantes desse código:

1. **`executedSteps` só recebe um passo depois que ele termina com sucesso.** Isso garante que a compensação só rode sobre passos que de fato tiveram efeito colateral — nunca sobre um passo que ainda nem começou ou que falhou antes de completar.
2. **O `SagaContext` carrega dados entre passos**, como o `PaymentTransactionId`. A compensação de um passo geralmente precisa de informação produzida por esse mesmo passo (não é possível estornar um pagamento sem saber qual transação estornar).

## Onde a Saga se encaixa na Clean Architecture

| Camada | Papel na Saga |
|---|---|
| **Use Cases** | O orquestrador da saga (`OrderProcessingSaga`) vive aqui — ele é, em essência, um Use Case mais complexo que coordena outros Use Cases/steps |
| **Entities** | Cada Entity envolvida (`Order`, `Payment`) continua validando suas próprias invariantes dentro de cada passo local |
| **Interface Adapters** | Os steps dependem de interfaces (`IPaymentGateway`, `IInventoryService`) — nunca de SDKs concretos |
| **Frameworks & Drivers** | A implementação real do gateway de pagamento, a fila de mensageria (se a saga for assíncrona) e o mecanismo de persistência do estado da saga |

A saga não é uma camada nova — ela é um Use Case que orquestra outros componentes, respeitando a mesma Regra da Dependência: o orquestrador depende de abstrações (`ISagaStep`, `IPaymentGateway`), nunca de implementações concretas de infraestrutura.

---

## Orquestração vs. Coreografia

| Aspecto | Orquestração | Coreografia |
|---|---|---|
| Coordenação | Um componente central (`OrderProcessingSaga`) comanda cada passo explicitamente | Cada serviço reage a eventos publicados pelos outros, sem coordenador central |
| Visibilidade do fluxo | Alta — o fluxo completo está em um único lugar, fácil de ler e depurar | Baixa — o fluxo está implícito, espalhado entre handlers de eventos em vários serviços |
| Acoplamento | O orquestrador conhece todos os passos (mas os passos não se conhecem entre si) | Nenhum serviço conhece o fluxo completo — apenas reage a eventos que lhe interessam |
| Ponto único de falha | O orquestrador é um componente crítico — se ele cair no meio de uma saga, o estado precisa ser recuperável | Não há orquestrador central, mas rastrear "onde a saga está" é mais difícil |
| Quando preferir | Fluxos com muitos passos e regras de compensação complexas, onde clareza importa mais | Fluxos simples, com poucos participantes, onde o desacoplamento total compensa a perda de visibilidade |

## Quando usar e limitações

**Quando usar:**
- Operações de negócio que precisam coordenar múltiplos serviços ou bancos de dados independentes, onde uma transação distribuída (2PC) não é viável ou desejável.
- Fluxos de negócio de longa duração (ex: processo de checkout que envolve pagamento, estoque e envio, cada um podendo levar segundos ou minutos).
- Cenários de microsserviços onde cada serviço deve manter autonomia sobre seu próprio banco de dados.

**Limitações e armadilhas comuns:**
- **Consistência eventual, não imediata**: entre o início e o fim de uma saga, o sistema passa por estados intermediários onde nem tudo está consistente ainda (ex: pagamento processado, mas estoque ainda não reservado). O restante do sistema precisa saber lidar com isso.
- **Nem toda ação é compensável de verdade**: "enviar um e-mail" não pode ser desfeito com um "des-envio". Nesses casos, a compensação costuma ser uma ação corretiva (enviar um segundo e-mail de cancelamento), não uma reversão literal.
- **Complexidade de estado**: a saga precisa persistir em qual passo está, para poder retomar ou compensar corretamente após uma falha do próprio processo orquestrador (queda do servidor no meio da execução, por exemplo).
- **Não é substituto de transação local**: dentro de um único serviço, com um único banco, a saga é over-engineering — uma transação de banco de dados tradicional resolve com muito menos complexidade.

## 🧩 Quiz de Fixação

1. Por que o Saga Pattern usa uma sequência de transações locais com compensação, em vez de um Two-Phase Commit (2PC), para coordenar operações entre múltiplos serviços?
2. No exemplo de código, por que `executedSteps.Push(step)` só acontece **depois** que `step.ExecuteAsync(context)` termina com sucesso, e não antes?
3. Qual a diferença fundamental entre orquestração e coreografia na implementação de uma saga, e quando cada uma é preferível?

**Respostas:**
1) Porque o 2PC exige que todos os participantes fiquem bloqueados aguardando uma decisão final de commit, o que não escala bem em sistemas distribuídos e é incompatível com a maioria dos brokers de mensageria e serviços de terceiros. O Saga Pattern evita esse bloqueio dividindo a operação em transações locais independentes, cada uma commitada isoladamente, e usa compensações explícitas para desfazer o efeito de passos já executados caso algo falhe adiante.
2) Porque a lista `executedSteps` representa os passos que **de fato tiveram efeito colateral** e, portanto, precisam ser compensados em caso de falha. Se um passo fosse empilhado antes de terminar (ou mesmo se falhasse), a saga tentaria compensar uma ação que nunca chegou a se completar, o que poderia gerar erros ou compensações incorretas (como tentar estornar um pagamento que nunca foi cobrado).
3) Na orquestração, um componente central conhece e comanda toda a sequência de passos explicitamente, o que facilita a leitura e a depuração do fluxo, mas cria um ponto de coordenação crítico. Na coreografia, não há coordenador central — cada serviço reage a eventos publicados pelos outros —, o que reduz o acoplamento mas torna o fluxo completo implícito e mais difícil de rastrear. Orquestração é preferível em fluxos complexos com muitos passos e regras de compensação elaboradas; coreografia funciona melhor em fluxos simples, com poucos participantes, onde o desacoplamento total compensa a perda de visibilidade.
