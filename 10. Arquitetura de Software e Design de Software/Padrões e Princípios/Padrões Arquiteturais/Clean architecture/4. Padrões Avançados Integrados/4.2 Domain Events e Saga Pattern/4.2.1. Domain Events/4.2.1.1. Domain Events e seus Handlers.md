### Domain Events e seus Handlers

Nas camadas de Entities e Use Cases já vimos como o núcleo do negócio toma decisões e aplica regras. Mas quando uma decisão importante acontece — um pagamento é confirmado, um pedido é cancelado — frequentemente **outras partes do sistema precisam reagir** a esse fato, sem que a Entity ou o Use Case precisem conhecê-las diretamente. É esse o papel dos Domain Events dentro da Clean Architecture.

---

## O que é um Domain Event

Um Domain Event representa **algo relevante que já aconteceu** no domínio — não uma intenção, não uma ordem, mas um fato consumado. Por convenção, é sempre **nomeado no passado**: `PaymentCompletedEvent`, `OrderCancelledEvent`, `UserRegisteredEvent`. Nunca `CompletePayment` (isso seria um Command, algo que ainda pode ser recusado).

**Analogia:** um Domain Event é como uma nota fiscal emitida após uma venda. Ninguém "edita" uma nota fiscal já emitida — se algo precisa mudar, emite-se um novo documento (uma nota de devolução, por exemplo). Da mesma forma, um evento é um registro imutável do passado: uma vez que `PaymentCompletedEvent` foi criado, ele descreve um fato histórico que não muda, mesmo que ações futuras revertam o pagamento (isso geraria um novo evento, como `PaymentRefundedEvent`).

Duas propriedades são inegociáveis:

| Propriedade | Por quê |
|---|---|
| **Imutável** | O evento é um registro histórico — se pudesse ser alterado depois de criado, deixaria de representar um fato consumado |
| **Nomeado no passado** | Deixa explícito, só pelo nome, que já aconteceu — diferencia de Commands (`CompletePayment`), que ainda podem falhar ou ser rejeitados |

---

## Onde o evento nasce: dentro da Entity, sem conhecer quem vai reagir

O ponto mais importante — e o que mais gera confusão — é **quem cria o evento e quem o publica**. Na Clean Architecture, a Entity (camada mais interna) apenas **registra** que algo aconteceu; ela não sabe, e não pode saber, quem vai reagir a isso. Publicar o evento (enviar para uma fila, disparar handlers) é responsabilidade do Use Case, na camada de Application Business Rules.

```csharp
// ENTITY (camada mais interna — não conhece MediatR, filas ou handlers)
public class Order : AggregateRoot
{
    private readonly List<IDomainEvent> _domainEvents = new();
    public IReadOnlyList<IDomainEvent> DomainEvents => _domainEvents.AsReadOnly();

    public void CompletePayment(decimal amount)
    {
        if (Status != OrderStatus.PaymentPending)
            throw new InvalidOperationException("Pagamento não pode ser processado");

        Status = OrderStatus.Paid;
        PaidAmount = amount;

        // A Entity apenas registra o fato — não sabe quem vai reagir
        _domainEvents.Add(new PaymentCompletedEvent(Id, amount, DateTime.UtcNow));
    }

    public void ClearDomainEvents() => _domainEvents.Clear();
}

// DOMAIN EVENT (imutável, nomeado no passado)
public record PaymentCompletedEvent(Guid OrderId, decimal Amount, DateTime OccurredAt) : IDomainEvent;
```

```csharp
// USE CASE (camada de Application Business Rules — orquestra a publicação)
public class CompleteOrderPaymentUseCase
{
    private readonly IOrderRepository _orderRepository;
    private readonly IEventPublisher _eventPublisher; // interface definida no domínio/aplicação

    public async Task ExecuteAsync(Guid orderId, decimal amount)
    {
        var order = await _orderRepository.GetByIdAsync(orderId);

        order.CompletePayment(amount); // Entity registra o evento internamente

        await _orderRepository.SaveAsync(order); // persiste o novo estado primeiro

        // Só depois de persistir com sucesso, o Use Case publica os eventos pendentes
        foreach (var domainEvent in order.DomainEvents)
        {
            await _eventPublisher.PublishAsync(domainEvent);
        }

        order.ClearDomainEvents();
    }
}
```

Note a ordem: **persistir primeiro, publicar depois**. Se o evento fosse publicado antes de salvar e a gravação no banco falhasse, handlers externos (como um serviço de e-mail) reagiriam a um fato que, na prática, nunca foi confirmado no sistema.

## Handlers: quem reage ao evento

Um Handler é uma classe dedicada a reagir a um tipo específico de evento. O ganho arquitetural está em que **cada handler não sabe da existência dos outros**, e o código que gerou o evento (`Order.CompletePayment`) não sabe da existência de nenhum handler.

```csharp
public interface IDomainEventHandler<TEvent> where TEvent : IDomainEvent
{
    Task HandleAsync(TEvent domainEvent);
}

public class SendPaymentConfirmationEmailHandler : IDomainEventHandler<PaymentCompletedEvent>
{
    private readonly IEmailService _emailService;

    public async Task HandleAsync(PaymentCompletedEvent domainEvent)
    {
        await _emailService.SendPaymentConfirmationAsync(domainEvent.OrderId);
    }
}

public class ReserveInventoryHandler : IDomainEventHandler<PaymentCompletedEvent>
{
    private readonly IInventoryService _inventoryService;

    public async Task HandleAsync(PaymentCompletedEvent domainEvent)
    {
        await _inventoryService.ReserveItemsAsync(domainEvent.OrderId);
    }
}
```

Dois handlers completamente diferentes — um dispara e-mail, outro reserva estoque — reagem ao **mesmo** evento sem se conhecerem e sem que `Order` saiba que eles existem. Um framework de mediação (como o MediatR, em .NET) ou um Event Bus interno resolve, em tempo de execução, quais handlers estão inscritos para `PaymentCompletedEvent` e os invoca.

## Fluxo completo: da Entity ao Handler

```
┌─────────────────────────────────────────────────────────────────┐
│  USE CASE: CompleteOrderPaymentUseCase.ExecuteAsync()            │
│                                                                     │
│  1. order.CompletePayment(amount)                                 │
│         │                                                          │
│         ▼                                                          │
│  ┌───────────────────────┐                                        │
│  │  ENTITY: Order          │  registra PaymentCompletedEvent      │
│  │  (não conhece handlers) │  numa lista interna                  │
│  └───────────────────────┘                                        │
│         │                                                          │
│  2. orderRepository.SaveAsync(order)   ◄── persiste primeiro      │
│         │                                                          │
│  3. eventPublisher.PublishAsync(evento) para cada evento pendente │
│         │                                                          │
└─────────┼───────────────────────────────────────────────────────┘
          │
          ▼
   ┌──────────────┐
   │ Event Publisher│  (implementado na Interface Adapters/
   │  / Event Bus    │   Frameworks & Drivers — ex: MediatR, Kafka)
   └──────┬─────────┘
          │  despacha PaymentCompletedEvent para todos os inscritos
          │
    ┌─────┴──────┐
    ▼            ▼
┌─────────┐  ┌──────────────┐
│ Handler  │  │ Handler       │
│ Email    │  │ Estoque       │
└─────────┘  └──────────────┘
```

Repare que a seta de dependência aponta sempre de fora para dentro: o Event Publisher e os Handlers **conhecem** `PaymentCompletedEvent` (definido perto do domínio) e o invocam, mas a `Order` nunca importa nada relacionado a e-mail, estoque ou mensageria.

## Como isso se encaixa nas camadas da Clean Architecture

| Camada | Responsabilidade em relação ao evento |
|---|---|
| **Entities** | Define o evento (`PaymentCompletedEvent`) e o registra internamente quando uma regra de negócio é satisfeita |
| **Use Cases** | Decide *quando* publicar (normalmente após persistir com sucesso) e chama a interface `IEventPublisher` |
| **Interface Adapters** | Implementa `IEventPublisher` fazendo a ponte entre o Use Case e o mecanismo concreto de despacho (ex: adapter para MediatR) |
| **Frameworks & Drivers** | A tecnologia real de mensageria/mediação (MediatR, Kafka, RabbitMQ, um simples `EventEmitter` em memória) |

Essa distribuição é a Regra da Dependência em ação: a definição do evento vive perto do centro (Entities), mas a tecnologia que o transporta vive na borda (Frameworks & Drivers) — e o Use Case, no meio, depende apenas de uma abstração (`IEventPublisher`), nunca da tecnologia concreta.

---

## Sem Domain Events vs. Com Domain Events

| Aspecto | Sem Domain Events | Com Domain Events |
|---|---|---|
| Acoplamento | `Order.CompletePayment()` chamaria diretamente `emailService.Send(...)` e `inventoryService.Reserve(...)` | `Order.CompletePayment()` apenas registra o evento; quem reage não é do conhecimento da Entity |
| Adicionar nova reação | Exige alterar o método `CompletePayment` (viola Open/Closed) | Exige apenas criar um novo Handler inscrito no evento — `Order` não muda |
| Testabilidade da Entity | Testar `CompletePayment` exigiria mockar serviço de e-mail e de estoque | Testar `CompletePayment` só verifica se o evento correto foi adicionado à lista — sem mocks externos |
| Consistência entre módulos | Acoplamento direto e síncrono entre módulos que, conceitualmente, não deveriam se conhecer | Consistência eventual entre módulos ou até microsserviços, através do evento |

## Quando usar e limitações

**Quando usar:**
- Quando uma ação de negócio precisa disparar múltiplas reações independentes (notificar, atualizar estoque, gerar auditoria) sem acoplar a Entity a cada uma delas.
- Para desacoplar módulos dentro do mesmo sistema (ex: módulo de Pedidos não deveria importar o módulo de Notificações diretamente).
- Como base para consistência eventual entre bounded contexts ou microsserviços (nesse caso, o evento de domínio interno costuma virar um Integration Event publicado externamente).

**Limitações e armadilhas comuns:**
- **Publicar antes de persistir**: se o evento for despachado antes da transação ser confirmada no banco, handlers podem reagir a um estado que nunca chegou a existir de fato caso a gravação falhe.
- **Handlers síncronos e lentos bloqueando o Use Case**: se um handler (ex: chamada de e-mail) é executado de forma síncrona e lenta, o tempo de resposta do Use Case inteiro é penalizado — nesses casos, considerar despachar o evento para uma fila e processar os handlers de forma assíncrona.
- **Encadeamento excessivo de eventos**: um handler que, ao reagir a um evento, dispara outro evento, que dispara outro handler, e assim por diante, cria um fluxo difícil de rastrear e depurar. Prefira manter cadeias de eventos curtas e explícitas.
- **Confundir Domain Event com Command**: um Domain Event nunca deve ser usado para *pedir* que algo aconteça (isso é um Command); ele apenas *informa* que algo já aconteceu, e os handlers decidem livremente como reagir (ou se reagem).

## 🧩 Quiz de Fixação

1. Por que a `Order` (Entity) apenas registra o `PaymentCompletedEvent` numa lista interna, em vez de chamar diretamente o serviço de e-mail e o serviço de estoque?
2. Na sequência do Use Case `CompleteOrderPaymentUseCase`, por que os eventos são publicados **depois** de `orderRepository.SaveAsync(order)`, e não antes?
3. Um evento chamado `ProcessPayment` (no presente/infinitivo) está nomeado corretamente como Domain Event? Por quê?

**Respostas:**
1) Porque isso acoplaria a Entity — a camada mais interna e mais protegida da Clean Architecture — a detalhes de infraestrutura (e-mail, estoque) que pertencem a camadas externas. Ao apenas registrar o evento, a `Order` permanece pura e testável sem mocks; é o Use Case, na camada de Application Business Rules, quem decide publicar o evento através de uma abstração (`IEventPublisher`), mantendo a Regra da Dependência intacta.
2) Porque se o evento fosse publicado antes da persistência e a gravação no banco falhasse (ex: erro de conexão, violação de constraint), os handlers reagiriam a um pagamento que, na prática, nunca foi confirmado no sistema — enviando um e-mail de confirmação ou reservando estoque para um pedido que não existe de fato no banco de dados.
3) Não. `ProcessPayment` está no infinitivo/presente, o que o caracteriza como um Command (uma ordem que ainda pode ser aceita ou recusada), não como um Domain Event. Um Domain Event deve ser nomeado no passado, como `PaymentProcessed` ou `PaymentCompleted`, para deixar explícito que descreve um fato já consumado e imutável.
