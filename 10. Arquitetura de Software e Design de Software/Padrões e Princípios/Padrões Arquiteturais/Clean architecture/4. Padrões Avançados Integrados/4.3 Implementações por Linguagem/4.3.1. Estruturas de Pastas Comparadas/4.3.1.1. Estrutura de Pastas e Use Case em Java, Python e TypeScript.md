### Estrutura de Pastas e Use Case em Java, Python e TypeScript

Até aqui vimos a Clean Architecture em termos de camadas conceituais (Entities, Use Cases, Interface Adapters, Frameworks & Drivers) e em exemplos concentrados em C#. Este arquivo mostra como essas mesmas quatro camadas se traduzem em **estrutura de pastas real** e em **código idiomático** de três ecossistemas bem diferentes — Java/Spring Boot, Python/FastAPI e TypeScript/NestJS —, deixando claro o que muda (sintaxe, convenções, mecanismo de injeção de dependência) e o que nunca muda (a direção da dependência).

---

## O que muda e o que não muda entre linguagens

**Analogia:** pense na Clean Architecture como uma planta baixa de uma casa (onde fica a cozinha, o quarto, a sala — e que a área de serviço nunca pode ter acesso direto ao quarto do bebê sem passar pelo corredor). A planta baixa é a mesma independente de a casa ser construída em tijolo, madeira ou concreto. A linguagem de programação é o material de construção: muda a técnica de construção, os nomes das ferramentas, mas a planta — onde cada cômodo fica e como se conectam — permanece idêntica.

Formalizando: a **estrutura de pastas é convenção**, específica de cada comunidade/framework; a **Regra da Dependência é invariante**, não muda com a linguagem.

| O que muda entre linguagens | O que nunca muda |
|---|---|
| Nome das pastas (`domain` vs `dominio`, `usecases` vs `interactors`) | A direção da dependência: sempre de fora para dentro |
| Mecanismo de abstração de Port (`interface` Java, `Protocol` Python, `interface` TypeScript) | Entities e Use Cases nunca importam frameworks ou bibliotecas de infraestrutura |
| Forma de injeção de dependência (constructor injection manual, DI container, decorators) | Use Cases dependem de abstrações, nunca de implementações concretas |
| Sintaxe de tipagem (estática forte, estrutural, gradual) | O fluxo de controle: Controller → Use Case → Entity → Repository (via interface) |

Repare que os três seguem a mesma partição em quatro grupos (domain / application / infrastructure / interface de entrada), apenas com nomes e granularidade ligeiramente diferentes — Python, por exemplo, tende a condensar `entities` e `value objects` num único módulo por simplicidade, já que não impõe "uma classe pública por arquivo" como o Java.

## Mecanismo de Port: a mesma ideia, três sintaxes

O ponto mais interessante para comparar não é a pasta, é **como cada linguagem expressa a abstração que o Use Case depende** (o Port, na terminologia Hexagonal/Clean).

### Java/Spring Boot — interface explícita + injeção via Spring

```java
@UseCase
@Transactional
public class TransferMoneyUseCase {
    private final AccountRepository accountRepository;
    private final TransactionRepository transactionRepository;
    private final DomainEventPublisher eventPublisher;

    public TransferResult execute(TransferMoneyCommand command) {
        Account sourceAccount = accountRepository.findById(command.getSourceAccountId())
            .orElseThrow(() -> new AccountNotFoundException(command.getSourceAccountId()));

        Account targetAccount = accountRepository.findById(command.getTargetAccountId())
            .orElseThrow(() -> new AccountNotFoundException(command.getTargetAccountId()));

        // Lógica de domínio
        Transaction transaction = sourceAccount.transferTo(targetAccount, command.getAmount());

        // Persistir mudanças
        accountRepository.save(sourceAccount);
        accountRepository.save(targetAccount);
        transactionRepository.save(transaction);

        // Publicar eventos
        eventPublisher.publish(transaction.getDomainEvents());

        return TransferResult.success(transaction.getId());
    }
}
```

Aqui, `AccountRepository` é uma `interface` Java definida na camada de aplicação — o Spring, em tempo de execução, injeta a implementação concreta (feita com Spring Data JPA) através do container de Inversão de Controle. O Use Case nunca importa nada de `infrastructure`.

### Python/FastAPI — `Protocol` (tipagem estrutural) no lugar de interface explícita

```python
# domain/entities.py
from dataclasses import dataclass, field
from typing import List

@dataclass
class Account:
    id: AccountId
    balance: Money
    customer_id: CustomerId
    _domain_events: List[DomainEvent] = field(default_factory=list, init=False)

    def withdraw(self, amount: Money) -> None:
        if self.balance < amount:
            raise InsufficientFundsError(f"Saldo insuficiente: {self.balance}")

        self.balance -= amount
        self._domain_events.append(
            MoneyWithdrawnEvent(account_id=self.id, amount=amount)
        )

    def deposit(self, amount: Money) -> None:
        self.balance += amount
        self._domain_events.append(
            MoneyDepositedEvent(account_id=self.id, amount=amount)
        )

# application/use_cases.py
from typing import Protocol

class AccountRepository(Protocol):
    async def get_by_id(self, account_id: AccountId) -> Account:
        ...
    async def save(self, account: Account) -> None:
        ...

class TransferMoneyInteractor:
    def __init__(
        self,
        account_repo: AccountRepository,
        event_publisher: EventPublisher
    ):
        self._account_repo = account_repo
        self._event_publisher = event_publisher

    async def execute(self, command: TransferMoneyCommand) -> TransferResult:
        source_account = await self._account_repo.get_by_id(command.source_account_id)
        target_account = await self._account_repo.get_by_id(command.target_account_id)

        # Executar transferência
        source_account.withdraw(command.amount)
        target_account.deposit(command.amount)

        # Salvar alterações
        await self._account_repo.save(source_account)
        await self._account_repo.save(target_account)

        # Publicar eventos
        all_events = source_account._domain_events + target_account._domain_events
        await self._event_publisher.publish_many(all_events)

        return TransferResult.success(source_account.id)
```

A diferença mais marcante em relação ao Java: `AccountRepository` aqui é um `Protocol` (tipagem estrutural do Python) — qualquer classe que implemente os métodos `get_by_id` e `save` com essas assinaturas **satisfaz** o Protocol automaticamente, sem precisar declarar `implements AccountRepository` explicitamente como faria em Java. É a mesma ideia de Port, mas resolvida em tempo de checagem estática (com `mypy`/`pyright`) em vez de em tempo de compilação com herança explícita.

### TypeScript/NestJS — interface + Injeção via decorators

```typescript
// domain/entities/User.ts
export class User {
  constructor(
    public readonly id: UserId,
    public email: Email,
    private _isActive: boolean = true
  ) {}

  deactivate(): DomainEvent[] {
    if (!this._isActive) {
      throw new UserAlreadyInactiveError();
    }

    this._isActive = false;
    return [new UserDeactivatedEvent(this.id, new Date())];
  }

  get isActive(): boolean {
    return this._isActive;
  }
}

// application/use-cases/DeactivateUser.usecase.ts
@Injectable()
export class DeactivateUserUseCase {
  constructor(
    @Inject('USER_REPOSITORY')
    private readonly userRepository: UserRepository,
    private readonly eventBus: EventBus
  ) {}

  async execute(command: DeactivateUserCommand): Promise<void> {
    const user = await this.userRepository.findById(command.userId);
    if (!user) {
      throw new UserNotFoundError(command.userId);
    }

    const events = user.deactivate();
    await this.userRepository.save(user);

    // Publicar eventos de domínio
    for (const event of events) {
      this.eventBus.publish(event);
    }
  }
}

// infrastructure/controllers/User.controller.ts
@Controller('users')
export class UserController {
  constructor(private readonly deactivateUserUseCase: DeactivateUserUseCase) {}

  @Delete(':id/deactivate')
  @HttpCode(HttpStatus.NO_CONTENT)
  async deactivateUser(@Param('id') userId: string): Promise<void> {
    const command = new DeactivateUserCommand(new UserId(userId));
    await this.deactivateUserUseCase.execute(command);
  }
}
```

Note que o exemplo em TypeScript ilustra um cenário diferente (desativar um usuário, em vez de transferir dinheiro) — mas a **forma** é idêntica à do Java e do Python: a `Entity` (`User`) concentra a regra de negócio e devolve os eventos gerados; o `UseCase` (`DeactivateUserUseCase`) orquestra repositório + publicação de eventos; o `Controller` só traduz HTTP em um Command e delega. O `@Inject('USER_REPOSITORY')` é o equivalente, em NestJS, à injeção automática por tipo que o Spring faz em Java — como TypeScript não tem reflection nativa sobre interfaces (elas somem em tempo de compilação), o NestJS exige um token string ou classe abstrata para saber qual implementação injetar.

## Comparativo dos mecanismos de Port/DI

| Aspecto | Java/Spring Boot | Python/FastAPI | TypeScript/NestJS |
|---|---|---|---|
| Como se declara um Port | `interface` explícita | `Protocol` (tipagem estrutural) | `interface` (existe só em compile-time) |
| Como a implementação "assina" o contrato | `implements NomeDaInterface` | Implicitamente — só precisa ter os métodos com a assinatura certa | Precisa de um token de DI (`@Inject('TOKEN')`) porque a interface não existe em runtime |
| Quem resolve a implementação concreta | Spring IoC Container, por tipo | Injeção manual ou biblioteca como `dependency-injector` | Nest IoC Container, por token/classe |
| Checagem do contrato | Em tempo de compilação | Em tempo de análise estática (mypy/pyright), não em runtime | Em tempo de compilação (apagada no JS final) |
| Verbosidade | Alta (interfaces + implementações explícitas) | Baixa (duck typing reduz boilerplate) | Média (decorators substituem XML/config, mas exigem tokens) |

## Quando usar cada abordagem e limitações

**Quando usar:**
- **Java/Spring**: equipes grandes, tipagem forte e verificação em tempo de compilação são prioridade, ecossistema corporativo já consolidado em torno do Spring.
- **Python/FastAPI**: velocidade de desenvolvimento, prototipagem rápida, times menores confortáveis com tipagem gradual — mas exige disciplina de testes, já que o `Protocol` não impede em runtime que uma implementação "incompleta" seja usada por engano.
- **TypeScript/NestJS**: aplicações Node.js que já se beneficiam de tipagem estática no desenvolvimento, mas precisam lembrar que interfaces desaparecem no JavaScript compilado — por isso os tokens de DI (`'USER_REPOSITORY'`) são obrigatórios.

**Limitações comuns:**
- Em Python, como o `Protocol` não é verificado em tempo de execução, um erro de assinatura só aparece se houver checagem estática configurada (`mypy`) no pipeline de CI — sem isso, o erro só aparece em runtime, quando o método errado é chamado.
- Em TypeScript, é comum desenvolvedores iniciantes esquecerem que `interface` é apagada na compilação e tentarem usar `@Inject(MinhaInterface)` diretamente — isso falha silenciosamente ou gera erro de DI, porque o Nest precisa de um valor real (string, classe, símbolo) para resolver a dependência, não de um tipo.
- Em Java, a verbosidade de declarar uma interface para cada repositório, mesmo quando só existe uma implementação, é às vezes criticada como boilerplate desnecessário — mas o ganho de testabilidade (poder trocar por um fake em testes) geralmente compensa.

## 🧩 Quiz de Fixação

1. O que muda entre as implementações em Java, Python e TypeScript, e o que permanece exatamente igual nos três casos?
2. Por que, em TypeScript/NestJS, `@Inject('USER_REPOSITORY')` usa uma string como token em vez de referenciar diretamente a interface `UserRepository`?
3. Qual é o risco de usar `Protocol` no Python para definir um Port, comparado a usar uma `interface` explícita em Java?

**Respostas:**
1) O que muda é a sintaxe de cada linguagem para expressar a mesma ideia: o nome das pastas, o mecanismo usado para declarar um Port (interface explícita em Java, Protocol estrutural em Python, interface apagada em compilação + token de DI em TypeScript) e a forma como a injeção de dependência é resolvida (container do Spring, injeção manual em Python, container do Nest). O que nunca muda é a Regra da Dependência: em todos os três, a Entity concentra a regra de negócio sem conhecer infraestrutura, e o Use Case depende apenas de abstrações (interfaces/Protocols), nunca de implementações concretas.
2) Porque o TypeScript compila para JavaScript, e interfaces são um recurso apenas do sistema de tipos — elas não existem mais no código JavaScript gerado (são "apagadas" na compilação). Como o Nest precisa resolver a dependência em tempo de execução (quando o JavaScript já está rodando), ele não pode usar a interface como referência; por isso exige um token concreto (uma string, uma classe ou um símbolo) que exista de fato em runtime para saber qual implementação injetar.
3) O risco é que o `Protocol` do Python só é verificado por ferramentas de análise estática (como `mypy` ou `pyright`) — se o time não rodar essa checagem no pipeline de CI, uma implementação com assinatura de método incorreta ou incompleta só vai gerar erro quando o método for de fato chamado em runtime (ex: `AttributeError`). Já uma `interface` explícita em Java é verificada pelo próprio compilador: se uma classe declara `implements AccountRepository` mas não implementa todos os métodos exigidos, o código simplesmente não compila — o erro é detectado muito mais cedo.
