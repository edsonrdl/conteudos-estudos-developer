### Over-engineering em CRUDs Simples e Entidades sem Comportamento

Depois de dominar as camadas, os fluxos e os padrões avançados da Clean Architecture, é comum cair em um de dois extremos opostos — e igualmente prejudiciais. O primeiro é aplicar a arquitetura completa onde ela não agrega valor algum (over-engineering). O segundo é adotar a estrutura de pastas da arquitetura, mas esvaziar seu componente mais importante — a Entity — de qualquer regra de negócio real (Anemic Domain Model). Este arquivo detalha os dois.

---

## Anti-padrão 1: Over-Engineering em Projetos Simples

A Clean Architecture existe para gerenciar a complexidade de sistemas com regras de negócio não triviais, múltiplas integrações e necessidade de evoluir por anos. Aplicá-la integralmente a uma operação que é, de fato, um CRUD simples — sem regra de negócio nenhuma além de "buscar pelo ID e devolver" — não traz nenhum dos benefícios da arquitetura e adiciona apenas camadas de indireção sem propósito.

**Analogia:** usar a estrutura completa de quatro camadas (Entity, Use Case, Interface Adapter, Framework) para buscar um usuário por ID é como preencher um formulário de três páginas, com aprovação de gerente, para pedir um copo de água na própria casa. O processo existe para decisões que realmente precisam de controle e rastreabilidade — aplicá-lo a algo trivial só adiciona atrito, sem nenhum ganho correspondente.

```java
// ANTI-PADRÃO: Clean Architecture para CRUD simples
public class GetUserByIdUseCase {
    public UserResponse execute(GetUserByIdRequest request) {
        User user = userRepository.findById(request.getId());
        return UserResponseMapper.toResponse(user);
    }
}

// MELHOR: Controller direto para operações simples
@GetMapping("/users/{id}")
public User getUser(@PathVariable Long id) {
    return userRepository.findById(id);
}
```

Note o que o `GetUserByIdUseCase` realmente faz: recebe um ID, chama o repositório, mapeia o resultado para um DTO de resposta. Não há decisão de negócio, não há validação, não há regra alguma sendo aplicada — é uma passagem direta de dados (`request.getId()` → `userRepository.findById()` → `mapper.toResponse()`). Criar um `Request`, um `Response`, um `Mapper` e um `UseCase` inteiros só para essa operação significa que qualquer mudança trivial (adicionar um campo na resposta, por exemplo) agora exige tocar em quatro arquivos em vez de um.

A alternativa "MELHOR" não abandona a arquitetura — ela reconhece que, **para essa operação específica**, o Controller pode falar diretamente com o repositório, sem um Use Case intermediário que não adiciona nenhuma lógica.

### Como saber se o Use Case está justificado

| Sinal de que o Use Case AGREGA valor | Sinal de que é over-engineering |
|---|---|
| Envolve validações de negócio (`if (saldo < valor) throw ...`) | Só delega para o repositório, sem nenhuma condição |
| Orquestra múltiplos colaboradores (repositório + gateway + publisher de eventos) | Chama um único método de um único colaborador |
| A lógica pode mudar independente da tecnologia de entrada (REST hoje, gRPC amanhã) | Não há lógica nenhuma que sobreviveria a uma troca de protocolo |
| Precisa ser testado isoladamente com múltiplos cenários de negócio | O "teste" seria apenas verificar se o mock foi chamado uma vez |

## Anti-padrão 2: Anemic Domain Model (Modelo de Domínio Anêmico)

O segundo anti-padrão é sutil porque **parece** estar seguindo a Clean Architecture: existe uma classe `Order` no pacote `domain`, existem Use Cases, existem Repositories. Mas, ao abrir a Entity, ela não passa de um conjunto de propriedades públicas com getters e setters — toda a lógica de negócio (validações, cálculos, transições de estado) foi parar nos Use Cases ou, pior, em "Services" genéricos espalhados pela aplicação.

```csharp
// ANTI-PADRÃO: Entidade sem comportamento
public class Order
{
    public Guid Id { get; set; }
    public decimal Total { get; set; }
    public OrderStatus Status { get; set; }
    // Apenas propriedades
}
```

Com essa `Order`, qualquer código em qualquer lugar do sistema pode fazer `order.Status = OrderStatus.Paid;` diretamente, sem passar por nenhuma validação. Nada impede um Use Case desavisado de marcar um pedido como pago sem verificar se ele tem itens, sem checar se já não estava cancelado, sem gerar o evento de domínio correspondente. A regra de negócio, se existir, precisa ser reimplementada (e mantida sincronizada) em **todo lugar** que manipula um `Order` — exatamente o problema de duplicação que a Entity deveria evitar.

```csharp
// CORREÇÃO: Entidade rica com comportamento
public class Order
{
    public Guid Id { get; private set; }
    public Money Total { get; private set; }
    public OrderStatus Status { get; private set; }

    public void AddItem(OrderItem item)
    {
        if (Status != OrderStatus.Draft)
            throw new InvalidOperationException("Não é possível modificar pedido processado");

        _items.Add(item);
        Total = CalculateTotal();
        AddDomainEvent(new ItemAddedToOrderEvent(Id, item));
    }
}
```

A diferença crucial: os setters somem (`private set`), e no lugar deles aparecem **métodos com nome de negócio** (`AddItem`, não `SetItems`). Só existe uma forma de adicionar um item a um pedido — chamando `AddItem` — e essa única porta de entrada garante que a validação (`Status != OrderStatus.Draft`), o recálculo do total e o disparo do evento de domínio **sempre** aconteçam juntos, não importa de onde o método seja chamado.

```
ANEMIC MODEL                           RICH MODEL
─────────────                          ──────────

  Order (só dados)                       Order (dados + comportamento)
    │                                       │
    ├─ Status = Paid  ◄── UseCase A          ├─ AddItem(item)  ◄── qualquer chamador
    ├─ Status = Paid  ◄── UseCase B          │     └─ valida, recalcula,
    ├─ Status = Paid  ◄── Service X          │        dispara evento — sempre junto
    │                                       │
  Regra "não pagar sem itens"            Regra vive DENTRO do método —
  reimplementada em cada lugar           impossível contornar por acidente
  que toca o Status — ou esquecida
```

## Comparativo direto

| Aspecto | Anemic Domain Model | Rich Domain Model |
|---|---|---|
| Onde vive a regra de negócio | Espalhada em Use Cases e Services | Concentrada na própria Entity |
| Como se modifica o estado | Setters públicos (`order.Status = x`) | Métodos com intenção de negócio (`order.AddItem(x)`) |
| Risco de inconsistência | Alto — fácil esquecer uma validação em algum ponto de chamada | Baixo — a validação está dentro do único ponto de entrada |
| Reuso de regra | Precisa duplicar a checagem em cada lugar que usa a Entity | A regra é reusada automaticamente por qualquer chamador |
| Testabilidade da regra | Precisa testar cada Use Case/Service separadamente | Testa-se a Entity uma única vez, isoladamente |

## Quando usar e limitações

**Quando o Use Case completo se justifica (evitar o over-engineering):**
- Quando existe alguma regra de negócio real, ainda que pequena — mesmo uma validação simples já justifica isolar a lógica num Use Case testável.
- Quando a operação provavelmente vai crescer em complexidade (ex: hoje é um CRUD simples, mas o roadmap já prevê regras de aprovação, auditoria, notificação).
- Quando múltiplos pontos de entrada (REST, mensageria, CLI) vão precisar executar exatamente a mesma lógica — nesse caso, um Use Case compartilhado evita duplicação entre Controllers.

**Quando o Controller direto é aceitável:**
- Buscas simples por ID/listagem sem regra de negócio (leitura pura).
- Protótipos e MVPs onde a estrutura completa ainda não se justifica — mas vale documentar a decisão, porque a operação pode crescer depois.

**Limitações e armadilhas ao corrigir um Anemic Domain Model:**
- **Migração parcial é arriscada**: transformar uma Entity anêmica em rica exige localizar *todos* os lugares que hoje manipulam os setters diretamente e substituí-los pelos novos métodos — deixar alguns pontos antigos convivendo com os novos métodos reabre a mesma inconsistência que se queria resolver.
- **Setters privados podem quebrar ORMs ingênuos**: frameworks de persistência mais antigos às vezes exigem setters públicos para popular objetos via reflection — a maioria dos ORMs modernos (JPA/Hibernate, Entity Framework Core, SQLAlchemy) já suporta construtores privados e reflection sobre campos, mas vale confirmar antes de remover os setters.
- **Nem toda propriedade precisa de método de negócio**: campos puramente descritivos (ex: um `Id` gerado uma vez na criação) continuam podendo ser apenas `get`, sem exagerar a modelagem — o objetivo é proteger invariantes de negócio, não eliminar toda propriedade simples.

## 🧩 Quiz de Fixação

1. Por que o `GetUserByIdUseCase` do primeiro exemplo é considerado over-engineering, mesmo seguindo a estrutura correta de Use Case da Clean Architecture?
2. No exemplo de `Order` anêmico, qual problema concreto pode acontecer se dois Use Cases diferentes alterarem `order.Status` diretamente, sem passar por um método como `AddItem` ou `ProcessPayment`?
3. Por que trocar `public set` por `private set` e adicionar métodos como `AddItem` resolve o problema do Anemic Domain Model?

**Respostas:**
1) Porque ele não contém nenhuma regra de negócio real — apenas repassa o ID recebido para o repositório e mapeia o resultado para um DTO, sem nenhuma validação, decisão ou orquestração de múltiplos colaboradores. Isolar essa operação trivial em um Use Case completo (com Request, Response e Mapper próprios) adiciona indireção e arquivos extras sem nenhum ganho de testabilidade ou flexibilidade correspondente, já que não há lógica capaz de mudar independentemente da tecnologia de entrada.
2) Se dois Use Cases diferentes (ou um Use Case e um Service) alterarem `order.Status` diretamente, cada um pode implementar (ou esquecer de implementar) suas próprias validações antes da mudança — por exemplo, um Use Case pode verificar corretamente se o pedido tem itens antes de marcar como pago, enquanto outro, escrito depois por outro desenvolvedor, esquece essa checagem. O resultado é inconsistência: alguns caminhos do sistema produzem pedidos pagos sem itens, e o bug só é percebido depois, em produção, sem nenhum teste capaz de pegá-lo de forma centralizada.
3) Porque, ao tornar o setter privado, a única forma de alterar o estado passa a ser através dos métodos públicos da própria Entity (`AddItem`, por exemplo) — e esses métodos concentram a validação, o recálculo de estado derivado (como o `Total`) e o disparo do evento de domínio em um único lugar. Isso torna impossível, por construção, que algum código externo altere o estado do `Order` pulando essas regras — a regra de negócio deixa de depender da disciplina de quem escreve cada Use Case e passa a ser garantida pelo próprio compilador/runtime.
