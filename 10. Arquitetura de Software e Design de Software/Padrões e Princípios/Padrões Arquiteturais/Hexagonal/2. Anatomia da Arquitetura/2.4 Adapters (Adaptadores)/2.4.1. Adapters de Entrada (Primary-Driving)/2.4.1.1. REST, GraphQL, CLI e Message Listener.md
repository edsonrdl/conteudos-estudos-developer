### REST, GraphQL, CLI e Message Listener

Com as Ports mapeadas (2.3), este arquivo mostra o lado que efetivamente conversa com o mundo externo: os Adapters de Entrada. Eles são a prova prática de um dos maiores benefícios da arquitetura — múltiplas interfaces diferentes podem acionar exatamente o mesmo caso de uso, sem duplicar uma linha de lógica.

---

## O papel do Adapter de Entrada

Um Adapter de Entrada (Primary/Driving Adapter) tem uma única responsabilidade: **traduzir** um formato de comunicação externo (HTTP, GraphQL, linha de comando, mensagem de fila) em uma chamada à Primary Port correspondente. Ele não decide nada de negócio — apenas converte formatos de entrada e saída.

**Analogia:** um Adapter de Entrada é como um intérprete em uma reunião internacional. O intérprete traduz o que cada pessoa fala para a língua comum da sala (a Primary Port), mas não participa da decisão sendo discutida — ele só garante que a mensagem chegue no formato certo.

Todos os quatro exemplos abaixo chamam a **mesma** Primary Port (`GestãoProdutos`, vista em 2.3.1.1) — a diferença está inteiramente em como cada um recebe o estímulo externo.

---

## REST Controller Adapter

```java
@RestController
@RequestMapping("/api/v1/produtos")
public class ProdutoRestController {
    private final GestãoProdutos gestãoProdutos;

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    public ProdutoResponse criarProduto(@Valid @RequestBody CriarProdutoRequest request) {
        // Converte request HTTP para Command
        CriarProdutoCommand comando = CriarProdutoCommand.builder()
            .nome(request.getNome())
            .preco(request.getPreco())
            .categoria(request.getCategoria())
            .build();

        // Chama o Port — a partir daqui, HTTP deixa de existir
        ProdutoId produtoId = gestãoProdutos.criarProduto(comando);

        return new ProdutoResponse(produtoId.getValue(), "Produto criado com sucesso");
    }

    @GetMapping("/{id}")
    public ProdutoDetalhesResponse buscarProduto(@PathVariable String id) {
        ProdutoDetalhes detalhes = gestãoProdutos.buscarProduto(new ProdutoId(id));
        return ProdutoDetalhesResponse.from(detalhes);
    }
}
```

## GraphQL Adapter

```java
@Component
public class ProdutoGraphQLResolver implements GraphQLQueryResolver {
    private final GestãoProdutos gestãoProdutos;

    public ProdutoType produto(String id) {
        ProdutoDetalhes detalhes = gestãoProdutos.buscarProduto(new ProdutoId(id));
        return GraphQLMapper.toGraphQL(detalhes);
    }

    @DgsQuery
    public List<ProdutoType> produtos(@InputArgument String categoria, @InputArgument Integer limite) {
        FiltrosProduto filtros = new FiltrosProduto(categoria, limite);
        return gestãoProdutos.listarProdutos(filtros)
            .stream()
            .map(GraphQLMapper::toGraphQL)
            .collect(Collectors.toList());
    }
}
```

## CLI Adapter

```java
@Component
public class ProdutoCLIAdapter {
    private final GestãoProdutos gestãoProdutos;

    @ShellMethod("Criar novo produto")
    public String criarProduto(
        @ShellOption String nome,
        @ShellOption BigDecimal preco,
        @ShellOption String categoria
    ) {
        CriarProdutoCommand comando = new CriarProdutoCommand(nome, preco, categoria);
        ProdutoId id = gestãoProdutos.criarProduto(comando);
        return "Produto criado com ID: " + id.getValue();
    }
}
```

## O ponto-chave: quatro portas de entrada, um único caso de uso

```
   HTTP Request ──► ProdutoRestController ──┐
   GraphQL Query ──► ProdutoGraphQLResolver ──┤
   Comando CLI ──► ProdutoCLIAdapter ──────────┼──► GestãoProdutos (Primary Port) ──► Domínio
   Mensagem Fila ──► ProdutoMessageListener ──┘
```

Nenhum dos quatro adapters sabe da existência dos outros três. Se amanhã for necessário adicionar um quinto canal de entrada (por exemplo, um webhook), basta criar mais um Adapter que chame `GestãoProdutos` — nenhuma linha de `GestãoProdutosService` ou do domínio precisa mudar.

| Adapter | Formato de entrada | Formato de saída |
|---|---|---|
| REST Controller | JSON via HTTP | JSON via HTTP (`ProdutoResponse`) |
| GraphQL Resolver | Query GraphQL | Tipo GraphQL (`ProdutoType`) |
| CLI | Argumentos de linha de comando | String impressa no terminal |
| Message Listener | Mensagem serializada (JSON/Avro) na fila | Nenhuma resposta síncrona — efeito colateral |

## Erro comum: lógica de negócio infiltrada no Adapter

```java
// ERRADO — o Controller decide uma regra de negócio
@PostMapping
public ProdutoResponse criarProduto(@RequestBody CriarProdutoRequest request) {
    if (request.getPreco().compareTo(BigDecimal.ZERO) <= 0) {
        throw new ResponseStatusException(HttpStatus.BAD_REQUEST, "Preço inválido");
    }
    // ...
}

// CORRETO — o Controller só traduz; a validação de negócio mora no domínio/Command
@PostMapping
public ProdutoResponse criarProduto(@Valid @RequestBody CriarProdutoRequest request) {
    CriarProdutoCommand comando = CriarProdutoCommand.builder()
        .preco(request.getPreco()) // @Positive já valida formato via Bean Validation
        .build();
    return converterResponse(gestãoProdutos.criarProduto(comando));
}
```

A diferença entre validação de **formato** (campo obrigatório, tipo correto — aceitável no Adapter via `@Valid`) e validação de **negócio** (preço mínimo permitido pela política comercial — pertence ao domínio) volta a aparecer aqui, do mesmo jeito que apareceu em 2.2.1.2.

## 🧩 Quiz de Fixação

1. Qual é a única responsabilidade permitida a um Adapter de Entrada, segundo a analogia do intérprete?
2. No diagrama com quatro adapters diferentes chamando `GestãoProdutos`, o que precisa mudar no domínio ou na aplicação se um quinto adapter (um webhook, por exemplo) for adicionado?
3. Por que validar `@Valid @RequestBody` no Controller é aceitável, mas validar "preço mínimo permitido pela política comercial" ali seria um erro?

**Respostas:**
1) A única responsabilidade permitida é traduzir o formato de comunicação externo (HTTP, GraphQL, linha de comando, mensagem de fila) para uma chamada à Primary Port, e traduzir o retorno de volta para o formato de saída esperado. O Adapter não deve decidir nada sobre a regra de negócio em si.
2) Nada precisa mudar no domínio ou na aplicação — o novo adapter (webhook) apenas passa a chamar a mesma Primary Port `GestãoProdutos` já existente. Essa é a prova prática do benefício de múltiplas interfaces de entrada sem duplicação de lógica.
3) Porque `@Valid @RequestBody` valida apenas o **formato** dos dados de entrada (campo obrigatório, tipo correto, valor positivo) — uma responsabilidade legítima do Adapter, já que é uma questão de contrato de entrada, não de regra de negócio. Já "preço mínimo permitido pela política comercial" é uma decisão de negócio que pode mudar com o tempo e precisa ser consistente para todos os canais de entrada (REST, CLI, fila) — por isso deve morar no domínio, não ser duplicada em cada Adapter.
