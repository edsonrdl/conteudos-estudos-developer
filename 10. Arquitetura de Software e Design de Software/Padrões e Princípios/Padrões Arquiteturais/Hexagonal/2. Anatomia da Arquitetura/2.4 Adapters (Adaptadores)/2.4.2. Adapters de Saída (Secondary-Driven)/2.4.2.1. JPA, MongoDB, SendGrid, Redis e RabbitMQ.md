### JPA, MongoDB, SendGrid, Redis e RabbitMQ

O arquivo anterior (2.4.1.1) mostrou os Adapters de Entrada. Este fecha o Domínio 2 (Anatomia da Arquitetura) com os Adapters de Saída — as implementações concretas das Secondary Ports vistas em 2.3.1.2, cada uma amarrada a uma tecnologia de infraestrutura específica.

---

## O papel do Adapter de Saída

Um Adapter de Saída implementa uma Secondary Port usando uma tecnologia concreta — banco relacional, banco não-relacional, serviço de e-mail, cache, sistema de filas. Toda a complexidade e o vocabulário específico daquela tecnologia (SQL, drivers, SDKs, protocolos) ficam confinados dentro do Adapter; do lado de fora, só existe a interface da Port.

---

## Database Adapter (JPA)

```java
@Repository
public class ProdutoJPAAdapter implements ProdutoRepository {
    private final ProdutoJPARepository jpaRepository;
    private final ProdutoEntityMapper mapper;

    @Override
    public Produto salvar(Produto produto) {
        ProdutoEntity entity = mapper.toEntity(produto);      // domínio → entidade JPA
        ProdutoEntity saved = jpaRepository.save(entity);
        return mapper.toDomain(saved);                        // entidade JPA → domínio
    }

    @Override
    public Optional<Produto> buscarPorId(ProdutoId id) {
        return jpaRepository.findById(id.getValue())
            .map(mapper::toDomain);
    }
}

// Entidade JPA — só existe aqui, nunca no domínio (reforça a regra de 1.2.1.1)
@Entity
@Table(name = "produtos")
public class ProdutoEntity {
    @Id
    private String id;

    @Column(nullable = false)
    private String nome;

    @Column(precision = 10, scale = 2)
    private BigDecimal preco;

    @Column(length = 3)
    private String moeda;
}
```

O `mapper` é o componente que faz a tradução bidirecional entre `Produto` (domínio, POJO puro) e `ProdutoEntity` (anotada com JPA). Essa fronteira de tradução é exatamente o que impede as anotações `@Entity`/`@Table` de vazarem para o domínio.

## NoSQL Adapter (MongoDB)

```java
@Repository
public class ProdutoMongoAdapter implements ProdutoRepository {
    private final MongoTemplate mongoTemplate;

    @Override
    public Produto salvar(Produto produto) {
        ProdutoDocument document = ProdutoDocument.from(produto);
        ProdutoDocument saved = mongoTemplate.save(document);
        return saved.toDomain();
    }

    @Override
    public Optional<Produto> buscarPorId(ProdutoId id) {
        Query query = new Query(Criteria.where("_id").is(id.getValue()));
        ProdutoDocument document = mongoTemplate.findOne(query, ProdutoDocument.class);
        return Optional.ofNullable(document).map(ProdutoDocument::toDomain);
    }
}
```

Repare que `ProdutoJPAAdapter` e `ProdutoMongoAdapter` implementam exatamente a mesma interface `ProdutoRepository`. Isso significa que trocar de PostgreSQL para MongoDB é uma questão de trocar qual Adapter é injetado na Aplicação — nenhuma linha de `GestãoProdutosService` ou do domínio muda.

## External Service Adapter (envio de e-mail)

```java
@Component
public class SendGridEmailAdapter implements ServicoEmail {
    private final SendGrid sendGrid;

    @Override
    public void enviar(Email destinatario, String assunto, String corpo) {
        Mail mail = new Mail(
            new com.sendgrid.helpers.mail.objects.Email("noreply@empresa.com"),
            assunto,
            new com.sendgrid.helpers.mail.objects.Email(destinatario.getValor()),
            new Content("text/html", corpo)
        );

        try {
            Request request = new Request();
            request.setMethod(Method.POST);
            request.setEndpoint("mail/send");
            request.setBody(mail.build());

            Response response = sendGrid.api(request);
            if (response.getStatusCode() >= 400) {
                throw new FalhaEnvioEmailException("Erro ao enviar email: " + response.getBody());
            }
        } catch (IOException e) {
            // Traduz exceção técnica (IOException) para exceção de domínio/aplicação
            throw new FalhaEnvioEmailException("Erro de comunicação com SendGrid", e);
        }
    }
}
```

Um detalhe importante aqui: o `catch (IOException e)` **captura** a exceção técnica do SDK do SendGrid e a **traduz** para `FalhaEnvioEmailException`, uma exceção que pertence ao vocabulário da aplicação. Isso evita que uma exceção específica de uma biblioteca externa vaze para quem chamou `ServicoEmail`, reforçando novamente a regra de dependência vista em 1.2.1.1.

## Cache Adapter

```java
@Component
public class RedisCacheAdapter implements CacheProduto {
    private final RedisTemplate<String, String> redisTemplate;
    private final ObjectMapper objectMapper;

    @Override
    public void salvar(ProdutoId id, Produto produto, Duration ttl) {
        try {
            String json = objectMapper.writeValueAsString(produto);
            redisTemplate.opsForValue().set(chaveCache(id), json, ttl);
        } catch (JsonProcessingException e) {
            log.error("Erro ao serializar produto para cache", e);
        }
    }

    @Override
    public Optional<Produto> buscar(ProdutoId id) {
        String json = redisTemplate.opsForValue().get(chaveCache(id));
        if (json == null) return Optional.empty();

        try {
            return Optional.of(objectMapper.readValue(json, Produto.class));
        } catch (JsonProcessingException e) {
            log.error("Erro ao deserializar produto do cache", e);
            return Optional.empty();
        }
    }

    private String chaveCache(ProdutoId id) {
        return "produto:" + id.getValue();
    }
}
```

Aqui vale notar uma decisão de design: falhas de cache (serialização, Redis indisponível) são tratadas como **degradação silenciosa** (loga e retorna vazio), não como exceção que interrompe o fluxo. Isso é uma escolha deliberada, típica de Adapters de cache — o cache é uma otimização, não uma fonte de verdade, então sua falha não deveria quebrar o caso de uso principal.

## Message Publisher Adapter

```java
@Component
public class RabbitMQEventPublisher implements PublicadorEventos {
    private final RabbitTemplate rabbitTemplate;
    private final ObjectMapper objectMapper;

    @Override
    public void publicar(EventoDominio evento) {
        try {
            String eventoJson = objectMapper.writeValueAsString(evento);
            rabbitTemplate.convertAndSend(
                "eventos-dominio",                    // exchange
                evento.getClass().getSimpleName(),    // routing key
                eventoJson
            );
            log.info("Evento publicado: {}", evento.getClass().getSimpleName());
        } catch (JsonProcessingException e) {
            throw new FalhaPublicacaoEventoException("Erro ao serializar evento", e);
        }
    }
}
```

Esse Adapter fecha o ciclo completo dos Domain Events vistos em 2.1.1.2: o domínio apenas registra o evento numa lista interna (`Pedido.obterEventosPendentes()`), a Aplicação chama `PublicadorEventos.publicar()` (a Secondary Port), e é só aqui, no Adapter, que RabbitMQ finalmente entra em cena.

## Visão consolidada: um Port, múltiplos Adapters possíveis

| Secondary Port | Adapters possíveis (intercambiáveis) |
|---|---|
| `ProdutoRepository` | `ProdutoJPAAdapter` (PostgreSQL/MySQL), `ProdutoMongoAdapter` (MongoDB), um `ProdutoInMemoryAdapter` (para testes) |
| `ServicoEmail` | `SendGridEmailAdapter`, um futuro `TwilioSmsAdapter`, um `ConsoleLogEmailAdapter` (ambiente de desenvolvimento) |
| `PublicadorEventos` | `RabbitMQEventPublisher`, um futuro `KafkaEventPublisher`, um `InMemoryEventPublisher` (testes) |

Essa tabela é a demonstração concreta de por que vale a pena isolar as Secondary Ports: cada linha representa uma decisão de infraestrutura que pode mudar no futuro (trocar de fila, trocar de provedor de e-mail, trocar de banco) sem que o domínio ou a aplicação percebam a diferença.

## 🧩 Quiz de Fixação

1. Qual é a função do `mapper` dentro do `ProdutoJPAAdapter`, e por que ele é necessário mesmo existindo uma Secondary Port bem definida?
2. Por que o `SendGridEmailAdapter` captura `IOException` e relança como `FalhaEnvioEmailException`, em vez de deixar a exceção original propagar?
3. Por que o `RedisCacheAdapter` trata falhas de serialização como degradação silenciosa (log + retorno vazio), enquanto o `ProdutoJPAAdapter` normalmente propagaria uma exceção em caso de falha?

**Respostas:**
1) O `mapper` converte entre a representação de domínio (`Produto`, um POJO puro) e a representação técnica exigida pelo JPA (`ProdutoEntity`, anotada com `@Entity`/`@Table`). Ele é necessário porque a Secondary Port (`ProdutoRepository`) fala a língua do domínio, mas a tecnologia de persistência exige uma estrutura de dados própria — o mapper é a ponte entre os dois mundos, mantendo o domínio livre de anotações JPA.
2) Porque `IOException` é uma exceção técnica específica do mecanismo de comunicação (rede, biblioteca do SendGrid) — deixá-la propagar faria com que quem chama `ServicoEmail` (a Aplicação) precisasse conhecer detalhes de implementação do SendGrid, violando a regra de que o domínio/aplicação não deve depender de tecnologia externa. Traduzir para `FalhaEnvioEmailException` mantém a abstração da Port consistente, independente de qual Adapter está por trás.
3) Porque o cache é uma otimização de performance, não uma fonte de verdade dos dados — se ele falhar, o sistema ainda pode funcionar corretamente buscando os dados de outra fonte (o banco, por exemplo), então faz sentido degradar silenciosamente. Já uma falha de persistência no banco de dados principal (JPA) normalmente representa uma falha real da operação que o usuário está tentando realizar, e por isso deve propagar como exceção para que o caso de uso saiba que a operação não foi concluída com sucesso.
