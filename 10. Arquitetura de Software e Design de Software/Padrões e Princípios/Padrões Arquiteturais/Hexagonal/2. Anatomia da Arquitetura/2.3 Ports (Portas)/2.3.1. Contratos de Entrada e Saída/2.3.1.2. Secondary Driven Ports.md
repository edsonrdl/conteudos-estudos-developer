### Secondary/Driven Ports

O arquivo anterior (2.3.1.1) mostrou as Portas de Entrada, que expõem o que a aplicação **oferece**. Este arquivo cobre o lado espelhado: as Portas de Saída, que declaram o que a aplicação **precisa** do mundo externo.

---

## O que é uma Secondary/Driven Port

Uma Secondary Port (ou Driven Port) é uma interface definida pela aplicação — não pela tecnologia — descrevendo uma necessidade: persistir dados, enviar um e-mail, publicar um evento. O nome "driven" (que é acionado, que obedece) reflete a direção invertida em relação às Primary Ports: aqui, é a **aplicação quem toma a iniciativa** de chamar a porta, e o adaptador do outro lado apenas obedece à necessidade declarada.

**Analogia:** pense numa tomada de força de uma furadeira. A furadeira (o domínio/aplicação) define o que precisa — "energia elétrica em um formato padrão" — sem se importar se a energia vem de uma tomada de parede, de um gerador ou de uma bateria portátil. A tomada da furadeira é a Secondary Port; o que está plugado nela (rede elétrica, gerador, bateria) é o Adapter.

```
   ┌─────────────────────┐
   │      Domínio /        │
   │      Aplicação        │
   └──────────┬────────────┘
              │ chama (a aplicação toma a iniciativa)
              ▼
   ┌─────────────────────┐
   │  Secondary Port        │   ← interface, definida pela necessidade da aplicação
   │  (ProdutoRepository)   │
   └──────────┬────────────┘
              │ implementada por
              ▼
   ┌─────────────────────┐
   │  Adapter de saída      │   (JPA, MongoDB, SendGrid, RabbitMQ...)
   └──────────┬────────────┘
              │
              ▼
      Banco / API externa / Fila
      (obedece à chamada — driven)
```

## Exemplos práticos

```java
// SECONDARY PORT — necessidade de persistência
public interface ProdutoRepository {
    Produto salvar(Produto produto);
    Optional<Produto> buscarPorId(ProdutoId id);
    List<Produto> buscarPorCategoria(Categoria categoria);
    void excluir(ProdutoId id);
    boolean existe(ProdutoId id);
}

// SECONDARY PORT — necessidade de comunicação externa
public interface ServicoEmail {
    void enviar(Email destinatario, String assunto, String corpo);
    void enviarComAnexo(Email destinatario, String assunto, String corpo, Anexo anexo);
}

// SECONDARY PORT — necessidade de publicação assíncrona
public interface PublicadorEventos {
    void publicar(EventoDominio evento);
    void publicarTodos(List<EventoDominio> eventos);
}
```

Note que nenhuma dessas três interfaces menciona JPA, SMTP, SendGrid, Kafka ou RabbitMQ. Elas descrevem **capacidades que a aplicação precisa**, no vocabulário do próprio domínio (`Produto`, `Email`, `EventoDominio`) — quem decide a tecnologia concreta por trás é sempre o Adapter, criado depois e independentemente da Port.

---

## A regra de ouro: quem desenha a interface

A diferença mais importante entre uma Secondary Port bem desenhada e uma mal desenhada não é sintática — é sobre **quem dita o formato da interface**.

| Quem desenha a interface | Resultado |
|---|---|
| O domínio/aplicação desenha pensando no que precisa (`buscarPorCategoria(Categoria)`) | Port estável, independente de tecnologia — pode trocar de banco livremente |
| O banco de dados (ou uma biblioteca) dita o formato (`findByCategoriaEquals(String, Pageable)`, no estilo Spring Data) | Port acoplada indiretamente à tecnologia escolhida — trocar de biblioteca de acesso a dados exige mudar a Port |

Essa regra é chamada, na literatura de DDD e hexagonal, de **"a porta pertence ao lado de dentro"**: mesmo sendo implementada por um adapter externo, a interface é definida e é dona do domínio/aplicação, nunca da tecnologia.

---

## Como Secondary Ports habilitam a substituição de tecnologia

```java
// A aplicação depende apenas da abstração
public class GestãoProdutosService implements GestãoProdutos {
    private final ProdutoRepository produtoRepository; // Secondary Port

    public ProdutoId criarProduto(CriarProdutoCommand comando) {
        Produto produto = new Produto(/* ... */);
        return produtoRepository.salvar(produto).getId();
    }
}
```

Trocar `ProdutoJPAAdapter` por `ProdutoMongoAdapter` (assunto do próximo domínio, sobre Adapters) não exige nenhuma mudança em `GestãoProdutosService` nem em `ProdutoRepository` — apenas a injeção de dependência aponta para uma implementação diferente.

## Erro comum: Secondary Port encapsulando lógica de negócio

Assim como as Application Services não devem decidir regras de negócio (visto em 2.2.1.1), uma Secondary Port também não deveria carregar decisões de negócio — ela deve ser uma operação técnica pura.

```java
// ERRADO — a Port decide uma regra de negócio (quem pode ser notificado)
public interface ServicoEmail {
    void enviarSeClienteAtivo(Cliente cliente, String mensagem); // decisão de negócio na Port!
}

// CORRETO — a Port só executa; a decisão fica no domínio/aplicação
public interface ServicoEmail {
    void enviar(Email destinatario, String mensagem);
}
// A decisão "só notificar se ativo" continua no domínio: if (cliente.isAtivo()) { ... }
```

## 🧩 Quiz de Fixação

1. Por que o nome "Driven Port" reflete o fato de que a aplicação toma a iniciativa de chamar essa porta, ao contrário do que acontece com uma Primary Port?
2. O que significa a regra "a porta pertence ao lado de dentro", e por que uma interface no estilo `findByCategoriaEquals(String, Pageable)` viola essa regra mesmo sendo tecnicamente uma abstração?
3. Por que colocar uma decisão de negócio (como "só enviar e-mail se o cliente estiver ativo") dentro da assinatura de uma Secondary Port é considerado um erro de design?

**Respostas:**
1) Porque, nas Secondary Ports, é a própria aplicação/domínio que decide chamar a porta quando precisa de algo do mundo externo (salvar, notificar, publicar) — o adaptador do outro lado apenas obedece e executa a operação solicitada. Isso é o oposto da Primary Port, onde é o mundo externo quem aciona a aplicação.
2) Significa que a interface deve ser desenhada em função das necessidades do domínio/aplicação, não em função de como uma tecnologia específica representa ou nomeia suas operações. Uma assinatura como `findByCategoriaEquals(String, Pageable)` reflete convenções de uma biblioteca específica (Spring Data), então trocar de biblioteca de acesso a dados exigiria alterar a própria porta — revelando que ela está, na prática, acoplada à tecnologia, mesmo sendo uma interface.
3) Porque isso mistura uma decisão de negócio (quem deve ou não receber a notificação) com uma capacidade puramente técnica (como enviar um e-mail). Se a regra de elegibilidade mudar no futuro (por exemplo, passar a notificar clientes inativos em certas situações), seria necessário alterar a Secondary Port e todos os seus Adapters, quando na verdade a mudança deveria ficar isolada dentro do domínio, que é quem decide "quando" chamar a porta.
