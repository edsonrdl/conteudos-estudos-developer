### Primary/Driving Ports

Com Domínio (2.1) e Aplicação (2.2) já mapeados, chegamos ao elemento que torna tudo isso "hexagonal" de fato: as Ports. Este arquivo cobre as Portas de Entrada — o contrato que define **o que a aplicação é capaz de fazer**.

---

## O que é uma Primary/Driving Port

Uma Primary Port (também chamada de Driving Port) é uma interface que declara as capacidades oferecidas pela aplicação — os casos de uso disponíveis para quem quiser "acionar" o sistema. O nome "driving" (que dirige, que aciona) vem exatamente disso: quem está do lado de fora é quem toma a iniciativa de chamar essa porta.

**Analogia:** pense no volante de um carro. O volante é a interface (porta) através da qual o motorista comanda o carro — ele não precisa saber como a direção hidráulica funciona por dentro. Só existe uma forma padronizada de "dar comandos" ao carro: girar o volante, pisar nos pedais. A Primary Port é esse painel de comandos da aplicação.

```
   Usuário / Sistema externo
            │
            │ aciona (drives)
            ▼
   ┌─────────────────────┐
   │  Adapter de Entrada   │   (REST Controller, CLI, GraphQL Resolver)
   └──────────┬────────────┘
              │ chama
              ▼
   ┌─────────────────────┐
   │   Primary Port        │   ← interface, vive no lado da Aplicação
   │  (GestãoProdutos)      │
   └──────────┬────────────┘
              │ implementada por
              ▼
   ┌─────────────────────┐
   │  Application Service  │
   └─────────────────────┘
```

## Exemplo prático

```java
// PRIMARY PORT — define as capacidades da aplicação
public interface GestãoProdutos {
    // Comandos (alteram estado)
    ProdutoId criarProduto(CriarProdutoCommand comando);
    void atualizarProduto(AtualizarProdutoCommand comando);
    void excluirProduto(ProdutoId id);

    // Consultas (apenas leitura)
    ProdutoDetalhes buscarProduto(ProdutoId id);
    ListaPaginada<ProdutoResumo> listarProdutos(FiltrosProduto filtros);
    EstatisticasProdutos obterEstatisticas();
}

// Implementação — o Application Service concretiza o contrato
@Service
public class GestãoProdutosService implements GestãoProdutos {
    @Override
    public ProdutoId criarProduto(CriarProdutoCommand comando) {
        // orquestra o caso de uso, como visto em 2.2.1.1
    }
    // ... demais métodos
}
```

Repare que a interface `GestãoProdutos` não menciona HTTP, JSON, REST ou qualquer detalhe de transporte — ela fala inteiramente no vocabulário da aplicação (`ProdutoId`, `CriarProdutoCommand`, `ProdutoDetalhes`). Isso é o que permite que múltiplos adapters de entrada diferentes (um REST Controller, um CLI, um listener de fila) chamem exatamente o mesmo Port sem duplicar lógica.

## Quem depende de quem

| Papel | Depende de | Não depende de |
|---|---|---|
| Adapter de entrada (REST Controller) | Da Primary Port (`GestãoProdutos`) | Da implementação concreta (`GestãoProdutosService`) diretamente |
| Application Service (`GestãoProdutosService`) | Implementa a Primary Port | Não conhece qual adapter vai chamá-lo |
| Primary Port (`GestãoProdutos`) | Nada — é uma interface pura | Não depende de HTTP, do Adapter ou de qualquer tecnologia |

Essa tabela evidencia a inversão de dependência: o adapter de entrada depende de uma abstração (`GestãoProdutos`), não de uma implementação concreta. Isso permite, por exemplo, trocar `GestãoProdutosService` por uma versão de teste (mock) sem alterar o Controller.

## Erro comum: Port "gorda" demais

Um erro recorrente é transformar uma única Primary Port em um "hub" gigantesco com dezenas de métodos não relacionados — o oposto do Princípio da Segregação de Interfaces (o "I" do SOLID).

| Sintoma | Problema |
|---|---|
| Uma única interface `SistemaService` com 40 métodos cobrindo produtos, pedidos, clientes e relatórios | Qualquer adapter que use um método precisa conhecer/implementar (ou mockar) uma interface enorme |
| Um novo caso de uso obriga a alterar uma interface já usada por vários adapters | Sinal de que a Port deveria ser dividida por área de responsabilidade |

**Correção:** dividir em portas menores e coesas — `GestãoProdutos`, `GestãoPedidos`, `RelatoriosProdutos` — cada uma representando um agrupamento coerente de casos de uso, em vez de uma porta única "para tudo".

## 🧩 Quiz de Fixação

1. Por que o nome "Driving Port" reflete o fato de que quem está do lado de fora "aciona" a aplicação?
2. Na tabela de dependências, por que o Adapter de entrada depende da interface `GestãoProdutos` e não diretamente da classe `GestãoProdutosService`?
3. Qual princípio do SOLID é violado quando uma única Primary Port acumula dezenas de métodos não relacionados, e qual é a correção recomendada?

**Respostas:**
1) Porque, nesse tipo de porta, é o mundo externo (um usuário, outro sistema, um job agendado) quem toma a iniciativa de chamar a aplicação — o adaptador de entrada traduz esse estímulo externo em uma chamada ao método da porta. A aplicação não inicia a ação; ela é "dirigida" (driven) a agir por quem está de fora.
2) Porque depender da interface, e não da implementação concreta, é o que permite trocar a implementação (por exemplo, por uma versão de teste ou uma nova versão do serviço) sem que o Adapter de entrada precise mudar. Essa é a aplicação prática da Inversão de Dependência: o código de alto nível (o contrato) não deve depender de detalhes de baixo nível (a implementação específica).
3) É violado o Princípio da Segregação de Interfaces (Interface Segregation Principle, o "I" do SOLID), que recomenda que clientes não devem ser forçados a depender de métodos que não usam. A correção é dividir a porta gigante em portas menores e coesas, cada uma representando um agrupamento coerente de casos de uso relacionados.
