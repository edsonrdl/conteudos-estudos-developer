### Application Services e Use Cases

Com os blocos do domínio (2.1) já mapeados, este arquivo entra na Camada de Aplicação — a camada que fica entre os Adapters e o Domínio, responsável por orquestrar o fluxo de um caso de uso sem carregar nenhuma regra de negócio própria.

---

## O papel da Camada de Aplicação

Se o Domínio é o "cérebro" que sabe as regras, a Aplicação é o "maestro" que rege a ordem em que essas regras são chamadas. Um Application Service (também chamado de Use Case) **coordena**, mas não **decide** — toda decisão de negócio é delegada ao domínio.

**Analogia:** pense em um garçom de restaurante. Ele não cozinha (isso é o domínio/cozinha) e não fabrica os ingredientes (isso é a infraestrutura/fornecedores) — ele coordena o pedido, leva a comanda até a cozinha, busca o prato pronto e leva até a mesa certa, na ordem certa. Um Application Service faz exatamente esse papel de coordenação entre as partes.

**Responsabilidades de um Application Service:**
- Buscar os Aggregates necessários (via Ports de saída).
- Chamar métodos do domínio para executar as regras de negócio.
- Coordenar múltiplos Aggregates ou Domain Services quando o caso de uso exige.
- Gerenciar a fronteira transacional (uma transação de banco por caso de uso, tipicamente).
- Publicar os eventos de domínio pendentes após a persistência.
- Registrar logs técnicos e auditoria da operação.

## Exemplo prático — um caso de uso completo

```java
@Service
@Transactional
public class FinalizarPedidoUseCase {
    private final PedidoRepository pedidoRepository;
    private final ClienteRepository clienteRepository;
    private final ServicoCalculoFrete servicoFrete;
    private final GatewayPagamento gatewayPagamento;
    private final ServicoNotificacao servicoNotificacao;
    private final PublicadorEventos publicadorEventos;

    public PedidoId executar(FinalizarPedidoCommand comando) {
        // 1. Busca agregados necessários (via Ports de saída)
        Pedido pedido = pedidoRepository.buscarPorId(comando.getPedidoId())
            .orElseThrow(() -> new PedidoNaoEncontradoException());

        Cliente cliente = clienteRepository.buscarPorId(pedido.getClienteId())
            .orElseThrow(() -> new ClienteNaoEncontradoException());

        // 2. Valida pré-condições (a REGRA em si mora no domínio)
        if (!cliente.podeRealizarCompra()) {
            throw new ClienteImpedidoCompraException();
        }

        // 3. Calcula frete (delega ao Domain Service)
        Dinheiro valorFrete = servicoFrete.calcularFrete(
            pedido, comando.getEnderecoEntrega(), comando.getTipoEntrega()
        );

        // 4. Aplica frete ao pedido (a lógica de "como aplicar" mora no domínio)
        pedido.aplicarFrete(valorFrete);

        // 5. Processa pagamento (chamada a um Secondary Port de infraestrutura)
        ResultadoPagamento resultado = gatewayPagamento.processar(
            new SolicitacaoPagamento(pedido.getValorTotal(), comando.getDadosPagamento())
        );
        if (!resultado.foiAprovado()) {
            throw new PagamentoRecusadoException(resultado.getMotivo());
        }

        // 6. Finaliza pedido (regra de negócio dentro do Aggregate)
        pedido.finalizar();
        pedido.registrarPagamento(resultado.getTransacaoId());

        // 7. Persiste mudanças (Secondary Port)
        Pedido pedidoSalvo = pedidoRepository.salvar(pedido);

        // 8. Publica eventos de domínio pendentes (Secondary Port)
        publicadorEventos.publicarTodos(pedido.obterEventosPendentes());

        // 9. Envia notificações (Secondary Port)
        servicoNotificacao.notificarPedidoFinalizado(cliente.getEmail(), pedidoSalvo);

        return pedidoSalvo.getId();
    }
}
```

Repare na numeração dos passos: cada um chama um Port (seja de domínio, seja de infraestrutura), mas nenhuma linha decide **se** o cliente pode comprar, **como** calcular o frete ou **quando** um pedido pode ser finalizado — essas decisões pertencem exclusivamente ao domínio (`Cliente.podeRealizarCompra()`, `ServicoCalculoFrete`, `Pedido.finalizar()`).

## Onde termina a Aplicação e começa o vazamento de regra de negócio

Esse é o erro mais comum ao escrever Application Services: deixar uma condição de negócio "vazar" para dentro do método `executar()`.

```java
// ERRADO — regra de negócio vazando para a Aplicação
public PedidoId executar(FinalizarPedidoCommand comando) {
    Pedido pedido = pedidoRepository.buscarPorId(comando.getPedidoId()).orElseThrow();

    // Essa condição é uma REGRA DE NEGÓCIO, não deveria estar aqui
    if (pedido.getItens().isEmpty() || pedido.getValorTotal().menorQue(VALOR_MINIMO)) {
        throw new PedidoInvalidoException();
    }

    pedido.finalizar();
    return pedidoRepository.salvar(pedido).getId();
}

// CORRETO — a regra mora dentro do Aggregate
public PedidoId executar(FinalizarPedidoCommand comando) {
    Pedido pedido = pedidoRepository.buscarPorId(comando.getPedidoId()).orElseThrow();
    pedido.finalizar(); // a própria Entity valida itens vazios e valor mínimo internamente
    return pedidoRepository.salvar(pedido).getId();
}
```

| Pergunta de verificação | Sinal de vazamento |
|---|---|
| O Application Service tem algum `if` que decide um comportamento de negócio (não apenas fluxo técnico)? | Sim → a regra deveria estar no domínio |
| O mesmo `if` precisaria ser repetido em outro Use Case que também manipula `Pedido`? | Sim → prova de que a regra pertence ao Aggregate, não a um Use Case isolado |
| Remover o Application Service e chamar o domínio "na mão" quebraria alguma regra? | Se sim, a regra estava, na verdade, escondida na Aplicação |

---

## Quando criar um Application Service

- Um Application Service por caso de uso do sistema — não um "service genérico" que faz várias coisas.
- Quando a operação envolve buscar e coordenar mais de um Aggregate.
- Quando é necessário abrir uma fronteira transacional explícita (`@Transactional`).
- Quando o fluxo depende de infraestrutura externa (pagamento, e-mail, fila) além do próprio domínio.

## 🧩 Quiz de Fixação

1. Qual é a diferença de responsabilidade entre um Application Service e uma regra dentro de um Aggregate, usando a analogia do garçom e da cozinha?
2. No exemplo do `FinalizarPedidoUseCase`, por que a validação "pedido não pode ser finalizado vazio" não deveria estar escrita diretamente dentro do método `executar()`?
3. Qual pergunta de verificação ajuda a identificar quando uma regra de negócio "vazou" para dentro de um Application Service?

**Respostas:**
1) O Application Service (garçom) coordena a ordem das etapas — busca dados, chama serviços, gerencia transação — mas não decide nada sobre o conteúdo do negócio. O Aggregate (cozinha) é quem efetivamente aplica as regras de negócio, como decidir se um pedido pode ou não ser finalizado.
2) Porque essa é uma regra de negócio (uma invariante do Aggregate `Pedido`), e não uma decisão de orquestração de fluxo. Se ficasse no Application Service, qualquer outro caso de uso que também manipulasse pedidos precisaria repetir a mesma validação manualmente, criando risco de divergência e duplicação.
3) A pergunta é: "removendo o Application Service e chamando o domínio diretamente, alguma regra de negócio deixaria de ser respeitada?" Se a resposta for sim, isso prova que a regra estava, na verdade, escondida dentro da camada de Aplicação, e deveria ser movida para dentro do Aggregate ou Domain Service correspondente.
