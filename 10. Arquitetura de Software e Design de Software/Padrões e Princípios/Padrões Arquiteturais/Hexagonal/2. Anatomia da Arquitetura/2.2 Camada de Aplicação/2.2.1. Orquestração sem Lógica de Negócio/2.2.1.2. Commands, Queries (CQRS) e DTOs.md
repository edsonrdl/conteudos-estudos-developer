### Commands, Queries (CQRS) e DTOs

O arquivo anterior (2.2.1.1) mostrou o Application Service orquestrando um caso de uso completo. Este arquivo detalha os objetos que entram e saem dessa orquestração: Commands e Queries, que representam intenções, e DTOs, que transportam dados sem vazar o modelo de domínio para fora da aplicação.

---

## Commands — intenções de mudança

Um Command é um objeto que representa a **intenção de alterar o estado** do sistema. Ele carrega os dados necessários para a operação, mas não decide se a operação é válida do ponto de vista de negócio — isso continua sendo papel do domínio.

```java
public class CriarProdutoCommand {
    @NotNull
    private String nome;

    @NotNull @Positive
    private BigDecimal preco;

    @NotNull
    private String categoria;

    private String descricao;

    // Validação de FORMATO (não de negócio) pode viver no próprio Command
    public void validar() {
        if (nome.length() < 3) {
            throw new ComandoInvalidoException("Nome deve ter no mínimo 3 caracteres");
        }
    }
}

@Service
public class CriarProdutoCommandHandler {
    @Transactional
    public ProdutoId handle(CriarProdutoCommand comando) {
        comando.validar();

        Produto produto = new Produto(
            comando.getNome(),
            new Dinheiro(comando.getPreco(), Moeda.BRL),
            Categoria.valueOf(comando.getCategoria())
        );

        Produto salvo = produtoRepository.salvar(produto);
        return salvo.getId();
    }
}
```

Repare na distinção sutil: `comando.validar()` verifica **formato** (nome tem tamanho mínimo?) — isso é aceitável no próprio Command. Mas qualquer verificação sobre **regra de negócio** (ex: "esse cliente pode criar produtos nessa categoria?") pertenceria ao domínio, não ao Command.

## Queries — intenções de consulta

Uma Query representa a intenção de **ler** dados, sem alterar nenhum estado. Diferente de um Command, uma Query normalmente não passa pelo domínio rico — ela pode usar um caminho de leitura otimizado, muitas vezes lendo diretamente para um modelo de leitura (Read Model) desenhado para a tela ou relatório que vai consumi-la.

```java
public class BuscarProdutosPorCategoriaQuery {
    private final String categoria;
    private final int pagina;
    private final int tamanhoPagina;
}

@Service
public class BuscarProdutosPorCategoriaQueryHandler {
    public PaginaResultado<ProdutoDTO> handle(BuscarProdutosPorCategoriaQuery query) {
        // Busca otimizada para leitura — não precisa reconstruir o Aggregate inteiro
        return produtoReadRepository.buscarPorCategoria(
            query.getCategoria(),
            PageRequest.of(query.getPagina(), query.getTamanhoPagina())
        );
    }
}
```

Essa separação entre o caminho de escrita (Commands, que passam pelo Aggregate e suas regras) e o caminho de leitura (Queries, que podem ir direto a uma projeção otimizada) é a essência do padrão **CQRS** (Command Query Responsibility Segregation). Na Arquitetura Hexagonal, CQRS não é obrigatório, mas se encaixa naturalmente: Commands viram chamadas a Primary Ports que acionam o domínio; Queries podem, quando fizer sentido, contornar o domínio e ir direto a um Secondary Port de leitura.

| Aspecto | Command | Query |
|---|---|---|
| Objetivo | Alterar estado | Ler dados, sem efeito colateral |
| Passa pelo domínio rico? | Sim — precisa respeitar invariantes do Aggregate | Não necessariamente — pode ler de uma projeção otimizada |
| Retorno típico | ID do recurso criado/alterado, ou vazio | DTO ou lista de DTOs prontos para exibição |
| Nomenclatura | Verbo no imperativo (`CriarProdutoCommand`) | Pergunta/busca (`BuscarProdutosPorCategoriaQuery`) |

## DTOs — a fronteira de dados entre camadas

Um DTO (Data Transfer Object) existe para transportar dados **para fora** da aplicação sem expor diretamente as classes de domínio. Isso evita dois problemas: acoplar o contrato externo (JSON de uma API, por exemplo) à estrutura interna do domínio, e vazar métodos de negócio para quem só deveria consumir dados.

```java
public class ProdutoDTO {
    private String id;
    private String nome;
    private BigDecimal preco;
    private String moeda;
    private String categoria;
    private String status;

    // Método factory converte do domínio para o DTO — nunca o contrário
    public static ProdutoDTO fromDomain(Produto produto) {
        ProdutoDTO dto = new ProdutoDTO();
        dto.id = produto.getId().getValue();
        dto.nome = produto.getNome();
        dto.preco = produto.getPreco().getValor();
        dto.moeda = produto.getPreco().getMoeda().getCodigo();
        dto.categoria = produto.getCategoria().name();
        dto.status = produto.getStatus().name();
        return dto;
    }
}
```

**Por que não devolver a Entity `Produto` diretamente pela API?** Três motivos práticos:

1. **Vazamento de estrutura interna:** se `Produto` ganhar um novo campo interno amanhã, ele apareceria automaticamente na resposta da API, mesmo sem ninguém decidir expor isso.
2. **Vazamento de comportamento:** a Entity pode ter métodos como `aplicarDesconto()` que não fazem sentido serializados como dado, e frameworks de serialização às vezes tentam serializar getters que na verdade são regras de negócio.
3. **Acoplamento de versionamento:** mudar o modelo de domínio (uma refatoração interna legítima) quebraria o contrato público da API, mesmo que o comportamento externo devesse continuar igual.

**Quando usar DTOs:**
- Toda vez que dados atravessam a fronteira da aplicação para o mundo externo (resposta HTTP, mensagem de fila, arquivo exportado).
- Quando é necessário otimizar uma consulta específica sem forçar o formato do Aggregate completo.
- Quando a API precisa evoluir de forma independente do modelo de domínio (versionamento).

## 🧩 Quiz de Fixação

1. Qual é a diferença de propósito entre um Command e uma Query, e por que uma Query pode "contornar" o domínio rico enquanto um Command normalmente não pode?
2. No exemplo do `CriarProdutoCommand`, por que o método `validar()` que checa o tamanho do nome é aceitável ali, mas uma verificação de regra de negócio não seria?
3. Cite dois motivos práticos para nunca devolver uma Entity de domínio diretamente como resposta de uma API, preferindo um DTO.

**Respostas:**
1) Um Command representa uma intenção de alterar o estado do sistema, e por isso precisa passar pelas regras e invariantes do Aggregate de domínio para garantir consistência. Uma Query apenas lê dados, sem efeito colateral, então pode ir direto a uma projeção de leitura otimizada, sem precisar reconstruir e validar um Aggregate completo.
2) Porque validar o tamanho mínimo de uma string é uma verificação de **formato** dos dados de entrada, não uma decisão sobre o negócio em si. Uma regra de negócio (como "esse cliente tem permissão para criar produtos nessa categoria") depende de contexto e estado do domínio, e por isso deve ser decidida dentro do domínio, não no próprio objeto de transporte de dados.
3) Primeiro, evita vazar a estrutura interna do domínio — um novo campo interno na Entity não aparece automaticamente na API. Segundo, evita vazar comportamento — métodos de negócio da Entity não são acidentalmente serializados como se fossem dados, e mudanças internas no modelo de domínio não quebram o contrato público da API.
