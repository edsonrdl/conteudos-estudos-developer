### Entities, Value Objects, Domain Services e Aggregates

Com os fundamentos e o princípio de dependência estabelecidos no Domínio 1, chega a hora de abrir o núcleo da arquitetura hexagonal — a Camada de Domínio — e ver os blocos de construção concretos que a compõem. Este arquivo cobre os quatro blocos mais usados no dia a dia: Entities, Value Objects, Domain Services e Aggregates.

## Entities (Entidades)

Uma Entity é um objeto que possui **identidade única** — algo que a distingue de qualquer outro objeto, mesmo que todos os outros atributos sejam idênticos. Essa identidade é o que importa, não o conteúdo momentâneo do objeto.

**Analogia:** duas pessoas podem ter o mesmo nome e a mesma data de nascimento, mas continuam sendo duas pessoas diferentes — o CPF (identidade) é o que as distingue, não os atributos. Uma Entity funciona da mesma forma: o `ClienteId` é o que importa, não o nome ou o e-mail momentâneo.

**Características:**
- Possui um ID único que não muda durante todo o ciclo de vida do objeto.
- Mantém estado ao longo do tempo — seus atributos podem mudar (nome, e-mail, status).
- Encapsula regras de negócio como métodos, não como dados soltos.

```java
public class Cliente {
    private ClienteId id;          // Identidade única
    private String nome;
    private Email email;           // Value Object
    private StatusCliente status;

    // Regra de negócio encapsulada, não delegada a um "service" externo
    public void ativar() {
        if (this.email == null || !this.email.isValido()) {
            throw new ClienteInvalidoException("Email é obrigatório para ativar cliente");
        }
        this.status = StatusCliente.ATIVO;
    }

    public boolean podeRealizarCompra() {
        return this.status == StatusCliente.ATIVO && !temPendenciaFinanceira();
    }
}
```

**Quando usar:** sempre que o objeto precisa ser rastreado ao longo do tempo e a identidade importa mais que o conjunto de atributos — clientes, pedidos, produtos, contas.

## Value Objects (Objetos de Valor)

Um Value Object é o oposto conceitual de uma Entity: não tem identidade própria, é definido inteiramente pelos seus atributos, e é **imutável**. Dois Value Objects com os mesmos valores são considerados iguais, mesmo sendo instâncias diferentes em memória.

**Analogia:** uma nota de R$ 50 não tem "identidade" — não importa qual nota física você está segurando, R$ 50 é R$ 50. Já um carro tem chassi, placa, histórico — duas unidades do mesmo modelo continuam sendo carros diferentes (Entities).

```java
public final class Dinheiro {
    private final BigDecimal valor;
    private final Moeda moeda;

    public Dinheiro(BigDecimal valor, Moeda moeda) {
        if (valor == null || valor.compareTo(BigDecimal.ZERO) < 0) {
            throw new ValorInvalidoException("Valor não pode ser negativo");
        }
        this.valor = valor;
        this.moeda = Objects.requireNonNull(moeda);
    }

    // Imutabilidade — qualquer operação retorna um NOVO objeto
    public Dinheiro somar(Dinheiro outro) {
        validarMesmaMoeda(outro);
        return new Dinheiro(this.valor.add(outro.valor), this.moeda);
    }

    @Override
    public boolean equals(Object o) {
        if (!(o instanceof Dinheiro)) return false;
        Dinheiro d = (Dinheiro) o;
        return valor.compareTo(d.valor) == 0 && moeda.equals(d.moeda);
    }
}
```

Repare que `somar` não altera o objeto atual — ele retorna uma nova instância. Isso elimina uma classe inteira de bugs causados por mutação compartilhada.

**Quando usar:** para representar conceitos medidos ou descritos (dinheiro, endereço, CPF, período de tempo), nunca para conceitos que precisam de rastreamento individual.

## Domain Services (Serviços de Domínio)

Nem toda regra de negócio pertence naturalmente a uma única Entity. Quando uma operação envolve **múltiplas** entidades, ou quando o cálculo é complexo o suficiente para merecer sua própria classe, ela vira um Domain Service.

```java
public class ServicoCalculoFrete {

    public Dinheiro calcularFrete(Pedido pedido, EnderecoEntrega destino, TipoEntrega tipoEntrega) {
        Dinheiro valorBase = calcularValorBasePorDistancia(pedido.getEnderecoOrigem(), destino);
        Dinheiro valorPeso = calcularAdicionalPorPeso(pedido.getPesoTotal());
        Dinheiro valorUrgencia = calcularAdicionalUrgencia(tipoEntrega);

        return valorBase.somar(valorPeso).somar(valorUrgencia);
    }
}
```

O cálculo de frete não pertence só ao `Pedido`, nem só ao `EnderecoEntrega` — ele nasce da combinação dos dois mais o tipo de entrega. Forçar essa lógica dentro de uma única Entity criaria uma dependência artificial entre classes que deveriam ser independentes.

**Erro comum:** transformar todo método que "não sabe onde colocar" em um Domain Service. Se a lógica pertence claramente a uma única Entity, ela deve morar lá — Domain Services existem para as exceções, não para a regra geral.

## Aggregates (Agregados)

Um Aggregate é um cluster de Entities e Value Objects tratado como uma **única unidade de consistência transacional**. Ele tem uma Entity principal — a **Aggregate Root** — que é o único ponto de entrada permitido para modificar qualquer coisa dentro do cluster.

```java
@AggregateRoot
public class Pedido {
    private PedidoId id;
    private List<ItemPedido> itens;      // Entidades internas do agregado
    private StatusPedido status;
    private Dinheiro valorTotal;

    // Toda modificação passa pela raiz — nunca acesse ItemPedido diretamente de fora
    public void adicionarItem(Produto produto, int quantidade) {
        if (status != StatusPedido.RASCUNHO) {
            throw new PedidoNaoEditavelException();
        }
        if (quantidade <= 0) {
            throw new QuantidadeInvalidaException();
        }
        itens.add(new ItemPedido(produto, quantidade));
        recalcularValorTotal();
    }

    public void finalizar() {
        if (itens.isEmpty()) {
            throw new PedidoVazioException();
        }
        this.status = StatusPedido.FINALIZADO;
    }
}
```

| Regra do Aggregate | Por quê |
|---|---|
| Só a Aggregate Root é referenciada de fora | Evita que código externo altere um `ItemPedido` sem passar pelas invariantes do `Pedido` |
| Uma transação de banco só deve alterar um Aggregate por vez | Mantém a fronteira de consistência clara e evita locks/travamentos entre agregados diferentes |
| Invariantes são validadas na raiz | Ex: "pedido não pode ser finalizado vazio" só pode ser garantido se toda alteração passa por `Pedido` |

## 🧩 Quiz de Fixação

1. Qual é a diferença fundamental entre uma Entity e um Value Object, e como cada um deve tratar a igualdade entre duas instâncias?
2. Por que a lógica de cálculo de frete, no exemplo, foi colocada em um Domain Service em vez de dentro da classe `Pedido`?
3. Por que a regra "só a Aggregate Root pode ser referenciada de fora do agregado" é importante para manter as invariantes de negócio?

**Respostas:**
1) Uma Entity é definida pela sua identidade (um ID único que não muda), então duas Entities só são iguais se tiverem o mesmo ID, mesmo que os demais atributos sejam diferentes. Um Value Object não tem identidade própria — é definido inteiramente pelos seus atributos, então dois Value Objects com os mesmos valores são considerados iguais, e além disso devem ser imutáveis.
2) Porque o cálculo de frete depende da combinação de múltiplas informações que não pertencem exclusivamente a uma única entidade — o pedido (peso, origem), o endereço de destino e o tipo de entrega. Colocar essa lógica dentro de `Pedido` criaria uma dependência artificial e forçaria a entidade a conhecer detalhes de entrega que não são sua responsabilidade primária.
3) Porque permitir que código externo modifique diretamente uma Entity interna (como `ItemPedido`) sem passar pela Aggregate Root abriria brecha para violar invariantes que só a raiz sabe validar — como "pedido não pode ser finalizado vazio" ou "pedido em rascunho não pode receber pagamento". Centralizar as modificações na raiz garante que toda mudança respeite as regras de consistência do agregado inteiro.
