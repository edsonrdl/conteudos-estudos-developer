### Domain Events e Specifications

O arquivo anterior (2.1.1.1) cobriu os quatro blocos estruturais do domínio — Entities, Value Objects, Domain Services e Aggregates. Este arquivo completa o kit de construção tático com dois blocos complementares: Domain Events, que comunicam fatos já ocorridos, e Specifications, que encapsulam regras de negócio reutilizáveis e combináveis.

---

## Domain Events (Eventos de Domínio)

Um Domain Event representa **algo relevante que já aconteceu** no domínio — não uma intenção, não um comando, mas um fato consumado, sempre nomeado no passado (`PedidoFinalizado`, `PagamentoRecusado`, `ClienteAtivado`).

**Analogia:** um evento de domínio é como um recibo de uma ação já concluída — ninguém "cancela" um recibo emitido; no máximo, emite-se outro documento para registrar uma ação corretiva. Da mesma forma, um evento representa um fato imutável do passado, não uma solicitação que pode ser recusada.

```java
public class PedidoFinalizadoEvent extends EventoDominio {
    private final PedidoId pedidoId;
    private final ClienteId clienteId;
    private final Dinheiro valorTotal;
    private final Instant ocorridoEm;

    public PedidoFinalizadoEvent(Pedido pedido) {
        this.pedidoId = pedido.getId();
        this.clienteId = pedido.getClienteId();
        this.valorTotal = pedido.getValorTotal();
        this.ocorridoEm = Instant.now();
    }
}

// O próprio Aggregate Root registra os eventos que produz
public class Pedido {
    private List<EventoDominio> eventos = new ArrayList<>();

    public void finalizar() {
        if (itens.isEmpty()) {
            throw new PedidoVazioException();
        }
        this.status = StatusPedido.FINALIZADO;
        eventos.add(new PedidoFinalizadoEvent(this));
    }

    // A camada de Aplicação lê e publica os eventos pendentes após persistir
    public List<EventoDominio> obterEventosPendentes() {
        List<EventoDominio> eventosPendentes = new ArrayList<>(eventos);
        eventos.clear();
        return eventosPendentes;
    }
}
```

Repare que o próprio `Pedido` (dentro do domínio, sem depender de nenhuma fila ou broker) apenas **registra** o evento numa lista interna. Quem efetivamente publica esse evento para Kafka, RabbitMQ ou qualquer outro mecanismo é a camada de Aplicação, através de um Secondary Port — o domínio nunca conhece a tecnologia de mensageria.

**Quando usar:**
- Para comunicar mudanças relevantes entre diferentes Aggregates sem acoplá-los diretamente.
- Para implementar consistência eventual entre partes do sistema (ou entre microsserviços).
- Para criar trilhas de auditoria a partir de fatos de negócio, não de logs técnicos.

| Sem Domain Events | Com Domain Events |
|---|---|
| `Pedido.finalizar()` chama diretamente `servicoEstoque.reservar()` e `servicoEmail.notificar()` | `Pedido.finalizar()` apenas registra `PedidoFinalizadoEvent`; outros módulos reagem de forma desacoplada |
| Adicionar uma nova reação exige alterar o método `finalizar()` | Adicionar uma nova reação exige apenas um novo assinante do evento — `Pedido` não muda |

## Specifications (Especificações)

O padrão Specification encapsula uma regra de negócio — geralmente uma condição booleana — em um objeto próprio, reutilizável e **combinável** com outras regras através de operadores lógicos (`and`, `or`, `not`).

```java
public interface Specification<T> {
    boolean isSatisfiedBy(T candidate);

    default Specification<T> and(Specification<T> other) {
        return candidate -> this.isSatisfiedBy(candidate)
            && other.isSatisfiedBy(candidate);
    }
}

public class ClienteAtivoSpecification implements Specification<Cliente> {
    @Override
    public boolean isSatisfiedBy(Cliente cliente) {
        return cliente.getStatus() == StatusCliente.ATIVO;
    }
}

public class ClientePremiumSpecification implements Specification<Cliente> {
    @Override
    public boolean isSatisfiedBy(Cliente cliente) {
        return cliente.getTotalCompras().ehMaiorQue(new Dinheiro(10000, Moeda.BRL));
    }
}

// Combinação de regras sem duplicar lógica
Specification<Cliente> clienteElegivelDesconto =
    new ClienteAtivoSpecification()
        .and(new ClientePremiumSpecification());

if (clienteElegivelDesconto.isSatisfiedBy(cliente)) {
    // aplica desconto
}
```

Sem o padrão Specification, a mesma verificação `cliente.getStatus() == StatusCliente.ATIVO && cliente.getTotalCompras()...` tenderia a ser copiada em vários lugares do sistema — um `if` no controller, outro na regra de desconto, outro em um relatório. Cada cópia é uma chance de a regra divergir com o tempo. Com Specifications, a regra existe em um único lugar e é reutilizada por composição.

**Quando usar:**
- Regras de negócio que aparecem em múltiplos pontos do sistema (validação, filtros de consulta, elegibilidade).
- Regras que precisam ser combinadas dinamicamente (ex: filtros de busca configuráveis pelo usuário).
- Quando a legibilidade de `if`s encadeados começa a prejudicar a leitura do código.

**Erro comum:** criar uma Specification para cada `if` trivial do sistema. O padrão vale a pena quando a regra é reutilizada ou combinada — uma condição usada uma única vez, sem necessidade de composição, pode continuar sendo um `if` simples dentro da Entity ou do Domain Service.

## Como Domain Events e Specifications se complementam aos outros blocos

```
Aggregate (Pedido)
  │
  ├── ao finalizar() ──► registra PedidoFinalizadoEvent (Domain Event)
  │                        └─► lido pela Aplicação, publicado via Secondary Port
  │
  └── antes de aplicar desconto ──► consulta ClienteElegivelDesconto (Specification)
                                       └─► combina regras sem duplicar lógica
```

## 🧩 Quiz de Fixação

1. Por que um Domain Event deve sempre ser nomeado no passado (ex: `PedidoFinalizado`, não `FinalizarPedido`)?
2. No exemplo de código, por que `Pedido.finalizar()` apenas registra o evento numa lista em vez de publicá-lo diretamente em uma fila como Kafka?
3. Quando vale a pena extrair uma condição para uma Specification, em vez de deixá-la como um `if` direto dentro da Entity?

**Respostas:**
1) Porque um Domain Event representa um fato que já aconteceu, não uma intenção ou comando futuro. Nomear no passado deixa explícito que o evento é imutável e consumado — diferente de um Command, que representa uma ação ainda a ser executada e que pode ser recusada.
2) Porque publicar diretamente em uma tecnologia de mensageria (Kafka, RabbitMQ) violaria a regra de que o domínio não conhece infraestrutura externa (vista em 1.2.1.1). Ao apenas registrar o evento numa lista interna, o domínio permanece puro; é a camada de Aplicação, através de um Secondary Port, quem decide como e onde publicar o evento.
3) Vale a pena quando a mesma condição é usada em múltiplos lugares do sistema (evitando duplicação) ou quando ela precisa ser combinada dinamicamente com outras regras (via `and`/`or`/`not`). Se a condição é usada uma única vez e não precisa ser combinada, um `if` simples dentro da Entity ou Domain Service é suficiente e mais direto.
