### Onde Colocar Cada Tipo de Código

O arquivo anterior (3.1.1.1) mostrou o fluxo completo de uma requisição atravessando as camadas. Uma dúvida prática que surge o tempo todo ao escrever código real é: "esse trecho específico que estou escrevendo agora — em qual camada ele deveria morar?" Este arquivo responde essa pergunta com um guia de decisão direto, incluindo o caso mais escorregadio: regras de negócio complexas.

---

## Tabela de decisão rápida

| Tipo de código | Camada correta | Exemplo |
|---|---|---|
| Validação de formato | Adapter de Entrada | E-mail com formato válido, CPF com máscara correta |
| Validação de negócio | Domínio | "Cliente pode comprar?" |
| Cálculos de negócio | Domínio | Calcular desconto |
| Orquestração | Aplicação | Processar um pedido completo, do início ao fim |
| Conversão de dados | Adapters | JSON → Command |
| Acesso a banco | Adapter de Saída | Repository (JPA/MongoDB) |
| Chamada a API externa | Adapter de Saída | Cliente REST para outro serviço |
| Autenticação | Adapter de Entrada | Validação de token JWT |
| Autorização | Aplicação | "Este usuário pode acessar este recurso?" |
| Transação | Aplicação | `@Transactional` |
| Cache | Adapter de Saída | Redis Adapter |
| Log técnico | Adapters | Logs de requisição HTTP |
| Log de auditoria | Aplicação | Registro de "quem fez o quê" |
| Eventos de negócio | Domínio | `PedidoCriado` |
| Publicação de eventos | Adapter de Saída | RabbitMQ/Kafka |

O critério por trás de cada linha é sempre o mesmo, e já apareceu em arquivos anteriores: **pergunte se a decisão depende de conhecimento de negócio ou apenas de execução técnica.** "Validação de formato" (e-mail bem formado) é puramente técnica — não muda com a política comercial da empresa. "Validação de negócio" (cliente pode comprar) depende de regras que só fazem sentido dentro do domínio.

---

## O caso mais escorregadio: onde colocar uma regra de negócio complexa

Regras simples são fáceis de posicionar — moram na Entity que elas descrevem. O desafio real aparece quando a regra é complexa o suficiente para gerar dúvida entre três candidatos: um método na própria Entity, um Domain Service, ou uma Specification.

```
1. Implementa no DOMÍNIO
   → Domain Service, se a regra envolver MÚLTIPLAS entidades
   → Método na própria Entidade, se a regra for específica dela
   → Specification, se a regra for reutilizável/combinável em vários lugares

2. Application Service apenas CHAMA a decisão já tomada pelo domínio
```

| Pergunta de triagem | Onde a regra deveria morar |
|---|---|
| A regra depende só dos atributos de uma única Entity? | Método dentro da própria Entity (ex: `Pedido.podeSerFinalizado()`) |
| A regra combina informações de duas ou mais Entities/Aggregates diferentes? | Domain Service (ex: `ServicoCalculoFrete`, que combina `Pedido` + `Endereco` + `TipoEntrega`) |
| A regra é reutilizada em múltiplos pontos e/ou combinada com outras regras (`and`/`or`)? | Specification (ex: `ClienteElegivelDesconto`) |

Essa tabela de triagem reforça uma regra que já apareceu em 2.2.1.1: se a Application Service tiver um `if` decidindo algo sobre negócio, é sinal de que a decisão foi parar no lugar errado — ela deveria estar em um dos três candidatos acima, nunca na camada de orquestração.

---

## Sinais de que a arquitetura está sendo violada

| ❌ Errado | ✅ Correto |
|---|---|
| Entidades com anotações JPA (`@Entity`, `@Table`) | Entidades como POJOs puros, sem dependência de framework |
| Domain Services chamando APIs externas diretamente | Domain Services usando apenas outros objetos de domínio; chamadas externas ficam nos Adapters |
| Controllers com lógica de negócio (`if` decidindo desconto, elegibilidade) | Controllers apenas convertendo dados de entrada/saída |
| Application Services fazendo cálculos de negócio | Application Services apenas orquestrando chamadas ao domínio e à infraestrutura |
| Adapters decidindo o fluxo do caso de uso | Adapters apenas traduzindo formatos, sem decidir "o que fazer" |

Esses cinco sinais funcionam como uma lista de verificação rápida durante revisão de código (code review): encontrar qualquer um deles é indício de que uma responsabilidade foi parar na camada errada.

## Exemplo consolidado — aplicando a tabela na prática

```java
// Trecho de um caso de uso hipotético de "Aplicar cupom de desconto"

// 1. Validação de FORMATO → Adapter de Entrada (Bean Validation no Controller)
@Valid @RequestBody AplicarCupomRequest request

// 2. Autenticação → Adapter de Entrada (filtro/interceptor JWT)
// (já resolvido antes de chegar no Controller)

// 3. Conversão de dados → Adapter (Controller monta o Command)
AplicarCupomCommand comando = new AplicarCupomCommand(request.getPedidoId(), request.getCodigoCupom());

// 4. Orquestração + Transação + Autorização → Application Service
@Transactional
public void executar(AplicarCupomCommand comando) {
    if (!usuarioAtual.podeAplicarCupom()) { // autorização
        throw new AcessoNegadoException();
    }
    Pedido pedido = pedidoRepository.buscarPorId(comando.getPedidoId()).orElseThrow();

    // 5. Cálculo/validação de NEGÓCIO → Domínio
    Cupom cupom = cupomRepository.buscarPorCodigo(comando.getCodigoCupom()).orElseThrow();
    pedido.aplicarCupom(cupom); // a REGRA de validade do cupom mora aqui dentro

    pedidoRepository.salvar(pedido);

    // 6. Publicação de evento → Adapter de Saída, acionado pela Application
    publicadorEventos.publicar(new CupomAplicadoEvent(pedido, cupom));
}
```

Cada comentário no código acima aponta exatamente para uma linha da tabela de decisão rápida — o exemplo existe para mostrar que a tabela não é teórica, ela se reflete diretamente na organização de um método real.

## 🧩 Quiz de Fixação

1. Qual é o critério geral (a "pergunta de triagem") usado para decidir se um trecho de código pertence ao Domínio ou a um Adapter?
2. Se uma regra de negócio precisa combinar dados de dois Aggregates diferentes (por exemplo, `Pedido` e `Estoque`), em qual dos três candidatos do domínio ela deveria morar, e por quê?
3. Cite dois dos cinco "sinais de problema" listados e explique por que cada um indica uma violação da arquitetura.

**Respostas:**
1) A pergunta de triagem é: "essa decisão depende de conhecimento sobre as regras do negócio, ou é apenas uma questão de execução/formato técnico?" Se depende de regras de negócio (o que pode mudar por decisão comercial), pertence ao Domínio. Se é puramente técnico (formato de dado, protocolo de comunicação, tecnologia de persistência), pertence aos Adapters.
2) Ela deveria morar em um Domain Service, porque a regra não pertence exclusivamente a uma única Entity/Aggregate — ela nasce da combinação de informações de `Pedido` e `Estoque`. Forçar essa lógica dentro de uma das duas Entities criaria uma dependência artificial e incorreta entre agregados que deveriam permanecer independentes.
3) Por exemplo: "Entidades com anotações JPA" indica violação porque acopla o domínio a uma tecnologia de persistência específica, contrariando a regra de que o domínio não deve depender de infraestrutura (vista em 1.2.1.1). "Controllers com lógica de negócio" indica violação porque a decisão de negócio deveria estar centralizada no domínio; deixá-la no Controller cria risco de duplicação e inconsistência caso outro Adapter de entrada (CLI, fila) precise da mesma regra.
