### Cinco Anti-padrões e Como Corrigi-los

O arquivo anterior (3.2.1.1) apresentou a tabela de "sinais de problema" em alto nível. Este arquivo aprofunda cada um dos cinco anti-padrões mais comuns com exemplos de código, mostrando exatamente como identificá-los durante uma revisão de código e como corrigi-los.

---

## Anti-padrão 1: Entidades com anotações JPA

```java
// ❌ ERRADO — a Entity depende diretamente do framework de persistência
@Entity
@Table(name = "clientes")
public class Cliente {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String nome;
}

// ✅ CORRETO — a Entity é um POJO puro; o mapeamento vive em uma classe separada
public class Cliente {
    private ClienteId id;
    private String nome;
}

@Entity
@Table(name = "clientes")
class ClienteEntity {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String nome;
}
```

**Como identificar:** procure por imports de `javax.persistence.*` ou `jakarta.persistence.*` dentro do pacote de domínio. **Como corrigir:** criar uma classe `*Entity` separada no pacote do Adapter de persistência, com um mapper fazendo a tradução bidirecional (visto em 2.4.2.1).

## Anti-padrão 2: Domain Services chamando APIs externas

```java
// ❌ ERRADO — o Domain Service conhece detalhes de uma API externa
public class ServicoCalculoFrete {
    public Dinheiro calcularFrete(Pedido pedido, Endereco destino) {
        HttpResponse response = httpClient.get("https://api-frete.com/calcular?cep=" + destino.getCep());
        return new Dinheiro(new BigDecimal(response.body()), Moeda.BRL);
    }
}

// ✅ CORRETO — o Domain Service depende de uma Secondary Port, não da API diretamente
public class ServicoCalculoFrete {
    private final CalculadoraFreteExterna calculadoraFrete; // Secondary Port

    public Dinheiro calcularFrete(Pedido pedido, Endereco destino) {
        return calculadoraFrete.calcular(pedido.getPesoTotal(), destino.getCep());
    }
}
```

**Como identificar:** procure por `HttpClient`, `RestTemplate`, `WebClient` ou qualquer SDK de terceiros importado dentro de uma classe do pacote de domínio. **Como corrigir:** extrair a chamada externa para uma Secondary Port, e mover a implementação concreta (com o HTTP client de fato) para um Adapter de saída.

## Anti-padrão 3: Controllers com lógica de negócio

```java
// ❌ ERRADO — o Controller decide uma regra de negócio
@PostMapping("/pedidos/{id}/finalizar")
public ResponseEntity<?> finalizar(@PathVariable String id) {
    Pedido pedido = pedidoRepository.buscarPorId(new PedidoId(id)).orElseThrow();

    if (pedido.getItens().isEmpty()) { // regra de negócio dentro do Controller!
        return ResponseEntity.badRequest().body("Pedido vazio");
    }
    pedido.setStatus(StatusPedido.FINALIZADO); // manipula estado diretamente!
    pedidoRepository.salvar(pedido);
    return ResponseEntity.ok().build();
}

// ✅ CORRETO — o Controller só traduz; a regra vive no Aggregate
@PostMapping("/pedidos/{id}/finalizar")
public ResponseEntity<?> finalizar(@PathVariable String id) {
    gestaoPedidos.finalizar(new FinalizarPedidoCommand(id)); // delega ao Primary Port
    return ResponseEntity.ok().build();
}
```

**Como identificar:** qualquer `if` em um Controller que avalia uma condição de negócio (não apenas formato de entrada), ou qualquer `setStatus`/mutação direta de campos de uma Entity. **Como corrigir:** mover a validação e a mutação de estado para dentro do método do Aggregate (`Pedido.finalizar()`, como visto em 2.1.1.1), e fazer o Controller chamar apenas a Primary Port.

## Anti-padrão 4: Application Services com cálculos de negócio

```java
// ❌ ERRADO — a Application Service calcula uma regra de negócio
@Service
public class FinalizarPedidoUseCase {
    public void executar(FinalizarPedidoCommand comando) {
        Pedido pedido = pedidoRepository.buscarPorId(comando.getPedidoId()).orElseThrow();

        // Cálculo de negócio vazando para a Aplicação!
        BigDecimal desconto = pedido.getValorTotal().multiply(new BigDecimal("0.1"));
        pedido.setValorTotal(pedido.getValorTotal().subtract(desconto));

        pedidoRepository.salvar(pedido);
    }
}

// ✅ CORRETO — o cálculo mora no domínio; a Aplicação só orquestra
@Service
public class FinalizarPedidoUseCase {
    public void executar(FinalizarPedidoCommand comando) {
        Pedido pedido = pedidoRepository.buscarPorId(comando.getPedidoId()).orElseThrow();
        pedido.aplicarDescontoPadrao(); // a REGRA de "10% de desconto" mora no Aggregate
        pedidoRepository.salvar(pedido);
    }
}
```

**Como identificar:** qualquer operação matemática ou lógica condicional em um Application Service que reflete uma política de negócio (percentuais, faixas, elegibilidade). **Como corrigir:** mover o cálculo para um método da Entity/Aggregate ou para um Domain Service, e deixar a Application Service apenas chamar o método já pronto.

## Anti-padrão 5: Adapters decidindo fluxo

```java
// ❌ ERRADO — o Adapter de saída decide o que fazer em seguida (fluxo de negócio)
@Component
public class ProdutoJPAAdapter implements ProdutoRepository {
    @Override
    public Produto salvar(Produto produto) {
        ProdutoEntity saved = jpaRepository.save(mapper.toEntity(produto));

        // O Adapter decidindo enviar notificação — isso é fluxo de negócio!
        if (produto.isNovo()) {
            emailService.enviar(admin, "Novo produto cadastrado");
        }
        return mapper.toDomain(saved);
    }
}

// ✅ CORRETO — o Adapter só persiste; a decisão de notificar fica na Application
@Component
public class ProdutoJPAAdapter implements ProdutoRepository {
    @Override
    public Produto salvar(Produto produto) {
        ProdutoEntity saved = jpaRepository.save(mapper.toEntity(produto));
        return mapper.toDomain(saved);
    }
}
// A Application Service decide chamar notificarAdmin() separadamente, se necessário
```

**Como identificar:** um Adapter que, além de traduzir/persistir, também decide chamar outra operação com base em uma condição de negócio. **Como corrigir:** mover a decisão de "o que fazer depois" para a Application Service, que já orquestra as chamadas para múltiplos Secondary Ports quando necessário (como visto em 2.2.1.1).

## Checklist de revisão de código

| Pergunta durante o code review | Se "sim" |
|---|---|
| Existe algum import de framework/tecnologia dentro do pacote de domínio? | Anti-padrão 1 ou 2 |
| O Controller tem algum `if` avaliando uma regra que não é formato de entrada? | Anti-padrão 3 |
| A Application Service tem alguma conta, percentual ou fórmula de negócio? | Anti-padrão 4 |
| Um Adapter de saída chama outro serviço com base em uma condição de negócio? | Anti-padrão 5 |

## 🧩 Quiz de Fixação

1. No Anti-padrão 2, por que trocar a chamada HTTP direta por uma Secondary Port resolve o problema, mesmo que a chamada HTTP ainda aconteça em algum lugar do sistema?
2. No Anti-padrão 3, qual é a diferença entre o Controller "errado" e o "correto" em termos de quem manipula o estado do `Pedido`?
3. Ao revisar um Pull Request, você encontra uma Application Service com uma linha `BigDecimal taxa = valor.multiply(new BigDecimal("0.05"))`. A qual anti-padrão isso corresponde, e qual seria a correção recomendada?

**Respostas:**
1) Porque a chamada HTTP continua existindo, mas passa a acontecer dentro de um Adapter de saída, que implementa a Secondary Port. O Domain Service passa a depender apenas da abstração (a interface da Port), não da tecnologia HTTP em si — isso preserva a regra de que o domínio não conhece infraestrutura, mesmo que, na prática completa do sistema, uma chamada de rede ainda seja feita em algum ponto.
2) No Controller errado, é o próprio Controller quem decide se o pedido pode ser finalizado (`if (pedido.getItens().isEmpty())`) e quem altera o status diretamente (`pedido.setStatus(...)`). No Controller correto, essas decisões e mutações ficam encapsuladas dentro do método `Pedido.finalizar()`, e o Controller apenas delega a chamada através da Primary Port, sem tocar diretamente no estado da Entity.
3) Isso corresponde ao Anti-padrão 4 (Application Services com cálculos de negócio) — uma fórmula de taxa/percentual é uma decisão de negócio que pode mudar por política comercial. A correção recomendada é mover esse cálculo para um método da Entity/Aggregate relevante ou para um Domain Service, deixando a Application Service apenas chamar esse método já pronto.
