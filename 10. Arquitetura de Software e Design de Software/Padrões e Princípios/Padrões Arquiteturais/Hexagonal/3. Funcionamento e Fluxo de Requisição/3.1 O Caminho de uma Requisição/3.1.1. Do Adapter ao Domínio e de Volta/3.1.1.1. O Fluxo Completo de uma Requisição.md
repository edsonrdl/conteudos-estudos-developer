### O Fluxo Completo de uma Requisição

Com toda a anatomia mapeada no Domínio 2 (Entities, Application Services, Ports, Adapters), este arquivo junta todas as peças e mostra como uma requisição percorre a arquitetura inteira, do primeiro contato externo até a resposta final — e como esse mesmo fluxo se aplica ao desenvolver uma funcionalidade nova do zero.

---

## O caminho de uma requisição, passo a passo

```
 1. REQUEST chega no sistema
    ↓
 2. PRIMARY ADAPTER recebe (ex: REST Controller)
    ↓
 3. Converte para Command/Query
    ↓
 4. Chama PRIMARY PORT
    ↓
 5. APPLICATION SERVICE processa
    ↓
 6. Chama lógica do DOMÍNIO
    ↓
 7. DOMÍNIO executa regras de negócio
    ↓
 8. APPLICATION chama SECONDARY PORTS (se necessário)
    ↓
 9. SECONDARY ADAPTERS executam (DB, APIs, etc.)
    ↓
10. Resultado volta pelo caminho inverso
    ↓
11. PRIMARY ADAPTER converte para Response
    ↓
12. RESPONSE retorna ao cliente
```

Cada uma dessas 12 etapas corresponde a um conceito já visto no Domínio 2:

| Etapa | Conceito | Arquivo de referência |
|---|---|---|
| 2, 11 | Primary Adapter | 2.4.1.1 |
| 3 | Command/Query | 2.2.1.2 |
| 4 | Primary Port | 2.3.1.1 |
| 5 | Application Service | 2.2.1.1 |
| 6, 7 | Domínio (Entities, Aggregates, Domain Services) | 2.1.1.1 / 2.1.1.2 |
| 8 | Secondary Port | 2.3.1.2 |
| 9 | Secondary Adapter | 2.4.2.1 |

**Analogia:** é como pedir uma pizza por um aplicativo de delivery. Seu pedido (Request) chega ao app (Primary Adapter), que traduz para um formato interno de pedido (Command). Esse pedido é roteado para a cozinha (Domínio) através da central de atendimento (Application Service), que verifica o estoque de ingredientes (Secondary Port → banco de dados) e aciona o motoboy (Secondary Adapter → serviço de entrega). O resultado (pizza entregue) volta pelo caminho inverso até você ver "Pedido entregue" no app.

Importante: em nenhum momento a etapa 2 (Adapter) "pula direto" para a etapa 7 (Domínio) — cada seta do diagrama representa uma travessia obrigatória por uma Port, nunca uma chamada direta que fure a camada intermediária.

---

## Aplicando o mesmo fluxo ao desenvolver uma funcionalidade nova

O fluxo de execução de uma requisição (de fora para dentro) é o espelho exato da ordem recomendada para **construir** uma funcionalidade nova (de dentro para fora):

```
1. Começa no DOMÍNIO
   → Criar/modificar Entidades e Value Objects
   → Implementar regras no Aggregate
   → Criar Domain Events se necessário

2. Define o PORT primário
   → Interface do caso de uso

3. Implementa APPLICATION SERVICE
   → Orquestra a lógica

4. Cria ADAPTER de entrada
   → REST Controller ou GraphQL Resolver

5. Se precisar persistência/serviços externos
   → Define PORT secundário
   → Implementa ADAPTER de saída
```

Por que começar pelo domínio, e não pelo Controller (como é comum em tutoriais que ensinam "de fora para dentro")? Porque o domínio é a parte que **não muda** conforme a tecnologia de entrega muda. Desenhar primeiro a regra de negócio, isolada, garante que ela seja pensada em termos do problema real — não condicionada pelo formato de um JSON de requisição ou pela estrutura de uma tabela de banco.

| Abordagem | Risco |
|---|---|
| Começar pelo Controller/Request DTO | A modelagem do domínio acaba refém do formato do JSON de entrada |
| Começar pela tabela do banco | O domínio vira um espelho do schema relacional, perdendo expressividade de negócio |
| Começar pelo Domínio (Entities/Aggregates) | O modelo reflete o vocabulário do negócio; Adapters se adaptam a ele depois |

## Erro comum: pular etapas do fluxo "para simplificar"

Uma tentação comum, especialmente sob pressão de prazo, é fazer um Adapter chamar diretamente um Repository, pulando a Application Service e até o Domínio:

```java
// ERRADO — o Controller pula direto para a persistência, sem Port nem Domínio
@RestController
public class ProdutoRestController {
    private final ProdutoJPARepository jpaRepository; // acesso direto ao JPA!

    @PostMapping
    public void criar(@RequestBody CriarProdutoRequest request) {
        ProdutoEntity entity = new ProdutoEntity(request.getNome(), request.getPreco());
        jpaRepository.save(entity); // nenhuma regra de negócio é aplicada!
    }
}
```

Esse atalho parece economizar código no curto prazo, mas reintroduz exatamente o problema do acoplamento visto em 1.1.1.1 — a regra de negócio (validações, invariantes do Aggregate) simplesmente deixa de existir, e qualquer outro canal de entrada que precisar criar um produto (CLI, fila) terá que reimplementar as mesmas validações manualmente, ou pior, esquecer de fazê-lo.

## 🧩 Quiz de Fixação

1. Na etapa 6-7 do fluxo completo, por que a Application Service "chama" a lógica do domínio em vez de implementá-la diretamente?
2. Por que a ordem recomendada para desenvolver uma funcionalidade nova começa pelo Domínio, e não pelo Adapter de entrada (Controller)?
3. Qual problema concreto reaparece quando um Controller acessa diretamente um `ProdutoJPARepository`, pulando a Application Service e o Domínio?

**Respostas:**
1) Porque a Application Service tem o papel de orquestrar o fluxo (buscar dados, coordenar chamadas), mas a decisão sobre regras de negócio — o que é válido, o que não é, como os dados devem ser transformados de acordo com as regras do negócio — pertence exclusivamente ao Domínio (Entities, Aggregates, Domain Services), conforme visto no Domínio 2.
2) Porque o Domínio representa o vocabulário e as regras do negócio, que devem existir independentemente de como a funcionalidade será exposta (REST, CLI, fila). Começar pelo Adapter de entrada arrisca moldar o modelo de negócio em função do formato de uma requisição específica (JSON, por exemplo), em vez de moldar a requisição em função do que o negócio realmente precisa.
3) Reaparece o problema do acoplamento e a perda de regras de negócio: sem passar pelo Domínio, nenhuma validação ou invariante é aplicada antes de persistir os dados. Além disso, qualquer outro Adapter de entrada que precisar da mesma funcionalidade (um CLI, por exemplo) teria que duplicar manualmente essas validações, com risco real de esquecê-las ou implementá-las de forma inconsistente.
