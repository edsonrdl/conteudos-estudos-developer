### Quando Usar Arquitetura Hexagonal

Os dois arquivos anteriores (4.1.1.1 e 4.1.2.1) mostraram os ganhos e os custos lado a lado. Este arquivo traduz essa balança em um critério prático: cinco sinais concretos de que vale a pena pagar o custo de isolamento em um projeto real.

---

## Os cinco sinais favoráveis

```
✅ Domínio complexo
✅ Múltiplas interfaces (REST, GraphQL, CLI)
✅ Longevidade esperada (anos)
✅ Equipe média/grande
✅ Necessidade de testes robustos
```

Nenhum desses sinais isolados é suficiente para justificar a arquitetura — o valor aparece quando **vários** deles coexistem no mesmo projeto, porque cada um reforça o benefício dos outros.

---

## Detalhando cada sinal

### Domínio complexo

Quando o negócio tem regras que mudam com frequência, têm exceções, dependem de combinações de estado (como o exemplo de `ServicoCalculoFrete` combinando pedido, endereço e tipo de entrega, visto em 2.1.1.1), isolar essas regras em um domínio rico evita que elas se espalhem e se dupliquem por todo o sistema.

### Múltiplas interfaces de entrada

Se o sistema precisa (ou vai precisar) ser acessado por mais de um canal — API REST para o app mobile, GraphQL para o painel administrativo, CLI para operações internas, listener de fila para integração com outros sistemas — o ganho mostrado em 4.1.1.1 (reaproveitar a mesma Primary Port em vários Adapters) se paga rapidamente.

### Longevidade esperada

Um sistema que deve viver por anos vai, inevitavelmente, passar por mudanças de tecnologia — trocar de banco, atualizar frameworks, migrar de mensageria. O custo de isolamento pago uma vez (4.1.2.1) se converte em economia repetida cada vez que uma dessas mudanças acontece sem tocar no domínio.

### Equipe média ou grande

Com mais desenvolvedores trabalhando no mesmo código, contratos explícitos (Ports) reduzem a chance de um time quebrar a integração de outro sem perceber. A separação de responsabilidades também permite que diferentes desenvolvedores trabalhem em Adapters diferentes (um cuidando do REST, outro do Adapter de banco) sem pisar no código um do outro.

### Necessidade de testes robustos

Sistemas com alto custo de erro (financeiro, saúde, segurança) se beneficiam diretamente da testabilidade isolada mostrada em 4.1.1.1 — testar regras de negócio críticas sem depender de infraestrutura real permite uma suíte de testes rápida o suficiente para rodar a cada commit.

---

## Como avaliar um projeto real contra esses sinais

| Pergunta de avaliação | Se "sim" |
|---|---|
| As regras de negócio deste sistema mudam com frequência e têm exceções? | Reforça "domínio complexo" |
| Este sistema será consumido por mais de um tipo de cliente (mobile, web, integração B2B)? | Reforça "múltiplas interfaces" |
| Existe expectativa de este sistema durar mais de 2-3 anos em produção? | Reforça "longevidade" |
| Mais de 3-4 desenvolvedores vão trabalhar simultaneamente neste código? | Reforça "equipe média/grande" |
| Um bug nesta regra de negócio geraria prejuízo financeiro ou risco legal? | Reforça "testes robustos" |

Quanto mais respostas "sim", mais forte é o caso para adotar a arquitetura. Um projeto com três ou mais "sins" já justifica o investimento; um projeto com zero ou um "sim" provavelmente se encaixa no cenário oposto, tratado no próximo arquivo (4.2.2.1).

---

## Exemplo de aplicação do critério

Um sistema de **gestão de pedidos de um marketplace de médio porte**, com regras de comissionamento variáveis por categoria, integração com múltiplos meios de pagamento, exposto via API REST para o site e via API para parceiros B2B, mantido por uma equipe de 8 desenvolvedores, e com expectativa de operar por vários anos: esse cenário marca "sim" em todos os cinco sinais — um caso claro e forte para arquitetura hexagonal.

Compare com um **microsserviço interno que só expõe um endpoint de consulta de CEP**, sem regra de negócio própria (apenas repassa a chamada para uma API dos Correios), mantido por 1 desenvolvedor: esse cenário não marca nenhum dos cinco sinais — a Hexagonal aqui seria custo puro, sem benefício correspondente.

## 🧩 Quiz de Fixação

1. Por que nenhum dos cinco sinais isoladamente é suficiente para justificar a adoção da arquitetura, segundo o texto?
2. No exemplo do marketplace de médio porte, quais dos cinco sinais estão presentes, e por que isso torna o caso "forte" para Hexagonal?
3. Um projeto atende a apenas um dos cinco sinais ("longevidade esperada de anos"), mas nenhum dos outros quatro. Isso, sozinho, já justifica adotar a arquitetura completa? Justifique.

**Respostas:**
1) Porque o valor da arquitetura vem da combinação de fatores que se reforçam mutuamente — por exemplo, múltiplas interfaces só geram economia real se o domínio for complexo o suficiente para ter regras que valeria a pena não duplicar. Um único sinal isolado, sem os outros, normalmente não gera benefício suficiente para compensar o custo de isolamento (overhead e curva de aprendizado, vistos em 4.1.2.1).
2) O exemplo marca todos os cinco sinais: domínio complexo (comissionamento variável), múltiplas interfaces (site e API B2B), longevidade esperada (vários anos), equipe média/grande (8 desenvolvedores) e necessidade de testes robustos (implícita pelo risco financeiro de erros de comissionamento). A presença simultânea de todos os sinais reforça uns aos outros, tornando o investimento em isolamento claramente compensador.
3) Não necessariamente. Um sistema pode ter vida longa mas continuar sendo um domínio simples, com uma única interface e mantido por uma pessoa só — nesse caso, mesmo durando anos, o sistema pode nunca precisar trocar de tecnologia ou de interface, então o custo de isolamento pago antecipadamente nunca seria recuperado. É necessário avaliar o conjunto de sinais, não um fator isolado.
