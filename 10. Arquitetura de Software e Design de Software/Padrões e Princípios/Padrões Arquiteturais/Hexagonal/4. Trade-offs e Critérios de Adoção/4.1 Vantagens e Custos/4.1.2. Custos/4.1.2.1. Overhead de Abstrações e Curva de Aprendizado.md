### Overhead de Abstrações e Curva de Aprendizado

O arquivo anterior (4.1.1.1) mostrou os ganhos concretos da Arquitetura Hexagonal. Nenhuma decisão de arquitetura vem de graça, e este arquivo cobre o lado que os tutoriais costumam pular: o preço real que se paga por esse isolamento, tanto em código quanto em tempo de equipe.

---

## O overhead de código para operações simples

Cada camada e cada Port adicionam uma peça de código que precisa existir, ser mantida e ser entendida por quem lê o projeto depois. Para um CRUD simples, esse custo fica visível de forma desproporcional ao benefício.

**Exemplo: criar um registro simples de "categoria de produto", sem regra de negócio nenhuma.**

```java
// Sem Hexagonal — CRUD direto (1 classe, ~10 linhas)
@RestController
@RequestMapping("/categorias")
public class CategoriaController {
    @Autowired private CategoriaRepository repository; // Spring Data JPA direto

    @PostMapping
    public Categoria criar(@RequestBody Categoria categoria) {
        return repository.save(categoria);
    }
}
```

```java
// Com Hexagonal completa — mesma funcionalidade, ~6 classes/interfaces
public class Categoria { /* Entity de domínio */ }

public interface CategoriaRepository { /* Secondary Port */
    Categoria salvar(Categoria categoria);
}

public interface GestaoCategorias { /* Primary Port */
    CategoriaId criar(CriarCategoriaCommand comando);
}

public class GestaoCategoriasService implements GestaoCategorias { /* Application Service */
    // ...
}

@Entity class CategoriaEntity { /* Entidade JPA */ }

@Repository
public class CategoriaJPAAdapter implements CategoriaRepository { /* Adapter */
    // ...
}

@RestController
public class CategoriaRestController { /* Adapter de entrada */
    // ...
}
```

Para uma operação que literalmente só grava um nome no banco, a versão hexagonal exige seis arquivos contra um. Esse não é um exagero didático — é o custo real de garantir isolamento onde, nesse caso específico, não existe nenhuma regra de negócio a proteger.

| Aspecto | CRUD direto | Hexagonal completa |
|---|---|---|
| Arquivos para uma operação simples | 1 | 5-6 |
| Tempo para implementar uma feature trivial | Minutos | Múltiplos minutos a horas, dependendo da familiaridade do time |
| Rastreabilidade de uma mudança simples | Direta (um arquivo) | Precisa navegar por Port → Application → Adapter |

---

## A curva de aprendizado

Um desenvolvedor acostumado com uma arquitetura em camadas tradicional (Controller → Service → Repository, todos falando diretamente uns com os outros) precisa desaprender alguns hábitos antes de internalizar os limites da Hexagonal:

| Hábito comum em arquiteturas tradicionais | Ajuste necessário na Hexagonal |
|---|---|
| Injetar o Repository diretamente no Controller quando "é mais rápido" | Entender por que isso quebra o isolamento do domínio, mesmo parecendo inofensivo numa tela simples |
| Colocar uma anotação `@Entity` na mesma classe que representa a regra de negócio | Aceitar manter duas classes (Entity de domínio + Entity JPA) para o mesmo conceito |
| Achar que "interface para uma implementação só" é over-engineering | Entender que a interface (Port) existe para permitir substituição futura e, principalmente, para testes |
| Resolver tudo dentro do Service, sem separar Domain de Application | Aprender a diferença entre "orquestrar" (Aplicação) e "decidir" (Domínio) — a distinção mais sutil de toda a arquitetura |

Esse último ponto costuma ser o mais difícil na prática: a linha entre "isso é orquestração" e "isso é uma regra de negócio" não é óbvia para quem está aprendendo, e times novos no padrão frequentemente cometem os anti-padrões vistos em 3.2.2.1 nas primeiras semanas, mesmo lendo a documentação corretamente.

---

## Custos que não aparecem no código, mas aparecem no time

- **Revisões de código mais lentas no início:** identificar se uma regra "vazou" para a camada errada exige que o revisor também entenda profundamente os limites da arquitetura — não é um erro que um linter pega automaticamente.
- **Onboarding mais longo:** um novo integrante do time precisa entender não só a stack tecnológica, mas também o vocabulário da arquitetura (Port, Adapter, Aggregate) antes de contribuir com confiança.
- **Risco de "hexagonal de fachada":** um time sob pressão de prazo pode criar as interfaces certas, mas continuar colocando lógica de negócio na Application Service "porque é mais rápido agora" — resultando em uma arquitetura que parece hexagonal na estrutura de pastas, mas não é hexagonal na prática (viola a regra de 1.2.1.1 por dentro).

---

## Quando o custo compensa e quando não compensa

O critério não é "a Hexagonal é cara, logo é ruim" — é comparar o custo de manter as camadas contra o custo de **não** ter isolamento quando ele é necessário. Um sistema com regras de negócio simples e vida curta paga um custo real sem nunca colher o benefício (isso é aprofundado no próximo arquivo, 4.2.2.1). Um sistema com domínio complexo e vida longa paga o mesmo custo inicial, mas o recupera muitas vezes ao longo dos anos, toda vez que uma tecnologia muda ou uma nova interface é adicionada sem duplicar regra de negócio.

## 🧩 Quiz de Fixação

1. No exemplo do CRUD de "categoria de produto", por que a versão hexagonal precisa de seis arquivos para uma operação que a versão direta resolve em um único arquivo?
2. Qual é, segundo o texto, o ajuste mais difícil de internalizar para um desenvolvedor vindo de uma arquitetura tradicional em camadas?
3. O que significa uma arquitetura ser "hexagonal de fachada", e por que isso é pior do que simplesmente não usar Hexagonal?

**Respostas:**
1) Porque cada responsabilidade (Entity de domínio, Secondary Port, Primary Port, Application Service, Entity JPA, Adapter de persistência, Adapter de entrada) é deliberadamente separada em uma classe ou interface própria, seguindo a regra de isolamento do domínio. Para uma operação sem nenhuma regra de negócio a proteger, essa separação não traz benefício correspondente ao custo de manter seis arquivos em vez de um.
2) O ajuste mais difícil é aprender a diferença entre "orquestrar" (responsabilidade da Aplicação) e "decidir" (responsabilidade do Domínio) — essa linha é sutil e não é detectada automaticamente por ferramentas, exigindo julgamento humano constante, especialmente nas primeiras semanas de um time novo no padrão.
3) Significa uma arquitetura que tem a estrutura de pastas e as interfaces corretas (Ports, Adapters) na aparência, mas que, na prática, tem regras de negócio vazando para Application Services ou Controllers, violando a regra de dependência internamente. Isso é pior do que simplesmente não usar Hexagonal porque o time paga todo o custo de manter as camadas extras (overhead de código, curva de aprendizado) sem colher nenhum dos benefícios reais de isolamento, testabilidade ou substituibilidade.
