### Quem Decide os Limites de um Microsserviço

Este é o último arquivo do guia de Arquitetura Hexagonal. Depois de ver a relação da Hexagonal com Onion, Clean Architecture e DDD, falta esclarecer uma confusão muito comum: a Hexagonal organiza o **interior** de um serviço, mas não é ela quem decide **onde termina um serviço e começa outro** em um sistema distribuído.

---

## Duas perguntas diferentes, duas respostas diferentes

| Pergunta | Quem responde |
|---|---|
| "Como organizar o código dentro de um serviço para isolar o domínio da infraestrutura?" | Arquitetura Hexagonal (Ports e Adapters) |
| "Onde deveria terminar este serviço e começar o próximo, em um sistema com múltiplos serviços?" | Bounded Context (DDD, Design Estratégico) |

Um erro comum entre times começando com microsserviços é tentar usar a Hexagonal para responder a segunda pergunta — "vamos criar um microsserviço para cada Adapter" ou "cada Port vira um serviço separado". Isso não faz sentido: Ports e Adapters são um mecanismo de organização **interna**, e não têm relação com fronteiras de rede entre processos.

```
                    UM SISTEMA (pode ser 1 ou N serviços)
        ┌─────────────────────────────────────────────────┐
        │                                                   │
        │   ┌───────────────────┐   ┌───────────────────┐  │
        │   │  Bounded Context A │   │  Bounded Context B │  │
        │   │  (ex: Pedidos)      │   │  (ex: Pagamentos)   │  │
        │   │                    │   │                    │  │
        │   │  ┌──────────────┐  │   │  ┌──────────────┐  │  │
        │   │  │  Hexagonal    │  │   │  │  Hexagonal    │  │  │
        │   │  │  (Ports e      │  │   │  │  (Ports e      │  │  │
        │   │  │  Adapters)     │  │   │  │  Adapters)     │  │  │
        │   │  └──────────────┘  │   │  └──────────────┘  │  │
        │   └───────────────────┘   └───────────────────┘  │
        │                                                   │
        └─────────────────────────────────────────────────┘

O Bounded Context decide ONDE cortar (fronteira de negócio/serviço).
A Hexagonal decide COMO organizar o que fica DENTRO de cada corte.
```

---

## Monólito modular vs microsserviços: a mesma Hexagonal por dentro

Um ponto sutil e importante: um **monólito modular** bem desenhado pode ter exatamente a mesma organização interna hexagonal que um conjunto de microsserviços — a diferença entre as duas abordagens está em **onde o Bounded Context é implantado**, não em como o domínio é isolado internamente.

| Abordagem | Bounded Context "Pedidos" | Bounded Context "Pagamentos" |
|---|---|---|
| Monólito modular | Módulo dentro do mesmo processo, com sua própria Hexagonal interna | Outro módulo no mesmo processo, com sua própria Hexagonal interna |
| Microsserviços | Processo/serviço separado, com sua própria Hexagonal interna | Outro processo/serviço separado, com sua própria Hexagonal interna |

Em ambos os casos, cada Bounded Context mantém seu próprio domínio isolado por Ports e Adapters. A migração de um monólito modular para microsserviços, quando bem preparada, é principalmente uma mudança de **onde o código é implantado** (mesmo processo vs processos separados) — não uma reescrita da organização interna de cada módulo, se a Hexagonal já estava sendo aplicada corretamente desde o início.

---

## Por que essa distinção evita um erro caro

Times que confundem "Adapter" com "microsserviço" tendem a cometer um erro caro: fragmentar um domínio coeso em múltiplos serviços minúsculos, baseando o corte na tecnologia (um serviço para REST, outro para a fila) em vez de no negócio (um serviço por Bounded Context). O resultado costuma ser um **monólito distribuído** — múltiplos processos separados por rede, mas que precisam ser implantados e evoluídos juntos, porque na verdade pertencem ao mesmo domínio de negócio e foram cortados no lugar errado.

```
❌ CORTE ERRADO (baseado em Adapter/tecnologia)          ✅ CORTE CERTO (baseado em Bounded Context)

Serviço "REST-Pedidos"  ←── mesma regra de negócio       Serviço "Pedidos"
Serviço "Fila-Pedidos"  ←── duplicada/acoplada           Serviço "Pagamentos"
(ambos manipulam o mesmo Aggregate Pedido remotamente!)  (cada um com seu próprio domínio isolado)
```

---

## Como aplicar os dois conceitos juntos, corretamente

1. **Primeiro**, use o Design Estratégico do DDD para identificar os Bounded Contexts — as fronteiras de negócio onde um modelo específico faz sentido (Pedidos, Pagamentos, Estoque).
2. **Depois**, dentro de cada Bounded Context, aplique a Arquitetura Hexagonal para isolar o domínio daquele contexto específico de sua própria infraestrutura.
3. A decisão de **implantar** cada Bounded Context como um serviço separado (microsserviço) ou como um módulo no mesmo processo (monólito modular) é uma decisão operacional posterior, guiada por fatores como necessidade de escalar independentemente, times distintos por contexto, ou requisitos de disponibilidade diferentes — não pela estrutura de Ports e Adapters em si.

## 🧩 Quiz de Fixação

1. Por que "criar um microsserviço para cada Adapter" é considerado um mal-entendido sobre o papel da Arquitetura Hexagonal?
2. O que muda, e o que permanece igual, quando um Bounded Context migra de um monólito modular para um microsserviço independente?
3. Descreva como um "monólito distribuído" pode surgir a partir da confusão entre fronteiras internas (Hexagonal) e fronteiras de serviço (Bounded Context).

**Respostas:**
1) Porque Ports e Adapters são um mecanismo de organização interna do código dentro de um único serviço — eles definem como isolar o domínio de detalhes técnicos, não onde cortar um sistema em processos distintos. A decisão de onde um serviço termina e outro começa é uma questão de fronteira de negócio, respondida pelo conceito de Bounded Context do Design Estratégico do DDD, não pela quantidade ou tipo de Adapters existentes.
2) O que muda é onde o código é implantado (executando no mesmo processo que outros módulos, versus executando como um processo/serviço independente na rede). O que permanece igual é a organização interna do domínio daquele Bounded Context — a mesma estrutura de Ports e Adapters, isolando o domínio de sua infraestrutura, continua válida nos dois cenários.
3) Um monólito distribuído surge quando o corte entre serviços é feito com base em critérios técnicos (por exemplo, um serviço para a interface REST e outro para o processamento de fila) em vez de critérios de negócio (Bounded Context). Isso resulta em múltiplos processos separados por rede que, na prática, continuam fortemente acoplados — pois manipulam o mesmo Aggregate ou a mesma regra de negócio remotamente — herdando a complexidade operacional de microsserviços sem ganhar a independência real que justificaria essa divisão.
