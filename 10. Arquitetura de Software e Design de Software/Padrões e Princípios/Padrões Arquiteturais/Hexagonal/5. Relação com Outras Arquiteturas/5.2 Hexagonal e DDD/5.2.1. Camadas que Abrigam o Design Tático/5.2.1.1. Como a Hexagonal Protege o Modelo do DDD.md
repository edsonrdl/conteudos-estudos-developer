### Como a Hexagonal Protege o Modelo do DDD

Os arquivos anteriores compararam a Hexagonal com outras arquiteturas (Onion, Clean). Este arquivo trata de uma relação diferente: o Domain-Driven Design (DDD) não é uma arquitetura concorrente — é um conjunto de práticas de modelagem que **vive dentro** da Camada de Domínio da Hexagonal, e a Hexagonal é o que garante que esse modelo permaneça protegido.

---

## Duas coisas diferentes que se encaixam perfeitamente

É comum confundir DDD e Hexagonal como se fossem alternativas — na prática, eles respondem perguntas diferentes:

| Pergunta | Quem responde |
|---|---|
| "Como modelar o domínio de forma rica e alinhada ao negócio?" | DDD (Entities, Aggregates, Domain Services, Bounded Contexts) |
| "Onde colocar esse modelo para que ele não seja corrompido por tecnologia externa?" | Hexagonal (Ports e Adapters) |

O DDD fornece o **conteúdo** da Camada de Domínio vista no Domínio 2 deste guia (Entities em 2.1.1.1, Aggregates também em 2.1.1.1, Domain Services e Domain Events em 2.1.1.2). A Hexagonal fornece o **contêiner** que protege esse conteúdo — a fronteira de Ports e Adapters que impede a infraestrutura de vazar para dentro.

```
┌───────────────────────────────────────────────────────┐
│                    ADAPTERS (Hexagonal)                  │
│  ┌─────────────────────────────────────────────────┐    │
│  │                 PORTS (Hexagonal)                  │    │
│  │  ┌───────────────────────────────────────────┐    │    │
│  │  │           DOMÍNIO (conteúdo do DDD)          │    │    │
│  │  │                                             │    │    │
│  │  │   Entities · Value Objects · Aggregates      │    │    │
│  │  │   Domain Services · Domain Events            │    │    │
│  │  │   Specifications                             │    │    │
│  │  │                                             │    │    │
│  │  └───────────────────────────────────────────┘    │    │
│  └─────────────────────────────────────────────────────┘    │
└───────────────────────────────────────────────────────────┘

A Hexagonal define a CASCA (fronteira). O DDD define o CONTEÚDO (modelo rico).
```

**Analogia:** pense em um cofre de banco. O DDD é a joia valiosa guardada dentro — o modelo de negócio rico e cuidadosamente lapidado. A Hexagonal é o próprio cofre — a estrutura de portas e travas (Ports e Adapters) que garante que só se acesse a joia através dos canais corretos, protegendo-a de ser adulterada por qualquer coisa vinda de fora.

## Onde cada bloco tático do DDD se encaixa na anatomia hexagonal

| Bloco tático do DDD | Camada da Hexagonal | Arquivo de referência |
|---|---|---|
| Entities, Value Objects | Domínio (Core) | 2.1.1.1 |
| Aggregates, Aggregate Root | Domínio (Core) | 2.1.1.1 |
| Domain Services | Domínio (Core) | 2.1.1.1 |
| Domain Events | Domínio (Core), publicados via Secondary Port | 2.1.1.2, 2.4.2.1 |
| Repositories (interface) | Secondary Port | 2.3.1.2 |
| Repositories (implementação) | Secondary Adapter | 2.4.2.1 |
| Application Services (orquestração de casos de uso) | Camada de Aplicação | 2.2.1.1 |

Essa tabela mostra que a Hexagonal não substitui nenhum conceito do DDD — ela simplesmente dá a cada bloco tático um endereço claro dentro da arquitetura. O `Repository`, por exemplo, é ao mesmo tempo um conceito de DDD (abstração que parece uma coleção em memória) e um Secondary Port (interface definida pelo domínio, implementada por um Adapter) — os dois vocabulários descrevem exatamente a mesma peça.

## O que aconteceria sem essa proteção

Se um projeto adotasse DDD sem a disciplina de isolamento da Hexagonal, o risco mais comum é a **Entity anêmica contaminada por infraestrutura** — o pior dos dois mundos:

```java
// SEM proteção hexagonal — DDD "de fachada"
@Entity // Anotação JPA vazando para dentro do modelo rico
@Table(name = "pedidos")
public class Pedido { // Deveria ser um Aggregate Root de DDD
    @Id
    private Long id;

    // O "modelo rico" de DDD nem chega a existir de verdade,
    // porque a classe já está amarrada ao JPA desde a definição
    public void finalizar() {
        if (itens.isEmpty()) throw new PedidoVazioException();
        this.status = StatusPedido.FINALIZADO;
    }
}
```

```java
// COM proteção hexagonal — o Aggregate Root do DDD fica puro
public class Pedido { // Aggregate Root — sem nenhuma anotação técnica
    private PedidoId id;
    private List<ItemPedido> itens;
    private StatusPedido status;

    public void finalizar() {
        if (itens.isEmpty()) throw new PedidoVazioException();
        this.status = StatusPedido.FINALIZADO;
    }
}

@Entity // Isolada no Adapter — nunca no Aggregate Root
@Table(name = "pedidos")
class PedidoEntity { /* mapeamento JPA, feito pelo mapper visto em 2.4.2.1 */ }
```

O segundo exemplo é DDD "de verdade" — um Aggregate Root que pode ser instanciado, testado e evoluído sem depender de tecnologia de persistência. Isso só é possível porque a regra de dependência da Hexagonal (1.2.1.1) força essa separação a existir.

## Bounded Context e a fronteira hexagonal

Um detalhe importante: o Bounded Context do DDD (a fronteira que delimita onde um modelo específico é válido) e o "hexágono" da arquitetura Hexagonal **não são necessariamente a mesma fronteira**. Um sistema pode ter um único hexágono contendo múltiplos Bounded Contexts internos (comum em monólitos modulares), ou pode ter um hexágono por Bounded Context (comum quando cada contexto vira um microsserviço próprio) — a decisão de quantos hexágonos existem é uma decisão de Design Estratégico do DDD, não da Hexagonal em si.

## 🧩 Quiz de Fixação

1. Qual é a diferença de papel entre o DDD e a Hexagonal, usando a analogia do cofre e da joia?
2. Por que o `Repository` é considerado, ao mesmo tempo, um conceito de DDD e uma Secondary Port da Hexagonal?
3. O que significa dizer que um projeto pode ter "DDD de fachada" mesmo usando os nomes corretos (Entity, Aggregate), e como a Hexagonal evita isso?

**Respostas:**
1) O DDD é a joia — o modelo de negócio rico, cuidadosamente modelado a partir do conhecimento do domínio. A Hexagonal é o cofre — a estrutura de Ports e Adapters que protege esse modelo de ser corrompido ou acoplado a detalhes técnicos externos. Um não substitui o outro: o DDD dá conteúdo à Camada de Domínio, e a Hexagonal garante que esse conteúdo permaneça isolado.
2) Porque, do ponto de vista do DDD, o Repository é uma abstração que faz a persistência parecer uma coleção de objetos em memória, definida pelo próprio domínio. Do ponto de vista da Hexagonal, essa mesma interface é exatamente uma Secondary Port — definida pela necessidade da aplicação e implementada por um Adapter de infraestrutura. Os dois vocabulários descrevem a mesma peça de design a partir de perspectivas diferentes.
3) Significa usar os nomes e padrões do DDD (classes chamadas "Entity", "Aggregate") sem realmente isolar essas classes de dependências técnicas — por exemplo, anotando o Aggregate Root diretamente com `@Entity` do JPA. A Hexagonal evita isso ao impor a regra de que o domínio não pode depender de infraestrutura (vista em 1.2.1.1), forçando a existência de uma classe de mapeamento separada (como `PedidoEntity`) para qualquer necessidade técnica de persistência.
