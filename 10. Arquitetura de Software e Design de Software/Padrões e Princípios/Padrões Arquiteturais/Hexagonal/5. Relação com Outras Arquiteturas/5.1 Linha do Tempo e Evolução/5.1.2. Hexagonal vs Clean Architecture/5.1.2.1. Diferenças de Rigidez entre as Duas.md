### Diferenças de Rigidez entre Hexagonal e Clean Architecture

O arquivo anterior (5.1.1.1) mostrou a linha do tempo evolutiva entre as três arquiteturas. Este arquivo aprofunda a comparação entre as duas mais discutidas no mercado — Hexagonal e Clean Architecture — focando na diferença que mais gera dúvida na prática: o grau de rigidez de cada uma.

---

## O eixo central da diferença: flexível vs prescritivo

A Hexagonal é **flexível** sobre quantas camadas existem dentro do núcleo — Cockburn definiu a fronteira (Ports e Adapters), mas não dita como organizar o interior. A Clean Architecture é **prescritiva**: Robert Martin define exatamente quatro camadas nomeadas, cada uma com um papel específico.

```
HEXAGONAL (flexível)                    CLEAN ARCHITECTURE (prescritiva)
┌───────────────────┐                  ┌──────────────────────────┐
│     ADAPTERS        │                  │   Frameworks & Drivers    │
│  ┌───────────────┐  │                  │ ┌────────────────────┐   │
│  │     PORTS       │  │                  │ │ Interface Adapters  │   │
│  │  ┌──────────┐  │  │                  │ │ ┌────────────────┐ │   │
│  │  │  DOMAIN   │  │  │                  │ │ │   Use Cases     │ │   │
│  │  │  (Core)   │  │  │                  │ │ │ ┌────────────┐ │ │   │
│  │  └──────────┘  │  │                  │ │ │ │ Entities   │ │ │   │
│  └───────────────┘  │                  │ │ │ └────────────┘ │ │   │
└───────────────────┘                  │ │ └────────────────┘ │   │
                                          │ └────────────────────┘   │
Número de camadas: livre                └──────────────────────────┘
                                          Número de camadas: exatamente 4
```

---

## Tabela de diferenças principais

| Aspecto | Hexagonal | Clean Architecture |
|---|---|---|
| Número de camadas | Flexível (tipicamente 3: Domínio, Aplicação, Infraestrutura) | Rígido — exatamente 4 (Entities, Use Cases, Interface Adapters, Frameworks & Drivers) |
| Nomenclatura | Ports & Adapters | Entities, Use Cases, Controllers/Presenters, Frameworks |
| Use Cases | Implícitos (dentro do Application Service) | Explícitos — camada própria e nomeada |
| Apresentação de saída | Responsabilidade do Adapter | Dividida entre Controller (entrada) e Presenter (formatação de saída) |
| Origem conceitual | Um padrão (Ports and Adapters) | Uma síntese de princípios (SOLID + DDD + padrões anteriores) |
| Grau de prescrição | Baixo — decisões de estrutura ficam com o time | Alto — a estrutura já vem definida |

---

## O que a rigidez da Clean Architecture adiciona na prática

A Clean Architecture separa explicitamente o que a Hexagonal deixa implícito dentro do Application Service — o **Use Case** vira uma classe própria e nomeada, e a formatação de saída ganha um componente dedicado, o **Presenter**, separado do Controller que recebe a entrada:

```java
// Hexagonal — Adapter de entrada faz entrada E formatação de saída
@RestController
public class ProdutoRestController {
    public ProdutoResponse buscarProduto(String id) {
        ProdutoDetalhes detalhes = gestãoProdutos.buscarProduto(new ProdutoId(id));
        return ProdutoDetalhesResponse.from(detalhes); // formatação dentro do Controller
    }
}

// Clean Architecture — Controller e Presenter são responsabilidades separadas
@RestController
public class ProdutoController {
    private final BuscarProdutoUseCase useCase;
    private final ProdutoPresenter presenter; // componente dedicado

    public ProdutoViewModel buscarProduto(String id) {
        ProdutoOutput output = useCase.executar(new ProdutoInput(id));
        return presenter.present(output); // formatação isolada em outra classe
    }
}
```

Esse nível extra de separação não é "melhor" por definição — é mais uma peça de código para manter, o que reforça o trade-off já visto em 4.1.2.1: mais rigidez tende a significar mais arquivos e mais boilerplate para a mesma funcionalidade.

---

## Vantagens e desvantagens de cada grau de rigidez

| | Mais flexível (Hexagonal) | Mais rígida (Clean) |
|---|---|---|
| **Vantagem** | Menos boilerplate; decisões adaptadas ao contexto real do time | Menos ambiguidade; qualquer desenvolvedor familiarizado com Clean reconhece a estrutura imediatamente |
| **Desvantagem** | Implementações variam muito entre times — menos padronização | Estrutura fixa pode ser exagero para domínios simples; mais curva de aprendizado |

---

## Como decidir entre as duas na prática

| Se o cenário for... | Tende a favorecer |
|---|---|
| Time pequeno/médio, migração gradual de um monolito, necessidade de simplicidade com isolamento | Hexagonal |
| Time grande, múltiplos squads, necessidade de um padrão rígido e onipresente entre vários serviços | Clean Architecture |
| Nenhuma das duas se encaixa claramente, mas o domínio é complexo | Um híbrido — usar a nomenclatura de Ports/Adapters da Hexagonal junto com a camada explícita de Use Cases da Clean, como muitos projetos reais fazem |

Vale reforçar o que já apareceu em 5.1.1.1: escolher uma não significa abandonar totalmente os conceitos da outra — o vocabulário de "Port" e o conceito de "Use Case explícito" convivem bem no mesmo projeto, na prática.

## 🧩 Quiz de Fixação

1. Qual é o eixo central que diferencia Hexagonal de Clean Architecture, segundo este arquivo?
2. Na Clean Architecture, por que a formatação de saída (Presenter) é separada da recepção de entrada (Controller), enquanto na Hexagonal isso normalmente fica junto no mesmo Adapter?
3. Em qual cenário a rigidez da Clean Architecture tende a ser uma vantagem, e em qual cenário ela tende a ser um custo desnecessário?

**Respostas:**
1) O eixo central é o grau de prescrição: a Hexagonal é flexível sobre como organizar o interior do domínio (número de camadas livre), enquanto a Clean Architecture é prescritiva, definindo exatamente quatro camadas nomeadas e suas responsabilidades específicas.
2) Porque a Clean Architecture leva a separação de responsabilidades a um nível mais granular, isolando a tradução de entrada (Controller) da formatação de saída (Presenter) em componentes distintos. Na Hexagonal, essa distinção não é prescrita, então normalmente as duas responsabilidades ficam agrupadas dentro do mesmo Adapter de entrada, por simplicidade.
3) A rigidez tende a ser uma vantagem em times grandes com múltiplos squads, onde um padrão onipresente reduz a ambiguidade e facilita que qualquer desenvolvedor reconheça a estrutura em qualquer parte do sistema. Ela tende a ser um custo desnecessário em domínios simples ou times pequenos, onde a quantidade extra de camadas e arquivos (boilerplate) supera o benefício de padronização, como discutido em 4.1.2.1 e 4.2.2.1.
