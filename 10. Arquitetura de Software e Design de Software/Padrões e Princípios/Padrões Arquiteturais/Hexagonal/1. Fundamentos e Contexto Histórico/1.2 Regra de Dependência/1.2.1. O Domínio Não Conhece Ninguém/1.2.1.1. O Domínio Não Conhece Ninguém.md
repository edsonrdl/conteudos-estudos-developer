### O Domínio Não Conhece Ninguém

Os três arquivos anteriores explicaram o problema do acoplamento, a origem do nome e o mecanismo de portas e adaptadores. Este arquivo fecha o domínio de fundamentos com a frase que resume tudo isso em uma única regra prática de arquitetura, usada como bússola para decidir "esse código pode ficar no domínio?".

---

## A frase-resumo da arquitetura

Se houvesse que reduzir toda a Arquitetura Hexagonal a uma única frase, seria esta: **"O Domínio não conhece ninguém, todos conhecem o Domínio."**

Isso significa que a seta de dependência do código sempre aponta **para dentro**, na direção do domínio — nunca o contrário:

```
                    ┌───────────────────────────┐
                    │      Adapters (REST,      │
                    │   JPA, Kafka, SendGrid)   │
                    │            │              │
                    │            ▼              │
                    │  ┌──────────────────────┐ │
                    │  │      Application     │ │
                    │  │            │         │ │
                    │  │            ▼         │ │
                    │  │  ┌──────────────────┐│ │
                    │  │  │      DOMÍNIO     ││ │
                    │  │  │   (não depende   ││ │
                    │  │  │ de nada externo) ││ │
                    │  │  └──────────────────┘│ │
                    │  └──────────────────────┘ │
                    └───────────────────────────┘

Todas as setas apontam PARA o domínio. Nenhuma sai dele.
```

Isso é uma aplicação direta do **Princípio da Inversão de Dependência** (o "D" do SOLID) na escala de uma arquitetura inteira, não apenas de uma classe: módulos de alto nível (o domínio, que carrega as regras de negócio) não devem depender de módulos de baixo nível (banco de dados, frameworks, bibliotecas de terceiros). Ambos devem depender de abstrações — e é justamente isso que as portas fornecem.

---

## Por que a direção da dependência importa mais que a tecnologia

Uma dúvida comum: "se meu domínio usa uma interface `Repository`, e não uma classe concreta, ele já está desacoplado?" Não necessariamente. A regra não é apenas "use interfaces" — é sobre **quem é dono da interface**.

| Situação | Quem depende de quem | Está correto? |
|---|---|---|
| Domínio define `ClienteRepository` (interface); JPA implementa | Adapter (JPA) depende do domínio | ✅ Correto — dependência aponta para dentro |
| Domínio importa `ClienteJpaRepository` (interface do Spring Data) | Domínio depende de uma abstração do framework | ❌ Errado — a interface pertence à tecnologia, não ao domínio |
| Domínio lança `SQLException` em um método de regra de negócio | Domínio depende de um tipo do driver JDBC | ❌ Errado — exceção técnica vazando para a camada de negócio |
| Entidade de domínio anotada com `@Entity`, `@Table` (JPA) | Domínio depende de anotações do framework de persistência | ❌ Errado — mesmo sem "chamar" código externo, a classe está acoplada ao ORM |

O terceiro e o quarto exemplos são os mais traiçoeiros: não existe uma chamada explícita a um método externo, mas a classe de domínio **não compila nem existe** sem aquela biblioteca no classpath. Isso já é uma dependência, mesmo sem uma linha de código "chamando" a infraestrutura.

## Como aplicar a regra na prática

```java
// ERRADO — domínio depende de anotações e exceções do JPA
@Entity
@Table(name = "clientes")
public class Cliente {
    @Id
    private Long id;

    public void ativar() throws PersistenceException {
        // ...
    }
}

// CORRETO — domínio é um objeto Java puro (POJO), sem nenhuma dependência externa
public class Cliente {
    private ClienteId id;
    private StatusCliente status;

    public void ativar() {
        if (status == StatusCliente.BLOQUEADO) {
            throw new ClienteBloqueadoException();
        }
        this.status = StatusCliente.ATIVO;
    }
}

// O mapeamento para a tecnologia de persistência fica isolado no ADAPTER
@Entity
@Table(name = "clientes")
public class ClienteEntity {
    @Id
    private Long id;
    private String status;
    // mapper converte ClienteEntity <-> Cliente
}
```

A entidade de domínio `Cliente` pode ser testada, instanciada e usada em qualquer contexto — inclusive um projeto sem nenhuma dependência de banco de dados no classpath. `ClienteEntity` é um detalhe do adapter de persistência, livre para ter quantas anotações técnicas forem necessárias.

## Consequência prática: um teste de bolso

Uma forma rápida de verificar se essa regra está sendo respeitada: **tente extrair o pacote/módulo do domínio para um projeto Java isolado, sem nenhuma outra dependência além do JDK.** Se ele compilar, a regra está sendo seguida. Se der erro de import ausente (JPA, Spring, um SDK de nuvem), há uma violação — a seta de dependência escapou do domínio.

| Sintoma de violação | Como corrigir |
|---|---|
| Domínio importa `javax.persistence.*` | Mover anotações para uma classe de Entity separada no adapter |
| Domínio lança exceções de bibliotecas (`SQLException`, `IOException`) | Capturar no adapter e traduzir para uma exceção de domínio |
| Domínio depende de `HttpServletRequest` ou `ResponseEntity` | Mover a lógica de extração de dados HTTP para o adapter de entrada |
| Domínio usa `@Autowired`/`@Service` do Spring | Fazer a injeção de dependência na camada de aplicação/configuração, não no domínio |

## 🧩 Quiz de Fixação

1. O que significa exatamente a frase "o Domínio não conhece ninguém, todos conhecem o Domínio" em termos de direção de dependência entre as camadas?
2. Por que uma entidade de domínio anotada com `@Entity` do JPA viola essa regra, mesmo que nenhum código do domínio "chame" explicitamente uma classe do JPA?
3. Qual é o "teste de bolso" sugerido para verificar se o domínio realmente está isolado de dependências externas?

**Respostas:**
1) Significa que todas as dependências de código devem apontar em direção ao domínio — adapters dependem de ports que o domínio define, a aplicação depende do domínio — mas o domínio em si nunca depende de nenhuma camada externa (adapters, frameworks, bibliotecas de infraestrutura). É uma aplicação do Princípio da Inversão de Dependência (SOLID) na escala da arquitetura inteira.
2) Porque a anotação `@Entity` faz a classe depender diretamente do framework JPA para sequer compilar e existir corretamente — mesmo sem uma chamada explícita de método, a classe está acoplada à tecnologia de persistência. Isso significa que trocar de ORM ou remover o JPA do projeto quebraria o domínio, revelando que a dependência técnica está presente, apenas de forma implícita (via anotações), não explícita (via chamadas de método).
3) O teste sugerido é tentar extrair o pacote do domínio para um projeto Java isolado, contendo apenas o JDK como dependência. Se o código compilar sem erros de import, o domínio está corretamente isolado; se aparecerem erros de dependências ausentes (JPA, Spring, SDKs), isso revela que alguma dependência externa vazou para dentro do domínio.
