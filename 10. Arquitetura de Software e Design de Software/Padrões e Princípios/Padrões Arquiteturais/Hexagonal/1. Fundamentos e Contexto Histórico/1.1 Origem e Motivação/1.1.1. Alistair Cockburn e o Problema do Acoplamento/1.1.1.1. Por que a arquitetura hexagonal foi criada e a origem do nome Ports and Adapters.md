### Por que a arquitetura hexagonal foi criada e a origem do nome Ports and Adapters

Este é o ponto de partida de todo o guia de Arquitetura Hexagonal: entender **por que** ela existe antes de estudar **como** ela funciona. Sem esse contexto histórico, as regras de "isolar o domínio" parecem burocracia arbitrária em vez de solução para um problema real e recorrente que Alistair Cockburn observou em 2005.

---

## O problema do acoplamento

Cockburn notou um padrão destrutivo se repetindo em praticamente todo projeto de software tradicional: a lógica de negócio ficava **entrelaçada** diretamente com detalhes técnicos — chamadas SQL dentro de métodos de regra de negócio, validação de formulário HTML misturada com cálculo de desconto, controllers que decidiam sozinhos se um cliente podia comprar.

O sintoma mais claro desse problema é a dificuldade de testar. Se a classe `Pedido` chama diretamente `JdbcConnection.execute(...)`, todo teste da regra "pedido não pode ser finalizado sem itens" exige um banco de dados rodando. Se o controller HTTP decide se um desconto se aplica, essa regra só pode ser validada simulando uma requisição HTTP inteira. O negócio e a tecnologia viram uma coisa só, e mudar uma significa arriscar quebrar a outra.

```
ANTES (acoplado)                        DEPOIS (Ports and Adapters)
┌──────────────────────┐                ┌──────────────────────┐
│   Controller HTTP    │                │   Adapter (HTTP)     │
│  + lógica de negócio │                │   traduz apenas      │
│  + acesso a banco    │                └──────────┬───────────┘
└──────────────────────┘                           │ Port
                                        ┌──────────▼────────────┐
                                        │   Domínio (puro)      │
                                        │   regra de negócio    │
                                        └──────────┬────────────┘
                                                   │ Port
                                        ┌──────────▼────────────┐
                                        │  Adapter (Banco)      │
                                        └───────────────────────┘
```

**Analogia:** pense numa tomada elétrica. A tomada (porta) tem um formato padrão — ela não sabe, nem precisa saber, se o aparelho plugado é uma lâmpada, um carregador ou uma TV. Qualquer aparelho (adaptador) que respeite o formato do plugue funciona. Cockburn quis que o domínio de negócio fosse como a tomada: um contrato estável, indiferente ao que está "plugado" do lado de fora (banco de dados, framework web, fila de mensagens).

---

## Por que o nome "Ports and Adapters"

O nome oficial e técnico do padrão criado por Cockburn não é "arquitetura hexagonal" — é **"Ports and Adapters"** ("Portas e Adaptadores"). Cada palavra tem um papel bem definido:

| Termo | O que representa | Analogia da tomada |
|---|---|---|
| **Port (Porta)** | Uma interface que declara um contrato — o que a aplicação oferece ou o que ela precisa do mundo externo | O formato físico da tomada na parede |
| **Adapter (Adaptador)** | Uma implementação concreta daquele contrato, usando uma tecnologia específica | O aparelho elétrico que você pluga (lâmpada, TV, carregador) |

O nome "hexagonal" surgiu depois, como apelido popular vindo do formato do diagrama que Cockburn desenhou para ilustrar o conceito — isso é aprofundado no próximo arquivo (1.1.1.2). O nome tecnicamente correto, usado em papers e discussões formais, continua sendo **Ports and Adapters**.

## Exemplo prático do problema resolvido

**Antes (acoplado):**
```java
public class PedidoController {
    public void finalizar(HttpServletRequest request) {
        int pedidoId = Integer.parseInt(request.getParameter("id"));

        Connection conn = DriverManager.getConnection(DB_URL);
        ResultSet rs = conn.createStatement()
            .executeQuery("SELECT * FROM pedidos WHERE id = " + pedidoId);

        if (rs.getInt("total_itens") == 0) {
            response.sendError(400, "Pedido vazio");
            return;
        }
        // regra de negócio misturada com SQL e HTTP
    }
}
```

**Depois (Ports and Adapters):**
```java
// Domínio - não conhece HTTP nem SQL
public class Pedido {
    public void finalizar() {
        if (itens.isEmpty()) {
            throw new PedidoVazioException();
        }
        this.status = StatusPedido.FINALIZADO;
    }
}

// Port - contrato de saída
public interface PedidoRepository {
    Optional<Pedido> buscarPorId(PedidoId id);
}

// Adapter de entrada - só traduz HTTP para chamada de domínio
@RestController
public class PedidoRestController {
    public ResponseEntity<?> finalizar(@PathVariable String id) {
        Pedido pedido = pedidoRepository.buscarPorId(new PedidoId(id))
            .orElseThrow();
        pedido.finalizar();
        return ResponseEntity.ok().build();
    }
}
```

A regra "pedido não pode ser finalizado vazio" agora vive isolada em `Pedido.finalizar()` e pode ser testada com um simples `new Pedido()`, sem banco, sem HTTP, sem framework.

## Quando isso importa / Erros comuns

| Cenário | Sem Ports and Adapters | Com Ports and Adapters |
|---|---|---|
| Trocar de banco de dados | Reescrever lógica de negócio junto com o acesso a dados | Trocar só o Adapter; o domínio não muda |
| Testar uma regra de negócio | Precisa de banco, servidor HTTP ou mocks pesados | Testa a classe de domínio isoladamente, sem infraestrutura |
| Adicionar uma nova interface (ex: CLI além de REST) | Duplicar ou reimplementar a regra de negócio | Criar um novo Adapter que chama o mesmo Port |

**Erro comum:** achar que o problema do acoplamento só existe com bancos de dados. Ele também aparece quando o domínio depende de bibliotecas de terceiros, frameworks de serialização (anotações JSON/JPA direto na entidade) ou até de outras APIs — qualquer dependência direta do domínio a algo externo reintroduz o mesmo problema que Cockburn queria eliminar.

## 🧩 Quiz de Fixação

1. Qual problema concreto Alistair Cockburn observou em 2005 que motivou a criação da arquitetura Ports and Adapters?
2. Na analogia da tomada elétrica, o que representa a "porta" e o que representa o "adaptador"?
3. Por que dizer que uma classe de domínio "não pode ser testada sem banco de dados" é um sintoma do problema de acoplamento, e não uma limitação normal de testes?

**Respostas:**
1) Ele observou que a lógica de negócio ficava entrelaçada com detalhes técnicos (SQL, HTTP, frameworks), tornando o sistema difícil de testar sem infraestrutura real e arriscado de evoluir, já que mudar a tecnologia podia quebrar a regra de negócio junto.
2) A porta é o contrato estável (a interface, como o formato físico da tomada) que não muda; o adaptador é a implementação concreta plugada naquele contrato (o aparelho elétrico), podendo ser trocado livremente sem afetar o outro lado.
3) Porque, numa arquitetura corretamente desacoplada, a regra de negócio deveria ser uma função pura sobre objetos de domínio — não deveria precisar de infraestrutura para ser verificada. A necessidade de banco de dados para testar uma regra revela que a regra está fisicamente misturada com o código de acesso a dados, violando o princípio central de Ports and Adapters.
