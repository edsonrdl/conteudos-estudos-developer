### Por que o nome hexagonal não tem relação com o número seis

O arquivo anterior (1.1.1.1) explicou o nome técnico correto do padrão, "Ports and Adapters", e o problema de acoplamento que ele resolve. Este arquivo trata de um mal-entendido extremamente comum: por que o apelido popular "arquitetura hexagonal" existe, e por que ele **não** significa que a arquitetura precisa ter seis de qualquer coisa.

---

## A escolha visual de Cockburn

Quando Alistair Cockburn precisou ilustrar seu padrão Ports and Adapters, ele enfrentou um problema de comunicação: os diagramas em camadas tradicionais (retângulos empilhados, um em cima do outro) carregam uma mensagem implícita indesejada. Em um diagrama assim, a camada do topo parece "mais importante" ou "mais próxima do usuário", e a camada da base parece a "fundação" do sistema — normalmente o banco de dados.

Esse é exatamente o tipo de pensamento que Cockburn queria combater. Para ele, o banco de dados não é a fundação de nada — é só mais um detalhe técnico substituível, do mesmo jeito que a interface web é. Um diagrama em camadas empilhadas comunica visualmente o oposto do que ele queria ensinar.

A solução foi desenhar o domínio como um polígono no centro, cercado por lados iguais, cada um representando uma porta diferente (uma para o banco, uma para a interface web, uma para uma fila de mensagens, e assim por diante). Como nenhum lado de um polígono regular é "mais alto" ou "mais baixo" que outro, a mensagem visual passa a ser: **todas as dependências externas têm o mesmo status — nenhuma é mais fundamental que a outra.**

```
DIAGRAMA EM CAMADAS (visão tradicional)      DIAGRAMA HEXAGONAL (visão de Cockburn)
┌─────────────────────────┐                              ┌──────────┐
│   Interface (Web/UI)    │  ← parece "importante"       │  Fila    │
├─────────────────────────┤                         ┌────┴────┬─────┴────┐
│   Lógica de Negócio     │                         │  REST   │  Domínio │  CLI
├─────────────────────────┤                         └────┬────┴─────┬────┘
│   Banco de Dados        │  ← parece a "fundação"       │  Banco   │
└─────────────────────────┘                              └──────────┘

Sugere hierarquia entre as camadas          Todos os lados têm o mesmo peso visual
```

O número de lados do polígono desenhado por Cockburn no material original **não corresponde a uma contagem fixa de portas**. Ele escolheu um hexágono simplesmente porque tinha espaço suficiente para desenhar algumas portas de exemplo (banco, UI, outro sistema, fila) sem o diagrama ficar apertado nem exageradamente vazio. Se o exemplo tivesse três portas, um triângulo serviria; se tivesse oito, um octógono serviria igualmente bem.

## A confusão mais comum

| Ideia equivocada | Realidade |
|---|---|
| "Preciso ter exatamente 6 portas ou adaptadores" | O número de portas depende inteiramente de quantas integrações externas o sistema realmente tem — pode ser 2, pode ser 15 |
| "Hexagonal" é o nome técnico oficial do padrão | O nome técnico é **Ports and Adapters**; "hexagonal" é apelido popular vindo do desenho |
| A forma hexagonal tem algum significado matemático ou arquitetural | É uma escolha de comunicação visual, sem significado técnico além de "lados equivalentes, sem hierarquia" |
| Um sistema "hexagonal" precisa ter uma estrutura de pastas específica | O padrão define um princípio (isolar o domínio via portas e adaptadores), não uma estrutura de arquivos obrigatória |

---

## Consequência prática

Entender essa origem evita dois erros opostos e igualmente comuns:

1. **Superengenharia por causa do nome:** criar seis interfaces artificiais só para "parecer hexagonal", quando o sistema real só precisa de duas ou três integrações externas.
2. **Rejeitar o padrão por achar a contagem obrigatória:** descartar a arquitetura achando que ela não se aplica a um sistema com "só uma porta de entrada e uma de saída" — quando, na verdade, isso é exatamente o mínimo válido de uma hexagonal simples e bem aplicada.

O critério real para saber se uma arquitetura é "hexagonal" nunca é contar lados no diagrama — é verificar se o domínio de negócio está isolado atrás de interfaces (portas), sem depender diretamente de nenhuma tecnologia externa concreta.

## 🧩 Quiz de Fixação

1. Por que Cockburn evitou o diagrama tradicional em camadas ao ilustrar seu padrão, e qual mensagem implícita ele queria eliminar?
2. O número de lados do hexágono no diagrama original tem algum significado técnico? Justifique.
3. Um colega afirma: "esse sistema não pode ser hexagonal porque só tem uma porta de entrada e uma de saída." Essa afirmação está correta? Por quê?

**Respostas:**
1) Ele evitou o diagrama em camadas porque esse formato sugere hierarquia — a camada do topo parece mais importante e a da base (geralmente o banco de dados) parece a "fundação" do sistema. Cockburn queria eliminar exatamente essa ideia, já que para ele o banco de dados é só mais um detalhe técnico substituível, sem status especial.
2) Não. O hexágono foi escolhido apenas porque tinha espaço visual suficiente para desenhar algumas portas de exemplo no diagrama original — não representa uma contagem obrigatória de portas, adaptadores ou qualquer outro elemento da arquitetura.
3) Está incorreta. O número de portas não define se uma arquitetura é "hexagonal" — o que define é se o domínio de negócio está isolado atrás de interfaces (portas) e livre de dependências diretas de tecnologia externa. Um sistema com apenas uma porta de entrada e uma de saída pode ser uma implementação perfeitamente válida e simples do padrão Ports and Adapters.
