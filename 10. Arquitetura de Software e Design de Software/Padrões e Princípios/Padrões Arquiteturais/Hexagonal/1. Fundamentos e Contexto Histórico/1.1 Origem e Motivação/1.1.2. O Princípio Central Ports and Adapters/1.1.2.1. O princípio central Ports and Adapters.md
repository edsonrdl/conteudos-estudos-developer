### O princípio central Ports and Adapters

Os dois arquivos anteriores explicaram o problema do acoplamento e a origem do nome. Este arquivo fecha o domínio de fundamentos definindo o mecanismo em si: a regra prática que faz o domínio ficar isolado sem virar uma promessa vaga de "baixo acoplamento".

---

## A regra: toda comunicação passa por uma porta

O princípio central é simples de enunciar e difícil de manter disciplina no dia a dia: **o núcleo de domínio nunca importa, instancia ou referencia diretamente uma classe concreta do mundo externo.** Toda interação — de entrada ou de saída — acontece através de uma interface (a porta), nunca de uma implementação (o adaptador).

Isso cria duas direções de comunicação, cada uma com um papel diferente:

```
                    ┌─────────────────────────────────────────┐
                    │                DOMÍNIO                    │
                    │         (não conhece ninguém)             │
                    └─────────────────────────────────────────┘
                          ▲                           │
                          │ Port de Entrada           │ Port de Saída
                          │ (Primary/Driving)          │ (Secondary/Driven)
                    ┌─────┴─────┐               ┌──────▼──────┐
                    │  Adapter  │               │   Adapter   │
                    │  (REST,   │               │  (Banco,    │
                    │  CLI...)  │               │  Email...)  │
                    └───────────┘               └─────────────┘
                          ▲                             │
                          │                             ▼
                    Usuário/Sistema              Banco/API externa
                    "empurra" (drive)            é "empurrado" (driven)
```

- **Portas de entrada (Primary/Driving):** alguém de fora "aciona" a aplicação — um usuário clicando em um botão, um sistema chamando uma API, um job agendado. O adaptador de entrada traduz esse estímulo externo em uma chamada à porta.
- **Portas de saída (Secondary/Driven):** a aplicação "aciona" algo de fora — salvar em um banco, enviar um e-mail, publicar um evento. Aqui é o domínio/aplicação que decide chamar a porta, e o adaptador de saída é quem obedece.

A diferença de direção importa porque muda quem depende de quem: nas portas de entrada, o adaptador depende da porta (chama-a). Nas portas de saída, é a porta que é definida pela necessidade do domínio, e o adaptador é quem se adapta a ela — daí o nome "adaptador".

## O mecanismo em código

Um port é apenas uma interface, definida no vocabulário do domínio (não no vocabulário da tecnologia):

```java
// Port de saída — definida em termos que o DOMÍNIO entende
public interface NotificadorCliente {
    void notificar(Cliente cliente, String mensagem);
}
```

O adaptador implementa essa interface usando uma tecnologia concreta, mas o nome dos métodos e os tipos de parâmetro continuam vindo do domínio:

```java
// Adapter — implementação concreta usando SendGrid
public class SendGridNotificadorAdapter implements NotificadorCliente {
    private final SendGrid sendGrid;

    @Override
    public void notificar(Cliente cliente, String mensagem) {
        // aqui, e só aqui, existe conhecimento de SendGrid, HTTP, etc.
        sendGrid.send(cliente.getEmail().getValor(), mensagem);
    }
}
```

Repare que a interface `NotificadorCliente` não menciona SendGrid, HTTP ou qualquer detalhe técnico — ela poderia ser implementada amanhã por um `TwilioSmsAdapter` ou por um `ConsoleLogAdapter` de teste, sem que uma linha do domínio precise mudar.

## Por que a direção da dependência é o teste real

| Pergunta de verificação | Se a resposta for "sim", há um vazamento |
|---|---|
| O domínio importa alguma classe de um driver JDBC, de um framework web ou de um SDK de terceiros? | Vazamento de tecnologia no domínio |
| A interface do port foi desenhada pensando em como o banco de dados representa os dados (colunas, tipos SQL)? | O port está "vazando" o adapter, invertendo a dependência |
| Trocar a implementação do adapter exige alterar a assinatura do port? | O port não está realmente desacoplado da tecnologia |

O teste mais simples e prático: **é possível escrever um teste de unidade para essa regra de negócio usando um adapter falso (in-memory), sem subir banco, sem subir servidor HTTP?** Se a resposta for não, alguma porta está sendo pulada e uma dependência direta está se infiltrando.

## Erro comum: portas "de aluguel" da tecnologia

Um erro frequente é criar uma porta que apenas espelha uma biblioteca específica, ao invés de expressar uma necessidade do domínio:

```java
// ERRADO — a porta "vaza" a tecnologia (JPA) para o domínio
public interface ClienteJpaPort {
    ClienteEntity findById(Long id); // tipo JPA, não tipo de domínio
}

// CORRETO — a porta fala a língua do domínio
public interface ClienteRepository {
    Optional<Cliente> buscarPorId(ClienteId id); // tipo de domínio
}
```

No exemplo errado, trocar de JPA para MongoDB exigiria mudar a assinatura da porta — ou seja, o domínio continuaria amarrado à tecnologia, só que indiretamente. No exemplo correto, a porta pode ser implementada por qualquer tecnologia sem alterar uma linha do domínio.

## 🧩 Quiz de Fixação

1. Qual é a regra central que define se uma dependência externa está corretamente isolada do domínio, segundo o princípio Ports and Adapters?
2. Qual a diferença de responsabilidade entre uma porta de entrada (Primary/Driving) e uma porta de saída (Secondary/Driven)?
3. Por que uma interface como `ClienteJpaPort findById(Long id): ClienteEntity` é considerada um "vazamento" de tecnologia, mesmo sendo tecnicamente uma interface?

**Respostas:**
1) A regra central é que o núcleo de domínio nunca importa, instancia ou referencia diretamente uma classe concreta do mundo externo — toda comunicação (entrada ou saída) deve passar por uma interface (porta), nunca por uma implementação (adaptador).
2) Na porta de entrada, algo externo "aciona" a aplicação (um usuário, outro sistema) e o adaptador traduz esse estímulo em uma chamada à porta — o adaptador depende da porta. Na porta de saída, é a própria aplicação que decide chamar algo externo (salvar, notificar, publicar), e o adaptador obedece à porta definida pelo domínio — a porta é definida pela necessidade do domínio, não pela tecnologia do adaptador.
3) Porque o tipo de retorno (`ClienteEntity`) e o tipo de parâmetro (`Long`, típico de chave primária JPA) revelam a tecnologia de persistência escolhida. Isso significa que trocar de JPA para outra tecnologia (MongoDB, por exemplo) exigiria alterar a própria assinatura da porta — ou seja, o domínio continuaria indiretamente amarrado à tecnologia, mesmo existindo uma interface de por meio.
