### A solução com Template Tags — CTRL + Espaço, Response tag e JSONPath

As **Template Tags** são o mecanismo do Insomnia para inserir valores dinâmicos em qualquer campo de uma requisição — URL, headers, body, query params. A tag mais poderosa é a **Response tag**, que permite extrair um valor específico da resposta de outro request e injetá-lo automaticamente no request atual. É a base do Request Chaining: o fluxo Login → Criar recurso → Operar sobre o recurso acontece sem nenhuma cópia manual.

---

## O que são Template Tags

```
Template Tags são expressões delimitadas por {{ }} que o Insomnia
avalia antes de enviar cada requisição.

Tipos de Template Tags:
  {{ variavel }}              → variável do Environment
  {{ $timestamp }}            → valor dinâmico built-in
  {{ $guid }}                 → UUID aleatório
  {{ _.response.body.id }}    → valor extraído de outra resposta (Response Tag)
  {{ _.response.header.X }}   → header de outra resposta
  {{ uuid() }}                → função built-in

Como acessar:
  Em QUALQUER campo editável do Insomnia:
  → Pressionar CTRL + ESPAÇO (Windows/Linux) ou CMD + ESPAÇO (Mac)
  → Aparece o menu de autocompletar com todas as tags disponíveis
```

## A Response Tag — o coração do Request Chaining

A Response Tag extrai valores de respostas de outros requests. Ao configurá-la, você define:
1. **Qual request** fornece o valor
2. **Onde buscar** na resposta (body via JSONPath, ou header)
3. **Qual comportamento** quando o valor não existe

```
Configuração visual da Response Tag:

┌─────────────────────────────────────────────────────────────────┐
│  Response Tag Configuration                                     │
│                                                                 │
│  Request:   [POST /auth/login ▼]       ← qual request usar      │
│                                                                 │
│  Filter:    [Body ▼]  [$.access_token] ← onde extrair           │
│                                                                 │
│  Trigger:   [Never ▼]                  ← quando re-executar     │
│                                                                 │
│  Preview:   eyJhbGciOiJSUzI1NiJ9...   ← valor atual            │
└─────────────────────────────────────────────────────────────────┘
```

### O campo "Filter" — Body vs Header

```
Body (extração via JSONPath):
  Resposta do POST /auth/login:
  {
    "access_token": "eyJhbGciOiJSUzI1NiJ9...",
    "user": {
      "id": 42,
      "name": "João"
    },
    "expires_in": 3600
  }

  JSONPath para extrair o token:   $.access_token
  JSONPath para extrair o ID:      $.user.id
  JSONPath para extrair o nome:    $.user.name

Header (extração de header da resposta):
  Resposta com Location header:
  HTTP/1.1 201 Created
  Location: /api/produtos/456

  Header Filter:  Location
  Resultado:      /api/produtos/456
```

## JSONPath — a linguagem de extração

JSONPath é uma sintaxe para navegar em documentos JSON. O Insomnia usa JSONPath para extrair valores específicos do body da resposta.

### Sintaxe básica

```
Dado o JSON de resposta:
{
  "status": "sucesso",
  "dados": {
    "usuario": {
      "id": 123,
      "nome": "João Silva",
      "email": "joao@empresa.com",
      "roles": ["admin", "editor"],
      "endereco": {
        "cidade": "São Paulo",
        "estado": "SP"
      }
    },
    "token": "eyJ...",
    "expira_em": 3600
  }
}

Expressões JSONPath:
  $.status                    → "sucesso"
  $.dados.token               → "eyJ..."
  $.dados.usuario.id          → 123
  $.dados.usuario.nome        → "João Silva"
  $.dados.usuario.roles[0]    → "admin" (primeiro elemento do array)
  $.dados.usuario.roles[1]    → "editor" (segundo elemento)
  $.dados.usuario.endereco.cidade → "São Paulo"
  $.dados.expira_em           → 3600

Operadores JSONPath:
  $       → raiz do documento
  .campo  → acessa um campo de objeto
  [n]     → acessa índice n de um array (começa em 0)
  [*]     → todos os elementos de um array
  ..campo → busca recursiva (todos os "campo" no documento)
```

### Casos práticos com JSONPath

```
Resposta de POST /auth/login:
  {"access_token": "eyJ...", "refresh_token": "8xL...", "expires_in": 3600}
  
  Extrair access_token:   $.access_token
  Extrair refresh_token:  $.refresh_token

Resposta de POST /usuarios:
  {"id": 789, "nome": "Maria", "criado_em": "2024-01-15T10:00:00Z"}
  
  Extrair ID:  $.id
  
Resposta de GET /pedidos:
  {
    "total": 3,
    "pedidos": [
      {"id": 101, "status": "pendente"},
      {"id": 102, "status": "aprovado"},
      {"id": 103, "status": "entregue"}
    ]
  }
  
  Extrair primeiro ID:  $.pedidos[0].id     → 101
  Extrair segundo ID:   $.pedidos[1].id     → 102
  Total de pedidos:     $.total             → 3

Resposta de API com envelope:
  {"success": true, "data": {"product": {"id": 456, "name": "Notebook"}}}
  
  Extrair ID:    $.data.product.id    → 456
  Extrair nome:  $.data.product.name  → "Notebook"
```

## O campo "Trigger" — quando re-executar o request de origem

O campo **Trigger** define quando o Insomnia deve re-executar o request de origem para buscar um valor atualizado.

```
Opções de Trigger:

Never (Nunca — padrão para tokens não expiráveis):
  → Usa a última resposta armazenada
  → Não re-executa o request de origem
  → Use para: tokens de desenvolvimento que não expiram, IDs fixos

No History (Quando não há histórico):
  → Só executa se não há resposta anterior armazenada
  → Re-usa a última resposta se já existe
  → Use para: IDs criados uma vez e reutilizados múltiplas vezes

Always (Sempre — ideal para tokens expiráveis):
  → Re-executa o request de origem ANTES de cada envio
  → Garante que sempre tem o valor mais recente
  → Use para: access_token com expiração, timestamps, UUIDs únicos
  → Custo: mais lento (executa 2 requests: origem + atual)

Quando Expiry Header Matches (condicional):
  → Verifica um header de expiração antes de re-executar
  → Inteligente: só re-executa se o valor realmente expirou
  → Avançado — requer conhecimento dos headers da API
```

### Escolhendo o Trigger correto

```
Token JWT com expiração de 1 hora:
  Trigger: Always
  → Cada vez que você enviar qualquer request, o login é feito antes
  → Garante token sempre fresco
  
  Alternativa melhor com Always:
  → Apenas configure em 1 pasta pai com Pre-request Script
  → Evita N logins para N requests simultâneos

ID de recurso criado no início do teste:
  Trigger: No History
  → Cria o recurso apenas uma vez (primeira execução)
  → Reutiliza o ID nas execuções seguintes
  → Quando quiser criar um novo: limpar o histórico manualmente

UUID para idempotência:
  Trigger: Always
  → Gera um novo UUID a cada envio
  → Equivalente a usar {{ $guid }} diretamente
```

## Configurando Response Tag na prática

### Passo a passo visual

```
Cenário: GET /usuarios/{{ id_do_usuario_criado }}
onde o ID vem do POST /usuarios

1. Clicar no campo da URL onde quer inserir o ID
   URL: https://api.exemplo.com/usuarios/

2. Pressionar CTRL + ESPAÇO
   → Aparece o menu de Template Tags

3. Clicar em "Response"
   → Abre o configurador da Response Tag

4. Em "Request": selecionar "POST /usuarios"
   → Lista todos os requests da collection

5. Em "Filter": deixar "Body" selecionado
   → Digitar o JSONPath: $.id

6. Em "Trigger": selecionar "No History"
   → Só executa o POST se não tem histórico

7. Em "Preview": deve aparecer o ID (se já executou o POST antes)
   → Preview: 789

8. Clicar "Done" / pressionar Enter para confirmar

URL final:
  https://api.exemplo.com/usuarios/{{ _.response.body.$.id }}
```

### O Preview — testando antes de enviar

```
O campo Preview mostra o valor que será inserido AGORA,
com base na última resposta armazenada do request de origem.

Preview verde (valor encontrado):
  Preview: eyJhbGciOiJSUzI1NiJ9...  ✓ token encontrado

Preview vazio / vermelho (valor não encontrado):
  Preview: (empty)  ← JSONPath não retornou nada
  
  Causas:
  → O request de origem ainda não foi executado
  → O JSONPath está errado
  → O campo não existe na resposta
  → O tipo de valor é diferente (array vs string)
  
  Como resolver:
  1. Executar o request de origem manualmente primeiro
  2. Verificar o JSONPath no painel de resposta do request de origem
  3. Usar o "Response Body" view no request de origem para testar o JSONPath
```

## Exemplo completo — fluxo Login → Criar → Buscar

```
Collection: E-commerce API

Request 1: POST /auth/login
  URL: {{ base_url }}/auth/login
  Body: {"email": "{{ email }}", "senha": "{{ senha }}"}
  → Resposta: {"access_token": "eyJ...", "user_id": 42}

Request 2: POST /produtos
  URL: {{ base_url }}/produtos
  Auth: Bearer [Response Tag → POST /auth/login → $.access_token → Always]
  Body: {"nome": "Notebook", "preco": 2999.90}
  → Resposta: {"id": 456, "nome": "Notebook"}

Request 3: GET /produtos/{{ produto_id }}
  URL: {{ base_url }}/produtos/[Response Tag → POST /produtos → $.id → No History]
  Auth: Bearer [Response Tag → POST /auth/login → $.access_token → Always]
  → Retorna os dados do produto criado

Fluxo ao clicar "Send" no Request 3:
  1. Insomnia verifica Response Tags
  2. Token (Always): re-executa POST /auth/login → obtém novo token
  3. produto_id (No History): já existe histórico → usa $.id = 456
  4. Monta Request 3: GET /produtos/456 com Bearer eyJ...
  5. Envia o request
  6. Retorna dados do produto 456

Nenhuma cópia manual. Nenhuma edição. 1 clique.
```

## Erros comuns e armadilhas

**JSONPath retorna vazio mas o campo existe:** verificar capitalização (JSON é case-sensitive), aspas extras no valor, ou se o campo está em um nível diferente do esperado. Usar o painel de resposta do request de origem para navegar manualmente e descobrir o caminho correto.

**Trigger "Always" causando loop infinito:** se o Request A depende do Request B, e o Request B depende do Request A, o Insomnia entra em loop. Evitar dependências circulares — o fluxo deve ser sempre linear (A → B → C).

**Preview vazio após executar o request:** o histórico de respostas no Insomnia tem limite. Se você limpou o histórico ou o Insomnia foi reiniciado, o Preview ficará vazio até que o request de origem seja executado novamente. Executar o request de origem manualmente resolve.

**Tag com Trigger "Always" em request dentro de loop de testes:** se você está executando muitos requests em sequência, "Always" fará login para CADA request — multiplicando o número de chamadas. Usar "No History" quando o token não expira durante os testes.

## 🧩 Quiz de Fixação

1. Um request POST retorna este JSON: `{"result": {"auth": {"token": "abc123", "expires": 3600}, "user": {"id": 789}}}`. Escreva os JSONPaths para extrair: (a) o token, (b) o ID do usuário, (c) o tempo de expiração.

2. Você configurou uma Response Tag com Trigger "Always" apontando para POST /auth/login para extrair o token. O time reclama que cada request está demorando o dobro do esperado. Qual é a causa e como otimizar sem perder a renovação automática do token?

3. Um Response Tag está configurada com `$.produtos[0].id` mas o Preview mostra vazio. O request de origem (GET /produtos) foi executado e retornou `{"itens": [...], "total": 5}`. Qual é o problema e como corrigir?

**Respostas:**

1) JSONPaths corretos:
- (a) Token: `$.result.auth.token` → `"abc123"`
- (b) ID do usuário: `$.result.user.id` → `789`
- (c) Tempo de expiração: `$.result.auth.expires` → `3600`

2) **Causa:** o Trigger "Always" re-executa o POST /auth/login antes de CADA request que usa a tag, dobrando o número de chamadas e o tempo total. Se você tem 10 requests na collection, serão feitos 10 logins desnecessários. **Otimização:** trocar para um **Pre-request Script na pasta pai** que verifica se o token ainda é válido antes de renovar — se não expirou, reutiliza; se expirou, faz login. Alternativamente, usar Trigger "No History" com um Environment que armazena o token e renová-lo manualmente quando expirar, ou usar o fluxo OAuth 2.0 nativo do Insomnia que gerencia a expiração automaticamente.

3) **Problema:** o JSONPath `$.produtos[0].id` está errado — a chave no JSON não é `produtos`, é `itens`. A Response Tag tentou encontrar `$.produtos[0].id` em `{"itens": [...], "total": 5}` e não encontrou nenhum match, resultando em Preview vazio. **Correção:** atualizar o JSONPath para `$.itens[0].id` — que corresponde ao nome real do campo na resposta. Para evitar esse tipo de erro, sempre verificar o JSONPath no painel de resposta do request de origem antes de configurar a Tag: abrir o request GET /produtos, ver a resposta, e navegar manualmente pela estrutura para confirmar o caminho correto.
