### O problema — dependência de token entre requisições

A maioria das APIs protegidas exige que você se autentique antes de fazer qualquer operação. Isso cria uma dependência inevitável: para testar `POST /pedidos`, você precisa de um token válido — que só existe após executar `POST /auth/login`. Sem um mecanismo de encadeamento, o desenvolvedor fica preso num ciclo manual e frustrante de copiar e colar entre requests.

---

## O ciclo doloroso sem Request Chaining

```
Cenário: testar a criação de um pedido numa API autenticada

Passo 1: Executar o login
  POST /auth/login
  Body: {"email": "joao@empresa.com", "senha": "123456"}
  
  Resposta:
  {
    "access_token": "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWI...",
    "expires_in": 3600,
    "token_type": "Bearer"
  }

Passo 2: Copiar o token manualmente
  → Selecionar o token na resposta (cuidado para não pegar aspas)
  → Ctrl+C

Passo 3: Ir ao request de pedidos
  → Clicar em POST /pedidos
  → Clicar na aba Auth ou Headers
  → Localizar o campo do Bearer Token
  → Ctrl+V

Passo 4: Finalmente executar o request de pedidos

Custo de cada teste:
  → 4 ações manuais
  → ~15-30 segundos de operação manual
  → Alta probabilidade de erro (copiar com espaço, token errado, etc.)
```

---

## Quando o problema escala

```
APIs com múltiplas dependências:

POST /auth/login → token de usuário
  ↓ (copia token)
POST /carrinho → cria carrinho, retorna carrinho_id
  ↓ (copia carrinho_id)
POST /carrinho/{{ carrinho_id }}/itens → adiciona item, retorna item_id
  ↓ (copia item_id)
POST /pedidos → cria pedido com carrinho_id
  ↓ (copia pedido_id)
POST /pedidos/{{ pedido_id }}/pagamento → processa pagamento

5 dependências encadeadas:
  → 10+ ações de copiar/colar
  → 2-3 minutos de trabalho manual para cada ciclo de teste
  → Se o token expira no meio: recomeçar do zero
  → Se você erra uma cópia: debug difícil (onde errou?)
```

---

## Tipos de dependência mais comuns

### 1. Token de autenticação

```
O mais universal — afeta quase todas as APIs protegidas:

Login → access_token → todos os requests subsequentes

Problemas adicionais:
  → Token expira (geralmente em 1 hora)
  → Após expirar: fazer login de novo e copiar o novo token
  → Com múltiplos dispositivos/sessions: token pode ser invalidado
  → Fluxo OAuth: precisa do authorization_code antes do token
```

### 2. ID gerado pelo servidor (resource creation)

```
IDs gerados automaticamente pelo backend:

POST /usuarios → {"id": 789, "nome": "Maria"}
GET /usuarios/789 → precisa do ID 789
PUT /usuarios/789 → precisa do ID 789
DELETE /usuarios/789 → precisa do ID 789

CRUD completo: 3 operações dependentes do ID criado no POST
```

### 3. IDs em fluxos de negócio

```
E-commerce completo:
  POST /clientes → cliente_id (para criar o pedido)
  POST /enderecos → endereco_id (para associar ao pedido)
  POST /pedidos (com cliente_id + endereco_id) → pedido_id
  POST /pedidos/{{ pedido_id }}/pagamento
  GET  /pedidos/{{ pedido_id }}/status

Saúde:
  POST /pacientes → paciente_id
  POST /consultas (com paciente_id) → consulta_id
  POST /consultas/{{ consulta_id }}/prescricoes

Cada nível depende do resultado do nível anterior
```

### 4. Upload + processamento

```
POST /uploads → upload_id (arquivo no storage)
  ↓ precisa do upload_id
POST /processar/{{ upload_id }} → job_id
  ↓ precisa do job_id
GET  /jobs/{{ job_id }}/status → "processado"
  ↓ precisa do job_id
GET  /resultados/{{ job_id }}

Sem encadeamento: 4 cópias manuais, uma por vez
```

## O impacto no dia a dia

```
Situação 1 — Token expirou durante o trabalho:
  → Desenvolvedor está 3 requests dentro de um fluxo
  → Recebe 401 Unauthorized
  → Tem que voltar ao login, copiar o novo token, voltar para o request atual
  → Interrupção de contexto: onde estava no fluxo?

Situação 2 — Collection compartilhada com o time:
  → Novo dev recebe a collection
  → Precisa descobrir em que ordem executar os requests
  → Qual ID usar? Qual token?
  → Documentação implícita que não está na collection

Situação 3 — Ambiente de CI/CD sem interação humana:
  → Impossível copiar e colar manualmente num pipeline automatizado
  → Sem encadeamento: não há como executar requests dependentes automaticamente
  → Com encadeamento: o Insomnia (via Inso CLI) executa tudo automaticamente

Situação 4 — Retestar após mudança de código:
  → Você reexecuta o fluxo completo para verificar uma correção
  → Sem encadeamento: 2-3 minutos de cópias manuais para cada reteste
  → Com encadeamento: 1 clique, tudo encadeado e executado em sequência
```

## Por que não basta colocar o token no environment?

```
Solução parcial — token fixo no environment:
  Environment "Dev":
    access_token: eyJhbGciOiJSUzI1... (token que você colou manualmente)

Problemas que persistem:
  1. Token expira em 1 hora → tem que copiar manualmente de novo
  2. Token é gerado dinamicamente → cada ambiente gera um token diferente
  3. IDs de recursos criados durante o teste não são conhecidos de antemão
     → Não tem como colocar no environment antecipadamente
  
  O environment resolve o problema de configuração estática
  O Request Chaining resolve o problema de dados DINÂMICOS
  (dados que só existem durante a execução dos testes)
```

---

## A solução — visão geral antes do próximo arquivo

```
O Request Chaining com Template Tags resolve todos esses problemas:

POST /auth/login → acesso ao token
  ↓ Template Tag extrai automaticamente o token
POST /pedidos com Authorization: Bearer [token extraído automaticamente]
  ↓ Template Tag extrai automaticamente o pedido_id
GET /pedidos/[pedido_id extraído automaticamente]

Nenhuma cópia manual. Nenhuma interrupção.
Se o token expirar: o Insomnia refaz o login automaticamente.

O mecanismo completo é explicado em:
  3.1.2.2. A solução com Template Tags
  3.1.2.3. Resultado — automação completa do fluxo
```

## 🧩 Quiz de Fixação

1. Um desenvolvedor testa uma API de e-commerce e faz isso regularmente: login → criar produto → criar pedido com o produto → verificar pedido. Sem Request Chaining, quantas ações manuais de copiar/colar são necessárias por ciclo completo de teste, e quais são elas?

2. Por que tokens com expiração curta (15-60 minutos) agravam especialmente o problema de dependência manual, e em quais momentos do trabalho o desenvolvedor é mais afetado?

3. Por que colocar o token no Environment não é suficiente para resolver dependências de IDs de recursos criados dinamicamente?

**Respostas:**

1) **3 ações de copiar/colar por ciclo completo:**
(1) Login → copiar o `access_token` → colar no header/auth dos próximos requests;
(2) Criar produto (POST /produtos) → copiar o `product_id` retornado → colar na URL/body do próximo request;
(3) Criar pedido com o produto (POST /pedidos com product_id) → copiar o `order_id` retornado → colar na URL do GET.
Se o token expirar durante o ciclo, há uma quarta ação: fazer novo login e repetir a cópia do token. Em total: 6-8 ações de seleção, cópia e colagem manualmente, ~30-60 segundos por ciclo completo de teste.

2) Tokens com expiração curta são especialmente problemáticos porque: (a) **Interrompem o raciocínio:** o desenvolvedor está no meio de um fluxo complexo quando recebe um 401. Tem que parar, fazer novo login, copiar o token, retornar ao request onde estava — perdendo o contexto mental; (b) **Expiram com mais frequência nos momentos mais críticos:** durante debugging intenso (muitas requisições em sequência), durante reuniões ou pausas, ou ao retomar o trabalho após uma reunião de 30 minutos; (c) **Multiplicam o problema:** em uma sessão de desenvolvimento de 4 horas com tokens de 1 hora, o desenvolvedor interrompe o trabalho de teste ~3-4 vezes. Sem encadeamento, cada interrupção custa 15-30 segundos mais a perda de contexto.

3) O Environment armazena dados **estáticos e pre-definidos** — valores que você conhece antes de começar o teste. IDs de recursos criados dinamicamente não existem até que o POST seja executado: o servidor gera o ID em tempo de criação (UUID, auto-increment, etc.) e você não tem como saber qual será antecipadamente. Mesmo que você faça o POST, copie o ID manualmente para o environment, e depois use `{{ product_id }}` nos requests subsequentes — você ainda precisou copiar manualmente. Além disso, se você refizer o POST (testando um cenário diferente), o ID muda e o environment fica desatualizado. O Request Chaining resolve isso extraindo o ID da resposta em tempo real, sem precisar saber o valor antecipadamente e sem intervenção manual.
