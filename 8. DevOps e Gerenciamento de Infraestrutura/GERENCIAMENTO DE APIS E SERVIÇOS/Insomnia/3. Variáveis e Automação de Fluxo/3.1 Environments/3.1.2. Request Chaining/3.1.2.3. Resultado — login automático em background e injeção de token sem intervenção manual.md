### Resultado — login automático em background e injeção de token sem intervenção manual

Quando o Request Chaining está corretamente configurado, o Insomnia executa toda a cadeia de dependências automaticamente ao clicar "Send" em um único request. O login roda em background, o token é capturado e injetado, os IDs de recursos são extraídos das respostas anteriores — tudo sem uma única cópia manual. Este arquivo mostra o resultado final: como o fluxo completo se comporta em execução e como isso transforma o dia a dia de teste de APIs.

## O antes e o depois

```
ANTES (sem Request Chaining):
  1. Executar POST /auth/login manualmente
  2. Copiar o access_token da resposta
  3. Abrir POST /pedidos
  4. Colar o token no header Authorization
  5. Executar POST /pedidos
  6. Copiar o pedido_id da resposta
  7. Abrir GET /pedidos/:id
  8. Colar o pedido_id na URL
  9. Executar GET /pedidos/:id
  → 9 passos, ~60 segundos, alta chance de erro

DEPOIS (com Request Chaining):
  1. Clicar "Send" no GET /pedidos/:id
  → 1 passo, ~2 segundos, zero erro manual

  O Insomnia, em background:
    - Detecta que o GET precisa de um pedido_id (Response Tag → POST /pedidos)
    - Detecta que o POST /pedidos precisa de um token (Response Tag → POST /auth/login)
    - Executa POST /auth/login → captura o access_token
    - Executa POST /pedidos com o token → captura o pedido_id
    - Executa GET /pedidos/:id com o token e o pedido_id
    - Mostra a resposta final
```

## Como o Insomnia resolve a cadeia de dependências

Quando você clica "Send", o Insomnia monta um **grafo de dependências** internamente e resolve na ordem correta:

```
Você clica "Send" em:  GET /pedidos/{{ pedido_id }}
                        Authorization: Bearer {{ token }}

O Insomnia analisa as Template Tags e descobre:
  {{ pedido_id }}  →  Response Tag apontando para POST /pedidos
  {{ token }}      →  Response Tag apontando para POST /auth/login

Resolução (respeitando triggers):
  ┌─────────────────────────────────────────────────────┐
  │  1. POST /auth/login (trigger: Always)              │
  │     → executa, captura access_token                 │
  │                                                     │
  │  2. POST /pedidos (trigger: No History)             │
  │     → usa o token do passo 1                        │
  │     → executa, captura pedido_id                    │
  │                                                     │
  │  3. GET /pedidos/{pedido_id} ← o request que você    │
  │     clicou                                           │
  │     → usa token + pedido_id dos passos anteriores    │
  │     → executa e mostra a resposta                    │
  └─────────────────────────────────────────────────────┘
```

## O comportamento do token expirado — renovação transparente

O caso mais valioso do Request Chaining é a renovação automática de token. Com o trigger correto, você nunca mais vê um `401 Unauthorized` por token expirado durante os testes.

```
Configuração:
  Response Tag do token:
    Request: POST /auth/login
    Filter:  Body → $.access_token
    Trigger: Always (ou "When Expiry Header Matches" para otimizar)

Comportamento com trigger "Always":
  Toda vez que você envia QUALQUER request que usa {{ token }}:
    1. O Insomnia re-executa o POST /auth/login em background
    2. Obtém um token novo (nunca expirado)
    3. Injeta esse token no request atual
    4. Envia

  Resultado: o token nunca expira do ponto de vista do seu teste.
             Você trabalha por horas sem nunca fazer login manual.
```

### Otimizando com "When Expiry Header Matches"

```
O trigger "Always" é simples mas faz login a CADA request (custo de performance).

O trigger "When Expiry Header Matches" é mais inteligente:
  → Só re-executa o login se o token realmente expirou
  → Verifica o tempo de expiração antes de decidir
  → Evita logins desnecessários

Alternativa avançada — Pre-request Script na pasta pai:
  Um script que verifica se o token no environment ainda é válido:
    - Se válido: reutiliza (zero requests extras)
    - Se expirado: faz login e atualiza o environment
  → Melhor performance para collections grandes
```

```javascript
// Pre-request Script na pasta pai — renovação inteligente
const expiry = insomnia.environment.get('token_expiry');
const agora = Math.floor(Date.now() / 1000);

// Renova apenas se faltam menos de 60s para expirar (ou não há token)
if (!expiry || agora > (expiry - 60)) {
  const resposta = await insomnia.send('req_login_id');  // ID do request de login
  const body = JSON.parse(resposta.body);

  insomnia.environment.set('access_token', body.access_token);
  insomnia.environment.set('token_expiry', agora + body.expires_in);
}
// Se o token ainda é válido, nenhum request extra é feito
```

## Erros comuns e armadilhas

**Esquecer que o "Send" dispara requests em background:** ao clicar "Send" num request com Response Tags de trigger "Always", o Insomnia realmente executa os requests de origem — incluindo POSTs. Cuidado ao ter um POST destrutivo (ex: criar cobrança real) na cadeia — cada "Send" pode criar recursos de verdade. Use ambientes de teste/sandbox.

**Trigger "Always" em cadeias longas causando lentidão:** se cada request re-executa toda a cadeia de dependências, um fluxo de 5 requests pode disparar dezenas de requests em background. Usar Pre-request Script com cache de token para requests que não mudam entre execuções.

**Confiar no Request Chaining sem validar a resposta:** encadear não valida se a resposta está correta — só extrai valores. Para validação real (status code, campos obrigatórios), adicione **After-response Scripts** com asserções ou use o Collection Runner com testes.

## 🧩 Quiz de Fixação

1. Um desenvolvedor configura um fluxo com Request Chaining onde o POST /cobrancas (que cria uma cobrança REAL no gateway de pagamento) está na cadeia de dependências de um GET /cobrancas/:id, com trigger "Always". Ele clica "Send" no GET cinco vezes seguidas para testar. Qual é o problema e como evitá-lo?

2. Explique por que o Request Chaining é o que torna possível rodar testes de API em um pipeline de CI/CD, algo impossível com o método manual de copiar/colar tokens.

3. Uma collection tem 10 requests que usam `{{ token }}` com Response Tag de trigger "Always" apontando para o login. Ao executar o Collection Runner, o desenvolvedor nota que foram feitas 20 chamadas HTTP em vez de 10. Por quê, e como reduzir para próximo de 10 sem perder a renovação automática do token?

**Respostas:**

1) O problema é que com trigger "Always", cada clique em "Send" no GET **re-executa toda a cadeia de dependências em background** — incluindo o POST /cobrancas, que cria uma cobrança **real** no gateway. Cinco cliques = cinco cobranças reais criadas (possivelmente cobrando um cartão de verdade cinco vezes). **Como evitar:** (a) usar sempre um **ambiente sandbox/teste** do gateway de pagamento, nunca produção, durante os testes; (b) mudar o trigger do POST /cobrancas para **"No History"** — assim ele cria a cobrança apenas uma vez (na primeira execução) e reutiliza o resultado nas execuções seguintes, em vez de criar uma nova a cada "Send"; (c) separar requests destrutivos em uma pasta isolada que não é acionada automaticamente pela cadeia. A regra geral: requests que criam recursos reais devem usar "No History", não "Always".

2) No método manual, um humano precisa: executar o login, copiar o token da resposta com o mouse/teclado, e colar no próximo request. Um pipeline de CI/CD **não tem humano nem interface gráfica** — é um processo automatizado rodando num servidor. Não existe "copiar e colar" possível. O Request Chaining resolve isso porque toda a lógica de "pegar o token da resposta A e injetar no request B" é **declarada na configuração da collection** (via Response Tags), não executada manualmente. Quando a Inso CLI roda a collection no CI, ela interpreta essas Response Tags e resolve a cadeia automaticamente — login, captura de token, injeção, encadeamento de IDs — tudo programaticamente. O mesmo fluxo que funciona quando você clica "Send" localmente funciona quando o `inso run collection` executa no pipeline, sem nenhuma intervenção.

3) Foram feitas 20 chamadas porque cada um dos 10 requests tem uma Response Tag de token com trigger **"Always"** — então, para cada request "real", o Insomnia executa **primeiro** o POST /auth/login (1 chamada de login) e **depois** o request em si (1 chamada real). 10 requests × 2 chamadas = 20 chamadas HTTP, sendo 10 logins redundantes. **Como reduzir:** substituir as Response Tags de trigger "Always" por um **Pre-request Script na pasta pai** que verifica se o token no environment ainda é válido antes de renovar — se o token não expirou, reutiliza o valor do environment (zero chamadas extras); se expirou, faz login uma única vez e atualiza o environment. Com isso, o login acontece apenas 1 vez (no primeiro request) e os outros 9 reutilizam o token em cache — total de ~11 chamadas (1 login + 10 requests) em vez de 20, mantendo a renovação automática quando realmente necessária.
