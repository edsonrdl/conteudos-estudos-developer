### Aplicação prática — nunca hardcode URLs, sempre {{ base_url }}

A regra é simples mas transformadora: nenhuma URL, token, ID ou configuração variável deve ser escrita literalmente em um request. Tudo que muda entre ambientes, usuários ou momentos no tempo deve ser uma variável. Este arquivo consolida os padrões práticos que tornam uma collection realmente utilizável por qualquer membro do time, em qualquer ambiente, sem edição manual.

---

## A regra de ouro: se muda entre contextos, é variável

```
O teste simples:
  "Este valor seria diferente em Dev, QA ou Produção?"
  SIM → variável de ambiente
  
  "Este valor seria diferente para outro usuário testando a collection?"
  SIM → variável de ambiente (Private ou compartilhado)
  
  "Este valor expira ou muda ao longo do tempo?"
  SIM → variável dinâmica (Template Tag ou script)
  
  "Este valor é sensível (senha, token, secret)?"
  SIM → variável no Private Environment

O que pode ser hardcoded:
  → Nomes de campos que nunca mudam ("nome", "email", "status")
  → Valores de enum fixos ("ativo", "inativo", "pendente")
  → Campos que são literalmente iguais em todos os ambientes
```

## Aplicação em todos os campos do request

### URL — nunca literal

```
❌ Errado (hardcoded):
  https://api.empresa.com/v2/usuarios/42

✓ Correto (variável):
  {{ base_url }}/{{ api_version }}/usuarios/{{ user_id }}

Composição inteligente:
  Base URL completa:   {{ base_url }}/api/{{ api_version }}
  Recurso:             /usuarios/{{ user_id }}/pedidos/{{ order_id }}
  
  URL final:
  http://localhost:3000/api/v2/usuarios/1/pedidos/123  (Dev)
  https://api.empresa.com/api/v2/usuarios/0/pedidos/0  (Prod — antes de configurar IDs)
```

### Headers — autenticação e contexto sempre variável

```
❌ Errado (token hardcoded no header):
  Authorization: Bearer eyJhbGciOiJSUzI1NiJ9.eyJzdWIiOiI0MiJ9...

✓ Correto (token do environment):
  Authorization: Bearer {{ access_token }}

Outros headers com variáveis:
  X-Api-Key: {{ api_key }}
  X-Tenant-ID: {{ tenant_id }}
  X-User-ID: {{ user_id }}
  X-Api-Version: {{ api_version }}
  Accept-Language: {{ locale }}
```

### Body JSON — dados de teste variáveis

```
❌ Errado (valores hardcoded):
{
  "usuario_id": 42,
  "email": "joao@empresa.com",
  "token": "eyJhbGciOiJSUzI..."
}

✓ Correto (variáveis):
{
  "usuario_id": {{ user_id }},
  "email": "{{ test_email }}",
  "token": "{{ access_token }}"
}

Campos que ainda podem ser hardcoded no body (não mudam por contexto):
{
  "tipo": "fisico",           ← valor de enum sempre igual
  "status": "pendente",       ← estado inicial sempre igual
  "moeda": "BRL",             ← fixo para esta API
  "quantidade": {{ qty }}     ← se variar no teste, usar variável
}
```

### Query Parameters — filtros e paginação dinâmicos

```
❌ Errado:
  /produtos?page=1&limit=20&categoria=eletronicos

✓ Correto (parte como variável, parte como valor fixo do teste):
  /produtos?page={{ current_page }}&limit={{ page_size }}&categoria={{ test_category }}

Hybrid approach (aceitável):
  /produtos?page=1&limit={{ page_size }}&sort=nome
  → page=1 é o valor de início do teste (fixo faz sentido)
  → page_size varia por ambiente (deve ser variável)
  → sort=nome é critério fixo do teste (pode ser hardcoded)
```

## Padrão de nomenclatura de variáveis

```
Convenção recomendada (snake_case, descritivo):

URLs e endpoints:
  base_url          → URL base da API
  auth_url          → URL do servidor de autenticação
  cdn_url           → URL do CDN (para testes de assets)

Autenticação:
  access_token      → JWT ou Bearer token de acesso
  refresh_token     → Token para renovar o access_token
  api_key           → API Key do serviço
  client_id         → OAuth client ID
  client_secret     → OAuth client secret (Private Environment)

IDs de teste:
  user_id           → ID de um usuário de teste
  admin_user_id     → ID de um usuário admin de teste
  product_id        → ID de produto para testes CRUD
  order_id          → ID de pedido para testes
  category_id       → ID de categoria

Configurações:
  api_version       → versão da API (v1, v2)
  page_size         → limite de itens por página
  locale            → idioma/região (pt-BR, en-US)
  timeout_ms        → timeout em milissegundos
  debug             → flag de modo debug

Dados de teste:
  test_email        → email de um usuário de teste
  test_password     → senha de teste (Private Environment)
  test_name         → nome para testes de criação
  test_phone        → telefone para testes
```

## Verificando variáveis não resolvidas

O Insomnia destaca variáveis não encontradas — útil para detectar problemas de configuração antes de enviar:

```
Indicadores visuais:
  {{ base_url }}     → fundo verde claro = variável resolvida
  {{ base_url }}     → fundo laranja/vermelho = variável NÃO encontrada

Causas de variável não resolvida:
  1. Nenhum ambiente ativo selecionado
  2. O ambiente ativo não define essa variável
  3. Erro de digitação no nome da variável (case-sensitive!)
     {{ base_url }} ≠ {{ Base_url }} ≠ {{ BASE_URL }}

Verificar antes de enviar:
  Hover sobre a variável em laranja → tooltip mostra "undefined"
  Abrir o environment e verificar o nome exato da variável
```

## Erros comuns e armadilhas

**Misturar ambientes em uma mesma collection:** ter `base_url=https://api.empresa.com` hardcoded em metade dos requests e `{{ base_url }}` na outra metade. Resultado: ao trocar de ambiente, metade dos requests muda e metade não — confusão garantida. Padronizar 100% com variáveis.

**Variáveis com nomes genéricos demais:** `{{ url }}`, `{{ token }}`, `{{ id }}` — ao ter múltiplas collections abertas no Insomnia, fica difícil saber a qual recurso cada variável se refere. Usar nomes específicos: `{{ orders_api_url }}`, `{{ bearer_token }}`, `{{ target_user_id }}`.

**Deixar IDs de produção no environment compartilhado:** `"user_id": 12345` em um environment de produção compartilhado pode resultar em testes inadvertidos no usuário real número 12345 em produção. Usar `user_id: 0` como placeholder e cada desenvolvedor configura o seu próprio ID no Private Environment.

## 🧩 Quiz de Fixação

1. Um desenvolvedor recebe a seguinte URL em um request da collection: `https://api-staging.empresa.com/v1/usuarios?page=1&limit=10`. Identifique todos os valores que deveriam ser variáveis de ambiente e proponha os nomes das variáveis.

2. A variável `{{ access_token }}` está destacada em laranja/vermelho em um request. O ambiente "Dev" está selecionado. Quais são as três causas possíveis e como diagnosticar cada uma?

3. Um novo desenvolvedor entra no time e importa a collection. O ambiente "Dev" tem `"user_id": 1`. O dev roda `DELETE /usuarios/{{ user_id }}` sem perceber que está deletando o usuário de ID 1 em produção (porque selecionou o ambiente errado). Como estruturar os ambientes e a collection para prevenir esse tipo de acidente?

**Respostas:**

1) Valores que devem ser variáveis:
- `https://api-staging.empresa.com` → `{{ base_url }}` (muda por ambiente: dev, staging, prod)
- `v1` → `{{ api_version }}` (pode mudar para v2 no futuro)
- `page=1` → pode ficar hardcoded se sempre começa na página 1 para testes; ou `{{ start_page }}`
- `limit=10` → `{{ page_size }}` (staging pode usar 10, prod 20 ou 50)

URL com variáveis: `{{ base_url }}/{{ api_version }}/usuarios?page=1&limit={{ page_size }}`

2) **Causa 1 — Variável não definida no ambiente "Dev":** o environment "Dev" não tem a chave `access_token`. Diagnosticar: abrir `Ctrl+E` → selecionar "Dev" → verificar se `access_token` existe no JSON. Solução: adicionar a variável. **Causa 2 — Nenhum ambiente selecionado:** o seletor de ambiente mostra "Nenhum ambiente" mesmo parecendo estar no "Dev". Diagnosticar: verificar o seletor de ambiente no topo da collection. Solução: clicar e selecionar "Dev". **Causa 3 — Erro de digitação (case-sensitive):** o environment define `Access_Token` mas o request usa `{{ access_token }}`. O Insomnia é case-sensitive — nomes de variáveis devem ser idênticos. Diagnosticar: copiar exatamente o nome da variável do environment e comparar com o do request. Solução: padronizar o nome em ambos.

3) **Prevenção em camadas:** (a) **Naming claro dos ambientes:** nomear como "🔴 PRODUÇÃO - CUIDADO" em vez de apenas "Produção" — o emoji vermelho e o aviso visual ajudam a identificar o ambiente antes de enviar; (b) **IDs de segurança no ambiente de Produção:** definir `"user_id": 0` ou `"user_id": null` no ambiente de Produção compartilhado — ao executar `DELETE /usuarios/0`, a API retorna 404 (ID inválido) em vez de deletar algo real; (c) **Private Environment por desenvolvedor:** cada dev tem seus IDs de teste no Private Environment, não no ambiente compartilhado — assim nenhum ID fica "pré-configurado" para deletar; (d) **Scripts de verificação:** adicionar um Pre-request Script em operações destrutivas (DELETE, PUT em massa) que verifica se o ambiente de produção está ativo e solicita confirmação: `if (insomnia.environment.get('env_name') === 'production') throw new Error('⚠️ Você está em PRODUÇÃO! Confirme antes de continuar.');`
