### Mecânica dos Environments — Base Environment, sub-ambientes Dev/QA/Prod e troca com um clique

Environments (ambientes) são a solução do Insomnia para o problema do hardcode: em vez de escrever `https://api.empresa.com` diretamente na URL, você escreve `{{ base_url }}` — e o valor real fica em um arquivo JSON de configuração chamado Environment. Com um clique, você troca o ambiente e todos os requests da collection apontam para outro servidor sem modificar nada. É a base de qualquer workflow profissional de teste de API.

---

## O problema do hardcode

```
Sem Environments — o problema:

Request 1: GET https://api-dev.empresa.com/usuarios
Request 2: GET https://api-dev.empresa.com/produtos
Request 3: GET https://api-dev.empresa.com/pedidos

Para testar em staging: editar a URL de CADA request
Para testar em produção: editar novamente todas as URLs
Para voltar ao dev: editar mais uma vez

Com 50 requests na collection: 50 edições manuais
Chance de erro: alta (esquecer um request)
Tempo desperdiçado: enorme
```

```
Com Environments — a solução:

Request 1: GET {{ base_url }}/usuarios
Request 2: GET {{ base_url }}/produtos
Request 3: GET {{ base_url }}/pedidos

Mudar de dev para staging: trocar o environment no canto superior
→ 1 clique = todos os 50 requests apontam para o novo servidor
```

## Hierarquia de Environments

O Insomnia organiza os environments em dois níveis:

```
Base Environment (globais para toda a collection):
  {
    "timeout_ms": 30000,
    "api_version": "v2",
    "default_page_size": 20
  }
  → Variáveis partilhadas entre todos os sub-ambientes
  → Valores que não mudam por ambiente

Sub-ambientes (específicos de cada contexto):
  ┌─────────────────┐  ┌─────────────────┐  ┌─────────────────────────┐
  │ Dev             │  │ Staging / QA    │  │ Produção                │
  │ {               │  │ {               │  │ {                       │
  │  "base_url":    │  │  "base_url":    │  │  "base_url":            │
  │   "http://local"│  │   "https://qa..",│  │   "https://api.empresa" │
  │  "token": "...", │  │  "token": "...",│  │  "token": "{{ secret }}"│
  │  "debug": true  │  │  "debug": false │  │  "debug": false         │
  │ }               │  │ }               │  │ }                       │
  └─────────────────┘  └─────────────────┘  └─────────────────────────┘

Merging: sub-ambiente + Base Environment = conjunto final de variáveis
  → Sub-ambiente sobrescreve o Base Environment quando há conflito
  → Base Environment preenche as lacunas que o sub-ambiente não define
```

## Criando e gerenciando Environments

### Abrir o gerenciador de Environments

```
Atalho: Ctrl + E  (ou botão no canto superior esquerdo da collection)

Tela de gerenciamento:
  Base Environment    ← sempre presente, não pode ser deletado
  ├── Meu Dev
  ├── QA / Staging
  └── Produção
```

### Estrutura de um Environment — arquivo JSON

```json
// Base Environment
{
  "api_version": "v2",
  "page_size": 20,
  "timeout": 30000,
  "content_type": "application/json"
}

// Sub-ambiente: Dev
{
  "base_url": "http://localhost:3000",
  "auth_url": "http://localhost:8080/auth",
  "user_id": 1,
  "access_token": "eyJhbGciOiJIUzI1NiJ9.dev_token",
  "debug": true
}

// Sub-ambiente: QA / Staging
{
  "base_url": "https://api-qa.empresa.com",
  "auth_url": "https://auth-qa.empresa.com",
  "user_id": 42,
  "access_token": "eyJhbGciOiJIUzI1NiJ9.qa_token",
  "debug": false
}

// Sub-ambiente: Produção
{
  "base_url": "https://api.empresa.com",
  "auth_url": "https://auth.empresa.com",
  "user_id": 0,
  "access_token": "",
  "debug": false
}
```

## Usando variáveis nos requests

```
Com os environments configurados, os requests usam {{ variavel }}:

URL:
  {{ base_url }}/{{ api_version }}/usuarios/{{ user_id }}

  Dev:     → http://localhost:3000/v2/usuarios/1
  QA:      → https://api-qa.empresa.com/v2/usuarios/42
  Prod:    → https://api.empresa.com/v2/usuarios/0

Headers:
  Authorization: Bearer {{ access_token }}
  Content-Type: {{ content_type }}
  X-Debug-Mode: {{ debug }}

Body JSON:
  {
    "pagina": 1,
    "limite": {{ page_size }},
    "usuario_id": {{ user_id }}
  }
```

## Variáveis built-in do Insomnia

Além das variáveis do environment, o Insomnia tem variáveis globais pré-definidas:

```
{{ $timestamp }}
  → Unix timestamp atual em segundos
  → Ex: 1705312800
  → Uso: campos de "data_criacao" em testes, Cache-busting

{{ $isoTimestamp }}
  → ISO 8601 timestamp atual
  → Ex: 2024-01-15T10:00:00.000Z
  → Uso: campos de data em APIs que requerem ISO

{{ $randomInt }}
  → Número inteiro aleatório entre 1 e 1.000.000
  → Uso: IDs de teste aleatórios, dados únicos em testes

{{ $guid }}
  → UUID v4 aleatório
  → Ex: a1b2c3d4-e5f6-7890-abcd-ef1234567890
  → Uso: X-Request-ID, IDs únicos, chaves de idempotência

Exemplos combinados:
  POST /pedidos com body:
  {
    "referencia": "PEDIDO-{{ $randomInt }}",
    "data": "{{ $isoTimestamp }}",
    "idempotency_key": "{{ $guid }}"
  }
```

## Ambiente privado (Private Environment)

```
O Insomnia tem um conceito de "Private Environment" separado:

Environment normal:
  → Sincronizado com o Insomnia Cloud (se ativado)
  → Visível para membros do time (se usando sync)
  → Salvo no arquivo de export da collection

Private Environment:
  → Apenas local — nunca sai do seu computador
  → Não sincronizado, não exportado
  → Ideal para: tokens reais de produção, client_secrets, senhas
  → Valores sensíveis que não devem ser compartilhados

Workflow recomendado:
  Environment público (versionado/sincronizado):
    base_url: https://api.empresa.com
    client_id: app-abc123

  Private Environment (local apenas):
    access_token: eyJhbGciOiJSUzI1...  ← token real de prod
    client_secret: s3cr3t_pr0d          ← segredo real
```

## Trocar de ambiente — o clique único

```
No canto superior esquerdo da collection:
  [Nenhum ambiente ▼]
  
Ao clicar, aparece o menu:
  ○ Nenhum ambiente
  ● Dev                ← selecionado (com •)
  ○ QA / Staging
  ○ Produção

Um clique em "QA / Staging":
  → Todas as variáveis são substituídas pelos valores do QA
  → Todos os requests da collection apontam para o novo servidor
  → Nenhum request foi editado — apenas o ambiente mudou

Dica: você pode trocar o ambiente mesmo COM um request aberto
  → A URL e os valores são atualizados em tempo real
```

## Organização recomendada de variáveis

```
Boas práticas para estruturar environments:

1. Base Environment — apenas o que é universal:
   {
     "app_name": "Minha API",
     "api_version": "v2",
     "timeout_ms": 30000,
     "accept": "application/json"
   }

2. Sub-ambientes — apenas o que muda por contexto:
   Dev:     base_url, credenciais de dev, flags de debug
   Staging: base_url, credenciais de staging
   Prod:    base_url (sem credenciais hardcoded — usar Private)

3. Nomear variáveis consistentemente:
   base_url         → URL principal da API
   auth_url         → URL do servidor de autenticação
   user_id          → ID do usuário de teste
   access_token     → Token de acesso atual
   refresh_token    → Token de renovação
   client_id        → Client ID do OAuth
   client_secret    → (apenas no Private Environment)

4. Documentar no próprio JSON (não é suportado nativo, usar convenção):
   {
     "__comment_base_url": "URL da API sem trailing slash",
     "base_url": "https://api.empresa.com",
     "__comment_token": "Atualizar após login manual",
     "access_token": ""
   }
   (O Insomnia ignora chaves que começam com __ em alguns casos)
```

## Erros comuns e armadilhas

**Usar o ambiente errado em produção:** testar com o ambiente "Dev" apontando para uma URL de produção por engano. Nomear claramente os ambientes e verificar sempre o seletor antes de disparar requisições destrutivas (DELETE, PUT em massa).

**Variável undefined (sem valor no environment):** ao selecionar "Nenhum ambiente" ou esquecer de definir uma variável no sub-ambiente ativo, a URL fica com `{{ base_url }}` literal — e a requisição falha com URL inválida. O Insomnia geralmente destaca em laranja as variáveis não resolvidas.

**Tokens expirados hardcoded no environment:** access_tokens com expiração curta (1 hora) ficam inválidos enquanto o environment não é atualizado. Resolver com Request Chaining (arquivo 3.1.2.2) para renovar automaticamente, ou com o fluxo OAuth 2.0 nativo (arquivo 4.1.1.2).

## 🧩 Quiz de Fixação

1. Uma collection tem 30 requests. Em Dev, a URL base é `http://localhost:3000`. Em Produção, é `https://api.empresa.com`. Explique como configurar o Insomnia para que um único clique troque todos os 30 requests entre os dois ambientes sem editar nenhum request individualmente.

2. Um developer define no Base Environment `"debug": true` e no sub-ambiente "Produção" não menciona a variável `debug`. Qual valor a variável `debug` terá quando o ambiente "Produção" estiver ativo, e por quê?

3. Um time usa sync do Insomnia e compartilha a collection. O ambiente de Produção contém `"access_token": "eyJhbGciOiJSUzI1..."` (token real). Por que isso é um risco de segurança e qual é a solução correta?

**Respostas:**

1) Configuração: (a) abrir o gerenciador de Environments (`Ctrl+E`); (b) no Base Environment, deixar apenas variáveis universais; (c) criar sub-ambiente "Dev" com `"base_url": "http://localhost:3000"`; (d) criar sub-ambiente "Produção" com `"base_url": "https://api.empresa.com"`; (e) em todos os 30 requests, substituir a URL hardcoded pela variável: `{{ base_url }}/endpoint`. A partir daí: ao selecionar "Dev" no seletor, todos os requests apontam para localhost; ao selecionar "Produção", todos apontam para a API em produção. Zero edição de requests — apenas a troca do environment ativo.

2) A variável `debug` terá o valor `true` (do Base Environment). A lógica de merging do Insomnia é: as variáveis do sub-ambiente **sobrescrevem** as do Base Environment quando existem em ambos; quando o sub-ambiente **não define** uma variável, o valor do Base Environment é usado como fallback. Como "Produção" não define `debug`, o Insomnia usa o valor do Base Environment (`true`). Isso é geralmente indesejado — boas práticas recomendam que o sub-ambiente de Produção defina explicitamente `"debug": false` para sobrescrever o valor do Base, evitando que o modo debug acidental seja ativado em produção.

3) O risco é que qualquer membro do time com acesso à collection sincronizada recebe o token real de produção — incluindo pessoas que não deveriam ter acesso a produção (ex: estagiários, consultores externos, membros que saíram do time mas ainda têm acesso ao sync). Um token vazado pode ser usado para acessar dados reais de clientes. **Solução correta:** usar o **Private Environment** (ambiente privado local) para armazenar o `access_token` de produção. O Private Environment existe apenas no computador local, nunca é sincronizado para o cloud do Insomnia, não aparece em exports da collection, e não é visível para outros membros do time. O environment compartilhado de Produção deve ter `"access_token": ""` (vazio) — cada desenvolvedor preenche o token no seu próprio Private Environment após autenticar.
