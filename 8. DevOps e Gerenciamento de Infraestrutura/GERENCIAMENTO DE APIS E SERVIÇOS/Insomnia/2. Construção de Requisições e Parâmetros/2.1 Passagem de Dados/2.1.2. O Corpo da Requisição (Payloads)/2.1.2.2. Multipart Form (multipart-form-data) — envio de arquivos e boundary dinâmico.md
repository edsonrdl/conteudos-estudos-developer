### Multipart Form (multipart/form-data) — envio de arquivos e boundary dinâmico

`multipart/form-data` é o único formato HTTP que permite enviar **arquivos binários e campos de texto na mesma requisição**. É o formato gerado por formulários HTML com `<input type="file">` e é amplamente usado em APIs para upload de imagens, documentos, CSVs e outros arquivos. O Insomnia abstrai completamente a complexidade do boundary gerado — você simplesmente adiciona os campos e arquivos na interface visual.

---

## Como funciona o multipart/form-data

Por baixo dos panos, o body multipart é dividido em "partes" separadas por um delimitador aleatório chamado **boundary**. Cada parte contém seu próprio cabeçalho e conteúdo:

```
Content-Type: multipart/form-data; boundary=----WebKitFormBoundaryXYZ

------WebKitFormBoundaryXYZ
Content-Disposition: form-data; name="nome"

João Silva
------WebKitFormBoundaryXYZ
Content-Disposition: form-data; name="email"

joao@empresa.com
------WebKitFormBoundaryXYZ
Content-Disposition: form-data; name="foto"; filename="avatar.jpg"
Content-Type: image/jpeg

[bytes binários da imagem aqui]
------WebKitFormBoundaryXYZ--
```

```
O boundary é:
  → Gerado aleatoriamente pelo Insomnia a cada requisição
  → Incluído no header Content-Type automaticamente
  → Garante que o separador nunca aparece dentro do conteúdo do arquivo
  → Você nunca precisa configurar isso manualmente
```

## Configurando Multipart no Insomnia

```
1. Selecionar POST (ou PUT/PATCH)
2. Aba "Body" → dropdown → "Multipart Form"

Interface visual:
  ┌──────────────────────────────────────────────────┐
  │  Tipo      │ Nome      │ Valor / Arquivo          │
  ├────────────┼───────────┼──────────────────────────┤
  │ 📝 Text    │ nome      │ João Silva                │
  │ 📝 Text    │ email     │ {{ user_email }}          │
  │ 📁 File    │ foto      │ [Selecionar arquivo...]   │
  │ 📝 Text    │ descricao │ Foto de perfil            │
  └──────────────────────────────────────────────────┘

  + Add Name Value Pair   → adicionar campo de texto
  + Add File              → adicionar campo de arquivo
```

## Campos de texto (Text fields)

```
Para dados simples junto com o arquivo:

Nome    → Campo de texto
Email   → Campo de texto com variável: {{ user_email }}
Tipo    → Campo de texto com valor fixo: "perfil"

Exemplos de uso:
  → Metadados do arquivo (descrição, categoria, título)
  → IDs relacionados ao arquivo (usuario_id, pedido_id)
  → Configurações de processamento (resize: "true", formato: "webp")
  → Qualquer dado de contexto que acompanha o upload
```

---

## Campos de arquivo (File fields)

```
Para selecionar um arquivo do sistema:

1. Clicar em "+ Add File"
2. Definir o nome do campo (ex: "foto", "documento", "arquivo")
3. Clicar em "Choose File" → selecionar o arquivo no sistema

O Insomnia:
  → Lê o arquivo do disco
  → Detecta automaticamente o Content-Type (image/jpeg, application/pdf, etc.)
  → Inclui o filename no header da parte
  → Envia os bytes binários do arquivo

Múltiplos arquivos no mesmo request:
  → Adicionar múltiplas linhas File com nomes diferentes
  
  foto_frente   → [frente.jpg]
  foto_verso    → [verso.jpg]
  comprovante   → [comprovante.pdf]
```

## Casos de uso práticos

### Upload de avatar/foto de perfil

```
POST /usuarios/{{ user_id }}/foto

Body (Multipart):
  foto → [arquivo selecionado: avatar.jpg]
  tipo → "perfil"

Header gerado automaticamente:
  Content-Type: multipart/form-data; boundary=----InsomniaBoundaryABC123
```

### Upload de documento com metadados

```
POST /documentos

Body (Multipart):
  arquivo      → [contrato.pdf]
  titulo       → Contrato de Prestação de Serviços
  categoria    → juridico
  descricao    → Contrato assinado em {{ $timestamp }}
  usuario_id   → {{ user_id }}

Request resultante no Timeline:
  Content-Type: multipart/form-data; boundary=----InsomniaXYZ
  
  ------InsomniaXYZ
  Content-Disposition: form-data; name="arquivo"; filename="contrato.pdf"
  Content-Type: application/pdf
  
  [bytes do PDF]
  ------InsomniaXYZ
  Content-Disposition: form-data; name="titulo"
  
  Contrato de Prestação de Serviços
  ------InsomniaXYZ--
```

### Importação em lote via CSV

```
POST /produtos/importar

Body (Multipart):
  planilha    → [produtos.csv]
  sobrescrever → false
  notificar    → true

Servidor processa o CSV em background e retorna job_id para polling
```

### Upload de múltiplos arquivos de um formulário

```
POST /galeria/{{ album_id }}/fotos

Body (Multipart):
  fotos[]  → [foto1.jpg]   ← mesmo nome com [] = indica array no servidor
  fotos[]  → [foto2.jpg]
  fotos[]  → [foto3.jpg]
  titulo   → Férias 2024
  publica  → true
```

## Diferença entre Multipart e Form URL Encoded

```
Quando usar Multipart Form:
  ✓ Upload de arquivos (obrigatório)
  ✓ Misto de texto + arquivo na mesma requisição
  ✓ Campos com dados binários
  ✓ Formulários HTML com <input type="file">

Quando usar Form URL Encoded:
  ✓ Apenas campos de texto simples
  ✓ Fluxo OAuth 2.0 (troca de código por token — exige esse formato)
  ✓ Formulários HTML sem arquivos (legado)
  ✓ APIs que explicitamente requerem application/x-www-form-urlencoded

Por que Multipart não pode substituir Form URL Encoded em OAuth?
  O protocolo OAuth 2.0 especifica que a troca de tokens deve usar
  application/x-www-form-urlencoded — não multipart/form-data.
  Servidores de autorização rejeitam o formato errado.
```

## Inspecionando o request no Timeline

Após enviar uma requisição multipart, a aba **Timeline** mostra exatamente o que foi enviado:

```
POST /usuarios/42/foto HTTP/1.1
Host: api.empresa.com
Content-Type: multipart/form-data; boundary=----InsomniaXYZ123
Content-Length: 48291
Authorization: Bearer eyJ...

------InsomniaXYZ123
Content-Disposition: form-data; name="foto"; filename="avatar.jpg"
Content-Type: image/jpeg

[BINARY DATA - 47.8 KB]
------InsomniaXYZ123
Content-Disposition: form-data; name="tipo"

perfil
------InsomniaXYZ123--
```

```
Informações úteis no Timeline:
  → Content-Length mostra o tamanho total do request (texto + arquivo)
  → O boundary gerado pelo Insomnia aparece no Content-Type
  → [BINARY DATA] representa os bytes do arquivo (não exibidos como texto)
  → Cada parte separada claramente para verificação
```

## Erros comuns e armadilhas

**Usar JSON para enviar arquivos em base64:** algumas APIs antigas aceitam `{"arquivo": "base64string..."}` em JSON, mas isso aumenta o tamanho do payload em ~33% (base64 é menos eficiente que binário). Se a API aceitar multipart, sempre preferir multipart/form-data para arquivos.

**Arquivo não selecionado antes de enviar:** se você clica em Add File mas não seleciona um arquivo, o Insomnia pode enviar a parte vazia ou gerar erro. Verificar na aba Timeline se o campo de arquivo aparece com `filename` e Content-Type corretos.

**Nome do campo não corresponde ao esperado pelo servidor:** a API pode esperar `foto`, `image`, `file` ou `arquivo` — o nome deve ser exatamente o que a documentação ou o código do servidor define. Erro comum: usar `file` quando a API espera `foto`, resultando em campo null no servidor.

**Confundir multipart com o header manual `Content-Type: multipart/form-data`:** ao selecionar Multipart Form no dropdown do Insomnia, o `Content-Type` com boundary é gerado automaticamente. Se você tentar definir manualmente `Content-Type: multipart/form-data` no header sem o boundary, o servidor não consegue parsear — e você não tem como saber o boundary gerado pelo Insomnia para inserir manualmente. Nunca sobrescrever o Content-Type de requisições multipart.

## 🧩 Quiz de Fixação

1. Por que o boundary do multipart/form-data é gerado aleatoriamente a cada requisição, e o que aconteceria se o boundary fosse uma string fixa como `---SEPARATOR---`?

2. Um desenvolvedor tenta enviar uma imagem de 5 MB via body JSON usando base64: `{"imagem": "data:image/jpeg;base64,/9j/4AAQ..."}`. A API aceita. Qual é a desvantagem em relação ao multipart/form-data e em qual situação o base64 seria justificável?

3. Uma API de importação de planilhas espera um campo `arquivo` (CSV) e um campo `config` (JSON como string). Como configurar isso no Insomnia sabendo que o campo `config` deve ser o JSON serializado como texto?

**Respostas:**

1) O boundary é aleatório porque ele funciona como **delimitador de partes** — e precisa ser uma string que **não aparece no conteúdo** que está sendo enviado. Se o boundary fosse fixo (`---SEPARATOR---`) e um arquivo binário contivesse exatamente esses bytes em sequência (possível em qualquer arquivo suficientemente grande), o parser do servidor interpretaria incorretamente como o fim de uma parte no meio do arquivo — **corrompendo o upload**. Com boundary aleatório e longo (tipicamente 30-70 caracteres aleatórios), a probabilidade de colisão com o conteúdo do arquivo é astronomicamente baixa, tornando o parse seguro e confiável.

2) **Desvantagem:** a codificação base64 **aumenta o tamanho do payload em aproximadamente 33%** (cada 3 bytes binários viram 4 caracteres ASCII). Uma imagem de 5 MB em base64 vira ~6,67 MB — consumindo mais largura de banda, mais memória para serialização/desserialização e mais tempo de processamento no servidor. Com multipart/form-data, os bytes binários são enviados diretamente sem overhead. **Quando base64 é justificável:** quando a API já é JSON-only e não suporta multipart (ex: APIs que usam application/json para tudo), ou quando o arquivo é pequeno (< 50 KB — overhead insignificante), ou quando o arquivo é parte de um payload JSON maior com muitos outros campos de lógica de negócio que tornariam o multipart mais complexo.

3) Configuração no Insomnia: dois campos na aba Multipart Form: (a) **File field** com nome `arquivo` → selecionar o arquivo CSV; (b) **Text field** com nome `config` → valor: `{"formato":"csv","separador":";","encoding":"utf-8","ignorar_cabecalho":false}` — o JSON serializado como uma string de texto, sem quebras de linha. O servidor recebe `config` como uma string e faz o `JSON.parse()` internamente. **Alternativa mais limpa:** verificar se a API aceita `Content-Type: application/json` para o campo `config` adicionando manualmente o Content-Type àquela parte — mas isso é avançado e requer configuração manual do boundary, o que o Insomnia não expõe facilmente. Na maioria dos casos, enviar como texto (string JSON) funciona corretamente.
