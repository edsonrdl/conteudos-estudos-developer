### Form URL Encoded — formulários HTML e fluxo OAuth 2.0

`application/x-www-form-urlencoded` é o formato mais antigo de envio de dados em HTTP — é o padrão dos formulários HTML desde os anos 90. Os dados viajam no body da requisição no mesmo formato de uma query string: `chave1=valor1&chave2=valor2`, com os valores percent-encoded. No Insomnia, a aba "Form URL Encoded" oferece a mesma interface visual de campos que a aba Multipart, mas gera esse formato específico no body. É obrigatório no fluxo OAuth 2.0 e ainda presente em muitas integrações legadas.

---

## Como funciona o formato URL Encoded

```
Dados no body no formato de query string:

grant_type=authorization_code&code=abc123&redirect_uri=https%3A%2F%2Fapp.com%2Fcallback&client_id=meu_app

Diferença do multipart:
  multipart/form-data:
    → Cada campo em uma "parte" separada por boundary
    → Suporta arquivos binários
    → Header inclui o boundary

  application/x-www-form-urlencoded:
    → Todos os campos concatenados com & em uma única string
    → Apenas texto (sem arquivos)
    → Header é simplesmente: Content-Type: application/x-www-form-urlencoded

Header gerado pelo Insomnia:
  Content-Type: application/x-www-form-urlencoded
```

---

## Configurando no Insomnia

```
1. Selecionar POST (ou PUT/PATCH)
2. Aba "Body" → dropdown → "URL Encoded"

Interface visual (igual ao multipart, mas só Text):
  ┌──────────────────────────────────────────────┐
  │ ☑  grant_type     │ authorization_code       │
  │ ☑  code           │ {{ auth_code }}           │
  │ ☑  redirect_uri   │ {{ redirect_uri }}        │
  │ ☑  client_id      │ {{ client_id }}           │
  │ ☑  client_secret  │ {{ client_secret }}       │
  └──────────────────────────────────────────────┘

Body gerado e enviado:
  grant_type=authorization_code&code=abc123XYZ&redirect_uri=https%3A%2F%2Fapp.com%2Fcallback&client_id=meu_app&client_secret=s3cr3t

O Insomnia faz o URL encoding automático dos valores:
  https://app.com/callback  →  https%3A%2F%2Fapp.com%2Fcallback
  espaços  →  +  ou  %20
  &  →  %26  (quando faz parte do valor, não separador)
```

## O caso mais importante: OAuth 2.0 token exchange

O **RFC 6749** (OAuth 2.0) especifica que a troca de tokens **deve** usar `application/x-www-form-urlencoded`. É um dos poucos casos onde o formato do body não é negociável — usar JSON ou multipart resultará em erro no servidor de autorização.

### Fluxo Authorization Code — troca do código por token

```
Após o usuário autorizar, o servidor de auth redireciona com:
  https://app.com/callback?code=SplxlOBeZQQYbYS6WxSbIA&state=xyz

Agora você precisa trocar o "code" por um access_token:

POST https://auth.servidor.com/oauth/token

Body (URL Encoded — obrigatório!):
  ☑ grant_type    → authorization_code
  ☑ code          → SplxlOBeZQQYbYS6WxSbIA
  ☑ redirect_uri  → https://app.com/callback
  ☑ client_id     → meu_client_id
  ☑ client_secret → meu_client_secret

Resposta do servidor de auth:
{
  "access_token": "eyJhbGciOiJSUzI1NiJ9...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "8xLOxBtZp8"
}
```

### Fluxo Client Credentials — server-to-server

```
Para autenticação de máquina a máquina (sem usuário):

POST https://auth.servidor.com/oauth/token

Body (URL Encoded):
  ☑ grant_type    → client_credentials
  ☑ client_id     → {{ client_id }}
  ☑ client_secret → {{ client_secret }}
  ☑ scope         → read:dados write:dados

Header adicional (algumas implementações):
  Authorization: Basic base64(client_id:client_secret)
  (alguns servidores preferem as credenciais no header, não no body)

Resposta:
{
  "access_token": "...",
  "expires_in": 3600,
  "token_type": "Bearer"
}
```

### Fluxo Password (legado — evitar em novos sistemas)

```
POST https://auth.servidor.com/oauth/token

Body (URL Encoded):
  ☑ grant_type → password
  ☑ username   → {{ username }}
  ☑ password   → {{ password }}
  ☑ client_id  → {{ client_id }}
  ☑ scope      → openid profile email

Deprecado no OAuth 2.1 — use Authorization Code + PKCE
```

### Refresh Token — renovar access token expirado

```
POST https://auth.servidor.com/oauth/token

Body (URL Encoded):
  ☑ grant_type    → refresh_token
  ☑ refresh_token → {{ refresh_token }}
  ☑ client_id     → {{ client_id }}
  ☑ client_secret → {{ client_secret }}
```

  ☑ cliente_id   → {{ cliente_id }}

## URL Encoding — o que é codificado automaticamente

```
O Insomnia aplica percent-encoding nos valores:

Caractere   Encoded     Exemplo
──────────────────────────────────────────────────
Espaço      %20 ou +    "João Silva" → "Jo%C3%A3o+Silva"
/           %2F         "path/to" → "path%2Fto"
:           %3A         "https:" → "https%3A"
@           %40         "user@mail" → "user%40mail"
=           %3D         (dentro do valor, não separador)
&           %26         (dentro do valor, não separador)
+           %2B         ("literal plus" → "literal%2Bplus")
#           %23         "anchor#sec" → "anchor%23sec"
ç, ã, é     UTF-8 hex   "João" → "Jo%C3%A3o"

O Insomnia aplica isso automaticamente quando você usa a aba URL Encoded
→ Você digita o valor normal, ele encoda na hora de enviar
→ Verificar no Timeline para confirmar o encoding correto
```

## Comparativo: JSON vs Multipart vs URL Encoded

```
┌──────────────────────┬────────────────────┬───────────────────┬────────────────────┐
│ Critério             │ JSON               │ Multipart         │ URL Encoded        │
├──────────────────────┼────────────────────┼───────────────────┼────────────────────┤
│ Content-Type         │ application/json   │ multipart/form-.. │ application/x-www- │
│                      │                    │ data; boundary=.. │ form-urlencoded    │
│ Suporta arquivos     │ Base64 apenas      │ Sim (binário)     │ Não                │
│ Dados estruturados   │ Sim (aninhado)     │ Não               │ Não                │
│ Obrigado em OAuth    │ Não                │ Não               │ Sim                │
│ Legibilidade         │ Alta               │ Média             │ Baixa              │
│ Tamanho              │ Moderado           │ Maior (overhead)  │ Compacto           │
│ Uso principal        │ APIs REST modernas │ Upload arquivos   │ OAuth, formulários │
└──────────────────────┴────────────────────┴───────────────────┴────────────────────┘
```

## Erros comuns e armadilhas

**Usar JSON no body da troca de tokens OAuth:** o servidor de autorização retorna `unsupported_grant_type` ou `invalid_request`. O RFC 6749 é explícito: a requisição de token deve usar `application/x-www-form-urlencoded`. Sem exceção.

**Não encodar corretamente a `redirect_uri`:** a URI de redirecionamento contém `://` e `/` que precisam ser encoded. O Insomnia faz automaticamente pela aba URL Encoded, mas se você montar manualmente na URL como query param, pode esquecer de encodar. `redirect_uri=https://app.com/callback` (sem encoding) é inválido; correto: `redirect_uri=https%3A%2F%2Fapp.com%2Fcallback`.

**Expor client_secret no Insomnia sem usar variáveis:** collections compartilhadas com o time que contêm `client_secret` hardcoded no body expõem credenciais de produção. Sempre usar `{{ oauth_client_secret }}` com o valor real apenas no environment local (não versionado).

## 🧩 Quiz de Fixação

1. Por que o RFC 6749 (OAuth 2.0) especifica `application/x-www-form-urlencoded` em vez de JSON para a troca de tokens, mesmo sendo um protocolo moderno criado em 2012?

2. Um servidor de autorização OAuth retorna `"error": "invalid_client"` quando você tenta o fluxo Client Credentials. As credenciais estão corretas. Você verificou que está usando URL Encoded. Quais são as duas outras causas prováveis e como diagnosticar?

3. Um webhook de pagamento chega no seu servidor com este body: `status=aprovado&valor=299.90&pedido_id=P-789&hash=abc%3D%3D`. Como você monta no Insomnia uma requisição que simula esse webhook para testar seu endpoint, e o que o `abc%3D%3D` significa decodificado?

**Respostas:**

1) O OAuth 2.0 foi especificado com `application/x-www-form-urlencoded` principalmente por **compatibilidade e simplicidade de implementação** em 2012. Na época, nem todos os servidores (especialmente aqueles executando PHP, Java EE antigo e outros frameworks legados) tinham parsers JSON robustos integrados ao pipeline de autenticação, mas todos suportavam form-parsing nativamente. Além disso, `x-www-form-urlencoded` é mais simples para transmitir pares chave-valor simples (sem necessidade de parser JSON, sem problemas de encoding de strings). Outro motivo: o fluxo HTTP redirect (Authorization Code) já usa query strings no redirecionamento — manter o mesmo formato no token exchange mantém consistência. Hoje, muitos servidores de auth modernos também aceitam JSON como extensão, mas o padrão do RFC permanece form-urlencoded para compatibilidade universal.

2) **Causa 1 — Credenciais no lugar errado:** alguns servidores OAuth esperam o `client_id` e `client_secret` no header `Authorization: Basic base64(client_id:client_secret)` em vez de no body. Verificar a documentação: se a spec pede `Basic Auth`, remover essas credenciais do body e adicionar o header `Authorization: Basic [base64]`. **Causa 2 — `scope` inválido ou não autorizado:** o client está solicitando um scope para o qual não tem permissão no servidor de autorização. Testar sem o campo `scope` (omitir completamente) para verificar se o erro persiste — se resolver, o scope está incorreto ou o client não foi configurado para esse scope no painel admin do servidor de auth. **Diagnóstico:** verificar o campo `error_description` na resposta — geralmente contém informação mais específica do que apenas `invalid_client`.

3) **Montagem no Insomnia:** criar um POST para `http://localhost:3000/webhooks/pagamento` (ou a URL do seu endpoint), selecionar "URL Encoded" no body, e adicionar os campos: `status=aprovado`, `valor=299.90`, `pedido_id=P-789`, `hash=abc==`. O Insomnia se encarrega do re-encoding automaticamente ao enviar. **O que `abc%3D%3D` significa decodificado:** `%3D` é o encoding de `=` (sinal de igual). Portanto `abc%3D%3D` decodifica para `abc==`. Este padrão é comum em hashes que usam Base64 — Base64 usa `=` como padding no final, e ao incluir em uma URL encoded, os `=` são escaped para `%3D`. O valor real do hash é `abc==` (provavelmente um hash Base64 truncado para o exemplo).
