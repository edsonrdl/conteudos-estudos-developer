### Path Variables — inserção na URL e uso com variáveis dinâmicas

Path Variables (também chamadas de Path Parameters ou Route Parameters) são segmentos dinâmicos dentro do caminho da URL que identificam um recurso específico. Diferente dos Query Parameters que ficam após o `?`, os Path Variables fazem parte da estrutura hierárquica da URL. No Insomnia, eles são inseridos diretamente na URL e podem ser dinamizados com variáveis de ambiente ou Template Tags.

---

## O que são Path Variables e onde ficam na URL

```
Anatomia da URL com Path Variable:

https://api.empresa.com/usuarios/123/pedidos/456/itens
                                  │           │
                                  │           └─ ID do pedido (path variable)
                                  └─ ID do usuário (path variable)

Comparação com Query Parameter:
  Path Variable:   GET /usuarios/123          → "me dê o usuário 123"
  Query Parameter: GET /usuarios?id=123       → "filtre usuários por id=123"

  Path Variable: faz parte da identidade do recurso (REST correto)
  Query Parameter: modifica/filtra uma coleção
```

---

## Inserindo Path Variables no Insomnia

No Insomnia, path variables são digitados diretamente na barra de URL. Não há uma aba separada — o valor está na própria URL.

### Forma 1 — Valor fixo (hardcoded)

```
URL na barra de endereço:
  https://api.empresa.com/usuarios/123/pedidos/456

Simples, mas pouco flexível:
  → Para testar outro usuário, você edita a URL manualmente
  → Difícil de reutilizar com diferentes IDs
```

### Forma 2 — Variável de ambiente (recomendado)

```
Environment "Dev":
  user_id: 42
  order_id: 789

URL com variável:
  https://api.empresa.com/usuarios/{{ user_id }}/pedidos/{{ order_id }}

Benefícios:
  → Trocar o user_id no environment = funciona em todas as requisições que o usam
  → Ambientes diferentes (Dev/QA/Prod) podem ter user_ids diferentes para testes
  → Legível: a URL comunica a intenção, não apenas um número mágico
```

### Forma 3 — Template Tag (dinâmica, de outra resposta)

```
Cenário: você criou um usuário via POST e quer buscar o usuário criado via GET

POST /usuarios → retorna: {"id": 999, "nome": "Maria"}

GET /usuarios/{{ _.response.body.id }}
                  ↑
                  Template Tag apontando para a resposta do POST

O Insomnia extrai o ID da resposta anterior e insere automaticamente na URL
→ Nenhuma cópia manual necessária
→ Fluxo completamente automatizado
```

## Usando Template Tags para Path Variables dinâmicas

O `CTRL + Espaço` dentro da barra de URL abre o menu de Template Tags — o mesmo disponível em qualquer campo do Insomnia.

```
Exemplos de Template Tags úteis em Path Variables:

1. Valor de outra resposta (Response Tag):
   GET /produtos/{{ _.response.body.id }}
   → Extrai o "id" da última resposta do request "Criar Produto"

2. Variável do ambiente:
   GET /usuarios/{{ user_id }}
   → Usa a variável user_id do Environment ativo

3. Timestamp (para recursos com ID temporal):
   DELETE /logs/{{ $timestamp }}
   → Insere o Unix timestamp atual

4. UUID aleatório (para criar recursos com ID próprio):
   PUT /configuracoes/{{ $guid }}
   → Gera um UUID v4 único

5. Variável de ambiente com fallback:
   GET /pedidos/{{ order_id | default('1') }}
   → Usa order_id do ambiente; se vazio, usa '1'
```

## Padrões REST e seus Path Variables

```
Recursos aninhados:
  GET    /usuarios/:userId                    → buscar usuário
  GET    /usuarios/:userId/pedidos            → pedidos do usuário
  GET    /usuarios/:userId/pedidos/:orderId   → pedido específico do usuário
  POST   /usuarios/:userId/pedidos            → criar pedido para usuário
  DELETE /usuarios/:userId/pedidos/:orderId   → cancelar pedido específico

Ações sobre recursos (verbos como segmentos):
  POST   /pedidos/:id/cancelar               → cancelar pedido
  POST   /usuarios/:id/bloquear              → bloquear usuário
  POST   /faturas/:id/reenviar               → reenviar fatura

Recursos com identificadores compostos:
  GET    /paises/:pais/estados/:estado/cidades/:cidade
  GET    /repos/:owner/:repo/commits/:sha
```

## Workflow prático — CRUD completo de um recurso

```
Exemplo de collection bem organizada para CRUD de Produtos:

📁 Produtos
  │  Auth: Bearer {{ token }}
  │  Variables: product_id (no env)
  │
  ├── POST   /produtos
  │     Body: {"nome": "...", "preco": 0}
  │     → cria produto, anota o ID retornado
  │
  ├── GET    /produtos/{{ product_id }}
  │     → lê produto pelo ID
  │
  ├── PUT    /produtos/{{ product_id }}
  │     Body: {"nome": "...", "preco": 0}
  │     → atualiza produto completo
  │
  ├── PATCH  /produtos/{{ product_id }}
  │     Body: {"preco": 99.90}
  │     → atualiza apenas o preço
  │
  └── DELETE /produtos/{{ product_id }}
        → deleta produto

Fluxo de uso:
  1. POST /produtos → copia o ID retornado para product_id no environment
  2. Executa GET, PUT, PATCH, DELETE usando {{ product_id }}
  3. Para testar outro produto: só muda product_id no environment

Com Request Chaining (sem copiar manualmente):
  Configura Template Tag no GET apontando para a resposta do POST
  → O Insomnia captura o ID automaticamente do POST e usa no GET
```

## Comparativo completo — Path Variable vs Query Parameter

```
┌──────────────────────────┬─────────────────────────┬──────────────────────────┐
│ Aspecto                  │ Path Variable           │ Query Parameter          │
├──────────────────────────┼─────────────────────────┼──────────────────────────┤
│ Posição na URL           │ /recursos/123           │ /recursos?id=123         │
│ Semântica REST           │ Identifica o recurso    │ Filtra/modifica          │
│ Obrigatoriedade          │ Geralmente obrigatório  │ Geralmente opcional      │
│ Uso típico               │ ID de recurso           │ Paginação, filtros       │
│ Múltiplos valores        │ Não (1 por segmento)    │ Sim (?tag=a&tag=b)       │
│ Aba dedicada Insomnia    │ Não (inserido na URL)   │ Sim (aba Query)          │
│ Cacheabilidade HTTP      │ Cache por URL           │ Cache por URL + params   │
│ Legibilidade             │ Alta                    │ Média                    │
│ Bookmarkable             │ Sim                     │ Sim (com cuidado)        │
└──────────────────────────┴─────────────────────────┴──────────────────────────┘
```

## Erros comuns e armadilhas

**Usar Query Parameter para ID de recurso:** `GET /usuarios?id=123` é semanticamente incorreto em REST — o ID faz parte da identidade do recurso, não é um filtro. A URL correta é `GET /usuarios/123`. Além de semântica, impacta no caching e na clareza da API.

**Esquecer de atualizar a variável de ambiente após criar um recurso:** o fluxo mais comum de bug em testes manuais é: criar um produto (POST), esquecer de copiar o ID, e tentar fazer GET com o ID antigo no environment. Usar Request Chaining (Template Tag apontando para a resposta do POST) elimina completamente esse problema.

**Path Variable vs segmento de ação:** `DELETE /usuarios/bloquear/123` tem a semântica errada (parece que "bloquear" é um ID). O correto é `POST /usuarios/123/bloquear` — o path variable é sempre o identificador, e a ação é o segmento depois.

## 🧩 Quiz de Fixação

1. Um desenvolvedor está testando uma API de e-commerce. Ele precisa executar sequencialmente: criar um produto (POST), buscar o produto criado (GET), atualizar seu preço (PATCH) e depois deletá-lo (DELETE). Todos os endpoints usam `/produtos/:id`. Como configurar o Insomnia para que o ID do produto criado seja usado automaticamente nos três próximos requests, sem copiar manualmente?

2. Uma API retorna um erro `404 Not Found` para `GET /usuarios?id=123`. O desenvolvedor verifica que o endpoint correto é `GET /usuarios/123`. Qual é a diferença semântica entre as duas URLs do ponto de vista REST, e por que a API pode se comportar diferente?

3. A URL `GET /paises/BR/estados/SP/cidades` tem três path variables possíveis (pais, estado) e uma coleção (cidades). Como você estruturaria essa URL no Insomnia usando variáveis de ambiente para poder testar facilmente diferentes países e estados?

**Respostas:**

1) Usar **Request Chaining com Template Tag** na Response. Configuração: (a) no request GET `/produtos/{{ product_id }}`, em vez de usar uma variável de environment, usar uma Template Tag configurada como "Response → Body Attribute → $.id → POST /produtos" — isso extrai o campo `id` da resposta do POST; (b) copiar a mesma Template Tag para o PATCH e DELETE. Com isso: ao executar GET, Insomnia automaticamente dispara o POST se necessário, captura o `id` da resposta, e insere na URL. O mesmo acontece para PATCH e DELETE. **Alternativa mais simples:** configurar um After-response Script no POST que salva o ID no environment (`insomnia.environment.set('product_id', body.id)`) — então GET, PATCH e DELETE usam `{{ product_id }}` do environment, que é populado automaticamente após o POST.

2) **`GET /usuarios?id=123`** semânticamente é "liste usuários filtrando por id=123" — é uma query sobre a coleção. O servidor pode retornar um array `[{id:123,...}]` ou `[]` vazio, mas raramente retorna 404. **`GET /usuarios/123`** semânticamente é "me dê o recurso identificado como 123" — é um acesso direto a um recurso específico. O servidor retorna o objeto `{id:123,...}` se existir, ou `404 Not Found` se não existir. São endpoints completamente diferentes no roteamento do servidor (diferentes route handlers), por isso a API se comporta diferente. A primeira URL pode nem ter um handler no backend, causando o 404 por rota não encontrada, não por recurso inexistente.

3) Configurar no Environment: `pais: BR` e `estado: SP`. URL no Insomnia: `https://api.exemplo.com/paises/{{ pais }}/estados/{{ estado }}/cidades`. Para testar SP: environment com `pais=BR, estado=SP`. Para testar RJ: só muda `estado=RJ` no environment (URL não precisa ser editada). Para testar outro país: muda `pais=AR, estado=BA` (Buenos Aires). Se precisar testar múltiplas combinações, criar sub-ambientes: "BR-SP", "BR-RJ", "AR-BA" — cada um com seus próprios valores de `pais` e `estado`. Com um clique no seletor de ambiente, toda a collection de requests aponta para a combinação correta.
