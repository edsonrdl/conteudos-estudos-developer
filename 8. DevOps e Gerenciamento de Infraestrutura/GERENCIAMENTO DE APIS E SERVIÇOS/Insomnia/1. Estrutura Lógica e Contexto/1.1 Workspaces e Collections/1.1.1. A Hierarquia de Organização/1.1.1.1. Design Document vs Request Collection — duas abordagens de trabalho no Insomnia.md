### Design Document vs Request Collection — as duas abordagens de trabalho no Insomnia

O Insomnia organiza o trabalho em torno de dois tipos principais de projeto dentro de um Workspace: a **Request Collection** e o **Design Document**. Escolher entre os dois não é apenas preferência visual — é uma decisão sobre qual fase do ciclo de desenvolvimento você está: construindo e explorando uma API (Collection) ou projetando o contrato dela antes de escrever uma linha de código (Design Document).

---

## Request Collection — debug e exploração

A **Request Collection** é a abordagem clássica e mais usada do dia a dia. É organizada como uma árvore de pastas onde você cria, organiza e dispara requisições HTTP, gRPC, GraphQL e WebSocket.

```
Request Collection — estrutura típica:

📁 API de Pedidos (Collection)
  │
  ├── 📁 Autenticação
  │     ├── POST /auth/login
  │     └── POST /auth/refresh
  │
  ├── 📁 Clientes
  │     ├── GET /clientes
  │     ├── GET /clientes/:id
  │     ├── POST /clientes
  │     └── DELETE /clientes/:id
  │
  └── 📁 Pedidos
        ├── GET /pedidos?status=pendente
        ├── POST /pedidos
        └── PATCH /pedidos/:id/status
```

### Quando usar Request Collection

```
✓ Testar e debugar uma API já existente
✓ Explorar endpoints de terceiros (APIs externas, microserviços do time)
✓ Fluxos de QA e validação de comportamento
✓ Onboarding de novos desenvolvedores ("execute essa collection para ver a API funcionar")
✓ Quando a API já tem um contrato definido e você só precisa consumi-la
✓ Uso diário, cotidiano — é o tipo mais rápido de criar e usar
```

---

## Design Document — API-First com OpenAPI

O **Design Document** parte de uma filosofia diferente: você **define o contrato da API primeiro** (em especificação OpenAPI/Swagger, escrita em YAML ou JSON) e o Insomnia gera automaticamente a interface de testes a partir dessa especificação.

```
Design Document — fluxo:

1. Você escreve a especificação OpenAPI no editor YAML:
   ──────────────────────────────────────────────────
   openapi: "3.0.0"
   info:
     title: "API de Pedidos"
     version: "1.0.0"
   paths:
     /pedidos:
       post:
         summary: "Criar pedido"
         requestBody:
           content:
             application/json:
               schema:
                 $ref: '#/components/schemas/NovoPedido'
         responses:
           201:
             description: "Pedido criado"
   ──────────────────────────────────────────────────

2. O Insomnia lê a especificação e gera automaticamente:
   → Todas as rotas como requisições testáveis
   → Documentação interativa ao lado
   → Validação de payload contra o schema
   → Exemplos de request/response baseados nos schemas

3. Você testa diretamente sobre a spec — sem duplicar trabalho
```

### Quando usar Design Document

```
✓ Desenvolvimento de uma nova API do zero (API-First)
✓ Times que precisam de contrato formal antes de codar (frontend + backend em paralelo)
✓ Documentação que precisa estar sempre sincronizada com os testes
✓ Projetos que exportarão a spec para o Swagger UI ou Redoc
✓ Quando você quer validar o design da API antes de implementá-la
✓ Geração automática de SDKs ou documentação pública
```

## Comparativo direto

```
┌──────────────────────────────┬────────────────────────────┬─────────────────────────────┐
│ Aspecto                      │ Request Collection         │ Design Document              │
├──────────────────────────────┼────────────────────────────┼─────────────────────────────┤
│ Ponto de partida             │ Request vazia              │ Especificação OpenAPI (YAML) │
│ Filosofia                    │ Test-first / Debug         │ Design-first / Contract      │
│ Geração de requests          │ Manual (você cria)         │ Automática (da spec)         │
│ Documentação                 │ Não inclusa                │ Gerada automaticamente       │
│ Validação de payload         │ Não                        │ Sim (contra o schema)        │
│ Curva de entrada             │ Mínima                     │ Requer conhecimento OpenAPI  │
│ Uso mais comum               │ Diário / QA / Debug        │ Greenfield / API pública     │
│ Portabilidade                │ Formato Insomnia (.json)   │ OpenAPI exportável           │
└──────────────────────────────┴────────────────────────────┴─────────────────────────────┘
```

## Estrutura de Workspace — onde tudo começa

Antes de Collections e Design Documents, existe o **Workspace** — o contêiner pai que agrupa projetos relacionados.

```
Insomnia
└── Workspace "Empresa XYZ"
      ├── Request Collection "API de Produção"
      ├── Request Collection "API de Pagamentos"
      ├── Design Document "Nova API de Notificações (v2)"
      └── Design Document "API de Relatórios (em design)"

Boas práticas:
  → 1 Workspace por contexto (empresa, projeto, cliente)
  → Collections separadas por API/microserviço (não tudo numa collection gigante)
  → Design Documents para novas APIs; Collections para APIs existentes
  → Não misturar ambientes de prod e dev na mesma collection sem variáveis de ambiente
```

## Importando e exportando

```bash
# Exportar Collection para compartilhar com o time
# File → Export Data → Current Workspace → Export

# Formatos de importação suportados:
  → Insomnia JSON/YAML (formato nativo)
  → OpenAPI 2.0 / 3.0 (Swagger) → cria Design Document
  → Postman Collection v2.0/v2.1 → converte para Insomnia Collection
  → HAR (HTTP Archive) → importa requests de logs de browser
  → cURL commands → converte para requests

# Importar via CLI (Inso CLI):
inso import spec openapi.yaml --workspaceId wrksp_abc123
```

## Erros comuns e armadilhas

**Criar uma única Collection gigante para tudo:** uma collection com 200+ requests sem organização em pastas torna-se impossível de navegar. Separar por módulo/recurso em pastas hierárquicas.

**Usar Design Document para debug de API legada:** se a API não tem especificação OpenAPI e você só quer testar, a Request Collection é muito mais rápida. Criar um Design Document do zero para uma API existente sem spec é trabalho desnecessário.

**Não versionar as Collections:** assim como código, Collections devem estar no Git. Exportar periodicamente (ou usar o plugin de sincronização com Git do Insomnia) para não perder configurações acumuladas.

## 🧩 Quiz de Fixação

1. Um time de backend e frontend vai desenvolver uma nova API de notificações em paralelo. O backend ainda não escreveu nenhum código. Qual tipo de projeto Insomnia usar e qual é a vantagem para o frontend trabalhar em paralelo?

2. Um desenvolvedor recebeu um link para documentação Swagger (OpenAPI) de uma API de pagamentos de terceiro. Ele precisa explorar e testar os endpoints. Qual é a forma mais eficiente de configurar o Insomnia para isso?

3. Uma Request Collection tem 50 requests em uma única pasta sem hierarquia. Por que isso é problemático e como reorganizar?

**Respostas:**

1) Usar **Design Document**. O time escreve a especificação OpenAPI primeiro, definindo contratos de request/response para todos os endpoints antes de implementar. O **benefício para o frontend:** pode trabalhar em paralelo usando o Design Document como "mock" do comportamento esperado — sabe exatamente quais campos retornar, quais enviar e quais status codes esperar. O Insomnia gera a interface de testes automaticamente a partir da spec, e o frontend pode usar ferramentas como Prism ou WireMock para mockar a API baseado no mesmo YAML. Ambos os times trabalham com o mesmo contrato como fonte da verdade.

2) A forma mais eficiente é **importar a especificação OpenAPI** via `File → Import → From URL` (ou colando a URL/arquivo). O Insomnia cria automaticamente um **Design Document** com todos os endpoints já como requests testáveis, documentação interativa ao lado e schemas dos payloads. Em segundos, o desenvolvedor tem todos os 50+ endpoints prontos para testar sem criar nada manualmente.

3) O problema é **navegabilidade e manutenibilidade**: 50 requests em lista plana tornam impossível encontrar rapidamente o que se precisa. Ao abrir o Insomnia, o desenvolvedor precisa rolar por toda a lista para encontrar o endpoint correto. **Reorganização:** criar uma hierarquia de pastas por **recurso/módulo** da API — ex: `📁 Autenticação (3)`, `📁 Usuários (8)`, `📁 Pedidos (12)`, `📁 Pagamentos (7)`, `📁 Relatórios (5)`. Além da navegação, pastas têm a vantagem de **herdar autenticação e variáveis** — ao configurar o Bearer Token na pasta `Pedidos`, todos os 12 requests internos herdam automaticamente, eliminando duplicação.
