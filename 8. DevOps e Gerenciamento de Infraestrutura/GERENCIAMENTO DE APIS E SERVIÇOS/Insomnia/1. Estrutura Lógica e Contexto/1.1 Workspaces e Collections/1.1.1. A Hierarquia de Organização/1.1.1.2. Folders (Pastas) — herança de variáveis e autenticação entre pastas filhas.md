### Folders (Pastas) — herança de variáveis e autenticação entre requisições filhas

As pastas no Insomnia são muito mais do que organizadores visuais. Elas formam uma hierarquia de herança: tudo que é configurado em uma pasta — autenticação, headers, scripts — é herdado automaticamente por todas as requisições e subpastas dentro dela. Esse mecanismo elimina a duplicação de configuração e garante consistência em toda a collection.

---

## Pastas como unidade de configuração

Sem pastas, cada requisição precisaria ter sua própria configuração de autenticação, headers e scripts. Com pastas, você configura uma vez e herda em cascata:

```
📁 API de Pedidos (Collection)
  │
  ├── 📁 Autenticação              ← sem auth configurada (não precisa)
  │     ├── POST /auth/login       ← sem auth (rota pública)
  │     └── POST /auth/refresh     ← sem auth (rota pública)
  │
  ├── 📁 Módulo Clientes           ← Auth: Bearer Token {{ access_token }}
  │     ├── GET /clientes          ← herda Bearer Token automaticamente
  │     ├── POST /clientes         ← herda Bearer Token automaticamente
  │     └── DELETE /clientes/:id   ← herda Bearer Token automaticamente
  │
  └── 📁 Módulo Admin              ← Auth: Bearer Token {{ admin_token }}
        ├── GET /admin/usuarios    ← herda admin_token automaticamente
        └── DELETE /admin/purge    ← herda admin_token automaticamente
```

**Resultado:** você configura o token uma vez na pasta — e se o esquema de autenticação mudar (ex: de Bearer para API Key), basta atualizar a pasta, não cada requisição individualmente.

## O que pode ser configurado a nível de pasta

### 1. Autenticação (Auth)

```
Configurar na pasta:
  → Aba "Auth" na pasta
  → Escolher o tipo: Bearer Token, Basic, OAuth 2.0, API Key, etc.
  → Usar variável dinâmica: {{ access_token }}

Herança:
  Pasta "Módulo Clientes" com Bearer {{ access_token }}
  ↳ GET /clientes       → Authorization: Bearer eyJ...
  ↳ POST /clientes      → Authorization: Bearer eyJ...
  ↳ PUT /clientes/:id   → Authorization: Bearer eyJ...

Sobrescrita individual:
  Se uma requisição específica precisar de auth diferente,
  configure na própria requisição — ela sobrescreve a da pasta.
  
  Ex: POST /clientes/import precisa de um token de serviço especial
  → configure Auth diretamente nessa requisição
  → as outras continuam usando o token da pasta
```

### 2. Headers customizados

```
Configurar na pasta:
  → Aba "Headers" na pasta
  → Adicionar headers comuns a todas as requisições

Exemplos úteis:
  X-Api-Version: v2
  X-Tenant-ID: {{ tenant_id }}
  X-Request-ID: {{ $guid }}        ← variável built-in: gera UUID único
  Accept: application/json
  Accept-Language: pt-BR

Herança em cascata:
  Pasta raiz com Accept-Language: pt-BR
  ↳ Todas as requisições enviam o header automaticamente
  ↳ Sub-pasta com Accept-Language: en-US sobrescreve apenas para ela
```

### 3. Scripts de pré-requisição e pós-resposta

```
Configurar na pasta:
  → Aba "Scripts" na pasta
  → Pre-request Script: executa antes de cada requisição da pasta
  → After-response Script: executa após cada resposta

Exemplo — verificar token antes de qualquer requisição:
  // Pre-request Script na pasta "Módulo Clientes"
  const tokenExpiry = insomnia.environment.get('token_expiry');
  const now = Date.now() / 1000;
  
  if (!tokenExpiry || now > tokenExpiry - 60) {
    // Token expirado ou faltam menos de 60s: renovar
    const response = await insomnia.send('req_login');
    const body = JSON.parse(response.body);
    insomnia.environment.set('access_token', body.access_token);
    insomnia.environment.set('token_expiry', body.expires_at);
  }
```

## Hierarquia de herança — como funciona na prática

```
Hierarquia com múltiplos níveis:

📁 API Principal
  │  Auth: Bearer {{ token }}
  │  Header: X-Api-Version: v2
  │
  ├── 📁 Módulo Público     ← Override: sem auth (Inherit = false)
  │     └── GET /health      ← sem auth, sem X-Api-Version
  │
  └── 📁 Módulo Privado     ← herda: Bearer {{ token }}, X-Api-Version
        │
        ├── GET /usuarios    ← herda tudo da API Principal
        │
        └── 📁 Sub-módulo Admin  ← herda + adiciona: X-Admin-Key: {{ admin_key }}
              └── DELETE /purge   ← tem: Bearer + X-Api-Version + X-Admin-Key

Regras de herança:
  → Configurações se acumulam descendo na hierarquia
  → Configuração mais específica (mais próxima da requisição) sobrescreve a mais geral
  → "No Override" ou "Inherit" = use o que veio da pasta pai
  → Configuração direta na requisição = máxima prioridade
```

## Organização recomendada — padrões práticos

### Por módulo/recurso (mais comum em REST)

```
📁 Minha API
  ├── 📁 🔐 Auth           → sem auth (endpoints públicos)
  ├── 📁 👤 Usuários       → Bearer Token
  ├── 📁 📦 Produtos       → Bearer Token
  ├── 📁 🛒 Pedidos        → Bearer Token
  └── 📁 ⚙️ Admin          → Bearer Token + Header X-Admin: true
```

### Por ambiente (útil para smoke tests)

```
📁 Minha API
  ├── 📁 🟢 Health Checks    → sem auth, GET apenas
  ├── 📁 🧪 Fluxo de Compra  → Bearer, sequência ordenada
  └── 📁 🔴 Casos de Erro    → sem auth, esperando 4xx/5xx
```

### Por fluxo de negócio (útil para QA)

```
📁 E-commerce API
  ├── 📁 Fluxo 1: Cadastro de Cliente
  │     ├── 1. POST /usuarios (criar)
  │     ├── 2. POST /auth/login (autenticar)
  │     └── 3. GET /usuarios/me (verificar)
  │
  └── 📁 Fluxo 2: Compra Completa
        ├── 1. POST /auth/login
        ├── 2. GET /produtos?q=notebook
        ├── 3. POST /carrinho/itens
        └── 4. POST /pedidos/checkout
```

## Erros comuns e armadilhas

**Configurar autenticação em cada requisição individualmente:** ao criar uma nova requisição, o Insomnia não herda nada por padrão — você precisa ter a pasta corretamente configurada E a requisição dentro da pasta. Se você criar a requisição fora da pasta e depois mover, a herança é aplicada automaticamente.

**Esquecer que a ordem das pastas importa para fluxos sequenciais:** se você usa pastas para organizar fluxos de teste que dependem de ordem (Login → Criar pedido → Verificar pedido), manter as requisições numeradas e em sequência visual ajuda o analista a executar na ordem correta.

**Sobrescrever sem querer:** se você configura um header na pasta e também na requisição com o mesmo nome mas valor diferente, a requisição vence. Pode causar comportamento inesperado se não for intencional. Auditar os headers efetivamente enviados pelo painel "Timeline" após enviar a requisição.

## 🧩 Quiz de Fixação

1. Uma collection tem 30 requisições que precisam do header `Authorization: Bearer {{ token }}`. Qual é a forma correta de configurar isso no Insomnia para evitar 30 configurações duplicadas, e como tratar a exceção de 2 requisições que são endpoints públicos (sem auth)?

2. Uma pasta está configurada com `X-Api-Version: v1`. Uma sub-pasta filha precisa usar `X-Api-Version: v2`. Uma requisição específica dentro dessa sub-pasta precisa de `X-Api-Version: v3`. Quais configurações você faria e qual valor será enviado por cada requisição?

3. Um analista de QA quer garantir que todo request de uma pasta específica sempre inclua um UUID único no header `X-Request-ID` para rastreamento. Como implementar isso no Insomnia sem precisar gerar e colar o UUID manualmente em cada requisição?

**Respostas:**

1) **Configuração correta:** criar uma pasta pai (ex: "API Autenticada") com `Auth: Bearer {{ token }}` configurado. Colocar as 28 requisições autenticadas dentro dessa pasta — elas herdam o token automaticamente. Para as 2 requisições públicas: criar uma pasta separada (ex: "Endpoints Públicos") **sem configuração de auth**, ou mover as 2 requisições para fora da pasta autenticada. Alternativa: colocar as 2 requisições dentro da pasta autenticada mas configurar individualmente com `Auth: No Auth` — isso sobrescreve a configuração da pasta para essas requisições específicas.

2) Configurações: (a) **Pasta pai:** `X-Api-Version: v1`; (b) **Sub-pasta filha:** `X-Api-Version: v2` (sobrescreve v1 para todas as requisições dessa sub-pasta); (c) **Requisição específica:** `X-Api-Version: v3` (sobrescreve v2 apenas para essa requisição). Valores enviados: requisições na pasta pai (fora da sub-pasta) enviam `v1`; requisições dentro da sub-pasta (exceto a específica) enviam `v2`; a requisição específica envia `v3`. A regra é: configuração mais próxima da requisição sempre vence.

3) Usar a **variável built-in `{{ $guid }}`** do Insomnia no header da pasta. Configurar na aba "Headers" da pasta: `X-Request-ID: {{ $guid }}`. O Insomnia gera um novo UUID v4 a cada envio automaticamente — sem intervenção manual, sem duplicação de configuração. O UUID é único por requisição (não o mesmo para todas as requisições da pasta na mesma execução). Para ver o UUID efetivamente enviado, verificar a aba "Timeline" da resposta, que mostra os headers exatos da requisição.
