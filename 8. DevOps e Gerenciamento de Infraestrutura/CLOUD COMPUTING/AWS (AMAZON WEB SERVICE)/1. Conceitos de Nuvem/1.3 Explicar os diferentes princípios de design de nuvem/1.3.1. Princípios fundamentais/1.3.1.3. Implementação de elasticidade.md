### Implementação de elasticidade — escalar automaticamente com a demanda real

Elasticidade é o princípio de provisionar exatamente os recursos necessários para a carga atual — nem mais, nem menos — de forma automática e contínua. Na prática, isso significa que seu sistema cresce quando a demanda aumenta e encolhe quando diminui, sem intervenção humana. Este documento cobre como implementar elasticidade de forma concreta nos principais serviços AWS, escolhendo a estratégia de scaling correta para cada padrão de carga.

---

## Os quatro tipos de Auto Scaling na AWS

Antes de escolher a estratégia, é importante distinguir os diferentes tipos de Auto Scaling disponíveis:

```
1. EC2 Auto Scaling (Auto Scaling Groups — ASG)
   → Escala instâncias EC2 adicionando ou removendo VMs

2. Application Auto Scaling
   → Escala recursos além do EC2:
   ├── ECS tasks (contêineres)
   ├── DynamoDB read/write capacity
   ├── Aurora replicas
   ├── Lambda provisioned concurrency
   └── SageMaker endpoints

3. AWS Auto Scaling (console unificado)
   → Interface única que gerencia EC2 ASG + Application Auto Scaling
   → Recomendações automáticas de scaling

4. Serviços nativamente elásticos (sem configuração):
   ├── Lambda: escala automaticamente, sem configuração
   ├── DynamoDB on-demand: escala automaticamente
   ├── S3: infinitamente elástico por design
   └── SQS: escala automaticamente
```

## Estratégia 1: Target Tracking Scaling

### O que é e quando usar

```
Target Tracking é a estratégia mais simples e recomendada
para a maioria dos casos:

Princípio: defina uma métrica-alvo → AWS mantém automaticamente

Analogia: termostato de ar-condicionado
  "Mantenha a temperatura em 22°C"
  → AC liga quando sobe → desliga quando chega a 22°C
  → Você não programa "ligue às 14h" ou "desligue às 16h"
  → Define o objetivo, não as ações

Na AWS:
  "Mantenha CPU média em 60%"
  → ASG adiciona instâncias quando CPU > 60%
  → ASG remove instâncias quando CPU < 60%
  → Você define o target, AWS calcula quando e quanto escalar
```

### Configuração para EC2 Auto Scaling Group

```
Configuração via Console / Terraform:

resource "aws_autoscaling_policy" "target_tracking" {
  name                   = "cpu-target-tracking"
  autoscaling_group_name = aws_autoscaling_group.app.name
  policy_type            = "TargetTrackingScaling"

  target_tracking_configuration {
    predefined_metric_specification {
      predefined_metric_type = "ASGAverageCPUUtilization"
    }
    target_value = 60.0  # mantenha CPU em 60%
    
    # Cooldown: aguarda antes de outro scale out/in
    # (evita flapping — escalar demais de uma vez)
    disable_scale_in = false
  }
}

# Limites do ASG
resource "aws_autoscaling_group" "app" {
  min_size         = 2   # nunca menos que 2 (HA)
  desired_capacity = 4   # ponto de partida
  max_size         = 20  # nunca mais que 20 (controle de custo)
}
```

### Métricas predefinidas para Target Tracking

```
Para EC2 Auto Scaling Groups:
  ├── ASGAverageCPUUtilization   ← mais comum
  ├── ASGAverageNetworkIn        ← para workloads de rede intensiva
  ├── ASGAverageNetworkOut
  └── ALBRequestCountPerTarget   ← ideal para apps web (req/instância)

Para Application Auto Scaling (ECS, DynamoDB, etc.):
  ├── ECSServiceAverageCPUUtilization
  ├── ECSServiceAverageMemoryUtilization
  ├── DynamoDBReadCapacityUtilization
  └── RDSReaderAverageCPUUtilization

Custom metrics (via CloudWatch):
  ├── Profundidade de fila SQS por worker
  ├── Tempo médio de resposta da aplicação
  └── Qualquer métrica de negócio publicada no CloudWatch
```

### Target Tracking com ALBRequestCountPerTarget

```
Para aplicações web, requisições por instância é melhor que CPU:

Cenário: você sabe que cada instância lida bem com 1.000 req/min
         mas degrada acima disso

Configuração:
  Target: ALBRequestCountPerTarget = 1.000
  → Se cada instância receber mais de 1.000 req/min: adiciona
  → Se cada instância receber menos de 700 req/min: remove

Vantagem sobre CPU:
  → CPU varia por tipo de requisição (algumas CPU-intensivas, outras não)
  → req/instância é diretamente ligado à experiência do usuário
  → Escala baseado em throughput real, não em indicador indireto
```

## Estratégia 2: Step Scaling

### O que é e quando usar

```
Step Scaling define ações diferentes para diferentes
magnitudes de desvio da métrica:

"Não é só escalar — é escalar proporcionalmente ao problema"

Cenário: CPU como métrica
  
  [0-60%]    → não fazer nada (dentro do normal)
  [60-70%]   → adicionar 1 instância
  [70-80%]   → adicionar 2 instâncias
  [80-90%]   → adicionar 4 instâncias
  [>90%]     → adicionar 8 instâncias

Analogia: controle de velocidade de um barco
  Pequena aceleração → pequena correção
  Grande aceleração  → grande correção
  
  Diferente do Target Tracking que calcula automaticamente.
  Step Scaling você define explicitamente os patamares.

Quando usar Step Scaling em vez de Target Tracking:
  ├── Quando precisa de controle fino sobre a resposta
  ├── Quando o padrão de carga é não-linear
  ├── Quando há custo de startup elevado por instância
  │   (evita escalar muito de uma vez)
  └── Quando métricas customizadas têm comportamentos específicos
```

### Configuração de Step Scaling

```
CloudWatch Alarm → notifica o ASG → ASG executa a step policy

Alarm: CPUHigh
  Threshold: CPU > 70% por 2 períodos de 60s

Step Scaling Policy: ScaleOut
  Ajustes:
  ├── CPU 70-80%:  +1 instância (ChangeInCapacity: 1)
  ├── CPU 80-90%:  +3 instâncias
  └── CPU > 90%:   +5 instâncias

Alarm: CPULow
  Threshold: CPU < 30% por 5 períodos de 60s

Step Scaling Policy: ScaleIn
  Ajustes:
  └── CPU < 30%: -1 instância por vez (proteção conservadora)

Cooldown period:
  Scale Out: 60 segundos (aguarda instância ficar healthy)
  Scale In: 300 segundos (mais conservador, evita remover demais)
```

## Estratégia 3: Scheduled Scaling

### O que é e quando usar

```
Scheduled Scaling programa mudanças de capacidade
em horários específicos baseados em padrões conhecidos:

"Eu sei que às 9h de segunda-feira sempre tenho pico"
→ Posso pré-provisionar ANTES do pico chegar

Problema do Target Tracking para picos previsíveis:
  8h55: CPU começa a subir (usuários logando)
  9h00: pico de acessos
  9h05: Target Tracking detecta CPU alta → começa a adicionar
  9h06: novas instâncias ficam healthy
  → 6 minutos de degradação para usuários

Com Scheduled Scaling:
  8h30: capacidade aumenta para 10 instâncias (schedule)
  9h00: pico chega → instâncias já estão prontas
  → Zero degradação
```

### Configuração de Scheduled Scaling

```
Exemplos de schedules úteis:

Segunda a Sexta, 8h30 (antes do horário comercial):
  MinSize: 5 → 10
  DesiredCapacity: 8 → 15
  MaxSize: 20 → 40

Segunda a Sexta, 20h (após horário comercial):
  MinSize: 10 → 2
  DesiredCapacity: 15 → 4
  MaxSize: 40 → 10

Sábado e Domingo (baixo tráfego):
  MinSize: 2
  DesiredCapacity: 2
  MaxSize: 5

Black Friday (evento especial):
  Data específica: 2024-11-29 00:00 UTC
  MinSize: 20
  DesiredCapacity: 50
  MaxSize: 200
  
  Data de fim: 2024-11-30 06:00 UTC
  (volta ao normal automaticamente)

Terraform:
resource "aws_autoscaling_schedule" "scale_up_morning" {
  scheduled_action_name  = "scale-up-business-hours"
  min_size               = 10
  desired_capacity       = 15
  max_size               = 40
  recurrence             = "30 8 * * MON-FRI"  # cron: 8h30, seg-sex
  time_zone              = "America/Sao_Paulo"
  autoscaling_group_name = aws_autoscaling_group.app.name
}
```

## Estratégia 4: Predictive Scaling

### O que é e quando usar

```
Predictive Scaling usa ML para analisar padrões históricos
e pré-provisionar capacidade ANTES do pico:

Diferença do Scheduled:
  Scheduled: você programa manualmente ("às 9h escale")
  Predictive: AWS analisa histórico e agenda automaticamente

Como funciona:
  1. Analisa 14 dias de métricas históricas
  2. Identifica padrões recorrentes:
     ├── Diários: pico às 9h e às 14h
     ├── Semanais: segunda-feira sempre maior
     └── Sazonais: último dia do mês sempre pico
  3. Projeta carga futura
  4. Agenda scale out com antecedência (padrão: 5 minutos antes)
  5. Combina com Target Tracking para picos imprevistos

Modos do Predictive Scaling:
  Forecast Only: apenas gera previsões (sem ação automática)
  → Útil para validar se as previsões fazem sentido
  
  Forecast and Scale: age automaticamente
  → Combinar com Target Tracking como "safety net"
  
Melhor para:
  ├── Workloads com padrões regulares
  ├── Situações onde instâncias demoram para ficar healthy
  └── Quando Scheduled seria muito trabalhoso de manter
```

## Elasticidade além do EC2

### Lambda — elasticidade zero-config

```
Lambda é o serviço mais elástico da AWS:

Comportamento:
  0 requisições → 0 execuções → $0 de custo
  1.000 req/s simultâneas → 1.000 execuções paralelas
  
  Sem configuração de Auto Scaling
  Sem min/max/desired capacity
  Escala automaticamente até o limite de concorrência da conta

Limite padrão: 1.000 execuções simultâneas por região
  (pode ser aumentado via Service Quotas)

Concorrência Reservada:
  "Garanta que esta função tenha sempre X unidades disponíveis"
  → Lambda reserva X unidades exclusivas para essa função
  → Outras funções não "roubam" a capacidade
  
  Caso de uso: função crítica de pagamento
  → Reserve 200 de concorrência → nunca é throttled

Concorrência Provisionada:
  "Mantenha N instâncias quentes (pré-inicializadas)"
  → Elimina cold start para funções de latência crítica
  → Custo: paga pelas instâncias quentes mesmo sem requisições
  
  Application Auto Scaling para Lambda Provisioned:
  resource "aws_appautoscaling_target" "lambda_concurrency" {
    max_capacity       = 100
    min_capacity       = 10
    resource_id        = "function:minha-funcao:LIVE"
    scalable_dimension = "lambda:function:ProvisionedConcurrency"
    service_namespace  = "lambda"
  }
  
  resource "aws_appautoscaling_policy" "lambda_scaling" {
    policy_type = "TargetTrackingScaling"
    target_tracking_scaling_policy_configuration {
      predefined_metric_specification {
        predefined_metric_type = "LambdaProvisionedConcurrencyUtilization"
      }
      target_value = 0.8  # mantenha utilização em 80%
    }
  }
```

### DynamoDB — elasticidade on-demand

```
Dois modos de capacidade:

1. Provisioned Capacity + Auto Scaling:
   → Você define read/write capacity units (RCU/WCU)
   → Auto Scaling ajusta entre min e max
   → Mais barato para cargas previsíveis e estáveis
   
   Auto Scaling para DynamoDB:
   Target: DynamoDBReadCapacityUtilization = 70%
   → Se leituras usarem >70% da capacidade: aumenta RCU
   → Se usarem <70%: diminui RCU
   
   Min RCU: 5  |  Max RCU: 1000
   Min WCU: 5  |  Max WCU: 500

2. On-Demand Mode:
   → Sem configuração de capacidade
   → DynamoDB escala automaticamente para qualquer throughput
   → Paga por requisição (não por capacidade provisionada)
   → Mais caro por requisição, mas zero gerenciamento
   
   Quando usar On-Demand:
   ├── Tráfego imprevisível ou com picos extremos
   ├── Novos workloads sem histórico de uso
   ├── Aplicações com tráfego "bursty" (grande variação)
   └── Quando simplicidade operacional supera custo
   
   Quando usar Provisioned + Auto Scaling:
   ├── Tráfego previsível e relativamente estável
   ├── Otimização de custo é prioritária
   └── Carga sustentada (não picos extremos)
```

### ECS — escalando contêineres

```
ECS Service Auto Scaling (Application Auto Scaling):

Target Tracking para ECS:
  Target: ECSServiceAverageCPUUtilization = 60%
  Min tasks: 2  |  Max tasks: 50
  
  → Aumenta tasks quando CPU média > 60%
  → Diminui tasks quando CPU média < 60%

Scale baseado em SQS (KEDA-like no ECS):
  Custom metric: ApproximateNumberOfMessagesVisible / RunningTaskCount
  
  "Cada task deve processar no máximo 100 mensagens da fila"
  
  10.000 mensagens → 100 tasks
  500 mensagens → 5 tasks
  0 mensagens → 2 tasks (min)
  
  CloudWatch metric math:
  (mensagens_na_fila / tasks_rodando) → target: 100

Fargate vs EC2 Launch Type para escalabilidade:
  EC2 Launch Type:
  ├── Controla as instâncias EC2 do cluster
  ├── Precisa escalar o cluster E os tasks
  └── Cluster capacity providers gerenciam isso

  Fargate Launch Type:
  ├── AWS gerencia a infraestrutura subjacente
  ├── Escala apenas os tasks (contêineres)
  └── Mais simples: menos configuração, mais caro por unidade
```

## Combinando estratégias: o modelo ideal para produção

```
Arquitetura de escalabilidade em camadas:

LAYER 1 — Scheduled Scaling (base):
  "Eu sei que às 8h30 sempre tenho pico"
  → Pré-provisiona ANTES do pico

LAYER 2 — Predictive Scaling (inteligência):
  "ML detectou que quinta-feira é sempre 30% maior"
  → Ajusta automaticamente sem configuração manual

LAYER 3 — Target Tracking (reatividade):
  "Mantém CPU em 60%"
  → Reage a variações não previstas pelas camadas acima

LAYER 4 — Step Scaling (proteção):
  "Se CPU > 90% por 1 minuto: escala agressivamente"
  → Resposta de emergência para picos extremos

Resultado:
  → Custo mínimo: sem overprovisioning nos vales
  → Performance máxima: sem underprovisioning nos picos
  → Automatizado: sem intervenção humana
  → Resiliente: múltiplas camadas de proteção
```

## Warmup Time — o custo oculto da elasticidade de EC2

```
EC2 não está imediatamente disponível após lançamento:

Linha do tempo de uma nova instância:
  t=0s: ASG decide escalar → inicia nova EC2
  t=60s: EC2 com status "running"
  t=90s: Sistema operacional inicializado
  t=120s: Docker/aplicação iniciando
  t=180s: Aplicação carregou dependências
  t=200s: Health check passa → ALB adiciona ao pool
  t=210s: Tráfego começa a chegar para nova instância
  
  Total: ~3-4 minutos de warmup

Implicação: se o pico chegou agora, as novas instâncias
            chegam disponíveis 3-4 minutos depois

Estratégias para minimizar o impacto:
  1. Scheduled Scaling: escalar ANTES do pico previsto
  2. Golden AMI: AMI pré-configurada com tudo instalado
     → Inicialização muito mais rápida (software já instalado)
  3. Lambda como complemento: zero warmup para requisições simples
  4. Scale conservadoramente (não esperar 90% para escalar)
     Target: 60% → escala mais cedo, mais tempo de warmup

Warm Pools (EC2 Auto Scaling feature):
  Mantém instâncias em estado "stopped" (pré-inicializadas)
  → Ao escalar: instância stopped inicia em 20-30s (vs. 3-4min)
  → Custo: paga apenas pelo EBS das instâncias paradas (~$0.08/GB/mês)
  → Grande redução no tempo de resposta ao pico
```

## 🧩 Quiz de Fixação

1. Qual estratégia de Auto Scaling é mais adequada para um sistema que experimenta picos de tráfego todo dia às 8h, às 12h e às 18h, e por quê é superior ao Target Tracking sozinho para esse padrão?
2. Uma função Lambda de checkout processa pagamentos com requisito de latência de p99 < 200ms. O time está considerando Lambda Provisioned Concurrency. O que é cold start, quando ocorre, e como Provisioned Concurrency resolve o problema?
3. Um banco DynamoDB usa Provisioned Capacity com 100 RCU. Durante uma campanha de marketing, o tráfego quintuplicou em 30 segundos, causando throttling. Auto Scaling não acompanhou o ritmo. Como On-Demand Mode e o design de Scheduled Scaling teriam prevenido o problema?

**Respostas:**
1) Scheduled Scaling combinado com Target Tracking. Scheduled Scaling pré-provisiona capacidade antes dos horários conhecidos de pico (ex: às 7h45, 11h45, 17h45), garantindo que as instâncias estejam prontas quando o tráfego chegar — eliminando os 3-4 minutos de warmup que causariam degradação. Target Tracking sozinho é reativo: detecta a CPU subindo após o pico já ter chegado, então escala quando o dano já está ocorrendo. A combinação usa Scheduled para picos previsíveis e Target Tracking como "safety net" para variações imprevisíveis dentro desses períodos ou fora do padrão esperado.
2) Cold start é o tempo de inicialização de uma função Lambda quando não há uma execução "quente" disponível. Ocorre em três situações: (1) primeira invocação após a função ser criada ou atualizada; (2) quando a concorrência necessária excede as execuções quentes disponíveis (burst de tráfego); (3) após período de inatividade (Lambda desaloca execuções ociosas). Para funções com runtime pesado (Java com Spring, Python com bibliotecas grandes), o cold start pode levar 1-5 segundos — violando o p99 de 200ms. Lambda Provisioned Concurrency mantém N instâncias da função pré-inicializadas e aquecidas: quando uma requisição chega, uma instância já está pronta para executar imediatamente. Custo: paga pelas instâncias provisionadas por hora, mesmo sem requisições. Application Auto Scaling pode ajustar a concorrência provisionada ao longo do dia para otimizar o custo (menos provisionado na madrugada, mais no pico).
3) Auto Scaling de DynamoDB tem latência de resposta — monitora utilização e escala, mas o processo leva alguns minutos. Para um spike de 5x em 30 segundos, o Auto Scaling simplesmente não é rápido o suficiente. On-Demand Mode teria resolvido completamente: sem capacidade provisionada, DynamoDB absorve qualquer volume de requisições instantaneamente (até limites da conta), pagando por requisição. Scheduled Scaling teria resolvido preventivamente: sabendo que campanhas de marketing causam picos previsíveis, escalar a capacidade para 500+ RCU antes da campanha iniciar — eliminando o problema mesmo com Provisioned Capacity. O ideal para sistemas com picos extremos imprevisíveis é On-Demand Mode; para picos previsíveis com orçamento controlado, Scheduled Scaling preventivo.
