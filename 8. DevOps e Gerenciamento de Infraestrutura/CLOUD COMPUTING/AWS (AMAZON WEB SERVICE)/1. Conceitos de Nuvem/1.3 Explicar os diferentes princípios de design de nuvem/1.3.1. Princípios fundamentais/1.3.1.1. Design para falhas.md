### Design para falhas — construir sistemas que sobrevivem ao inevitável

Design para falhas é o princípio de arquitetura que parte de uma premissa simples e radical: **tudo vai falhar em algum momento**. Servidores vão travar, discos vão falhar, redes vão oscilar, código vai ter bugs, humanos vão errar. Sistemas resilientes não são os que nunca falham — são os que continuam funcionando quando seus componentes falham. Na AWS, esse princípio é um dos pilares que diferencia arquiteturas amadoras de arquiteturas de produção.

---

## A mudança de mentalidade

```
Mentalidade tradicional:
  "Como evito que meu sistema falhe?"
  → Compra hardware mais caro e "confiável"
  → Adiciona mais memória e CPU "para ter folga"
  → Testa exaustivamente antes de ir para produção
  → Resultado: sistema ainda falha (hardware falha,
               software tem bugs, rede oscila)
               E quando falha: catastroficamente

Mentalidade de design para falhas:
  "Quando (não se) meu sistema falhar, o que acontece?"
  → Assume falha como condição normal de operação
  → Projeta cada componente para falhar graciosamente
  → Testa falhas ativamente em produção
  → Resultado: sistema falha frequentemente em componentes
               individuais, mas o todo continua funcionando
```

A Amazon descreve isso como: *"Everything fails, all the time."* — Werner Vogels, CTO da Amazon.

## Os componentes do Design para Falhas

### 1. Eliminar Pontos Únicos de Falha (SPOF)

```
Single Point of Failure (SPOF) — componente cuja falha
derruba o sistema inteiro:

SPOF típicos e como eliminar:

┌─────────────────────────────────────────────────────────┐
│ COMPONENTE        │ COM SPOF       │ SEM SPOF           │
├───────────────────┼────────────────┼────────────────────┤
│ Servidor web      │ 1 EC2          │ ≥2 EC2 + ALB       │
│ Banco de dados    │ RDS Single-AZ  │ RDS Multi-AZ       │
│ Load balancer     │ Nginx no EC2   │ ALB (gerenciado)   │
│ DNS               │ Servidor único │ Route 53 (HA nat.) │
│ Cache             │ Redis único    │ ElastiCache cluster │
│ Mensageria        │ RabbitMQ único │ SQS (gerenciado)   │
│ Armazenamento     │ EBS único      │ S3 (11 noves)      │
└───────────────────┴────────────────┴────────────────────┘

Exemplo — evolução de arquitetura:

Versão 1 (SPOFs em todo lugar):
  Internet → EC2 (app + banco + cache) → nada mais
  Se essa EC2 cair: sistema 100% fora do ar

Versão 2 (design para falhas):
  Internet
    ↓
  [Route 53] → DNS com health check e failover
    ↓
  [ALB] → distribui entre múltiplas AZs
    ↓
  [EC2 #1 AZ-a]  [EC2 #2 AZ-b]  [EC2 #3 AZ-c]
    ↓
  [ElastiCache cluster] → cache redundante
    ↓
  [RDS Multi-AZ] → banco com failover automático
  
  Se EC2 #1 falhar: ALB para de rotear para ela (health check)
  Se AZ-a falhar: tráfego vai para AZ-b e AZ-c
  Se banco primary falhar: standby assume em 30-60 segundos
```

### 2. Health Checks — detectar falhas rapidamente

```
Health check é o mecanismo pelo qual o sistema verifica
se um componente está saudável antes de rotear tráfego para ele:

ALB Health Check (configuração):
  Protocol: HTTP
  Path: /health
  Interval: 30 segundos
  Healthy threshold: 2 respostas OK consecutivas → saudável
  Unhealthy threshold: 3 falhas consecutivas → remove do pool
  
  Exemplo de endpoint /health:
  def health_check():
      # Verifica dependências críticas
      db_ok = check_database_connection()
      cache_ok = check_cache_connection()
      
      if db_ok and cache_ok:
          return {"status": "healthy"}, 200
      else:
          return {"status": "unhealthy", 
                  "db": db_ok, "cache": cache_ok}, 503

  Se /health retornar 503:
  → ALB para de enviar tráfego para essa instância
  → Auto Scaling Group marca como unhealthy
  → ASG termina a instância e lança uma nova
  
  Tempo de recuperação: detecção (~90s) + novo deploy (~60s) = ~2.5 min
  Sem health check: tráfego continua indo para instância quebrada
                    → erros para usuários por tempo indeterminado

RDS Health Check:
  Multi-AZ faz health check contínuo do primary
  → Heartbeat entre primary e standby
  → Se primary não responde: failover automático em 30-60s

Route 53 Health Check:
  Monitora endpoints periodicamente
  → Se endpoint falhar: redireciona DNS para endpoint secundário
  → Disaster recovery multi-region automatizado
```

### 3. Timeout — não esperar para sempre

```
Problema sem timeout:
  Serviço A chama Serviço B (que está lento/travado)
  → Thread do Serviço A fica bloqueada esperando
  → 1.000 requisições simultâneas = 1.000 threads bloqueadas
  → Serviço A fica sem threads → também trava
  → Falha em cascata (cascade failure)

Com timeout bem configurado:
  Serviço A chama Serviço B com timeout de 2 segundos
  → Após 2s sem resposta: retorna erro ao cliente
  → Thread liberada para próxima requisição
  → Serviço A continua funcionando (degradado, não travado)

Hierarquia de timeouts (regra crítica):
  O timeout do chamador DEVE ser menor que o do chamado:
  
  Client → API Gateway (timeout: 29s)
              ↓
           Lambda (timeout: 25s)
              ↓
           RDS (query timeout: 20s)
              ↓
           Serviço externo (timeout: 15s)
  
  Se a hierarquia for invertida:
  Client espera 5s → Lambda tem timeout de 15s
  → Client desiste e tenta de novo
  → Lambda ainda está executando a query original
  → Queries duplicadas no banco
  → Problema de consistência de dados

Configuração de timeout na AWS:
  Lambda: máximo 15 minutos, defina pelo contexto
  API Gateway: máximo 29 segundos (limitação da AWS)
  RDS proxy: timeout de conexão configurável
  SDK AWS: tem retry automático com backoff (configurável)
```

### 4. Retry com Backoff Exponencial e Jitter

```
Falhas transitórias (momentâneas):
  → Pacote perdido na rede
  → Pico temporário de carga no serviço chamado
  → Rate limiting momentâneo
  → Solução: tentar de novo após breve espera

Retry ingênuo (problemático):
  for i in range(5):
      try:
          resultado = chamar_servico()
          break
      except Exception:
          time.sleep(1)  # espera fixa de 1 segundo
  
  Problema: se 10.000 clientes fizerem retry ao mesmo tempo
  → Thundering herd: spike massivo no momento exato do retry
  → Pode derrubar o serviço que estava se recuperando

Retry com backoff exponencial + jitter (correto):
  import random
  
  for tentativa in range(5):
      try:
          resultado = chamar_servico()
          break
      except Exception as e:
          if tentativa == 4:
              raise e
          
          # Backoff exponencial: 1s, 2s, 4s, 8s, 16s
          espera_base = (2 ** tentativa)
          
          # Jitter: aleatoriedade para distribuir os retries
          jitter = random.uniform(0, espera_base * 0.3)
          
          time.sleep(espera_base + jitter)
  
  Resultado:
  Tentativa 1: falha → espera ~1-1.3s (aleatório)
  Tentativa 2: falha → espera ~2-2.6s
  Tentativa 3: falha → espera ~4-5.2s
  Tentativa 4: sucesso ✓
  
  10.000 clientes fazendo retry:
  → Retries distribuídos ao longo de vários segundos
  → Sem spike → serviço consegue se recuperar

O SDK AWS implementa isso automaticamente:
  Todas as chamadas de API AWS já têm retry com
  backoff exponencial + jitter por padrão
  → Você se beneficia sem configurar nada
```

### 5. Graceful Degradation — degradar, não travar

```
Graceful degradation: quando um componente falha,
o sistema entrega funcionalidade reduzida em vez de
parar completamente:

Exemplo: e-commerce com serviço de recomendações

Sem graceful degradation:
  Página do produto:
  ├── Carrega foto e preço ← dados críticos
  ├── Carrega avaliações ← importante mas não crítico
  └── Chama Serviço de Recomendações ← timeout de 3s
      → Se timeout: página inteira fica em erro 500
      → Usuário não consegue nem ver o produto

Com graceful degradation:
  def carregar_pagina_produto(produto_id):
      produto = buscar_produto(produto_id)  # crítico, sem fallback
      
      try:
          recomendacoes = buscar_recomendacoes(produto_id, timeout=0.5)
      except TimeoutError:
          recomendacoes = []  # fallback: lista vazia
          log.warning("Serviço de recomendações indisponível")
      
      try:
          avaliacoes = buscar_avaliacoes(produto_id, timeout=1.0)
      except TimeoutError:
          avaliacoes = cache.get(f"avaliacoes:{produto_id}", default=[])
          # fallback: versão em cache (pode estar levemente desatualizada)
      
      return render_template(produto, recomendacoes, avaliacoes)
  
  Resultado:
  → Produto exibido sempre (serviço crítico funciona)
  → Recomendações: ausentes se serviço falhar (não crítico)
  → Avaliações: versão em cache se serviço falhar
  → Usuário consegue comprar mesmo com degradação

Cache como fallback:
  ElastiCache com dados do catálogo (TTL: 5 minutos)
  → Banco de dados fora do ar → serve dados do cache
  → Levemente desatualizados, mas disponíveis
  → Muito melhor que página de erro
```

### 6. Circuit Breaker — parar de chamar o que está quebrado

```
(Revisando o padrão com foco na implementação na AWS)

Sem Circuit Breaker:
  Serviço de pagamento fora do ar
  → Sistema tenta chamar a cada requisição
  → Cada chamada: espera pelo timeout (ex: 5 segundos)
  → 1.000 req/s × 5s de espera = recursos esgotados

Com Circuit Breaker (estados):

  [FECHADO] → operação normal, chama o serviço
       │
       │ N falhas consecutivas
       ▼
  [ABERTO] → retorna erro imediatamente (sem chamar o serviço)
       │       → salva recursos, responde rápido
       │
       │ Após X segundos (cooling period)
       ▼
  [SEMI-ABERTO] → permite uma requisição de teste
       │
       ├── Sucesso → volta para [FECHADO]
       └── Falha → volta para [ABERTO]

Na AWS:
  AWS App Mesh / Envoy → circuit breaker nativo entre microserviços
  Lambda → SDK com retry automático (partial circuit breaker)
  Step Functions → retry policy + catch para falhas
  
  Implementação manual com ElastiCache:
  # Verifica se circuito está aberto
  if redis.get("circuit:pagamento:aberto"):
      return {"erro": "Serviço temporariamente indisponível"}
  
  try:
      resultado = chamar_pagamento()
      redis.delete("circuit:pagamento:falhas")
      return resultado
  except Exception:
      falhas = redis.incr("circuit:pagamento:falhas")
      if falhas >= 5:
          redis.setex("circuit:pagamento:aberto", 30, 1)
      raise
```

## Testando falhas ativamente: Chaos Engineering

```
"Se você não testa falhas, descobrirá que seu sistema
não sobrevive a elas no pior momento possível."

AWS Fault Injection Simulator (FIS):
  Ferramenta gerenciada para injetar falhas controladas:
  
  Experimentos disponíveis:
  ├── Terminar instâncias EC2 aleatoriamente
  ├── Causar falha de uma AZ inteira
  ├── Injetar latência em chamadas de rede (500ms, 2s, 5s)
  ├── Throttling de API calls
  ├── Timeout em chamadas de banco de dados
  ├── Preencher CPU/memória ao máximo
  └── Cortar conectividade de rede de uma instância

  Exemplo de experimento:
  Nome: "Terminar instância primária do banco"
  Target: RDS Primary
  Ação: rds:failover-db-cluster
  Métricas de sucesso: aplicação se recupera em < 2 minutos
                       error rate volta a 0% em < 3 minutos
  
  Se falhar no experimento → descobriu vulnerabilidade
                              em ambiente controlado
  Se passar → confiança que o sistema é resiliente

Princípios do Chaos Engineering:
  1. Definir estado estável (linha de base de métricas normais)
  2. Formular hipótese ("sistema sobrevive à falha de X")
  3. Introduzir variável real (injetar a falha)
  4. Medir: estado estável foi mantido?
  5. Corrigir vulnerabilidades encontradas
  6. Repetir com falhas mais complexas
```

## Checklist de Design para Falhas

```
Infraestrutura:
  ✓ Nenhum SPOF: toda camada tem pelo menos 2 instâncias em AZs distintas
  ✓ ALB com health checks configurados corretamente
  ✓ RDS Multi-AZ ou Aurora (não Single-AZ em produção)
  ✓ Auto Scaling configurado para repor instâncias unhealthy

Aplicação:
  ✓ Timeouts em todas as chamadas externas
  ✓ Retry com backoff exponencial + jitter
  ✓ Circuit breaker para dependências externas
  ✓ Graceful degradation para features não-críticas
  ✓ Fallback para cache quando banco indisponível

Operação:
  ✓ Chaos Engineering regular (FIS ou manual)
  ✓ Runbooks testados para cenários de falha
  ✓ Alertas para detecção rápida
  ✓ Post-mortems blameless após incidentes
  ✓ Disaster recovery testado (não apenas planejado)
```

## 🧩 Quiz de Fixação

1. Uma aplicação tem um único servidor EC2 com RDS Single-AZ. Liste três SPOFs nessa arquitetura e descreva como eliminá-los usando serviços AWS.
2. Um serviço faz chamadas a uma API externa sem timeout configurado. Em um dia de alta carga, a API externa fica lenta (10 segundos por resposta). Descreva o que acontece com o serviço e como o timeout previne o problema.
3. Por que retry com jitter é superior ao retry com backoff exponencial puro, e qual problema específico o jitter resolve?

**Respostas:**
1) Os três SPOFs e como eliminá-los: (1) EC2 única — eliminar com ALB + ≥2 instâncias EC2 em AZs distintas + Auto Scaling Group; se uma EC2 falhar, o ALB detecta via health check e para de rotear tráfego; (2) RDS Single-AZ — eliminar com RDS Multi-AZ; AWS mantém um standby em outra AZ com replicação síncrona e faz failover automático em 30-60 segundos se o primary falhar; (3) Própria AZ — eliminar distribuindo instâncias em pelo menos 2 AZs; se uma AZ inteira falhar (raro mas acontece), o tráfego continua fluindo para a outra AZ através do ALB.
2) Sem timeout: cada thread que chama a API externa fica bloqueada por 10 segundos aguardando a resposta. Com 500 requisições/segundo chegando, em 10 segundos há 5.000 threads bloqueadas esperando. O servidor tem um pool de 200 threads → esgotado em 0.4 segundos. Novas requisições não conseguem ser atendidas → também ficam na fila → o próprio serviço fica sem resposta. Toda a aplicação trava por causa de uma dependência externa lenta. Com timeout de 2 segundos: cada thread espera no máximo 2s; retorna erro para o cliente; a thread é liberada. O serviço continua respondendo às demais requisições (degradado, com erros nas chamadas à API externa, mas funcionando).
3) O backoff exponencial puro faz todos os clientes que falharam ao mesmo tempo retryarem também ao mesmo tempo — após 2 segundos, todos os 10.000 clientes que falharam simultaneamente fazem retry simultaneamente, criando um novo spike idêntico ao que causou a falha original (thundering herd). O sistema que estava se recuperando é atingido por outro pico e falha novamente. O jitter adiciona aleatoriedade ao tempo de espera (ex: em vez de exatamente 2 segundos, cada cliente espera entre 1.4s e 2.6s de forma aleatória), distribuindo os 10.000 retries ao longo de 1.2 segundos em vez de todos no mesmo instante. O serviço recebe uma carga distribuída que consegue absorver, e se recupera gradualmente.
