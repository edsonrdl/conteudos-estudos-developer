### Desacoplamento de componentes — sistemas que não se afogam juntos

Desacoplamento é o princípio de projetar componentes de um sistema de forma que eles se comuniquem sem dependência direta de disponibilidade um do outro. Em sistemas fortemente acoplados, a falha de um componente propaga para todos os que dependem dele. Em sistemas desacoplados, cada componente opera de forma independente — produz trabalho, deposita em um intermediário, e o consumidor processa no seu próprio ritmo.

---

## O problema do acoplamento forte

```
Sistema acoplado (síncrono e direto):

Usuário faz pedido
    ↓
[Serviço de Pedidos] ←────── chamada síncrona ──────►
    ├── [Serviço de Estoque]    (responde em 50ms)
    ├── [Serviço de Pagamento]  (responde em 200ms)
    ├── [Serviço de E-mail]     (responde em 800ms)
    └── [Serviço de Analytics]  (responde em 1200ms)
    
Tempo total de resposta: 50 + 200 + 800 + 1.200 = 2.250ms

Problemas:
  1. Latência somada: usuário espera 2.25 segundos
     (Analytics sendo o gargalo de um pedido simples)
  
  2. Disponibilidade multiplicada:
     Se cada serviço tem 99.9% de disponibilidade:
     0.999 × 0.999 × 0.999 × 0.999 = 99.6% de disponibilidade total
     → 4 serviços de 99.9% resultam em sistema de 99.6%
  
  3. Falha em cascata:
     Serviço de E-mail com timeout → pedido inteiro falha
     → Usuário não consegue comprar
     → Por causa de um email que nem era crítico para a compra

  4. Escalabilidade acoplada:
     Pico no Analytics → você precisa escalar todos os serviços
     em vez de apenas o Analytics
```

## Desacoplamento com filas (SQS)

### Como funciona a comunicação assíncrona

```
Sistema desacoplado (assíncrono com SQS):

Usuário faz pedido
    ↓
[Serviço de Pedidos]
    ├── Chama Estoque (síncrono — crítico, precisa de resposta)
    ├── Chama Pagamento (síncrono — crítico, precisa de resposta)
    │
    ├── Publica em [Fila SQS: pedido-confirmado]
    │         → E-mail worker consome quando puder
    │         → Analytics worker consome quando puder
    │
    └── Retorna: "Pedido confirmado" para o usuário em 260ms

Workers independentes:
  [E-mail Worker] → consome da fila → envia email → deletar msg
  [Analytics Worker] → consome da fila → registra evento → deletar msg

Benefícios imediatos:
  ├── Latência do pedido: 260ms (vs. 2.250ms acoplado)
  ├── E-mail fora do ar → mensagens acumulam na fila → processadas quando voltar
  ├── Analytics lento → fila cresce → auto scaling do worker
  └── Cada serviço escala independentemente
```

### SQS em profundidade

```
Tipos de filas:

1. Standard Queue:
   ├── Throughput: virtualmente ilimitado (milhões de msg/s)
   ├── Ordenação: melhor esforço (não garantida)
   ├── Entrega: pelo menos uma vez (at-least-once)
   └── Uso: processamento de tarefas onde ordem não importa
             (envio de e-mails, resize de imagens, analytics)

2. FIFO Queue:
   ├── Throughput: 3.000 msg/s com batching, 300/s sem
   ├── Ordenação: garantida (First-In-First-Out)
   ├── Entrega: exatamente uma vez (exactly-once)
   └── Uso: transações financeiras, processamento de pedidos
             onde ordem e deduplicação importam

Visibilidade e retry automático:
  Mensagem enviada para a fila
    ↓
  Worker recebe e inicia processamento
  → Mensagem fica "invisível" (Visibility Timeout: 30s)
    ↓
  Worker processa com sucesso:
  → Worker deleta a mensagem da fila explicitamente
  
  Worker falha ou trava:
  → Após Visibility Timeout: mensagem volta a ficar visível
  → Outro worker (ou o mesmo) recebe e reprocessa
  → Retry automático sem configuração adicional

Dead Letter Queue (DLQ):
  Após N tentativas falhas (ex: 3 vezes):
  → Mensagem vai para DLQ (fila separada)
  → Time investiga: por que falhou 3 vezes?
  → Corrige o problema → reprocessa da DLQ
  → Sem perda de mensagem, sem loop infinito de retry

Configuração típica:
  fila-pedidos (main):
  ├── Visibility Timeout: 30 segundos
  ├── Message Retention: 4 dias
  ├── Max Receive Count: 3 (tentativas antes de DLQ)
  └── DLQ: fila-pedidos-dlq

  fila-pedidos-dlq:
  ├── Message Retention: 14 dias
  └── Alarme CloudWatch: se > 0 mensagens → notifica time
```

## Desacoplamento com Pub/Sub (SNS)

### Quando múltiplos consumidores precisam do mesmo evento

```
Problema com SQS para fan-out:
  Um pedido confirmado precisa ser processado por:
  E-mail, Analytics, Estoque, Parceiros externos

  Opção A — Uma fila por consumidor:
  [Pedidos] → [Fila E-mail] → [Worker E-mail]
  [Pedidos] → [Fila Analytics] → [Worker Analytics]
  [Pedidos] → [Fila Estoque] → [Worker Estoque]
  → Publicar em N filas: código de publicação acoplado aos consumidores
  → Adicionar novo consumidor: modificar o publicador

  Opção B — SNS + SQS (Fan-out pattern):
  [Pedidos] → Publica em [SNS Topic: pedido-confirmado]
                    ↓
            SNS entrega para todos os assinantes:
            ├── [SQS: fila-email]      → [Worker E-mail]
            ├── [SQS: fila-analytics]  → [Worker Analytics]
            ├── [SQS: fila-estoque]    → [Worker Estoque]
            └── [Lambda: notif-parceiros]

Vantagem do SNS:
  → Publicador não sabe quem são os consumidores
  → Adicionar novo consumidor: assinar o tópico (sem tocar no publicador)
  → Remover consumidor: cancelar assinatura
  → Publicador e consumidores completamente desacoplados
```

### SNS — características

```
Protocolos de assinatura suportados:
  ├── SQS (mais comum — buffering + retry automático)
  ├── Lambda (processamento imediato sem buffer)
  ├── HTTP/HTTPS (webhooks para sistemas externos)
  ├── Email (notificações diretas)
  ├── SMS (notificações via texto)
  └── Mobile Push (APNs, FCM)

Message Filtering (filtro por atributo):
  SNS permite que assinantes recebam apenas mensagens
  que correspondem a filtros específicos:
  
  Pedido publicado: {
    "produto_categoria": "eletrônicos",
    "valor": 1500,
    "cliente_premium": true
  }
  
  Assinante A (Worker de Frete Expresso):
    Filtro: cliente_premium = true
    → Recebe apenas pedidos de clientes premium
  
  Assinante B (Worker de Analytics Eletrônicos):
    Filtro: produto_categoria = "eletrônicos"
    → Recebe apenas pedidos de eletrônicos
  
  Assinante C (Worker de Confirmação Geral):
    Sem filtro → recebe todos os pedidos
  
  Resultado: consumidores processam apenas o que é relevante
             sem código de filtragem na aplicação
```

## Desacoplamento com EventBridge — Event Bus

### Eventos de negócio como cidadãos de primeira classe

```
EventBridge é o barramento de eventos da AWS:
  → Recebe eventos de qualquer fonte (AWS, SaaS, custom)
  → Roteia para targets baseado em regras (event patterns)
  → Substitui código de roteamento espalhado pelo sistema

Fontes de eventos:
  ├── Serviços AWS: RDS, EC2, CodePipeline, GuardDuty...
  ├── Aplicações custom: PUT Event via SDK/API
  ├── SaaS integrados: Datadog, PagerDuty, Stripe, Zendesk...
  └── Event buses de outras contas AWS (cross-account)

Exemplo — arquitetura orientada a eventos:

Evento: pedido finalizado (enviado pelo serviço de pedidos)
{
  "source": "com.empresa.pedidos",
  "detail-type": "PedidoFinalizado",
  "detail": {
    "pedido_id": "ORD-12345",
    "valor": 299.90,
    "cliente_id": "USR-789",
    "itens": [{"produto": "Notebook", "quantidade": 1}]
  }
}

Regras configuradas no EventBridge:

Regra 1: pedido finalizado → Lambda de e-mail
  Pattern: source = "com.empresa.pedidos"
           detail-type = "PedidoFinalizado"
  Target: Lambda (enviar-email-confirmacao)

Regra 2: pedido de alto valor → SQS de análise de fraude
  Pattern: source = "com.empresa.pedidos"
           detail.valor > 1000
  Target: SQS (fila-analise-fraude)

Regra 3: qualquer evento de pedido → Kinesis para BI
  Pattern: source = "com.empresa.pedidos"
  Target: Kinesis Data Stream (stream-analytics)

O serviço de pedidos publica um evento.
EventBridge roteia para todos os targets corretos.
Cada consumidor é completamente desacoplado dos outros.
```

### EventBridge Scheduler — substituindo cron jobs acoplados

```
Problema tradicional: cron job no servidor
  → Servidor único = SPOF
  → Gerenciar fuso horário, holidays
  → Logs espalhados
  → Se servidor reinicia: perde o cron

EventBridge Scheduler:
  Cria schedule como recurso AWS:
  
  Schedule: "todo dia às 03h UTC"
  Target: Lambda (processar-relatorio-diario)
  
  Benefícios:
  ├── Sem servidor dedicado
  ├── Alta disponibilidade (gerenciado pela AWS)
  ├── Logs no CloudWatch
  ├── Retry automático se Lambda falhar
  └── Gerenciável via Console/CLI/IaC
```

## Padrões de desacoplamento na AWS

### Padrão 1: Request-Response Assíncrono com SQS

```
Para tarefas longas que não precisam de resposta imediata:

Cliente → API Gateway → Lambda (aceita e retorna ticket_id)
                              ↓
                         [SQS: tarefas]
                              ↓
                      [Worker Lambda/ECS]
                         (processa em background)
                              ↓
                    Resultado salvo no DynamoDB
                    (chave: ticket_id)

Cliente consulta periodicamente:
GET /status/{ticket_id} → busca no DynamoDB
→ Se "pendente": aguarda
→ Se "concluído": retorna resultado

Ou: Worker notifica quando terminar (SNS → email/webhook)
```

### Padrão 2: Competing Consumers

```
Múltiplos workers consumindo da mesma fila:

[SQS: resize-imagens]
      ↓
  ┌───┴───┐
  ▼       ▼       ▼
[W1]   [W2]   [W3]   ← workers independentes
  
Cada mensagem é processada por exatamente UM worker
(SQS garante via Visibility Timeout)

Auto Scaling baseado em profundidade de fila:
  CloudWatch Alarm: QueueDepth > 100 mensagens
  → Auto Scaling adiciona workers
  
  CloudWatch Alarm: QueueDepth < 10 mensagens
  → Auto Scaling remove workers
  
  Resultado: custo proporcional ao trabalho real
             sem capacidade ociosa
```

### Padrão 3: Event Sourcing com SQS + DynamoDB

```
Cada ação do sistema gera um evento imutável:

Usuário adiciona item ao carrinho
→ Evento: {"tipo": "ItemAdicionado", "produto": "X", "timestamp": "..."}
→ Publicado no EventBridge
→ Armazenado no DynamoDB (event store)
→ Projeção atualizada (read model do carrinho)

Estado atual = replay de todos os eventos

Benefícios do desacoplamento:
→ Qualquer sistema pode "ouvir" os eventos e construir sua própria visão
→ Analytics constrói data warehouse a partir dos eventos
→ Estoque constrói sua visão a partir dos mesmos eventos
→ Sem acoplamento entre sistemas — cada um usa o que precisa
```

## Comparativo: síncrono vs. assíncrono

```
                    SÍNCRONO              ASSÍNCRONO
                    ──────────────────    ──────────────────
Latência            Somada (A+B+C+D)      Mínima (apenas A)
Disponibilidade     Produto das SLAs      Independente
Acoplamento         Forte                 Fraco
Escalabilidade      Todos juntos          Cada um separado
Ordem               Garantida             Depende do tipo
Debugging           Simples (stack trace) Complexo (eventos)
Consistência        Imediata              Eventual
Casos de uso        APIs síncronas        Workers, notificações,
                    (consultas, auth)     processamento, analytics
```

## Quando NÃO desacoplar

```
Nem tudo deve ser assíncrono:

Manter síncrono quando:
  ├── O resultado é necessário para continuar:
  │   "Verificar se CPF é válido antes de aceitar o pedido"
  │   → Precisa da resposta para tomar decisão
  │
  ├── Consistência imediata é requisito:
  │   "Verificar saldo antes de debitar"
  │   → Não pode ser eventual: pode haver overdraft
  │
  ├── Latência é crítica para UX:
  │   Autocomplete de busca (< 100ms necessário)
  │   → Fila introduz latência inaceitável
  │
  └── Fluxo simples sem fan-out:
      CRUD básico, leitura de dados
      → Complexidade de fila não justificada

Desacoplar quando:
  ├── Consumidores múltiplos (fan-out)
  ├── Processamento pode ser posterior
  ├── Workloads independentes que não precisam se sincronizar
  ├── Capacidades diferentes de processamento (produtor rápido, consumidor lento)
  └── Tolerância a inconsistência eventual (analytics, notificações)
```

## 🧩 Quiz de Fixação

1. Um sistema de e-commerce chama sincronamente 5 serviços ao confirmar um pedido (estoque, pagamento, email, analytics, parceiro externo). Cada serviço tem 99.9% de disponibilidade. Qual é a disponibilidade total do sistema e como o desacoplamento com SQS/SNS resolve esse problema?
2. Qual é a diferença entre SQS e SNS, e por que o padrão SNS + SQS (fan-out) é superior a publicar diretamente em múltiplas filas SQS?
3. Um pedido chega ao sistema e o worker de e-mail falha durante o processamento (exceção não tratada, processo reiniciado). O que acontece com a mensagem SQS e como a Dead Letter Queue complementa esse mecanismo?

**Respostas:**
1) Com 5 serviços de 99.9% em série: 0.999⁵ = 99.5% de disponibilidade total — o sistema fica indisponível ~43 horas/ano por causa da composição de dependências. Com desacoplamento: apenas estoque e pagamento permanecem síncronos (críticos para confirmar o pedido). E-mail, analytics e parceiro externo são publicados em fila SQS/SNS após o pedido ser confirmado. A disponibilidade passa a ser determinada apenas pelos dois serviços críticos: 0.999² = 99.8% (~17h/ano). Se e-mail ou analytics estiverem fora do ar, as mensagens acumulam na fila e são processadas quando voltarem — sem impacto na confirmação do pedido.
2) SQS é uma fila point-to-point: uma mensagem é consumida por um único worker. SNS é pub/sub: uma mensagem é entregue a todos os assinantes simultaneamente. O padrão fan-out (SNS + múltiplas SQS) é superior a publicar em múltiplas filas diretamente porque: o publicador envia uma mensagem para um único tópico SNS (desacoplado dos consumidores); SNS faz o roteamento automaticamente; adicionar um novo consumidor requer apenas criar uma nova fila SQS e assinar o tópico — sem modificar o publicador; remover um consumidor é cancelar a assinatura. Publicar em múltiplas filas diretamente acopla o publicador à lista de consumidores, tornando adições e remoções uma mudança de código no publicador.
3) Quando o worker recebe a mensagem SQS, ela se torna "invisível" por um período configurado (Visibility Timeout, ex: 30s). Se o worker falhar (exceção, crash, timeout) sem deletar explicitamente a mensagem, após o Visibility Timeout ela volta a ficar visível na fila e outro worker (ou o mesmo, reiniciado) a recebe e reprocessa. Isso garante at-least-once delivery. A Dead Letter Queue (DLQ) complementa: se a mensagem falhar N vezes (ex: 3) — talvez por bug no código do worker ou dado corrompido — ela é movida automaticamente para a DLQ em vez de ficar em loop infinito de retry. A DLQ isola mensagens problemáticas, permite investigação sem bloquear o processamento da fila principal, e um alarme CloudWatch notifica o time quando mensagens chegam na DLQ.
