### Paralelização — dividir para conquistar em escala

Paralelização é o princípio de dividir um problema grande em partes independentes e processá-las simultaneamente em vez de sequencialmente. Na nuvem, onde recursos são virtualmente ilimitados, paralelização transforma trabalho que levaria horas em segundos — pagando proporcionalmente ao trabalho feito, não ao tempo decorrido. É uma das vantagens mais poderosas e exclusivas da arquitetura cloud que o modelo on-premises raramente consegue explorar plenamente.

---

## A diferença fundamental: serial vs. paralelo

```
Problema: processar 10.000 imagens para gerar thumbnails

Abordagem SERIAL (sequencial):
  [Imagem 1] → processa (2s) → [Imagem 2] → processa (2s) → ...
  
  Tempo total: 10.000 × 2s = 20.000 segundos = 5,5 horas
  Custo (1 EC2 t3.medium): 5,5h × $0.0416 = $0.23

Abordagem PARALELA:
  [Imagem 1]    → processa (2s) ┐
  [Imagem 2]    → processa (2s) │ simultaneamente
  [Imagem 3]    → processa (2s) │
  ...                           │
  [Imagem 1000] → processa (2s) ┘
  
  10 lotes de 1.000 imagens cada
  Tempo total: 10 × 2s = 20 segundos
  Custo (1000 Lambda × 2s × 512MB): ~$0.04

Resultado:
  Tempo: 5,5 horas → 20 segundos (990x mais rápido)
  Custo: $0.23 → $0.04 (5x mais barato)
  
  A nuvem cobra pelo trabalho, não pelo tempo de relógio.
  Paralelizar é quase sempre mais barato E mais rápido.
```

## Lei de Amdahl — o limite teórico da paralelização

```
"O ganho de velocidade máximo é limitado pela fração
 serial do problema"

Se 90% do trabalho pode ser paralelizado e 10% é serial:

  Speedup máximo = 1 / (fração serial)
                 = 1 / 0.10
                 = 10x (independente de quantos workers)

Exemplo prático:
  Processamento de relatório: 60 minutos total
  
  Serial (não paralelizável):
  ├── Buscar dados consolidados do banco: 10 minutos (17%)
  └── Gerar PDF final: 2 minutos (3%)
  
  Paralelizável:
  └── Calcular métricas por cliente: 48 minutos (80%)
  
  Com 10 workers paralelos:
  ├── Busca: 10 min (serial, não muda)
  ├── Cálculo: 48/10 = 4.8 min (10 workers)
  └── PDF: 2 min (serial, não muda)
  Total: 16.8 minutos (3.6x mais rápido)
  
  Com 100 workers:
  ├── Busca: 10 min
  ├── Cálculo: 48/100 ≈ 0.5 min
  └── PDF: 2 min
  Total: 12.5 minutos (4.8x mais rápido)
  
  Ir de 10 para 100 workers não deu 10x mais velocidade
  porque as partes seriais dominam.
  
  → Antes de paralelizar: identifique e otimize as partes seriais
```

## Padrão 1: Lambda Fan-out (scatter-gather)

### Dispersar trabalho e coletar resultados

```
O padrão mais comum de paralelização serverless:

SCATTER (dispersar):
  Uma Lambda orquestradora divide o trabalho e
  invoca múltiplas Lambdas filhas em paralelo

GATHER (coletar):
  Aguarda todas as Lambdas filhas terminarem
  e consolida os resultados

Implementação:

# Lambda orquestradora
import boto3
import json
from concurrent.futures import ThreadPoolExecutor

lambda_client = boto3.client('lambda')

def handler(event, context):
    # 1. Divide: 10.000 IDs em lotes de 100
    todos_ids = event['produto_ids']
    lotes = [todos_ids[i:i+100] for i in range(0, len(todos_ids), 100)]
    
    # 2. Scatter: invoca 100 Lambdas filhas em paralelo
    def invocar_lambda(lote):
        return lambda_client.invoke(
            FunctionName='processar-lote',
            InvocationType='RequestResponse',  # síncrono
            Payload=json.dumps({'ids': lote})
        )
    
    with ThreadPoolExecutor(max_workers=100) as executor:
        respostas = list(executor.map(invocar_lambda, lotes))
    
    # 3. Gather: consolida resultados de todos os lotes
    resultados = []
    for resposta in respostas:
        dados = json.loads(resposta['Payload'].read())
        resultados.extend(dados['processados'])
    
    return {'total_processados': len(resultados)}

# 100 Lambdas rodando simultaneamente:
# Tempo total ≈ tempo de 1 Lambda (não 100x)
```

## Padrão 2: Step Functions Map State

### Paralelização gerenciada de alto nível

```
Step Functions oferece o estado Map para processar
coleções em paralelo de forma visual e gerenciável:

{
  "ProcessarRelatorio": {
    "Type": "Map",
    "ItemsPath": "$.clientes",      // lista de 1.000 clientes
    "MaxConcurrency": 10,            // 10 em paralelo (controle)
    "Iterator": {
      "StartAt": "CalcularMetricas",
      "States": {
        "CalcularMetricas": {
          "Type": "Task",
          "Resource": "arn:aws:lambda:...:calcular-metricas-cliente",
          "End": true
        }
      }
    },
    "Next": "GerarRelatorioFinal"
  }
}

Vantagem sobre Lambda fan-out manual:
  ├── Gerenciamento de estado automático (sem código de coleta)
  ├── Retry automático por item que falhar
  ├── MaxConcurrency controla o nível de paralelismo
  ├── Visualização do progresso no console AWS
  └── Cada invocação tem timeout e error handling independente
```

### Step Functions Parallel State

```
Para branches completamente independentes:
```

## Padrão 3: SQS + Workers para paralelismo controlado

### Processamento paralelo de volumes massivos

```
Para volumes muito grandes (milhões de itens), Lambda
fan-out direto não escala bem (custo de coordenação).
SQS + Workers é o padrão ideal:

Arquitetura:
  [Job Producer]
        ↓
  Publica 1.000.000 mensagens no SQS
  (uma mensagem por item de trabalho)
        ↓
  [Auto Scaling Group de Workers] ou [ECS Service]
  → ASG escala de 2 para 200 instâncias (baseado em QueueDepth)
  → Cada worker puxa e processa mensagens da fila
  → Worker deleta mensagem após processamento bem-sucedido
  → Visibility Timeout + DLQ garante retry automático
        ↓
  Quando fila esvazia → ASG encolhe para 2 instâncias

Controle de paralelismo via ASG:
  CloudWatch Metric: ApproximateNumberOfMessagesVisible
  Target Tracking: mensagens/worker = 100
  
  1.000.000 mensagens / 100 = 10.000 workers (ideal)
  MaxSize do ASG: 500 (controle de custo)
  
  Com 500 workers × 100 msg cada = 50.000 msg/ciclo
  1.000.000 / 50.000 = 20 ciclos para processar tudo

Vantagem sobre Lambda fan-out:
  ├── Sem limite de invocações simultâneas de Lambda
  ├── Workers stateful (mantêm conexões abertas ao banco)
  ├── Processamento mais eficiente por item (batch)
  └── Custo menor para volumes muito grandes
```

## Padrão 4: S3 + Spark / Athena para dados massivos

### Paralelismo em analytics

```
Athena — consultas SQL paralelas em S3:

100TB de dados de logs no S3:
  Serial (download + processar local): dias
  
  Athena:
  → Distribui a consulta em centenas de workers internos
  → Cada worker processa uma partição dos dados em paralelo
  → Resultados consolidados automaticamente
  → Tempo: minutos (para a maioria das consultas)
  → Custo: $5 por TB escaneado

Particionamento para maximizar paralelismo:
  s3://bucket/logs/
    year=2024/
      month=01/
        day=01/
          log-0001.parquet
          log-0002.parquet
        day=02/
          ...
  
  Query com filtro de partição:
  SELECT * FROM logs WHERE year=2024 AND month=01 AND day=15
  → Athena escaneia APENAS o dia 15 (não 100TB inteiro)
  → Paralelismo máximo nas partições relevantes
  → Custo: cents (vs. $500 escaneando tudo)

EMR (Spark):
  Para transformações complexas que Athena não suporta:
  → Cluster Spark com dezenas/centenas de nodes
  → Processa em paralelo por partição do dataset
  → Auto-termina quando job finaliza (sem custo idle)
```

## Paralelização e idempotência — o requisito fundamental

```
Para paralelizar com segurança, as operações devem ser
IDEMPOTENTES: executar a mesma operação múltiplas vezes
produz o mesmo resultado que executar uma vez.

Por que idempotência é crítica:
  Em processamento paralelo, um item pode ser processado
  mais de uma vez (retry, at-least-once delivery do SQS,
  falha de rede)
  
  Operação NÃO idempotente (perigosa):
  INSERT INTO pedidos VALUES (novo_pedido)
  → Se executada 2x: dois pedidos duplicados no banco
  
  Operação idempotente (segura):
  INSERT INTO pedidos VALUES (novo_pedido)
  ON CONFLICT (pedido_id) DO NOTHING
  → Se executada 2x: resultado idêntico ao executar 1x

Técnicas para garantir idempotência:
  ├── IDs únicos por operação (UUID gerado pelo produtor)
  ├── Chaves de deduplicação no banco (UNIQUE constraint)
  ├── SQS FIFO: deduplication ID automático
  ├── DynamoDB: conditional writes (só insere se não existe)
  └── State machine com status: "pendente" → "processado"
      (verifica status antes de reprocessar)

Exemplo DynamoDB condicional:
  # Só processa se ainda não foi processado
  table.update_item(
      Key={'pedido_id': pedido_id},
      UpdateExpression='SET status = :novo_status',
      ConditionExpression='attribute_not_exists(status) OR status = :pendente',
      ExpressionAttributeValues={
          ':novo_status': 'processado',
          ':pendente': 'pendente'
      }
  )
  # Se já foi processado: ConditionalCheckFailedException
  # Worker captura e ignora (deduplication)
```

## Casos de uso reais de paralelização na AWS

```
1. ETL de dados — transformar 500GB diariamente:
   Serial: 1 instância × 4 horas = 4 horas
   Paralelo: 40 Lambda × 6 minutos = 6 minutos (40x mais rápido)
   
2. Machine Learning — treinar modelo com 1M de exemplos:
   Serial: 1 GPU × 10 horas
   Paralelo: 10 GPUs (p3.2xlarge Spot) × 1 hora = $30 vs. $120
   (SageMaker Distributed Training automatiza isso)

3. Testes automatizados — suíte com 10.000 testes:
   Serial: 1 hora em CI/CD pipeline
   Paralelo: 100 containers ECS × 36 segundos = 1 minuto
   (pytest-xdist ou Jest --runInBand=false)

4. Crawling de e-commerce — 1 milhão de páginas:
   Serial (1 worker): ~14 horas (a 2s/página)
   Paralelo (500 Lambda): ~7 minutos
   
5. Processamento de vídeo — encoding de 10.000 vídeos:
   MediaConvert (serviço gerenciado):
   → Distribui automaticamente em workers da AWS
   → Scaling sem configuração
   → 10.000 jobs em paralelo (dentro dos limites)
```

## Anti-padrões de paralelização

```
1. Paralelizar operações que compartilham estado mutável:
   ❌ 100 workers atualizando o mesmo registro no banco
   → Race conditions, deadlocks, dados corrompidos
   ✓ Usar filas para serializar atualizações críticas
   
2. Coordenação excessiva (overhead > benefício):
   ❌ Paralelizar tasks de 10ms com overhead de 100ms
   → Versão paralela é 10x mais lenta
   ✓ Paralelizar apenas tasks com tempo >> overhead de coordenação

3. Paralelismo sem controle de concorrência:
   ❌ 10.000 Lambda simultâneas abrindo conexão com RDS
   → RDS tem limite de ~1.000 conexões → todas falham
   ✓ RDS Proxy: pool de conexões compartilhado (resolve o problema)
   ✓ Limitar MaxConcurrency no Step Functions Map

4. Não garantir idempotência:
   ❌ Processar pagamento em paralelo sem deduplicação
   → Cliente cobrado duas vezes
   ✓ Chave de idempotência obrigatória para operações financeiras
```

## 🧩 Quiz de Fixação

1. Um job de ETL precisa processar 500.000 arquivos CSV, cada um levando ~3 segundos. Com uma única instância, levaria ~17 horas. Como você usaria Lambda Fan-out com SQS para reduzir para menos de 5 minutos, e qual o custo estimado comparando as duas abordagens (EC2 m5.xlarge vs Lambda 512MB)?
2. Por que idempotência é um requisito indispensável ao paralelizar processamento com SQS, e qual técnica garante idempotência em operações de escrita no banco de dados?
3. Step Functions Map State tem o parâmetro MaxConcurrency. Por que simplesmente usar MaxConcurrency ilimitado (0) nem sempre é a melhor escolha, mesmo que tecnicamente processe mais rápido?

**Respostas:**
1) Arquitetura: Producer publica 500.000 mensagens no SQS (uma por arquivo). Auto Scaling Group de workers Lambda (ou ECS Fargate) consome em paralelo, com MaxConcurrency de 500-1000 (limitado pelo RDS/S3 de destino). Com 1.000 workers × 3s cada: 500.000/1.000 = 500 segundos = ~8 minutos. Refinando: SQS com Lambda Event Source Mapping (batch de 10 arquivos por invocação, 500 concorrentes) = 500.000/(500×10) = 100 lotes = 300 segundos = 5 minutos. Custo EC2 m5.xlarge × 17h = $3.26. Custo Lambda: 500.000 invocações × (512MB × 3s) = 750.000 GB-s × $0.0000166667 = $12.50 + $0.10 requests = $12.60. Lambda é mais caro nesse caso específico — para volumes de processamento contínuo e alto, ECS Spot seria mais econômico (~70% desconto sobre On-Demand). O ganho de 17 horas para 5 minutos frequentemente justifica o custo maior.
2) SQS garante at-least-once delivery — em condições de rede adversas, timeout ou reboot de worker, a mesma mensagem pode ser entregue mais de uma vez. Sem idempotência, processar um pagamento duas vezes cobra o cliente duas vezes. Técnicas para garantir idempotência em escrita: (1) INSERT ... ON CONFLICT DO NOTHING com chave única por operação (PostgreSQL/MySQL); (2) DynamoDB conditional write: `ConditionExpression='attribute_not_exists(pedido_id)'` — falha silenciosamente se o item já existir; (3) Tabela de deduplicação: antes de processar, verifica se `mensagem_id` já está na tabela de processados; (4) SQS FIFO com MessageDeduplicationId: SQS garante entrega única por deduplication ID na janela de 5 minutos.
3) MaxConcurrency ilimitado (0) pode ser problemático porque: (1) Downstream services têm limites — RDS suporta ~1.000 conexões; 10.000 workers simultâneos tentando conectar causam falhas em cascata; (2) Rate limits de APIs externas — chamar uma API de parceiro 10.000x/segundo pode violar o rate limit e causar bloqueio de IP; (3) Custo de Lambda Concurrency — pode esgotar o limite de concorrência da conta (padrão 1.000), throttlando outras funções críticas; (4) Escrita massiva simultânea no banco pode criar hotspots e degradar performance do banco para outros usuários. O MaxConcurrency ideal é calculado como: capacidade máxima do downstream ÷ throughput por worker. Ex: RDS suporta 500 conexões úteis → MaxConcurrency = 500.
