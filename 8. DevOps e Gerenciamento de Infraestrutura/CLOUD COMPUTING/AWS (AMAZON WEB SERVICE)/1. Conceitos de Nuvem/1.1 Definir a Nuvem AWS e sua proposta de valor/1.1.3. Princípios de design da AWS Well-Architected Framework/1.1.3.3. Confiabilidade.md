### Confiabilidade — projetar sistemas que se recuperam automaticamente de falhas

Confiabilidade é o terceiro pilar da AWS Well-Architected Framework. Ele trata da capacidade de um sistema executar sua função pretendida corretamente e de forma consistente — e de se recuperar automaticamente de falhas quando elas inevitavelmente ocorrem. Confiabilidade não é sobre evitar falhas; é sobre absorvê-las sem que o usuário perceba.

---

## O que é confiabilidade na prática

```
Sistema não confiável:
  Usuário faz pedido → serviço de pagamento falha → erro na tela
  → Usuário tenta de novo → erro de novo → abandona a compra
  → Empresa perde receita + reputação

Sistema confiável (mesmo com falha):
  Usuário faz pedido → serviço de pagamento falha
  → Sistema detecta falha → tenta outro provedor automaticamente
  → Ou: coloca na fila para retry → processa em segundos
  → Usuário vê: "Pedido confirmado" — nunca soube da falha

A diferença: o sistema confiável foi projetado esperando a falha.
```

O pilar de confiabilidade se organiza em **três áreas principais**:

---

## Área 1: Fundamentos (Foundations)

Antes de pensar em recuperação de falhas, os pré-requisitos de infraestrutura precisam estar corretos.

### Service Quotas (Limites de serviço)

Cada serviço AWS tem limites padrão (soft limits) que podem ser atingidos e causar falhas inesperadas:

```
Exemplos de service quotas:
  EC2: máximo de 32 vCPUs On-Demand por região (padrão)
  Lambda: 1.000 execuções concorrentes por região (padrão)
  SQS: máximo de 120.000 mensagens em voo por fila
  RDS: máximo de 40 instâncias por região (padrão)

O que acontece quando você atinge o limite:
  → API retorna ThrottlingException ou LimitExceededException
  → Sua aplicação falha inesperadamente em produção
  → Muitas vezes descoberto na pior hora (pico de tráfego)

Boas práticas:
  ├── Monitorar service quotas via CloudWatch (Service Quotas console)
  ├── Solicitar aumento de limite ANTES de precisar
  ├── Alertas quando atingir 80% do limite
  └── AWS Service Quotas: painel centralizado de todos os limites
```

### Topologia de rede bem projetada

```
VPC mal projetada (causa de falhas):
  ├── Subnet única → toda a aplicação na mesma AZ
  ├── CIDR muito pequeno → endereços IP esgotam com crescimento
  ├── Sem VPC Endpoints → tráfego S3/DynamoDB vai pela internet
  └── Roteamento incorreto → serviços não se comunicam

VPC confiável:
  ├── Múltiplas AZs (mínimo 2, ideal 3)
  ├── Subnets públicas: apenas ALB e NAT Gateway
  ├── Subnets privadas: EC2, RDS, ElastiCache (sem acesso direto da internet)
  ├── VPC Endpoints: S3, DynamoDB, Secrets Manager (sem NAT)
  └── CIDR generoso: /16 para VPC, /24 para subnets

Exemplo de topologia resiliente:
  VPC: 10.0.0.0/16
  ├── us-east-1a:
  │     Public subnet:  10.0.1.0/24  (ALB, NAT GW)
  │     Private subnet: 10.0.2.0/24  (EC2, RDS primary)
  ├── us-east-1b:
  │     Public subnet:  10.0.3.0/24  (ALB, NAT GW)
  │     Private subnet: 10.0.4.0/24  (EC2, RDS standby)
  └── us-east-1c:
        Public subnet:  10.0.5.0/24  (ALB)
        Private subnet: 10.0.6.0/24  (EC2)
```

## Área 2: Gerenciamento de mudanças (Change Management)

A maioria dos incidentes de produção tem origem em mudanças. Gerenciar mudanças de forma controlada é central para a confiabilidade.

### Monitorar recursos e demanda

```
CloudWatch Metrics → detecta tendências antes de virar problema:

Exemplo: crescimento de uso de banco de dados
  Jan: conexões médias = 50    (capacidade: 500)
  Fev: conexões médias = 120
  Mar: conexões médias = 220
  Abr: conexões médias = 380   ← CloudWatch Alarm: 75% do limite
  
  Ação proativa: aumentar instância ou implementar connection pooling
  ANTES de chegar a 100% e causar falha
```

### Adaptar-se automaticamente à demanda

```
Auto Scaling + CloudWatch = ajuste automático sem intervenção:

Regra: mantenha CPU média em 60%
  CPU = 80% → adiciona 2 instâncias → CPU volta para 55%
  CPU = 20% → remove 1 instância → CPU volta para 35%

Predictive Scaling:
  Analisa padrões históricos → provisiona ANTES do pico
  Ex: toda segunda-feira às 9h há pico de acessos
  → Às 8h45 já sobe instâncias → zero degradação no pico
```

### Implantar mudanças de forma controlada

```
Problema com deploy direto em produção:
  Deploy v2.0 → 100% dos usuários → bug crítico → rollback manual
  → Downtime: tempo de detecção + tempo de rollback

Deploy controlado (Canary):
  Deploy v2.0 → 5% dos usuários
  Monitorar por 10 minutos:
    ├── Error rate aumentou? → rollback automático dos 5%
    └── Tudo normal? → 25% → 50% → 100%
  
  Se problema: apenas 5% dos usuários afetados, por 10 minutos
  Rollback: automático, sem intervenção humana

AWS CodeDeploy com rollback automático:
  auto_rollback:
    enabled: true
    events:
      - DEPLOYMENT_FAILURE
      - CLOUDWATCH_ALARM  ← se alarm disparar durante deploy, reverte
```

## Área 3: Recuperação de falhas (Failure Management)

O coração da confiabilidade: o sistema deve se recuperar automaticamente.

### Backup e recuperação

```
Estratégia de backup por tipo de dado:

Dados críticos (banco de dados transacional):
  RDS Automated Backups:
  ├── Backup diário automático (janela de manutenção)
  ├── Transaction logs a cada 5 minutos
  ├── RPO: 5 minutos (perde no máximo 5min de dados)
  ├── Retenção: 1-35 dias configurável
  └── Point-in-Time Recovery: restaura para qualquer segundo
        dentro da janela de retenção

RDS Snapshots manuais:
  ├── Persistem além da retenção automática
  ├── Copiáveis para outra região (disaster recovery)
  └── Compartilháveis entre contas

Objetos e arquivos (S3):
  S3 Versioning:
  ├── Mantém todas as versões de cada objeto
  ├── Restaura versão anterior com 1 clique
  └── Protege contra delete acidental e ransomware

  S3 Cross-Region Replication:
  ├── Replica objetos para outra região automaticamente
  └── RPO: segundos (replicação quase em tempo real)
```

### Testar procedimentos de recuperação

```
Erro comum: fazer backup mas nunca testar a restauração

"Você não tem backup — você tem uma tentativa de backup.
 Backup real é o que você consegue restaurar."

Testes de recuperação regulares:
  ├── Mensal: restaurar RDS snapshot em ambiente de staging
  ├── Trimestral: simular failover Multi-AZ
  ├── Semestral: simular disaster recovery regional completo
  └── Documentar: quanto tempo levou? O que falhou?

AWS Backup Audit Manager:
  ├── Verifica automaticamente se backups estão sendo feitos
  ├── Reporta conformidade com políticas de backup
  └── Alertas se algum recurso não está sendo protegido
```

### Escala horizontal para aumentar disponibilidade

```
Por que horizontal é mais confiável que vertical:

Vertical (1 instância grande):
  ┌─────────────────┐
  │   m6i.16xlarge  │  ← single point of failure
  │   64 vCPU       │     se falhar: 100% de impacto
  │   256 GB RAM    │
  └─────────────────┘

Horizontal (múltiplas instâncias menores):
  [ALB]
    ├── [m6i.xlarge AZ-a]  ← se falhar: 33% de impacto
    ├── [m6i.xlarge AZ-b]  ← ALB remove do pool automaticamente
    └── [m6i.xlarge AZ-c]  ← ASG lança substituta
  
  Custo similar, disponibilidade muito maior
```

### Parar de adivinhar capacidade

```
Anti-padrão: provisionar baseado em estimativa
  "Acho que vamos ter 10.000 usuários" → compra hardware para 10.000
  → Se forem 100.000: sistema cai
  → Se forem 1.000: hardware desperdiçado

Confiabilidade real: provisionar baseado em dados reais
  Começar pequeno + Auto Scaling + CloudWatch
  → Sistema cresce (ou encolhe) com a demanda real
  → Sem surpresas, sem superprovisionamento
```

## Padrões de confiabilidade na AWS

### Circuit Breaker

```
Problema: serviço B está lento → serviço A fica esperando →
          threads do A esgotam → A também cai → falha em cascata

Circuit Breaker pattern:
  FECHADO (normal):
    A → B (funciona normalmente)
  
  ABERTO (após N falhas consecutivas):
    A → retorna erro imediatamente (sem esperar B)
    → Protege o A de ser arrastado pela falha do B
    → Dá tempo para B se recuperar
  
  SEMI-ABERTO (após timeout):
    Testa se B voltou → se sim: fecha o circuito
                      → se não: mantém aberto

Na AWS:
  AWS App Mesh (Envoy) implementa circuit breaker nativamente
  Lambda + Step Functions: retry com backoff exponencial
  SDK AWS: retry automático com jitter
```

### Retry com Backoff Exponencial

```
Falha transiente (rede momentaneamente instável):
  Sem retry: usuário vê erro
  
  Com retry simples (retry imediato):
  Tentativa 1: falha → retry imediato
  Tentativa 2: falha → retry imediato (servidor ainda sobrecarregado)
  Tentativa 3: falha → pior ainda (thundering herd)

  Com backoff exponencial + jitter:
  Tentativa 1: falha → aguarda 1s (+ jitter aleatório)
  Tentativa 2: falha → aguarda 2s (+ jitter)
  Tentativa 3: falha → aguarda 4s (+ jitter)
  Tentativa 4: sucesso ✓
  
  → Dá tempo para o serviço se recuperar
  → Jitter evita que todos retryem ao mesmo tempo

SDK AWS implementa isso automaticamente para chamadas de API.
```

### Bulkhead (Compartimentalização)

```
Analogia: compartimentos estanques de um navio
  Se um compartimento alaga, os outros ficam intactos
  O navio não afunda inteiro

Na AWS:
  SQS separadas por tipo de processamento:
  ├── Fila de pedidos críticos   → workers dedicados (pool A)
  ├── Fila de relatórios         → workers dedicados (pool B)
  └── Fila de notificações       → workers dedicados (pool C)
  
  Se a geração de relatórios explodir em volume:
  → Pool B fica sobrecarregado
  → Pool A (pedidos críticos) não é afetado
  → Usuários continuam fazendo pedidos normalmente
```

## Métricas de confiabilidade

```
Disponibilidade e o que significa na prática:

99%     → ~87 horas de downtime/ano   (inaceitável para produção)
99.9%   → ~8.7 horas de downtime/ano  (básico)
99.95%  → ~4.4 horas de downtime/ano  (médio)
99.99%  → ~52 minutos de downtime/ano (alto)
99.999% → ~5 minutos de downtime/ano  (missão crítica)

SLA dos serviços AWS (exemplos):
  S3:       99.99% (designed for 99.999999999% de durabilidade)
  EC2:      99.99% (com Multi-AZ)
  RDS:      99.95% (single-AZ) / 99.99% (Multi-AZ)
  DynamoDB: 99.99% (por padrão)
  Lambda:   99.95%
```

## 🧩 Quiz de Fixação

1. Uma aplicação começa a falhar esporadicamente em produção com `ThrottlingException` no Lambda. O que provavelmente causou isso e como prevenir com antecedência?
2. Qual a diferença entre RPO e RTO, e como o RDS Multi-AZ com backups automáticos atende a cada um deles?
3. Um serviço de checkout depende de um serviço de estoque que está lento. Sem Circuit Breaker, o que acontece? Como o padrão Circuit Breaker protege o serviço de checkout?

**Respostas:**
1) A aplicação atingiu o service quota de 1.000 execuções simultâneas de Lambda na região (limite padrão). Para prevenir: monitorar a métrica `ConcurrentExecutions` no CloudWatch com alarme em 80% do limite (800); solicitar aumento de quota antes de atingir o limite via Service Quotas console; implementar SQS como buffer (Lambda processa da fila em vez de ser invocado diretamente) para absorver picos sem atingir o limite de concorrência; e usar Reserved Concurrency para garantir capacidade para funções críticas.
2) RPO (Recovery Point Objective) é quanto de dado pode ser perdido — o RDS com backups automáticos a cada 5 minutos de transaction logs garante RPO de ~5 minutos (perde no máximo 5 minutos de dados em caso de falha total). RTO (Recovery Time Objective) é quanto tempo leva para recuperar — o RDS Multi-AZ garante RTO de 1-2 minutos (failover automático para o standby sem intervenção humana), enquanto restaurar de backup pode levar 15-60 minutos dependendo do tamanho do banco.
3) Sem Circuit Breaker: o serviço de checkout faz chamadas ao serviço de estoque que ficam pendentes aguardando resposta (timeout longo). As threads do checkout ficam presas esperando. Com volume de tráfego normal, todas as threads do checkout ficam bloqueadas aguardando o estoque → o checkout fica sem threads disponíveis → também começa a falhar → falha em cascata. Com Circuit Breaker: após N falhas consecutivas no estoque, o circuito "abre" e o checkout para de chamar o estoque imediatamente, retornando um fallback (ex: "estoque não verificado, pedido aceito com ressalva") ou erro rápido. O checkout continua funcionando, o estoque tem tempo de se recuperar, e quando se recuperar o circuito fecha automaticamente.
