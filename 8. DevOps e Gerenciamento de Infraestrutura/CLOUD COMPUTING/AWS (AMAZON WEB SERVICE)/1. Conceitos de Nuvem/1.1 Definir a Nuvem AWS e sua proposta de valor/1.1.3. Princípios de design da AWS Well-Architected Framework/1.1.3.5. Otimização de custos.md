### Otimização de custos — pagar apenas pelo que entrega valor, nada mais

Otimização de custos é o quinto pilar da AWS Well-Architected Framework. Ele trata da capacidade de executar sistemas ao menor custo possível, entregando o valor de negócio esperado. Não se trata de ser barato — trata-se de eliminar desperdício, usar o modelo de precificação certo para cada carga e ter visibilidade financeira real sobre o que está sendo gasto e por quê.

---

## FinOps: a disciplina por trás da otimização de custos

```
FinOps (Financial Operations) é a prática de trazer
responsabilidade financeira para a cultura cloud:

Modelo antigo (on-premises):
  → Time de infra compra hardware → custo fixo anual
  → Desenvolvedores não veem custo de suas decisões
  → "Usar mais RAM não custa nada para mim"

Modelo cloud sem FinOps:
  → Desenvolvedor sobe instância p3.16xlarge para teste
  → Esquece ligada por 30 dias
  → Custo: $14.688 por um teste que durou 2 horas
  → Ninguém percebeu até chegar a fatura

Modelo cloud com FinOps:
  → Todo recurso tem tag de dono/produto/ambiente
  → Budget alarms disparam se gasto exceder threshold
  → Times veem e são responsáveis pelo custo de suas decisões
  → Otimizações são contínuas, não acontecimentos anuais
```

O pilar organiza-se em **5 áreas de boas práticas**:

## Área 1: Praticar Cloud Financial Management

### Visibilidade: saber onde o dinheiro está indo

```
AWS Cost Explorer:
  Dashboard de custos com filtros por:
  ├── Serviço: quanto cada serviço custa
  ├── Região: quanto cada região custa
  ├── Tag: quanto cada produto/time/ambiente custa
  ├── Conta: quanto cada conta AWS custa (Organizations)
  └── Período: comparar mês a mês, detectar anomalias

Exemplo de análise:
  Total mensal: $45.000
  ├── EC2: $28.000 (62%)
  │     ├── Prod: $18.000
  │     ├── Staging: $7.000  ← suspeito (muito próximo de prod)
  │     └── Dev: $3.000
  ├── RDS: $8.000 (18%)
  ├── S3: $2.000 (4%)
  └── Outros: $7.000 (16%)

Ação imediata: por que Staging custa quase tanto quanto Prod?
→ Provavelmente instâncias superdimensionadas em staging
→ Staging não precisa rodar 24/7
```

### Tags: a base da visibilidade financeira

```
Sem tags:
  Fatura: $45.000 em EC2
  → Quem gastou? Para qual produto? Qual ambiente?
  → Impossível saber → impossível otimizar

Com tags estruturadas:
  Obrigatórias em todo recurso:
  ├── Environment: production | staging | development
  ├── Product: checkout | search | recommendation | data-science
  ├── Team: backend | frontend | platform | data
  └── Owner: joao.silva | maria.santos

  Resultado:
  Product=checkout → $12.000/mês
  Product=search → $8.000/mês
  Team=data-science → $15.000/mês
  Environment=development → $3.000/mês (candidato a redução noturna)

AWS Tag Policies (via Organizations):
  → Força tags obrigatórias em todos os recursos
  → Recursos sem tags são marcados como não conformes
  → Relatório de conformidade de tagging
```

### AWS Budgets: alertas proativos

```
Tipos de Budget:

1. Cost Budget:
   "Alerta se gastar mais de $50.000 no mês"
   ├── Alerta em 80% ($40.000): "atenção, você está no caminho"
   ├── Alerta em 100% ($50.000): "limite atingido"
   └── Alerta de previsão: "você vai gastar $62.000 este mês"

2. Usage Budget:
   "Alerta se usar mais de 1.000 horas de EC2"

3. Reservation Budget:
   "Alerta se utilização de Reserved Instances cair abaixo de 80%"

4. Savings Plans Budget:
   "Alerta se cobertura de Savings Plans cair abaixo de 90%"

Cost Anomaly Detection:
   ML detecta gastos anômalos automaticamente
   "Gasto em Lambda aumentou 300% vs. semana passada"
   → Alerta imediato antes de virar fatura grande
```

## Área 2: Adotar um modelo de consumo (Pay for What You Use)

### Eliminar recursos ociosos

```
Recursos mais comuns desperdiçados:

EC2 paradas/subutilizadas:
  ├── Instâncias com CPU < 5% por semanas → candidatas a stop/terminate
  ├── "Servidor de testes" que ninguém usa há 3 meses
  └── Dev environments que rodam 24/7 mas são usados 8h/dia

Ação: schedule para ligar/desligar automaticamente
  EventBridge Scheduler:
  Segunda-Sexta 8h: aws ec2 start-instances --instance-ids i-xxx
  Segunda-Sexta 20h: aws ec2 stop-instances --instance-ids i-xxx
  Sábado/Domingo: permanecem desligadas
  Economia: ~66% do custo das instâncias de dev

EBS volumes não associados:
  → Snapshot e terminate a instância → volume fica órfão
  → Cobra $0.08/GB/mês sem fazer nada
  
  Detectar: aws ec2 describe-volumes --filters Name=status,Values=available
  Ação: snapshot → delete (ou script automatizado)

Elastic IPs não utilizados:
  → IPs alocados mas não associados a instâncias
  → Cobra $0.005/hora ($3.60/mês cada)
  → Deletar quando não estiver em uso

Load Balancers sem backends:
  → ALB sem targets registrados: cobra $0.008/hora + LCUs
  → Deletar quando não estiver em uso

RDS parado mas não deletado:
  → RDS parado: cobra apenas storage (não compute)
  → Mas continua acumulando custo de storage + snapshots
  → Se não vai usar em 7 dias: snapshot + delete
```

### Dimensionar pelo uso real (Right-sizing)

```
AWS Compute Optimizer analisa 14 dias de métricas:

Cenário real de right-sizing:
  Instância atual: m5.2xlarge (8 vCPU, 32GB RAM)
  Custo: $0.384/hora = $276/mês

  Métricas reais (14 dias):
  ├── CPU: média 12%, p99: 35%
  └── RAM: média 8GB usados (25% de 32GB)

  Recomendação do Compute Optimizer:
  → m5.xlarge (4 vCPU, 16GB RAM)
  → Custo: $0.192/hora = $138/mês
  → Economia: $138/mês (50%)
  → Performance: adequada (p99 de CPU terá headroom suficiente)

Escala de impacto em uma frota grande:
  100 instâncias superdimensionadas × $138/mês = $13.800/mês economizados
  = $165.600/ano de economia apenas com right-sizing
```

## Área 3: Medir eficiência geral (Measure Overall Efficiency)

```
Métrica-chave: custo por unidade de negócio

Não basta saber que gastou $50.000/mês.
Precisa saber: qual o custo para atender 1 usuário?
              Qual o custo por pedido processado?
              Qual o custo por GB de dados analisado?

Exemplo:
  Janeiro:
    Custo AWS: $30.000
    Pedidos processados: 100.000
    Custo por pedido: $0.30

  Março (após otimizações):
    Custo AWS: $28.000
    Pedidos processados: 150.000
    Custo por pedido: $0.187

  → O custo absoluto caiu E o volume cresceu
  → Eficiência melhorou 37% por unidade de negócio

Custom metrics no CloudWatch:
  Publicar métricas de negócio (pedidos/hora, usuários ativos)
  Cruzar com métricas de custo no Cost Explorer
  → Visibilidade de custo unitário ao longo do tempo
```

## Área 4: Parar de gastar em tarefas indiferenciadas

```
Tarefas indiferenciadas = trabalho pesado que não diferencia
seu negócio mas consome recursos

Exemplos:
  Gerenciar servidor de banco de dados:
  ├── Patches de SO e banco
  ├── Configurar replicação
  ├── Implementar backups
  ├── Monitorar performance
  └── Fazer failover manual

  → Usar RDS: AWS faz tudo isso → você foca em schema e queries

  Gerenciar cluster de Kubernetes:
  ├── Provisionar masters e workers
  ├── Atualizar versão do Kubernetes
  ├── Gerenciar certificados
  └── Monitorar saúde do cluster

  → Usar EKS: AWS gerencia o control plane → você foca nos pods

Regra: se um serviço gerenciado da AWS resolve seu problema,
       use-o. O custo de engenharia para manter auto-gerenciado
       frequentemente supera o custo adicional do serviço gerenciado.
```

## Área 5: Analisar e atribuir despesas (Expenditure Attribution)

### Modelos de precificação: escolher o certo para cada workload

```
On-Demand:
  ├── Paga por hora/segundo sem compromisso
  ├── Mais caro por hora
  └── Use para: cargas imprevisíveis, experimentos, picos temporários

Reserved Instances (RI):
  ├── Compromete-se com 1 ou 3 anos
  ├── Desconto: 30-60% vs On-Demand
  ├── Tipos:
  │     Standard RI: desconto máximo, sem flexibilidade de tipo
  │     Convertible RI: menor desconto, pode trocar tipo/tamanho
  └── Use para: workloads estáveis e previsíveis 24/7

Savings Plans:
  ├── Compromete gasto mínimo por hora (ex: $10/hora)
  ├── Desconto similar ao RI mas mais flexível
  ├── Compute Savings Plans: cobre EC2 qualquer tipo/região + Lambda + Fargate
  └── Use para: quando não sabe exatamente qual instância vai usar

Spot Instances:
  ├── Capacidade ociosa da AWS com desconto de 70-90%
  ├── Pode ser interrompida com aviso de 2 minutos
  ├── Use para: batch jobs, ML training, rendering, CI/CD workers
  └── NUNCA use para: banco de dados primário, aplicação stateful crítica

Dedicated Hosts:
  ├── Servidor físico dedicado ao seu uso
  ├── Necessário para: licenças por socket/core (Oracle, Windows Server)
  └── Mais caro — use apenas quando licença exige

Comparativo de custo (exemplo m5.xlarge por mês):
  On-Demand:    ~$140/mês
  1yr Reserved: ~$89/mês  (36% desconto)
  3yr Reserved: ~$60/mês  (57% desconto)
  Spot:         ~$28/mês  (80% desconto, interruptível)
```

### Estratégia de mix de pricing

```
Workload de produção estável (web server):
  Baseline garantida: Reserved/Savings Plans (70% da capacidade)
  + Picos: On-Demand via Auto Scaling (20%)
  + Buffer: Spot (10% com diversificação de tipos)
  
  Economia vs. 100% On-Demand: 40-50%

ML Training (batch, tolerante a interrupção):
  100% Spot com checkpointing:
  → Se interrompido, recomeça do último checkpoint
  → Economia: ~80% vs On-Demand

CI/CD workers:
  Spot Fleet com múltiplos tipos de instância:
  → Se um tipo não está disponível, usa outro
  → Reduz risco de interrupção
  → Economia: ~70% vs On-Demand
```

## Ferramentas de otimização de custos na AWS

```
AWS Compute Optimizer:
  → Recomendações de right-sizing para EC2, Lambda, EBS
  → Gratuito

AWS Cost Explorer:
  → Análise histórica e previsão de custos
  → Recomendações de RI e Savings Plans
  → Gratuito (relatórios detalhados têm custo)

AWS Trusted Advisor:
  → Verifica: instâncias EC2 subutilizadas
  → Verifica: EBS volumes não utilizados
  → Verifica: Elastic IPs não utilizados
  → Verifica: RDS instâncias ociosas
  → Acesso completo: plano Business ou Enterprise

  → Dados granulares de custo por hora/recurso/tag

Savings Plans recommendations (Cost Explorer):
  → "Se você comprar $15/hora de Compute Savings Plans
     por 1 ano, economizará $48.000 vs. On-Demand atual"
```

## Padrões práticos de otimização

```
1. Desligar ambientes de não-produção fora do horário:
   Dev/Staging: ligar 8h, desligar 20h, fim de semana desligado
   Economia: ~66% do custo dessas instâncias

2. S3 Intelligent-Tiering para dados com acesso imprevisível:
   Dados acessados frequentemente: S3 Standard (normal)
   Dados não acessados por 30 dias: automove para Infrequent Access
   Dados não acessados por 90 dias: Glacier Instant Retrieval
   Sem overhead operacional, economia automática

3. CloudFront na frente de S3/ALB:
   Reduz custo de data transfer do S3/ALB (até $0.09/GB)
   CloudFront: $0.0085/GB para primeiros 10TB
   Economia: ~90% em custo de egress para conteúdo estático

4. Lambda Power Tuning:
   Ferramenta open source que testa sua função em múltiplas
   configurações de memória e encontra o ponto ótimo
   custo × performance (nem mais memória, nem menos)

5. RDS: usar Read Replicas antes de aumentar instância:
   Read Replica r6g.large: $0.24/hora
   vs. Upgrade de r6g.xlarge para r6g.2xlarge: +$0.48/hora
   Solução: mais barata e escala melhor
```

## 🧩 Quiz de Fixação

1. Uma empresa tem 50 instâncias EC2 m5.2xlarge em produção rodando 24/7. O Compute Optimizer indica que todas são candidatas a downgrade para m5.xlarge. Além do right-sizing, qual modelo de precificação deveria ser aplicado para maximizar a economia nessas instâncias previsíveis?
2. Um time de data science usa instâncias p3.8xlarge ($12.24/hora) para treinar modelos de ML. Os treinos levam 6-8 horas e são interruptíveis com checkpointing. Qual estratégia de precificação é ideal e qual a economia estimada?
3. A fatura de AWS chegou em $120.000 e ninguém sabe exatamente o que gerou esse custo. Que prática de FinOps fundamental estava ausente e quais seriam os primeiros três passos para ganhar visibilidade?

**Respostas:**
1) Right-sizing para m5.xlarge + Savings Plans (ou Reserved Instances de 1-3 anos). Como são instâncias previsíveis e estáveis 24/7, comprometer-se com Savings Plans (Compute) de 1 ano garante ~36% de desconto. Se o tipo de instância for fixo, Reserved Instances Standard de 3 anos garante ~57%. Combinando right-sizing (50% de economia) + Reserved de 1 ano (36% de desconto adicional): de $276/instância/mês → $89/instância/mês, economia total de ~$9.350/mês para as 50 instâncias (~$112.000/ano).
2) Spot Instances com checkpointing. p3.8xlarge Spot custa ~$2.45-$3.67/hora (70-80% de desconto vs $12.24/hora On-Demand). Com checkpointing, se a instância for interrompida, o treino recomeça do último ponto salvo em S3 — sem perder todo o progresso. Estratégia adicional: usar Spot Fleet com múltiplos tipos de instância (p3.8xlarge + p3.16xlarge + p2.8xlarge) para reduzir risco de interrupção. Economia: treino de 7h × $12.24 = $85.68 On-Demand → ~$17-$26 com Spot = 70-80% de economia.
3) A prática ausente foi **tagging estruturado** — sem tags, é impossível atribuir custo a times, produtos ou ambientes. Primeiros três passos: (1) Implementar Tag Policy via AWS Organizations com tags obrigatórias (Environment, Product, Team, Owner) e configurar relatório de conformidade de tagging; (2) Ativar AWS Cost Explorer e filtrar por serviço para identificar os maiores custos — geralmente EC2 e RDS respondem por 70-80%; (3) Ativar Cost Anomaly Detection para receber alertas automáticos de gastos anômalos via ML, evitando surpresas no futuro. Com essas três ações, em 30 dias há visibilidade suficiente para priorizar otimizações.
