### Segurança — projetar sistemas seguros por design, não por correção

Segurança é o segundo pilar da AWS Well-Architected Framework e permeia todos os outros. Ele trata da capacidade de proteger informações, sistemas e ativos enquanto entrega valor ao negócio. Na AWS, segurança não é uma camada adicionada depois — é um princípio que deve estar presente desde a concepção da arquitetura.

---

## O princípio fundamental: Security by Design

```
Segurança retroativa (anti-padrão):
  Constrói o sistema → coloca em produção → adiciona segurança
  → Resultado: brechas estruturais difíceis de corrigir,
    permissões excessivas consolidadas, custo alto de remediação

Security by Design (correto):
  Define requisitos de segurança → projeta o sistema com eles
  → Resultado: menor superfície de ataque, permissões mínimas
    desde o início, custo muito menor de manutenção
```

A AWS estrutura o pilar de segurança em **7 áreas de boas práticas**:

---

## Área 1: Fundamentos de segurança (Security Foundations)

Antes de qualquer serviço, estabelecer a base:

```
Conta AWS raiz (root):
  ├── Nunca usar para operações do dia a dia
  ├── MFA obrigatório na conta raiz
  ├── Não criar access keys para root
  └── Usar apenas para tarefas que exigem root (ex: fechar conta)

AWS Organizations:
  ├── Centraliza múltiplas contas AWS
  ├── Service Control Policies (SCPs): limites máximos de permissão
  │     Exemplo: "Nenhuma conta pode criar recursos fora de us-east-1 e sa-east-1"
  ├── Contas separadas por ambiente (dev, staging, prod)
  └── Consolidated Billing: visibilidade de custos por conta

Estrutura de contas recomendada:
  Organização
  ├── Management Account (apenas billing e organizações)
  ├── Security Account (GuardDuty, Security Hub, logs centralizados)
  ├── Shared Services (Active Directory, DNS, ferramentas compartilhadas)
  ├── Production Account
  ├── Staging Account
  └── Development Account
```

## Área 2: Gerenciamento de identidade e acesso (IAM)

O princípio do **menor privilégio** é a base de toda segurança na AWS:

```
Menor privilégio:
  Conceder apenas as permissões estritamente necessárias
  para realizar a tarefa específica

❌ Anti-padrão:
  Política: AdministratorAccess para o desenvolvedor
  → Pode criar, modificar e deletar qualquer recurso
  → Se credencial for comprometida: catástrofe total

✓ Correto:
  Política: acesso read-only ao S3 bucket específico
            + permissão de escrita apenas na pasta /uploads
  → Se credencial for comprometida: dano limitado

Exemplo de política IAM mínima (S3 específico):
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": [
      "s3:GetObject",
      "s3:PutObject"
    ],
    "Resource": "arn:aws:s3:::meu-bucket/uploads/*"
  }]
}

Comparado com:
{
  "Effect": "Allow",
  "Action": "s3:*",        ← tudo no S3: perigoso
  "Resource": "*"           ← qualquer bucket: perigoso
}
```

### IAM Roles vs. IAM Users

```
IAM Users (credenciais permanentes):
  Access Key ID + Secret Access Key
  → Credenciais de longa duração → maior risco se vazarem
  → Use apenas para automação que não suporta roles

IAM Roles (credenciais temporárias):
  → EC2, Lambda, ECS assumem roles automaticamente
  → Credenciais temporárias (expiram em 1-12h)
  → Sem access keys hardcoded no código
  → Rotação automática → menor risco

✓ Padrão correto para aplicação no EC2:
  1. Cria IAM Role com permissões necessárias
  2. Associa a role à instância EC2
  3. Aplicação usa SDK → pega credenciais automaticamente
     via Instance Metadata Service (IMDS)
  4. Sem credenciais no código, sem .env com secrets
```

## Área 3: Detecção (Detection)

Monitorar ativamente o ambiente para identificar comportamentos anômalos:

```
AWS CloudTrail:
  Registra TODAS as chamadas de API na conta
  → Quem fez o quê, quando, de onde
  
  Exemplo de log:
  {
    "eventTime": "2024-03-15T14:32:00Z",
    "userIdentity": {"arn": "arn:aws:iam::123:user/joao"},
    "eventName": "DeleteBucket",
    "requestParameters": {"bucketName": "producao-dados-criticos"}
  }
  → Auditoria: quem deletou o bucket de produção?

Amazon GuardDuty:
  Threat detection service — analisa automaticamente:
  ├── VPC Flow Logs (tráfego de rede suspeito)
  ├── DNS Logs (consultas a domínios maliciosos)
  └── CloudTrail Events (comportamento de API anômalo)
  
  Exemplos de alertas:
  ├── "EC2 instance comunicando com IP de botnet conhecida"
  ├── "Credencial usada de país diferente do padrão (travel anomaly)"
  ├── "Tentativa de cryptocurrency mining detectada"
  └── "Port scanning originado de EC2 interna"

AWS Security Hub:
  Centraliza findings de GuardDuty, Inspector, Macie, Config
  → Dashboard único de postura de segurança
  → Prioriza por severidade
  → Integra com SIEM externos (Splunk, etc.)

Amazon Macie:
  Descobre e protege dados sensíveis no S3:
  ├── PII (CPF, nome, email, cartão de crédito)
  ├── Credenciais (senhas, access keys em arquivos)
  └── Dados financeiros
  → Alerta se bucket S3 expõe dados sensíveis publicamente
```

## Área 4: Proteção de infraestrutura (Infrastructure Protection)

Controlar o que pode entrar e sair de cada camada:

```
Defesa em profundidade (Defense in Depth):

Internet
    │
[AWS WAF]              ← Layer 7: bloqueia SQLi, XSS, bad bots
    │
[CloudFront]           ← CDN + absorção de DDoS (AWS Shield)
    │
[ALB]                  ← Load balancer com SSL termination
    │
[Security Group]       ← Firewall stateful de instância
    │
[EC2 (app)]            ← Apenas recebe tráfego do ALB
    │
[Security Group]       ← Banco só aceita tráfego da app
    │
[RDS]                  ← Em subnet privada, sem acesso público

Cada camada filtra independentemente.
Se WAF falhar, Security Group ainda protege.
Se Security Group for mal configurado, NACL ainda filtra.
```

### Security Groups vs. NACLs

```
Security Groups (nível de instância):
  ├── Stateful: permite resposta automaticamente
  ├── Apenas ALLOW (sem DENY explícito)
  └── Aplicado por instância/ENI

NACLs (nível de subnet):
  ├── Stateless: precisa de regra de entrada E saída
  ├── ALLOW e DENY explícitos
  └── Aplicado a toda a subnet

Uso combinado:
  NACL da subnet: bloqueia IPs maliciosos conhecidos (DENY)
  Security Group: define o que pode acessar cada instância (ALLOW)
```

## Área 5: Proteção de dados (Data Protection)

Criptografar dados em repouso e em trânsito:

```
Dados em trânsito:
  ├── HTTPS/TLS obrigatório (ACM: certificados gratuitos)
  ├── VPC endpoints: tráfego AWS não sai para internet
  ├── Direct Connect: link dedicado on-premises → AWS
  └── VPN: túnel criptografado

Dados em repouso:
  ├── S3: SSE-S3 (AWS gerencia chaves), SSE-KMS (você controla)
  ├── EBS: criptografia AES-256 com KMS
  ├── RDS: criptografia habilitada na criação (não após)
  └── Secrets: AWS Secrets Manager (rotação automática de credenciais)

AWS KMS (Key Management Service):
  ├── Cria e gerencia chaves de criptografia
  ├── Integrado nativamente com S3, RDS, EBS, Lambda...
  ├── Audit trail de quem usou qual chave (CloudTrail)
  └── Rotação automática anual de chaves

AWS Secrets Manager:
  ❌ Anti-padrão: senha do banco hardcoded no código
  
  ✓ Correto:
  // Código busca a senha dinamicamente
  secret = secretsmanager.get_secret_value("prod/db/password")
  
  → Rotação automática a cada 30/60/90 dias
  → Auditoria de quem acessou qual secret
  → Aplicação nunca vê a senha real no código
```

## Área 6: Proteção de dados em repouso — classificação

```
Classificação de dados:
  Nível 1 — Público:        pode ser exposto sem impacto
  Nível 2 — Interno:        uso interno, não expor externamente
  Nível 3 — Confidencial:   dados de negócio sensíveis
  Nível 4 — Restrito/PII:   dados pessoais, financeiros, saúde

Por nível, aplicar controles diferentes:
  Nível 1: S3 público OK
  Nível 2: S3 privado, sem criptografia obrigatória
  Nível 3: S3 com SSE-KMS, acesso restrito por IAM
  Nível 4: S3 com SSE-KMS + Macie + audit logs + retenção
```

## Área 7: Resposta a incidentes (Incident Response)

Ter um plano antes do incidente — não durante:

```
Plano de resposta a incidente de segurança:

1. PREPARAÇÃO:
   ├── Definir playbooks para cenários comuns
   │   (credencial comprometida, EC2 minerando crypto,
   │    bucket S3 exposto publicamente, etc.)
   ├── Conta de segurança isolada com acesso de leitura
   ├── Snapshots automáticos para análise forense
   └── AWS Config rules: detecta configurações inseguras

2. DETECÇÃO:
   GuardDuty + Security Hub → alerta automático
   PagerDuty/OpsGenie → notifica o time de resposta

3. CONTENÇÃO:
   Credencial comprometida:
   → aws iam delete-access-key --access-key-id AKIA...
   → Revoga permissões imediatamente
   
   EC2 comprometida:
   → Isola a instância (Security Group que bloqueia tudo)
   → Tira snapshot para análise forense
   → NÃO termina ainda (preserva evidências)

4. ERRADICAÇÃO E RECUPERAÇÃO:
   → Remove o vetor de ataque
   → Restaura de backup limpo
   → Valida integridade

5. PÓS-INCIDENTE:
   → Post-mortem: como aconteceu, como prevenir
   → Atualiza playbooks
   → Implementa controles adicionais
```

## 🧩 Quiz de Fixação

1. Um desenvolvedor recebe a policy `AdministratorAccess` no IAM "para facilitar o desenvolvimento". Por que isso viola o pilar de segurança do Well-Architected e qual seria a abordagem correta?
2. Qual a diferença entre Security Groups e NACLs, e por que usar os dois juntos representa defesa em profundidade?
3. Uma aplicação armazena a senha do banco de dados como variável de ambiente no código. Qual serviço AWS resolve esse problema e quais são as vantagens além de simplesmente "não ter a senha no código"?

**Respostas:**
1) Viola o princípio do menor privilégio — AdministratorAccess permite criar, modificar e destruir qualquer recurso em qualquer serviço da conta. Se as credenciais do desenvolvedor forem comprometidas (phishing, credencial vazada no GitHub, etc.), o atacante tem controle total da conta AWS. A abordagem correta é criar uma policy customizada com apenas as permissões que o desenvolvedor realmente precisa para as tarefas do dia a dia (ex: acesso a serviços específicos em ambiente de dev), e usar IAM Identity Center (SSO) com sessões temporárias em vez de access keys permanentes.
2) Security Groups são stateful (permitem resposta automaticamente) e operam no nível da instância — definem o que pode acessar cada recurso individualmente. NACLs são stateless (precisam de regras de entrada e saída explícitas) e operam no nível da subnet — aplicam a todos os recursos dela. Usar os dois juntos cria defesa em profundidade: se um Security Group for mal configurado acidentalmente (ex: abre para 0.0.0.0/0), a NACL ainda pode bloquear IPs maliciosos conhecidos na camada de subnet, limitando o dano.
3) AWS Secrets Manager. As vantagens além de remover a senha do código: (1) Rotação automática das credenciais em intervalos configuráveis (30/60/90 dias) — a aplicação sempre pega a senha atual via API, sem redeploy; (2) Auditoria completa via CloudTrail de quem acessou qual secret e quando — visibilidade de segurança; (3) Acesso controlado por IAM — apenas as roles autorizadas podem ler o secret; (4) Versionamento — pode reverter para versão anterior da credencial; (5) Integração nativa com RDS para rotação automática de senha do banco sem downtime.
