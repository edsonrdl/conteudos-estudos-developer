### Sustentabilidade — reduzir o impacto ambiental de sistemas na nuvem

Sustentabilidade é o sexto e mais recente pilar da AWS Well-Architected Framework, adicionado em dezembro de 2021. Ele trata da responsabilidade de minimizar o impacto ambiental de cargas de trabalho em nuvem — especialmente consumo de energia e emissões de carbono. É o único pilar cujo beneficiário primário não é o negócio em si, mas o planeta. Curiosamente, as práticas de sustentabilidade frequentemente se sobrepõem às de otimização de custos: um workload eficiente consome menos energia e custa menos.

---

## Por que sustentabilidade importa na nuvem

```
Impacto de TI no clima global:
  Setor de TI: responsável por ~2-4% das emissões globais de CO₂
  (comparável à aviação civil)
  
  Data centers globais: ~1-2% do consumo elétrico mundial
  
  Tendência: crescimento exponencial de dados, ML e streaming
  → Sem eficiência ativa, impacto ambiental cresce junto

Por que a nuvem já é mais sustentável que on-premises:
  Data center corporativo típico:
  ├── PUE (Power Usage Effectiveness): 1.5-2.0
  ├── Utilização de servidores: 15-20%
  └── Energia renovável: baixa ou zero

  AWS data centers modernos:
  ├── PUE: 1.1-1.2 (eficiência 25-40% superior)
  ├── Utilização de servidores: 65-75% (via multitenancy)
  └── Meta: 100% energia renovável até 2025

  Migrar para AWS pode reduzir a pegada de carbono
  de uma empresa em até 80% vs. data center próprio.
```

## Os 6 princípios de design de sustentabilidade

### 1. Entender seu impacto

```
O primeiro passo é medir:

AWS Customer Carbon Footprint Tool:
  ├── Disponível no AWS Billing Console
  ├── Mostra emissões estimadas de CO₂ equivalente
  ├── Breakdown por serviço, região e período
  ├── Compara sua pegada vs. equivalente on-premises
  └── Rastreia tendência mês a mês

Exemplo de relatório:
  Período: 2024 Q1
  Emissões estimadas AWS: 12 toneladas CO₂e
  Emissões equivalentes on-premises: 85 toneladas CO₂e
  Redução pela nuvem: 86%
  
  Por serviço:
  ├── EC2: 7.2 tCO₂e (60%)
  ├── RDS: 2.1 tCO₂e (18%)
  ├── S3: 0.8 tCO₂e (7%)
  └── Outros: 1.9 tCO₂e (15%)

Sem medir, não há como melhorar.
```

### 2. Estabelecer metas de sustentabilidade

```
Alinhamento com objetivos corporativos:

Frameworks de comprometimento:
  Science Based Targets (SBTi):
  → Empresa define meta de redução alinhada ao Acordo de Paris
  → Ex: reduzir emissões em 50% até 2030 vs. 2020

  RE100:
  → Compromisso de usar 100% energia renovável
  → Mais de 350 empresas globais signatárias

  Net Zero:
  → Eliminar ou compensar 100% das emissões

Metas específicas para TI:
  "Reduzir PUE médio dos nossos sistemas para < 1.15"
  "Migrar 100% de workloads para regiões com energia renovável"
  "Reduzir consumo de CPU ociosa em 30% até dezembro"
```

### 3. Maximizar utilização

```
Recurso subutilizado = energia desperdiçada desnecessariamente:

EC2 com CPU a 5%:
  → Consome energia para resfriamento, rede, storage
  → 95% dessa energia: desperdício puro

Estratégias de maximização de utilização:

Right-sizing (já visto em eficiência de performance):
  → Menos instâncias maiores, mais utilizadas
  → Ou instâncias menores mas com maior utilização

Consolidação de instâncias:
  10 instâncias t3.micro @ 10% CPU cada
  → Considerar 2-3 instâncias t3.small @ 40-50% CPU
  → Mesma capacidade, menos hardware ativo

Auto Scaling agressivo:
  Min: 1 instância (madrugada)
  Max: 20 instâncias (pico)
  → Zero instâncias ociosas no vale
  → Oposto de manter capacidade fixa para o pico

Serverless como padrão:
  Lambda: consume energia apenas quando executa
  vs. EC2: consome energia 24/7 mesmo sem requisições
  
  Para workloads intermitentes: Lambda é significativamente
  mais sustentável que EC2 equivalente
```

### 4. Antecipar e adotar ofertas de hardware e software mais eficientes

```
AWS Graviton — o chip de sustentabilidade:

  Graviton3 vs. equivalente x86:
  ├── ~60% menos energia por operação
  ├── ~20% melhor performance por watt
  └── Mesmo custo menor (20% mais barato)

  Impacto real:
  Migrar 100 instâncias m5.xlarge → m7g.xlarge:
  ├── Custo: -20% (~$2.700/mês de economia)
  ├── Performance: similar ou superior
  └── Consumo de energia: -60% por instância

AWS Inferentia e Trainium:
  Chips especializados para ML:
  ├── Inferentia2: inferência de ML com 4x melhor performance/watt vs. GPU
  ├── Trainium2: treinamento de ML mais eficiente energeticamente
  └── Para workloads de ML: muito mais sustentável que GPU genérica

Atualizações automáticas de serviços gerenciados:
  RDS, EKS, Lambda: AWS otimiza continuamente o hardware subjacente
  → Você se beneficia de chips mais eficientes sem ação manual
```

### 5. Usar serviços gerenciados

```
Por que serviços gerenciados são mais sustentáveis:

Auto-gerenciado (EC2 + PostgreSQL manual):
  → Servidor dedicado: hardware reservado, uso variável
  → Você configura o tamanho para o pico
  → Hardware ocioso nas horas de baixo uso

RDS (gerenciado):
  → AWS otimiza o hardware subjacente continuamente
  → Compartilha infraestrutura física entre clientes
  → Usa hardware mais eficiente (Graviton por padrão em alguns tipos)
  → AWS tem incentivo para maximizar eficiência energética

Lambda (serverless):
  → Zero hardware dedicado quando não executa
  → AWS empacota milhares de execuções no mesmo hardware
  → Densidade máxima = menor impacto por execução

S3 vs. EBS para dados raramente acessados:
  → S3 Glacier: armazenamento em cold storage com energia mínima
  → EBS: disco ativo consumindo energia mesmo se nunca acessado
  → Mover dados frios para Glacier é mais sustentável
```

### 6. Reduzir o impacto downstream dos workloads

```
O código ineficiente desperdiça energia em escala:

Queries sem índice:
  → Full table scan em 100 milhões de registros
  → CPU + I/O por segundos ao invés de milissegundos
  → Multiplicado por 10.000 requisições/dia = energia desperdiçada

Assets não otimizados (web):
  → Imagem PNG de 5MB quando WebP de 200KB seria equivalente
  → Transferida para 1 milhão de usuários/dia
  → Custo de bandwidth + energia de transferência desnecessária

  Boas práticas:
  ├── CloudFront: cache na borda → menos transferência de origem
  ├── Compressão Brotli/gzip: menos bytes transferidos
  ├── Images WebP/AVIF: 50-80% menor que JPEG/PNG
  ├── Lazy loading: não carrega o que não está na viewport
  └── API responses minimizadas: sem campos desnecessários

Processamento síncrono vs. assíncrono:
  Processamento síncrono (para cada request):
  → Usuário espera → recursos alocados durante a espera
  
  Processamento assíncrono (SQS + Lambda):
  → Usuário recebe confirmação imediata
  → Processamento em background quando há capacidade disponível
  → Lambda pode usar Spot/hardware ocioso → mais eficiente
```

## Escolha de região por energia renovável

```
AWS e energia renovável por região (aproximado 2024):

Regiões com alta % de energia renovável:
  eu-west-1 (Irlanda):     ~96% renovável (eólica + hidro)
  eu-north-1 (Estocolmo):  ~100% hidro
  us-west-2 (Oregon):      ~100% renovável (eólica + solar + hidro)
  ca-central-1 (Canadá):   ~80%+ hidro

Regiões em desenvolvimento:
  sa-east-1 (São Paulo):   crescente (Brasil tem ~65% hidro na matriz)
  ap-southeast-1 (Cingapura): menor % renovável (grid local)

Implicação para arquitetura sustentável:
  Se sua latência permite servir da Irlanda vs. São Paulo:
  → Escolher eu-west-1 reduz significativamente a pegada de carbono
  
  Para workloads batch sem requisito de região específica:
  → Priorizar regiões com maior % de energia renovável
  → Reduz emissões sem impacto na performance do usuário

AWS Infrastructure Map:
  → aws.amazon.com/about-aws/global-infrastructure/
  → Mostra regiões e comprometimentos de energia renovável
```

## Sustentabilidade e otimização de custos: a sobreposição

```
Prática sustentável          → Benefício de custo

Right-sizing instâncias      → Menos horas de compute cobradas
Graviton em vez de x86       → 20% mais barato + 60% menos energia
Auto Scaling no vale         → Zero instâncias ociosas
Lambda para eventos          → Paga por execução, não por hora ociosa
S3 Intelligent Tiering       → Dados frios em Glacier (mais barato)
Compressão de assets         → Menos bandwidth (menos custo de egress)
Queries com índice           → Menos CPU do banco (instância menor)
Desligar dev fora do horário → 66% menos custo + menos energia

Conclusão: sustentabilidade e economia andam juntas.
Um time comprometido com otimização de custos
automaticamente reduz impacto ambiental.
O inverso também é verdadeiro.
```

## 🧩 Quiz de Fixação

1. Por que migrar workloads de on-premises para AWS já reduz a pegada de carbono em até 80%, mesmo antes de qualquer otimização ativa?
2. Um time de ML treina modelos diariamente usando instâncias p3.8xlarge. Do ponto de vista de sustentabilidade, quais duas mudanças teriam maior impacto imediato?
3. Uma empresa precisa processar 10 milhões de imagens por mês para gerar thumbnails. O CTO propõe um cluster EC2 dedicado rodando 24/7. Qual arquitetura seria mais sustentável e por quê?

**Respostas:**
1) Dois fatores principais: (1) Eficiência de hardware — AWS opera data centers com PUE de 1.1-1.2 vs. 1.5-2.0 de data centers corporativos, e usa hardware mais moderno e eficiente energeticamente; (2) Utilização via multitenancy — servidores AWS têm utilização de 65-75% (múltiplos clientes compartilham o hardware), enquanto servidores corporativos ficam em 15-20% de utilização. Menos hardware físico necessário para o mesmo workload = menos energia consumida. Somado ao uso crescente de energia renovável (85%+ em 2023), a redução de carbono é estrutural, não apenas incremental.
2) As duas mudanças de maior impacto: (1) Migrar para instâncias Trainium (trn1) ou Graviton-based — chips especializados da AWS consomem 60-75% menos energia por operação de ML que GPUs NVIDIA equivalentes, além de serem mais baratos; (2) Usar Spot Instances com checkpointing — treinos tolerantes a interrupção com Spot aproveitam capacidade ociosa da AWS que já está consumindo energia de qualquer forma, maximizando a utilização do hardware existente em vez de provisionar novo hardware dedicado. O impacto combinado pode reduzir emissões do workload em 70-80%.
3) Lambda + S3 é a arquitetura mais sustentável. Lambda é invocado apenas quando há uma imagem para processar — consume energia zero quando não há workload. EC2 dedicado 24/7 consome energia constantemente, mesmo às 3h quando não há imagens para processar. Para 10 milhões de imagens/mês (~330.000/dia, ~14.000/hora), Lambda escala automaticamente, processa e encerra — sem hardware ocioso. Adicionalmente, usar instâncias Lambda arm64 (Graviton) reduz 60% o consumo de energia por invocação. A arquitetura Lambda também é mais barata: sem custo de EC2 ociosa, pagando apenas por milissegundos de execução real.
