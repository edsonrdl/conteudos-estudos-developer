### Eficiência de performance — usar os recursos certos, na medida certa, para o trabalho certo

Eficiência de performance é o quarto pilar da AWS Well-Architected Framework. Ele trata da capacidade de usar recursos de computação eficientemente para atender aos requisitos do sistema — e de manter essa eficiência conforme a demanda muda e as tecnologias evoluem. A essência é: não basta funcionar; precisa funcionar bem, sem desperdício e sem gargalos.

---

## O problema da ineficiência de performance

```
Sintomas de sistema sem eficiência de performance:

Superprovisionado:
  → 32 vCPUs rodando a 5% de uso → dinheiro desperdiçado
  → RDS r6g.16xlarge para 10 requisições/segundo
  → ElastiCache com 200GB de RAM para 1GB de dados

Subprovisionado:
  → t3.micro tentando processar 10.000 req/s → timeout
  → Banco de dados sem índices → queries de 30 segundos
  → Lambda com 128MB tentando processar arquivos de 500MB

Tipo errado de recurso:
  → Banco relacional para dados de grafos → queries impossíveis
  → EBS General Purpose (gp2) para banco com I/O intensivo
  → EC2 para processar 1.000 arquivos/dia (Lambda seria 10x mais barato)
```

O pilar de eficiência de performance organiza-se em **5 áreas de boas práticas**:

---

## Área 1: Seleção de arquitetura (Selection)

### Computação: escolher o modelo certo

```
Modelos de computação na AWS e quando usar cada um:

EC2 — servidores virtuais:
  ├── Workloads que precisam de controle total do SO
  ├── Aplicações que rodam continuamente 24/7
  ├── Cargas com requisitos específicos de CPU/GPU/memória
  └── Aplicações legadas que não podem ser refatoradas

Lambda — serverless, event-driven:
  ├── Processamento de eventos (S3, SQS, API calls)
  ├── APIs com tráfego irregular (paga por invocação)
  ├── Tarefas agendadas (substituindo cron jobs)
  └── Duração máxima: 15 minutos por execução
  
  Custo Lambda vs EC2 para carga intermitente:
  EC2 t3.small 24/7: ~$15/mês (mesmo sem usar)
  Lambda 1 milhão invocações × 200ms × 512MB: ~$1.04/mês

ECS/EKS — contêineres:
  ├── Microserviços com múltiplos componentes
  ├── Times que já usam Docker
  ├── Portabilidade entre ambientes (dev → prod idênticos)
  └── Necessidade de orquestração complexa (blue/green, canary)

Fargate — contêineres sem gerenciar servidores:
  ├── ECS/EKS sem provisionar instâncias EC2
  ├── Paga por vCPU e memória alocados por segundo
  └── Ideal quando não quer gerenciar capacity de cluster
```

### Tipos de instância EC2: famílias e casos de uso

```
Famílias de instâncias e para que servem:

Propósito geral (t3, m6i, m6g):
  t3: burstable — bom para cargas irregulares (dev, pequenas APIs)
  m6i: balanceado CPU/RAM — web servers, aplicações gerais
  m6g: Graviton (ARM) — 20% mais barato, 40% mais eficiente

Compute optimized (c6i, c6g):
  → Alto ratio CPU/RAM
  → Uso: video encoding, análise científica, gaming servers

Memory optimized (r6i, r6g, x2idn):
  → Alto ratio RAM/CPU
  → Uso: bancos de dados em memória, Hadoop, Spark, SAP HANA
  → x2idn: até 24 TB de RAM para workloads in-memory extremos

Storage optimized (i3, i4i, d3):
  → Alto throughput de I/O local
  → Uso: NoSQL de alta performance (Cassandra), data warehousing

Accelerated Computing (p4, g5, trn1):
  → GPU ou chips especializados
  → p4: ML training (NVIDIA A100)
  → g5: ML inference + graphics
  → trn1: Trainium (chip AWS para ML — mais econômico)

Regra de seleção:
  1. Identifique o gargalo da sua aplicação (CPU? RAM? I/O? GPU?)
  2. Escolha a família que otimiza esse gargalo
  3. Use Graviton (g) quando possível: mesmo performance, menor custo
  4. Dimensione pelo percentil p99, não pelo pico absoluto
```

### Storage: o tipo certo de disco para cada workload

```
Tipos de EBS e quando usar:

gp3 (General Purpose SSD) — padrão atual:
  → 3.000 IOPS base, configurável até 16.000 IOPS
  → Uso: boot volumes, aplicações web, banco de dados de médio porte
  → Custo: $0.08/GB/mês (+ IOPS adicionais se necessário)

io2 Block Express (Provisioned IOPS SSD):
  → Até 256.000 IOPS por volume
  → Uso: Oracle RAC, SQL Server de alta performance, bancos críticos
  → Custo: mais caro — use apenas quando IOPS é o gargalo comprovado

st1 (Throughput Optimized HDD):
  → Alto throughput sequencial (500 MB/s)
  → Uso: data warehouse, log processing, Kafka brokers
  → Custo: $0.045/GB/mês — barato para grandes volumes sequenciais

sc1 (Cold HDD):
  → Throughput sequencial, acesso infrequente
  → Uso: backups, dados de arquivo raramente acessados
  → Custo: $0.015/GB/mês — mais barato do EBS

Regra:
  Banco de dados OLTP → gp3 (ou io2 se IOPS for gargalo)
  Data warehouse → st1
  Backup e arquivo → sc1 ou S3 Glacier
  Nunca use gp2: gp3 é mais barato E mais configurável
```

### Banco de dados: não use o mesmo para tudo

```
Tipos de banco e casos de uso:

RDS (PostgreSQL, MySQL, SQL Server, Oracle):
  → Dados estruturados, transações ACID
  → Relações complexas entre entidades
  → Ex: pedidos, usuários, produtos, financeiro

DynamoDB:
  → Alta performance com acesso por chave
  → Escala para qualquer volume sem tuning
  → Ex: sessões, carrinho, catálogo com acesso previsível

Aurora:
  → PostgreSQL/MySQL com performance 3-5x superior
  → Storage distribuído e auto-escalável
  → Ex: substituição de RDS quando performance é crítica

ElastiCache (Redis/Memcached):
  → Cache de dados frequentemente acessados
  → Ex: resultado de queries caras, sessões, contadores
  → Latência: sub-milissegundo

Redshift:
  → Data warehouse — queries analíticas em petabytes
  → Ex: relatórios de BI, análise histórica

Neptune:
  → Grafos — relacionamentos complexos entre entidades
  → Ex: redes sociais, detecção de fraude, recomendações

DocumentDB:
  → Documentos JSON, compatível com MongoDB
  → Ex: catálogos de produto, conteúdo CMS

Regra: use o banco certo para o padrão de acesso —
       não force um banco relacional a fazer o trabalho de um grafo.
```

## Área 2: Revisão contínua (Review)

A AWS lança novos serviços e tipos de instância constantemente. A eficiência de performance exige revisão periódica:

```
Exemplos de evolução que exigem revisão:

2022: AWS lança gp3
  → Migrar de gp2 para gp3: mesmo performance, 20% mais barato
  → Ação: script de migração em lote via AWS CLI

2022: AWS lança Graviton3 (c7g, m7g, r7g)
  → ~25% mais eficiente que Graviton2
  → Ação: testar workload → se compatível, migrar

2023: AWS lança trn1 (Trainium para ML)
  → ~50% mais barato que p3 para training de modelos
  → Ação: avaliar para novos workloads de ML training

Cadência de revisão recomendada:
  ├── Mensal: AWS Cost Explorer → identificar instâncias ociosas
  ├── Trimestral: Compute Optimizer → recomendações de right-sizing
  └── Semestral: avaliar novos tipos de instância/serviço lançados
```

## Área 3: Monitoramento (Monitoring)

Performance precisa ser medida para ser gerenciada:

```
Métricas essenciais por camada:

EC2:
  ├── CPUUtilization: meta 40-70% (headroom para picos)
  ├── NetworkIn/Out: detecta saturação de rede
  ├── EBSReadOps/WriteOps: detecta gargalo de disco
  └── MemoryUtilization: via CloudWatch agent (não nativo)

RDS:
  ├── CPUUtilization: > 80% por horas → aumentar instância
  ├── DatabaseConnections: próximo do max → connection pooling
  ├── ReadLatency/WriteLatency: > 20ms → investigar queries
  ├── FreeStorageSpace: < 20% → alarme para expandir
  └── ReadIOPS/WriteIOPS: compare com provisioned IOPS

Lambda:
  ├── Duration: percentis p50, p95, p99 (não apenas média)
  ├── Throttles: indicam limite de concorrência atingido
  ├── Errors: taxa de erro por função
  └── ConcurrentExecutions: monitora uso vs. limite

ALB:
  ├── TargetResponseTime: p99 > SLA → investigar backends
  ├── HTTPCode_Target_5XX_Count: erros dos backends
  └── RequestCount: baseline para capacity planning
```

### AWS Compute Optimizer

```
Analisa métricas de 14 dias e recomenda:
  EC2: "Você está usando t3.xlarge com CPU média de 8%
        → downsell para t3.medium (economiza 50%)"
  
  Lambda: "Sua função usa 512MB mas pico foi 120MB
           → reduza para 256MB (economiza 50%)"
  
  EBS: "Volume gp2 com IOPS utilizados 400/3000
        → migre para gp3 com 400 IOPS (economiza 20%)"

Acesso: AWS Console → Compute Optimizer
Custo: gratuito
```

## Área 4: Trade-offs conscientes (Trade-offs)

Às vezes, trocar consistência por performance — conscientemente — é correto:

```
Trade-off 1: Consistência eventual vs. Forte

  Forte (padrão RDS): toda leitura reflete a última escrita
  → Latência maior (espera confirmação de replicação)
  → Necessário para: inventário, saldo bancário, transações

  Eventual (DynamoDB, ElastiCache, Read Replica):
  → Leitura pode retornar dado levemente desatualizado
  → Latência menor (lê da réplica mais próxima)
  → Aceitável para: feed de redes sociais, contadores aproximados,
                    catálogos de produto

Trade-off 2: Cache vs. Frescor dos dados

  Sem cache:
    Requisição → banco → resposta (20-50ms, repetida 1000x)
    → 1000 queries idênticas no banco → lento e caro
  
  Com ElastiCache:
    Requisição 1 → banco → salva no Redis (TTL: 60s)
    Requisições 2-1000 → Redis → resposta em <1ms
    → Dado tem até 60s de atraso (aceitável para catálogo)
    → 999 queries economizadas no banco
    
  Quando cache é inadequado:
    → Dados mudam a cada segundo (preço de ação, saldo)
    → Dados são únicos por usuário (não há reuso do cache)
    → Consistência absoluta é requisito

Trade-off 3: Compute vs. Network

  Processar dado no cliente vs. no servidor:
  → ML inference: EC2 com GPU perto dos dados vs. API call para SageMaker
  → Compressão de imagem: na borda (Lambda@Edge) vs. no servidor central
  → Regra: processe onde está o dado, minimize transferência de rede
```

## Área 5: Democratizar tecnologias avançadas

A AWS remove a barreira de entrada para tecnologias que antes exigiam expertise especializada:

```
Antes da AWS:
  Machine Learning:
  → Contratar PhD em ML + comprar cluster de GPU ($100k+)
  → Construir infraestrutura de treinamento do zero
  → Meses para ter o primeiro modelo em produção

  Com AWS:
  SageMaker: plataforma completa de ML
  ├── Notebooks gerenciados (SageMaker Studio)
  ├── Treinamento distribuído gerenciado
  ├── Deploy automatizado de modelos (endpoints)
  └── AutoML (Autopilot): encontra o melhor algoritmo automaticamente

  Rekognition: computer vision como API
  → Detecta objetos, faces, texto em imagens via uma chamada de API
  → Sem ML knowledge necessário

  Comprehend: NLP como API
  → Análise de sentimento, extração de entidades, detecção de idioma
  → Sem modelo para treinar

  Polly: text-to-speech como API
  Transcribe: speech-to-text como API

Resultado: uma pessoa sem expertise em ML pode integrar visão
computacional em sua aplicação em horas, não meses.
```

## 🧩 Quiz de Fixação

1. Uma aplicação processa 500 arquivos de imagem por dia, cada processamento leva 2 minutos. Comparando EC2 t3.medium rodando 24/7 vs. Lambda, qual é mais eficiente em performance e custo, e por quê?
2. Um banco RDS PostgreSQL tem `ReadLatency` de 150ms e `CPUUtilization` de 15%. Qual é o provável gargalo e qual solução de eficiência de performance a AWS oferece?
3. O time quer usar consistência forte para todas as leituras do DynamoDB para "garantir que os dados estão sempre atualizados". Por que isso pode ser um trade-off de performance desnecessário para a maioria dos casos?

**Respostas:**
1) Lambda é drasticamente mais eficiente. EC2 t3.medium 24/7: ~$30/mês independente do uso — fica ocioso 22+ horas por dia. Lambda: 500 invocações × 120 segundos × 512MB de memória = ~$0.50/mês. Além do custo, Lambda escala automaticamente se o volume crescer para 5.000 arquivos/dia, sem nenhuma mudança. O EC2 ficaria sobrecarregado ou continua igualmente ocioso. Lambda é o modelo certo para workloads event-driven e intermitentes.
2) Com CPU a 15%, o gargalo não é computação. ReadLatency de 150ms indica que as queries estão lentas — provavelmente por falta de índices nas colunas mais consultadas, queries N+1 ou queries complexas sem otimização. Soluções de eficiência de performance: (1) Performance Insights do RDS: identifica quais queries são as mais lentas e por quê — sem custo adicional para instâncias até db.t3; (2) Read Replicas: distribui tráfego de leitura para réplicas, reduzindo carga no primário; (3) ElastiCache: cacheia resultados de queries frequentes e caras. Primeiro investiga com Performance Insights, depois decide a solução.
3) Leitura fortemente consistente no DynamoDB consome o dobro de read capacity units (RCU) comparada à leitura eventual — custa o dobro e tem latência ligeiramente maior. Para a maioria dos casos (catálogos de produto, perfis de usuário, feeds), um dado com 1-2 segundos de atraso é completamente aceitável pelo usuário — ele não percebe. Consistência forte só é necessária quando o dado lido logo após uma escrita precisa refletir aquela escrita exata (ex: após decrementar estoque, a próxima leitura precisa ver o estoque decrementado). Usar consistência forte para tudo é um trade-off de custo e performance sem benefício real para a maioria dos dados.
