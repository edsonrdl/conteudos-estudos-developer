### Alta disponibilidade e tolerância a falhas — projetar para quando as coisas derem errado

Alta disponibilidade (HA) e tolerância a falhas (FT) são princípios de arquitetura que garantem que um sistema continue funcionando mesmo quando componentes individuais falham. Na AWS, esses princípios são implementados através da infraestrutura física distribuída — Zonas de Disponibilidade e Regiões — combinada com serviços que abstraem a complexidade de replicação e failover.

---

## O princípio fundamental: tudo vai falhar

A AWS opera com a premissa de que falhas são inevitáveis e previsíveis, não excepcionais:

```
Fontes de falha em qualquer sistema:
  ├── Hardware: discos falham, NICs falham, servidores pegam fogo
  ├── Software: bugs, memory leaks, deadlocks
  ├── Rede: enlaces caem, roteadores falham, BGP oscila
  ├── Energia: quedas, picos, falha de UPS
  ├── Humano: deploy errado, configuração incorreta, delete acidental
  └── Desastre: inundação, incêndio no data center, terremoto

Pergunta errada: "Como evito falhas?"
Pergunta certa:  "Como meu sistema continua funcionando quando falhas ocorrem?"
```

## Alta Disponibilidade vs. Tolerância a Falhas

São conceitos relacionados mas com níveis de proteção e custo diferentes:

### Alta Disponibilidade (High Availability — HA)

O sistema continua operando mesmo com falhas, mas pode haver **breve interrupção** durante o failover:

```
HA típica (Multi-AZ RDS como exemplo):

Normal:
  Aplicação → [RDS Primary — AZ-a] ←→ [RDS Standby — AZ-b]
                    (ativo)                  (replicando)

Falha na AZ-a:
  ├── RDS detecta falha (~30 segundos)
  ├── Standby promovido a Primary
  ├── DNS atualizado automaticamente
  └── Aplicação reconecta ao novo primary

Downtime: 30-60 segundos (percebido como lentidão/erro momentâneo)
Custo: 2x instâncias (primary + standby)
```

### Tolerância a Falhas (Fault Tolerance — FT)

O sistema continua operando **sem nenhuma interrupção perceptível**, mesmo com falhas:

```
FT (exemplo: S3):
  Objeto armazenado no S3 → replicado em ≥3 AZs automaticamente
  
  Se AZ-a falhar completamente:
  → S3 continua servindo o objeto das outras AZs
  → Zero downtime, zero intervenção
  → Aplicação não percebe nada

FT (exemplo: EC2 com Multi-AZ + ALB):
  ALB → [EC2 #1 AZ-a] [EC2 #2 AZ-b] [EC2 #3 AZ-c]
  
  EC2 #1 falha:
  → ALB para de rotear para EC2 #1 (health check falhou)
  → Tráfego vai para EC2 #2 e EC2 #3
  → Usuário não percebe nada
  → ASG lança nova instância em AZ-a para repor
```

| Aspecto | Alta Disponibilidade | Tolerância a Falhas |
|---|---|---|
| Downtime em falha | Segundos a minutos | Zero (imperceptível) |
| Custo | Moderado (2x recursos) | Alto (N+redundância) |
| Complexidade | Média | Alta |
| Exemplos AWS | RDS Multi-AZ, ElastiCache | S3, DynamoDB, ALB+ASG multi-AZ |

## A infraestrutura física da AWS: AZs e Regiões

A AWS construiu sua infraestrutura para isolar falhas geograficamente:

### Zonas de Disponibilidade (Availability Zones — AZs)

```
Região: us-east-1 (Norte da Virgínia)
  │
  ├── AZ: us-east-1a  → Data center(s) fisicamente separados
  ├── AZ: us-east-1b  → Data center(s) fisicamente separados
  ├── AZ: us-east-1c  → Data center(s) fisicamente separados
  ├── AZ: us-east-1d  → Data center(s) fisicamente separados
  └── AZ: us-east-1f  → Data center(s) fisicamente separados

Características de cada AZ:
  ├── Localização física diferente (km de distância)
  ├── Energia independente (subestações diferentes)
  ├── Conectividade de rede redundante
  ├── Resfriamento independente
  └── Conectadas por fibra de baixíssima latência (<2ms entre AZs)
```

**Por que isso importa:** uma enchente, incêndio ou falha elétrica que destrói uma AZ não afeta as outras. Uma falha em `us-east-1a` não impacta `us-east-1b`.

### Regiões

```
Regiões AWS (exemplos):
  us-east-1      → Norte da Virgínia, EUA (6 AZs)
  us-west-2      → Oregon, EUA (4 AZs)
  eu-west-1      → Irlanda (3 AZs)
  eu-central-1   → Frankfurt (3 AZs)
  sa-east-1      → São Paulo, Brasil (3 AZs)
  ap-southeast-1 → Singapura (3 AZs)

Características:
  ├── Geograficamente distantes (centenas a milhares de km)
  ├── Completamente independentes
  ├── Dados não replicam entre regiões por padrão (soberania de dados)
  └── Alta latência entre regiões (ms a dezenas de ms)
```

Regiões são usadas para **disaster recovery** (se uma região inteira for afetada) e para **latência** (servir usuários próximos geograficamente).

## RPO e RTO — métricas que definem o nível de proteção necessário

Antes de escolher a arquitetura de HA, é preciso entender o que o negócio tolera:

```
RPO — Recovery Point Objective:
  "Quanto de dado posso perder?"
  
  Backup diário → RPO = 24h (perco até 24h de dados se tudo falhar)
  Replicação em tempo real → RPO ≈ 0 (perco segundos ou nada)

RTO — Recovery Time Objective:
  "Quanto tempo posso ficar fora do ar?"
  
  Manual recovery → RTO = horas (alguém precisa intervir)
  Multi-AZ automático → RTO = minutos
  Multi-region ativo-ativo → RTO ≈ 0
```

**Regra geral:** quanto menor o RPO e RTO desejados, maior o custo da arquitetura.

```
Custo vs. Proteção:

  RPO/RTO alto   │ Backup S3 diário            → barato
  (horas)        │ Snapshot RDS               → custo moderado
                 │
  RPO/RTO médio  │ Multi-AZ RDS               → 2x custo do banco
  (minutos)      │ ALB + EC2 multi-AZ          → custo moderado
                 │
  RPO/RTO baixo  │ Aurora Global Database      → caro
  (segundos)     │ DynamoDB Global Tables      → caro
                 │
  RPO/RTO ≈ 0   │ Multi-region ativo-ativo    → muito caro
  (zero)         │ + Route 53 health checks    → complexidade alta
```

## Padrões de arquitetura multi-AZ na AWS

### Padrão 1: Stateless application + ALB + ASG

O padrão mais comum para aplicações web:

```
Internet
    │
[Route 53] → resolve DNS
    │
[ALB — Application Load Balancer]
    │        (distribuído automaticamente entre AZs)
    ├────────────────────────────────┐
    ▼                                ▼
[EC2 #1 — AZ-a]              [EC2 #2 — AZ-b]
[EC2 #3 — AZ-a]              [EC2 #4 — AZ-b]
    │                                │
    └────────────┬───────────────────┘
                 ▼
        [RDS Multi-AZ]
        Primary: AZ-a ←sync→ Standby: AZ-b

Se AZ-a falhar:
  → ALB remove EC2 #1 e #3 do pool (health check)
  → Todo tráfego vai para EC2 #2 e #4 em AZ-b
  → ASG lança novas instâncias em AZ-c
  → RDS faz failover para Standby em AZ-b (30-60s)
  → Sistema volta ao normal automaticamente
```

### Padrão 2: Multi-region com Route 53

Para disaster recovery a nível de região:

```
[Route 53 Health Checks]
    │
    ├── Primary: us-east-1   (100% tráfego — saudável)
    │       └── [Stack completo: ALB + EC2 + RDS]
    │
    └── Secondary: us-west-2 (0% tráfego — em standby)
            └── [Stack replicado: Aurora Global replica]

Se us-east-1 falhar:
  → Route 53 detecta falha via health check (~30s)
  → Redireciona DNS para us-west-2
  → Aurora Global promove replica para primary
  → RTO: ~1-5 minutos
  → RPO: segundos (replicação contínua do Aurora Global)
```

## Serviços AWS nativamente altamente disponíveis

Alguns serviços da AWS são projetados com HA por padrão — você não precisa configurar nada:

| Serviço | Como é HA por design |
|---|---|
| **S3** | Replicado em ≥3 AZs automaticamente (99.999999999% durabilidade) |
| **DynamoDB** | Replicado em 3 AZs por padrão, failover automático |
| **SQS** | Distribuído e redundante por design |
| **Lambda** | Executa em múltiplas AZs automaticamente |
| **ALB** | Distribuído entre AZs automaticamente |
| **CloudFront** | Distribuído globalmente em Edge Locations |

Para esses serviços, HA é o padrão — a responsabilidade de HA recai sobre **o que você constrói em cima deles**, não sobre eles mesmos.

## Erros comuns de arquitetura que quebram HA

```
Erro 1: Single point of failure no banco
  ❌ RDS Single-AZ → se AZ cair, banco cai
  ✓  RDS Multi-AZ  → failover automático

Erro 2: Sessão armazenada localmente no servidor
  ❌ Sessão na memória do EC2 → se EC2 cair, usuário perde sessão
  ✓  Sessão no ElastiCache/DynamoDB → qualquer EC2 atende o usuário

Erro 3: EC2 em uma única AZ
  ❌ Todas as instâncias em us-east-1a → AZ falha → sistema cai
  ✓  Instâncias distribuídas em ≥2 AZs

Erro 4: Endpoint fixo em vez de DNS
  ❌ Hardcoded IP do banco → failover muda IP → aplicação não reconecta
  ✓  Usar endpoint DNS do RDS → failover atualiza DNS automaticamente

Erro 5: Sem health checks configurados
  ❌ ALB envia tráfego para instância doente → erros para o usuário
  ✓  Health checks garantem que só instâncias saudáveis recebem tráfego
```

## 🧩 Quiz de Fixação

1. Qual a diferença entre Alta Disponibilidade e Tolerância a Falhas? Por que FT é mais cara que HA?
2. Uma empresa define RPO = 1 hora e RTO = 15 minutos para seu sistema crítico. Que arquitetura AWS você recomendaria e por quê?
3. Um desenvolvedor armazena a sessão do usuário na memória local do EC2. Por que isso quebra a alta disponibilidade em um ambiente multi-AZ com Auto Scaling?

**Respostas:**
1) Alta Disponibilidade permite um breve downtime durante o failover (segundos a minutos) — o sistema para brevemente e se recupera automaticamente. Tolerância a Falhas significa zero downtime perceptível — o sistema continua operando sem interrupção mesmo com falhas. FT é mais cara porque exige redundância ativa em tempo real (múltiplas cópias processando simultaneamente), enquanto HA pode manter uma cópia em standby que só entra em operação quando a principal falha.
2) RPO de 1h e RTO de 15min: Multi-AZ é suficiente e mais econômico que multi-region. Recomendaria: ALB + EC2 em pelo menos 2 AZs com Auto Scaling (RTO ~5min para EC2), RDS Multi-AZ (RTO ~1min para banco, RPO ~segundos com replicação síncrona), snapshots automáticos do RDS a cada hora (garantia de RPO de 1h). Route 53 com health checks para failover de DNS se necessário.
3) Quando o usuário faz login, a sessão é criada na memória do EC2 #1. Se o Auto Scaling terminar o EC2 #1 (scale in), a sessão é perdida e o usuário é deslogado. Se um health check falhar e o ALB parar de enviar tráfego para EC2 #1, as requisições seguintes do mesmo usuário vão para EC2 #2 — que não tem a sessão — e o usuário aparece como não autenticado. A solução é externalizar a sessão para ElastiCache (Redis) ou DynamoDB: qualquer EC2 do pool pode atender o usuário independentemente de qual instância criou a sessão.
