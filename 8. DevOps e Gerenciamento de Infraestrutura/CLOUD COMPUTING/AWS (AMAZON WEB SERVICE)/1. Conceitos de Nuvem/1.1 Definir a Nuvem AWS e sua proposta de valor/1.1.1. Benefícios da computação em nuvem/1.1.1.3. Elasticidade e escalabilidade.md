### Elasticidade e escalabilidade — crescer quando precisa, encolher quando não precisa

Escalabilidade é a capacidade de um sistema suportar crescimento de carga. Elasticidade é a capacidade de fazer isso **automaticamente e em ambas as direções** — expandindo nos picos e reduzindo nos vales. Na AWS, esses dois conceitos formam a base de uma infraestrutura que se adapta à demanda real em vez de ser dimensionada para o pior cenário imaginável.

---

## Escalabilidade vs. Elasticidade — a diferença fundamental

Os termos são frequentemente confundidos, mas representam capacidades distintas:

```
ESCALABILIDADE:
  Sistema consegue crescer para suportar mais carga.
  → Pode ser manual ou automático
  → Só cresce (não necessariamente encolhe)
  → Exemplo: adicionar mais servidores quando o tráfego aumenta

ELASTICIDADE:
  Sistema cresce E encolhe automaticamente conforme a demanda.
  → Sempre automático (reagindo a métricas)
  → Bidirecional: escala para cima E para baixo
  → Exemplo: 100 servidores às 20h (pico), 5 servidores às 3h (vale)

┌─────────────────────────────────────────┐
│  Toda elasticidade implica escalabilidade│
│  Nem toda escalabilidade é elástica      │
└─────────────────────────────────────────┘
```

---

## Os dois tipos de escalabilidade

### Escala Vertical (Scale Up) — mais poder na mesma máquina

Aumentar os recursos de uma instância existente: mais CPU, mais RAM, mais disco.

```
t3.small  (2 vCPU,  2GB RAM)  →  t3.xlarge (4 vCPU,  16GB RAM)
                               →  t3.2xlarge (8 vCPU, 32GB RAM)
                               →  m6i.16xlarge (64 vCPU, 256GB RAM)

Analogia: trocar um carro 1.0 por um 2.0 turbo.
```

**Limitações da escala vertical:**
- Tem um teto — não existe instância infinita
- Requer downtime para redimensionar (na maioria dos casos)
- É sempre manual — alguém precisa decidir e executar
- Não é elástica — você não "encolhe" facilmente no vale
- Ponto único de falha — se a instância maior cair, tudo cai

**Quando usar:** bancos de dados relacionais (RDS), workloads que não distribuem bem (legados), casos onde a complexidade de distribuição não compensa.

### Escala Horizontal (Scale Out) — mais máquinas iguais

Adicionar instâncias idênticas para distribuir a carga entre elas.

```
1 servidor → 10 servidores (pico) → 2 servidores (vale)

Analogia: em vez de um caminhão maior, contratar mais caminhões
          pequenos — e dispensar os extras quando o volume cai.

Arquitetura:
  ┌─────────────┐
  │Load Balancer│ ← distribui requisições entre instâncias
  └──────┬──────┘
         │
    ┌────┴─────┐
    ▼          ▼
[EC2 #1]  [EC2 #2]  ... [EC2 #N]
```

**Vantagens da escala horizontal:**
- Sem teto teórico — adiciona quantas instâncias precisar
- Sem downtime — instâncias entram e saem do pool dinamicamente
- Alta disponibilidade — falha de uma instância não derruba o sistema
- É a base da elasticidade real na AWS

## Como o Auto Scaling funciona por baixo

O Auto Scaling Group (ASG) é o serviço AWS que implementa elasticidade real. Ele monitora métricas e toma decisões automaticamente:

```
Componentes do Auto Scaling:

1. Launch Template → "receita" de como criar novas instâncias
   (AMI, tipo de instância, security group, user data)

2. Auto Scaling Group → define os limites:
   ├── min: 2   (nunca menos que isso, garantia de HA)
   ├── desired: 4  (alvo atual)
   └── max: 20  (nunca mais que isso, controle de custo)

3. Scaling Policies → quando e quanto escalar:
   ├── Target Tracking: "mantenha CPU média em 60%"
   ├── Step Scaling: "se CPU > 80% por 2 min → +2 instâncias"
   └── Scheduled: "às 8h aumenta para 10, às 22h reduz para 2"

4. CloudWatch Alarm → detecta a métrica e dispara a policy
```

### O ciclo de vida de uma instância no ASG

```
Evento: tráfego aumenta → CPU média sobe para 85%

CloudWatch detecta: CPU > 80% por 2 minutos
          ↓
Alarm dispara → notifica o ASG
          ↓
ASG decide: adicionar 2 instâncias (conforme policy)
          ↓
Launch Template é usado: EC2 criada (~60 segundos)
          ↓
Health check: instância responde na porta 80? ✓
          ↓
Load Balancer registra a nova instância
          ↓
Tráfego distribuído entre todas as instâncias

Tempo total: ~3-5 minutos do alarme ao tráfego distribuído
```

### Scale In (redução automática)

```
Evento: tráfego cai → CPU média baixa para 20%

CloudWatch detecta: CPU < 40% por 10 minutos
          ↓
ASG decide: remover 1 instância
          ↓
Connection draining: Load Balancer para de enviar novas
                     requisições para a instância
          ↓
Aguarda requisições ativas finalizarem (~30 segundos)
          ↓
Instância terminada → custo para imediatamente
```

## Métricas usadas para escalar

A AWS permite escalar com base em diversas métricas além de CPU:

| Métrica | Serviço | Caso de uso |
|---|---|---|
| CPU Utilization | EC2 / ASG | Workloads compute-intensive |
| Request Count | ALB | Aplicações web com picos de tráfego |
| Queue Depth | SQS | Workers que processam mensagens |
| Memory Usage | CloudWatch custom | Aplicações memory-intensive |
| Latency (p99) | ALB | Manter SLA de tempo de resposta |
| Custom metric | CloudWatch | Qualquer métrica do negócio |

## O problema do on-premises: elasticidade impossível

No modelo tradicional, dimensionar para a demanda é fisicamente impossível:

```
Empresa de e-commerce — tráfego real ao longo do ano:

Jan  ████                          (baixo)
Fev  ███
Mar  █████
Abr  ████
Mai  ██████
Jun  ████
Jul  █████
Ago  ████
Set  █████
Out  ████████
Nov  ████████████████████████████  (Black Friday — 10x o normal)
Dez  ██████████████████████████

On-premises: compra hardware para o pico de novembro
→ Paga pelo pico durante 11 meses de uso normal
→ 90% do hardware ocioso a maior parte do ano

AWS com elasticidade:
→ 5 instâncias em janeiro
→ 50 instâncias na Black Friday
→ Volta para 5 em dezembro
→ Paga exatamente pelo que usou, quando usou
```

## Elasticidade além do EC2

O princípio elástico se aplica a quase todos os serviços AWS:

| Serviço | Como é elástico |
|---|---|
| **Lambda** | Escala de 0 a milhares de execuções simultâneas em segundos |
| **DynamoDB** | On-demand mode: sem capacidade pré-provisionada, cobra por requisição |
| **RDS Aurora** | Aurora Serverless v2: escala CPU/RAM em incrementos finos |
| **ECS/EKS** | Tasks/Pods escalam com base em métricas via HPA/KEDA |
| **S3** | Infinitamente elástico por design — sem limite de objetos ou tamanho |
| **SQS** | Escala para bilhões de mensagens sem configuração |

## 🧩 Quiz de Fixação

1. Qual a diferença fundamental entre escalabilidade e elasticidade? Dê um exemplo de cada na AWS.
2. Um sistema escala verticalmente (aumenta o tipo da instância EC2). Por que isso não é elasticidade verdadeira?
3. Uma aplicação web sofre picos toda sexta-feira às 19h e volta ao normal às 23h. Como você configuraria o Auto Scaling para lidar com isso de forma eficiente e econômica?

**Respostas:**
1) Escalabilidade é a capacidade de crescer para suportar mais carga — pode ser manual ou automática, e não implica encolher. Elasticidade é bidirecional e automática: o sistema cresce nos picos e reduz nos vales sem intervenção humana. Exemplo de escalabilidade: aumentar manualmente o tipo de instância RDS. Exemplo de elasticidade: Auto Scaling Group que sobe de 2 para 20 instâncias no pico e volta para 2 automaticamente.
2) Escala vertical é geralmente manual (alguém decide e executa), tem downtime, não encolhe automaticamente quando a carga diminui (você não "downgrade" automaticamente a instância) e tem um teto físico. Elasticidade real requer automação bidirecional — o sistema deve tanto crescer quanto encolher de forma autônoma baseada em métricas, o que a escala vertical não oferece.
3) Usaria Scheduled Scaling: às 18h30 (antes do pico), o ASG aumenta automaticamente o desired count para 15 instâncias; às 23h, reduz para 2. Combinaria com Target Tracking Policy (CPU em 60%) para lidar com variações imprevisíveis dentro do pico. Assim, às 19h as instâncias já estão prontas (evitando o warm-up delay), e às 23h o custo cai automaticamente — sem ninguém precisar acordar para apertar botão.
