### Right Sizing — dimensionar recursos pelo uso real, não pela intuição

Right sizing é a prática de selecionar e ajustar continuamente o tipo e tamanho dos recursos de computação para corresponder ao que a carga de trabalho realmente exige — nem maior (desperdício), nem menor (gargalo). É uma das alavancas mais impactantes de otimização de custos na AWS porque a maioria dos ambientes migrados de on-premises ou provisionados sem dados históricos chegam superdimensionados em 40-70%.

---

## Por que o superdimensionamento é tão comum

```
Origem histórica do problema:

On-premises (mentalidade herdada):
  "Vamos comprar para o pico + 30% de buffer"
  + hardware leva meses para chegar
  + melhor errar para mais (não dá para reduzir depois)
  → Resultado: 15-20% de utilização média típica

Migração lift-and-shift:
  Servidor físico: 32 cores, 256GB RAM
  → Migrado para: m5.16xlarge (64 vCPU, 256GB RAM)
  → "Só para garantir que funciona"
  → CPU real: 8% | RAM real: 20%
  → Custo: $2.784/mês quando m5.2xlarge ($348/mês) seria suficiente
  → Desperdício: $2.436/mês ($29.232/ano por instância)

Nova aplicação sem dados:
  "Vou pegar uma instância maior para ter folga"
  → Nunca revisada → fica superdimensionada por anos
```

---

## As três dimensões do right sizing

```
Para dimensionar corretamente, analisa-se três eixos:

1. COMPUTE (CPU):
   Métrica: CPUUtilization (CloudWatch)
   
   Superdimensionado: CPU média < 20%, p99 < 50%
   Bem dimensionado: CPU média 40-70%, p99 < 85%
   Subdimensionado: CPU média > 85% ou p99 > 95%
   
   Armadilha: olhar apenas a média esconde picos
   Correto: analisar p50, p90, p99 ao longo de 2+ semanas

2. MEMÓRIA (RAM):
   Métrica: MemoryUtilization (requer CloudWatch Agent)
   → Não coletada por padrão — precisa instalar o agente
   
   Superdimensionado: RAM usada < 30% do alocado
   Bem dimensionado: RAM usada 50-75% do alocado
   Subdimensionado: RAM > 85% com swap ativo
   
   Atenção: aplicações Java reservam heap na inicialização
   → RAM "usada" pode parecer alta mesmo com folga real

3. REDE / I/O:
   Métricas: NetworkIn, NetworkOut, EBSReadOps, EBSWriteOps
   
   Superdimensionado: throughput de rede < 10% do máximo do tipo
   Subdimensionado: frequente burst de rede ou throttling de EBS
   
   Cada família de instância tem limite de throughput de rede
   → Downgrade de tipo pode atingir esse limite inesperadamente
```

## AWS Compute Optimizer — right sizing automatizado

### Como funciona

```
O Compute Optimizer:
  1. Coleta métricas dos últimos 14 dias (padrão) ou 3 meses (enhanced)
  2. Aplica ML para identificar padrões de uso
  3. Gera recomendações com análise de risco

Serviços analisados:
  ├── EC2 (instâncias e Auto Scaling Groups)
  ├── Lambda (memória alocada)
  ├── EBS (tipo e tamanho de volumes)
  ├── ECS on Fargate (CPU e memória de tasks)
  └── RDS (tipo de instância — preview)

Acesso: Console AWS → Compute Optimizer
Custo: gratuito (dados básicos) / pago (enhanced infrastructure metrics)
```

### Interpretando as recomendações

```
Exemplo de saída do Compute Optimizer:

Instância atual: m5.2xlarge
├── vCPU: 8  |  RAM: 32GB
├── Custo: $276/mês

Métricas observadas (14 dias):
├── CPUUtilization: max=38%, p99=28%, avg=12%
├── MemoryUtilization: max=45%, avg=22%  (via CloudWatch agent)
└── NetworkBandwidth: max=15% do limite da instância

Recomendação: m5.xlarge (Finding: OVER_PROVISIONED)
├── vCPU: 4  |  RAM: 16GB
├── Custo: $138/mês
├── Risco: Baixo
└── Economia: $138/mês (50%)

Flags de risco:
  OVER_PROVISIONED:  claramente superdimensionado
  UNDER_PROVISIONED: claramente subdimensionado
  OPTIMIZED:         bem dimensionado
  NOT_OPTIMIZED:     dados insuficientes (< 3 dias de métricas)
```

### Categorias de recomendação e o que significam

```
Tipo de recomendação | Ação recomendada
─────────────────────────────────────────────────────
Same family, smaller  | t3.xlarge → t3.large
  → Menor risco, mesmo comportamento de CPU/rede

Different family      | m5.2xlarge → c5.xlarge
  → Avalie compatibilidade de software antes de aplicar
  → Família c5 é otimizada para CPU, m5 é balanceada

Graviton migration    | m5.2xlarge → m6g.xlarge
  → Requer compatibilidade com ARM64 (Linux OK, Windows não)
  → Economia adicional de 20% + 60% menos energia

Lambda memory         | 1024MB → 512MB
  → Função usa no máximo 180MB → 512MB com folga
  → Economia: 50% do custo de compute da função
```

## Right Sizing proativo vs. reativo

### Proativo — antes de ir para produção

```
Antes de definir o tipo de instância para produção:

Passo 1: Load testing em staging
  Ferramenta: k6, Artillery, Locust, JMeter
  
  Simular carga esperada + 2x o pico:
  k6 run --vus 1000 --duration 30m load-test.js
  
  Monitorar durante o teste:
  ├── CPUUtilization → qual instância saturou?
  ├── MemoryUtilization → RAM foi suficiente?
  ├── ResponseTime p99 → SLA atendido?
  └── ErrorRate → começaram erros com qual carga?

Passo 2: Identificar o ponto de saturação
  "Com m5.xlarge, a partir de 800 usuários simultâneos
   a CPU passa de 80% e latência sobe acima do SLA"
   
  → Usar m5.2xlarge para produção (dá headroom para 1.600 usuários)
  → Configurar Auto Scaling para adicionar instâncias acima de 70% CPU

Passo 3: Validar em produção nas primeiras semanas
  → Monitorar métricas reais vs. estimadas
  → Ajustar se necessário (right sizing reativo inicial)

Vantagem do proativo:
  → Não superdimensiona por medo
  → Tem dados antes de comprometer Reserved Instances
```

### Reativo — ajustando o que já está em produção

```
Fluxo contínuo de right sizing reativo:

Mensal:
  1. Abrir Compute Optimizer
  2. Exportar recomendações para CSV
  3. Filtrar por "OVER_PROVISIONED" e risco "Low"
  4. Ordenar por economia mensal (maior primeiro)
  5. Aplicar top 10 recomendações de menor risco

Processo seguro de right sizing de EC2:
  1. Tirar snapshot da instância (rollback se necessário)
  2. Parar instância (stop, não terminate)
  3. Modificar tipo de instância
  4. Iniciar e monitorar por 48-72 horas
  5. Confirmar que métricas estão adequadas
  6. Remover snapshot antigo após validação

Para Lambda (sem downtime):
  1. Atualizar memória configurada
  2. Mudança é imediata, sem interrupção
  3. Monitorar Duration e erros por 24h

Para EBS:
  gp2 → gp3: pode ser feito sem downtime (online resize)
  Mudar IOPS: aplica em segundos sem parar o volume
```

## Right Sizing de Lambda — o caso especial

```
Lambda tem uma relação não-óbvia entre memória e performance:

Mais memória = mais CPU alocado proporcionalmente
→ Função com 512MB tem 2x mais CPU que com 256MB

Resultado paradoxal:
  256MB: função executa em 800ms → custo = 256 × 0.8 = 204.8 GB-ms
  512MB: função executa em 350ms → custo = 512 × 0.35 = 179.2 GB-ms
  
  Dobrando a memória → execução 2.3x mais rápida
  → Custo MENOR com mais memória (e experiência melhor)

AWS Lambda Power Tuning:
  Ferramenta open source (Step Functions) que testa automaticamente
  sua função em múltiplos tamanhos de memória e encontra o
  ponto ótimo de custo × performance:
  
  Resultados:
  ┌──────────┬──────────┬────────────┬─────────────┐
  │ Memória  │ Duração  │ GB-ms      │ Custo/1M    │
  ├──────────┼──────────┼────────────┼─────────────┤
  │ 128 MB   │ 1400ms   │ 179.200    │ $2.99       │
  │ 256 MB   │ 750ms    │ 192.000    │ $3.20       │
  │ 512 MB   │ 350ms    │ 179.200    │ $2.99  ←opt │
  │ 1024 MB  │ 180ms    │ 184.320    │ $3.07       │
  │ 2048 MB  │ 95ms     │ 194.560    │ $3.25       │
  └──────────┴──────────┴────────────┴─────────────┘
  
  Ótimo: 512MB — mesmo custo que 128MB mas 4x mais rápido
```

## Armadilhas comuns do right sizing

```
1. Olhar apenas a média de CPU:
   CPU média de 10% → parece superdimensionado
   Mas: pico de 95% por 5 minutos às 9h → downgrade causaria timeout
   
   Correto: analisar p99 e picos ao longo de 2+ semanas

2. Right-sizing sem load testing prévio:
   Reduz instância → funciona bem por 2 semanas
   → Campanha de marketing → pico de 3x → sistema cai
   
   Correto: configurar Auto Scaling antes de right-sizing
             o downgrade é seguro quando há elasticidade

3. Ignorar a família de instância:
   m5.2xlarge → t3.2xlarge (mesma vCPU, menos RAM, menor custo)
   Mas: t3 tem burst de CPU, não é sustentado
   → Workloads de CPU constante degradam com t3 (créditos esgotados)
   
   Correto: usar t3 apenas para cargas com CPU irregular (web servers)
             usar m5/c5/r5 para cargas de CPU sustentada

4. Right-sizing de banco de dados sem análise de queries:
   RDS r5.2xlarge → r5.xlarge (50% de economia)
   Mas: query sem índice fazia full scan → usava 90% da RAM para buffer
   → Após downgrade: queries 10x mais lentas
   
   Correto: antes de right-sizing de banco, analisar queries
             lentas (Performance Insights) e otimizar primeiro

5. Não revisar após right-sizing:
   Aplicou right-sizing → nunca mais revisou
   6 meses depois: tráfego cresceu 3x → instância subdimensionada
   
   Correto: estabelecer ciclo mensal/trimestral de revisão
```

## Impacto financeiro de um programa de right sizing

```
Exemplo real de programa de right sizing (100 instâncias EC2):

Antes:
  50 × m5.2xlarge: 50 × $276 = $13.800/mês
  30 × r5.xlarge:  30 × $252 = $7.560/mês
  20 × c5.2xlarge: 20 × $340 = $6.800/mês
  Total: $28.160/mês

Após Compute Optimizer (aplicou 70 recomendações):
  50 → 20 × m5.2xlarge + 30 × m5.xlarge: $5.520 + $4.140 = $9.660
  30 → 15 × r5.xlarge + 15 × r5.large:   $3.780 + $1.710 = $5.490
  20 → 10 × c5.2xlarge + 10 × c5.xlarge: $3.400 + $1.700 = $5.100
  Total: $20.250/mês

Economia: $7.910/mês = $94.920/ano (28% de redução)

Adicionando Graviton (migração para m6g, r6g, c6g):
  Redução adicional de ~20% → economia total ~43%
  = $12.108/mês = $145.296/ano
```

## 🧩 Quiz de Fixação

1. O Compute Optimizer recomenda fazer downgrade de uma instância m5.2xlarge para m5.xlarge com risco classificado como "Low". A CPU média foi de 12% e p99 foi de 31%. Por que o risco é baixo e em quais condições essa recomendação seria perigosa mesmo assim?
2. Por que olhar apenas CPUUtilization pode levar a um right-sizing incorreto, especialmente para bancos de dados?
3. Uma função Lambda processa imagens e usa 1024MB de memória, executando em 800ms. O Compute Optimizer sugere reduzir para 512MB. Antes de aplicar, qual teste você faria e por que o resultado pode ser contraintuitivo?

**Respostas:**
1) O risco é baixo porque o p99 (31%) está bem abaixo do limite de saturação (~85%), indicando que mesmo nos momentos de maior demanda nos últimos 14 dias, a instância menor teria headroom suficiente. A recomendação seria perigosa em dois cenários: (1) se houver eventos sazonais não captados nos 14 dias analisados — ex: processamento de final de mês, campanha de marketing planejada, onde o pico real seria 3-5x o usual; (2) se a aplicação for stateful e sensível a latência — mesmo com CPU baixa, o downgrade pode mudar a performance de rede ou I/O. Solução: aplicar em staging primeiro, monitorar durante um ciclo completo de negócio antes de confirmar em produção.
2) Para bancos de dados, o gargalo frequentemente não é CPU mas sim memória (buffer pool/cache de queries) e I/O. Um RDS com CPU a 15% pode estar com 90% da RAM usada como buffer de páginas de disco — reduzir a instância diminuiria o buffer pool, forçando mais leituras do disco e aumentando a latência. Além de CPU e RAM, bancos precisam de análise de: DatabaseConnections (próximo do máximo?), ReadLatency/WriteLatency (acima de 20ms?), ReadIOPS vs. provisioned IOPS (perto do limite?), e FreeStorageSpace. O right-sizing de banco sem analisar queries e perfil de I/O pode degradar severamente a performance mesmo com a instância "parecendo" ociosa.
3) Usar AWS Lambda Power Tuning para testar a função em múltiplos tamanhos de memória (128MB, 256MB, 512MB, 1024MB, 2048MB) e medir GB-ms (custo) e duração. O resultado contraintuitivo: com 512MB, o Lambda aloca proporcionalmente menos CPU — a função pode executar em 1.600ms em vez de 800ms. Multiplicando: 512MB × 1.6s = 819 GB-ms vs. 1024MB × 0.8s = 819 GB-ms — o custo é idêntico, mas a performance é 2x pior. Em alguns casos, aumentar a memória reduz o custo (execução muito mais rápida supera o custo do GB-ms adicional). O Power Tuning encontra o ótimo real com dados, não com intuição.
