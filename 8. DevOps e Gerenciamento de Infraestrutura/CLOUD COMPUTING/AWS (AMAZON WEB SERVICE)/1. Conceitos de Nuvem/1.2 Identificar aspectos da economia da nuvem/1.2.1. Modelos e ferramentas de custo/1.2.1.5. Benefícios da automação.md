### Benefícios da automação — eliminar trabalho manual, reduzir erros e liberar equipes

Automação na AWS é a prática de substituir tarefas manuais, repetitivas e propensas a erros por processos executados por software de forma confiável, rápida e escalável. Ela impacta diretamente o TCO ao reduzir horas de trabalho humano, eliminar erros custosos e permitir que times pequenos operem infraestruturas grandes. Na AWS, automação não é um luxo — é o modelo de operação esperado.

---

## Por que automação importa: o custo do trabalho manual

```
Tarefa manual típica: deployment de nova versão

Sem automação:
  1. Dev notifica Ops que há nova versão (email/Slack)
  2. Ops aguarda janela de manutenção (sexta, 23h)
  3. SSH no servidor de produção
  4. git pull / docker pull / atualiza configurações
  5. Reinicia serviço
  6. Testa manualmente (5-10 URLs)
  7. Documenta o que foi feito
  
  Tempo: 2-4 horas da noite
  Risco: passo esquecido, configuração errada, rollback manual
  Frequência: 1-2 deploys/semana (medo reduz cadência)
  Custo: horas do Ops + horas do Dev esperando + downtime possível

Com automação (CI/CD pipeline):
  Dev faz push para main
  → Pipeline executa testes automaticamente
  → Build da imagem Docker
  → Deploy canário: 10% → monitoramento → 100%
  → Notificação automática no Slack
  
  Tempo: 8-15 minutos (sem intervenção humana)
  Risco: mínimo (testes automatizados + rollback automático)
  Frequência: vários deploys por dia (confiança alta)
  Custo: fracção do custo manual
```

## Os quatro pilares de automação na AWS

### Pilar 1: Infraestrutura como Código (IaC)

```
Problema manual:
  Criar ambiente de staging = 3 dias de trabalho manual
  → Configura VPC, subnets, security groups
  → Sobe EC2, instala software, configura banco
  → Documenta (talvez)
  → Provavelmente diferente do ambiente de produção

Com IaC (Terraform / CloudFormation / CDK):

# main.tf — ambiente completo em um arquivo
module "vpc" {
  source = "./modules/vpc"
  cidr   = "10.0.0.0/16"
  azs    = ["us-east-1a", "us-east-1b"]
}

module "ecs_cluster" {
  source      = "./modules/ecs"
  vpc_id      = module.vpc.id
  environment = var.environment  # "staging" ou "production"
}

module "rds" {
  source     = "./modules/rds"
  multi_az   = var.environment == "production"
  instance_class = var.environment == "production" ? "db.r6g.large" : "db.t3.medium"
}

# terraform apply -var="environment=staging"
# Resultado: ambiente completo em 10-15 minutos
# Idêntico ao de produção, documentado no código

Benefícios:
  ├── Reprodutível: mesmo arquivo → mesmo ambiente sempre
  ├── Revisável: git blame mostra quem mudou o quê e quando
  ├── Testável: validates e plans antes de aplicar
  └── Destruível: terraform destroy → zera ambiente (dev/staging)
                  → não paga por ambiente quando não usa
```

### Pilar 2: Automação Orientada a Eventos (EventBridge + Lambda)

```
Padrão: evento ocorre → Lambda reage automaticamente

Caso 1: Limpeza automática de recursos esquecidos
  EventBridge Scheduler (todo dia às 22h):
  → Lambda verifica instâncias com tag "Environment=dev"
  → Se rodando há mais de 12 horas: envia alerta no Slack
  → Se rodando há mais de 24 horas: para automaticamente
  
  Benefício: nenhuma instância de dev fica ligada de madrugada
  Economia: ~66% do custo das instâncias de desenvolvimento

Caso 2: Resposta automática a alarmes de custo
  CloudWatch Alarm: gasto diário > $500
  → SNS → Lambda
  → Lambda: lista instâncias criadas nas últimas 24h
  → Lambda: envia relatório detalhado para o time
  → Lambda: aplica tag "review-required" nos recursos suspeitos

Caso 3: Escalamento automático de banco de dados
  CloudWatch Alarm: DatabaseConnections > 80% do máximo
  → SNS → Lambda
  → Lambda: verifica se é horário comercial
  → Se sim: aumenta max_connections via Parameter Group
  → Notifica DBA no Slack com contexto

Caso 4: Rotação automática de credenciais
  Secrets Manager schedule (a cada 30 dias):
  → Lambda customizado rotaciona a senha do banco
  → Atualiza o secret com nova senha
  → Verifica que aplicação conecta com nova senha
  → Invalida senha antiga
  → Sem intervenção humana, sem risco de esquecer
```

### Pilar 3: Automação de Operações (Systems Manager)

```
AWS Systems Manager (SSM) — gerenciamento sem SSH:

Run Command: executa scripts em frota de instâncias
  # Atualizar pacotes em todas as instâncias de produção
  aws ssm send-command \
    --targets "Key=tag:Environment,Values=production" \
    --document-name "AWS-RunShellScript" \
    --parameters "commands=['apt-get update && apt-get upgrade -y']"
  
  → Executa em paralelo em todas as instâncias tagueadas
  → Log de saída centralizado no CloudWatch
  → Sem abrir SSH, sem gerenciar chaves SSH

Patch Manager: patching automatizado
  Configuração:
  ├── Baseline de patches: "instalar patches críticos e importantes"
  ├── Janela de manutenção: Domingo, 02h-04h
  ├── Targets: todas as instâncias Linux de produção
  └── Pré-condição: snapshot antes do patch (rollback garantido)
  
  Resultado: 100% das instâncias sempre com patches de segurança
              sem intervenção manual, sem janelas manuais
              
  Custo do patch manual por instância: 30-60min de trabalho
  Com SSM Patch Manager: 0 minutos de trabalho humano

Session Manager: acesso seguro sem SSH/Bastion
  Sem automação: manter Bastion Host ($15-30/mês) + gerenciar chaves SSH
  Com SSM Session Manager:
  ├── Acesso via console ou CLI sem SSH key
  ├── Todo acesso logado no CloudTrail
  ├── Sem porta 22 aberta nos Security Groups
  └── Bastion Host pode ser desligado → economia + mais seguro

State Manager: manter configuração desejada
  Define: "todas as instâncias de produção devem ter o CloudWatch agent instalado"
  → SSM verifica periodicamente e reinstala se necessário
  → Drift de configuração detectado e corrigido automaticamente
```

### Pilar 4: CI/CD — Automação de Delivery

```
Pipeline completo automatizado:

Dev faz push → GitHub
         │
         ▼
[CodePipeline] orquestra:
    │
    ├── [CodeBuild] Stage: Test
    │     ├── Unit tests (pytest, jest)
    │     ├── Integration tests
    │     ├── Security scan (SAST)
    │     └── Docker build + vulnerability scan
    │
    ├── [CodeBuild] Stage: Build
    │     ├── Build artifact
    │     ├── Push imagem para ECR
    │     └── Atualiza versão no S3
    │
    └── [CodeDeploy] Stage: Deploy
          ├── Deploy canário: 10% das instâncias
          ├── Aguarda 10 minutos + monitora CloudWatch
          ├── Se alarm disparar → rollback automático
          └── Se OK → completa o deploy (100%)

Tempo total: 12-20 minutos
Intervenção humana: zero (a menos de alarme)
Frequência possível: múltiplos deploys por dia
```

## Automação e custo: exemplos quantificados

```
Caso 1: Agendamento de ambientes não-produção

  Antes (24/7):
  10 instâncias de dev × m5.xlarge × $0.192/h × 720h = $1.382/mês

  Com automação (8h/dia, 22 dias/mês):
  10 × m5.xlarge × $0.192/h × 176h = $338/mês
  
  Economia: $1.044/mês = $12.528/ano por 10 instâncias
  Custo da automação: ~4 horas de desenvolvimento (uma vez)
  ROI: payback em 2-3 dias de economia

Caso 2: Patching automatizado vs. manual

  Manual:
  50 servidores × 2h de trabalho/servidor/mês = 100h/mês
  SysAdmin sênior @ R$ 80/h = R$ 8.000/mês em patching
  
  SSM Patch Manager:
  Configuração inicial: 8 horas (uma vez)
  Manutenção mensal: 30 minutos de revisão de relatórios
  Custo: ~R$ 200/mês
  
  Economia: R$ 7.800/mês = R$ 93.600/ano
  (+ zero risco de esquecer servidor crítico sem patch)

Caso 3: Auto-remediation de alarmes

  Alarme "disco cheio" às 3h:
  Manual: Ops acordado → conecta → resolve → volta a dormir
  Custo: 2h de trabalho noturno (@150% = R$ 300) + plantão
  
  Automatizado: Lambda limpa logs antigos → resolve em 2 min
  Custo: ~$0.0002 de Lambda + 0 horas humanas
  
  Frequência: 3 ocorrências/mês
  Economia mensal: ~R$ 900 + bem-estar da equipe

Caso 4: Provisionamento de ambiente para novo cliente

  Manual (SaaS multi-tenant):
  30 minutos de trabalho de Ops → cria infraestrutura do cliente
  20 clientes/mês = 10 horas de Ops
  
  Automatizado (API call → CloudFormation StackSet):
  Cliente finaliza cadastro → webhook → CloudFormation
  Ambiente completo em 8 minutos, sem intervenção
  
  Economia: 10 horas/mês de Ops liberadas para outras tarefas
  Escalabilidade: 200 clientes/mês = mesmo custo de automação
```

## Automação de segurança (Security Automation)

```
Resposta automática a incidentes de segurança:

GuardDuty detecta: "EC2 comunicando com IP de C2 (malware)"
         │
         ▼
EventBridge rule → Lambda (Security Response)
         │
         ├── Isola a instância (Security Group → nega todo tráfego)
         ├── Tira snapshot para análise forense
         ├── Cria ticket no Jira
         ├── Notifica canal #security-incidents no Slack
         └── Registra no CloudTrail para auditoria

Tempo de resposta:
  Manual: 15-60 minutos (alguém precisa ver o alerta)
  Automatizado: 30-90 segundos

Impacto:
  Manual: malware tem 30-60 minutos para propagar/exfiltrar
  Automatizado: contenção em < 2 minutos

Config Rule + Auto-remediation:
  Regra: "Buckets S3 não podem ser públicos"
  Se violada:
  → Notifica imediatamente
  → Reverte automaticamente o ACL para privado
  → Registra quem fez a mudança (CloudTrail)
  → Time tem 0 minutos de exposição vs. horas sem automação
```

## Ferramentas de automação na AWS — resumo

| Ferramenta | Para que serve |
|---|---|
| **CloudFormation** | Provisionar e gerenciar infraestrutura como código |
| **CDK** | IaC com linguagens reais (Python, TypeScript, Java) |
| **Terraform** | IaC multi-cloud, estado gerenciado |
| **Lambda** | Automações event-driven, sem servidor a gerenciar |
| **EventBridge** | Roteamento de eventos para automações (agendamentos, reações) |
| **Systems Manager** | Gerenciamento de frota sem SSH (Run Command, Patch, State) |
| **CodePipeline** | Orquestra pipelines de CI/CD |
| **CodeBuild** | Build e testes automatizados |
| **CodeDeploy** | Deploy automatizado com rollback |
| **Step Functions** | Orquestra workflows complexos de múltiplos passos |
| **Config + Remediation** | Detecta e corrige desvios de configuração automaticamente |

## 🧩 Quiz de Fixação

1. Uma empresa tem 30 instâncias de desenvolvimento rodando 24/7. A equipe alega que "desligar manualmente é trabalhoso". Qual solução de automação resolve isso com zero esforço diário e qual a economia estimada para instâncias m5.large ($0.096/hora)?
2. O time de Ops gasta 40 horas/mês aplicando patches de segurança manualmente em 80 servidores. Qual serviço AWS elimina esse trabalho e quais são as garantias adicionais de segurança que o processo manual não oferece?
3. Por que automação de infraestrutura (IaC) reduz o custo total de operação além da simples redução de horas humanas?

**Respostas:**
1) EventBridge Scheduler + Lambda: regra para desligar instâncias com tag "Environment=development" todo dia às 20h e religar às 8h de segunda a sexta. Implementação: 4-8 horas de desenvolvimento, zero esforço diário. Economia: 30 instâncias × m5.large × $0.096/h × (720h - 176h) = 30 × $0.096 × 544h = $1.566/mês = $18.792/ano. Considerando que a implementação custa ~R$ 2.000 em horas de desenvolvimento, o payback é em menos de 2 meses.
2) AWS Systems Manager Patch Manager. Além de eliminar as 40 horas/mês de trabalho manual, oferece garantias que o processo manual não oferece: (1) Conformidade verificável — relatório de quais instâncias foram patcheadas, quais patches foram aplicados, quais falharam; (2) Sem instância esquecida — o processo é declarativo (define o target group, não instâncias individuais) — novas instâncias são automaticamente incluídas; (3) Snapshot pré-patch automático — rollback garantido se um patch quebrar a aplicação; (4) Log centralizado no CloudWatch — auditoria completa para compliance; (5) Janela de manutenção configurável — patches aplicados apenas no horário de menor impacto.
3) IaC reduz custo além das horas por várias razões: (1) Elimina drift de configuração — ambientes manuais divergem ao longo do tempo, causando bugs difíceis de reproduzir e custosos de investigar; com IaC, dev/staging/prod são idênticos; (2) Permite destruir e recriar — ambientes temporários (testes, demos) são criados e destruídos em minutos, eliminando custo de manter ambientes ociosos; (3) Revisão de mudanças — terraform plan mostra exatamente o que vai mudar antes de aplicar, eliminando surpresas custosas; (4) Onboarding de novos ambientes — novo cliente, nova região, novo ambiente: terraform apply resolve em minutos sem trabalho adicional da equipe; (5) Recuperação de desastres — recria o ambiente completo do zero em minutos a partir do código, em vez de horas ou dias de reconstrução manual.
