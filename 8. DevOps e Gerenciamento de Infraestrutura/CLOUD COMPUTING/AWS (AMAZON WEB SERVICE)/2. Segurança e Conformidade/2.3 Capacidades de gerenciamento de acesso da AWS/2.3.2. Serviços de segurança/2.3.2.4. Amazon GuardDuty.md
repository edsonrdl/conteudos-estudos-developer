### Amazon GuardDuty — detecção inteligente de ameaças sem agentes

Amazon GuardDuty é um serviço de threat detection gerenciado que monitora continuamente sua conta AWS em busca de atividades maliciosas e comportamentos anômalos. Diferente de ferramentas que precisam de agentes instalados ou configuração complexa de regras, o GuardDuty funciona analisando fontes de dados nativas da AWS (CloudTrail, VPC Flow Logs, DNS Logs) usando machine learning, análise de comportamento e inteligência de ameaças. É habilitado em segundos e começa a detectar ameaças imediatamente — sem modificar sua infraestrutura.

---

## Por que GuardDuty é diferente de outras ferramentas

```
Abordagem tradicional (SIEM/IDS):
  → Instalar agente em cada servidor
  → Configurar regras de detecção manualmente
  → Manter banco de assinaturas atualizado
  → Alta taxa de falsos positivos
  → Custos de infraestrutura para processar logs
  → Semanas para configurar e afinar

GuardDuty:
  → Zero agente, zero configuração de infraestrutura
  → Habilitado em 2 cliques ou 1 CLI call
  → ML pré-treinado pela AWS (anos de dados de ameaças)
  → Inteligência de ameaças da AWS + parceiros (CrowdStrike, Proofpoint)
  → Começa a detectar em minutos
  → Baixa taxa de falsos positivos (ML específico para AWS)
  → Custo baseado em volume de dados analisados
```

## Fontes de dados analisadas pelo GuardDuty

```
O GuardDuty analisa logs que a AWS já coleta internamente:

1. AWS CloudTrail Management Events:
   → Todas as chamadas de API de gerenciamento
   → "Quem criou/deletou/modificou recursos?"
   → Detecta: criação de IAM users, modificação de policies,
              download de credenciais, ações fora do padrão

2. VPC Flow Logs:
   → Tráfego de rede de/para instâncias EC2
   → "Quem está se comunicando com quem?"
   → Detecta: comunicação com C2 servers, port scanning,
              mineração de cripto (portas típicas), data exfiltration

3. DNS Query Logs:
   → Consultas DNS feitas pelas instâncias EC2
   → "Para quais domínios as instâncias estão resolendo?"
   → Detecta: consultas a domínios de malware conhecidos,
              DNS tunneling, C2 via DNS

4. EKS Audit Logs (proteção Kubernetes):
   → Eventos do plano de controle do EKS
   → Detecta: escalonamento de privilégios, pods maliciosos,
              acesso não autorizado à API do Kubernetes

5. S3 Data Events (proteção S3):
   → Operações em objetos S3 (GetObject, PutObject, etc.)
   → Detecta: exfiltração de dados, acesso anômalo,
              ransomware (criptografando objetos S3)

6. RDS Login Events (proteção banco de dados):
   → Tentativas de login em instâncias RDS
   → Detecta: força bruta, uso de credenciais comprometidas,
              logins de IPs suspeitos

7. Lambda Network Activity (proteção serverless):
   → Comunicação de rede de funções Lambda
   → Detecta: funções invocadas de IPs maliciosos,
              Lambda com comportamento de C2

Observação crítica:
  GuardDuty não precisa que você habilite VPC Flow Logs ou CloudTrail
  separadamente — ele acessa os logs diretamente de fontes internas
  da AWS. Você não paga duplo pelos logs.
```

## Como o GuardDuty detecta ameaças

### Machine Learning e Behavioral Analysis

```
GuardDuty aprende o baseline de comportamento normal:

Após 2 semanas de operação:
  "João normalmente faz login de São Paulo, das 9h às 19h,
   usa a API em us-east-1, acessa EC2 e S3"

Finding gerado quando:
  → João faz login de IP na Rússia às 3h
  → João acessa 10.000 objetos S3 em 5 minutos (padrão incomum)
  → João cria 5 IAM users em sequência (nunca fez isso antes)

Comparação contra peers:
  "Instâncias EC2 desta conta nunca se comunicaram
   com IPs em portas 6379/8333 antes"
  
  Finding: "EC2 comunicando com porta típica de mineração de cripto"
  
ML aprende padrões específicos de CADA conta
→ Menos falsos positivos que regras genéricas
```

### Threat Intelligence Feeds

```
GuardDuty integra listas de IPs e domínios maliciosos conhecidos:

Fontes próprias da Amazon:
  ├── IPs de C2 servers conhecidos
  ├── IPs usados em ataques anteriores contra clientes AWS
  └── Domínios de malware conhecidos

Parceiros integrados:
  ├── CrowdStrike: threat intelligence comercial
  ├── Proofpoint: threat intelligence de email/domínios
  └── Abuse.ch: listas de malware/botnet

Feeds customizados (você pode adicionar):
  → Threat IP List: IPs que você quer monitorar especificamente
  → Trusted IP List: IPs que nunca devem gerar findings (whitelist)
```

## Tipos de findings — o que o GuardDuty detecta

```
Findings são organizados por categoria e severidade:

Severidade:
  HIGH (7.0-8.9): ação imediata necessária
  MEDIUM (4.0-6.9): investigar em breve
  LOW (0.1-3.9): informacional, monitorar

Formato do finding:
  ThreatPurpose:ResourceTypeAffected/ThreatFamilyName.DetectionMechanism!Artifact
  
  Exemplo: UnauthorizedAccess:EC2/SSHBruteForce
  → Acesso não autorizado, EC2 sendo alvo, SSH brute force
```

### Principais findings por categoria

```
RECONHECIMENTO (Recon):
  Recon:EC2/PortProbing
  → Instância EC2 sendo varrida por scanner de portas
  → Severidade: LOW-MEDIUM

  Recon:IAMUser/MaliciousIPCaller
  → Chamadas de API IAM de IP malicioso conhecido
  → Severidade: MEDIUM

ACESSO NÃO AUTORIZADO (UnauthorizedAccess):
  UnauthorizedAccess:EC2/SSHBruteForce
  → Tentativas de força bruta SSH na instância
  → Severidade: LOW (entrada bloqueada)

  UnauthorizedAccess:IAMUser/ConsoleLoginSuccess.B
  → Login bem-sucedido no console de IP malicioso
  → Severidade: HIGH (acesso comprometido!)

  UnauthorizedAccess:IAMUser/TorIPCaller
  → Credenciais IAM usadas de nó TOR
  → Severidade: MEDIUM-HIGH

ESCALADA DE PRIVILÉGIOS (PrivilegeEscalation):
  PrivilegeEscalation:IAMUser/AdministrativePermissions
  → Usuário tentou criar role com privilégios maiores que os seus
  → Severidade: HIGH

PERSISTÊNCIA (Persistence):
  Persistence:IAMUser/UserPermissions
  → Usuário criou/modificou policies para manter acesso
  → Severidade: HIGH

  Persistence:EC2/MaliciousFile
  → Arquivo malicioso detectado na instância EC2
  → Severidade: HIGH

IMPACTO (Impact):
  Impact:EC2/BitcoinDomainRequest.Reputation
  → EC2 consultando domínios de pool de mineração de Bitcoin
  → Severidade: HIGH (instância comprometida, mineirando cripto)

  Impact:S3/AnomalousBehavior
  → Padrão anômalo de acesso a objetos S3 (possível exfiltração)
  → Severidade: HIGH

  Impact:EC2/PortSweep
  → EC2 varrendo outras instâncias em busca de portas abertas
  → Severidade: HIGH (EC2 comprometida fazendo reconhecimento interno)

CREDENCIAIS COMPROMETIDAS (CredentialAccess):
  CredentialAccess:IAMUser/AnomalousBehavior
  → Padrão anômalo de uso de credenciais IAM
  → Severidade: HIGH

  CredentialAccess:Kubernetes/ServiceAccountTokenUsedFromOutsideCluster
  → Token Kubernetes usado de fora do cluster
  → Severidade: HIGH

EXFILTRAÇÃO (Exfiltration):
  Exfiltration:S3/ObjectRead.Unusual
  → Volume incomum de leitura de objetos S3
  → Possível exfiltração de dados
  → Severidade: HIGH
```

## Resposta automática com EventBridge

```
GuardDuty + EventBridge = resposta automática a ameaças

Todo finding do GuardDuty é publicado como evento no EventBridge:

{
  "source": "aws.guardduty",
  "detail-type": "GuardDuty Finding",
  "detail": {
    "severity": 8.0,
    "type": "UnauthorizedAccess:IAMUser/ConsoleLoginSuccess.B",
    "resource": {
      "resourceType": "AccessKey",
      "accessKeyDetails": {
        "userName": "joao.silva",
        "accessKeyId": "AKIA..."
      }
    },
    "service": {
      "action": {
        "actionType": "NETWORK_CONNECTION",
        "remoteIpDetails": {
          "country": {"countryName": "Russia"},
          "ipAddressV4": "195.206.105.X"
        }
      }
    }
  }
}

Regras EventBridge para diferentes severidades:

HIGH (≥ 7.0) — resposta imediata automatizada:
  EventBridge rule: severity >= 7 → Lambda → ação automática
  
  Lambda "IncidentResponse":
  def handler(event, context):
      finding = event['detail']
      finding_type = finding['type']
      
      if 'IAMUser' in finding_type:
          # Desativar o usuário comprometido imediatamente
          iam.update_access_key(
              UserName=finding['resource']['accessKeyDetails']['userName'],
              AccessKeyId=finding['resource']['accessKeyDetails']['accessKeyId'],
              Status='Inactive'
          )
          
      if 'EC2' in finding_type and 'BitcoinDomain' in finding_type:
          # Isolar a instância comprometida
          ec2.modify_instance_attribute(
              InstanceId=finding['resource']['instanceDetails']['instanceId'],
              Groups=['sg-quarantine']  # Security Group que bloqueia tudo
          )
      
      # Notificar sempre
      sns.publish(
          TopicArn='arn:aws:sns:...:security-incidents',
          Subject=f"[CRITICAL] GuardDuty: {finding_type}",
          Message=json.dumps(finding, indent=2)
      )

MEDIUM (4.0-6.9) — notificação + ticket:
  EventBridge → SNS → email ao time de segurança
  EventBridge → Lambda → cria ticket no Jira/PagerDuty

LOW (0.1-3.9) — log e dashboard:
  EventBridge → CloudWatch Logs
  EventBridge → Security Hub (agregação)
```

## GuardDuty em múltiplas contas (Organizations)

```
Problema sem centralização:
  10 contas AWS × GuardDuty habilitado em cada uma
  → 10 consoles separados para verificar
  → Atacante compromete 1 conta: findings nessa conta
    enquanto outras contas não veem

Solução: GuardDuty Master/Member via Organizations

Configuração:
  Security Account = GuardDuty Administrator
  → Habilita GuardDuty como delegated admin
  → Todos os findings de TODAS as contas aparecem aqui
  
  aws organizations enable-aws-service-access \
    --service-principal guardduty.amazonaws.com
  
  aws guardduty enable-organization-admin-account \
    --admin-account-id [security-account-id]

Resultado:
  Security Account:
  ├── Vê findings de prod, dev, staging, tooling...
  ├── Configura supressão de findings centralmente
  └── Um único painel para toda a organização

Auto-enable para novas contas:
  Quando nova conta é adicionada à organização:
  → GuardDuty automaticamente habilitado
  → Findings enviados para Security Account
  → Zero configuração manual por conta

Custo com múltiplas contas:
  → Desconto de 70-80% no volume de dados após o primeiro threshold
  → Gerenciar como organização = custo menor que contas individuais
```

## Supressão de findings — reduzir ruído

```
Nem todo finding merece atenção imediata.
Supression Rules filtram findings conhecidos e esperados:

Caso comum: scanner de segurança interno
  Sua empresa roda Nessus/Qualys em 10.0.0.100
  → GuardDuty gera: Recon:EC2/PortProbing repetidamente
  → É comportamento esperado (seu scanner autorizado)
  
  Suppression Rule:
  Critério: tipo = "Recon:EC2/PortProbing"
            E IP de origem = "10.0.0.100"
  Ação: suprimir automaticamente (não mostrar no console, não alertar)
  
  Resultado: apenas port probing externo/inesperado gera finding

Caso comum 2: deploy automatizado de infra
  Pipeline cria/deleta instâncias frequentemente
  → Pode gerar findings de "atividade incomum de API"
  
  Suppression Rule:
  Critério: principal tag = "PipelineRole"
            E tipo = "UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration"
  Ação: suprimir

Atenção com supressão:
  → Suprimir muito = perder findings legítimos
  → Documentar cada supression rule (por que foi criada)
  → Revisar trimestralmente: a regra ainda faz sentido?
```

## 🧩 Quiz de Fixação

1. GuardDuty detecta o finding `Impact:EC2/BitcoinDomainRequest.Reputation` com severidade 8.0 em uma instância EC2 de produção. O que esse finding significa exatamente, e quais são os dois primeiros passos de resposta a incidente que devem ser tomados automaticamente via EventBridge?
2. Por que o GuardDuty pode detectar ameaças sem que o cliente precise habilitar VPC Flow Logs ou CloudTrail explicitamente, e qual a vantagem disso sobre soluções SIEM tradicionais?
3. Um engenheiro de segurança está vendo centenas de findings `Recon:EC2/PortProbing` por dia, todos originados do mesmo IP interno `10.0.0.50`, que é o servidor de vulnerability scanning da empresa. Como resolver isso sem perder visibilidade de port probing legítimo de atacantes externos?

**Respostas:**
1) O finding `Impact:EC2/BitcoinDomainRequest.Reputation` significa que a instância EC2 está fazendo consultas DNS para domínios conhecidos de pools de mineração de criptomoedas (como Monero ou Bitcoin). Isso indica fortemente que a instância foi comprometida e está sendo usada por um atacante para minerar cripto às custas da conta AWS — gerando custo de compute e expondo a instância como comprometida. Os dois primeiros passos automáticos via EventBridge + Lambda: (1) Isolamento imediato — modificar o Security Group da instância para um SG de "quarentena" que nega todo tráfego de entrada e saída (preserva a instância para análise forense mas impede comunicação com o pool de mineração e possível C2); (2) Snapshot forense — criar snapshot de todos os volumes EBS da instância para análise posterior, garantindo que as evidências não sejam perdidas. Concomitantemente: notificar o time de segurança via SNS/PagerDuty com todos os detalhes do finding.
2) GuardDuty acessa fontes de dados que a AWS já coleta internamente em sua própria infraestrutura — os logs existem independentemente de o cliente tê-los habilitado para seu próprio uso (S3, CloudWatch). A AWS tem acesso a esses logs de telemetria interna e os processa para o GuardDuty sem precisar que o cliente crie novos fluxos de dados. A vantagem sobre SIEMs tradicionais é tripla: (1) Zero overhead de infraestrutura — não há fluxo adicional de dados, storage de logs duplicado, ou custo de agentes; (2) Latência zero de setup — começa a analisar dados históricos e em tempo real imediatamente ao ser habilitado; (3) Sem "blind spots" de configuração — em SIEMs tradicionais, se o agente não está instalado em uma instância, ela não é monitorada; com GuardDuty, todo tráfego de rede (via VPC Flow Logs internos) e toda chamada de API (via CloudTrail interno) é analisado, independente de configuração.
3) Criar uma Suppression Rule no GuardDuty: critério combinado de `findingType = "Recon:EC2/PortProbing"` AND `remoteIpDetails.ipAddressV4 = "10.0.0.50"`. Essa regra suprime automaticamente apenas os findings de port probing originados especificamente desse IP interno — todos os outros findings de port probing (de IPs externos, de outros IPs internos não autorizados) continuam aparecendo normalmente. A suppressão não deleta os findings — eles ficam arquivados e podem ser consultados se necessário; apenas não aparecem no dashboard ativo nem geram alertas. Documentar a regra: "Supressão de PortProbing do scanner Qualys — IP 10.0.0.50 — aprovado pelo CISO em [data]". Revisar trimestralmente para verificar que o IP ainda pertence ao scanner autorizado (se o IP mudar, a regra precisa de atualização).
