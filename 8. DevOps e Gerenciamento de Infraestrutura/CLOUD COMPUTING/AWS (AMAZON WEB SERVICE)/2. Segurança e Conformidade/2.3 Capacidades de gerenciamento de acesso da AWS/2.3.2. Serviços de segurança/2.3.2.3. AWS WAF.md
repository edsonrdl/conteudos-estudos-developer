### AWS WAF — firewall de aplicação web para proteção na camada 7

AWS WAF (Web Application Firewall) é um serviço que inspeciona e filtra tráfego HTTP/HTTPS na camada de aplicação (Layer 7). Enquanto o AWS Shield protege contra ataques volumétricos de rede, o WAF protege contra ataques que exploram vulnerabilidades da aplicação em si — SQL injection, XSS, bots maliciosos, scrapers e abuso de APIs. É a última linha de defesa antes que uma requisição maliciosa chegue ao seu backend.

---

## Como o WAF funciona

```
Sem WAF:
  Internet → CloudFront/ALB → Aplicação
  → Qualquer requisição chega ao backend
  → SQL injection, XSS, bots: chegam ao código

Com WAF:
  Internet → [WAF] → CloudFront/ALB → Aplicação
  
  Cada requisição HTTP é inspecionada:
  ├── Headers (User-Agent, Host, Referer, Authorization)
  ├── URI path (/admin, /api/v1/users)
  ├── Query strings (?id=1 OR 1=1)
  ├── Body da requisição (JSON payload, form data)
  └── Cookies
  
  Decisão para cada requisição:
  ├── ALLOW: repassa para o backend
  ├── BLOCK: retorna 403 (sem chegar ao backend)
  └── COUNT: permite mas registra (modo de monitoramento)
```

## Componentes do AWS WAF

### Web ACL (Access Control List)

```
Web ACL é o contêiner principal das regras WAF:
  → Criada por região (exceto CloudFront: us-east-1 global)
  → Associada a um ou mais recursos (CloudFront, ALB, API GW, AppSync)
  → Avalia regras em ordem de prioridade (menor número = maior prioridade)
  → Ação padrão: ALLOW (tudo que não casou com nenhuma regra)
    ou BLOCK (modo restritivo, mais seguro)

Capacidade (WCU — WAF Capacity Units):
  → Cada Web ACL tem limite de 1.500 WCU (padrão, aumentável)
  → Cada regra consome WCUs (mais complexa = mais WCUs)
  → Managed Rules: pacotes que consomem entre 100-700 WCUs cada
  → Monitorar: não ultrapassar o limite da Web ACL

Custo do WAF:
  → $5/mês por Web ACL
  → $1/mês por regra
  → $0.60 por 1 milhão de requisições inspecionadas
  → Managed Rule Groups: gratuitas (AWS) ou pagas (marketplace)
```

### Tipos de regras

```
RULE GROUPS (grupos de regras):
  → Conjunto de regras reutilizável
  → Criadas por AWS (Managed), marketplace, ou pelo cliente (Custom)
  → Adicionadas à Web ACL como unidade

Exemplo de hierarquia:
  Web ACL: "producao-waf"
  ├── Prioridade 1: AWS-ManagedRules-CommonRuleSet (bloqueio OWASP Top 10)
  ├── Prioridade 2: AWS-ManagedRules-SQLiRuleSet (proteção SQL Injection)
  ├── Prioridade 3: RateLimit-API (custom: 100 req/5min por IP)
  ├── Prioridade 4: BlockBadBots (custom: bloqueia User-Agents conhecidos)
  └── Prioridade 100: AWS-ManagedRules-BotControl (bots)
  
  Ação padrão (nenhuma regra casou): ALLOW
```

## Managed Rule Groups — proteção pronta para usar

### AWS Managed Rules (gratuitas)

```
1. Core Rule Set (CRS) — proteção OWASP Top 10:
   Protege contra:
   ├── Cross-site scripting (XSS)
   ├── Local file inclusion (LFI)
   ├── Remote file inclusion (RFI)
   ├── Command injection
   ├── Malicious path traversal (../../etc/passwd)
   └── Hosts bloqueados: locais, loopback, link-local
   
   WCU: 700 | Ação: Block

2. SQL Database Rule Set:
   Protege contra SQL injection especificamente
   ├── Detecta padrões SQL em query strings, body, cookies
   ├── Exemplos: OR 1=1, UNION SELECT, DROP TABLE
   └── WCU: 200 | Ação: Block

3. Known Bad Inputs:
   ├── Log4J exploit (Log4Shell — CVE-2021-44228)
   ├── SSRF patterns
   ├── Shellshock
   └── WCU: 200 | Ação: Block

4. Linux OS Rule Set:
   ├── Tentativas de exploração de SO Linux
   ├── Shell commands em headers/body
   └── WCU: 200

5. Windows OS Rule Set:
   ├── PowerShell injection
   ├── Windows path traversal
   └── WCU: 200

6. PHP Application Rule Set:
   ├── PHP function injection
   ├── PHP object injection
   └── WCU: 100

7. Anonymous IP List:
   ├── Bloqueia TOR exit nodes
   ├── Bloqueia VPNs conhecidas
   ├── Bloqueia proxies conhecidos
   └── WCU: 50 | Útil contra scrapers que usam anonimização

8. Amazon IP Reputation List:
   ├── IPs com histórico de atividade maliciosa na AWS
   ├── Atualizada pela inteligência de ameaças da Amazon
   └── WCU: 25
```

### AWS WAF Bot Control (pago)

```
Bot Control — gerenciamento de bots:

Custo: $10/mês + $1 por 1 milhão de requisições verificadas

Categorias de bots:
  COMMON Bots (nível básico):
  ├── Bots verificados: Googlebot, Bingbot, Slackbot (permitir)
  ├── Bots monitorados: scrapers genéricos (count ou block)
  └── Bots maliciosos: ferramentas de scanning (block)
  
  TARGETED Bots (nível avançado, +$30/mês):
  ├── TLS fingerprinting: identifica bots que imitam browsers
  ├── Browser interrogation: verifica execução de JavaScript
  ├── CAPTCHA integration: desafia bots sofisticados
  └── Detecção de sessão: comportamento anômalo ao longo da sessão

Por que bots importam:
  → 40-50% do tráfego internet é bot
  → Scrapers coletam seu conteúdo e preços
  → Credential stuffing: testa senhas vazadas em massa
  → Inventory hoarding: bots compram estoque antes de humanos
  → Fake account creation: registro em massa por bots
```

## Regras customizadas — lógica específica do seu negócio

### Rate-based Rules (controle de taxa)

```
Bloqueia IPs que excedem limite de requisições em janela de tempo:

Regra básica — proteção geral:
{
  "Name": "RateLimitGeral",
  "Priority": 5,
  "Action": {"Block": {}},
  "Statement": {
    "RateBasedStatement": {
      "Limit": 2000,           ← máximo de requisições
      "AggregateKeyType": "IP", ← por IP de origem
      "EvaluationWindowSec": 300  ← janela de 5 minutos
    }
  }
}
→ Qualquer IP que fizer mais de 2.000 req em 5 min: BLOQUEADO
→ Após 5 min sem atingir o limite: IP desbloqueado automaticamente

Regra específica — proteção de endpoint sensível:
{
  "Name": "RateLimitLogin",
  "Priority": 3,
  "Action": {"Block": {}},
  "Statement": {
    "RateBasedStatement": {
      "Limit": 20,
      "AggregateKeyType": "IP",
      "EvaluationWindowSec": 300,
      "ScopeDownStatement": {  ← aplica apenas para este path
        "ByteMatchStatement": {
          "SearchString": "/auth/login",
          "FieldToMatch": {"UriPath": {}},
          "TextTransformations": [{"Type": "LOWERCASE", "Priority": 0}],
          "PositionalConstraint": "STARTS_WITH"
        }
      }
    }
  }
}
→ Máximo 20 tentativas de login por IP em 5 min
→ Protege contra credential stuffing sem afetar navegação normal
```

### Regras de correspondência (Match Rules)

```
Bloquear por User-Agent (bots conhecidos):
{
  "Name": "BlockKnownBadUserAgents",
  "Priority": 2,
  "Action": {"Block": {}},
  "Statement": {
    "OrStatement": {
      "Statements": [
        {
          "ByteMatchStatement": {
            "SearchString": "sqlmap",
            "FieldToMatch": {"SingleHeader": {"Name": "user-agent"}},
            "PositionalConstraint": "CONTAINS",
            "TextTransformations": [{"Type": "LOWERCASE", "Priority": 0}]
          }
        },
        {
          "ByteMatchStatement": {
            "SearchString": "nikto",
            "FieldToMatch": {"SingleHeader": {"Name": "user-agent"}},
            "PositionalConstraint": "CONTAINS",
            "TextTransformations": [{"Type": "LOWERCASE", "Priority": 0}]
          }
        },
        {
          "ByteMatchStatement": {
            "SearchString": "masscan",
            "FieldToMatch": {"SingleHeader": {"Name": "user-agent"}},
            "PositionalConstraint": "CONTAINS",
            "TextTransformations": [{"Type": "LOWERCASE", "Priority": 0}]
          }
        }
      ]
    }
  }
}

Bloquear por IP (IP Set):
  IP Set: lista de IPs ou CIDRs a bloquear/permitir
  
  Uso: lista negra de IPs conhecidamente maliciosos
  Uso: lista branca de IPs de parceiros (apenas eles acessam /admin)
  
  Criação:
  aws wafv2 create-ip-set \
    --name "BlockedIPs" \
    --scope REGIONAL \
    --ip-address-version IPV4 \
    --addresses "192.0.2.0/24" "198.51.100.0/24"

Bloquear por geo (geo-block):
{
  "Name": "GeoBlock",
  "Priority": 1,
  "Action": {"Block": {}},
  "Statement": {
    "GeoMatchStatement": {
      "CountryCodes": ["KP", "RU", "CN", "IR"]
    }
  }
}
→ Bloquear países sem usuários legítimos
→ Reduz superfície de ataque drasticamente para aplicações locais
```

### Regras com Labels (encadeamento de regras)

```
Labels permitem criar lógica complexa multi-passo:

Regra 1: marcar IPs suspeitos
  Detecta: mais de 5 erros 4xx em 1 minuto
  Ação: COUNT (não bloqueia) + adicionar label "suspicious-ip"

Regra 2: verificar suspeitos
  Condição: requisição tem label "suspicious-ip" E tenta acessar /admin
  Ação: BLOCK

→ Combinação de comportamento (5 erros) + alvo (admin)
   produz bloqueio mais preciso do que cada condição isolada
```

## Posicionamento do WAF

### CloudFront + WAF (proteção global)

```
Vantagens de WAF no CloudFront:
  ├── Proteção na edge (160+ locais globais)
  ├── Ataque bloqueado antes de chegar à região
  ├── Latência de processamento WAF na edge (< 1ms)
  ├── Bloqueia tráfego antes de gerar custo de processamento no backend
  └── Web ACL em us-east-1 (global, não por região)

Posicionamento:
  Internet → [WAF + CloudFront] → ALB → EC2/ECS
  
  Consideração importante:
  → Se ALB é publicamente acessível (sem CloudFront na frente):
    atacante pode bypassar o WAF acessando ALB diretamente
  → Solução: Security Group do ALB aceita apenas IPs do CloudFront
    (lista de IPs mantida por AWS: ip-ranges.amazonaws.com)

### ALB + WAF (proteção regional)

```
Vantagens de WAF no ALB:
  ├── Segunda camada de defesa (se CloudFront for bypassado)
  ├── Inspeção de tráfego que não passa pelo CloudFront
  ├── Web ACL por região (mais controle)
  └── Necessário para APIs não servidas pelo CloudFront

Dupla proteção (CloudFront + ALB):
  WAF no CloudFront: bloqueia na edge globalmente
  WAF no ALB: segunda camada se tráfego chegar direto ao ALB
  
  Cada WAF pode ter regras diferentes:
  → CloudFront WAF: geo-block + bot control (amplo)
  → ALB WAF: rate limit por endpoint + regras específicas de API
```

## Logging e visibilidade

```
WAF Full Logging:
  → Todo log de cada requisição avaliada
  → Destinos: S3, CloudWatch Logs, Kinesis Firehose
  
  O que está no log:
  ├── Timestamp, URI, IP de origem
  ├── Regra que casou (ou nenhuma)
  ├── Ação tomada (ALLOW/BLOCK/COUNT)
  ├── Headers relevantes
  └── Labels aplicadas

Query de análise (Athena sobre S3 logs):
  -- Quais regras estão bloqueando mais?
  SELECT ruleGroupList, COUNT(*) as blocks
  FROM waf_logs
  WHERE action = 'BLOCK'
  AND from_unixtime(timestamp/1000) > now() - interval '24' hour
  GROUP BY 1
  ORDER BY 2 DESC;
  
  -- Quais IPs estão sendo mais bloqueados?
  SELECT httprequest.clientip, COUNT(*) as blocks
  FROM waf_logs
  WHERE action = 'BLOCK'
  GROUP BY 1
  ORDER BY 2 DESC
  LIMIT 20;

CloudWatch Metrics automáticas:
  ├── AllowedRequests: requests permitidas
  ├── BlockedRequests: requests bloqueadas
  ├── CountedRequests: requests em modo COUNT
  └── PassedRequests: requests que não casaram com nenhuma regra
  
  Dashboard: proporção de BlockedRequests durante um ataque
  Alarm: BlockedRequests > 10.000/min → SNS → alerta
```

## Modo de implantação seguro: COUNT antes de BLOCK

```
Nunca adicionar uma nova regra diretamente em BLOCK em produção.

Processo correto:

Semana 1 — Modo COUNT:
  Adicionar regra com ação COUNT (não bloqueia, apenas registra)
  → Monitorar logs: quantas requisições a regra teria bloqueado?
  → Verificar: há falsos positivos (usuários legítimos sendo contados)?
  
  Análise:
  → 10.000 blocks/dia: a regra está funcionando
  → 5 requests de usuários legítimos bloqueadas: falso positivo!
    (precisa ajustar a regra antes de ativar BLOCK)

Semana 2 — Ajuste e validação:
  → Se falsos positivos: refinar a regra (adicionar exceções)
  → Se nenhum falso positivo: pronto para bloquear

Semana 3 — Ativar BLOCK:
  → Mudar ação de COUNT para BLOCK
  → Monitorar CloudWatch nas primeiras horas
  → Se tráfego legítimo afetado: reverter para COUNT

Exceções (whitelist para falsos positivos):
  Regra que bloqueia mas tem falso positivo:
  → Adicionar regra de prioridade MAIOR (número menor)
  → Regra de exceção: ALLOW para o padrão legítimo
  → Regra principal: BLOCK para o padrão malicioso geral
  
  Exemplo:
  Prioridade 1: ALLOW se /api/internal (sua própria API)
  Prioridade 5: BLOCK se body contém SQL keywords (CRS)
  → /api/internal com SQL válido: passa (prioridade 1 vence)
  → Request externa com SQL: bloqueia
```

## 🧩 Quiz de Fixação

1. Um e-commerce brasileiro usa CloudFront + ALB. O time de segurança quer adicionar o AWS Managed Rule Group "Core Rule Set" para proteção OWASP. Qual o risco de adicionar diretamente em BLOCK sem testar, e qual o processo correto de implantação?
2. A aplicação está sofrendo credential stuffing: bots testam senhas de usuários vazadas em `/auth/login` a 500 tentativas por IP por hora. O time quer bloquear isso sem afetar usuários legítimos (que raramente tentam mais de 5 logins por hora). Escreva a lógica da Rate-Based Rule que resolveria isso.
3. Por que adicionar WAF apenas no CloudFront pode ser insuficiente, e qual é a configuração complementar necessária para garantir que nenhum tráfego bypass o WAF acessando o ALB diretamente?

**Respostas:**
1) O risco de adicionar Core Rule Set em BLOCK diretamente: o CRS é uma regra genérica que detecta padrões OWASP em headers, query strings e body. Aplicações legítimas frequentemente têm parâmetros que casam com padrões de XSS/SQLi — ex: um campo de busca que aceita `<` e `>` para filtros matemáticos pode ser bloqueado como XSS, ou uma API que recebe queries com `SELECT` em nomes de campos pode ser bloqueada como SQLi. Bloquear em produção sem teste pode derrubar funcionalidades críticas para usuários reais. Processo correto: (1) Adicionar CRS com ação COUNT por 1-2 semanas em horário de tráfego real; (2) Analisar logs: quais URIs, headers e bodies estão sendo contados? São legítimos ou maliciosos? (3) Para cada falso positivo identificado: criar regra de exceção com prioridade maior (ALLOW explícito para esse padrão específico); (4) Após validar que não há mais falsos positivos não tratados: mudar ação para BLOCK; (5) Monitorar CloudWatch nas primeiras 2-4 horas após ativação.
2) Rate-Based Rule para credential stuffing: `{"Name": "ProtectLogin", "Priority": 3, "Action": {"Block": {}}, "Statement": {"RateBasedStatement": {"Limit": 10, "AggregateKeyType": "IP", "EvaluationWindowSec": 300, "ScopeDownStatement": {"ByteMatchStatement": {"SearchString": "/auth/login", "FieldToMatch": {"UriPath": {}}, "PositionalConstraint": "STARTS_WITH", "TextTransformations": [{"Type": "LOWERCASE", "Priority": 0}]}}}}}` — limite de 10 requisições em 5 minutos (300s) por IP, aplicado apenas ao path `/auth/login`. Usuário legítimo que erra a senha 3-4 vezes nunca atingirá 10; bot que testa 500 senhas por hora atingirá o limite em menos de 1 minuto e ficará bloqueado pelos 5 minutos seguintes, tornando o ataque 300x mais lento. O threshold de 10 dá margem para um usuário legítimo esquecido sem impactar a proteção.
3) O WAF no CloudFront protege apenas tráfego que passa pelo CloudFront. Se o ALB tem um IP/DNS público e o atacante o descobre (via reverse DNS, certificate transparency logs, ou enumeração de IPs), pode enviar requisições diretamente ao ALB bypassando completamente o CloudFront e o WAF. A configuração complementar necessária: (1) Security Group do ALB deve aceitar tráfego APENAS dos IPs do CloudFront — a AWS publica a lista de IPs de borda do CloudFront em `ip-ranges.amazonaws.com` (filtrar por `service: CLOUDFRONT`); (2) Automatizar atualização do Security Group: EventBridge + Lambda que atualiza o SG quando a lista de IPs do CloudFront é publicada (a AWS notifica via SNS quando a lista muda); (3) Opcional mas recomendado: adicionar WAF também no ALB como segunda camada de defesa, mesmo que o SG já restrinja — defense in depth garante proteção mesmo se o SG for mal configurado.
