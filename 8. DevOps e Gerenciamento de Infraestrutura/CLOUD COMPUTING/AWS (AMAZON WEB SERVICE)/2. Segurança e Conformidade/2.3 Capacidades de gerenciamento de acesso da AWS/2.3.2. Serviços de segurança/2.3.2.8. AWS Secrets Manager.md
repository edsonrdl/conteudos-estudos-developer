### AWS Secrets Manager — gerenciamento seguro e rotação automática de credenciais

AWS Secrets Manager é o serviço que armazena, gerencia e rotaciona automaticamente credenciais sensíveis — senhas de banco de dados, API keys, tokens OAuth, certificados — eliminando a necessidade de hardcodar ou gerenciar manualmente esses segredos nas aplicações. É a solução definitiva para o problema mais comum de segurança em código: credenciais expostas. A rotação automática é a característica que o diferencia fundamentalmente de qualquer alternativa de armazenamento seguro.

---

## O problema que o Secrets Manager resolve

```
O ciclo vicioso das credenciais hardcoded:

1. Dev cria conexão com banco:
   DB_PASSWORD = "senha123prod"  ← hardcoded no código
   
2. Código vai para o repositório Git
3. Alguém faz grep no repositório → encontra a senha
4. Vazamento ocorre
5. Time muda a senha → precisa atualizar em todos os lugares
   (código, variáveis de ambiente, scripts, pipelines...)
6. Algum lugar esquece de atualizar → aplicação quebra
7. Time tem medo de mudar a senha novamente
8. A senha nunca mais é rotacionada → fica exposta permanentemente

Evidência real: GitHub tem bots que escaneiam repos públicos
em busca de credenciais em milissegundos após o push.
AWS detecta suas próprias access keys expostas no GitHub e
as desativa automaticamente — nenhum humano aciona isso.

Com Secrets Manager:
  → Sem credenciais no código
  → Sem credenciais em variáveis de ambiente em texto claro
  → Rotação automática periódica
  → Aplicação sempre usa a versão atual do secret
  → Auditoria de quem acessou qual secret e quando
```

## Secrets Manager vs Parameter Store — qual usar

```
AWS tem dois serviços para armazenar segredos/configurações:

PARAMETER STORE (SSM Parameter Store):
  Tipos:
  ├── String: texto simples
  ├── StringList: lista de strings
  └── SecureString: criptografado com KMS

  Características:
  ├── Gratuito (Standard tier, até 4KB por parâmetro)
  ├── Advanced: $0.05/parâmetro/mês
  ├── SEM rotação automática
  ├── Versionamento simples
  ├── Integrado nativo com SSM Agent e Run Command
  └── Ideal para: configurações da aplicação, flags,
                  parâmetros não-secretos, tuning de infra

SECRETS MANAGER:
  Características:
  ├── $0.40/secret/mês + $0.05 por 10.000 API calls
  ├── Rotação automática (com Lambda)
  ├── Integração nativa com RDS, Redshift, DocumentDB, Elasticsearch
  ├── Cross-account replication (replicar em múltiplas regiões/contas)
  ├── Versionamento com stages (AWSPENDING, AWSCURRENT, AWSPREVIOUS)
  └── Ideal para: credenciais de banco, API keys, tokens,
                  qualquer segredo que precise de rotação

REGRA PRÁTICA:
  Precisa de rotação automática? → Secrets Manager
  Senha de banco de produção? → Secrets Manager
  API key de terceiro? → Secrets Manager
  Parâmetro de configuração? → Parameter Store (mais barato)
  Feature flag? → Parameter Store
  String de conexão estática? → Parameter Store (SecureString)
```

## Criando e usando secrets

### Criar um secret

```
Via Console:
  Secrets Manager → Store a new secret
  Tipo: "Credentials for Amazon RDS database"
  → Preenche automaticamente com username e password
  → Configura o banco associado
  
  Ou manualmente:
  Secret type: Other type of secret
  Key/value pairs:
    username: app_user
    password: SenhaForte!2024
    host: mydb.abc.us-east-1.rds.amazonaws.com
    port: 5432
    dbname: producao

Via CLI:
  aws secretsmanager create-secret \
    --name "prod/checkout/database" \
    --description "Credenciais do banco de checkout em produção" \
    --secret-string '{
      "username": "checkout_user",
      "password": "SenhaForte!2024",
      "host": "checkout-db.cluster-xxx.us-east-1.rds.amazonaws.com",
      "port": 5432,
      "dbname": "checkout_prod"
    }' \
    --kms-key-id alias/checkout-secrets-key

Convenção de nomenclatura recomendada:
  {ambiente}/{serviço}/{tipo}
  prod/checkout/database
  prod/checkout/stripe-api-key
  staging/auth/jwt-secret
  dev/payments/sandbox-api-key
```

### Acessar o secret na aplicação

```
Python (boto3):
import boto3
import json

def get_db_credentials():
    client = boto3.client('secretsmanager', region_name='us-east-1')
    
    response = client.get_secret_value(
        SecretId='prod/checkout/database'
    )
    
    secret = json.loads(response['SecretString'])
    return {
        'host': secret['host'],
        'port': secret['port'],
        'database': secret['dbname'],
        'user': secret['username'],
        'password': secret['password']
    }

# Uso na aplicação
db_creds = get_db_credentials()
connection = psycopg2.connect(**db_creds)

Node.js (AWS SDK v3):
const { SecretsManagerClient, GetSecretValueCommand } = require('@aws-sdk/client-secrets-manager');

async function getDatabaseCredentials() {
  const client = new SecretsManagerClient({ region: 'us-east-1' });
  const command = new GetSecretValueCommand({ SecretId: 'prod/checkout/database' });
  const response = await client.send(command);
  return JSON.parse(response.SecretString);
}

// Cache local para evitar chamadas repetidas ao SM:
let cachedCreds = null;
let cacheExpiry = null;

async function getCachedCredentials() {
  if (cachedCreds && Date.now() < cacheExpiry) {
    return cachedCreds;
  }
  cachedCreds = await getDatabaseCredentials();
  cacheExpiry = Date.now() + (5 * 60 * 1000); // cache por 5 minutos
  return cachedCreds;
}

Boas práticas de acesso:
  ├── Cache local: não chamar SM a cada requisição (latência + custo)
  ├── Cache por 5-10 minutos (considera que rotação pode alterar o secret)
  ├── Catch de exception: se SM falhar, usar credencial em cache
  └── Rotation-aware: após rotação, cache expira e nova cred é buscada
```

## Rotação automática — o diferencial do Secrets Manager

### Como funciona a rotação

```
O Secrets Manager usa uma função Lambda para implementar a rotação.
A Lambda segue um protocolo de 4 etapas:

ETAPA 1 — createSecret:
  → Lambda cria nova credencial (ex: nova senha no banco)
  → Armazena com stage "AWSPENDING"
  → Versão AWSCURRENT ainda ativa (aplicação continua funcionando)

ETAPA 2 — setSecret:
  → Lambda testa se a nova credencial funciona
  → Verifica conectividade com o banco usando AWSPENDING

ETAPA 3 — testSecret:
  → Lambda verifica que AWSPENDING está funcional
  → Testa operação real (SELECT 1, por exemplo)

ETAPA 4 — finishSecret:
  → Lambda promove AWSPENDING para AWSCURRENT
  → AWSCURRENT anterior vira AWSPREVIOUS
  → Aplicação na próxima chamada GetSecretValue recebe nova senha

Stages de versão:
  AWSCURRENT:  versão ativa (o que GetSecretValue retorna por padrão)
  AWSPENDING:  nova versão em processo de rotação
  AWSPREVIOUS: versão anterior (disponível por período de graça)
  
  Se a aplicação usa AWSPREVIOUS (por cache):
  → Ainda funciona durante o período de transição
  → Período de graça: geralmente algumas horas
  → Após período de graça: banco invalida senha antiga
```

### Rotação nativa para bancos de dados AWS

```
Para RDS (MySQL, PostgreSQL, Oracle, SQL Server):
  Secrets Manager tem Lambda pré-construída pela AWS

Configuração:
  1. Console Secrets Manager → secret → Rotation
  2. Automatic rotation: ON
  3. Schedule: 
     ├── Rate: "30 days" (rotacionar a cada 30 dias)
     └── Cron: "0 6 1 * ? *" (todo dia 1 do mês às 6h UTC)
  4. Rotation function: 
     ├── Use rotation function provided by Secrets Manager (automático)
     └── Ou: escolher Lambda customizada

Tipos de rotação para RDS:
  1. Single user rotation:
     → A mesma senha do usuário é rotacionada
     → Risco: janela pequena onde a senha antiga ainda funciona
        mas Secrets Manager já atualizou (race condition)
     → Adequado: aplicação tem retry logic
  
  2. Alternating users rotation:
     → Dois usuários alternados (app_user_a, app_user_b)
     → Enquanto um está sendo rotacionado, o outro está ativo
     → Zero race condition
     → Adequado: aplicações de produção de alta disponibilidade

Via CLI:
  aws secretsmanager rotate-secret \
    --secret-id prod/checkout/database \
    --rotation-rules AutomaticallyAfterDays=30
```

### Lambda customizada para rotação de outros secrets

```
Para API keys de terceiros (Stripe, SendGrid, etc.):
  Não há Lambda pré-construída pela AWS → você cria

Estrutura da Lambda de rotação:

import boto3
import json

def lambda_handler(event, context):
    arn = event['SecretId']
    token = event['ClientRequestToken']
    step = event['Step']
    
    sm_client = boto3.client('secretsmanager')
    
    if step == 'createSecret':
        # Gerar nova API key no serviço de terceiro
        new_key = generate_new_stripe_key()
        
        sm_client.put_secret_value(
            SecretId=arn,
            ClientRequestToken=token,
            SecretString=json.dumps({'api_key': new_key}),
            VersionStages=['AWSPENDING']
        )
    
    elif step == 'setSecret':
        # Ativar a nova key no serviço de terceiro
        pending = get_secret_dict(sm_client, arn, 'AWSPENDING')
        activate_stripe_key(pending['api_key'])
    
    elif step == 'testSecret':
        # Testar que a nova key funciona
        pending = get_secret_dict(sm_client, arn, 'AWSPENDING')
        test_stripe_api_call(pending['api_key'])
    
    elif step == 'finishSecret':
        # Promover AWSPENDING → AWSCURRENT
        sm_client.update_secret_version_stage(
            SecretId=arn,
            VersionStage='AWSCURRENT',
            MoveToVersionId=token,
            RemoveFromVersionId=get_current_version_id(sm_client, arn)
        )
        # Revogar key antiga no Stripe
        revoke_old_stripe_key()
```

## Replicação cross-region e cross-account

```
Cross-Region Replication:
  Secret em us-east-1 → replicado para sa-east-1

  Caso de uso: DR (disaster recovery)
    → Aplicação failover para sa-east-1: secret disponível localmente
    → Sem latência de cross-region para GetSecretValue

  Caso de uso: compliance de residência de dados
    → Secret com credenciais de dados brasileiros em sa-east-1
    → Réplica de leitura disponível para aplicações na região

  Configuração:
  aws secretsmanager replicate-secret-to-regions \
    --secret-id prod/checkout/database \
    --add-replica-regions '[{"Region": "sa-east-1"}]'

Cross-Account (compartilhar secret):
  Resource Policy no secret:
  {
    "Statement": [{
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::conta-analytics:role/DataEngineeringRole"
      },
      "Action": ["secretsmanager:GetSecretValue"],
      "Resource": "*"
    }]
  }
  → Conta de Analytics pode ler o secret sem ter credenciais na conta principal
```

## Integração com ECS e Kubernetes

```
ECS Task Definition — injetar secret como variável de ambiente:
  {
    "containerDefinitions": [{
      "name": "checkout-api",
      "secrets": [{
        "name": "DB_PASSWORD",
        "valueFrom": "arn:aws:secretsmanager:us-east-1:123:secret:prod/checkout/database:password::"
      }]
    }]
  }
  → ECS busca o secret no Secrets Manager automaticamente
  → Injetado como variável de ambiente DB_PASSWORD
  → Task Role precisa de permissão secretsmanager:GetSecretValue

Kubernetes (EKS) — External Secrets Operator:
  ExternalSecret manifest:
  apiVersion: external-secrets.io/v1beta1
  kind: ExternalSecret
  metadata:
    name: checkout-db-secret
  spec:
    refreshInterval: 1h
    secretStoreRef:
      name: aws-secretsmanager
      kind: SecretStore
    target:
      name: checkout-db-secret  # Cria um Kubernetes Secret
    data:
      - secretKey: password
        remoteRef:
          key: prod/checkout/database
          property: password
  
  → External Secrets Operator busca do SM periodicamente
  → Cria/atualiza Kubernetes Secret automaticamente
  → Pods usam o Kubernetes Secret (sem acesso direto ao SM)
```

## Auditoria e monitoramento

```
CloudTrail registra todos os acessos:
  GetSecretValue: quem acessou qual secret e quando
  PutSecretValue: quem atualizou um secret
  RotateSecret: quando rotação ocorreu

Query útil (CloudWatch Logs Insights):
  -- Quem acessou o secret de produção nas últimas 24h?
  fields userIdentity.arn, eventName, @timestamp
  | filter eventSource = "secretsmanager.amazonaws.com"
    AND requestParameters.secretId = "prod/checkout/database"
  | sort @timestamp desc

CloudWatch Alarms importantes:
  1. Secret acessado fora do horário normal:
     Metric: CloudTrail → GetSecretValue fora das 6h-22h
     Alarm: > 0 acessos → SNS → security team

  2. Rotação falhou:
     Metric: RotationFailed event
     Alarm: EventBridge rule → SNS → alerta imediato

  3. Secret acessado por role inesperada:
     CloudTrail Insights + EventBridge
     → Detectar padrão anômalo de acesso
```

## Custo e considerações

```
Custo:
  $0.40/secret/mês (base)
  $0.05 por 10.000 API calls

  10 secrets, 100.000 calls/mês:
  → 10 × $0.40 = $4.00 (secrets)
  → 100.000 / 10.000 × $0.05 = $0.50 (API calls)
  → Total: $4.50/mês

Cache para reduzir custo e latência:
  → Não chamar GetSecretValue a cada request HTTP
  → Cachear por 5-15 minutos na memória da aplicação
  → AWS SDK para Python/Java tem SecretsManagerCache integrado:
  
  from aws_secretsmanager_caching import SecretCache
  cache = SecretCache()  # TTL padrão: 1 hora
  secret = cache.get_secret_string('prod/checkout/database')
  
  → Cache + TTL de 1h = ~720 chamadas/mês por instância (mínimo)
  → vs. 1 chamada por request = potencialmente milhões

Checklist de implementação:
  ✓ Nenhuma senha em código ou variáveis de ambiente em texto claro
  ✓ Secrets Manager para todas as credenciais de banco de produção
  ✓ Rotação automática habilitada (30-90 dias)
  ✓ Cache na aplicação (5-15 min)
  ✓ Resource Policy: apenas roles necessárias podem acessar
  ✓ KMS CMK customizada para criptografar os secrets
  ✓ CloudTrail habilitado (automático)
  ✓ Alarm para rotação falha
```

## 🧩 Quiz de Fixação

1. A rotação automática do Secrets Manager tem 4 etapas (createSecret, setSecret, testSecret, finishSecret). Por que a etapa `testSecret` existe separada da `setSecret`, e o que acontece se a testSecret falhar?
2. Uma aplicação Node.js chama `GetSecretValue` a cada requisição HTTP que recebe (1.000 req/s). Quais são os dois problemas dessa abordagem e como resolver com cache?
3. Um desenvolvedor propõe usar Parameter Store (SecureString) em vez de Secrets Manager para armazenar senhas de banco de dados de produção, argumentando que é mais barato. Qual é o argumento técnico mais importante contra essa escolha?

**Respostas:**
1) A `setSecret` aplica a nova credencial no sistema de destino (ex: cria a nova senha no banco de dados) e a `testSecret` verifica que a credencial realmente funciona após ser aplicada — são verificações distintas e necessárias. Separá-las permite que: (1) a aplicação das credenciais e a verificação de funcionamento tenham tratamentos de erro independentes; (2) a rotação possa ser interrompida após `setSecret` mas antes de promover para AWSCURRENT se o teste falhar. Se `testSecret` falhar: o Secrets Manager NÃO promove a credencial para AWSCURRENT — a versão AWSPENDING é mantida como pendente, AWSCURRENT permanece ativo e funcionando, e o Secrets Manager gera um evento de falha que pode disparar um alarme. A aplicação continua funcionando com as credenciais antigas. O time de segurança recebe o alerta, investiga a falha (banco fora do ar? Lambda com bug?), corrige e re-dispara a rotação manualmente.
2) Dois problemas: (1) Latência — cada chamada ao Secrets Manager via HTTPS tem latência de 20-100ms; com 1.000 req/s, cada requisição HTTP adicionaria essa latência, tornando a aplicação muito mais lenta; (2) Custo — 1.000 req/s × 60s × 60min × 24h × 30 dias = 2,6 bilhões de chamadas/mês × $0.05/10.000 = $13.000/mês apenas em Secrets Manager, vs. poucos dólares com cache. Solução: implementar cache local com TTL de 5-15 minutos. Com o AWS SDK Secrets Manager Caching (disponível para Python, Java, Go, .NET, JavaScript): `const cache = new SecretsManagerCaching()` — o cache retorna o valor em memória e faz refresh em background quando o TTL expira. 1.000 req/s com cache de 10 minutos = 6 chamadas/hora ao SM em vez de 3,6 milhões, com latência adicional < 1ms para cache hits.
3) O argumento técnico mais importante: o Parameter Store não tem rotação automática de credenciais. Senhas de banco de produção que nunca são rotacionadas são um risco de segurança significativo e frequentemente um requisito de compliance (PCI DSS Requirement 8.6 exige rotação periódica de credenciais de contas não-humanas). Com Secrets Manager, a rotação acontece automaticamente a cada 30-90 dias sem intervenção humana — a aplicação nem percebe. Com Parameter Store, rotacionar a senha do banco exigiria: (1) criar nova senha manualmente no banco; (2) atualizar o Parameter Store; (3) reiniciar as aplicações para pegar a nova senha (ou implementar lógica customizada de refresh). O custo adicional do Secrets Manager ($0.40/secret/mês) é insignificante comparado ao risco de credenciais não-rotacionadas em produção — uma única credencial comprometida pode custar dezenas ou centenas de milhares de reais em danos.
