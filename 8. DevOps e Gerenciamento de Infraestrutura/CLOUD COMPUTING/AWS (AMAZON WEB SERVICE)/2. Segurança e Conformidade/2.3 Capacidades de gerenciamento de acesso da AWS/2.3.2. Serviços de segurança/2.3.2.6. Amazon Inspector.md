### Amazon Inspector — detecção contínua de vulnerabilidades em workloads AWS

Amazon Inspector é o serviço de vulnerability management da AWS que detecta automaticamente vulnerabilidades de software (CVEs) e desvios de configuração de segurança em instâncias EC2, funções Lambda e imagens de containers no ECR. Na versão atual (Inspector v2), a varredura é contínua — não pontual — e os resultados são enriquecidos com contexto de exploitability real para ajudar a priorizar o que realmente importa. É a peça central de um programa de gestão de vulnerabilidades na AWS.

---

## Inspector v1 vs Inspector v2 — a mudança fundamental

```
Inspector v1 (descontinuado em 2023):
  → Varredura manual/agendada (você dispara quando quiser)
  → Requer agente instalado em cada EC2
  → Apenas EC2 (sem Lambda, sem containers)
  → Relatório pontual (snapshot do momento da varredura)
  → Integração manual com Security Hub

Inspector v2 (atual):
  → Varredura CONTÍNUA e automática
  → Agente integrado ao SSM Agent (sem instalação separada)
  → EC2 + Lambda functions + container images (ECR + ECS/EKS)
  → Findings atualizados em tempo real quando nova CVE é publicada
  → Integração nativa com Security Hub e ECR
  → Habilitado em segundos, sem configuração de target

Impacto da mudança:
  Inspector v1: nova CVE publicada hoje
    → Você descobre apenas na próxima varredura manual
    → Pode levar semanas ou meses se não houver cadência definida
  
  Inspector v2: nova CVE publicada hoje
    → Inspector v2 reavalia TODOS os recursos automaticamente
    → Finding aparece em minutos para instâncias afetadas
    → Sem depender de ação humana para disparar nova varredura
```

## O que o Inspector v2 detecta

### Vulnerability scanning (CVEs)

```
Common Vulnerabilities and Exposures (CVE):
  → Banco de dados global de vulnerabilidades conhecidas
  → Gerenciado pelo NIST (National Vulnerability Database — NVD)
  → Cada CVE tem: ID único, descrição, CVSS score, affected packages

Inspector consulta:
  ├── NVD (National Vulnerability Database)
  ├── Amazon VulnDB (intelligence proprietária da AWS)
  ├── Red Hat Security Advisories
  ├── Ubuntu Security Notices
  ├── Debian Security Advisory
  └── Alpine Linux Security Database

O que é detectado em EC2:
  → Packages instalados no SO (apt, yum, rpm)
  → Linguagens de programação instaladas (Python, Node.js, Java)
  → Dependências de runtime detectadas nos processos em execução

O que é detectado em Lambda:
  → Layers e deployment packages
  → Dependências em requirements.txt, package.json, pom.xml
  → Arquivos no ZIP do deployment package

O que é detectado em containers (ECR):
  → Imagem base (ubuntu:22.04, debian:bullseye, alpine:3.18)
  → Packages instalados via apt/apk/yum no Dockerfile
  → Dependências de aplicação (npm, pip, maven, gradle)
```

### Network reachability assessment

```
Inspector avalia também se vulnerabilidades são alcançáveis:

Contexto de rede:
  EC2 com CVE crítica + Security Group fechado:
  → Vulnerabilidade existe mas porta afetada não é acessível
  → Finding: "package vulnerability, network path closed"
  → Prioridade menor (não é exploitável remotamente no momento)
  
  EC2 com CVE crítica + Security Group 0.0.0.0/0 na porta afetada:
  → Vulnerabilidade existe E porta está exposta para internet
  → Finding: "package vulnerability, network path open"
  → Prioridade MÁXIMA (exploitável remotamente!)

Inspector Score:
  Score próprio do Inspector (0-10) que combina:
  ├── CVSS Base Score (severidade intrínseca da CVE)
  ├── Network reachability (porta exposta ou não)
  ├── Exploitability (existe exploit público?)
  └── Amazon threat intelligence (está sendo explorado ativamente?)
  
  CVE crítica (CVSS 9.8) em porta fechada:
  → Inspector Score: 5.5 (grave mas não urgente)
  
  CVE moderada (CVSS 6.2) em porta aberta com exploit público:
  → Inspector Score: 9.1 (urgente!)
  
  A combinação de contexto > o CVSS isolado para priorização
```

## Como o Inspector funciona por tipo de recurso

### EC2 — varredura contínua via SSM

```
Pré-requisito: SSM Agent instalado e rodando na instância
  → AMIs Amazon Linux, Amazon Linux 2, Ubuntu: SSM Agent pré-instalado
  → Windows Server: SSM Agent pré-instalado nas AMIs da AWS
  → Outras distros: instalar SSM Agent manualmente

Como funciona:
  1. Inspector detecta instância EC2 via tags e SSM inventory
  2. SSM Agent coleta inventário de software (packages instalados)
  3. Inspector compara com banco de CVEs
  4. Finding gerado para cada package vulnerável
  5. Quando nova CVE é publicada: Inspector reavalia automaticamente
  6. Quando instância é atualizada (package upgrade): Inspector reavalia

Sem agente adicional:
  → SSM Agent já está presente na maioria das AMIs
  → Inspector usa comunicação existente do SSM
  → Sem abertura de portas adicionais

Verificar se instância está sendo varrida:
  Console Inspector → EC2 instances → filtrar por status
  
  Status possíveis:
  ACTIVE:     sendo varrida ativamente
  INACTIVE:   SSM Agent não responde (verificar agente)
  UNMANAGED:  sem SSM Agent (instalar agente)
```

### Lambda — varredura de deployment packages

```
Como funciona:
  1. Lambda function ativa é inventariada automaticamente
  2. Inspector extrai o deployment package (ZIP)
  3. Analisa: requirements.txt, package.json, pom.xml, etc.
  4. Detecta dependências com CVEs conhecidas
  5. Finding: "lambda function dependency X has CVE-2024-XXXX"

Layers também são varridos:
  → Lambda Layer com numpy vulnerável → finding
  → Layers compartilhados entre funções: cada função tem finding próprio

Cobertura de linguagens:
  ├── Python (requirements.txt, Pipfile)
  ├── Node.js (package.json)
  ├── Java (pom.xml, build.gradle)
  ├── .NET (packages.config, .csproj)
  └── Ruby (Gemfile)

Limitação:
  → Lambda executa código no runtime gerenciado AWS (Python 3.11, Node 20...)
  → O runtime em si é atualizado pela AWS (não há CVEs de runtime gerenciado)
  → Inspector varre apenas as DEPENDÊNCIAS que você adiciona
```

### Container Images (ECR) — scanning no push

```
Integração com ECR:

Sem Inspector: ECR Basic Scanning
  → Varredura manual após push
  → Apenas pacotes do SO (não dependências de app)
  → Banco de CVEs básico
  
Com Inspector: ECR Enhanced Scanning
  → Varredura automática no push E contínua
  → Pacotes do SO + dependências de aplicação
  → Banco de CVEs do Inspector (mais abrangente)
  → Finding aparece no Security Hub automaticamente

Fluxo no pipeline de CI/CD:
  1. docker build → imagem construída
  2. docker push para ECR
  3. ECR Enhanced Scanning (Inspector) varre automaticamente
  4. Finding gerado por CVE detectada
  5. EventBridge → Lambda → pode bloquear deploy se CRITICAL
  
  Gate de segurança no pipeline:
  aws ecr describe-image-scan-findings \
    --repository-name minha-api \
    --image-id imageTag=latest \
    --query 'imageScanFindings.findingSeverityCounts'
  
  Se CRITICAL > 0: falhar o pipeline (não permite deploy)
  Se HIGH > 5: notificar e decidir se bloqueia

Scanning de imagens em runtime (ECS/EKS):
  → Inspector também varre imagens que estão rodando em containers
  → Mesmo que não tenham sido pushed recentemente
  → Se nova CVE afeta imagem rodando em produção: finding gerado
```

### Como priorizar findings

```
Framework de priorização (do mais urgente ao menos):

PRIORIDADE 1 — Remediar esta semana:
  Inspector Score >= 9.0
  E (network reachable = true OU exploit público disponível)
  E recurso em produção
  
  Exemplo: Log4Shell (CVE-2021-44228) em EC2 pública
  → Score: 10.0, porta aberta, exploit trivial
  → Prioridade máxima, remediar hoje

PRIORIDADE 2 — Remediar neste sprint:
  Inspector Score 7.0-8.9
  E recurso em produção
  
  Exemplo: OpenSSL heartbleed em EC2 de produção com porta fechada
  → Score: 7.5, porta fechada (menos urgente mas grave)

PRIORIDADE 3 — Incluir no próximo ciclo:
  Inspector Score 4.0-6.9
  Ou qualquer score em ambiente não-produção

PRIORIDADE 4 — Backlog / aceitar risco:
  Inspector Score 0.1-3.9
  Sem exploit público
  Sem network reachability

Filtros no console Inspector:
  Severity=CRITICAL AND NetworkReachability=OPEN
  → Apenas os mais urgentes
  
  ResourceType=AWS_ECR_CONTAINER_IMAGE AND Severity=HIGH
  → Vulnerabilidades em imagens de container para remediar nas imagens
```

## Remediação — como resolver os findings

```
Estratégia por tipo de vulnerabilidade:

PACKAGE SYSTEM (SO):
  # Identificar o package e versão com fix
  aws inspector2 list-findings \
    --filter-criteria '{"findingStatus": [{"comparison":"EQUALS","value":"ACTIVE"}]}'
  
  Finding diz: "openssl 1.1.1k → fixedInVersion: 1.1.1n"
  
  Remediação no servidor:
  ubuntu: sudo apt-get update && sudo apt-get install openssl
  amazon linux: sudo yum update openssl
  
  Remediação via imagem (preferível para containers/EC2 imutável):
  → Atualizar imagem base no Dockerfile: FROM ubuntu:22.04 (mais recente)
  → Rebuild e redeploy

LAMBDA DEPENDENCY:
  Finding: "requests 2.27.0 → fixedInVersion: 2.28.0"
  
  Atualizar requirements.txt:
  requests>=2.28.0
  
  Rebuild deployment package → redeploy Lambda

CONTAINER IMAGE:
  Finding: "curl 7.68.0 em imagem myapp:1.0.0"
  
  Dockerfile:
  FROM ubuntu:22.04  ← versão mais recente da imagem base
  RUN apt-get update && apt-get upgrade -y  ← atualiza todos os packages
  
  Reconstruir e republicar no ECR → redeploy containers

Automação de remediação:
  Para Lambda e containers: CI/CD pipeline
  → Dependabot/Renovate: PRs automáticos para atualizar deps
  → CI/CD: rebuild e redeploy automático após merge
  
  Para EC2: SSM Patch Manager
  → Define baseline de patches
  → Aplica patches automaticamente na janela de manutenção
  → Inspector detecta conformidade pós-patch
```

## Inspector em múltiplas contas

```
Via Organizations (recomendado):

Security Account = Inspector Delegated Administrator
  → Configura Inspector em todas as contas
  → Vê findings de todas as contas centralmente

Configuração:
  aws inspector2 enable-delegated-admin-account \
    --delegated-admin-account-id [security-account-id]
  
  # Auto-enable para todas as contas member
  aws inspector2 update-organization-configuration \
    --auto-enable ec2=true,lambda=true,lambdaCode=true,ecr=true

Vantagem:
  → Nova conta criada na organização: Inspector habilitado automaticamente
  → Findings de produção, dev, staging: todos visíveis centralmente
  → Uma conta sem SSM Agent: aparece como "UNMANAGED" no console central
```

## 🧩 Quiz de Fixação

1. Uma instância EC2 tem uma CVE com CVSS score 9.8 (crítico), mas o Inspector Score é 5.2. Como isso é possível e o que esse score mais baixo significa em termos de priorização?
2. Um time de DevOps quer bloquear o deploy de uma imagem Docker para produção se ela tiver vulnerabilidades CRITICAL detectadas pelo Inspector/ECR. Descreva a arquitetura do gate de segurança no pipeline de CI/CD.
3. Por que o Inspector v2 detecta novas vulnerabilidades em recursos existentes sem precisar de nova varredura manual, e qual é a implicação prática disso para um time de segurança que usa Inspector v1?

**Respostas:**
1) O CVSS score mede a severidade intrínseca da vulnerabilidade em condições ideais de exploração. O Inspector Score adiciona contexto real: se a instância EC2 tem a porta afetada pela CVE fechada no Security Group (não acessível externamente) e não existe exploit público funcional para essa CVE específica, o Inspector ajusta o score para baixo — a vulnerabilidade existe mas é muito menos explorável na prática. Isso significa que, em termos de priorização, essa instância não precisa de atenção imediata: a vulnerabilidade deve ser remediada (como todo software desatualizado), mas pode aguardar o próximo ciclo regular de patches em vez de demandar resposta de emergência. Contrariamente, uma CVE com CVSS 6.2 em porta aberta com exploit público funcional pode ter Inspector Score 9+ e exigir ação urgente — a exploitability real supera a severidade teórica.
2) Arquitetura do gate de segurança: (1) Build stage: `docker build -t myapp:$COMMIT_SHA .`; (2) Push stage: `docker push $ECR_REPO:$COMMIT_SHA` — o push dispara automaticamente o ECR Enhanced Scanning (Inspector); (3) Gate stage: Lambda ou script no pipeline aguarda conclusão do scan (`aws ecr wait image-scan-complete`) e chama `aws ecr describe-image-scan-findings`; (4) Parsing dos resultados: se `findingSeverityCounts.CRITICAL > 0` → falhar o build com exit code 1 (pipeline para, deploy não acontece); se `findingSeverityCounts.HIGH > threshold` configurável → dependendo da política, pode bloquear ou apenas alertar; (5) Notificação: independente de bloquear ou não, publicar os findings para o canal de segurança via SNS/Slack com lista de CVEs encontradas; (6) Exception path: se há CVE conhecida e aceita como risco (com prazo de remediação documentado), manter lista de supressão no pipeline que permite bypass com registro de auditoria.
3) O Inspector v2 mantém um banco de dados interno mapeando quais packages estão instalados em quais recursos (inventário coletado continuamente via SSM Agent). Quando o NVD ou a Amazon VulnDB publica uma nova CVE, o Inspector v2 imediatamente cruza a nova CVE com seu inventário de packages — sem precisar que os recursos sejam varridos novamente. Se `openssl 1.1.1k` está instalado em 30 instâncias e uma nova CVE afetando essa versão é publicada hoje, todos os 30 findings aparecem em minutos. A implicação prática para quem usa Inspector v1 é crítica: o v1 apenas descobre vulnerabilidades existentes no momento da varredura programada — se a varredura é semanal ou mensal, a janela de exposição pode ser de semanas. Com v2, a janela de exposição é de minutos (do momento da publicação da CVE até o finding aparecer). Para compliance, isso também significa que a "data de descoberta" da vulnerabilidade é muito mais precisa — relevante para SLAs de remediação.
