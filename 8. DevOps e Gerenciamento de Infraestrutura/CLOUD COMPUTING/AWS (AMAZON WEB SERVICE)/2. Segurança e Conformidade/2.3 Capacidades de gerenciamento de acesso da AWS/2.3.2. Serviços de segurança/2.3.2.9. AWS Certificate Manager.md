### AWS Certificate Manager (ACM) — certificados TLS gratuitos com renovação automática

AWS Certificate Manager é o serviço que provisiona, gerencia e renova automaticamente certificados TLS/SSL para uso com serviços AWS. Ele elimina completamente o ciclo manual de comprar certificados de CAs comerciais, instalá-los, monitorar a expiração e renovar antes do vencimento — tarefas que, quando esquecidas, causam incidentes de segurança e disponibilidade de alto impacto. Na AWS, HTTPS deveria ser o padrão em todos os endpoints públicos, e o ACM torna isso trivial e gratuito.

---

## O problema do gerenciamento manual de certificados

```
Fluxo tradicional (sem ACM):

1. Gerar CSR (Certificate Signing Request) no servidor
2. Enviar CSR para CA comercial (Digicert, Sectigo, GoDaddy)
3. Pagar: $70-$300/ano por certificado
4. Aguardar validação (horas a dias)
5. Receber certificado (.crt, .key, .chain)
6. Instalar no servidor/load balancer
7. Configurar renovação manual no calendário (11 meses depois)
8. Repetir para cada domínio/subdomínio
9. Se alguém esquecer a renovação: certificado expira → downtime

Consequências de certificado expirado:
  → Navegadores mostram "Sua conexão não é privada"
  → Usuários abandonam o site (86% não continuam)
  → APIs param de funcionar (clientes recusam conexão SSL)
  → SEO penalizado pelo Google
  → Incidente de segurança formalmente registrado
  → Vergonha operacional e reuniões de post-mortem

Com ACM:
  → Certificado gratuito (para uso com serviços AWS)
  → Provisionado em minutos
  → Renovação automática (sem intervenção humana)
  → Sem expiração acidental
  → Integração nativa com ALB, CloudFront, API Gateway
  → Zero gerenciamento de chaves privadas
```

## Tipos de certificados ACM

### Certificados Públicos (gratuitos)

```
Emitidos por Amazon Trust Services — CA pública confiada por todos
os principais browsers e SOs (Chrome, Firefox, Safari, iOS, Android)

Características:
  ├── Gratuitos (sem custo de certificado)
  ├── Válidos por 13 meses (renovação automática antes de expirar)
  ├── Apenas para uso com serviços AWS integrados (não baixa a chave privada)
  ├── Domain Validation (DV) — não Organization Validation (OV) ou Extended (EV)
  └── Suporte a wildcards: *.empresa.com

Serviços que aceitam certificados ACM públicos:
  ├── Application Load Balancer (ALB)
  ├── Network Load Balancer (NLB) com TLS listener
  ├── Amazon CloudFront
  ├── API Gateway (REST, HTTP, WebSocket)
  ├── AWS Elastic Beanstalk
  ├── AWS AppSync
  └── Amazon CloudFront Functions

NÃO pode usar diretamente em:
  ├── EC2 (não exporta a chave privada)
  ├── Servidores on-premises
  └── Software que você instala fora dos serviços AWS integrados
  (Para esses casos: use Let's Encrypt ou CA comercial)
```

### Certificados Privados (ACM Private CA)

```
Para infraestrutura interna que precisa de certificados privados:

Casos de uso:
  ├── mTLS entre microserviços internos
  ├── VPN clients com autenticação por certificado
  ├── Dispositivos IoT
  ├── Ambientes on-premises integrados com AWS
  └── Certificados de código (code signing)

Custo:
  → $400/mês por CA privada (independente de certificados emitidos)
  → $0.75 por certificado emitido (primeiros 1.000/mês gratuitos)

Hierarquia de CA privada:
  Root CA (offline, alta segurança)
  └── Subordinate CA (operacional)
        └── Certificados de entidade final (servidores, clientes)
  
  ACM Private CA suporta essa hierarquia
  Root CA pode ser mantida offline (mais seguro)
```

## Criando e validando certificados públicos

### Método 1: Validação por DNS (recomendado)

```
Como funciona:
  1. Solicitar certificado para domínio.com
  2. ACM gera um registro CNAME específico para validação
  3. Você adiciona esse CNAME no seu DNS
  4. ACM verifica que o CNAME existe → valida propriedade do domínio
  5. Certificado emitido em minutos após validação

Console:
  ACM → Request certificate → Request a public certificate
  → Domain names: empresa.com (adicionar *.empresa.com para wildcard)
  → Validation method: DNS validation
  → Create records in Route 53 (se usar Route 53: 1 clique)

Via CLI:
  # 1. Solicitar certificado
  aws acm request-certificate \
    --domain-name empresa.com \
    --subject-alternative-names "*.empresa.com" "api.empresa.com" \
    --validation-method DNS

  # 2. Obter os registros de validação
  aws acm describe-certificate \
    --certificate-arn arn:aws:acm:us-east-1:123:certificate/xxx \
    --query 'Certificate.DomainValidationOptions'
  
  # Retorna o CNAME a adicionar no DNS:
  {
    "ResourceRecord": {
      "Name": "_abc123.empresa.com.",
      "Type": "CNAME",
      "Value": "_def456.acm-validations.aws."
    }
  }

Com Route 53 (automático via console ou CLI):
  aws acm describe-certificate --certificate-arn xxx | \
    jq '.Certificate.DomainValidationOptions[0].ResourceRecord'
  
  → Criar o registro no Route 53:
  aws route53 change-resource-record-sets \
    --hosted-zone-id Z123 \
    --change-batch '{"Changes":[{"Action":"CREATE","ResourceRecordSet":{
      "Name":"_abc123.empresa.com.",
      "Type":"CNAME",
      "TTL":300,
      "ResourceRecords":[{"Value":"_def456.acm-validations.aws."}]
    }}]}'

Validação concluída:
  → Status: ISSUED
  → Certificado disponível para uso
  → O registro CNAME permanece no DNS para permitir renovação automática
     (NÃO remover após validação!)
```

### Método 2: Validação por Email (alternativo)

```
Quando usar: você não controla o DNS diretamente

Como funciona:
  1. ACM envia email para endereços administrativos do domínio:
     admin@empresa.com, administrator@empresa.com,
     hostmaster@empresa.com, postmaster@empresa.com, webmaster@empresa.com
  2. Alguém clica no link do email para validar
  3. Certificado emitido

Desvantagem:
  → Validação manual (não automática)
  → Renovação também requer clique manual no email
  → Perder o email de renovação → certificado expira sem renovação
  
Prefira sempre DNS validation para renovação automática completa.
```

## Renovação automática — como funciona

```
ACM gerencia o ciclo de vida do certificado:

Timeline de renovação:
  Certificado emitido (válido por 13 meses)
  
  60 dias antes da expiração:
  → ACM tenta renovar automaticamente
  
  Se DNS validation ainda configurado (CNAME no DNS):
  → ACM re-valida via DNS (automático, sem intervenção)
  → Novo certificado emitido com nova data de expiração
  → ALB/CloudFront automaticamente usam o novo certificado
  → Usuário final: zero percepção de mudança
  
  Se DNS validation não configurado (CNAME removido):
  → ACM envia email de aviso 45 dias antes
  → 30 dias antes: novo aviso
  → 7 dias antes: aviso crítico
  → Se não renovado: certificado expira → site mostra erro SSL

CloudWatch Event para monitoramento:
  ACM publica evento quando certificado está próximo de expirar:
  EventBridge rule → SNS → alerta ao time de operações
  
  Melhor prática: mesmo com renovação automática,
  criar alarme para certificados expirando em < 30 dias
  (pode haver falha de renovação por problema de DNS)
```

## Integração com serviços AWS

### ALB — terminação TLS

```
Application Load Balancer com HTTPS:

1. Criar HTTPS Listener (porta 443):
   ALB → Listeners → Add listener
   Protocol: HTTPS
   Port: 443
   SSL certificate: [selecionar certificado ACM]
   SSL Policy: ELBSecurityPolicy-TLS13-1-2-2021-06 (recomendada)
   
   → Certificado selecionado é servido ao cliente
   → ALB descriptografa → encaminha HTTP para o backend
   → Backend não precisa gerenciar TLS

2. Redirecionar HTTP → HTTPS:
   Listener HTTP (80):
   Action: Redirect → HTTPS (443) [301 Permanent]
   
   Todo tráfego HTTP automaticamente promovido para HTTPS

3. SNI (Server Name Indication) — múltiplos certificados:
   Um ALB pode servir múltiplos domínios com certificados diferentes:
   listener 443:
   ├── Default: certificado empresa.com
   ├── SNI rule: api.empresa.com → certificado api.empresa.com
   └── SNI rule: parceiro.empresa.com → certificado parceiro.empresa.com
   
   Browser envia SNI no handshake TLS → ALB serve o cert correto

Via Terraform:
resource "aws_alb_listener" "https" {
  load_balancer_arn = aws_alb.main.arn
  port              = 443
  protocol          = "HTTPS"
  ssl_policy        = "ELBSecurityPolicy-TLS13-1-2-2021-06"
  certificate_arn   = aws_acm_certificate.main.arn

  default_action {
    type             = "forward"
    target_group_arn = aws_alb_target_group.app.arn
  }
}

resource "aws_alb_listener" "http_redirect" {
  load_balancer_arn = aws_alb.main.arn
  port              = 80
  protocol          = "HTTP"

  default_action {
    type = "redirect"
    redirect {
      port        = "443"
      protocol    = "HTTPS"
      status_code = "HTTP_301"
    }
  }
}
```

### CloudFront — TLS na edge global

```
CloudFront com certificado ACM:

Requisito importante:
  → Certificados para CloudFront DEVEM estar em us-east-1 (N. Virginia)
  → Mesmo que sua origem seja em sa-east-1 (São Paulo)
  → Motivo: CloudFront é um serviço global gerenciado de us-east-1

Configuração:
  CloudFront Distribution → Edit
  SSL Certificate: Custom SSL Certificate (ACM)
  Certificate: [selecionar cert de us-east-1]
  Minimum Protocol Version: TLSv1.2_2021 (recomendado)
  
  Resultado:
  → Usuário conecta via HTTPS ao edge do CloudFront
  → CloudFront termina TLS na edge (< 10ms de latência para certificado)
  → CloudFront comunica com origin via HTTPS ou HTTP (configurável)

Custom domain em CloudFront:
  Distribution domain: d123abc.cloudfront.net
  Alternate domain: www.empresa.com
  
  Route 53: A record empresa.com → alias para d123abc.cloudfront.net
  → Usuário acessa empresa.com → Route 53 → CloudFront → sua origin
  → TLS com certificado da empresa.com servido pelo CloudFront
```

### API Gateway — HTTPS por padrão

```
API Gateway tem HTTPS por padrão em todos os endpoints:
  https://abc123.execute-api.us-east-1.amazonaws.com/prod

Custom domain com certificado ACM:
  1. Solicitar certificado para api.empresa.com
  2. API Gateway → Custom domain names → Create
     Domain name: api.empresa.com
     Certificate: [cert ACM]
  3. Route 53: CNAME api.empresa.com → [API Gateway domain]
  
  → API acessível via https://api.empresa.com
  → Certificado gerenciado pelo ACM
```

## Políticas TLS — segurança do cipher suite

```
Ao configurar HTTPS no ALB, escolher a política de segurança correta:

Políticas disponíveis (do mais ao menos seguro):

ELBSecurityPolicy-TLS13-1-2-2021-06 (RECOMENDADA):
  → TLS 1.3 + TLS 1.2 (sem TLS 1.0/1.1)
  → Cipher suites modernos (ECDHE, AES-GCM)
  → Suporte: browsers modernos (95%+ dos usuários)
  → Use para: novas aplicações, APIs

ELBSecurityPolicy-TLS13-1-1-2021-06:
  → TLS 1.3 + TLS 1.2 + TLS 1.1
  → Maior compatibilidade
  → Use para: se ainda suporta usuários com browsers antigos

ELBSecurityPolicy-2016-08 (EVITAR):
  → Inclui TLS 1.0 (vulnerável a POODLE, BEAST)
  → Apenas para sistemas legados muito antigos

Verificar a política configurada:
  Qualys SSL Labs: ssllabs.com/ssltest
  → Analisa TLS, cipher suites, certificado, headers
  → Score A/A+/B/C/F
  → Meta: Score A+ (TLS 1.3 + HSTS + HPKP)

HSTS (HTTP Strict Transport Security):
  Header adicionado pelo ALB ou aplicação:
  Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
  
  → Browser memoriza: este domínio SEMPRE usa HTTPS
  → Próximas visitas: browser recusa conexão HTTP mesmo antes de receber redirect
  → Proteção contra SSL stripping attacks
```

## Checklist de certificados na AWS

```
✓ Todos os endpoints públicos usam HTTPS?
✓ Certificados em ALB, CloudFront, API Gateway via ACM?
✓ DNS validation configurado (CNAME no DNS permanente)?
✓ Renovação automática testada (verificar status no console ACM)?
✓ HTTP → HTTPS redirect configurado em todos os listeners?
✓ Política TLS 1.2+ mínima (sem TLS 1.0/1.1)?
✓ CloudWatch alarm para certificados expirando < 30 dias?
✓ Certificados CloudFront em us-east-1?
✓ HSTS configurado para domínios principais?
✓ Score A no SSL Labs para domínios críticos?
```

## 🧩 Quiz de Fixação

1. Uma empresa usa validação por DNS para seus certificados ACM. O time de infraestrutura removeu o registro CNAME de validação do Route 53 após o certificado ser emitido, achando que "já não era mais necessário". O que vai acontecer em 11 meses e como prevenir?
2. Um time quer adicionar HTTPS ao ALB de produção. O certificado ACM foi solicitado para `api.empresa.com` e está com status `ISSUED`. Ao tentar associar ao ALB, recebe erro. O ALB está em `sa-east-1` e o certificado foi solicitado em `us-east-1`. O que está errado e qual é a solução?
3. Por que certificados ACM públicos não podem ser exportados (a chave privada não fica disponível para download) e qual é a implicação prática dessa limitação para quem precisa de TLS em servidores EC2?

**Respostas:**
1) Quando o ACM tentar renovar automaticamente o certificado (60 dias antes da expiração), ele fará a validação DNS buscando o registro CNAME que foi removido. Sem o CNAME, a validação falhará, e o ACM enviará emails de aviso (45, 30, 7 dias antes da expiração). Se ninguém perceber ou agir, o certificado expirará — o ALB/CloudFront continuará servindo o certificado expirado, e browsers mostrarão o erro "NET::ERR_CERT_DATE_INVALID" para todos os usuários, causando um incidente de disponibilidade. Para prevenir: (1) nunca remover o CNAME de validação após emissão — ele é necessário para renovações futuras; (2) criar um CloudWatch Alarm monitorando o evento `ACM Certificate Approaching Expiration` via EventBridge, que notifica o time com 45+ dias de antecedência; (3) documentar no runbook de DNS que registros prefixados com `_` em domínios são de validação ACM e não devem ser removidos.
2) O problema é de região: certificados ACM são regionais para a maioria dos serviços (EC2, ALB, NLB, API Gateway). Um certificado solicitado em `us-east-1` só pode ser usado por recursos em `us-east-1`. O ALB em `sa-east-1` só enxerga certificados criados em `sa-east-1`. Exceção: CloudFront requer certificados em `us-east-1` (serviço global). Solução: solicitar um novo certificado ACM diretamente em `sa-east-1` para `api.empresa.com`, completar a validação DNS (adicionar o novo CNAME no Route 53), aguardar o status `ISSUED` e então associar ao ALB em `sa-east-1`. O certificado em `us-east-1` pode ser mantido se houver recursos lá (ou CloudFront), ou pode ser deletado se não for usado.
3) A chave privada de certificados ACM públicos nunca é disponibilizada para download por design de segurança — ela é gerada e armazenada em HSMs dentro do KMS da AWS e nunca sai em texto claro. Isso é uma feature de segurança, não uma limitação: garante que a chave privada não pode ser roubada mesmo que alguém obtenha acesso à conta AWS. A implicação prática para EC2: não é possível instalar um certificado ACM diretamente no Apache, Nginx ou qualquer software que rode na instância EC2 — você precisaria da chave privada para isso. Para TLS em EC2, as alternativas são: (1) posicionar um ALB ou NLB (com certificado ACM) na frente da EC2 e fazer terminação TLS no load balancer — a EC2 recebe tráfego HTTP não criptografado internamente (mais comum e recomendado); (2) usar Let's Encrypt (Certbot) para obter um certificado cujas chaves você controla e pode instalar diretamente no EC2; (3) usar ACM Private CA que permite exportar certificados.
