### AWS Organizations — governança centralizada de múltiplas contas AWS

AWS Organizations é o serviço que permite criar e gerenciar centralmente múltiplas contas AWS como uma única entidade. Ele é o fundamento da arquitetura de contas recomendada pela AWS — em vez de colocar tudo em uma conta, criar contas separadas por ambiente, time ou produto, governadas centralmente por políticas organizacionais. Organizations transforma o caos de contas isoladas em uma estrutura hierárquica controlada, com billing centralizado, políticas aplicadas em cascata e isolamento real entre ambientes.

---

## Por que múltiplas contas é o padrão correto

```
O anti-padrão: tudo em uma conta
  ├── Dev, staging, produção: na mesma conta
  ├── Todos os times: compartilhando os mesmos recursos
  └── Erro humano em dev pode destruir recursos de prod
  
  Blast radius de um erro: TOTAL (toda a empresa)
  Blast radius de uma credencial comprometida: TOTAL
  Separação entre ambientes: apenas lógica (convencão de tags)

O padrão correto: conta por ambiente/produto
  ├── Dev: conta isolada (erros ficam no dev)
  ├── Staging: conta isolada (igual à prod mas separada)
  ├── Produção: conta isolada (proteção máxima)
  ├── Segurança: conta isolada (logs centralizados, imutáveis)
  └── Billing: conta isolada (apenas para governança financeira)
  
  Blast radius de um erro no dev: zero impacto na prod
  Blast radius de credencial comprometida: limitado à conta
  Separação entre ambientes: REAL (diferente conta AWS)

Por que conta separada é melhor que VPC separada:
  VPC separada (mesma conta):
  → IAM policies afetam ambas as VPCs
  → CloudTrail logs compartilhados
  → Billing misturado
  → Acidente com "aws ec2 terminate-instances" pode atingir prod
  
  Conta separada:
  → IAM completamente isolado
  → CloudTrail independente
  → Billing separado por produto
  → Impossível acidentalmente afetar prod com credenciais de dev
```

## Estrutura do AWS Organizations

### Hierarquia de componentes

```
MANAGEMENT ACCOUNT (raiz)
  └── ROOT (raiz da organização)
        ├── OU: Infraestrutura
        │     ├── Conta: Network (Transit Gateway, Direct Connect)
        │     └── Conta: Shared Services (AD, DNS, ferramentas)
        │
        ├── OU: Segurança
        │     ├── Conta: Security (GuardDuty master, SIEM)
        │     ├── Conta: Audit (CloudTrail central, logs imutáveis)
        │     └── Conta: Billing (apenas acesso financeiro)
        │
        ├── OU: Workloads
        │     ├── OU: Produção
        │     │     ├── Conta: App A - Produção
        │     │     └── Conta: App B - Produção
        │     │
        │     ├── OU: Staging
        │     │     ├── Conta: App A - Staging
        │     │     └── Conta: App B - Staging
        │     │
        │     └── OU: Desenvolvimento
        │           ├── Conta: App A - Dev
        │           └── Conta: App B - Dev
        │
        └── OU: Sandbox
              └── Conta: Sandbox-Engineers (experimentos livres)

Regras de herança:
  SCP aplicada ao ROOT → afeta TODAS as contas
  SCP aplicada à OU Produção → afeta apenas contas de produção
  SCP aplicada à Conta específica → apenas aquela conta
  
  SCPs se acumulam (mais restritivo prevalece)
```

### Management Account — a conta raiz

```
A Management Account (antes chamada de Master Account):
  → Paga as faturas de toda a organização (Consolidated Billing)
  → Cria e gerencia outras contas
  → Aplica SCPs em toda a organização
  → Tem acesso especial que não pode ser bloqueado por SCP

Princípio crítico: não hospedar workloads na Management Account
  → É o ponto de maior poder → deve ter menor superfície de ataque
  → Apenas billing team e cloud admins têm acesso
  → Zero aplicações, zero EC2, zero banco de dados
  → Se comprometida: atacante controla toda a organização

Proteções da Management Account:
  ├── Pouquíssimos usuários com acesso (1-3 pessoas)
  ├── MFA hardware obrigatório para todo acesso
  ├── Alertas para qualquer ação realizada
  ├── Acesso via IAM Identity Center (não IAM Users diretos)
  └── CloudTrail com S3 e MFA Delete (logs imutáveis)
```

## Service Control Policies (SCPs) — guardrails organizacionais

### O que são SCPs

```
SCPs são políticas que definem o MÁXIMO de permissões que
qualquer identidade em qualquer conta pode ter.

NÃO concedem permissões — apenas limitam o teto.
Para ter acesso, é necessário:
  1. SCP permite (não nega)
  2. IAM Policy permite

Hierarquia de avaliação:
  SCP bloqueia? → DENIED (nem IAM Policy salva)
  IAM Policy nega? → DENIED
  IAM Policy permite? → ALLOWED (se SCP também não bloquear)

Tipos de SCP:
  AllowList (lista de permissão):
    "Apenas estas ações são permitidas"
    → Deny implícito para tudo mais
    → Mais restritivo, mais seguro, mais trabalho para manter
  
  DenyList (lista de negação):
    "Estas ações específicas são negadas, o resto pode"
    → Allow implícito para tudo mais
    → Mais flexível, mais comum na prática
    
AWS recomenda: começar com DenyList (menor atrito inicial)
               evoluir para AllowList em ambientes maduros
```

### SCPs essenciais para toda organização

```
1. Proteção de regiões — recursos apenas em regiões aprovadas:
{
  "Sid": "DenyOutsideApprovedRegions",
  "Effect": "Deny",
  "Action": "*",
  "Resource": "*",
  "Condition": {
    "StringNotEquals": {
      "aws:RequestedRegion": ["us-east-1", "sa-east-1"]
    },
    "ArnNotLike": {
      "aws:PrincipalARN": [
        "arn:aws:iam::*:role/OrganizationAdminRole"
      ]
    }
  }
}
→ Ninguém cria recursos fora de us-east-1 e sa-east-1
→ Previne contra shadow IT em regiões não monitoradas
→ Exceção: role de admin da organização

2. Proteção do CloudTrail — ninguém pode desabilitar:
{
  "Sid": "DenyCloudTrailDisable",
  "Effect": "Deny",
  "Action": [
    "cloudtrail:DeleteTrail",
    "cloudtrail:StopLogging",
    "cloudtrail:UpdateTrail",
    "cloudtrail:PutEventSelectors"
  ],
  "Resource": "*"
}
→ Audit trail é imutável — nem admin da conta pode desativar
→ Crítico para compliance e investigação forense

3. Proteção de GuardDuty — ninguém pode desativar:
{
  "Sid": "DenyGuardDutyDisable",
  "Effect": "Deny",
  "Action": [
    "guardduty:DeleteDetector",
    "guardduty:DisassociateFromMasterAccount",
    "guardduty:StopMonitoringMembers",
    "guardduty:UpdateDetector"
  ],
  "Resource": "*"
}

4. Proibir saída da organização:
{
  "Sid": "DenyLeaveOrganization",
  "Effect": "Deny",
  "Action": "organizations:LeaveOrganization",
  "Resource": "*"
}
→ Conta não pode "sair" da organização e escapar das SCPs

5. Bloquear criação de IAM Users em contas gerenciadas:
{
  "Sid": "DenyIAMUsersCreation",
  "Effect": "Deny",
  "Action": [
    "iam:CreateUser",
    "iam:CreateAccessKey"
  ],
  "Resource": "*",
  "Condition": {
    "ArnNotLike": {
      "aws:PrincipalARN": "arn:aws:iam::*:role/BreakGlassRole"
    }
  }
}
→ Força o uso de IAM Identity Center para acesso humano
→ Sem IAM Users nas contas member (apenas Roles via SSO)

6. SCP específica para Produção — mais restritiva:
{
  "Sid": "DenyDirectDeployInProd",
  "Effect": "Deny",
  "Action": [
    "ec2:RunInstances",
    "ecs:UpdateService",
    "lambda:UpdateFunctionCode",
    "cloudformation:UpdateStack"
  ],
  "Resource": "*",
  "Condition": {
    "ArnNotLike": {
      "aws:PrincipalARN": "arn:aws:iam::*:role/PipelineDeployRole"
    }
  }
}
→ Apenas o pipeline pode fazer deploy em produção
→ Nenhum humano, nem admin, pode fazer deploy direto
```

## Consolidated Billing — visibilidade financeira centralizada

```
Como funciona:
  → Todas as contas da organização têm suas faturas
    consolidadas na Management Account
  → Você paga uma fatura única
  → Visibility por conta no Cost Explorer

Benefícios financeiros:

1. Volume discounts compartilhados:
   Conta dev usa 50TB de S3 → preço tier 1
   Conta prod usa 30TB de S3 → preço tier 1
   
   Sem Consolidated Billing:
   → Conta dev: paga preço tier 1 por 50TB
   → Conta prod: paga preço tier 1 por 30TB
   
   Com Consolidated Billing:
   → 80TB combinados → parte entra no tier 2 (mais barato)
   → Desconto compartilhado entre todas as contas

2. Reserved Instances e Savings Plans compartilhados:
   Reserved Instance comprada na conta A:
   → Se a conta A não usar totalmente: desconto aplicado
     automaticamente na conta B (se tiver instância compatível)
   → Sem Consolidated Billing: desconto não é compartilhado
   
   Savings Plans:
   → Aplicados a qualquer conta da organização
   → Otimização automática sem mover recursos

3. Free Tier por organização:
   → 12 meses de free tier: por organização, não por conta
   → Criar várias contas para acumular free tier: não funciona
   → Free tier é compartilhado entre as contas

4. Visibilidade por conta (Cost Explorer):
   Organização gasta $50.000/mês:
   ├── Conta de produção: $30.000
   ├── Conta de staging: $8.000  ← por que staging custa tanto?
   ├── Conta de dev: $5.000
   ├── Conta de segurança: $2.000
   └── Conta de tooling: $5.000
   
   Drill-down: dentro de cada conta, por serviço, por tag
   → Quem está gastando e onde ficou transparente
```

## AWS Control Tower — Organizations com guardrails prontos

```
Control Tower é uma camada sobre Organizations que:
  → Provisiona a estrutura multi-account com boas práticas
  → Aplica guardrails (SCPs + Config Rules) automaticamente
  → Cria Landing Zone (estrutura inicial de contas)
  → Permite criar novas contas com Account Factory (padronizadas)

Landing Zone criada pelo Control Tower:
  ├── Log Archive Account (CloudTrail centralizado)
  ├── Audit Account (Security Hub, Config aggregator)
  ├── Management Account (billing)
  └── Suas contas de workload (criadas via Account Factory)

Guardrails do Control Tower:
  Mandatory (não podem ser desabilitados):
  ├── CloudTrail habilitado em todas as contas
  ├── CloudWatch Logs retidos por 1 ano
  └── AWS Config habilitado em todas as contas
  
  Strongly Recommended:
  ├── MFA para root de cada conta
  ├── S3 Block Public Access
  └── EBS sem volumes não criptografados
  
  Elective (escolha):
  ├── Restrição de regiões específicas
  └── Outras políticas customizadas

Account Factory (Vending Machine):
  Engenheiro solicita nova conta de desenvolvimento:
  → Control Tower provisiona:
     → Nova conta AWS
     → Structure de OU correta
     → SCPs aplicadas automaticamente
     → CloudTrail configurado
     → IAM Identity Center configurado
     → Account pronta em ~20 minutos, padronizada
  → Sem processo manual de configuração
```

## Criação e gerenciamento de contas

```
Criar nova conta via Organizations:
  aws organizations create-account \
    --email nova-conta@empresa.com \
    --account-name "App-Checkout-Prod"
  
  → Conta criada automaticamente como member da organização
  → Email separado necessário (não pode reutilizar)
  → Acesso inicial: via OrganizationAccountAccessRole (role cross-account)
    criada automaticamente na nova conta

OrganizationAccountAccessRole:
  → Role criada em cada member account pela Management Account
  → Permite que Management Account assume admin na member account
  → Usar apenas para configuração inicial e emergência
  → Não usar para acesso regular (use IAM Identity Center)

Mover conta entre OUs:
  aws organizations move-account \
    --account-id 123456789012 \
    --source-parent-id ou-xxxx-source \
    --destination-parent-id ou-xxxx-destination
  
  → Quando a conta muda de OU: SCPs são atualizadas automaticamente
  → Aplicação de produção promovida: move de OU Staging para OU Produção
    → SCPs de produção passam a se aplicar

Fechar conta (encerrar):
  → Console Organizations → Close account
  → Processo de 90 dias (quarentena antes de encerrar definitivamente)
  → Recursos são encerrados, billing para imediatamente
  → Não pode criar nova conta com mesmo email antes dos 90 dias
```

## Padrão de contas recomendado para startups/scale-ups

```
FASE 1 — Startup inicial (1-3 contas):
  ├── Management Account (apenas billing)
  ├── Production Account (tudo em produção)
  └── Non-Production Account (dev + staging juntos)
  
  SCP básico: proteção de região + CloudTrail imutável

FASE 2 — Crescimento (5-8 contas):
  ├── Management Account
  ├── Security Account (GuardDuty + logs)
  ├── Shared Services Account (AD, ferramentas)
  ├── Production Account
  ├── Staging Account
  └── Development Account
  
  SCP adicional: segregação de deploy, proteção de prod

FASE 3 — Escala (10+ contas):
  ├── Management Account
  ├── Security OU: Security + Audit + Compliance
  ├── Infrastructure OU: Network + Shared Services
  ├── Workloads OU:
  │     ├── Produção OU (1 conta por produto)
  │     ├── Staging OU (1 conta por produto)
  │     └── Dev OU (1 conta por produto ou compartilhada)
  └── Sandbox OU (experimentação livre com limites)
  
  Control Tower + Account Factory para escala
```

## 🧩 Quiz de Fixação

1. Um engenheiro com permissão `AdministratorAccess` na conta de produção tenta habilitar uma nova região (ap-southeast-1) porque quer testar um serviço, mas recebe "Access Denied". Ele tem AdministratorAccess, por que está sendo bloqueado e o que exatamente está negando a ação?
2. Por que usar contas AWS separadas para dev/staging/prod é mais seguro do que usar VPCs separadas dentro da mesma conta, mesmo que as VPCs estejam completamente isoladas?
3. Uma startup tem tudo em uma conta AWS. O CTO diz "somos pequenos demais para múltiplas contas". Quais dois argumentos técnicos (não de compliance) você usaria para convencê-lo a adotar pelo menos a estrutura mínima de 3 contas?

**Respostas:**
1) O engenheiro está sendo bloqueado por uma SCP (Service Control Policy) aplicada à OU ou conta de produção que restringe criação de recursos a regiões aprovadas — a SCP tem `"Effect": "Deny"` para ações com `"aws:RequestedRegion"` diferente das regiões permitidas. O ponto crítico é que SCPs funcionam como um teto de permissões que IAM não pode ultrapassar: mesmo `AdministratorAccess` (que é uma IAM Policy com Allow em tudo) não consegue superar um Deny explícito em uma SCP. A hierarquia de avaliação IAM verifica SCPs antes de qualquer IAM Policy — se a SCP bloqueia, a requisição é negada independente do que a IAM Policy diga. Para resolver: um administrador da organização na Management Account precisa adicionar ap-southeast-1 à lista de regiões permitidas na SCP (se for uma necessidade legítima de negócio).
2) VPCs separadas na mesma conta isolam a rede, mas não isolam IAM. Com contas separadas: (1) Um erro de IAM na conta de dev (ex: policy que permite `ec2:TerminateInstances` em `*`) não pode atingir instâncias de produção — elas estão em outra conta, completamente fora do escopo de qualquer IAM da conta de dev; (2) Uma credencial comprometida (access key, role) da conta de dev tem blast radius limitado àquela conta — o atacante precisaria de credenciais separadas para acessar produção; (3) CloudTrail e logs são independentes por conta — um atacante que compromete a conta de dev e apaga logs não apaga os logs de produção; (4) Billing e cost attribution são transparentes por conta sem configuração de tagging complexa. VPCs isolam rede mas não isolam identidade, billing nem governança.
3) Dois argumentos técnicos: (1) Blast radius de erro humano — em uma conta única, um `aws ec2 terminate-instances --instance-ids $(aws ec2 describe-instances --query "Reservations[].Instances[].InstanceId" --output text)` executado acidentalmente (ou via credencial comprometida) termina TODAS as instâncias, incluindo produção. Com contas separadas, o mesmo comando executado com credenciais de dev afeta apenas as instâncias de dev — produção continua intacta. Para uma startup, uma hora de produção fora do ar pode custar mais do que o custo de configurar múltiplas contas (que é zero — contas AWS são gratuitas); (2) Custo de debug e auditoria — em conta única, CloudTrail mistura logs de dev, staging e prod. Quando há um incidente em produção, investigar o que aconteceu é exponencialmente mais difícil com logs misturados. Com contas separadas, o CloudTrail da conta de produção contém apenas logs de produção — investigação em minutos vs. horas. Além disso, AWS Cost Explorer mostra exatamente quanto cada ambiente custa sem configuração complexa de tags.
