### AWS Key Management Service (KMS) — gerenciamento centralizado de chaves de criptografia

AWS KMS é o serviço que cria, armazena, rotaciona e controla o uso de chaves criptográficas usadas para proteger dados em repouso e em trânsito na AWS. É o fundamento de toda estratégia de criptografia na AWS — praticamente todo serviço que suporta criptografia (S3, RDS, EBS, Lambda, Secrets Manager, CloudWatch Logs) usa o KMS como backend. Entender o KMS significa entender como a criptografia funciona na AWS do ponto de vista arquitetural, não apenas operacional.

---

## Por que um serviço dedicado de gerenciamento de chaves

```
O problema de gerenciar chaves manualmente:

Cenário sem KMS:
  Você gera uma chave AES-256 localmente
  → Onde armazenar a chave? No servidor? No banco?
  → Como rotacionar sem downtime?
  → Como auditar quem usou a chave e quando?
  → Como revogar acesso de forma granular?
  → Se o servidor que tem a chave for comprometido:
    dados E chave comprometidos juntos = catástrofe

Com KMS:
  → Chaves nunca saem dos HSMs do KMS em texto claro
  → Rotação automática anual (ou sob demanda)
  → CloudTrail: audit log de cada uso da chave
  → IAM: controle granular de quem pode usar qual chave
  → Se um servidor for comprometido: os dados cifrados
    são inúteis sem a chave, que permanece segura no KMS

KMS é baseado em HSMs validados FIPS 140-2 Level 3:
  → Hardware Security Module: chip físico dedicado a cripto
  → Chaves nunca existem em RAM comum
  → Resistente a extração física
  → Auditado independentemente por laboratório certificado
```

## Tipos de chaves KMS

### AWS Managed Keys (chaves gerenciadas pela AWS)

```
Criadas e gerenciadas automaticamente pela AWS para serviços específicos:

Exemplos:
  aws/s3      → chave padrão para SSE-S3 com KMS
  aws/rds     → chave padrão para RDS encryption
  aws/ebs     → chave padrão para EBS encryption
  aws/lambda  → chave para variáveis de ambiente Lambda
  aws/secretsmanager → chave para Secrets Manager

Características:
  ├── Criadas automaticamente quando o serviço é primeiro usado
  ├── Rotação: automática a cada 3 anos (forçada pela AWS)
  ├── Key policy: gerenciada pela AWS (você não modifica)
  ├── Não podem ser desabilitadas ou deletadas manualmente
  ├── Sem custo de chave (apenas $0.03 por 10.000 API calls)
  └── Sem controle de acesso granular (qualquer entidade da conta pode usar)

Quando usar:
  → Criptografia básica sem requisito de controle granular
  → Compliance mínimo: dados "precisam ser criptografados"
  → Não há necessidade de auditoria por chave
  → Não há compartilhamento cross-account necessário

Limitação crítica:
  → Você não controla quem pode usar a chave
  → Qualquer IAM identity na conta com permissão no serviço
    pode usar a chave implicitamente
  → Para controle granular: use Customer Managed Keys
```

### Customer Managed Keys (CMK — chaves gerenciadas pelo cliente)

```
Criadas e gerenciadas por você:

Criação:
  aws kms create-key \
    --description "Chave para dados de clientes - checkout service" \
    --key-usage ENCRYPT_DECRYPT \
    --origin AWS_KMS

  → Retorna: KeyId, KeyArn
  → Cria alias para facilitar referência:
  aws kms create-alias \
    --alias-name alias/checkout-customer-data \
    --target-key-id [KeyId]

Custo:
  → $1/mês por chave ativa
  → $0.03 por 10.000 chamadas de API criptográficas

Características:
  ├── Rotação automática: a cada 12 meses (opcional, configurável)
  ├── Key policy: você controla completamente
  ├── Pode ser desabilitada (suspende uso) ou agendada para deleção
  ├── Compartilhamento cross-account possível
  └── Auditoria completa via CloudTrail

Quando usar:
  → Requisito de controle granular de acesso à chave
  → Compliance que exige gerenciamento próprio de chaves (PCI DSS, HIPAA)
  → Criptografia cross-account (compartilhar chave entre contas)
  → Quando precisa de política de rotação personalizada
  → Quando precisa poder revogar acesso à chave independentemente
```

### CloudHSM Keys (External Key Store — XKS)

```
Para requisitos extremos de controle:

AWS CloudHSM:
  → Cluster de HSMs dedicados (não compartilhados) em sua VPC
  → Você controla totalmente o hardware do HSM
  → Chaves nunca existem fora do seu HSM
  → Custo: ~$1.45/hora por HSM (~$1.044/mês)
  → Uso: regulamentações que proíbem chaves em HSM compartilhado

External Key Store (XKS):
  → Suas chaves ficam no seu próprio HSM on-premises
  → KMS faz proxy das operações criptográficas para seu HSM externo
  → Dados na AWS criptografados com chaves que nunca chegam à AWS
  → Uso: soberania de dados absoluta, regulamentações específicas

Quando CloudHSM/XKS faz sentido:
  → Setores financeiros regulados (compliance exige HSM dedicado)
  → Governo com requisito de soberania de dados
  → Empresas com políticas de "chaves nunca na nuvem"

Para a maioria das empresas: CMK standard é suficiente
→ KMS usa HSMs compartilhados mas FIPS 140-2 Level 3 certificados
```

## Criptografia Envelope — o conceito fundamental

```
Problema da criptografia direta com KMS:
  Criptografar 1GB de dados com KMS direto:
  → Enviar 1GB para o KMS → esperar processamento → receber cifrado
  → Latência: inaceitável para grandes volumes
  → KMS: não é otimizado para grandes payloads

Solução: Envelope Encryption (criptografia em envelope)

Como funciona:

1. Você pede ao KMS para gerar um Data Encryption Key (DEK):
   aws kms generate-data-key \
     --key-id alias/minha-chave \
     --key-spec AES_256
   
   Resposta:
   {
     "Plaintext": "<DEK em texto claro — use imediatamente>",
     "CiphertextBlob": "<DEK criptografada com sua CMK — armazenar>"
   }

2. Use o DEK em texto claro para criptografar seus dados localmente:
   → AES-256 local (muito rápido, sem latência de rede)
   → 1GB de dados criptografados em segundos

3. Descarte o DEK em texto claro da memória imediatamente

4. Armazene junto com os dados cifrados: DEK criptografada (CiphertextBlob)

5. Para descriptografar:
   → Chame KMS com a DEK criptografada: KMS descriptografa com CMK
   → Use DEK em texto claro para descriptografar seus dados localmente
   → Descarte DEK da memória novamente

Resultado:
  → Sua CMK no KMS NUNCA toca seus dados diretamente
  → Apenas o pequeno DEK (32 bytes) vai e vem do KMS
  → Seus dados são cifrados/decifrados localmente (velocidade total)
  → Para comprometer seus dados: atacante precisa da DEK E da CMK

Hierarquia de chaves:
  CMK (KMS) ─── cifra ───► DEK (gerada por operação)
  DEK ──────── cifra ───► Dados reais
  
  Para decifrar dados: precisa do DEK
  Para decifrar o DEK: precisa da CMK no KMS
  CMK nunca sai do KMS em texto claro
```

### Como os serviços AWS usam Envelope Encryption

```
S3 (SSE-KMS):
  PUT /bucket/objeto (payload: 500MB)
  → S3 chama KMS: generate-data-key (CMK configurada)
  → S3 usa DEK para criptografar os 500MB localmente
  → S3 armazena: dados cifrados + DEK cifrada (nos metadados do objeto)
  → S3 descarta DEK da memória
  
  GET /bucket/objeto
  → S3 recupera DEK cifrada dos metadados
  → S3 chama KMS: decrypt(DEK cifrada)
  → S3 usa DEK decifrada para descriptografar os dados
  → S3 entrega dados em texto claro para o cliente
  → S3 descarta DEK da memória
  
  Você não vê nada disso: transparente para o cliente S3

RDS (criptografia at-rest):
  → RDS usa envelope encryption para todos os dados no volume EBS
  → CMK do KMS protege o DEK
  → DEK protege os dados do banco
  → Se alguém rouba o disco físico do servidor: inútil sem o DEK
  → Se alguém rouba o DEK cifrado: inútil sem a CMK do KMS
```

## Key Policy — controle de acesso à chave

```
Key Policy é a política de recurso da CMK:
  → Controla quem pode usar, gerenciar e administrar a chave
  → Obrigatória — toda CMK tem uma (default ou customizada)
  → Diferente de IAM Policy: ambas devem permitir o acesso

Policy padrão (default) de uma CMK:
{
  "Statement": [
    {
      "Sid": "Enable IAM User Permissions",
      "Effect": "Allow",
      "Principal": {"AWS": "arn:aws:iam::123456789:root"},
      "Action": "kms:*",
      "Resource": "*"
    }
  ]
}
→ A conta root pode gerenciar e usar a chave
→ IAM policies da conta também se aplicam

Key Policy customizada para menor privilégio:
{
  "Statement": [
    {
      "Sid": "KeyAdmins",
      "Effect": "Allow",
      "Principal": {"AWS": "arn:aws:iam::123:role/SecurityAdminRole"},
      "Action": ["kms:Create*", "kms:Describe*", "kms:Enable*",
                 "kms:List*", "kms:Put*", "kms:Update*",
                 "kms:Revoke*", "kms:Disable*", "kms:Delete*",
                 "kms:ScheduleKeyDeletion", "kms:CancelKeyDeletion"],
      "Resource": "*"
    },
    {
      "Sid": "CheckoutServiceUse",
      "Effect": "Allow",
      "Principal": {"AWS": "arn:aws:iam::123:role/checkout-lambda-role"},
      "Action": ["kms:Decrypt", "kms:GenerateDataKey"],
      "Resource": "*",
      "Condition": {
        "StringEquals": {
          "kms:ViaService": "s3.us-east-1.amazonaws.com"
        }
      }
    }
  ]
}

Elementos-chave:
  kms:Decrypt, kms:GenerateDataKey → uso (aplicações)
  kms:Create*, kms:Delete*, kms:Disable* → administração (SecurityAdmin)
  kms:ViaService → permite uso apenas via serviço específico (não direto)
```

## Rotação de chaves

```
Rotação automática:
  → Habilitada por chave (desabilitada por padrão)
  → Quando habilitada: nova versão da chave criada anualmente
  
  aws kms enable-key-rotation \
    --key-id alias/checkout-customer-data

Como a rotação funciona:
  → KMS cria novo material criptográfico (nova versão da chave)
  → Novas operações de Encrypt usam a versão mais recente
  → Dados cifrados com versão antiga: descriptografados com versão antiga (automaticamente)
  → Dados antigos NÃO são re-criptografados automaticamente
  → Sem downtime, sem mudança de KeyId, transparente para aplicações
  
  Por que isso é importante:
  → Se a chave antiga foi comprometida: dados novos usam chave nova
  → Dados antigos ainda estão sob risco (a versão antiga ainda existe no KMS)
  → Para re-criptografar dados antigos: processo manual ou automatizado separado

Rotação manual (on-demand):
  aws kms rotate-key-on-demand \
    --key-id alias/checkout-customer-data
  → Força nova versão imediatamente (sem esperar o ciclo anual)
  → Útil após suspeita de comprometimento

Deleção de chave:
  → KMS não permite deleção imediata
  → Mínimo de espera: 7 dias | Máximo: 30 dias
  → Durante a espera: chave desabilitada
  → Use: aws kms schedule-key-deletion --key-id xxx --pending-window-in-days 7
  → CUIDADO: dados cifrados com a chave deletada são PERDIDOS PARA SEMPRE
```

## KMS em múltiplas contas (cross-account)

```
Caso de uso: conta A precisa acessar dados criptografados
             com chave da conta B

Configuração na conta B (dona da chave):
  Key Policy:
  {
    "Sid": "AllowCrossAccountAccess",
    "Effect": "Allow",
    "Principal": {
      "AWS": "arn:aws:iam::conta-A:role/data-processor-role"
    },
    "Action": ["kms:Decrypt", "kms:GenerateDataKey"],
    "Resource": "*"
  }

Configuração na conta A (usuária da chave):
  IAM Policy para a role da conta A:
  {
    "Effect": "Allow",
    "Action": ["kms:Decrypt", "kms:GenerateDataKey"],
    "Resource": "arn:aws:kms:us-east-1:conta-B:key/[KeyId]"
  }

Ambas precisam permitir — a Key Policy E a IAM Policy

Uso comum:
  → Conta de Data Engineering acessa dados criptografados
    da conta de Produção
  → Conta de Backup usa chave da conta principal para
    criptografar backups cross-account
```

## Auditoria com CloudTrail

```
Todo uso da chave KMS gera evento no CloudTrail:

Evento de Decrypt:
{
  "eventName": "Decrypt",
  "userIdentity": {
    "arn": "arn:aws:iam::123:role/checkout-lambda-role",
    "sessionContext": {
      "sessionIssuer": {"userName": "checkout-lambda-role"}
    }
  },
  "requestParameters": {
    "encryptionContext": {
      "aws:s3:arn": "arn:aws:s3:::bucket/dados/pedido-12345.enc"
    }
  },
  "responseElements": null
}

Queries úteis no CloudWatch Logs Insights:
  -- Quem usou a chave X nas últimas 24h?
  fields userIdentity.arn, eventName, @timestamp
  | filter requestParameters.keyId = "alias/checkout-customer-data"
  | sort @timestamp desc
  
  -- Volume de decryptions por hora (detectar pico anormal)
  fields @timestamp
  | filter eventName = "Decrypt"
  | stats count() by bin(1h)
  
  -- Tentativas de uso não autorizado
  fields @timestamp, userIdentity.arn, errorCode
  | filter eventSource = "kms.amazonaws.com"
    AND errorCode = "AccessDenied"

Encryption context:
  → Metadados opcionais passados junto com operações de criptografia
  → Devem ser idênticos no Encrypt e no Decrypt
  → Adicionam segurança: "este dado só pode ser decriptado
    se você souber que é do pedido-12345"
  → Aparecem no CloudTrail (auditoria do contexto do uso)
```

## 🧩 Quiz de Fixação

1. Por que a criptografia envelope (envelope encryption) é usada em vez de criptografar dados diretamente com a CMK do KMS, e o que acontece se o DEK (Data Encryption Key) for comprometido mas a CMK não?
2. Uma aplicação armazenando dados PCI em S3 precisa garantir que apenas a role `checkout-service-role` possa descriptografar os dados, mesmo que outros usuários/roles da conta tenham permissão ao bucket S3. Como a Key Policy do KMS implementa isso, e por que IAM Policy sozinha não é suficiente?
3. A empresa vai demitir um funcionário que tinha acesso à CMK usada para criptografar dados de clientes. Quais são os passos corretos para revogar o acesso dessa pessoa sem interromper os serviços que dependem da chave?

**Respostas:**
1) A criptografia direta com KMS tem duas limitações: (1) o KMS tem limite de tamanho de payload de 4KB — não é possível criptografar arquivos maiores diretamente; (2) cada operação de Encrypt/Decrypt exige uma chamada de rede ao KMS com latência de dezenas a centenas de milissegundos — inviável para grandes volumes de dados. A criptografia envelope resolve: a CMK criptografa apenas o DEK (32 bytes), operação rápida; o DEK criptografa os dados localmente na memória, operação ultrarrápida sem latência de rede. Se o DEK for comprometido: o atacante consegue descriptografar apenas os dados criptografados com aquele DEK específico — mas como cada operação de criptografia gera um DEK novo, o impacto é limitado a um conjunto específico de dados. A CMK comprometida seria muito mais grave: permitiria gerar/descriptografar qualquer DEK, comprometendo todos os dados.
2) IAM Policy sozinha não é suficiente porque a Key Policy da CMK é uma camada independente de controle — ambas devem permitir o acesso para que ele seja concedido. Uma IAM Policy que permite `kms:Decrypt` para outro usuário não tem efeito se a Key Policy não incluir esse usuário como principal permitido. Implementação na Key Policy: adicionar um statement que permite `kms:Decrypt` e `kms:GenerateDataKey` apenas para `arn:aws:iam::123:role/checkout-service-role`, e adicionar a condição `"kms:ViaService": "s3.us-east-1.amazonaws.com"` para garantir que o uso seja apenas via S3 (não chamadas diretas à API do KMS). Outros usuários com acesso ao bucket S3 receberão erro de `AccessDeniedException` ao tentar acessar objetos criptografados porque, mesmo que o S3 tente chamar o KMS para descriptografar em nome deles, a Key Policy negará (sem estar explicitamente permitido).
3) Passos corretos para revogar acesso sem interromper serviços: (1) Identificar: verificar a Key Policy e IAM policies para determinar como o funcionário tinha acesso — diretamente pelo ARN de usuário IAM ou via grupo/role; (2) Remover o funcionário do IAM Identity Center/grupo — isso revoga o acesso imediatamente à conta AWS; (3) Atualizar a Key Policy: se o ARN do usuário IAM estava explicitamente na Key Policy, removê-lo; (4) Desativar (não deletar) as access keys IAM do usuário imediatamente; (5) Verificar se o funcionário tinha chaves guardadas localmente (no laptop ou em scripts) — revogar access keys é suficiente pois sem autenticação válida não há como usar o KMS; (6) NÃO é necessário rotacionar ou deletar a CMK — isso interromperia todos os serviços que dependem dela. A rotação de chave não revoga acesso já concedido: muda o material criptográfico para novos dados, mas o acesso é controlado por IAM/Key Policy. Remover o usuário das políticas é o mecanismo correto de revogação.
