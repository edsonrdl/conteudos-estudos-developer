### AWS Security Hub — visão unificada da postura de segurança AWS

AWS Security Hub é o serviço que centraliza, agrega e prioriza findings de segurança de múltiplos serviços AWS e ferramentas de terceiros em um único painel. Em vez de verificar GuardDuty, Inspector, Macie e Config em consoles separados, o Security Hub consolida tudo em um lugar, avalia sua postura contra padrões de segurança estabelecidos (CIS, PCI DSS, FSBP) e gera um score de segurança que evolui conforme você remedia problemas. É o ponto de partida para qualquer programa de gestão de postura de segurança (CSPM) na AWS.

---

## O problema que o Security Hub resolve

```
Sem Security Hub — mundo fragmentado:

Time de segurança verifica diariamente:
  Console GuardDuty → findings de threat detection
  Console Inspector → vulnerabilidades em EC2 e containers
  Console Macie → exposição de dados sensíveis em S3
  Console Config → non-compliance de configurações
  Console IAM Access Analyzer → acessos externos
  Console Trusted Advisor → recomendações de segurança
  
  + Ferramentas de terceiros: Crowdstrike, Palo Alto, Qualys...
  
  Resultado:
  ├── 6+ consoles para verificar diariamente
  ├── Findings duplicados (GuardDuty + Inspector sobre o mesmo EC2)
  ├── Sem priorização centralizada
  ├── Sem score de postura de segurança
  └── Difícil demonstrar melhoria ao longo do tempo

Com Security Hub — mundo unificado:
  Um console → todos os findings de todos os serviços
  Score de segurança: 72% → 85% → 94% (melhoria mensurável)
  Priorização automática por severidade e serviço
  Compliance standards: "você atende 87% do CIS Benchmark"
```

## Arquitetura do Security Hub

```
FONTES DE FINDINGS:

Serviços AWS nativos (integração automática):
  ├── Amazon GuardDuty → threat detection
  ├── Amazon Inspector v2 → vulnerabilidades
  ├── Amazon Macie → dados sensíveis expostos
  ├── AWS Config → non-compliance de configurações
  ├── IAM Access Analyzer → acessos externos a recursos
  ├── AWS Firewall Manager → violações de políticas de firewall
  └── Amazon Detective → investigação aprofundada

Parceiros de marketplace (50+ integrações):
  ├── Palo Alto Prisma Cloud → CSPM
  ├── CrowdStrike Falcon → EDR
  ├── Qualys → vulnerability management
  ├── Tenable.io → vulnerability scanning
  ├── Rapid7 InsightVM → vulnerability management
  └── Splunk → SIEM

Findings customizados (via API):
  → Sua própria aplicação pode enviar findings
  → Ferramentas internas de segurança
  → Resultados de pentests automatizados

FORMATO PADRÃO — ASFF:
  Amazon Security Finding Format (ASFF)
  → Formato JSON padronizado para todos os findings
  → Permite processar findings de qualquer fonte de forma uniforme

SAÍDAS:
  ├── Console Security Hub (dashboard, filtros, priorização)
  ├── EventBridge → automação de resposta
  ├── AWS Chatbot → notificações no Slack/Teams
  └── SIEM externos (via Kinesis, S3, ou API)
```

## Security Standards — avaliação de conformidade

### O que são Security Standards

```
Security Standards são conjuntos de controles que o Security Hub
verifica automaticamente contra sua configuração AWS.

Security Hub avalia cada controle:
  PASSED:   configuração está correta
  FAILED:   configuração viola o controle
  WARNING:  verificação inconclusiva
  NOT_AVAILABLE: não verificável no contexto atual

Score de conformidade:
  # controles PASSED / # controles PASSED + FAILED × 100
  
  Exemplo:
  180 controles PASSED, 40 FAILED, 5 WARNING
  Score = 180 / (180+40) = 82%

Score geral da conta:
  Média ponderada de todos os Standards habilitados
```

### Standard 1: AWS Foundational Security Best Practices (FSBP)

```
Criado pela AWS com base nas melhores práticas dos serviços AWS
→ Padrão recomendado para começar
→ Mais de 200 controles cobrindo todos os principais serviços

Controles de exemplo:

[IAM.1] IAM policies should not allow full "*" administrative privileges
  → Detecta: policies com "Action": "*" e "Resource": "*"
  → Severidade: HIGH

[S3.1] S3 Block Public Access setting should be enabled
  → Detecta: contas sem S3 Block Public Access no nível de conta
  → Severidade: HIGH

[RDS.3] RDS DB instances should have encryption at-rest enabled
  → Detecta: instâncias RDS sem criptografia habilitada
  → Severidade: MEDIUM

[CloudTrail.1] CloudTrail should be enabled and configured with log validation
  → Detecta: contas sem CloudTrail com log file validation
  → Severidade: HIGH

[EC2.15] EC2 subnets should not automatically assign public IP addresses
  → Detecta: subnets com auto-assign de IP público habilitado
  → Severidade: MEDIUM

[GuardDuty.1] GuardDuty should be enabled
  → Detecta: contas sem GuardDuty ativo
  → Severidade: MEDIUM
```

### Standard 2: CIS AWS Foundations Benchmark

```
Center for Internet Security (CIS) — padrão independente
→ Amplamente aceito por auditores e reguladores
→ Duas versões: v1.4.0 e v3.0.0

Seções do CIS Benchmark:
  1. Identity and Access Management (IAM)
  2. Storage (S3)
  3. Logging (CloudTrail, CloudWatch)
  4. Monitoring (métricas e alarmes)
  5. Networking (VPC, Security Groups)

Controles CIS de exemplo:

[CIS 1.4] Ensure access keys are rotated every 90 days or less
  → Verifica: data de rotação das access keys de IAM users
  → Severidade: MEDIUM

[CIS 2.1] Ensure S3 Bucket Policy is set to deny HTTP requests
  → Verifica: bucket policies que forçam HTTPS
  → Severidade: MEDIUM

[CIS 3.1] Ensure CloudTrail is enabled in all regions
  → Verifica: multi-region trail ativo
  → Severidade: HIGH

[CIS 4.1] Ensure a log metric filter and alarm exist for unauthorized API calls
  → Verifica: CloudWatch Metric Filter para eventos não autorizados
  → Severidade: LOW

[CIS 5.4] Ensure no security groups allow ingress from 0.0.0.0/0 to port 22
  → Verifica: Security Groups com SSH aberto para qualquer IP
  → Severidade: HIGH

Uso em auditorias:
  Security Hub → Standards → CIS → Exportar relatório
  → "Conta atende 89% do CIS Benchmark v1.4.0"
  → Auditores aceitam como evidência de conformidade
```

### Standard 3: PCI DSS

```
Payment Card Industry Data Security Standard
→ Para empresas que processam dados de cartão de crédito
→ ~200 controles verificados automaticamente

Controles PCI de exemplo:

[PCI.IAM.4] Hardware MFA should be enabled for the root user
  → Verifica: MFA hardware na conta root
  → Severidade: CRITICAL

[PCI.EC2.2] VPC default security group should not allow inbound and outbound traffic
  → Verifica: security group default não tem regras permissivas
  → Severidade: MEDIUM

[PCI.CloudTrail.1] CloudTrail should be enabled
  → Requirement 10: log de todos os acessos
  → Severidade: CRITICAL

[PCI.KMS.1] Customer master key rotation should be enabled
  → Verifica: CMKs KMS com rotação anual habilitada
  → Severidade: MEDIUM

Score PCI DSS separado do FSBP:
  "Sua conta está 76% conforme com PCI DSS 3.2.1"
  → Útil para demonstrar progresso ao QSA antes da auditoria formal
```

## Findings — agregação e priorização

### Dashboard de findings

```
Security Hub dashboard mostra:

Por severidade (últimos 24h):
  CRITICAL: 3 findings → ação imediata
  HIGH:    15 findings → investigar hoje
  MEDIUM:  42 findings → planejar remediação
  LOW:     87 findings → baclog de melhoria

Por serviço/produto:
  GuardDuty: 8 findings
  Inspector: 35 findings (vulnerabilidades)
  Config:    18 findings (misconfigurations)
  Macie:      4 findings (dados expostos)

Filtragem útil:
  WorkflowStatus = NEW AND Severity = CRITICAL
  → Apenas findings críticos não tratados
  
  RecordState = ACTIVE AND ResourceType = AwsS3Bucket
  → Apenas findings ativos relacionados a S3
  
  ProductName = GuardDuty AND CreatedAt > 2024-01-01
  → Findings do GuardDuty nos últimos dias
```

### Workflow de findings — gestão de ciclo de vida

```
Todo finding tem um WorkflowStatus:

NEW:        finding novo, não foi revisado
NOTIFIED:   time foi notificado
SUPPRESSED: falso positivo, ignorar deliberadamente
RESOLVED:   remediado

Processo de gestão:

1. Finding NEW crítico chega (EC2 comprometida)
   → Automação EventBridge notifica time via Slack

2. Engenheiro revisa:
   → Legítimo: muda para NOTIFIED, abre ticket de remediação
   → Falso positivo: muda para SUPPRESSED com justificativa

3. Remediação executada:
   → Engenheiro muda para RESOLVED
   → Security Hub automaticamente re-avalia em próxima verificação

4. Se ainda vulnerável após re-avaliação:
   → Finding volta para ACTIVE automaticamente
   → Não pode "resolver" sem realmente resolver

Notas (Notes) em findings:
  → Adicionar contexto ao investigar
  → "Investigado em 15/01/2024 por joão.silva"
  → "Plano de remediação: será resolvido no sprint 23"
```

## Automação de resposta com EventBridge

```
Security Hub publica todos os findings como eventos EventBridge:

{
  "source": "aws.securityhub",
  "detail-type": "Security Hub Findings - Imported",
  "detail": {
    "findings": [{
      "Severity": {"Label": "HIGH"},
      "Title": "S3 bucket should have access logging enabled",
      "Resources": [{
        "Type": "AwsS3Bucket",
        "Id": "arn:aws:s3:::bucket-producao"
      }],
      "ProductName": "Security Hub",
      "ComplianceStandards": ["CIS AWS Foundations Benchmark v1.4.0"]
    }]
  }
}

Automações úteis:

1. CRITICAL → isolamento automático:
   EventBridge: severity = CRITICAL → Lambda (incident response)
   
2. HIGH → ticket automático:
   EventBridge: severity = HIGH → Lambda → cria Jira ticket
   com todos os detalhes do finding

3. S3 público → remediação automática:
   EventBridge: finding.Title contains "S3 Block Public Access"
   → Lambda: aws s3api put-public-access-block para o bucket

4. Security Score semanal:
   EventBridge Scheduler (toda segunda 8h) → Lambda
   → Busca score via Security Hub API
   → Publica no canal #security-metrics no Slack
   "Security Score: 84% (+2% vs semana passada)"

5. Relatório semanal de findings:
   EventBridge Scheduler → Lambda
   → Agrupa findings por severidade e produto
   → Envia email para CISO com resumo executivo
```

## Security Hub em múltiplas contas

```
Configuração via Organizations:

Security Account = Security Hub Administrator
→ Vê findings de TODAS as contas da organização
→ Habilita Security Standards em todas as contas centralmente

Configuração:
  aws securityhub enable-organization-admin-account \
    --admin-account-id [security-account-id]
  
  # Habilitar auto-enable para novas contas
  aws securityhub update-organization-configuration \
    --auto-enable \
    --auto-enable-standards DEFAULT

Benefício:
  Antes: 10 contas → verificar Security Hub em 10 consoles
  Depois: 1 console (Security Account) → todos os findings

Score de segurança por conta:
  Security Account → Settings → Accounts
  ├── conta-producao: 91%
  ├── conta-staging: 78%
  ├── conta-dev: 65%  ← atenção: muito abaixo da média
  └── conta-tooling: 88%
  
  → Identificar rapidamente qual conta precisa de atenção
  → Demonstrar melhoria ao longo do tempo para o board
```

## 🧩 Quiz de Fixação

1. Um CISO precisa demonstrar para o board que a postura de segurança da empresa melhorou em 6 meses. Quais métricas específicas do Security Hub você usaria para essa apresentação e como obtê-las?
2. O Security Hub mostra o controle `[S3.1] S3 Block Public Access setting should be enabled` como FAILED em 15 buckets. O time quer remediar isso com automação em vez de manualmente. Descreva a arquitetura completa de remediação automática usando EventBridge e Lambda.
3. Um engenheiro marca como SUPPRESSED um finding `GuardDuty: UnauthorizedAccess:IAMUser/ConsoleLoginSuccess.B` sem documentar o motivo, alegando que "é falso positivo". Por que essa prática é perigosa e qual é o processo correto para suprimir findings?

**Respostas:**
1) Métricas para o board: (1) Security Score histórico — Security Hub → Summary → Security Score histórico: mostrar evolução de, ex., 62% em julho para 84% em dezembro, com gráfico de linha mês a mês; (2) Findings críticos abertos ao longo do tempo — número de findings CRITICAL/HIGH com WorkflowStatus=NEW no início vs. agora; mostrar redução de 45 findings CRITICAL para 3 (contidos e monitorados); (3) Compliance por padrão — % de conformidade com CIS Benchmark e FSBP em cada mês; (4) Tempo médio de remediação (MTTR) — average time between finding creation e WorkflowStatus=RESOLVED para findings HIGH. Como obter: Security Hub → Insights (métricas pré-construídas) + exportar via API para Excel/QuickSight para visualizações executivas. Apresentação ideal: dois slides — (1) gráfico de score 6 meses, (2) tabela: CRITICAL findings: 45→3, tempo médio remediação: 14 dias → 4 dias.
2) Arquitetura de remediação automática: (1) Config Rule `s3-bucket-public-access-prohibited` detecta bucket sem Block Public Access → gera finding no Security Hub; (2) Security Hub finding publicado como evento EventBridge com `detail.findings[0].Title = "S3 Block Public Access setting should be enabled"`; (3) EventBridge Rule filtra por esse título específico + `detail.findings[0].Severity.Label = "HIGH"`; (4) EventBridge aciona Lambda `RemediateS3BlockPublicAccess`; (5) Lambda extrai o ARN do bucket do finding (`detail.findings[0].Resources[0].Id`), chama `s3api put-public-access-block` com `BlockPublicAcls=true, IgnorePublicAcls=true, BlockPublicPolicy=true, RestrictPublicBuckets=true`, atualiza o WorkflowStatus do finding para RESOLVED via Security Hub API, e envia notificação ao canal de segurança documentando o que foi remediado e quando. Proteção adicional: Lambda deve verificar se o bucket tem tag `public-access-intentional=true` (alguns buckets de hospedagem de site estático precisam ser públicos) antes de bloquear, e notificar o owner via tag `Owner` em vez de bloquear automaticamente nesses casos.
3) Suprimir `UnauthorizedAccess:IAMUser/ConsoleLoginSuccess.B` sem documentação é perigoso por duas razões: (1) Esse finding especificamente indica que alguém fez login bem-sucedido no console de um IP malicioso conhecido — suprimi-lo sem investigação pode esconder um comprometimento real em andamento; um atacante poderia ter credenciais válidas e estar operando na conta enquanto o finding permanece suprimido; (2) Sem documentação, outros engenheiros de segurança que revisarem futuramente não saberão por que foi suprimido, se ainda é um falso positivo válido, ou se a situação mudou. O processo correto: (1) Investigar primeiro — verificar no CloudTrail qual usuário, de qual IP exatamente, quais ações foram realizadas após o login; (2) Se confirmado falso positivo: documentar no campo "Notes" do finding: "Confirmado em [data] por [nome]: login de escritório de São Paulo via VPN — IP do provedor VPN corporativo listado como malicioso (Proofpoint). Usuário: maria.silva, ação: login de IP 200.x.x.x (VPN Cisco AnyConnect). Nenhuma ação maliciosa detectada nos 30 minutos seguintes."; (3) Criar Suppression Rule com condição específica (IP da VPN corporativa) em vez de suprimir o tipo de finding genericamente; (4) Revisar em 90 dias se a supressão ainda é válida.
