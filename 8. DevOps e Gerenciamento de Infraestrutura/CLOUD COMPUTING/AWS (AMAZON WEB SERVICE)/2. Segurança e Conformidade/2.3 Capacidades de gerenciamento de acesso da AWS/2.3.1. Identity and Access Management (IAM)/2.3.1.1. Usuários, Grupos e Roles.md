### Usuários, Grupos e Roles — as três identidades fundamentais do IAM

O IAM (Identity and Access Management) é o sistema central de controle de acesso da AWS. Ele define **quem pode fazer o quê** em quais recursos. Para isso, usa três tipos de identidade: Usuários (para pessoas), Grupos (para organizar usuários) e Roles (para serviços, automações e acesso temporário). Entender quando e por que usar cada um é a base de qualquer arquitetura segura na AWS.

---

## IAM User — identidade para pessoas (e legados)

### O que é

```
IAM User é uma identidade permanente associada a uma pessoa
ou sistema com credenciais de longa duração:

Tipos de credencial de um IAM User:
  ├── Console password: login no browser (console.aws.amazon.com)
  ├── Access Key ID + Secret Access Key: acesso programático (CLI, SDK)
  └── MFA device: segundo fator para console e/ou operações sensíveis

Criação:
  aws iam create-user --user-name joao.silva
  aws iam create-login-profile --user-name joao.silva --password S3nha@Fort3
  aws iam create-access-key --user-name joao.silva
```

### Quando usar IAM Users

```
✓ Use IAM User para:
  ├── Pessoas que precisam acessar o Console AWS
  ├── Sistemas legados que não suportam IAM Roles (raro)
  └── Cenários onde SSO/IAM Identity Center não é viável

✗ NÃO use IAM User para:
  ├── Aplicações rodando em EC2, Lambda, ECS (use Roles)
  ├── CI/CD pipelines (use OIDC + Roles ou CodePipeline)
  └── Automações e scripts (use Roles)
```

### O problema das credenciais de longa duração

```
Access Keys: credenciais permanentes até serem deletadas

Riscos:
  1. Vazamento acidental:
     git commit com AWS_ACCESS_KEY no .env → GitHub → escaneado
     → Bots encontram em minutos e começam a usar

  2. Sem expiração automática:
     Key criada em 2021, funcionário saiu em 2022, key ainda ativa
     → Ex-funcionário tem acesso ativo até alguém desativar

  3. Difícil de revogar em emergência:
     Se a key estiver sendo usada em 50 scripts, desativar quebra tudo
     → Hesitação em revogar compromisso de segurança

  4. Não há como saber de onde vieram:
     Sem MFA, qualquer pessoa com a key pode usá-la de qualquer lugar
     → Difícil distinguir uso legítimo de comprometimento

Boas práticas para quem usa IAM Users:
  ├── MFA obrigatório para TODOS os usuários com acesso ao console
  ├── Access keys rotacionadas a cada 90 dias (máximo)
  ├── Credenciais Report: identificar keys inativas > 90 dias
  ├── Nunca criar access keys para o usuário root
  └── Preferir IAM Identity Center (SSO) sobre IAM users diretos
```

## IAM Group — organização de usuários

### O que é

```
IAM Group é uma coleção de IAM Users que compartilham as
mesmas políticas de permissão. Não é uma identidade que
pode fazer chamadas de API — serve apenas para organização.

Groups NÃO podem:
  → Assumir roles
  → Fazer chamadas de API diretamente
  → Ser usados como Principal em políticas de recursos

Groups SÃO úteis para:
  → Aplicar mesma política a vários usuários simultaneamente
  → Gerenciar permissões por função (devs, sres, dados)
  → Quando novo membro entra: adicionar ao grupo, não recriar políticas
```

### Estrutura de grupos por função

```
Grupos típicos numa organização:

Group: Developers
  Políticas:
  ├── DeveloperPolicy (acesso de dev a serviços não-prod)
  ├── ReadOnlyAccess-Staging (visualização de staging)
  └── CloudWatchReadOnly (ver logs)
  
  Membros: joao.silva, ana.souza, carlos.mendes

Group: SRE-DevOps
  Políticas:
  ├── InfrastructureManagementPolicy (EC2, ECS, RDS management)
  ├── CloudFormationFullAccess
  └── IAMReadOnly (ver mas não modificar IAM)
  
  Membros: maria.lima, pedro.costa

Group: Security
  Políticas:
  ├── IAMFullAccess (gerenciar permissões)
  ├── SecurityAuditPolicy (leitura em todos os serviços de segurança)
  └── CloudTrailFullAccess
  
  Membros: ana.security

Group: DataEngineering
  Políticas:
  ├── S3FullAccess-DataLake
  ├── GlueFullAccess
  └── AthenaFullAccess

Operação diária:
  Novo desenvolvedor contratado:
  → aws iam add-user-to-group --user-name novo.dev --group-name Developers
  → Herda automaticamente todas as permissões do grupo
  → Sem necessidade de configurar permissões individuais
  
  Dev promovido a SRE:
  → aws iam remove-user-from-group --user-name dev --group-name Developers
  → aws iam add-user-to-group --user-name dev --group-name SRE-DevOps
  → Permissões ajustadas automaticamente
```

## IAM Role — identidade para serviços e acesso temporário

### O que é e por que é fundamental

```
IAM Role é uma identidade que pode ser ASSUMIDA temporariamente
por serviços AWS, usuários, ou contas externas.

Diferença crítica de um IAM User:
  IAM User: credenciais permanentes (access key nunca expira)
  IAM Role: credenciais TEMPORÁRIAS (expiram em 15min a 12h)
  
  Quando EC2 assume uma role:
  → STS (Security Token Service) emite:
    AccessKeyId (temporário, começa com ASIA...)
    SecretAccessKey (temporário)
    SessionToken (prova que é temporário)
    Expiration (quando as credenciais expiram)
  
  → Renova automaticamente antes de expirar
  → Se vazar: expira em horas, não fica ativa para sempre
```

### Estrutura de uma IAM Role

```
Uma Role tem dois componentes essenciais:

1. TRUST POLICY (quem pode assumir esta role):
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "Service": "lambda.amazonaws.com"   ← apenas Lambda pode assumir
    },
    "Action": "sts:AssumeRole"
  }]
}

Outros exemplos de Principal:
  "Service": "ec2.amazonaws.com"          → instâncias EC2
  "Service": "ecs-tasks.amazonaws.com"    → ECS tasks
  "AWS": "arn:aws:iam::123:user/joao"     → usuário específico
  "AWS": "arn:aws:iam::456:root"          → conta AWS externa
  "Federated": "cognito-identity.amazonaws.com" → usuários Cognito

2. PERMISSION POLICY (o que a role pode fazer):
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:PutObject"],
    "Resource": "arn:aws:s3:::bucket-prod/uploads/*"
  }]
}
```

### Tipos de IAM Roles e quando usar cada um

```
1. Service Role (EC2, Lambda, ECS, etc.):
   Uso: aplicações que precisam acessar outros serviços AWS
   
   Lambda que lê do SQS e escreve no DynamoDB:
   Trust: lambda.amazonaws.com
   Permissions: sqs:ReceiveMessage + dynamodb:PutItem
   
   EC2 Instance Profile:
   Trust: ec2.amazonaws.com
   Permissions: o que a aplicação na EC2 precisa
   
   Como a EC2 usa a role:
   A aplicação chama o SDK → SDK busca credenciais automaticamente
   via Instance Metadata Service (http://169.254.169.254/...)
   → Zero configuração de credenciais no código

2. Cross-Account Role:
   Uso: conta A acessa recursos da conta B
   
   Conta B (produção) cria role:
   Trust: "AWS": "arn:aws:iam::conta-tooling:role/PipelineRole"
   Permissions: deploy permissions em conta B
   
   Conta A (tooling) assume a role:
   aws sts assume-role \
     --role-arn "arn:aws:iam::conta-producao:role/DeployRole" \
     --role-session-name "pipeline-deploy-123"
   → Recebe credenciais temporárias para usar na conta B

3. Web Identity / OIDC Role:
   Uso: CI/CD (GitHub Actions, CircleCI) sem access keys
   
   GitHub Actions assumindo role via OIDC:
   Trust:
   {
     "Principal": {"Federated": "token.actions.githubusercontent.com"},
     "Condition": {
       "StringLike": {
         "token.actions.githubusercontent.com:sub":
           "repo:empresa/repositorio:ref:refs/heads/main"
       }
     }
   }
   → Apenas o repositório específico, apenas na branch main
   → Zero access keys no GitHub Secrets
   → Credenciais temporárias por job

4. Role para humanos (assumida via SSO):
   Uso: engenheiros acessam a conta de produção temporariamente
   
   IAM Identity Center configura:
   Grupo "SRE-Produção" → Permission Set "ReadOnly-Prod"
   → SRE acessa console com sessão de 8h via SSO
   → Sem IAM user na conta de produção, sem access key permanente
```

## O fluxo de assunção de roles (sts:AssumeRole)

```
Como a EC2 obtém credenciais da role automaticamente:

1. EC2 inicia com Instance Profile associado
2. Aplicação chama SDK sem credenciais:
   boto3.client('s3')  ← sem aws_access_key_id
3. SDK verifica a cadeia de credenciais:
   a. Variáveis de ambiente?  → não
   b. ~/.aws/credentials?     → não
   c. Instance Metadata?      → sim!
4. SDK busca: GET http://169.254.169.254/latest/meta-data/iam/security-credentials/
5. Retorna: AccessKeyId (ASIA...), SecretAccessKey, SessionToken, Expiration
6. SDK usa as credenciais temporárias para a chamada S3
7. SDK monitora a expiração e renova automaticamente

Todo isso: transparente para o desenvolvedor.
O código não precisa saber de credenciais.

Cadeia de credenciais completa (por ordem de verificação):
  1. Variáveis de ambiente (AWS_ACCESS_KEY_ID, etc.)
  2. Arquivo de credenciais (~/.aws/credentials)
  3. AWS config file (~/.aws/config)
  4. Container credentials (ECS task role)
  5. Instance Profile (EC2 role)
  6. IAM Identity Center SSO
```

## Comparativo final: User vs Group vs Role

```
                  │ IAM USER    │ IAM GROUP   │ IAM ROLE
──────────────────┼─────────────┼─────────────┼──────────────────
Tipo de identidade│ Permanente  │ Organização │ Temporária
Faz chamadas API? │ Sim         │ NÃO         │ Sim (assumida)
Credenciais       │ Permanentes │ N/A         │ Temporárias (STS)
Expira            │ Nunca       │ N/A         │ 15min a 12h
Uso para serviços │ ❌ Não      │ N/A         │ ✓ Padrão
Uso para humanos  │ ✓ Possível  │ Organiza    │ ✓ Preferido (SSO)
Uso para CI/CD    │ ❌ Evitar   │ N/A         │ ✓ OIDC Roles
Cross-account     │ ❌ Não      │ N/A         │ ✓ Trust Policy
MFA suportado     │ Sim         │ N/A         │ Via condição
Rotação automática│ NÃO (manual)│ N/A         │ ✓ Automática (STS)
```

## Recomendações práticas

```
1. Prefira IAM Identity Center (SSO) a IAM Users diretos:
   → Usuários gerenciados no diretório corporativo (AD, Google Workspace)
   → Acesso temporário via sessões (não access keys permanentes)
   → MFA gerenciado pelo IdP existente
   → Melhor auditoria e revogação imediata

2. Para aplicações em AWS: sempre use Roles (nunca access keys):
   EC2 → Instance Profile
   Lambda → Execution Role
   ECS → Task Role
   → Zero configuração de credenciais no código

3. Para CI/CD externo: OIDC Roles (nunca access keys):
   GitHub Actions, GitLab CI, CircleCI → OIDC + Role
   → Credenciais temporárias por job, zero segredos no CI

4. Quando IAM Users são necessários:
   → Sistemas legados sem suporte a roles
   → Acesso de terceiros sem IdP compatível
   → MFA obrigatório + rotação de keys a cada 90 dias

5. Grupos como organização:
   → Sempre use grupos para aplicar políticas a humanos
   → Nunca aplique política diretamente ao usuário (exceto políticas específicas)
   → Facilita onboarding, offboarding e mudanças de função
```

## 🧩 Quiz de Fixação

1. Uma aplicação Node.js rodando em EC2 precisa ler arquivos do S3. O desenvolvedor está pensando em criar um IAM User com access keys e configurar como variável de ambiente na EC2. Por que isso é problemático e qual é a abordagem correta?
2. Um usuário IAM está no grupo "Developers" (com permissão de S3 read) e também no grupo "DataEngineering" (com permissão de S3 full access). Qual é a permissão efetiva do usuário no S3, e por que?
3. Por que credenciais emitidas pelo STS para uma IAM Role são intrinsecamente mais seguras que access keys permanentes de um IAM User, mesmo que ambas sejam vazadas acidentalmente?

**Respostas:**
1) Problemas com access keys em variáveis de ambiente: (1) As credenciais ficam visíveis no ambiente do processo — qualquer código que rode na EC2 (inclusive injeção via SSRF) pode lê-las com `os.environ`; (2) São permanentes — se vazarem, ficam ativas até alguém manualmente deletar ou desativar; (3) Não há rotação automática — se o desenvolvedor esquecer de rotar, ficam ativas indefinidamente; (4) Harder to audit — não é claro de qual instância específica uma chamada veio. A abordagem correta: criar uma IAM Role com permission policy que permite apenas as ações necessárias no S3 (ex: `s3:GetObject` no bucket específico), atribuí-la como Instance Profile da EC2. O SDK Node.js (`aws-sdk`) automaticamente busca credenciais via Instance Metadata Service — zero configuração no código, credenciais temporárias renovadas automaticamente a cada hora.
2) A permissão efetiva é S3 full access. IAM usa avaliação aditiva para múltiplos grupos: as permissões de todos os grupos são unidas (union), não intersectadas. O usuário herda S3 read do grupo Developers E S3 full access do DataEngineering — a permissão mais ampla prevalece. Isso tem implicação importante: para restringir um usuário que está em múltiplos grupos, um Deny explícito é necessário (Deny sempre prevalece sobre Allow em IAM), pois adicionar permissão em um grupo não "cancela" permissão de outro grupo.
3) As credenciais STS têm expiração embutida — tipicamente 1 hora (configurável de 15min a 12h dependendo do tipo de role). Se vazarem, são inúteis após a expiração sem que o atacante tenha como renová-las (precisaria ser a identidade que originalmente assumiu a role). Access keys permanentes, se vazadas, ficam ativas indefinidamente até detecção e revogação manual — que pode levar horas ou dias. Além disso, as credenciais STS incluem um SessionToken que prova que são temporárias e rastreia a sessão de origem, tornando mais fácil identificar de qual role vieram e invalidar especificamente aquela sessão sem afetar outras.
