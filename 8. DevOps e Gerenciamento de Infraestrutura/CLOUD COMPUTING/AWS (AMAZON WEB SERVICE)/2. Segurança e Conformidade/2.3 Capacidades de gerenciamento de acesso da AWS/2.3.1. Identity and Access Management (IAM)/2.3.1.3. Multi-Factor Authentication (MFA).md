### Multi-Factor Authentication (MFA) — a defesa mais efetiva contra credenciais comprometidas

MFA (Autenticação Multifator) exige que o usuário prove sua identidade com dois ou mais fatores independentes: algo que ele sabe (senha), algo que ele tem (dispositivo MFA) e, opcionalmente, algo que ele é (biometria). Na AWS, MFA é a proteção mais impactante contra comprometimento de credenciais — estudos da Microsoft e Google mostram que MFA bloqueia mais de 99% dos ataques automatizados de força bruta e phishing de credenciais. É simples de implementar e deveria ser o primeiro controle habilitado em qualquer conta AWS.

---

## Por que MFA é transformador

```
Ataque sem MFA:
  Atacante obtém: usuario@empresa.com + Senha123@
  → Faz login no console AWS
  → Acesso completo à conta
  
  Como obter: phishing, breach de outro serviço
              (mesmo usuário e senha em vários sistemas),
              keylogger, vazamento de arquivo .env

Ataque com MFA:
  Atacante obtém: usuario@empresa.com + Senha123@
  → Tenta login no console AWS
  → Pedido de código MFA
  → Atacante não tem o dispositivo físico
  → Login bloqueado

Eficácia do MFA (Google/Microsoft studies):
  Contra credential stuffing: bloqueia 99%+ dos ataques
  Contra phishing automatizado: bloqueia 96%+ dos ataques
  Contra força bruta: bloqueia 100% (código muda a cada 30s)

O que o MFA NÃO protege:
  → Atacante com acesso físico ao dispositivo MFA
  → Ataques de SIM swapping (SMS MFA)
  → TOTP phishing em tempo real (atacante age no segundo que código é inserido)
  → Por isso: hardware MFA > FIDO2 > TOTP virtual > SMS
```

## Tipos de MFA suportados pela AWS

### 1. Virtual MFA (TOTP — Time-based One-Time Password)

```
Como funciona:
  → App no smartphone gera código de 6 dígitos
  → Código muda a cada 30 segundos (TOTP — RFC 6238)
  → Baseado em segredo compartilhado (QR code na configuração)
  
Apps compatíveis:
  ├── Google Authenticator (Android/iOS)
  ├── Microsoft Authenticator (Android/iOS)
  ├── Authy (multi-device, recomendado para backup)
  ├── 1Password (integrado ao gerenciador de senhas)
  └── Qualquer app compatível com TOTP/RFC 6238

Configuração no console AWS:
  IAM → Users → [usuário] → Security credentials
  → Assign MFA device → Virtual MFA device
  → Escanear QR code com o app
  → Inserir dois códigos consecutivos (validação)
  → MFA ativo

Vantagens:
  ├── Gratuito (app no smartphone)
  ├── Funciona offline (não precisa de rede)
  └── Fácil de usar

Limitações:
  ├── Vulnerável a phishing em tempo real (real-time phishing attack)
  ├── Dispositivo pode ser perdido/roubado
  └── Não vinculado ao domínio (qualquer dispositivo pode usar o segredo)
```

### 2. Hardware MFA (YubiKey e outros)

```
Como funciona:
  → Dispositivo físico (USB, NFC, Bluetooth)
  → Dois tipos de suporte na AWS:
    a. TOTP via hardware (YubiKey com OATH)
    b. FIDO2/WebAuthn (mais seguro — ver próxima seção)
  
  Para TOTP hardware:
  → YubiKey usa o protocolo OATH-TOTP
  → Funciona como app TOTP mas em hardware dedicado
  → Toca o YubiKey → gera o código automaticamente

Dispositivos certificados pela AWS:
  ├── YubiKey 5 Series (Yubico)
  ├── Feitian FIDO (série de hardware tokens)
  └── Qualquer dispositivo compatível com TOTP/RFC 6238

Vantagens sobre Virtual MFA:
  ├── Dispositivo físico dedicado (mais difícil de comprometer)
  ├── Não compartilha recursos com o smartphone (isolado)
  └── Melhor para contas de alta segurança (root, admin)

Limitações:
  ├── Custo (~$50-$100 por dispositivo)
  ├── Pode ser perdido (ter backup é essencial)
  └── TOTP hardware ainda vulnerável a real-time phishing
```

### 3. FIDO2 / WebAuthn (o mais seguro)

```
Como funciona:
  → Protocolo de autenticação baseado em criptografia de chave pública
  → Dispositivo gera par de chaves: pública (salva na AWS) + privada (no device)
  → Na autenticação: AWS envia challenge → device assina com chave privada
  → Chave privada NUNCA sai do dispositivo
  
  Dispositivos suportados:
  ├── YubiKey 5 Series (FIDO2/WebAuthn nativo)
  ├── Apple Touch ID / Face ID (plataforma passkey)
  ├── Windows Hello (biometria integrada ao Windows)
  ├── Google Titan Security Key
  └── Dispositivos passkey compatíveis (Android, iOS)

Por que FIDO2 é mais seguro que TOTP:
  
  Ataque TOTP (real-time phishing):
  1. Atacante cria site falso idêntico ao console AWS
  2. Usuário digita usuario + senha + código TOTP
  3. Atacante usa as credenciais imediatamente (30 segundos)
  4. Acesso comprometido
  
  FIDO2 é imune a esse ataque:
  1. Atacante cria site falso
  2. Usuário tenta autenticar
  3. Dispositivo FIDO2 verifica o domínio da requisição
  4. Domínio fake ≠ domínio registrado → autenticação NEGADA
  5. Nenhum código para interceptar — não há código!
  
  A chave privada nunca é transmitida — apenas a assinatura do challenge.
  O device verifica que está respondendo ao domínio correto.

Configuração na AWS:
  IAM → Users → Security credentials
  → Assign MFA device → FIDO security key
  → Inserir dispositivo FIDO2 → autenticar
  → MFA registrado com origem de domínio vinculada

Recomendação: usar FIDO2 para contas de alta sensibilidade
  Root account: FIDO2 hardware key
  Admin IAM users: FIDO2 hardware key
  Usuários regulares: Virtual MFA (TOTP) com Authy ou 1Password
```

### 4. SMS MFA (não recomendado, não disponível para IAM)

```
A AWS não oferece SMS como MFA para contas IAM.
(Era disponível historicamente mas foi removido por segurança)

Por que SMS é fraco:
  ├── SIM swapping: atacante convence operadora a transferir seu número
  ├── SS7 vulnerabilities: protocolo de telefonia pode ser interceptado
  ├── Malware no celular: captura SMS antes de você ver
  └── Social engineering: phishing de código por telefone

Se você usa Cognito para usuários da aplicação:
  Cognito suporta SMS MFA para usuários finais
  Mas implemente TOTP como opção preferencial
```

## Onde habilitar MFA na AWS

### Conta Root — prioridade máxima

```
A conta root tem acesso irrestrito e irreversível.
MFA na root é a primeira coisa a fazer em qualquer conta AWS.

Configuração:
  Console → [menu da conta] → Security credentials
  → Multi-factor authentication (MFA)
  → Assign MFA device
  
  Recomendado: FIDO2 hardware key dedicado para root
               Armazenado em local seguro (cofre, não na mesa)
  
  Dica: se usar hardware key para root, ter TOTP como backup
        (AWS permite até 8 dispositivos MFA por identidade)

Boas práticas para conta root:
  ├── MFA obrigatório (hardware key)
  ├── Não criar access keys para root
  ├── Email da conta root: caixa monitorada, não pessoal
  ├── Usar root apenas quando absolutamente necessário
  └── Qualquer uso de root: gera alerta CloudWatch
      (EventBridge rule + SNS → notifica toda a equipe)
```

### IAM Users — todos que acessam o console

```
Política de MFA obrigatório via IAM:

Estratégia: permitir que usuários sem MFA apenas gerenciem
            seu próprio dispositivo MFA (nada mais)

Policy: RequireMFAPolicy (anexar a todos os grupos/usuários)

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowViewAccountInfo",
      "Effect": "Allow",
      "Action": ["iam:GetAccountPasswordPolicy", "iam:ListVirtualMFADevices"],
      "Resource": "*"
    },
    {
      "Sid": "AllowManageOwnMFA",
      "Effect": "Allow",
      "Action": [
        "iam:CreateVirtualMFADevice",
        "iam:EnableMFADevice",
        "iam:GetUser",
        "iam:ListMFADevices",
        "iam:ResyncMFADevice"
      ],
      "Resource": [
        "arn:aws:iam::*:mfa/${aws:username}",
        "arn:aws:iam::*:user/${aws:username}"
      ]
    },
    {
      "Sid": "DenyAllExceptMFAManagementWithoutMFA",
      "Effect": "Deny",
      "NotAction": [
        "iam:CreateVirtualMFADevice",
        "iam:EnableMFADevice",
        "iam:GetUser",
        "iam:ListMFADevices",
        "iam:ResyncMFADevice",
        "sts:GetSessionToken"
      ],
      "Resource": "*",
      "Condition": {
        "BoolIfExists": {
          "aws:MultiFactorAuthPresent": "false"
        }
      }
    }
  ]
}

Resultado:
  Usuário sem MFA configurado:
  → Pode apenas configurar seu dispositivo MFA
  → Qualquer outra ação: DENIED
  → Após configurar MFA: acesso completo conforme políticas do grupo
```

### MFA para operações sensíveis com Conditions

```
Mesmo com MFA habilitado no login, exigir MFA
especificamente para operações de alto impacto:

Caso 1: Exigir MFA para deletar recursos:
{
  "Sid": "DenyDeleteWithoutMFA",
  "Effect": "Deny",
  "Action": [
    "s3:DeleteObject",
    "s3:DeleteBucket",
    "ec2:TerminateInstances",
    "rds:DeleteDBInstance",
    "dynamodb:DeleteTable"
  ],
  "Resource": "*",
  "Condition": {
    "BoolIfExists": {
      "aws:MultiFactorAuthPresent": "false"
    }
  }
}
→ Para deletar qualquer recurso: sessão deve ter MFA ativo
→ Se sessão de 8h sem MFA: delete bloqueado mesmo que sessão seja válida

Caso 2: Exigir MFA recente para operações financeiras:
{
  "Sid": "RequireRecentMFA",
  "Effect": "Deny",
  "Action": ["aws-portal:*", "budgets:*"],
  "Resource": "*",
  "Condition": {
    "NumericGreaterThan": {
      "aws:MultiFactorAuthAge": "300"  ← MFA deve ter sido usado nos últimos 5 minutos
    }
  }
}
→ Para acessar billing: autenticou com MFA há menos de 5 minutos
→ Mesmo com sessão ativa de 8h: re-autentica com MFA para billing

aws:MultiFactorAuthAge vs aws:MultiFactorAuthPresent:
  Present: MFA foi usado na sessão (qualquer hora atrás)
  Age:     MFA foi usado há X segundos (controle temporal preciso)
```

## MFA e AWS CLI — acesso programático

```
Problema: MFA é para console login, mas CLI usa access keys
Como usar MFA com CLI?

Solução: STS GetSessionToken com MFA

# Passo 1: obter token MFA do app (ex: 123456)
# Passo 2: chamar STS com as credenciais permanentes + token MFA

aws sts get-session-token \
  --serial-number arn:aws:iam::123456789:mfa/joao.silva \
  --token-code 123456 \
  --duration-seconds 3600

# Retorna credenciais temporárias COM MFA validado:
{
  "Credentials": {
    "AccessKeyId": "ASIAEXAMPLE...",
    "SecretAccessKey": "wJalrXUtnFEMI...",
    "SessionToken": "AQoXnyc4Pi...",
    "Expiration": "2024-01-15T14:00:00Z"
  }
}

# Passo 3: configurar as credenciais temporárias
export AWS_ACCESS_KEY_ID=ASIAEXAMPLE...
export AWS_SECRET_ACCESS_KEY=wJalrXUtnFEMI...
export AWS_SESSION_TOKEN=AQoXnyc4Pi...

# Agora as chamadas CLI têm MFA validado
aws s3 rm s3://bucket-critico/arquivo.txt  ← funciona (MFA presente)

Script helper (~/.aws/mfa.sh):
#!/bin/bash
MFA_ARN="arn:aws:iam::123456789:mfa/joao.silva"
read -p "MFA Token: " TOKEN
CREDS=$(aws sts get-session-token \
  --serial-number $MFA_ARN \
  --token-code $TOKEN \
  --output json)
export AWS_ACCESS_KEY_ID=$(echo $CREDS | jq -r '.Credentials.AccessKeyId')
export AWS_SECRET_ACCESS_KEY=$(echo $CREDS | jq -r '.Credentials.SecretAccessKey')
export AWS_SESSION_TOKEN=$(echo $CREDS | jq -r '.Credentials.SessionToken')
echo "Credenciais MFA ativas por 1 hora"
```

## MFA em AWS Organizations e IAM Identity Center

```
Com IAM Identity Center (SSO):
  MFA gerenciado pelo Identity Provider (IdP):
  ├── Microsoft Entra ID (Azure AD): MFA configurado no IdP
  ├── Okta: MFA configurado no Okta
  ├── Google Workspace: MFA configurado no Google
  └── IAM Identity Center nativo: MFA configurado no próprio IdC
  
  Benefício: MFA centralizado, política uniforme em todas as contas
  
  Política de MFA no IAM Identity Center:
  Settings → Authentication → MFA
  ├── Context-aware (MFA baseado em risk score) → básico
  ├── Always-on MFA (sempre exige MFA) → recomendado para produção
  └── MFA types: TOTP + FIDO2

SCP de proteção contra desabilitar MFA:
{
  "Effect": "Deny",
  "Action": [
    "iam:DeactivateMFADevice",
    "iam:DeleteVirtualMFADevice"
  ],
  "Resource": "*",
  "Condition": {
    "ArnNotLike": {
      "aws:PrincipalArn": "arn:aws:iam::*:role/SecurityAdminRole"
    }
  }
}
→ Apenas o Security Admin pode desabilitar MFA de outros
→ Previne que usuário remova seu próprio MFA para bypass
```

## Plano de recuperação — MFA perdido

```
O que fazer se o dispositivo MFA for perdido:

Usuário regular perde o smartphone:
  1. Contatar Security/IT team
  2. Admin desativa o dispositivo MFA antigo:
     aws iam deactivate-mfa-device \
       --user-name joao.silva \
       --serial-number arn:aws:iam::123:mfa/joao.silva
  3. Admin pode configurar MFA temporário ou usar
     aws iam create-login-profile com senha temporária
  4. Usuário reconfigura MFA no novo dispositivo

Conta root perde o hardware key:
  1. Usar o segundo dispositivo MFA de backup (se configurado)
  2. Se não houver backup: processo de recuperação de conta AWS
     → Verificação via email + telefone cadastrado + documentos
     → Pode levar dias — por isso backup MFA é essencial!

Prevenção:
  ├── Configurar 2+ dispositivos MFA na conta root
  ├── Usar Authy (multi-device) ou 1Password para TOTP
  ├── Armazenar QR code inicial em local seguro (cofre)
  └── Testar recuperação antes de precisar dela em emergência
```

## 🧩 Quiz de Fixação

1. Por que FIDO2/WebAuthn é imune a ataques de real-time phishing, enquanto TOTP (Google Authenticator) não é? Explique o mecanismo técnico que torna isso possível.
2. Um usuário IAM tem MFA configurado e faz login no console com MFA. Mais tarde, tenta deletar um bucket S3 de produção, mas recebe "Access Denied" mesmo tendo permissão de `s3:DeleteBucket`. Qual é a explicação provável e como resolver legitimamente?
3. Uma empresa quer garantir que nenhum usuário IAM acesse o console AWS sem MFA, mas não quer bloquear completamente quem ainda não configurou o MFA (para dar chance de configurar). Como implementar isso com IAM policies?

**Respostas:**
1) TOTP funciona transmitindo um código de 6 dígitos que é válido por 30 segundos. Em um ataque de real-time phishing: o atacante cria um site fake idêntico ao console AWS; o usuário insere sua senha e o código TOTP no site fake; o atacante usa imediatamente essas credenciais (tem ~30 segundos de janela); o ataque funciona. FIDO2/WebAuthn usa criptografia de chave pública: ao registrar, o dispositivo gera um par de chaves e armazena a chave privada internamente com o domínio registrado (ex: signin.aws.amazon.com). Na autenticação, o servidor envia um "challenge" único; o dispositivo verifica que o domínio da requisição corresponde ao domínio registrado e, se sim, assina o challenge com a chave privada. Em um site fake (domínio diferente), o dispositivo NEGA a autenticação porque o domínio não corresponde — não há código para interceptar, e a chave privada nunca é transmitida.
2) A explicação provável é que existe uma IAM policy com Condition `"BoolIfExists": {"aws:MultiFactorAuthPresent": "false"}` → `Deny s3:DeleteBucket`. Mesmo que o usuário tenha feito login com MFA, se a sessão atual foi obtida via `sts:AssumeRole` ou se o token foi renovado de forma que o atributo `aws:MultiFactorAuthPresent` ficou como `false` (ou ausente), o Deny se aplica. Para resolver legitimamente: o usuário precisa obter uma sessão onde MFA está explicitamente presente — fazer login no console novamente com MFA, ou usar `aws sts get-session-token --serial-number [arn-mfa] --token-code [código]` via CLI para obter credenciais temporárias com MFA validado, e então executar a operação de delete.
3) Implementar a IAM policy de "MFA self-enrollment": Política que permite (1) visualizar informações básicas da conta, (2) gerenciar apenas o próprio dispositivo MFA, e (3) nega TUDO mais quando MFA não está presente. Específicamente usando `NotAction` com as ações de gerenciamento de MFA + `Deny` condicional em `"BoolIfExists": {"aws:MultiFactorAuthPresent": "false"}`. Usuário sem MFA: consegue acessar o console, vê que as permissões são limitadas, vai direto para IAM → Security credentials → configura seu dispositivo MFA, então todas as outras permissões do grupo se tornam acessíveis. Usuário com MFA configurado e autenticado: acesso completo conforme políticas do grupo. O truque é usar `NotAction` (inverso de Action) para listar as poucas ações que são permitidas sem MFA, e negar tudo o mais.
