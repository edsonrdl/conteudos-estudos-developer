### Políticas IAM — definindo o que cada identidade pode fazer

Uma política IAM é um documento JSON que define permissões: quais ações são permitidas ou negadas em quais recursos sob quais condições. É o mecanismo central de controle de acesso da AWS — toda decisão de "pode ou não pode" passa pela avaliação de políticas. Entender os tipos de políticas, como elas se combinam e como o motor de avaliação toma decisões é fundamental para construir ambientes seguros e auditáveis.

---

## Os tipos de políticas IAM

```
IDENTITY-BASED POLICIES:
  → Anexadas a identidades (users, groups, roles)
  → Controlam o que a identidade pode fazer
  → "João pode ler do S3"

RESOURCE-BASED POLICIES:
  → Anexadas a recursos (S3 bucket, SQS queue, KMS key, etc.)
  → Controlam quem pode acessar o recurso
  → "Este bucket pode ser acessado pela conta X"

PERMISSION BOUNDARIES:
  → Limite máximo de permissões de uma identidade
  → Não concede permissão — apenas limita o teto
  → "Esta role nunca poderá ter mais que S3 e DynamoDB"

SERVICE CONTROL POLICIES (SCPs):
  → Aplicadas a contas/OUs no AWS Organizations
  → Limite organizacional máximo
  → "Nenhuma conta desta OU pode criar recursos fora de us-east-1"

SESSION POLICIES:
  → Passadas ao assumir uma role temporariamente
  → Restringe ainda mais o escopo da sessão
  → "Nesta sessão, apenas acesso de leitura ao S3"

AWS MANAGED POLICIES:
  → Criadas e mantidas pela AWS
  → Ex: AdministratorAccess, ReadOnlyAccess, AmazonS3FullAccess
  → Atualizadas automaticamente quando AWS adiciona novos serviços

CUSTOMER MANAGED POLICIES:
  → Criadas e mantidas por você
  → Reutilizáveis em múltiplas identidades
  → Versionadas (até 5 versões, uma ativa por vez)

INLINE POLICIES:
  → Embutidas diretamente em uma identidade específica
  → Não reutilizáveis
  → Deletadas junto com a identidade
  → Usar apenas para permissões únicas e específicas
```

## Anatomia de uma policy — os elementos obrigatórios

```json
{
  "Version": "2012-10-17",     ← sempre este valor (versão da linguagem)
  "Statement": [               ← array de declarações de permissão
    {
      "Sid": "PermitirLeituraNoBucket",  ← identificador (opcional, mas recomendado)
      "Effect": "Allow",                  ← Allow ou Deny
      "Action": [                         ← quais operações
        "s3:GetObject",
        "s3:ListBucket"
      ],
      "Resource": [                       ← em quais recursos
        "arn:aws:s3:::meu-bucket",
        "arn:aws:s3:::meu-bucket/*"
      ],
      "Condition": {                      ← quando (opcional)
        "StringEquals": {
          "s3:prefix": ["uploads/"]
        }
      }
    }
  ]
}
```

### Elemento Effect: Allow vs Deny

```
Allow: concede permissão explicitamente
Deny:  nega permissão explicitamente (sobrepõe qualquer Allow)

Regra fundamental: Deny explícito SEMPRE vence qualquer Allow.

Cenário:
  Policy A (em grupo): Allow s3:DeleteObject em qualquer bucket
  Policy B (inline):   Deny s3:DeleteObject em bucket-prod
  
  Resultado: João pode deletar em qualquer bucket EXCETO bucket-prod.
  O Deny de B sobrepõe o Allow de A para aquele recurso específico.
```

### Elemento Action: granularidade de operações

```
Ação específica (melhor prática):
  "Action": ["s3:GetObject"]

Wildcard por serviço (use com cuidado):
  "Action": ["s3:Get*"]    ← todas as ações Get do S3
  "Action": ["s3:*"]       ← TODAS as ações do S3 (amplo)

Múltiplos serviços (quando necessário):
  "Action": [
    "ec2:DescribeInstances",
    "cloudwatch:GetMetricData",
    "logs:GetLogEvents"
  ]

Notação correta:
  "serviço:Ação"
  s3:GetObject, ec2:RunInstances, rds:DescribeDBInstances

Ações comuns por serviço:
  S3:        GetObject, PutObject, DeleteObject, ListBucket
  EC2:       RunInstances, TerminateInstances, DescribeInstances
  IAM:       CreateUser, AttachRolePolicy, PassRole
  Lambda:    InvokeFunction, CreateFunction, UpdateFunctionCode
  DynamoDB:  GetItem, PutItem, Query, Scan, DeleteItem
```

### Elemento Resource: especificidade é segurança

```
Regra: quanto mais específico o Resource, menor o blast radius.

ARN format: arn:partition:service:region:account-id:resource

Exemplos progressivamente mais específicos:

Muito amplo (evitar):
  "Resource": "*"                                    ← tudo na AWS

Serviço todo (use com cuidado):
  "Resource": "arn:aws:s3:::*"                       ← todos os buckets

Recurso específico:
  "Resource": "arn:aws:s3:::bucket-producao"         ← um bucket

Objeto específico dentro do bucket:
  "Resource": "arn:aws:s3:::bucket-prod/uploads/*"   ← objetos em uploads/

Com variável de contexto (dinâmico):
  "Resource": "arn:aws:s3:::empresa-${aws:username}" ← bucket do próprio usuário

DynamoDB — tabela específica:
  "Resource": "arn:aws:dynamodb:us-east-1:123456789:table/Pedidos"

DynamoDB — tabela e seus índices:
  "Resource": [
    "arn:aws:dynamodb:us-east-1:123456789:table/Pedidos",
    "arn:aws:dynamodb:us-east-1:123456789:table/Pedidos/index/*"
  ]
```

## O motor de avaliação de políticas — como a AWS decide

```
Quando uma requisição chega, a AWS executa este algoritmo:

PASSO 1: Existe um Deny explícito em QUALQUER política aplicável?
  → Sim: DENIED (fim da avaliação)
  → Não: continue

PASSO 2: Existe um Allow em uma SCP (se usar Organizations)?
  → Não: DENIED (SCPs devem permitir explicitamente)
  → Sim: continue

PASSO 3: Existe um Allow em Resource-based Policy que
         também permite o principal?
  → Sim (cross-account): ALLOWED (fim)
  → Continue para identity-based

PASSO 4: Existe um Allow em Permission Boundary?
  → Boundary existe E não permite: DENIED
  → Continue

PASSO 5: Existe um Allow em Session Policy (se assumiu role)?
  → Session policy existe E não permite: DENIED
  → Continue

PASSO 6: Existe um Allow em Identity-based Policy?
  → Sim: ALLOWED
  → Não: DENIED (default implícito)

Resumindo:
  Default é DENY (sem políticas = sem acesso)
  Um Allow é necessário para acesso
  Um Deny explícito sobrepõe qualquer Allow
```

### Diagrama do motor de avaliação

```
Requisição chega
       │
       ▼
[Deny explícito em qualquer política?] ──Sim──► DENIED
       │ Não
       ▼
[SCP bloqueia a ação?] ──Sim──► DENIED
       │ Não
       ▼
[Resource-based policy permite diretamente?] ──Sim──► ALLOWED
       │ Não
       ▼
[Permission Boundary impede?] ──Sim──► DENIED
       │ Não
       ▼
[Session Policy impede?] ──Sim──► DENIED
       │ Não
       ▼
[Identity-based policy permite?] ──Sim──► ALLOWED
       │ Não
       ▼
     DENIED (implicit deny)
```

### Exemplo prático de avaliação

```
Cenário: João (membro do grupo Developers) tenta deletar
         objeto no bucket bucket-prod

Políticas aplicáveis:
  SCP (Organizations): Allow * para us-east-1 (não bloqueia)
  Group Policy (Developers): Allow s3:* em arn:aws:s3:::*
  Bucket Policy (bucket-prod): Deny s3:DeleteObject para todos
  Permission Boundary: Allow s3:GetObject, s3:PutObject (não inclui Delete)
  Session Policy: não aplicável (João usa IAM user direto)

Avaliação:
  Passo 1: Deny explícito? Bucket Policy tem Deny s3:DeleteObject → DENIED
  
  Resultado: DENIED (mesmo que a Group Policy permita s3:*)
  O Deny da bucket policy vence.

Cenário 2: João tenta fazer PutObject no mesmo bucket
  Passo 1: Deny explícito? Bucket Policy: Deny apenas para DeleteObject → Não
  Passo 2: SCP bloqueia? Não
  Passo 3: Resource-based policy (bucket policy) permite? Não explicitamente
  Passo 4: Permission Boundary impede? Boundary permite s3:PutObject → Não
  Passo 5: Session Policy: N/A
  Passo 6: Identity-based (Group Policy): Allow s3:* → ALLOWED
  
  Resultado: ALLOWED
```

## Identity-based vs Resource-based — qual usar?

```
IDENTITY-BASED (mais comum):
  Uso: controlar o que uma identidade pode fazer
  Onde: na role, user ou group
  
  Caso de uso:
  "Qualquer instância EC2 com esta role pode ler do S3"
  → Role tem a policy, qualquer EC2 que assume a role herda

RESOURCE-BASED (complementar):
  Uso: controlar quem acessa um recurso específico
       especialmente cross-account
  Onde: no recurso (S3, SQS, Lambda, KMS, etc.)
  
  Caso de uso:
  "Este bucket S3 pode ser acessado pela conta de produção
   E pela conta de staging"
  
  Bucket Policy:
  {
    "Statement": [{
      "Effect": "Allow",
      "Principal": {
        "AWS": [
          "arn:aws:iam::conta-prod:root",
          "arn:aws:iam::conta-staging:root"
        ]
      },
      "Action": ["s3:GetObject"],
      "Resource": "arn:aws:s3:::bucket-compartilhado/*"
    }]
  }
  
  Vantagem do resource-based para cross-account:
  → Identidade da conta A assume a policy de recurso da conta B
  → Não precisa de identity-based policy na conta A para o recurso
  
  Serviços que suportam resource-based policies:
  S3, SQS, SNS, Lambda, KMS, Secrets Manager, ECR, CloudWatch Logs...
  EC2 e RDS NÃO têm resource-based policies (use Security Groups)
```

## Conditions — poder além do básico

```
Conditions permitem criar políticas contextuais sofisticadas:

Operadores de condição por tipo de dado:
  String:   StringEquals, StringNotEquals, StringLike, StringNotLike
  Numérico: NumericEquals, NumericGreaterThan, NumericLessThan
  Data:     DateEquals, DateGreaterThan, DateLessThan
  Bool:     Bool
  ARN:      ArnEquals, ArnLike, ArnNotEquals
  IP:       IpAddress, NotIpAddress

Chaves de condição mais usadas:

aws:RequestedRegion — restringir por região:
  "Condition": {
    "StringEquals": {"aws:RequestedRegion": "us-east-1"}
  }

aws:MultiFactorAuthPresent — exigir MFA:
  "Condition": {
    "Bool": {"aws:MultiFactorAuthPresent": "true"}
  }
  Uso: operações sensíveis (deletar recursos, modificar IAM)
  
  Política completa: permitir tudo mas exigir MFA para delete:
  Statement 1: Allow * (acesso geral)
  Statement 2: Deny *:Delete* sem MFA (proteção extra)

aws:SourceIp — restringir por IP:
  "Condition": {
    "IpAddress": {"aws:SourceIp": "203.0.113.0/24"}
  }
  Uso: acesso apenas da rede corporativa

aws:PrincipalTag / aws:ResourceTag — ABAC (Attribute-Based Access):
  "Condition": {
    "StringEquals": {
      "aws:ResourceTag/Environment": "${aws:PrincipalTag/Environment}"
    }
  }
  → Time de dev só acessa recursos tagueados como dev
  → Time de prod só acessa recursos tagueados como prod
  → Escala sem criar políticas por environment

s3:prefix — restringir por prefixo no S3:
  "Condition": {
    "StringLike": {"s3:prefix": "home/${aws:username}/*"}
  }
  → Cada usuário acessa apenas sua própria "pasta" no bucket

kms:ViaService — permitir KMS apenas por serviço específico:
  "Condition": {
    "StringEquals": {"kms:ViaService": "s3.us-east-1.amazonaws.com"}
  }
  → Chave KMS só pode ser usada via S3, não diretamente
```

## ABAC — Attribute-Based Access Control

```
ABAC escala IAM usando tags em vez de policies por recurso:

RBAC tradicional (role-based):
  Novo projeto → criar nova policy → anexar à role certa
  10 projetos × 5 ambientes = 50 políticas para gerenciar

ABAC com tags:
  Uma política que usa tags para controle dinâmico:
  
  {
    "Effect": "Allow",
    "Action": ["ec2:StartInstances", "ec2:StopInstances"],
    "Resource": "*",
    "Condition": {
      "StringEquals": {
        "ec2:ResourceTag/Project": "${aws:PrincipalTag/Project}",
        "ec2:ResourceTag/Environment": "${aws:PrincipalTag/Environment}"
      }
    }
  }
  
  João tem tags: Project=checkout, Environment=dev
  → Pode iniciar/parar EC2 com tags Project=checkout E Environment=dev
  → NÃO pode tocar EC2 de outros projetos ou de prod
  
  Novo projeto "search" adicionado:
  → Tag EC2 com Project=search
  → Tag role do time de search com Project=search
  → Funciona automaticamente, sem nova policy!

Implementação prática:
  1. Taggear todos os recursos consistentemente
  2. Taggear IAM users/roles com os atributos relevantes
  3. Política centralizada usa ${aws:PrincipalTag/X}
  4. Controle é automático baseado nas tags
```

## Boas práticas de políticas IAM

```
1. Managed Policies > Inline Policies:
   ✓ Customer managed: reutilizável, versionada, auditável
   ✗ Inline: acoplada ao user/role, difícil de auditar

2. Nunca usar "Resource": "*" com Actions sensíveis:
   ✗ Allow iam:* em * → qualquer operação IAM em qualquer recurso
   ✓ Allow iam:GetRole em arn específico

3. Validar antes de aplicar:
   AWS Console: policy validator inline
   CLI: aws iam simulate-principal-policy
   IAM Access Analyzer: policy validation

4. Testar com simulate-principal-policy:
   aws iam simulate-principal-policy \
     --policy-source-arn arn:aws:iam::123:role/AppRole \
     --action-names s3:GetObject s3:DeleteObject \
     --resource-arns arn:aws:s3:::bucket-prod/file.txt
   
   Retorna: "allowed" ou "denied" com o motivo

5. Política mais restritiva primeiro:
   Quando há múltiplas policies, verificar sobreposições
   IAM Access Analyzer identifica conflitos

6. Conditions em operações destrutivas:
   Qualquer Delete, Terminate, Drop: exigir MFA na condition
```

## 🧩 Quiz de Fixação

1. Uma role tem duas políticas: Policy A permite `s3:*` em `*`, e Policy B nega `s3:DeleteObject` em `arn:aws:s3:::bucket-critico/*`. Uma Lambda com essa role tenta deletar um arquivo em `bucket-critico`. Qual é o resultado e qual regra do motor de avaliação determina isso?
2. Um desenvolvedor cria uma policy com `"Action": "s3:*", "Resource": "*"` e defende que "é mais fácil de manter". Quais são os três riscos específicos dessa política e como refatorá-la para seguir o menor privilégio?
3. O que é ABAC e por que escala melhor que RBAC em organizações com muitos times e projetos? Dê um exemplo concreto de como adicionar um novo projeto sem criar novas policies com ABAC.

**Respostas:**
1) Resultado: DENIED. O motor de avaliação IAM verifica primeiro se há Deny explícito em qualquer política aplicável — Policy B tem `Deny s3:DeleteObject` para `bucket-critico/*`, que é exatamente o recurso e ação sendo tentados. A regra é: Deny explícito sempre vence qualquer Allow, independente de quantas outras políticas permitam a ação. Mesmo que Policy A conceda `s3:*` (que inclui DeleteObject) em todos os recursos, o Deny de Policy B para aquele recurso específico é absoluto e não pode ser sobreposto por Allow.
2) Três riscos: (1) Blast radius total em caso de comprometimento — se a role for comprometida, o atacante pode ler, modificar e deletar QUALQUER objeto em QUALQUER bucket da conta, incluindo buckets de log, backups e dados de outros times; (2) Permite operações destrutivas sem restrição — `s3:DeleteBucket`, `s3:DeleteObject` em buckets de produção pode ser executado acidentalmente ou maliciosamente; (3) Viola compliance — PCI DSS, HIPAA e outras regulações exigem menor privilégio documentado. Refatoração: identificar quais buckets e quais ações a Lambda realmente usa (via CloudTrail Access Advisor), então criar: `{"Action": ["s3:GetObject", "s3:PutObject"], "Resource": "arn:aws:s3:::bucket-especifico/*"}` — apenas as ações necessárias no bucket específico.
3) ABAC (Attribute-Based Access Control) usa atributos (tags) das identidades e recursos para tomar decisões de acesso dinamicamente, em vez de criar uma política por papel/recurso. Escala melhor porque: com RBAC, cada novo projeto requer novas políticas IAM e atualização de roles; com ABAC, uma única política genérica cobre todos os projetos usando tags. Exemplo concreto: com a política `{"Condition": {"StringEquals": {"aws:ResourceTag/Project": "${aws:PrincipalTag/Project}"}}}`, ao adicionar o projeto "payments": basta criar os recursos EC2/RDS com tag `Project=payments` e taggear a role do time de payments com `Project=payments`. O time de payments automaticamente acessa apenas seus recursos — sem criar nenhuma nova política IAM. Com RBAC seria necessário criar uma `PaymentsPolicy`, anexar à role e manter essa política indefinidamente.
