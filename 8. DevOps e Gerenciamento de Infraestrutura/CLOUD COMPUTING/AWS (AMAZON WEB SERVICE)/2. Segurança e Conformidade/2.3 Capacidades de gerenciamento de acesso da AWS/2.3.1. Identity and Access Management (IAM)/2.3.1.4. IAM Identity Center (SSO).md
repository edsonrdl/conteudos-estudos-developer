### IAM Identity Center (SSO) — acesso centralizado a todas as contas AWS

IAM Identity Center (anteriormente AWS SSO) é o serviço que centraliza o gerenciamento de acesso humano a múltiplas contas AWS e aplicações de negócio, usando um único ponto de login com identidade corporativa. Ele elimina a necessidade de criar e gerenciar IAM Users em cada conta separadamente — o maior problema operacional e de segurança em organizações com múltiplas contas AWS. Com o Identity Center, um único usuário corporativo pode acessar dezenas de contas AWS com a mesma identidade, sem senhas separadas, sem access keys permanentes.

---

## O problema que o Identity Center resolve

```
Organização com 10 contas AWS sem Identity Center:

Situação:
  20 engenheiros precisam de acesso a diferentes combinações
  de 10 contas (dev, staging, prod, security, data, tooling...)

Sem Identity Center:
  20 IAM Users em conta de dev
  20 IAM Users em conta de staging
  15 IAM Users em conta de prod (só quem precisa)
  8 IAM Users em conta de security
  ...
  
  Total: ~150 IAM Users para criar e gerenciar
  
  Problemas:
  ├── Onboarding: criar 8-10 users em contas diferentes
  │     → Processo manual de horas/dias
  ├── Offboarding: ex-funcionário saiu
  │     → Lembrar de desativar em TODAS as contas (esquece?)
  │     → Risco de acesso residual (critical security issue)
  ├── Rotação de senha: 20 pessoas × 10 senhas = 200 senhas
  ├── MFA: 150 MFAs para configurar e auditar
  └── Auditoria: acessos espalhados em 10 contas

Com Identity Center:
  1 diretório central (ou integração com AD/Okta)
  Acesso a todas as contas: via permission sets
  
  Onboarding: criar 1 usuário → atribuir grupos → pronto
  Offboarding: desativar 1 usuário → acesso revogado em todas as contas
  Senha: gerenciada pelo IdP corporativo (AD, Google)
  MFA: configurado uma vez, válido para todas as contas
```

## Componentes principais

### Identity Provider (fonte de identidade)

```
Opção 1 — Identity Center como diretório próprio:
  → Cria usuários e grupos diretamente no Identity Center
  → Gerencia senhas e MFA no Identity Center
  → Adequado para organizações pequenas ou sem IdP existente

Opção 2 — Microsoft Entra ID (Azure AD) via SAML/SCIM:
  → Usuários e grupos sincronizados automaticamente do Azure AD
  → Login: usuário usa credenciais Microsoft (mesmo login do Teams/Outlook)
  → MFA: gerenciado pelo Azure AD (Conditional Access)
  → SCIM: usuários/grupos criados no Azure aparecem no Identity Center
  
  Benefício: offboarding no Azure = revogação imediata em todas as contas AWS

Opção 3 — Okta:
  → Similar ao Azure AD
  → SCIM para sincronização automática de usuários/grupos
  → MFA gerenciado pelo Okta (políticas Okta Verify, biometria)

Opção 4 — Google Workspace:
  → Federação via SAML 2.0
  → Login: credenciais Google
  → SCIM disponível para sincronização

SCIM (System for Cross-domain Identity Management):
  → Protocolo que sincroniza automaticamente usuários/grupos do IdP
  → Usuário desativado no Azure AD → em minutos: desativado no Identity Center
  → Sem necessidade de atualização manual em cada conta AWS
```

### Permission Sets — o equivalente a IAM Roles

```
Permission Set = template de permissões que é convertido em
                 IAM Role em cada conta onde é atribuído

Criação de Permission Set:
  Identity Center → Permission Sets → Create
  ├── Nome: "ReadOnly-Produção"
  ├── Duração da sessão: 4 horas (padrão: 1h, máx: 12h)
  ├── Policies anexadas:
  │     ├── AWS Managed: ReadOnlyAccess (política AWS)
  │     └── Customer Managed: MinhaPolíticaCustomizada
  └── Inline Policy (opcional): permissões específicas

Permission Sets comuns:
  AdministratorAccess:
  → Policy: AdministratorAccess
  → Uso: conta de tooling para platform team
  → Duração: 4-8h (sessão de trabalho)

  ReadOnly-Produção:
  → Policy: ReadOnlyAccess
  → Uso: acesso de leitura para devs em prod (debug/monitoring)
  → Duração: 2h

  DevAccess:
  → Policy: customer managed (dev tools, não produção)
  → Uso: desenvolvedores em contas de dev/staging
  → Duração: 8h (dia de trabalho)

  EmergencyAccess:
  → Policy: AdministratorAccess
  → Uso: break-glass emergencial
  → Duração: 1h (máximo útil em emergência)
  → Requer aprovação adicional

Como o Permission Set vira IAM Role:
  Quando você atribui "ReadOnly-Produção" ao Grupo "Devs" na conta de prod:
  → Identity Center cria automaticamente uma IAM Role na conta de prod
  → Role name: AWSReservedSSO_ReadOnly-Producao_abc123def
  → Trust policy: permite que apenas o Identity Center assuma
  → Permission policy: ReadOnlyAccess + suas customizações
```

### Atribuições (Assignments)

```
Assignment = quem tem acesso ao quê com qual nível

Estrutura: [Usuário ou Grupo] → [Permission Set] → [Conta AWS]

Exemplos reais:

Grupo "SRE-Team" → ReadOnly-Produção → todas as contas
  → Qualquer membro do SRE pode ver (não modificar) qualquer conta

Grupo "SRE-Team" → AdministratorAccess → conta-tooling
  → SRE tem admin na conta de ferramentas (pipeline, monitoramento)

Grupo "Backend-Devs" → DevAccess → conta-desenvolvimento
Grupo "Backend-Devs" → ReadOnly-Staging → conta-staging
  → Devs têm acesso de dev no dev e leitura no staging

Usuário "joao.silva" → EmergencyAccess → conta-producao
  → João especificamente tem break-glass em produção
  → (Exceção pontual para um usuário específico)

Criação em massa com Terraform:
resource "aws_ssoadmin_account_assignment" "sre_readonly_prod" {
  instance_arn       = data.aws_ssoadmin_instances.main.arns[0]
  permission_set_arn = aws_ssoadmin_permission_set.readonly.arn
  
  principal_id   = data.aws_identitystore_group.sre.group_id
  principal_type = "GROUP"
  
  target_id   = "111222333444"  ← ID da conta de produção
  target_type = "AWS_ACCOUNT"
}
```

## O fluxo de login do usuário

```
1. Usuário acessa o portal do Identity Center:
   https://d-xxxxxxxxxx.awsapps.com/start
   (URL customizável: https://empresa.awsapps.com/start)

2. Autenticação:
   → Com diretório nativo: usuário/senha do Identity Center + MFA
   → Com Azure AD: redireciona para login Microsoft → MFA do Azure
   → Com Okta: redireciona para login Okta → MFA do Okta

3. Portal mostra contas e roles disponíveis:
   ┌─────────────────────────────────────────────────┐
   │ Bem-vindo, João Silva                           │
   │                                                  │
   │ AWS Accounts:                                    │
   │                                                  │
   │ 📁 Development (111222333444)                   │
   │    [DevAccess] → Console  → CLI                  │
   │                                                  │
   │ 📁 Staging (222333444555)                        │
   │    [ReadOnly] → Console   → CLI                  │
   │                                                  │
   │ 📁 Production (333444555666)                     │
   │    [ReadOnly-Prod] → Console → CLI               │
   └─────────────────────────────────────────────────┘

4. Para acessar o console:
   → Clica em "Console" → abre console AWS direto na conta correta
   → Sessão temporária (ex: 4 horas) — expira automaticamente
   → Nenhuma senha separada para essa conta

5. Para acesso CLI:
   → Clica em "CLI" → copia comando ou abre Cloud Shell
   → Ou via AWS CLI v2:
   aws configure sso
     SSO start URL: https://empresa.awsapps.com/start
     SSO region: us-east-1
     → Abre browser para autenticar
     → Lista as contas/roles disponíveis
     → Configura profiles automaticamente
   
   aws sso login --profile producao-readonly
   aws s3 ls --profile producao-readonly
```

## Identity Center vs IAM Users — comparativo definitivo

```
                     IAM USERS            IAM IDENTITY CENTER
                     ─────────────────    ──────────────────────────
Credencial tipo      Access keys (perm.)  Tokens STS (temporários)
Duração das creds    Permanente           1-12h (configurável)
Múltiplas contas     N usuários × contas  1 identidade central
Onboarding           N contas × criação   1 usuário + grupos
Offboarding          N contas × disable   1 desativação → tudo revogado
MFA                  Por usuário IAM      Via IdP (centralizado)
Auditoria            Logs espalhados      Centralizado no Identity Center
IdP corporativo      Integração complexa  Nativo (SAML + SCIM)
Custo                Gratuito             Gratuito
Maturidade           Legado               Padrão atual recomendado pela AWS
```

## Integração com Azure AD — exemplo completo

```
Configuração passo a passo:

1. No Azure AD:
   → Criar aplicativo Enterprise (AWS IAM Identity Center)
   → Configurar SAML: Entity ID, ACS URL (fornecidos pelo IdC)
   → Configurar SCIM: URL + Token (fornecidos pelo IdC)
   → Atribuir usuários/grupos ao aplicativo

2. No Identity Center:
   → Settings → Identity source → External identity provider
   → Carregar metadados SAML do Azure AD
   → Copiar URL + Token SCIM para o Azure AD
   → Habilitar sincronização automática

3. Sincronização automática (SCIM):
   Grupo "AWS-SRE-Team" criado no Azure AD:
   → Em minutos: grupo aparece no Identity Center
   
   João Silva adicionado ao grupo no Azure AD:
   → Em minutos: João aparece no Identity Center
   
   João desativado no Azure AD (saiu da empresa):
   → Em minutos: João desativado no Identity Center
   → Acesso revogado em todas as contas AWS automaticamente

4. MFA via Azure Conditional Access:
   Regra: "Ao acessar AWS IAM Identity Center: exigir MFA"
   → Usuário sem MFA registrado no Azure: bloqueado
   → Usuário com MFA: autenticado normalmente
   → MFA: Microsoft Authenticator, FIDO2 security key, etc.
```

## Auditoria com Identity Center

```
CloudTrail registra eventos do Identity Center:

Eventos importantes:
  ├── UserAuthentication: usuário logou com sucesso/falhou
  ├── Federate: usuário assumiu role em uma conta
  ├── RoleAssigned: permission set atribuído a usuário/grupo
  └── UserCreated/UserDeleted: mudanças de usuário

Exemplo de evento no CloudTrail:
{
  "eventName": "Federate",
  "userIdentity": {
    "username": "joao.silva@empresa.com"
  },
  "requestParameters": {
    "accountId": "333444555666",
    "roleName": "AWSReservedSSO_ReadOnly-Prod_abc123"
  },
  "responseElements": {
    "credentials": {
      "expiration": "2024-01-15T16:30:00Z"
    }
  }
}
→ João acessou a conta 333444555666 com ReadOnly-Prod

Query no CloudWatch Logs Insights:
fields eventName, userIdentity.username, requestParameters.accountId
| filter eventSource = "sso.amazonaws.com"
| filter eventName = "Federate"
| sort @timestamp desc
| limit 100

→ "Mostre todos os acessos a contas AWS via SSO nas últimas 24h"
```

## 🧩 Quiz de Fixação

1. Uma empresa tem 15 desenvolvedores e 8 contas AWS. Sem IAM Identity Center, quantos IAM Users precisariam ser gerenciados (assumindo acesso a 5 contas cada em média), e quais são os três maiores riscos operacionais desse modelo?
2. Um desenvolvedor precisa de acesso temporário de administrador para resolver um incidente em produção. Com IAM Identity Center, como esse acesso seria concedido de forma segura e auditável, sem criar um IAM User admin permanente?
3. O que é SCIM e por que é fundamental para a segurança quando integrado com um IdP corporativo como Azure AD?

**Respostas:**
1) Sem Identity Center: 15 desenvolvedores × 5 contas = 75 IAM Users para criar e gerenciar (na prática mais, pois administradores precisam de acesso a mais contas). Os três maiores riscos operacionais: (1) Offboarding incompleto — quando um desenvolvedor sai da empresa, é necessário lembrar de desativar o IAM User em cada uma das contas individualmente; esquecer uma conta significa acesso residual de um ex-funcionário, que pode persistir por semanas ou meses sem ser detectado; (2) Proliferação de credenciais — 75 access keys permanentes para rotacionar a cada 90 dias; na prática, a rotação nunca é feita sistematicamente, deixando credenciais antigas ativas indefinidamente; (3) Inconsistência de permissões — política de acesso aplicada manualmente em cada conta pode divergir; um desenvolvedor pode ter permissões diferentes em contas diferentes por erro de configuração, impossibilitando auditoria efetiva.
2) Com IAM Identity Center: (1) Criar (ou já ter) um Permission Set "EmergencyAdminAccess" com AdministratorAccess e duração de sessão de 1 hora; (2) Fazer uma atribuição pontual e temporária: Usuário específico → EmergencyAdminAccess → conta de produção; (3) Informar ao desenvolvedor para acessar via portal SSO; (4) O CloudTrail registra automaticamente: quando o usuário acessou, qual conta, qual permission set, e TODAS as ações realizadas durante a sessão; (5) Após resolução do incidente: remover a atribuição — o acesso expira imediatamente (próxima sessão não terá o acesso); (6) Configurar CloudWatch Alarm para notificar o time de segurança quando qualquer Permission Set de "Emergency" é assumido. Resultado: acesso temporário, rastreado, sem credencial permanente criada.
3) SCIM (System for Cross-domain Identity Management) é um protocolo padronizado que sincroniza automaticamente usuários e grupos do Identity Provider (Azure AD, Okta, etc.) para o Identity Center. É fundamental para segurança por três razões: (1) Offboarding em tempo real — quando um funcionário é desativado no Azure AD (ex: demitido, fim de contrato), o SCIM propaga essa mudança ao Identity Center em minutos, revogando o acesso a todas as contas AWS automaticamente — sem depender de processo manual que pode ser esquecido; (2) Source of truth único — o diretório corporativo (Azure AD) é a única fonte de verdade; mudanças de grupo (ex: desenvolvedor promovido a SRE) refletem automaticamente nas permissões AWS sem intervenção adicional; (3) Auditoria consistente — como todos os usuários vêm do IdP, a identidade no CloudTrail ("joao.silva@empresa.com") é rastreável de volta ao sistema de RH, facilitando investigações de segurança e demonstração de conformidade em auditorias.
