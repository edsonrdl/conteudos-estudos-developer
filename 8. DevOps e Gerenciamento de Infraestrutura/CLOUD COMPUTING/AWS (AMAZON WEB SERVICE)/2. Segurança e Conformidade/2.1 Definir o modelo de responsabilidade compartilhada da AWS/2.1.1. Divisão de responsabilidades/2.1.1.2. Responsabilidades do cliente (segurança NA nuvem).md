### Responsabilidades do cliente — segurança NA nuvem

Enquanto a AWS protege a infraestrutura subjacente, o cliente é inteiramente responsável por tudo que configura, coloca e opera dentro dessa infraestrutura. Essa responsabilidade varia em escopo conforme o tipo de serviço usado — quanto mais gerenciado, menor a superfície do cliente. Mas independente do serviço, certas responsabilidades nunca são delegadas: proteção de dados, controle de acesso e configuração correta de segurança são sempre do cliente.

```
Modelo em camadas — cliente sempre responsável pelas camadas superiores:

│  └── O que armazena, como classifica, encripta   │
├─────────────────────────────────────────────────┤
│ IDENTIDADE E ACESSO (IAM)                        │ ← sempre do cliente
│  └── Quem pode fazer o quê nos recursos          │
├─────────────────────────────────────────────────┤
│ APLICAÇÃO                                        │ ← sempre do cliente
│  └── Código, dependências, lógica de negócio     │

│ CONFIGURAÇÃO DE REDE                             │ ← sempre do cliente
│  └── Security Groups, NACLs, VPC, rotas          │
```

## Responsabilidade 1: Dados

```
A proteção dos dados é 100% responsabilidade do cliente,
independente do serviço usado.

Classificação de dados:
  → Você decide o que é público, interno, confidencial ou restrito
  → AWS não sabe (e não deve saber) o significado dos seus dados

Criptografia em repouso:
  ❌ Padrão S3: dados não criptografados se você não habilitar
  ✓ S3 SSE-S3: habilitado por padrão desde 2023 (mas você verifica)
  ✓ S3 SSE-KMS: você controla as chaves (KMS)
  
  ❌ RDS sem criptografia: dado legível se disco fosse comprometido
  ✓ RDS com criptografia: habilitar no momento da criação
     ATENÇÃO: não é possível habilitar criptografia em instância
     RDS existente sem criptografia — precisa migrar

Criptografia em trânsito:
  ❌ HTTP: tráfego em texto claro interceptável
  ✓ HTTPS: certificado via ACM (gratuito), obrigatório no ALB
  
  ❌ Aplicação conecta ao RDS sem SSL:
  ✓ Forçar SSL no RDS:
    -- PostgreSQL: verificar ssl = on no parâmetro group
    -- MySQL: REQUIRE SSL no grant do usuário

Retenção e ciclo de vida:
  → Você define por quanto tempo dados são mantidos
  → LGPD/GDPR: você é responsável por apagar quando necessário
  → S3 Lifecycle Policies: mover para Glacier ou deletar após N dias
  → CloudWatch Logs: definir retention policy (default: nunca expira)
```

## Responsabilidade 2: Identidade e Acesso (IAM)

```
Nenhum controle de acesso na AWS funciona sozinho —
você precisa configurar cada permissão intencionalmente.

Princípio do menor privilégio (sua responsabilidade aplicar):

❌ Anti-padrão extremamente comum:
  Usuario: AdministratorAccess
  EC2 Instance Profile: AdministratorAccess
  Lambda Execution Role: AdministratorAccess
  "Funciona, então tá bom"
  
  → Se qualquer credential for comprometida: game over

✓ Correto — permissões mínimas necessárias:
  Lambda de processamento de pedidos:
  {
    "Statement": [
      {
        "Effect": "Allow",
        "Action": ["sqs:ReceiveMessage", "sqs:DeleteMessage",
                   "sqs:GetQueueAttributes"],
        "Resource": "arn:aws:sqs:us-east-1:123:fila-pedidos"
      },
      {
        "Effect": "Allow",
        "Action": ["dynamodb:PutItem", "dynamodb:UpdateItem"],
        "Resource": "arn:aws:dynamodb:us-east-1:123:table/Pedidos"
      }
    ]
  }
  → Pode apenas ler da fila de pedidos e escrever na tabela Pedidos
  → Nada mais

Gerenciamento de usuários:
  ├── MFA obrigatório para todos os usuários humanos
  ├── Access keys rotacionadas regularmente (ou eliminadas: usar SSO)
  ├── Usuários inativos desativados
  ├── Grupos para organizar permissões (não permissões individuais)
  └── Nunca compartilhar credenciais entre usuários

Proteção da conta raiz (root):
  ├── MFA OBRIGATÓRIO na conta raiz
  ├── Não criar access keys para root
  ├── Não usar root para operações do dia a dia
  ├── Email da conta raiz: caixa monitorada (não pessoal)
  └── Considerar AWS Organizations para isolamento de ambientes
```

## Responsabilidade 3: Sistema Operacional (EC2)

```
Para instâncias EC2, o cliente é o "SysAdmin":

Patches e atualizações:
  ❌ "Vou atualizar quando tiver tempo"
  → CVEs críticos explorados em dias/horas após publicação
  → Sem patches: instância vulnerável a exploits conhecidos
  
  ✓ AWS Systems Manager Patch Manager:
    → Aplica patches automaticamente na janela de manutenção
    → Baseline: patches críticos e importantes
    → Relatório de conformidade
    → Sem intervenção manual

Contas de usuário do SO:
  ├── Desativar conta root por SSH (PermitRootLogin no)
  ├── Usar usuários não-privilegiados para aplicações
  ├── Remover usuários desnecessários
  └── Chaves SSH: rotacionar, nunca compartilhar

Hardening do SO:
  ├── Desabilitar serviços não utilizados
  ├── Firewall local (iptables/nftables) além dos Security Groups
  ├── Auditd para logging de ações privilegiadas
  └── Usar AMIs hardened (CIS Benchmarks disponíveis no Marketplace)

IMDSv2 (Instance Metadata Service):
  ❌ IMDSv1: vulnerável a SSRF (Server-Side Request Forgery)
     → Atacante pode roubar credenciais da IAM Role via:
     curl http://169.254.169.254/latest/meta-data/iam/security-credentials/
  
  ✓ IMDSv2: requer token de sessão (protege contra SSRF)
  # Forçar IMDSv2 na criação:
  aws ec2 modify-instance-metadata-options \
    --instance-id i-xxx \
    --http-tokens required  # IMDSv2 obrigatório
```

## Responsabilidade 4: Configuração de Rede

```
VPC e Security Groups não se configuram sozinhos:

Security Groups — regras de firewall por instância:
  ❌ Abrir porta 22 para 0.0.0.0/0:
  inbound:
    - port: 22
      source: 0.0.0.0/0   ← SSH aberto para o mundo inteiro
  → Bots varrem a internet e tentam força bruta SSH
  
  ✓ Correto:
  inbound:
    - port: 22
      source: 203.0.113.10/32   ← apenas IP do administrador
  Ou melhor: usar SSM Session Manager (sem porta 22 aberta)

Princípio de menor exposição:
  ├── Subnets privadas: EC2, RDS, ElastiCache (sem IP público)
  ├── Subnets públicas: apenas ALB e NAT Gateway
  ├── RDS: nunca com Publicly Accessible = true (em produção)
  ├── S3: Block Public Access habilitado no nível de conta
  └── Lambda: VPC apenas se precisar acessar recursos privados

NACLs como segunda camada:
  → Bloquear IPs maliciosos conhecidos no nível da subnet
  → Negar portas desnecessárias (ex: bloquear porta 23 Telnet)
  → Complementa os Security Groups (defense in depth)

VPC Flow Logs:
  → Habilitar para ter visibilidade de tráfego de rede
  → Logs de todas as conexões aceitas e rejeitadas
  → Fundamental para investigação de incidentes
  → Custo: CloudWatch Logs ou S3 (considerar o volume)
```

## Responsabilidade 5: Aplicação e código

```
A AWS não revisa seu código — vulnerabilidades de aplicação
são inteiramente sua responsabilidade:

OWASP Top 10 — sua aplicação deve ser protegida contra:
  1. Broken Access Control
     → Verificar permissões em cada endpoint da API
     → Não confiar apenas no que o cliente envia

  2. Cryptographic Failures
     → Nunca armazenar senha em texto claro
     → Usar bcrypt/Argon2 (não MD5/SHA1)
     → Dados sensíveis nunca em logs

  3. Injection (SQL, NoSQL, Command)
     → Sempre parametrizar queries (nunca concatenar strings)
     → Validar e sanitizar inputs

  4. Security Misconfiguration
     → Debug mode desabilitado em produção
     → Stack traces não expostos ao usuário
     → Headers de segurança no HTTP (HSTS, CSP, X-Frame-Options)

  5. Sensitive Data Exposure
     → Logs sem dados de cartão, senha, CPF
     → Respostas de API sem dados além do necessário
     → HTTPS obrigatório

Dependências e bibliotecas:
  ❌ npm install e nunca mais atualizar
  → CVEs em bibliotecas são vetores de ataque comuns
  
  ✓ Verificação automática de vulnerabilidades:
    → Amazon Inspector: escaneia EC2 e containers
    → dependabot (GitHub): PRs automáticos para atualizar deps
    → AWS CodeGuru Security: revisão de código com foco em segurança
    → Snyk, OWASP Dependency-Check: integrado ao CI/CD

Secrets no código — o erro mais comum:
  ❌ Frequente no GitHub:
  DB_PASSWORD = "senha123"
  AWS_ACCESS_KEY = "AKIA..."
  
  ✓ Correto:
  → Variáveis de ambiente (mas não em texto claro em arquivos)
  → AWS Secrets Manager: busca credenciais em runtime
  → Parameter Store (SSM): para configurações não-secretas
  → git-secrets: previne commit de credenciais
  → AWS detecta access keys expostos no GitHub e desativa automaticamente
```

## Responsabilidade 6: Monitoramento e detecção

```
Você deve monitorar o que acontece nos seus recursos:

Logs essenciais que você deve habilitar:
  ├── CloudTrail: todas as chamadas de API (quem fez o quê)
  │     → Habilitar em TODAS as regiões
  │     → Habilitar multi-region trail
  │     → Manter por pelo menos 1 ano (compliance)
  │
  ├── VPC Flow Logs: tráfego de rede das suas instâncias
  │     → Detectar conexões suspeitas
  │
  ├── Application Logs: sua aplicação deve logar
  │     → Tentativas de login falhas
  │     → Acesso a dados sensíveis
  │     → Erros e exceções
  │
  └── RDS Logs: slow query log, error log, audit log

Alertas que você deve configurar:
  ├── CloudWatch Alarm: uso de root account (ANY API call)
  ├── GuardDuty findings de alta severidade
  ├── Budget alerts (custo inesperado = possível ataque)
  ├── Tentativas de login falhas no Cognito/aplicação
  └── S3 bucket policy mudada (CloudTrail + EventBridge)
```

## As 10 configurações incorretas mais comuns (e custosas)

```
1. S3 bucket público com dados sensíveis
   Fix: Enable S3 Block Public Access na conta

2. Security Group com 0.0.0.0/0 em portas de admin (22, 3389)
   Fix: Restrict to known IPs ou usar SSM Session Manager

3. Root account sem MFA
   Fix: Habilitar MFA virtual ou hardware imediatamente

4. Access keys de usuário root existentes
   Fix: Deletar — usar IAM users ou SSO

5. CloudTrail desabilitado
   Fix: Habilitar multi-region trail, S3 com MFA Delete

6. EC2 Instance Profiles com AdministratorAccess
   Fix: Criar roles com permissões mínimas específicas

7. RDS com Publicly Accessible = true
   Fix: Colocar em subnet privada + bastion/SSM para acesso admin

8. Credenciais hardcoded no código
   Fix: AWS Secrets Manager + git-secrets no pre-commit

9. Logs sem retenção definida (CloudWatch Logs)
   Fix: Definir retention policy (30/90/365 dias conforme compliance)

10. GuardDuty desabilitado
    Fix: Habilitar em todas as regiões ($3-$5/mês para ambientes pequenos)
```

## 🧩 Quiz de Fixação

1. Uma instância EC2 foi comprometida por exploit de vulnerabilidade no sistema operacional. A AWS não aplicou o patch disponível há 3 semanas. De quem é a responsabilidade? O que poderia ter prevenido?
2. Uma equipe armazena dados de clientes no S3 mas não habilitou criptografia. Os dados foram acessados indevidamente por um funcionário com permissões IAM excessivas. Identifique duas falhas de responsabilidade do cliente nesse cenário.
3. Por que IMDSv1 é considerado um risco de segurança para instâncias EC2, e como IMDSv2 mitiga especificamente o ataque SSRF que explora esse serviço?

**Respostas:**
1) Responsabilidade do cliente. Patches do sistema operacional de instâncias EC2 são explicitamente responsabilidade do cliente no modelo de responsabilidade compartilhada — a AWS gerencia o hipervisor e a infraestrutura física, mas o SO dentro da VM é gerenciado pelo cliente. O que poderia ter prevenido: (1) AWS Systems Manager Patch Manager configurado para aplicar patches críticos automaticamente na janela de manutenção — o patch teria sido aplicado sem intervenção humana; (2) Amazon Inspector para identificar CVEs nas instâncias e alertar o time; (3) Golden AMI com patcher integrado ao pipeline de CI/CD para reconstruir instâncias regularmente com imagens atualizadas.
2) Duas falhas de responsabilidade do cliente: (1) Ausência de criptografia em repouso — habilitar SSE-KMS (ou ao menos SSE-S3) é responsabilidade do cliente; dados não criptografados são acessíveis a qualquer pessoa com permissão de leitura no S3, sem camada adicional de proteção; (2) Permissões IAM excessivas — conceder ao funcionário mais acesso do que necessário para sua função viola o princípio do menor privilégio, que é inteiramente responsabilidade do cliente configurar. Combinadas, essas duas falhas permitiram que uma credencial com permissões incorretas acessasse dados desprotegidos — ambas são configurações que o cliente controlava e deveria ter feito corretamente.
3) IMDSv1 permite qualquer processo dentro da instância (ou qualquer requisição HTTP que chegue ao IP 169.254.169.254) recuperar credenciais da IAM Role sem autenticação. Um ataque SSRF ocorre quando a aplicação é manipulada a fazer requisições HTTP para URLs controladas pelo atacante — o atacante aponta para `http://169.254.169.254/latest/meta-data/iam/security-credentials/[role-name]` e a aplicação vulnerável executa a requisição, retornando as credenciais temporárias da IAM Role ao atacante. Com essas credenciais, o atacante tem os mesmos poderes da Role da instância. IMDSv2 mitiga isso exigindo um token de sessão obtido via requisição PUT com header especial (`X-aws-ec2-metadata-token-ttl-seconds`) antes de qualquer consulta ao metadata. Requisições SSRF simples (GET direto) não conseguem obter o token — precisariam de uma segunda requisição do tipo PUT, que a maioria das vulnerabilidades SSRF simples não suporta, tornando o ataque inviável.
