### Responsabilidades da AWS — segurança DA nuvem

O modelo de responsabilidade compartilhada (Shared Responsibility Model) é um dos conceitos mais importantes da AWS. Ele divide as obrigações de segurança entre a AWS e o cliente de forma clara: **a AWS é responsável pela segurança DA nuvem** (a infraestrutura que torna os serviços possíveis), enquanto o cliente é responsável pela segurança **NA nuvem** (o que ele coloca e configura dentro dessa infraestrutura). Entender esse limite é fundamental para saber onde sua equipe precisa agir e onde pode confiar na AWS.

---

## A analogia do prédio de escritórios

```
AWS como proprietária do prédio:
  ├── Estrutura física do prédio (fundações, paredes, telhado)
  ├── Sistema elétrico e de energia
  ├── Sistema de incêndio e sprinklers
  ├── Segurança no lobby (porteiros, câmeras)
  ├── Elevadores e escadas (funcionando e seguros)
  └── Manutenção geral do imóvel

Inquilino (cliente AWS):
  ├── Trancas nas portas do seu escritório
  ├── Quem tem chave para entrar
  ├── O que você guarda dentro do escritório
  ├── Configuração dos móveis e equipamentos
  └── Seus próprios sistemas de segurança internos

A AWS garante que o prédio é seguro.
Você é responsável pelo que faz dentro do seu espaço.
```

## O que a AWS é responsável por proteger

### 1. Infraestrutura física

```
Data centers AWS:
  ├── Localização não divulgada publicamente
  ├── Acesso físico restrito e monitorado 24/7
  │     → Múltiplos fatores: badge, biometria, câmeras
  │     → Apenas funcionários autorizados com necessidade real
  │     → Log de acesso físico completo
  ├── Segurança perimetral (cercas, guardas, drones em alguns)
  ├── Sistemas de detecção e supressão de incêndio
  ├── Redundância de energia: geradores, UPS, múltiplas subestações
  └── Resfriamento: sistemas redundantes N+1 ou 2N

Destruição segura de hardware:
  → Discos que falham ou são aposentados: destruição certificada
  → NIST 800-88 guidelines para sanitização de mídia
  → Certificado de destruição disponível para auditoria
  → Clientes nunca precisam se preocupar com dados residuais
    em hardware descartado
```

### 2. Infraestrutura de rede global

```
Rede backbone da AWS:
  ├── Rede privada global entre regiões e AZs
  │     → Não passa pela internet pública entre AZs
  │     → Fibra dedicada de baixíssima latência
  ├── Proteção DDoS nativa (AWS Shield Standard)
  │     → Mitigação automática de ataques volumétricos
  │     → SYN flood, UDP reflection, etc.
  ├── Monitoramento contínuo de tráfego anômalo
  ├── Separação lógica de tráfego entre clientes
  └── Criptografia de tráfego entre data centers
      (em trânsito na rede interna da AWS)

O que isso significa para você:
  → Não precisa se preocupar com ataques à infraestrutura de rede
  → Proteção DDoS básica é automática e gratuita
  → Tráfego entre suas instâncias na mesma região:
    AWS garante que não é interceptado por outros clientes
```

### 3. Virtualização e hipervisor

```
AWS Nitro Hypervisor:
  ├── Isolamento entre VMs de clientes diferentes
  │     → Memória de uma VM nunca acessível por outra
  │     → CPU isolada: sem side-channel attacks entre clientes
  ├── Segurança do hipervisor em si
  │     → Patches e atualizações do Nitro: responsabilidade AWS
  │     → Vulnerabilidades como Spectre/Meltdown: AWS corrige
  └── Attestation: VMs não podem comprometer o hipervisor

O que isso significa para você:
  → Mesmo que outra VM de outro cliente esteja comprometida,
    ela não pode "escapar" para sua VM (VM escape é AWS's problema)
  → Patches do hipervisor: você não precisa fazer nada
  → Isolamento multi-tenant: garantido pela AWS

AWS Nitro Security Chip:
  ├── Hardware dedicado para funcionalidades de segurança
  ├── Root of trust (confiança estabelecida em hardware)
  └── Verifica integridade do sistema ao inicializar
```

### 4. Serviços gerenciados — o espectro de responsabilidade

```
Quanto mais gerenciado o serviço, mais a AWS é responsável:

[EC2] ←──── cliente responsável por mais ────── [S3/Lambda] ──── AWS responsável por mais ────►

EC2 (IaaS):
  AWS responsável: hardware, hipervisor, rede física
  Cliente responsável: SO, patches, configuração, aplicação

RDS (PaaS gerenciado):
  AWS responsável: hardware, hipervisor, SO do banco,
                   patches do banco, backups, replicação, failover
  Cliente responsável: schema, usuários do banco,
                        security groups, dados

Lambda (FaaS/Serverless):
  AWS responsável: hardware, hipervisor, SO, runtime,
                   escalabilidade, patches de segurança do runtime
  Cliente responsável: código da função, permissões IAM,
                        variáveis de ambiente, dados processados

S3:
  AWS responsável: hardware, durabilidade (11 noves),
                   criptografia do lado do servidor (se habilitada),
                   replicação interna entre AZs
  Cliente responsável: políticas de acesso (bucket policy, ACL),
                        criptografia (habilitar ou não), dados
```

### 5. Regiões e Zonas de Disponibilidade

```
Separação física garantida pela AWS:
  ├── AZs fisicamente separadas (km de distância)
  ├── Alimentação elétrica independente por AZ
  ├── Conectividade de rede redundante entre AZs
  └── Falha de uma AZ não propaga para outras (isolamento de falha)

Conformidade das instalações:
  AWS mantém certificações para os data centers:
  ├── SOC 1, SOC 2, SOC 3
  ├── ISO 27001, ISO 27017, ISO 27018
  ├── PCI DSS Level 1
  ├── HIPAA (para serviços elegíveis)
  └── FedRAMP (para governo americano)

Herdando conformidade:
  → Quando você usa RDS, herda a conformidade do data center
  → Não precisa auditar o hardware do banco
  → Os relatórios de conformidade da AWS estão disponíveis
    via AWS Artifact (gratuitamente)
```

## Certificações e auditorias da AWS

```
AWS Artifact — acesso a relatórios de conformidade:

O que está disponível:
  ├── SOC 2 Report: controles de segurança, disponibilidade,
  │                 confidencialidade e privacidade
  ├── PCI DSS AOC: Attestation of Compliance para pagamentos
  ├── ISO 27001 Certificate: gestão de segurança da informação
  ├── HIPAA BAA: Business Associate Agreement para saúde
  └── Documentos regionais (LGPD, GDPR, etc.)

Como usar:
  Acesse: Console AWS → AWS Artifact → Reports
  Baixe → compartilhe com auditores
  
  Benefício: sua empresa não precisa auditar o hardware AWS
              Os auditores aceitam os relatórios da AWS como evidência
              das camadas de infraestrutura

Responsabilidade compartilhada nos relatórios:
  Relatório SOC 2 da AWS cobre: data center, rede, hipervisor
  Seu SOC 2 (se necessário): cobre o que você faz na AWS
  → Divisão clara de escopo de auditoria
```

## O que a AWS NÃO é responsável

```
Fica claro o que está FORA da responsabilidade AWS:

✗ Configuração incorreta de Security Groups
  → Você abriu porta 22 para 0.0.0.0/0: problema seu

✗ Dados não criptografados em S3 público
  → Você não habilitou criptografia ou deixou o bucket público: problema seu

✗ Senha fraca do banco de dados RDS
  → Você configurou a senha: problema seu

✗ Código com SQL injection na aplicação
  → Você escreveu o código: problema seu

✗ IAM com permissões excessivas
  → Você configurou o IAM: problema seu

✗ Sistema operacional do EC2 sem patches
  → Você gerencia o SO: problema seu

✗ Dados do cliente enviados para a nuvem
  → Você decide o que enviar: problema seu (LGPD/GDPR)

A linha divisória é: AWS protege o que ela controla.
Você protege o que você configura e coloca lá dentro.
```

## Como isso impacta decisões de arquitetura

```
Princípio: quanto mais gerenciado o serviço, menor sua
           superfície de responsabilidade de segurança

Exemplo 1: banco de dados
  EC2 + PostgreSQL manual:
  → Você gerencia: SO + patches + configuração + backups
  → Superfície de responsabilidade: grande
  
  RDS PostgreSQL:
  → AWS gerencia: SO + patches do banco + backups + replicação
  → Você gerencia: schema + usuários + security groups
  → Superfície de responsabilidade: menor

Exemplo 2: aplicação web
  EC2 com Nginx + app:
  → Você gerencia: SO + patches + runtime + dependências
  
  Lambda:
  → AWS gerencia: SO + patches + runtime + escala
  → Você gerencia: código + permissões IAM
  → Superfície de responsabilidade: muito menor

Estratégia: preferir serviços gerenciados
  → Reduz a superfície de ataque que você precisa gerenciar
  → AWS já tem equipes de segurança dedicadas aos serviços gerenciados
  → Você foca no que diferencia seu negócio
```

## 🧩 Quiz de Fixação

1. Um cliente AWS sofreu um ataque porque um disco físico de um servidor EC2 foi roubado por um funcionário de data center. De quem é a responsabilidade? Justifique usando o modelo de responsabilidade compartilhada.
2. Um bucket S3 foi configurado como público por erro, expondo dados sensíveis de clientes. A AWS falhou em proteger os dados? Justifique.
3. Por que usar RDS em vez de instalar PostgreSQL em uma EC2 reduz a superfície de responsabilidade de segurança do cliente, e quais atividades de segurança específicas passam a ser responsabilidade da AWS?

**Respostas:**
1) Responsabilidade da AWS. Segurança física dos data centers — incluindo controle de acesso físico, vetting de funcionários, câmeras, segurança perimetral e destruição segura de hardware — é explicitamente responsabilidade da AWS no modelo de responsabilidade compartilhada. O cliente nunca tem acesso ou controle sobre o hardware físico. Se houve falha no processo de segurança física ou na seleção de funcionários, é um problema da infraestrutura que a AWS gerencia. O cliente herdou a suposição de que a segurança física está garantida ao usar os serviços AWS.
2) Não — a AWS não falhou. A configuração de ACLs e políticas de acesso de buckets S3 é responsabilidade do cliente (segurança NA nuvem). A AWS fornece os mecanismos de controle (bucket policies, ACLs, Block Public Access, Macie) e os mantém funcionando corretamente. A decisão de habilitar acesso público foi do cliente. A AWS inclusive fornece ferramentas proativas para evitar esse erro (S3 Block Public Access no nível de conta, AWS Config rules para detectar buckets públicos, Macie para identificar dados sensíveis expostos) — mas configurar e usar essas ferramentas também é responsabilidade do cliente.
3) Com PostgreSQL em EC2, o cliente é responsável por: patches do sistema operacional Linux, patches de segurança do PostgreSQL, configuração de autenticação, hardening do SO, backups e teste de restauração, configuração de replicação, e failover manual. Com RDS, todas essas responsabilidades passam para a AWS: patches automáticos do SO (janela de manutenção configurável), patches automáticos do engine PostgreSQL, Multi-AZ com failover automático, backups automáticos com retenção configurável, e monitoramento de hardware. O cliente mantém: schema do banco, usuários e senhas do banco, security groups, parâmetros do banco via Parameter Groups, e proteção dos dados em repouso/trânsito (habilitar criptografia).
