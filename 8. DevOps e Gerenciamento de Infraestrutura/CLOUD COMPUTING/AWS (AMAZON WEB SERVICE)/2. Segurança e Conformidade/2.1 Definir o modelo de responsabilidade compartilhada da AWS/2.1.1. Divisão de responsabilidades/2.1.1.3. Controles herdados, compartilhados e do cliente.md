### Controles herdados, compartilhados e do cliente

O modelo de responsabilidade compartilhada vai além da divisão binária "AWS cuida disso, cliente cuida daquilo". Ele define três categorias de controles de segurança e compliance: os que o cliente **herda** completamente da AWS, os que são **compartilhados** (ambos implementam sua parte), e os que são **exclusivamente do cliente**. Entender essas categorias transforma a conversa de compliance de algo abstrato para algo prático e auditável.

---

## As três categorias de controles

```
CONTROLES HERDADOS
  → AWS implementa e o cliente herda automaticamente
  → Cliente não precisa fazer nada — só evidenciar que usa AWS
  → Exemplos: segurança física, controles do hipervisor

CONTROLES COMPARTILHADOS
  → Ambos implementam: AWS na infraestrutura, cliente na aplicação
  → A responsabilidade existe nos dois lados, em camadas diferentes
  → Exemplos: patches, treinamento de pessoal, criptografia

CONTROLES DO CLIENTE
  → Apenas o cliente implementa
  → AWS não tem visibilidade ou controle sobre esses aspectos
  → Exemplos: configuração de segurança da aplicação,
              controles de acesso de usuários finais
```

---

## Controles Herdados — o que você ganha de graça

```
Ao usar AWS, você herda automaticamente todos os controles
que a AWS implementa para proteger a infraestrutura:

Segurança física dos data centers:
  Controle: "Acesso físico às instalações de processamento
            de informações é restrito a pessoal autorizado"
  
  On-premises: você precisa implementar:
    → Torniquetes, leitores de badge, câmeras, guardas
    → Política de acesso físico
    → Logs de entrada e saída
    → Auditoria anual do sistema de controle físico
    
  Na AWS: AWS implementa tudo isso
    → Você herda o controle
    → Evidência: baixar relatório SOC 2 no AWS Artifact
    → Auditores aceitam: "nosso provedor de nuvem AWS
      implementa e certifica o controle físico"

Outros controles herdados:
  ├── Controles ambientais (temperatura, umidade, energia)
  ├── Segurança de rede física (cabos, switches físicos)
  ├── Segurança do hipervisor e firmware dos servidores
  ├── Gerenciamento do ciclo de vida do hardware
  ├── Separação entre clientes (multi-tenancy seguro)
  └── Destruição de mídia de armazenamento

Impacto prático em auditorias:
  Auditoria ISO 27001 (Controle A.11.1.1 — Perímetro físico):
  
  Sem AWS: precisa de fotos, logs, políticas, evidências do data center
  Com AWS:
    1. Baixar ISO 27001 Certificate no AWS Artifact
    2. Apresentar ao auditor: "usamos AWS que possui ISO 27001"
    3. Auditoria desse controle: concluída em 5 minutos
    
  Estimativa de redução de escopo de auditoria:
  → SOC 2: 30-50% dos controles podem ser herdados da AWS
  → ISO 27001: similar redução de escopo
  → PCI DSS: herda controles de infraestrutura física (Requirements 9)
```

## Controles Compartilhados — responsabilidade em camadas

```
Cada controle compartilhado tem uma camada AWS e uma camada cliente.
Ambas precisam existir para o controle estar completo.

Controle: Gerenciamento de Patches

  Camada AWS (infraestrutura):
    → Patches do hipervisor (Nitro)
    → Patches do SO de serviços gerenciados (RDS, Lambda, ECS Fargate)
    → Patches de firmware de hardware
    → Atualizações de segurança dos serviços AWS

  Camada Cliente:
    → Patches do SO das instâncias EC2
    → Patches de aplicação (seu código)
    → Patches de dependências (bibliotecas, packages)
    → Patches de containers (imagem base do Docker)
  
  Falha na camada cliente: instância EC2 não patcheada
  → Controle de patch como um todo está INCOMPLETO
  → Auditores vão encontrar a lacuna
  
  Evidência completa do controle:
  AWS lado: relatório SOC 2 cobre patches da infraestrutura
  Cliente lado: SSM Patch Manager compliance report
  Juntos: controle de patch completo e evidenciado

────────────────────────────────────────────────────

Controle: Treinamento e Conscientização de Segurança

  Camada AWS:
    → Treinamentos de segurança para funcionários da AWS
    → Verificação de antecedentes dos funcionários AWS
    → Programa de segurança interno da Amazon
    (evidenciado no SOC 2)

  Camada Cliente:
    → Treinamentos de segurança para SEUS funcionários
    → Conscientização sobre phishing, senha, dados sensíveis
    → Política de uso aceitável para usuários AWS
    → Treinamentos específicos para devs (OWASP, IaC segura)
  
  A AWS fazer treinamento dos próprios funcionários NÃO
  exime você de treinar os seus.

────────────────────────────────────────────────────

Controle: Gerenciamento de Configuração

  Camada AWS:
    → Configuração base dos serviços AWS (como RDS é construído)
    → Garantia de que o serviço funciona conforme documentado
    → Auditoria interna de baseline de configuração

  Camada Cliente:
    → Configuração específica do que você usa:
      → Parâmetros do RDS (max_connections, ssl, etc.)
      → Security Groups e NACLs
      → Variáveis de configuração da aplicação
      → IaC (Terraform/CloudFormation) para configuração como código
    → Drift detection (AWS Config para detectar mudanças não autorizadas)

────────────────────────────────────────────────────

Controle: Criptografia

  Camada AWS:
    → Criptografia de tráfego entre data centers (interna)
    → Opções de criptografia disponíveis (KMS, ACM)
    → Gerenciamento de HSMs (CloudHSM, KMS backend)
    → Algoritmos criptográficos validados (FIPS 140-2)

  Camada Cliente:
    → DECIDIR se habilita criptografia em repouso (S3, RDS, EBS)
    → CONFIGURAR TLS no ALB e nas conexões com banco
    → GERENCIAR chaves (se usar CMK no KMS)
    → VERIFICAR que aplicação não transmite dados sensíveis
      em texto claro
  
  AWS disponibiliza os mecanismos de criptografia.
  Usar ou não, e como configurar: decisão do cliente.
```

## Controles do Cliente — exclusivamente sua responsabilidade

```
Esses controles não têm camada AWS — são 100% sua:

Controle de Acesso de Usuários Finais:
  → Quem são seus clientes / usuários da aplicação
  → Como eles se autenticam (senha, MFA, SSO)
  → O que cada tipo de usuário pode fazer na sua aplicação
  → Revogação de acesso quando usuário sai
  
  AWS não sabe quem são seus usuários finais.
  (Cognito é uma ferramenta que você usa — mas você configura)

Políticas e Procedimentos de Segurança:
  → Política de senha da sua organização
  → Processo de onboarding/offboarding de funcionários
  → Política de uso de dispositivos (BYOD)
  → Plano de resposta a incidentes da sua organização
  → Política de backup e recuperação de negócio
  
  AWS pode ajudar com ferramentas, mas as políticas são suas.

Classificação e Proteção de Dados de Negócio:
  → Definir o que é dado público, interno, confidencial, secreto
  → Decidir quais dados vão para a nuvem
  → Garantir conformidade com LGPD/GDPR para SEUS dados
  → Responder a solicitações de titulares de dados
  
  AWS não sabe o valor de negócio dos seus dados.

Testes de Segurança da Aplicação:
  → Pentest na sua aplicação
  → DAST (Dynamic Application Security Testing)
  → SAST no seu código
  → Bug bounty program
  
  AWS faz seus próprios pentests na infraestrutura.
  Penetration testing na sua aplicação: você faz.

Segregação de Funções no IAM:
  → Garantir que dev não tem acesso a prod
  → Garantir que quem aprova deploys é diferente de quem os faz
  → Separação entre equipe de segurança e equipe de operações
  
  AWS fornece o IAM como ferramenta.
  Definir e aplicar a segregação: você define.
```

## AWS Artifact — evidenciando controles herdados

```
AWS Artifact é o repositório de relatórios de conformidade da AWS:
  Acesso: Console AWS → AWS Artifact → Reports

Relatórios disponíveis:

SOC 1 (SSAE 18):
  → Controles relevantes para relatórios financeiros
  → Tipo I: relatório pontual de design dos controles
  → Tipo II: relatório de efetividade ao longo do período
  → Uso: auditorias financeiras, SOX compliance

SOC 2:
  → Segurança, Disponibilidade, Integridade, Confidencialidade, Privacidade
  → O mais solicitado por clientes corporativos
  → Type II: evidencia que controles funcionaram durante o período
  → NDA requerido: assinar antes de baixar

SOC 3:
  → Versão pública do SOC 2 (sem NDA)
  → Sumário executivo — não detalha controles internos
  → Use para divulgação pública sem revelar detalhes

ISO 27001 Certificate:
  → Gestão de segurança da informação
  → Aceito globalmente para demonstrar maturidade de segurança
  → Cobre: data centers, operações, desenvolvimento de software

PCI DSS AOC (Attestation of Compliance):
  → Para empresas que processam pagamentos com cartão
  → AWS é PCI DSS Level 1 Service Provider
  → Seus sistemas de pagamento herdam o compliance do data center
  → Você ainda precisa demonstrar compliance na camada aplicação

HIPAA:
  → Para serviços de saúde nos EUA
  → AWS tem Business Associate Agreement (BAA) disponível
  → Serviceable: lista de serviços cobertos pelo BAA

Como usar em uma auditoria:
  Auditor pede evidência de controles físicos de segurança:
  
  1. Acesse AWS Artifact → Reports
  2. Baixe o SOC 2 Type II report do período relevante
  3. Assine o NDA (se ainda não assinou)
  4. Envie ao auditor com nota:
     "A AWS, nosso provedor de infraestrutura, implementa
     e certifica os controles de segurança física e de rede.
     O relatório SOC 2 Type II evidencia a efetividade
     desses controles no período de [datas]."
  
  Auditor revisa: controles físicos → cobertos
  Você foca em evidenciar: seus controles de aplicação e acesso
```

## Mapeamento prático: controles por framework

```
ISO 27001 — exemplo de mapeamento:

Controle A.8.3 (Mídias removíveis):
  Tipo: HERDADO
  Evidência: SOC 2 / ISO 27001 da AWS
  Cliente: sem ação necessária (você não acessa hardware físico)

Controle A.9.2 (Gerenciamento de acesso de usuários):
  Tipo: COMPARTILHADO
  AWS lado: gerenciamento de acesso à infraestrutura AWS
  Cliente lado: gerenciamento de IAM users, roles, políticas
  Evidência cliente: IAM Access Analyzer reports + revisões periódicas

Controle A.12.2 (Proteção contra malware):
  Tipo: COMPARTILHADO
  AWS lado: Amazon GuardDuty (threat detection na infraestrutura)
  Cliente lado: antivírus em instâncias EC2 Windows/Linux,
                scanning de imagens container (Amazon Inspector)
  Evidência: GuardDuty habilitado + Inspector findings report

Controle A.12.3 (Backup):
  Tipo: COMPARTILHADO
  AWS lado: RDS backups automáticos, S3 replicação interna
  Cliente lado: DEFINIR política de retenção, TESTAR restauração,
                AWS Backup para backup centralizado
  Evidência: AWS Backup compliance reports

Controle A.14.2 (Segurança em processos de desenvolvimento):
  Tipo: DO CLIENTE
  AWS: nenhuma camada (você desenvolve o código)
  Cliente: code review, SAST, DAST, testes de segurança
  Evidência: relatórios de CodeGuru, SonarQube, pentest

PCI DSS — exemplo de mapeamento:

Req 1 (Firewalls): COMPARTILHADO
  AWS: rede física, infraestrutura
  Cliente: Security Groups, NACLs, WAF

Req 6 (Sistemas seguros): COMPARTILHADO
  AWS: patches de serviços gerenciados
  Cliente: patches de EC2, código da aplicação seguro

Req 9 (Acesso físico): HERDADO
  AWS: controles físicos completos
  Cliente: sem ação (não tem acesso físico)

Req 10 (Logs de acesso): COMPARTILHADO
  AWS: logs de infraestrutura interna
  Cliente: CloudTrail habilitado, VPC Flow Logs, logs de aplicação
```

## 🧩 Quiz de Fixação

1. Uma empresa está passando por auditoria SOC 2 e o auditor pede evidência dos controles de segurança física do data center. A empresa usa apenas AWS (sem data center próprio). Qual a resposta correta e como obter a evidência necessária?
2. O controle de "Gerenciamento de Patches" é classificado como compartilhado. Uma empresa usa exclusivamente serviços gerenciados (RDS, Lambda, ECS Fargate) e nenhuma instância EC2. Ainda existe responsabilidade de patch para o cliente? Explique.
3. Qual a diferença entre SOC 2 Type I e Type II, e por que auditores corporativos geralmente exigem o Type II?

**Respostas:**
1) A resposta correta é que os controles físicos são herdados da AWS — a empresa não precisa implementar nada além de usar a AWS. Para obter a evidência: acessar Console AWS → AWS Artifact → Reports → baixar o SOC 2 Type II report (requer assinar NDA). Apresentar ao auditor com o contexto: a empresa utiliza AWS como provedor de infraestrutura, e o relatório SOC 2 da AWS evidencia a implementação e efetividade dos controles de segurança física durante o período auditado. O auditor testa o controle através do relatório da AWS e marca como coberto — sem necessidade de evidência própria do data center.
2) Sim, ainda existe responsabilidade de patch para o cliente, mas em camadas diferentes. Com RDS/Lambda/Fargate, a AWS é responsável pelos patches do SO e do runtime — essa parte está coberta. O cliente ainda é responsável por: (1) patches do código da própria aplicação (bugs e CVEs em código próprio); (2) patches de dependências e bibliotecas usadas pela aplicação (npm packages, pip packages, bibliotecas Java — vulnerabilidades como Log4Shell afetam o código da aplicação, não o runtime); (3) imagens base dos containers (mesmo em Fargate, a imagem Docker que você usa como base precisa ser atualizada pelo cliente — AWS não atualiza sua imagem). O fato de não haver EC2 elimina patches de SO, mas não elimina patches de aplicação e dependências.
3) SOC 2 Type I é um relatório pontual que avalia se os controles foram adequadamente desenhados em um único momento no tempo — uma "fotografia". Não evidencia que os controles funcionaram ao longo do tempo. SOC 2 Type II é um relatório de período (tipicamente 6-12 meses) que evidencia que os controles foram efetivos e funcionaram consistentemente durante todo o período auditado — um "filme". Auditores corporativos exigem Type II porque: (1) Type I apenas prova que o design dos controles é adequado — uma empresa pode ter bons controles no papel que nunca são executados; (2) Type II prova que os controles realmente funcionaram no período — é evidência de operação real, não apenas de planejamento; (3) para fins de compliance contínuo (PCI, HIPAA, SOX), o que importa é que os controles operaram durante o período, não apenas que existiam no início.
