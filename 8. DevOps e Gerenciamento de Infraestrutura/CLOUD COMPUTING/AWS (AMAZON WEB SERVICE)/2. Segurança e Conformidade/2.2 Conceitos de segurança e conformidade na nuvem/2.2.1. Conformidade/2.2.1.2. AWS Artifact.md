### AWS Artifact — repositório central de documentos de conformidade da AWS

AWS Artifact é o serviço da AWS que fornece acesso sob demanda a relatórios de segurança e conformidade da AWS e a determinados contratos online. É o ponto de partida para qualquer processo de auditoria, due diligence ou demonstração de compliance que envolva a infraestrutura AWS. Entender o que está disponível no Artifact e como usá-lo transforma semanas de trabalho de compliance em horas.

---

## O que é e onde acessar

```
AWS Artifact:
  → Serviço gratuito (sem custo para acessar relatórios)
  → Acesso: Console AWS → AWS Artifact
  → Alternativa: artifacts.aws.amazon.com

Dois componentes principais:

┌─────────────────────────────────────────────────────┐
│ AWS ARTIFACT REPORTS                                 │
│  → Relatórios de conformidade da AWS                │
│  → SOC, ISO, PCI DSS, FedRAMP, HIPAA, etc.         │
│  → Emitidos por auditores independentes terceiros   │
│  → Atualizados quando a AWS renova as certificações │
└─────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────┐
│ AWS ARTIFACT AGREEMENTS                              │
│  → Contratos que você pode assinar online            │
│  → Business Associate Agreement (HIPAA BAA)         │
│  → Nondisclosure Agreement (NDA para SOC reports)   │
│  → Data Processing Addendum (GDPR/LGPD DPA)        │
└─────────────────────────────────────────────────────┘
```

## Artifact Reports — relatórios disponíveis

### SOC Reports

```
SOC 1 (SSAE 18 / ISAE 3402):
  Disponível: Type I e Type II
  Período: semestral (jan-jun e jul-dez)
  Requer NDA: sim (assinar antes de baixar)
  Contém: descrição dos sistemas, controles implementados,
          testes de efetividade (Type II), resultados dos testes
  
  Quando solicitar:
  → Auditorias financeiras / SOX
  → Clientes que precisam evidência dos controles financeiros
    dos sistemas que você usa

SOC 2:
  Disponível: Type I e Type II
  Critérios: Security (obrigatório) + Availability + outros
  Requer NDA: sim
  Período: Type II cobre 12 meses (mais comum) ou 6 meses
  
  Seções do relatório:
  ├── Seção I: Declaração de Gerenciamento da AWS
  ├── Seção II: Relatório do Auditor Independente
  ├── Seção III: Descrição do Sistema
  ├── Seção IV: Critérios de Confiança e Controles
  └── Seção V: Outras Informações (não auditadas)
  
  Como ler o SOC 2:
  → Tabela de controles (Seção IV) é o coração do relatório
  → Cada controle tem: descrição, testes realizados, resultado
  → "No exceptions noted": controle passou
  → "Exceptions noted": controle falhou (raro para AWS)
  → Use a tabela para mapear a frameworks como ISO 27001

SOC 3:
  Disponível: sem NDA (público)
  Conteúdo: sumário executivo sem detalhes dos controles
  URL: pode ser baixado e publicado
  Uso: demostração de alto nível para parceiros/clientes
```

### ISO Certificates

```
ISO 27001:
  Conteúdo: Certificado de conformidade + Statement of Applicability
  Emitido por: BSI Group (ou outro auditor acreditado)
  Vigência: 3 anos com auditorias anuais de manutenção
  Escopo: lista de data centers e serviços cobertos
  
  Atenção ao escopo:
  → O certificado lista quais serviços e regiões estão cobertos
  → Serviços novos podem não estar no certificado atual
  → Verificar se os serviços que você usa estão no escopo

ISO 27017 (Cloud Security):
  Certificado separado do 27001
  Escopo específico para controles de cloud computing
  
ISO 27018 (Privacy in Cloud):
  Certificado para proteção de PII
  Fundamental para GDPR/LGPD due diligence

ISO 9001 (Quality Management):
  Processos internos de qualidade da AWS
  Menos solicitado por times técnicos, mais por procurement
```

### PCI DSS Documents

```
AOC (Attestation of Compliance):
  → Documento assinado pelo QSA confirmando conformidade
  → Indica nível: AWS é Level 1 Service Provider
  → Inclui: escopo dos serviços cobertos
  → Não requer NDA (documento de declaração, não relatório interno)
  
  Responsabilidade do Shared Responsibility Matrix:
  → Documento específico que detalha, para cada requirement PCI:
    AWS responsável | Cliente responsável | Compartilhado
  → Essencial para: saber exatamente o que você precisa implementar
  
  Package PCI disponível:
  ├── AOC da AWS
  ├── Shared Responsibility Matrix
  └── Guia de implementação PCI na AWS
```

### FedRAMP

```
Para empresas que trabalham com governo americano:

  → FedRAMP Authorization Package
  → Lista de serviços com autorização FedRAMP (Moderate/High)
  → AWS GovCloud (US) tem autorizações específicas
  → Package inclui: Security Assessment Report, System Security Plan
  
  Acesso: marketplace.fedramp.gov (público) ou via Artifact
```

## Artifact Agreements — contratos online

### Business Associate Agreement (HIPAA BAA)

```
O que é:
  Contrato legal que formaliza a relação entre você (Covered Entity
  ou Business Associate) e a AWS (Business Associate) para
  processamento de PHI conforme exigido pelo HIPAA.

Como assinar:
  1. Console AWS → Artifact → Agreements
  2. "AWS Business Associate Addendum"
  3. Revisar os termos
  4. "Accept Agreement"
  5. Confirmação instantânea — sem processo manual/email
  
  Nota: o BAA é aceito no nível da conta AWS
  → Se usa AWS Organizations: assinar em cada conta relevante
  → Ou: assinar na management account (pode cobrir sub-accounts)

O que o BAA cobre:
  ├── AWS se compromete a usar PHI apenas para fornecer os serviços
  ├── Notificação de breach conforme HIPAA Breach Notification Rule
  ├── Proteção de PHI conforme HIPAA Security Rule
  └── Lista de serviços elegíveis (só esses podem processar PHI)

Importante:
  → BAA não torna você automaticamente HIPAA compliant
  → Você ainda precisa configurar criptografia, acesso, logs
  → BAA é apenas um dos requisitos, não o único
```

### NDA para Relatórios SOC

```
Por que existe:
  Relatórios SOC contêm informações detalhadas sobre controles
  internos da AWS — revelar ao público pode criar riscos de segurança

Processo:
  1. Artifact → Reports → Seleciona relatório SOC
  2. Apresenta os termos do NDA
  3. Aceita eletronicamente
  4. Download imediato do relatório
  
  → NDA é aceito por conta (uma vez por tipo de relatório)
  → Após aceitar: downloads subsequentes sem repetir o NDA

Compartilhamento com auditores:
  → O NDA geralmente permite compartilhar com auditores externos
    desde que estejam também sob NDA
  → Verificar os termos específicos antes de compartilhar
  → Nunca postar publicamente o SOC 2 completo
  → Usar SOC 3 (versão pública) para divulgação ampla
```

### Data Processing Addendum (GDPR/LGPD)

```
Para conformidade com GDPR e LGPD:

AWS Data Processing Addendum:
  → Formaliza AWS como Data Processor conforme GDPR Article 28
  → Inclui: Standard Contractual Clauses (SCCs) da UE
  → Cobre transferências de dados da UE para fora (adequacy decisions)
  → Disponível: Artifact → Agreements → Data Processing Addendum

O que o DPA garante:
  ├── AWS processa dados apenas conforme suas instruções
  ├── Sub-processadores (data centers) são listados e gerenciados
  ├── Medidas técnicas e organizacionais adequadas
  ├── Notificação de breach conforme GDPR (sem atraso indevido)
  └── Direito de auditoria (geralmente via relatórios Artifact)
  
Assinar o DPA:
  → Para GDPR: obrigatório se processar dados de cidadãos europeus
  → Para LGPD: recomendado como evidência de due diligence
  → Processo: Artifact → Agreements → aceitar online
```

## Como usar Artifact em processos reais

### Processo de Due Diligence com cliente enterprise

```
Situação: cliente grande (banco, seguradora) pede evidência
de que sua infraestrutura é segura antes de assinar contrato

Passo 1 — Identificar o que foi pedido:
  "Envie: SOC 2 Type II, ISO 27001, evidência de PCI DSS"

Passo 2 — Acessar Artifact:
  Console → AWS Artifact → Reports

Passo 3 — Baixar relatórios relevantes:
  ├── SOC 2 Type II (período mais recente)
  │     → Aceitar NDA → Download PDF
  ├── ISO 27001 Certificate
  │     → Download imediato (sem NDA)
  └── PCI DSS AOC (se aplicável)
        → Download imediato

Passo 4 — Preparar carta de cobertura:
  "Nossa plataforma é hospedada na Amazon Web Services (AWS).
   Os relatórios anexos demonstram a conformidade da infraestrutura
   AWS com os frameworks solicitados.
   
   Os controles cobertos pela AWS incluem: segurança física,
   virtualização, rede e serviços de plataforma.
   
   Os controles sob nossa responsabilidade (aplicação, acesso,
   dados) são demonstrados em [documentos adicionais seus]."

Passo 5 — Fornecer seus próprios controles:
  → IAM policy documents
  → Configurações de segurança
  → Seus próprios testes de pentest
  → Policies internas

Resultado: processo que levaria semanas é concluído em horas
```

### Auditor solicita evidências durante auditoria ISO 27001

```
Controle A.11.1.1 — Perímetro físico:
  → Artifact → ISO 27001 Certificate
  → "A AWS, nosso provedor, possui ISO 27001 que cobre
     controles físicos de seus data centers"
  → Auditor: "Verificado. Próximo controle."

Controle A.9.4.1 — Restrição de acesso à informação:
  → Artifact sozinho não basta
  → Você precisa mostrar: IAM policies configuradas corretamente
  → Artifact SOC 2 ajuda como evidência de que a AWS tem controles
  → Você apresenta suas próprias evidências de IAM

Controle A.12.3.1 — Backup de informações:
  → RDS Automated Backups ativo (screenshot do console)
  → AWS Backup compliance report
  → Procedimento de teste de restauração que você executa
  → Artifact SOC 2 evidencia a confiabilidade da infraestrutura
    de backup da AWS
```

### Gerenciamento de múltiplas contas AWS (Organizations)

```
Com AWS Organizations, o gerenciamento de acordos é centralizado:

Opção 1: Aceitar acordos na management account
  → BAA e DPA aceitos uma vez cobrem sub-accounts (verificar termos)
  
Opção 2: Aceitar em cada conta separadamente
  → Controle granular por conta/ambiente

Relatórios por conta:
  → Cada conta acessa Artifact independentemente
  → Mesmos relatórios disponíveis em todas as contas
  → Relatórios refletem toda a AWS, não por conta específica

Centralizar via AWS Organizations + Delegated Admin:
  → Uma conta de segurança pode gerenciar acordos centralmente
  → Compliance team acessa Artifact de uma conta central
```

## Limitações e o que o Artifact não cobre

```
O que o Artifact NÃO faz:
  ├── Não prova que VOCÊ está em compliance
  │   → Prova que a AWS está — você ainda precisa dos seus controles
  │
  ├── Não cobre todos os serviços AWS
  │   → Verificar escopo de cada relatório
  │   → Serviços novos podem não estar certificados ainda
  │
  ├── Relatórios têm período de cobertura
  │   → SOC 2 do ano passado pode não ser aceito em auditorias atuais
  │   → Verificar datas de cobertura e renovar quando necessário
  │
  └── Não substitui sua própria documentação de controles
      → Para SOC 2 próprio: Artifact é insumo, não a saída
      → Para ISO 27001 próprio: Artifact reduz escopo, não elimina
```

## 🧩 Quiz de Fixação

1. Uma empresa usa AWS para processar dados de pacientes (PHI) de hospitais americanos. O time jurídico diz que precisam de um BAA com a AWS antes de qualquer processamento de PHI. Como assinar o BAA e qual a consequência se processarem PHI sem assiná-lo?
2. Um auditor externo pede o relatório SOC 2 Type II da sua empresa. Você usa 100% AWS. Você pode simplesmente enviar o SOC 2 da AWS baixado do Artifact? O que mais é necessário?
3. Qual a diferença prática entre baixar o SOC 2 e o SOC 3 do Artifact, e quando você usaria cada um?

**Respostas:**
1) Para assinar: Console AWS → AWS Artifact → Agreements → "AWS Business Associate Addendum" → revisar termos → "Accept Agreement" — processo 100% online, instantâneo, sem email ou negociação. Se processarem PHI sem o BAA assinado: (1) violação direta do HIPAA Conduit Exception Rule — a AWS não pode ser Business Associate sem o contrato formal; (2) a empresa é totalmente responsável pela breach se ocorrer PHI — sem o BAA, não há proteção legal da parceria com a AWS; (3) multas do HHS (Department of Health and Human Services) de $100-$50.000 por violação, com teto anual de $1.9M por categoria; (4) perda potencial de contratos com hospitais que exigem compliance HIPAA demonstrável. Importante: o BAA é necessário mas não suficiente — os serviços usados devem estar na lista de HIPAA Eligible Services.
2) Não — o SOC 2 da AWS não é o SOC 2 da sua empresa. O SOC 2 da AWS cobre apenas a infraestrutura AWS. Para apresentar ao auditor externo da sua empresa, você precisa: (1) contratar uma auditoria SOC 2 própria realizada por um auditor CPA independente que avalie seus controles de aplicação, acesso, operações e processos; (2) no escopo dessa auditoria, o SOC 2 da AWS serve como evidência dos controles subcontratados (herdados) — o auditor da sua empresa aceita o SOC 2 da AWS como cobrindo a camada de infraestrutura; (3) você demonstra seus próprios controles (IAM, logs, monitoramento, resposta a incidentes, desenvolvimento seguro) para as camadas sob sua responsabilidade. O resultado final é um SOC 2 Type II da sua empresa, onde o SOC 2 da AWS é evidência de suporte para os controles de infraestrutura.
3) SOC 2 (completo): requer aceitar NDA, contém detalhes dos controles, testes realizados e resultados — informação confidencial que pode ser compartilhada apenas com auditores e stakeholders sob NDA. Use quando: auditor externo solicita evidência detalhada, processo de due diligence com cliente enterprise que precisa revisar os controles, ou para sua própria auditoria SOC 2 onde o auditor precisa mapear controles herdados. SOC 3 (sumário público): sem NDA, não contém detalhes de controles — apenas declaração de que a AWS passou pela auditoria SOC 2. Use quando: cliente ou parceiro quer verificação rápida de alto nível, publicar no seu site como evidência de que usa infraestrutura certificada, resposta a questionários de segurança de baixo risco, ou qualquer situação onde detalhes internos não podem ser compartilhados.
