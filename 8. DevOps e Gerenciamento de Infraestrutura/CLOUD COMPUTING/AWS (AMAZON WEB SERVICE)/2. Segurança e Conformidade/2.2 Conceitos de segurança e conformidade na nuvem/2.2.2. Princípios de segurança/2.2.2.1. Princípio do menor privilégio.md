### Princípio do menor privilégio — conceder apenas o acesso estritamente necessário

O princípio do menor privilégio (Principle of Least Privilege — PoLP) é o controle de segurança mais fundamental na AWS: cada identidade (usuário, role, serviço) deve ter apenas as permissões mínimas necessárias para realizar sua função específica — nada mais. É simples de enunciar e permanentemente difícil de manter, porque a tendência natural é conceder mais acesso "para garantir que funciona". O resultado dessa tendência é um ambiente onde uma credencial comprometida tem poder devastador.

---

## Por que o menor privilégio importa na AWS

```
Cenário sem menor privilégio:
  Desenvolvedor tem: AdministratorAccess
  Lambda de produção tem: AdministratorAccess
  Pipeline de CI/CD tem: AdministratorAccess
  
  "Funciona para tudo, então está bom"

O que acontece quando algo dá errado:

  Cenário A — Credencial de dev vazada no GitHub:
    Atacante tem AdministratorAccess
    → Pode criar instâncias EC2 para mineração de cripto
    → Pode deletar todos os backups
    → Pode exfiltrar todos os dados
    → Pode criar novos usuários IAM persistentes
    → Custo potencial: $50.000+ em compute + dados perdidos

  Cenário B — Mesmo vazamento, com menor privilégio:
    Dev tinha acesso: apenas leitura em buckets S3 de dev
    Atacante tem: acesso de leitura a S3 de dev (apenas)
    → Impacto: limitado a dados não-críticos de desenvolvimento
    → Sem acesso a produção, sem capacidade de criar recursos

A diferença entre catástrofe e incidente contido
é o escopo das permissões da identidade comprometida.
```

## A hierarquia de identidades IAM e menor privilégio

```
USUÁRIOS IAM (humanos):
  Acesso: mínimo para a função do trabalho
  
  Desenvolvedor Backend:
  ├── Leitura em S3 buckets de dev
  ├── Acesso ao CloudWatch Logs do ambiente de dev
  ├── Acesso ao ECR para push/pull de imagens
  └── Acesso ao Secrets Manager (apenas segredos de dev)
  
  SEM:
  └── Qualquer acesso a recursos de produção
  └── IAM management (criar/modificar roles/users)
  └── Billing management

IAM ROLES para serviços (EC2, Lambda, ECS, etc.):
  Acesso: apenas o que o serviço precisa para funcionar
  
  Lambda de processamento de pedidos:
  ├── sqs:ReceiveMessage, DeleteMessage (fila específica)
  ├── dynamodb:PutItem, UpdateItem (tabela Pedidos específica)
  ├── secretsmanager:GetSecretValue (ARN específico do secret)
  └── logs:CreateLogGroup, PutLogEvents (para CloudWatch)
  
  SEM:
  └── Acesso a qualquer outro serviço
  └── Acesso a outras tabelas DynamoDB
  └── Qualquer operação de leitura no Secrets Manager geral

ROLES de CI/CD (GitHub Actions, CodePipeline):
  Acesso: apenas o necessário para o deploy
  
  Pipeline de deploy para staging:
  ├── ecs:UpdateService (apenas cluster staging)
  ├── ecr:PutImage (apenas repositório da aplicação)
  └── cloudformation:UpdateStack (apenas stack staging)
  
  SEM:
  └── Qualquer acesso a produção
  └── IAM changes
  └── Billing ou account management
```

## Construindo políticas IAM com menor privilégio

### Anatomia de uma política IAM

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "LerPedidosDaFila",
      "Effect": "Allow",
      "Action": [
        "sqs:ReceiveMessage",
        "sqs:DeleteMessage",
        "sqs:GetQueueAttributes"
      ],
      "Resource": "arn:aws:sqs:us-east-1:123456789:fila-pedidos-prod"
    },
    {
      "Sid": "EscreverPedidosNoBanco",
      "Effect": "Allow",
      "Action": [
        "dynamodb:PutItem",
        "dynamodb:UpdateItem",
        "dynamodb:GetItem"
      ],
      "Resource": "arn:aws:dynamodb:us-east-1:123456789:table/Pedidos",
      "Condition": {
        "StringEquals": {
          "dynamodb:LeadingKeys": "${aws:PrincipalTag/ClienteId}"
        }
      }
    }
  ]
}
```

**Elementos do menor privilégio:**
- `Action`: lista explícita (não `*`) — apenas as ações necessárias
- `Resource`: ARN específico (não `*`) — apenas o recurso correto
- `Condition`: restrição adicional (apenas dados do próprio cliente)

### Escalada de permissões — o erro mais perigoso

```
Permissão perigosa: iam:PassRole

Sem controle:
  {
    "Action": "iam:PassRole",
    "Resource": "*"  ← qualquer role
  }
  
  → Atacante que tem essa permissão pode criar EC2 com role de admin
  → Mesmo sem ser admin, consegue escalada de privilégios

Com menor privilégio:
  {
    "Action": "iam:PassRole",
    "Resource": "arn:aws:iam::123:role/ec2-web-server-role",
    "Condition": {
      "StringEquals": {
        "iam:PassedToService": "ec2.amazonaws.com"
      }
    }
  }
  → Só pode passar ESSA role específica, APENAS para EC2

Outras permissões que permitem escalada:
  ├── iam:CreatePolicyVersion
  ├── iam:AttachUserPolicy
  ├── iam:PutUserPolicy
  ├── sts:AssumeRole (sem conditions)
  └── lambda:CreateFunction + iam:PassRole
```

### Conditions — restringir além do resource

```
Conditions adicionam restrições contextuais às permissões:

Restringir por IP (acesso apenas da VPN corporativa):
  "Condition": {
    "IpAddress": {
      "aws:SourceIp": "203.0.113.0/24"
    }
  }

Restringir por MFA (operações sensíveis exigem MFA):
  "Condition": {
    "Bool": {
      "aws:MultiFactorAuthPresent": "true"
    }
  }

Restringir por tempo (acesso apenas em horário comercial):
  "Condition": {
    "DateGreaterThan": {"aws:CurrentTime": "2024-01-01T08:00:00Z"},
    "DateLessThan": {"aws:CurrentTime": "2024-12-31T18:00:00Z"}
  }

Restringir por tag de recurso (só acessa recursos da própria equipe):
  "Condition": {
    "StringEquals": {
      "ec2:ResourceTag/Team": "${aws:PrincipalTag/Team}"
    }
  }
  → Usuário com tag Team=backend só acessa EC2 com tag Team=backend

Restringir S3 por prefixo (acesso apenas à própria pasta):
  "Resource": "arn:aws:s3:::bucket-uploads/${aws:username}/*"
  → Cada usuário só acessa sua própria pasta no bucket
```

## Ferramentas para identificar permissões excessivas

### IAM Access Analyzer

```
Analisa políticas e recursos para identificar acesso excessivo:

Dois modos de análise:

1. External Access Analyzer:
   → Identifica recursos acessíveis fora da sua conta
   → "Este bucket S3 está acessível pela conta X (externa)"
   → "Esta role pode ser assumida por qualquer conta AWS"
   → Findings são contínuos (não apenas pontual)
   
   Configuração:
   IAM → Access Analyzer → Create Analyzer
   Tipo: External Access (zona de confiança = sua conta/org)
   
   Exemplo de finding crítico:
   Resource: arn:aws:s3:::bucket-dados-clientes
   Finding: "Bucket accessible from Principal: * (anonymous)"
   Severity: HIGH
   → Bucket público! Investigar imediatamente.

2. Unused Access Analyzer:
   → Identifica credenciais, permissões e acessos não usados
   → "Esta role não foi usada nos últimos 90 dias"
   → "Este usuário tem estas permissões mas nunca as usou"
   → Base de dados: CloudTrail (últimos 90 dias de atividade)
   
   Exemplo de finding:
   IAM User: joao.silva
   Unused permissions: ec2:*, rds:*, s3:DeleteBucket
   Last activity: 120 days ago
   → Revisar e remover permissões não utilizadas
   
3. Policy Validation:
   → Valida sintaxe e boas práticas de políticas IAM
   → "Esta condição nunca será verdadeira" (lógica impossível)
   → "Este action não existe no serviço especificado"
   → Feedback em tempo real no console ao editar políticas
```

### IAM Credentials Report

```
Relatório de todas as credenciais de usuários IAM na conta:

Gerar:
  Console → IAM → Credential Report → Download
  
Ou via CLI:
  aws iam generate-credential-report
  aws iam get-credential-report --output text --query Content | base64 -d

Conteúdo do relatório (CSV):
  user | arn | user_creation_time | password_enabled | 
  password_last_used | password_last_changed | password_next_rotation |
  mfa_active | access_key_1_active | access_key_1_last_used |
  access_key_2_active | access_key_2_last_used

Análises que você deve fazer regularmente:

  1. Usuários sem MFA:
  → Filtrar: mfa_active = false AND password_enabled = true
  → Ação: exigir MFA ou desativar o usuário
  
  2. Senhas nunca usadas:
  → password_last_used = N/A (nunca logou)
  → Ação: desativar ou deletar se foi criado mas nunca usado
  
  3. Access keys antigas (> 90 dias sem rotação):
  → access_key_1_last_rotated > 90 dias
  → Ação: rotacionar access key
  
  4. Access keys não usadas:
  → access_key_active = true AND access_key_last_used > 90 dias
  → Ação: desativar e deletar após período de carência
  
  5. Usuários inativos:
  → password_last_used > 90 dias
  → Ação: desativar (possível ex-funcionário)
```

### IAM Last Accessed Information

```
Para cada role ou usuário, mostra quando cada serviço foi acessado:

Console: IAM → Users/Roles → Access Advisor tab

Informação exibida:
  Serviço     | Último Acesso   | Ações usadas
  ─────────────────────────────────────────────
  S3          | 3 days ago      | GetObject, PutObject
  EC2         | 90 days ago     | DescribeInstances (once)
  RDS         | Never           | —
  Lambda      | Never           | —
  CloudWatch  | Today           | PutLogEvents

Análise:
  → EC2: acesso raro (1x em 90 dias) — revisar se é necessário
  → RDS: nunca acessado — remover permissão de RDS
  → Lambda: nunca acessado — remover permissão de Lambda
  
  Resultado: policy mais enxuta, menor superfície de ataque
```

## Permission Boundaries — guardrails de segurança

```
Problema com delegação de acesso:
  Admin delega para dev a capacidade de criar roles
  → Dev pode criar role com AdministratorAccess
  → Dev agora tem acesso admin via a role que criou
  → Escalada de privilégios

Permission Boundary resolve isso:
  → Define o MÁXIMO que uma role/user pode ter
  → Mesmo que a policy explícita dê mais, o boundary limita
  
  Exemplo:
  Permission Boundary: "pode ter no máximo acesso a S3 e DynamoDB"
  Policy explícita: AdministratorAccess
  Resultado efetivo: apenas S3 e DynamoDB (intersecção)
  
  Implementação:
  {
    "Version": "2012-10-17",
    "Statement": [{
      "Effect": "Allow",
      "Action": ["s3:*", "dynamodb:*", "cloudwatch:*", "logs:*"],
      "Resource": "*"
    }]
  }
  
  Ao criar roles, obrigar uso do boundary:
  {
    "Effect": "Allow",
    "Action": ["iam:CreateRole"],
    "Condition": {
      "StringEquals": {
        "iam:PermissionsBoundary": "arn:aws:iam::123:policy/DevBoundary"
      }
    }
  }
  → Dev só pode criar roles com esse boundary → sem escalada
```

## Service Control Policies (SCPs) — menor privilégio organizacional

```
Para ambientes com AWS Organizations:

SCPs definem o máximo de permissões para contas inteiras:
  → Uma SCP não dá permissão — apenas limita o máximo possível
  → Ações bloqueadas por SCP não podem ser permitidas por IAM

Exemplo: Restringir criação de recursos a regiões específicas
  {
    "Effect": "Deny",
    "Action": "*",
    "Resource": "*",
    "Condition": {
      "StringNotEquals": {
        "aws:RequestedRegion": ["us-east-1", "sa-east-1"]
      },
      "ArnNotLike": {
        "aws:PrincipalARN": "arn:aws:iam::*:role/PipelineRole"
      }
    }
  }
  → Ninguém na organização pode criar recursos fora de us-east-1
    e sa-east-1 (exceto o pipeline role)
  → Protege contra criação acidental/maliciosa em regiões erradas

Exemplo: Proteger CloudTrail de ser desabilitado
  {
    "Effect": "Deny",
    "Action": [
      "cloudtrail:DeleteTrail",
      "cloudtrail:StopLogging",
      "cloudtrail:UpdateTrail"
    ],
    "Resource": "*"
  }
  → Ninguém pode desabilitar o CloudTrail — nem admins das contas
```

## Processo de implementação gradual

```
Implementar menor privilégio em ambiente existente:

FASE 1 — Inventário (sem mudanças):
  1. Gerar Credentials Report → identificar usuários com acesso excessivo
  2. Habilitar IAM Access Analyzer → inventariar acessos externos
  3. Revisar Access Advisor de cada role crítica
  4. Documentar o estado atual

FASE 2 — Permissões novas (menor privilégio desde o início):
  5. Toda nova role/user: criado com menor privilégio
  6. Revisão obrigatória de IAM em code review de IaC
  7. Policy validation no Terraform/CloudFormation

FASE 3 — Remediação gradual (sem quebrar produção):
  8. Identificar permissões não usadas (Access Advisor)
  9. Adicionar SCP de deny explícito para ações nunca usadas
  10. Monitorar por 30 dias (erros aparecem nos CloudTrail logs)
  11. Se sem erros: remover das policies de IAM definitivamente
  12. Repetir para as próximas permissões

FASE 4 — Automação:
  13. AWS Config Rule: iam-no-inline-policy
  14. AWS Config Rule: iam-user-no-policies-check
  15. AWS Config Rule: iam-root-access-key-check
  16. Alertas automáticos para policies com "*" em Resource
```

## 🧩 Quiz de Fixação

1. Uma Lambda function precisa apenas ler mensagens de uma fila SQS específica e escrever itens em uma tabela DynamoDB específica. A equipe criou a execution role com `"Action": "*", "Resource": "*"`. Quais são os riscos específicos dessa configuração e como seria a policy correta com menor privilégio?
2. O IAM Access Analyzer reporta um finding: "Role arn:aws:iam::123:role/DataScienceRole pode ser assumida por qualquer entidade autenticada da AWS (Principal: *)". Por que isso é crítico e como corrigir?
3. O Credentials Report mostra um usuário `pipeline-user` com access key criada há 180 dias, nunca rotacionada, e com last_used de 5 dias atrás. Qual o risco e qual a ação correta?

**Respostas:**
1) Riscos com `Action: *, Resource: *`: a Lambda pode chamar qualquer API da AWS com qualquer recurso — se o código for comprometido por injeção ou dependência maliciosa, o atacante tem controle total da conta. Pode deletar dados de produção, criar instâncias EC2 para mineração, exfiltrar segredos, ou criar usuários IAM persistentes. A policy correta com menor privilégio: `{"Statement": [{"Effect": "Allow", "Action": ["sqs:ReceiveMessage", "sqs:DeleteMessage", "sqs:GetQueueAttributes"], "Resource": "arn:aws:sqs:us-east-1:123:nome-da-fila-especifica"}, {"Effect": "Allow", "Action": ["dynamodb:PutItem", "dynamodb:UpdateItem"], "Resource": "arn:aws:dynamodb:us-east-1:123:table/NomeDaTabelaEspecifica"}, {"Effect": "Allow", "Action": ["logs:CreateLogGroup", "logs:CreateLogStream", "logs:PutLogEvents"], "Resource": "arn:aws:logs:*:*:*"}]}` — apenas as 3 ações necessárias nos 3 recursos específicos.
2) É crítico porque qualquer conta AWS autenticada no mundo pode assumir essa role — não apenas contas da sua organização. Um atacante que tenha qualquer conta AWS válida pode fazer `aws sts assume-role` e obter as permissões dessa role. Com `Principal: *`, não há restrição por conta de origem, organização ou condição. Para corrigir: no trust policy da role, restringir o principal ao mínimo necessário: `{"Principal": {"AWS": "arn:aws:iam::123456789:role/DataSciencePipelineRole"}}` (apenas a role específica que precisa assumir) ou adicionar condição: `"Condition": {"StringEquals": {"aws:PrincipalOrgID": "o-xxxxxxxxxx"}}` para restringir à sua organização AWS Organizations.
3) O risco é duplo: (1) access key com 180 dias de vida é um risco de segurança — cada dia a mais representa mais tempo que a key pode ter sido comprometida sem detecção (ex: vazada em log, repositório Git, tráfego não criptografado); (2) 180 dias sem rotação viola boas práticas (recomendação AWS: rotacionar a cada 90 dias máximo) e provavelmente viola políticas de compliance. A ação correta não é simplesmente deletar a key atual (o pipeline quebraria), mas rotacionar: (1) criar uma nova access key 2 para o mesmo usuário; (2) atualizar o pipeline com a nova key (CI/CD secrets, parameter store, etc.); (3) aguardar alguns horas e verificar que o pipeline funciona com a nova key; (4) desativar a key antiga (não deletar ainda); (5) após 24-48h sem erros: deletar a key antiga. Paralelamente, avaliar migrar para IAM Roles via OIDC (GitHub Actions, CircleCI) eliminando access keys completamente.
