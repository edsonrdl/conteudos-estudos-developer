### Defense in Depth — segurança em camadas que protegem umas às outras

Defense in depth (defesa em profundidade) é o princípio de implementar múltiplas camadas independentes de controles de segurança, de forma que comprometer uma camada não seja suficiente para comprometer o sistema inteiro. É a estratégia de segurança análoga às muralhas, fosso e guardiões de um castelo medieval — o atacante precisa superar cada barreira sequencialmente. Na AWS, esse princípio se manifesta em controles que abrangem rede, identidade, aplicação, dados e monitoramento.

---

## A analogia do castelo

```
Castelo medieval — defense in depth clássico:

Camada 1: Fosso (perímetro)
  → Dificulta acesso inicial
  
Camada 2: Muralha externa
  → Barreira física para quem cruzou o fosso
  
Camada 3: Portão com guardas
  → Verificação de identidade
  
Camada 4: Torre de vigia
  → Monitoramento e detecção
  
Camada 5: Muralha interna
  → Segunda barreira para partes mais sensíveis
  
Camada 6: Cofre interno (tesouro)
  → Controles específicos para o ativo mais valioso

Se o atacante supera o fosso:
  → Ainda tem a muralha, portão, torre, muralha interna, cofre
  → Cada camada adiciona custo e tempo para o atacante
  → Em alguma camada: detecção e resposta

AWS — equivalente moderno:
  Camada 1: AWS Shield + CloudFront (perímetro/DDoS)
  Camada 2: VPC + Security Groups (rede)
  Camada 3: IAM + Cognito (identidade)
  Camada 4: WAF + aplicação (camada de aplicação)
  Camada 5: KMS + criptografia (dados)
  Camada 6: GuardDuty + CloudTrail (detecção)
```

## As camadas de defense in depth na AWS

### Camada 1: Borda (Edge) — antes de chegar na sua VPC

```
AWS Shield Standard (automático, gratuito):
  → Proteção contra DDoS na camada de rede (L3/L4)
  → SYN floods, UDP reflection, ICMP floods
  → Mitigação automática em milissegundos
  → Sem configuração necessária

AWS Shield Advanced ($3.000/mês por organização):
  → Proteção expandida (L3/L4/L7)
  → Proteção para recursos específicos (EC2, ALB, CloudFront, Route 53)
  → Equipe AWS DDoS Response Team (DRT) disponível
  → Proteção de custo: reembolso de escalonamento EC2 causado por DDoS

Amazon CloudFront como primeira linha:
  → CDN que absorve tráfego globalmente em edge locations
  → Ataque atinge CloudFront (não seu origin)
  → Origin só vê tráfego legítimo que passou pelo CloudFront
  → Geoblocking: bloqueia tráfego de países/regiões específicos

Route 53:
  → DNS resiliente e distribuído (sem SPOF)
  → Anycast routing: consultas respondidas pela edge mais próxima
  → Health checks: failover automático se origin falhar
```

### Camada 2: Rede — VPC e controles de tráfego

```
Topologia de VPC com defense in depth:

Internet
    │
[CloudFront + AWS WAF]        ← Camada de borda
    │
[Internet Gateway]
    │
[ALB em subnet pública]       ← Única entrada pública
    │    ↕ Security Group: só aceita 80/443 de qualquer IP
    │
[EC2/ECS em subnet privada]  ← Sem IP público
    │    ↕ Security Group: só aceita tráfego do ALB (SG-ALB)
    │
[RDS em subnet privada]      ← Completamente isolado
    │    ↕ Security Group: só aceita 5432 da subnet privada das apps
    │
[Sem saída direta para internet]  ← NAT Gateway se necessário

Múltiplos controles de rede:
  
  Security Groups (stateful):
  → Por instância: controla o que pode acessar cada recurso
  → Referência por Security Group ID (não por IP)
    → "EC2 pode falar com RDS" não "IP x.x.x.x pode falar com RDS"
    → Mais robusto: quando EC2 reinicia com novo IP, a regra ainda funciona
  
  NACLs (stateless):
  → Por subnet: complementa os Security Groups
  → Regras de DENY explícito para IPs maliciosos conhecidos
  → Bloqueio em nível de subnet, antes de chegar na instância
  
  VPC Flow Logs:
  → Registra todo o tráfego (aceito e rejeitado)
  → Fundamental para investigação de incidentes
  → "Quem tentou conectar na porta 3306 do banco?"

Isolamento por subnet:
  ├── Subnet pública: apenas recursos que precisam de IP público (ALB, NAT GW)
  ├── Subnet privada (app tier): EC2/ECS sem IP público
  ├── Subnet privada (data tier): RDS, ElastiCache, sem acesso da internet
  └── Subnet privada (management): Bastion/SSM, acesso restrito
```

### Camada 3: Identidade — IAM e autenticação

```
Defense in depth na identidade:

Autenticação múltipla:
  ├── MFA obrigatório para todos os usuários humanos
  ├── SSO (IAM Identity Center): usuários gerenciados centralmente
  ├── Roles para serviços (não credenciais de longa duração)
  └── OIDC para CI/CD (GitHub Actions com roles temporárias)

Autorização em camadas:
  
  SCP (nível organizacional):
  → "Nenhuma conta pode criar recursos fora de us-east-1"
  → Limite máximo que IAM policies não podem ultrapassar
  
  IAM Policy (nível de conta):
  → "Este usuário pode acessar apenas estes serviços específicos"
  
  Resource Policy (nível de recurso):
  → "Este bucket só aceita requisições desta account e desta role"
  
  Session Policy (nível de sessão):
  → "Este acesso temporário é válido apenas por 1 hora"
  
  Conditions (nível de contexto):
  → "Só permite se MFA está ativo e o IP é da rede corporativa"
  
  Um atacante que obtém uma credencial precisa superar
  todas as camadas de autorização, não apenas uma.

Segregação de ambientes:
  ├── Conta de dev: IAM users de desenvolvimento
  ├── Conta de staging: CI/CD roles, sem humanos diretos
  ├── Conta de produção: acesso humano mínimo, via SSO com MFA
  └── Conta de segurança: GuardDuty master, CloudTrail centralizados
  
  Comprometer a conta de dev não dá acesso a produção.
```

### Camada 4: Aplicação — WAF e controles de L7

```
AWS WAF — filtragem na camada de aplicação:
  
  Proteção contra OWASP Top 10:
  ├── SQL Injection: bloqueia payloads com padrões SQL maliciosos
  ├── XSS (Cross-Site Scripting): bloqueia scripts em parâmetros
  ├── LFI/RFI: bloqueia tentativas de path traversal
  ├── Rate-based rules: bloqueia IPs com excesso de requisições
  └── Geoblocking: bloqueia países sem usuários legítimos

  Managed Rules (atualizadas pela AWS/parceiros):
  ├── AWS Managed Rules - Common Rule Set
  ├── AWS Managed Rules - Known Bad Inputs
  ├── AWS Managed Rules - SQL Database
  ├── AWS Managed Rules - PHP Application
  └── Regras de provedores como Fortinet, F5, Imperva

  Custom Rules:
  → "Bloquear qualquer request com header User-Agent contendo 'scanner'"
  → "Rate limit: máximo 100 req/5min por IP"
  → "Bloquear requests sem header Authorization em /api/v1/*"

  Posicionamento: CloudFront (global) + ALB (regional):
  CloudFront WAF: bloqueia na edge, antes de chegar na região
  ALB WAF: segunda camada de filtragem se tráfego chegar direto ao ALB

Aplicação em si:
  ├── Validação de input em cada endpoint
  ├── Autenticação e autorização por endpoint
  ├── Tokens JWT com expiração curta
  └── Rate limiting na aplicação (além do WAF)
```

### Camada 5: Dados — criptografia e controles de acesso

```
Criptografia como camada independente:

"Mesmo que um atacante contorne todas as outras camadas
 e acesse o disco ou o banco, os dados são ilegíveis
 sem as chaves de criptografia."

Em repouso:
  ├── S3 SSE-KMS: chaves gerenciadas no KMS (CMK ou AWS managed)
  ├── EBS: criptografia de volume com KMS
  ├── RDS: criptografia de storage com KMS
  └── DynamoDB: criptografia com KMS (gratuito se AWS managed)

Em trânsito:
  ├── HTTPS obrigatório (HTTP → HTTPS redirect no ALB)
  ├── Certificados gerenciados pelo ACM (renovação automática)
  ├── TLS 1.2 mínimo (configurar no ALB/CloudFront)
  └── Conexão banco: SSL/TLS obrigatório (não opcional)

KMS — controle de acesso às chaves:
  {
    "Sid": "QuemPoDeUsarEstaChave",
    "Effect": "Allow",
    "Principal": {
      "AWS": "arn:aws:iam::123:role/producao-app-role"
    },
    "Action": ["kms:Decrypt", "kms:GenerateDataKey"],
    "Resource": "*",
    "Condition": {
      "StringEquals": {
        "kms:ViaService": "s3.us-east-1.amazonaws.com"
      }
    }
  }
  → Só a role de produção pode usar esta chave
  → Só via S3 (não pode usar diretamente via API)
  → CloudTrail: todo uso da chave é logado

Secrets Management:
  → Secrets Manager: credenciais rotacionadas automaticamente
  → Parameter Store: configurações com hierarquia e versionamento
  → Nunca em variáveis de ambiente em texto claro
  → Nunca em código ou repositórios Git
```

### Camada 6: Detecção e Resposta — monitoramento contínuo

```
"Assume breach": mesmo com todas as camadas de prevenção,
projete como se o atacante já estivesse dentro."

GuardDuty — threat detection inteligente:
  → Analisa CloudTrail, VPC Flow Logs, DNS logs via ML
  → Detecta comportamentos anômalos:
    "EC2 fazendo chamadas de API que nunca fez antes"
    "Credencial usada de IP que nunca usou antes"
    "Requisições para domínios de C2 conhecidos"
  → Habilitado em segundos, sem agente, sem mudança de infra

CloudTrail — auditoria completa:
  → Log de cada chamada de API na conta
  → Multi-region trail: nenhuma região esquecida
  → CloudTrail Insights: detecta atividade incomum (ex: spike de DeleteObject)
  → Armazenar em S3 com MFA Delete: nem admin pode deletar logs

AWS Config — detecção de drift de configuração:
  → "Security Group foi alterado para aceitar 0.0.0.0/0 às 14h32"
  → Auto-remediation: reverte automaticamente
  → Conformidade contínua com baseline definido

Amazon Macie — proteção de dados sensíveis no S3:
  → Detecta PII (CPF, email, cartão) em buckets S3
  → Alerta se dados sensíveis estiverem em bucket público
  → Avalia permissões de acesso dos buckets

Security Hub — painel unificado:
  → Agrega findings de GuardDuty, Inspector, Macie, Config
  → Score de postura de segurança por conta
  → Priorização automática por severidade
  → Integração com ferramentas SIEM (Splunk, DataDog Security)

VPC Flow Logs + CloudWatch Logs Insights:
  → "Mostre todas as conexões rejeitadas na porta 22 das últimas 24h"
  → "Qual instância fez mais conexões de saída ontem?"
  → Investigação forense quando incidente ocorre
```

## Como as camadas se protegem mutuamente

```
Cenário de ataque: SQL Injection tentativa

Camada 1 (WAF):
  Request: GET /api/users?id=1 OR 1=1
  WAF Rule: "SQL Injection pattern detected"
  Ação: BLOCK — request nunca chega à aplicação

Se WAF falhar (misconfigured rule):
Camada 4 (Aplicação):
  Query parametrizada:
  SELECT * FROM users WHERE id = ?  (parameter: "1 OR 1=1")
  → Banco trata como literal string, não como SQL
  → Ataque falha

Se aplicação não validar:
Camada 3 (IAM — banco):
  Usuário do banco tem: SELECT apenas na própria tabela
  → Não pode SELECT em outras tabelas
  → Não pode UPDATE, DELETE, DROP

Se o banco for comprometido:
Camada 5 (Criptografia):
  Dados no banco estão criptografados com KMS
  → Atacante lê bytes cifrados sem valor

Camada 6 (Detecção):
  GuardDuty: "Acesso incomum a tabela users às 3h"
  CloudTrail: "KMS key usada 1.000x em 1 minuto"
  Alerta → equipe de segurança → resposta ← em minutos

Resultado: ataque detectado e contido, dados protegidos
mesmo que múltiplos controles individuais tenham sido testados
```

## Configuração mínima de defense in depth para produção

```
NÍVEL 1 — Fundamentos (implementar no dia 1):
  ✓ VPC com subnets públicas e privadas em 2+ AZs
  ✓ Security Groups restritivos (default deny, allow específico)
  ✓ RDS e ElastiCache em subnets privadas
  ✓ IAM roles para EC2/Lambda (sem access keys em instâncias)
  ✓ MFA para todos os usuários IAM console
  ✓ CloudTrail multi-region habilitado
  ✓ S3 Block Public Access no nível de conta

NÍVEL 2 — Proteção adicional (implementar na primeira sprint):
  ✓ AWS WAF no ALB/CloudFront
  ✓ GuardDuty habilitado em todas as regiões
  ✓ AWS Config com regras básicas
  ✓ VPC Flow Logs habilitados
  ✓ Criptografia em repouso (RDS, EBS, S3)
  ✓ ACM para certificados (sem certs autoassinados em produção)
  ✓ Secrets Manager para credenciais (sem hardcoded)

NÍVEL 3 — Maturidade avançada:
  ✓ AWS Shield Advanced (para workloads críticos)
  ✓ Security Hub habilitado e integrado
  ✓ Amazon Macie para S3
  ✓ Amazon Inspector para EC2/containers
  ✓ Permission Boundaries para delegação segura
  ✓ SCPs em AWS Organizations
  ✓ IMDSv2 obrigatório em todas as instâncias
  ✓ Runbooks de resposta a incidentes testados
```

## 🧩 Quiz de Fixação

1. Um atacante conseguiu obter a execution role de uma Lambda com acesso ao S3. A Lambda está em uma VPC privada. Quais camadas de defense in depth ainda protegem os dados, e como cada uma contribui?
2. Por que configurar AWS WAF no CloudFront E no ALB (dupla proteção) é mais seguro do que apenas no CloudFront?
3. Um time de segurança descobre que um bucket S3 estava público por 3 horas antes de ser detectado pelo AWS Config. Quais camadas falharam, quais funcionaram, e o que implementar para reduzir o tempo de detecção a menos de 5 minutos?

**Respostas:**
1) Camadas que ainda protegem: (1) IAM/menor privilégio — se a role tem acesso apenas a um bucket específico e apenas GetObject, o atacante só acessa esses objetos, não todo o S3 nem outros serviços; (2) KMS — se os objetos estão criptografados com SSE-KMS, o atacante precisa usar a chave KMS que também tem policy restritiva; a Lambda pode usar a chave via kms:Decrypt, mas o atacante externo não tem permissão direta ao KMS, dificultando a exfiltração em texto claro; (3) VPC/rede — a Lambda está em VPC privada; o atacante externo não tem acesso direto à VPC, só pode agir através das APIs que a Lambda expõe; (4) CloudTrail/GuardDuty — todas as chamadas à API S3 e KMS são logadas; GuardDuty detecta comportamento anômalo como volume incomum de GetObject, atividade em horário incomum, ou acesso de IP/user-agent nunca visto antes — gerando alert para resposta.
2) Porque o CloudFront pode ser bypassado: se um atacante descobre o IP do ALB (via varredura, DNS reverso, certificado SSL, ou vazamento de header), pode enviar requests direto ao ALB, contornando o WAF do CloudFront. Com WAF também no ALB, o tráfego que chega diretamente ao ALB ainda é inspecionado. A configuração mais segura é: WAF no CloudFront (bloqueia na edge globalmente, antes de consumir recursos do origin) + WAF no ALB (segunda camada se CloudFront for bypassado) + Security Group do ALB aceitando apenas tráfego de IPs do CloudFront (lista mantida pela AWS: ip-ranges.amazonaws.com).
3) Camadas que falharam: prevenção não estava habilitada (S3 Block Public Access por conta poderia ter impedido a mudança), e a detecção demorou — AWS Config tem periodicidade de avaliação que pode ser de minutos a horas dependendo da configuração. Camadas que funcionaram: AWS Config eventualmente detectou e alertou. Para reduzir a detecção para menos de 5 minutos: (1) Habilitar S3 Block Public Access no nível de conta — previne a situação completamente; (2) CloudTrail + EventBridge: regra que detecta `PutBucketAcl` ou `PutBucketPolicy` em tempo real e dispara Lambda de verificação/remediação; (3) AWS Config com regra `s3-bucket-public-read-prohibited` em modo "triggered" (roda quando o recurso muda) em vez de periódico; (4) Config com Auto Remediation: quando a regra falha, SSM Automation reverte automaticamente a política do bucket para privado — sem esperar intervenção humana.
