### Segregação de funções — ninguém deve ter poder irrestrito de ponta a ponta

Segregação de funções (Separation of Duties — SoD) é o princípio de dividir tarefas críticas entre múltiplas pessoas ou sistemas, de forma que nenhum indivíduo ou processo tenha controle completo de uma operação do início ao fim. É simultaneamente um controle de segurança (previne abuso de acesso) e um controle de compliance (exigido por SOX, PCI DSS, ISO 27001). Na AWS, implementar SoD significa usar múltiplas contas, roles distintas, pipelines automatizados e aprovações explícitas para que nenhuma identidade única possa comprometer o ambiente sozinha.

---

## O problema que a segregação resolve

```
Sem segregação de funções:
  João é desenvolvedor sênior com acesso a:
  ├── Repositório de código (pode fazer commit)
  ├── Pipeline de CI/CD (pode aprovar deploy)
  ├── Conta AWS de produção (pode modificar infraestrutura)
  └── Banco de dados de produção (pode ler/modificar dados)
  
  João pode (sem aprovação de ninguém):
  → Inserir código malicioso
  → Aprovar o próprio PR
  → Fazer deploy direto em produção
  → Ler ou modificar dados de clientes
  → Cobrir os rastros modificando logs
  
  Risco: insider threat, erro humano catastrófico,
         comprometimento de credencial com blast radius total.

Com segregação de funções:
  João (desenvolvedor):
  ├── Repositório: pode fazer commit, NÃO pode aprovar PR
  ├── Pipeline: disparo automático, NÃO tem acesso manual
  ├── AWS produção: sem acesso direto (apenas via pipeline)
  └── Banco produção: sem acesso (apenas aplicação tem)
  
  Maria (tech lead):
  ├── Aprova PRs (não faz commits diretos em main)
  └── Sem acesso a produção (separação do aprovador)
  
  Pipeline automatizado:
  ├── Deploy automático após aprovação de PR
  └── Sem interação humana direta com produção
  
  Para comprometer a produção: João precisa de Maria.
  Para comprometer o banco: precisa comprometer a aplicação.
  Para cobrir rastros: CloudTrail é imutável.
```

## Os quatro pilares da segregação na AWS

### Pilar 1: Separação de ambientes por contas AWS

```
O isolamento mais forte é em nível de conta:

AWS Organizations — estrutura de contas:

  Management Account (apenas billing/org):
  └── Não tem workloads de aplicação
  └── Acessível apenas por Cloud Financial Management team

  Security Account (segurança centralizada):
  ├── GuardDuty master
  ├── Security Hub aggregator
  ├── CloudTrail central (S3 imutável)
  └── Acessível apenas por Security team

  Shared Services Account:
  ├── Active Directory / SSO
  ├── Ferramentas compartilhadas
  └── Acessível por Platform team

  Tooling Account (CI/CD):
  ├── CodePipeline, CodeBuild
  ├── Artifact registry (ECR)
  └── Deploy automation roles

  Development Account:
  └── Desenvolvedores têm acesso amplo (sandbox)

  Staging Account:
  ├── Apenas CI/CD pipeline tem acesso
  └── Nenhum desenvolvedor acessa diretamente

  Production Account:
  ├── Nenhum desenvolvedor acessa diretamente
  ├── Apenas pipeline assume role para deploy
  └── Break-glass role: acesso emergencial, auditado

Resultado:
  João não tem credencial na conta de produção.
  Não há senha ou access key que ele poderia usar.
  A única forma de alterar produção é pelo pipeline aprovado.
```

### Pilar 2: Separação de responsabilidades por role

```
IAM Roles com escopos distintos e não sobrepostos:

Developer Role (assumida por João):
  ├── CodeCommit: GitPull, GitPush
  ├── CloudWatch Logs: GetLogEvents (apenas dev account)
  ├── S3: GetObject nos buckets de dev
  └── PROIBIDO: iam:*, ec2:*, rds:*, cloudformation:*

Tech Lead Role (assumida por Maria):
  ├── CodeCommit: GitPull, MergePullRequest (não GitPush direto)
  ├── CodePipeline: visualizar status, aprovar stage manual
  └── PROIBIDO: deploy direto, modificar infra

SRE/DevOps Role:
  ├── EC2, ECS, RDS: criar e gerenciar INFRAESTRUTURA
  ├── CloudFormation: deploy de stacks
  └── PROIBIDO: modificar código da aplicação, acessar dados de prod

Security Team Role:
  ├── IAM: criar roles, gerenciar permissões
  ├── GuardDuty, Security Hub: visualizar findings
  ├── CloudTrail: visualizar logs
  └── PROIBIDO: modificar aplicações, acessar dados de negócio

Database Admin Role:
  ├── RDS: criar, modificar, snapshot
  └── PROIBIDO: acesso direto aos dados (queries)

Data Access Role (apenas aplicação usa):
  ├── Execute queries via RDS Proxy
  └── Apenas a aplicação assume essa role (não humanos)
```

### Pilar 3: Pipeline como único vetor de deploy

```
Nenhum humano faz deploy manual em produção:

Fluxo de deploy com segregação:

  Developer (João):
  git push origin feature/nova-feature
                    ↓
  Pull Request criado automaticamente
                    ↓
  Code Review obrigatório (Tech Lead / outro dev):
  ├── Revisão de código
  ├── Testes passando
  └── Aprovação: Maria clica "Merge"
                    ↓
  Pipeline automatizado dispara (sem interação humana):
  ├── Build + testes unitários
  ├── Security scan (SAST)
  ├── Deploy em staging automaticamente
  ├── Testes de integração em staging
  └── Stage manual de aprovação (para produção):
      → Maria ou outro tech lead aprova
      → (Quem aprovou PR ≠ quem aprova deploy — separação adicional)
                    ↓
  Deploy em produção (apenas pelo pipeline):
  ├── Pipeline assume role de deploy (sts:AssumeRole)
  ├── CloudFormation/ECS apply
  └── Nenhuma credencial humana tocou produção

Controle técnico que torna isso real:
  Production account SCP:
  {
    "Effect": "Deny",
    "Action": [
      "ecs:UpdateService",
      "cloudformation:UpdateStack",
      "ec2:RunInstances"
    ],
    "Resource": "*",
    "Condition": {
      "StringNotLike": {
        "aws:PrincipalArn": "arn:aws:iam::prod-account:role/PipelineDeployRole"
      }
    }
  }
  → Apenas a PipelineDeployRole pode fazer deploy em produção
  → SCP garante que NENHUM outro IAM user/role — nem admin — pode
```

### Pilar 4: Aprovação de 4 olhos para operações críticas

```
"Four eyes principle" — operações críticas exigem 2 aprovadores

Exemplos de operações que exigem aprovação dupla:

1. Deploy em produção:
   Aprovação 1: Tech Lead (revisou código)
   Aprovação 2: QA/Release Manager (validou staging)
   
   CodePipeline Manual Approval:
   {
     "name": "ApproveProduction",
     "actions": [{
       "actionTypeId": {
         "category": "Approval",
         "owner": "AWS",
         "provider": "Manual"
       },
       "configuration": {
         "NotificationArn": "arn:aws:sns:...:deploy-approvals",
         "CustomData": "Staging validado. Aprovar deploy em produção?"
       }
     }]
   }

2. Criação de nova IAM policy com permissões amplas:
   Criador: DevOps engenheiro
   Aprovador: Security team
   
   Implementação: Pull Request no repositório Terraform de IAM
   → Merge requer aprovação do Security team (CODEOWNERS)

3. Acesso emergencial a produção (Break-glass):
   Solicitante: engenheiro de plantão
   Aprovador: manager on-call
   
   Implementação:
   ├── Ticket criado no sistema de incidentes
   ├── Manager aprova via Slack bot
   ├── Lambda cria acesso temporário (1 hora)
   ├── Todas as ações logadas no CloudTrail
   └── Acesso revogado automaticamente após 1 hora
```

## Segregação e compliance: SOX, PCI DSS, ISO 27001

### SOX (Sarbanes-Oxley Act)

```
Aplicável para: empresas públicas americanas (e subsidiárias)
Objetivo: prevenir fraude contábil e proteger investidores

Requisitos SOX relevantes para TI:

Section 404 — Controles internos sobre relatórios financeiros:
  → Sistemas que processam dados financeiros devem ter controles
  → SoD é um controle fundamental

SoD para sistemas financeiros na AWS:
  ├── Quem configura o sistema ≠ quem opera o sistema
  ├── Quem aprova transações ≠ quem as processa
  ├── Quem faz deploy ≠ quem tem acesso a dados financeiros
  └── Todos os acessos são auditados (CloudTrail)

Evidência para auditoria SOX:
  ├── IAM policies documentadas: quem tem acesso a quê
  ├── Pipeline logs: quem aprovou cada deploy
  ├── CloudTrail: quem acessou sistemas financeiros e quando
  └── Credential Report: usuários ativos e seus últimos acessos
```

### PCI DSS (Payment Card Industry)

```
Requirement 6.3.2 — Separation of duties:
  "Separação de funções entre pessoal responsável por
   desenvolvimento e manutenção de sistemas de produção"
  
  Na AWS:
  ├── Desenvolvedor ≠ pode fazer deploy em produção (Req 6.4.2)
  ├── Testador ≠ pode fazer deploy em produção
  └── Conta de desenvolvimento separada da conta de produção

Requirement 7 — Restrict access:
  "Acesso a componentes do sistema e dados do portador de cartão
   restrito aos indivíduos com necessidade de negócio"
  
  Na AWS:
  ├── Apenas a aplicação de pagamento acessa dados PCI
  ├── Desenvolvedores não têm acesso a dados de cartão em produção
  └── DBA não pode executar queries em tabelas PCI sem aprovação

Evidência para QSA:
  ├── Diagrama da arquitetura com separação de contas
  ├── IAM policies mostrando segregação
  ├── Pipeline configuration mostrando aprovações obrigatórias
  └── CloudTrail demonstrando que apenas pipeline acessa produção
```

### ISO 27001 — Controle A.6.1.2

```
Controle A.6.1.2: Segregação de funções
  "Tarefas e áreas de responsabilidade conflitantes devem ser
   segregadas para reduzir oportunidades de modificação não
   autorizada ou não intencional ou uso indevido dos ativos"

Conflitos de interesse a detectar e resolver:
  ├── Desenvolvedor de segurança que também audita segurança
  ├── Admin de banco que também desenvolve queries de negócio
  ├── Engenheiro de infra que também aprova seus próprios PRs
  └── Único admin que configura e verifica seus próprios backups

Evidência:
  ├── Matriz de separação de funções (RACI adaptado)
  └── IAM policies documentadas por função
```

## Implementação técnica com AWS Organizations + SCPs

```
Estrutura de SCPs para enforce de SoD:

SCP: NoDirectProductionAccess (aplicada à conta de produção)
{
  "Effect": "Deny",
  "Action": [
    "ec2:RunInstances", "ec2:TerminateInstances",
    "ecs:UpdateService", "ecs:RegisterTaskDefinition",
    "rds:ModifyDBInstance", "rds:DeleteDBInstance",
    "cloudformation:CreateStack", "cloudformation:UpdateStack",
    "lambda:UpdateFunctionCode", "lambda:CreateFunction"
  ],
  "Resource": "*",
  "Condition": {
    "ArnNotLike": {
      "aws:PrincipalArn": [
        "arn:aws:iam::prod-account:role/PipelineDeployRole",
        "arn:aws:iam::prod-account:role/BreakGlassEmergencyRole"
      ]
    }
  }
}

SCP: NoIAMChangesWithoutSecurityApproval (todas as contas dev/staging)
{
  "Effect": "Deny",
  "Action": [
    "iam:CreateRole", "iam:AttachRolePolicy",
    "iam:PutRolePolicy", "iam:CreatePolicy"
  ],
  "Resource": "*",
  "Condition": {
    "ArnNotLike": {
      "aws:PrincipalArn": "arn:aws:iam::*:role/SecurityApprovedIAMRole"
    }
  }
}

SCP: ProtectCloudTrail (todas as contas)
{
  "Effect": "Deny",
  "Action": [
    "cloudtrail:DeleteTrail", "cloudtrail:StopLogging",
    "cloudtrail:PutEventSelectors"
  ],
  "Resource": "*"
}
→ Ninguém, nem admins, pode desabilitar auditoria
```

## Matriz de segregação — exemplo prático

```
AÇÃO                     │ Dev  │ Tech Lead │ DevOps │ Security │ Pipeline
─────────────────────────┼──────┼───────────┼────────┼──────────┼─────────
Escrever código          │  ✓   │     ✓     │        │          │
Fazer commit em main     │      │     ✓     │        │          │   ✓
Aprovar PR               │      │     ✓     │        │          │
Deploy em staging        │      │           │        │          │   ✓
Aprovar deploy em prod   │      │     ✓     │        │          │
Deploy em produção       │      │           │        │          │   ✓
Modificar IAM policies   │      │           │   ✓    │    ✓     │
Revisar CloudTrail logs  │      │           │        │    ✓     │
Acessar dados de prod    │      │           │        │          │
Responder incidente      │      │           │   ✓    │    ✓     │
Criar/modificar infra    │      │           │   ✓    │          │   ✓
Aprovar mudança infra    │      │     ✓     │        │    ✓     │

Regras críticas de segregação:
  ├── Dev não aprova próprio PR (precisa de Tech Lead)
  ├── Ninguém faz deploy manual em produção (apenas pipeline)
  ├── Quem escreve código ≠ quem aprova deploy
  └── Quem gerencia IAM (DevOps) ≠ quem audita IAM (Security)
```

## Break-glass — acesso emergencial auditado

```
"O que fazer quando produção está em chamas e precisa de
acesso direto urgente, mas ninguém tem permissão?"

Break-glass role — acesso de emergência controlado:

Propriedades:
  ├── IAM Role com permissões amplas de produção
  ├── Trust policy: apenas pessoas pré-autorizadas podem assumir
  ├── Duração: máximo 1 hora (sts:AssumeRole com DurationSeconds)
  ├── CloudTrail: CADA ação loada e alertada
  └── Pós-incidente: revisão obrigatória de tudo que foi feito

Processo:
  1. Engenheiro identifica emergência
  2. Abre ticket de incidente (PagerDuty/Opsgenie)
  3. Manager on-call aprova via Slack bot
  4. Lambda cria acesso temporário (1 hora)
  5. Engenheiro age com acesso de break-glass
  6. Acesso expira automaticamente após 1 hora
  7. CloudWatch Alarm: "Break-glass role assumed!" → notifica CISO
  8. Post-mortem: revisão de todas as ações realizadas

CloudWatch Alarm para uso de break-glass:
  EventBridge Rule:
  {
    "source": ["aws.sts"],
    "detail-type": ["AWS API Call via CloudTrail"],
    "detail": {
      "eventName": ["AssumeRole"],
      "requestParameters": {
        "roleArn": ["arn:aws:iam::prod:role/BreakGlassEmergencyRole"]
      }
    }
  }
  → Target: SNS → email para CTO, CISO, Security team
  → "ALERTA: Acesso de emergência ativado por [usuário] às [hora]"
```

## 🧩 Quiz de Fixação

1. Uma empresa passa por auditoria PCI DSS e o QSA questiona que desenvolvedores têm acesso direto à conta de produção AWS. Por que isso viola o requisito de segregação do PCI DSS e qual arquitetura de contas AWS resolve o problema?
2. O CTO argumenta que a equipe é pequena (3 pessoas) e segregação de funções "não faz sentido com time tão pequeno". Quais riscos específicos esse argumento ignora, e como implementar segregação mínima efetiva mesmo com 3 pessoas?
3. Uma Lambda function no ambiente de produção precisa ser atualizada com urgência para corrigir um bug crítico. O engenheiro plantão quer fazer o update direto via console AWS. Por que isso viola SoD e qual o processo correto mesmo em situação de urgência?

**Respostas:**
1) O PCI DSS Requirement 6.4.2 exige que ambientes de desenvolvimento e produção sejam separados — a mesma pessoa não deve ter acesso a ambos simultaneamente, pois poderia introduzir código malicioso em desenvolvimento e fazer deploy diretamente em produção sem revisão. Com acesso direto à conta de produção, um desenvolvedor pode: bypasear o processo de aprovação de código, modificar funções Lambda ou configurações diretamente no console, acessar dados de cartão de crédito. A arquitetura de contas AWS que resolve: conta separada para desenvolvimento (devs têm acesso amplo), conta separada para produção (devs sem acesso — apenas a role do pipeline de CI/CD pode fazer deploy). SCP na conta de produção nega qualquer ação de deploy para ARNs que não sejam a PipelineDeployRole. Desenvolvedores simplesmente não têm credenciais válidas para a conta de produção.
2) O argumento ignora três riscos reais: (1) Insider threat — mesmo em times pequenos, um único acidente, descontentamento ou comprometimento de credencial pode ter impacto catastrófico quando não há controles; (2) Erro humano — sem revisão por outra pessoa, bugs críticos ou mudanças destrutivas chegam a produção com muito maior frequência; (3) Compliance — clientes enterprise e auditores exigem SoD mesmo em empresas pequenas; sem ele, contratos são perdidos. Segregação mínima com 3 pessoas: (1) Código: commits em feature branches por qualquer um, mas merge em main exige aprovação de pelo menos uma outra pessoa (GitHub branch protection + CODEOWNERS); (2) Deploy: pipeline automático após merge — ninguém faz deploy manual (o pipeline é a "quarta pessoa"); (3) IAM: mudanças de permissões revisadas por outra pessoa antes de aplicar; (4) Produção: break-glass com alerta imediato para os outros dois quando usado. O pipeline automatizado efetivamente atua como um controlador neutro separado das pessoas.
3) Viola SoD porque um único engenheiro modificaria código em produção sem revisão — exatamente o que a segregação previne. O processo correto mesmo em urgência: (1) Abrir pull request com a correção (pode ser rápido — 5 minutos de código); (2) Solicitar aprovação emergencial de outro membro do time via mensagem direta/Slack (não esperar processo normal de 24h — urgência justifica revisão em 10 minutos); (3) Após aprovação, o pipeline automaticamente detecta o merge e faz deploy acelerado em staging e produção; (4) Se o tempo realmente não permite nem 15 minutos de pipeline: usar o processo de break-glass com aprovação do manager, que cria acesso temporário de 1 hora, com TODAS as ações logadas e notificação imediata ao time de segurança e CTO. O break-glass não elimina a segregação — mantém auditabilidade completa e exige aprovação prévia de outra pessoa.
