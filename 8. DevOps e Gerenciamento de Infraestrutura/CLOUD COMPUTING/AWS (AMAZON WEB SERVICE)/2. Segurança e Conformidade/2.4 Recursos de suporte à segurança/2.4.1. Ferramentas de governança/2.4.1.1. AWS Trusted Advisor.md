### AWS Trusted Advisor — consultor automatizado de boas práticas AWS

AWS Trusted Advisor é um serviço que analisa continuamente sua conta AWS e fornece recomendações em tempo real com base nas melhores práticas em cinco categorias: custo, performance, segurança, tolerância a falhas e limites de serviço. É como ter um especialista AWS revisando sua conta 24/7 e sinalizando quando algo está fora do padrão recomendado — sem precisar disparar manualmente nenhuma auditoria.

---

## As cinco categorias do Trusted Advisor

```
CUSTO (Cost Optimization):
  → Identifica recursos ociosos e oportunidades de economia
  → "Esta instância EC2 tem CPU < 5% há 14 dias → candidata a stop"
  → "Você tem Reserved Instances não utilizadas"
  → "Estes Elastic IPs não estão associados a instâncias"

PERFORMANCE (Performance):
  → Identifica gargalos e oportunidades de melhoria
  → "CloudFront pode ser configurado para servir este conteúdo S3"
  → "Instâncias EC2 com alta utilização de CPU consistente"
  → "Security Groups com regras excessivamente permissivas afetando performance"

SEGURANÇA (Security):
  → Detecta configurações que violam boas práticas de segurança
  → "Porta 22 (SSH) aberta para 0.0.0.0/0"
  → "Conta root sem MFA"
  → "S3 buckets com permissão de acesso público"
  → "Credenciais IAM expostas"

TOLERÂNCIA A FALHAS (Fault Tolerance):
  → Identifica configurações que criam pontos únicos de falha
  → "RDS sem Multi-AZ habilitado"
  → "EC2 sem Auto Scaling configurado"
  → "EBS snapshots não criados há mais de 7 dias"

LIMITES DE SERVIÇO (Service Limits):
  → Monitora uso de recursos vs. limites da conta
  → "Você está usando 80% do limite de instâncias EC2 em us-east-1"
  → "Você está usando 90% do limite de VPCs por região"
  → Previne falhas por atingir limite inesperadamente
```

## Níveis de acesso por plano de suporte

```
BASIC e DEVELOPER (acesso limitado):
  Apenas 6 verificações de segurança:
  ├── S3 Bucket Permissions (acesso público)
  ├── Security Groups - Specific Ports Unrestricted (SSH/RDP aberto)
  ├── IAM Use (uso de IAM em vez de root)
  ├── MFA on Root Account
  ├── EBS Public Snapshots
  └── RDS Public Snapshots
  
  + Todas as verificações de Service Limits (limites)

BUSINESS e ENTERPRISE (acesso completo):
  Todas as verificações: ~115 verificações em todas as 5 categorias
  API access: integração com sistemas externos
  CloudWatch integration: alarmes automáticos
  Refresh automático semanal dos dados
  
  Verificações adicionais importantes:
  ├── IAM Access Key Rotation
  ├── Exposed Access Keys (keys em repositórios públicos)
  ├── EC2 instances with low utilization
  ├── Unassociated Elastic IP Addresses
  ├── Idle Load Balancers
  └── Underutilized EBS Volumes
```

## Status de cada verificação

```
Cada verificação tem um dos três status:

✅ Verde (OK):
   Nenhum problema detectado — configuração está correta

⚠️ Amarelo (Investigation Recommended):
   Possível problema — recomenda investigar
   Ex: instância EC2 com CPU entre 10-20% (pode ser ociosidade ou uso legítimo)

🔴 Vermelho (Action Recommended):
   Problema confirmado — ação necessária
   Ex: bucket S3 público, porta 22 aberta para 0.0.0.0/0, MFA desabilitado

ℹ️ Azul (Informational):
   Informação útil sem ação imediata necessária
```

## Verificações de segurança em detalhes

```
Security Groups — Specific Ports Unrestricted:
  Detecta: SGs com portas críticas abertas para 0.0.0.0/0 ou ::/0
  Portas monitoradas:
  ├── 20/21: FTP
  ├── 22: SSH
  ├── 23: Telnet
  ├── 25: SMTP
  ├── 110: POP3
  ├── 135: RPC
  ├── 143: IMAP
  ├── 445: SMB
  ├── 1433/1434: SQL Server
  ├── 3306: MySQL
  ├── 3389: RDP (Windows Remote Desktop)
  └── 5432: PostgreSQL
  
  Status VERMELHO para qualquer dessas portas aberta para 0.0.0.0/0.
  
  Ação: restringir ao IP necessário (ex: apenas IP do administrador)

IAM Use:
  Detecta: conta com apenas usuário root e sem IAM users/roles
  → Boas práticas: criar IAM users para operações do dia a dia
  → Root apenas para tarefas que exigem root

MFA on Root Account:
  Detecta: conta root sem MFA configurado
  Status: VERMELHO (crítico)
  Ação: configurar MFA imediatamente

Exposed Access Keys:
  Detecta: access keys IAM que a AWS identificou em repositórios públicos
  (GitHub, GitLab, BitBucket, code snippets, fóruns)
  Status: VERMELHO (crítico — chave comprometida!)
  Ação: desativar/deletar a chave e investigar uso indevido
```

## Automação com CloudWatch e EventBridge

```
Trusted Advisor publica eventos no EventBridge quando status muda:

EventBridge rule para alertas automáticos:
  {
    "source": ["aws.trustedadvisor"],
    "detail-type": ["Trusted Advisor Check Item Refreshed"],
    "detail": {
      "status": ["ERROR", "WARN"]
    }
  }
  
  Target: SNS → email/Slack para time de segurança

CloudWatch Alarms para verificações de Service Limits:
  Metric: AWS/TrustedAdvisor → ServiceLimits
  Dimension: CheckName + ServiceName + Region
  
  Alarm: "EC2 On-Demand Instances Usage" > 80% do limite
  → SNS → alerta → solicitar aumento de limite antes de atingir
  
  Isso previne falhas inesperadas onde instâncias EC2 não conseguem
  ser criadas por limite atingido durante Auto Scaling.
```

## AWS Trusted Advisor vs. AWS Security Hub

```
                    Trusted Advisor         Security Hub
                    ─────────────────       ──────────────────────
Foco               Boas práticas gerais    Segurança e compliance
Categorias         5 (custo, perf, seg...) Apenas segurança
Fontes             Análise da própria conta GuardDuty, Inspector,
                                            Macie, Config, + parceiros
Standards          Não                     CIS, PCI DSS, FSBP
Findings           Verificações pontuais   Eventos contínuos
Remediação         Sugestões               Automation possível
Custo              Business plan requer    $0.001/finding (volume)
Uso principal      Otimização geral        Postura de segurança

Usar ambos em conjunto:
  → Trusted Advisor: visão geral + custo + limites + performance
  → Security Hub: postura de segurança detalhada + compliance
  → Não são redundantes — complementares
```

## Casos de uso práticos

```
1. REDUÇÃO DE CUSTOS MENSAL:
   Agenda: todo dia 1 do mês, revisar Trusted Advisor
   → Verificação "Underutilized EC2 Instances": lista de candidatos
   → Verificação "Idle Load Balancers": ALBs sem tráfego para deletar
   → Verificação "Unassociated Elastic IPs": IPs ociosos ($0.005/hora)
   → Ação: stop/terminate + delete = economia imediata

2. PREVENÇÃO DE INCIDENTES DE DISPONIBILIDADE:
   Monitor: Service Limits com CloudWatch Alarm
   → "Você está usando 85% do limite de instâncias"
   → Solicitar aumento de limite antes do Auto Scaling precisar
   → Previne: Auto Scaling falha silenciosamente durante pico de tráfego

3. AUDITORIA DE SEGURANÇA RÁPIDA:
   Nova conta AWS ou conta que nunca foi auditada:
   → Abrir Trusted Advisor → Security
   → Em 5 minutos: lista de todos os problemas críticos de segurança
   → Priorizar: vermelhos primeiro, amarelos depois

4. RELATÓRIO EXECUTIVO MENSAL:
   Lambda agendada mensalmente:
   → Busca status de todas as verificações via API
   → Gera relatório: X problemas críticos, Y resolvidos este mês
   → Envia para CISO/CTO como indicador de saúde da conta
```

## 🧩 Quiz de Fixação

1. O Trusted Advisor mostra verificação VERMELHA "Security Groups — SSH (22) Open to 0.0.0.0/0" em 3 Security Groups de produção. Qual é o risco específico e quais são as duas alternativas para corrigir sem interromper o acesso dos administradores?
2. Uma empresa usa o plano de suporte Basic. Quais verificações de segurança ela tem acesso no Trusted Advisor e qual é o principal argumento para upgradar para o plano Business em termos de segurança?
3. Por que monitorar os "Service Limits" via Trusted Advisor + CloudWatch Alarm é crítico para aplicações com Auto Scaling, e qual o cenário de falha silenciosa que isso previne?

**Respostas:**
1) O risco específico: qualquer IP na internet pode tentar conectar via SSH à instância — bots automatizados varrem a internet em busca de portas 22 abertas e realizam ataques de força bruta contra credenciais SSH (root, admin, ubuntu, ec2-user). Uma credencial fraca ou chave SSH mal protegida resulta em comprometimento completo da instância. Duas alternativas para corrigir: (1) Restringir a 0.0.0.0/0 para apenas o IP fixo do administrador (`203.0.113.10/32`) — simples, mas problemático se o admin usa IP dinâmico (casa, hotel); (2) Fechar a porta 22 completamente e usar AWS Systems Manager Session Manager — o administrador acessa a instância via console/CLI sem SSH, sem abrir nenhuma porta no Security Group, com todas as ações registradas no CloudTrail. Session Manager é a abordagem mais segura e recomendada pela AWS.
2) No plano Basic, o acesso ao Trusted Advisor se limita a 6 verificações de segurança: S3 Bucket Permissions, Security Groups com portas críticas abertas, uso de IAM (vs. root), MFA na conta root, EBS Public Snapshots e RDS Public Snapshots. O argumento principal para upgradar para Business: no plano Business, todas as ~115 verificações ficam disponíveis, incluindo verificações críticas como "Exposed Access Keys" (detecta access keys IAM vazadas em repositórios GitHub/GitLab públicos — provavelmente o tipo de comprometimento mais comum e devastador em contas AWS), "IAM Access Key Rotation" (identifica keys sem rotação há mais de 90 dias), e acesso à API do Trusted Advisor para integração com sistemas de monitoramento. A verificação de Exposed Access Keys sozinha justifica o upgrade — uma key vazada descoberta pelo Trusted Advisor pode prevenir um incidente de custo de dezenas de milhares de dólares.
3) Quando o Auto Scaling tenta criar novas instâncias EC2 durante um pico de tráfego, se o limite da conta para instâncias EC2 naquela região já foi atingido, o Auto Scaling falha ao criar as instâncias sem gerar nenhum erro visível para o usuário da aplicação — simplesmente não cria novas instâncias. O resultado: a aplicação não escala quando mais precisa, usuários enfrentam timeout e degradação durante o pico, e o time de operações não entende por que o Auto Scaling não funcionou (o evento de falha de Auto Scaling não é óbvio). Monitorar com Trusted Advisor + CloudWatch Alarm previne isso: quando o uso atinge 80% do limite, o alarme dispara uma notificação para o time de infra, que então abre um ticket no AWS Support solicitando aumento de limite — processo que leva horas a poucos dias. O limite é aumentado antes de ser atingido durante um pico real, garantindo que o Auto Scaling funcione quando necessário.
