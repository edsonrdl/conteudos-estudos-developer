### AWS Well-Architected Tool — revisão estruturada de arquiteturas AWS

AWS Well-Architected Tool é o serviço que implementa o AWS Well-Architected Framework como uma ferramenta interativa de revisão. Ele guia equipes técnicas por questionários estruturados sobre seu workload, identifica riscos de alto e médio impacto em relação às melhores práticas AWS, e gera planos de melhoria priorizados. É a diferença entre "achamos que estamos bem arquitetados" e "temos evidência estruturada de onde estamos e o que melhorar".

---

## O que é o AWS Well-Architected Framework

```
Framework criado pela AWS com base em anos de revisão de
arquiteturas de clientes em produção. Define:

OS 6 PILARES:
  1. Excelência Operacional
     → Como operar e monitorar sistemas para entregar valor
     
  2. Segurança
     → Como proteger informações, sistemas e ativos
     
  3. Confiabilidade
     → Como garantir que workloads executam as funções
        pretendidas e se recuperam de falhas
     
  4. Eficiência de Performance
     → Como usar recursos de computação eficientemente
     
  5. Otimização de Custos
     → Como evitar custos desnecessários
     
  6. Sustentabilidade (adicionado em 2021)
     → Como minimizar impacto ambiental

PRINCÍPIOS DE DESIGN:
  → Stop guessing capacity needs (use elasticidade)
  → Test systems at production scale (load testing real)
  → Automate to make experimentation easier (IaC)
  → Allow for evolutionary architectures (mudança contínua)
  → Drive architectures using data (métricas reais)
  → Improve through game days (chaos engineering)
```

## Como funciona a Well-Architected Tool

### Criar um Workload

```
Acesso: Console AWS → Well-Architected Tool → Workloads → Define Workload

Campos do Workload:
  ├── Nome: "Plataforma de E-commerce - Checkout"
  ├── Descrição: o que o sistema faz e para quem
  ├── Ambiente: produção / pré-produção
  ├── Regiões AWS utilizadas
  ├── Nível de profissionalismo (para calibrar perguntas)
  └── Lenses a aplicar (Framework base + Lenses específicas)

Boas práticas de definição:
  → Um workload por sistema/produto significativo
  → Não agrupar toda a empresa em um workload
  → Time responsável pelo workload participa da revisão
  → Revisar ao menos anualmente ou após mudanças significativas
```

### Executar a Revisão

```
A revisão é um questionário por pilar:

Exemplo de perguntas por pilar:

EXCELÊNCIA OPERACIONAL:
  OPS 1: How do you determine what your priorities are?
  OPS 2: How do you structure your organization to support your business outcomes?
  OPS 5: How do you reduce defects, ease remediation, and improve flow into production?
  
  Para cada pergunta: selecionar as melhores práticas que o workload implementa

SEGURANÇA:
  SEC 1: How do you securely operate your workload?
  SEC 2: How do you manage identities for people and machines?
  SEC 6: How do you protect your compute resources?
  
CONFIABILIDADE:
  REL 1: How do you manage service quotas and constraints?
  REL 7: How do you design your workload to withstand component failures?
  REL 10: How do you use fault isolation to protect your workload?

PERFORMANCE:
  PERF 1: How do you select the best performing architecture?
  PERF 4: How do you select your storage solution?

CUSTO:
  COST 2: How do you govern usage?
  COST 6: How do you meet cost targets when you select resource type, size and number?

SUSTENTABILIDADE:
  SUS 1: How do you select Regions to support your sustainability goals?
  SUS 4: How do you take advantage of software and architecture patterns to support your sustainability goals?
```

### Risk Identification — entender o resultado

```
Após responder todas as perguntas:

HIGH RISK (HRI — High Risk Issues):
  → Práticas ausentes que provavelmente causarão incidentes graves
  → Exemplos: sem backup automatizado, sem Multi-AZ para banco crítico,
    sem autenticação na API pública, sem alarmes para erros
  → Ação: remediar com prioridade máxima

MEDIUM RISK (MRI — Medium Risk Issues):
  → Práticas ausentes que podem causar problemas, mas risco gerenciável
  → Exemplos: sem rate limiting na API, sem right-sizing periódico,
    sem documentação de runbooks
  → Ação: incluir no planejamento de próximos sprints

NONE:
  → Pergunta respondida adequadamente — boas práticas implementadas

Relatório resumo:
  Well-Architected Report:
  ├── Pillar: Reliability
  │     HRI: 3 | MRI: 5
  │     "Workload does not have a DR strategy tested"
  ├── Pillar: Security
  │     HRI: 1 | MRI: 3
  │     "IAM roles have overly permissive policies"
  └── Pillar: Cost Optimization
        HRI: 0 | MRI: 7
        "No compute optimizer recommendations applied"
```

## Plano de Melhoria — da revisão à ação

```
Para cada High Risk ou Medium Risk identificado:
  → Tool sugere melhores práticas a implementar
  → Link para documentação AWS relevante
  → Você pode adicionar notas e marcar como "acknowledged" (ciência do risco)
  → Ou marcar como item de melhoria com owner e data alvo

Fluxo de melhoria:

1. Revisão identifica HRI: "Sem estratégia de backup testada"
2. Well-Architected Tool: link para AWS Backup documentation
3. Time cria ticket: "Implementar AWS Backup + testar restore"
4. Sprint: implementa AWS Backup + cria runbook de restore
5. Teste: simula restore e valida RPO/RTO
6. Well-Architected Tool: atualiza a resposta da pergunta REL-9
7. HRI removido do relatório
8. Próxima revisão: confirma que a prática continua implementada

Milestone (versão da revisão):
  → Antes de uma revisão: salva Milestone "2024-Q1 Baseline"
  → Após melhorias: salva Milestone "2024-Q2 After Remediation"
  → Comparação: visualizar progresso entre milestones
  → "Fomos de 12 HRI para 3 HRI em 90 dias"
```

## Lenses — especialização por domínio

```
Além do Framework base (6 pilares), existem Lenses:
conjuntos de perguntas adicionais para domínios específicos.

Lenses disponíveis:

AWS Lenses (gratuitas):
  ├── Serverless Lens: para workloads Lambda + API Gateway + DynamoDB
  ├── SaaS Lens: para empresas que vendem software como serviço
  ├── IoT Lens: para soluções de Internet of Things
  ├── Machine Learning Lens: para workloads de ML
  ├── Data Analytics Lens: para pipelines de dados e analytics
  ├── SAP Lens: para workloads SAP na AWS
  ├── Games Industry Lens: para jogos online
  └── Financial Services Lens: para fintech e bancos

Custom Lenses (você cria):
  → Define perguntas específicas do seu contexto empresarial
  → Ex: "Seguimos as políticas de segurança da nossa empresa?"
  → Compartilhável entre contas da organização

Quando usar Lenses:
  Um e-commerce com checkout via Lambda:
  → Framework base (6 pilares): revisão geral
  → Serverless Lens: perguntas específicas de Lambda/serverless
  → Resultado: visão mais completa do que só o framework base
```

## Well-Architected Reviews em escala — organizações

```
Para empresas com múltiplas contas e workloads:

AWS Well-Architected Tool + Organizations:
  → Compartilhar workloads entre contas (para times centrais)
  → Relatórios agregados de HRI/MRI por toda a organização
  → Um time de arquitetura vê todos os workloads da empresa

AWS Partners (AWS Well-Architected Partners):
  → Parceiros certificados pela AWS para conduzir WAF reviews
  → Vantagem: isenção de créditos AWS após a review (via Partner)
  → Para: revisões mais aprofundadas com facilidador especializado
  → Processo: parceiro conduz as entrevistas, você responde

Integração com AWS Security Hub:
  → HRI de segurança do Well-Architected aparecem como findings
  → Visibilidade centralizada no Security Hub
  → EventBridge: quando novo HRI identificado → notificação automática
```

## Cadência de revisão recomendada

```
INICIAL (novo workload):
  → Revisar antes de ir para produção
  → Identificar riscos antes que estejam em produção
  → Corrigir na fase de desenvolvimento (mais barato)

ANUAL (manutenção):
  → Revisão completa do workload
  → Verifica que melhorias do ano anterior foram mantidas
  → Identifica novos riscos por mudanças no sistema

APÓS EVENTOS SIGNIFICATIVOS:
  → Lançamento de nova feature grande
  → Após incidente de produção
  → Após crescimento 10x de usuários
  → Após mudança de regulação que afeta o workload
  → Após migração de serviço significativo

GAME DAY (complementar à revisão):
  → Simular falhas para validar confiabilidade
  → AWS FIS (Fault Injection Simulator)
  → Chaos Engineering para confirmar que REL responses funcionam
```

## Well-Architected Tool vs. Trusted Advisor

```
                    Well-Architected Tool   Trusted Advisor
                    ─────────────────────   ───────────────
Tipo               Questionário guiado      Verificação automática
Disparo            Manual (você inicia)     Contínuo (automático)
Profundidade       Alta (perguntas abertas) Média (checks binários)
Contexto           Você define o workload   Analisa tudo na conta
Foco               Arquitetura + processo   Configuração técnica
Output             Plano de melhoria        Lista de issues
Custo              Gratuito                 Plano Business para tudo
Ideal para         Revisão planejada        Monitoramento contínuo

Usar os dois em conjunto:
  → Trusted Advisor: detecta problemas técnicos automaticamente
  → Well-Architected Tool: revisão estruturada periódica de arquitetura
  → Não são substitutos — são complementares
```

## 🧩 Quiz de Fixação

1. Durante uma Well-Architected Review, o workload recebe 8 High Risk Issues no pilar de Confiabilidade, incluindo "O workload não tem estratégia de DR testada" e "Não há Multi-AZ para o banco de dados principal". Como você priorizaria a remediação entre esses dois itens e qual o critério de decisão?
2. O que são Lenses no Well-Architected Tool e por que um time de Data Engineering que usa Athena, Glue e S3 deveria usar a Data Analytics Lens além do Framework base?
3. Um CTO propõe fazer a Well-Architected Review do sistema de pagamentos apenas uma vez, "quando lançar o produto". Por que isso é insuficiente e qual seria a cadência correta para um sistema de pagamentos em produção?

**Respostas:**
1) Critério de priorização: impacto no negócio + probabilidade de ocorrência + custo de remediação. Entre os dois: (1) Multi-AZ para banco de dados deve ser priorizado primeiro — a falha do banco de dados primário sem standby causa downtime imediato e perda de transações; é um SPOF (ponto único de falha) que pode ocorrer a qualquer momento por falha de hardware, patch de OS, ou problema de AZ; habilitar Multi-AZ é uma mudança simples e rápida (algumas horas de janela de manutenção, sem código a alterar). (2) Estratégia de DR testada é importante mas de escopo maior — envolve definir RPO/RTO, implementar AWS Backup, criar runbooks, testar o processo end-to-end; leva mais tempo para implementar adequadamente. Critério final: o Multi-AZ resolve o risco de indisponibilidade imediata do banco (catastrófico, imediato) enquanto o DR resolve o risco de recuperação após desastre maior (importante, mas mais raro); ambos são críticos, mas o Multi-AZ tem menor esforço e maior impacto imediato na confiabilidade do dia a dia.
2) Lenses são conjuntos de perguntas adicionais específicas para domínios ou padrões arquiteturais que o Framework base não cobre com suficiente profundidade. O Framework base (6 pilares) faz perguntas gerais sobre confiabilidade, custo, segurança — válidas para qualquer workload. A Data Analytics Lens adiciona perguntas específicas para pipelines de dados como: "Como você gerencia a qualidade e consistência dos dados durante transformações?", "Como você lida com dados sensíveis e PII em pipelines de analytics?", "Como você monitora a saúde de jobs Glue e o impacto de falhas no pipeline?", "Como você gerencia custos de consultas Athena (scanning excessivo)?". Para um time de Data Engineering, o Framework base sozinho pode não identificar riscos como: particionamento inadequado no S3 causando scans desnecessários ($$$), ausência de validação de qualidade de dados entre etapas do pipeline, ou dados de produção sendo copiados para ambientes de analytics sem anonimização. A Data Analytics Lens captura esses riscos específicos do domínio.
3) Uma única revisão no lançamento é insuficiente por quatro razões: (1) O sistema evolui — features adicionadas, arquitetura refatorada, volume crescente mudam o perfil de riscos; o que era adequado no lançamento pode tornar-se inadequado após 6 meses de crescimento; (2) O ambiente de ameaças muda — novas CVEs, novos padrões de ataque, novas regulações (ex: mudança na interpretação de compliance PCI DSS) podem criar novos riscos; (3) Incidentes revelam lacunas — cada incidente de produção expõe práticas ausentes que não foram identificadas na revisão inicial; (4) Boas práticas evoluem — a própria AWS atualiza o Framework com novas perguntas e melhores práticas periodicamente. Cadência correta para sistema de pagamentos: Anual (revisão completa + nova certificação); Após cada incidente de produção relevante (post-mortem aciona revisão parcial do pilar afetado); Após mudança significativa de arquitetura (ex: migração de EC2 para Lambda); Antes de eventos de alto tráfego previsíveis (ex: Black Friday — revisão de confiabilidade e performance); Após qualquer mudança regulatória relevante para PCI DSS ou BACEN.
