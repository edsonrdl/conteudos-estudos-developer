### Internet pública — como recursos AWS se conectam e são expostos à internet

A internet pública é o meio de conectividade padrão para aplicações que precisam ser acessíveis a usuários externos ou consumir serviços externos. Na AWS, a arquitetura de acesso à internet é deliberada — você define explicitamente quais recursos têm IP público, quais saem para internet via NAT, e quais ficam completamente isolados. Entender os componentes (Internet Gateway, NAT Gateway, Elastic IP) e o princípio de exposição mínima é fundamental para construir arquiteturas seguras e funcionais.

---

## O modelo de rede pública vs. privada na AWS

```
Arquitetura de VPC com exposição mínima (padrão recomendado):

Internet
    │
[Internet Gateway] ← única porta de entrada/saída para internet
    │
┌───┴──────────────────────────────────────────┐
│  VPC (10.0.0.0/16)                           │
│                                              │
│  Subnet PÚBLICA (10.0.1.0/24):              │
│  ├── Application Load Balancer              │ ← recebe tráfego externo
│  └── NAT Gateway                           │ ← saída da rede privada
│                                              │
│  Subnet PRIVADA - App (10.0.2.0/24):       │
│  └── EC2 / ECS / Lambda (sem IP público)   │ ← não acessível diretamente
│                                              │
│  Subnet PRIVADA - Data (10.0.3.0/24):      │
│  └── RDS / ElastiCache (sem IP público)    │ ← completamente isolada
└──────────────────────────────────────────────┘

Regra: o mínimo de recursos possível na subnet pública.
       Apenas o que PRECISA ser público (ALB, NAT GW) fica lá.
```

## Internet Gateway (IGW) — a porta da VPC para internet

```
O que é:
  → Componente altamente disponível que a AWS provisiona na VPC
  → Permite que recursos com IP público se comuniquem com a internet
  → Stateful: permite respostas de saída para conexões de entrada
  → Um por VPC (não tem custo de hora — gratuito)

O que o IGW faz:
  1. NAT para instâncias com IP público:
     EC2 com IP público (10.0.1.50 / 54.23.45.67):
     → Pacote saindo: src=10.0.1.50 → IGW substitui por 54.23.45.67
     → Pacote entrando: dst=54.23.45.67 → IGW substitui por 10.0.1.50
     
  2. Rota de saída para 0.0.0.0/0:
     Route Table (subnet pública):
     Destination    Target
     10.0.0.0/16   local
     0.0.0.0/0     igw-xxxxxxxx  ← qualquer IP externo → via IGW

O que o IGW NÃO faz:
  → Não cria IPs públicos (você precisa alocar Elastic IPs)
  → Não roteia tráfego de subnets privadas (sem IP público = sem saída)
  → Não filtra tráfego (isso é papel do Security Group/NACL)

Criar e associar:
  aws ec2 create-internet-gateway
  aws ec2 attach-internet-gateway \
    --internet-gateway-id igw-xxx \
    --vpc-id vpc-yyy
  
  # Adicionar rota na subnet pública
  aws ec2 create-route \
    --route-table-id rtb-xxx \
    --destination-cidr-block 0.0.0.0/0 \
    --gateway-id igw-yyy
```

## NAT Gateway — saída para internet sem exposição de entrada

```
O que é:
  → Serviço gerenciado que permite que instâncias em subnets PRIVADAS
    se conectem à internet (saída) sem terem IP público
  → Sem conexões de entrada (apenas inicia conexões, não recebe)
  → Stateful: respostas de saída são permitidas automaticamente

Por que NAT Gateway é necessário:
  Instância EC2 privada (10.0.2.50, sem IP público):
  → Precisa fazer: apt-get update, download de bibliotecas, API calls
  → Sem NAT: não tem como sair para internet (sem IP público)
  → Com NAT Gateway: tráfego vai para NAT GW → IGW → internet

Funcionamento:
  EC2 privada (10.0.2.50) → [NAT GW (10.0.1.100 / 54.10.20.30)] → Internet
  
  Source: 10.0.2.50 → NAT traduz para 54.10.20.30 (Elastic IP do NAT)
  Sites externos veem: 54.10.20.30 (IP do NAT, não da EC2)
  Conexões de entrada para 54.10.20.30: não chegam à EC2 privada

Route Table da subnet privada:
  Destination    Target
  10.0.0.0/16   local
  0.0.0.0/0     nat-xxxxxxxx  ← saída via NAT Gateway

Custo do NAT Gateway:
  $0.045/hora (us-east-1) = ~$32/mês
  + $0.045/GB processado
  
  Para 100 GB/mês processados: $32 + $4.50 = $36.50/mês

NAT Gateway por AZ (alta disponibilidade):
  ├── NAT GW na AZ-a → para instâncias em subnet privada AZ-a
  ├── NAT GW na AZ-b → para instâncias em subnet privada AZ-b
  └── NAT GW na AZ-c → para instâncias em subnet privada AZ-c
  
  Se a AZ-a cair: instâncias em AZ-a vão junto (não importa o NAT)
  → Não é necessário cross-AZ para o NAT GW
  → Um NAT GW por AZ = resiliente e sem custo de cross-AZ data transfer

NAT Gateway vs. NAT Instance (legado):
  NAT Gateway: gerenciado pela AWS, escalável, HA automático
  NAT Instance: EC2 com forwarding IP (você gerencia, single point of failure)
  → SEMPRE use NAT Gateway (exceto custo muito baixo/lab)
```

## Elastic IP (EIP) — IP público estático

```
O que é:
  → Endereço IPv4 público estático alocado para sua conta
  → Persiste mesmo se a instância for parada/reiniciada
  → Pode ser remapeado rapidamente entre instâncias/ENIs

Diferença de IP público dinâmico:
  IP público dinâmico (auto-assign):
  → Atribuído na inicialização, muda a cada stop/start
  → Gratuito enquanto a instância está rodando
  → Problemático para: DNS fixo, whitelists, certificados
  
  Elastic IP:
  → Estático — não muda
  → Custo: gratuito se associado a instância running
  → Custo: $0.005/hora se NÃO associado (incentivo a não deixar ociosos)

Casos de uso:
  ├── NAT Gateway (precisa de EIP)
  ├── Bastion Host (IP fixo para whitelist)
  ├── Servidor de email (IP fixo para reputação SPF/DMARC)
  └── Aplicação que não usa ALB (single EC2 com IP fixo)

Boa prática:
  → Preferir ALB + Route 53 em vez de EIP direto na EC2
  → EIP direto expõe a instância; ALB abstrai
  → Menos EIPs = menor superfície de exposição

Alocar e associar:
  aws ec2 allocate-address --domain vpc
  # Retorna: AllocationId = eipalloc-xxx, PublicIp = 54.10.20.30
  
  aws ec2 associate-address \
    --instance-id i-yyy \
    --allocation-id eipalloc-xxx
```

## VPC Endpoints — acessar serviços AWS sem internet

```
Problema sem VPC Endpoints:
  EC2 em subnet privada → NAT GW → IGW → S3 (endpoint público)
  → Tráfego sai da VPC, passa pelo IGW, vai à internet, volta
  → Custo de NAT GW + data transfer
  → Tráfego passa por internet (mesmo que dentro da AWS)

Com VPC Endpoints:
  EC2 em subnet privada → VPC Endpoint → S3 (direto, sem internet)
  → Tráfego nunca sai da rede AWS
  → Sem custo de NAT GW para esses serviços
  → Mais seguro: S3 Bucket Policy pode exigir acesso via VPC Endpoint

Tipos de VPC Endpoints:

1. Gateway Endpoint (gratuito):
   Disponível para: S3 e DynamoDB
   
   Route Table modificada:
   Destination                    Target
   10.0.0.0/16                   local
   0.0.0.0/0                     nat-xxxxxxxx
   pl-xxxxxx (S3 prefix list)    vpce-xxxxxxxx  ← via endpoint, não NAT
   
   EC2 → S3: rota automaticamente via endpoint (sem código mudando)

2. Interface Endpoint (custo ~$0.01/hora por AZ):
   Para outros serviços: SQS, SNS, Secrets Manager, SSM, etc.
   Cria ENI privado na subnet → DNS resolve para IP privado
   
   Exemplo: Secrets Manager via Interface Endpoint:
   EC2 → secretsmanager.us-east-1.amazonaws.com
   → Resolve para 10.0.2.XXX (IP privado do endpoint)
   → Sem sair da VPC, sem internet

Quando usar VPC Endpoints:
  → S3 e DynamoDB: SEMPRE (Gateway é gratuito)
  → Secrets Manager, SSM, ECR: se instâncias são privadas
    (evita necessidade de NAT GW ou rota para internet)
  → Custo-benefício: endpoint de $7/mês vs. NAT GW de $32/mês
    para workloads que acessam muito SSM ou Secrets Manager
```

## Boas práticas de exposição à internet

```
PRINCÍPIO: expor o mínimo possível, com o mínimo de privilégio

1. NUNCA colocar banco de dados com IP público:
   ❌ RDS com PubliclyAccessible=true
   ✓ RDS em subnet privada, acessível apenas pela aplicação

2. NUNCA colocar EC2 de aplicação diretamente na internet:
   ❌ EC2 com IP público recebendo requisições HTTP na porta 80
   ✓ ALB (público) → EC2 (subnet privada, sem IP público)

3. USAR ALB em vez de IP direto:
   ❌ DNS apontando para IP da EC2 diretamente
   ✓ Route 53 → ALB → EC2 (ALB abstrai e protege)
   
   Vantagens do ALB:
   ├── SSL termination (não precisa de cert na EC2)
   ├── Health checks automáticos
   ├── Integração com WAF
   └── Troca de instância sem mudança de DNS

4. MINIMIZAR EIPs:
   → Cada EIP é uma superfície de ataque
   → ALB tem IP dinâmico (gerenciado pela AWS, com HA)
   → EIP direto na EC2: se EC2 for comprometida, o IP é dela

5. S3 buckets: Block Public Access por padrão:
   → Habilitar no nível da conta (bloqueia todos os buckets)
   → Exceção explícita apenas para buckets que precisam ser públicos
     (ex: hosting de site estático)

6. Security Groups: default deny para entrada:
   → Nenhum SG padrão deve ter 0.0.0.0/0 na entrada
   → Entrada permitida apenas para:
     ALB SG → EC2 SG (referência por SG, não por IP)
     Specific IP → Bastion SG (administração)

7. CloudFront na frente de tudo:
   → Absorve DDoS (Shield Standard automático)
   → WAF na edge
   → Origin fica oculta (IP do ALB não exposto diretamente)
   → Cache + compressão reduzem carga no backend
```

## Fluxos de tráfego — entrar e sair da internet

```
FLUXO 1 — Usuário → Aplicação (entrada):
  Internet → CloudFront → ALB (subnet pública) → EC2 (subnet privada)
  
  IP público: apenas o CloudFront/ALB tem
  EC2: sem IP público, inacessível diretamente da internet

FLUXO 2 — EC2 privada → Internet (saída):
  EC2 (subnet privada) → NAT Gateway (subnet pública) → IGW → Internet
  
  EC2: sem IP público (não recebe conexões de entrada)
  NAT GW: tem EIP, faz NAT para a EC2
  Internet: vê o IP do NAT GW

FLUXO 3 — EC2 → Serviço AWS (via endpoint):
  EC2 (subnet privada) → VPC Endpoint → S3/SQS/SM/etc.
  
  Sem passar por NAT GW ou IGW
  Sem custo de NAT GW para esse tráfego
  Mais seguro: tráfego permanece na rede AWS

FLUXO 4 — Usuário → Site estático (S3):
  Internet → CloudFront → S3 (Origin Access Control)
  
  S3 bucket: privado (sem acesso público direto)
  CloudFront: única forma de acessar os objetos
  OAC (Origin Access Control): S3 Policy permite apenas CloudFront
```

## 🧩 Quiz de Fixação

1. Uma instância EC2 em uma subnet privada precisa baixar atualizações do sistema via `apt-get update`. A subnet privada tem Route Table com apenas `10.0.0.0/16 → local`. O que precisa ser adicionado à arquitetura e como configurar o roteamento para que a EC2 acesse a internet sem ter IP público?
2. Um arquiteto percebe que a conta AWS tem 15 Elastic IPs alocados mas apenas 5 instâncias ativas. Quais são os dois problemas dessa situação e como resolver?
3. Uma aplicação em EC2 privada faz 1.000 chamadas por hora ao AWS Secrets Manager. Atualmente o tráfego vai: EC2 → NAT Gateway → IGW → Secrets Manager (endpoint público). Como um VPC Interface Endpoint melhora segurança E custo nesse cenário?

**Respostas:**
1) Para que a EC2 privada acesse a internet sem ter IP público, é necessário: (1) Criar um NAT Gateway em uma subnet pública da VPC (que já deve ter Internet Gateway e rota `0.0.0.0/0 → igw-xxx`); (2) O NAT Gateway precisa de um Elastic IP alocado; (3) Na Route Table da subnet privada onde está a EC2, adicionar a rota: `0.0.0.0/0 → nat-xxxxxxxx`. Com essa configuração: quando a EC2 tenta `apt-get update`, o pacote vai para o NAT GW (via rota `0.0.0.0/0`), o NAT GW substitui o IP source privado pelo seu Elastic IP e encaminha via IGW para a internet. A resposta volta pelo caminho inverso. A EC2 nunca tem IP público — não pode receber conexões de entrada, apenas inicia conexões de saída.
2) Dois problemas: (1) Custo desnecessário — EIPs não associados a instâncias running custam $0.005/hora cada = $0.12/dia × 10 EIPs ociosos = $1.20/dia = $36/mês desperdiçados. A AWS cobra para desencorajar o desperdício de espaço de endereços IPv4; (2) Superfície de exposição — EIPs alocados são IPs públicos que podem ser alvos de scanning e ataques mesmo sem instância associada (alguém pode tentar conectar neles); além disso, se remapearmos um EIP de uma instância comprometida para outra, o IP problemático continua na conta. Solução: auditoria via `aws ec2 describe-addresses --query 'Addresses[?AssociationId==null]'` → lista EIPs sem associação → liberar (`aws ec2 release-address`) todos que não são necessários. Implementar automação: EventBridge + Lambda que alerta quando EIP fica sem associação por mais de 24h.
3) Segurança: sem o endpoint, o tráfego EC2 → Secrets Manager passa pelo NAT Gateway → Internet Gateway → endpoint público do Secrets Manager na internet (mesmo que seja dentro da AWS, tecnicamente vai ao IP público). Com o Interface Endpoint, o tráfego permanece dentro da rede privada AWS — o DNS resolve `secretsmanager.us-east-1.amazonaws.com` para um IP privado da VPC. Adicionalmente, o Secrets Manager Endpoint Policy pode restringir acesso apenas à VPC específica (`aws:sourceVpc`), impedindo que credentials sejam acessados de fora da VPC. Custo: NAT Gateway cobra $0.045/GB processado. 1.000 chamadas/hora × cada chamada ~1 KB de resposta = ~24 MB/dia × 30 = ~720 MB/mês de data NAT processing = custo insignificante aqui, mas o Interface Endpoint ($0.01/hora = $7.20/mês) elimina completamente o custo de NAT para esse tráfego E melhora a segurança. Para volumes maiores (logs, S3), a economia do endpoint é ainda mais expressiva.
