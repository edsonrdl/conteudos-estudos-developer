### AWS Direct Connect — link dedicado e privado entre on-premises e AWS

AWS Direct Connect é uma conexão de rede dedicada e privada entre seu data center (ou escritório) e a AWS — sem passar pela internet pública. Enquanto a VPN Site-to-Site usa a internet como meio de transporte (com latência variável e largura de banda compartilhada), o Direct Connect oferece um link físico exclusivo com latência determinística, throughput garantido e sem o overhead de criptografia IPsec. É a solução para workloads que precisam de conectividade híbrida previsível, de alto volume e consistente.

---

## Por que Direct Connect em vez de VPN

```
VPN Site-to-Site:
  Seu data center ── internet pública ── Região AWS
  ├── Latência: variável (50-200ms, dependendo do ISP)
  ├── Bandwidth: 1.25 Gbps máximo por túnel
  ├── Confiabilidade: dependente da internet
  ├── Jitter: alto (tráfego compartilha com outros usuários)
  └── Criptografia: AES-256 (overhead de CPU)

AWS Direct Connect:
  Seu data center ── fibra dedicada ── backbone AWS ── Região AWS
  ├── Latência: determinística e baixa (5-20ms São Paulo → us-east-1)
  ├── Bandwidth: 1 Mbps a 100 Gbps
  ├── Confiabilidade: SLA da operadora + AWS backbone
  ├── Jitter: mínimo (link dedicado)
  └── Sem criptografia nativa (adicionar MACsec ou VPN over DX)

Quando Direct Connect é necessário:
  ├── Migrações massivas de dados (terabytes por dia)
  ├── Aplicações que exigem latência consistente
  ├── Alto volume de dados transferidos (custo de egress menor)
  ├── Compliance que proíbe dados na internet pública
  └── Vídeo/voz em tempo real entre on-prem e cloud
```

## Como o Direct Connect funciona fisicamente

```
Topologia física:

Seu Data Center (São Paulo)
    │
    │ Fibra do cliente
    │ (você contrata operadora local)
    ▼
Direct Connect Location (São Paulo)
    [Equinix SP1, Tivit, etc.]
    │
    │ Cross-connect: cabo físico dentro do data center colocado
    │ conectando seu equipment ao equipment da AWS
    ▼
AWS Direct Connect Router
    │
    │ Backbone privado da AWS
    ▼
Região AWS (sa-east-1, us-east-1, etc.)

Processo de provisionamento:
  1. AWS provisiona uma porta em um DX Location
  2. Você (ou parceiro) conecta seu equipment ao DX Location
  3. Cross-connect físico: cabo dentro do DX Location
  4. Configuração de BGP em ambos os lados
  5. Virtual Interfaces criadas para rotear para serviços/VPCs
```

## Tipos de conexão Direct Connect

### Dedicated Connection (conexão dedicada)

```
Você recebe uma porta física exclusiva no equipment da AWS:

Capacidades disponíveis:
  ├── 1 Gbps (SFP+, transceiver single-mode)
  ├── 10 Gbps (SFP+, transceiver single-mode)
  └── 100 Gbps (QSFP28, transceiver single-mode)

Processo:
  1. Solicitar conexão via Console AWS
  2. AWS provê Letter of Authorization (LOA-CFA)
  3. Você apresenta LOA-CFA ao DX Location para o cross-connect
  4. DX Location instala o cabo físico (~3-5 dias úteis)
  5. Configurar BGP e VIFs no console AWS

Vantagem:
  → Porta física exclusiva: toda a capacidade para você
  → Máxima previsibilidade

Desvantagem:
  → Mais lento para provisionar (semanas a meses)
  → Custo de porto é alto ($0.30/hora para 10 Gbps em us-east-1)
  → Mínimo de capacidade alta
```

### Hosted Connection (conexão hospedada)

```
Parceiro AWS Direct Connect compartilha a infraestrutura física
e você aluga uma fração da capacidade:

Capacidades disponíveis:
  50 Mbps, 100 Mbps, 200 Mbps, 300 Mbps, 400 Mbps, 500 Mbps,
  1 Gbps, 2 Gbps, 5 Gbps, 10 Gbps

Parceiros no Brasil:
  ├── Oi (operadora de telecomunicações)
  ├── Algar Telecom
  ├── TIVIT (infraestrutura de DX Location)
  └── Outros parceiros certificados

Vantagem:
  → Provisionamento mais rápido (dias vs. semanas)
  → Menor capacidade mínima (50 Mbps vs. 1 Gbps)
  → Custo menor para volumes menores

Desvantagem:
  → Compartilhamento de infraestrutura física com outros clientes
  → Menor previsibilidade que Dedicated em caso de saturação
  → Depende do gerenciamento do parceiro
```

## Virtual Interfaces (VIFs) — tipos de acesso

```
Virtual Interface é a configuração lógica sobre a conexão física
que define para onde o tráfego vai:

Uma conexão física pode ter múltiplas VIFs:
  10 Gbps Dedicated Connection
  ├── Private VIF → VPC de Produção
  ├── Private VIF → VPC de Staging
  ├── Transit VIF → Transit Gateway (N VPCs)
  └── Public VIF → Serviços públicos AWS (S3, SQS, etc.)
```

### Private VIF — acesso a VPCs

```
Conecta on-premises diretamente a uma VPC via Virtual Private Gateway:

Uso: acessar instâncias EC2, RDS, ElastiCache, e outros
     recursos privados dentro de uma VPC específica

Configuração:
  ├── VLAN ID: 100 (para separar tráfego no trunk)
  ├── BGP ASN: seu ASN on-premises (ex: 65000)
  ├── Endereços BGP: IPs de peering (ex: 169.254.100.0/30)
  ├── Prefixos anunciados: suas redes on-prem (ex: 10.0.0.0/8)
  └── Virtual Private Gateway: o VGW da sua VPC

Limitação:
  → Um Private VIF por VPC (via VGW)
  → Para múltiplas VPCs: usar Transit VIF

Roteamento:
  BGP on-prem → AWS:
  "Anuncio 10.0.0.0/8 (minha rede on-prem)"
  
  BGP AWS → on-prem:
  "Anuncio 172.16.0.0/12 (CIDR da VPC)"
  
  Resultado: pacotes roteados automaticamente via BGP
```

### Transit VIF — acesso a múltiplas VPCs via Transit Gateway

```
Conecta on-premises ao Transit Gateway, que roteia para N VPCs:

Topologia:
  On-premises
      │
  [Direct Connect]
      │
  [Transit VIF]
      │
  [Transit Gateway]
      ├── VPC Produção (172.16.0.0/16)
      ├── VPC Staging (172.17.0.0/16)
      ├── VPC Dev (172.18.0.0/16)
      └── VPC Data (172.19.0.0/16)

Vantagem:
  → Uma conexão DX + Transit Gateway → acesso a todas as VPCs
  → Sem criar Private VIF por VPC (mais simples de gerenciar)
  → Transit Gateway também conecta VPCs entre si
  → Central para roteamento híbrido complexo

Custo adicional:
  → Transit Gateway: $0.05/hora + $0.02/GB processado
  → Vale o custo para múltiplas VPCs
```

### Public VIF — acesso a endpoints públicos da AWS

```
Acesso a serviços AWS públicos sem passar pela internet:

Exemplos de serviços acessíveis via Public VIF:
  ├── Amazon S3 (endpoint público)
  ├── Amazon SQS, SNS
  ├── DynamoDB (endpoint público)
  ├── API Gateway
  └── Outros serviços com endpoints públicos

Uso:
  → Transferir dados on-prem → S3 sem passar pela internet
  → Custo de data transfer menor que internet
  → Latência mais baixa e consistente
  
  ATENÇÃO: Public VIF acessa o endpoint PÚBLICO do serviço
  → S3 via Public VIF: endpoint público (não VPC endpoint)
  → Para acesso privado: usar Private VIF + VPC Endpoint

Configuração:
  → BGP: anunciar prefixo AWS específico ou all AWS prefixes
  → A AWS anuncia seus prefixos públicos para sua rede on-prem
  → Tráfego para esses prefixos vai pelo DX, não pela internet
```

## Resiliência — arquiteturas de alta disponibilidade

```
Direct Connect SLA: 99.9% por conexão
Para HA real: múltiplas conexões

NÍVEL 1 — Alta disponibilidade (99.99%):
  Duas conexões Dedicated em DX Locations DIFERENTES
  (ou Hosted de operadoras diferentes)
  
  DX Location A (Equinix SP1)       DX Location B (Tivit)
        │                                   │
  Conexão 1 (ativa)              Conexão 2 (standby/ativo)
        │                                   │
        └──────────── VGW ou TGW ──────────┘
  
  Se DX Location A falhar: tráfego automático para Conexão 2
  Se operadora A falhar: idem

NÍVEL 2 — Máxima resiliência (99.999%+):
  DX Location A com 2 conexões
  + DX Location B com 2 conexões
  + VPN como fallback adicional
  
  Total: 4 conexões físicas + VPN
  Usado por: bancos, telcos, missão crítica absoluta

NÍVEL 3 — Desenvolvimento/Baixo risco:
  1 conexão DX + VPN como fallback
  
  DX (primário, latência baixa)
  ├── Se DX cair: BGP remove rotas DX
  ├── VPN assume automaticamente
  └── Latência aumenta mas conectividade mantida

BGP para failover DX → VPN:
  DX routes: AS Path curto (preferido)
  VPN routes: AS Path prepending (menos preferido)
  
  Quando DX cai: rotas DX removidas
  → BGP usa VPN routes automaticamente
  → Failover sem intervenção humana
```

## MACsec — criptografia no Direct Connect

```
Direct Connect NÃO criptografa nativamente.
Para segurança dos dados em trânsito: adicionar MACsec

MACsec (IEEE 802.1AE):
  → Criptografia na camada de enlace (Layer 2)
  → AES-256 nativo
  → Sem overhead de CPU significativo
  → Transparente para protocolos de camada superior

Suporte:
  → Apenas em Dedicated Connections (não Hosted)
  → Apenas em 10 Gbps e 100 Gbps
  → Não disponível em todas as regiões

Alternativa para Hosted ou onde MACsec não está disponível:
  → VPN over Direct Connect:
    IPsec tunnel transportado sobre o link DX
    Criptografado, mas com algum overhead de latência
    
Recomendação:
  Dados não classificados: MACsec suficiente
  Dados altamente sensíveis: VPN over DX (criptografia adicional)
  Compliance específico (ex: PCI data): verificar requisito exato
```

## Custo do Direct Connect

```
Componentes de custo:

1. PORTO (Port Fee):
   Dedicated 1 Gbps (us-east-1):  $0.30/hora = $216/mês
   Dedicated 10 Gbps (us-east-1): $1.50/hora = $1.080/mês
   Dedicated 100 Gbps:            negociado
   
   Hosted: custo do parceiro (varia significativamente)

2. DATA TRANSFER (egress da AWS para on-prem):
   Standard: $0.02/GB (us-east-1 → on-prem)
   vs. internet: $0.09/GB
   → DX é 4.5x mais barato para egress de alto volume

3. CROSS-CONNECT (DX Location):
   ~$300-$500/mês por conexão (cobrado pelo data center parceiro)

Custo total típico (1 Gbps Dedicated, us-east-1):
  Porto: $216/mês
  Cross-connect: $400/mês
  Data transfer (1 TB/mês): $20/mês
  Total: ~$636/mês

Quando DX compensa vs. VPN:
  VPN: $72/mês + $0.09/GB egress
  DX 1 Gbps: $636/mês + $0.02/GB egress
  
  Break-even em dados:
  (636 - 72) / (0.09 - 0.02) = 8.057 GB/mês ≈ 8 TB/mês
  
  Se você transfere > 8 TB/mês entre on-prem e AWS:
  → Direct Connect é mais barato que VPN mesmo com o custo do porto
  → Além disso: latência melhor e mais confiável
```

## 🧩 Quiz de Fixação

1. Uma empresa precisa transferir 100 TB/mês de dados on-premises para S3 (backup e analytics). Atualmente usa a internet (link de 1 Gbps). Calcule o custo mensal atual vs. com Direct Connect (assumindo custo de egress de $0.09/GB via internet e $0.02/GB via DX, porto de $1.080/mês para 10 Gbps, cross-connect de $400/mês) e quando DX é a escolha certa.
2. Uma empresa tem uma conexão Direct Connect de 10 Gbps e quer que tanto a VPC de produção quanto a VPC de staging tenham acesso on-prem via DX. Quais são as duas arquiteturas possíveis e qual é mais recomendada para uma empresa que planeja escalar para 10+ VPCs?
3. O Direct Connect não tem criptografia nativa. Uma empresa com requisitos PCI DSS precisa garantir que dados de cartão transmitidos entre on-prem e AWS via Direct Connect estejam criptografados. Quais são as duas opções técnicas e qual é mais adequada para uma conexão Hosted de 1 Gbps?

**Respostas:**
1) Custo atual via internet: 100 TB = 100.000 GB × $0.09 = $9.000/mês em egress + custo do link de internet (já existe, custo incremental zero para esse cálculo). Custo com Direct Connect 10 Gbps: Porto $1.080 + Cross-connect $400 + Data transfer 100.000 GB × $0.02 = $2.000 = $3.480/mês total. Economia: $9.000 - $3.480 = $5.520/mês = $66.240/ano. Além da economia, o DX oferece throughput muito superior — 100 TB via link de 1 Gbps levaria ~9 dias; via DX de 10 Gbps, menos de 1 dia. DX é claramente a escolha correta: economia significativa, velocidade 10x maior e latência consistente para os workloads de analytics que consomem os dados transferidos.
2) Duas arquiteturas: (1) **Private VIF por VPC** — criar um Private VIF separado para cada VPC, cada um apontando para o Virtual Private Gateway da sua VPC. Funciona mas escala mal: 10 VPCs = 10 Private VIFs, cada um com configuração BGP separada, limite de VIFs por conexão, complexidade operacional alta. (2) **Transit VIF + Transit Gateway** — criar um único Transit VIF que conecta ao Transit Gateway; o TGW roteia para todas as VPCs conectadas a ele. Recomendada para quem planeja escalar: adicionar uma nova VPC requer apenas conectá-la ao Transit Gateway (sem novo VIF, sem nova configuração BGP), uma única configuração de roteamento centralizada, e o Transit Gateway funciona como hub para interconexão entre as próprias VPCs também. O custo adicional do TGW ($0.05/hora + $0.02/GB) é amplamente justificado pela simplicidade operacional em ambientes com múltiplas VPCs.
3) Duas opções técnicas: (1) **MACsec (IEEE 802.1AE)** — criptografia Layer 2 nativa, AES-256, sem overhead significativo, transparente para aplicações. Limitação: disponível apenas em Dedicated Connections de 10 Gbps e 100 Gbps — não está disponível em Hosted Connections de 1 Gbps. (2) **VPN over Direct Connect (IPsec)** — cria túnel IPsec sobre o link DX; os dados são criptografados por AES-256 do IPsec enquanto ainda usam o DX como transporte (latência menor e mais consistente que VPN pura pela internet). Funciona em qualquer tipo/capacidade de Direct Connect. Para este cenário (Hosted de 1 Gbps): MACsec não é uma opção. A solução correta é VPN over Direct Connect — configura um Virtual Private Gateway com VPN, mas o tráfego IPsec usa o Direct Connect como transporte em vez da internet. Resultado: criptografia PCI-compliant (AES-256) + benefícios de latência do DX + sem dependência de internet para o caminho principal.
