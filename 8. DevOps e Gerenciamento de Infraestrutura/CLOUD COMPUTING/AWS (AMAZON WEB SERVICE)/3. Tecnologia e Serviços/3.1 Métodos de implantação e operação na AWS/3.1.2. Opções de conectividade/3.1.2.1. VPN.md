### VPN na AWS — conexão criptografada entre ambientes

AWS oferece duas soluções de VPN com propósitos distintos: AWS Site-to-Site VPN conecta redes inteiras (data center on-premises com VPC AWS), e AWS Client VPN conecta dispositivos individuais (laptops de funcionários remotos com a VPC AWS). Ambas usam criptografia IPsec/TLS, mas diferem em escopo, caso de uso e arquitetura. Entender quando usar cada uma — e quando usar Direct Connect em vez de VPN — é fundamental para projetar conectividade híbrida adequada.

---

## AWS Site-to-Site VPN — conectando redes

### O que é e como funciona

```
Site-to-Site VPN conecta sua rede on-premises à sua VPC AWS
através de dois túneis IPsec redundantes via internet pública:

On-premises (10.0.0.0/8)
  └── Customer Gateway (seu roteador/firewall)
        └── Túnel IPsec 1 (endpoint AWS us-east-1a)
        └── Túnel IPsec 2 (endpoint AWS us-east-1b) ← redundância
              └── Virtual Private Gateway (VGW) na VPC
                    └── VPC AWS (172.16.0.0/12)

Os dois túneis:
  → Mesmo destino (sua VPC), diferentes endpoints AWS
  → Se um endpoint AWS cair: tráfego automaticamente
    usa o segundo túnel (sem intervenção manual)
  → Ambos podem ser usados simultaneamente (ECMP com roteamento dinâmico)

Protocolos usados:
  ├── IKEv1 ou IKEv2 (Key Exchange)
  ├── IPsec ESP (criptografia AES-128 ou AES-256)
  └── BGP ou roteamento estático (para troca de rotas)
```

### Componentes da VPN Site-to-Site

```
1. VIRTUAL PRIVATE GATEWAY (VGW):
   Ponto de terminação da VPN no lado da AWS
   ├── Criado e associado à sua VPC
   ├── Um VGW por VPC
   ├── Gerenciado pela AWS (HA automático)
   └── Custo: ~$0.05/hora (enquanto a conexão VPN existir)

2. TRANSIT GATEWAY (alternativa ao VGW):
   Para múltiplas VPCs ou múltiplas conexões VPN:
   ├── Hub central para conectar N VPCs + N conexões VPN
   ├── Uma VPN conecta ao Transit Gateway, acessa todas as VPCs
   └── Custo: ~$0.05/hora por attachment + $0.02/GB processado

3. CUSTOMER GATEWAY (CGW):
   Representa o roteador on-premises no lado da AWS
   ├── Recurso AWS que armazena o IP público do seu roteador
   ├── Configuração: IP, ASN (para BGP), tipo de roteamento
   └── O roteador on-premises REAL que termina o túnel IPsec

4. VPN CONNECTION:
   O vínculo entre VGW e CGW
   ├── Configuração de criptografia (algoritmos, DH groups)
   ├── Download da configuração (para aplicar no roteador on-prem)
   └── Custo: $0.05/hora + data transfer
```

### Configuração passo a passo

```
1. Criar Customer Gateway:
   aws ec2 create-customer-gateway \
     --type ipsec.1 \
     --public-ip 203.0.113.10 \  ← IP público do roteador on-prem
     --bgp-asn 65000            ← ASN da rede on-premises (para BGP)

2. Criar Virtual Private Gateway:
   aws ec2 create-vpn-gateway \
     --type ipsec.1 \
     --amazon-side-asn 64512  ← ASN da AWS (default: 64512)

3. Associar VGW à VPC:
   aws ec2 attach-vpn-gateway \
     --vpn-gateway-id vgw-xxx \
     --vpc-id vpc-yyy

4. Criar VPN Connection:
   aws ec2 create-vpn-connection \
     --type ipsec.1 \
     --customer-gateway-id cgw-aaa \
     --vpn-gateway-id vgw-bbb \
     --options '{"StaticRoutesOnly":false}'  ← usar BGP

5. Baixar configuração:
   aws ec2 describe-vpn-connections \
     --vpn-connection-ids vpn-xxx \
     --query 'VpnConnections[0].CustomerGatewayConfiguration'
   
   → XML com configuração específica para o modelo do roteador
   → Suporte: Cisco ASA, Juniper SRX, Palo Alto, pfSense, etc.
   → Aplicar no roteador on-premises

6. Verificar status dos túneis:
   aws ec2 describe-vpn-connections \
     --query 'VpnConnections[0].VgwTelemetry'
   
   Status esperado:
   [
     {"Status": "UP", "StatusMessage": "IPSEC IS UP"},
     {"Status": "UP", "StatusMessage": "IPSEC IS UP"}
   ]

7. Habilitar Route Propagation na VPC:
   → Route Table → Route Propagation → Enable VGW
   → Rotas on-premises aparecem automaticamente via BGP
```

### Roteamento: BGP vs. Estático

```
ROTEAMENTO ESTÁTICO:
  → Você define manualmente as rotas on-premises na configuração AWS
  → Simples: sem necessidade de BGP no roteador on-prem
  → Desvantagem: sem failover automático entre túneis
  → Desvantagem: novas subnets on-premises precisam de atualização manual

ROTEAMENTO DINÂMICO (BGP):
  → Roteador on-prem e VGW trocam rotas via BGP automaticamente
  → Failover automático: se túnel 1 cair, BGP anuncia via túnel 2
  → Novas subnets on-prem: anunciadas automaticamente
  → Recomendado para produção

BGP com dois túneis simultâneos (ECMP):
  Se o roteador on-prem suporta ECMP (Equal-Cost Multi-Path):
  → Tráfego distribuído entre os dois túneis
  → Largura de banda efetiva: até 2.5 Gbps (2 × 1.25 Gbps)
  → Se um túnel cair: 100% do tráfego no outro (zero interrupção)
```

## AWS Client VPN — acesso remoto de usuários individuais

### O que é e como funciona

```
Client VPN: serviço gerenciado para acesso remoto de usuários
ao ambiente AWS via VPN client no laptop/dispositivo:

Usuário remoto (casa, hotel, aeroporto)
  └── VPN Client (AWS VPN Client, OpenVPN)
        └── Conexão TLS (OpenVPN protocol)
              └── Client VPN Endpoint (endpoint na VPC)
                    └── VPC AWS + recursos associados

Diferença do Site-to-Site:
  Site-to-Site: rede ↔ rede (data center ↔ VPC)
  Client VPN:   dispositivo ↔ rede (laptop ↔ VPC)
```

### Componentes do Client VPN

```
1. CLIENT VPN ENDPOINT:
   ├── Recurso AWS criado em uma ou mais subnets da VPC
   ├── Certificados TLS (servidor + CA via ACM)
   ├── CIDR da rede VPN: pool de IPs para os clientes
   └── Custo: $0.10/hora (endpoint ativo) + $0.05/hora por conexão

2. AUTENTICAÇÃO (escolher um ou mais):
   ├── Mutual TLS: certificados de cliente (mais seguro)
   ├── Active Directory: credenciais corporativas (AD/LDAP)
   ├── SAML (SSO): Okta, Azure AD, Google Workspace
   └── MFA: pode ser adicionado em cima de qualquer método

3. AUTORIZAÇÃO:
   Authorization rules: define quais grupos acessam quais CIDRs
   Exemplo:
   Grupo "Desenvolvedores" → pode acessar 172.16.10.0/24 (subnet app)
   Grupo "DBAs" → pode acessar 172.16.20.0/24 (subnet banco)
   Grupo "SRE" → pode acessar 0.0.0.0/0 (tudo)
```

### Configuração básica do Client VPN

```
1. Criar certificados (se usando mutual TLS):
   # Usar easy-rsa para gerar CA + certificados
   git clone https://github.com/OpenVPN/easy-rsa.git
   cd easy-rsa/easyrsa3
   ./easyrsa init-pki
   ./easyrsa build-ca nopass
   ./easyrsa build-server-full server nopass
   ./easyrsa build-client-full client1 nopass
   
   # Importar certificados no ACM
   aws acm import-certificate \
     --certificate file://pki/issued/server.crt \
     --private-key file://pki/private/server.key \
     --certificate-chain file://pki/ca.crt

2. Criar Client VPN Endpoint:
   aws ec2 create-client-vpn-endpoint \
     --client-cidr-block 10.100.0.0/22 \  ← IPs para clientes VPN
     --server-certificate-arn arn:acm:...:certificate/server \
     --authentication-options Type=certificate-authentication,
       MutualAuthentication={ClientRootCertificateChainArn=arn:acm:...:ca} \
     --connection-log-options Enabled=true,CloudwatchLogGroup=/aws/vpn/connections

3. Associar à subnet da VPC:
   aws ec2 associate-client-vpn-target-network \
     --client-vpn-endpoint-id cvpn-xxx \
     --subnet-id subnet-yyy  ← subnet da VPC

4. Criar authorization rule:
   aws ec2 authorize-client-vpn-ingress \
     --client-vpn-endpoint-id cvpn-xxx \
     --target-network-cidr 172.16.0.0/16 \  ← VPC CIDR
     --authorize-all-groups

5. Exportar configuração para usuários:
   aws ec2 export-client-vpn-client-configuration \
     --client-vpn-endpoint-id cvpn-xxx
   
   → Arquivo .ovpn para importar no AWS VPN Client
```

## Site-to-Site VPN vs. Client VPN vs. Direct Connect

```
                    SITE-TO-SITE VPN    CLIENT VPN          DIRECT CONNECT
                    ────────────────    ──────────          ──────────────
Conecta             Rede ↔ VPC          Usuário ↔ VPC       Rede ↔ VPC
Protocolo           IPsec               TLS/OpenVPN         Ethernet privada
Passa pela internet Sim                 Sim                 NÃO (link dedicado)
Latência            Variável            Variável            Consistente e baixa
Banda               1.25 Gbps/túnel     Variável (internet) 1 Gbps - 100 Gbps
Custo               ~$36/mês + data     ~$72/mês + conexões $200-$5.000/mês
Criptografia        AES-256 (IPsec)     TLS                 MACsec opcional
Setup               Horas               Horas               Semanas/meses
Uso principal       Integração híbrida  Acesso remoto       Migração de dados,
                    on-prem/AWS         para desenvolvedores alta disponibilidade,
                                        e funcionários      missão crítica
```

## Acelerando VPN com Global Accelerator

```
Problema da VPN via internet pública:
  → Tráfego percorre a internet com hops imprevisíveis
  → Latência variável e potencialmente alta (especialmente Brasil → EUA)
  
AWS VPN + Global Accelerator:
  → Cliente VPN conecta ao edge location da AWS mais próximo
  → Tráfego percorre o backbone privado da AWS (não internet)
  → Resultado: latência reduzida e mais consistente

Implementação:
  → Habilitar: Client VPN Endpoint → Acceleration → Enable
  → Custo adicional: $0.025/hora + data transfer do Global Accelerator
  → Benefício: latência ~30-60% menor para usuários distantes
```

## Monitoramento e troubleshooting de VPN

```
Métricas CloudWatch para Site-to-Site VPN:
  TunnelState: 0 = DOWN, 1 = UP
  TunnelDataIn: bytes recebidos
  TunnelDataOut: bytes enviados
  
  Alarm para túnel DOWN:
  aws cloudwatch put-metric-alarm \
    --alarm-name VPNTunnel1Down \
    --namespace AWS/VPN \
    --metric-name TunnelState \
    --dimensions Name=TunnelIpAddress,Value=x.x.x.x \
    --statistic Average \
    --period 60 \
    --threshold 1 \
    --comparison-operator LessThanThreshold \
    --alarm-actions arn:aws:sns:...:vpn-alerts

Troubleshooting de túneis caídos:
  1. Verificar status no console: VPC → Site-to-Site VPN
  2. Verificar se IKE está negociando: logs no roteador on-prem
  3. Verificar se algoritmos de criptografia são compatíveis
     (AWS suporta: AES-128/256, SHA-1/256, DH 2/5/14/19/20/21/23/24)
  4. Verificar se Dead Peer Detection está configurado no roteador
  5. Checar se NAT Traversal (NAT-T) é necessário (roteador atrás de NAT)

Troubleshooting de Client VPN:
  CloudWatch Logs: /aws/vpn/connections
  → Cada sessão: Connect, Authenticate, Authorize, Disconnect
  → Filtrar por username para investigar falha de autenticação
```

## 🧩 Quiz de Fixação

1. Um Site-to-Site VPN tem dois túneis IPsec configurados com BGP. O túnel 1 cai às 3h da madrugada. O que acontece automaticamente com o tráfego e qual é o papel do BGP nesse processo?
2. Uma empresa quer implementar Client VPN para 200 desenvolvedores remotos acessarem instâncias EC2 em uma VPC privada. O time de segurança exige que cada desenvolvedor use suas credenciais corporativas do Azure AD e MFA. Como a autenticação do Client VPN deve ser configurada?
3. Uma empresa tem Site-to-Site VPN e Direct Connect entre o data center e a AWS. O VPN é configurado como failover do DX. O DX cai e o tráfego falha para a VPN, mas a latência aumenta significativamente. Por que isso acontece e como o Global Accelerator poderia melhorar o cenário?

**Respostas:**
1) Quando o túnel 1 cai, o BGP detecta a perda da sessão peer do túnel 1 (o keepalive BGP falha) e remove as rotas aprendidas por esse túnel da tabela de roteamento. O roteador on-premises, que ainda tem BGP ativo no túnel 2, continua anunciando e recebendo rotas por esse segundo túnel. O Virtual Private Gateway da AWS também redireciona o tráfego para o túnel 2. O failover acontece automaticamente em segundos (tipicamente 20-30 segundos, que é o tempo de detecção do BGP keepalive failure com configuração padrão). O tráfego existente pode ter uma breve interrupção durante a convergência BGP, mas conexões novas estabelecidas após o failover usam o túnel 2 sem problema. Para minimizar o tempo de failover, configurar BFD (Bidirectional Forwarding Detection) no roteador on-premises reduz a detecção de falha para sub-segundo.
2) Configuração com Azure AD e MFA: (1) Usar autenticação SAML 2.0 no Client VPN Endpoint — Azure AD suporta SAML nativamente; (2) Configurar Azure AD como Identity Provider: criar uma aplicação enterprise "AWS Client VPN" no Azure AD, configurar SAML com o endpoint da AWS; (3) Habilitar MFA no Azure AD para o aplicativo AWS Client VPN via Conditional Access — ao tentar conectar, Azure AD exige o segundo fator (Microsoft Authenticator, FIDO2, etc.) antes de emitir o token SAML; (4) Criar grupos no Azure AD (ex: "Desenvolvedores") e criar Authorization Rules no Client VPN mapeando esses grupos para os CIDRs que podem acessar; (5) Os 200 desenvolvedores usam o AWS VPN Client com o arquivo .ovpn configurado → são redirecionados ao Azure AD login → autenticam com senha + MFA → recebem acesso à VPC conforme as authorization rules do grupo.
3) Quando o Direct Connect falha, o tráfego muda para o Site-to-Site VPN, que usa a internet pública como caminho de transporte. O Direct Connect usa o backbone privado da AWS com latência determinística e baixa (ex: 5-10ms São Paulo → US-East); a internet pública tem latência variável com múltiplos hops por ISPs diferentes (ex: 80-200ms São Paulo → US-East, dependendo do roteamento BGP da internet). O Global Accelerator melhora esse cenário porque: em vez de o tráfego percorrer toda a internet pública até a região AWS de destino, o cliente conecta ao edge location da AWS mais próximo (com latência mínima de internet) e o restante do percurso usa o backbone privado da AWS. Isso reduz o número de hops pela internet (apenas o trecho "cliente → edge AWS mais próximo") e aproveita a rede privada da AWS para o trecho restante — resultando em latência 30-60% menor e mais consistente que a VPN pura pela internet.
