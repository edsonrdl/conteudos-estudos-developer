### Modelo Híbrido — on-premises e nuvem trabalhando juntos

Arquitetura híbrida é o modelo onde parte da infraestrutura permanece em data centers próprios (on-premises) enquanto outra parte roda na nuvem, com ambos os ambientes integrados e comunicando-se como se fossem uma rede única. Não é uma solução temporária de migração — para muitas organizações é o estado permanente ideal, especialmente quando existem requisitos regulatórios, sistemas legados inamovíveis ou necessidades específicas de latência que tornam o all-in cloud inviável ou indesejável no curto prazo.

---

## Por que o híbrido existe — os motivadores reais

```
1. SISTEMAS LEGADOS INAMOVÍVEIS:
   Mainframe IBM z/OS com 40 anos de lógica de negócio crítica
   → Migrar: anos de trabalho, alto risco de regressão
   → Solução: manter mainframe on-premises + nova camada de API na AWS
   → Frontend moderno (React na AWS) consome API Gateway → 
     Lambda → VPN → mainframe

2. LATÊNCIA ULTRA-BAIXA:
   Robôs de trading de alta frequência: latência < 100 microsegundos
   → Data center co-localizado à bolsa de valores (NYSE, B3)
   → Processamento de ordens on-premises (latência mínima)
   → Analytics, compliance, histórico: na AWS

3. HARDWARE ESPECIALIZADO:
   Processamento de imagens médicas (MRI, CT-Scan)
   → GPUs especializadas e aprovadas para uso médico (FDA)
   → Processamento on-premises (regulação exige)
   → Armazenamento de longo prazo e analytics: AWS (S3 Glacier)

4. INVESTIMENTO RECENTE EM HARDWARE:
   "Compramos $5M em servidores há 2 anos. Depreciam em 5 anos."
   → Não faz sentido financeiro abandonar agora
   → Novos workloads: AWS
   → Workloads existentes: on-premises até depreciar

5. REQUISITO REGULATÓRIO ESPECÍFICO:
   Setor bancário (alguns países): dados transacionais
   devem estar em infraestrutura própria da instituição
   → Transações: on-premises
   → Analytics, backups frios, aplicativos de suporte: AWS

6. PERÍODO DE TRANSIÇÃO:
   Empresa migrando para all-in cloud
   → A migração leva 2-4 anos
   → Durante: híbrido é o estado intermediário necessário
```

## Tecnologias de conexão híbrida

### AWS Site-to-Site VPN

```
Conexão criptografada via internet entre on-premises e VPC AWS:

Componentes:
  ├── Virtual Private Gateway (VGW): ponto de entrada na VPC
  ├── Customer Gateway (CGW): roteador on-premises
  └── VPN Connection: dois túneis IPsec redundantes

Topologia:
  On-premises (10.0.0.0/8)
  ├── Roteador/Firewall → Customer Gateway
  └── Túnel VPN (IPsec/AES-256) via internet
  → Virtual Private Gateway
  → VPC AWS (172.16.0.0/12)

Características:
  ├── Custo: ~$0.05/hora + data transfer
  ├── Largura de banda: até 1.25 Gbps por túnel
  ├── Latência: variável (depende da internet)
  ├── Alta disponibilidade: dois túneis automáticos
  └── Setup: horas (sem instalação física)

Quando usar:
  → Workloads tolerantes a latência variável
  → Backup e disaster recovery
  → Acesso administrativo a recursos AWS
  → Conectividade de menor custo para tráfego não-crítico
  → Ambiente híbrido de menor escala

Configuração básica:
  1. Criar Virtual Private Gateway na VPC
  2. Criar Customer Gateway com IP público do roteador on-prem
  3. Criar VPN Connection (selecionar VGW + CGW)
  4. Baixar configuração e aplicar no roteador on-prem
  5. Verificar túneis ativos (status UP/UP)
```

### AWS Direct Connect

```
Link de rede dedicado e privado entre on-premises e AWS
(não passa pela internet pública):

Como funciona:
  On-premises
  └── Fibra dedicada → Direct Connect Location (instalação parceira)
                     → Backbone privado da AWS
                     → Regiões AWS

  AWS tem 100+ Direct Connect Locations globalmente
  (data centers parceiros: Equinix, CyrusOne, Latisys...)

Tipos de conexão:
  Dedicated Connection:
  ├── 1 Gbps, 10 Gbps, 100 Gbps (fibra física dedicada)
  ├── Você (ou parceiro) conecta diretamente ao equipment da AWS
  └── Latência mais baixa e consistente

  Hosted Connection:
  ├── 50 Mbps a 10 Gbps (compartilhada via parceiro)
  ├── Mais rápida de provisionar (semanas vs. meses)
  └── Compartilha infraestrutura física do parceiro

Características:
  ├── Latência: determinística e baixa (não varia com internet)
  ├── Largura de banda: 50 Mbps a 100 Gbps
  ├── Custo: $0.03-$0.30/GB + custo do porto (~$200-$5.000/mês)
  ├── Sem criptografia nativa (adicionar MACsec ou VPN sobre DX)
  └── Provisionamento: semanas a meses (instalação física)

Quando usar vs. VPN:
  ├── Alto volume de dados (> 1 GB/dia consistente)
  ├── Latência determinística necessária
  ├── Aplicações de tempo real (voz, vídeo, trading)
  ├── Compliance que exige rede privada (não internet)
  └── Migrações massivas de dados

Direct Connect + VPN (melhor prática):
  → Direct Connect: path primário (baixa latência, alto throughput)
  → VPN: failover automático se Direct Connect cair
  → BGP routing: failover transparente

Custo típico:
  10 Gbps Dedicated:
  ├── Port fee: ~$2.250/mês (us-east-1)
  ├── Data transfer: $0.02/GB (AWS → on-prem)
  └── Cross-connect fee: ~$300-$500/mês (data center físico)
  Total: ~$3.000-$5.000/mês + data transfer
```

### AWS Outposts

```
Infraestrutura AWS física instalada no seu data center:

Conceito: AWS entrega, instala e gerencia hardware da AWS
          dentro do seu datacenter on-premises

Formatos:
  Outposts Rack:
  ├── Rack completo de 42U da AWS (servidores, switches, storage)
  ├── Instalado no seu data center
  ├── Conectado à Region AWS via link dedicado
  └── Você usa APIs AWS normalmente

  Outposts Servers (1U/2U):
  ├── Hardware menor para espaços menores
  ├── Para lojas, filiais, fábricas, hospitais
  └── Mesmos serviços, menor capacidade

Serviços disponíveis em Outposts:
  ├── EC2, ECS, EKS (computação)
  ├── RDS (banco de dados)
  ├── S3 on Outposts (armazenamento local)
  └── ElastiCache (cache)

Por que Outposts existe:
  → Aplicações que precisam de latência < 5ms com sistemas locais
  → Dados que regulatoriamente não podem sair do data center
  → Processamento local para ambientes com conectividade limitada
  → Fábricas/indústrias (manufatura, petróleo)
  → Hospitais com equipamentos médicos locais

Como funciona:
  [Outposts Rack no seu DC]
  ├── Você usa Console/CLI/API AWS normalmente
  ├── Recursos criados no Outpost aparecem na mesma Region AWS
  ├── Subnet de Outpost: recursos têm endereços IP locais
  └── Link de retorno para Region: para plano de controle e sincronização

Custo: significativo
  → ~$12.000-$120.000/mês dependendo da configuração
  → Inclui hardware, manutenção 24/7 pela AWS, software
  → Compromisso de 3 anos geralmente
```

## Arquiteturas híbridas comuns

### Padrão 1: Extensão de rede (VPN/DX)

```
Cenário: empresa com ERP on-premises + nova aplicação web na AWS

On-premises (192.168.0.0/16):
  ├── ERP (SAP) — inamovível
  ├── Active Directory — fonte de identidade
  └── SQL Server — banco de dados legado

AWS (10.0.0.0/16) conectado via Direct Connect:
  ├── Nova aplicação web (ECS + ALB)
  ├── API Gateway → Lambda → comunica com ERP via DX
  ├── AWS Managed Microsoft AD — sincronizado com AD on-prem
  └── RDS Aurora — novos dados separados do legado

Fluxo de dados:
  Usuário → ALB → ECS → Lambda → DX (link dedicado)
  → ERP on-premises → resposta → Lambda → usuário
  
  Latência do DX: 5-20ms (aceitável para consultas ERP)
  Volume: médio (não necessita 10 Gbps)
  VPN: fallback se DX cair
```

### Padrão 2: Burst to cloud (cloud bursting)

```
Capacidade base on-premises + overflow na AWS:

Cenário: empresa de processamento de dados com
         carga variável (picos mensais de fechamento)

Base: on-premises (capacidade para 80% do tempo)
  ├── 50 servidores físicos
  └── Carga normal: bem atendida

Pico (fechamento mensal): 5x a carga normal
  → On-premises satura
  → Auto Scaling cria EC2 na AWS automaticamente
  → Dados acessados via Direct Connect
  → Após pico: instâncias EC2 terminadas
  
Implementação:
  Kubernetes (on-prem) + EKS (AWS):
  → Cluster principal: on-premises
  → Quando nós on-prem esgotados: pods schedulados no EKS via VPN
  → Dados compartilhados: NFS/EFS ou S3

Economia:
  Pico por 3 dias/mês: EC2 custos = 3 dias
  vs. manter hardware suficiente para o pico: 100% do custo
```

### Padrão 3: Data pipeline híbrido

```
Dados gerados on-premises → processados na AWS:

Fábrica com sensores IoT:
  Sensores → PLC/SCADA on-premises (tempo real, latência 0)
           → Dados agregados → AWS IoT Core (via VPN)
           → Kinesis → Lambda → S3 → Athena → QuickSight
  
  On-premises: controle de linha de produção (crítico, latência 0)
  AWS: analytics, ML, dashboard executivo

Banco de dados legado + analytics na nuvem:
  Oracle on-premises → AWS DMS (Database Migration Service)
  → Replica continuamente para RDS Aurora ou Redshift na AWS
  → Analytics na AWS sem impacto no banco de produção
  → Quando pronto: migrar o Oracle para RDS (fim do híbrido)
```

## Desafios operacionais do modelo híbrido

```
1. GERENCIAMENTO DE IDENTIDADE E ACESSO:
   
   Problema: usuários têm contas no AD on-premises E precisam
   acessar recursos da AWS
   
   Solução: AWS IAM Identity Center + AD Connector
   → AD Connector faz ponte entre AD on-prem e IAM Identity Center
   → Usuário usa credenciais corporativas para acessar AWS
   → MFA centralizado no AD (ou IAM Identity Center)

2. MONITORAMENTO UNIFICADO:
   
   Problema: métricas e logs em dois mundos diferentes
   
   Solução: CloudWatch Agent + Unified Observability
   → CloudWatch Agent instalado on-premises: envia métricas e logs
   → Mesmo dashboard CloudWatch monitora on-prem + AWS
   → Ou: SIEM centralizado (Splunk, Datadog) coletando de ambos

3. GESTÃO DE CONFIGURAÇÃO:
   
   Problema: IaC para AWS (Terraform) mas scripts manuais para on-prem
   
   Solução: Terraform gerencia ambos
   → Provider AWS: recursos na AWS
   → Provider VMware/vSphere: VMs on-premises
   → Mesmo estado (state file) garante consistência

4. NETWORKING COMPLEXO:
   
   Problema: endereços IP, roteamento, DNS em dois ambientes
   
   Solução cuidadosa de planejamento de subnets:
   On-premises: 10.0.0.0/8 (NUNCA sobrepor com AWS)
   AWS VPC: 172.16.0.0/12 (espaço distinto)
   
   DNS híbrido:
   → Route 53 Resolver: resolve DNS de recursos AWS on-premises
   → Inbound Endpoint: on-prem consulta Route 53 para recursos AWS
   → Outbound Endpoint: Lambda na AWS consulta DNS on-premises

5. SEGURANÇA EM DOIS MUNDOS:
   
   Problema: Surface de ataque maior (dois environments)
   
   → Direct Connect não criptografa nativamente → adicionar MACsec
   → VPN: criptografada por design
   → Firewalls de ambos os lados da conexão
   → AWS Security Hub + SIEM on-prem integrados
```

## AWS Systems Manager — gerenciamento híbrido unificado

```
AWS Systems Manager (SSM) funciona em instâncias EC2 E on-premises:

SSM Agent instalado em servidores on-premises:
  → Aparecem no SSM como "managed instances"
  → Mesmas funcionalidades que EC2:
    Run Command, Patch Manager, Session Manager, Inventory
  
Configuração:
  1. Criar Service Role para on-prem (sem chave permanente)
  2. Baixar e instalar SSM Agent nos servidores on-prem
  3. Registrar servers no SSM via activation code
  4. Servidores aparecem em SSM Fleet Manager como on-prem nodes

Benefícios:
  → Patch Management unificado (AWS + on-prem no mesmo console)
  → Sem SSH: Session Manager funciona on-prem também
  → Inventory: software instalado on-prem visível no SSM
  → Run Command: executar scripts em massa em servidores on-prem
```

## 🧩 Quiz de Fixação

1. Uma empresa tem Direct Connect de 1 Gbps entre seu data center e a AWS. O time quer usar como failover uma VPN Site-to-Site. Como o roteamento BGP deve ser configurado para garantir que o Direct Connect seja sempre preferido e a VPN seja usada apenas quando o DX cair?
2. AWS Outposts vs. Direct Connect — ambos permitem integração entre on-premises e AWS. Qual é a diferença fundamental entre os dois em termos de onde o processamento ocorre e quando cada um é a solução correta?
3. Uma empresa tem Active Directory (AD) on-premises e está migrando aplicações para AWS. Os usuários precisam acessar tanto recursos on-premises quanto recursos AWS com as mesmas credenciais. Descreva a arquitetura de identidade híbrida que resolve isso com AWS.

**Respostas:**
1) Configuração BGP para preferência de Direct Connect sobre VPN: o BGP usa o atributo AS Path e Local Preference para determinar o melhor caminho. Para que DX seja preferido: (1) No Virtual Private Gateway (VGW), configurar as rotas do Direct Connect com AS Path mais curto (menos hops) comparado às rotas da VPN — o BGP prefere AS Paths menores; (2) Usar BGP communities para marcar rotas DX com Local Preference mais alta no roteador on-premises — rotas com Local Preference maior são preferidas na saída; (3) No lado da AWS: configurar o Virtual Private Gateway para anunciar a mesma rede através de ambos (DX e VPN), mas com AS Path prepending nas rotas VPN, tornando-as menos preferíveis; (4) No lado on-premises: configurar o roteador para preferir rotas via DX usando Local Preference (ex: DX=200, VPN=100). Quando DX cair: BGP retira as rotas aprendidas via DX, mantendo apenas as da VPN, e o tráfego automaticamente failover para o túnel IPsec — sem intervenção humana.
2) Diferença fundamental: Direct Connect é uma **conexão de rede** — o processamento acontece na AWS (Região), mas os dados trafegam em uma linha privada dedicada. A latência é menor que a internet, mas ainda envolve round-trip entre on-premises e a região AWS (5-20ms típico). Outposts é **infraestrutura AWS fisicamente no seu data center** — o processamento acontece localmente, no hardware AWS instalado no seu prédio, com latência de sub-milissegundo para sistemas adjacentes. Direct Connect é correto quando: os dados podem ir para a AWS e a latência de rede é aceitável, o volume de dados é alto mas não exige processamento local. Outposts é correto quando: aplicações precisam de latência < 1-5ms com equipamentos locais (robótica, controle de processo industrial), regulação proíbe dados saírem fisicamente do site, ou conectividade WAN é instável e o processamento local é necessário para resiliência.
3) Arquitetura de identidade híbrida com AWS: (1) **AD Connector** — conector bidirecional entre Active Directory on-premises e AWS; nenhum dado de usuário é armazenado na AWS, todas as autenticações são redirecionadas ao AD on-premises; usado para autenticar no console AWS usando credenciais AD; (2) **IAM Identity Center** configurado com AD Connector como identity source — usuários e grupos do AD são sincronizados via LDAP; IAM Identity Center cria Permission Sets que mapeiam para IAM Roles em cada conta AWS; (3) Fluxo de login: usuário acessa o portal IAM Identity Center → autenticação redirecionada ao AD on-premises via AD Connector → se autenticado, IAM Identity Center assume a Role apropriada e gera credenciais temporárias → acesso ao console/CLI da conta AWS solicitada; (4) MFA: pode ser gerenciado pelo AD (com AD MFA extensions) ou pelo IAM Identity Center — o usuário usa o mesmo segundo fator para tudo; (5) Resultado: um único username/password do AD corporativo dá acesso a sistemas on-premises (via Kerberos/LDAP) E à AWS (via IAM Identity Center) — sem credenciais duplicadas, com offboarding centralizado (desativar no AD revoga tudo).
