### On-premises — quando manter infraestrutura própria ainda faz sentido

On-premises significa que a infraestrutura de TI — servidores, redes, storage, banco de dados — está fisicamente localizada nas instalações da própria organização ou em data centers por ela controlados. Em um cenário onde a maioria das empresas migra para a nuvem, on-premises ainda representa a escolha correta para casos específicos onde os requisitos de latência, soberania, custo previsível ou regulação não podem ser atendidos pela nuvem pública. Entender quando on-premises é legítimo evita tanto a migração forçada inadequada quanto a permanência desnecessária no modelo legado.

---

## Por que on-premises ainda existe — casos legítimos

### 1. Latência sub-milissegundo (ultra-low latency)

```
Aplicações que precisam de latência < 1ms com sistemas locais:

Trading de alta frequência (HFT):
  → Algoritmos de trading executam em microssegundos (μs)
  → Bolsa de valores B3 em São Paulo: co-location no próprio prédio
  → Latência rede → B3: 50-200 μs (co-location) vs 5.000+ μs (VPN)
  → Diferença de microsegundos = milhões de reais em P&L
  → Solução: servidores físicos co-locados no data center da bolsa
  → AWS? Apenas para analytics, compliance, backups

Controle industrial (SCADA/PLC):
  → Linha de produção em fábrica: controle de robôs e sensores
  → Falha ou latência em controle → acidente físico
  → PLC (Programmable Logic Controller) deve responder em < 1ms
  → Solução: PLC e servidores de controle on-premises
  → AWS? Dados agregados, analytics preditivo, dashboards remotos

Cirurgia robótica remota:
  → Robot cirúrgico controlado por médico remoto
  → Latência > 100ms → perigoso para o paciente
  → Solução: edge computing local + AWS para dados/coordenação
```

### 2. Soberania de dados e regulação absoluta

```
Setores onde dados NÃO podem sair da infraestrutura própria:

Defesa e governo classificado:
  → Informações sigilosas (TS/SCI): proibido armazenar em nuvem
    comercial não certificada
  → Exceção: AWS GovCloud (certificado para dados sensíveis do
    governo americano) — mas nem todos os países têm equivalente
  → Brasil: órgãos de defesa podem exigir infraestrutura própria

Bancos centrais (em alguns países):
  → Regulação pode exigir sistemas core de pagamentos em infra própria
  → BACEN no Brasil: exige que sistemas SITRAF/STR estejam em infra
    controlada pelas próprias instituições participantes
  → Sistemas adjacentes (analytics, CRM): podem ir para nuvem

Dados de saúde em jurisdições específicas:
  → Alguns países: dados de prontuário eletrônico não podem
    ser processados fora do território nacional em nuvem pública
  → Verificar: cada país tem regulação diferente
  → Brasil/LGPD: permite nuvem com contratos adequados (DPA)

Segredo industrial crítico:
  → Fórmulas de medicamentos, designs de chips, algoritmos proprietários
  → Risco de espionagem industrial justifica custo adicional on-premises
  → Decisão de negócio, não técnica
```

### 3. Workloads ultra-previsíveis de alto volume

```
Quando on-premises pode ser mais barato que nuvem:

Cenário específico onde faz sentido:
  → Workload: 100% de utilização de CPU 24/7, ano inteiro
  → Sem picos, sem sazonalidade, sem variação
  → Volume: centenas de servidores
  
  Cálculo de TCO em 5 anos:
  
  AWS (c6g.4xlarge, 16 vCPU, 32GB):
  Reserved 3yr, No Upfront: $0.338/hora
  100 instâncias × $0.338 × 8.760h/ano × 3 anos = $888.744
  + suporte, data transfer: ~$1M total (3 anos)
  
  On-premises (servidor físico similar):
  100 servidores × $15.000 = $1.500.000 hardware
  + colocation, energia, rede: ~$400.000 (3 anos)
  + equipe de infra: ~$600.000 (3 anos, já existente)
  Total: ~$2.500.000 (3 anos) — mais caro que AWS
  
  Mas se a equipe de infra já existe (custo fixo não-incremental):
  Custo incremental on-premises = hardware + colocation
  = ~$1.900.000 vs $1.000.000 AWS
  
  → Mesmo com workload previsível, a AWS geralmente compete
  
  Exceção real: mainframes IBM e sistemas proprietários
  Custo de mainframe: $500k-$5M em hardware
  Custo AWS equivalente em poder computacional: comparável
  Mas custo de MIGRAÇÃO do mainframe (código COBOL 40 anos): $50M+
  → On-premises é a escolha racional (não pelo custo de infra,
    mas pelo custo proibitivo de migração)
```

### 4. Conectividade limitada ou crítica

```
Ambientes com conectividade WAN ruim ou inexistente:

Navios e plataformas de petróleo:
  → Conectividade via satélite: alta latência (600ms+), baixa banda
  → Processamento local obrigatório
  → AWS Snow Family para sincronização quando em porto

Bases militares remotas:
  → Sem conectividade de internet confiável
  → Sistemas autônomos on-premises
  → AWS Snow Edge para capacidade de computação em campo

Minas e locais de extração:
  → Data center em container no local de extração
  → Dados coletados por semanas/meses
  → Snow device transportado fisicamente para ingestão em AWS
```

## AWS Snow Family — bridging on-premises para a nuvem

```
Para mover dados massivos on-premises → AWS quando rede é insuficiente:

Snowcone (menor):
  ├── 8 TB utilizáveis de HDD ou 14 TB NVMe
  ├── Peso: 2,1 kg (cabe em uma mochila)
  ├── Uso: IoT, edge, ambientes de campo
  ├── AWS DataSync opcional (sync via rede quando disponível)
  └── Preço: ~$300/uso por 10 dias

Snowball Edge:
  ├── Storage Optimized: 80 TB de HDD + 28 TB de NVMe
  ├── Compute Optimized: 104 TB NVMe + GPU opcional
  ├── Capacidade de computação: EC2 instances, Lambda localmente!
  ├── Uso: migração de dados, edge computing, analytics local
  └── Preço: ~$300-$3.500 por trabalho

Snowmobile (maior):
  ├── Caminhão físico da AWS com 100 Petabytes de capacidade
  ├── Uso: migração de data center inteiro
  └── Preço: negociado (projeto customizado)

Quando usar Snow Family vs. Direct Transfer:
  Regra prática:
  
  Dados: 10 TB, largura de banda: 1 Gbps
  Transfer time: 10 TB / (1 Gbps × 3.600s/h × 24h) = ~22 horas
  → Transferir pela rede é mais rápido e barato
  
  Dados: 100 TB, largura de banda: 100 Mbps
  Transfer time: 100 TB / (100 Mbps × 3.600s/h × 24h) = ~111 dias
  → Snowball Edge: entregue, carregado, devolvido em ~10 dias
  → Snow Family ganha quando tempo de transferência > 1 semana
```

## Operação on-premises com ferramentas AWS

### AWS Systems Manager — gerenciamento sem sair da AWS

```
SSM pode gerenciar servidores on-premises como se fossem EC2:

Instalação do SSM Agent on-premises:
  1. Criar IAM Service Role para SSM
  2. Criar "Hybrid Activation" no SSM
  3. Instalar SSM Agent no servidor on-prem com o activation code
  4. Servidor aparece em SSM Fleet Manager como "on-premises"

Funcionalidades disponíveis on-premises:
  ├── Patch Manager: aplica patches de SO automaticamente
  ├── Run Command: executa scripts em lote sem SSH
  ├── Session Manager: acesso seguro sem abrir portas SSH
  ├── Inventory: coleta inventário de software e hardware
  └── State Manager: mantém configuração desejada

Resultado:
  Um console (SSM) para gerenciar:
  ├── 50 instâncias EC2 na AWS
  └── 30 servidores físicos on-premises
```

### AWS CloudWatch — observabilidade híbrida

```
CloudWatch Agent instalado on-premises:
  → Coleta: CPU, memória, disco, rede dos servidores físicos
  → Envia para CloudWatch (via VPN ou Direct Connect)
  → Mesmo dashboard CloudWatch para EC2 + on-prem
  → Mesmos alarmes, mesmas métricas, mesma experiência

Configuração do CloudWatch Agent:
  {
    "agent": {"metrics_collection_interval": 60},
    "metrics": {
      "metrics_collected": {
        "cpu": {"measurement": ["cpu_usage_idle", "cpu_usage_user"]},
        "disk": {"measurement": ["used_percent"]},
        "mem": {"measurement": ["mem_used_percent"]}
      }
    },
    "logs": {
      "logs_collected": {
        "files": {
          "collect_list": [{
            "file_path": "/var/log/application.log",
            "log_group_name": "/onprem/servers/app-01"
          }]
        }
      }
    }
  }
```

## Custo real do on-premises — o que muitas empresas subestimam

```
Custos que frequentemente não entram no cálculo inicial:

VISÍVEIS (fáceis de calcular):
  ├── Hardware: servidores, storage, switches, UPS
  ├── Licenças de software: VMware, Windows Server, SQL Server
  └── Data center / colocation: rack space, energia

OCULTOS (frequentemente esquecidos):
  ├── Equipe de infra: SysAdmins, Engenheiros de Rede, DBAs
  │     (não apenas salário: benefícios, férias, cursos, rescisão)
  ├── Depreciação: hardware fica obsoleto em 3-5 anos
  ├── Renovação de hardware: CapEx recorrente a cada ciclo
  ├── Downtime: custo de indisponibilidade por falha de hardware
  ├── Disaster recovery on-premises: segundo site completo = 2x custo
  ├── Segurança física: câmeras, controle de acesso, segurança 24/7
  ├── Conformidade: auditorias do data center, certificações ISO
  └── Oportunidade: engenheiros de infra poderiam estar inovando

Cálculo de TCO justo:
  Não compare "custo de hardware on-prem" vs "custo AWS"
  Compare "TCO total on-prem" vs "TCO total AWS + equipe SRE"
  
  Em geral: TCO real on-premises é 40-60% maior que o cálculo
  inicial considera, tornando a nuvem competitiva para
  a maioria dos workloads.
```

## Quando on-premises NÃO faz sentido (mitos comuns)

```
Mito 1: "Nuvem é mais cara que on-premises"
  Realidade: Apenas se você ignora os custos ocultos do TCO.
  Para workloads variáveis, a nuvem é quase sempre mais barata.

Mito 2: "Meus dados são mais seguros on-premises"
  Realidade: A maioria das empresas não tem recursos para implementar
  os controles de segurança que a AWS tem nativamente (GuardDuty,
  Shield, Inspector, WAF, KMS com HSMs FIPS 140-3...).
  Breach em servidor on-premises de empresa média: muito mais comum
  que breach em infraestrutura AWS bem configurada.

Mito 3: "Precisamos de latência baixa, então on-premises"
  Realidade: Latência baixa com serviços AWS na mesma região:
  5-15ms para a maioria dos casos. On-premises necessário apenas
  para < 1ms (casos muito específicos).

Mito 4: "Não podemos colocar dados sensíveis na nuvem"
  Realidade: LGPD, GDPR, PCI DSS, HIPAA — todos permitem nuvem
  com configuração e contratos adequados. A maioria dos requisitos
  de compliance é sobre controles, não sobre localização física.
```

## 🧩 Quiz de Fixação

1. Uma empresa de manufatura tem PLCs (Programmable Logic Controllers) controlando linhas de produção que precisam responder em < 500 microssegundos. O time de TI quer migrar para AWS para "simplicidade operacional". Por que esse workload específico não deve ser migrado e qual é a arquitetura híbrida correta?
2. Uma empresa tem 500 TB de dados históricos em servidores on-premises e quer migrá-los para S3. O link de internet é de 500 Mbps compartilhado. Calcule o tempo de transferência via rede e justifique por que o Snowball Edge seria uma alternativa melhor.
3. O CFO de uma empresa on-premises diz: "Nossos 100 servidores físicos custaram $1,5M há 3 anos. Migrá-los para AWS seria jogar esse dinheiro fora." Qual é o erro de raciocínio financeiro nessa afirmação e como você reformularia a análise corretamente?

**Respostas:**
1) PLCs que precisam de resposta em < 500 microssegundos (μs) têm um requisito de latência 1.000x menor que o que qualquer conexão de rede viável para a nuvem pode oferecer. Uma chamada de rede para a mesma região AWS tem latência mínima de 1-2 milissegundos = 1.000-2.000 microssegundos — 2 a 4x acima do requisito. Adicionar qualquer hop de VPN ou Direct Connect só piora. A migração desse workload para a nuvem violaria o requisito de controle em tempo real e poderia causar acidentes industriais (linhas de produção fora de controle, equipamentos danificados, risco para trabalhadores). Arquitetura híbrida correta: PLCs e servidores SCADA permanecem on-premises para controle em tempo real (latência sub-ms); dados de telemetria (temperatura, pressão, produção) são agregados e enviados via VPN/DX para AWS; Lambda/Kinesis processa dados de IoT para analytics e manutenção preditiva; dashboards em QuickSight para supervisores remotos; alarmes de manutenção via CloudWatch. O controle fica local; a inteligência analítica fica na nuvem.
2) Cálculo via rede: 500 TB = 500.000 GB × 8 bits = 4.000.000 Gb. Banda disponível: 500 Mbps = 0.5 Gbps. Assumindo 50% de uso prático (rede compartilhada): 0.25 Gbps efetivo. Tempo = 4.000.000 Gb ÷ 0.25 Gbps = 16.000.000 segundos ÷ 86.400 s/dia = **185 dias** (~6 meses). Com Snowball Edge (Storage Optimized — 80 TB por dispositivo): necessário ~7 dispositivos (500/80 ≈ 7). Cada dispositivo: solicitar → receber (2-3 dias) → carregar dados localmente (velocidade de disco ~250 MB/s → 80 TB em ~4 dias) → devolver → AWS ingere nos dados (3-5 dias). Com múltiplos Snowballs em paralelo: processo completo em **2-3 semanas**. Custo aproximado: 7 dispositivos × ~$3.500/uso = ~$24.500 vs. 185 dias de banda dedicada + tempo de engenheiro monitorando. O Snowball não consome a banda de internet existente — dados chegam à AWS via truck/avião, não via rede.
3) O erro é o "sunk cost fallacy" (falácia do custo irrecuperável). Os $1,5M gastos há 3 anos já foram despendidos — esse dinheiro não retorna independentemente da decisão de migrar ou não. A decisão correta de migrar ou não deve ser baseada exclusivamente nos **custos futuros** de cada cenário, não em investimentos passados. Reformulação correta: "Nossos servidores têm 3 anos e depreciação de 5 anos. Temos 2 anos restantes de vida útil. Nos próximos 5 anos, qual cenário tem menor TCO total?" Análise: custos dos próximos 5 anos on-premises (renovação de hardware em 2 anos: +$1,5M, energia, resfriamento, equipe de infra, data center) vs. AWS (custo mensal previsível, sem renovação de hardware, equipe menor). Em muitos casos, o TCO dos próximos 5 anos é menor na AWS mesmo ignorando completamente os $1,5M já gastos — esse é o único número que importa para a decisão.
