### AWS Lambda — computação serverless orientada a eventos

AWS Lambda é o serviço de computação serverless da AWS: você escreve o código e a AWS cuida de tudo mais — provisionamento de servidores, escalabilidade, patches, balanceamento de carga, alta disponibilidade. Lambda executa código em resposta a eventos (uma requisição HTTP, um arquivo enviado ao S3, uma mensagem na fila, um timer) e cobra exatamente pelo tempo de execução. É o modelo que mais radicalmente elimina o trabalho operacional de infraestrutura.

---

## O que é serverless e o que Lambda resolve

```
ANTES de Lambda — modelo tradicional:
  Para processar imagens enviadas por usuários:
  1. Provisionar EC2 com workers
  2. Configurar Auto Scaling
  3. Gerenciar patches do SO
  4. Monitorar saúde das instâncias
  5. Pagar pelo servidor 24/7 mesmo sem imagens para processar
  
  Com Lambda:
  1. Escrever a função de processamento (código puro)
  2. Configurar trigger: "execute quando objeto chegar no S3"
  3. Lambda faz tudo mais
  
  Benefícios:
  ├── Zero servidores para gerenciar
  ├── Escala de 0 a milhares de execuções em segundos
  ├── Paga apenas pelas execuções reais (não por idle)
  ├── Alta disponibilidade nativa (sem configuração)
  └── Patches e atualizações do runtime: responsabilidade da AWS

"Serverless" não significa "sem servidores"
→ Significa "você não gerencia servidores"
→ A AWS gerencia toda a infraestrutura subjacente
```

## Como Lambda funciona — o ciclo de vida

### Invocação e execução

```
Fluxo de uma invocação Lambda:

1. EVENTO CHEGA (trigger):
   S3 PutObject, API Gateway request, SQS message, etc.

2. LAMBDA RUNTIME ENVIRONMENT (ambiente de execução):
   Se existe ambiente "quente" (já inicializado):
   → Reutiliza o ambiente existente (sem cold start)
   
   Se NÃO existe ambiente quente:
   → Cold Start: inicializa novo ambiente (ver abaixo)

3. EXECUÇÃO DO HANDLER:
   Lambda chama sua função com o event object
   
   Python:
   def handler(event, context):
       # event: payload do trigger (ex: S3 object info)
       # context: informações sobre a execução (time remaining, etc.)
       
       bucket = event['Records'][0]['s3']['bucket']['name']
       key = event['Records'][0]['s3']['object']['key']
       
       # ... processar a imagem ...
       
       return {'statusCode': 200, 'body': 'Processed'}

4. RETORNO:
   → Handler retorna resultado
   → Para invocações síncronas (API GW): resposta devolvida ao caller
   → Para invocações assíncronas (S3, SQS): resultado descartado

5. AMBIENTE DISPONÍVEL:
   → Lambda mantém o ambiente "quente" por ~15 minutos
   → Próxima invocação reutiliza o ambiente (sem cold start)
   → Inicializações fora do handler são cacheadas
```

### Cold Start — o principal desafio de latência

```
Cold Start é o tempo de inicialização de um novo ambiente Lambda:
Inclui:
  ├── Provisionar micro-VM (container isolado)
  ├── Download do código/container
  ├── Inicializar o runtime (Python interpreter, JVM, Node.js, etc.)
  └── Executar o código FORA do handler (imports, conexões, etc.)

Tempo de cold start por runtime (típico):
  Python 3.12:       50-200ms (leve)
  Node.js 20:        50-150ms (leve)
  Java 21 (JVM):     500-2000ms (pesado — JVM é lento para iniciar)
  .NET 8:            200-600ms (médio)
  Go 1.x:            50-100ms (muito leve)
  Container custom:  pode ser segundos (depende da imagem)

Java Cold Start — o problema mais comum:
  Spring Boot + Lambda = cold start de 2-5 segundos
  → Inaceitável para APIs síncronas com SLA de < 500ms
  
  Soluções:
  ├── Lambda SnapStart (Java 11+, 21+):
  │   → Tira snapshot do estado após inicialização
  │   → Restore do snapshot em vez de reinicializar: 10x mais rápido
  │   → Cold start Java: 2000ms → 100-200ms
  │
  ├── Provisioned Concurrency:
  │   → Mantém N ambientes pré-inicializados e aquecidos
  │   → Zero cold start garantido para as N invocações simultâneas
  │   → Custo: paga pelas instâncias quentes mesmo sem invocação
  │
  └── Graal VM Native Image:
      → Compila Java para binário nativo (sem JVM em runtime)
      → Cold start < 100ms
      → Requer: build mais complexo, não é padrão ainda

Cold Start vs. Warm execution:
  Código fora do handler: executa apenas no cold start (uma vez)
  Código dentro do handler: executa a cada invocação
  
  BOAS PRÁTICAS — código fora do handler (inicialização):
  import boto3
  import json
  
  # Executado UMA VEZ no cold start → cacheado
  s3_client = boto3.client('s3')  # reutilizado em todas as invocações
  db_connection = create_db_connection()  # reutilizado
  config = load_config_from_parameter_store()  # carregado uma vez
  
  def handler(event, context):
      # Executado a CADA invocação
      # Usa s3_client, db_connection, config do cache
      ...
```

## Modelos de invocação

### Síncrono (Request-Response)

```
Caller aguarda a resposta antes de continuar:
  API Gateway → Lambda → retorna resposta HTTP
  
  Uso: APIs REST, funções que precisam retornar resultado imediato
  Timeout máximo: 29 segundos (limitado pelo API Gateway)
  Lambda timeout máximo: 15 minutos (mas limitado pelo caller)
  
  Se Lambda retorna erro: caller recebe o erro
  Sem retry automático (caller decide o que fazer)
  
  sdk.invoke(FunctionName='minha-funcao', InvocationType='RequestResponse')
```

### Assíncrono (Event)

```
Caller dispara e não aguarda:
  S3 → Lambda (sem esperar resposta)
  EventBridge → Lambda
  SNS → Lambda
  
  Lambda coloca o evento em fila interna e retorna imediatamente
  Lambda executa o handler de forma assíncrona
  
  Retry automático: 2 tentativas em caso de erro
  Dead Letter Queue (DLQ): eventos que falharam nas 2 tentativas
  → Configure DLQ (SQS ou SNS) para não perder eventos falhos
  
  sdk.invoke(FunctionName='minha-funcao', InvocationType='Event')
```

### Baseado em Stream/Fila (Poll-based)

```
Lambda "puxa" eventos de uma fila ou stream:
  SQS → Lambda (Lambda polling a fila automaticamente)
  Kinesis → Lambda (Lambda polling o stream)
  DynamoDB Streams → Lambda
  
  Configuração: Event Source Mapping
  → Lambda gerencia o polling automaticamente
  → Processa em batches (até 10.000 mensagens por vez para SQS)
  → Retry: mensagem volta à fila se processamento falhar
  
  Concorrência com SQS:
  → Lambda escala automaticamente baseado na profundidade da fila
  → Limite de concorrência da conta se torna o throttle
```

## Triggers disponíveis

```
Praticamente qualquer serviço AWS pode invocar Lambda:

HTTP/API:
  ├── API Gateway (REST, HTTP, WebSocket APIs)
  └── Application Load Balancer (ALB)

Storage:
  ├── S3 (PutObject, DeleteObject, etc.)
  └── DynamoDB Streams (mudanças nas tabelas)

Mensageria:
  ├── SQS (standard e FIFO queues)
  ├── SNS (notificações)
  ├── EventBridge (eventos de qualquer serviço AWS)
  └── Kinesis Data Streams

Banco de dados:
  └── RDS Proxy (Lambda como handler de stored procedure)

Computação:
  ├── CloudWatch Events/EventBridge (cron jobs)
  └── Step Functions (orquestração de workflows)

IoT:
  └── AWS IoT Rules

Outros:
  ├── Cognito (triggers de autenticação)
  ├── CloudFront (Lambda@Edge)
  └── Outra função Lambda (invocação direta)
```

## Configuração de memória e performance

```
Lambda tem uma relação especial entre memória e performance:

Configuração de memória: 128MB a 10.240MB (10GB)

CPU proporcional à memória:
  128MB:  ~12.5% de um vCPU
  1.7GB:  1 vCPU completo
  3.4GB:  2 vCPU
  10GB:   6 vCPU

Mais memória = mais CPU:
  Função que usa só 200MB de memória mas precisa de CPU:
  → Configurar 1024MB (mais memória → mais CPU → execução mais rápida)
  → Paradoxo: pode ser mais barato com mais memória (executa mais rápido)

Cálculo de custo:
  Cobrança = memória_GB × duração_segundos × preço_por_GB_s
  
  256MB, 1000ms: 0.25 × 1.0 × $0.0000166667 = $0.0000041667
  512MB, 500ms:  0.50 × 0.5 × $0.0000166667 = $0.0000041667
  → Mesmo custo! Mas a segunda opção é 2× mais rápida

AWS Lambda Power Tuning:
  Ferramenta open source que testa a função em múltiplas configs
  e encontra o ponto ótimo custo × performance automaticamente
```

## Limites importantes

```
Por conta (ajustáveis via Service Quotas):
  Concurrent executions: 1.000 (padrão, pode aumentar)
  → Throttling se exceder (429 Too Many Requests)

Por função:
  Memory: 128MB - 10.240MB
  Timeout: máximo 15 minutos (900 segundos)
  Deployment package: 50MB zipped, 250MB unzipped
  Container image: até 10GB (via ECR)
  /tmp storage: 512MB-10.240MB (ephemeral, limpo entre execuções frias)
  Environment variables: 4KB total
  Payload síncrono: 6MB (request + response)
  Payload assíncrono: 256KB

Limites que impactam arquitetura:
  Timeout de 15 min: Lambda não é adequado para jobs longos
  → Workloads > 15 min: usar EC2, ECS, Batch, Step Functions
  
  /tmp ephemeral: não é persistente entre cold starts diferentes
  → Para dados persistentes: S3, EFS montado no Lambda, DynamoDB
  
  1.000 concurrent executions: pode ser limitante em alto tráfego
  → Aumentar o limite via Service Quotas (gratuito, basta solicitar)
  → Para Lambda crítico: Reserved Concurrency garante capacidade
```

## Lambda com container images

```
Alternativa ao deployment package ZIP:

Dockerfile:
  FROM public.ecr.aws/lambda/python:3.12
  
  COPY requirements.txt .
  RUN pip install -r requirements.txt
  
  COPY app.py .
  
  CMD ["app.handler"]

Vantagens:
  ├── Até 10GB (vs. 250MB do ZIP)
  ├── Reprodutibilidade total do ambiente
  ├── Reutilização de imagens Docker existentes
  └── Dependências pesadas (SciPy, TensorFlow, etc.) sem problema

Deploy:
  docker build -t minha-funcao:latest .
  aws ecr create-repository --repository-name minha-funcao
  docker tag minha-funcao:latest $ECR_URI/minha-funcao:latest
  docker push $ECR_URI/minha-funcao:latest
  
  aws lambda update-function-code \
    --function-name minha-funcao \
    --image-uri $ECR_URI/minha-funcao:latest
```

## Quando NÃO usar Lambda

```
Lambda é excelente para muitos casos, mas inadequado para outros:

❌ Jobs longos (> 15 minutos):
   Lambda tem timeout de 15 min
   → Alternativa: AWS Batch, ECS Tasks, EC2

❌ Workloads de CPU intensivo e contínuo:
   Lambda tem CPU limitado por memória
   Para HPC, rendering, encoding longo:
   → EC2 com instâncias C/P/G families

❌ Aplicações com estado complexo em memória:
   Ambiente Lambda pode ser substituído a qualquer momento
   Estado em memória entre invocações: não garantido
   → Use ElastiCache, DynamoDB para estado compartilhado

❌ Quando latência de cold start é inaceitável e custoso:
   Se 99.9% das requisições precisam ser < 50ms
   E Provisioned Concurrency seria muito caro:
   → EC2/ECS pode ser mais previsível

❌ Workloads com GPU pesado:
   Lambda não tem suporte a GPU
   → EC2 P/G families ou SageMaker

❌ Quando custo EC2 é drasticamente menor:
   Lambda muito barato para workloads intermitentes
   Para 24/7 com alto uso: EC2 Reserved pode ser mais barato

Exemplo de cálculo:
  10.000 invocações/segundo × 200ms × 512MB
  = 10.000 × 0.2 × (512/1024) × $0.0000166667
  = $0.0167/segundo = $1.000/minuto = $1.44 milhão/dia
  
  vs. 1.000 EC2 c6g.xlarge = 1.000 × $0.136 = $136/hora = $3.264/dia
  
  → Nesse volume extremo: EC2 é 440x mais barato que Lambda!
```

## Casos de uso ideais

```
✓ APIs de baixo a médio volume (< 1M req/dia em geral):
  API Gateway + Lambda = API serverless sem servidores

✓ Processamento de eventos assíncronos:
  S3 object upload → resize de imagem → salvar resultado

✓ Automações e cron jobs:
  EventBridge Scheduler → Lambda (substitui cron no servidor)
  Rotação de credenciais, limpeza de logs, relatórios diários

✓ Backends de webhook:
  Stripe/GitHub/Slack webhook → Lambda → processa e responde

✓ Transformações de dados em pipelines:
  Kinesis → Lambda → transforma → S3/DynamoDB

✓ Functions-as-a-Service (micro-backends):
  Cada Lambda = um micro-serviço
  Escala cada funcionalidade independentemente

✓ Testes de integração e smoke tests:
  Lambda invocado pelo pipeline para validar após deploy

✓ Edge computing (Lambda@Edge):
  Executa no edge do CloudFront para manipulação de requests
```

## 🧩 Quiz de Fixação

1. Uma API crítica de autenticação usa Lambda Java com Spring Boot e tem p99 de 3 segundos no cold start. A empresa tem SLA de 500ms para 99.9% das requisições. Quais são as três opções técnicas para resolver o cold start e qual seria a recomendação para esse caso específico?
2. Um Lambda de processamento de pedidos recebe eventos da fila SQS e falha em 5% dos casos por um bug intermitente. O que acontece automaticamente com as mensagens que falharam, e qual configuração você adicionaria para não perder pedidos importantes?
3. Um serviço processa 50 requisições/segundo × 300ms × 1GB de memória no Lambda. Calcule o custo mensal (30 dias) e determine se valeria a pena migrar para EC2 (c6g.2xlarge: $0.272/hora, 8 vCPU, 16GB RAM) — justifique levando em conta que Lambda tem custo zero quando não há requisições.

**Respostas:**
1) Três opções para resolver cold start Java/Spring Boot no Lambda: (1) **Lambda SnapStart** (recomendado) — disponível para Java 11 e 21; a AWS tira um snapshot do estado da JVM após a fase INIT (após o Spring context ser inicializado) e restaura esse snapshot em vez de reinicializar do zero; reduz cold start de 2.000-3.000ms para 100-200ms; sem custo adicional; é o caminho mais simples e eficiente para o problema específico de Spring Boot; (2) **Provisioned Concurrency** — mantém N ambientes pre-aquecidos sem cold start garantido; custo: paga pelas instâncias quentes 24/7; para uma API com tráfego constante isso pode ser caro, mas para picos previsíveis (manhã de dias úteis) pode-se usar Application Auto Scaling para aumentar o provisionado apenas durante o horário de pico; (3) **Migrar para runtime mais leve** — substituir Spring Boot por Micronaut, Quarkus (com Graal VM Native Image) ou reescrever em Go/Python; cold start < 100ms; exige trabalho de migração. Recomendação para esse caso: SnapStart primeiro (sem código, sem custo adicional, resolve o problema principal); se ainda insuficiente, combinar com Provisioned Concurrency mínimo para as primeiras invocações do dia.
2) Com Event Source Mapping SQS + Lambda: quando o Lambda falha ao processar uma mensagem (lança exception), a mensagem não é deletada da fila — permanece visível para reprocessamento após o Visibility Timeout expirar. O Lambda tenta automaticamente até que a mensagem seja processada com sucesso ou atinja o `maxReceiveCount` configurado na fila (ex: 3 tentativas). Após `maxReceiveCount` excedido, a mensagem vai para a Dead Letter Queue (DLQ) se configurada; sem DLQ, a mensagem é deletada e o pedido se perde. Configuração para não perder pedidos: (1) configurar DLQ na fila SQS (fila separada para mensagens problemáticas), (2) configurar `maxReceiveCount` adequado (ex: 5 tentativas), (3) CloudWatch Alarm quando DLQ tem mensagens (`ApproximateNumberOfMessagesVisible > 0`), (4) processo periódico de revisão e reprocessamento das mensagens na DLQ após corrigi o bug. Adicionalmente: implementar idempotência no Lambda (verificar se o pedido já foi processado antes de processar novamente) para que reprocessamentos não causem duplicatas.
3) Cálculo Lambda: 50 req/s × 300ms × 1GB × $0.0000166667/GB-s = 50 × 0.3 × 1 × $0.0000166667 = $0.00025/segundo = $0.90/hora = $648/mês (requests: 50/s × 86.400s/dia × 30 dias × $0.0000002 = $25.92/mês). Total Lambda: ~$674/mês. Cálculo EC2 c6g.2xlarge: $0.272/hora × 24 × 30 = $195.84/mês (uma instância). Para 50 req/s com segurança, talvez precisaria de 2 instâncias em Multi-AZ: $391.68/mês. EC2 é ~42% mais barato para essa carga constante ($391 vs $674). Mas a decisão não é só de custo: Lambda é zero custo em períodos sem tráfego (madrugada, fins de semana) enquanto EC2 corre 24/7. Se o tráfego de 50 req/s for apenas durante horário comercial (8 horas/dia, 22 dias/mês): Lambda: ~$224/mês; EC2: $391/mês (Lambda ganha). Para tráfego realmente constante 24/7: EC2 é mais barato. Para tráfego com variação diária/semanal: Lambda provavelmente ganha pela ausência de custo nos períodos ociosos. Conclusão: depende do perfil de tráfego real — analisar com CloudWatch para decidir.
