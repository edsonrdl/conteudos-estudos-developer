### Networking no EKS — VPC CNI, AWS Load Balancer Controller e Ingress

Rede é uma das áreas mais complexas do Kubernetes, e o EKS adiciona camadas específicas da AWS por cima. Este arquivo cobre três componentes que juntos respondem pela questão fundamental: como o tráfego da internet chega nos pods, e como os pods se comunicam entre si e com serviços externos.

---

## AWS VPC CNI — IPs nativos da VPC para pods

O **AWS VPC CNI** (Container Network Interface) é o plugin de rede padrão do EKS. Ele atribui endereços IP da VPC diretamente a cada pod — sem overlay de rede, sem NAT, sem encapsulamento.

### Como outros CNIs funcionam (contexto)

```
CNI com overlay (ex: Flannel, Calico em modo overlay):

Pod A (10.244.1.5) ──▶ encapsula pacote ──▶ nó 1 (192.168.1.10)
                         VXLAN/IP-in-IP          │
                                                 │ desencapsula
                                                 ▼
                                            nó 2 (192.168.1.20)
                                                 │
                                                 ▼
                                           Pod B (10.244.2.7)

Overhead: encapsulamento/desencapsulamento em cada salto
```

```
AWS VPC CNI — IPs nativos:

Pod A (10.0.1.20) ──▶ roteamento direto na VPC ──▶ Pod B (10.0.2.15)

Nenhum encapsulamento — o tráfego usa as tabelas de roteamento
da VPC diretamente. Latência equivalente a EC2 ↔ EC2.
```

### Como o VPC CNI aloca IPs

```
Nó EC2 (m7g.large) com VPC CNI:

ENI primária:           10.0.1.10  (IP do nó)
ENI secundária 1:       IPs secundários pré-alocados no "warm pool"
  │  10.0.1.20  ──▶  Pod A
  │  10.0.1.21  ──▶  Pod B
  │  10.0.1.22  ──▶  (reservado no warm pool — aguarda pod)
  └  10.0.1.23  ──▶  (reservado)
ENI secundária 2:
  │  10.0.1.30  ──▶  Pod C
  └  10.0.1.31  ──▶  (warm pool)

O VPC CNI pré-aloca IPs para reduzir latência de startup de pods.
Quando um pod é criado, um IP já está disponível instantaneamente.
```

### Configurações importantes do VPC CNI

```bash
# Ver configuração atual do VPC CNI
kubectl describe daemonset aws-node -n kube-system | grep -A5 "Environment"

# Habilitar prefix delegation (aumenta drasticamente limite de pods/nó)
kubectl set env daemonset aws-node -n kube-system \
  ENABLE_PREFIX_DELEGATION=true \
  WARM_PREFIX_TARGET=1

# Habilitar Network Policy com VPC CNI
kubectl set env daemonset aws-node -n kube-system \
  ENABLE_NETWORK_POLICY=true

# Ver quantos IPs estão sendo usados por nó
kubectl get node -o json | \
  jq '.items[] | {node: .metadata.name, allocatable: .status.allocatable}'
```

### Network Policies — firewall de rede entre pods

Com `ENABLE_NETWORK_POLICY=true`, é possível criar regras de firewall entre pods:

```yaml
# Isolar namespace: apenas o namespace "frontend" pode chamar "backend"
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-only
  namespace: backend
spec:
  podSelector:
    matchLabels:
      app: minha-api    # aplica para pods da minha-api no namespace backend
  policyTypes:
    - Ingress
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              name: frontend   # apenas do namespace frontend
          podSelector:
            matchLabels:
              app: web-app     # apenas do pod web-app
      ports:
        - protocol: TCP
          port: 8080
```

## AWS Load Balancer Controller — ALB e NLB nativos

O **AWS Load Balancer Controller** (AWS LBC) é um add-on do EKS que cria e gerencia ALBs e NLBs automaticamente com base em anotações nos objetos Kubernetes. Sem ele, `Service type: LoadBalancer` cria apenas CLBs (Classic Load Balancers) legados.

```bash
# Instalar AWS LBC via Helm
helm repo add eks https://aws.github.io/eks-charts
helm install aws-load-balancer-controller eks/aws-load-balancer-controller \
  --namespace kube-system \
  --set clusterName=meu-cluster \
  --set serviceAccount.create=true \
  --set serviceAccount.annotations."eks\.amazonaws\.com/role-arn"=\
arn:aws:iam::123:role/AWSLoadBalancerControllerRole
```

### Service com NLB (camada 4)

```yaml
apiVersion: v1
kind: Service
metadata:
  name: minha-api-nlb
  namespace: producao
  annotations:
    service.beta.kubernetes.io/aws-load-balancer-type: "external"
    service.beta.kubernetes.io/aws-load-balancer-nlb-target-type: "ip"
    service.beta.kubernetes.io/aws-load-balancer-scheme: "internet-facing"
    service.beta.kubernetes.io/aws-load-balancer-cross-zone-load-balancing-enabled: "true"
    # IP fixo (Elastic IP) por AZ:
    service.beta.kubernetes.io/aws-load-balancer-eip-allocations: "eipalloc-abc,eipalloc-def"
spec:
  type: LoadBalancer
  selector:
    app: minha-api
  ports:
    - port: 443
      targetPort: 8080
      protocol: TCP
```

### Ingress com ALB (camada 7)

O **Ingress** é o objeto Kubernetes para roteamento HTTP/HTTPS. O AWS LBC transforma um Ingress em um ALB com regras de listener:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: minha-api-ingress
  namespace: producao
  annotations:
    kubernetes.io/ingress.class: "alb"
    alb.ingress.kubernetes.io/scheme: "internet-facing"
    alb.ingress.kubernetes.io/target-type: "ip"   # registra pods por IP (awsvpc)
    alb.ingress.kubernetes.io/listen-ports: '[{"HTTPS":443}]'
    alb.ingress.kubernetes.io/certificate-arn: "arn:aws:acm:...:certificate/abc"
    alb.ingress.kubernetes.io/ssl-redirect: "443"
    alb.ingress.kubernetes.io/healthcheck-path: "/health"
    alb.ingress.kubernetes.io/healthcheck-interval-seconds: "30"
    # Grupos — múltiplos Ingress compartilham o mesmo ALB
    alb.ingress.kubernetes.io/group.name: "producao"
    alb.ingress.kubernetes.io/group.order: "10"
spec:
  rules:
    - host: api.meudominio.com
      http:
        paths:
          - path: /v1/pedidos
            pathType: Prefix
            backend:
              service:
                name: servico-pedidos
                port:
                  number: 80
          - path: /v1/pagamentos
            pathType: Prefix
            backend:
              service:
                name: servico-pagamentos
                port:
                  number: 80
          - path: /
            pathType: Prefix
            backend:
              service:
                name: servico-gateway
                port:
                  number: 80
```

### IngressGroup — múltiplos serviços em um único ALB

```
Sem IngressGroup:               Com IngressGroup:
                                
Ingress A → ALB A ($$/mês)      Ingress A ─┐
Ingress B → ALB B ($$/mês)      Ingress B ─┼─▶ ALB compartilhado
Ingress C → ALB C ($$/mês)      Ingress C ─┘    (um ALB = $16/mês fixo)

3 ALBs = $48/mês base           1 ALB = $16/mês base
+ custo por LCU                 + custo por LCU

Para múltiplos serviços no mesmo cluster:
IngressGroup reduz custo e simplifica o DNS (mesmo IP de entrada)
```

## Padrões de tráfego no EKS

### Tráfego externo → pods

```
Internet
  │ HTTPS 443
  ▼
ALB (criado pelo AWS LBC)
  │ HTTP 8080 (ou HTTPS interno)
  │ registra pods diretamente por IP (target-type: ip)
  ▼
Pod A (10.0.1.20:8080)  ou  Pod B (10.0.1.21:8080)
  (sem passar pelo Service do Kubernetes — vai direto ao pod)
```

### Tráfego interno — pod para pod

```
Pod A (namespace: checkout)
  │ http://pagamentos.pagamentos.svc.cluster.local:80
  ▼
CoreDNS resolve → Service "pagamentos" → ClusterIP (virtual)
  │
  ▼ kube-proxy (iptables/IPVS)
  │
  ▼
Pod de pagamentos (10.0.2.15:8080) ou (10.0.2.16:8080)
  (roteamento direto via VPC — sem encapsulamento)
```

### Tráfego pod → serviços externos AWS

```
Pod → RDS (fora do cluster):
  Pod → ENI do nó → VPC routing → RDS endpoint
  (sem NAT se RDS na mesma VPC)

Pod → S3 / DynamoDB:
  Pod → VPC Gateway Endpoint (S3/DynamoDB) → serviço AWS
  (sem saída para internet — mais seguro e sem custo de NAT)

Pod → serviço externo (internet):
  Pod → ENI do nó → NAT Gateway → Internet
  (nós em subnet privada, NAT Gateway na subnet pública)
```

## ExternalDNS — DNS automático para Services e Ingresses

O **ExternalDNS** é um add-on que cria automaticamente registros DNS no Route 53 quando você cria Services ou Ingresses com o annotation correto:

```yaml
# Ingress com ExternalDNS
metadata:
  annotations:
    external-dns.alpha.kubernetes.io/hostname: api.meudominio.com
    # ExternalDNS cria automaticamente:
    # api.meudominio.com → CNAME → <alb-dns>.us-east-1.elb.amazonaws.com
```

```bash
# Instalar ExternalDNS
helm install external-dns external-dns/external-dns \
  --namespace kube-system \
  --set provider=aws \
  --set aws.region=us-east-1 \
  --set txtOwnerId=meu-cluster \
  --set serviceAccount.annotations."eks\.amazonaws\.com/role-arn"=\
arn:aws:iam::123:role/ExternalDNSRole
```

## cert-manager — TLS automático

O **cert-manager** gerencia certificados TLS dentro do cluster, podendo integrar com ACM ou Let's Encrypt:

```yaml
# Certificate via ACM (para uso com ALB)
# O ALB usa certificados do ACM diretamente — referenciado por ARN no Ingress

# Certificate via Let's Encrypt (para TLS dentro do cluster)
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: minha-api-tls
  namespace: producao
spec:
  secretName: minha-api-tls-secret
  issuerRef:
    name: letsencrypt-prod
    kind: ClusterIssuer
  dnsNames:
    - api-interno.meudominio.com
```

## Comparativo: ALB via Ingress vs NLB via Service

```
Quando usar Ingress + ALB:
  ✓ Roteamento por path (/api/v1, /static, /)
  ✓ Roteamento por host (api.site.com, admin.site.com)
  ✓ Autenticação via Cognito ou OIDC no load balancer
  ✓ SSL termination + redirect HTTP → HTTPS
  ✓ WAF integration
  ✓ IngressGroup para compartilhar ALB entre serviços

Quando usar Service + NLB:
  ✓ TCP/UDP não-HTTP (gRPC, MQTT, WebSocket de baixa latência)
  ✓ IP estático necessário (Elastic IPs fixos por AZ)
  ✓ Latência ultra-baixa (NLB < 1ms overhead vs ALB ~5ms)
  ✓ Preservar IP de origem do cliente
  ✓ Protocolo proprietário / binário
```

## Erros comuns e armadilhas

**`target-type: instance` em vez de `ip` com awsvpc:** com VPC CNI (awsvpc), os pods têm IPs diretos. Usar `target-type: instance` registra o nó EC2 como target — o ALB envia para o nó, que faz um segundo hop via kube-proxy até o pod. Usar `target-type: ip` registra o pod diretamente — menos latência, sem double-hop.

**Muitos ALBs sem IngressGroup:** cada Ingress sem `group.name` cria um ALB separado (~$16/mês base + custos por LCU). Com 20 serviços, isso é $320/mês apenas em ALBs. Use IngressGroup para consolidar.

**Subnets não tagueadas para ALB:** o AWS LBC descobre as subnets automaticamente por tags. Sem as tags corretas, a criação do ALB falha:

```bash
# Tags obrigatórias nas subnets:
# Para ALB interno:
aws ec2 create-tags --resources subnet-abc123 \
  --tags Key=kubernetes.io/role/internal-elb,Value=1

# Para ALB externo (internet-facing):
aws ec2 create-tags --resources subnet-def456 \
  --tags Key=kubernetes.io/role/elb,Value=1

# Tag de descoberta do cluster (para todos os tipos):
aws ec2 create-tags --resources subnet-abc123 subnet-def456 \
  --tags Key=kubernetes.io/cluster/meu-cluster,Value=shared
```

## 🧩 Quiz de Fixação

1. Por que `target-type: ip` é superior a `target-type: instance` para Services EKS quando se usa VPC CNI, e em qual situação `target-type: instance` ainda faria sentido?

2. Um time cria 10 Ingresses separados para 10 microserviços, cada um sem `group.name`. Após 1 mês, o custo de load balancers está muito alto. Como corrigir sem downtime, e qual é o impacto esperado na rede?

3. Um pod precisa fazer uma requisição para uma API externa na internet, mas o cluster EKS usa nós em subnets privadas. Descreva o caminho completo do pacote desde o pod até a internet.

**Respostas:**

1) Com `target-type: ip`, o ALB registra e roteia tráfego **diretamente para o IP do pod** via VPC routing — um único salto de rede. Com `target-type: instance`, o ALB envia o pacote para o **IP do nó EC2**, e o kube-proxy (iptables/IPVS) dentro do nó faz um segundo roteamento até o pod correto. O resultado é latência adicional (~0.5-1ms por hop extra), complexidade desnecessária, e possibilidade de o pacote ser enviado para um pod em um nó diferente do que recebeu a requisição. **Situação onde `target-type: instance` ainda faz sentido:** quando os pods usam network mode `hostNetwork: true` (compartilham o IP do nó) ou quando há um proxy reverso rodando no nó que precisa receber o tráfego antes de encaminhar. Em clusters com overlay CNI (não VPC CNI), `target-type: instance` também é a única opção porque os pods não têm IPs da VPC diretamente roteáveis.

2) **Solução sem downtime:** adicionar o annotation `alb.ingress.kubernetes.io/group.name: "producao"` e `alb.ingress.kubernetes.io/group.order: "N"` em todos os 10 Ingresses, `kubectl apply` em cada um. O AWS LBC automaticamente consolida tudo no mesmo ALB e atualiza os Listener Rules. Os DNS dos ALBs antigos ainda apontam para os ALBs individuais que serão deletados — portanto é necessário atualizar o Route 53 (ou ExternalDNS faz isso automaticamente) para apontar para o novo ALB compartilhado. **Impacto:** (a) custo: 10 ALBs × ~$16/mês base = $160/mês → 1 ALB = $16/mês (economia de $144/mês em custo base); (b) rede: um único endpoint DNS/IP para todos os serviços — mais fácil para firewall e whitelist; (c) risco: todos os serviços no mesmo ALB significa que uma configuração errada em um Ingress pode impactar todos os outros — cuidado com regras conflitantes.

3) O caminho completo: (1) **Pod** gera o pacote com IP de destino da API externa (ex: 93.184.216.34); (2) O pacote sai do pod via a **ENI secundária** atribuída pelo VPC CNI com o IP do pod como origem (ex: 10.0.1.20); (3) A **tabela de roteamento da subnet privada** não tem rota direta para internet (0.0.0.0/0 aponta para o **NAT Gateway**); (4) O pacote chega ao **NAT Gateway** (na subnet pública), que faz **SNAT** — substitui o IP de origem 10.0.1.20 pelo **Elastic IP** do NAT Gateway; (5) O pacote sai para a internet via o **Internet Gateway** com o IP público do NAT Gateway como origem; (6) A resposta retorna ao IP do NAT Gateway → NAT faz DNAT de volta para 10.0.1.20 → pacote chega ao pod. Custo: $0.045/hora por NAT Gateway + $0.045/GB processado — para workloads com alto volume de tráfego de saída, VPC Endpoints (para serviços AWS) e PrivateLink reduzem esse custo evitando o NAT para tráfego intra-AWS.
