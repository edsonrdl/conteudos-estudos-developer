### Pod, Deployment, ReplicaSet e Service — objetos fundamentais do Kubernetes

Kubernetes opera através de objetos declarativos — recursos YAML que descrevem o estado desejado do sistema. Quatro objetos formam o núcleo de qualquer aplicação rodando no EKS: **Pod** (a unidade de execução), **ReplicaSet** (o controlador de réplicas), **Deployment** (o gerenciador de ciclo de vida) e **Service** (a abstração de rede). Entender como esses quatro objetos se relacionam é o pré-requisito para tudo mais em Kubernetes.

---

## Pod — a unidade fundamental de execução

O **Pod** é o menor objeto deployável no Kubernetes. Um Pod encapsula um ou mais containers que compartilham:
- O mesmo endereço IP (e se comunicam via `localhost`)
- O mesmo namespace de rede
- Os mesmos volumes montados

```yaml
# Pod mínimo — raramente criado diretamente em produção
apiVersion: v1
kind: Pod
metadata:
  name: minha-api-pod
  namespace: producao
  labels:
    app: minha-api
    version: v2.1
spec:
  containers:
    - name: api
      image: 123456789.dkr.ecr.us-east-1.amazonaws.com/minha-api:v2.1
      ports:
        - containerPort: 8080
      resources:
        requests:        # mínimo garantido (usado pelo scheduler)
          cpu: "250m"    # 250 millicores = 0.25 vCPU
          memory: "256Mi"
        limits:          # máximo permitido (OOM kill se ultrapassar memória)
          cpu: "500m"
          memory: "512Mi"
      env:
        - name: NODE_ENV
          value: production
        - name: DB_HOST
          valueFrom:
            secretKeyRef:
              name: db-credentials
              key: host
      readinessProbe:    # "estou pronto para receber tráfego?"
        httpGet:
          path: /health
          port: 8080
        initialDelaySeconds: 10
        periodSeconds: 5
        failureThreshold: 3
      livenessProbe:     # "ainda estou vivo?"
        httpGet:
          path: /health
          port: 8080
        initialDelaySeconds: 30
        periodSeconds: 10
        failureThreshold: 3
```

### Requests vs Limits — a distinção mais importante de recursos

```
requests: o scheduler usa para DECIDIR onde colocar o pod
          "Este pod precisa de pelo menos 250m CPU e 256Mi RAM"
          → Nó sem esses recursos disponíveis: pod não vai para lá

limits: o kubelet usa para CONTROLAR o pod em execução
        CPU limit: o container é throttled (nunca morto por CPU)
        Memory limit: o container é killed com OOMKilled se ultrapassar

Cenários:

Pod com requests=250m, limits=500m rodando em nó com 1 CPU:
  → Garantido: 250m sempre disponíveis
  → Pode usar até 500m se o nó tiver CPU ociosa
  → Throttled se tentar usar >500m

Pod sem limits de memória:
  → Pode consumir toda a memória do nó
  → Mata outros pods por falta de memória (NUNCA faça isso em produção)
```

### Probes — health checks do Kubernetes

```
readinessProbe:
  → Controla se o pod RECEBE TRÁFEGO do Service
  → Se falha: pod é removido do endpoint do Service (sem matar)
  → Útil durante inicialização lenta ou degradação temporária

livenessProbe:
  → Controla se o pod está VIVO
  → Se falha consecutivamente: pod é REINICIADO pelo kubelet
  → Use com cuidado — liveness probe muito agressiva causa restart loops

startupProbe (opcional):
  → Período de graça durante o startup da aplicação
  → Substitui initialDelaySeconds para apps com inicialização variável
  → Se falha além do failureThreshold: pod é reiniciado
```

## ReplicaSet — o controlador de réplicas

O **ReplicaSet** garante que um número específico de Pods idênticos esteja sempre rodando. Se um pod morre, o ReplicaSet cria outro. Se há pods demais, ele termina o excesso.

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: minha-api-rs
spec:
  replicas: 3
  selector:
    matchLabels:
      app: minha-api   # gerencia pods com este label
  template:            # template do pod a criar
    metadata:
      labels:
        app: minha-api
    spec:
      containers:
        - name: api
          image: minha-api:v2.1
```

**Na prática, você raramente cria ReplicaSets diretamente.** O Deployment cria e gerencia ReplicaSets automaticamente — é a abstração acima.

## Deployment — gerenciamento de ciclo de vida

O **Deployment** é o objeto de produção para stateless applications. Ele gerencia ReplicaSets para implementar rolling updates, rollbacks e versionamento de forma segura:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: minha-api
  namespace: producao
  labels:
    app: minha-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: minha-api
  
  # Estratégia de atualização
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # pode criar até 1 pod extra durante update
      maxUnavailable: 0  # nunca reduzir abaixo de 3 pods disponíveis
  
  template:
    metadata:
      labels:
        app: minha-api
        version: v2.1
    spec:
      # Distribuição entre AZs
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: DoNotSchedule
          labelSelector:
            matchLabels:
              app: minha-api
      
      # Afinidade — evitar dois pods no mesmo nó
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                topologyKey: kubernetes.io/hostname
                labelSelector:
                  matchLabels:
                    app: minha-api
      
      containers:
        - name: api
          image: 123456789.dkr.ecr.us-east-1.amazonaws.com/minha-api:v2.1
          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"
            limits:
              cpu: "500m"
              memory: "512Mi"
          readinessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 10
            periodSeconds: 5
      
      # Graceful shutdown
      terminationGracePeriodSeconds: 30
```

### Rolling Update — como o Deployment atualiza

```
Deployment com 3 réplicas, maxSurge=1, maxUnavailable=0:

Estado inicial: [v1] [v1] [v1]

Passo 1: Cria 1 pod v2 (surge): [v1] [v1] [v1] [v2]
         Aguarda readinessProbe passar no v2

Passo 2: Remove 1 pod v1: [v1] [v1] [v2]
         Cria 1 pod v2:   [v1] [v1] [v2] [v2]
         Aguarda readinessProbe...

Passo 3: Remove 1 pod v1: [v1] [v2] [v2]
         Cria 1 pod v2:   [v1] [v2] [v2] [v2]
         Aguarda...

Passo 4: Remove 1 pod v1: [v2] [v2] [v2] ← concluído

Se v2 falhar na readinessProbe:
  → Pods v1 permanecem (minUnavailable=0 garantido)
  → Pod v2 problemático fica no estado Not Ready
  → Deployment para de avançar — aguarda intervenção
```

### Comandos essenciais de Deployment

```bash
# Aplicar/atualizar Deployment
kubectl apply -f deployment.yaml

# Verificar status do rollout
kubectl rollout status deployment/minha-api -n producao

# Ver histórico de revisões
kubectl rollout history deployment/minha-api -n producao

# Rollback para a revisão anterior
kubectl rollout undo deployment/minha-api -n producao

# Rollback para uma revisão específica
kubectl rollout undo deployment/minha-api --to-revision=3 -n producao

# Forçar restart de todos os pods (sem mudar a imagem)
kubectl rollout restart deployment/minha-api -n producao

# Escalar manualmente
kubectl scale deployment minha-api --replicas=10 -n producao

# Ver pods do deployment com mais detalhes
kubectl get pods -l app=minha-api -n producao -o wide
```

## Service — abstração de rede e descoberta

O **Service** fornece um endereço IP estável e DNS para acessar um conjunto de pods. Como os pods têm IPs efêmeros (mudam quando reiniciam), o Service é a abstração que torna a comunicação confiável:

```
Sem Service:                Com Service:
Pod A: 10.0.1.20            Service minha-api:
Pod B: 10.0.1.21  →  Pod A  → IP virtual estável: 172.20.0.50
Pod C morre e               DNS: minha-api.producao.svc.cluster.local
  recria em: 10.0.1.55      → Roteamento automático para pods saudáveis
```

### Tipos de Service

```yaml
# ClusterIP — apenas acesso interno ao cluster (padrão)
apiVersion: v1
kind: Service
metadata:
  name: minha-api
  namespace: producao
spec:
  type: ClusterIP
  selector:
    app: minha-api    # roteia para pods com este label
  ports:
    - port: 80        # porta do Service
      targetPort: 8080 # porta do container
      protocol: TCP
```

```yaml
# NodePort — expõe em uma porta de cada nó (30000-32767)
# Usado para debug ou quando não há load balancer
spec:
  type: NodePort
  ports:
    - port: 80
      targetPort: 8080
      nodePort: 31080  # acessível em <IP do nó>:31080
```

```yaml
# LoadBalancer — provisiona um AWS Load Balancer automaticamente
# (sem AWS Load Balancer Controller: cria CLB legado)
# (com AWS LBC: cria ALB ou NLB via annotations)
spec:
  type: LoadBalancer
  ports:
    - port: 80
      targetPort: 8080
  annotations:
    service.beta.kubernetes.io/aws-load-balancer-type: "nlb"
    service.beta.kubernetes.io/aws-load-balancer-scheme: "internet-facing"
```

```yaml
# ExternalName — alias DNS para serviço externo
# Útil para referenciar RDS, ElastiCache, etc., como se fossem serviços K8s
spec:
  type: ExternalName
  externalName: meu-rds.cluster.us-east-1.rds.amazonaws.com
```

### Como o Service roteia o tráfego

```
Service "minha-api" com selector app=minha-api:

Pods com label app=minha-api:
  Pod 1: 10.0.1.20 (Ready)
  Pod 2: 10.0.1.21 (Ready)
  Pod 3: 10.0.1.22 (Not Ready — falhou readinessProbe)

Endpoint slice do Service:
  [10.0.1.20, 10.0.1.21]  ← Pod 3 excluído automaticamente

Requisição chega no Service:
  → kube-proxy roteia para um dos endpoints (round-robin por padrão)
  → 10.0.1.20 ou 10.0.1.21 (nunca 10.0.1.22)
```

O `readinessProbe` é diretamente responsável por incluir/excluir pods dos endpoints do Service — é assim que zero-downtime deploy funciona: pods novos só recebem tráfego após passar no readiness check.

## Outros objetos importantes

### ConfigMap — configuração não-sensível

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: minha-api-config
data:
  LOG_LEVEL: "info"
  FEATURE_FLAG_NOVO_CHECKOUT: "true"
  config.yaml: |
    database:
      pool_size: 10
    cache:
      ttl: 300
```

```yaml
# Usando ConfigMap em um Pod
env:
  - name: LOG_LEVEL
    valueFrom:
      configMapKeyRef:
        name: minha-api-config
        key: LOG_LEVEL
volumeMounts:
  - name: config-volume
    mountPath: /app/config
volumes:
  - name: config-volume
    configMap:
      name: minha-api-config
```

### Secret — dados sensíveis

```bash
# Criar Secret via kubectl
kubectl create secret generic db-credentials \
  --from-literal=host=meu-rds.us-east-1.rds.amazonaws.com \
  --from-literal=password=s3cur3P@ssw0rd \
  -n producao

# Verificar (valores são base64, não criptografados por padrão)
kubectl get secret db-credentials -n producao -o yaml
```

> **Atenção:** Secrets do Kubernetes são apenas base64 por padrão — não criptografados. Para dados realmente sensíveis em produção, use **AWS Secrets Manager via IRSA** (coberto no arquivo de segurança) ou habilite **Envelope Encryption** com KMS no cluster.

## Outros tipos de workload

| Objeto | Uso | Quando usar |
|---|---|---|
| **Deployment** | Apps stateless com rolling update | APIs, workers, frontends |
| **StatefulSet** | Apps stateful com identidade persistente | Bancos, Kafka, ZooKeeper |
| **DaemonSet** | Um pod por nó do cluster | Agentes de log, monitoring, segurança |
| **Job** | Execução única até conclusão | Migrações, batch jobs |
| **CronJob** | Job em schedule periódico | Relatórios, limpeza de dados |

```yaml
# CronJob — equivalente ao EventBridge Schedule no ECS
apiVersion: batch/v1
kind: CronJob
metadata:
  name: relatorio-diario
spec:
  schedule: "0 8 * * MON-FRI"  # toda segunda a sexta às 8h UTC
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: relatorio
              image: minha-api:v2.1
              command: ["node", "scripts/gerar-relatorio.js"]
```

## 🧩 Quiz de Fixação

1. Um pod tem `requests.memory: 256Mi` e `limits.memory: 512Mi`. A aplicação começa a vazar memória e chega a 600Mi de uso. O que o Kubernetes faz e por quê é diferente do comportamento com CPU?

2. Um Deployment tem 3 réplicas com `maxSurge: 1` e `maxUnavailable: 1`. Durante um rolling update, quantos pods podem existir simultaneamente no pior caso, e qual é o mínimo de pods disponíveis garantido durante o processo?

3. Um Service do tipo ClusterIP aponta para 3 pods via `selector: app=minha-api`. Dois pods passam na `readinessProbe` e um falha. Uma requisição chega no Service — para qual(is) pod(s) ela pode ser roteada, e o que acontece com o pod que falhou na readiness probe?

**Respostas:**

1) O Kubernetes **mata o container com OOMKilled** (Out of Memory Killed). A diferença do comportamento com CPU é fundamental: **CPU é compressível** — quando um container tenta usar mais CPU do que seu limit, ele é *throttled* (desacelerado), mas continua rodando. **Memória é incompressível** — não há como "desacelerar" o uso de memória; o sistema operacional simplesmente não tem como liberar memória alocada sem matar o processo. Portanto, quando o container ultrapassa `limits.memory`, o kubelet envia SIGKILL imediatamente. O pod é reiniciado (conforme a `restartPolicy`), e se isso acontecer repetidamente, o pod entra em `CrashLoopBackOff`.

2) **Máximo de pods simultâneos:** replicas + maxSurge = 3 + 1 = **4 pods**. **Mínimo garantido disponível:** replicas - maxUnavailable = 3 - 1 = **2 pods**. O processo seria: (1) criar 1 pod novo (surge) → 4 pods; (2) terminar 1 pod antigo (unavailable) → 3 pods; (3) aguardar readiness do novo → repetir. A diferença para `maxUnavailable=0` é que neste caso há momentos com apenas 2 pods servindo tráfego — a capacidade cai temporariamente. Isso acelera o deploy mas reduz a capacidade de atender requisições durante o processo. O trade-off: `maxUnavailable=0` é mais seguro (capacidade constante), `maxUnavailable=1` é mais rápido (terminação antecipada de pods antigos).

3) A requisição pode ser roteada **apenas para os dois pods que passaram na readinessProbe** — o pod que falhou é **removido automaticamente do EndpointSlice do Service**. O kube-proxy mantém a tabela de iptables/IPVS atualizada, excluindo pods com readiness falha. O pod que falhou **não é reiniciado automaticamente** por falha de readiness — ele continua rodando (o processo está vivo), mas simplesmente não recebe tráfego até que a readinessProbe passe novamente. Isso permite que um pod "se recupere" temporariamente (ex: durante um pico de CPU que causou lentidão) sem ser reiniciado. Se o problema for permanente, a **livenessProbe** (configurada separadamente) é quem determina se o pod deve ser reiniciado.
