### Escalamento no EKS — HPA, VPA, Karpenter e Cluster Autoscaler

Escalamento no Kubernetes opera em dois níveis independentes: **escalamento de pods** (quantas réplicas da aplicação rodar) e **escalamento de nós** (quantos servidores EC2 o cluster tem). Esses dois níveis precisam trabalhar juntos — de nada adianta o HPA criar 50 pods se não há nós suficientes para hospedá-los. Este arquivo cobre as quatro ferramentas principais e como elas se coordenam.

---

## Visão geral — dois níveis de escalamento

```
Escalamento em dois níveis:

Nível 1 — Pods (dentro do cluster):
  HPA → escala horizontal (mais réplicas do mesmo pod)
  VPA → escala vertical (mais CPU/memória por pod)
  KEDA → escala por eventos externos (SQS, Kafka, etc.)

Nível 2 — Nós (infraestrutura EC2):
  Cluster Autoscaler → adiciona/remove nós via ASG
  Karpenter          → provisiona nós diretamente (mais rápido e inteligente)

Fluxo típico de um scale-out:
  1. Carga aumenta → HPA decide que precisa de mais pods
  2. Novos pods ficam em Pending (sem nós com capacidade)
  3. Karpenter/CA detecta pods Pending → provisiona novo nó EC2
  4. Nó EC2 entra no cluster → pods são agendados no novo nó
  5. Carga cai → HPA reduz pods → nó fica ocioso
  6. Karpenter/CA consolida e termina o nó ocioso
```

---

## HPA — Horizontal Pod Autoscaler

O **HPA** monitora métricas e ajusta automaticamente o `replicas` de um Deployment (ou StatefulSet) para manter a métrica no valor alvo.

### HPA baseado em CPU (mais comum)

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: minha-api-hpa
  namespace: producao
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: minha-api
  minReplicas: 2
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70  # manter CPU média em 70%
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80  # manter memória média em 80%
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0    # escala up imediatamente
      policies:
        - type: Pods
          value: 4
          periodSeconds: 60            # máximo 4 pods novos por minuto
    scaleDown:
      stabilizationWindowSeconds: 300  # aguarda 5 min antes de reduzir
      policies:
        - type: Percent
          value: 10
          periodSeconds: 60            # reduz no máximo 10% por minuto
```

**`behavior`** é crucial em produção:
- `scaleUp` sem stabilization = reação imediata a picos (correto)
- `scaleDown` com 300s de janela = evita flapping (escalar/desescalar repetidamente em picos brevísimos)

### HPA com métricas customizadas (via KEDA ou Prometheus Adapter)

```yaml
# HPA usando profundidade de fila SQS via KEDA
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: worker-sqs-scaler
  namespace: producao
spec:
  scaleTargetRef:
    name: worker-pedidos
  minReplicaCount: 1
  maxReplicaCount: 50
  triggers:
    - type: aws-sqs-queue
      metadata:
        queueURL: https://sqs.us-east-1.amazonaws.com/123/pedidos
        queueLength: "500"        # 1 pod por 500 mensagens na fila
        awsRegion: us-east-1
      authenticationRef:
        name: keda-trigger-auth-aws
```

### Pré-requisito: metrics-server

O HPA depende do **metrics-server** para coletar métricas de CPU e memória dos pods. No EKS, ele é instalado separadamente:

```bash
# Instalar metrics-server
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

# Verificar funcionamento
kubectl top nodes
kubectl top pods -n producao
```

## VPA — Vertical Pod Autoscaler

O **VPA** (Vertical Pod Autoscaler) analisa o consumo histórico de CPU e memória dos pods e **recomenda ou aplica automaticamente** valores otimizados de requests/limits. Em vez de mais réplicas, ele ajusta o tamanho de cada réplica.

```yaml
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: minha-api-vpa
  namespace: producao
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: minha-api
  updatePolicy:
    updateMode: "Off"  # Off | Initial | Recreate | Auto
  resourcePolicy:
    containerPolicies:
      - containerName: api
        minAllowed:
          cpu: "100m"
          memory: "128Mi"
        maxAllowed:
          cpu: "2"
          memory: "2Gi"
```

### Modos de operação do VPA

```
updateMode: "Off"
  → Apenas coleta dados e gera recomendações
  → Não modifica pods automaticamente
  → Ideal para começar: observar por 24-72h e ajustar manualmente
  → kubectl describe vpa minha-api-vpa → ver recomendações

updateMode: "Initial"
  → Aplica as recomendações apenas em pods NOVOS (após restart)
  → Pods existentes não são modificados
  → Mais seguro que "Auto"

updateMode: "Recreate"
  → Recria pods para aplicar novas recomendações
  → Causa breve downtime por pod (se não houver réplicas suficientes)

updateMode: "Auto"
  → Recria pods automaticamente quando as recomendações mudam
  → Pode causar instabilidade em produção — use com cautela
```

```bash
# Ver recomendações do VPA
kubectl describe vpa minha-api-vpa -n producao

# Saída exemplo:
# Recommendation:
#   Container Recommendations:
#     Container Name: api
#     Lower Bound:
#       Cpu: 100m
#       Memory: 200Mi
#     Target:          ← valor recomendado ideal
#       Cpu: 350m
#       Memory: 384Mi
#     Upper Bound:
#       Cpu: 1
#       Memory: 1Gi
```

### HPA + VPA — incompatibilidade parcial

**HPA e VPA não devem ser usados simultaneamente para CPU e memória** — eles conflitam: HPA adiciona réplicas quando CPU está alta; VPA aumenta o CPU request do pod, o que muda a base de cálculo do HPA. O VPA pode escalar horizontalmente para recursos que não estão sendo gerenciados pelo HPA (ex: VPA para memória + HPA para CPU é uma combinação válida com cuidado).

## Cluster Autoscaler — escalamento de nós via ASG

O **Cluster Autoscaler (CA)** é o mecanismo clássico para escalar os nós EC2 do cluster. Ele monitora pods em estado `Pending` (sem nós com capacidade) e instrui o Auto Scaling Group a lançar novas instâncias.

```
Fluxo do Cluster Autoscaler:

Loop contínuo (a cada ~10s):
  1. Verifica pods em estado Pending
  2. Simula: "Se eu adicionar um nó deste ASG, o pod seria agendado?"
  3. Se sim: aumenta desiredCount do ASG → EC2 é lançado (1-3 min)
  4. Verifica nós subutilizados (< 50% por 10+ minutos)
  5. Drena e termina nós ociosos (respeitando PodDisruptionBudgets)
```

```bash
# Instalar Cluster Autoscaler via Helm
helm repo add autoscaler https://kubernetes.github.io/autoscaler
helm install cluster-autoscaler autoscaler/cluster-autoscaler \
  --namespace kube-system \
  --set autoDiscovery.clusterName=meu-cluster \
  --set awsRegion=us-east-1 \
  --set rbac.serviceAccount.annotations."eks\.amazonaws\.com/role-arn"=\
arn:aws:iam::123:role/ClusterAutoscalerRole
```

### Limitações do Cluster Autoscaler

```
Problemas do CA em produção:

1. Lento: precisa esperar EC2 provisionar (1-3 min) + node join (~1 min)
   Total: 2-4 min de espera para pods Pending serem atendidos

2. Baseado em ASG: limitado aos tipos de instância do ASG pré-configurado
   → Não pode escolher o tipo certo dinamicamente

3. Scale-in conservador: evita terminar nós que podem ter pods críticos
   → Pode deixar nós ociosos por longos períodos

4. Multi-AZ complexo: balancear nós entre AZs requer configuração cuidadosa
   → ASGs separados por AZ são recomendados
```

## Karpenter — a evolução do escalamento de nós

**Karpenter** é um provisionador de nós open-source desenvolvido pela AWS que resolve as limitações do Cluster Autoscaler. Em vez de trabalhar com ASGs, ele provisiona EC2 **diretamente**, com muito mais inteligência e velocidade.

```
Cluster Autoscaler vs Karpenter:

CA: Pod Pending → instrui ASG → ASG lança EC2 (tipo pré-definido)
    → 2-4 minutos para o pod ser atendido

Karpenter: Pod Pending → analisa requisitos do pod → escolhe o tipo
           EC2 ideal → provisiona diretamente → 30-60 segundos
           (frequentemente abaixo de 60s)
```

### Conceitos centrais do Karpenter

```yaml
# NodePool — define as regras para provisionar nós
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: default
spec:
  template:
    metadata:
      labels:
        billing-team: plataforma
    spec:
      nodeClassRef:
        apiVersion: karpenter.k8s.aws/v1
        kind: EC2NodeClass
        name: default
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["spot", "on-demand"]
        - key: kubernetes.io/arch
          operator: In
          values: ["arm64"]          # preferir Graviton
        - key: karpenter.k8s.aws/instance-category
          operator: In
          values: ["m", "c", "r"]    # famílias permitidas
        - key: karpenter.k8s.aws/instance-size
          operator: NotIn
          values: ["nano", "micro", "small"]  # evitar instâncias muito pequenas
  limits:
    cpu: 1000                        # máximo de vCPU total no NodePool
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 30m            # consolidar nós ociosos após 30 min
```

```yaml
# EC2NodeClass — define detalhes de infraestrutura dos nós
apiVersion: karpenter.k8s.aws/v1
kind: EC2NodeClass
metadata:
  name: default
spec:
  amiFamily: AL2023
  role: KarpenterNodeRole
  subnetSelectorTerms:
    - tags:
        karpenter.sh/discovery: meu-cluster
  securityGroupSelectorTerms:
    - tags:
        karpenter.sh/discovery: meu-cluster
  blockDeviceMappings:
    - deviceName: /dev/xvda
      ebs:
        volumeSize: 50Gi
        volumeType: gp3
        encrypted: true
```

### Principais vantagens do Karpenter

```
1. Velocidade: provisionamento em ~30-60s (vs 2-4 min do CA)

2. Flexibilidade de tipo: escolhe automaticamente o melhor tipo
   de instância para cada grupo de pods Pending
   → Pod precisa de 8 CPU + 16 GiB: Karpenter pode escolher
     m7g.2xlarge, c7g.2xlarge, r7g.xlarge — o que estiver mais barato
     e disponível no Spot

3. Consolidação inteligente: detecta nós subutilizados e os consolida
   → Move pods para outros nós → termina nó ocioso
   → Economia automática sem configuração manual

4. Diversificação de Spot: ao usar Spot, escolhe entre muitos tipos
   de instância compatíveis → menor chance de interrupção simultânea

5. Sem ASG: provisiona EC2 diretamente → menos peças para gerenciar
```

### Karpenter com Spot — estratégia de diversificação

```yaml
# NodePool com Spot prioritário e On-Demand como fallback
spec:
  template:
    spec:
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["spot", "on-demand"]
        # Karpenter tentará Spot primeiro (mais barato)
        # Se Spot não disponível: usa On-Demand automaticamente
        - key: karpenter.k8s.aws/instance-family
          operator: In
          values: ["m7g", "m6g", "c7g", "c6g", "r7g"]
          # Diversificação: múltiplas famílias = menor probabilidade de interrupção
```

## Comparativo: CA vs Karpenter

| Aspecto | Cluster Autoscaler | Karpenter |
|---|---|---|
| Velocidade de escala | 2-4 minutos | 30-60 segundos |
| Tipo de instância | Fixo (por ASG) | Dinâmico (qualquer tipo) |
| Integração com Spot | Via ASG com múltiplos tipos | Nativa, com diversificação automática |
| Consolidação | Conservadora | Agressiva e configurável |
| Complexidade de configuração | Menor (mais familiar) | Maior (novo modelo mental) |
| Maturidade | Alta (anos em produção) | Alta (adoção crescente desde 2022) |
| Recomendação AWS | Legado | **Recomendado para novos clusters** |

## Estratégia de escalamento recomendada para produção

```
Configuração recomendada para a maioria dos clusters:

Nível de pods:
  HPA (CPU + memória):
    → minReplicas: 2 (nunca abaixo de 2 para HA)
    → maxReplicas: calculado pelo pico esperado × 1.5
    → scaleDown stabilizationWindow: 300s

  Para workers com fila:
    → KEDA com trigger de queue depth (SQS, Kafka, etc.)

Nível de nós:
  Karpenter:
    → NodePool com Spot + On-Demand como fallback
    → Múltiplas famílias de instância para diversificação
    → consolidateAfter: 30m para nós ociosos
    → limits de CPU/memória total para controle de custo

  Opcional: NodePool separado para workloads críticos (On-Demand only):
    → Banco de dados, serviços core
    → Labels/taints para direcionar pods específicos
```

## 🧩 Quiz de Fixação

1. Um HPA está configurado com `minReplicas: 2`, `maxReplicas: 10`, `averageUtilization: 70%` para CPU. O Deployment tem 4 réplicas com CPU média de 90%. Quantas réplicas o HPA vai criar, e como ele calcula esse número?

2. Por que usar VPA em modo `Auto` em um Deployment de produção sem múltiplas réplicas é perigoso?

3. Karpenter consolida um nó que tem um Pod com `PodDisruptionBudget` de `minAvailable: 2` e o Deployment tem apenas 2 réplicas. O que acontece e por que isso é importante?

**Respostas:**

1) O HPA calcula: `réplicas_desejadas = ceil(réplicas_atuais × (métrica_atual / métrica_alvo))` = `ceil(4 × (90/70))` = `ceil(4 × 1.286)` = `ceil(5.14)` = **6 réplicas**. O HPA aumenta para 6 porque com 6 pods a CPU média esperada seria ~60% (distribuindo a mesma carga por mais instâncias), que está abaixo do target de 70% — e há margem de segurança. O HPA não vai direto para 10 (maxReplicas) porque o algoritmo calcula o número mínimo necessário para atingir o target, não o máximo possível. Após o scale-up, se a CPU continuar alta, o HPA pode escalar novamente no próximo ciclo de avaliação (padrão: 15 segundos).

2) O VPA em modo `Auto` recria os pods para aplicar novas recomendações de CPU e memória. Se um Deployment tem apenas **1 réplica** e o VPA decide recriar o pod (por exemplo, para aumentar o memory request de 256Mi para 512Mi), haverá um período de **downtime** — o pod antigo é terminado e o novo ainda está iniciando. Mesmo com `minAvailable: 1` no PDB, o VPA pode violar essa garantia dependendo da implementação. Para Deployments de produção com 1 réplica, o VPA `Auto` pode causar quedas periódicas e imprevisíveis do serviço. A recomendação é: (a) sempre manter `minReplicas >= 2` para que a recriação de 1 pod não cause downtime; (b) começar com modo `Off` para coletar recomendações e aplicar manualmente; (c) usar modo `Initial` em vez de `Auto` para aplicar apenas em novos pods.

3) O Karpenter **não consegue drenar o pod** desse nó e, portanto, **não termina o nó**. O PodDisruptionBudget garante `minAvailable: 2`, mas o Deployment tem apenas 2 réplicas totais. Para drenar o pod do nó a ser consolidado, o Kubernetes precisaria terminar 1 réplica — mas isso violaria o PDB (ficaria com apenas 1 disponível). O Karpenter respeita PDBs durante consolidação e interrompe o processo quando detecta que a drenagem violaria as garantias configuradas. **Por que isso é importante:** PDBs são o mecanismo correto para garantir que operações de manutenção de nós (consolidação, atualização, substituição) não causem downtime. Eles criam uma "trava" que impede automação excessivamente agressiva de impactar a disponibilidade do serviço. A solução no caso do exemplo seria aumentar o Deployment para 3 réplicas (com `minAvailable: 2`, sempre haverá 1 pod que pode ser terminado sem violar o PDB).
