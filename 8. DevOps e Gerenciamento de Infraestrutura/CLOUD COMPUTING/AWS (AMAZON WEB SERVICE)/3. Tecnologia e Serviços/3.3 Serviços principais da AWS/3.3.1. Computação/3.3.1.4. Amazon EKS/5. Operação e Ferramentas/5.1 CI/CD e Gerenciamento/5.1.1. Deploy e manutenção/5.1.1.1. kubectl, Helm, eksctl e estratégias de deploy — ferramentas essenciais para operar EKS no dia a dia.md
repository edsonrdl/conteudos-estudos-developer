### kubectl, Helm, eksctl e estratégias de deploy — ferramentas essenciais para operar EKS

Operar um cluster EKS no dia a dia envolve três ferramentas indispensáveis: **kubectl** (o CLI do Kubernetes para tudo), **Helm** (gerenciador de pacotes para deploy de aplicações complexas) e **eksctl** (o CLI da AWS para criar e gerenciar clusters). Além das ferramentas, conhecer as estratégias de deploy disponíveis — rolling update, blue/green e canary — define como você lança novas versões sem impacto nos usuários.

---

## kubectl — a interface universal do Kubernetes

`kubectl` é o CLI que se comunica com o API Server do Kubernetes. Praticamente toda operação no cluster passa por ele.

### Configuração e contextos

```bash
# Adicionar cluster EKS ao kubeconfig
aws eks update-kubeconfig --region us-east-1 --name meu-cluster

# Ver configuração atual
kubectl config current-context
kubectl config get-contexts

# Trocar entre clusters
kubectl config use-context arn:aws:eks:us-east-1:123:cluster/staging
kubectl config use-context arn:aws:eks:us-east-1:123:cluster/producao

# Alias útil para evitar digitar namespace sempre
alias k=kubectl
alias kprod="kubectl -n producao"
```

### Comandos do dia a dia — referência rápida

```bash
# ── Visualização ─────────────────────────────────────────────────
kubectl get pods -n producao
kubectl get pods -n producao -o wide          # mostra IPs e nós
kubectl get all -n producao                   # pods, services, deployments
kubectl get events -n producao --sort-by='.lastTimestamp'

# ── Inspeção ─────────────────────────────────────────────────────
kubectl describe pod minha-api-abc123 -n producao   # detalhes + eventos
kubectl describe deployment minha-api -n producao
kubectl describe node ip-10-0-1-10.us-east-1.compute.internal

# ── Logs ─────────────────────────────────────────────────────────
kubectl logs minha-api-abc123 -n producao            # logs do container
kubectl logs minha-api-abc123 -n producao --previous # logs do container anterior (após crash)
kubectl logs -l app=minha-api -n producao --tail=100 # logs de todos os pods com label
kubectl logs -f minha-api-abc123 -n producao          # follow (streaming)

# ── Deploy ───────────────────────────────────────────────────────
kubectl apply -f deployment.yaml              # criar/atualizar (declarativo)
kubectl apply -f ./k8s/                       # aplicar todos os YAMLs de um diretório
kubectl delete -f deployment.yaml             # deletar os recursos do arquivo
kubectl rollout restart deployment/minha-api -n producao  # reiniciar pods

# ── Debugging ────────────────────────────────────────────────────
kubectl exec -it minha-api-abc123 -n producao -- /bin/sh     # shell interativo
kubectl exec minha-api-abc123 -n producao -- env | grep AWS  # comando único
kubectl port-forward svc/minha-api 8080:80 -n producao       # túnel local
kubectl cp minha-api-abc123:/app/logs/app.log ./app.log -n producao  # copiar arquivo

# ── Recursos e saúde ─────────────────────────────────────────────
kubectl top nodes                             # CPU/memória dos nós
kubectl top pods -n producao                  # CPU/memória dos pods
kubectl get hpa -n producao                   # estado do autoscaler
kubectl get pdb -n producao                   # PodDisruptionBudgets

# ── Dry-run e diff ───────────────────────────────────────────────
kubectl apply -f deployment.yaml --dry-run=server  # valida sem aplicar
kubectl diff -f deployment.yaml                    # mostra o que mudaria
```

### Outputs úteis

```bash
# JSON path — extrair campos específicos
kubectl get pods -n producao \
  -o jsonpath='{.items[*].metadata.name}'

# Tabela customizada
kubectl get pods -n producao \
  -o custom-columns='NAME:.metadata.name,STATUS:.status.phase,NODE:.spec.nodeName'

# Filtrar por label
kubectl get pods -l app=minha-api,env=prod -n producao

# Ordenar por uso de memória
kubectl top pods -n producao --sort-by=memory
```

## Helm — gerenciador de pacotes Kubernetes

**Helm** é ao Kubernetes o que o `apt`/`brew` é a um SO — um gerenciador de pacotes que empacota conjuntos de YAMLs em **charts** reutilizáveis, parametrizáveis e versionáveis.

### Conceitos do Helm

```
Chart: pacote Helm (análogo a um pacote npm/pip)
  minha-api/
  ├── Chart.yaml          ← metadados do chart
  ├── values.yaml         ← valores padrão configuráveis
  ├── templates/          ← YAMLs parametrizados com Go templates
  │   ├── deployment.yaml
  │   ├── service.yaml
  │   ├── ingress.yaml
  │   ├── hpa.yaml
  │   └── _helpers.tpl    ← funções auxiliares
  └── charts/             ← dependências (sub-charts)

Release: instância de um chart instalada no cluster
  helm install minha-api ./minha-api -n producao
  ↑ "minha-api" é o nome da release

Repository: coleção de charts (como npm registry)
  helm repo add bitnami https://charts.bitnami.com/bitnami
  helm search repo bitnami/redis
```

### Estrutura de um chart — exemplo real

```yaml
# Chart.yaml
apiVersion: v2
name: minha-api
description: API de pedidos
version: 1.3.0         # versão do chart
appVersion: "v2.1.0"   # versão da aplicação
```

```yaml
# values.yaml — valores padrão (sobrescrevíveis no deploy)
replicaCount: 3
image:
  repository: 123456789.dkr.ecr.us-east-1.amazonaws.com/minha-api
  tag: "v2.1.0"
  pullPolicy: IfNotPresent

resources:
  requests:
    cpu: 250m
    memory: 256Mi
  limits:
    cpu: 500m
    memory: 512Mi

autoscaling:
  enabled: true
  minReplicas: 2
  maxReplicas: 20
  targetCPUUtilizationPercentage: 70

ingress:
  enabled: true
  host: api.meudominio.com
  certificateArn: ""  # sobrescrito por ambiente

service:
  port: 80
  targetPort: 8080
```

```yaml
# templates/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "minha-api.fullname" . }}
  namespace: {{ .Release.Namespace }}
  labels:
    {{- include "minha-api.labels" . | nindent 4 }}
spec:
  {{- if not .Values.autoscaling.enabled }}
  replicas: {{ .Values.replicaCount }}
  {{- end }}
  selector:
    matchLabels:
      {{- include "minha-api.selectorLabels" . | nindent 6 }}
  template:
    metadata:
      labels:
        {{- include "minha-api.selectorLabels" . | nindent 8 }}
    spec:
      containers:
        - name: {{ .Chart.Name }}
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          imagePullPolicy: {{ .Values.image.pullPolicy }}
          resources:
            {{- toYaml .Values.resources | nindent 12 }}
```

### Operações Helm essenciais

```bash
# Instalar um chart
helm install minha-api ./minha-api \
  --namespace producao \
  --create-namespace \
  --values values-prod.yaml \
  --set image.tag=v2.1.0

# Atualizar uma release existente
helm upgrade minha-api ./minha-api \
  --namespace producao \
  --values values-prod.yaml \
  --set image.tag=v2.2.0 \
  --atomic \      # reverte automaticamente se falhar
  --timeout 5m

# Ver histórico de releases
helm history minha-api -n producao

# Rollback para versão anterior
helm rollback minha-api 3 -n producao   # reverte para revisão 3

# Ver o YAML que seria gerado sem aplicar (debug)
helm template minha-api ./minha-api --values values-prod.yaml

# Instalar chart de repositório público (ex: Redis)
helm repo add bitnami https://charts.bitnami.com/bitnami
helm install meu-redis bitnami/redis \
  --namespace cache \
  --set auth.password=minhasenha \
  --set master.persistence.size=10Gi
```

### values por ambiente

```bash
# Estrutura recomendada para múltiplos ambientes:
minha-api/
  values.yaml           ← defaults
  values-staging.yaml   ← overrides de staging
  values-prod.yaml      ← overrides de produção

# Deploy em staging
helm upgrade --install minha-api ./minha-api \
  -f values.yaml \
  -f values-staging.yaml \
  --set image.tag=$(git rev-parse --short HEAD)

# Deploy em produção
helm upgrade --install minha-api ./minha-api \
  -f values.yaml \
  -f values-prod.yaml \
  --set image.tag=v2.1.0
```

## eksctl — CLI para gerenciamento do cluster

**eksctl** é a ferramenta oficial para criar, atualizar e gerenciar clusters EKS. Mais simples e seguro que usar a AWS CLI diretamente.

```bash
# Criar cluster
eksctl create cluster -f cluster.yaml

# Listar clusters
eksctl get cluster --region us-east-1

# Adicionar Node Group
eksctl create nodegroup \
  --cluster meu-cluster \
  --name workers-spot \
  --node-type m7g.large \
  --nodes 3 \
  --managed \
  --spot

# Atualizar versão do Kubernetes (control plane)
eksctl upgrade cluster \
  --name meu-cluster \
  --version 1.30 \
  --approve

# Atualizar Node Group para nova versão K8s
eksctl upgrade nodegroup \
  --cluster meu-cluster \
  --name workers \
  --kubernetes-version 1.30

# Deletar Node Group (drena pods automaticamente)
eksctl delete nodegroup \
  --cluster meu-cluster \
  --name workers-antigo \
  --drain

# Criar IRSA (simplifica a configuração manual)
eksctl create iamserviceaccount \
  --cluster meu-cluster \
  --namespace producao \
  --name minha-api-sa \
  --attach-policy-arn arn:aws:iam::aws:policy/AmazonS3ReadOnlyAccess \
  --approve

# Gerar kubeconfig
eksctl utils write-kubeconfig --cluster meu-cluster
```

## Estratégias de deploy

### Rolling Update (padrão do Deployment)

Já coberto no arquivo de Pods e Deployments. Substitui pods gradualmente, garantindo que sempre haja réplicas disponíveis.

```
Quando usar: maioria das APIs stateless
Vantagem: nativo, sem infraestrutura extra
Desvantagem: v1 e v2 rodam simultaneamente por alguns minutos
```

### Blue/Green Deploy

Duas versões do Deployment rodam simultaneamente — o Service aponta para a versão "active". A troca é feita mudando o selector do Service:

```
Infraestrutura Blue/Green:

Deployment "minha-api-blue" (v1, 3 réplicas) ← atual
Deployment "minha-api-green" (v2, 3 réplicas) ← nova versão

Service "minha-api" aponta para: blue (label: version=blue)
```

```yaml
# Service apontando para blue
spec:
  selector:
    app: minha-api
    version: blue       # apenas pods com version=blue recebem tráfego
```

```bash
# Fazer a troca (zero downtime — muda o selector atomicamente)
kubectl patch service minha-api -n producao \
  -p '{"spec":{"selector":{"app":"minha-api","version":"green"}}}'

# Verificar
kubectl get service minha-api -n producao -o yaml | grep -A5 selector

# Se green tiver problemas: rollback instantâneo
kubectl patch service minha-api -n producao \
  -p '{"spec":{"selector":{"app":"minha-api","version":"blue"}}}'
```

```
Vantagem: rollback instantâneo (muda o selector de volta)
Desvantagem: dobra o custo durante o deploy (dois Deployments ativos)
Quando usar: deploys críticos onde rollback rápido é essencial
```

### Canary Deploy

Envia uma fração do tráfego para a nova versão — útil para validar antes de migrar tudo:

```
Canary com pesos no Ingress (via AWS LBC annotations):

minha-api-deployment (v1): 3 réplicas → recebe 90% do tráfego
minha-api-canary (v2):     1 réplica  → recebe 10% do tráfego
```

```yaml
# Ingress canary — 10% do tráfego vai para a nova versão
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: minha-api-canary
  annotations:
    kubernetes.io/ingress.class: "alb"
    alb.ingress.kubernetes.io/group.name: "producao"
    alb.ingress.kubernetes.io/actions.minha-api: |
      {
        "type": "forward",
        "forwardConfig": {
          "targetGroups": [
            {"serviceName": "minha-api-stable", "servicePort": 80, "weight": 90},
            {"serviceName": "minha-api-canary",  "servicePort": 80, "weight": 10}
          ]
        }
      }
spec:
  rules:
    - http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: minha-api
                port:
                  name: use-annotation
```

```
Vantagem: valida a nova versão com tráfego real antes da migração total
Desvantagem: complexidade maior; v1 e v2 coexistem mais tempo
Quando usar: mudanças de alto risco, experimentos A/B, feature flags
```

### GitOps com ArgoCD — deploy declarativo

**ArgoCD** monitora um repositório Git e sincroniza automaticamente o estado do cluster com o estado declarado no repo:

```
Fluxo GitOps com ArgoCD:

Developer faz merge de PR no Git
  │
  ▼
ArgoCD detecta mudança no repo (polling ou webhook)
  │
  ▼
ArgoCD compara Git state vs cluster state
  │
  ▼
Aplica as diferenças (kubectl apply equivalente)
  │
  ▼
Cluster converge para o estado do Git

Rollback = reverter o commit no Git → ArgoCD sincroniza automaticamente
```

```yaml
# ArgoCD Application — define o que sincronizar
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: minha-api
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/minha-org/k8s-configs
    targetRevision: HEAD
    path: apps/minha-api/producao
    helm:
      valueFiles:
        - values-prod.yaml
  destination:
    server: https://kubernetes.default.svc
    namespace: producao
  syncPolicy:
    automated:
      prune: true      # deleta recursos que saíram do Git
      selfHeal: true   # reverte mudanças manuais no cluster
    syncOptions:
      - CreateNamespace=true
```

## Pipeline CI/CD completo — do commit ao cluster

```
Git push (imagem nova) → GitHub Actions/GitLab CI
  │
  ├── Build Docker image
  ├── Run tests
  ├── Push para ECR: 123.ecr.../minha-api:v2.2.0
  │
  └── Atualizar values.yaml no repo de configuração
      (image.tag: v2.2.0)
        │
        ▼
      ArgoCD detecta mudança
        │
        ▼
      helm upgrade automático no cluster
        │
        ▼
      Rolling update via Kubernetes
```

```bash
# Exemplo de step GitHub Actions para deploy via Helm
- name: Deploy to EKS
  run: |
    aws eks update-kubeconfig --region us-east-1 --name meu-cluster
    helm upgrade --install minha-api ./helm/minha-api \
      --namespace producao \
      --values helm/minha-api/values-prod.yaml \
      --set image.tag=${{ github.sha }} \
      --atomic \
      --timeout 5m \
      --wait
```

## 🧩 Quiz de Fixação

1. Um pod está em `CrashLoopBackOff`. Quais comandos `kubectl` você executaria em sequência para diagnosticar o problema, e o que cada um revela?

2. Um time usa Helm com `--atomic` nos deploys. O deploy de `v2.3.0` falha (pods não ficam saudáveis). O que acontece automaticamente e qual é o estado do cluster após a falha?

3. Qual é a diferença prática entre Blue/Green e Canary deploy em termos de risco, custo e velocidade de rollback, e em qual cenário cada um é a escolha certa?

**Respostas:**

1) Sequência de diagnóstico:
```bash
# 1. Ver o estado e os últimos eventos do pod
kubectl describe pod <nome-do-pod> -n producao
# Revela: motivo do crash, exit code, número de restarts, eventos de scheduling

# 2. Ver logs do container que está crashando
kubectl logs <nome-do-pod> -n producao
# Se o container já reiniciou, os logs atuais podem estar vazios

# 3. Ver logs da execução anterior (antes do crash)
kubectl logs <nome-do-pod> -n producao --previous
# Revela: o que o processo imprimiu antes de morrer (stack trace, erro de configuração)

# 4. Se conseguir acessar antes do crash (janela curta)
kubectl exec -it <nome-do-pod> -n producao -- /bin/sh
# Revela: estado interno, variáveis de ambiente, conectividade de rede

# 5. Verificar eventos do namespace para contexto adicional
kubectl get events -n producao --sort-by='.lastTimestamp' | tail -20
# Revela: OOMKilled, falhas de mount de volume, imagem não encontrada
```
O `--previous` é crucial: em CrashLoopBackOff o container reinicia frequentemente, e os logs do run atual podem ser vazios porque o crash foi rápido. `--previous` mostra o stderr/stdout do último run completo.

2) O flag `--atomic` no Helm faz duas coisas: aguarda que todos os pods fiquem saudáveis dentro do timeout configurado; e se não ficarem, **executa rollback automático para a versão anterior**. Após a falha do deploy de `v2.3.0`, o Helm: (a) detecta que os pods não ficaram em estado `Ready` dentro do timeout; (b) executa `helm rollback` automaticamente para `v2.2.0`; (c) aguarda que `v2.2.0` fique saudável; (d) retorna erro no pipeline de CI/CD. O estado final do cluster é idêntico ao estado antes do deploy — todos os pods rodando `v2.2.0`. O histórico do Helm registra a tentativa falha como uma revisão, visível em `helm history minha-api`. Sem `--atomic`, o Helm retornaria erro mas não faria rollback automático — o cluster ficaria em estado parcialmente atualizado.

3) **Blue/Green:** mantém duas versões completas do Deployment simultaneamente — custo dobra durante o deploy. Rollback é **instantâneo** (muda o selector do Service em milissegundos). Todo o tráfego vai para uma versão de cada vez — sem tráfego misto. Ideal quando: o rollback precisa ser instantâneo (falha crítica detectada pós-deploy), quando as versões são incompatíveis entre si (não podem servir tráfego simultâneo por mudanças de schema de banco), ou quando o time precisa validar a nova versão em ambiente de produção real antes de expor ao tráfego. **Canary:** envia fração do tráfego (ex: 5-10%) para a nova versão enquanto o resto vai para a versão estável. Custo adicional é pequeno (poucos pods). Rollback requer mudar os pesos de roteamento (segundos, mas não atômico). Versões v1 e v2 coexistem servindo tráfego real simultaneamente. Ideal quando: a mudança pode ter comportamento diferente com dados reais e precisa de validação gradual, quando se quer métricas de erro/latência comparativas antes de migrar 100%, ou para experimentos A/B. **Resumo:** Blue/Green = zero tráfego misto, rollback mais rápido, custo maior. Canary = validação gradual com tráfego real, rollback um pouco mais lento, custo menor.
