### Segurança no EKS — IRSA, RBAC e autenticação

Segurança no EKS opera em duas dimensões independentes: **quem pode fazer o quê na API do Kubernetes** (autenticação + RBAC) e **quais serviços AWS os pods podem acessar** (IRSA). Entender cada camada e como elas se complementam é fundamental para construir clusters seguros sem sacrificar a operabilidade.

---

## Duas dimensões de segurança no EKS

```
Dimensão 1 — Acesso à API do Kubernetes:
  "Quem pode criar/listar/deletar pods, deployments, secrets?"
  
  Autenticação: "Quem é você?"
    → AWS IAM (usuários e roles AWS)
    → kubectl usa tokens aws-iam-authenticator
  
  Autorização: "O que você pode fazer?"
    → Kubernetes RBAC (Role-Based Access Control)
    → Roles + RoleBindings + ClusterRoles + ClusterRoleBindings

Dimensão 2 — Acesso a serviços AWS pelos Pods:
  "Este pod pode chamar S3/DynamoDB/SQS?"
  
  IRSA (IAM Roles for Service Accounts):
    → ServiceAccount K8s vinculado a IAM Role AWS
    → Cada pod tem credenciais AWS precisas para sua função
    → Equivalente ao Task Role do ECS
```

---

## IRSA — IAM Roles for Service Accounts

### O problema que IRSA resolve

Antes do IRSA, pods obtinham credenciais AWS através do **Instance Profile** do nó EC2 — ou seja, todos os pods do nó compartilhavam as mesmas permissões da instância. Se um pod precisava de `s3:PutObject`, a instância inteira precisava dessa permissão, afetando todos os outros pods.

```
Sem IRSA (Instance Profile compartilhado — anti-padrão):

Nó EC2 com Instance Profile "NodeRole":
  ├── Pod de API       → usa permissões do NodeRole
  ├── Pod de worker    → usa permissões do NodeRole
  └── Pod comprometido → usa permissões do NodeRole
  
  NodeRole precisa ter TUDO que qualquer pod precise:
  s3:PutObject + dynamodb:* + sqs:* + rds:* ...
  → Qualquer pod comprometido tem acesso a tudo

Com IRSA:
  Pod de API    → IAM Role "ApiRole"    (só DynamoDB:GetItem)
  Pod de worker → IAM Role "WorkerRole" (só SQS:ReceiveMessage)
  Pod comprometido: acesso restrito ao seu Role específico
```

### Como IRSA funciona — OIDC

O IRSA usa o padrão **OIDC (OpenID Connect)**. O EKS age como um OIDC provider — quando um pod precisa de credenciais AWS, ele troca um token JWT do ServiceAccount K8s por credenciais temporárias do STS via `AssumeRoleWithWebIdentity`:

```
Fluxo IRSA:

1. Pod tem ServiceAccount vinculado a IAM Role via anotação

2. Pod inicia: o EKS injeta automaticamente:
   - Token JWT do ServiceAccount em /var/run/secrets/eks.amazonaws.com/serviceaccount/token
   - Variáveis AWS_ROLE_ARN e AWS_WEB_IDENTITY_TOKEN_FILE

3. AWS SDK detecta as variáveis e chama:
   STS:AssumeRoleWithWebIdentity(
     RoleArn: "arn:aws:iam::123:role/MinhaApiRole",
     WebIdentityToken: <JWT do ServiceAccount>
   )

4. AWS STS valida o JWT contra o OIDC provider do cluster

5. STS retorna credenciais temporárias (AccessKey + SecretKey + SessionToken)
   Validade: 1 hora, renovadas automaticamente pelo SDK

6. Pod usa credenciais para chamar S3, DynamoDB, etc.
```

### Configurando IRSA passo a passo

```bash
# 1. Habilitar OIDC provider no cluster (feito uma vez)
eksctl utils associate-iam-oidc-provider \
  --cluster meu-cluster \
  --approve

# Verificar OIDC URL do cluster
aws eks describe-cluster \
  --name meu-cluster \
  --query "cluster.identity.oidc.issuer" \
  --output text
# Saída: https://oidc.eks.us-east-1.amazonaws.com/id/ABCD1234

# 2. Criar IAM Role com trust policy referenciando o OIDC provider
OIDC_PROVIDER=$(aws eks describe-cluster \
  --name meu-cluster \
  --query "cluster.identity.oidc.issuer" \
  --output text | sed 's|https://||')

cat > trust-policy.json << EOF
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "Federated": "arn:aws:iam::123456789:oidc-provider/${OIDC_PROVIDER}"
    },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "${OIDC_PROVIDER}:aud": "sts.amazonaws.com",
        "${OIDC_PROVIDER}:sub": "system:serviceaccount:producao:minha-api-sa"
        # ^ namespace:nome-do-serviceaccount — restringe ao SA específico
      }
    }
  }]
}
EOF

aws iam create-role \
  --role-name MinhaApiRole \
  --assume-role-policy-document file://trust-policy.json

# 3. Adicionar permissões ao Role
aws iam put-role-policy \
  --role-name MinhaApiRole \
  --policy-name MinhaApiPermissions \
  --policy-document '{
    "Version": "2012-10-17",
    "Statement": [{
      "Effect": "Allow",
      "Action": ["dynamodb:GetItem", "dynamodb:PutItem"],
      "Resource": "arn:aws:dynamodb:us-east-1:123:table/pedidos"
    }]
  }'

# 4. Criar ServiceAccount no Kubernetes com a anotação do Role
kubectl create serviceaccount minha-api-sa -n producao

kubectl annotate serviceaccount minha-api-sa -n producao \
  eks.amazonaws.com/role-arn=arn:aws:iam::123:role/MinhaApiRole

# Equivalente em YAML:
```

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: minha-api-sa
  namespace: producao
  annotations:
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789:role/MinhaApiRole
```

```yaml
# 5. Referenciar ServiceAccount no Deployment
spec:
  template:
    spec:
      serviceAccountName: minha-api-sa  # vincula o SA ao pod
      containers:
        - name: api
          image: minha-api:v1
          # AWS SDK usa automaticamente IRSA — nenhum código extra necessário
```

### EKS Pod Identity — substituto mais simples do IRSA

A partir de 2023, a AWS lançou **EKS Pod Identity** como alternativa mais simples ao IRSA — sem configurar OIDC provider manualmente:

```bash
# Instalar o agente de Pod Identity (add-on EKS)
aws eks create-addon \
  --cluster-name meu-cluster \
  --addon-name eks-pod-identity-agent

# Criar associação Pod Identity (substitui a trust policy OIDC)
aws eks create-pod-identity-association \
  --cluster-name meu-cluster \
  --namespace producao \
  --service-account minha-api-sa \
  --role-arn arn:aws:iam::123:role/MinhaApiRole
```

**Diferença principal:** Pod Identity não requer trust policy complexa com OIDC — a associação é feita diretamente na API do EKS. Para novos clusters, Pod Identity é a abordagem recomendada.

## Autenticação na API do Kubernetes

O EKS usa **AWS IAM** para autenticar usuários na API do Kubernetes. O `kubectl` obtém um token JWT temporário via `aws eks get-token` e o envia ao API Server, que valida com o **aws-iam-authenticator**:

```bash
# Como o kubectl autentica no EKS
aws eks update-kubeconfig \
  --region us-east-1 \
  --name meu-cluster \
  --profile meu-perfil-aws

# O kubeconfig gerado usa o AWS CLI para gerar tokens:
# exec:
#   command: aws
#   args: [eks, get-token, --cluster-name, meu-cluster]
```

### access-entries — gestão moderna de acesso ao cluster

A partir de 2024, o EKS usa **Access Entries** como mecanismo moderno (substitui o `aws-auth` ConfigMap):

```bash
# Dar acesso de administrador a um IAM Role
aws eks create-access-entry \
  --cluster-name meu-cluster \
  --principal-arn arn:aws:iam::123:role/DevOpsEngineerRole \
  --type STANDARD

aws eks associate-access-policy \
  --cluster-name meu-cluster \
  --principal-arn arn:aws:iam::123:role/DevOpsEngineerRole \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSClusterAdminPolicy \
  --access-scope type=cluster

# Dar acesso somente leitura a um namespace específico
aws eks create-access-entry \
  --cluster-name meu-cluster \
  --principal-arn arn:aws:iam::123:role/DeveloperRole \
  --type STANDARD

aws eks associate-access-policy \
  --cluster-name meu-cluster \
  --principal-arn arn:aws:iam::123:role/DeveloperRole \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSViewPolicy \
  --access-scope type=namespace namespaces=time-checkout,time-pagamentos
```

## RBAC — autorização dentro do Kubernetes

Após autenticado via IAM, o RBAC do Kubernetes determina **o que o usuário pode fazer** dentro do cluster. O modelo é baseado em Roles (permissões) e Bindings (quem tem a Role):

```
Hierarquia RBAC:

Role         → permissões em um NAMESPACE específico
ClusterRole  → permissões em TODO o cluster (ou compartilhadas entre namespaces)

RoleBinding         → associa Role/ClusterRole a um usuário/grupo em um namespace
ClusterRoleBinding  → associa ClusterRole a um usuário/grupo em todo o cluster
```

### Role e RoleBinding — permissões por namespace

```yaml
# Role: permissões no namespace "producao"
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: developer-role
  namespace: producao
rules:
  - apiGroups: [""]          # "" = core API group
    resources: ["pods", "pods/log", "services"]
    verbs: ["get", "list", "watch"]
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "watch", "update", "patch"]
    # update/patch: permite mudar a imagem (deploy)
    # delete: NÃO incluído — não pode deletar deployments
  - apiGroups: [""]
    resources: ["secrets"]
    verbs: []                # sem acesso a secrets
---
# RoleBinding: associa a Role ao grupo "developers" no namespace
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: developer-binding
  namespace: producao
subjects:
  - kind: Group
    name: "developers"           # grupo IAM → mapeado pelo aws-auth/Access Entry
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: developer-role
  apiGroup: rbac.authorization.k8s.io
```

### ClusterRole e ClusterRoleBinding — permissões globais

```yaml
# ClusterRole para operadores de monitoramento (leitura global)
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: monitoring-reader
rules:
  - apiGroups: [""]
    resources: ["nodes", "pods", "services", "endpoints", "namespaces"]
    verbs: ["get", "list", "watch"]
  - apiGroups: ["apps"]
    resources: ["deployments", "replicasets", "daemonsets", "statefulsets"]
    verbs: ["get", "list", "watch"]
  - nonResourceURLs: ["/metrics", "/healthz"]
    verbs: ["get"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: monitoring-binding
subjects:
  - kind: ServiceAccount
    name: prometheus
    namespace: monitoring
roleRef:
  kind: ClusterRole
  name: monitoring-reader
  apiGroup: rbac.authorization.k8s.io
```

### Verbos RBAC disponíveis

```
Verbos de leitura:  get, list, watch
Verbos de escrita:  create, update, patch, delete, deletecollection
Verbos especiais:   exec (kubectl exec), portforward, proxy

Combinações comuns:
  Somente leitura:  get + list + watch
  Operador:         get + list + watch + update + patch
  Admin namespace:  todos os verbos, sem delete de namespace
  Cluster admin:    todos os verbos em tudo (cuidado!)
```

## Secrets no Kubernetes — limitações e integração com AWS

Secrets K8s são apenas base64 por padrão — qualquer pessoa com `get secrets` no RBAC pode ver o valor. Para dados sensíveis em produção:

### Envelope Encryption com KMS

```bash
# Habilitar envelope encryption no cluster EKS (no momento da criação)
aws eks create-cluster \
  --name meu-cluster \
  --encryption-config '[{
    "resources": ["secrets"],
    "provider": {
      "keyArn": "arn:aws:kms:us-east-1:123:key/abc-123"
    }
  }]'

# Habilitar em cluster existente
aws eks associate-encryption-config \
  --cluster-name meu-cluster \
  --encryption-config '[{
    "resources": ["secrets"],
    "provider": {"keyArn": "arn:aws:kms:us-east-1:123:key/abc-123"}
  }]'
```

Com envelope encryption, os Secrets são criptografados com KMS em repouso no etcd. Ainda visíveis para quem tem acesso RBAC — mas protegidos contra acesso direto ao etcd.

### AWS Secrets Manager no EKS via External Secrets Operator

Para gestão completa (rotação, auditoria, sincronização), o **External Secrets Operator** sincroniza secrets do Secrets Manager como Secrets K8s:

```yaml
# ExternalSecret — puxa do AWS Secrets Manager e cria Secret K8s
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: db-credentials
  namespace: producao
spec:
  refreshInterval: 1h          # sincroniza a cada hora
  secretStoreRef:
    name: aws-secrets-manager
    kind: ClusterSecretStore
  target:
    name: db-credentials       # nome do Secret K8s criado
    creationPolicy: Owner
  data:
    - secretKey: password      # chave no Secret K8s
      remoteRef:
        key: prod/db           # nome no Secrets Manager
        property: password     # campo JSON do secret
    - secretKey: username
      remoteRef:
        key: prod/db
        property: username
```

## Erros comuns e armadilhas

**Trust policy do IRSA com `StringLike` em vez de `StringEquals`:** usar `StringLike: *:sub: system:serviceaccount:*:*` na trust policy permite que QUALQUER ServiceAccount de QUALQUER namespace assuma o Role. Use sempre `StringEquals` com namespace e nome específicos.

**Dar `cluster-admin` para todos os desenvolvedores:** é tentador por simplicidade, mas dá acesso total ao cluster — incluindo leitura de todos os Secrets. Implemente RBAC com permissões mínimas por time/namespace desde o início.

**Não revogar acesso no `aws-auth` ao desligar funcionários:** em clusters antigos usando `aws-auth` ConfigMap, o acesso de um funcionário desligado persiste até ser removido manualmente. Com Access Entries, a revogação do IAM Role na conta AWS automaticamente revoga o acesso ao cluster.

**Não auditar com CloudTrail:** toda chamada à API do EKS (incluindo kubectl) gera eventos no CloudTrail. Habilitar CloudTrail + audit logs do EKS permite investigar "quem deletou o deployment de produção às 2h da manhã".

## 🧩 Quiz de Fixação

1. Por que a condition `StringEquals` na trust policy do IRSA deve especificar tanto o namespace quanto o nome do ServiceAccount, e o que acontece se especificar apenas o namespace?

2. Um desenvolvedor tem uma `Role` com `verbs: ["get", "list", "watch", "update", "patch"]` para deployments, mas não consegue executar `kubectl exec` em pods. Por que, e o que precisaria ser adicionado ao RBAC?

3. Uma empresa usa IRSA para dar ao pod de backup acesso ao S3. O backup está funcionando. Após 59 minutos, o pod começa a retornar erros de `ExpiredTokenException` do AWS SDK. Qual é a causa e como o AWS SDK deveria tratar isso?

**Respostas:**

1) Se a condition especificar apenas o namespace (ex: `system:serviceaccount:producao:*`), **qualquer ServiceAccount dentro do namespace `producao`** pode assumir o Role — incluindo ServiceAccounts de outros workloads, controllers, ou pods comprometidos naquele namespace. Isso viola o princípio do menor privilégio no nível de pod. Com `StringEquals` especificando `system:serviceaccount:producao:minha-api-sa`, apenas o ServiceAccount exato `minha-api-sa` no namespace `producao` pode assumir o Role. A granularidade deve ser: um IAM Role por aplicação (ou até por componente), nunca um Role compartilhado por namespace inteiro.

2) `kubectl exec` não é uma operação sobre o objeto `pods` em si — é uma operação sobre o sub-recurso `pods/exec`. RBAC no Kubernetes diferencia recursos de sub-recursos. Para permitir `kubectl exec`, é necessário adicionar à Role:
```yaml
- apiGroups: [""]
  resources: ["pods/exec"]
  verbs: ["create"]
```
Da mesma forma, `kubectl logs` requer `pods/log` com `get`, e `kubectl port-forward` requer `pods/portforward` com `create`. O RBAC do K8s é granular ao nível de sub-recurso — um desenvolvedor pode ter `get pods` sem conseguir fazer `exec` nos pods.

3) A causa é que as credenciais IRSA têm validade de **1 hora** (TTL padrão do STS). Após 59 minutos de uso contínuo, as credenciais expiram. O AWS SDK deve **renovar automaticamente** as credenciais antes de expirar — e faz isso por padrão quando configurado corretamente com IRSA. O problema geralmente ocorre quando: (a) o AWS SDK está desatualizado e não implementa renovação automática via `WebIdentityTokenFileCredentialsProvider`; (b) as credenciais foram cached manualmente pelo código da aplicação sem respeitar o `expiration` field; (c) o token JWT do ServiceAccount expirou (validade configurada no cluster — geralmente 24h). A solução correta é usar o **AWS SDK v2** (ou boto3 >= 1.9 para Python), que implementa refresh automático de credenciais IRSA, e nunca armazenar em cache as credenciais AWS além do `Expiration` retornado pelo STS.
