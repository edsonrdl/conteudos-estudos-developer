### Amazon EKS — o que é, como gerencia o plano de controle e diferença em relação ao ECS

Amazon EKS (Elastic Kubernetes Service) é o serviço gerenciado da AWS para executar Kubernetes. Kubernetes é o orquestrador de containers open-source mais adotado no mundo — e EKS resolve seu principal problema prático: operar o plano de controle (control plane) do Kubernetes é complexo, trabalhoso e crítico para a disponibilidade do cluster. O EKS gerencia esse componente, deixando você responsável apenas pelos nós de trabalho e pelos workloads.

---

## O que é Kubernetes e por que ele existe

Antes de entender o EKS, é necessário entender o problema que o Kubernetes resolve. Containers Docker resolvem o empacotamento de aplicações — mas não respondem: onde rodar? Como reiniciar se falhar? Como escalar? Como distribuir tráfego?

```
Kubernetes — o orquestrador:

Você declara o estado desejado:
  "Quero 5 réplicas da minha API rodando,
   com no máximo 1 GiB de RAM cada,
   expostas na porta 80 via load balancer"

Kubernetes garante esse estado continuamente:
  → Distribui os 5 pods entre os nós disponíveis
  → Reinicia pods que falham
  → Escala de 5 para 20 se a CPU aumentar
  → Substitui pods em nós que ficam indisponíveis
  → Faz rolling deploy sem downtime quando a imagem muda

Você nunca diz "faça X" — você declara "o estado deve ser Y"
e o Kubernetes trabalha continuamente para convergir para esse estado.
```

## A arquitetura do Kubernetes — Control Plane e Data Plane

Kubernetes tem dois planos separados:

```
┌─────────────────────────────────────────────────────────────────┐
│                    CONTROL PLANE                                │
│  (o "cérebro" do cluster — decide o que rodar e onde)          │
│                                                                 │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────────────┐  │
│  │ API Server   │  │  Scheduler   │  │  Controller Manager  │  │
│  │ (ponto de   │  │  (decide em  │  │  (garante que o      │  │
│  │  entrada de  │  │   qual nó    │  │   estado atual =     │  │
│  │  toda API)   │  │   vai o pod) │  │   estado desejado)   │  │
│  └──────────────┘  └──────────────┘  └──────────────────────┘  │
│  ┌──────────────┐                                               │
│  │    etcd      │  ← banco de dados distribuído com TODO       │
│  │  (estado do  │    o estado do cluster (extremamente crítico) │
│  │   cluster)   │                                               │
│  └──────────────┘                                               │
└─────────────────────────────────────────────────────────────────┘
                           │ API
                           │
┌─────────────────────────────────────────────────────────────────┐
│                      DATA PLANE                                 │
│  (os nós de trabalho — onde os containers realmente rodam)      │
│                                                                 │
│  ┌─────────────────────┐   ┌─────────────────────┐             │
│  │   Worker Node 1     │   │   Worker Node 2     │             │
│  │  ┌───────────────┐  │   │  ┌───────────────┐  │             │
│  │  │    kubelet    │  │   │  │    kubelet    │  │ ← agente    │
│  │  │  (comunica    │  │   │  │               │  │   que       │
│  │  │   com API     │  │   │  │               │  │   executa   │
│  │  │   server)     │  │   │  │               │  │   as ordens │
│  │  └───────────────┘  │   │  └───────────────┘  │             │
│  │  ┌──────┐ ┌──────┐  │   │  ┌──────┐ ┌──────┐  │             │
│  │  │ Pod1 │ │ Pod2 │  │   │  │ Pod3 │ │ Pod4 │  │             │
│  │  └──────┘ └──────┘  │   │  └──────┘ └──────┘  │             │
│  └─────────────────────┘   └─────────────────────┘             │
└─────────────────────────────────────────────────────────────────┘
```

**O problema de operar o Control Plane:**
- O `etcd` precisa de alta disponibilidade (3 ou 5 instâncias em quorum)
- O API Server é o ponto de acesso de tudo — precisa de uptime 99.9%+
- Upgrades do Kubernetes são complexos e arriscados
- Backup e restauração do etcd são críticos e delicados
- Certificados TLS expiram e precisam ser renovados

Com Kubernetes self-managed, tudo isso é responsabilidade sua. Com EKS, a AWS assume.

## Como o EKS gerencia o Control Plane

O EKS opera o Control Plane em **infraestrutura separada e dedicada** para cada cluster, invisível para o usuário:

```
Amazon EKS — o que a AWS gerencia vs. o que você gerencia:

┌─────────────────────────────────────────────────────────────┐
│              GERENCIADO PELA AWS (EKS)                      │
│                                                             │
│  Control Plane multi-AZ (3 AZs por padrão):                │
│  ├── API Server (HA, com endpoint público ou privado)       │
│  ├── etcd (3 instâncias em quorum, backup automático)       │
│  ├── Scheduler + Controller Manager                         │
│  ├── Upgrades do Kubernetes (você escolhe quando)           │
│  ├── Rotação de certificados TLS                            │
│  └── Patches de segurança do control plane                  │
│                                                             │
│  SLA: 99.95% de disponibilidade do API server              │
└─────────────────────────────────────────────────────────────┘
                         │ API segura (TLS)
                         │
┌─────────────────────────────────────────────────────────────┐
│              GERENCIADO POR VOCÊ                            │
│                                                             │
│  Data Plane (Worker Nodes):                                 │
│  ├── EC2 Node Groups (você provisiona, patch, atualiza)     │
│  │   ou Fargate Profiles (AWS gerencia os nós)              │
│  ├── Add-ons (CoreDNS, kube-proxy, VPC CNI, etc.)           │
│  ├── Workloads (Deployments, Services, ConfigMaps...)       │
│  ├── RBAC e permissões IAM para Service Accounts            │
│  └── Networking (VPC, subnets, security groups)             │
└─────────────────────────────────────────────────────────────┘
```

### Custo do Control Plane

O EKS cobra **$0.10/hora por cluster** (~$72/mês) pelo control plane gerenciado, independente de quantos nós ou pods rodam. Os nós EC2 são cobrados separadamente pelo preço normal de EC2.

```
Custo total de um cluster EKS:
  Control Plane: $0.10/h × 720h = $72/mês (fixo)
  Worker Nodes:  depende do tipo/quantidade de EC2
  
  Cluster pequeno (3× m7g.large):
    Control plane: $72/mês
    3× m7g.large On-Demand: 3 × $0.0816 × 720 = $176/mês
    Total: ~$248/mês
    
  Comparação com ECS Fargate (mesma carga):
    Sem custo de "cluster" — paga apenas pelas tasks
    Para workloads pequenos: ECS Fargate é mais barato
    Para clusters grandes com muitos workloads: $72 se diluem
```

## Criando um cluster EKS

### Via eksctl (forma mais simples)

```bash
# Instalar eksctl
brew install eksctl  # macOS
# ou: https://eksctl.io/installation/

# Criar cluster com configuração mínima
eksctl create cluster \
  --name meu-cluster \
  --region us-east-1 \
  --version 1.30 \
  --nodegroup-name workers \
  --node-type m7g.large \
  --nodes 3 \
  --nodes-min 2 \
  --nodes-max 10 \
  --managed  # Node Group gerenciado pela AWS (recomendado)

# Configurar kubectl para usar o cluster
aws eks update-kubeconfig \
  --region us-east-1 \
  --name meu-cluster

# Verificar conectividade
kubectl get nodes
kubectl get pods -A
```

### Via arquivo de configuração (ClusterConfig)

```yaml
# cluster.yaml — configuração declarativa
apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig

metadata:
  name: producao
  region: us-east-1
  version: "1.30"
  tags:
    Environment: production
    Team: platform

vpc:
  cidr: 10.0.0.0/16

managedNodeGroups:
  - name: workers-geral
    instanceType: m7g.large
    minSize: 3
    maxSize: 20
    desiredCapacity: 5
    amiFamily: AmazonLinux2023
    privateNetworking: true  # nós apenas em subnets privadas
    iam:
      attachPolicyARNs:
        - arn:aws:iam::aws:policy/AmazonEKSWorkerNodePolicy
        - arn:aws:iam::aws:policy/AmazonEKS_CNI_Policy
        - arn:aws:iam::aws:policy/AmazonEC2ContainerRegistryReadOnly

  - name: workers-gpu
    instanceType: g5.xlarge
    minSize: 0
    maxSize: 5
    labels:
      workload: ml-inference

addons:
  - name: vpc-cni
    version: latest
  - name: coredns
    version: latest
  - name: kube-proxy
    version: latest
  - name: aws-ebs-csi-driver
    version: latest
```

```bash
# Criar cluster a partir do arquivo
eksctl create cluster -f cluster.yaml
```

## EKS vs ECS — diferença fundamental

Ambos orquestram containers na AWS, mas partem de filosofias e trade-offs opostos:

```
ECS — orquestrador proprietário AWS:
  Conceitos próprios:  Cluster, Service, Task, Task Definition
  Integração:          Nativa e profunda com ALB, IAM, CloudWatch
  Complexidade:        Baixa — menos peças, menos configuração
  Portabilidade:       Nenhuma — 100% AWS
  Curva aprendizado:   Semanas para produtividade
  Custo de cluster:    Nenhum (sem custo de control plane)

EKS — Kubernetes gerenciado na AWS:
  Conceitos K8s:       Pod, Deployment, Service, Ingress, ConfigMap
  Integração:          Via add-ons e controllers (AWS LBC, IRSA, etc.)
  Complexidade:        Alta — mais peças, mais configuração, mais YAML
  Portabilidade:       Alta — mesmo YAML roda em GKE, AKS, on-prem
  Curva aprendizado:   Meses para dominar Kubernetes + especificidades EKS
  Custo de cluster:    $72/mês por cluster (control plane)
```

### Mapeamento de conceitos ECS → Kubernetes

| Conceito ECS | Equivalente Kubernetes |
|---|---|
| Task | Pod |
| Task Definition | Pod Spec / Deployment |
| Service | Deployment + Service |
| Cluster | Cluster + Namespace |
| Target Group | Service (ClusterIP/LoadBalancer) |
| ALB Listener Rule | Ingress |
| Task Role (IRSA) | ServiceAccount + IAM Role |
| Container Insights | metrics-server + Prometheus |
| Fargate Profile | Fargate Profile (EKS também tem) |

## O ecossistema Kubernetes — por que times escolhem EKS

A grande vantagem do EKS não é o EKS em si — é o **ecossistema open-source do Kubernetes**:

```
Ferramentas do ecossistema K8s disponíveis no EKS:

CI/CD e GitOps:
  ArgoCD    → deploy declarativo via Git (GitOps)
  Flux      → alternativa ao ArgoCD
  Tekton    → pipelines CI nativas no cluster

Service Mesh:
  Istio     → observabilidade, traffic management, mTLS
  Linkerd   → service mesh mais simples que Istio
  AWS App Mesh → alternativa gerenciada da AWS

Escalamento avançado:
  Karpenter → provisionamento de nós inteligente e rápido
  KEDA      → Event Driven Autoscaling (SQS, Kafka, etc.)

Observabilidade:
  Prometheus + Grafana → métricas e dashboards
  Jaeger / Tempo       → distributed tracing
  Loki                 → agregação de logs

Segurança:
  OPA/Gatekeeper → policy enforcement
  Falco          → runtime security
  cert-manager   → gestão automática de certificados TLS

Nenhuma dessas ferramentas existe nativamente no ECS.
```

## Versões do Kubernetes e ciclo de atualização

O EKS suporta versões do Kubernetes com um ciclo de vida bem definido. É responsabilidade do operador manter o cluster atualizado:

```
Suporte de versões EKS (exemplo):
  1.28 → suporte até Nov 2024
  1.29 → suporte até Mar 2025
  1.30 → suporte até Jul 2025
  1.31 → suporte até Nov 2025

Processo de atualização:
  1. Atualizar o Control Plane:
     eksctl upgrade cluster --name meu-cluster --version 1.30

  2. Atualizar os add-ons (CoreDNS, kube-proxy, VPC CNI):
     eksctl utils update-coredns --cluster meu-cluster
     eksctl utils update-kube-proxy --cluster meu-cluster
     eksctl utils update-aws-node --cluster meu-cluster

  3. Atualizar os Node Groups (rolling update dos nós):
     eksctl upgrade nodegroup \
       --cluster meu-cluster \
       --name workers-geral \
       --kubernetes-version 1.30

  4. Verificar workloads após atualização:
     kubectl get pods -A
```

A AWS cobra uma taxa adicional por versões com **extended support** (após o fim do suporte padrão): +$0.60/hora por cluster (~$432/mês). Manter o cluster atualizado é economicamente importante além de ser uma boa prática de segurança.

## Erros comuns e armadilhas

**Subestimar a complexidade operacional:** EKS resolve o control plane, mas o data plane (nós, add-ons, upgrades, networking) ainda exige expertise. Times sem experiência em Kubernetes frequentemente subestimam o trabalho necessário para operar EKS em produção de forma confiável.

**Um único cluster para tudo:** colocar produção e desenvolvimento no mesmo cluster cria riscos de isolamento e de "vizinho barulhento" (um workload consumindo recursos de outro). Use namespaces para isolamento lógico e clusters separados para isolamento físico em ambientes críticos.

**Ignorar o custo de $72/mês:** para projetos pequenos ou times com 2-3 microsserviços, $72/mês de control plane mais os nós pode ser mais caro que ECS Fargate. Consolide workloads em menos clusters.

**Não automatizar upgrades:** versões sem suporte não recebem patches de segurança. Configure processos de upgrade regulares antes que a versão entre em "extended support" (custo 6x maior).

## 🧩 Quiz de Fixação

1. Por que o `etcd` é considerado o componente mais crítico do Kubernetes, e como o EKS resolve o problema de sua operação?

2. Um time tem 3 microsserviços simples (APIs REST stateless) e está decidindo entre ECS Fargate e EKS. O custo total mensal esperado é de $200 em compute. Como o custo de $72/mês do EKS control plane impacta essa decisão?

3. O que significa o Kubernetes ser "declarativo" em vez de "imperativo", e qual é a vantagem prática disso para operações de produção?

**Respostas:**

1) O `etcd` é um banco de dados chave-valor distribuído que armazena **todo o estado do cluster Kubernetes** — quais pods existem, em quais nós estão, qual é a configuração de cada Service, Deployment, Secret e ConfigMap. Se o `etcd` for corrompido ou perdido, o cluster perde toda a memória de estado e não pode ser recuperado sem um backup — essencialmente o cluster "morre". Operá-lo corretamente exige: (a) cluster de 3 ou 5 instâncias em quorum para tolerância a falhas; (b) backups regulares e testados; (c) monitoramento de espaço em disco e latência; (d) procedimentos rigorosos de upgrade. O EKS resolve isso ao operar o etcd em infraestrutura dedicada multi-AZ, com backup automático, monitoramento contínuo e garantia de SLA de 99.95% — removendo completamente essa responsabilidade do operador.

2) O custo de $72/mês representa **36% do total de compute** ($72/$200). Para 3 microsserviços simples e stateless, ECS Fargate é muito mais adequado: sem custo de control plane, mesma capacidade de escalonamento automático, integração nativa com ALB e IAM sem add-ons adicionais. EKS só justificaria o custo extra de $72/mês se o time já tivesse expertise em Kubernetes (economizando tempo de aprendizado), se houvesse necessidade de ferramentas específicas do ecossistema K8s (ArgoCD, Istio, KEDA), ou se houvesse planos concretos de portabilidade multi-cloud. Para 3 APIs REST simples com time sem K8s skills, ECS Fargate entrega o mesmo resultado operacional por $72/mês menos.

3) **Imperativo** significa "execute este comando agora": `kubectl scale deployment minha-api --replicas=5`. **Declarativo** significa "o estado desejado é este": um arquivo YAML dizendo `replicas: 5` aplicado com `kubectl apply`. A vantagem prática: (a) **idempotência** — aplicar o mesmo YAML múltiplas vezes tem o mesmo efeito que aplicar uma vez (ao contrário de comandos imperativos que podem criar duplicatas); (b) **GitOps** — o estado do cluster pode ser versionado em Git e qualquer drift é detectável comparando Git vs cluster real; (c) **auto-healing** — o Controller Manager monitora continuamente o estado real vs. desejado e corrige automaticamente qualquer divergência (pod morreu? K8s sobe outro; nó ficou indisponível? K8s reprograma os pods em outros nós). Em produção, isso significa que o cluster converge para o estado correto mesmo após falhas, sem intervenção manual.
