### Componentes do cluster EKS — Control Plane, Node Groups e Add-ons

Um cluster EKS é composto por três camadas distintas: o **Control Plane** (gerenciado pela AWS), o **Data Plane** (nós onde os pods rodam — sua responsabilidade) e os **Add-ons** (componentes que estendem as capacidades do Kubernetes). Entender cada camada e as opções disponíveis é fundamental para projetar clusters eficientes, seguros e com o custo correto.

---

## Camada 1 — Control Plane (gerenciado pela AWS)

O Control Plane do EKS roda em VPC dedicada da AWS — separada da sua VPC — e expõe um **endpoint do API Server** que você acessa via `kubectl`. Por padrão, esse endpoint é público (acessível pela internet com autenticação), mas pode ser configurado como privado.

```
Opções de endpoint do API Server:

Público (padrão):
  → Acessível via internet
  → kubectl funciona de qualquer lugar com credenciais corretas
  → Nós EC2 na sua VPC se comunicam via internet pública

Público + Privado:
  → Acesso externo via internet (para ops remotas)
  → Comunicação nó ↔ API Server via rede privada (sem saída para internet)
  → Recomendado para produção

Privado:
  → Apenas acessível dentro da VPC (via VPN ou Direct Connect)
  → kubectl só funciona dentro da VPC ou via VPN
  → Maior segurança, maior restrição operacional
```

```bash
# Configurar endpoint como público+privado (recomendado)
aws eks update-cluster-config \
  --name meu-cluster \
  --resources-vpc-config \
    endpointPublicAccess=true,\
    endpointPrivateAccess=true,\
    publicAccessCidrs="203.0.113.0/24"  # restringir acesso público ao IP do escritório
```

## Camada 2 — Data Plane: onde os pods rodam

O Data Plane é composto pelos **nós de trabalho** (worker nodes). O EKS oferece três formas de provisionar esses nós, com diferentes trade-offs de controle e responsabilidade:

### Opção A — Managed Node Groups (recomendado)

Node Groups gerenciados são grupos de instâncias EC2 provisionadas e mantidas pelo EKS, com integração nativa para atualizações e drenagem de nós:

```
Managed Node Group — o que o EKS gerencia:
  ├── Provisionamento das instâncias EC2
  ├── Registro automático no cluster (kubelet configurado)
  ├── Atualização de versão do Kubernetes (rolling update dos nós)
  ├── Drenagem segura antes de terminar nós (respeitando PodDisruptionBudgets)
  └── Integração com Auto Scaling Group

Você ainda é responsável por:
  ├── Escolher o tipo de instância
  ├── Definir min/max/desired de nós
  ├── Aplicar patches de SO entre versões K8s (ou usar Launch Templates customizados)
  └── Monitorar custo e utilização
```

```bash
# Criar Managed Node Group
aws eks create-nodegroup \
  --cluster-name meu-cluster \
  --nodegroup-name workers \
  --node-role arn:aws:iam::123:role/AmazonEKSNodeRole \
  --subnets subnet-abc123 subnet-def456 \
  --instance-types m7g.large m7g.xlarge \  # múltiplos tipos = mais disponibilidade Spot
  --ami-type AL2023_ARM_64_STANDARD \      # Amazon Linux 2023 ARM (Graviton)
  --capacity-type ON_DEMAND \              # ON_DEMAND ou SPOT
  --scaling-config minSize=2,maxSize=10,desiredSize=3 \
  --labels 'workload=geral,env=prod'
```

```yaml
# Labels e taints por Node Group — para direcionar pods a nós específicos
labels:
  workload: geral
  env: prod

taints:
  - key: dedicated
    value: gpu-workloads
    effect: NoSchedule
# Apenas pods com toleration para este taint serão colocados nesses nós
```

### Opção B — Self-managed Node Groups

Você provisiona e gerencia as instâncias EC2 manualmente, usando Launch Templates e Auto Scaling Groups. Mais trabalhoso, mas permite customizações que o Managed Node Group não suporta (ex: Bottlerocket OS customizado, configurações específicas de kernel, Nitro Enclaves):

```bash
# Registrar manualmente um nó EC2 no cluster EKS
# (via User Data na instância):
/etc/eks/bootstrap.sh meu-cluster \
  --b64-cluster-ca <CA_DATA> \
  --apiserver-endpoint <API_ENDPOINT>
```

### Opção C — Fargate Profiles

Com Fargate, **cada pod roda em sua própria microVM** gerenciada pela AWS — sem nós EC2 para provisionar ou gerenciar. É equivalente ao ECS Fargate mas no contexto do Kubernetes:

```yaml
# Fargate Profile — define quais pods vão para Fargate
apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig
metadata:
  name: meu-cluster

fargateProfiles:
  - name: default
    selectors:
      - namespace: fargate-ns        # todos os pods neste namespace
      - namespace: kube-system
        labels:
          app: coredns               # apenas pods com este label
```

```
Limitações do Fargate no EKS:
  ✗ Sem suporte a DaemonSets (não há "host" para anexar)
  ✗ Sem volumes hostPath ou emptyDir persistentes
  ✗ Sem GPU
  ✗ Sem acesso privilegiado ao host
  ✗ Cada pod tem exatamente 1 container (sem sidecars de init complexos)
  ✓ Zero gerenciamento de nós
  ✓ Isolamento por microVM (segurança superior)
  ✓ Paga por pod (vCPU + memória), não por nó
```

### Comparativo das opções de Data Plane

| Aspecto | Managed Node Group | Self-managed | Fargate |
|---|---|---|---|
| Gerenciamento | Baixo | Alto | Zero |
| Flexibilidade | Média | Máxima | Baixa |
| DaemonSets | Sim | Sim | Não |
| GPU | Sim | Sim | Não |
| Custo 24/7 | EC2 (nós ociosos pagam) | EC2 | Por pod |
| Custo variável | EC2 + ASG | EC2 + ASG | Excelente |
| Kubernetes features | Todas | Todas | Subset |

**Padrão recomendado:** Managed Node Groups para a maioria dos workloads + Fargate para workloads de desenvolvimento, jobs batch e namespaces isolados.

## Tipos de instância e AMIs para Worker Nodes

### AMI Types disponíveis

| AMI Type | Base OS | Arquitetura | Quando usar |
|---|---|---|---|
| `AL2023_x86_64_STANDARD` | Amazon Linux 2023 | x86_64 | Padrão Intel/AMD |
| `AL2023_ARM_64_STANDARD` | Amazon Linux 2023 | ARM64 | Graviton (20% mais barato) |
| `AL2023_x86_64_NVIDIA` | AL2023 + NVIDIA drivers | x86_64 | Nós GPU |
| `BOTTLEROCKET_x86_64` | Bottlerocket | x86_64 | Segurança máxima |
| `BOTTLEROCKET_ARM_64` | Bottlerocket | ARM64 | Segurança + Graviton |
| `WINDOWS_CORE_2022_x86_64` | Windows Server Core | x86_64 | Containers Windows |

**Graviton (ARM64)** é a escolha padrão para novos clusters — 20% mais barato, mesmo desempenho ou superior para workloads Linux nativos.

## Camada 3 — Add-ons do EKS

Add-ons são componentes de sistema que estendem as capacidades do Kubernetes. O EKS gerencia o ciclo de vida deles (instalação, atualização, compatibilidade de versão):

### Add-ons gerenciados pela AWS (EKS Add-ons)

```
Add-on          │ Função                                   │ Obrigatório?
────────────────┼──────────────────────────────────────────┼────────────
vpc-cni         │ Atribui IPs da VPC a pods (AWS VPC CNI)  │ Sim
coredns         │ DNS interno do cluster                   │ Sim
kube-proxy      │ Roteamento de rede entre pods/services   │ Sim
aws-ebs-csi     │ Volumes EBS como PersistentVolumes       │ Recomendado
aws-efs-csi     │ Volumes EFS compartilhados               │ Opcional
eks-pod-identity│ Autenticação IAM para pods (nova IRSA)   │ Recomendado
```

```bash
# Listar add-ons instalados no cluster
aws eks list-addons --cluster-name meu-cluster

# Instalar ou atualizar um add-on
aws eks create-addon \
  --cluster-name meu-cluster \
  --addon-name aws-ebs-csi-driver \
  --addon-version v1.26.0-eksbuild.1 \
  --service-account-role-arn arn:aws:iam::123:role/EBSCSIDriverRole

# Ver versões disponíveis de um add-on
aws eks describe-addon-versions \
  --addon-name vpc-cni \
  --query 'addons[0].addonVersions[*].addonVersion'
```

### VPC CNI — o add-on mais crítico

O **AWS VPC CNI** (Container Network Interface) é responsável por atribuir IPs da VPC diretamente a cada pod — sem NAT, sem overlay de rede. Cada pod recebe um IP real da subnet:

```
VPC CNI — como funciona:

Subnet: 10.0.1.0/24 (253 IPs disponíveis)

Worker Node (m7g.large):
  ENI primária: 10.0.1.10 (IP do nó)
  ENIs secundárias: até 3 ENIs com até 10 IPs cada
  → Total: até ~30 pods por nó (depende do tipo)

Pods no nó:
  Pod A: 10.0.1.20 ← IP real da VPC
  Pod B: 10.0.1.21 ← IP real da VPC
  Pod C: 10.0.1.22 ← IP real da VPC

Comunicação pod ↔ pod:
  Pod A (10.0.1.20) → Pod B em outro nó (10.0.2.15)
  → Tráfego direto na VPC, sem encapsulamento
  → Mesma latência que EC2 ↔ EC2
```

**Implicação importante:** o número de pods por nó é limitado pelo número de IPs que a instância EC2 pode ter. Instâncias menores têm menos ENIs e menos IPs disponíveis — isso afeta o planejamento de capacidade:

```bash
# Verificar o limite de pods por tipo de instância
# m7g.large: 3 ENIs × 10 IPs = 29 pods máximos (30 - 1 para o nó)
# m7g.xlarge: 4 ENIs × 15 IPs = 58 pods máximos

# Habilitar prefix delegation (aumenta drasticamente o limite de pods)
kubectl set env daemonset aws-node \
  -n kube-system \
  ENABLE_PREFIX_DELEGATION=true
# Com prefix delegation: cada IP secundário vira /28 = 16 IPs
# m7g.large: 3 ENIs × 10 prefixes × 16 IPs = ~480 pods por nó
```

### CoreDNS — DNS interno do cluster

CoreDNS resolve nomes de services dentro do cluster:

```
Resolução DNS no cluster:

minha-api.default.svc.cluster.local
├── minha-api        → nome do Service
├── default          → namespace
├── svc              → tipo (service)
└── cluster.local    → domínio do cluster

De dentro de qualquer pod no namespace "default":
  curl http://minha-api          → mesmo namespace, funciona
  curl http://minha-api.default  → com namespace, funciona
  curl http://minha-api.pagamentos.svc.cluster.local → namespace diferente
```

## Namespaces — isolamento lógico dentro do cluster

Namespaces dividem logicamente os recursos de um cluster entre times, ambientes ou aplicações:

```yaml
# Criar namespace para um time
apiVersion: v1
kind: Namespace
metadata:
  name: time-checkout
  labels:
    team: checkout
    env: production
```

```bash
kubectl create namespace time-checkout

# Trabalhar em um namespace específico
kubectl get pods -n time-checkout
kubectl apply -f deployment.yaml -n time-checkout

# Definir namespace padrão para a sessão
kubectl config set-context --current --namespace=time-checkout
```

```
Boas práticas de namespaces:
  kube-system     → componentes do K8s (não modifique)
  kube-public     → recursos públicos (raro usar)
  default         → evite em produção — use namespaces próprios
  
  Organização recomendada:
  prod-checkout    → time de checkout em produção
  prod-pagamentos  → time de pagamentos em produção
  staging          → ambiente de staging compartilhado
  monitoring       → Prometheus, Grafana, AlertManager
```

## Erros comuns e armadilhas

**Não planejar IPs da VPC antes de criar o cluster:** com VPC CNI, cada pod consome um IP da subnet. Clusters grandes em subnets pequenas esgotam IPs rapidamente. Plan: use subnets /19 ou maiores para nós, ou habilite prefix delegation.

**Não configurar PodDisruptionBudgets:** sem PDB, durante atualização de Node Groups o EKS pode drenar múltiplos nós simultaneamente, causando downtime. Configure PDB para garantir que sempre haja réplicas suficientes:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: minha-api-pdb
spec:
  minAvailable: 2  # sempre pelo menos 2 pods disponíveis durante drenagem
  selector:
    matchLabels:
      app: minha-api
```

**Misturar todos os workloads no namespace `default`:** sem namespaces próprios, é impossível aplicar RBAC granular, quotas de recursos ou políticas de rede por time/aplicação.

## 🧩 Quiz de Fixação

1. Um cluster EKS usa instâncias `m7g.large` com VPC CNI padrão (sem prefix delegation). Cada nó suporta no máximo 29 pods. Com `desired count = 5` nós e pods de 128 MiB cada, qual é o número máximo de pods que o cluster pode hospedar, e o que acontece quando esse limite é atingido?

2. Por que o endpoint do API Server ser "Público" por padrão representa um risco de segurança, e como a configuração "Público + Privado com CIDR restrito" mitiga esse risco sem sacrificar a operabilidade?

3. Um time quer usar DaemonSets para instalar um agente de segurança em todos os nós do cluster EKS. Eles estão considerando Fargate para reduzir o gerenciamento de nós. Por que Fargate não é compatível com esse requisito?

**Respostas:**

1) Máximo de pods: 5 nós × 29 pods = **145 pods**. Quando esse limite é atingido, novos pods ficam no estado **Pending** com o evento `0/5 nodes are available: 5 Too many pods` — o scheduler não consegue alocar o pod em nenhum nó. O cluster não falha, mas novos pods não iniciam. Soluções: (a) aumentar o número de nós (Auto Scaling Group escala); (b) habilitar **prefix delegation** no VPC CNI, que aumenta o limite para ~480 pods por `m7g.large`; (c) usar instâncias maiores com mais ENIs (ex: `m7g.2xlarge` suporta ~58 pods sem prefix delegation). Com Karpenter, o provisionamento de novos nós seria automático ao detectar pods Pending.

2) Com endpoint **público**, o API Server do Kubernetes está exposto na internet — qualquer IP no mundo pode tentar autenticar. Mesmo com autenticação forte (certificados, tokens), a superfície de ataque é global: bots varrem endereços IP conhecidos da AWS procurando endpoints EKS, exploram CVEs de versões desatualizadas do K8s, ou tentam ataques de força bruta em tokens. A configuração **Público + Privado com `publicAccessCidrs` restrito** mitiga isso sem sacrificar operabilidade: (a) `endpointPrivateAccess=true` permite que os nós EC2 se comuniquem com o API Server via rede privada da VPC, sem usar internet; (b) `publicAccessCidrs=["203.0.113.0/32"]` restringe o acesso público apenas ao IP do escritório ou da VPN — bloqueando todo o resto da internet. Engenheiros ainda conseguem rodar `kubectl` remotamente (via VPN/IP autorizado), mas atacantes externos não têm acesso ao endpoint.

3) **DaemonSets** criam um pod em **cada nó** do cluster — exatamente um por nó, independente do número de pods. No Fargate, não existem "nós" visíveis ou acessíveis — cada pod roda em sua própria microVM efêmera gerenciada pela AWS, sem um host compartilhado persistente que possa ser acessado por um DaemonSet. O Fargate não expõe o conceito de "nó" da forma que o DaemonSet espera. Para instalar agentes de segurança em nós Fargate, a alternativa é usar **sidecars** (um container adicional em cada pod) — mas isso requer modificar todas as Task Definitions/specs de pods, é operacionalmente muito mais complexo, e nem todos os agentes de segurança suportam esse modelo. Para esse requisito específico (agente de segurança via DaemonSet em todos os nós), **Managed Node Groups com EC2** é a única opção adequada no EKS.
