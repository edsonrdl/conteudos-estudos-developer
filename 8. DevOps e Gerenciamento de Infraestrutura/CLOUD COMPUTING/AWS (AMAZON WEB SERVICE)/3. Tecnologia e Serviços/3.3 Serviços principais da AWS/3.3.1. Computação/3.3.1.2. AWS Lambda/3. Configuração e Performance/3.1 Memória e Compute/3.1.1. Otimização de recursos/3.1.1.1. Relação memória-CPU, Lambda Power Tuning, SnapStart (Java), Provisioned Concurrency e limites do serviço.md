### Otimização de recursos Lambda — memória, CPU, Power Tuning e limites

Configurar Lambda corretamente vai além de fazer o código funcionar — a quantidade de memória alocada determina diretamente a velocidade de execução e o custo. Uma função com memória errada pode ser 3x mais lenta e 2x mais cara simultaneamente. Este arquivo cobre como Lambda aloca recursos, como encontrar a configuração ideal e os limites que definem os tetos do serviço.

---

## A relação memória ↔ CPU no Lambda

Lambda não permite configurar vCPU diretamente — você configura apenas a **memória**, e a CPU é alocada **proporcionalmente**:

```
Relação memória → CPU alocada:

 128 MiB  → ~0.08 vCPU
 512 MiB  → ~0.33 vCPU
 1.024 MiB (1 GB)  → ~0.64 vCPU
 1.769 MiB → 1 vCPU completo
 3.008 MiB → ~1.7 vCPU
 5.308 MiB → ~3 vCPU
10.240 MiB (máx) → ~6 vCPU
```

**Ponto de inflexão importante:** apenas acima de **1.769 MiB** a função tem acesso a mais de 1 vCPU. Abaixo disso, código multi-thread não se beneficia de paralelismo real — todos os threads competem pela mesma fração de CPU.

```
Impacto prático da memória na duração:

Função de processamento de imagem (CPU-bound):
  128 MiB  → 8.200ms de execução
  256 MiB  → 4.100ms
  512 MiB  → 2.050ms
  1.024 MiB → 1.025ms
  1.769 MiB → 600ms    ← 1 vCPU completo
  3.008 MiB → 350ms
  
Custo por invocação (GB-segundos):
  128 MiB:   0.125 GB × 8.2s = 1.025 GB-s × $0.0000166667 = $0.0000171
  1.769 MiB: 1.769 GB × 0.6s = 1.061 GB-s × $0.0000166667 = $0.0000177
  
Conclusão: mais memória pode ter MESMO custo com muito mais velocidade.
```

A relação não é linear para todas as funções — funções I/O-bound (esperando rede, banco) não ganham tanto com mais memória porque o gargalo não é CPU.

## Lambda Power Tuning

Encontrar a configuração ideal de memória manualmente é tedioso — exige testar múltiplas configurações e calcular custo vs. velocidade. O **AWS Lambda Power Tuning** é uma Step Function open-source da AWS que automatiza esse processo.

```
Funcionamento do Power Tuning:

Você define:
  - ARN da função a testar
  - Configurações de memória para testar (ex: 128, 256, 512, 1024, 2048, 3008)
  - Número de invocações por configuração (ex: 10 para média estatística)
  - Payload de teste
  - Estratégia: "cost", "speed" ou "balanced"

Power Tuning executa:
  Para cada configuração de memória:
    → Invoca a função N vezes
    → Coleta duração real de cada invocação
    → Calcula custo médio (GB-segundos)
    → Calcula duração média
  
  Gera relatório visual:
    Custo vs. Memória    (qual config é mais barata)
    Velocidade vs. Memória (qual config é mais rápida)
    Recomendação por estratégia
```

### Executando Power Tuning

```bash
# Deploy da Step Function de Power Tuning via SAR (Serverless Application Repository)
aws serverlessrepo create-cloud-formation-change-set \
  --application-id arn:aws:serverlessrepo:us-east-1:451282441545:applications/aws-lambda-power-tuning \
  --stack-name power-tuning \
  --capabilities CAPABILITY_IAM \
  --parameter-overrides '[{"name":"lambdaResource","value":"*"}]'

# Iniciar análise via CLI
aws stepfunctions start-execution \
  --state-machine-arn arn:aws:states:us-east-1:123:stateMachine:powerTuningStateMachine \
  --input '{
    "lambdaARN": "arn:aws:lambda:us-east-1:123:function:minha-funcao",
    "powerValues": [128, 256, 512, 1024, 1769, 3008],
    "num": 10,
    "payload": {"chave": "valor-de-teste"},
    "parallelInvocation": true,
    "strategy": "balanced"
  }'
```

### Interpretando os resultados

```
Exemplo de resultado para função de processamento de dados:

Memória  │ Duração média │ Custo/invocação │ Recomendação
─────────┼───────────────┼─────────────────┼─────────────
128 MiB  │ 3.200ms       │ $0.0000067      │
256 MiB  │ 1.800ms       │ $0.0000075      │
512 MiB  │ 950ms         │ $0.0000079      │
1.024 MiB│ 520ms         │ $0.0000087      │
1.769 MiB│ 310ms         │ $0.0000090      │ ← "speed"
3.008 MiB│ 290ms         │ $0.0000146      │
─────────────────────────────────────────────
Estratégia "cost":    128 MiB ($0.0000067) 
Estratégia "speed":   1.769 MiB (310ms)
Estratégia "balanced":512 MiB (bom custo + boa velocidade)
```

A estratégia "balanced" geralmente encontra o "joelho da curva" — o ponto onde mais memória ainda melhora significativamente a velocidade sem aumentar muito o custo.

## Provisioned Concurrency

Provisioned Concurrency mantém ambientes de execução **pré-inicializados e prontos**, eliminando cold starts para as invocações cobertas. Detalhe aprofundado foi coberto no arquivo de cold start — aqui o foco é a configuração operacional.

### Quando usar Provisioned Concurrency

```
Critérios para ativar:

✓ API com SLA de latência P99 estrito (ex: < 200ms)
✓ Função com cold start > 500ms (Java, .NET, funções com init pesada)
✓ Tráfego previsível que justifica o custo fixo

✗ Funções assíncronas (S3, SQS) — latência não importa para o usuário
✗ Funções com cold start < 100ms (Python/Node simples)
✗ Tráfego muito irregular sem padrão definido
```

### Configuração com Auto Scaling por horário

```bash
# 1. Publicar versão (Provisioned Concurrency requer versão específica, não $LATEST)
aws lambda publish-version \
  --function-name minha-api \
  --description "v1.2.0 prod"
# Retorna: {"Version": "5", "FunctionArn": "arn:...:minha-api:5"}

# 2. Criar alias apontando para a versão
aws lambda create-alias \
  --function-name minha-api \
  --name prod \
  --function-version 5

# 3. Configurar Provisioned Concurrency no alias
aws lambda put-provisioned-concurrency-config \
  --function-name minha-api \
  --qualifier prod \
  --provisioned-concurrent-executions 20

# 4. Registrar como scalable target
aws application-autoscaling register-scalable-target \
  --service-namespace lambda \
  --resource-id "function:minha-api:prod" \
  --scalable-dimension lambda:function:ProvisionedConcurrency \
  --min-capacity 5 \
  --max-capacity 50

# 5. Escalonamento por horário — mais capacidade no horário comercial
aws application-autoscaling put-scheduled-action \
  --service-namespace lambda \
  --resource-id "function:minha-api:prod" \
  --scalable-dimension lambda:function:ProvisionedConcurrency \
  --scheduled-action-name "scale-up-business-hours" \
  --schedule "cron(0 8 * * MON-FRI)" \
  --scalable-target-action MinCapacity=20,MaxCapacity=50

aws application-autoscaling put-scheduled-action \
  --service-namespace lambda \
  --resource-id "function:minha-api:prod" \
  --scalable-dimension lambda:function:ProvisionedConcurrency \
  --scheduled-action-name "scale-down-night" \
  --schedule "cron(0 20 * * MON-FRI)" \
  --scalable-target-action MinCapacity=5,MaxCapacity=20
```

### Custo do Provisioned Concurrency

```
Preços adicionais (us-east-1):
  Provisionamento: $0.0000097222 por GB-hora provisionada
  Invocações cobertas: $0.0000097222 por GB-segundo (mesmo para On-Demand)
  
Exemplo — 10 ambientes × 1 GiB × 720h/mês:
  7.200 GB-h × $0.0000097222 = $0.07/mês (negligenciável)

Exemplo — 100 ambientes × 3 GiB × 720h/mês:
  216.000 GB-h × $0.0000097222 = $2.10/mês
  
O custo escala com memória × concorrência × horas provisionadas.
Para funções com muita memória e alta concorrência provisionada, o
custo pode ser relevante — monitore.
```

## SnapStart (Java)

SnapStart foi coberto no arquivo de cold start. Resumo operacional:

```bash
# Ativar SnapStart em uma função Java
aws lambda update-function-configuration \
  --function-name minha-funcao-java \
  --snap-start ApplyOn=PublishedVersions

# Publicar versão com SnapStart (snapshot é criado no publish)
aws lambda publish-version \
  --function-name minha-funcao-java
# A Init Phase é executada agora, snapshot salvo
# Próximas cold starts restauram do snapshot: 200-500ms vs 2-6s
```

**Compatibilidade:** Java 11 e Java 17 managed runtimes. Não disponível para Java em container image customizada.

## Limites do serviço Lambda

Conhecer os limites evita surpresas em produção. Alguns são hard limits (não podem ser aumentados), outros são soft limits (aumentáveis via AWS Support).

### Limites de configuração da função

| Parâmetro | Limite | Tipo |
|---|---|---|
| Memória | 128 MiB – 10.240 MiB | Hard |
| Timeout máximo | 15 minutos (900s) | Hard |
| Armazenamento `/tmp` | 512 MiB – 10.240 MiB | Hard |
| Variáveis de ambiente | 4 KB total | Hard |
| Tamanho do pacote ZIP | 50 MB (direto) / 250 MB (S3) | Hard |
| Tamanho da container image | 10 GB | Hard |
| Camadas (Layers) | máx 5 por função | Hard |
| Tamanho total de layers | 250 MB (extraído) | Hard |

### Limites de concorrência

| Parâmetro | Limite padrão | Tipo |
|---|---|---|
| Concorrência simultânea por conta/região | 1.000 | Soft (aumentável) |
| Burst limit (novas instâncias/minuto) | 500–3.000 (varia por região) | Soft |
| Provisioned Concurrency por função | sem limite documentado | Soft |
| Reserved Concurrency (máx por função) | até o limite da conta | — |

```
Como a concorrência é consumida:

Limite da conta: 1.000 execuções simultâneas

  Função A (Reserved: 200):  pode usar até 200
  Função B (Reserved: 300):  pode usar até 300
  Funções sem reserved:      compartilham os 500 restantes

Se Função A chegar a 200 simultâneas e precisar de mais:
  → Throttling (TooManyRequestsException)
  → Mesmo que existam 500 disponíveis para outras funções
  
Reserved Concurrency serve como TETO (limita) E RESERVA (garante).
```

### Limites de payload

| Parâmetro | Limite |
|---|---|
| Payload de invocação síncrona | 6 MB (request + response) |
| Payload de invocação assíncrona | 256 KB |
| Payload Event Source Mapping (SQS) | 6 MB por batch |

```
Implicação dos limites de payload:

Se sua API via API Gateway recebe arquivos grandes:
  → NÃO envie o arquivo no body da requisição Lambda
  → Use pre-signed URL do S3: cliente faz upload direto para S3
  → Lambda recebe apenas metadados (URL, nome, tamanho)
  
Fluxo correto para upload de arquivo grande:
  Client ──▶ API Gateway/Lambda ──▶ gera pre-signed URL S3
  Client ──▶ S3 (upload direto via URL) ──▶ S3 Event ──▶ Lambda processa
```

### Limites de execução simultânea — Burst Limit

O burst limit controla quantas novas instâncias Lambda podem ser criadas **por minuto** em uma região. Isso afeta o escalonamento rápido:

```
Burst limit por região (exemplos):
  us-east-1, us-west-2, eu-west-1: 3.000 novas instâncias/minuto
  Outras regiões: 500 novas instâncias/minuto

Cenário de escalonamento:
  Minuto 0: 0 invocações simultâneas
  Minuto 1: 10.000 requisições chegam simultaneamente
  
  Com burst limit de 3.000:
    Minuto 1: 3.000 invocações atendidas, restante em throttling
    Minuto 2: +3.000 = 6.000
    Minuto 3: +3.000 = 9.000
    Minuto 4: 10.000 atingido
    
  Para picos abruptos muito grandes, Provisioned Concurrency
  garante capacidade imediata sem esperar pelo burst ramp-up.
```

## Reservando e limitando concorrência

### Reserved Concurrency — garantia + teto

```bash
# Reservar 200 execuções simultâneas para uma função crítica
# (garante capacidade mesmo se a conta estiver saturada)
aws lambda put-function-concurrency \
  --function-name api-pagamentos \
  --reserved-concurrent-executions 200

# Definir 0 para desativar completamente a função temporariamente
aws lambda put-function-concurrency \
  --function-name funcao-temporariamente-desativada \
  --reserved-concurrent-executions 0
```

**Reserved Concurrency = 0** é uma forma de "desligar" uma função sem deletá-la — útil durante manutenção ou para bloquear processamento durante investigação de incidente.

## 🧩 Quiz de Fixação

1. Uma função Lambda com 256 MiB de memória leva 4.000ms por invocação. O time aumenta para 1.769 MiB e a duração cai para 600ms. O custo por invocação aumentou, diminuiu ou ficou similar? Mostre o cálculo.

2. Sua conta Lambda tem limite de 1.000 execuções simultâneas. A função `api-principal` tem Reserved Concurrency de 800. Em um pico, `api-principal` usa 700 simultâneas e outras 5 funções tentam usar o restante da conta. Quantas execuções simultâneas essas outras 5 funções podem ter, e por quê?

3. Um desenvolvedor tenta invocar Lambda com um payload de 300 KB via invocação assíncrona (InvocationType=Event). O que acontece e como redesenhar para contornar o limite?

**Respostas:**

1) O custo ficou **similar** — é o efeito "sweet spot" da memória no Lambda:
- **256 MiB / 4.000ms:** 0.256 GB × 4.0s = **1.024 GB-segundos** → $0.0000171
- **1.769 MiB / 600ms:** 1.769 GB × 0.6s = **1.061 GB-segundos** → $0.0000177

Diferença de apenas ~3% no custo, com a função sendo **6.6x mais rápida**. Isso é típico para funções CPU-bound: mais memória = mais CPU = execução mais rápida = menos GB-segundos consumidos. O aumento no custo por GB é compensado pela redução no tempo. Para funções I/O-bound (esperando rede), o ganho de velocidade é menor porque o gargalo não é CPU.

2) As outras 5 funções podem ter no máximo **200 execuções simultâneas combinadas** (1.000 - 800 = 200 do pool sem Reserved). Não importa que `api-principal` esteja usando apenas 700 das suas 800 reservadas — as 100 não utilizadas ficam "presas" na reserva de `api-principal` e **não voltam para o pool compartilhado**. Reserved Concurrency funciona como silos isolados: os 800 são exclusivos de `api-principal` (não podem ser usados por outras funções mesmo que sobrem) e as outras funções competem pelos 200 restantes. Isso é ao mesmo tempo a força do mecanismo (garante capacidade para funções críticas) e sua limitação (mal dimensionado, desperdiça capacidade da conta).

3) A invocação assíncrona falha com erro **`RequestEntityTooLargeException`** — o limite é 256 KB e o payload tem 300 KB. Para contornar: (1) salvar os dados do payload no S3 antes de invocar Lambda; (2) passar apenas a referência (bucket + key) no payload da invocação assíncrona; (3) a função Lambda lê os dados diretamente do S3. Esse pattern (payload por referência) é o padrão recomendado para qualquer dado grande em sistemas event-driven — além de contornar o limite, desacopla o tamanho do dado do sistema de mensageria.
