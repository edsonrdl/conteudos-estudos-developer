### Empacotamento e execução Lambda — ZIP, Container Image, Layers e variáveis de ambiente

Como você empacota e distribui uma função Lambda afeta o fluxo de deploy, o cold start, os limites de tamanho e a portabilidade. Lambda suporta dois modelos de empacotamento fundamentalmente diferentes — ZIP e Container Image — cada um com trade-offs de flexibilidade, conveniência e velocidade.

---

## Modelo ZIP (deployment package)

O modelo ZIP é o padrão histórico do Lambda. Você empacota código + dependências em um arquivo ZIP e faz upload diretamente ou via S3.

```
Estrutura de um pacote ZIP Python:

minha-funcao.zip
├── lambda_function.py      ← handler
├── utils/
│   └── helpers.py
└── python/                 ← dependências (se não usar Layer)
    ├── boto3/
    ├── requests/
    └── ...
```

### Limites do modelo ZIP

| Limite | Valor |
|---|---|
| Tamanho do ZIP (upload direto) | 50 MB |
| Tamanho do ZIP (via S3) | 250 MB |
| Tamanho total extraído (código + layers) | 250 MB |

Para a maioria dos projetos Python/Node.js simples, esses limites nunca são atingidos. Para Java com JARs pesados ou projetos com muitas dependências, pode ser necessário usar Layers ou migrar para Container Image.

### Deploy via CLI

```bash
# Python — empacotar e fazer deploy
zip -r function.zip lambda_function.py utils/

# Com dependências incluídas no ZIP
pip install -r requirements.txt -t ./package
cd package && zip -r ../function.zip . && cd ..
zip -g function.zip lambda_function.py

# Upload direto (< 50 MB)
aws lambda update-function-code \
  --function-name minha-funcao \
  --zip-file fileb://function.zip

# Upload via S3 (> 50 MB)
aws s3 cp function.zip s3://meu-bucket-deploy/function.zip
aws lambda update-function-code \
  --function-name minha-funcao \
  --s3-bucket meu-bucket-deploy \
  --s3-key function.zip
```

```bash
# Node.js — empacotar
npm install --production
zip -r function.zip index.js node_modules/

# Java — o JAR já é o artefato de deploy
mvn clean package -DskipTests
aws lambda update-function-code \
  --function-name minha-funcao-java \
  --zip-file fileb://target/minha-funcao-1.0.jar
```

## Modelo Container Image

Lambda suporta imagens Docker de até **10 GB**, baseadas na AWS Lambda Runtime Interface. Você constrói a imagem, faz push para o ECR (Elastic Container Registry) e aponta a função para ela.

```
Vantagens do Container Image sobre ZIP:
  → Até 10 GB de tamanho (vs 250 MB extraídos do ZIP)
  → Ferramentas de build e CI/CD familiares (Docker)
  → Teste local idêntico ao ambiente Lambda (sam local)
  → Dependências do SO controláveis (binários, libs nativas)
  → Portabilidade: mesma imagem roda localmente e na AWS
```

### Criando uma imagem Lambda

A AWS fornece imagens base com o runtime já configurado:

```dockerfile
# Python 3.12 com Lambda Runtime Interface
FROM public.ecr.aws/lambda/python:3.12

# Copiar requirements e instalar dependências
COPY requirements.txt .
RUN pip install -r requirements.txt --target "${LAMBDA_TASK_ROOT}"

# Copiar código da função
COPY lambda_function.py ${LAMBDA_TASK_ROOT}

# Definir o handler
CMD ["lambda_function.lambda_handler"]
```

```dockerfile
# Node.js 20
FROM public.ecr.aws/lambda/nodejs:20

COPY package*.json ./
RUN npm ci --production

COPY index.js ./

CMD ["index.handler"]
```

```dockerfile
# Java 21 com SnapStart
FROM public.ecr.aws/lambda/java:21

COPY target/minha-funcao.jar ${LAMBDA_TASK_ROOT}/lib/

CMD ["com.exemplo.Handler::handleRequest"]
```

### Deploy via ECR

```bash
# Autenticar no ECR
aws ecr get-login-password --region us-east-1 | \
  docker login --username AWS --password-stdin \
  123456789.dkr.ecr.us-east-1.amazonaws.com

# Criar repositório ECR
aws ecr create-repository --repository-name minha-funcao-lambda

# Build e push
docker build -t minha-funcao-lambda .
docker tag minha-funcao-lambda:latest \
  123456789.dkr.ecr.us-east-1.amazonaws.com/minha-funcao-lambda:latest
docker push \
  123456789.dkr.ecr.us-east-1.amazonaws.com/minha-funcao-lambda:latest

# Atualizar função Lambda para usar a nova imagem
aws lambda update-function-code \
  --function-name minha-funcao \
  --image-uri 123456789.dkr.ecr.us-east-1.amazonaws.com/minha-funcao-lambda:latest
```

### Imagem customizada (sem base AWS)

Para usar uma imagem totalmente customizada (ex: baseada em Alpine ou Debian), é necessário instalar o **Lambda Runtime Interface Client (RIC)**:

```dockerfile
FROM python:3.12-slim

# Instalar Lambda Runtime Interface Client
RUN pip install awslambdaric

COPY lambda_function.py /app/
WORKDIR /app

# Entrypoint usa o RIC para se comunicar com o Lambda Runtime API
ENTRYPOINT ["/usr/local/bin/python", "-m", "awslambdaric"]
CMD ["lambda_function.lambda_handler"]
```

### ZIP vs Container Image — quando usar cada um

```
Guia de decisão:

Use ZIP quando:
  ├── Projeto simples (código + poucas dependências)
  ├── Tamanho total < 50 MB (deploy direto, sem S3)
  ├── Time não usa Docker no workflow atual
  └── Velocidade de iteração é prioridade (zip + upload é mais rápido)

Use Container Image quando:
  ├── Dependências pesadas (modelos ML, bibliotecas nativas)
  ├── Código + deps > 250 MB extraídos
  ├── Precisa de binários do SO específicos (ffmpeg, wkhtmltopdf, etc.)
  ├── Time já usa Docker e quer portabilidade local ↔ Lambda
  └── Quer testar localmente com ambiente idêntico (sam local invoke)
```

## Runtimes disponíveis

Lambda suporta runtimes gerenciados (mantidos pela AWS com patches automáticos) e runtimes customizados (você traz o runtime).

### Runtimes gerenciados (managed runtimes)

| Runtime | Versões disponíveis | Notas |
|---|---|---|
| Python | 3.8, 3.9, 3.10, 3.11, 3.12 | Mais popular; cold start baixo |
| Node.js | 18, 20 | Excelente para APIs e webhooks |
| Java | 8, 11, 17, 21 | SnapStart disponível no 11+ |
| .NET | 6, 8 | C# e F# |
| Go | 1.x | Binário nativo; cold start muito baixo |
| Ruby | 3.2 | |

> Runtimes são descontinuados ao chegar no fim de vida da linguagem. Funções em runtime deprecated continuam funcionando mas não recebem patches — migrar é responsabilidade do desenvolvedor.

### Runtime customizado (custom runtime)

Para linguagens não suportadas nativamente (Rust, PHP, Erlang, COBOL), use `provided.al2023` como runtime e inclua um bootstrap executável:

```bash
# Estrutura para Rust com runtime customizado
minha-funcao.zip
├── bootstrap     ← executável que implementa o Lambda Runtime API
└── (outros arquivos)
```

```rust
// Rust com AWS Lambda Rust Runtime
use lambda_runtime::{run, service_fn, Error, LambdaEvent};
use serde::{Deserialize, Serialize};

#[derive(Deserialize)]
struct Request { nome: String }

#[derive(Serialize)]
struct Response { mensagem: String }

async fn handler(event: LambdaEvent<Request>) -> Result<Response, Error> {
    Ok(Response {
        mensagem: format!("Olá, {}!", event.payload.nome),
    })
}

#[tokio::main]
async fn main() -> Result<(), Error> {
    run(service_fn(handler)).await
}
```

```bash
# Compilar para Linux ARM64 (Graviton) e empacotar
cargo build --release --target aarch64-unknown-linux-musl
cp target/aarch64-unknown-linux-musl/release/minha-funcao bootstrap
zip function.zip bootstrap
```

## Lambda Layers

Layers são arquivos ZIP com código ou dependências que podem ser **compartilhados entre múltiplas funções**. São montados em `/opt` no ambiente de execução, separados do código da função.

```
Sem Layers:                    Com Layers:
                               
Função A: 45 MB                Função A: 2 MB (só código)
  ├── código: 2 MB              └── usa Layer "dependências-comuns"
  └── deps: 43 MB
                               Função B: 3 MB (só código)
Função B: 46 MB                └── usa Layer "dependências-comuns"
  ├── código: 3 MB
  └── deps: 43 MB              Layer "dependências-comuns": 43 MB
                                 → armazenado UMA vez
Total armazenado: 91 MB        Total armazenado: 48 MB
Deploy de deps: sempre         Deploy de deps: só quando mudar
```

### Criando e usando uma Layer

```bash
# Criar Layer com dependências Python
mkdir -p python/lib/python3.12/site-packages
pip install requests pandas -t python/lib/python3.12/site-packages/
zip -r dependencies-layer.zip python/

# Publicar Layer
aws lambda publish-layer-version \
  --layer-name "dependencias-comuns" \
  --description "requests, pandas" \
  --zip-file fileb://dependencies-layer.zip \
  --compatible-runtimes python3.12 \
  --compatible-architectures x86_64 arm64

# Retorna: {"LayerVersionArn": "arn:aws:lambda:...:layer:dependencias-comuns:1"}

# Associar Layer a uma função
aws lambda update-function-configuration \
  --function-name minha-funcao \
  --layers arn:aws:lambda:us-east-1:123:layer:dependencias-comuns:1
```

### Limites de Layers

| Parâmetro | Limite |
|---|---|
| Layers por função | 5 |
| Tamanho total extraído (código + todas as layers) | 250 MB |
| Tamanho de uma layer (ZIP) | 50 MB (direto) / 250 MB (S3) |

### Layers públicas da AWS e de terceiros

A AWS e parceiros publicam layers públicas prontas — você pode usar sem criar:

```bash
# Layer do AWS SDK for pandas (AWS Data Wrangler) — oficial da AWS
# ARN varia por região; consultar: https://aws-sdk-pandas.readthedocs.io
arn:aws:lambda:us-east-1:336392948345:layer:AWSSDKPandas-Python312:13

# Layer de extensão do Datadog (observabilidade)
arn:aws:lambda:us-east-1:464622532012:layer:Datadog-Extension:56
```

## Variáveis de ambiente

Variáveis de ambiente são a forma padrão de injetar configuração na função — URLs de banco, nomes de tabelas, feature flags, chaves de API — sem hardcodar no código.

```python
import os

# Acessar variável de ambiente
DB_HOST = os.environ.get('DB_HOST', 'localhost')  # com fallback
TABLE_NAME = os.environ['TABLE_NAME']              # obrigatória; KeyError se ausente
LOG_LEVEL = os.environ.get('LOG_LEVEL', 'INFO')

def lambda_handler(event, context):
    print(f"Conectando em {DB_HOST}, tabela {TABLE_NAME}")
```

### Configurando variáveis de ambiente

```bash
aws lambda update-function-configuration \
  --function-name minha-funcao \
  --environment Variables='{
    "DB_HOST": "meu-rds.cluster.us-east-1.rds.amazonaws.com",
    "TABLE_NAME": "pedidos-prod",
    "LOG_LEVEL": "INFO",
    "FEATURE_FLAG_NOVO_CHECKOUT": "true"
  }'
```

### Criptografia de variáveis sensíveis

Por padrão, Lambda criptografa variáveis de ambiente em repouso com uma chave KMS gerenciada pela AWS. Para chaves sensíveis (senhas, tokens), use criptografia adicional com chave KMS própria ou — preferível — armazene em **AWS Secrets Manager** ou **SSM Parameter Store** e acesse em runtime:

```python
import boto3
import json
import os

# ── INIT PHASE — carregado uma vez ──────────────────────────
ssm = boto3.client('ssm')
secrets_manager = boto3.client('secretsmanager')

# SSM Parameter Store (para configs não-secretas)
DB_HOST = ssm.get_parameter(
    Name='/app/prod/db-host'
)['Parameter']['Value']

# Secrets Manager (para senhas e tokens)
secret = json.loads(
    secrets_manager.get_secret_value(
        SecretId='prod/app/db-credentials'
    )['SecretString']
)
DB_PASSWORD = secret['password']

# ── HANDLER ──────────────────────────────────────────────────
def lambda_handler(event, context):
    # DB_HOST e DB_PASSWORD já disponíveis (carregados na init)
    ...
```

### Limites de variáveis de ambiente

| Parâmetro | Limite |
|---|---|
| Tamanho total de todas as variáveis | 4 KB |
| Chave: tamanho máximo | 512 bytes |
| Valor: tamanho máximo | 4 KB menos o tamanho das outras vars |

Para configurações maiores que 4 KB, use SSM Parameter Store ou S3.

## Variáveis de ambiente reservadas pela AWS

Lambda injeta automaticamente algumas variáveis que não podem ser sobrescritas:

| Variável | Conteúdo |
|---|---|
| `AWS_REGION` | Região onde a função executa |
| `AWS_LAMBDA_FUNCTION_NAME` | Nome da função |
| `AWS_LAMBDA_FUNCTION_VERSION` | Versão em execução (`$LATEST` ou número) |
| `AWS_LAMBDA_FUNCTION_MEMORY_SIZE` | Memória configurada em MiB |
| `LAMBDA_TASK_ROOT` | Diretório do código da função |
| `LAMBDA_RUNTIME_DIR` | Diretório do runtime |
| `AWS_EXECUTION_ENV` | Identificador do runtime (ex: `AWS_Lambda_python3.12`) |

## 🧩 Quiz de Fixação

1. Uma função Lambda Python precisa de `ffmpeg` (binário nativo Linux de 60 MB) para processamento de vídeo. Qual modelo de empacotamento usar e por quê o modelo ZIP padrão não resolve?

2. Três funções Lambda usam a mesma biblioteca `pandas` (40 MB). Sem Layers, cada função carrega sua própria cópia. Qual é o impacto prático disso além do espaço de armazenamento, e como Layers resolve cada impacto?

3. Um desenvolvedor armazena a senha do banco de dados diretamente em uma variável de ambiente da função Lambda. Por que isso é insuficiente do ponto de vista de segurança, e qual é a abordagem recomendada?

**Respostas:**

1) O modelo ZIP não resolve porque `ffmpeg` é um binário nativo Linux de 60 MB — somado ao código da função e outras dependências Python, facilmente supera o limite de 250 MB extraídos do ZIP. Além disso, o ZIP não garante que as libs de sistema necessárias pelo `ffmpeg` (como `libavcodec`) estejam disponíveis no ambiente Lambda. A solução correta é **Container Image**: você cria um Dockerfile baseado na imagem Lambda oficial, instala `ffmpeg` via `apt` ou copia o binário estático durante o build, e tem controle total sobre o ambiente. O limite sobe para 10 GB, e você pode testar localmente com `docker run` antes de fazer push para o ECR.

2) Sem Layers, cada cópia de `pandas` (40 MB) é incluída no pacote de cada função. Os impactos práticos além do armazenamento são: (1) **Deploy mais lento** — cada atualização de qualquer função exige re-upload dos 40 MB de `pandas`, mesmo que só o código da função tenha mudado; (2) **Limite de tamanho mais apertado** — os 40 MB de `pandas` consomem parte dos 250 MB extraídos de cada função, reduzindo o espaço disponível para código; (3) **Inconsistência de versão** — é possível que cada função use uma versão ligeiramente diferente de `pandas` se os `requirements.txt` divergirem ao longo do tempo. Com Layer: (1) deploy de atualização da função não inclui `pandas` — apenas o código é re-enviado; (2) `pandas` consome os 40 MB uma única vez no storage, compartilhado entre as três funções; (3) a versão é centralizada — atualizar o Layer atualiza todas as funções que o usam.

3) A variável de ambiente tem criptografia em repouso (KMS da AWS por padrão), mas a senha fica visível em texto claro para **qualquer pessoa com permissão `lambda:GetFunctionConfiguration`** na conta — que inclui muitos desenvolvedores e papéis de CI/CD. Além disso, rotacionar a senha exige atualizar a variável de ambiente da função e fazer um novo deploy. A abordagem recomendada é armazenar a senha no **AWS Secrets Manager**: a função recebe apenas a permissão IAM `secretsmanager:GetSecretValue` para o secret específico, a senha nunca aparece em configurações da função, a rotação automática é gerenciada pelo Secrets Manager sem alterar a função, e o acesso é auditado via CloudTrail. A senha é lida em runtime na Init Phase e reutilizada nas warm starts — sem overhead por invocação.
