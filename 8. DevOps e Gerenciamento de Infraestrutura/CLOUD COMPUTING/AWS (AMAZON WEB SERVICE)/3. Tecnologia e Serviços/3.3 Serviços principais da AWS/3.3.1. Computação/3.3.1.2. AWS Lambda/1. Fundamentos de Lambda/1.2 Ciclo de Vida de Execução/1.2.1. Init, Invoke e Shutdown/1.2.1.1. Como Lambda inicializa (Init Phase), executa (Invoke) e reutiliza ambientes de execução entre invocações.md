### Ciclo de vida de execução Lambda — Init, Invoke e reutilização de ambientes

Entender como Lambda gerencia ambientes de execução internamente é essencial para escrever funções eficientes e evitar bugs sutis. Lambda não cria e destrói um novo processo a cada invocação — ele reutiliza ambientes quando possível, e isso tem implicações diretas em performance, custo e comportamento do código.

---

## As três fases do ciclo de vida

Cada ambiente de execução Lambda passa por três fases distintas:

```
Ciclo de vida completo de um ambiente de execução:

┌─────────────────────────────────────────────────────────────────┐
│                         INIT PHASE                              │
│                                                                 │
│  1. Baixar código da função (ZIP ou container image)            │
│  2. Criar microVM Firecracker                                   │
│  3. Iniciar runtime (Python, Node, JVM, Go...)                  │
│  4. Executar código fora do handler (inicialização global)      │
│                                                                 │
│  Duração: 100ms–10s (depende do runtime e tamanho do código)    │
│  Cobrado: NÃO (não entra no billing de duração)                 │
└─────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│                        INVOKE PHASE                             │
│                                                                 │
│  Handler recebe o evento e executa                              │
│                                                                 │
│  Duração: até 15 minutos (timeout configurável)                 │
│  Cobrado: SIM (GB-segundos de execução)                         │
└─────────────────────────────────────────────────────────────────┘
                              │
              ┌───────────────┴────────────────┐
              │  Nova invocação chega?          │
              │                                │
        SIM ──┤  Ambiente reutilizado          │── NÃO
              │  → volta para INVOKE           │   ↓
              │  (sem nova INIT)               │  Ambiente fica em
              │                                │  "freeze" por tempo
              └────────────────────────────────┘  indeterminado
                                                        │
                                                        ▼
┌─────────────────────────────────────────────────────────────────┐
│                       SHUTDOWN PHASE                            │
│                                                                 │
│  Lambda encerra o ambiente após inatividade                     │
│  (tempo exato não é documentado — tipicamente minutos)          │
│                                                                 │
│  Extensions registradas recebem sinal SHUTDOWN                  │
│  Duração: até 2 segundos para cleanup                           │
│  Cobrado: NÃO                                                   │
└─────────────────────────────────────────────────────────────────┘
```

## Init Phase em detalhe

A fase de Init é onde acontece todo o trabalho de preparação. Ela se divide em três sub-fases:

```
Sub-fases da Init Phase:

Extension Init  →  Runtime Init  →  Function Init
    │                  │                 │
    │                  │                 └── Código global da sua
    │                  │                     função é executado
    │                  │
    │                  └── Runtime inicializado
    │                      (interpretador Python, JVM Java,
    │                       processo Node.js...)
    │
    └── Lambda Extensions inicializadas
        (agentes de observabilidade, segurança, etc.)
```

### Function Init — o código que roda fora do handler

O ponto mais importante para desenvolvedores: **todo código escrito fora do handler é executado apenas uma vez durante a Init Phase**, e o resultado fica disponível para todas as invocações subsequentes no mesmo ambiente.

```python
import boto3
import json

# ── INIT PHASE ── executado UMA vez por ambiente ──────────────────
# Conexão com DynamoDB criada aqui — reutilizada em todas as invocações
dynamodb = boto3.resource('dynamodb')
table = dynamodb.Table('minha-tabela')

# Configurações carregadas do SSM Parameter Store — uma vez só
ssm = boto3.client('ssm')
config = json.loads(
    ssm.get_parameter(Name='/app/config', WithDecryption=True)
    ['Parameter']['Value']
)

print("Init: conexões e configurações carregadas")  # aparece só na cold start

# ── INVOKE PHASE ── executado a CADA invocação ────────────────────
def lambda_handler(event, context):
    # 'table' e 'config' já estão prontos — sem overhead de inicialização
    item = table.get_item(Key={'id': event['id']})
    
    return {
        'statusCode': 200,
        'body': json.dumps(item.get('Item'))
    }
```

**Por que isso importa:** se você criar a conexão com o banco dentro do handler, ela será criada a cada invocação — overhead desnecessário de 50-200ms. Fora do handler, é criada uma vez e reutilizada.

## Reutilização de ambientes — warm starts

Quando Lambda recebe uma nova invocação e já existe um ambiente "congelado" (frozen) da mesma função, ele **reutiliza esse ambiente** — sem passar pela Init Phase. Isso é chamado de **warm start**.

```
Sequência de invocações:

Invocação 1 → INIT (100-500ms) + INVOKE (ex: 50ms) = 150-550ms total
                                         │
                          Ambiente congelado aguarda
                                         │
Invocação 2 → INVOKE (50ms) apenas = 50ms total  ← warm start
                                         │
                          Ambiente congelado aguarda
                                         │
Invocação 3 → INVOKE (50ms) apenas = 50ms total  ← warm start

... longa pausa (sem invocações) ...

Ambiente destruído pela AWS

Invocação N → INIT (100-500ms) + INVOKE (50ms)  ← cold start novamente
```

### O que persiste entre invocações (no mesmo ambiente)

| Elemento | Persiste? | Implicação |
|---|---|---|
| Variáveis globais | Sim | Reutilize conexões, clientes SDK, cache local |
| Diretório `/tmp` | Sim (até 10 GiB) | Pode ser usado como cache de arquivo entre invocações |
| Conexões de rede abertas | Sim | Conexões DB, HTTP keep-alive funcionam |
| Memória heap | Sim | Objetos em memória permanecem |
| Processos filhos | Sim | Background threads sobrevivem entre invocações |

### Armadilha: estado global contaminado

A reutilização de ambiente é útil mas pode causar bugs se o código assume incorretamente que começa "limpo" a cada invocação:

```python
# ❌ PERIGOSO — lista acumula dados entre invocações
resultados_globais = []  # inicializado na Init Phase

def lambda_handler(event, context):
    resultados_globais.append(processar(event))  # acumula a cada warm start!
    return resultados_globais  # retorna dados de invocações anteriores!

# ✅ CORRETO — estado local à invocação
def lambda_handler(event, context):
    resultados = []  # criado a cada invocação — sempre limpo
    resultados.append(processar(event))
    return resultados
```

```python
# ❌ PERIGOSO — contador global acumula entre invocações
contador = 0

def lambda_handler(event, context):
    global contador
    contador += 1
    print(f"Esta é a invocação #{contador}")  # número crescente incorreto

# A primeira cold start retorna 1, mas warm starts retornam 2, 3, 4...
# O valor não reflete "invocação atual" — reflete "invocações neste ambiente"
```

## Shutdown Phase e Lambda Extensions

A Shutdown Phase é acionada quando Lambda decide encerrar o ambiente. Extensions registradas têm até **2 segundos** para executar ações de cleanup — flush de logs, envio de telemetria final, fechamento de conexões:

```python
# Lambda Extension registrando para receber evento SHUTDOWN
# (normalmente implementado como agente externo, não no handler)

# No handler principal, você pode usar atexit para cleanup:
import atexit

def cleanup():
    print("Ambiente sendo encerrado — limpando recursos")
    # fechar conexões, flush de buffers, etc.

atexit.register(cleanup)

# Inicialização global
conn = criar_conexao_db()
```

## Múltiplos ambientes paralelos

Quando há várias invocações simultâneas, Lambda cria múltiplos ambientes paralelos — cada um com sua própria Init Phase:

```
100 invocações simultâneas simultâneas chegando:

Ambiente 1: INIT → INVOKE (invocação 1)
Ambiente 2: INIT → INVOKE (invocação 2)
Ambiente 3: INIT → INVOKE (invocação 3)
...
Ambiente 100: INIT → INVOKE (invocação 100)

Cada ambiente é independente — variáveis globais NÃO são compartilhadas
entre ambientes paralelos.
```

Isso tem uma implicação importante: **não use variáveis globais como cache compartilhado entre invocações paralelas**. Para cache compartilhado, use ElastiCache ou DynamoDB.

## Boas práticas baseadas no ciclo de vida

**1. Inicialize conexões e clientes fora do handler:**
```python
# Clientes SDK, conexões de banco, carregamento de modelos ML
# → fora do handler, executado uma vez na Init Phase
s3_client = boto3.client('s3')
model = carregar_modelo_ml('/tmp/modelo.pkl')

def lambda_handler(event, context):
    # s3_client e model já prontos
    ...
```

**2. Use `/tmp` como cache entre invocações (com validação):**
```python
import os

def lambda_handler(event, context):
    cache_path = '/tmp/dados_referencia.json'
    
    if not os.path.exists(cache_path):
        # Baixar do S3 apenas se não está em cache
        s3_client.download_file('meu-bucket', 'dados.json', cache_path)
    
    with open(cache_path) as f:
        dados = json.load(f)
    # ...
```

**3. Sempre inicialize estado dentro do handler:**
```python
def lambda_handler(event, context):
    # Variáveis que dependem do evento atual → sempre locais
    resultado = {}
    erros = []
    items_processados = 0
    ...
```

**4. Projete funções como se o ambiente fosse sempre novo:**
O código deve funcionar corretamente tanto em cold starts quanto em warm starts. Não dependa de estado global entre invocações para lógica de negócio.

## 🧩 Quiz de Fixação

1. Uma função Lambda conecta a um banco RDS dentro do handler. Após migrar a criação da conexão para fora do handler (escopo global), o time observa redução de latência de 120ms para 8ms nas invocações. Por que a redução não é 100% consistente (algumas invocações ainda levam 130ms)?

2. Um desenvolvedor usa uma variável global `cache = {}` fora do handler para armazenar resultados de queries pesadas. Após algumas horas, a função começa a retornar resultados desatualizados. Explique o que está acontecendo e como corrigir.

3. Uma função Lambda processa pedidos de e-commerce e foi instrumentada com um agente de APM (monitoramento de performance) via Lambda Extension. Por que é importante que esse agente registre o evento SHUTDOWN, e o que acontece se não fizer isso?

**Respostas:**

1) A redução não é consistente porque **cold starts ainda ocorrem**. Quando o ambiente é reutilizado (warm start), a conexão global já está estabelecida e a invocação leva ~8ms. Mas quando Lambda cria um novo ambiente (cold start) — seja por escalonamento para atender invocações simultâneas, por inatividade prolongada, ou por atualização do código — a Init Phase é executada novamente, incluindo a criação da conexão. Nesse caso a latência volta para ~130ms. A melhoria de 120ms → 8ms está correta para warm starts; os picos de 130ms são cold starts normais que ainda incluem o tempo de Init Phase.

2) O `cache = {}` é inicializado na Init Phase e **persiste entre invocações no mesmo ambiente**. O problema é que o cache nunca é invalidado: se os dados no banco mudam, o cache do ambiente continua com a versão antiga até o ambiente ser destruído (o que pode levar horas ou nunca acontecer para ambientes quentes). **Correção:** adicionar TTL (time-to-live) ao cache, armazenando junto com cada entrada o timestamp de quando foi populada, e invalidando entradas com mais de X segundos. Alternativa mais robusta: usar ElastiCache ou DAX como cache compartilhado com TTL gerenciado externamente, eliminando o problema de estado local em cada ambiente.

3) Agentes de APM precisam enviar a telemetria final (traces, métricas, logs buffered) **antes** do ambiente ser destruído. Se o agente não registra o evento SHUTDOWN, o Lambda pode encerrar o ambiente antes do flush completo, perdendo os dados de telemetria da última invocação ou do período final de atividade. Lambda garante até 2 segundos após o evento SHUTDOWN para que extensões completem seu trabalho — sem esse registro, o agente não recebe essa janela de tempo e o ambiente é encerrado abruptamente. Na prática, isso causa gaps nos dashboards de APM (últimas invocações de cada ambiente "somem" dos traces) e dificulta a correlação de erros que ocorrem próximos ao shutdown.
