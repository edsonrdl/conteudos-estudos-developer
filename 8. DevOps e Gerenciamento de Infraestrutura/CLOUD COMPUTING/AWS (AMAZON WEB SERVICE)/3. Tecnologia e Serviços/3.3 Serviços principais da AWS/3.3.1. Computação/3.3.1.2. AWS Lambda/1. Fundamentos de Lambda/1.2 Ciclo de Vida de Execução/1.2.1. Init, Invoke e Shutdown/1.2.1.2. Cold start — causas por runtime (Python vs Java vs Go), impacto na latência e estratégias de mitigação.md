### Cold start — causas, impacto por runtime e estratégias de mitigação

Cold start é o tempo adicional de latência que ocorre quando Lambda precisa criar um novo ambiente de execução antes de processar a invocação. É uma das características mais discutidas do serverless — frequentemente superestimada em impacto, mas real e relevante para aplicações sensíveis à latência. Entender suas causas permite escolher as mitigações certas.

---

## O que causa um cold start

Um cold start ocorre sempre que Lambda não tem um ambiente de execução "aquecido" disponível para a função. Os cenários que causam cold start:

```
Quando ocorre cold start:

1. Primeira invocação após deploy ou atualização de código
   → Nenhum ambiente existe ainda

2. Escalamento para atender invocações simultâneas
   → 10 requisições simultâneas = até 10 ambientes novos criados

3. Retorno após período de inatividade
   → Lambda encerrou o ambiente após X minutos sem uso
   → Próxima invocação recria do zero

4. Atualização de variáveis de ambiente ou configuração
   → Lambda recicla os ambientes existentes

5. VPC — ao criar ENI (Elastic Network Interface)
   → Historicamente lento; melhorou muito após 2019 com Hyperplane
```

```
Warm start vs Cold start — comparação de latência:

Warm start:
  ├── Ambiente já existe e está congelado
  └── Total: apenas tempo do handler (ex: 50ms)

Cold start:
  ├── Extension Init:   ~10-50ms
  ├── Runtime Init:     ~50ms (Python) a ~1.000ms (Java com JVM)
  ├── Function Init:    ~10-500ms (depende do código de inicialização)
  └── Handler Invoke:   50ms (igual ao warm)
  Total: 120ms (Python leve) a 2.000ms+ (Java com Spring)
```

---

## Tempo de cold start por runtime

O tempo de Init Phase varia drasticamente por linguagem — a diferença entre Python e Java pode ser de 10x ou mais:

```
Cold start médio por runtime (função mínima, 128 MiB, us-east-1):
────────────────────────────────────────────────────────────────
Runtime              │ Cold start típico │ Pior caso
─────────────────────┼───────────────────┼───────────────────
Python 3.12          │ 100–200ms         │ 400ms
Node.js 20           │ 100–300ms         │ 600ms
Go 1.x               │ 50–100ms          │ 200ms
Ruby 3.2             │ 200–400ms         │ 700ms
.NET 8               │ 300–600ms         │ 1.200ms
Java 21 (sem Spring) │ 400–800ms         │ 1.500ms
Java 21 (Spring Boot)│ 2.000–6.000ms     │ 10.000ms+
────────────────────────────────────────────────────────────────
```

### Por que Java é tão mais lento

A JVM (Java Virtual Machine) foi projetada para processos de longa duração — ela faz compilação JIT (Just-In-Time), carrega muitas classes na inicialização e aquece caches internos ao longo do tempo. Tudo isso é ótimo para um servidor rodando 24/7, mas é custo puro em um ambiente que inicializa do zero a cada cold start.

Spring Boot agrava o problema porque o framework carrega centenas de classes, configura injeção de dependência, registra beans e faz component scanning na inicialização — tudo antes do primeiro request.

```
Breakdown do cold start Java com Spring Boot:
  JVM startup:              ~200ms
  Spring context loading:   ~1.500ms
  Dependency injection:     ~800ms
  Component scanning:       ~500ms
  Handler pronto:           ~3.000ms total
```

### Por que Go e Python são rápidos

**Go** compila para binário nativo — sem VM, sem interpretador, sem JIT. O processo inicia como qualquer executável Linux: rápido e previsível.

**Python** é interpretado mas o runtime em si é leve. O cold start depende principalmente de quantas bibliotecas são importadas:

```python
# Python — impacto dos imports no cold start

# Função leve (cold start ~100ms):
import json
import boto3

# Função pesada (cold start ~400-800ms):
import pandas as pd        # ~150ms de import
import numpy as np         # ~80ms de import
import sklearn             # ~200ms de import
import tensorflow as tf    # ~500ms+ de import
```

## Impacto real no usuário

Cold start afeta apenas a **primeira requisição** em um novo ambiente. Para a maioria das aplicações, o impacto real é menor do que parece:

```
Percentil de requisições afetadas por cold start:

Aplicação com 1.000 req/min (tráfego constante):
  Ambientes aquecidos: ~20-50 (dependendo da memória e concorrência)
  Cold starts por hora: ~5-20 (novos ambientes criados para escala)
  % de requisições afetadas: < 0.1%

Aplicação com tráfego irregular (API interna, batch noturno):
  Pode ficar sem invocações por horas → cold start em toda retomada
  % de requisições afetadas: 10-50%
```

**Onde cold start realmente importa:**
- APIs com SLA de latência P99 < 200ms
- Funções chamadas de forma esporádica (webhooks, cron jobs)
- Java/Spring com cold start de 2-6 segundos em APIs síncronas
- Funções em VPC que precisam criar ENIs (menos relevante desde 2019)

**Onde cold start raramente importa:**
- Processamento assíncrono (S3 events, SQS, SNS)
- Batch jobs e ETL
- Aplicações onde 200-500ms de latência eventual é aceitável
- Funções com tráfego constante (ambientes sempre aquecidos)

## Estratégias de mitigação

### 1. Provisioned Concurrency

A solução oficial da AWS: mantém um número configurável de ambientes **sempre inicializados e prontos**, eliminando cold starts para as invocações cobertas por eles.

```
Provisioned Concurrency = 10:
  10 ambientes passam pela Init Phase antecipadamente
  e ficam "quentes" aguardando invocações

  Invocações 1-10 simultâneas → sem cold start (usam os provisionados)
  Invocação 11+ → cold start (novos ambientes criados sob demanda)
```

**Custo:** cobrado por hora de provisionamento, independente de uso — mesmo sem invocações, os ambientes provisionados geram custo.

```
Custo de Provisioned Concurrency (us-east-1):
  $0.0000097222/GB-hora provisionado
  
  10 ambientes × 1 GiB × 720h = 7.200 GB-h × $0.0000097222 = $0.07/mês
  
  Para funções com memória maior ou muitos ambientes, o custo escala.
  Use com Auto Scaling para ajustar o provisionamento por horário.
```

**Combinando com Application Auto Scaling:**
```bash
# Escalar Provisioned Concurrency por horário (mais durante o dia)
aws application-autoscaling register-scalable-target \
  --service-namespace lambda \
  --resource-id function:minha-funcao:producao \
  --scalable-dimension lambda:function:ProvisionedConcurrency \
  --min-capacity 5 \
  --max-capacity 50

# Target tracking: manter utilização em 70%
aws application-autoscaling put-scaling-policy \
  --policy-name lambda-provisioned-scaling \
  --service-namespace lambda \
  --resource-id function:minha-funcao:producao \
  --scalable-dimension lambda:function:ProvisionedConcurrency \
  --policy-type TargetTrackingScaling \
  --target-tracking-scaling-policy-configuration \
    '{"TargetValue": 0.7, "PredefinedMetricSpecification": {"PredefinedMetricType": "LambdaProvisionedConcurrencyUtilization"}}'
```

### 2. SnapStart (Java)

SnapStart é a solução específica da AWS para cold starts em Java. Ao publicar uma nova versão da função, Lambda executa a Init Phase uma vez e tira um **snapshot da memória e do estado do ambiente** (usando CRIU — Checkpoint/Restore In Userspace). Nas invocações subsequentes, o ambiente é restaurado do snapshot em vez de inicializado do zero.

```
Fluxo com SnapStart:

Deploy da versão:
  Init Phase executada → snapshot salvo no S3 (criptografado)
  Duração: 1x, durante o deploy (não afeta usuários)

Invocação (cold start com SnapStart):
  Restaurar snapshot → 200-500ms (vs 2.000-6.000ms sem SnapStart)
  Handler executa → latência normal

Redução típica: 80-90% do cold start em Java com Spring Boot
```

**Limitações do SnapStart:**
- Disponível apenas para Java 11+ com runtime `java11` ou `java17`
- Requer que o código seja **restaurável de snapshot** — algumas bibliotecas que usam valores únicos por processo (UUIDs gerados na init, seeds de random, conexões TCP) precisam de ajuste
- A AWS fornece hooks `@BeforeCheckpoint` e `@AfterRestore` para código que precisa reinicializar após restauração:

```java
import com.amazonaws.services.lambda.runtime.events.SnapStartEvent;
import com.amazonaws.services.lambda.runtime.SnapStartHandler;

public class Handler implements SnapStartHandler {
    
    private DatabaseConnection conn;
    
    @Override
    public void beforeCheckpoint(SnapStartEvent event) {
        // Fechar conexões antes do snapshot — não podem ser serializadas
        conn.close();
    }
    
    @Override  
    public void afterRestore(SnapStartEvent event) {
        // Recriar conexões após restauração do snapshot
        conn = new DatabaseConnection();
    }
    
    public String handleRequest(Map<String,String> event, Context context) {
        return conn.query(event.get("query"));
    }
}
```

### 3. Otimização de código de inicialização

Independente do runtime, reduzir o trabalho feito na Init Phase diminui o cold start:

```python
# ❌ Importando tudo no topo — mesmo se nem for usado
import pandas as pd
import numpy as np
import sklearn
import tensorflow as tf

def lambda_handler(event, context):
    if event.get('tipo') == 'ml':
        return executar_ml(event)
    else:
        return processar_simples(event)  # não usa pandas/sklearn/tf

# ✅ Lazy imports — carregar só quando necessário
def lambda_handler(event, context):
    if event.get('tipo') == 'ml':
        import pandas as pd      # importado só na primeira invocação ml
        import tensorflow as tf  # e reutilizado nas warm starts seguintes
        return executar_ml(event, pd, tf)
    else:
        return processar_simples(event)
```

```java
// Java — preferir Micronaut ou Quarkus a Spring Boot para Lambda
// Micronaut: cold start ~300-500ms (vs Spring Boot: 2.000-6.000ms)
// Quarkus com GraalVM native: cold start ~50-100ms (compilação nativa)
```

### 4. Escolher runtime adequado para o SLA

```
Guia de runtime por requisito de latência:

Latência P99 < 100ms  → Go ou Rust (compilados nativos)
Latência P99 < 300ms  → Python, Node.js
Latência P99 < 1s     → .NET, Ruby, Java sem Spring
Latência P99 > 1s OK  → Java com Spring + SnapStart
Não tem SLA de latência → qualquer runtime com lógica de negócio
```

### 5. Warming periódico (pattern legado)

Antes do Provisioned Concurrency, times usavam CloudWatch Events para invocar funções periodicamente e mantê-las "quentes". É um pattern gambiarra — Provisioned Concurrency é a solução correta — mas ainda aparece em sistemas legados:

```python
# ❌ Pattern legado de warming — evitar em novos projetos
def lambda_handler(event, context):
    # Invocação de warming do CloudWatch Scheduled Event
    if event.get('source') == 'aws.events' and event.get('warming'):
        return {'status': 'warmed'}
    
    # Lógica real
    return processar(event)
```

## Resumo: quando cada mitigação usar

| Mitigação | Quando usar | Custo adicional |
|---|---|---|
| **Provisioned Concurrency** | API com SLA estrito, tráfego previsível | Sim — por hora provisionada |
| **SnapStart** | Java com Spring Boot ou init pesada | Não (gratuito) |
| **Lazy imports** | Python/Node com bibliotecas pesadas | Não |
| **Trocar runtime** | Novo projeto com requisito de baixa latência | Não (custo de reescrita) |
| **Micronaut/Quarkus** | Java obrigatório + latência importa | Não (custo de migração) |
| **Warming periódico** | Legado apenas | Baixo (invocações extras) |

## 🧩 Quiz de Fixação

1. Uma API Java com Spring Boot no Lambda tem cold start de 5 segundos. O time ativa SnapStart e o cold start cai para 600ms. Por que 600ms e não zero — o que ainda ocorre mesmo com SnapStart?

2. Uma função Python com cold start de 800ms importa `pandas`, `numpy` e `sklearn` no topo do arquivo. O time move esses imports para dentro do handler usando lazy loading. O cold start cai para 120ms, mas agora a primeira invocação depois de um warm start leva 820ms. Por que isso acontece?

3. Uma função Lambda é chamada uma vez por noite via EventBridge Scheduled Rule para gerar um relatório (execução de 8 minutos). O time está considerando Provisioned Concurrency para eliminar o cold start. Essa é a decisão correta? Justifique.

**Respostas:**

1) SnapStart elimina a Init Phase ao restaurar um snapshot pré-computado, mas **não elimina o tempo de restauração do snapshot em si**. Os 600ms restantes são o tempo necessário para: (1) copiar o snapshot da memória do S3 para o ambiente de execução (~200-400ms dependendo do tamanho); (2) executar os hooks `@AfterRestore` (reconexão com banco de dados, recriação de objetos não-serializáveis); (3) preparar o ambiente para receber o handler. SnapStart substitui a Init Phase lenta por uma restauração mais rápida — mas não por zero.

2) Lazy imports dentro do handler são executados na **primeira invocação** que os acessa, não na Init Phase. Na primeira invocação após um cold start ou warm start (quando as bibliotecas ainda não foram importadas), Python executa `import pandas`, `import numpy` e `import sklearn` — levando os mesmos ~700ms de antes. Nas invocações seguintes do **mesmo ambiente**, os módulos já estão no cache do interpretador Python (`sys.modules`) e o import é instantâneo. O comportamento correto é: cold start rápido (120ms), primeira invocação que usa ML: 820ms, todas as invocações seguintes no mesmo ambiente: rápidas. A solução está correta para o cold start, mas o primeiro warm start que chega ao código ML ainda paga o custo de import uma vez.

3) **Não é a decisão correta.** Provisioned Concurrency cobra por hora de provisionamento independente de invocações — manter 1 ambiente provisionado 24 horas custa ~$0.007/hora × 24h × 30 dias = ~$5/mês, mais o custo da função em si. Para uma função que roda **uma vez por dia por 8 minutos**, o cold start ocorre uma única vez por execução. Mesmo que o cold start seja de 5 segundos, ele representa menos de 0.1% do tempo total de execução de 480 segundos — um overhead completamente irrelevante para um job batch noturno. A decisão correta é **não fazer nada**: aceitar o cold start para esse workload assíncrono de baixa frequência e evitar o custo fixo do Provisioned Concurrency.
