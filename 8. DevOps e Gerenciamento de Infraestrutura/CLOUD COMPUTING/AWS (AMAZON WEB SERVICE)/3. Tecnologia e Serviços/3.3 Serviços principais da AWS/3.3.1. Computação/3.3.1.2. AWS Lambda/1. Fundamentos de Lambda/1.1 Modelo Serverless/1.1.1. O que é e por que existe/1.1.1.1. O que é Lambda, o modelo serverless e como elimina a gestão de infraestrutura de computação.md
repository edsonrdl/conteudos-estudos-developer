### AWS Lambda — o que é, o modelo serverless e como elimina a gestão de infraestrutura

AWS Lambda é um serviço de computação onde você fornece apenas o código e a AWS gerencia tudo o mais: servidores, sistema operacional, patches, escalabilidade, disponibilidade e capacidade. Você não provisiona instâncias, não configura Auto Scaling Groups, não gerencia SO — existe apenas a função e o evento que a dispara. Esse modelo é chamado de **serverless** (sem servidor), não porque não existam servidores, mas porque eles são completamente invisíveis para quem desenvolve.

---

## O problema que Lambda resolve

Antes do serverless, rodar qualquer código na nuvem exigia gerenciar infraestrutura, mesmo que o código em si fosse simples:

```
Fluxo tradicional para rodar uma função simples (ex: redimensionar imagem):

1. Provisionar instância EC2 (tipo, SO, rede, security group)
2. Instalar runtime (Python, Node, Java...)
3. Fazer deploy da aplicação
4. Configurar Auto Scaling para picos
5. Configurar Load Balancer
6. Monitorar saúde das instâncias
7. Aplicar patches de SO periodicamente
8. Pagar pela instância 24/7, mesmo quando ociosa

Com Lambda:
1. Escrever a função
2. Fazer upload
3. Definir o trigger
→ Pronto. Todo o resto é responsabilidade da AWS.
```

Lambda não elimina a complexidade de toda arquitetura — mas elimina a complexidade de **gerenciar servidores** para código que pode ser estruturado como funções acionadas por eventos.

---

## O modelo de execução serverless

Lambda segue o modelo **FaaS — Function as a Service**. Cada unidade de deploy é uma **função** — um bloco de código com entrada, processamento e saída bem definidos. A função não fica rodando continuamente: ela é instanciada sob demanda, executa, e o ambiente é suspenso (ou descartado).

```
Modelo de execução Lambda:

         Evento ocorre
              │
              ▼
   ┌──────────────────────┐
   │  AWS provisiona      │  ← você não vê isso
   │  ambiente de execução│
   │  (microVM Firecracker│
   │   + runtime + código)│
   └──────────┬───────────┘
              │
              ▼
   ┌──────────────────────┐
   │  Handler executa     │  ← seu código
   │  com o evento        │
   │  como entrada        │
   └──────────┬───────────┘
              │
              ▼
   ┌──────────────────────┐
   │  Resultado retornado │
   │  Ambiente suspenso   │  ← pode ser reutilizado
   │  (ou descartado)     │     na próxima invocação
   └──────────────────────┘
```

### A abstração de infraestrutura em detalhes

Por baixo dos panos, Lambda usa **AWS Firecracker** — um hypervisor de microVMs desenvolvido internamente pela AWS. Cada função roda em uma microVM isolada, com seu próprio kernel Linux, memória e sistema de arquivos efêmero. A AWS gerencia o pool dessas microVMs, criando e destruindo conforme a demanda.

Do ponto de vista do desenvolvedor, isso é completamente transparente. O que você vê:

| O que você configura | O que a AWS gerencia |
|---|---|
| Código da função | Servidores físicos |
| Runtime (Python, Node, Java...) | Sistema operacional |
| Memória alocada (128 MiB–10 GiB) | Escalabilidade automática |
| Timeout máximo (até 15 min) | Patches de segurança |
| Permissões IAM | Disponibilidade e redundância |
| Variáveis de ambiente | Balanceamento de carga |
| Triggers e integrações | Monitoramento de infraestrutura |

## Escalabilidade automática: de zero a milhares

Uma das propriedades mais importantes do Lambda é escalar **automaticamente**, sem nenhuma configuração:

```
Comportamento de escala do Lambda:

Invocações simultâneas →

       1     →  1 ambiente de execução
      10     →  10 ambientes paralelos
     100     →  100 ambientes paralelos
   1.000     →  1.000 ambientes paralelos
  10.000     →  10.000 ambientes paralelos (limite padrão por conta/região)

Escala para baixo:
  Após inatividade → ambientes são suspensos/removidos
  Custo quando sem invocações = $0
```

Esse comportamento elimina dois problemas clássicos de infraestrutura:
- **Over-provisioning:** pagar por capacidade ociosa em horários de baixo tráfego
- **Under-provisioning:** ficar sem capacidade durante picos inesperados

O limite padrão de **10.000 execuções simultâneas por conta/região** pode ser aumentado via AWS Support. Para a maioria dos workloads, esse limite nunca é atingido.

## Modelo de cobrança: pague pelo que usar

Lambda cobra com granularidade de **1 milissegundo**, com dois componentes:

| Componente | Preço (us-east-1) |
|---|---|
| Requisições | $0.20 por 1 milhão de invocações |
| Duração | $0.0000166667 por GB-segundo |

**GB-segundo** = memória alocada (em GB) × tempo de execução (em segundos).

```
Exemplo de cálculo de custo:
  Função: 512 MiB de memória, 200ms de duração média
  Volume: 10 milhões de invocações/mês

  Custo de requisições:
    10M × $0.20/1M = $2.00

  Custo de duração:
    GB-segundos = 0.5 GB × 0.2s × 10.000.000 = 1.000.000 GB-s
    Custo = 1.000.000 × $0.0000166667 = $16.67

  Total: $18.67/mês

  Free Tier (permanente, não expira):
    1 milhão de invocações/mês gratuitas
    400.000 GB-segundos/mês gratuitos
```

Para funções leves com volume moderado, o Lambda fica dentro do free tier ou custa alguns dólares por mês — algo que EC2 jamais conseguiria para o mesmo workload.

## Anatomia de uma função Lambda

Uma função Lambda tem uma estrutura mínima universal: um **handler** — a função de entrada que recebe o evento e o contexto de execução.

```python
# Python — handler básico
def lambda_handler(event, context):
    """
    event:   dicionário com os dados do trigger (ex: corpo do HTTP,
             metadados do S3, mensagem do SQS...)
    context: objeto com metadados da execução (tempo restante,
             nome da função, ARN, request ID...)
    """
    print(f"Evento recebido: {event}")
    print(f"Tempo restante: {context.get_remaining_time_in_millis()}ms")
    
    # Processamento
    resultado = processar(event)
    
    # Retorno (formato depende do trigger)
    return {
        "statusCode": 200,
        "body": resultado
    }
```

```javascript
// Node.js — handler básico
exports.handler = async (event, context) => {
    console.log('Evento:', JSON.stringify(event));
    
    const resultado = await processar(event);
    
    return {
        statusCode: 200,
        body: JSON.stringify(resultado)
    };
};
```

```java
// Java — handler com interface funcional
public class Handler implements RequestHandler<Map<String,String>, String> {
    @Override
    public String handleRequest(Map<String,String> event, Context context) {
        context.getLogger().log("Evento: " + event);
        return processar(event);
    }
}
```

O nome do handler é configurado no Lambda como `arquivo.função` (ex: `index.handler` para Node.js, `app.lambda_handler` para Python).

## Comparativo: Lambda vs EC2 vs ECS

```
Espectro de controle vs. responsabilidade:

Alto controle ◄──────────────────────────► Baixo controle
Baixa abstração                             Alta abstração

  EC2            ECS/Fargate      Lambda
  │              │                │
  ├── SO         ├── SO           ├── Nada de infra
  ├── Runtime    ├── Runtime      │
  ├── Scaling    │                ├── Foco: função + evento
  ├── Patches    │
  └── Rede       └── Rede/tasks

Alto gerenciamento ◄─────────────────► Zero gerenciamento
```

| Critério | EC2 | ECS/Fargate | Lambda |
|---|---|---|---|
| Gerenciamento de infra | Alto | Médio | Nenhum |
| Tempo de provisionamento | Minutos | Segundos | Milissegundos |
| Escala para zero | Não | Com esforço | Sim (automático) |
| Duração máxima de execução | Ilimitada | Ilimitada | 15 minutos |
| Estado entre execuções | Sim (disco/memória) | Sim (com volume) | Não (efêmero) |
| Cold start | Não | Sim (menor) | Sim |
| Custo quando ocioso | Sim | Sim | $0 |
| Ideal para | Workloads longos, stateful | Microsserviços em container | Eventos, webhooks, automações |

## O que "serverless" NÃO significa

**Não significa gratuito:** Lambda tem custo por invocação e por tempo de execução. Para volumes muito altos ou funções longas, pode ser mais caro que EC2.

**Não significa sem estado:** o código da função não deve assumir estado entre invocações, mas a função pode usar DynamoDB, RDS, ElastiCache, S3 e outros serviços para persistir estado externamente.

**Não significa zero operação:** você ainda gerencia código, permissões IAM, variáveis de ambiente, limites de concorrência, monitoramento via CloudWatch e arquitetura de triggers.

**Não é adequado para tudo:** workloads que precisam de execução contínua (websockets permanentes, processos daemon, jobs que duram mais de 15 minutos) não se encaixam no modelo Lambda.

## 🧩 Quiz de Fixação

1. Por que Lambda cobra $0 quando não há invocações, enquanto EC2 continua sendo cobrado mesmo sem processar requisições?

2. Uma empresa tem um sistema de processamento de pedidos que recebe entre 5 e 50.000 pedidos por hora, variando sem padrão previsível. Por que Lambda é mais adequado que EC2 para esse cenário específico?

3. Qual é a tecnologia subjacente que permite ao Lambda isolar funções de diferentes clientes com segurança, e o que ela tem de diferente de uma VM tradicional?

**Respostas:**

1) EC2 aloca recursos físicos (vCPU, RAM) dedicados à sua instância 24 horas por dia — o servidor está reservado independente de processar ou não. Lambda usa um modelo de execução sob demanda: ambientes de execução (microVMs Firecracker) são criados quando há invocações e suspensos/descartados quando não há. Como a AWS gerencia um pool compartilhado dessas microVMs entre múltiplos clientes, não há recurso físico reservado exclusivamente para sua função quando ela está ociosa — logo, não há custo.

2) O problema central é a amplitude da variação: 5 vs 50.000 pedidos/hora é uma razão de 10.000x. Com EC2, você precisaria provisionar para o pico (50.000 req/h) e pagar por essa capacidade 24/7 — incluindo os períodos com apenas 5 req/h, desperdiçando >99% da capacidade. Lambda escala automaticamente de 5 para 50.000 invocações simultâneas sem configuração e sem custo nas horas de baixo volume. A variação imprevisível elimina a possibilidade de usar Reserved Instances, tornando o EC2 ainda mais caro. Lambda cobra exatamente pelo processamento real, independente do volume.

3) Lambda usa **AWS Firecracker** — um hypervisor de microVMs open source desenvolvido pela AWS. Diferente de VMs tradicionais (que emulam hardware completo incluindo BIOS, drivers de dispositivo e um sistema operacional completo), o Firecracker usa o KVM do Linux para criar VMs minimalistas: apenas o kernel Linux, os recursos mínimos necessários para o runtime, e o código da função. O resultado é isolamento de segurança equivalente a uma VM (cada função em seu próprio kernel) com tempo de inicialização de ~125 milissegundos — ordens de magnitude mais rápido que VMs tradicionais, viabilizando a escala instantânea do Lambda.
