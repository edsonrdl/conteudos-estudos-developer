### Quando usar Lambda, quando evitar e comparativo de custo vs EC2

Lambda não é a solução universal para computação na AWS — é uma ferramenta excelente para um conjunto específico de problemas e uma escolha cara ou tecnicamente inadequada para outros. Entender os critérios de decisão evita tanto a sub-utilização (não usar Lambda onde seria perfeito) quanto a super-aplicação (forçar Lambda em cenários onde EC2 ou containers são superiores).

---

## Quando Lambda é ideal

### 1. Workloads orientados a eventos com escala variável

O melhor caso de uso do Lambda: código que executa em resposta a eventos discretos, com volume imprevisível ou altamente variável.

```
Exemplos canônicos:

Upload de arquivo → processamento → resultado
  S3 → Lambda (resize, OCR, virus scan) → S3/DynamoDB

Mensagem na fila → processamento → ack
  SQS → Lambda (processar pedido, enviar email) → RDS/SNS

Requisição HTTP esporádica → resposta
  API Gateway → Lambda (CRUD, webhooks, integrações) → DynamoDB

Evento de sistema → reação
  EventBridge → Lambda (reagir a mudanças de infraestrutura)
  CloudTrail → Lambda (auditoria, alertas de segurança)
```

### 2. APIs com tráfego intermitente ou muito variável

Uma API que recebe 0 requisições às 3h da manhã e 10.000/minuto às 12h do dia é o perfil ideal para Lambda — você paga exatamente pelo que usa, sem pagar pela capacidade ociosa das madrugadas.

### 3. Automações e tarefas de operação

Jobs de manutenção que rodam periodicamente (limpeza de dados, geração de relatórios, sincronização de sistemas) são perfeitos para Lambda + EventBridge Scheduler:

```python
# Exemplo: limpeza diária de sessões expiradas
def lambda_handler(event, context):
    """Executado todo dia às 2h via EventBridge cron(0 2 * * ? *)"""
    tabela = dynamodb.Table('sessoes')
    agora = int(time.time())
    
    # Deletar sessões expiradas há mais de 7 dias
    response = tabela.scan(
        FilterExpression=Attr('expira_em').lt(agora - 7*86400)
    )
    
    with tabela.batch_writer() as batch:
        for item in response['Items']:
            batch.delete_item(Key={'sessao_id': item['sessao_id']})
    
    return {'deletadas': len(response['Items'])}
```

### 4. Backends de microsserviços simples e stateless

Para microsserviços que fazem operações CRUD simples (criar, ler, atualizar, deletar dados), Lambda elimina toda a infraestrutura de servidor — sem EC2, sem ECS, sem gerenciamento de SO.

### 5. Processamento de stream com picos imprevisíveis

Kinesis + Lambda para processar eventos de clickstream, logs de aplicação ou telemetria IoT escala automaticamente com o volume de dados sem nenhuma configuração adicional.

## Quando evitar Lambda (anti-padrões)

### ❌ Execuções longas (> 15 minutos)

Lambda tem timeout máximo de 15 minutos — hard limit, não configurável. Processos que precisam rodar por horas (importação de grandes datasets, encoding de vídeos longos, treinamento de ML sem checkpointing) não cabem no Lambda.

**Alternativa:** AWS Batch, ECS Tasks, ou Step Functions com múltiplas funções Lambda encadeadas (cada uma dentro do timeout).

### ❌ Workloads com estado persistente em memória

Lambda não garante que o mesmo ambiente de execução será reutilizado. Qualquer estado que precise sobreviver entre invocações independentes deve estar em armazenamento externo (DynamoDB, ElastiCache, S3). Aplicações que dependem de estado em memória entre requisições (WebSocket connections, sessões em memória, filas em memória) precisam de uma abordagem diferente.

**Alternativa:** ECS com conexões persistentes, ElastiCache para estado compartilhado.

### ❌ WebSockets e conexões persistentes de longa duração

Lambda é stateless e cada invocação é independente. WebSockets requerem uma conexão persistente entre cliente e servidor — Lambda não mantém conexões abertas entre invocações.

**Alternativa:** API Gateway WebSocket API (que mantém a conexão e invoca Lambda para cada mensagem), ECS com servidor WebSocket dedicado, ou App Runner.

### ❌ Alto volume de requisições curtas e contínuas (CPU-bound)

Para funções que rodam 24/7 com volume constante e altíssimo, o custo por invocação do Lambda pode superar EC2 + Reserved Instances.

**Critério de ruptura:** se a função roda continuamente por mais de 60-70% do tempo, EC2 ou Fargate com Reserved/Savings Plans geralmente é mais barato.

### ❌ Latência de rede < 1ms entre serviços

Lambda em VPC adiciona latência de rede. Para sistemas que precisam de comunicação ultra-low-latency entre componentes (trading de alta frequência, processamento de jogos em tempo real com µs de latência), Lambda não é adequado.

### ❌ Dependências com estado de processo (PIDs, sockets, FIFOs)

Algumas bibliotecas e ferramentas assumem que são o único processo rodando, usam arquivos de lock, ou dependem de PIDs específicos. No ambiente Lambda, múltiplas invocações paralelas compartilham o host de formas que podem causar conflitos.

## Comparativo de custo: Lambda vs EC2

O ponto de break-even depende de três fatores: **volume de invocações**, **duração média** e **memória configurada**. Não existe uma resposta universal — é um cálculo específico por workload.

### Cenário 1: API com tráfego baixo e irregular

```
API interna com 500.000 requisições/mês, duração média 200ms, 512 MiB

Lambda:
  Requisições: 500K × $0.20/1M = $0.10
  Duração: 0.5 GB × 0.2s × 500.000 = 50.000 GB-s × $0.0000166667 = $0.83
  Total Lambda: $0.93/mês

EC2 menor (t3.small — 2 vCPU, 2 GiB, para ficar ativo 24/7):
  On-Demand: $0.023/hora × 720h = $16.56/mês
  Reserved 1yr: ~$10/mês

Vencedor: Lambda — 10-17x mais barato para baixo volume
```

### Cenário 2: API com tráfego alto e constante

```
API de produção com 100 milhões de requisições/mês, duração 100ms, 512 MiB

Lambda:
  Requisições: 100M × $0.20/1M = $20.00
  Duração: 0.5 GB × 0.1s × 100.000.000 = 5.000.000 GB-s × $0.0000166667 = $83.33
  Total Lambda: $103.33/mês

EC2 (m7g.large — 2 vCPU, 8 GiB — consegue ~1.000 req/s):
  Necessário: 100M req / (30dias × 86.400s × 1000 req/s) = ~0.04 instâncias
  1 instância m7g.large On-Demand: $0.0816/h × 720h = $58.75/mês
  Reserved 1yr: ~$37/mês

Vencedor: EC2 Reserved — 2-3x mais barato para alto volume constante
```

### Cenário 3: Picos sazonais (Black Friday)

```
E-commerce: 1M req/dia normalmente, 50M req/dia no Black Friday

Lambda:
  Novembro normal (29 dias): 29M req
  Black Friday (1 dia): 50M req
  Total: 79M requisições, duração 150ms, 512 MiB

  Requisições: 79M × $0.20/1M = $15.80
  Duração: 0.5 × 0.15 × 79.000.000 = 5.925.000 GB-s × $0.0000166667 = $98.75
  Total Lambda novembro: $114.55

EC2 para aguentar o Black Friday:
  50M req/dia ÷ 86.400s = 579 req/s → ~1 m7g.xlarge (4 vCPU)
  m7g.xlarge Reserved 1yr: ~$88/mês
  Mas sobreprovisiona 50x nos outros 29 dias

Vencedor: Lambda — elimina o risco de over-provisioning para picos imprevisíveis
```

### Gráfico do ponto de break-even

```
Custo mensal (função 512 MiB, 200ms de duração):

$120 ─────────────────────────────────────────────
      EC2 t3.medium Reserved ($24/mês fixo)
$100 ─────────────────── ←── EC2 mais barato aqui
 $80 ─────────────────/──────────────────────────
 $60 ───────────────/────────────────────────────
 $40 ─────────────/──────────────────────────────
 $20 ───────────/────── Break-even: ~8M req/mês ─
  $0 ─────────────────────────────────────────────
       0    2M   4M   6M   8M   10M  12M  req/mês
           ↑                    ↑
      Lambda mais barato    EC2 mais barato

Acima de ~8M req/mês com esse perfil → EC2 Reserved compensa
Abaixo de ~8M req/mês → Lambda é mais econômico
```

O break-even varia com memória, duração e preço do EC2. Para calcular o seu:

```
Break-even (requisições/mês) =
  Custo fixo EC2 / (Custo Lambda por requisição)
  
Custo Lambda por req = 
  $0.20/1M + (memória_GB × duração_s × $0.0000166667)
```

## Árvore de decisão: Lambda ou não?

```
A função precisa rodar por mais de 15 minutos?
  SIM → ❌ Lambda não serve → AWS Batch / ECS Task

A carga é contínua (>70% do tempo ativa) e o volume é alto?
  SIM → Calcule o break-even; provavelmente EC2 + Reserved é melhor

A função mantém estado em memória entre requisições independentes?
  SIM → ❌ Redesenhar com estado externo ou usar ECS

Precisa de WebSocket / conexão persistente?
  SIM → ❌ API Gateway WebSocket + Lambda (para mensagens) ou ECS

Precisa de latência sub-milissegundo entre componentes?
  SIM → ❌ ECS na mesma AZ / mesmo host

Nenhuma das anteriores?
  → ✅ Lambda é provavelmente a escolha certa
     Verifique o volume e calcule o break-even para confirmar o custo
```

## Padrões arquiteturais onde Lambda se destaca

### API serverless (o mais comum)

```
Client → API Gateway → Lambda → DynamoDB
                             ↘ S3
                             ↘ SES (email)
```

### Pipeline de processamento assíncrono

```
Upload → S3 → Lambda (validar) → SQS → Lambda (processar) → RDS
                                     ↘ SNS (notificar)
```

### Event-driven entre microsserviços

```
Serviço A → EventBridge → Lambda B (reagir ao evento)
                        → Lambda C (outra reação)
                        → SQS → Lambda D (processamento)
```

### Backend de automação e operação

```
EventBridge Scheduler (cron) → Lambda → AWS APIs
                                      → Slack/PagerDuty
                                      → DynamoDB (auditoria)
```

## Erros comuns ao decidir usar Lambda

**"Lambda é sempre mais barato":** falso para workloads de alto volume contínuo. Calcule o break-even antes de migrar uma API de alto tráfego de EC2/ECS para Lambda.

**"Lambda não escala para produção":** falso. Lambda escala para dezenas de milhares de execuções simultâneas. O limite padrão de 1.000 por conta é configurável via Support, e empresas como Amazon, Netflix e Coca-Cola rodam produção crítica em Lambda.

**"Lambda é só para microserviços pequenos":** falso. Funções Lambda podem ter até 10 GB de memória, 15 minutos de timeout e 10 GB de container image — suficiente para workloads complexos.

**"Migrar para Lambda resolve problemas de escala":** Lambda escala automaticamente, mas isso pode **amplificar** problemas downstream. Se sua função Lambda faz 10.000 conexões simultâneas ao RDS, o banco pode não aguentar. Lambda com RDS requer RDS Proxy para gerenciar o pool de conexões.

## 🧩 Quiz de Fixação

1. Uma startup tem uma API com 2 milhões de requisições/mês, duração média de 300ms e 256 MiB de memória. O CTO sugere migrar para EC2 `t3.micro` Reserved (1yr, ~$6/mês) para "economizar". Calcule o custo atual no Lambda e avalie se a migração faz sentido.

2. Um time quer usar Lambda para manter um cache em memória compartilhado entre todas as instâncias da função, evitando queries repetidas ao DynamoDB. Por que essa arquitetura está fundamentalmente errada e qual é a solução correta?

3. Uma plataforma de streaming tem um encoder de vídeo que leva em média 25 minutos para processar um arquivo. O time quer migrar para Lambda para "eliminar servidores". Qual é o bloqueio técnico e como redesenhar a solução usando Lambda dentro de seus limites?

**Respostas:**

1) **Custo Lambda atual:**
- Requisições: 2M × $0.20/1M = **$0.40**
- Duração: 0.256 GB × 0.3s × 2.000.000 = 153.600 GB-s × $0.0000166667 = **$2.56**
- **Total Lambda: $2.96/mês**

O `t3.micro` Reserved custa ~$6/mês — **mais que o dobro do Lambda**. A migração não faz sentido financeiramente. EC2 tem custo fixo de $6/mês independente do volume; Lambda cobra $2.96/mês proporcional ao uso real. Nesse volume (2M req/mês), Lambda é muito mais econômico. A migração só valeria a pena se o volume crescesse para ~20M+ requisições/mês com esse perfil de duração/memória — e mesmo assim, um `t3.micro` pode não ter capacidade para essa carga.

2) A arquitetura está errada porque **cada invocação Lambda pode rodar em um ambiente de execução diferente** — Lambda escala horizontalmente criando múltiplos ambientes paralelos, e cada um tem sua própria memória isolada. Um cache em memória numa variável global é local ao ambiente, não compartilhado entre os outros. Em um momento de alta concorrência com 100 ambientes paralelos, existem 100 caches independentes, cada um com estado diferente. O resultado é inconsistência de dados e múltiplas queries ao DynamoDB (uma por ambiente na primeira invocação de cada). **Solução correta:** usar **Amazon ElastiCache (Redis ou Memcached)** como cache centralizado externo ao Lambda. Todos os ambientes consultam o mesmo Redis — o cache é verdadeiramente compartilhado, com TTL gerenciado, e o DynamoDB só é consultado quando o dado não está no Redis.

3) O bloqueio técnico é o **timeout máximo de 15 minutos** — um encoding de 25 minutos sempre vai estourar esse limite. A solução é usar **AWS Step Functions** para orquestrar o processamento em etapas menores, cada uma dentro do timeout do Lambda: (1) Lambda 1: validar e dividir o vídeo em segmentos de 5 minutos; (2) Lambda 2 (paralelo, via Step Functions Map): encodar cada segmento independentemente em < 5 minutos cada; (3) Lambda 3: concatenar os segmentos encodados em S3 e gerar o arquivo final. Cada Lambda individual executa em < 15 minutos, e a Step Function orquestra o fluxo total — que pode durar horas se necessário. Alternativamente, para encoding muito pesado, **AWS Elemental MediaConvert** (serviço gerenciado de encoding) ou **AWS Batch** (para jobs longos de computação intensiva) são mais adequados que Lambda.
