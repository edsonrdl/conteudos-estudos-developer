### Modelos de invocação Lambda — Síncrono, Assíncrono e Poll-based

Lambda pode ser invocado de três formas fundamentalmente diferentes, e cada uma tem comportamento distinto de retry, tratamento de erro e entrega de resultado. Escolher o modelo errado para um caso de uso resulta em mensagens perdidas, retries infinitos ou respostas duplicadas. Entender os três modelos é pré-requisito para arquitetar sistemas confiáveis com Lambda.

---

## Visão geral dos três modelos

```
Os três modelos de invocação:

SÍNCRONO (InvocationType: RequestResponse)
  Caller ──invoke──▶ Lambda ──resultado──▶ Caller
  Caller espera a resposta antes de continuar.
  Retry: responsabilidade do caller.

ASSÍNCRONO (InvocationType: Event)
  Caller ──invoke──▶ Lambda (fila interna) ──▶ Lambda executa
  Caller não espera — apenas confirma que a AWS recebeu.
  Retry: Lambda retenta automaticamente 2x em caso de erro.

POLL-BASED (Event Source Mapping)
  Lambda ──polling──▶ Fonte (SQS/Kinesis/DynamoDB Streams)
  Lambda lê mensagens da fonte em lotes.
  Retry: mensagem permanece na fila/stream até ser processada.
```

---

## 1. Invocação Síncrona

No modelo síncrono, o caller invoca Lambda e **aguarda bloqueado** até receber a resposta. É o modelo de uma chamada de função normal — quem chama espera o resultado.

```
Fluxo síncrono:

Client HTTP
    │
    │  POST /pedido
    ▼
API Gateway ──────────────────▶ Lambda
                                   │
                                   │ executa handler
                                   │ (pode levar 10ms ou 10s)
                                   │
API Gateway ◀──────────────────── │ retorna resultado
    │
    │  HTTP 200 {"pedido": "criado"}
    ▼
Client HTTP
(esperou todo esse tempo)
```

### Comportamento em caso de erro

Em invocação síncrona, **Lambda não faz retry automático**. Se a função lança uma exceção ou retorna um erro, o erro é devolvido diretamente ao caller. É responsabilidade de quem chamou decidir se retentar ou não.

```python
# Função Lambda síncrona — erros voltam para o caller
def lambda_handler(event, context):
    try:
        resultado = processar_pedido(event)
        return {
            "statusCode": 200,
            "body": json.dumps(resultado)
        }
    except ValueError as e:
        # Erro de negócio — retorna 400 para o API Gateway
        return {
            "statusCode": 400,
            "body": json.dumps({"erro": str(e)})
        }
    except Exception as e:
        # Erro inesperado — retorna 500
        # Lambda NÃO vai retentar automaticamente
        return {
            "statusCode": 500,
            "body": json.dumps({"erro": "Erro interno"})
        }
```

### Throttling em invocação síncrona

Se Lambda atingir o limite de concorrência, a invocação síncrona recebe um erro `TooManyRequestsException` (HTTP 429) imediatamente — sem retry automático. O caller (API Gateway, SDK) é quem decide como tratar.

### Principais callers síncronos

- **API Gateway** (REST API e HTTP API) — o caso de uso mais comum
- **Application Load Balancer** — Lambda como target de um ALB
- **Amazon Cognito** — Lambda triggers de autenticação
- **SDK direto** (`invoke` com `InvocationType=RequestResponse`)
- **AWS CloudFormation** — custom resources

## 2. Invocação Assíncrona

No modelo assíncrono, o caller entrega o evento ao Lambda e **recebe confirmação imediata** de que a AWS aceitou o evento (HTTP 202 Accepted). A execução da função acontece de forma independente — o caller não espera e não recebe o resultado diretamente.

```
Fluxo assíncrono:

S3 (arquivo uploaded)
    │
    │  notifica Lambda
    ▼
Lambda Service ──▶ [Fila interna de eventos]
    │                        │
    │  202 Accepted          │ Lambda lê e executa
    ▼                        │ de forma independente
S3 (não espera resultado)    ▼
                         Lambda executa
                         (pode levar segundos ou minutos)
```

### Retry automático em invocação assíncrona

Lambda **retenta automaticamente 2 vezes** em caso de erro na função (total de 3 tentativas). O intervalo entre retentativas aumenta progressivamente (1 minuto, depois 2 minutos):

```
Comportamento de retry assíncrono:

Tentativa 1: evento processado → ERRO
    Aguarda ~1 minuto
Tentativa 2: evento reprocessado → ERRO
    Aguarda ~2 minutos
Tentativa 3: evento reprocessado → ERRO
    → Evento enviado para DLQ (se configurada)
    → Ou descartado (se sem DLQ)
```

### Dead Letter Queue (DLQ)

A DLQ é onde eventos que falharam em todas as tentativas são depositados para análise e reprocessamento manual. Lambda suporta SQS e SNS como DLQ:

```bash
# Configurar DLQ em uma função Lambda
aws lambda update-function-configuration \
  --function-name minha-funcao \
  --dead-letter-config TargetArn=arn:aws:sqs:us-east-1:123456:minha-dlq
```

```
Estrutura de uma mensagem na DLQ:
{
  "version": "1.0",
  "timestamp": "2024-01-15T10:30:00Z",
  "requestContext": {
    "requestId": "abc-123",
    "functionArn": "arn:aws:lambda:...",
    "condition": "RetriesExhausted",
    "approximateInvokeCount": 3
  },
  "requestPayload": {
    // evento original que falhou
  },
  "responseContext": {
    "statusCode": 200,
    "executedVersion": "$LATEST",
    "functionError": "Unhandled"
  },
  "responsePayload": {
    // erro retornado pela função
  }
}
```

### Event Destinations — alternativa moderna à DLQ

Mais flexível que DLQ, **Event Destinations** permite configurar destinos para **sucesso e falha** separadamente:

```
Event Destinations:
  OnSuccess → SQS, SNS, Lambda, EventBridge
  OnFailure → SQS, SNS, Lambda, EventBridge

Vantagem sobre DLQ:
  → Captura tanto sucessos quanto falhas (DLQ só falhas)
  → Inclui metadados da execução (duração, tentativas, resultado)
  → Destino pode ser EventBridge para roteamento complexo
```

```bash
# Configurar Event Destinations
aws lambda put-function-event-invoke-config \
  --function-name minha-funcao \
  --destination-config '{
    "OnSuccess": {
      "Destination": "arn:aws:sqs:us-east-1:123:fila-sucesso"
    },
    "OnFailure": {
      "Destination": "arn:aws:sqs:us-east-1:123:fila-falha"
    }
  }'
```

### Principais callers assíncronos

- **Amazon S3** — eventos de upload, delete, replicação
- **Amazon SNS** — notificações pub/sub
- **EventBridge** — eventos de regras agendadas e event buses
- **SES** — email recebido
- **SDK direto** (`invoke` com `InvocationType=Event`)

## 3. Invocação Poll-based (Event Source Mapping)

No modelo poll-based, Lambda **lê ativamente** mensagens de uma fonte de dados em vez de ser notificado. Lambda gerencia o polling internamente — você não precisa de código de loop de leitura. Esse modelo é usado com filas, streams e bancos de dados que acumulam eventos.

```
Fluxo poll-based:

SQS Queue
  [msg1] [msg2] [msg3] [msg4] [msg5]
                    ▲
                    │ Lambda faz polling contínuo
                    │ lê lotes de mensagens
                    │
               Lambda Service
                    │
                    │ entrega lote para a função
                    ▼
               Lambda executa
               com batch de mensagens
```

### Event Source Mapping — como configurar

```bash
# Criar Event Source Mapping para SQS
aws lambda create-event-source-mapping \
  --function-name minha-funcao \
  --event-source-arn arn:aws:sqs:us-east-1:123:minha-fila \
  --batch-size 10 \
  --maximum-batching-window-in-seconds 5
```

### SQS — modelo de fila (at-least-once delivery)

```
Comportamento com SQS:

Lambda lê até [batch-size] mensagens
    │
    ├── Função executa com sucesso
    │   → Lambda deleta mensagens da fila automaticamente
    │
    └── Função lança exceção
        → Mensagens voltam para a fila após visibility timeout
        → SQS reentrega após o timeout
        → Após [maxReceiveCount] tentativas → DLQ do SQS

IMPORTANTE: SQS é "at-least-once" — uma mensagem pode ser
entregue mais de uma vez. Funções devem ser idempotentes.
```

```python
# Handler para SQS — processando lote com tratamento por item
def lambda_handler(event, context):
    falhas = []
    
    for record in event['Records']:
        try:
            mensagem = json.loads(record['body'])
            processar(mensagem)
        except Exception as e:
            print(f"Falha no item {record['messageId']}: {e}")
            # Reportar falha individual — outros itens do lote foram OK
            falhas.append({'itemIdentifier': record['messageId']})
    
    # Partial batch response — apenas itens com falha voltam para a fila
    return {'batchItemFailures': falhas}
```

O **partial batch response** é crítico: sem ele, se 1 de 10 mensagens falha, todas as 10 voltam para a fila e são reprocessadas — 9 duplicatas. Com partial batch response, apenas a mensagem que falhou é reentregue.

### Kinesis Data Streams — modelo de stream (ordered, at-least-once)

```
Comportamento com Kinesis:

Cada shard do stream → 1 invocação Lambda paralela
Lambda processa registros em ordem dentro do shard

    Shard 0: [r1][r2][r3][r4] → Lambda instância A (em ordem)
    Shard 1: [r5][r6][r7][r8] → Lambda instância B (em ordem)
    Shard 2: [r9][r10][r11]   → Lambda instância C (em ordem)

Em caso de erro:
    → Lambda retenta o mesmo batch ATÉ que expire o retention period
    → Ou até função ter sucesso
    → Shard fica BLOQUEADO — novos registros não são processados
    (comportamento diferente do SQS!)
```

O bloqueio de shard no Kinesis é um ponto crítico: **um registro com erro persistente pode bloquear o processamento de todos os registros posteriores no shard**. Mitigações:

```bash
# Configurar bisect-on-error — divide o lote ao meio para isolar o registro problemático
aws lambda update-event-source-mapping \
  --uuid <mapping-id> \
  --bisect-batch-on-function-error true \
  --maximum-retry-attempts 3 \
  --destination-config '{"OnFailure": {"Destination": "arn:aws:sqs:...:dlq"}}'
```

### DynamoDB Streams — modelo similar ao Kinesis

DynamoDB Streams tem comportamento idêntico ao Kinesis para Lambda: processamento ordenado por shard, bloqueio em caso de erro persistente, e recomenda-se as mesmas configurações de `bisect-batch-on-error` e `maximum-retry-attempts`.

## Comparativo dos três modelos

```
┌─────────────────┬──────────────┬──────────────┬──────────────────┐
│                 │  Síncrono    │  Assíncrono  │   Poll-based     │
├─────────────────┼──────────────┼──────────────┼──────────────────┤
│ Caller espera?  │ Sim          │ Não          │ N/A (Lambda lê)  │
│ Retry automático│ Não          │ 2x           │ Depende da fonte │
│ DLQ nativa      │ Não          │ Sim          │ No serviço fonte │
│ Resultado       │ Devolvido    │ Descartado   │ Ack implícito    │
│ Throttling      │ 429 imediato │ Fila interna │ Reduz batch size │
│ Ordenação       │ N/A          │ Não          │ Kinesis/DDB: Sim │
│ Exemplos        │ API Gateway  │ S3, SNS      │ SQS, Kinesis     │
│                 │ ALB, Cognito │ EventBridge  │ DynamoDB Streams │
└─────────────────┴──────────────┴──────────────┴──────────────────┘
```

## Erros comuns e armadilhas

**Esquecer idempotência em invocação assíncrona e SQS:** ambos garantem "at-least-once delivery" — a mesma mensagem pode ser processada mais de uma vez. Funções que criam registros em banco sem verificação de duplicata podem inserir dados repetidos.

**Não usar partial batch response com SQS:** sem ele, qualquer erro no lote causa reprocessamento de todas as mensagens do lote — incluindo as que já foram processadas com sucesso.

**Deixar Kinesis bloqueado por erro persistente:** sem `bisect-on-error` e `maximum-retry-attempts`, um registro corrompido ou inválido bloqueia o shard indefinidamente. Sempre configure um máximo de retentativas e DLQ para Kinesis.

**Confundir DLQ do Lambda com DLQ do SQS:** em poll-based com SQS, a DLQ de reprocessamento fica na configuração do SQS (não do Lambda). Em invocação assíncrona, a DLQ fica na configuração do Lambda. São mecanismos diferentes.

## 🧩 Quiz de Fixação

1. Uma função Lambda é invocada via API Gateway (síncrono) e falha com exceção. O usuário recebe erro 500. Quantas vezes Lambda executou a função antes de devolver o erro?

2. Um sistema usa S3 para acionar Lambda assincronamente quando arquivos são enviados. Um arquivo causa erro em todas as 3 tentativas (incluindo retries). A DLQ está configurada. O que está na DLQ e qual é o próximo passo operacional correto?

3. Uma função Lambda processa mensagens de SQS em lotes de 20. O processamento do item 7 falha com exceção não tratada (a função retorna erro). Sem partial batch response configurado, o que acontece com as mensagens 1-6 e 8-20?

**Respostas:**

1) **Uma vez apenas.** Em invocação síncrona, Lambda não faz retry automático. A função executa uma vez, lança a exceção, e Lambda devolve o erro imediatamente ao API Gateway, que repassa o HTTP 500 para o cliente. Não há reprocessamento. Se o cliente quiser retentar, ele deve fazer uma nova requisição HTTP.

2) Na DLQ está o **payload original do evento S3** (metadados do arquivo: bucket, chave, tamanho, etc.) enriquecido com metadados da falha (requestId, ARN da função, número de tentativas). O próximo passo operacional correto é: (1) inspecionar a mensagem na DLQ para entender o payload do evento; (2) identificar por que o arquivo causa falha — pode ser arquivo corrompido, formato inesperado, ou bug na função; (3) corrigir o problema (na função ou no arquivo); (4) reprocessar manualmente o evento da DLQ (mover a mensagem de volta para a fila original ou invocar a função diretamente com o payload).

3) **As mensagens 1-6 e 8-20 são recolocadas na fila e reprocessadas novamente**, junto com a mensagem 7 que realmente falhou. Lambda não tem visibilidade de quais itens do lote tiveram sucesso — a granularidade de erro é do lote inteiro. Quando a função retorna erro, o SQS considera que nenhuma das 20 mensagens foi processada e as reentrega após o visibility timeout. Resultado: 19 mensagens processadas com sucesso terão seus efeitos colaterais (inserções em banco, emails enviados, etc.) executados uma segunda vez — potencialmente causando duplicatas. A solução é implementar partial batch response (`batchItemFailures`) para que apenas a mensagem 7 seja reentregue.
