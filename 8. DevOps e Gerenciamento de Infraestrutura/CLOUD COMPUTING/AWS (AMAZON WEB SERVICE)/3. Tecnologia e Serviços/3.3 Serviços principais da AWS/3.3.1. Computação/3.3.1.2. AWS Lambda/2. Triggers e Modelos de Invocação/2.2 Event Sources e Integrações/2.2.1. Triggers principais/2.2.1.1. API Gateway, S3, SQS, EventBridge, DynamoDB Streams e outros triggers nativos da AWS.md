### Triggers nativos da AWS para Lambda — event sources e integrações

Lambda integra-se nativamente com dezenas de serviços AWS como event source. Cada trigger tem seu próprio formato de evento, modelo de invocação, garantias de entrega e particularidades de configuração. Conhecer os triggers principais é essencial para construir arquiteturas event-driven eficientes e evitar surpresas com comportamentos específicos de cada fonte.

---

## Mapa dos principais triggers por modelo de invocação

```
Triggers organizados por modelo de invocação:

SÍNCRONO (caller espera resposta):
  API Gateway (REST/HTTP)   ALB   Cognito Triggers
  CloudFront Functions      Lex   Alexa

ASSÍNCRONO (fire-and-forget):
  S3 Events       SNS          EventBridge Rules
  SES (e-mail)    CloudWatch   CodeCommit / CodePipeline
  IoT Rules       Config       CloudFormation (custom resources)

POLL-BASED (Lambda lê da fonte):
  SQS             Kinesis Data Streams
  DynamoDB Streams Kafka (MSK)   Kafka (self-managed)
  DocumentDB Streams
```

## API Gateway

O trigger mais comum para APIs REST e HTTP — Lambda age como backend de cada rota.

```
Arquitetura típica:

Client ──▶ API Gateway ──▶ Lambda ──▶ DynamoDB / RDS / S3
                │
                └─ Autenticação (Cognito / Lambda Authorizer)
                   Throttling
                   Cache
                   CORS
```

### Formato do evento (HTTP API — payload format 2.0)

```json
{
  "version": "2.0",
  "routeKey": "POST /pedidos",
  "rawPath": "/pedidos",
  "rawQueryString": "origem=web",
  "headers": {
    "content-type": "application/json",
    "authorization": "Bearer eyJ..."
  },
  "queryStringParameters": {
    "origem": "web"
  },
  "requestContext": {
    "accountId": "123456789",
    "apiId": "abc123",
    "http": {
      "method": "POST",
      "path": "/pedidos",
      "sourceIp": "203.0.113.10"
    },
    "requestId": "req-abc-123",
    "stage": "$default"
  },
  "body": "{\"produto\": \"notebook\", \"quantidade\": 1}",
  "isBase64Encoded": false
}
```

### REST API vs HTTP API

| Aspecto | REST API | HTTP API |
|---|---|---|
| Latência | ~6ms overhead | ~1ms overhead |
| Custo | $3.50/milhão | $1.00/milhão |
| Recursos | Completo (cache, WAF, usage plans) | Básico (JWT auth, CORS) |
| Payload format | 1.0 | 2.0 (mais limpo) |
| Quando usar | Produção com necessidades avançadas | APIs simples e de baixo custo |

## Amazon S3

S3 notifica Lambda assincronamente quando objetos são criados, modificados ou deletados.

```
Casos de uso comuns:
  Upload de imagem → Lambda → redimensionar → S3 (outra pasta)
  Upload de CSV    → Lambda → processar    → DynamoDB
  Arquivo de log   → Lambda → parsear      → CloudWatch / Elasticsearch
```

### Configuração de notificação S3

```json
{
  "LambdaFunctionConfigurations": [
    {
      "LambdaFunctionArn": "arn:aws:lambda:...:minha-funcao",
      "Events": ["s3:ObjectCreated:*"],
      "Filter": {
        "Key": {
          "FilterRules": [
            {"Name": "prefix", "Value": "uploads/"},
            {"Name": "suffix", "Value": ".jpg"}
          ]
        }
      }
    }
  ]
}
```

### Formato do evento S3

```json
{
  "Records": [
    {
      "eventSource": "aws:s3",
      "eventName": "ObjectCreated:Put",
      "s3": {
        "bucket": {
          "name": "meu-bucket",
          "arn": "arn:aws:s3:::meu-bucket"
        },
        "object": {
          "key": "uploads/foto-usuario-123.jpg",
          "size": 204800,
          "eTag": "abc123def456"
        }
      }
    }
  ]
}
```

**Armadilha S3 → Lambda → S3:** se a função Lambda grava de volta no mesmo bucket que dispara o trigger, pode criar um loop infinito (arquivo criado → Lambda → cria arquivo → Lambda → ...). Use prefixos/sufixos diferentes para entrada e saída, ou buckets separados.

## Amazon SQS

O trigger poll-based mais usado. Lambda lê mensagens em lotes e as deleta após processamento bem-sucedido.

```
Arquitetura de worker assíncrono:

API Gateway ──▶ Lambda (producer) ──▶ SQS ──▶ Lambda (consumer)
                                               │
                                          processa em background
                                          sem bloquear a API
```

### Configurações importantes no Event Source Mapping

```bash
aws lambda create-event-source-mapping \
  --function-name processador-pedidos \
  --event-source-arn arn:aws:sqs:us-east-1:123:fila-pedidos \
  --batch-size 10 \
  --maximum-batching-window-in-seconds 5 \
  --function-response-types ReportBatchItemFailures
  # ^ habilita partial batch response
```

| Parâmetro | Valor | Significado |
|---|---|---|
| `batch-size` | 1–10.000 | Mensagens por invocação |
| `maximum-batching-window` | 0–300s | Aguardar mais mensagens antes de invocar |
| `ReportBatchItemFailures` | — | Habilita partial batch response |

### Formato do evento SQS

```json
{
  "Records": [
    {
      "messageId": "msg-abc-123",
      "receiptHandle": "AQEBw...",
      "body": "{\"pedidoId\": \"PED-001\", \"valor\": 299.90}",
      "attributes": {
        "ApproximateReceiveCount": "1",
        "SentTimestamp": "1705312800000"
      },
      "messageAttributes": {},
      "eventSource": "aws:sqs",
      "eventSourceARN": "arn:aws:sqs:us-east-1:123:fila-pedidos",
      "awsRegion": "us-east-1"
    }
  ]
}
```

## Amazon EventBridge

EventBridge é o barramento de eventos da AWS — permite rotear eventos entre serviços com regras declarativas. Lambda é o target mais comum.

```
Dois padrões principais:

1. Scheduled Rules (cron):
   EventBridge ──(a cada 5 min)──▶ Lambda
   Equivalente a um cron job gerenciado

2. Event Pattern Rules (roteamento):
   EC2 state-change event
        │
        ▼
   EventBridge Rule
   (filtra: state = "terminated")
        │
        ├──▶ Lambda (notifica Slack)
        ├──▶ SQS (registra no sistema)
        └──▶ SNS (alerta o time)
```

### Scheduled Rules — cron syntax

```bash
# Executar a cada 5 minutos
aws events put-rule \
  --name "cleanup-cache-5min" \
  --schedule-expression "rate(5 minutes)"

# Cron: toda segunda às 8h UTC
aws events put-rule \
  --name "relatorio-semanal" \
  --schedule-expression "cron(0 8 ? * MON *)"
```

### Formato do evento EventBridge (scheduled)

```json
{
  "version": "0",
  "id": "evt-abc-123",
  "detail-type": "Scheduled Event",
  "source": "aws.events",
  "account": "123456789",
  "time": "2024-01-15T08:00:00Z",
  "region": "us-east-1",
  "resources": ["arn:aws:events:...:rule/relatorio-semanal"],
  "detail": {}
}
```

### Event Pattern Rules

```json
{
  "source": ["aws.ec2"],
  "detail-type": ["EC2 Instance State-change Notification"],
  "detail": {
    "state": ["terminated", "stopped"]
  }
}
```

## DynamoDB Streams

DynamoDB Streams captura todas as modificações (insert, update, delete) em uma tabela em ordem cronológica. Lambda processa essas mudanças para replicação, auditoria ou propagação de eventos.

```
Casos de uso:
  DynamoDB (tabela principal)
       │ stream de mudanças
       ▼
  Lambda
       ├──▶ ElasticSearch (sincronizar índice de busca)
       ├──▶ SQS (propagar para outros sistemas)
       ├──▶ DynamoDB (outra região — replicação custom)
       └──▶ SNS (notificar sobre mudanças específicas)
```

### Formato do evento DynamoDB Streams

```json
{
  "Records": [
    {
      "eventSource": "aws:dynamodb",
      "eventName": "INSERT",
      "dynamodb": {
        "Keys": {
          "userId": {"S": "user-123"}
        },
        "NewImage": {
          "userId": {"S": "user-123"},
          "nome": {"S": "João Silva"},
          "email": {"S": "joao@exemplo.com"},
          "criadoEm": {"S": "2024-01-15T10:00:00Z"}
        },
        "OldImage": null,
        "StreamViewType": "NEW_AND_OLD_IMAGES",
        "SequenceNumber": "111",
        "SizeBytes": 128
      }
    },
    {
      "eventName": "MODIFY",
      "dynamodb": {
        "Keys": {"userId": {"S": "user-456"}},
        "NewImage": {"userId": {"S": "user-456"}, "status": {"S": "ativo"}},
        "OldImage": {"userId": {"S": "user-456"}, "status": {"S": "pendente"}}
      }
    }
  ]
}
```

**StreamViewType** determina o que está disponível no evento:
- `KEYS_ONLY` — apenas as chaves do item modificado
- `NEW_IMAGE` — estado atual do item após modificação
- `OLD_IMAGE` — estado anterior à modificação
- `NEW_AND_OLD_IMAGES` — ambos (mais útil, mais dados)

## Amazon SNS

SNS invoca Lambda de forma assíncrona para cada mensagem publicada em um tópico. Múltiplas funções podem subscrever o mesmo tópico.

```
Fan-out pattern com SNS:

Evento de pagamento aprovado
          │
          ▼
       SNS Topic
          │
    ┌─────┼─────┐
    ▼     ▼     ▼
Lambda  Lambda  SQS
(email) (nota) (auditoria)
```

### Formato do evento SNS

```json
{
  "Records": [
    {
      "EventSource": "aws:sns",
      "Sns": {
        "TopicArn": "arn:aws:sns:us-east-1:123:pagamentos",
        "Subject": "Pagamento Aprovado",
        "Message": "{\"pedidoId\": \"PED-001\", \"valor\": 299.90}",
        "MessageAttributes": {
          "tipo": {
            "Type": "String",
            "Value": "pagamento"
          }
        },
        "Timestamp": "2024-01-15T10:00:00Z",
        "MessageId": "msg-abc-123"
      }
    }
  ]
}
```

## Outros triggers relevantes

### Cognito User Pools Triggers

Lambda pode ser invocado em diferentes pontos do fluxo de autenticação do Cognito — todos síncronos, pois o Cognito espera a resposta da função para prosseguir:

| Trigger | Quando | Caso de uso |
|---|---|---|
| Pre Sign-up | Antes de registrar usuário | Validar domínio de email |
| Post Confirmation | Após confirmar email | Criar perfil no DynamoDB |
| Pre Token Generation | Antes de gerar JWT | Adicionar claims customizados |
| Custom Auth Challenge | Auth flow customizado | MFA customizado |

### Application Load Balancer (ALB)

ALB pode rotear requests HTTP diretamente para Lambda, sem API Gateway. Útil quando já existe um ALB na arquitetura:

```
Client ──▶ ALB (regras de roteamento) ──┬──▶ ECS/EC2 targets
                                        └──▶ Lambda target group
```

### CloudFront Functions e Lambda@Edge

Para execução na borda (edge locations), com latência mínima global:

```
Lambda@Edge:
  Viewer Request  → manipular request antes do cache
  Origin Request  → manipular request antes de ir à origem
  Origin Response → manipular response da origem
  Viewer Response → manipular response antes de entregar ao cliente

Limitações: timeout de 5s, sem VPC, sem variáveis de ambiente,
memória máxima de 128 MiB (Viewer) ou 10.240 MiB (Origin)
```

## 🧩 Quiz de Fixação

1. Um sistema processa imagens enviadas ao S3 e grava as versões redimensionadas no mesmo bucket, na pasta `processed/`. Qual configuração no trigger S3 é obrigatória para evitar loop infinito?

2. Você precisa propagar mudanças de uma tabela DynamoDB para um índice Elasticsearch em tempo real. Qual trigger usar, qual `StreamViewType` configurar e por quê?

3. Uma API tem dois endpoints: `POST /pedidos` (cria pedido, resposta imediata ao cliente) e `GET /relatorio` (gera relatório pesado, pode levar 2 minutos). Por que usar API Gateway + Lambda síncrono para `/pedidos` é correto, mas para `/relatorio` é um anti-padrão — e qual arquitetura alternativa você proporia?

**Respostas:**

1) Configurar um **filtro de prefixo no trigger S3** para que Lambda só seja invocado para objetos na pasta de entrada, não de saída. Por exemplo: prefixo `uploads/` (onde os originais são enviados) e excluir `processed/`. Sem esse filtro, cada imagem gravada em `processed/` pelo Lambda acionaria o trigger novamente, criando um loop infinito de invocações até esgotar o limite de concorrência ou o orçamento. A solução mais segura é usar **dois buckets separados** — um para entrada e outro para saída — eliminando qualquer possibilidade de loop.

2) Usar **DynamoDB Streams** com `StreamViewType: NEW_AND_OLD_IMAGES`. O `NEW_IMAGE` sozinho seria suficiente para inserções (indexar o novo documento), mas para **atualizações** é necessário saber o estado anterior para poder atualizar corretamente o documento no Elasticsearch (identificar quais campos mudaram). Para **deleções**, só o `OLD_IMAGE` ou `KEYS_ONLY` estão disponíveis (o `NEW_IMAGE` de um delete é vazio). `NEW_AND_OLD_IMAGES` cobre todos os casos — insert, update e delete — com informação completa para manter o índice Elasticsearch sincronizado fielmente.

3) `POST /pedidos` é correto com síncrono porque a operação é rápida (inserção no banco + retorno do ID do pedido) e o cliente precisa do resultado imediatamente para confirmar a criação. `GET /relatorio` com Lambda síncrono é um anti-padrão por dois motivos: (1) API Gateway tem **timeout máximo de 29 segundos** — um relatório de 2 minutos sempre estoura esse limite; (2) manter a conexão HTTP aberta por 2 minutos é má experiência para o cliente e desperdiça conexões. **Arquitetura alternativa:** `POST /relatorio` (inicia a geração) → Lambda coloca job na SQS → retorna `202 Accepted` com um `jobId`. Lambda consumer processa assincronamente e salva o resultado em S3. O cliente usa `GET /relatorio/{jobId}/status` para verificar o progresso e, quando pronto, recebe uma URL pre-assinada do S3 para download.
