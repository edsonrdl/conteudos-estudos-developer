### Rede no ECS — awsvpc, integração com ALB/NLB e Service Discovery com Cloud Map

Rede é um dos aspectos mais críticos de uma arquitetura ECS. Cada task precisa de conectividade para receber tráfego, comunicar-se com outros serviços e acessar recursos como bancos de dados. O ECS oferece o network mode `awsvpc` como padrão moderno, integração nativa com load balancers AWS e Service Discovery via Cloud Map para comunicação entre serviços sem passar por um load balancer.

---

## Network Modes no ECS

ECS suporta três network modes, mas apenas um é recomendado para a maioria dos casos:

| Mode | Onde funciona | ENI própria | Acesso por IP | Obrigatório para |
|---|---|---|---|---|
| `awsvpc` | EC2 + Fargate | Sim (uma por task) | Sim | Fargate |
| `bridge` | EC2 apenas | Não (usa a do host) | Via port mapping | Legado |
| `host` | EC2 apenas | Não (usa a do host) | Porta do host diretamente | Casos específicos |

**`awsvpc` é o padrão recomendado** para todos os novos projetos e obrigatório para Fargate.

---

## awsvpc — uma ENI por task

No mode `awsvpc`, cada task recebe sua própria **ENI (Elastic Network Interface)** — um endereço IP privado dedicado dentro da VPC, com seu próprio Security Group. Isso muda fundamentalmente como a rede funciona em relação aos modos legados:

```
awsvpc — isolamento de rede por task:

VPC (10.0.0.0/16)
  Subnet privada (10.0.1.0/24):
  
  ┌─────────────────────────────────────────────────────┐
  │  Task A                                             │
  │  ENI: 10.0.1.10  ← IP privado dedicado             │
  │  SG: sg-api-tasks                                   │
  │  Container: porta 8080 → acessível em 10.0.1.10:8080│
  └─────────────────────────────────────────────────────┘
  
  ┌─────────────────────────────────────────────────────┐
  │  Task B                                             │
  │  ENI: 10.0.1.11  ← IP privado dedicado             │
  │  SG: sg-api-tasks                                   │
  └─────────────────────────────────────────────────────┘
  
  ┌─────────────────────────────────────────────────────┐
  │  Task C (worker — diferente SG)                     │
  │  ENI: 10.0.1.12                                     │
  │  SG: sg-worker-tasks  ← SG diferente da API         │
  └─────────────────────────────────────────────────────┘
```

### Vantagens do awsvpc

**Security Groups por task:** cada task tem seu próprio SG — é possível ter regras de firewall precisas (ex: workers SQS não precisam receber tráfego de entrada, apenas fazer saída para SQS/RDS).

**Sem conflito de portas:** no mode `bridge`, múltiplos containers no mesmo host competem pelas portas do host. Com `awsvpc`, cada task tem seu próprio IP — múltiplas tasks na porta 8080 coexistem sem conflito.

**Visibilidade de rede nativa:** o IP da task aparece no VPC Flow Logs, facilitando debugging de rede.

### Limitação: ENI trunking

Cada instância EC2 tem um **limite de ENIs** baseado no tipo de instância (ex: `m5.large` suporta até 3 ENIs). Com `awsvpc`, cada task consome uma ENI — isso limita quantas tasks podem rodar por instância.

**Solução: ENI Trunking (ECS-managed ENIs)** permite que uma única ENI trunk suporte múltiplas tasks via interfaces secundárias, aumentando a densidade de tasks por instância:

```bash
# Verificar se o tipo de instância suporta ENI trunking
# e quantas tasks pode hospedar
# Consultar: https://docs.aws.amazon.com/AmazonECS/latest/developerguide/container-instance-eni.html

# Ativar ENI trunking no cluster (para EC2 Launch Type)
aws ecs put-account-setting \
  --name awsvpcTrunking \
  --value enabled
```

## Integração com Application Load Balancer (ALB)

ALB é o load balancer padrão para serviços HTTP/HTTPS no ECS. Distribui tráfego entre tasks via Target Groups, fazendo health checks e removendo tasks não saudáveis automaticamente.

```
Arquitetura completa com ALB:

Internet
  │  HTTPS 443
  ▼
ALB (público)
  ├── Listener HTTPS :443
  │     └── Regra: path /api/* → Target Group "api-tg"
  │                path /ws/*  → Target Group "ws-tg"
  │
  ▼
Target Group "api-tg"
  ├── Target: 10.0.1.10:8080 (Task A) ← registrado automaticamente pelo ECS
  ├── Target: 10.0.1.11:8080 (Task B)
  └── Target: 10.0.1.12:8080 (Task C)
  
(Tasks são registradas/desregistradas automaticamente
 pelo ECS conforme sobem e descem)
```

### Configuração do Service com ALB

```bash
# Criar Target Group
aws elbv2 create-target-group \
  --name minha-api-tg \
  --protocol HTTP \
  --port 8080 \
  --vpc-id vpc-abc123 \
  --target-type ip \  # obrigatório para awsvpc (registra por IP, não instância)
  --health-check-path /health \
  --health-check-interval-seconds 30 \
  --healthy-threshold-count 2 \
  --unhealthy-threshold-count 3

# Criar Service apontando para o Target Group
aws ecs create-service \
  --cluster producao \
  --service-name minha-api \
  --task-definition minha-api:5 \
  --desired-count 3 \
  --load-balancers '[{
    "targetGroupArn": "arn:aws:elasticloadbalancing:...:targetgroup/minha-api-tg/abc",
    "containerName": "api",
    "containerPort": 8080
  }]' \
  --health-check-grace-period-seconds 60
```

**`target-type ip`** é obrigatório para awsvpc — o ALB registra as tasks pelo IP da ENI, não pelo ID da instância EC2.

### Deregistration delay — conexões em flight

Quando o ECS precisa encerrar uma task (scale-in ou deploy), ele a desregistra do Target Group primeiro. O **deregistration delay** (padrão: 300s) é o tempo que o ALB aguarda conexões existentes terminarem antes de parar de enviar tráfego para aquela task:

```bash
# Reduzir deregistration delay para deploys mais rápidos
# (use apenas se suas requisições são curtas — APIs REST < 30s)
aws elbv2 modify-target-group-attributes \
  --target-group-arn arn:...:targetgroup/minha-api-tg/abc \
  --attributes Key=deregistration_delay.timeout_seconds,Value=30
```

## Integração com Network Load Balancer (NLB)

NLB opera na camada 4 (TCP/UDP) — sem inspecionar o conteúdo HTTP. Use NLB quando:

```
Use NLB quando:
  ✓ Protocolo não-HTTP (gRPC, WebSocket de baixa latência, MQTT, custom TCP)
  ✓ Latência ultra-baixa (NLB adiciona <1ms vs ~5ms do ALB)
  ✓ IP estático necessário (NLB tem IPs fixos por AZ — útil para whitelist)
  ✓ Preservar IP de origem do cliente (ALB substitui o IP; NLB preserva)
  ✓ Milhões de requisições/segundo (NLB escala para volumes extremos)

Use ALB quando:
  ✓ HTTP/HTTPS com roteamento por path/header
  ✓ Autenticação (Cognito, OIDC)
  ✓ SSL termination
  ✓ Redirect HTTP → HTTPS
  ✓ WAF integration
```

## Service Discovery com AWS Cloud Map

Para comunicação **serviço-a-serviço** dentro da VPC (sem passar por um load balancer público), Cloud Map fornece **DNS-based service discovery** — cada service ECS registra suas tasks como registros DNS, e outros serviços descobrem os endpoints via DNS.

```
Service Discovery com Cloud Map:

Namespace: interno.producao.local (Route 53 Private Hosted Zone)

Service "pagamentos" registra tasks:
  pagamentos.interno.producao.local → [10.0.1.20, 10.0.1.21, 10.0.1.22]
  (atualizado automaticamente conforme tasks sobem/descem)

Service "pedidos" precisa chamar "pagamentos":
  const response = await fetch('http://pagamentos.interno.producao.local:8080/cobrar')
  // DNS resolve para um dos IPs → Round-robin entre tasks saudáveis
```

### Configurando Service Discovery

```bash
# 1. Criar namespace privado (Private DNS no Route 53)
aws servicediscovery create-private-dns-namespace \
  --name "interno.producao.local" \
  --vpc vpc-abc123

# 2. Criar service registry no Cloud Map
aws servicediscovery create-service \
  --name "pagamentos" \
  --namespace-id ns-abc123 \
  --dns-config '{
    "NamespaceId": "ns-abc123",
    "DnsRecords": [{"Type": "A", "TTL": 10}],
    "RoutingPolicy": "MULTIVALUE"
  }' \
  --health-check-custom-config FailureThreshold=1

# 3. Associar ao ECS Service
aws ecs create-service \
  --cluster producao \
  --service-name pagamentos \
  --task-definition pagamentos:3 \
  --desired-count 3 \
  --service-registries '[{
    "registryArn": "arn:aws:servicediscovery:...:service/srv-abc123",
    "containerName": "pagamentos-api",
    "containerPort": 8080
  }]'
```

### Cloud Map vs ALB para comunicação interna

```
Quando usar Cloud Map (Service Discovery):
  ✓ Comunicação interna serviço-a-serviço (sem exposição externa)
  ✓ Protocolos não-HTTP (gRPC, custom TCP)
  ✓ Latência mais baixa (sem hop pelo load balancer)
  ✓ Custo menor (sem custo de ALB interno)
  ✓ Acesso direto ao IP de tasks específicas

Quando usar ALB interno:
  ✓ HTTP com health check sofisticado
  ✓ SSL termination interna
  ✓ Path-based routing interno
  ✓ Sticky sessions
  ✓ Logs de acesso centralizados (ALB access logs)
```

## ECS Service Connect — evolução do Service Discovery

**Service Connect** é a geração mais recente de conectividade entre services ECS (lançado em 2022). Combina o conceito de service mesh com a simplicidade do Cloud Map:

```
Service Connect vs Cloud Map vs ALB interno:

Cloud Map:        DNS round-robin simples, sem observabilidade
ALB interno:      HTTP com health checks, mas custo adicional
Service Connect:  proxy sidecar por task + observabilidade integrada
                  + retry automático + métricas no CloudWatch
```

```bash
# Configurar Service Connect no cluster
aws ecs update-cluster \
  --cluster producao \
  --service-connect-defaults namespace=interno.producao.local

# Service com Service Connect habilitado
aws ecs create-service \
  --cluster producao \
  --service-name pedidos \
  --task-definition pedidos:2 \
  --service-connect-configuration '{
    "enabled": true,
    "namespace": "interno.producao.local",
    "services": [{
      "portName": "pedidos-port",      // nome do portMapping na Task Def
      "discoveryName": "pedidos",       // nome DNS
      "clientAliases": [{"port": 8080}]
    }]
  }'
```

Com Service Connect, o container `pedidos` pode chamar `http://pagamentos:8080` — o proxy sidecar gerenciado pelo ECS faz o roteamento, retries e coleta métricas automaticamente.

## Erros comuns e armadilhas

**Security Group do ALB não permite tráfego para as tasks:** o SG das tasks ECS deve permitir entrada na porta do container **do SG do ALB**, não de `0.0.0.0/0`. Erro clássico de iniciantes.

```
Regra correta no SG das tasks:
  Inbound: TCP 8080 from sg-alb (não de 0.0.0.0/0)
  
  Isso garante que apenas o ALB pode chamar as tasks diretamente.
```

**TTL alto no Cloud Map em scale-down:** com TTL de 60s no registro DNS, clients podem continuar tentando conectar em IPs de tasks já encerradas por até 60 segundos. Use TTL baixo (10-30s) para Service Discovery.

**`assignPublicIp: ENABLED` em subnet privada:** tasks Fargate em subnets privadas precisam de NAT Gateway para acesso à internet — não de IP público. Ativar `assignPublicIp` em subnet privada não funciona e gera custo desnecessário.

## 🧩 Quiz de Fixação

1. Uma task ECS em mode `awsvpc` não consegue fazer pull da imagem do ECR, retornando `CannotPullContainerError`. A task está em subnet privada sem NAT Gateway. Quais são as duas formas de resolver sem criar um NAT Gateway?

2. O ALB está com health check falhando para novas tasks ECS, mas as tasks parecem saudáveis via `docker exec`. O Security Group das tasks tem regra `TCP 8080 from 0.0.0.0/0`. Qual é o problema real e como corrigi-lo?

3. Um microserviço `checkout` precisa chamar o microserviço `pagamentos` internamente. O time está debatendo entre ALB interno e Cloud Map. O `pagamentos` usa gRPC (HTTP/2). Qual opção usar e por quê o ALB padrão não resolveria?

**Respostas:**

1) **Opção 1 — VPC Endpoints para ECR:** criar Interface Endpoints para `ecr.api`, `ecr.dkr` e `s3` (as imagens ECR são armazenadas em S3) na VPC. A task faz pull da imagem via rede privada da AWS, sem precisar de internet. Custo: ~$7/mês por endpoint por AZ. **Opção 2 — Usar imagem do ECR Public Gallery ou armazenar a imagem em S3 na mesma região via S3 Gateway Endpoint (gratuito):** S3 Gateway Endpoint é gratuito e permite que as layers da imagem ECR (armazenadas em S3) sejam baixadas sem NAT. Ainda precisaria do endpoint `ecr.api` e `ecr.dkr` para autenticação e metadados — esses têm custo. Na prática, a combinação VPC Endpoints (ECR + S3) é a solução mais comum e completa para Fargate em subnet privada sem NAT.

2) O problema real é que o **ALB não consegue alcançar as tasks** — não porque o SG das tasks bloqueie, mas porque o **SG do ALB não tem regra de saída para as tasks**, ou mais provavelmente, o **SG das tasks está correto em permitir `0.0.0.0/0` mas o Health Check do Target Group está configurado com path ou porta errada**. Verificar: (a) o path `/health` existe e retorna HTTP 200? (b) o Health Check no Target Group está apontando para a porta correta (8080)? (c) o SG das tasks tem `TCP 8080 inbound from [SG do ALB]`? A regra `0.0.0.0/0` funciona mas é desnecessariamente permissiva — a correção é restringir para `from sg-alb`, que é a prática correta de segurança e ajuda a identificar o problema: se a regra for `from sg-alb` e o health check ainda falhar, o problema está no ALB SG (sem regra de saída para a porta) ou na configuração do health check em si.

3) Usar **Cloud Map (Service Discovery)** ou **Service Connect**. O ALB padrão (ALB Layer 7) **não suporta gRPC nativamente** no sentido de roteamento — o ALB suporta gRPC como protocolo desde 2020, mas requer configuração específica e ainda adiciona latência de hop. gRPC usa HTTP/2 com streaming bidirecional; ALB clássico pode quebrar o streaming em alguns cenários. Cloud Map é mais adequado: o `checkout` resolve `pagamentos.interno.producao.local` via DNS e conecta diretamente ao IP da task via HTTP/2 sem intermediário. Service Connect é ainda melhor para esse caso — adiciona retry automático, circuit breaking e métricas sem precisar configurar o client gRPC manualmente, e suporta HTTP/2 nativamente.
