### ECS vs EKS vs Lambda vs EC2 — critérios de escolha, trade-offs e perfis de workload

Escolher entre EC2, ECS, EKS e Lambda é uma das decisões arquiteturais mais impactantes em um projeto AWS. Não existe resposta universal — cada serviço representa um ponto diferente no espectro de controle vs. abstração, custo vs. conveniência, e flexibilidade vs. simplicidade. Este arquivo desmonta os critérios de decisão com profundidade suficiente para justificar a escolha em qualquer contexto.

---

## O espectro de abstração

```
Controle total ◄──────────────────────────────► Zero gerenciamento
Maior responsabilidade                           Menor responsabilidade

    EC2           ECS (EC2)      ECS (Fargate)      Lambda
     │                │               │               │
     │  VMs           │  Containers   │  Containers   │  Funções
     │  você gerencia │  nós EC2      │  serverless   │  serverless
     │  tudo          │  você gerencia│  AWS gerencia │  AWS gerencia
     │                │  nós          │  tudo         │  tudo
     │
     ▼
  Bare Metal /
  Dedicated Host
  (máximo controle)

Duração de execução:
  EC2:       Ilimitada (processo sempre rodando)
  ECS:       Ilimitada (containers de longa duração)
  Lambda:    Máximo 15 minutos por invocação

Estado em memória:
  EC2:       Stateful (memória persiste)
  ECS:       Stateful enquanto o container roda
  Lambda:    Efêmero (sem garantia de estado entre invocações)
```

## Comparativo dimensional

### Dimensão 1: Gerenciamento de infraestrutura

| Serviço | O que você gerencia | O que a AWS gerencia |
|---|---|---|
| **EC2** | SO, runtime, patches, scaling, LB, rede | Hardware físico |
| **ECS (EC2)** | Nós EC2, AMI, patches do SO dos nós | Plano de controle ECS, hardware |
| **ECS (Fargate)** | Código, Task Definition, IAM, rede | Tudo de infra (nós, SO, patches) |
| **EKS** | Nós EC2 (ou Fargate), add-ons K8s, manifests | Plano de controle K8s, etcd |
| **Lambda** | Código, IAM, triggers, variáveis de ambiente | Tudo de infra + scaling automático |

### Dimensão 2: Custo por perfil de uso

```
Custo mensal estimado para 2 vCPU / 4 GiB de computação:

Uso esporádico (10% do tempo = ~72h/mês):
  EC2 On-Demand: $0.096/h × 720h = $69/mês (paga 24/7)
  ECS Fargate:   $0.04048×2 + $0.004445×4 × 72h = $8.20/mês ✓
  Lambda:        depende da duração — pode ser < $1/mês ✓✓

Uso contínuo 24/7:
  EC2 Reserved:  ~$35-50/mês ✓✓
  ECS Fargate:   $0.04048×2 + $0.004445×4 × 720h = $70/mês
  Lambda:        $83+/mês (alto volume de invocações longas)

Pico intenso imprevisível (0 a 1000 instâncias em segundos):
  EC2:    Não consegue escalar tão rápido
  Fargate: Escala em ~30-60s por task ✓
  Lambda:  Escala em milissegundos ✓✓
```

### Dimensão 3: Cold start e latência

```
Impacto de cold start por serviço:

EC2:    Sem cold start (processo sempre rodando)
        Latência de startup de nova instância: 1-3 minutos

ECS/Fargate: Cold start de task: 10-30s
             (pull de imagem + inicialização do container)
             Warm: sem overhead

Lambda: Cold start: 100ms (Python/Go) a 6s (Java+Spring)
        Warm: milissegundos adicionais

Para APIs com SLA P99 < 100ms:
  ECS (Fargate) com desired count > 0 → sem cold start em warm
  Lambda com Provisioned Concurrency → sem cold start
  EC2 → sem cold start (mas gerenciamento de nós)
```

### Dimensão 4: Modelo de escalonamento

```
Escalamento automático por serviço:

Lambda:
  0 → 10.000 invocações simultâneas em segundos
  Escala por invocação individual
  Ideal para: picos imprevisíveis, escala por requisição

ECS Fargate:
  Escala por task (unidade: uma task)
  Demora 30-60s para nova task ficar saudável
  Ideal para: apps que precisam de mais de 15min de execução

ECS EC2:
  Escala nós EC2 (2-5 min) + tasks (30-60s)
  Mais lento, mas mais controle e menor custo em escala

EKS:
  Semelhante ao ECS EC2, com Cluster Autoscaler ou Karpenter
  Karpenter pode provisionar nós mais rápido (~1-2 min)
```

## Perfis de workload e serviço recomendado

### API REST de propósito geral

```
Critérios:
  - Requisições HTTP < 30s
  - Volume variável (dia vs noite)
  - Stateless (dados no banco/cache)

Tráfego baixo/médio (<5M req/mês):
  → Lambda + API Gateway ✓✓
    Custo mínimo, zero operação, escala automática

Tráfego alto constante (>20M req/mês, 24/7):
  → ECS Fargate ou EC2 Reserved ✓✓
    Lambda fica caro em alto volume contínuo

Time pequeno sem ops:
  → Lambda ou ECS Fargate (Fargate elimina gerenciamento de nós)

Time grande com infraestrutura dedicada:
  → ECS EC2 Reserved (melhor custo em escala)
```

### Worker de processamento assíncrono (SQS/Kinesis)

```
Critérios:
  - Consome mensagens de fila
  - Processamento pode levar de 1s a 10min
  - Volume variável com picos

Processamento < 15min, volume variável:
  → Lambda (SQS trigger) ✓✓
    Poll gerenciado, scaling por profundidade de fila

Processamento > 15min ou stateful:
  → ECS Fargate Service + SQS
    Workers sempre rodando, consomem fila ativamente
    Auto Scaling por ApproximateNumberOfMessages (SQS)

Alto volume 24/7 previsível:
  → ECS EC2 Reserved (melhor custo que Fargate em volume)
```

### Aplicação com estado em memória (cache, conexões WebSocket)

```
Critérios:
  - Estado precisa persistir entre requisições do MESMO cliente
  - Conexões de longa duração
  - WebSocket ou streaming

→ ECS (EC2 ou Fargate) com sticky sessions no ALB ✓
  ou
→ EC2 diretamente se muito stateful

Lambda:
  → Inadequado: sem garantia de reutilização de ambiente
    para o mesmo cliente, sem WebSocket nativo
```

### Machine Learning — Inferência em produção

```
Modelo pequeno/médio (BERT, ResNet) — resposta síncrona:
  → Lambda com container image (modelo na imagem)
    ou ECS Fargate

Modelo grande (LLM > 7B parâmetros) — GPU necessária:
  → ECS EC2 (instâncias G/P) ✓✓
    Fargate não suporta GPU

Treinamento de modelos (batch, horas de duração):
  → EC2 Spot (P/G) + ECS ou AWS Batch
    Lambda: timeout de 15min inviabiliza
```

### Microsserviços em escala enterprise

```
Time único, stack AWS, sem planos multi-cloud:
  → ECS Fargate ✓ (simplicidade) ou ECS EC2 (custo)

Múltiplos times, necessidade de isolamento por namespace:
  → EKS ✓
    Namespaces K8s isolam times naturalmente

Portabilidade multi-cloud ou on-prem:
  → EKS ✓✓
    Mesmo YAML funciona no GKE, AKS, on-prem

Ecossistema K8s necessário (Istio, ArgoCD, Keda):
  → EKS ✓✓
    ECS não tem equivalente nativo para todos esses tools
```

### Jobs batch de alta computação (HPC)

```
Jobs curtos (< 15min), paralelos, independentes:
  → Lambda ✓ (máxima escala, zero gerenciamento)

Jobs longos (horas), com dependências:
  → AWS Batch (serviço gerenciado para HPC)
    ou ECS Tasks no Fargate/EC2 Spot

Jobs com requisitos de GPU ou NVMe:
  → AWS Batch com EC2 (instâncias I/P/G)
  → ECS EC2 com placement constraints
```

## Árvore de decisão principal

```
O workload requer execução > 15 minutos?
│
├── SIM → ECS, ECS Fargate, EC2 ou AWS Batch
│         (Lambda está fora — timeout de 15min)
│
└── NÃO → Pode tolerar cold start ocasional?
          │
          ├── SIM → Considera Lambda (menor custo para baixo volume)
          │
          └── NÃO → ECS Fargate com desired count > 0
                    (sempre aquecido, sem cold start)

↓ (assumindo ECS, EC2 ou EKS)

O time tem expertise em Kubernetes?
│
├── SIM → Portabilidade multi-cloud é requisito?
│         ├── SIM → EKS ✓
│         └── NÃO → ECS ou EKS (ambos funcionam bem)
│
└── NÃO → Workload precisa de GPU ou Dedicated Host?
          ├── SIM → ECS EC2 (ou EC2 direto para GPU)
          └── NÃO → Custo vs simplicidade:
                    Alto volume 24/7 → ECS EC2 Reserved
                    Volume variável   → ECS Fargate
                    Menor operação    → ECS Fargate
```

## Combinações híbridas — o mundo real

Na prática, arquiteturas maduras combinam múltiplos serviços:

```
Exemplo: plataforma de e-commerce

API de pedidos (HTTP, alto tráfego, 24/7):
  → ECS Fargate + ALB + Reserved Savings Plans

Workers de processamento (SQS, variável):
  → Lambda (SQS trigger, < 5min por pedido)

Geração de relatórios (batch, 2h, noturno):
  → ECS Fargate Task (run-task via EventBridge Schedule)

Recomendações ML (inferência com GPU):
  → ECS EC2 (instâncias G5) com Auto Scaling

Site estático + CDN:
  → S3 + CloudFront (sem compute)

Serviço de notificações (webhooks esporádicos):
  → Lambda (zero custo quando ocioso)
```

Não existe "escolha do serviço certo" — existe "serviço certo para cada componente da arquitetura".

## Erros comuns na decisão

**Usar Lambda para tudo por ser "serverless":** Lambda não é adequado para workers que precisam processar filas grandes continuamente (o polling ativo é mais eficiente no ECS), para conexões de banco persistentes de alto volume, ou para qualquer execução > 15min.

**Escolher EKS por "modernidade":** EKS é excelente — quando o time tem expertise e os requisitos justificam. Para times sem K8s skills, EKS adiciona meses de curva de aprendizado para entregar algo que ECS Fargate faria em dias.

**Manter EC2 legado quando Fargate seria mais barato:** para workloads irregulares migrados de EC2 para ECS, manter EC2 Launch Type por inércia pode custar mais que Fargate — especialmente se os nós ficam ociosos à noite.

**Não considerar AWS Batch:** para jobs de computação intensiva e paralela, AWS Batch (que usa ECS por baixo) é mais adequado que gerenciar ECS Tasks manualmente — tem gerenciamento de filas de jobs, prioridades e integração com Spot.

## 🧩 Quiz de Fixação

1. Uma startup de fintech está construindo uma API de pagamentos que receberá entre 100 e 50.000 requisições por minuto (variação imprevisível ao longo do dia), cada requisição levando ~200ms. O time tem 2 engenheiros. Qual serviço escolher e justifique considerando custo, operação e escalonamento.

2. Um sistema de processamento de vídeo precisa encodar arquivos de 2-4 horas de duração. Cada encode leva entre 20 e 90 minutos e requer GPU. O volume é de 50 vídeos/dia. Por que Lambda é inviável, e qual combinação de serviços AWS atende?

3. Uma empresa com 15 times de desenvolvimento quer padronizar a plataforma de deploy de microsserviços. Metade dos times já usa Kubernetes em outras clouds, metade nunca usou containers. Os microsserviços são 100% AWS sem planos de multi-cloud. ECS ou EKS — qual recomendar e por quê cada lado da equação tem um argumento válido?

**Respostas:**

1) **ECS Fargate + ALB**, com Auto Scaling configurado. Justificativa: (a) **Custo:** a variação de 100 a 50.000 req/min significa que em horários de baixo tráfego o custo do Fargate cai junto com a demanda — ao contrário de EC2, que pagaria capacidade ociosa. Lambda seria competitivo, mas 50.000 req/min × 0.2s = 10.000 execuções simultâneas em pico, podendo atingir o limite padrão de concorrência de conta; (b) **Operação:** com 2 engenheiros, Fargate elimina toda a gestão de nós EC2 — sem AMI, sem patches, sem Capacity Providers. EKS adicionaria complexidade operacional inaceitável para um time pequeno; (c) **Escalonamento:** Fargate escala em 30-60s por task — adequado para a maioria dos padrões de tráfego. Para picos abruptos (0 → 50K em segundos), configurar `desired count` mínimo de 5-10 tasks garante capacidade base sem cold start. Lambda seria mais rápido para escala, mas conexões ao banco e a latência de cold start Java (se for o stack) podem ser problemáticos em fintech.

2) **Lambda é inviável** por dois motivos: (1) timeout máximo de 15 minutos — encodings de 20-90 minutos excedem o limite; (2) Lambda não suporta GPUs. A combinação adequada é **AWS Batch + EC2 Spot com instâncias G5** (GPU NVIDIA A10G). AWS Batch gerencia automaticamente a fila de 50 jobs/dia, provisiona instâncias Spot G5 apenas quando há jobs na fila (custo zero quando ocioso), e encerra as instâncias após o processamento. O custo de 50 jobs/dia × 55min médios em `g5.xlarge` Spot (~$0.30/h) = ~$12/dia vs ~$40/dia On-Demand — economia de 70%. Se o job tiver checkpointing implementado, Spot Interruption é tolerável; caso contrário, usar On-Demand para jobs críticos.

3) **A resposta certa é ECS, com um plano de capacitação para os times sem experiência em containers** — mas reconhecendo que há argumento válido para EKS. **Para ECS:** (1) os times sem K8s não precisam aprender Kubernetes para começar a usar containers — ECS tem curva muito menor; (2) 100% AWS sem multi-cloud elimina o principal diferencial do K8s (portabilidade); (3) operacionalmente mais simples de padronizar — menos configurações, menos add-ons, menos falhas de cluster. **Argumento válido para EKS:** (1) os 7-8 times com K8s já têm conhecimento, tooling (Helm, ArgoCD, manifests YAML) e podem acelerar o onboarding dos outros; (2) se a empresa crescer e quiser híbrido (on-prem + AWS), EKS facilita; (3) ecossistema de observabilidade K8s (Prometheus/Grafana nativo) é mais maduro que CloudWatch. A decisão final pende para ECS pela **maioria dos times sem K8s** e pelo **princípio de menor esforço operacional** — mas deve incluir investimento em training para que os times K8s possam adaptar seus processos de CI/CD para ECS sem atrito.
