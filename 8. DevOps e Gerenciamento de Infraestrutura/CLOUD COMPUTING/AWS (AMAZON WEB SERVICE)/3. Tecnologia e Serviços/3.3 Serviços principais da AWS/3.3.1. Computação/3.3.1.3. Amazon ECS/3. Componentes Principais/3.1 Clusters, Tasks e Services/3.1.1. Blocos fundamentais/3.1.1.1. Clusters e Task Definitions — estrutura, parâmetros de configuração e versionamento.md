### Clusters e Task Definitions — estrutura, parâmetros e versionamento

Cluster e Task Definition são os dois pilares estruturais do ECS. O Cluster define **onde** os containers rodam (o ambiente de computação). A Task Definition define **como** os containers rodam (o blueprint imutável). Entender cada parâmetro dessas duas entidades é fundamental para configurar ECS corretamente desde o primeiro deploy.

---

## Cluster ECS

### O que é um Cluster

O Cluster é o **agrupador lógico** de recursos de computação e serviços ECS. Ele não é um servidor — é um namespace que contém:

```
Cluster "producao":
  ├── Capacity Providers (Fargate, Fargate Spot, ASGs EC2)
  ├── Services (minha-api, worker-pedidos, scheduler...)
  ├── Tasks em execução
  ├── Configurações de namespace (Service Connect)
  └── Configurações padrão de logging e monitoramento
```

### Criando um Cluster

```bash
# Cluster simples com Fargate
aws ecs create-cluster \
  --cluster-name producao \
  --capacity-providers FARGATE FARGATE_SPOT \
  --default-capacity-provider-strategy \
    capacityProvider=FARGATE,weight=1,base=1 \
  --settings name=containerInsights,value=enabled \
  --configuration executeCommandConfiguration='{
    "logging": "DEFAULT"
  }'
```

### Configurações importantes do Cluster

| Configuração | Valores | Impacto |
|---|---|---|
| `containerInsights` | `enabled` / `disabled` | Ativa métricas detalhadas de CPU/memória por task no CloudWatch |
| `executeCommandConfiguration` | `NONE`, `DEFAULT`, `OVERRIDE` | Controla se `ecs execute-command` (shell interativo) é permitido |
| `capacity-providers` | FARGATE, FARGATE_SPOT, ASG | Fontes de computação disponíveis para o cluster |

**Container Insights** gera custo adicional no CloudWatch (métricas customizadas) mas é essencial para debugging e alertas em produção. Em dev/staging, pode ser desabilitado para economizar.

## Task Definition — o blueprint imutável

### Estrutura completa de uma Task Definition

Uma Task Definition é um documento JSON com seções bem definidas. Vamos percorrer cada parte:

```json
{
  // ── Identificação e compatibilidade ────────────────────────────
  "family": "minha-api",                    // nome base (sem versão)
  "requiresCompatibilities": ["FARGATE"],   // FARGATE | EC2 | EXTERNAL
  "networkMode": "awsvpc",                  // obrigatório para Fargate

  // ── Recursos da task (nível task, não container) ───────────────
  "cpu": "1024",     // 1 vCPU (em unidades: 1 vCPU = 1024)
  "memory": "2048",  // 2 GiB (em MiB)

  // ── IAM ────────────────────────────────────────────────────────
  "taskRoleArn": "arn:aws:iam::123:role/MinhaApiTaskRole",
  // ^ permissões que o CÓDIGO da aplicação tem (acessar S3, DynamoDB...)

  "executionRoleArn": "arn:aws:iam::123:role/ecsTaskExecutionRole",
  // ^ permissões que o ECS AGENT tem (pull imagem ECR, enviar logs CloudWatch)

  // ── Armazenamento efêmero (Fargate) ────────────────────────────
  "ephemeralStorage": { "sizeInGiB": 50 },  // padrão: 20, máx: 200

  // ── Plataforma (Fargate ARM64/x86) ─────────────────────────────
  "runtimePlatform": {
    "cpuArchitecture": "ARM64",     // ARM64 | X86_64
    "operatingSystemFamily": "LINUX"
  },

  // ── Volumes ────────────────────────────────────────────────────
  "volumes": [
    {
      "name": "dados-compartilhados",
      "efsVolumeConfiguration": {
        "fileSystemId": "fs-0abc123",
        "rootDirectory": "/app/dados",
        "transitEncryption": "ENABLED"
      }
    }
  ],

  // ── Containers ─────────────────────────────────────────────────
  "containerDefinitions": [ /* ver seção abaixo */ ]
}
```

### containerDefinitions — o coração da Task Definition

Cada item em `containerDefinitions` define um container dentro da task. Uma task pode ter múltiplos containers — útil para sidecars (agentes de log, proxies, etc.):

```json
"containerDefinitions": [
  {
    // ── Identidade ──────────────────────────────────────────────
    "name": "api",
    "image": "123456789.dkr.ecr.us-east-1.amazonaws.com/minha-api:v2.1",
    "essential": true,
    // ^ se true: se este container morrer, a task inteira é encerrada
    //   se false: falha deste container não encerra os outros

    // ── Recursos (soft/hard limits) ─────────────────────────────
    "cpu": 768,              // unidades reservadas (soft limit)
    "memory": 1536,          // hard limit: OOM kill se ultrapassar
    "memoryReservation": 1024, // soft limit: usado no scheduling

    // ── Rede ────────────────────────────────────────────────────
    "portMappings": [
      {
        "containerPort": 8080,
        "protocol": "tcp",
        "name": "api-port"   // nome usado no Service Connect
      }
    ],

    // ── Variáveis de ambiente ───────────────────────────────────
    "environment": [
      {"name": "NODE_ENV",   "value": "production"},
      {"name": "LOG_LEVEL",  "value": "info"}
    ],

    // ── Secrets (via Secrets Manager ou SSM) ───────────────────
    "secrets": [
      {
        "name": "DB_PASSWORD",
        "valueFrom": "arn:aws:secretsmanager:us-east-1:123:secret:prod/db:password::"
      },
      {
        "name": "API_KEY",
        "valueFrom": "/prod/app/api-key"  // SSM Parameter Store
      }
    ],

    // ── Logging ─────────────────────────────────────────────────
    "logConfiguration": {
      "logDriver": "awslogs",
      "options": {
        "awslogs-group": "/ecs/minha-api",
        "awslogs-region": "us-east-1",
        "awslogs-stream-prefix": "api",
        "awslogs-create-group": "true"
      }
    },

    // ── Health check ────────────────────────────────────────────
    "healthCheck": {
      "command": ["CMD", "curl", "-f", "http://localhost:8080/health"],
      "interval": 30,    // segundos entre checks
      "timeout": 5,      // segundos para timeout do check
      "retries": 3,      // falhas consecutivas antes de UNHEALTHY
      "startPeriod": 60  // grace period após start (ignora falhas)
    },

    // ── Volumes montados ────────────────────────────────────────
    "mountPoints": [
      {
        "sourceVolume": "dados-compartilhados",
        "containerPath": "/app/dados",
        "readOnly": false
      }
    ],

    // ── Dependências entre containers ───────────────────────────
    "dependsOn": [
      {
        "containerName": "init-container",
        "condition": "SUCCESS"
        // Condições: START | COMPLETE | SUCCESS | HEALTHY
      }
    ],

    // ── Comando customizado ─────────────────────────────────────
    "command": ["node", "dist/server.js"],
    "workingDirectory": "/app",

    // ── Usuário (segurança) ─────────────────────────────────────
    "user": "1000:1000",    // não rodar como root
    "readonlyRootFilesystem": true,  // filesystem read-only
    "privileged": false     // nunca true em produção
  },

  // ── Sidecar de log (exemplo de container não-essential) ────────
  {
    "name": "log-router",
    "image": "amazon/aws-for-fluent-bit:latest",
    "essential": false,
    "firelensConfiguration": {
      "type": "fluentbit"
    }
  }
]
```

## Versionamento de Task Definitions

Task Definitions são **imutáveis** — cada atualização cria uma nova revisão numerada. Isso é intencional e garante rastreabilidade completa:

```
Histórico de revisões — family "minha-api":

minha-api:1  → imagem v1.0, cpu 512, memory 1024  (criada em Jan)
minha-api:2  → imagem v1.1, cpu 512, memory 1024  (bug fix Feb)
minha-api:3  → imagem v2.0, cpu 1024, memory 2048 (feature Mar)
minha-api:4  → imagem v2.1, cpu 1024, memory 2048 (hotfix Mar)
              ↑
         revisão ativa
```

### Operações de versionamento

```bash
# Registrar nova revisão (cria minha-api:5)
aws ecs register-task-definition \
  --cli-input-json file://task-definition.json

# Listar todas as revisões de uma family
aws ecs list-task-definitions \
  --family-prefix minha-api \
  --sort DESC

# Descrever uma revisão específica
aws ecs describe-task-definition \
  --task-definition minha-api:3

# Desativar revisão antiga (não deleta, apenas marca como INACTIVE)
aws ecs deregister-task-definition \
  --task-definition minha-api:1

# Deletar permanentemente revisões INACTIVE
aws ecs delete-task-definitions \
  --task-definitions minha-api:1 minha-api:2
```

### Rollback via Task Definition

O versionamento imutável torna rollback trivial — basta apontar o Service para a revisão anterior:

```bash
# Rollback: reverter Service para revisão anterior
aws ecs update-service \
  --cluster producao \
  --service minha-api \
  --task-definition minha-api:3  # revisão estável anterior
  # ECS faz rolling update de volta para a versão anterior
```

## Múltiplos containers em uma Task — padrões comuns

### Sidecar de proxy (Envoy / AWS App Mesh)

```
Task com sidecar Envoy:

┌─────────────────────────────────────┐
│  Task                               │
│  ┌─────────────┐  ┌───────────────┐ │
│  │  Container  │  │  Envoy Proxy  │ │
│  │  Principal  │◄─│  (sidecar)    │ │
│  │  (minha-api)│  │               │ │
│  └─────────────┘  └───────────────┘ │
│                                     │
│  Tráfego entra → Envoy → api        │
│  Tráfego sai   → Envoy → destino    │
└─────────────────────────────────────┘
```

### Init container (preparação antes do principal)

```json
// Container que roda migrações de banco antes da API subir
{
  "name": "db-migrate",
  "image": "minha-api:v2.1",
  "command": ["npm", "run", "migrate"],
  "essential": false  // task não termina quando este encerra
},
{
  "name": "api",
  "image": "minha-api:v2.1",
  "essential": true,
  "dependsOn": [
    {"containerName": "db-migrate", "condition": "SUCCESS"}
    // API só sobe DEPOIS que o migrate completar com sucesso
  ]
}
```

## Erros comuns e armadilhas

**Confundir `taskRoleArn` com `executionRoleArn`:** `taskRole` é para o código da aplicação (acessar AWS services); `executionRole` é para o ECS Agent (pull de imagem, envio de logs). Misturar os dois gera permissões incorretas e falhas silenciosas.

**Não configurar `startPeriod` no health check:** aplicações que demoram para inicializar (Spring Boot, Rails) podem ser marcadas como UNHEALTHY e reiniciadas antes mesmo de terminar o boot. Defina `startPeriod` maior que o tempo de inicialização esperado.

**`essential: true` em todos os containers:** se um sidecar de log (não-essential) for marcado como essential, uma falha nele derruba a task principal junto. Sidecars auxiliares devem ser `essential: false`.

**Hardcodar segredos em `environment`:** senhas e tokens em `environment` ficam visíveis em texto claro na Task Definition. Use sempre `secrets` com Secrets Manager ou SSM Parameter Store.

## 🧩 Quiz de Fixação

1. Uma Task Definition tem dois containers: `api` (essential: true) e `metrics-sidecar` (essential: false). O `metrics-sidecar` falha e encerra. O que acontece com o container `api` e com a task?

2. Qual é a diferença prática entre `taskRoleArn` e `executionRoleArn`, e o que acontece se você colocar a permissão `s3:GetObject` na `executionRole` em vez da `taskRole`?

3. Você precisa garantir que um container de migração de banco de dados execute e complete com sucesso ANTES que o container da API suba. Como configurar isso na Task Definition, e o que acontece se a migração falhar?

**Respostas:**

1) O container `api` **continua rodando normalmente** e a task permanece ativa. `essential: false` significa que a falha desse container não afeta o ciclo de vida da task ou dos outros containers. A task só é encerrada se um container `essential: true` falhar (no caso, o `api`). Isso é o comportamento correto para sidecars auxiliares — um agente de métricas que cai não deve derrubar o serviço principal.

2) **`taskRoleArn`** é o IAM Role assumido pelo **processo da aplicação dentro do container** — é o que define o que o código pode fazer na AWS (chamar DynamoDB, ler S3, publicar no SNS). **`executionRoleArn`** é o IAM Role assumido pelo **ECS Agent** para operações de infraestrutura antes do container subir — pull de imagem do ECR, enviar logs para CloudWatch, buscar secrets do Secrets Manager para injetar como variáveis de ambiente. Se você colocar `s3:GetObject` na `executionRole`, o ECS Agent terá permissão para acessar S3, mas o **código da aplicação** dentro do container não terá essa permissão — tentativas de `s3.getObject()` no código retornarão `AccessDenied`. A permissão precisa estar na `taskRole` para que o processo da aplicação possa usá-la.

3) Configure `dependsOn` no container da API com `condition: SUCCESS`:
```json
{"containerName": "db-migrate", "condition": "SUCCESS"}
```
O ECS inicia `db-migrate` primeiro e aguarda sua conclusão. Se `db-migrate` encerrar com código de saída 0 (sucesso), o container `api` é iniciado normalmente. Se `db-migrate` falhar (código de saída != 0), a task inteira é marcada como FAILED e encerrada — o container `api` nunca sobe. Isso é o comportamento correto: uma API rodando com banco desatualizado causaria erros de runtime; é melhor falhar o deploy e alertar do que subir em estado inconsistente.
