### Tasks e Services — execução única, serviço contínuo, Auto Scaling e health checks

Task e Service são os dois modos de execução no ECS. A **Task** é a unidade de execução — um container (ou grupo) rodando. O **Service** é o controlador que garante que um número específico de Tasks esteja sempre rodando, gerencia deploys rolling e integra com load balancers. Entender quando usar cada um e como configurar Auto Scaling e health checks é essencial para sistemas confiáveis.

---

## Task — execução standalone

Uma Task pode ser executada de forma independente, sem um Service, para jobs que têm início, meio e fim:

```
Casos de uso para Tasks standalone:

  ✓ Migração de banco de dados (roda uma vez, termina)
  ✓ Job de geração de relatório mensal
  ✓ Processamento de um arquivo específico
  ✓ Seed de dados em ambiente de staging
  ✓ Scripts de manutenção / limpeza de dados
```

```bash
# Executar task standalone (run-task)
aws ecs run-task \
  --cluster producao \
  --task-definition minha-api:5 \
  --launch-type FARGATE \
  --count 1 \
  --network-configuration '{
    "awsvpcConfiguration": {
      "subnets": ["subnet-abc123", "subnet-def456"],
      "securityGroups": ["sg-xyz789"],
      "assignPublicIp": "DISABLED"
    }
  }' \
  --overrides '{
    "containerOverrides": [{
      "name": "api",
      "command": ["node", "scripts/migrate.js"],
      "environment": [{"name": "RUN_MODE", "value": "migration"}]
    }]
  }'
```

`containerOverrides` permite substituir o comando padrão da Task Definition para um caso de uso específico — útil quando a mesma imagem serve múltiplas funções.

### Ciclo de vida de uma Task

```
Estados de uma Task:

PROVISIONING → PENDING → ACTIVATING → RUNNING → DEACTIVATING → STOPPING → DEPROVISIONING → STOPPED

PROVISIONING:   recursos de rede sendo criados (ENI no awsvpc)
PENDING:        aguardando capacidade de computação
ACTIVATING:     container sendo iniciado
RUNNING:        container rodando e saudável
DEACTIVATING:   recebeu sinal para encerrar
STOPPING:       aguardando graceful shutdown (até 30s por padrão)
DEPROVISIONING: liberando recursos de rede
STOPPED:        encerrada — tem motivo e exit code registrados
```

```bash
# Verificar motivo de encerramento de uma task
aws ecs describe-tasks \
  --cluster producao \
  --tasks arn:aws:ecs:...:task/abc-123 \
  --query 'tasks[0].{Status:lastStatus,StopCode:stopCode,StopReason:stoppedReason,ExitCode:containers[0].exitCode}'
```

## Service — controlador de longa duração

O Service garante que `desiredCount` tasks estejam sempre rodando. É o componente correto para APIs, workers contínuos e qualquer processo que deve estar permanentemente disponível.

### Criando um Service

```bash
aws ecs create-service \
  --cluster producao \
  --service-name minha-api \
  --task-definition minha-api:5 \
  --desired-count 3 \
  --launch-type FARGATE \
  --network-configuration '{
    "awsvpcConfiguration": {
      "subnets": ["subnet-abc123", "subnet-def456"],
      "securityGroups": ["sg-api-ecs"],
      "assignPublicIp": "DISABLED"
    }
  }' \
  --load-balancers '[{
    "targetGroupArn": "arn:aws:elasticloadbalancing:...:targetgroup/minha-api/abc",
    "containerName": "api",
    "containerPort": 8080
  }]' \
  --health-check-grace-period-seconds 60 \
  --deployment-configuration '{
    "deploymentCircuitBreaker": {"enable": true, "rollback": true},
    "maximumPercent": 200,
    "minimumHealthyPercent": 100
  }'
```

### deploymentConfiguration — controlando o rolling update

```
maximumPercent e minimumHealthyPercent definem a janela do rolling update:

desired count = 4, maximumPercent = 200, minimumHealthyPercent = 100:

Situação inicial: [v1] [v1] [v1] [v1] (4 tasks = 100%)

Passo 1: ECS pode ter até 200% = 8 tasks
         Lança 4 novas: [v1] [v1] [v1] [v1] [v2] [v2] [v2] [v2]
         
Passo 2: Aguarda health checks das v2 passarem
         
Passo 3: Termina as 4 v1:
         [v2] [v2] [v2] [v2] (4 tasks = 100% novamente)

Com minimumHealthyPercent = 50 (deploy mais agressivo, menor custo):
Passo 1: Termina 2 v1: [v1] [v1] (50% mínimo mantido)
Passo 2: Lança 2 v2:   [v1] [v1] [v2] [v2]
Passo 3: Termina 2 v1: [v2] [v2]
Passo 4: Lança 2 v2:   [v2] [v2] [v2] [v2]
→ Menor custo (nunca ultrapassa 100%), mas há redução temporária de capacidade
```

### Deployment Circuit Breaker

Com `deploymentCircuitBreaker` ativado, o ECS monitora o deploy e faz rollback automático se as novas tasks não ficarem saudáveis:

```
Circuit Breaker em ação:

Deploy iniciado: minha-api:5 → minha-api:6

Nova task v6 sobe → health check falha repetidamente
Circuit Breaker detecta: X tasks consecutivas falharam
→ Para o deploy automaticamente
→ Se rollback=true: reverte para minha-api:5
→ Service Event registrado: "Service reached a steady state" (com falha)

Sem Circuit Breaker:
→ ECS continuaria tentando lançar tasks v6 indefinidamente
→ Serviço degradado por tempo indeterminado
```

## Health Checks — dois níveis

ECS tem dois sistemas de health check que trabalham juntos:

```
Nível 1: Container Health Check (na Task Definition)
  → Verifica saúde do processo dentro do container
  → Comando executado dentro do container (ex: curl /health)
  → Se falhar: ECS marca container como UNHEALTHY e reinicia a task

Nível 2: Load Balancer Health Check (no Target Group)
  → Verifica se o container responde corretamente ao ALB
  → HTTP request para a porta e path configurados
  → Se falhar: ALB remove o container do pool de tráfego
               ECS marca a task como unhealthy e substitui

Os dois são complementares — o container pode estar "vivo"
mas não servir tráfego (nível 1 passa, nível 2 falha).
```

### Configurando o health check no Target Group (ALB)

```bash
aws elbv2 modify-target-group \
  --target-group-arn arn:aws:elasticloadbalancing:...:targetgroup/minha-api/abc \
  --health-check-protocol HTTP \
  --health-check-path /health \
  --health-check-interval-seconds 30 \
  --health-check-timeout-seconds 5 \
  --healthy-threshold-count 2 \
  --unhealthy-threshold-count 3
```

### Graceful shutdown — SIGTERM handling

Quando o ECS precisa encerrar uma task (scale-in, deploy, substituição), ele envia **SIGTERM** ao container. O container tem até `stopTimeout` segundos para finalizar gracefully antes de receber SIGKILL:

```javascript
// Node.js — graceful shutdown
const server = app.listen(8080);

process.on('SIGTERM', () => {
  console.log('SIGTERM recebido — encerrando gracefully');
  
  // Para de aceitar novas conexões
  server.close(() => {
    console.log('Servidor HTTP fechado');
    
    // Fechar conexões com banco, flush de cache, etc.
    db.pool.end(() => {
      console.log('Pool de banco fechado');
      process.exit(0);  // exit code 0 = encerramento normal
    });
  });
  
  // Forçar encerramento após 25s (antes do SIGKILL em 30s)
  setTimeout(() => {
    console.warn('Forçando encerramento após timeout');
    process.exit(1);
  }, 25000);
});
```

```json
// stopTimeout na Task Definition (padrão: 30s, máximo: 120s)
{
  "containerDefinitions": [{
    "name": "api",
    "stopTimeout": 30
  }]
}
```

## Auto Scaling do Service

ECS Services integram com **Application Auto Scaling** para ajustar `desiredCount` automaticamente com base em métricas.

### Target Tracking — a política mais simples

```bash
# 1. Registrar o Service como scalable target
aws application-autoscaling register-scalable-target \
  --service-namespace ecs \
  --resource-id "service/producao/minha-api" \
  --scalable-dimension ecs:service:DesiredCount \
  --min-capacity 2 \
  --max-capacity 20

# 2. Criar política de Target Tracking (manter CPU em 70%)
aws application-autoscaling put-scaling-policy \
  --policy-name "cpu-tracking" \
  --service-namespace ecs \
  --resource-id "service/producao/minha-api" \
  --scalable-dimension ecs:service:DesiredCount \
  --policy-type TargetTrackingScaling \
  --target-tracking-scaling-policy-configuration '{
    "TargetValue": 70.0,
    "PredefinedMetricSpecification": {
      "PredefinedMetricType": "ECSServiceAverageCPUUtilization"
    },
    "ScaleOutCooldown": 60,
    "ScaleInCooldown": 300
  }'
```

```
Comportamento do Target Tracking:

CPU média das tasks: 80% (acima de 70%)
  → Scale OUT: adiciona tasks até CPU voltar a ~70%

CPU média das tasks: 30% (abaixo de 70%)
  → Aguarda ScaleInCooldown (300s)
  → Scale IN: remove tasks até CPU voltar a ~70%
             (nunca abaixo de min-capacity = 2)
```

### Step Scaling — controle fino por faixa

```bash
# Política de scale-out escalonada por faixa de CPU
aws application-autoscaling put-scaling-policy \
  --policy-name "step-scale-out" \
  --service-namespace ecs \
  --resource-id "service/producao/minha-api" \
  --scalable-dimension ecs:service:DesiredCount \
  --policy-type StepScaling \
  --step-scaling-policy-configuration '{
    "AdjustmentType": "ChangeInCapacity",
    "StepAdjustments": [
      {"MetricIntervalLowerBound": 0,  "MetricIntervalUpperBound": 20, "ScalingAdjustment": 2},
      {"MetricIntervalLowerBound": 20, "MetricIntervalUpperBound": 40, "ScalingAdjustment": 4},
      {"MetricIntervalLowerBound": 40, "ScalingAdjustment": 8}
    ],
    "Cooldown": 60
  }'
# CPU 70-90%: +2 tasks | CPU 90-110%: +4 tasks | CPU > 110%: +8 tasks
```

### Métricas disponíveis para Auto Scaling

| Métrica | Tipo | Uso |
|---|---|---|
| `ECSServiceAverageCPUUtilization` | Predefinida | APIs CPU-bound |
| `ECSServiceAverageMemoryUtilization` | Predefinida | Workers com uso de memória variável |
| `ALBRequestCountPerTarget` | Predefinida (requer ALB) | APIs com carga por requisição |
| Métricas customizadas do CloudWatch | Custom | SQS queue depth, latência P99, etc. |

**SQS queue depth** é uma métrica customizada muito útil para workers: escala o número de tasks com base no tamanho da fila — mais mensagens acumuladas = mais workers processando.

## Scheduled Scaling

Para workloads com padrão previsível (horário comercial), Scheduled Scaling ajusta capacidade por horário:

```bash
# Scale up antes do horário comercial (8h UTC, seg-sex)
aws application-autoscaling put-scheduled-action \
  --service-namespace ecs \
  --resource-id "service/producao/minha-api" \
  --scalable-dimension ecs:service:DesiredCount \
  --scheduled-action-name "scale-up-morning" \
  --schedule "cron(0 8 ? * MON-FRI *)" \
  --scalable-target-action MinCapacity=10,MaxCapacity=50

# Scale down à noite (20h UTC)
aws application-autoscaling put-scheduled-action \
  --service-namespace ecs \
  --resource-id "service/producao/minha-api" \
  --scalable-dimension ecs:service:DesiredCount \
  --scheduled-action-name "scale-down-night" \
  --schedule "cron(0 20 ? * MON-FRI *)" \
  --scalable-target-action MinCapacity=2,MaxCapacity=10
```

## Erros comuns e armadilhas

**`health-check-grace-period` muito curto:** aplicações que demoram para inicializar (Spring Boot, Rails) são marcadas como unhealthy antes de terminar o boot. O Service substitui a task que acabou de subir, criando um loop. Defina `healthCheckGracePeriodSeconds` maior que o tempo de startup da aplicação.

**Não implementar SIGTERM handling:** sem graceful shutdown, tasks que estão processando requisições são mortas abruptamente durante deploys ou scale-in. Clientes recebem erros 502/504. Sempre implemente handler de SIGTERM.

**Scale-in muito agressivo (cooldown curto):** cooldown de scale-in muito curto causa instabilidade — o Service remove tasks durante um vale de CPU, mas um novo pico chega antes das tasks serem removidas, causando scale-out imediato. Cooldown de scale-in de 3-5 minutos é mais estável.

**Usar `desiredCount = 1` em produção:** uma única task é um SPOF (single point of failure). Se ela falha ou está sendo substituída durante um deploy, há downtime. Sempre `desiredCount >= 2` em produção, com tasks em AZs diferentes.

## 🧩 Quiz de Fixação

1. Um Service ECS tem `desiredCount = 4`, `minimumHealthyPercent = 100` e `maximumPercent = 125`. Quantas tasks podem existir simultaneamente durante um rolling deploy, e o que isso significa para a velocidade do deploy?

2. Uma aplicação Node.js no ECS está recebendo erros 502 durante deploys. Os logs mostram que requisições em andamento são interrompidas quando tasks antigas são encerradas. Qual é a causa e como corrigir?

3. Um worker ECS processa mensagens do SQS. A fila tem picos de 50.000 mensagens pela manhã e fica vazia à tarde. Como configurar Auto Scaling para esse padrão, e por que Target Tracking com CPU não é a melhor métrica para esse caso?

**Respostas:**

1) Com `desiredCount = 4` e `maximumPercent = 125`: máximo de `4 × 1.25 = 5 tasks` simultâneas. Com `minimumHealthyPercent = 100`: sempre pelo menos 4 tasks saudáveis. Isso significa que durante o deploy, o ECS pode lançar apenas **1 task nova de cada vez** (para não ultrapassar 5), aguarda ela ficar saudável, e só então termina 1 task antiga — e assim por diante. O deploy será mais lento (4 turnos de 1 task cada) mas a capacidade nunca cai abaixo de 100%. Para um deploy mais rápido, aumentar `maximumPercent` para 200 permitiria lançar todas as 4 novas tasks de uma vez, terminando as 4 antigas logo em seguida.

2) A causa é a **falta de graceful shutdown**. Quando o ECS encerra uma task antiga durante o rolling deploy, envia SIGTERM ao container. Sem um handler de SIGTERM, o processo Node.js termina imediatamente — mesmo com requisições HTTP em andamento. O ALB ainda pode estar direcionando tráfego para a task nos segundos antes de ela ser removida do Target Group, resultando em 502. **Correção:** implementar handler de SIGTERM no Node.js que (1) chama `server.close()` para parar de aceitar novas conexões e aguardar as existentes terminarem, (2) fecha o pool de banco e (3) chama `process.exit(0)` após o cleanup. Também aumentar `stopTimeout` na Task Definition para dar tempo suficiente ao graceful shutdown (ex: 30s).

3) A melhor abordagem é **Target Tracking com métrica customizada baseada no tamanho da fila SQS** (`ApproximateNumberOfMessagesVisible`). Configurar a política para manter, por exemplo, 500 mensagens por task — quando a fila tem 50.000 mensagens, o Auto Scaling provisiona 100 tasks; quando a fila esvazia, reduz gradualmente. **Por que CPU não é ideal:** workers SQS tendem a ter uso de CPU irregular — uma mensagem pode ser processada em 50ms com 5% de CPU, outra em 2s com 80% de CPU. A profundidade da fila é uma métrica direta da carga de trabalho pendente, enquanto a CPU média das tasks existentes não reflete quantas mensagens estão esperando para ser processadas. Com CPU, o escalamento só ocorre depois que as tasks existentes já estão sobrecarregadas; com queue depth, o escalamento é proativo — novas tasks são criadas quando há mais trabalho na fila, antes da saturação.
