### IAM no ECS — Task Role, Task Execution Role e injeção de secrets

Segurança no ECS começa com IAM. Dois roles distintos controlam permissões em níveis diferentes — um para o código da aplicação, outro para a infraestrutura do ECS. Entender a separação entre eles e como injetar segredos com segurança são fundamentos para qualquer deployment ECS em produção.

---

## Os dois IAM Roles do ECS

```
Dois roles completamente distintos:

┌─────────────────────────────────────────────────────────────┐
│                         TASK                                │
│                                                             │
│   ┌─────────────────────────────────────────────┐          │
│   │            CONTAINER (seu código)            │          │
│   │                                             │          │
│   │  s3.getObject()  → usa → Task Role          │          │
│   │  dynamodb.query() → usa → Task Role         │          │
│   │  sns.publish()   → usa → Task Role          │          │
│   └─────────────────────────────────────────────┘          │
│                                                             │
│   ECS Agent (infraestrutura)                               │
│     ecr:GetAuthorizationToken   → usa → Execution Role     │
│     logs:CreateLogStream        → usa → Execution Role     │
│     secretsmanager:GetSecretValue → usa → Execution Role   │
│     (para injetar como env var antes do container subir)   │
└─────────────────────────────────────────────────────────────┘
```

---

## Task Role — permissões da aplicação

O **Task Role** é o IAM Role que o **código da sua aplicação** assume para interagir com serviços AWS. É equivalente a um "Instance Profile" no EC2, mas com escopo de task.

### Criando o Task Role

```bash
# 1. Criar a trust policy (quem pode assumir o role)
cat > trust-policy.json << 'EOF'
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {"Service": "ecs-tasks.amazonaws.com"},
    "Action": "sts:AssumeRole"
  }]
}
EOF

# 2. Criar o role
aws iam create-role \
  --role-name MinhaApiTaskRole \
  --assume-role-policy-document file://trust-policy.json

# 3. Anexar políticas de permissão
aws iam put-role-policy \
  --role-name MinhaApiTaskRole \
  --policy-name MinhaApiPermissions \
  --policy-document '{
    "Version": "2012-10-17",
    "Statement": [
      {
        "Effect": "Allow",
        "Action": [
          "dynamodb:GetItem",
          "dynamodb:PutItem",
          "dynamodb:Query",
          "dynamodb:UpdateItem"
        ],
        "Resource": "arn:aws:dynamodb:us-east-1:123:table/pedidos"
      },
      {
        "Effect": "Allow",
        "Action": ["s3:GetObject", "s3:PutObject"],
        "Resource": "arn:aws:s3:::meu-bucket-uploads/*"
      },
      {
        "Effect": "Allow",
        "Action": ["sns:Publish"],
        "Resource": "arn:aws:sns:us-east-1:123:pedidos-topic"
      }
    ]
  }'
```

### Princípio do menor privilégio no Task Role

```
❌ Anti-padrão — permissão ampla demais:
  "Action": "dynamodb:*"
  "Resource": "*"

✓ Correto — ação específica, recurso específico:
  "Action": ["dynamodb:GetItem", "dynamodb:PutItem"]
  "Resource": "arn:aws:dynamodb:us-east-1:123:table/pedidos"

Por quê importa:
  Se um container for comprometido (injeção de código, dependência maliciosa),
  o atacante tem acesso apenas às ações explicitamente permitidas.
  Com "dynamodb:*" + "*", o atacante poderia deletar todas as tabelas da conta.
```

## Task Execution Role — permissões da infraestrutura ECS

O **Task Execution Role** é usado pelo **ECS Agent** (não pelo código da aplicação) para operações de ciclo de vida do container:

```
O que o ECS Agent precisa fazer antes do seu código rodar:
  1. Autenticar no ECR para fazer pull da imagem
  2. Criar o log group no CloudWatch
  3. Enviar logs do container para o CloudWatch
  4. Buscar secrets do Secrets Manager para injetar como env vars
  5. Buscar parâmetros do SSM Parameter Store

Tudo isso requer permissões — e todas ficam no Execution Role,
não no Task Role.
```

### Policy gerenciada base

A AWS fornece uma policy gerenciada que cobre a maioria dos casos:

```bash
# Criar o Execution Role
aws iam create-role \
  --role-name ecsTaskExecutionRole \
  --assume-role-policy-document file://trust-policy.json  # mesmo trust policy

# Anexar a policy gerenciada base
aws iam attach-role-policy \
  --role-name ecsTaskExecutionRole \
  --policy-arn arn:aws:iam::aws:policy/service-role/AmazonECSTaskExecutionRolePolicy

# A policy gerenciada inclui:
# - ecr:GetAuthorizationToken
# - ecr:BatchCheckLayerAvailability
# - ecr:GetDownloadUrlForLayer
# - ecr:BatchGetImage
# - logs:CreateLogStream
# - logs:PutLogEvents
```

### Adicionando permissões para Secrets Manager e SSM

Para injetar secrets, o Execution Role precisa de permissões adicionais:

```bash
aws iam put-role-policy \
  --role-name ecsTaskExecutionRole \
  --policy-name SecretsAccess \
  --policy-document '{
    "Version": "2012-10-17",
    "Statement": [
      {
        "Effect": "Allow",
        "Action": ["secretsmanager:GetSecretValue"],
        "Resource": [
          "arn:aws:secretsmanager:us-east-1:123:secret:prod/db-*",
          "arn:aws:secretsmanager:us-east-1:123:secret:prod/api-*"
        ]
      },
      {
        "Effect": "Allow",
        "Action": ["ssm:GetParameters"],
        "Resource": [
          "arn:aws:ssm:us-east-1:123:parameter/prod/*"
        ]
      },
      {
        "Effect": "Allow",
        "Action": ["kms:Decrypt"],
        "Resource": "arn:aws:kms:us-east-1:123:key/abc-123"
        // Necessário se os secrets usam KMS customer-managed key
      }
    ]
  }'
```

## Injeção de secrets — como funciona

A injeção de secrets acontece **antes do container iniciar**. O ECS Agent busca os valores e os injeta como variáveis de ambiente — o container os recebe como `os.environ` normais, sem conhecer a origem.

```
Fluxo de injeção de secret:

Task Definition (secrets section)
  "DB_PASSWORD" → arn:...:secret:prod/db:password::

                    ECS Agent (usa Execution Role)
                         │
                         │  secretsmanager:GetSecretValue
                         ▼
                    Secrets Manager
                         │
                         │  retorna: "s3cur3P@ssw0rd"
                         ▼
                    Container inicia com:
                    DB_PASSWORD=s3cur3P@ssw0rd
                    (em memória, não em disco)
```

### Configurando secrets na Task Definition

```json
"containerDefinitions": [{
  "name": "api",
  "secrets": [
    {
      "name": "DB_PASSWORD",
      "valueFrom": "arn:aws:secretsmanager:us-east-1:123:secret:prod/db-xyz123:password::"
      // Formato: arn:...:secret:nome:chave-json::
      // Se o secret é uma string simples (não JSON): omitir ":chave::"
    },
    {
      "name": "DB_USERNAME",
      "valueFrom": "arn:aws:secretsmanager:us-east-1:123:secret:prod/db-xyz123:username::"
      // Mesmo secret, campo diferente (secret JSON com múltiplos campos)
    },
    {
      "name": "API_KEY_TERCEIRO",
      "valueFrom": "arn:aws:secretsmanager:us-east-1:123:secret:prod/api-key-abc123"
      // Secret simples (string) — sem especificar campo
    },
    {
      "name": "LOG_LEVEL",
      "valueFrom": "/prod/minha-api/log-level"
      // SSM Parameter Store — usa o path do parâmetro (não ARN)
    }
  ]
}]
```

### Secrets Manager vs SSM Parameter Store

| Aspecto | Secrets Manager | SSM Parameter Store |
|---|---|---|
| Rotação automática | Sim (Lambda trigger) | Não nativo |
| Custo | $0.40/secret/mês + $0.05/10K chamadas | Standard: grátis; Advanced: $0.05/param/mês |
| Tamanho máximo | 65 KB | 4 KB (Standard) / 8 KB (Advanced) |
| Versionamento | Sim (AWSCURRENT, AWSPREVIOUS) | Sim (histórico de versões) |
| Cross-account | Sim (via resource policy) | Limitado |
| Ideal para | Senhas, tokens, chaves de API | Configurações, feature flags, parâmetros não-secretos |

```
Regra prática:
  Dados sensíveis (senhas, tokens OAuth, private keys) → Secrets Manager
  Configurações não-sensíveis (URLs, nomes de fila, feature flags) → SSM
  
  Usar SSM para senhas é um anti-padrão — falta rotação automática
  e o dado fica visível para qualquer um com ssm:GetParameter.
```

## Rotação automática de secrets

O Secrets Manager pode rotacionar credenciais automaticamente via Lambda:

```bash
# Configurar rotação automática a cada 30 dias
aws secretsmanager rotate-secret \
  --secret-id prod/db \
  --rotation-lambda-arn arn:aws:lambda:...:function:SecretsManagerRDSRotation \
  --rotation-rules AutomaticallyAfterDays=30
```

**Importante:** a rotação do secret não reinicia as tasks ECS automaticamente. O container continuará usando o valor antigo (injetado no início) até ser substituído. Para que tasks peguem o novo secret:

```
Opções após rotação de secret:

1. Force new deployment (reinicia todas as tasks):
   aws ecs update-service \
     --cluster producao \
     --service minha-api \
     --force-new-deployment

2. Ler o secret em runtime (não como env var):
   → A aplicação chama secretsmanager:GetSecretValue diretamente
   → Pode renovar o valor periodicamente sem reiniciar o container
   → Requer permissão no Task Role (não no Execution Role)
```

### Lendo secret em runtime (Task Role)

```python
import boto3
import json
import time

sm_client = boto3.client('secretsmanager')
_secret_cache = {}
_secret_ttl = {}
CACHE_TTL_SECONDS = 300  # renovar a cada 5 minutos

def get_secret(secret_name: str) -> dict:
    now = time.time()
    if secret_name in _secret_cache and now < _secret_ttl.get(secret_name, 0):
        return _secret_cache[secret_name]
    
    response = sm_client.get_secret_value(SecretId=secret_name)
    secret = json.loads(response['SecretString'])
    
    _secret_cache[secret_name] = secret
    _secret_ttl[secret_name] = now + CACHE_TTL_SECONDS
    return secret

def lambda_handler(event, context):
    # Pega o secret fresco (ou do cache) — sem reiniciar o container
    creds = get_secret('prod/db')
    conn = conectar_banco(creds['host'], creds['password'])
    ...
```

## ECS Exec — acesso interativo seguro ao container

Para debugging sem SSH, o **ECS Exec** permite abrir uma sessão interativa diretamente em um container rodando:

```bash
# Pré-requisito: habilitar execute-command no Service
aws ecs update-service \
  --cluster producao \
  --service minha-api \
  --enable-execute-command

# Abrir sessão interativa no container
aws ecs execute-command \
  --cluster producao \
  --task arn:aws:ecs:...:task/abc-123 \
  --container api \
  --interactive \
  --command "/bin/sh"

# Executar comando único
aws ecs execute-command \
  --cluster producao \
  --task arn:aws:ecs:...:task/abc-123 \
  --container api \
  --command "env | grep DB_"  # verificar variáveis sem expor no log
```

**Controle de acesso do ECS Exec via IAM:**

```json
{
  "Effect": "Allow",
  "Action": ["ecs:ExecuteCommand"],
  "Resource": "*",
  "Condition": {
    "StringEquals": {
      "ecs:container-name": "api"
    }
  }
}
```

O ECS Exec usa SSM Session Manager — toda sessão é auditada no CloudTrail e pode ser logada no S3 ou CloudWatch.

## Erros comuns e armadilhas

**Colocar permissões de aplicação no Execution Role:** se o código da aplicação precisa acessar S3, essa permissão vai no **Task Role**. No Execution Role colocam-se apenas permissões para o ECS Agent operar (ECR pull, CloudWatch logs, Secrets Manager para injeção). Misturar os dois cria permissões desnecessárias no Agent.

**ARN incorreto do secret:** o formato do `valueFrom` para Secrets Manager é `arn:...:secret:nome-SUFIXO:campo::`. O sufixo aleatório (ex: `-xyz123`) faz parte do ARN real — copiar só o nome sem o sufixo causa falha na injeção.

**Não versionar secrets no Secrets Manager:** durante rotação, o Secrets Manager mantém `AWSCURRENT` (novo) e `AWSPREVIOUS` (antigo). Tasks que ainda usam o valor antigo continuam funcionando com `AWSPREVIOUS` até serem reiniciadas — mas apenas por um período configurável. Não deletar `AWSPREVIOUS` imediatamente após rotação.

**Expor secrets como env vars em logs:** `env | grep DB` em logs imprime a senha em texto claro. Use ECS Exec com comando específico e garanta que os logs de aplicação não registram variáveis de ambiente na inicialização.

## 🧩 Quiz de Fixação

1. Uma task ECS falha ao iniciar com erro `ResourceInitializationError: unable to pull secrets`. A Task Definition tem um secret referenciando um ARN do Secrets Manager. Quais são as três causas mais prováveis e como diagnosticar cada uma?

2. Um desenvolvedor adiciona `secretsmanager:GetSecretValue` ao **Task Role** (em vez do Execution Role) esperando que isso permita a injeção de secrets na Task Definition. A task sobe mas a variável de ambiente `DB_PASSWORD` está vazia. Por que?

3. Uma aplicação Python que lê secrets como variáveis de ambiente (injetadas pelo ECS na inicialização) está usando uma senha de banco que foi rotacionada ontem. As tasks existentes estão com erros de autenticação no banco. Qual é a solução imediata e qual é a solução definitiva para evitar que isso aconteça novamente?

**Respostas:**

1) **Causa 1 — Permissão ausente no Execution Role:** o Execution Role não tem `secretsmanager:GetSecretValue` para o ARN do secret específico. Diagnóstico: verificar a policy do Execution Role com `aws iam get-role-policy --role-name ecsTaskExecutionRole --policy-name SecretsAccess` e conferir se o ARN do secret está no Resource. **Causa 2 — ARN incorreto do secret:** o ARN do secret inclui um sufixo aleatório (ex: `prod/db-xyz123`) que frequentemente é omitido. Diagnóstico: copiar o ARN exato do Secrets Manager console ou via `aws secretsmanager describe-secret --secret-id prod/db`. **Causa 3 — KMS sem permissão de decrypt:** se o secret usa uma Customer Managed Key (CMK) em vez da AWS managed key, o Execution Role precisa de `kms:Decrypt` para a chave específica. Diagnóstico: verificar no CloudTrail se há eventos `AccessDenied` para `kms:Decrypt` com o key ID do secret.

2) A injeção de secrets na Task Definition (campo `secrets`) é feita pelo **ECS Agent**, que usa o **Execution Role** — não o Task Role. O ECS Agent busca o valor do Secrets Manager antes de iniciar o container e o injeta como variável de ambiente. Se a permissão `secretsmanager:GetSecretValue` está apenas no Task Role, o ECS Agent não tem acesso ao secret (ele não usa o Task Role), e a injeção silenciosamente falha ou injeta string vazia. O Task Role só é usado pelo processo dentro do container quando ele mesmo chama a API do Secrets Manager no código — que é um padrão diferente (leitura em runtime). Para injeção automática via Task Definition, a permissão deve estar no Execution Role.

3) **Solução imediata:** executar `aws ecs update-service --cluster producao --service minha-api --force-new-deployment`. Isso reinicia todas as tasks do Service, que ao iniciar buscam o secret atualizado (AWSCURRENT) do Secrets Manager e recebem a nova senha via injeção. As tasks antigas (com senha antiga) são gradualmente substituídas pelo rolling update. **Solução definitiva:** migrar da injeção por variável de ambiente para **leitura em runtime com cache TTL**. Em vez de injetar `DB_PASSWORD` como env var (valor fixo na inicialização), o código chama `secretsmanager.GetSecretValue()` diretamente, com cache de 5 minutos. Quando o secret é rotacionado, na próxima expiração do cache o código automaticamente obtém a nova senha — sem precisar reiniciar tasks. Isso requer adicionar `secretsmanager:GetSecretValue` ao **Task Role** (não ao Execution Role) para o ARN do secret específico.
