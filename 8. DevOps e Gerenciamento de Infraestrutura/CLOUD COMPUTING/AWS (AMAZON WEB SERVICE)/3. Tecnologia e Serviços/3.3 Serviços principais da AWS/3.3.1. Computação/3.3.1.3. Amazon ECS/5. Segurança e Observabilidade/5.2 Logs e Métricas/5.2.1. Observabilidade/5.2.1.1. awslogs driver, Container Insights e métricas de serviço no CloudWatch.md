### Observabilidade no ECS — awslogs, Container Insights e métricas de serviço

Sem observabilidade, um cluster ECS em produção é uma caixa preta. Você precisa saber o que os containers estão fazendo (logs), como estão consumindo recursos (métricas) e quando algo está errado (alertas). O ECS integra-se nativamente com CloudWatch para as três dimensões, com complexidade e custo progressivos conforme a profundidade necessária.

---

## Logging — awslogs driver

O driver `awslogs` é o mecanismo nativo de envio de logs de containers para o **CloudWatch Logs**. Cada linha de stdout/stderr do container vira um evento de log no CloudWatch.

### Configuração na Task Definition

```json
"logConfiguration": {
  "logDriver": "awslogs",
  "options": {
    "awslogs-group": "/ecs/minha-api",
    "awslogs-region": "us-east-1",
    "awslogs-stream-prefix": "api",
    "awslogs-create-group": "true",
    "awslogs-datetime-format": "%Y-%m-%dT%H:%M:%S",
    "mode": "non-blocking",
    "max-buffer-size": "4m"
  }
}
```

### Como os logs são organizados no CloudWatch

```
CloudWatch Log Group: /ecs/minha-api
  │
  ├── Log Stream: api/api/abc123-task-id-1   ← uma stream por task
  ├── Log Stream: api/api/def456-task-id-2
  └── Log Stream: api/api/ghi789-task-id-3

Formato do stream: {stream-prefix}/{container-name}/{task-id}
```

Cada task cria sua própria Log Stream — isso é fundamental para debugar problemas específicos de uma task vs comportamento geral do service.

### Parâmetros importantes

| Parâmetro | Valor | Impacto |
|---|---|---|
| `awslogs-create-group` | `true` | Cria o Log Group automaticamente se não existir |
| `mode` | `non-blocking` | Container não trava se CloudWatch estiver lento |
| `max-buffer-size` | `4m` | Buffer de 4 MB; logs descartados se buffer encher (non-blocking) |
| `awslogs-datetime-format` | formato strftime | Agrupamento de linhas multi-linha (stack traces) |

**`mode: non-blocking`** é crítico em produção: no modo padrão (`blocking`), se o CloudWatch Logs estiver com latência alta, o container trava aguardando o log ser enviado. Com `non-blocking`, logs são bufferizados e descartados se o buffer encher — melhor perder alguns logs do que deixar a aplicação travada.

### Configurando o Log Group com retenção

O CloudWatch Logs cobra por GB armazenado — sem retenção configurada, logs se acumulam indefinidamente:

```bash
# Criar Log Group com retenção de 30 dias
aws logs create-log-group \
  --log-group-name /ecs/minha-api

aws logs put-retention-policy \
  --log-group-name /ecs/minha-api \
  --retention-in-days 30

# Políticas de retenção disponíveis (dias):
# 1, 3, 5, 7, 14, 30, 60, 90, 120, 150, 180, 365, 400, 545, 731, 1827, 3653
```

### Consultando logs via CLI

```bash
# Ver logs recentes de todas as tasks de um service
aws logs filter-log-events \
  --log-group-name /ecs/minha-api \
  --start-time $(date -d '1 hour ago' +%s000) \
  --filter-pattern "ERROR" \
  --query 'events[*].{Time:timestamp,Message:message}' \
  --output table

# Ver logs de uma task específica
aws logs get-log-events \
  --log-group-name /ecs/minha-api \
  --log-stream-name "api/api/abc123-task-id-1" \
  --start-from-head

# CloudWatch Logs Insights — query SQL-like
aws logs start-query \
  --log-group-name /ecs/minha-api \
  --start-time $(date -d '1 hour ago' +%s) \
  --end-time $(date +%s) \
  --query-string '
    fields @timestamp, @message
    | filter @message like /ERROR/
    | stats count(*) as erros by bin(5m)
    | sort @timestamp desc
  '
```

## Outros log drivers disponíveis

`awslogs` não é o único driver — para pipelines de log mais sofisticados:

| Driver | Destino | Quando usar |
|---|---|---|
| `awslogs` | CloudWatch Logs | Padrão — simples e integrado |
| `awsfirelens` | Qualquer destino via Fluent Bit | Roteamento avançado, filtros, múltiplos destinos |
| `splunk` | Splunk Enterprise/Cloud | Empresas com Splunk já adotado |
| `json-file` | Disco local do host | Dev/debug local apenas |

### FireLens — roteamento avançado de logs

FireLens é um sidecar container que roda Fluent Bit ou Fluentd para processar e rotear logs:

```json
// Task Definition com FireLens
"containerDefinitions": [
  {
    "name": "log-router",
    "image": "amazon/aws-for-fluent-bit:stable",
    "essential": true,
    "firelensConfiguration": {
      "type": "fluentbit",
      "options": {"enable-ecs-log-metadata": "true"}
    }
  },
  {
    "name": "api",
    "image": "minha-api:v1",
    "logConfiguration": {
      "logDriver": "awsfirelens",
      "options": {
        "Name": "cloudwatch_logs",
        "region": "us-east-1",
        "log_group_name": "/ecs/minha-api",
        "log_stream_prefix": "api-",
        "auto_create_group": "true"
        // Pode rotear para S3, Kinesis, OpenSearch simultaneamente
      }
    }
  }
]
```

## Container Insights — métricas por task e container

**Container Insights** é uma feature do CloudWatch que coleta métricas detalhadas de performance em nível de cluster, service, task e container. É habilitada no nível do cluster:

```bash
# Habilitar Container Insights no cluster
aws ecs update-cluster \
  --cluster producao \
  --settings name=containerInsights,value=enabled

# Ou ao criar o cluster
aws ecs create-cluster \
  --cluster-name producao \
  --settings name=containerInsights,value=enabled
```

### Métricas disponíveis com Container Insights

```
Hierarquia de métricas no Container Insights:

Nível CLUSTER:
  CpuUtilized / CpuReserved / CpuUtilization (%)
  MemoryUtilized / MemoryReserved / MemoryUtilization (%)
  NetworkRxBytes / NetworkTxBytes
  StorageReadBytes / StorageWriteBytes

Nível SERVICE:
  CpuUtilized / MemoryUtilized
  DesiredTaskCount / RunningTaskCount / PendingTaskCount

Nível TASK:
  CpuUtilized / MemoryUtilized
  NetworkRxBytes / NetworkTxBytes (awsvpc mode)
  EphemeralStorageUtilized (Fargate)

Nível CONTAINER:
  CpuUtilized / MemoryUtilized (por container individual)
  → Útil para identificar qual sidecar está consumindo recursos
```

### Consultando métricas via CloudWatch

```bash
# CPU utilization do Service nos últimos 60 minutos
aws cloudwatch get-metric-statistics \
  --namespace ECS/ContainerInsights \
  --metric-name CpuUtilized \
  --dimensions \
    Name=ClusterName,Value=producao \
    Name=ServiceName,Value=minha-api \
  --start-time $(date -d '1 hour ago' -Iseconds) \
  --end-time $(date -Iseconds) \
  --period 300 \
  --statistics Average \
  --query 'Datapoints[*].{Time:Timestamp,CPU:Average}' \
  --output table
```

### Custo do Container Insights

Container Insights gera métricas customizadas no CloudWatch, que têm custo:

```
Custo aproximado:
  $0.30 por métrica por mês (primeiras 10.000 métricas)
  
  Cluster com 10 services, 50 tasks, 100 containers:
  → ~500-1000 séries de métricas ativas
  → ~$150-300/mês adicionais no CloudWatch

Quando vale o custo:
  ✓ Produção com SLA — diagnóstico rápido de problemas
  ✓ Auto Scaling baseado em métricas de memória
  ✓ Capacity planning com dados históricos

Quando economizar:
  ✗ Ambientes dev/staging — desabilitar Container Insights
  ✗ Clusters pequenos com poucas tasks
```

## Métricas nativas do ECS (sem Container Insights)

Mesmo sem Container Insights, o ECS publica métricas básicas no CloudWatch **gratuitamente**:

```
Namespace: AWS/ECS
Dimensões: ClusterName, ServiceName

Métricas disponíveis:
  CPUUtilization     — % de CPU reservada que está sendo usada
  MemoryUtilization  — % de memória reservada que está sendo usada

Limitação: apenas % de utilização, sem valores absolutos.
Não há métricas por task ou container individual.
```

Essas métricas são suficientes para **Auto Scaling básico** (manter CPU em 70%) mas insuficientes para diagnóstico detalhado.

## CloudWatch Alarms — alertas baseados em métricas

```bash
# Alarme: CPU do Service acima de 85% por 5 minutos
aws cloudwatch put-metric-alarm \
  --alarm-name "ecs-minha-api-cpu-alto" \
  --alarm-description "CPU do service minha-api acima de 85%" \
  --namespace AWS/ECS \
  --metric-name CPUUtilization \
  --dimensions Name=ClusterName,Value=producao Name=ServiceName,Value=minha-api \
  --statistic Average \
  --period 300 \
  --threshold 85 \
  --comparison-operator GreaterThanThreshold \
  --evaluation-periods 1 \
  --alarm-actions arn:aws:sns:us-east-1:123:alertas-producao \
  --ok-actions arn:aws:sns:us-east-1:123:alertas-producao

# Alarme: tasks em estado Pending (possível falta de capacidade)
aws cloudwatch put-metric-alarm \
  --alarm-name "ecs-minha-api-tasks-pendentes" \
  --namespace ECS/ContainerInsights \
  --metric-name PendingTaskCount \
  --dimensions Name=ClusterName,Value=producao Name=ServiceName,Value=minha-api \
  --statistic Maximum \
  --period 60 \
  --threshold 0 \
  --comparison-operator GreaterThanThreshold \
  --evaluation-periods 3 \
  --alarm-actions arn:aws:sns:us-east-1:123:alertas-producao
```

## Erros comuns e armadilhas

**Não configurar retenção no Log Group:** sem retenção, logs se acumulam indefinidamente. Um service com 1 GB/dia de logs sem retenção custa ~$0.50/GB/mês de armazenamento acumulado. Defina retenção de 7-30 dias para logs de aplicação e 90+ dias para logs de auditoria.

**Usar `mode: blocking` (padrão) em produção:** se o CloudWatch Logs tiver instabilidade, containers bloqueiam aguardando o envio de logs. Use sempre `mode: non-blocking` em produção.

**Container Insights em todos os ambientes:** pagar por Container Insights em dev e staging adiciona custo sem benefício operacional. Habilite apenas em produção e ambientes de staging críticos.

**Não usar CloudWatch Logs Insights:** muitos times ficam com `filter-log-events` para queries simples mas não exploram o Logs Insights para análise de tendências, correlação de erros e queries agregadas — que são muito mais poderosas e rápidas em grandes volumes de log.

## 🧩 Quiz de Fixação

1. Uma aplicação Python no ECS gera stack traces de 15 linhas quando há exceções. No CloudWatch Logs, cada linha aparece como um evento separado, dificultando a leitura. Como resolver?

2. Um Service ECS tem Container Insights habilitado. O time observa que `MemoryUtilization` está em 95% consistentemente, mas não sabe qual container dentro da task está consumindo mais memória. Como identificar?

3. O time quer criar um alarme que dispara quando tasks ficam no estado `PENDING` por mais de 3 minutos seguidos — indicando falta de capacidade no cluster. Qual métrica usar, qual threshold e quantos evaluation periods configurar?

**Respostas:**

1) Configurar o parâmetro `awslogs-datetime-format` no log driver para corresponder ao formato de timestamp dos logs da aplicação. Quando o CloudWatch Logs identifica que uma linha não começa com um novo timestamp (formato configurado), ela é agrupada à linha anterior como continuação do mesmo evento. Por exemplo, para logs Python com formato `2024-01-15 10:30:00`: `"awslogs-datetime-format": "%Y-%m-%d %H:%M:%S"`. Linhas do stack trace (que não começam com timestamp) serão agrupadas ao evento original. Alternativa mais robusta: usar **FireLens com Fluent Bit** e o parser `multiline`, que oferece controle mais fino sobre o agrupamento de linhas multi-linha com regex customizado.

2) Container Insights coleta métricas no nível de **container individual** dentro de cada task. No CloudWatch, navegar para: **CloudWatch → Container Insights → View performance dashboards → ECS Containers**. Filtrar pelo ClusterName e ServiceName, e a visão de container mostra `MemoryUtilized` separadamente por container (ex: `api`, `log-router`, `envoy-proxy`). Via CLI: `aws cloudwatch get-metric-statistics --namespace ECS/ContainerInsights --metric-name MemoryUtilized --dimensions Name=ClusterName,Value=producao Name=ServiceName,Value=minha-api Name=ContainerName,Value=api`. Comparar `MemoryUtilized` de cada container para identificar o consumidor. Se o sidecar `log-router` estiver consumindo 60% da memória da task, pode estar com buffer acumulado por falha no destino de log.

3) Usar a métrica `PendingTaskCount` do namespace `ECS/ContainerInsights`, dimensionada por `ClusterName` e `ServiceName`. Threshold: `> 0` (qualquer task pendente é um sinal). Para "3 minutos seguidos": com `period = 60` segundos (1 minuto por evaluation period) e `evaluation-periods = 3`, o alarme dispara após 3 pontos consecutivos com `PendingTaskCount > 0` — ou seja, 3 minutos seguidos com tasks pendentes. Usar `statistic = Maximum` (não Average) — se o máximo no período for > 0, há tasks pendentes; a média poderia mascarar picos curtos. A action do alarme deve notificar o time E triggerar um scale-out do ASG se for EC2 Launch Type, ou simplesmente alertar se for Fargate (onde a capacidade escala automaticamente mas pode estar demorando mais que o esperado).
