### EC2 Launch Type — controle de infraestrutura, AMIs otimizadas e quando usar

No EC2 Launch Type, você provisiona e gerencia instâncias EC2 que atuam como **nós de computação** do cluster ECS. O ECS Agent — um processo que roda em cada instância — comunica-se com o plano de controle do ECS para receber instruções de onde colocar tasks, reportar saúde e gerenciar o ciclo de vida dos containers. Você tem controle total sobre o hardware, mas também toda a responsabilidade de gerenciar os servidores.

---

## Arquitetura do EC2 Launch Type

```
EC2 Launch Type — visão geral:

┌─────────────────────────────────────────────────────────────┐
│                    Cluster ECS                              │
│                                                             │
│  ┌──────────────────┐  ┌──────────────────┐                │
│  │   EC2 i-001      │  │   EC2 i-002      │                │
│  │   (ECS-optimized │  │   (ECS-optimized │                │
│  │    AMI)          │  │    AMI)          │                │
│  │                  │  │                  │                │
│  │  ┌────────────┐  │  │  ┌────────────┐  │                │
│  │  │ ECS Agent  │  │  │  │ ECS Agent  │  │  ← processo    │
│  │  └────────────┘  │  │  └────────────┘  │    em cada nó  │
│  │  ┌───┐ ┌───┐     │  │  ┌───┐ ┌───┐    │                │
│  │  │ C1│ │ C2│     │  │  │ C3│ │ C4│    │  ← containers  │
│  │  └───┘ └───┘     │  │  └───┘ └───┘    │                │
│  └──────────────────┘  └──────────────────┘                │
└─────────────────────────────────────────────────────────────┘
           ▲                        ▲
           │  ECS Agent reporta     │
           └────────────────────────┘
                para o ECS Control Plane
                (gerenciado pela AWS)
```

O **ECS Control Plane** (plano de controle) é gerenciado inteiramente pela AWS — você não instala nem opera. Você é responsável pelos **nós EC2** (o plano de dados).

## ECS-Optimized AMI

A AWS mantém AMIs pré-configuradas especificamente para rodar como nós ECS. Usar a ECS-Optimized AMI é fortemente recomendado sobre configurar uma instância manualmente.

### O que a ECS-Optimized AMI inclui

```
ECS-Optimized AMI (baseada em Amazon Linux 2023):
  ├── ECS Agent (versão mais recente)
  ├── Docker daemon configurado e otimizado
  ├── containerd (runtime de container)
  ├── SSM Agent (para acesso via Systems Manager)
  ├── CloudWatch Agent (para métricas do host)
  └── Kernel com patches de segurança aplicados
      (atualizado regularmente pela AWS)
```

### Registrar instâncias no cluster

Ao iniciar uma instância com a ECS-Optimized AMI, basta incluir no User Data o nome do cluster:

```bash
#!/bin/bash
# User Data da instância EC2
echo ECS_CLUSTER=meu-cluster >> /etc/ecs/ecs.config

# Configurações opcionais úteis:
echo ECS_ENABLE_CONTAINER_METADATA=true >> /etc/ecs/ecs.config
echo ECS_AVAILABLE_LOGGING_DRIVERS='["json-file","awslogs","splunk"]' >> /etc/ecs/ecs.config
echo ECS_RESERVED_MEMORY=256 >> /etc/ecs/ecs.config
# ^ reserva 256 MiB do host para o SO — não aloca para containers
```

### Variantes da ECS-Optimized AMI

| AMI | Base | Arquitetura | Quando usar |
|---|---|---|---|
| `Amazon ECS-optimized Amazon Linux 2023` | AL2023 | x86_64 / ARM64 | Padrão recomendado |
| `Amazon ECS-optimized Amazon Linux 2023 (GPU)` | AL2023 + NVIDIA drivers | x86_64 | Workloads com GPU (P/G instances) |
| `Amazon ECS-optimized Bottlerocket` | Bottlerocket OS | x86_64 / ARM64 | Segurança máxima, SO mínimo |
| `Amazon ECS-optimized Windows Server` | Windows Server 2019/2022 | x86_64 | Containers Windows |

**Bottlerocket** merece destaque: é um SO Linux da AWS projetado exclusivamente para containers — superfície de ataque mínima (sem gerenciador de pacotes, sem shell interativo por padrão), atualizações atômicas e rollback de SO automático.

## Auto Scaling de nós EC2

Com EC2 Launch Type, você gerencia a capacidade dos nós. A forma recomendada é usar **ECS Capacity Providers** com Auto Scaling Groups:

```
ECS Capacity Provider + ASG:

ECS Service precisa de mais tasks
    │
    ▼
ECS Capacity Provider detecta falta de capacidade
    │
    ▼
Aumenta o desired count do Auto Scaling Group
    │
    ▼
Nova instância EC2 é lançada (com ECS-Optimized AMI)
    │
    ▼
ECS Agent registra a instância no cluster
    │
    ▼
Task é alocada na nova instância
```

```bash
# Criar Capacity Provider com Managed Scaling
aws ecs create-capacity-provider \
  --name "meu-capacity-provider" \
  --auto-scaling-group-provider '{
    "autoScalingGroupArn": "arn:aws:autoscaling:...:autoScalingGroup:...",
    "managedScaling": {
      "status": "ENABLED",
      "targetCapacity": 80,
      "minimumScalingStepSize": 1,
      "maximumScalingStepSize": 10
    },
    "managedTerminationProtection": "ENABLED"
  }'
```

`targetCapacity: 80` significa que o ECS mantém o cluster com 80% de utilização — sempre há 20% de capacidade livre para absorver novos containers sem esperar por uma nova instância.

`managedTerminationProtection: ENABLED` protege instâncias com tasks rodando de serem terminadas pelo ASG durante scale-in — o ECS drena as tasks primeiro.

## Alocação de tasks nos nós — o scheduler do ECS

O ECS scheduler decide em qual instância colocar cada nova task baseado em:

```
Estratégias de placement disponíveis:

binpack (recomendado para economia):
  Preenche uma instância ao máximo antes de usar a próxima
  → Minimiza número de instâncias em uso
  → Reduz custo (instâncias subutilizadas podem ser terminadas)

spread (recomendado para disponibilidade):
  Distribui tasks igualmente entre instâncias/AZs
  → Falha de uma instância afeta menos tasks
  → Usado com: "field": "attribute:ecs.availability-zone"

random:
  Aloca aleatoriamente
  → Simples, sem otimização específica
```

```json
// Placement strategy no Service — binpack + spread por AZ
{
  "placementStrategy": [
    {"type": "spread", "field": "attribute:ecs.availability-zone"},
    {"type": "binpack", "field": "memory"}
  ]
}
```

Essa combinação distribui tasks entre AZs (alta disponibilidade) e dentro de cada AZ preenche as instâncias ao máximo (economia).

## Visibilidade e controle que o EC2 Launch Type oferece

Em comparação com Fargate, o EC2 Launch Type dá acesso direto à instância:

```bash
# Acessar instância ECS via SSM Session Manager (sem chave SSH)
aws ssm start-session --target i-0abc123def456

# Dentro da instância: ver containers rodando
docker ps

# Ver tasks registradas no ECS Agent
curl http://localhost:51678/v1/tasks

# Ver logs do ECS Agent
sudo journalctl -u ecs -f

# Inspecionar uso de recursos dos containers
docker stats
```

Esse nível de acesso é fundamental para debugging de problemas que não aparecem nos logs do CloudWatch — problemas de rede no host, contenção de recursos entre containers, issues de disco.

## Quando usar EC2 Launch Type vs Fargate

```
Use EC2 Launch Type quando:

✓ Workloads que requerem GPU (instâncias P/G — Fargate não suporta GPU)
✓ Containers Windows (Fargate Windows tem limitações significativas)
✓ Acesso direto ao host é necessário (debugging, agentes de segurança)
✓ Instâncias Spot para reduzir custo (Fargate Spot existe mas é mais limitado)
✓ Workloads com perfil de uso previsível e alto — Reserved Instances no EC2
   são mais baratas que Fargate em uso contínuo
✓ Requisitos de hardware específicos (NVMe local, rede de alta banda)
✓ Containers com muito /tmp ou armazenamento efêmero (> 200 GiB)
✓ Compliance que exige Dedicated Hosts (Fargate não suporta)

Use Fargate quando:
✓ Simplicidade operacional é prioridade
✓ Workloads variáveis ou imprevisíveis
✓ Time pequeno sem especialista em infraestrutura
✓ Isolamento de container-por-microVM é desejado
(coberto no arquivo 2.1.1.2)
```

## Custo: EC2 vs Fargate para uso contínuo

```
Comparativo para workload 24/7 (2 vCPU, 4 GiB por task, 10 tasks):

EC2 (m7g.large — 2 vCPU, 8 GiB):
  Cabe ~2 tasks por instância → 5 instâncias necessárias
  On-Demand: 5 × $0.0816/h × 720h = $293/mês
  Reserved 1yr: 5 × ~$0.051/h × 720h = $184/mês

Fargate (2 vCPU, 4 GiB por task × 10 tasks):
  vCPU: 10 × 2 × $0.04048/vCPU-h × 720h = $583/mês
  Memória: 10 × 4 × $0.004445/GB-h × 720h = $128/mês
  Total Fargate: ~$711/mês

Conclusão para uso 24/7:
  EC2 On-Demand: $293/mês
  EC2 Reserved:  $184/mês  ← mais barato
  Fargate:       $711/mês  ← 2-4x mais caro

Para uso 24/7 de longa duração → EC2 com Reserved é mais econômico.
Fargate compensa quando: tráfego variável, sem compromisso de reserva,
ou quando o custo operacional de gerenciar EC2 é maior que a diferença.
```

## Erros comuns e armadilhas

**Não usar Capacity Providers:** sem Capacity Providers, o cluster não escala automaticamente os nós EC2. Tasks ficam pendentes (`PENDING`) esperando por capacidade que nunca chega. Sempre associe um ASG com Managed Scaling ao cluster.

**ECS_RESERVED_MEMORY não configurado:** sem reservar memória para o SO, o ECS pode alocar toda a RAM da instância para containers, causando OOM (Out of Memory) no host e instabilidade.

**Usar a mesma instância para múltiplas famílias de workload:** misturar containers CPU-bound e memory-bound na mesma instância cria contenção de recursos. Separe com placement constraints.

**Não habilitar `managedTerminationProtection`:** sem proteção, o ASG pode terminar instâncias com tasks rodando durante scale-in, causando falhas abruptas em vez de drain ordenado.

## 🧩 Quiz de Fixação

1. Um cluster ECS com EC2 Launch Type tem 3 instâncias `m7g.large` (2 vCPU, 8 GiB cada). O Service tenta lançar uma task que requer 4 vCPU e 6 GiB. O que acontece e como resolver?

2. Por que `managedTerminationProtection` é essencial quando se usa Capacity Providers com Managed Scaling, e o que acontece sem ele durante um evento de scale-in?

3. Uma empresa roda 20 tasks ECS 24/7 em Fargate (cada uma com 1 vCPU e 2 GiB). O FinOps detecta que o custo mensal está muito alto. Como calcular se migrar para EC2 Launch Type com Reserved Instances geraria economia, e quais fatores operacionais precisam ser considerados na decisão?

**Respostas:**

1) A task fica no estado **PENDING** indefinidamente — nenhuma das 3 instâncias tem 4 vCPU livres (cada `m7g.large` tem apenas 2 vCPU total). O ECS scheduler não pode fragmentar uma task entre instâncias. **Resolução:** (a) usar uma instância maior como nó (ex: `m7g.xlarge` com 4 vCPU) — adicionar ao ASG e deixar o Capacity Provider lançar; (b) redesenhar a Task Definition para usar menos CPU (se o workload permite); (c) adicionar uma placement constraint que direciona essa task para instâncias de família diferente com mais recursos.

2) Sem `managedTerminationProtection`, quando o Capacity Provider decide fazer scale-in (reduzir instâncias por baixo uso), o ASG pode selecionar e terminar qualquer instância imediatamente — incluindo instâncias com tasks rodando ativamente. O resultado é containers mortos abruptamente, requisições em andamento interrompidas e potencial perda de estado. Com `managedTerminationProtection: ENABLED`, o ECS marca instâncias com tasks rodando como protegidas contra terminação. O Capacity Provider primeiro **drena** a instância (move as tasks para outros nós via ECS Service Drain), aguarda confirmação de que todas as tasks foram realocadas, remove a proteção e só então permite que o ASG termine a instância — processo ordenado e sem impacto nos usuários.

3) **Cálculo:**
- Fargate atual: 20 tasks × (1 vCPU × $0.04048 + 2 GiB × $0.004445) × 720h = 20 × ($29.15 + $6.40) = **$711/mês**
- EC2 necessário: cada `m7g.large` (2 vCPU, 8 GiB) acomoda ~2 tasks (1 vCPU + 2 GiB cada) → 10 instâncias. Reserved 1yr: ~$0.051/h × 10 × 720h = **$367/mês**
- Economia potencial: ~$344/mês (~48% de redução)

**Fatores operacionais a considerar:** (1) custo de engenharia para configurar e manter ASG, Capacity Providers, patches de AMI e monitoramento de nós — se esse custo for > $344/mês em horas de engenheiro, a migração não compensa; (2) o time precisa de expertise para gerenciar EC2 (rotação de AMI, gestão de patches, debugging de host); (3) o compromisso de 1 ano da Reserved Instance — se o workload for reduzido, paga-se pela capacidade ociosa; (4) Fargate tem custo zero de operação de infraestrutura — o diferencial de preço é o "custo do gerenciamento terceirizado".
