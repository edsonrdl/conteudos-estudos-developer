### AWS Fargate — serverless para containers, cobrança por vCPU/memória e quando preferir

Fargate é o launch type serverless do ECS (e também do EKS): você define a Task Definition com CPU e memória necessários, e a AWS provisiona, gerencia e escala a infraestrutura subjacente automaticamente. Não existem instâncias EC2 para configurar, AMIs para atualizar, ou nós para monitorar — o contrato é simples: você cuida do container, a AWS cuida do servidor onde ele roda.

---

## Como Fargate funciona internamente

Por baixo dos panos, cada task Fargate roda em sua própria **microVM isolada**, usando a mesma tecnologia Firecracker do Lambda. Isso tem duas implicações importantes:

```
Isolamento no Fargate:

EC2 Launch Type:           Fargate:
┌──────────────────┐       ┌──────────────────────────────────┐
│   EC2 Host       │       │  Task A (microVM isolada)        │
│  ┌────┐ ┌────┐   │       │  ┌──────────────────────────┐    │
│  │ C1 │ │ C2 │   │       │  │ Container 1 | Container 2│    │
│  └────┘ └────┘   │       │  └──────────────────────────┘    │
│  ┌────┐ ┌────┐   │       └──────────────────────────────────┘
│  │ C3 │ │ C4 │   │
│  └────┘ └────┘   │       ┌──────────────────────────────────┐
└──────────────────┘       │  Task B (microVM isolada)        │
Containers compartilham    │  ┌──────────────────────────┐    │
o kernel do host           │  │ Container 3 | Container 4│    │
                           │  └──────────────────────────┘    │
                           └──────────────────────────────────┘
                           Cada task tem seu próprio kernel
                           → isolamento mais forte por padrão
```

**Consequência prática:** no Fargate, não há "host compartilhado" entre tasks de clientes diferentes. Cada task é sua própria VM — mais seguro, mas você perde o acesso ao host (o que às vezes é necessário em EC2 Launch Type).

## Configuração de CPU e memória no Fargate

Fargate não permite qualquer combinação de CPU e memória — você escolhe de uma **matriz de combinações válidas**:

```
Combinações válidas de CPU e memória no Fargate:

CPU (vCPU) │ Memória disponível
───────────┼────────────────────────────────────────────
0.25 vCPU  │ 0.5, 1, 2 GiB
0.5 vCPU   │ 1, 2, 3, 4 GiB
1 vCPU     │ 2, 3, 4, 5, 6, 7, 8 GiB
2 vCPU     │ 4–16 GiB (em incrementos de 1 GiB)
4 vCPU     │ 8–30 GiB (em incrementos de 1 GiB)
8 vCPU     │ 16–60 GiB (em incrementos de 4 GiB)
16 vCPU    │ 32–120 GiB (em incrementos de 4 GiB)
```

Na Task Definition, CPU é especificada em **unidades** (1 vCPU = 1024 unidades) e memória em **MiB**:

```json
{
  "family": "minha-api",
  "networkMode": "awsvpc",
  "requiresCompatibilities": ["FARGATE"],
  "cpu": "1024",     // 1 vCPU
  "memory": "2048",  // 2 GiB
  "containerDefinitions": [
    {
      "name": "api",
      "image": "123.ecr.../minha-api:v1.0",
      "cpu": 512,     // 0.5 vCPU do total — reserva soft
      "memory": 1024, // hard limit: container é morto se ultrapassar
      "memoryReservation": 768, // soft limit: usado para scheduling
      "portMappings": [{"containerPort": 8080, "protocol": "tcp"}]
    }
  ]
}
```

**`memory` (hard limit) vs `memoryReservation` (soft limit):**
- `memory`: se o container ultrapassar esse valor, é morto com OOM
- `memoryReservation`: valor usado pelo scheduler para decidir onde colocar a task — o container pode usar mais se o host tiver disponível (irrelevante no Fargate, onde cada task tem recursos dedicados)

## Modelo de cobrança do Fargate

Fargate cobra por **vCPU-hora** e **GB-hora** alocados à task, com granularidade de 1 segundo (mínimo de 1 minuto):

| Recurso | Preço (us-east-1, Linux) |
|---|---|
| vCPU | $0.04048 por vCPU-hora |
| Memória | $0.004445 por GB-hora |

```
Exemplos de custo Fargate:

Task de API (1 vCPU, 2 GiB, 24/7):
  vCPU:   1 × $0.04048 × 720h = $29.15/mês
  Memória: 2 × $0.004445 × 720h = $6.40/mês
  Total: $35.55/mês por task

Task de worker assíncrono (0.25 vCPU, 0.5 GiB, 24/7):
  vCPU:   0.25 × $0.04048 × 720h = $7.29/mês
  Memória: 0.5 × $0.004445 × 720h = $1.60/mês
  Total: $8.89/mês por task

Task de processamento batch (4 vCPU, 8 GiB, 2h/dia):
  vCPU:   4 × $0.04048 × 60h = $9.72/mês
  Memória: 8 × $0.004445 × 60h = $2.13/mês
  Total: $11.85/mês (vs $71/mês se rodasse 24/7)
```

### Fargate Spot

Assim como EC2 Spot, **Fargate Spot** usa capacidade ociosa com desconto de até 70%. Tasks podem ser interrompidas com 2 minutos de aviso:

```bash
# Configurar Capacity Provider com Fargate Spot
aws ecs create-capacity-provider \
  --name FARGATE_SPOT \  # nome reservado pela AWS

# Service com mix Fargate + Fargate Spot
aws ecs create-service \
  --cluster meu-cluster \
  --service-name minha-api \
  --task-definition minha-api:3 \
  --desired-count 10 \
  --capacity-provider-strategy '[
    {"capacityProvider": "FARGATE",      "weight": 2, "base": 2},
    {"capacityProvider": "FARGATE_SPOT", "weight": 8}
  ]'
# base: 2 = mínimo de 2 tasks em Fargate On-Demand (garantidas)
# weight: para cada 2 tasks On-Demand, 8 tasks Spot (80% Spot)
```

Para workloads tolerantes a interrupção (workers SQS, batch jobs), Fargate Spot reduz custo significativamente.

## Armazenamento efêmero no Fargate

Por padrão, cada task Fargate tem **20 GiB de armazenamento efêmero** no sistema de arquivos do container. Esse armazenamento é perdido quando a task encerra.

Para workloads que precisam de mais espaço temporário, é possível aumentar até **200 GiB** por task:

```json
{
  "family": "processamento-video",
  "requiresCompatibilities": ["FARGATE"],
  "cpu": "4096",
  "memory": "8192",
  "ephemeralStorage": {
    "sizeInGiB": 100
  }
}
```

Para persistência real (dados que sobrevivem ao ciclo de vida da task), use **Amazon EFS** montado na task.

## Fargate com ARM64 (Graviton)

Assim como no EC2, Fargate suporta arquitetura ARM64 (AWS Graviton2/3), com ~20% de redução de custo para o mesmo desempenho:

```json
{
  "family": "minha-api-graviton",
  "requiresCompatibilities": ["FARGATE"],
  "cpu": "1024",
  "memory": "2048",
  "runtimePlatform": {
    "cpuArchitecture": "ARM64",
    "operatingSystemFamily": "LINUX"
  }
}
```

**Pré-requisito:** a imagem Docker deve ser buildada para `linux/arm64`. Para suportar ambas as arquiteturas, use multi-arch builds:

```bash
# Build multi-arch (x86_64 + ARM64) e push para ECR
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  -t 123.ecr.../minha-api:v1.0 \
  --push .
```

## O que o Fargate gerencia (e você não precisa)

```
Responsabilidades no Fargate vs EC2 Launch Type:

                        Fargate    EC2 Launch Type
─────────────────────────────────────────────────
Provisionar instâncias    AWS           Você
Atualizar AMI/SO          AWS           Você
Escalar nós               AWS           Você (via ASG)
Monitorar saúde dos nós   AWS           Você
Patches de segurança      AWS           Você
ECS Agent                 AWS           AWS (mas na sua VM)
Kubernetes/ECS Agent      AWS           AWS

Containers (código)       Você          Você
Task Definition           Você          Você
IAM roles das tasks       Você          Você
Networking (VPC, SG)      Você          Você
Logs e métricas           Você          Você
```

O trade-off é claro: Fargate remove toda a responsabilidade de infraestrutura, mas também remove todo o controle e visibilidade sobre os nós.

## Limitações do Fargate

| Limitação | Detalhes |
|---|---|
| Sem acesso ao host | Não é possível fazer `docker exec` no host ou instalar agentes no SO |
| Sem suporte a GPU | Instâncias GPU (P/G) não estão disponíveis no Fargate |
| Sem Dedicated Hosts | Não compatível com Dedicated Hosts (mas tem isolamento de microVM) |
| Sem Instance Store | Apenas armazenamento efêmero limitado (20–200 GiB) |
| Containers Windows | Funciona, mas com conjunto de recursos menor que Linux |
| Rede — apenas awsvpc | Fargate só suporta o network mode `awsvpc` |

## Quando preferir Fargate

```
Prefira Fargate quando:

✓ Time pequeno ou sem especialista em infraestrutura
  → Elimina toda operação de nós EC2

✓ Workloads variáveis ou imprevisíveis
  → Paga exatamente pelo que usa, sem capacidade ociosa

✓ Microserviços com ciclos de vida curtos
  → Tasks que sobem e descem frequentemente

✓ Ambientes de desenvolvimento e staging
  → Sem custo fixo de instâncias EC2 ociosas à noite

✓ Isolamento de segurança por task
  → Cada task em microVM separada, sem compartilhar kernel

✓ Adoção rápida — sem setup de infraestrutura
  → Cluster rodando em minutos

✓ Jobs batch esporádicos
  → Paga apenas durante a execução do job
```

## 🧩 Quiz de Fixação

1. Uma task Fargate tem `cpu: 512` (0.5 vCPU) e `memory: 1024` (1 GiB) e roda por exatamente 45 segundos. Qual é o custo dessa execução única?

2. Por que Fargate oferece isolamento de segurança superior ao EC2 Launch Type por padrão, e em qual cenário de compliance isso seria um argumento decisivo para escolher Fargate?

3. Um time tem 50 tasks Fargate rodando 24/7 para um serviço de produção estável há 18 meses, sem variação de volume. O FinOps aponta o custo como alto. Quais são as duas otimizações possíveis dentro do próprio Fargate (sem migrar para EC2), e qual seria o limite dessas otimizações?

**Respostas:**

1) Fargate cobra com mínimo de 1 minuto — os 45 segundos são arredondados para 60 segundos:
- vCPU: 0.5 × $0.04048 × (60/3600)h = 0.5 × $0.04048 × 0.01667 = **$0.000337**
- Memória: 1 × $0.004445 × (60/3600)h = 1 × $0.004445 × 0.01667 = **$0.0000741**
- **Total: ~$0.000411 por execução** (menos de meio centavo de dólar)

Para contexto: 1 milhão dessas execuções custaria ~$411 — comparável ao modelo Lambda para workloads de curta duração.

2) No EC2 Launch Type, múltiplos containers de diferentes tasks compartilham o **mesmo kernel Linux** do host EC2. Vulnerabilidades de kernel (como escapes de container) podem teoricamente permitir que um container acesse recursos de outro no mesmo host. No Fargate, cada task tem seu **próprio kernel em uma microVM Firecracker isolada** — mesmo que um container seja comprometido e consiga um "escape", ele estaria dentro de uma VM isolada sem acesso ao kernel dos outros clientes. O cenário de compliance decisivo seria **PCI DSS** (processamento de cartões de crédito) ou **HIPAA** (dados de saúde): ambos exigem isolamento de workloads sensíveis. Fargate permite demonstrar aos auditores que tasks que processam dados de cartão ou PHI (Protected Health Information) rodam em ambientes isolados por hardware, sem possibilidade de contaminação lateral de outros workloads.

3) **Otimização 1 — Migrar para ARM64 (Graviton):** recompilando a imagem Docker para `linux/arm64` e alterando a Task Definition para `cpuArchitecture: ARM64`, o custo do Fargate cai ~20% com o mesmo desempenho computacional. Para 50 tasks 24/7, isso representa economia imediata sem nenhuma mudança operacional após o build da imagem. **Otimização 2 — Lambda Power Tuning equivalente (right-sizing):** revisar se as tasks estão super-provisionadas. Se tasks com 2 GiB de memória alocada usam consistentemente apenas 600 MiB, reduzir para 1 GiB reduz a fatura de memória em 50%. Ferramentas como Container Insights e CloudWatch métricas de `MemoryUtilized` permitem identificar o headroom real. **Limite dessas otimizações:** para workloads 100% estáveis de longa duração, o teto das otimizações no Fargate é ~40-50% de redução (Graviton + right-sizing). Acima disso, a única forma de economizar mais é migrar para EC2 Launch Type com Reserved Instances — que para 50 tasks rodando 24/7 há 18 meses é claramente um candidato forte, com potencial de economia de 50-60% adicional.
