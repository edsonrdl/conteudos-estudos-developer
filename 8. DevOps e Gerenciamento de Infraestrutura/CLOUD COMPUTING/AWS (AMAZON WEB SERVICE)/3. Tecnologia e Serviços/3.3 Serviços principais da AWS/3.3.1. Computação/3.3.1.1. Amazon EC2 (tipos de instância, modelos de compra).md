### Amazon EC2 — o serviço de computação fundamental da AWS

Amazon Elastic Compute Cloud (EC2) é o serviço que fornece capacidade de computação escalável na nuvem — essencialmente, servidores virtuais que você provisiona, configura e gerencia. É a base de grande parte da infraestrutura AWS: desde simples servidores web até workloads de machine learning com GPU. Entender as famílias de instâncias e os modelos de preço é fundamental para fazer escolhas técnicas e financeiras corretas.

---

## Famílias de instâncias EC2

```
EC2 organiza instâncias em famílias por perfil de recursos:

Nomenclatura: [família][geração][processador/feature].[tamanho]
  m6g.xlarge:
  ├── m: propósito geral (general purpose)
  ├── 6: geração 6
  ├── g: Graviton (ARM da AWS)
  └── xlarge: 4 vCPU, 16GB RAM

Sufixos especiais:
  a: AMD EPYC processor
  g: AWS Graviton (ARM)
  i: Intel Ice Lake
  n: rede aprimorada
  d: NVMe storage local
  b: storage block optimized
  z: alta frequência de CPU
  e: extra memory
```

### Propósito Geral (T, M)

```
Equilíbrio entre CPU, memória e rede:

Família T (Burstable):
  t3.micro, t3.small, t3.medium, t3.large, t3.xlarge...
  
  Conceito de CPU Credits:
  → Instância acumula créditos quando CPU < baseline
  → Usa créditos quando CPU > baseline (burst)
  → Baseline: 20% CPU para t3.small
  → Burst: até 100% (enquanto tem créditos)
  
  Ideal para:
  ├── Servidores de desenvolvimento
  ├── Bancos de dados de baixo uso
  ├── Microsserviços com carga irregular
  └── Qualquer workload com CPU intermitente
  
  EVITAR para:
  ├── Workloads com CPU constante > baseline
  ├── Produção crítica que não tolera throttling de CPU
  
  t3a.medium vs t3.medium:
  t3.medium (Intel): $0.0416/hora
  t3a.medium (AMD): $0.0376/hora (10% mais barato, mesma performance)

Família M (Propósito Geral Balanceado):
  m6g.large, m6i.xlarge, m7g.2xlarge...
  
  CPU sustentada (sem burst limits)
  Ratio: ~4GB RAM por vCPU
  
  Ideal para:
  ├── Web servers de produção
  ├── Backends de aplicação
  ├── Bancos de dados pequenos/médios
  └── Cargas de trabalho genéricas de produção
  
  m6g (Graviton) vs m6i (Intel):
  m6g.xlarge: $0.154/hora
  m6i.xlarge: $0.192/hora
  → Graviton é ~20% mais barato, mesma performance ou melhor
  → Requer: SO Linux 64-bit ARM, software compatível com ARM
```

### Compute Optimized (C)

```
Alto ratio CPU:RAM para workloads CPU-intensivos:

c6g.large, c6i.xlarge, c7g.2xlarge...
  Ratio: ~2GB RAM por vCPU (mais CPU, menos RAM)

Ideal para:
  ├── Processamento batch de alto CPU
  ├── Media transcoding (encode de vídeo)
  ├── Servidores de jogo de alta performance
  ├── Machine Learning inference
  ├── Web servers de alto tráfego CPU-bound
  └── Processamento científico

Comparação:
  m6i.xlarge: 4 vCPU, 16GB RAM = $0.192/hora
  c6i.xlarge: 4 vCPU,  8GB RAM = $0.17/hora (10% mais barato, mesma CPU)
  
  Se sua aplicação usa 4 vCPU mas apenas 4GB RAM:
  → c6i é mais eficiente e mais barato que m6i
```

### Memory Optimized (R, X, z)

```
Alto ratio RAM:CPU para workloads memory-intensive:

Família R (Memory Optimized):
  r6g.large, r6i.xlarge, r7g.2xlarge...
  Ratio: ~8GB RAM por vCPU
  
  Ideal para:
  ├── Bancos de dados in-memory (Redis, Memcached)
  ├── SAP HANA, SAP Business Objects
  ├── Apache Spark em memória
  ├── Bancos de dados com buffer pool grande (MySQL, PostgreSQL)
  └── Real-time big data analytics

Família X (Extra Memory):
  x2gd, x1e...
  Ratio: até 32GB RAM por vCPU
  
  Extremo: x2idn.32xlarge = 1TB RAM
  Para: SAP HANA in-memory, workloads que precisam de RAM absurda

Família z (High Clock Speed):
  z1d.large...
  Frequência: até 4.0 GHz
  Para: simulações financeiras, EDA (Electronic Design Automation),
        qualquer workload onde clock speed é o gargalo
```

### Storage Optimized (I, D, H)

```
Alto throughput de I/O local com armazenamento NVMe:

Família I (NVMe SSD Local):
  i3.large, i3en.xlarge, i4i.xlarge...
  
  I/O local de baixíssima latência (< 1ms)
  Armazenamento local (NVMe): dados PERDIDOS se instância parar
  
  Ideal para:
  ├── Bancos NoSQL de alta performance (Cassandra, MongoDB)
  ├── Elasticsearch/OpenSearch (índice em disco local)
  ├── Data warehousing temporário
  ├── OLTP de alta transação com acesso a disco
  └── Cache de disco para dados quentes

Família D (Dense HDD):
  d2.xlarge, d3.xlarge...
  HDD de alta capacidade (até 48TB por instância)
  
  Ideal para:
  ├── Hadoop distributed file system (HDFS)
  ├── Data lakes com dados históricos
  └── Qualquer coisa que precise de muitos TB baratos

IMPORTANTE: Storage Local em I e D:
  Esses discos são efêmeros (ephemeral):
  → Dados PERDIDOS quando a instância é PARADA (stop)
  → Dados PRESERVADOS durante REBOOT
  → NUNCA armazene dados persistentes nestes discos sem backup
  → Use EBS para persistência ou S3 para dados de longo prazo
```

### Accelerated Computing (P, G, Trn, Inf)

```
Hardware especializado (GPU, chips de ML):

Família P (GPU para ML Training):
  p3.2xlarge, p4d.24xlarge, p5.48xlarge...
  GPU: NVIDIA V100 (p3), A100 (p4), H100 (p5)
  
  p3.2xlarge: 1 GPU NVIDIA V100, 8 vCPU, 61GB RAM = $3.06/hora
  p4d.24xlarge: 8 GPU NVIDIA A100 = $32.77/hora
  
  Ideal para:
  ├── Treinamento de modelos de deep learning
  ├── High performance computing (HPC)
  └── Simulações científicas com GPU

Família G (GPU para Gráficos e ML Inference):
  g4dn.xlarge, g5.xlarge...
  GPU: NVIDIA T4 (g4dn), A10G (g5)
  
  g4dn.xlarge: 1 GPU NVIDIA T4, 4 vCPU, 16GB RAM = $0.526/hora
  
  Ideal para:
  ├── ML Inference (rodar modelos já treinados)
  ├── Renderização 3D
  ├── Transcodificação de vídeo GPU-accelerated
  └── Streaming de aplicações gráficas

Família Trn (Trainium - chip AWS para ML):
  trn1.2xlarge, trn1.32xlarge...
  Chip: AWS Trainium (otimizado para training)
  
  Preço: ~30-40% mais barato que P3/P4 para mesmos workloads de ML
  
  Família Inf (Inferentia - chip AWS para ML Inference):
  inf2.xlarge...
  Chip: AWS Inferentia 2
  Preço: mais barato que G4 para workloads de inference
```

## Tamanhos de instâncias

```
Dentro de cada família: tamanhos escaláveis
  nano, micro, small, medium, large, xlarge, 2xlarge, 4xlarge, 8xlarge, 16xlarge...

Relação entre tamanhos (família m6i como exemplo):
  m6i.large:   2 vCPU,   8GB RAM = $0.096/hora
  m6i.xlarge:  4 vCPU,  16GB RAM = $0.192/hora (2x o large)
  m6i.2xlarge: 8 vCPU,  32GB RAM = $0.384/hora (2x o xlarge)
  m6i.4xlarge: 16 vCPU, 64GB RAM = $0.768/hora
  m6i.8xlarge: 32 vCPU, 128GB RAM = $1.536/hora
  
  Cada dobramento de tamanho = dobramento de vCPU, RAM e custo
  
Regra de escalabilidade:
  2× o tamanho = 2× o custo (linear)
  → Avaliar se é mais eficiente: 1 instância grande ou 2 pequenas
  → Para HA: 2 pequenas (sobrevive falha de uma) vs 1 grande (SPOF)
```

## Modelos de compra

### On-Demand — total flexibilidade

```
Paga por segundo (mínimo 60s), sem compromisso:

Custo: mais alto por hora
Compromisso: zero
Flexibilidade: máxima (inicia e termina a qualquer hora)

Quando usar:
  ├── Workloads imprevisíveis
  ├── Experimentos e testes de curta duração
  ├── Desenvolvimento e staging
  ├── Picos sazonais além da capacidade base
  └── Primeira vez num tipo de workload (antes de comprometer)

m6i.xlarge On-Demand: $0.192/hora = $138.24/mês (24/7)
```

### Reserved Instances — desconto por compromisso

```
Compromisso de 1 ou 3 anos em troca de desconto:

Tipos de RI:
  Standard RI: desconto máximo, menos flexibilidade
  → Só pode ser usado para a família/região/OS específicos
  → Pode ser vendido no marketplace se não precisar mais
  
  Convertible RI: desconto menor, mais flexibilidade
  → Pode trocar para outro tipo de instância (mesma família ou outra)
  → Pode mudar para Graviton após comprar Intel RI

Opções de pagamento:
  No Upfront: nenhum pagamento inicial, parcelas mensais
  Partial Upfront: parte inicial + parcelas reduzidas
  All Upfront: pagamento total → maior desconto

Exemplos de desconto (m6i.xlarge, us-east-1, Linux):
  On-Demand:                $0.192/hora = $1.681/ano
  1yr No Upfront:          $0.121/hora = $1.059/ano (37% desconto)
  1yr All Upfront:         $1.009/ano  (40% desconto)
  3yr Partial Upfront:     $0.073/hora = $639/ano   (62% desconto)
  3yr All Upfront:         $613/ano    (64% desconto)

Quando usar RI:
  ├── Workloads estáveis 24/7 (produção sempre ativa)
  ├── Quando você sabe que vai usar por 1-3 anos
  └── APÓS validar com On-Demand que o tipo está correto
  
  NÃO use RI se:
  ├── Não tem certeza do workload
  ├── Pode crescer para outro tipo em 6 meses
  └── Workload é intermitente (paga mesmo sem usar)
```

### Savings Plans — RI mais flexível

```
Compromisso de gasto mínimo/hora por 1 ou 3 anos:

Tipos:
  Compute Savings Plans:
  → Cobre: EC2 (qualquer família/região), Lambda, Fargate
  → Maior flexibilidade: aplica ao que você usar
  → Desconto: até 66%
  
  EC2 Instance Savings Plans:
  → Cobre: EC2 de uma família específica em uma região
  → Menor flexibilidade que Compute
  → Desconto: até 72% (um pouco mais que Compute)

Como funciona:
  Você se compromete a gastar $5/hora em EC2+Lambda+Fargate
  → AWS aplica desconto automaticamente ao uso
  → Se usar mais que $5/hora: excesso cobrado On-Demand
  → Se usar menos: você paga os $5/hora mesmo assim

Exemplo:
  Hoje você gasta $8/hora em EC2 On-Demand
  Compra Compute Savings Plans: $6/hora
  → Os primeiros $6/hora têm desconto de 66%: você paga $4/hora equiv.
  → Os últimos $2/hora: cobrados On-Demand ($2/hora)
  → Total: $4 + $2 = $6/hora (vs. $8/hora sem SP = 25% de economia)

Vantagem sobre RI:
  → Aplica automaticamente ao mix de instâncias que você usar
  → Migrar de m6i para m6g? O Savings Plan cobre automaticamente
  → Muito mais simples de gerenciar que múltiplas RIs

Cost Explorer recomenda automaticamente:
  "Se você comprar $X/hora de Compute Savings Plans por 1 ano,
   economizará $Y/mês baseado no seu uso atual"
```

### Spot Instances — capacidade ociosa com desconto extremo

```
Usa capacidade EC2 não utilizada com desconto de 70-90%:

Preço Spot:
  m6i.xlarge On-Demand: $0.192/hora
  m6i.xlarge Spot:      ~$0.035-0.060/hora (80-85% de desconto)

Risco: pode ser interrompida pela AWS com 2 minutos de aviso
  → AWS precisa da capacidade de volta → encerra a instância
  → Você recebe aviso 2 minutos antes via Instance Metadata

Quando Spot É adequado:
  ├── Processamento batch tolerante a interrupção
  ├── Treinamento de ML com checkpointing
  ├── Renderização de vídeo/imagem
  ├── CI/CD workers (novo job se for interrompido)
  ├── Data analytics jobs (re-executável)
  └── Qualquer workload stateless re-executável

Quando Spot NÃO é adequado:
  ├── Bancos de dados de produção (estado crítico)
  ├── Servidores web que não podem ser interrompidos
  ├── Qualquer coisa que não suporte interrupção abrupta
  └── Processamento que não pode ser retomado do início/checkpoint

Estratégias para maximizar disponibilidade com Spot:
  1. Spot Fleet com múltiplos tipos de instância:
     → Diversificar: m6i.xlarge + m6a.xlarge + m5.xlarge + c6i.xlarge
     → Se um pool for interrompido: outro pool assume
     → Reduz dramaticamente a probabilidade de interrupção simultânea
  
  2. Capacity-Optimized strategy:
     → AWS escolhe o pool com mais capacidade disponível
     → Menor probabilidade de interrupção (mais espaço)
  
  3. Checkpointing:
     → Salvar progresso periodicamente (ex: a cada 5 minutos)
     → Se interrompida: retomar do último checkpoint
     → S3 ou EFS para armazenar checkpoints

Mixed ASG (produção):
  Auto Scaling Group com mix de On-Demand + Spot:
  Base capacity: 20% On-Demand (garantida)
  Burst: 80% Spot (quando disponível)
  → Economiza 60-70% vs. 100% On-Demand
  → Se Spot for escasso: ASG usa mais On-Demand (proteção automática)
```

### Dedicated Instances e Dedicated Hosts

```
Dedicated Instances:
  → Hardware físico dedicado ao seu AWS account (não ao instância)
  → Outros tenants da AWS não compartilham o servidor físico
  → Custo: +$2/hora por Região onde usa ($0.02/hora On-Demand adicional)
  → Quando: compliance que proíbe hardware compartilhado (alguns reguladores)

Dedicated Hosts:
  → Servidor físico inteiro dedicado ao seu uso
  → Você controla onde as instâncias são colocadas no servidor
  → Visibilidade de: núcleos, sockets, IDs de hardware
  → Quando:
    ├── Licenças por socket/core: Oracle, Windows Server, SQL Server
    │   → "Minha licença Oracle cobre 4 sockets" = host com 4 sockets
    ├── Compliance que exige visibilidade de hardware
    └── Quando você paga licença de software por hardware físico

Custo Dedicated Host (m6i 24-core host):
  ~$4.089/hora = $2.944/mês
  vs. 12 × m6i.xlarge On-Demand = 12 × $0.192 = $2.304/mês

  Dedicated Host pode ser mais barato quando você tem licença própria:
  → Não paga a licença Windows da AWS (usa a sua)
  → Windows On-Demand: $0.384/hora para m6i.xlarge (inclui Windows)
  → Windows Dedicated Host (BYOL): custo do host + sua licença
```

## Estratégia de mix — combinando modelos

```
Para uma aplicação de produção com 10 instâncias:

Baseline previsível (sempre rodando):
  6 instâncias m6i.xlarge × 3yr All Upfront Savings Plans
  → ~$0.065/hora × 6 = $0.39/hora
  → Custo anual: ~$3.400

Burst previsível (horário comercial):
  2 instâncias adicionais × 1yr Savings Plans
  → ~$0.121/hora × 2 = $0.242/hora
  → Custo anual: ~$2.120

Burst imprevisível (picos sazonais, Black Friday):
  2 instâncias adicionais × On-Demand (pago só quando usar)
  → $0.192/hora × 2 = $0.384/hora (quando ativas)
  → Custo: apenas quando há pico

Processamento batch em background:
  Workers de CI/CD, relatórios, ML → Spot
  → $0.035/hora × variável
  → Economia de 80% vs On-Demand

Total anual estimado vs. 100% On-Demand:
  100% On-Demand: 10 × $0.192 × 8.760h = $16.819/ano
  Mix otimizado:  ~$7.000-9.000/ano
  Economia: 40-55%
```

## 🧩 Quiz de Fixação

1. Uma aplicação Java de e-commerce usa instâncias m6i.2xlarge (8 vCPU, 32GB RAM). O Compute Optimizer indica que a CPU média é 12% e o pico de p99 é 35%, mas a memória está sempre em 24GB usados (75%). Qual tipo de instância seria mais apropriado e por quê?
2. Um time de Data Science treina modelos de ML que levam 6-8 horas cada e podem ser retomados do último checkpoint. Eles treinam 3 modelos por semana. Compare o custo mensal entre Spot (p3.2xlarge) e On-Demand para esse workload e justifique a escolha.
3. Uma startup tem 5 instâncias c6g.xlarge (Graviton, 4 vCPU, 8GB) rodando 24/7 em produção há 6 meses. O CTO quer manter esse setup por pelo menos 2 anos. Qual modelo de compra recomendaria e calcule a economia anual vs. On-Demand (c6g.xlarge On-Demand: $0.136/hora)?

**Respostas:**
1) A instância atual (m6i.2xlarge: 8 vCPU, 32GB RAM) está superdimensionada em CPU (12% de uso, p99 apenas 35%) mas bem utilizada em memória (75%). A família correta é a **r** (Memory Optimized), que tem maior ratio RAM:CPU. Especificamente, r6g.large (2 vCPU, 16GB RAM) ou r6g.xlarge (4 vCPU, 32GB RAM) seriam candidatos. Análise: r6g.xlarge tem 4 vCPU (o p99 de 35% com 4 vCPU = 1.4 vCPU utilizado no pico — adequado) e 32GB RAM (mesma que a atual, mas com ratio melhor para o workload). Custo: r6g.xlarge = $0.2016/hora (Graviton) vs m6i.2xlarge = $0.384/hora — redução de 47% no custo com melhor fit de recursos. Alternativa mais econômica ainda: r7g.xlarge (Graviton3) se disponível, para ~20% mais eficiência. Migrar de m6i para r6g requer compatibilidade com ARM64 (Java 11+ roda em ARM sem recompilação).
2) Custo On-Demand: p3.2xlarge = $3.06/hora × 7 horas/modelo × 3 modelos/semana × 4 semanas = $256.68/mês. Custo Spot: p3.2xlarge Spot ≈ $0.92/hora (média ~70% desconto). Com checkpointing (salva a cada 30 min no S3): 7h × 3 × 4 = 84 horas de GPU/mês. Custo: $0.92 × 84 = $77.28/mês. Economia: $256.68 - $77.28 = $179.40/mês = $2.152/ano (70% de economia). A escolha é Spot com checkpointing porque: (1) treinamento de ML é interruptível e re-executável por natureza; (2) com checkpointing a cada 30 minutos, no pior caso perde-se apenas 30 minutos de progresso se a instância for interrompida; (3) a probabilidade de interrupção de uma p3.2xlarge por sessão de 7 horas é ~5-15%; na maioria das semanas os 3 treinos completarão sem interrupção; mesmo com 1-2 reinicializações mensais, o custo ainda fica muito abaixo do On-Demand.
3) Recomendação: **3-year Compute Savings Plans com All Upfront** para máximo desconto em workload previsível de 2+ anos. Cálculo: c6g.xlarge On-Demand = $0.136/hora × 5 instâncias × 8.760h/ano = $5.957/ano. Com 3yr Compute Savings Plans (aproximadamente 60-64% de desconto para Graviton/ARM): desconto médio ~64% → preço efetivo ~$0.049/hora por instância. 5 instâncias × $0.049 × 8.760h = $2.145/ano. Economia anual: $5.957 - $2.145 = $3.812/ano (64% de economia). Em 2 anos: $7.624 de economia total. Justificativa: Compute Savings Plans cobre EC2 de qualquer família/tamanho incluindo Graviton, e se em algum momento precisarem migrar para r6g ou m6g, o plano continua aplicando automaticamente — vantagem sobre Reserved Instances Standard que ficaria "presa" na família c6g. Com 6 meses de histórico confirmando o uso, o compromisso de 3 anos tem baixo risco.
