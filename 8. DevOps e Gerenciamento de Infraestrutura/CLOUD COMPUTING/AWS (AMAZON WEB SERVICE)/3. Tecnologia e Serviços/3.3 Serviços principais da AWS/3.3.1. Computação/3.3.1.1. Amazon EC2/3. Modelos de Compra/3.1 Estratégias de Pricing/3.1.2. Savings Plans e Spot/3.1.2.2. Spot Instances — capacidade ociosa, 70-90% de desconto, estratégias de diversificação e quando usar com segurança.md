### Spot Instances — capacidade ociosa com 70-90% de desconto

Spot Instances são instâncias EC2 que usam capacidade computacional ociosa dos datacenters da AWS. Como a AWS prefere vender essa capacidade a qualquer preço em vez de deixá-la ociosa, oferece descontos de 70-90% sobre o preço On-Demand. A contrapartida é que a AWS pode **interromper a instância com apenas 2 minutos de aviso** quando precisar recuperar essa capacidade. Quem entende esse trade-off e projeta para ele transforma Spot no modelo de compute mais econômico da AWS.

---

## Como o mercado Spot funciona

A AWS divide sua capacidade em **pools** — cada pool é uma combinação de família de instância + tamanho + AZ + SO. Cada pool tem seu próprio preço Spot, que varia com a oferta e demanda de capacidade naquele pool específico.

```
Estrutura de um pool Spot:
  m7g.xlarge + us-east-1a + Linux  → preço: $0.048/h  (~70% off)
  m7g.xlarge + us-east-1b + Linux  → preço: $0.051/h  (~69% off)
  c7g.2xlarge + us-east-1a + Linux → preço: $0.087/h  (~70% off)
  r7g.xlarge + us-east-1c + Linux  → preço: $0.063/h  (~71% off)
```

O preço Spot de um pool muda quando a demanda por aquele pool aumenta. A AWS publica o histórico de preços — pools com preço historicamente estável têm menor probabilidade de interrupção.

### O aviso de interrupção (interruption notice)

Quando a AWS decide recuperar capacidade de um pool, ela envia um **aviso de 2 minutos** antes de encerrar a instância. Esse aviso chega via:

1. **EC2 Instance Metadata** — a instância pode polling e detectar o aviso:

```bash
# Verificar se há aviso de interrupção pendente
TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")

curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/spot/termination-time

# Retorna vazio se não há aviso
# Retorna timestamp ISO 8601 se a instância vai ser encerrada
```

2. **EventBridge** — evento `EC2 Spot Instance Interruption Warning` publicado automaticamente, integrável com Lambda para ações de graceful shutdown.

3. **Instance rebalance recommendation** — aviso antecipado (antes dos 2 minutos) de que o risco de interrupção aumentou, permitindo ação proativa.

## Taxa de interrupção por pool

A AWS publica dados históricos de interrupção em `aws.amazon.com/ec2/spot/instance-advisor`. Os pools são classificados de 0% a >20% de taxa de interrupção por mês:

| Frequência de interrupção | Classificação | Estratégia |
|---|---|---|
| < 5% | Muito baixa | Pools preferidos para workloads mais sensíveis |
| 5-10% | Baixa | Aceitável com diversificação |
| 10-20% | Média | Apenas para workloads tolerantes |
| > 20% | Alta | Evitar ou diversificar muito |

**Regra prática:** pools de instâncias grandes (16xlarge, metal) têm menor taxa de interrupção porque há menos concorrência por eles. Pools de instâncias pequenas e populares (como `m5.xlarge`) têm maior concorrência e interrupção mais frequente.

## Estratégias de diversificação

A regra fundamental do Spot é: **nunca depender de um único pool**. A diversificação entre múltiplos pools é o que transforma Spot de "arriscado" em "confiável o suficiente para produção em muitos casos".

### Spot Fleet com múltiplos tipos

```
Spot Fleet diversificado para workload de processamento:
                                                              
Pools configurados:
  m7g.xlarge   (us-east-1a)  ─┐
  m7g.xlarge   (us-east-1b)  ─┤
  m6g.xlarge   (us-east-1a)  ─┤─ Se um pool for interrompido,
  m6i.xlarge   (us-east-1b)  ─┤  os outros absorvem a carga
  c7g.xlarge   (us-east-1a)  ─┤
  c6g.xlarge   (us-east-1c)  ─┘
                                                              
Estratégia de alocação: capacity-optimized
  → AWS escolhe o pool com MAIS capacidade disponível
  → Menor probabilidade de interrupção imediata
  → Melhor que price-capacity-optimized para workloads críticos
```

### Auto Scaling Group com mixed instances

Para aplicações web ou workers com Auto Scaling, o **Mixed Instances Policy** permite combinar múltiplos tipos em um único ASG:

```yaml
# Trecho de configuração de Mixed Instances Policy
MixedInstancesPolicy:
  InstancesDistribution:
    OnDemandBaseCapacity: 2          # mínimo de instâncias On-Demand
    OnDemandPercentageAboveBaseCapacity: 20  # 20% On-Demand, 80% Spot
    SpotAllocationStrategy: price-capacity-optimized
  LaunchTemplate:
    LaunchTemplateSpecification:
      LaunchTemplateId: lt-0abc123
    Overrides:
      - InstanceType: m7g.xlarge
      - InstanceType: m7g.large
      - InstanceType: m6g.xlarge
      - InstanceType: c7g.xlarge
      - InstanceType: c6g.xlarge
```

Resultado: se instâncias Spot são interrompidas, o ASG lança novas automaticamente em outro pool disponível, ou usa On-Demand se Spot estiver escasso.

## Casos de uso ideais para Spot

### Processamento batch e ETL

O caso mais simples: jobs que podem ser re-executados do início (ou de um checkpoint) se interrompidos.

```
Pipeline de ETL com Spot:
┌─────────┐    ┌─────────────────────────────────┐    ┌──────────┐
│  S3     │───▶│  Spot workers (m7g.4xlarge)     │───▶│  S3 /    │
│ (input) │    │  Auto Scaling Group             │    │  Redshift│
└─────────┘    │  Processa em paralelo           │    └──────────┘
               │  Se interrompido: novo worker   │
               │  retoma do checkpoint em S3     │
               └─────────────────────────────────┘
```

### Treinamento de ML com checkpointing

Modelos de ML salvam estado periodicamente (checkpoints). Se a instância Spot for interrompida, o próximo worker carrega o último checkpoint e continua.

```python
# Padrão de checkpoint para Spot com PyTorch
import os
import torch
import requests

def check_spot_interruption():
    """Verifica se há aviso de interrupção via metadata."""
    try:
        token = requests.put(
            "http://169.254.169.254/latest/api/token",
            headers={"X-aws-ec2-metadata-token-ttl-seconds": "21600"},
            timeout=1
        ).text
        response = requests.get(
            "http://169.254.169.254/latest/meta-data/spot/termination-time",
            headers={"X-aws-ec2-metadata-token": token},
            timeout=1
        )
        return response.status_code == 200  # 200 = interrupção iminente
    except:
        return False

def save_checkpoint(model, optimizer, epoch, loss, path="s3://bucket/checkpoint.pt"):
    torch.save({
        "epoch": epoch,
        "model_state_dict": model.state_dict(),
        "optimizer_state_dict": optimizer.state_dict(),
        "loss": loss,
    }, "/tmp/checkpoint.pt")
    os.system(f"aws s3 cp /tmp/checkpoint.pt {path}")

# Loop de treinamento com tratamento de interrupção
for epoch in range(start_epoch, max_epochs):
    train_one_epoch(model, optimizer, dataloader)
    
    # Salvar checkpoint a cada 5 épocas
    if epoch % 5 == 0:
        save_checkpoint(model, optimizer, epoch, loss)
    
    # Verificar aviso de interrupção
    if check_spot_interruption():
        save_checkpoint(model, optimizer, epoch, loss)
        print("Interrupção iminente — checkpoint salvo. Encerrando.")
        break
```

### Workers de CI/CD

Pipelines de CI (builds, testes) são naturalmente re-executáveis — se um worker Spot for interrompido no meio de um build, o pipeline simplesmente reinicia o job em outro worker.

```
Economia típica em CI/CD com Spot:
  Build médio: 15 minutos
  c7g.2xlarge On-Demand: $0.29/hora → $0.0725 por build
  c7g.2xlarge Spot:      ~$0.087/hora → $0.0218 por build
  
  100 builds/dia × $0.0507 de economia = $5.07/dia = $1.850/ano
  por pipeline de build
```

### Renderização e processamento de mídia

Renderização de frames de animação, transcoding de vídeo e processamento de imagens são paralelizáveis e cada unidade de trabalho é independente. Uma interrupção perde no máximo o frame/segmento atual.

### Análise de dados e queries ad-hoc

Clusters Spark/EMR no modo Spot processam grandes datasets por horas. Com checkpointing do Spark e tolerância a falha de nós, perder um nó Spot é um evento normal que o framework gerencia automaticamente.

                          │
                          ▼

## Spot com serviços gerenciados

Além do EC2 direto, Spot está disponível em serviços gerenciados:

| Serviço | Como usar Spot | Benefício |
|---|---|---|
| **ECS** | `capacityProviders: FARGATE_SPOT` | Containers com 70% de desconto |
| **EKS** | Node groups com Spot | Kubernetes com workers baratos |
| **EMR** | Task nodes como Spot | Spark/Hadoop ~70% mais barato |
| **SageMaker** | Managed Spot Training | ML training sem gerenciar EC2 |
| **Batch** | `type: SPOT` na compute env | Jobs batch totalmente gerenciados |

O **AWS Batch** em particular é ideal para quem quer Spot sem gerenciar interrupções manualmente — o serviço reatribui jobs automaticamente quando um nó Spot é encerrado.

## Erros comuns e armadilhas

**Usar um único pool Spot:** concentrar tudo em `m5.xlarge + us-east-1a` cria um ponto único de falha. Se esse pool for interrompido, toda a carga cai de uma vez. Diversificar em 5-8 pools diferentes reduz drasticamente esse risco.

**Não implementar graceful shutdown:** os 2 minutos de aviso são suficientes para finalizar transações, fazer flush de buffers e salvar estado — mas só se o código foi escrito para isso. Sem graceful shutdown, o processo é encerrado abruptamente.

**Armazenar estado no disco local da instância Spot:** Instance Store + Spot = perda garantida. Todo estado deve ir para S3, EFS, ElastiCache ou outro armazenamento externo.

**Usar Spot para o nó coordenador de um cluster:** em clusters Spark ou Hadoop, o nó master/driver deve ser On-Demand. Perder o coordenador derruba o job inteiro, não só um worker.

**Não monitorar interrupções:** sem métricas de interrupção, é impossível saber se Spot está prejudicando o throughput. CloudWatch + EventBridge + métricas de jobs permitem identificar se a taxa de interrupção está impactando SLAs.

## 🧩 Quiz de Fixação

1. Você tem um pipeline de ingestão de dados que processa arquivos do S3 com workers stateless — cada worker pega um arquivo, processa e salva o resultado no S3. Qual configuração de Spot você usaria e por que esse workload é ideal para Spot?

2. Um engenheiro propõe usar Spot para o cluster Redis de cache de produção, argumentando que "o cache pode ser reconstruído se cair". Por que essa proposta tem um risco oculto grave mesmo que tecnicamente o dado seja reconstruível?

3. Qual é a diferença entre as estratégias de alocação `lowest-price` e `capacity-optimized` em um Spot Fleet, e em qual cenário cada uma é mais adequada?

**Respostas:**

1) Configuração ideal: **Spot Fleet com `capacity-optimized`**, diversificando entre 6-8 pools compatíveis (ex: m7g.xlarge, m6g.xlarge, c7g.xlarge em múltiplas AZs). Esse workload é ideal para Spot por três razões: (1) é **stateless** — cada worker não carrega estado entre arquivos; (2) é **idempotente** — processar o mesmo arquivo duas vezes não causa problema (o resultado no S3 simplesmente sobrescreve); (3) a unidade de trabalho é pequena (um arquivo por vez), então uma interrupção perde no máximo o progresso de um arquivo — não horas de computação. Com SQS como fila, mensagens não confirmadas voltam automaticamente para re-processamento, tornando o sistema totalmente tolerante a interrupções sem código adicional.

2) O risco oculto é o **thundering herd** (manada trovejante): quando o Redis cai, **todas as requisições que antes eram atendidas pelo cache vão simultaneamente para o banco de dados**. Se o cache cobria 90% das leituras de um banco que recebia 10.000 req/s, o banco de repente recebe 100.000 req/s — provavelmente derrubando o banco também. A reconstrução do cache leva minutos (cold start), durante os quais o sistema pode ficar completamente inoperante em cascata. Spot é inadequado para Redis de produção não pelo dado em si, mas pelo impacto sistêmico da interrupção súbita sem aviso suficiente para warmup controlado.

3) **`lowest-price`**: a AWS aloca no pool de menor preço no momento da solicitação. Maximiza o desconto imediato, mas esses pools baratos tendem a ser os mais disputados — maior probabilidade de interrupção frequente. Adequado para workloads muito curtos (< 30 minutos) onde o risco de interrupção por sessão é baixo, e onde o custo mínimo é prioridade absoluta. **`capacity-optimized`**: a AWS aloca no pool com maior capacidade disponível, independente do preço (dentro dos limites Spot). O resultado prático é menor taxa de interrupção, porque pools com muita capacidade têm menos pressão para recuperar instâncias. Adequado para jobs longos (horas), workloads onde interrupções têm custo alto (reiniciar do checkpoint é caro) e produção onde a estabilidade importa mais que o desconto máximo. Para a maioria dos casos de produção, `capacity-optimized` é a recomendação padrão.
