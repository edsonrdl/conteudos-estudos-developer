### Dedicated Instances e Dedicated Hosts — hardware físico exclusivo na AWS

A maioria das instâncias EC2 roda em hardware compartilhado — o mesmo servidor físico hospeda VMs de múltiplos clientes AWS diferentes (multi-tenancy). Para a grande maioria dos workloads isso é seguro e invisível, mas alguns cenários exigem isolamento físico: regulações de compliance, licenças de software que contam por núcleo físico, ou políticas corporativas que proíbem hardware compartilhado. Dedicated Instances e Dedicated Hosts resolvem esses cenários de formas diferentes, com implicações de custo e controle distintas.

---

## Multi-tenancy vs. isolamento físico

```
Modelo padrão (shared tenancy):
┌─────────────────────────────────────────────┐
│         Servidor físico AWS                 │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  │
│  │ VM:      │  │ VM:      │  │ VM:      │  │
│  │ Conta A  │  │ Conta B  │  │ Conta C  │  │
│  │ (você)   │  │(terceiro)│  │(terceiro)│  │
│  └──────────┘  └──────────┘  └──────────┘  │
└─────────────────────────────────────────────┘
O hypervisor isola as VMs — dados não vazam entre contas.
Mas o hardware físico é compartilhado.

Dedicated Instances:
┌─────────────────────────────────────────────┐
│         Servidor físico AWS                 │
│  ┌──────────┐  ┌──────────┐                │
│  │ VM:      │  │ VM:      │  Apenas VMs    │
│  │ Conta A  │  │ Conta A  │  da sua conta  │
│  │          │  │          │  neste servidor │
│  └──────────┘  └──────────┘                │
└─────────────────────────────────────────────┘
Mesmo servidor pode hospedar outras instâncias
da SUA conta, mas nenhuma de outros clientes.

Dedicated Hosts:
┌─────────────────────────────────────────────┐
│    Servidor físico atribuído à sua conta    │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  │
│  │ VM:      │  │ VM:      │  │ VM:      │  │
│  │ Conta A  │  │ Conta A  │  │ Conta A  │  │
│  └──────────┘  └──────────┘  └──────────┘  │
│  Você sabe: quantos sockets, núcleos, IDs  │
└─────────────────────────────────────────────┘
O servidor inteiro é seu. Visibilidade total
de topologia física.
```

## Dedicated Instances

Dedicated Instances garantem que **nenhuma outra conta AWS** rodará instâncias no mesmo servidor físico que as suas. A AWS pode mover suas instâncias entre servidores físicos (ex: em caso de manutenção), mas sempre para hardware exclusivo da sua conta.

### Custo

O modelo de cobrança tem dois componentes:

| Componente | Valor |
|---|---|
| Taxa por região (dedicação) | **$2/hora** por região onde você tem Dedicated Instances ativas (independente de quantas instâncias) |
| Preço da instância | ~10% a mais que o preço On-Demand equivalente |

```
Exemplo de custo mensal — 3 instâncias m7g.xlarge Dedicated:
  Taxa de região:   $2/hora × 720h = $1.440/mês
  Instâncias:       3 × $0.1795/h × 720h = $388/mês
  Total:            $1.828/mês

  Comparação com shared tenancy:
  3 × $0.1632/h × 720h = $352/mês

  Custo adicional pelo isolamento: +$1.476/mês (+419%)
```

A taxa de $2/hora por região torna Dedicated Instances muito caras para poucos workloads isolados. O custo se dilui quando há muitas instâncias na região.

### Quando usar Dedicated Instances

- Compliance que proíbe hardware compartilhado com outros clientes, mas **não** exige visibilidade de topologia física (sockets, núcleos)
- Políticas corporativas ou setoriais (ex: alguns contratos governamentais) que exigem isolamento de tenant
- Cenários onde a equipe de segurança quer eliminar completamente o risco teórico de side-channel attacks entre tenants (ex: Spectre/Meltdown em ambientes muito sensíveis)

---

## Dedicated Hosts

Dedicated Hosts vão além: você aloca um **servidor físico inteiro** para uso exclusivo da sua conta, com visibilidade completa da topologia de hardware — número de sockets, núcleos físicos, núcleos por socket e IDs do host. As instâncias são colocadas explicitamente nesse host.

### O que você controla em um Dedicated Host

```
Dedicated Host — m7i.48xlarge host (exemplo):
  Sockets:         2
  Núcleos físicos: 48 (24 por socket)
  vCPUs totais:    96
  RAM:             384 GiB
  
  Capacidade disponível para instâncias:
  Você pode rodar, por exemplo:
  ├── 24× m7i.xlarge  (4 vCPU cada = 96 vCPU total)
  ├── 12× m7i.2xlarge (8 vCPU cada = 96 vCPU total)
  ├── 6×  m7i.4xlarge (16 vCPU cada = 96 vCPU total)
  └── Mix de tamanhos dentro da mesma família
```

### Custo dos Dedicated Hosts

O Dedicated Host é cobrado **pelo host por hora**, não por instância. O preço varia por família e geração:

| Host | Sockets | Núcleos | $/hora (On-Demand) | $/hora (1yr RI All Upfront) |
|---|---|---|---|---|
| m7i.metal-24xl host | 2 | 24 | ~$5.40 | ~$3.20 |
| m7i.metal-48xl host | 2 | 48 | ~$10.80 | ~$6.40 |
| c7i.metal-24xl host | 2 | 24 | ~$4.80 | ~$2.90 |
| r7i.metal-24xl host | 2 | 24 | ~$10.40 | ~$6.20 |

Não há cobrança adicional pelas instâncias que rodam dentro do host — você paga pelo host e pode colocar quantas instâncias couberem.

## BYOL — Bring Your Own License

O caso de uso mais importante dos Dedicated Hosts é o **BYOL (Bring Your Own License)**: usar licenças de software proprietário que você já possui, em vez de pagar as licenças incluídas nos AMIs da AWS.

### Oracle Database

Oracle licencia por **núcleo físico** com um fator de licença que varia por processador:

```
Fator de licença Oracle por processador:
  Intel Xeon (multi-core): 0.5 licença por núcleo físico
  AMD EPYC:                0.5 licença por núcleo físico
  
  Dedicated Host m7i.metal-24xl (24 núcleos físicos Intel):
  Licenças Oracle necessárias: 24 × 0.5 = 12 licenças de processador
  
  Comparação:
  Oracle Enterprise Edition On-Demand (em instância shared):
  → AWS cobra a licença incluída no preço da instância
  → m5.4xlarge Oracle EE: ~$4.50/hora (vs $0.768/hora sem Oracle)
  
  Oracle BYOL em Dedicated Host:
  → Você paga o host ($10.80/hora) + suas 12 licenças próprias
  → Se você já tem 12 licenças Oracle: elimina ~$3.73/hora de custo
    de licença por instância m5.4xlarge equivalente
```

Com licenças próprias e uso intenso do host, BYOL em Dedicated Host pode ser **significativamente mais barato** que pagar Oracle On-Demand na AWS.

### Windows Server

Microsoft licencia Windows Server por **núcleo físico** em pacotes de 2 núcleos (mínimo 8 núcleos por servidor):

```
Windows Server BYOL em Dedicated Host vs. On-Demand:
  
  m7i.metal-24xl com 48 vCPUs (24 núcleos físicos):
  
  On-Demand com Windows (licença inclusa):
  → 24× m7i.xlarge com Windows = 24 × $0.48/h = $11.52/hora
  
  BYOL em Dedicated Host (você tem licença Windows SA):
  → Custo do host: $10.80/hora
  → Licença Windows: já paga via Software Assurance
  → Economia: $0.72/hora = $6.307/ano
  
  Com Reserved Host (1 ano All Upfront):
  → ~$6.40/hora → economia aumenta para ~$5.12/hora = $44.851/ano
```

### SQL Server

SQL Server Enterprise é uma das licenças mais caras no modelo On-Demand da AWS. O BYOL em Dedicated Host é frequentemente a única forma economicamente viável de rodar SQL Server Enterprise na AWS para workloads grandes.

## Affinity e Host Tenancy — controle de placement

Dedicated Hosts oferecem dois mecanismos de controle de onde as instâncias rodam:

**Host Affinity:** vincula uma instância específica a um host específico. Após um stop/start, a instância sempre volta para o mesmo host físico.

```bash
# Modificar affinity de uma instância para um host específico
aws ec2 modify-instance-placement \
  --instance-id i-0abc123def456 \
  --tenancy host \
  --host-id h-0123456789abcdef0 \
  --affinity host
```

**Auto-placement:** quando ativado, instâncias "sem host específico" podem ser automaticamente alocadas em qualquer Dedicated Host com capacidade disponível da família correta.

## Comparativo completo: Shared vs. Dedicated Instances vs. Dedicated Hosts

| Critério | Shared Tenancy | Dedicated Instances | Dedicated Hosts |
|---|---|---|---|
| Hardware compartilhado | Com outros clientes | Não (só sua conta) | Não (host dedicado) |
| Visibilidade de sockets/núcleos | Não | Não | Sim |
| Controle de placement | Não | Não | Sim |
| BYOL (Oracle, Windows) | Não | Não | Sim |
| Custo adicional | — | +$2/h/região + ~10%/instância | Por host/hora |
| Compliance de isolamento | Não | Sim (sem visibilidade) | Sim (com visibilidade) |
| Reserva de capacidade na AZ | Não | Não | Sim |
| Ideal para | Maioria dos workloads | Compliance simples | BYOL + compliance avançado |

## Trade-offs de custo na prática

**Dedicated Instances valem a pena quando:**
- A exigência de compliance é real e documentada — não apenas "parece mais seguro"
- O custo de $2/hora/região é diluído entre muitas instâncias (>20-30 instâncias na região)
- Não há necessidade de BYOL (senão Dedicated Host é mais adequado)

**Dedicated Hosts valem a pena quando:**
- Há licenças Oracle, SQL Server Enterprise ou Windows com Software Assurance que podem ser reutilizadas
- O volume de uso justifica o custo fixo do host (host sub-utilizado é pior que On-Demand)
- Existe exigência de visibilidade de topologia física para auditoria ou compliance específico (ex: PCI DSS, HIPAA com requisito de isolamento físico documentado)

**Quando nenhum dos dois vale:**
- A maioria dos workloads não tem requisito regulatório real de isolamento físico
- O hypervisor da AWS (Nitro) provê isolamento muito forte — side-channel attacks práticos entre tenants em Nitro são extremamente raros e de baixo impacto real
- O custo adicional raramente se justifica por percepção de segurança sem exigência explícita de compliance

---

## Erros comuns e armadilhas

**Usar Dedicated por "segurança" sem requisito real:** a grande maioria das regulações (SOC 2, ISO 27001, GDPR) não exige isolamento físico — o isolamento lógico do Nitro Hypervisor é suficiente e auditável. Pagar pelo Dedicated sem obrigação regulatória é desperdício.

**Sub-utilizar um Dedicated Host:** um host alocado mas com 20% de ocupação ainda cobra o preço cheio do host. Planejar a consolidação de instâncias para maximizar a utilização do hardware (>80% de vCPUs ocupados) é essencial.

**BYOL sem verificar os termos da licença:** nem toda licença Oracle ou Windows permite uso em nuvem pública via BYOL. Licenças sem Software Assurance ou com cláusulas específicas de ambiente podem ser inválidas em cloud. Verificar com o fornecedor antes de assumir que BYOL é permitido.

**Misturar BYOL e licença inclusa no mesmo host:** se uma instância com licença AWS-included rodar no mesmo Dedicated Host que instâncias BYOL, pode haver ambiguidade de compliance de licenciamento. Manter hosts separados para cada modelo de licenciamento.

## 🧩 Quiz de Fixação

1. Uma empresa tem 50 instâncias `m7i.xlarge` e precisa de isolamento de hardware para atender a um requisito de compliance. Qual a diferença de custo mensal entre usar Dedicated Instances vs. Shared Tenancy, e o que determina se vale a pena?

2. Um time tem 30 licenças Oracle Enterprise Edition (com fator 0.5 para Intel) e quer rodar Oracle Database na AWS. Explique por que um Dedicated Host é necessário para o BYOL e como calcular quantos hosts são necessários.

3. Por que sub-utilizar um Dedicated Host é financeiramente mais prejudicial do que sub-utilizar instâncias On-Demand, e como mitigar esse risco?

**Respostas:**

1) **Shared Tenancy:** 50 × $0.1632/h × 720h = **$5.875/mês**. **Dedicated Instances:** taxa de região: $2 × 720h = $1.440/mês + instâncias: 50 × ($0.1632 × 1.10) × 720h = $6.463/mês. **Total Dedicated:** ~$7.903/mês — custo adicional de **$2.028/mês (+35%)**. Vale a pena quando: (1) existe obrigação regulatória documentada que especificamente exige isolamento de hardware (ex: certos contratos governamentais ou normas setoriais específicas); (2) o risco de compliance de não ter isolamento é maior que $2.028/mês; (3) a organização passou por auditoria e o isolamento físico foi apontado como requisito concreto. Não vale a pena por "parecer mais seguro" sem requisito explícito.

2) O BYOL para Oracle só é permitido em **Dedicated Hosts** porque é a única forma de ter visibilidade e controle dos núcleos físicos — que é exatamente o que Oracle licencia. Em shared tenancy ou Dedicated Instances, você não sabe em quantos núcleos físicos sua VM está rodando, tornando impossível contar e comprovar as licenças. **Cálculo:** 30 licenças ÷ fator 0.5 = 60 núcleos físicos cobertos. Um host `m7i.metal-24xl` tem 24 núcleos físicos → 30 licenças ÷ 24 núcleos/host = **2 hosts necessários** (cobrem 48 núcleos; você teria 12 licenças de folga). Com 2 hosts, é possível rodar até 48 × 2 = 96 vCPUs de instâncias Oracle, distribuídas como precisar (ex: 2× `m7i.24xlarge` por host).

3) **On-Demand** tem custo variável — instâncias paradas não cobram pelo compute. Se você para 10 instâncias às 18h, paga apenas pelas horas rodadas. **Dedicated Host** tem custo fixo — o host cobra **24 horas por dia, 7 dias por semana**, independente de quantas instâncias estão rodando nele. Um host a $10.80/hora com 20% de ocupação custa $7.776/mês, mas entrega apenas $1.555 de compute efetivo — 80% de desperdício. **Mitigação:** (1) planejar a consolidação de workloads antes de alocar o host, mirando >80% de ocupação de vCPUs; (2) usar **Reserved Hosts** (1 ou 3 anos) para reduzir o custo fixo do host quando o uso é previsível; (3) monitorar com CloudWatch a utilização do host e consolidar instâncias de hosts sub-utilizados quando possível.
