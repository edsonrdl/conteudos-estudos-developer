### Família M — o padrão de propósito geral para produção

A família M (de "general purpose") é a família mais usada do EC2 e a referência de baseline de desempenho da AWS. Enquanto a família T sacrifica consistência de CPU em favor de preço menor, a família M entrega CPU **sustentada** — sem burst, sem créditos, sem throttling. Ela equilibra vCPU e RAM na proporção 1:4 (1 vCPU para cada 4GB de RAM), tornando-a adequada para uma vasta gama de workloads de produção que não têm um gargalo específico de CPU ou memória.

---

## Por que a família M é o "padrão"

```
Proporção de recursos da família M:
  4 vCPU : 16GB RAM = 1:4 (padrão de propósito geral)

Compare com outras famílias:
  Família C (compute): 1:2  → mais CPU por RAM (CPU-intensive)
  Família M (geral):   1:4  → balanceado (maioria dos apps)
  Família R (memory):  1:8  → mais RAM por CPU (memory-intensive)

Por que 1:4 é o "padrão":
  A maioria das aplicações web e backend consomem
  CPU e memória de forma relativamente proporcional:
  → Web server Node.js: usa CPU para JSON, RAM para buffers
  → Python API (Flask/FastAPI): similar
  → Java Spring Boot: mais RAM (JVM heap), mas CPU proporcional
  → Banco PostgreSQL pequeno: CPU para queries, RAM para buffer pool
  
  M atende todos esses sem deixar recurso sobrando ou faltando.
```

## Geração atual: m6i, m6a, m6g (e m7x)

```
Geração 6 — atual e mais usada:

m6i (Intel Ice Lake):
  Processador: Intel Xeon Scalable 3ª geração (Ice Lake)
  Clock: até 3.5 GHz em burst de frequência
  Preço base (xlarge, us-east-1, Linux): $0.192/hora

m6a (AMD EPYC Milan):
  Processador: AMD EPYC 7003 (Milan)
  Clock: até 3.6 GHz
  Preço base (xlarge): $0.1728/hora → 10% mais barato que m6i
  Mesma performance para a maioria dos workloads

m6g (AWS Graviton2, ARM64):
  Processador: AWS Graviton2 (ARM Neoverse N1)
  Arquitetura: ARM64 (requer SO e software compatíveis)
  Preço base (xlarge): $0.154/hora → 20% mais barato que m6i
  Performance: igual ou melhor que m6i em muitos benchmarks

m6gd (Graviton2 + NVMe local):
  Mesma base do m6g + disco NVMe local efêmero
  Útil para: cache temporário, scratch disk para processamento

Geração 7 (mais nova, melhor performance/preço):
  m7i (Intel Sapphire Rapids): ~15% mais rápido que m6i
  m7a (AMD Genoa): ~20% mais rápido que m6a
  m7g (Graviton3): ~25% mais rápido que m6g, mais eficiente energeticamente
```

## Intel vs AMD vs Graviton — como escolher

### Graviton (ARM) — o caminho da eficiência

```
AWS Graviton é o chip ARM desenvolvido internamente pela AWS.
É a escolha mais eficiente em custo-benefício quando compatível.

Vantagens do Graviton:
  ├── 20-40% mais barato que equivalente Intel/AMD
  ├── 40% menos energia (sustentabilidade e custo em Dedicated)
  ├── Performance igual ou superior em muitos benchmarks
  └── Chips projetados especificamente para workloads de nuvem

Compatibilidade — quando Graviton funciona sem esforço:
  ✓ Linux 64-bit ARM (Ubuntu, Amazon Linux, Debian, RHEL)
  ✓ Docker/containers com imagens multi-arch (linux/arm64)
  ✓ Linguagens com JIT/bytecode: Java 11+, Python, Node.js, Go, Rust
  ✓ Binários compilados para ARM64 (Go, Rust, C/C++ com recompilação)
  ✓ A maioria dos softwares open source tem builds ARM64

Incompatibilidades — quando Graviton NÃO funciona:
  ✗ Windows Server (não suportado em Graviton)
  ✗ Binários x86 compilados sem suporte ARM (software legado, EXEs)
  ✗ Algumas ferramentas de segurança/DLP que têm apenas x86
  ✗ Software proprietário sem versão ARM64

Verificar compatibilidade de imagem Docker:
  docker manifest inspect nginx:latest | grep -i architecture
  → Se incluir "arm64": funciona no Graviton
  → Se só x86_64/amd64: não funciona (ou roda via emulação lenta)

Estratégia de migração para Graviton:
  1. Construir imagem Docker multi-arch:
     docker buildx build --platform linux/amd64,linux/arm64 -t app:v1 .
  2. Testar em instância t4g.small (barata)
  3. Validar: benchmarks, testes de integração
  4. Migrar gradualmente via ASG (novo launch template com m6g)
  5. Economia imediata de 20-40%
```

### Intel vs AMD — para quando Graviton não é opção

```
Quando escolher Intel (m6i):
  ├── Software com otimizações específicas para Intel (AVX-512, etc.)
  ├── Workloads de HPC que se beneficiam de Intel MKL (Math Kernel Library)
  ├── Equipe familiarizada com tuning Intel
  ├── Alguns bancos de dados que têm certificação explícita Intel
  └── Quando vendor exige Intel para suporte

Quando escolher AMD (m6a):
  ├── Qualquer workload x86 onde Intel não é obrigatório
  ├── 10% de desconto sem mudança de arquitetura ou SO
  ├── Workloads gerais de web, API, banco de dados
  └── Nenhuma diferença de comportamento vs Intel para a maioria dos apps

Decisão rápida para x86:
  Graviton compatível? → Graviton (melhor custo)
  Não → AMD (10% mais barato que Intel)
  Intel obrigatório? → Intel (apenas se houver razão técnica real)
```

## Tamanhos da família M e quando usar cada um

```
Regra de sizing — por tipo de aplicação:

m6g.medium (1 vCPU, 4GB): 
  → Microserviço leve, worker de background, cron job
  → Tráfego: < 100 req/min

m6g.large (2 vCPU, 8GB):
  → API de produção leve a moderada
  → Banco de dados de desenvolvimento/staging
  → Worker de processamento assíncrono
  → Tráfego: 100-500 req/min

m6g.xlarge (4 vCPU, 16GB):
  → API de produção de médio porte
  → Banco de dados pequeno (PostgreSQL < 1.000 QPS)
  → Serviço com estado moderado em memória
  → Tráfego: 500-2.000 req/min

m6g.2xlarge (8 vCPU, 32GB):
  → Backend de aplicação com alta concorrência
  → Banco de dados médio
  → Serviços com lógica de processamento intensiva
  → Tráfego: 2.000-10.000 req/min

m6g.4xlarge (16 vCPU, 64GB):
  → Monólitos grandes ou serviços de alto throughput
  → Banco de dados de produção médio-grande
  → Analytics em memória

m6g.8xlarge+ (32+ vCPU, 128+ GB):
  → Servidores de banco de dados pesados
  → Aplicações com estado massivo em memória
  → Considerar arquitetura horizontal antes de escalar vertical

REGRA DE OURO: prefira instâncias menores × mais instâncias
  2 × m6g.large > 1 × m6g.xlarge para produção
  → Melhor HA (falha de 1 = 50% capacidade, não 0%)
  → Auto Scaling mais granular
  → Mesma CPU total, mesma RAM total
  → Mesmo custo ($0.077 × 2 = $0.154 = $0.154/h)
```

## Quando fazer upgrade de T para M

```
Sinais claros de que é hora de migrar T → M:

1. CPUCreditBalance consistentemente zero:
   → CloudWatch mostra créditos zerados todo dia
   → Throttling frequente, latência irregular

2. CPU utilization > baseline por horas contínuas:
   → Baseline do T3.medium = 20%
   → Se CPU média no horário de pico > 30% por horas: hora de M

3. Reclamações de performance inconsistente:
   → "De manhã é rápido, de tarde fica lento"
   → Clássico sinal de créditos esgotando com tráfego

4. Migração de dev para produção:
   → T3 funcionou no dev com tráfego simulado
   → Produção tem carga real e constante → M desde o início

5. SLA de latência:
   → Qualquer SLA de latência p99 em produção → M (CPU previsível)
   → T com throttling = spikes de latência imprevisíveis

Custo de fazer o upgrade:
  t3.medium ($0.0416/h) → m6g.medium ($0.0385/h)
  ESPERA! m6g.medium é mais BARATO que t3.medium?
  
  Sim! Para algumas comparações:
  t3.medium: 2 vCPU, 4GB, $0.0416/hora (com burst limitado)
  m6g.medium: 1 vCPU, 4GB, $0.0385/hora (CPU sustentada)
  m6g.large:  2 vCPU, 8GB, $0.077/hora  (CPU sustentada, 2× RAM)
  
  Para cargas onde CPU precisa ser constante e não há burst:
  M é melhor negócio, não necessariamente mais caro.
```

## M em arquiteturas de produção comuns

```
Padrão 1: Web + App em camadas
  ALB → [m6g.large × 3] → [RDS db.r6g.large]
  
  Por que m6g.large para app tier:
  → CPU sustentada para processar requisições web
  → 3 instâncias Multi-AZ para HA
  → Graviton = 20% mais barato que equivalente Intel

Padrão 2: API Gateway + Microserviços
  API GW → Lambda OU [m6g.medium × 2 por serviço]
  
  Quando usar m6g.medium para microserviços:
  → Serviços stateless com carga moderada contínua
  → Container (ECS/EKS) on m6g para melhor densidade

Padrão 3: App + Banco all-in-one (projetos pequenos)
  [m6g.xlarge: app + banco na mesma instância]
  → Apenas para MVP ou serviços de baixíssima carga
  → Banco e app na mesma instância: não recomendado para produção séria

Padrão de escala (ASG):
  Min: 2 (m6g.large, Multi-AZ)
  Desired: 4
  Max: 20
  Target Tracking: CPU = 60%
  → Em picos: ASG adiciona m6g.large automaticamente
  → Sem créditos, sem throttling, escala elástica real
```

## 🧩 Quiz de Fixação

1. Um serviço de API REST em Java (Spring Boot) roda em t3.medium em staging sem problemas. Ao subir para produção com 10× mais tráfego, o serviço começa a ter latência alta às 10h e normaliza às 11h. Qual família de instância resolve o problema e como escolher o tamanho correto?
2. O time está decidindo entre m6i.xlarge ($0.192/h) e m6g.xlarge ($0.154/h) para um novo serviço Node.js. O CTO quer Intel "por garantia". Qual argumento técnico e financeiro apresentaria para reconsiderar, e como validar que o Graviton é compatível?
3. Por que "2 × m6g.large" é preferível a "1 × m6g.xlarge" para um serviço de produção que precisa das mesmas 4 vCPUs e 16GB de RAM no total, e qual o único cenário onde a instância única seria melhor?

**Respostas:**
1) O diagnóstico é o esgotamento de CPU Credits — em staging com baixo tráfego, a t3.medium acumula créditos; em produção com 10× mais carga, os créditos esgotam por volta das 10h (após o início do expediente) e a CPU é throttled para 20%, causando alta latência. Às 11h os créditos começam a se reacumular com menor carga. A família M resolve: sem burst, sem créditos, CPU sustentada. Para sizing: Spring Boot tipicamente precisa de ~500-800MB de heap por instância + CPU para processar requests. Com 10× mais tráfego que o staging, meça a CPU real em staging e multiplique por 10 para estimar necessidade. Se staging roda com ~15% de CPU numa t3.medium (2 vCPU), produção precisaria de ~150% de CPU — ou seja, ~3 vCPUs sustentados. m6g.xlarge (4 vCPU, 16GB) com 2 instâncias em Multi-AZ seria a escolha: sobra headroom para picos, HA garantida, e Graviton é compatível com Java 11+.
2) Argumento técnico: Node.js tem suporte nativo e excelente para ARM64; o runtime V8 do Node.js é compilado para ARM64 e a performance é igual ou superior em benchmarks de throughput de API. O NPM ecosystem usa binários nativos ARM64 para a maioria dos pacotes (aqueles que usam módulos nativos geralmente têm builds ARM64). Argumento financeiro: m6g.xlarge = $0.154/h vs m6i.xlarge = $0.192/h = 20% de economia. Em 1 ano com 3 instâncias: 3 × ($0.192 - $0.154) × 8.760h = $998/ano economizados por fazer uma mudança de 30 minutos. Como validar: verificar `docker manifest inspect [imagem]:latest | grep arm64` para confirmar que a imagem tem suporte; criar instância t4g.small, rodar a aplicação, executar load test básico e comparar latência e throughput com a instância Intel atual em staging. Se passar: migrar.
3) Duas instâncias menores são preferíveis por três razões: (1) Resiliência: com 2 × m6g.large, se uma instância falhar ou a AZ ficar indisponível, o sistema continua com 50% da capacidade — degradado mas funcionando. Com 1 × m6g.xlarge, qualquer falha causa 100% de downtime; (2) Auto Scaling mais granular: o ASG pode adicionar instâncias de 2 vCPU incrementalmente, ajustando a capacidade com mais precisão ao invés de dobrar tudo de uma vez; (3) Manutenção sem downtime: para update de AMI ou software, é possível terminar uma instância enquanto a outra serve tráfego. O único cenário onde a instância única faz sentido: aplicações stateful que não podem ser distribuídas (banco de dados single-node sem replicação, aplicação legada com estado em memória que não suporta balanceamento) — nesses casos, o SPOF já é inerente à arquitetura e não há ganho de HA com múltiplas instâncias.
