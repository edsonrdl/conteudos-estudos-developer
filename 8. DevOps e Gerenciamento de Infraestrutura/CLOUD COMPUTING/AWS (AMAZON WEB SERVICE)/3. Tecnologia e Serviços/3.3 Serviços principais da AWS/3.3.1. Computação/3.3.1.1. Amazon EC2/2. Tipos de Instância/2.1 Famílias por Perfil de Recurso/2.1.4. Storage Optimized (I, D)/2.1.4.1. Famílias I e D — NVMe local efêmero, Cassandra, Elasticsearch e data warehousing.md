### Famílias I e D — Storage Optimized: NVMe local efêmero e alta densidade de disco

As famílias I e D são projetadas para workloads onde o **armazenamento local — velocidade ou volume — é o recurso crítico**. Diferentemente de instâncias que dependem exclusivamente do EBS (rede), essas famílias incluem discos físicos diretamente conectados ao servidor, eliminando a latência de rede do storage e entregando IOPS e throughput que o EBS não consegue igualar em custo.

---

## O conceito central: Instance Store (armazenamento efêmero)

O Instance Store é um disco físico anexado ao host físico da instância — não é EBS, não passa pela rede. Isso tem implicações importantes:

```
Comparativo: EBS gp3 vs Instance Store NVMe
──────────────────────────────────────────────────────────────
                    │ EBS gp3 (máx)  │ Instance Store NVMe (I4i)
────────────────────┼────────────────┼──────────────────────────
Latência            │ ~1-2 ms        │ ~100-200 µs  (10x menor)
IOPS máximos        │ 16.000 (por vol)│ 1.000.000+ (por instância)
Throughput          │ 1.000 MiB/s    │ 40+ GiB/s
Persistência        │ Permanente     │ Efêmero (perdido ao parar)
Custo por GiB       │ $0.08/GB-mês   │ Incluso no preço da instância
──────────────────────────────────────────────────────────────
```

**Efêmero significa:** os dados do Instance Store são perdidos quando a instância é **parada** (stop), **terminada** (terminate) ou quando o host físico falha. O reboot preserva os dados.

Isso não é um problema para workloads que gerenciam replicação na camada da aplicação — como Cassandra, Elasticsearch e Kafka — onde cada nó armazena apenas uma parte dos dados e o cluster tolera perda de um nó.

---

## Família I — NVMe de alta velocidade

A família **I** é otimizada para **alto IOPS e baixa latência** com discos NVMe locais. É a escolha para bancos de dados NoSQL, search engines e qualquer workload que exija operações de I/O muito rápidas.

### Gerações disponíveis

| Instância | vCPU | RAM | NVMe local | IOPS leitura | Uso principal |
|---|---|---|---|---|---|
| **I4i.xlarge** | 4 | 32 GiB | 937 GiB | 200.000 | Cassandra, nó pequeno |
| **I4i.2xlarge** | 8 | 64 GiB | 1.875 GiB | 400.000 | Elasticsearch, nó médio |
| **I4i.4xlarge** | 16 | 128 GiB | 3.750 GiB | 800.000 | Kafka, nó padrão |
| **I4i.8xlarge** | 32 | 256 GiB | 7.500 GiB | 1.600.000 | HBase, nó grande |
| **I4i.16xlarge** | 64 | 512 GiB | 15.000 GiB | 3.200.000 | Clusters de alta densidade |
| **I4i.metal** | 128 | 1.024 GiB | 30.000 GiB | 6.400.000 | Bare metal, máxima I/O |
| **I3en** | vários | vários | até 60 TB | — | Alta capacidade (geração anterior) |

A família I4i usa processadores **Intel Ice Lake** com NVMe conectados via PCIe 4.0 — a latência é tipicamente abaixo de 200 microsegundos para leitura aleatória.

### Cassandra com família I

Apache Cassandra é o caso de uso canônico para a família I. Sua arquitetura é distribuída, sem nó central, com replicação configurável entre nós — o que torna a perda de um nó (e seus dados efêmeros) tolerável:

```
Cluster Cassandra com instâncias I4i (replication_factor=3):
┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│ i4i.4xlarge  │   │ i4i.4xlarge  │   │ i4i.4xlarge  │
│ NVMe: 3.7 TB │   │ NVMe: 3.7 TB │   │ NVMe: 3.7 TB │
│              │   │              │   │              │
│  Dados A,B,C │   │  Dados B,C,D │   │  Dados C,D,A │
│  (réplicas)  │   │  (réplicas)  │   │  (réplicas)  │
└──────┬───────┘   └──────┬───────┘   └──────┬───────┘
       └──────────────────┴──────────────────┘
                   Gossip Protocol
                   (nós se comunicam
                    diretamente)

Se um nó falha: os outros dois têm todas as réplicas.
O nó substituto sincroniza automaticamente via repair.
```

**Por que não usar EBS para Cassandra?** EBS tem latência de rede (~1-2ms) que multiplica pelo número de operações. Em cargas de escrita intensiva, o overhead de rede no EBS cria gargalos que a família I elimina completamente.

### Elasticsearch / OpenSearch com família I

Elasticsearch distribui índices em shards entre nós. Cada shard é essencialmente um índice Lucene que faz I/O intenso durante indexação e busca. Instâncias I permitem:
- Indexação mais rápida (menos tempo para tornar documentos buscáveis)
- Buscas com menor latência (leitura NVMe local vs EBS pela rede)
- Merges de segmentos Lucene sem impacto perceptível no cluster

### Kafka com família I

Kafka persiste mensagens em disco antes de confirmar ao produtor. Com EBS, cada mensagem confirmada envolve uma gravação em rede. Com NVMe local, a latência de write cai de ~1-2ms para ~100-200µs — crítico para pipelines de baixa latência.

## Família D — Alta densidade de HDD

A família **D** troca velocidade (IOPS) por **volume massivo de armazenamento magnético a baixo custo**. São instâncias com múltiplos discos HDD (até 336 TB por instância), projetadas para data warehouses e processamento em lote de grandes volumes.

| Instância | vCPU | RAM | HDD local | Throughput sequencial |
|---|---|---|---|---|
| `d3.xlarge` | 4 | 32 GiB | 6.9 TB (2× HDD) | Alta |
| `d3.2xlarge` | 8 | 64 GiB | 13.8 TB (4× HDD) | Alta |
| `d3.4xlarge` | 16 | 128 GiB | 27.6 TB (8× HDD) | Alta |
| `d3en.xlarge` | 4 | 32 GiB | 14 TB (2× HDD) | Muito alta |
| `d3en.8xlarge` | 32 | 256 GiB | 112 TB (16× HDD) | Muito alta |
| `d3en.metal` | 48 | 384 GiB | 336 TB (24× HDD) | Máxima |

### Casos de uso da família D

**Data warehousing distribuído (Hadoop HDFS):** clusters Hadoop que armazenam dados localmente em HDFS se beneficiam da família D. O padrão de acesso sequencial (leitura de blocos grandes) compensa a latência maior dos HDDs.

**ETL e processamento em lote de grandes volumes:** cargas que leem terabytes sequencialmente (log processing, batch analytics) são adequadas para D. O custo por TB é muito menor que NVMe ou EBS.

**Backup e arquivamento temporário:** dados que precisam estar acessíveis rapidamente mas não justificam o custo do S3 Glacier (que tem latência de horas) e nem o custo do EBS.

```
Quando usar I vs D:
────────────────────────────────────────────────────────────
Critério              │ Família I (NVMe)   │ Família D (HDD)
──────────────────────┼────────────────────┼────────────────
Latência de acesso    │ ~100-200 µs        │ ~5-10 ms
Acesso aleatório      │ Excelente          │ Ruim
Acesso sequencial     │ Excelente          │ Bom
Capacidade por inst.  │ Até 30 TB          │ Até 336 TB
Custo por TB          │ Alto               │ Baixo
Banco NoSQL           │ Ideal              │ Inadequado
HDFS / Hadoop         │ Funciona, caro     │ Ideal
Kafka / Elasticsearch │ Ideal              │ Inadequado
────────────────────────────────────────────────────────────
```

## Estratégias para lidar com a efemeridade do Instance Store

Como os dados são perdidos ao parar/terminar a instância, é necessário uma estratégia explícita:

### 1. Replicação na camada da aplicação (mais comum)

Cassandra, Elasticsearch e Kafka já replicam dados entre nós. A perda de um nó é um evento normal — o cluster tolera e recupera automaticamente.

```bash
# Exemplo: verificar status de replicação Cassandra após reiniciar nó
nodetool status

# Iniciar reparo para sincronizar dados no nó recuperado
nodetool repair -dc datacenter1
```

### 2. RAID com múltiplos volumes Instance Store

Quando a instância tem múltiplos discos NVMe (comum em `I4i.8xlarge` e maiores), é possível usar RAID 0 para throughput máximo ou RAID 1/10 para redundância local:

```bash
# RAID 0 com 4 discos NVMe para throughput máximo
mdadm --create /dev/md0 --level=0 --raid-devices=4 \
  /dev/nvme1n1 /dev/nvme2n1 /dev/nvme3n1 /dev/nvme4n1

mkfs.xfs /dev/md0
mount /dev/md0 /data
```

### 3. Snapshot periódico para EBS ou S3

Para dados que precisam sobreviver a paradas planejadas, scripts de snapshot transferem dados do Instance Store para EBS ou S3 antes do stop.

## Erros comuns e armadilhas

**Usar Instance Store sem replicação:** armazenar dados únicos (sem réplicas) no Instance Store é uma armadilha grave. Qualquer falha de hardware do host físico perde os dados permanentemente.

**Escolher família D para Cassandra:** HDDs têm latência de acesso aleatório muito alta (~5-10ms). Cassandra faz leituras aleatórias intensas — o resultado é degradação severa de performance. Sempre use NVMe (família I) para Cassandra.

**Não ajustar o sistema de arquivos para NVMe:** o sistema de arquivos padrão pode não estar otimizado para NVMe. Para workloads de I/O intenso, XFS com configurações específicas (noatime, nobarrier em casos de teste) pode dobrar o throughput observado.

**Confundir Instance Store com EBS:** ao criar AMIs de instâncias com Instance Store, os dados do disco local não são incluídos no snapshot da AMI. Apenas o volume raiz (EBS) é capturado.

## 🧩 Quiz de Fixação

1. Por que um cluster Cassandra pode usar instâncias com Instance Store efêmero sem risco de perda de dados, enquanto um banco PostgreSQL standalone não pode?

2. Você precisa armazenar 80 TB de logs históricos para análise batch semanal com Spark. O acesso é predominantemente sequencial. Família I ou D — qual escolher e por quê?

3. Um cluster Elasticsearch está com latência de indexação alta (>500ms por documento). O time quer migrar de `m6i.4xlarge` para instâncias storage-optimized. Que família você recomenda e qual métrica você monitoraria para confirmar a melhora?

**Respostas:**

1) Cassandra foi projetado com replicação distribuída como garantia de durabilidade — os dados são replicados em múltiplos nós (tipicamente replication_factor=3) de forma que a perda de um nó não resulta em perda de dados. O cluster detecta a falha, e ao substituir o nó, os dados são sincronizados automaticamente dos nós sobreviventes via `nodetool repair`. PostgreSQL standalone não tem esse mecanismo — é um único ponto de falha, e seus dados devem estar em armazenamento persistente (EBS) para sobreviver a eventos de infraestrutura.

2) Família **D**. O acesso predominantemente sequencial (leitura de grandes blocos para Spark) compensa a latência maior dos HDDs. A família D oferece até 336 TB por instância a custo por TB muito inferior à família I. Para 80 TB com acesso aleatório mínimo, pagar pelo NVMe de alta velocidade da família I seria desperdício — a família D entrega o throughput sequencial necessário a uma fração do custo.

3) Família **I** (ex: `i4i.4xlarge`). Elasticsearch faz I/O aleatório intenso durante indexação (escrita em segmentos Lucene) e busca (leitura de posting lists em disco). A migração de EBS gp3 (~1-2ms de latência) para NVMe local (~100-200µs) pode reduzir a latência de indexação em 5-10x. A métrica-chave para confirmar a melhora é o **indexing throughput** (documentos/segundo) no Elasticsearch Monitoring e a latência P99 de indexação — além do tempo de merge de segmentos, que aparece em `_cat/segments` e impacta diretamente a disponibilidade de buscas.
