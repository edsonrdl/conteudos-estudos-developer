### Família T — Burstable Performance e o modelo de CPU Credits

As instâncias da família T são as mais econômicas do EC2 para cargas de trabalho intermitentes. Elas introduzem um conceito único na AWS: o modelo de **Burstable Performance**, onde a instância recebe uma quantidade baseline de CPU e pode "estourar" (burst) acima disso usando créditos de CPU acumulados quando ociosa. Entender como esse modelo funciona é essencial para usá-las corretamente — e para evitar o problema silencioso de throttling de CPU que derruba a performance em produção.

---

## O modelo de CPU Credits

```
Conceito central: a instância T tem dois modos de operação

MODO BASELINE (créditos acumulando):
  CPU utilizada < baseline%
  → Instância acumula créditos a uma taxa constante
  → Créditos armazenados no "banco de créditos"
  → Limite de créditos: varia por tipo (banco máximo)

MODO BURST (créditos sendo consumidos):
  CPU utilizada > baseline%
  → Instância usa créditos para sustentar o burst
  → Cada crédito permite 1 vCPU a 100% por 1 minuto
  → Quando os créditos acabam: CPU throttled para o baseline
```

### Taxa de acúmulo e baseline por tipo

```
Tipo          vCPU  RAM    Baseline  Créditos/hora  Banco máximo
────────────  ────  ─────  ────────  ─────────────  ────────────
t3.nano       2     0.5GB  5%        6              144
t3.micro      2     1GB    10%       12             288
t3.small      2     2GB    20%       24             576
t3.medium     2     4GB    20%       24             576
t3.large      2     8GB    30%       36             864
t3.xlarge     4     16GB   40%       96             2.304
t3.2xlarge    8     32GB   40%       192            4.608

Interpretando baseline:
  t3.small (20% de baseline, 2 vCPUs):
  → Tem direito a usar 0.4 vCPU constantemente sem gastar créditos
  → Se usar 100% de 2 vCPUs: consome 5× mais rápido que acumula
  → Banco de 576 créditos: sustenta burst total por ~2.4 horas
```

### Visualizando o fluxo de créditos

```
t3.small ao longo de um dia de trabalho típico:

00:00 - 08:00 (instância ociosa):
  CPU: 2-3%  (abaixo do baseline de 20%)
  → Acumula 24 créditos/hora × 8h = 192 créditos
  → Banco: começa em 0, vai para 192

09:00 - 11:00 (deploy e compilação pesada):
  CPU: 95% (muito acima do 20% de baseline)
  → Gasta créditos para sustentar o burst
  → Deficit: (95% - 20%) = 75% de gasto extra
  → Em 2 vCPUs: usando 1.9 vCPU extra = 1.9 créditos/min = 114/hora
  → 2 horas × 114/hora = 228 créditos gastos
  → Banco: 192 - 228 = NEGATIVO → CPU throttled!

11:30 (após throttling, compilação lenta):
  CPU forçada para 20% (baseline)
  → Developer nota que a build ficou 5× mais lenta
  → Confunde com problema de código ou dependência

Lição: T3 pequena para build de Java/Go/Rust = má ideia
       T3 para servidor web com picos curtos = ótima ideia
```

## Modo Unlimited — burst sem throttling (com custo)

```
Por padrão (Standard mode):
  Quando banco de créditos = 0 → CPU throttled para baseline
  Sem custo extra

Modo Unlimited (opt-in):
  Instância pode burst ALÉM dos créditos disponíveis
  AWS cobra $0.05 por vCPU-hora extra de burst
  CPU nunca é throttled
  
Ativar:
  aws ec2 modify-instance-credit-specification \
    --instance-id i-xxx \
    --instance-credit-specifications '[{"CpuCredits":"unlimited"}]'

Quando usar Unlimited:
  ├── Workloads com bursts imprevisíveis que não podem ser throttled
  ├── Dev servers onde performance inconsistente causa confusão
  └── Quando você quer a economia do T3 mas sem risco de throttling

Custo do Unlimited na prática:
  t3.small, burst de 100% por 1 hora extra além dos créditos:
  → 2 vCPUs × 80% de burst extra (100% - 20% baseline) × 1 hora
  → 1.6 vCPU-horas × $0.05 = $0.08 de custo extra
  → vs. t3.small: $0.02/hora = 4× mais caro aquela hora
  → t3.medium (Standard) = $0.032/hora; t3.medium com burst = similar a m6i
  
  Alerta: Unlimited mal configurado pode custar mais que instância M
  → Monitorar métrica: CPUSurplusCreditBalance e CPUSurplusCreditsCharged
```

## Geração atual — T3 vs T3a vs T4g

```
T3 (Intel Skylake/Cascade Lake):
  → Processadores Intel Xeon
  → Baseline amplamente suportado
  → t3.micro: $0.0104/hora (us-east-1, Linux)

T3a (AMD EPYC):
  → Mesmo perfil que T3
  → ~10% mais barato por mesma capacidade
  → t3a.micro: $0.0094/hora (us-east-1, Linux)
  → Escolha padrão se você não tem razão para Intel

T4g (AWS Graviton2, ARM):
  → ARM64 — requer SO/software compatível
  → ~40% mais barato que T3 para mesma capacidade
  → ~20% melhor performance por dólar que T3
  → t4g.micro: $0.0084/hora (us-east-1, Linux)
  → GRATUITO: t4g.micro tem free tier permanente expandido
  
Comparativo de custo mensal (24/7):
  t3.small:  $0.0208/h × 720h = $14.98/mês
  t3a.small: $0.0188/h × 720h = $13.54/mês  (-10%)
  t4g.small: $0.0168/h × 720h = $12.10/mês  (-19%)
  
  Para novos projetos: t4g sempre que o software suportar ARM
```

## Quando usar a família T — guia prático

### ✓ Ideal para

```
1. Ambientes de desenvolvimento e staging:
   → Dev server: longos períodos ociosos (offline), bursts curtos
   → IDE remoto (VS Code Server, JetBrains Gateway)
   → Banco de desenvolvimento local

2. Servidores web de baixo tráfego:
   → Sites institucionais, landing pages, MVPs
   → Tráfego irregular: 0 usuários à noite, picos durante o dia
   → Blogs, portfólios, documentação

3. Serviços internos de baixo uso:
   → Monitoramento interno (Prometheus, Grafana leve)
   → Serviços de autenticação (Keycloak para poucos usuários)
   → Ferramentas DevOps com uso intermitente (Jenkins ocasional)

4. Bancos de dados de desenvolvimento:
   → MySQL/PostgreSQL de dev: usado durante builds e testes
   → Redis para cache de dev: idle na maior parte do tempo

5. Bastion hosts e jump servers:
   → Usados apenas para acessar a infra (poucos minutos/dia)
   → t3.nano ou t3.micro são perfeitos e ultra-baratos
```

### ✗ Evitar para

```
1. Compilações pesadas contínuas:
   → Java, Go, Rust, C++: consome CPU constantemente
   → Builder de CI/CD que compila continuamente = throttling garantido

2. Servidores de aplicação com carga constante:
   → APIs com tráfego contínuo durante horas de pico
   → Se CPU fica > baseline por horas: use família M

3. Bancos de dados de produção:
   → MySQL/PostgreSQL de produção com queries constantes
   → Throttling de CPU afeta latência de queries críticas

4. Machine Learning e processamento pesado:
   → Qualquer workload que precisa de CPU alta e constante
   → Use C (compute optimized) ou instâncias com GPU

5. Microsserviços que precisam de latência consistente:
   → Throttling de CPU introduz spikes de latência imprevisíveis
   → SLA de latência p99 → impossível garantir com T throttled
```

## Monitorando saúde de créditos no CloudWatch

```
Métricas essenciais para instâncias T:

CPUCreditBalance:
  → Créditos disponíveis no banco
  → Ideal: nunca chegar a zero (modo Standard)
  → Alarm: CPUCreditBalance < 30 → aviso
  → Alarm: CPUCreditBalance < 5 → crítico (throttling iminente)

CPUCreditUsage:
  → Créditos consumidos por período
  → Alto e constante = seu workload está além do baseline
  → Sinal para fazer upgrade para família M

CPUSurplusCreditsCharged (apenas Unlimited):
  → Créditos extras cobrados além do banco
  → Alto = Unlimited está te custando caro
  → Comparar: custo do surplus vs. custo de upgrade para M

CPUSurplusCreditBalance:
  → Débito de créditos no modo Unlimited
  → Se sempre positivo: você deveria usar família M

Dashboard recomendado para servidor T3 de produção:
  ├── CPUCreditBalance (gráfico de linha - tendência)
  ├── CPUUtilization vs baseline (linha horizontal)
  └── CPUSurplusCreditsCharged (detectar custos hidden)

Script para verificar todas instâncias T com crédito baixo:
  aws cloudwatch get-metric-statistics \
    --namespace AWS/EC2 \
    --metric-name CPUCreditBalance \
    --dimensions Name=InstanceId,Value=i-xxx \
    --start-time $(date -u -d '1 hour ago' +%Y-%m-%dT%H:%M:%S) \
    --end-time $(date -u +%Y-%m-%dT%H:%M:%S) \
    --period 300 \
    --statistics Average
```

## Tomando a decisão: T vs M

```
Regra prática simples:

CPU utilização média nos horários de pico > baseline%?
  Sim → Use família M (general purpose sem burst)
  Não → T pode ser adequada, monitore os créditos

Baseline por tipo de T3:
  t3.nano/micro: 5-10% → qualquer uso real vai burstar
  t3.small/medium: 20% → aguenta carga web leve
  t3.large/xlarge: 30-40% → suporta mais, ainda burst

Exemplo de decisão:
  API Node.js com 50 req/s, CPU média de 15%:
  → t3.medium: baseline 20% > 15% → acumulando créditos ✓
  → Picos de 80% por 5 minutos → usa créditos, depois reacumula ✓
  → t3.medium é adequado
  
  API Node.js com 200 req/s, CPU média de 45%:
  → t3.medium: baseline 20% < 45% → sempre consumindo créditos ✗
  → Banco esgota em horas → throttling silencioso
  → Upgrade para m6i.medium ou c6i.medium ✓
```

## 🧩 Quiz de Fixação

1. Uma instância t3.small tem baseline de 20% de CPU. Ela ficou ociosa a noite toda (8 horas) acumulando créditos. De manhã, uma compilação Java consome 100% de CPU por 2 horas. Calcule se os créditos são suficientes para os 2 horas de burst e o que acontece quando acabam.
2. Um time usa t3.medium no modo Standard para um servidor de API de produção. Em dias de pico (segunda-feira de manhã), usuários reclamam que a API fica lenta por ~30 minutos e depois normaliza. Qual é o diagnóstico mais provável e como confirmar?
3. Qual é a diferença fundamental entre t3.small Standard e t3.small Unlimited, e por que usar Unlimited indiscriminadamente pode resultar em uma fatura surpreendente?

**Respostas:**
1) Cálculo de créditos: t3.small acumula 24 créditos/hora × 8 horas = 192 créditos. Cada crédito = 1 vCPU a 100% por 1 minuto. Com 2 vCPUs a 100% (full burst): gasta 2 créditos/minuto. Com baseline de 20% já coberto sem crédito: gasta apenas (100% - 20%) × 2 vCPUs = 1.6 créditos/minuto para o burst extra. Em 2 horas (120 minutos): 120 × 1.6 = 192 créditos — exatamente o que foi acumulado! Os créditos acabam precisamente no final das 2 horas. A partir daí, CPU throttled para 20% (baseline). A compilação Java, que rodava em 15 minutos com CPU plena, passaria a levar 75 minutos (5× mais lento) pelo throttling, e o desenvolvedor notaria uma lentidão abrupta.
2) Diagnóstico: a instância t3.medium de produção tem baseline de 20%. Segunda de manhã, ao retornar os usuários com tráfego alto, a CPU dispara acima de 20% e começa a consumir créditos acumulados durante o fim de semana. O banco de créditos dura aproximadamente 30-60 minutos de tráfego intenso, após o qual a CPU é throttled para 20% — causando a lentidão relatada. Como confirmar: no CloudWatch, verificar o gráfico de CPUCreditBalance no horário do incidente — se mostrar uma linha caindo de ~576 até zero seguida de queda abrupta na performance, é o diagnóstico correto. Também verificar CPUUtilization ultrapassando 20% de forma consistente nesse horário. Solução: migrar para m6i.medium (sem CPU Credits) ou habilitar Unlimited se os picos forem curtos e toleráveis financeiramente.
3) t3.small Standard: quando o banco de créditos chega a zero, a CPU é fisicamente limitada (throttled) ao baseline de 20%. Zero custo extra mas com degradação garantida de performance. t3.small Unlimited: a CPU nunca é throttled — pode burst indefinidamente, mas cada vCPU-hora de burst extra além dos créditos custa $0.05. O risco financeiro: se uma aplicação roda consistentemente com CPU acima do baseline (ex: 80% o dia todo), o custo de surplus pode facilmente ultrapassar o custo de uma instância m6i. Exemplo: t3.small ($0.0208/hora) com 60% de surplus de CPU por 720 horas/mês = 1.2 vCPU × 720 × $0.05 = $43.20 de surplus + $14.98 da instância = $58.18/mês, enquanto m6i.medium (sem burst problems) custaria $30.24/mês. Unlimited deve ser monitorado com alarme em CPUSurplusCreditsCharged para detectar esse cenário antes da fatura.
