### Famílias R, X e z — Memory Optimized: quando RAM é o recurso crítico

As famílias R, X e z são projetadas para workloads onde a memória RAM é o gargalo — seja porque o conjunto de dados precisa caber inteiramente na memória para performance aceitável, seja porque a aplicação exige GiBs massivos por instância. São as instâncias mais caras por unidade de vCPU, mas indispensáveis quando a alternativa é trocar dados com disco (o que destrói latência e throughput).

---

## Por que memória é o gargalo em algumas cargas

A maioria das aplicações web tolera ter dados no disco porque o padrão de acesso é previsível e cacheável. Mas algumas cargas não toleram:

```
Custo de acesso relativo (ordens de magnitude):
─────────────────────────────────────────────────
Registrador CPU    │  ~0.3 ns
Cache L1           │  ~1 ns
Cache L3           │  ~10 ns
RAM (DRAM)         │  ~100 ns          ← teto aceitável
NVMe SSD           │  ~100.000 ns      ← 1.000x mais lento
HDD                │  ~10.000.000 ns   ← 100.000x mais lento
─────────────────────────────────────────────────
```

Bancos de dados in-memory, engines analíticas e ERPs como SAP HANA foram projetados assumindo que **todos os dados ativos cabem na RAM**. Se não couberem, a performance degrada catastroficamente — não gradualmente.

---

## Família R — Memory Optimized de uso geral

A família **R** é a entrada no segmento memory-optimized. Oferece ~8 GiB de RAM por vCPU — o dobro da família M e quatro vezes a família C.

### Gerações disponíveis

| Instância | Processador | Máx. memória | Destaque |
|---|---|---|---|
| **R8g** | Graviton4 | 1.536 GiB | Geração mais nova; melhor desempenho/$ |
| **R7g** | Graviton3 | 512 GiB | Boa relação custo/desempenho para Linux |
| **R7i** | Intel Xeon Sapphire Rapids | 1.536 GiB | Compatibilidade x86, AVX-512 |
| **R7a** | AMD EPYC Genoa | 1.536 GiB | Alternativa AMD para cargas x86 |
| **R6g / R6i** | Graviton2 / Intel Ice Lake | 512 GiB | Geração anterior, ainda amplamente usada |

### Casos de uso da família R

**Bancos de dados relacionais com working set grande:** RDS com PostgreSQL ou MySQL em instâncias R permite manter buffer pools maiores, reduzindo drasticamente disk I/O. Uma `r7g.4xlarge` (128 GiB) costuma ser mais eficiente que escalar disco em instâncias M.

**Caches distribuídos:** ElastiCache (Redis/Memcached) e clusters Redis self-managed. O objetivo é manter o máximo possível de chaves na memória para evitar cache misses.

**Apache Spark e processamento analítico:** Spark distribui dados entre executores em memória. Executores com pouca RAM sofrem spill to disk — a operação mais lenta no Spark. Instâncias R permitem executores maiores com menos spill.

**Bancos de dados em tempo real e jogos:** partidas multiplayer com estado de jogo complexo, leaderboards e sessões de usuário que precisam de acesso sub-milissegundo.

```
Exemplo: cluster Spark com instâncias R vs M
─────────────────────────────────────────────────────────────────
r7g.4xlarge: 16 vCPU, 128 GiB RAM → executor pode ter 100 GiB
m7g.4xlarge: 16 vCPU,  64 GiB RAM → executor com 50 GiB → spill frequente

Para datasets de 80 GiB por executor: R elimina o spill completamente.
─────────────────────────────────────────────────────────────────
```

## Família X — Memória extrema para SAP HANA e workloads Enterprise

A família **X** vai além do que a R oferece — são instâncias com até **6 TiB de RAM por instância**, projetadas para os workloads mais exigentes em memória do mercado.

| Instância | vCPU | Memória | Uso típico |
|---|---|---|---|
| `x2idn.16xlarge` | 64 | 1.024 GiB | SAP HANA médio porte |
| `x2idn.32xlarge` | 128 | 2.048 GiB | SAP HANA grande porte |
| `x2iedn.32xlarge` | 128 | 4.096 GiB | SAP HANA / Oracle EBS muito grandes |
| `x2iedn.metal` | 128 | 4.096 GiB | Bare metal, sem hypervisor |
| `x1e.32xlarge` | 128 | 3.904 GiB | Geração anterior, ainda usada |

### SAP HANA: o caso de uso principal

SAP HANA é um banco de dados in-memory projetado para processar transações OLTP e análise OLAP simultaneamente — o que o SAP chama de HTAP (Hybrid Transactional/Analytical Processing). Para funcionar, **todo o banco de dados deve caber na RAM**. Um sistema SAP S/4HANA médio exige entre 512 GiB e 2 TiB de RAM.

```
Arquitetura SAP HANA na AWS com instâncias X:
┌──────────────────────────────────────────────────┐
│           x2iedn.32xlarge (2 TiB RAM)            │
│  ┌─────────────────┐  ┌────────────────────────┐ │
│  │  OLTP Engine    │  │  OLAP / Analytics      │ │
│  │  (transações)   │  │  (relatórios em tempo  │ │
│  │                 │  │   real sobre dados      │ │
│  │                 │  │   transacionais)        │ │
│  └────────┬────────┘  └──────────┬─────────────┘ │
│           └──────────┬───────────┘               │
│              ┌───────▼────────┐                  │
│              │  In-Memory DB  │                  │
│              │  (dados ativos │                  │
│              │   na RAM)      │                  │
│              └───────────────┘                  │
└──────────────────────────────────────────────────┘
```

**Por que não usar instâncias menores com múltiplos nós?** SAP HANA escala verticalmente por design — a arquitetura assume dados locais na memória. Embora exista SAP HANA Scale-Out (múltiplos nós), escalar verticalmente com instâncias X é mais simples, mais barato de operar e evita overhead de rede entre nós.

### Outros casos de uso da família X

- **Oracle Database** com licença BYOL e large SGA (System Global Area)
- **Microsoft SQL Server Enterprise** com grandes buffer pools
- **Genomics e bioinformática** — análise de grandes genomas inteiros na memória
- **ERP on-premises migrado para cloud** com requisito de RAM alto

## Família z — Alta frequência de clock + memória

A família **z1d** é única no catálogo EC2: combina processadores com **até 4.0 GHz de frequência de clock** com memória alta. Enquanto outras instâncias priorizam throughput por núcleo, a z1d prioriza **latência de operações single-threaded**.

| Instância | vCPU | Memória | Clock | Uso típico |
|---|---|---|---|---|
| `z1d.large` | 2 | 16 GiB | 4.0 GHz | EDA leve |
| `z1d.xlarge` | 4 | 32 GiB | 4.0 GHz | Simulações menores |
| `z1d.2xlarge` | 8 | 64 GiB | 4.0 GHz | CAD, EDA médio |
| `z1d.6xlarge` | 24 | 192 GiB | 4.0 GHz | EDA e simulações grandes |
| `z1d.metal` | 48 | 384 GiB | 4.0 GHz | Bare metal, EDA de alta precisão |

### Por que frequência de clock importa

Muitas simulações de EDA (Electronic Design Automation) e CAD são fundamentalmente **single-threaded ou de baixo paralelismo** — o software não consegue distribuir o trabalho por muitos núcleos. Nesses casos, adicionar mais vCPUs não ajuda; o que importa é a velocidade de cada ciclo de clock.

```
Comparativo de quando usar z1d vs R vs C:
───────────────────────────────────────────────────────────────────
Workload                    │ Família ideal │ Motivo
───────────────────────────────────────────────────────────────────
EDA (SPICE simulation)      │ z1d           │ Single-thread + memória
Transcoding 4K              │ C             │ Multi-thread, CPU-bound
SAP HANA 1 TiB              │ X             │ Memória massiva
Redis cluster               │ R             │ Memória, multi-nó
Spark com datasets grandes  │ R             │ Memória por executor
Oracle OLTP com SGA grande  │ R ou X        │ Buffer pool na RAM
───────────────────────────────────────────────────────────────────
```

## Como identificar que memória é o gargalo

Antes de migrar para instâncias memory-optimized, confirme que memória é de fato o problema:

**Sinais no Linux (via CloudWatch ou `free`, `vmstat`):**

| Métrica | Sinal de problema |
|---|---|
| `MemAvailable` < 10% | Memória quase esgotada |
| `SwapUsed` > 0 | Swap ativo = disco sendo usado como RAM |
| `BufferCacheHitRatio` (DB) < 90% | Buffer pool muito pequeno |
| Disk IOPS muito alto | Possível swap ou spill to disk |
| `kswapd` com CPU alta | Kernel trocando páginas agressivamente |

**Comando rápido para verificar pressão de memória:**
```bash
# Ver uso de memória e swap em tempo real
watch -n 2 'free -h && echo "---" && vmstat -s | grep -E "swap|memory"'

# Ver se há processos usando swap
for pid in /proc/*/status; do
  awk '/VmSwap/{if($2>0) print FILENAME, $2" kB"}' $pid 2>/dev/null
done | sort -k2 -rn | head -10
```

## Erros comuns e armadilhas

**Escolher memory-optimized sem medir:** provisionar uma `r7i.4xlarge` quando uma `m7i.2xlarge` com ajuste de buffer pool resolveria é desperdício. Sempre meça antes.

**Ignorar a família R em favor do X por "segurança":** instâncias X custam 3-5x mais que R equivalentes. Se o banco cabe em 512 GiB, uma `r8g.16xlarge` (512 GiB) é muito mais econômica que uma `x2idn.16xlarge`.

**Usar z1d para cargas paralelas:** a frequência alta da z1d só importa para código single-threaded. Para cargas altamente paralelas, C ou M são mais eficientes e baratas.

**Não usar Reserved Instances para SAP HANA:** instâncias X são caras no On-Demand. Workloads SAP HANA são 24/7 por natureza — Reserved Instances de 1 ou 3 anos geram economia de 40-70%.

## 🧩 Quiz de Fixação

1. Sua aplicação usa Redis como cache com 200 GiB de dados ativos. O servidor atual tem 256 GiB de RAM e está com 95% de utilização, causando evicções frequentes. Qual família EC2 você escolheria para escalar e por quê?

2. Um cliente quer migrar o SAP S/4HANA com banco de 800 GiB para a AWS. Por que instâncias X são necessárias em vez de múltiplas instâncias R menores em cluster?

3. Uma equipe de chip design usa SPICE para simulações de circuito analógico. O software é single-threaded e precisa de 96 GiB de RAM por simulação. Qual família EC2 é mais adequada e por que não seria a família R?

**Respostas:**

1) Família **R** — especificamente uma `r7g.8xlarge` (256 GiB) ou `r7g.12xlarge` (384 GiB) para ter folga. A família R foi criada exatamente para caches Redis e workloads que precisam manter grandes volumes de dados na memória. Com ~8 GiB por vCPU, oferece a melhor relação custo/memória para esse caso. A alternativa seria aumentar o cluster Redis com mais nós menores, mas isso aumenta a complexidade operacional.

2) SAP HANA não escala horizontalmente de forma nativa para todos os casos — sua arquitetura assume que os dados estão localmente na memória do mesmo servidor. O scale-out existe mas adiciona latência de rede entre nós e complexidade operacional significativa. Instâncias X entregam até 4 TiB em um único servidor, que é como SAP HANA foi projetado para operar. Para 800 GiB, uma `x2idn.16xlarge` (1.024 GiB) resolve com folga para crescimento.

3) Família **z1d**. O simulador SPICE é single-threaded, então ter mais vCPUs (que a família R oferece em grande quantidade) não ajuda. O que determina o tempo de simulação é a velocidade de cada ciclo de CPU — e a `z1d` entrega até **4.0 GHz**, a maior frequência de clock do catálogo EC2. Uma `z1d.6xlarge` (24 vCPU, 192 GiB) atenderia a necessidade de 96 GiB com excelente performance single-thread, algo que uma `r7i` equivalente em memória não replicaria por rodar em frequências menores (~3.2 GHz).
