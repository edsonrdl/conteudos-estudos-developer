### Accelerated Computing — GPU e chips especializados: P, G, Trainium e Inferentia

As famílias de Accelerated Computing existem porque CPUs convencionais — por mais rápidas que sejam — são fundamentalmente inadequadas para certas classes de problemas. Treinamento de modelos de ML, inferência de alta escala e renderização 3D envolvem operações matemáticas massivamente paralelas que GPUs e chips especializados executam centenas de vezes mais rápido que CPUs equivalentes em custo.

---

## Por que aceleração de hardware importa

CPUs são otimizadas para execução serial rápida — poucos núcleos altamente complexos, com branch prediction, cache hierárquico e execução fora de ordem. GPUs e aceleradores invertem esse trade-off: milhares de núcleos simples, todos executando a mesma operação em paralelo.

```
CPU vs GPU — arquitetura e paralelismo:
┌─────────────────────────────┐  ┌──────────────────────────────────┐
│         CPU (ex: Xeon)      │  │        GPU (ex: A100)            │
│                             │  │                                  │
│  ┌────┐ ┌────┐ ┌────┐ ┌────┐│  │ ┌─┐┌─┐┌─┐┌─┐┌─┐┌─┐┌─┐┌─┐┌─┐┌─┐│
│  │Core│ │Core│ │Core│ │Core││  │ │C││C││C││C││C││C││C││C││C││C││
│  │    │ │    │ │    │ │    ││  │ └─┘└─┘└─┘└─┘└─┘└─┘└─┘└─┘└─┘└─┘│
│  └────┘ └────┘ └────┘ └────┘│  │ (×6.912 CUDA cores no A100)     │
│                             │  │                                  │
│  Bom para: lógica complexa, │  │  Bom para: multiplicação de      │
│  I/O, latência baixa        │  │  matrizes, operações paralelas   │
└─────────────────────────────┘  └──────────────────────────────────┘

Multiplicação de matriz 4096×4096:
  CPU (64 cores): ~10 segundos
  GPU A100:       ~0.01 segundos  (1000x mais rápido)
```

## Família P — ML Training de alta escala

A família **P** é a linha de topo para **treinamento de modelos de deep learning**. Usa GPUs NVIDIA de datacenter (A100, H100) com NVLink para comunicação GPU-a-GPU de altíssima banda.

### Gerações e GPUs

| Instância | GPUs | GPU Model | VRAM total | GPU Interconnect | Uso |
|---|---|---|---|---|---|
| `p3.2xlarge` | 1 | NVIDIA V100 | 16 GiB | — | Treinamento pequeno/médio |
| `p3.8xlarge` | 4 | V100 | 64 GiB | NVLink | Multi-GPU médio |
| `p3.16xlarge` | 8 | V100 | 128 GiB | NVLink | Multi-GPU grande |
| `p4d.24xlarge` | 8 | A100 (40GiB) | 320 GiB | NVLink 3.0 | LLMs médios |
| `p4de.24xlarge` | 8 | A100 (80GiB) | 640 GiB | NVLink 3.0 | LLMs grandes |
| `p5.48xlarge` | 8 | H100 (80GiB) | 640 GiB | NVLink 4.0 + 3200 Gbps EFA | LLMs de fronteira |

A `p5.48xlarge` com H100 é a instância de maior performance do catálogo EC2 para ML — inclui **3.200 Gbps de rede EFA** (Elastic Fabric Adapter) para clusters multi-instância via AWS UltraCluster.

### Treinamento distribuído com família P

Modelos grandes (GPT-4, Llama 3, etc.) não cabem em uma única GPU. O treinamento distribuído divide o trabalho de formas diferentes:

```
Estratégias de paralelismo para treinamento distribuído:

1. Data Parallelism — mesmo modelo, dados diferentes
   ┌──────────┐  ┌──────────┐  ┌──────────┐
   │ GPU 0    │  │ GPU 1    │  │ GPU 2    │
   │ Modelo A │  │ Modelo A │  │ Modelo A │  ← cópia igual
   │ Batch 0  │  │ Batch 1  │  │ Batch 2  │  ← dados diferentes
   └────┬─────┘  └────┬─────┘  └────┬─────┘
        └─────────────┴─────────────┘
              AllReduce de gradientes

2. Model Parallelism — modelo dividido entre GPUs
   ┌──────────┐  ┌──────────┐  ┌──────────┐
   │ GPU 0    │  │ GPU 1    │  │ GPU 2    │
   │ Camadas  │  │ Camadas  │  │ Camadas  │
   │ 1-10     │→ │ 11-20    │→ │ 21-30    │
   └──────────┘  └──────────┘  └──────────┘

3. Tensor Parallelism — operações divididas dentro de uma camada
   (comum em transformers com cabeças de atenção)
```

## Família G — GPU para inferência e renderização

A família **G** usa GPUs NVIDIA voltadas para **inferência de ML em produção e renderização gráfica**. Custo menor que a família P, com GPUs menos potentes para treinamento mas adequadas para inferência.

| Instância | GPUs | GPU Model | VRAM total | Caso de uso |
|---|---|---|---|---|
| `g4dn.xlarge` | 1 | T4 (16 GiB) | 16 GiB | Inferência pequena, dev |
| `g4dn.12xlarge` | 4 | T4 (16 GiB) | 64 GiB | Inferência em lote |
| `g5.xlarge` | 1 | A10G (24 GiB) | 24 GiB | Inferência LLM médio |
| `g5.48xlarge` | 8 | A10G (24 GiB) | 192 GiB | Inferência LLM grande |
| `g6.xlarge` | 1 | L4 (24 GiB) | 24 GiB | Inferência eficiente |
| `g6e.48xlarge` | 8 | L40S (48 GiB) | 384 GiB | Inferência + renderização |

### Inferência de ML com família G

A diferença entre treinamento e inferência muda radicalmente qual hardware é adequado:

```
Treinamento vs Inferência — requisitos diferentes:
──────────────────────────────────────────────────────────────
                  │ Treinamento          │ Inferência
──────────────────┼──────────────────────┼──────────────────────
Objetivo          │ Otimizar parâmetros  │ Executar forward pass
Precisão numérica │ FP32 / BF16          │ INT8, FP16, INT4
VRAM necessária   │ Modelo + gradientes  │ Só o modelo
Latência          │ Não crítica          │ Crítica (ms)
Throughput        │ Importante           │ Importante
GPU ideal         │ A100, H100           │ T4, A10G, L4
──────────────────────────────────────────────────────────────
```

**g4dn com T4** é a referência de custo-benefício para inferência. O T4 tem Tensor Cores para INT8 e FP16, permitindo quantização de modelos sem perda significativa de qualidade — um modelo que precisaria de 40 GiB em FP32 pode rodar em 10 GiB com INT8.

### Renderização com família G

Para renderização 3D (Unreal Engine, Blender, DCC tools), workstations virtuais e streaming de aplicações gráficas, as instâncias G oferecem GPUs com suporte a OpenGL, DirectX e Vulkan via NVIDIA GRID/VGPU.

## Trainium — Chip da AWS para treinamento de ML

**AWS Trainium** é o chip customizado da AWS para treinamento de deep learning, disponível nas instâncias da família **Trn**. É uma alternativa às GPUs NVIDIA com melhor relação custo/performance para workloads específicos.

| Instância | Chips Trainium | Memória HBM | Rede | Uso |
|---|---|---|---|---|
| `trn1.2xlarge` | 1 | 32 GiB | 12.5 Gbps | Dev, modelos pequenos |
| `trn1.32xlarge` | 16 | 512 GiB | 800 Gbps EFA | Treinamento em larga escala |
| `trn1n.32xlarge` | 16 | 512 GiB | 1.600 Gbps EFA | Clusters multi-instância |

### Como o Trainium funciona

O Trainium usa a arquitetura **NeuronCore-v2** — um acelerador de matriz otimizado para operações de multiplicação de matrizes em BF16 e FP32. A AWS desenvolveu o **AWS Neuron SDK** para compilar modelos PyTorch e TensorFlow para o Trainium:

```python
# Compilando um modelo PyTorch para Trainium com Neuron SDK
import torch
import torch_neuronx

model = MyTransformerModel()
model.load_state_dict(torch.load("weights.pt"))

# Compilar para NeuronCore
example_input = torch.zeros([batch_size, seq_len], dtype=torch.long)
model_neuron = torch_neuronx.trace(model, example_input)

# Salvar modelo compilado
torch.jit.save(model_neuron, "model_neuron.pt")
```

**Vantagem de custo:** instâncias Trn1 costam ~30-40% menos que instâncias P4 equivalentes para treinamento de transformers. A desvantagem é que o ecossistema Neuron SDK é menos maduro que CUDA — modelos precisam de adaptação.

## Quando usar cada família de aceleração

```
Árvore de decisão para escolha de acelerador:
                                                
Qual é o workload?
│
├── Treinamento de modelo
│     │
│     ├── Modelo grande (>10B parâmetros) ──→ P5 (H100) ou Trn1
│     ├── Modelo médio (1B-10B) ──────────→ P4 (A100) ou Trn1
│     └── Modelo pequeno (<1B) ───────────→ P3 (V100) ou G5
│
├── Inferência em produção
│     │
│     ├── LLM (>7B parâmetros) ──────────→ G5 (A10G), Inf2 ou G6e
│     ├── Modelo médio / BERT-like ───────→ G4dn (T4) ou Inf1
│     └── Modelo pequeno / latência crítica→ Inf1 (melhor custo/req)
│
└── Renderização / VDI / Streaming
      └─────────────────────────────→ G4dn, G5, G6e (NVIDIA GRID)
```

## Erros comuns e armadilhas

**Usar família P para inferência:** as GPUs A100/H100 são superdimensionadas e caras para inferência. Uma `p4d.24xlarge` (~$32/h) pode fazer a mesma inferência que várias `g4dn.xlarge` (~$0.53/h cada) com custo muito maior.

**Ignorar a VRAM como limitação:** o modelo precisa caber na VRAM da GPU. Um modelo LLaMA-3 70B em FP16 requer ~140 GiB de VRAM — isso exige múltiplas GPUs (ex: `g5.48xlarge` com 192 GiB) ou quantização (INT4/INT8 para ~35-70 GiB).

**Não compilar para Inferentia/Trainium antes de comparar:** esses chips requerem compilação prévia com o Neuron SDK. Comparar performance sem compilar é inválido — o modelo roda em fallback lento.

**Subestimar o overhead de inicialização:** GPUs demoram alguns segundos para carregar o modelo na VRAM. Para inferência serverless de baixa frequência, o cold start de GPU pode ser um problema maior que a latência de inferência em si.

## 🧩 Quiz de Fixação

1. Você precisa fazer inferência de um modelo BERT-large (330M parâmetros) em produção, processando 1.000 requisições/segundo com latência máxima de 50ms. Considerando custo como prioridade, qual família você escolheria entre G4dn, P4 e Inf1?

2. Qual é a diferença fundamental entre as famílias P e G, e por que usar G para treinamento seria um erro?

3. Um time quer treinar um modelo de linguagem de 7 bilhões de parâmetros. O modelo em BF16 ocupa ~14 GiB de VRAM. Por que ainda assim uma única GPU de 16 GiB (como a T4) seria insuficiente para o treinamento, mesmo que o modelo "caiba"?

**Respostas:**

1) **Inf1** — especificamente `inf1.6xlarge`. Para inferência de BERT-large em alta escala, o Inferentia entrega o menor custo por requisição (~$0.12/1M req vs $0.16 na G4dn). A G4dn (T4) é uma boa segunda opção, mas o Inferentia foi projetado especificamente para esse perfil. A família P4 seria um erro — é otimizada para treinamento, custa ~27x mais por hora que a G4dn, e o throughput de inferência não justifica o custo.

2) A família P usa GPUs de datacenter de alta performance (V100, A100, H100) com NVLink de alta banda, otimizadas para o ciclo de treinamento: forward pass + backward pass + atualização de pesos com precisão FP32/BF16. A família G usa GPUs de menor custo (T4, A10G, L4) otimizadas para forward pass (inferência) e renderização. Usar G para treinamento é um erro porque as GPUs da família G têm menor poder de processamento em FP32 (o T4 tem ~8 TFLOPS FP32 vs 312 TFLOPS BF16 do A100), menor memória HBM e a ausência de NVLink (comunicação GPU-GPU vai pelo barramento PCI, muito mais lento) torna o treinamento multi-GPU ineficiente.

3) Durante o treinamento, a GPU precisa armazenar na VRAM muito mais do que apenas os pesos do modelo: os **gradientes** (mesma memória dos pesos: ~14 GiB adicionais em BF16), os **estados do otimizador** (Adam armazena dois momentos por parâmetro: ~56 GiB em FP32), e as **ativações intermediárias** de cada camada durante o forward pass (variável, mas pode adicionar mais 10-30 GiB para seq_len longo). O total realista para treinar 7B parâmetros com Adam é de ~112-140 GiB de VRAM — muito além dos 16 GiB da T4. Técnicas como gradient checkpointing (trocar ativações por recomputação) e mixed-precision reduzem a necessidade, mas ainda exigem múltiplas GPUs de alta memória.
