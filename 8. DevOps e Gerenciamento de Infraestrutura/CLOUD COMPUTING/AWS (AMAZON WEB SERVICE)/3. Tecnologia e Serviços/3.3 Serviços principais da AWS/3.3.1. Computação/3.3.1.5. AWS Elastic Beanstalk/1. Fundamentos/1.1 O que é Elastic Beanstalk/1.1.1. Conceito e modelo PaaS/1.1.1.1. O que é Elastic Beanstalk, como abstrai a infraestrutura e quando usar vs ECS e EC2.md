### AWS Elastic Beanstalk — o que é, como abstrai a infraestrutura e quando usar

AWS Elastic Beanstalk é o serviço PaaS (Platform as a Service) da AWS. Você fornece o código — em um ZIP, WAR, ou Dockerfile — e o Beanstalk provisiona e gerencia toda a infraestrutura necessária: instâncias EC2, load balancer, Auto Scaling Group, CloudWatch, Security Groups, certificados e deploys. É a forma mais rápida de colocar uma aplicação web em produção na AWS sem aprender EC2, ECS, VPC ou nenhum outro serviço de infraestrutura.

---

## O modelo PaaS — o que o Beanstalk gerencia por você

```
Espectro de abstração AWS:

Você gerencia tudo ◄──────────────────────────────► AWS gerencia tudo
        │                                                    │
       EC2              ECS/EKS         Beanstalk         Lambda
        │                  │               │                 │
    SO, runtime,       Containers,      Código apenas    Código apenas
    patches, scaling,  nós, deploys     (infraestrutura  (sem servidor,
    LB, rede           manuais          automática)      sem estado)
```

Com Beanstalk, você mantém **visibilidade e controle** sobre a infraestrutura subjacente (você pode acessar as instâncias EC2, modificar configurações), mas não precisa provisioná-la nem mantê-la manualmente. É o meio-termo entre controle total (EC2) e abstração total (Lambda).

## Plataformas suportadas

O Beanstalk oferece **plataformas gerenciadas** para as principais linguagens e frameworks, onde o runtime já está instalado e configurado:

| Plataforma | Versões | Runtime |
|---|---|---|
| **Node.js** | 18, 20 | Express, NestJS, etc. |
| **Python** | 3.9, 3.11, 3.12 | Django, Flask, FastAPI |
| **Java** | Corretto 8, 11, 17, 21 | Tomcat, JAR standalone |
| **.NET** | 6, 8 | ASP.NET Core |
| **PHP** | 8.1, 8.2, 8.3 | Apache/Nginx |
| **Ruby** | 3.2, 3.3 | Puma, Passenger |
| **Go** | 1.21, 1.22 | Standalone binary |
| **Docker** | Single/Multi-container | Qualquer imagem |

A plataforma **Docker** é a mais flexível — permite rodar qualquer stack não listada acima usando um `Dockerfile` ou `docker-compose.yml`.

## Ciclo de vida básico — do código ao ambiente

### 1. Instalar o EB CLI

```bash
pip install awsebcli
eb --version
```

### 2. Inicializar a aplicação

```bash
# Em qualquer projeto existente
cd meu-projeto-node/

eb init \
  --platform "Node.js 20" \
  --region us-east-1 \
  minha-aplicacao

# Estrutura criada pelo eb init:
# .elasticbeanstalk/
#   config.yml     ← configurações do EB CLI
```

### 3. Criar o ambiente e fazer o primeiro deploy

```bash
# Cria o ambiente "producao" e deploy da aplicação
eb create producao \
  --instance-type m7g.large \
  --min-instances 2 \
  --max-instances 10 \
  --elb-type application \
  --tags "Environment=prod,Team=backend"

# Aguarda provisionamento (~5 min) e exibe a URL
eb open producao
```

### 4. Deploy de novas versões

```bash
# Fazer deploy da versão atual do código
eb deploy producao

# Deploy de uma versão específica
eb deploy producao --version "v2.1.0"

# Ver status do ambiente
eb status producao

# Ver logs
eb logs producao

# SSH na instância (acesso direto ao EC2)
eb ssh producao
```

## Estratégias de deploy disponíveis

O Beanstalk oferece 5 estratégias de deploy com diferentes trade-offs de velocidade vs. disponibilidade:

```
All at once (padrão):
  → Atualiza todas as instâncias simultaneamente
  → Downtime durante o deploy
  → Mais rápido, mais barato (sem instâncias extras)
  → Use apenas em dev/staging

Rolling:
  → Atualiza um lote de instâncias por vez (ex: 25% cada)
  → Sem downtime, mas capacidade reduzida temporariamente
  → Sem custo extra

Rolling with additional batch:
  → Lança instâncias novas antes de atualizar as antigas
  → Capacidade total mantida durante o deploy
  → Custo ligeiramente maior (instâncias extras temporárias)

Immutable:
  → Cria um novo Auto Scaling Group com instâncias novas
  → Só redireciona tráfego após tudo estar saudável
  → Rollback mais rápido (mantém o ASG antigo)
  → Maior custo temporário (dobra as instâncias)
  → Mais seguro para produção

Traffic splitting (Canary):
  → Envia X% do tráfego para novas instâncias
  → Valida antes de migrar 100%
  → Requer ALB
```

```bash
# Configurar estratégia de deploy
eb deploy producao \
  --staged \
  --label "v2.1.0"

# Via .ebextensions (configuração permanente):
# .ebextensions/deploy.config
option_settings:
  aws:elasticbeanstalk:command:
    DeploymentPolicy: Immutable
    HealthCheckSuccessThreshold: Ok
```

## O que você ainda controla no Beanstalk

Apesar da abstração, você mantém controle sobre:

```
O que você configura explicitamente:
  ├── Tipo de instância EC2 (t3.medium, m7g.large, etc.)
  ├── Min/Max de instâncias no ASG
  ├── Regras de escalamento (CPU, requisições/seg)
  ├── VPC e subnets (onde as instâncias rodam)
  ├── Security Groups (portas abertas)
  ├── Certificados SSL/TLS (ACM)
  ├── Variáveis de ambiente da aplicação
  ├── Configurações de saúde e health checks
  └── Acesso SSH às instâncias (via eb ssh)

O que o Beanstalk gerencia automaticamente:
  ├── Provisionamento das instâncias EC2
  ├── Instalação do runtime/plataforma
  ├── Configuração do ALB e Target Groups
  ├── Patches da plataforma (OS + runtime)
  ├── Rotação de logs para S3
  └── Métricas e alarmes CloudWatch básicos
```

## Beanstalk vs EC2 vs ECS — quando cada um é adequado

```
EC2 direto:
  Use quando: controle total sobre SO, runtime customizado,
              configurações de kernel, compliance específico
  Custo operacional: alto (patches, scaling, deploys manuais)

ECS (Fargate ou EC2):
  Use quando: arquitetura de containers, múltiplos serviços,
              CI/CD sofisticado com Docker, microserviços
  Curva: média — exige conhecimento de containers e task definitions

Elastic Beanstalk:
  Use quando: aplicação web monolítica ou simples,
              migração de on-premises sem reescrita,
              time pequeno sem expertise de infraestrutura,
              prototipagem rápida de MVPs
  Curva: baixa — deploy com 2 comandos

Lambda:
  Use quando: APIs stateless de baixo volume,
              processamento orientado a eventos,
              nenhuma execução > 15 minutos
  Custo: zero quando ocioso

App Runner (alternativa moderna ao Beanstalk):
  Use quando: mesma simplicidade do Beanstalk mas com containers,
              sem gerenciar instâncias EC2,
              carga variável (paga por uso como Lambda)
```

## Erros comuns e armadilhas

**Não configurar VPC e subnets corretamente:** por padrão, o Beanstalk pode lançar instâncias na VPC default com IPs públicos. Para produção, especifique sempre uma VPC privada com subnets privadas para as instâncias e pública para o ALB.

**Usar "All at once" em produção:** essa estratégia causa downtime. Configure "Immutable" ou "Rolling with additional batch" desde o início em ambientes produtivos.

**Confundir aplicação com ambiente:** no Beanstalk, uma **Application** é o contêiner lógico (ex: "minha-api"), e um **Environment** é uma implantação específica (ex: "producao", "staging"). A mesma aplicação pode ter múltiplos ambientes com configurações diferentes.

**Não usar `.ebextensions` para configurações repetíveis:** configurações feitas pelo console são esquecidas em recriações do ambiente. Use sempre `.ebextensions` para garantir que o ambiente seja reproduzível.

## 🧩 Quiz de Fixação

1. Um desenvolvedor faz `eb deploy` e a aplicação fica indisponível por 2 minutos durante o processo. Qual estratégia de deploy está sendo usada e como corrigir para zero downtime?

2. Por que o Elastic Beanstalk ainda provisiona instâncias EC2 mesmo sendo chamado de PaaS, e como isso difere do modelo de Lambda ou App Runner?

3. Uma startup com 2 desenvolvedores quer colocar uma API Django em produção na AWS pela primeira vez. Por que Beanstalk pode ser mais adequado que ECS Fargate neste momento, e qual seria o critério para migrar para ECS no futuro?

**Respostas:**

1) A estratégia **All at once** está sendo usada — ela atualiza todas as instâncias simultaneamente, causando downtime durante a troca. Para zero downtime em produção, configurar a estratégia **Immutable** (mais segura: cria novo ASG com instâncias novas antes de desligar as antigas) ou **Rolling with additional batch** (mantém capacidade total durante o deploy). Configurar via `.ebextensions/deploy.config` com `DeploymentPolicy: Immutable` para que seja persistente entre deploys.

2) O Beanstalk é PaaS no sentido de **abstrair o gerenciamento** de infraestrutura — você não precisa provisionar, configurar ou manter as instâncias EC2 manualmente. Mas por baixo, instâncias EC2 reais existem e você paga por elas 24/7, independente do tráfego. Isso é diferente de Lambda (que escala para zero — sem tráfego = $0) e App Runner (que também pode escalar para zero ou usar modelos de billing por uso). O Beanstalk é "PaaS sobre EC2" — você ganha a conveniência de não configurar, mas mantém o modelo de custo de servidores sempre ativos. Para workloads com tráfego constante isso é eficiente; para workloads irregulares, Lambda ou App Runner são mais econômicos.

3) **Por que Beanstalk agora:** (a) com 2 desenvolvedores, ninguém tem tempo para aprender Task Definitions, ECR, VPC CNI, Capacity Providers e o ecossistema ECS — o Beanstalk entrega produção com `eb create` + `eb deploy`; (b) Django com Gunicorn é exatamente o perfil de aplicação para o qual Beanstalk foi projetado — plataforma Python gerenciada, sem Docker necessário; (c) o foco deve estar no produto, não na infraestrutura. **Critério para migrar para ECS no futuro:** quando a aplicação crescer e precisar de múltiplos serviços independentes (API + workers + scheduler), quando o time contratar alguém com expertise de containers/DevOps, quando os recursos de deploy do Beanstalk se tornarem limitantes (ex: precisar de múltiplos containers por deploy, pipelines CI/CD mais sofisticados), ou quando os custos de EC2 24/7 justificarem a migração para Fargate com escalonamento mais granular.
