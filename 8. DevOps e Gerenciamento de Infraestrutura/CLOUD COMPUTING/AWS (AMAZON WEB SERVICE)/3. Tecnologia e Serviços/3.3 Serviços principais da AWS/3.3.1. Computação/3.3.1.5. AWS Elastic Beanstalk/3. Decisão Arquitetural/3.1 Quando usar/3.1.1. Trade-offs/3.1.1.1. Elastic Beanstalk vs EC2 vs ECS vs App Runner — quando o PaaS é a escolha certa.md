### Elastic Beanstalk vs EC2 vs ECS vs App Runner — quando o PaaS é a escolha certa

Escolher o serviço de computação correto é uma das decisões mais impactantes em uma arquitetura AWS. Este arquivo fecha o sub-glossário do Elastic Beanstalk comparando-o com as quatro alternativas mais próximas: EC2, ECS, Lambda e App Runner. O objetivo não é declarar um vencedor universal, mas definir o perfil de problema onde cada um se encaixa melhor.

---

## Comparativo dimensional completo

### Dimensão 1: Gerenciamento operacional

| Tarefa | EC2 | ECS EC2 | Beanstalk | App Runner | Lambda |
|---|---|---|---|---|---|
| Provisionar servidor | Manual | Manual (ASG) | Automático | Automático | N/A |
| Aplicar patches de SO | Manual | Manual (AMI) | Automático | Automático | N/A |
| Configurar Load Balancer | Manual | Manual | Automático | Automático | Via API GW |
| Configurar Auto Scaling | Manual | Via ASG/CP | Automático | Automático | Nativo |
| Deploy de nova versão | Manual | Via CLI/CI | `eb deploy` | Push imagem | Publish |
| Rollback | Manual | Via CLI | CNAME swap | Via console | Via versão |

### Dimensão 2: Flexibilidade e customização

| Aspecto | EC2 | ECS | Beanstalk | App Runner | Lambda |
|---|---|---|---|---|---|
| Customização de SO | Total | Via container | Limitada (.ebext) | Nenhuma | Nenhuma |
| Binários nativos (ffmpeg) | Sim | Via Docker | Via .ebextensions | Via Docker | Via Layer |
| Múltiplos containers | N/A | Nativo | Limitado (Docker) | Não | Não |
| GPU | Sim | Sim (EC2) | Não | Não | Não |
| Duração máxima exec. | Ilimitada | Ilimitada | Ilimitada | Ilimitada | 15 min |
| Acesso SSH ao servidor | Sim | Sim (nó) | Sim (`eb ssh`) | Não | Não |

### Dimensão 3: Custo para diferentes padrões de uso

```
Workload: API web, 2 vCPU / 4 GiB, tráfego constante 24/7
──────────────────────────────────────────────────────────
EC2 Reserved (1yr): ~$35-50/mês ← mais barato em uso contínuo
ECS Fargate:        ~$70/mês
Beanstalk (EC2):    ~$35-50/mês + overhead mínimo (S3 para artefatos)
App Runner:         ~$50-70/mês (depende de concurrência/memória)
Lambda:             ~$80+/mês para alto volume constante

Workload: API esporádica, 100k req/mês, duração 200ms
──────────────────────────────────────────────────────────
EC2 On-Demand:  ~$35/mês (paga mesmo quando ocioso)
Beanstalk:      ~$35/mês (idem — EC2 por baixo)
ECS Fargate:    ~$35/mês (idem — sempre com 1+ task)
App Runner:     ~$5-10/mês (escala para zero)
Lambda:         < $1/mês ← imbatível para baixo volume

Workload: pico sazonal (normal: 2 instâncias, pico: 50)
──────────────────────────────────────────────────────────
EC2:        Pré-provisionar 50 = custo fixo alto; ou escalar lento
Beanstalk:  Auto Scaling nativo, mas ainda EC2 (lento para picos bruscos)
ECS Fargate: Escala em ~30-60s por task
App Runner:  Escala automaticamente, mas limites de concorrência menores
Lambda:     Escala em milissegundos ← ideal para picos imprevisíveis
```

## App Runner — o concorrente direto do Beanstalk

**AWS App Runner** (lançado em 2021) é o substituto moderno para muitos casos de uso do Beanstalk, com foco em containers e simplicidade ainda maior:

```
App Runner vs Elastic Beanstalk:

Elastic Beanstalk:
  → Baseado em EC2 (instâncias sempre ativas)
  → Plataformas gerenciadas (Node.js, Python, Java, etc.)
  → Configuração via .ebextensions (YAML)
  → Controle de VPC, Security Groups, instâncias
  → Custo: EC2 24/7 mesmo sem tráfego
  → Maturidade: alta (desde 2011)

App Runner:
  → Baseado em containers (você fornece Dockerfile ou imagem ECR)
  → Pode escalar para zero (sem tráfego = custo mínimo)
  → Configuração simples (console/CLI)
  → Sem controle de nós ou infraestrutura
  → Custo: por vCPU-hora e memória-hora de uso ativo
  → Maturidade: menor (desde 2021), mas crescendo
  → VPC connector disponível (para acesso a RDS/ElastiCache privados)
```

### Quando App Runner supera Beanstalk

```
Prefira App Runner quando:
  ✓ Workload variável ou com períodos de baixo tráfego
    → Escala para zero = sem custo em madrugadas/finais de semana
  ✓ Stack já dockerizada
    → App Runner consome diretamente a imagem ECR
  ✓ Máxima simplicidade — sem configurar nada de infraestrutura
  ✓ Projeto novo sem legado on-premises

Prefira Beanstalk quando:
  ✓ Aplicação legada em JAR/WAR sem Dockerfile
    → Beanstalk aceita o artefato direto sem containerizar
  ✓ Necessidade de SSH nas instâncias para debugging
  ✓ Controle de VPC, subnets e Security Groups é necessário
  ✓ Plataformas nativas (Python, PHP, Ruby) sem Docker
  ✓ Equipe já usa Beanstalk e não há incentivo para migrar
```

## Perfis de projeto e serviço recomendado

### Startup com MVP para lançar rápido

```
Contexto: 2 engenheiros, API Django, sem containers, 0 a 50k usuários

→ Elastic Beanstalk ✓✓
  Motivo: deploy em horas, não dias. `eb create producao` e está online.
  Sem aprender EC2, ECS, VPC, Task Definitions, etc.
  Pode migrar para ECS/EKS quando o time crescer.
```

### Aplicação legada migrada de on-premises

```
Contexto: monolito Java com WAR, equipe de Ops tradicional

→ Elastic Beanstalk ✓✓
  Motivo: o Beanstalk aceita WARs diretamente (Tomcat platform).
  Migração de lift-and-shift sem reescrever nada.
  Infraestrutura similar ao que a equipe conhece (EC2 por baixo).
```

### Microserviços com times independentes

```
Contexto: 10 serviços, 4 times, CI/CD sofisticado, Docker em todos

→ ECS Fargate ou EKS ✓✓
  Motivo: Beanstalk não tem suporte nativo a múltiplos containers
  por ambiente, Service Discovery, sidecars. ECS/EKS resolvem.
```

### API serverless com tráfego imprevisível

```
Contexto: API de webhook recebendo de 0 a 10.000 req/min

→ Lambda + API Gateway ✓✓ (se < 15 min por request)
→ App Runner ✓ (se precisa de container, > 15 min, ou estado)
  Motivo: ambos escalam para zero. Beanstalk e ECS pagam pela
  capacidade mínima mesmo sem tráfego.
```

### Plataforma de ML com inferência

```
Contexto: modelos de ML servidos via API, GPU necessária

→ ECS EC2 (instâncias G5) ✓✓
  Motivo: Beanstalk não suporta GPU. ECS EC2 com Node Groups
  de instâncias G5 e Auto Scaling por métrica de utilização de GPU.
```

## Cenários de migração — quando sair do Beanstalk

O Beanstalk é frequentemente um ponto de partida — o momento de migrar para ECS/EKS geralmente é impulsionado por um desses sinais:

```
Sinal 1: Múltiplos containers por deployment
  → Beanstalk Docker single-container tem limitações
  → Migrar para ECS Task Definitions com múltiplos containers

Sinal 2: Times independentes precisam de isolamento
  → Beanstalk é um único ambiente, difícil de compartilhar
  → ECS com múltiplos Services ou EKS com namespaces

Sinal 3: Pipelines CI/CD complexos
  → Beanstalk tem deploy simples mas limitado para estratégias avançadas
  → ECS + CodeDeploy ou EKS + ArgoCD para canary/blue-green sofisticado

Sinal 4: Observabilidade avançada necessária
  → Beanstalk tem CloudWatch básico
  → ECS/EKS permitem Prometheus, Jaeger, Datadog APM com mais controle

Sinal 5: Custo em escala
  → Em centenas de instâncias, o overhead do Beanstalk é mínimo
  → Mas ECS com Spot + Graviton pode ser significativamente mais barato
```

## Tabela de decisão rápida

```
Pergunta                                    Resposta → Serviço

Preciso de GPU?                             Sim → EC2 ou ECS EC2
                                            Não → continua ↓

Tenho containers Docker?                    Sim → ECS, App Runner, EKS
                                            Não (JAR/ZIP/WAR) → Beanstalk ou EC2

Múltiplos microserviços independentes?      Sim → ECS ou EKS
                                            Não (monolito/API única) → Beanstalk, App Runner

Execução > 15 minutos?                      Sim → EC2, ECS, Beanstalk
                                            Não → Lambda é opção

Tráfego próximo de zero em parte do dia?    Sim → Lambda ou App Runner (escala a zero)
                                            Não → Beanstalk ou ECS são eficientes

Time pequeno sem expertise de infra?        Sim → Beanstalk ou App Runner
                                            Não → ECS ou EKS

Portabilidade multi-cloud necessária?       Sim → EKS (Kubernetes padrão)
                                            Não → qualquer um
```

## 🧩 Quiz de Fixação

1. Uma empresa tem uma API Node.js rodando no Elastic Beanstalk com 2 instâncias `m7g.large` (custo ~$120/mês). A API fica ociosa das 22h às 8h nos dias de semana e o fim de semana inteiro (~60% do tempo). Quais alternativas reduziriam o custo e quais são os trade-offs de cada uma?

2. Uma equipe decide migrar uma aplicação do Beanstalk para ECS Fargate. O principal argumento é "ECS é mais moderno". Por que esse argumento é insuficiente como justificativa técnica, e quais seriam os argumentos técnicos válidos para a migração?

3. Um JAR de Spring Boot está rodando no Beanstalk (Java platform). O time quer migrar para App Runner. Quais passos técnicos são necessários e por que a migração pode ser mais complexa do que parece?

**Respostas:**

1) **Alternativa 1 — AWS Instance Scheduler + Beanstalk:** configurar o Instance Scheduler para parar as instâncias às 22h e reiniciar às 8h. Redução de custo: ~60% ($120 → ~$48/mês). Trade-off: cold start de ~2-5 minutos quando as instâncias sobem às 8h; requer automação adicional; dados em memória são perdidos. **Alternativa 2 — App Runner:** migrar para container e usar App Runner, que escala para zero. Custo: ~$0 nas horas ociosas + custo de uso durante o dia (~$20-40/mês). Trade-off: exige containerizar a aplicação (Dockerfile); menos controle de infraestrutura; possível cold start quando App Runner sobe de zero. **Alternativa 3 — Lambda + API Gateway:** se a API é stateless e cada request < 15min. Custo: praticamente zero para baixo volume. Trade-off: mudança arquitetural significativa — não é "lift and shift"; pode haver cold start; limites de timeout e payload.

2) "ECS é mais moderno" não é argumento técnico — Beanstalk continua sendo suportado e atualizado pela AWS, recebendo novas plataformas e features regularmente. Argumentos técnicos válidos para migrar seriam: (a) a aplicação evoluiu para múltiplos containers que precisam comunicar entre si — Beanstalk Docker tem limitações para isso; (b) a equipe adotou uma estratégia de deploy canário com pesos de tráfego que o Beanstalk não suporta nativamente; (c) há necessidade de Service Discovery entre múltiplos serviços — ECS com Cloud Map resolve, Beanstalk não tem equivalente; (d) o custo das instâncias EC2 ociosas está sendo alto e Fargate com Fargate Spot seria mais econômico para o padrão de uso específico; (e) a equipe cresceu e agora tem engenheiros com expertise em containers que tornam a operação do ECS mais eficiente que Beanstalk.

3) A migração de Beanstalk Java Platform para App Runner não é trivial porque: (1) **App Runner requer container** — o JAR precisa ser containerizado com um `Dockerfile` (FROM amazoncorretto:21, COPY .jar, ENTRYPOINT java -jar), o que exige criar e testar a imagem Docker; (2) **Configuração do servidor web** — no Beanstalk, o Nginx e o Tomcat são gerenciados automaticamente; no App Runner, a aplicação precisa expor a porta correta e o health check precisa estar configurado no Spring Boot (Spring Actuator em `/actuator/health`); (3) **Variáveis de ambiente e secrets** — as variáveis configuradas via `.ebextensions` ou `eb setenv` precisam ser reconfiguradas no App Runner; secrets do Secrets Manager precisam ser referenciados na configuração do App Runner; (4) **Sem acesso a VPC privada por padrão** — se a API acessa RDS em subnet privada, é necessário configurar o VPC Connector do App Runner (que tem custo adicional); (5) **Sem `.ebextensions`** — qualquer customização de SO ou configuração de servidor feita via `.ebextensions` precisa ser incorporada no Dockerfile ou na lógica da aplicação.
