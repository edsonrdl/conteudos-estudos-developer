### Aplicações, ambientes, plataformas e o ciclo de deploy no Elastic Beanstalk

O Elastic Beanstalk organiza seus recursos em três camadas hierárquicas: **Application** (o contêiner lógico), **Environment** (a implantação em execução) e **Application Version** (o artefato de código). Entender como essas três entidades se relacionam é fundamental para operar o Beanstalk de forma correta — especialmente para gerenciar múltiplos ambientes (staging, produção) com a mesma base de código.

---

## Hierarquia de conceitos

```
Application "minha-api"
│
├── Application Versions (artefatos imutáveis):
│     ├── v1.0.0 (ZIP em S3)
│     ├── v1.1.0 (ZIP em S3)
│     └── v2.0.0 (ZIP em S3) ← versão atual
│
├── Environment "staging"
│     ├── Plataforma: Node.js 20
│     ├── Instâncias: 1× t3.small
│     ├── Versão ativa: v1.1.0
│     └── URL: staging.us-east-1.elasticbeanstalk.com
│
└── Environment "producao"
      ├── Plataforma: Node.js 20
      ├── Instâncias: 3-10× m7g.large (Auto Scaling)
      ├── Versão ativa: v2.0.0
      └── URL: minha-api.us-east-1.elasticbeanstalk.com
```

---

## Application — o agrupador lógico

A **Application** é apenas um namespace — não tem custo próprio, não tem infraestrutura associada. Ela agrupa versões e ambientes relacionados a uma mesma aplicação.

```bash
# Criar uma aplicação via CLI
aws elasticbeanstalk create-application \
  --application-name minha-api \
  --description "API de pedidos — backend principal"

# Listar aplicações
aws elasticbeanstalk describe-applications

# Deletar aplicação (deleta TODOS os ambientes e versões associados)
aws elasticbeanstalk delete-application \
  --application-name minha-api \
  --terminate-env-by-force
```

---

## Application Version — o artefato de deploy

Cada **Application Version** é um artefato imutável (ZIP, WAR, ou referência Docker) armazenado no S3. Versões são independentes dos ambientes — a mesma versão pode ser deployada em múltiplos ambientes.

```bash
# Criar versão manualmente (normalmente feito pelo eb deploy)
# 1. Compactar o código
zip -r minha-api-v2.0.0.zip . -x "*.git*" "node_modules/*"

# 2. Upload para S3
aws s3 cp minha-api-v2.0.0.zip \
  s3://elasticbeanstalk-us-east-1-123456/minha-api/minha-api-v2.0.0.zip

# 3. Registrar a versão no Beanstalk
aws elasticbeanstalk create-application-version \
  --application-name minha-api \
  --version-label "v2.0.0" \
  --description "Novo módulo de checkout" \
  --source-bundle S3Bucket=elasticbeanstalk-us-east-1-123456,\
S3Key=minha-api/minha-api-v2.0.0.zip \
  --auto-create-application

# Listar versões
aws elasticbeanstalk describe-application-versions \
  --application-name minha-api

# Deletar versões antigas (limpeza)
aws elasticbeanstalk delete-application-version \
  --application-name minha-api \
  --version-label "v1.0.0" \
  --delete-source-bundle  # também deleta o ZIP do S3
```

### Lifecycle Policy — limpeza automática de versões antigas

Por padrão, o Beanstalk mantém todas as versões indefinidamente. Para evitar acúmulo em S3 e limites de quota:

```bash
aws elasticbeanstalk update-application-resource-lifecycle \
  --application-name minha-api \
  --resource-lifecycle-config '{
    "ServiceRole": "arn:aws:iam::123:role/AWSElasticBeanstalkService",
    "VersionLifecycleConfig": {
      "MaxCountRule": {
        "Enabled": true,
        "MaxCount": 20,
        "DeleteSourceFromS3": true
      }
    }
  }'
# Mantém apenas as 20 versões mais recentes, deleta o resto do S3
```

## Environment — onde a aplicação realmente roda

O **Environment** é a infraestrutura provisionada. Existem dois tipos:

### Web Server Environment

Para aplicações que respondem a requisições HTTP/HTTPS:

```
Web Server Environment:
  ALB → Auto Scaling Group → EC2 com a aplicação
  
  Componentes provisionados:
  ├── Application Load Balancer (ou Classic, se configurado)
  ├── Auto Scaling Group (min/max instâncias)
  ├── EC2 Instances (com plataforma + código)
  ├── Security Groups (ALB e instâncias)
  ├── CloudWatch Alarms
  └── IAM Instance Profile
```

### Worker Environment

Para processamento em background via fila SQS — sem ALB:

```
Worker Environment:
  SQS Queue → EC2 Worker → processa mensagem
  
  Uso: jobs assíncronos, processamento de imagens, envio de emails
  O daemon SQS do Beanstalk faz o polling e chama a aplicação via HTTP POST local
```

```bash
# Criar Worker Environment
eb create worker-env \
  --tier worker \
  --instance-type m7g.large

# A aplicação recebe mensagens via POST em /
# O corpo da requisição é o payload da mensagem SQS
```

## Plataformas — versões e atualizações

Cada Environment usa uma **plataforma** que define o SO + runtime + servidor web. As plataformas têm versões próprias e são atualizadas periodicamente pela AWS:

```
Plataforma "Node.js 20" — estrutura:
  ├── SO: Amazon Linux 2023
  ├── Runtime: Node.js 20.x
  ├── Servidor web: Nginx (como proxy reverso)
  ├── Processo: PM2 ou node direto
  └── Versão da plataforma: 6.1.0 (exemplo)

Plataforma "Python 3.12" — estrutura:
  ├── SO: Amazon Linux 2023
  ├── Runtime: Python 3.12
  ├── WSGI: Gunicorn
  ├── Proxy: Nginx
  └── Versão da plataforma: 4.0.0 (exemplo)
```

```bash
# Listar plataformas disponíveis
aws elasticbeanstalk list-platform-versions \
  --filters Type=PlatformName,Operator=contains,Values=Node.js

# Atualizar plataforma de um ambiente (managed platform updates)
aws elasticbeanstalk update-environment \
  --environment-name producao \
  --solution-stack-name "64bit Amazon Linux 2023 v6.1.0 running Node.js 20"

# Configurar atualizações automáticas de plataforma (Managed Updates)
# Via console: Environment → Configuration → Managed Platform Updates
# Ou via .ebextensions:
```

```yaml
# .ebextensions/managed-updates.config
option_settings:
  aws:elasticbeanstalk:managedactions:
    ManagedActionsEnabled: true
    PreferredStartTime: "Tue:10:00"  # UTC — terças às 10h
  aws:elasticbeanstalk:managedactions:platformupdate:
    UpdateLevel: minor   # minor | patch
    InstanceRefreshEnabled: true
```

## Ciclo de deploy completo

### Fluxo via EB CLI (desenvolvimento local)

```bash
# 1. Preparar o artefato (Beanstalk comprime o diretório atual)
eb deploy producao

# O eb deploy faz automaticamente:
#   1. Comprime o código (ZIP)
#   2. Upload para S3
#   3. Cria nova Application Version
#   4. Atualiza o Environment com a nova versão
#   5. Monitora o health até concluir (ou reverter se configurado)

# 2. Verificar o resultado
eb status producao
# Mostra: Status, Health, Versão ativa, URL, instâncias

# 3. Acompanhar eventos em tempo real
eb events -f producao
```

### Fluxo via pipeline CI/CD (GitHub Actions)

```yaml
# .github/workflows/deploy.yml
name: Deploy to Elastic Beanstalk

on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123:role/GitHubActionsRole
          aws-region: us-east-1

      - name: Install dependencies
        run: npm ci --production

      - name: Create deployment package
        run: |
          zip -r deploy.zip . \
            -x "*.git*" \
            -x "*.github*" \
            -x "*.test.*" \
            -x "coverage/*"

      - name: Deploy to Elastic Beanstalk
        run: |
          VERSION_LABEL="v$(date +%Y%m%d%H%M%S)-${GITHUB_SHA::8}"
          
          # Upload para S3
          aws s3 cp deploy.zip \
            s3://elasticbeanstalk-us-east-1-123/minha-api/${VERSION_LABEL}.zip
          
          # Criar Application Version
          aws elasticbeanstalk create-application-version \
            --application-name minha-api \
            --version-label "${VERSION_LABEL}" \
            --source-bundle S3Bucket=elasticbeanstalk-us-east-1-123,\
S3Key=minha-api/${VERSION_LABEL}.zip
          
          # Deploy no ambiente
          aws elasticbeanstalk update-environment \
            --application-name minha-api \
            --environment-name producao \
            --version-label "${VERSION_LABEL}"
          
          # Aguardar conclusão
          aws elasticbeanstalk wait environment-updated \
            --application-name minha-api \
            --environment-names producao
```

### URL swap — swap de ambientes (blue/green nativo)

O Beanstalk suporta **CNAME swap** — troca os URLs de dois ambientes de forma atômica, implementando Blue/Green nativo:

```bash
# Manter dois ambientes:
# minha-api-blue (produção atual):   minha-api.us-east-1.elasticbeanstalk.com
# minha-api-green (nova versão):     minha-api-green.us-east-1.elasticbeanstalk.com

# Testar o green antes do swap
curl https://minha-api-green.us-east-1.elasticbeanstalk.com/health

# Fazer o swap (troca os CNAMEs — instantâneo)
aws elasticbeanstalk swap-environment-cnames \
  --source-environment-name minha-api-green \
  --destination-environment-name minha-api-blue

# Após o swap:
# minha-api.us-east-1.elasticbeanstalk.com → aponta para green (nova versão)
# minha-api-green.us-east-1.elasticbeanstalk.com → aponta para blue (versão anterior)

# Se necessário: rollback imediato (swap de volta)
aws elasticbeanstalk swap-environment-cnames \
  --source-environment-name minha-api-blue \
  --destination-environment-name minha-api-green
```

## Health e monitoramento

```bash
# Estado de saúde do ambiente
aws elasticbeanstalk describe-environment-health \
  --environment-name producao \
  --attribute-names All

# Estados possíveis:
# Green  → todas as instâncias saudáveis
# Yellow → algumas instâncias com problemas
# Red    → ambiente com falha crítica
# Grey   → informações insuficientes / ambiente pausado

# Ver eventos recentes do ambiente
aws elasticbeanstalk describe-events \
  --application-name minha-api \
  --environment-name producao \
  --max-records 20

# Baixar logs das instâncias
aws elasticbeanstalk request-environment-info \
  --environment-name producao \
  --info-type tail

aws elasticbeanstalk retrieve-environment-info \
  --environment-name producao \
  --info-type tail
```

## Erros comuns e armadilhas

**Não ter Lifecycle Policy:** sem ela, o Beanstalk acumula centenas de Application Versions no S3, eventualmente atingindo o limite de 1.000 versões por aplicação — o que bloqueia novos deploys.

**Deletar o ambiente em vez da versão:** `eb terminate` deleta o ambiente inteiro (infraestrutura + dados). Para apenas remover versões antigas, use `delete-application-version`. Sempre confirme o que será deletado.

**CNAME swap não atualiza registros DNS customizados:** o swap troca os CNAMEs do `.elasticbeanstalk.com`, mas se você tem um Route 53 CNAME apontando para o ambiente, ele continua apontando para o mesmo DNS name — que agora aponta para o green. Se tiver Record Type A (Alias para o LB), pode precisar de atualização manual.

## 🧩 Quiz de Fixação

1. Você tem uma Application com dois Environments: "staging" rodando v1.9.0 e "producao" rodando v1.8.0. Você quer promover a v1.9.0 para produção sem fazer um novo deploy. Como fazer isso e qual é a vantagem dessa abordagem?

2. Por que o Beanstalk armazena Application Versions no S3 separadamente do Environment, e qual problema isso resolve em uma arquitetura com múltiplos ambientes?

3. Qual é a diferença entre usar a estratégia "Immutable" nativa do Beanstalk e o "CNAME swap" para implementar um deploy seguro, e quando cada abordagem é mais adequada?

**Respostas:**

1) Para promover v1.9.0 para produção sem novo deploy, basta **atualizar o Environment de produção para usar a versão já existente**: `aws elasticbeanstalk update-environment --environment-name producao --version-label "v1.9.0"`. O Beanstalk usa o artefato já existente no S3, sem recompilar ou reempacotar nada. A vantagem é que o artefato que está sendo promovido para produção é **exatamente o mesmo** que foi testado em staging — não há risco de diferença de build entre ambientes. Isso implementa o princípio de "build once, deploy many" — o mesmo ZIP/imagem percorre todos os ambientes, eliminando inconsistências de build.

2) Ao separar Application Versions dos Environments, o Beanstalk permite que o mesmo artefato seja usado por múltiplos ambientes simultaneamente sem duplicação. Se staging e produção usassem artefatos embutidos no ambiente, a promoção de staging para produção exigiria recriar o artefato. Com versionamento separado: staging testa v1.9.0 → aprovado → produção aplica v1.9.0 sem recompilação. Isso também permite rollback instantâneo — em vez de redeployar código antigo, basta apontar o Environment para uma Application Version anterior já existente no S3, que é muito mais rápido que um deploy completo.

3) **Immutable deploy:** cria um novo Auto Scaling Group com novas instâncias rodando a nova versão, aguarda health check, então termina o ASG antigo. Tudo acontece **dentro do mesmo Environment** — a URL não muda. Rollback é mais lento (precisa redeployar a versão anterior). Ideal quando você quer deploy seguro sem manter dois ambientes separados, e quando a URL não pode mudar. **CNAME swap:** mantém **dois Environments separados** (blue e green) com infraestruturas completamente independentes. A troca é instantânea (mudança de DNS) e o rollback é igualmente instantâneo (swap de volta). Ideal quando rollback ultrarápido é essencial, quando você quer validar o novo ambiente com tráfego real antes de trocar (apontando para o green com um subdomínio de teste), ou quando tem carga pesada e quer evitar que a instância realize a transição enquanto ainda serve tráfego. O custo do CNAME swap é maior (dois ambientes ativos = dobro de EC2) enquanto o blue/green está em andamento.
