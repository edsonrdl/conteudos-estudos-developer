### .ebextensions, variáveis de ambiente, Auto Scaling e personalização da infraestrutura

O Elastic Beanstalk abstrai a infraestrutura, mas não a torna imutável — você tem controle fino sobre praticamente tudo através de arquivos de configuração declarativos. O `.ebextensions` é o mecanismo central de personalização: permite instalar pacotes, executar scripts, configurar o servidor web, definir variáveis de ambiente, ajustar o Auto Scaling e até criar recursos AWS adicionais, tudo como código versionado junto com a aplicação.

---

## .ebextensions — configuração como código

O diretório `.ebextensions/` fica na raiz do projeto e contém arquivos `.config` no formato YAML. Todos os arquivos são processados em ordem alfabética durante o deploy, antes da aplicação iniciar.

```
Estrutura do projeto com .ebextensions:
meu-projeto/
├── .ebextensions/
│   ├── 01-packages.config      ← instalar pacotes do SO
│   ├── 02-env.config           ← variáveis de ambiente
│   ├── 03-nginx.config         ← customizar Nginx
│   ├── 04-autoscaling.config   ← regras de escalamento
│   └── 05-resources.config     ← criar recursos AWS extras
├── app.js
├── package.json
└── ...
```

### Seções disponíveis nos arquivos .config

```yaml
# Estrutura completa de um arquivo .config
packages:     # instalar pacotes do SO (yum, rpm, python, etc.)
groups:       # criar grupos do SO
users:        # criar usuários do SO
sources:      # baixar e extrair arquivos de URLs
files:        # criar/editar arquivos no sistema
commands:     # comandos executados antes do app iniciar
container_commands:  # comandos executados após o código ser extraído
services:     # gerenciar serviços (iniciar/parar)
option_settings:     # configurar opções do Beanstalk
Resources:    # criar recursos AWS (CloudFormation)
Outputs:      # exportar valores (CloudFormation)
```

```yaml
# .ebextensions/01-packages.config

packages:
  yum:
    git: []
    ImageMagick: []

    postgresql15: []

  rpm:
    newrelic-sysmond:
      - https://download.newrelic.com/pub/newrelic/el5/x86_64/newrelic-sysmond-2.3.0.132-1.x86_64.rpm

  python:
    awscli: []               # instalar via pip

commands:
  01_install_node_deps:
    command: "npm ci --production"
    cwd: "/var/app/current"
    ignoreErrors: false

  02_create_log_dir:
    command: "mkdir -p /var/log/myapp"
    test: "[ ! -d /var/log/myapp ]"   # executa apenas se o diretório não existe
```

## Variáveis de ambiente

Variáveis de ambiente são injetadas nas instâncias EC2 e ficam disponíveis para o processo da aplicação via `process.env` (Node.js), `os.environ` (Python), etc.

### Via EB CLI

```bash
# Definir variáveis de ambiente
eb setenv NODE_ENV=production \
           DB_HOST=meu-rds.cluster.us-east-1.rds.amazonaws.com \
           LOG_LEVEL=info \
           -e producao

# Ver variáveis do ambiente
eb printenv producao

# Remover uma variável
eb setenv VARIAVEL_ANTIGA= -e producao
```

### Via .ebextensions

```yaml
# .ebextensions/02-env.config
option_settings:
  aws:elasticbeanstalk:application:environment:
    NODE_ENV: production
    LOG_LEVEL: info
    PORT: "8080"
    TZ: America/Sao_Paulo
```

### Variáveis sensíveis — integração com Secrets Manager

Para senhas e tokens, **nunca** armazene em `.ebextensions` (vai para o repositório Git). Use SSM Parameter Store ou Secrets Manager:

```yaml
# .ebextensions/03-secrets.config
files:
  "/opt/elasticbeanstalk/tasks/bundlelogs.d/app.conf":
    mode: "000644"
    owner: root
    group: root
    content: |
      /var/log/myapp/*.log

commands:
  fetch_secrets:
    command: |
      DB_PASSWORD=$(aws secretsmanager get-secret-value \
        --secret-id prod/db \
        --query 'SecretString' \
        --output text | jq -r '.password')
      
      # Injetar no arquivo de ambiente que o Beanstalk lê
      echo "DB_PASSWORD=${DB_PASSWORD}" >> /etc/profile.d/app_env.sh
    env:
      AWS_REGION: us-east-1
```

> A abordagem mais robusta é ler os secrets **dentro do código da aplicação** na inicialização, usando o SDK da AWS com as credenciais do Instance Profile — sem passar pelo sistema de variáveis de ambiente.

## Configuração do Nginx

O Beanstalk usa Nginx como proxy reverso por padrão nas plataformas Node.js, Python e outras. Você pode customizar a configuração:

```nginx
# .platform/nginx/conf.d/proxy.conf
# (nova forma recomendada para AL2023)

upstream nodejs {
    server 127.0.0.1:8080;
    keepalive 256;
}

server {
    listen 80;
    
    location / {
        proxy_pass          http://nodejs;
        proxy_set_header    Host $host;
        proxy_set_header    X-Real-IP $remote_addr;
        proxy_set_header    X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header    X-Forwarded-Proto $scheme;
        
        # Timeout para requests longos
        proxy_read_timeout  300;
        proxy_send_timeout  300;
        
        # Gzip compression
        gzip on;
        gzip_types text/plain application/json application/javascript text/css;
    }
    
    # Health check endpoint — responde diretamente sem passar pelo app
    location /health-check {
        access_log  off;
        return 200 'OK';
        add_header Content-Type text/plain;
    }
    
    # Limite de tamanho de upload
    client_max_body_size 50M;
}
```

## Auto Scaling — configuração via .ebextensions

```yaml
# .ebextensions/04-autoscaling.config
option_settings:

  # Configuração das instâncias
  aws:autoscaling:launchconfiguration:
    InstanceType: m7g.large
    SecurityGroups: sg-abc123
    IamInstanceProfile: aws-elasticbeanstalk-ec2-role

  # Configuração do Auto Scaling Group
  aws:autoscaling:asg:
    MinSize: 2
    MaxSize: 10
    Availability Zones: Any 2    # distribuir entre 2 AZs

  # Trigger de escalamento por CPU
  aws:autoscaling:trigger:
    MeasureName: CPUUtilization
    Statistic: Average
    Unit: Percent
    Period: "5"              # janela de 5 minutos
    BreachDuration: "5"      # manter por 5 minutos antes de agir
    UpperThreshold: "75"     # scale out acima de 75%
    LowerThreshold: "30"     # scale in abaixo de 30%
    UpperBreachScaleIncrement: "2"   # adicionar 2 instâncias
    LowerBreachScaleIncrement: "-1"  # remover 1 instância

  # Configuração do Load Balancer
  aws:elasticbeanstalk:environment:
    LoadBalancerType: application    # application | network | classic

  aws:elbv2:loadbalancer:
    IdleTimeout: "120"
    DeletionProtection: true   # evitar deleção acidental

  # Health check do ALB
  aws:elasticbeanstalk:environment:process:default:
    HealthCheckPath: /health
    HealthCheckInterval: "30"
    HealthCheckTimeout: "5"
    HealthyThresholdCount: "2"
    UnhealthyThresholdCount: "3"
    StickinessEnabled: false

  # Estratégia de deploy
  aws:elasticbeanstalk:command:
    DeploymentPolicy: Immutable
    HealthCheckSuccessThreshold: Ok
    IgnoreHealthCheck: false
    Timeout: "600"           # timeout de 10 min para o deploy

  # Logs
  aws:elasticbeanstalk:cloudwatch:logs:
    StreamLogs: true
    DeleteOnTerminate: false
    RetentionInDays: "30"
```

## Resources — criar recursos AWS extras via CloudFormation

A seção `Resources` usa sintaxe CloudFormation para criar recursos AWS adicionais que fazem parte do ambiente:

```yaml
# .ebextensions/06-resources.config

Resources:
  # SQS Queue para workers assíncronos
  MinhaFila:
    Type: AWS::SQS::Queue
    Properties:
      QueueName: "minha-api-jobs"
      VisibilityTimeout: 300
      MessageRetentionPeriod: 86400
      RedrivePolicy:
        deadLetterTargetArn: !GetAtt MinhaFilaDLQ.Arn
        maxReceiveCount: 3

  MinhaFilaDLQ:
    Type: AWS::SQS::Queue
    Properties:
      QueueName: "minha-api-jobs-dlq"

  # DynamoDB Table
  SessoesTable:
    Type: AWS::DynamoDB::Table
    Properties:
      TableName: "sessoes-beanstalk"
      BillingMode: PAY_PER_REQUEST
      AttributeDefinitions:
        - AttributeName: sessao_id
          AttributeType: S
      KeySchema:
        - AttributeName: sessao_id
          KeyType: HASH
      TimeToLiveSpecification:
        AttributeName: expira_em
        Enabled: true

# Exportar o URL da fila como variável de ambiente automaticamente
option_settings:
  aws:elasticbeanstalk:application:environment:
    JOBS_QUEUE_URL: !Ref MinhaFila
```

## container_commands vs commands

Uma distinção importante e frequentemente confundida:

```
commands:
  → Executados ANTES da aplicação ser extraída para /var/app/current
  → Sem acesso ao código da aplicação
  → Útil para: instalar dependências do SO, criar diretórios

container_commands:
  → Executados DEPOIS da aplicação ser extraída, antes de iniciar
  → COM acesso ao código em /var/app/staging
  → Útil para: migrações de banco, compilações, seeds de dados
  → Suporta "leader_only: true" (executa apenas em uma instância)
```

```yaml
# .ebextensions/07-migrations.config
container_commands:
  01_migrate:
    command: "python manage.py migrate --noinput"
    leader_only: true    # executar apenas na instância líder do ASG
    env:
      DJANGO_SETTINGS_MODULE: "config.settings.production"

  02_collectstatic:
    command: "python manage.py collectstatic --noinput"
    # sem leader_only: executa em TODAS as instâncias
```

**`leader_only: true`** é essencial para migrações de banco — sem isso, múltiplas instâncias tentariam rodar a migração simultaneamente durante um deploy em ambiente com ASG, causando conflitos.

## Erros comuns e armadilhas

**Colocar secrets em .ebextensions:** o diretório `.ebextensions` é incluído no ZIP do deploy e pode ser commitado no Git — senhas em texto claro ficam expostas no histórico do repositório. Use Secrets Manager ou SSM e leia via SDK no código.

**Não usar `leader_only` em migrações:** em um ASG com 3 instâncias, sem `leader_only` a migração roda 3 vezes em paralelo — possível corrupção de banco ou erros de constraint.

**Usar `commands` quando precisa de `container_commands`:** código em `/var/app/current` ainda não existe durante `commands`. Se seu script precisa acessar arquivos da aplicação (ex: `manage.py`), use sempre `container_commands`.

**Não versionar o `.ebextensions`:** times que configuram ambientes pelo console perdem toda a configuração ao recriar o ambiente. Tudo que é feito pelo console deve ser replicado em `.ebextensions` para ser reproduzível.

## 🧩 Quiz de Fixação

1. Um time usa `commands` para rodar `python manage.py migrate`, mas a migração falha com "No such file or directory". Por que, e como corrigir?

2. Um ambiente Beanstalk tem 5 instâncias EC2 e um `container_commands` sem `leader_only: true` que executa uma migração de banco de dados. Quantas vezes a migração é executada durante um deploy e qual é o risco?

3. Um `.ebextensions` contém uma seção `Resources` com uma tabela DynamoDB. O que acontece com essa tabela quando o ambiente Beanstalk é terminado com `eb terminate`?

**Respostas:**

1) O problema é que `commands` é executado **antes** da aplicação ser extraída para `/var/app/current` — o arquivo `manage.py` ainda não existe no sistema durante essa fase. A correção é mover o comando para `container_commands`, que é executado **após** a extração do código para `/var/app/staging` (onde os arquivos da aplicação já estão disponíveis). Com `container_commands`, o caminho correto seria referenciar `/var/app/staging/manage.py` ou simplesmente `python manage.py` com `cwd: /var/app/staging`.

2) Sem `leader_only: true`, o `container_commands` é executado em **todas as 5 instâncias** simultaneamente durante o deploy. Para migrações de banco de dados, isso significa que 5 processos tentam aplicar as mesmas alterações de schema ao mesmo tempo. Os riscos são: (a) **race conditions** — duas instâncias tentam criar a mesma coluna/tabela simultaneamente, uma delas falha com erro de constraint; (b) **dados duplicados** — se a migração insere dados seed, eles podem ser inseridos 5 vezes; (c) **locks de banco** — dependendo do banco de dados, pode causar deadlocks que bloqueiam a migração indefinidamente. A correção é adicionar `leader_only: true` — o Beanstalk elege uma instância como líder do ASG e apenas ela executa o comando, enquanto as outras aguardam sua conclusão.

3) A tabela DynamoDB criada pela seção `Resources` é gerenciada pelo **CloudFormation stack do ambiente Beanstalk**. Quando o ambiente é terminado com `eb terminate`, o CloudFormation deleta a stack inteira — incluindo todos os recursos definidos em `Resources`, como a tabela DynamoDB. Se a tabela contém dados que precisam ser preservados, é necessário: (a) usar `DeletionPolicy: Retain` na definição do resource para que o CloudFormation não delete o recurso ao deletar a stack; (b) ou criar a tabela DynamoDB separadamente (fora do Beanstalk), como um recurso independente, e apenas referenciar o ARN/nome via variável de ambiente no `.ebextensions`. Para dados persistentes de produção, a segunda abordagem é mais segura e recomendada.
