### Performance no S3 — Multipart Upload, Transfer Acceleration e S3 Select

Transferir objetos grandes para o S3 e processar dados diretamente no bucket são dois cenários onde a configuração padrão deixa muito desempenho na mesa. Multipart Upload paraleliza uploads de grandes arquivos; Transfer Acceleration usa a rede global da AWS para uploads de clientes geograficamente distantes; S3 Select filtra dados no lado do servidor, evitando baixar GiBs para processar apenas KiBs. Este arquivo cobre as três ferramentas com configuração prática.

---

## Multipart Upload — upload paralelo de arquivos grandes

O **Multipart Upload** divide um objeto grande em partes menores, faz upload de cada parte independentemente (em paralelo), e ao final o S3 monta o objeto completo. Isso resolve três problemas do upload sequencial:

```
Problemas do upload sequencial para arquivos grandes:

1. Falha = recomeçar do zero:
   Upload de 10 GB → falha na parte 95% → recomeça do início
   Com Multipart: falha na parte 95 de 100 → só reenviar essa parte

2. Sem aproveitamento de banda paralela:
   Conexão com múltiplos canais disponíveis → upload usa apenas 1
   Com Multipart: cada parte usa um canal diferente simultaneamente

3. Impossível fazer upload > 5 GiB em PUT único:
   Limite hard do S3: 5 GiB por PutObject
   Com Multipart: até 5 TB por objeto
```

### Como o Multipart Upload funciona

```
Processo em 3 etapas:

1. Iniciar (CreateMultipartUpload):
   → S3 retorna um UploadId único para esta operação
   
2. Upload das partes (UploadPart):
   → Cada parte: mínimo 5 MiB (exceto a última)
   → Máximo 10.000 partes por upload
   → Partes enviadas em paralelo com threads/processos diferentes
   → Cada parte retorna um ETag (checksum da parte)
   
3. Completar (CompleteMultipartUpload):
   → Enviar lista de partes (número + ETag) em ordem
   → S3 monta o objeto final e retorna ETag do objeto completo
   
(Se cancelado: AbortMultipartUpload — limpa as partes incompletas)
```

### Implementação em Python

```python
import boto3
import os
import threading
from concurrent.futures import ThreadPoolExecutor, as_completed

def upload_multipart(bucket: str, key: str, filepath: str, part_size_mb: int = 100):
    """Upload paralelo com Multipart — partes de 100 MiB por padrão."""
    s3 = boto3.client('s3')
    file_size = os.path.getsize(filepath)
    part_size = part_size_mb * 1024 * 1024  # converter para bytes
    
    # 1. Iniciar multipart upload
    response = s3.create_multipart_upload(Bucket=bucket, Key=key)
    upload_id = response['UploadId']
    print(f"Iniciado: {upload_id}")
    
    # Calcular número de partes
    parts_count = (file_size + part_size - 1) // part_size
    parts = []
    lock = threading.Lock()
    
    def upload_part(part_number: int):
        offset = (part_number - 1) * part_size
        size = min(part_size, file_size - offset)
        
        with open(filepath, 'rb') as f:
            f.seek(offset)
            data = f.read(size)
        
        response = s3.upload_part(
            Bucket=bucket,
            Key=key,
            UploadId=upload_id,
            PartNumber=part_number,
            Body=data
        )
        
        with lock:
            parts.append({'PartNumber': part_number, 'ETag': response['ETag']})
            print(f"Parte {part_number}/{parts_count} concluída")
        
        return part_number
    
    # 2. Upload paralelo das partes
    try:
        with ThreadPoolExecutor(max_workers=8) as executor:
            futures = [
                executor.submit(upload_part, i)
                for i in range(1, parts_count + 1)
            ]
            for future in as_completed(futures):
                future.result()  # propaga exceções
        
        # 3. Completar o upload
        parts.sort(key=lambda x: x['PartNumber'])
        s3.complete_multipart_upload(
            Bucket=bucket,
            Key=key,
            UploadId=upload_id,
            MultipartUpload={'Parts': parts}
        )
        print(f"Upload concluído: s3://{bucket}/{key}")
    
    except Exception as e:
        # Limpar partes incompletas
        s3.abort_multipart_upload(Bucket=bucket, Key=key, UploadId=upload_id)
        raise e

# Uso
upload_multipart('meu-bucket', 'dados/arquivo-grande.parquet', '/tmp/arquivo.parquet')
```

### Usando o SDK de alto nível (mais simples)

O boto3 tem métodos de alto nível que gerenciam Multipart Upload automaticamente:

```python
import boto3
from boto3.s3.transfer import TransferConfig

s3 = boto3.client('s3')

# TransferConfig controla quando usar Multipart e quantas threads
config = TransferConfig(
    multipart_threshold=100 * 1024 * 1024,    # usar multipart acima de 100 MiB
    max_concurrency=10,                         # 10 threads paralelas
    multipart_chunksize=100 * 1024 * 1024,     # partes de 100 MiB
    use_threads=True
)

# upload_file usa Multipart automaticamente se o arquivo for grande
s3.upload_file(
    '/tmp/dataset-10gb.parquet',
    'meu-bucket',
    'dados/dataset-10gb.parquet',
    Config=config,
    Callback=lambda bytes_transferred: print(f"{bytes_transferred} bytes enviados")
)
```

### Lifecycle para limpar multiparts abandonados

Uploads interrompidos deixam partes incompletas que **consomem storage e geram custo**. Configure uma regra de lifecycle para limpar automaticamente:

```json
{
  "Rules": [{
    "ID": "limpar-multiparts-incompletos",
    "Status": "Enabled",
    "Filter": {},
    "AbortIncompleteMultipartUpload": {
      "DaysAfterInitiation": 7
    }
  }]
}
```

```bash
aws s3api put-bucket-lifecycle-configuration \
  --bucket meu-bucket \
  --lifecycle-configuration file://lifecycle.json
```

## S3 Transfer Acceleration — upload global via rede AWS

**S3 Transfer Acceleration** roteia uploads de clientes geograficamente distantes através da rede global privada da AWS (mesma rede do CloudFront), em vez de usar a internet pública. O cliente faz upload para o edge location do CloudFront mais próximo, e de lá a AWS usa sua backbone de alta velocidade para transferir para o bucket S3 na região de destino.

```
Upload sem Transfer Acceleration (São Paulo → us-east-1):

Usuário (BR) ──internet pública──▶ S3 em us-east-1
              ~15.000 km de cabo,   ~200ms RTT, throughput variável

Upload com Transfer Acceleration:

Usuário (BR) ──▶ Edge Location (GRU) ──backbone AWS──▶ S3 em us-east-1
              ~20ms RTT              rede privada ultra-rápida
              conexão rápida        throughput otimizado
```

```bash
# Habilitar Transfer Acceleration no bucket
aws s3api put-bucket-accelerate-configuration \
  --bucket meu-bucket \
  --accelerate-configuration Status=Enabled

# URL de acesso com Transfer Acceleration:
# https://meu-bucket.s3-accelerate.amazonaws.com/arquivo.jpg
# (em vez de meu-bucket.s3.amazonaws.com)
```

```python
# SDK Python com Transfer Acceleration
s3_accelerated = boto3.client(
    's3',
    config=boto3.session.Config(s3={'use_accelerate_endpoint': True})
)

s3_accelerated.upload_file(
    '/tmp/arquivo.zip',
    'meu-bucket',
    'uploads/arquivo.zip'
)
```

### Quando Transfer Acceleration vale o custo

```
Custo adicional:
  $0.04/GB para uploads acelerados (além do custo normal de PUT)
  $0.08/GB para downloads acelerados (além do custo normal de GET)

Break-even: Transfer Acceleration vale quando o ganho de velocidade
  compensa o custo adicional. A AWS oferece uma ferramenta de teste:
  https://s3-accelerate-speedtest.s3-accelerate.amazonaws.com/en/accelerate-speed-comparsion.html

Quando usar:
  ✓ Usuários geograficamente dispersos fazendo upload de arquivos grandes
  ✓ Aplicações móveis com usuários globais
  ✓ Upload de datasets por parceiros internacionais
  ✓ Quando latência da internet pública é o gargalo (> 500ms RTT)

Quando NÃO usar:
  ✗ Upload de instâncias EC2 na mesma região do bucket (latência já < 1ms)
  ✗ Uploads de pequenos arquivos (overhead fixo > ganho)
  ✗ Conexões já rápidas para a região do bucket
```

## S3 Select — filtrar dados no servidor, não no cliente

**S3 Select** permite executar queries SQL simples diretamente no S3, retornando apenas os dados que passam no filtro — sem baixar o objeto inteiro para a memória do cliente.

```
Sem S3 Select:
  Arquivo CSV de 10 GB → Download completo → Filter no cliente
  Custo: 10 GB × $0.09/GB egress = $0.90 por query
  Tempo: download de 10 GB + processamento

Com S3 Select:
  Arquivo CSV de 10 GB → S3 executa SQL → Retorna apenas 50 MB de resultado
  Custo: $0.002/GB escaneado + $0.0007/GB retornado = ~$0.02 por query
  Tempo: S3 executa internamente, retorna apenas o resultado
```

### Formatos suportados pelo S3 Select

```
Formatos de entrada suportados:
  CSV (incluindo com headers, diferentes delimitadores)
  JSON (LINES — um JSON por linha, ou documento único)
  Apache Parquet (colunar — mais eficiente com S3 Select)
  
Formatos de saída:
  CSV
  JSON

Compressão suportada: GZIP, BZIP2 (não para Parquet)
```

### Exemplo de uso — S3 Select em Python

```python
import boto3
import json

s3 = boto3.client('s3')

# Query em arquivo CSV
response = s3.select_object_content(
    Bucket='meu-bucket-datalake',
    Key='vendas/2024/vendas-janeiro.csv',
    ExpressionType='SQL',
    Expression="""
        SELECT s.produto, s.valor, s.data
        FROM S3Object s
        WHERE s.regiao = 'Sul'
          AND CAST(s.valor AS FLOAT) > 1000.0
        LIMIT 1000
    """,
    InputSerialization={
        'CSV': {
            'FileHeaderInfo': 'USE',  # usar primeira linha como headers
            'RecordDelimiter': '\n',
            'FieldDelimiter': ','
        },
        'CompressionType': 'GZIP'
    },
    OutputSerialization={
        'CSV': {
            'RecordDelimiter': '\n',
            'FieldDelimiter': ','
        }
    }
)

# Processar o stream de resultados
resultado = []
for event in response['Payload']:
    if 'Records' in event:
        records = event['Records']['Payload'].decode('utf-8')
        resultado.extend(records.strip().split('\n'))
    elif 'Stats' in event:
        stats = event['Stats']['Details']
        print(f"Bytes escaneados: {stats['BytesScanned']:,}")
        print(f"Bytes retornados: {stats['BytesReturned']:,}")
        economia = (1 - stats['BytesReturned']/stats['BytesScanned']) * 100
        print(f"Economia de dados: {economia:.1f}%")

print(f"Registros retornados: {len(resultado)}")
```

### S3 Select com Parquet — máxima eficiência

Com Parquet (formato colunar), S3 Select só lê as colunas da query — se o arquivo tem 100 colunas e a query usa 3, apenas 3% dos dados são lidos:

```python
# Query em Parquet — S3 só lê as colunas necessárias
response = s3.select_object_content(
    Bucket='meu-datalake',
    Key='dados/usuarios/2024/part-0001.parquet',
    ExpressionType='SQL',
    Expression="SELECT nome, email FROM S3Object WHERE ativo = true",
    InputSerialization={'Parquet': {}},
    OutputSerialization={'JSON': {}}
)
```

### Limitações do S3 Select

```
Limitações:
  ✗ Sem JOIN entre múltiplos objetos (use Athena para isso)
  ✗ Sem GROUP BY ou funções de agregação (SUM, COUNT, AVG)
  ✗ Objeto máximo: 128 MB comprimido / 5 GB sem compressão
  ✗ Resultado máximo: 128 MB por query
  ✗ Sem suporte a ORC (apenas CSV, JSON, Parquet)
  
Para queries complexas com JOIN e agregações: use Amazon Athena
(Athena usa o mesmo princípio mas com SQL completo e múltiplos arquivos)
```

## Outras otimizações de performance

### Byte-Range Fetches — download paralelo

Assim como Multipart para upload, você pode fazer download em paralelo especificando ranges de bytes:

```python
import boto3
import threading
from concurrent.futures import ThreadPoolExecutor

def download_range(s3_client, bucket, key, start, end, output_buffer, position):
    response = s3_client.get_object(
        Bucket=bucket,
        Key=key,
        Range=f'bytes={start}-{end}'
    )
    data = response['Body'].read()
    output_buffer[position] = data

def parallel_download(bucket, key, output_path, part_size_mb=100):
    s3 = boto3.client('s3')
    
    # Obter tamanho do objeto
    metadata = s3.head_object(Bucket=bucket, Key=key)
    total_size = metadata['ContentLength']
    part_size = part_size_mb * 1024 * 1024
    
    parts_count = (total_size + part_size - 1) // part_size
    buffer = [None] * parts_count
    
    with ThreadPoolExecutor(max_workers=10) as executor:
        futures = []
        for i in range(parts_count):
            start = i * part_size
            end = min(start + part_size - 1, total_size - 1)
            futures.append(
                executor.submit(download_range, s3, bucket, key, start, end, buffer, i)
            )
        
        for future in futures:
            future.result()
    
    with open(output_path, 'wb') as f:
        for part in buffer:
            f.write(part)
```

### Uso de prefixos para paralelizar throughput

Como visto no arquivo de fundamentos, distribuir objetos em múltiplos prefixos aumenta o throughput linear:

```
# Para uploads de alta velocidade (> 3.500 req/s):
# Usar hash do conteúdo como prefixo de roteamento

import hashlib

def s3_key_com_prefixo(nome_arquivo: str) -> str:
    hash_prefix = hashlib.md5(nome_arquivo.encode()).hexdigest()[:4]
    return f"{hash_prefix}/{nome_arquivo}"

# "relatorio-jan.csv" → "a3f2/relatorio-jan.csv"
# "relatorio-fev.csv" → "c1b9/relatorio-fev.csv"
```

## Erros comuns e armadilhas

**Não configurar lifecycle para multiparts abandonados:** cada upload iniciado e não finalizado (por falha ou por código que não chama `AbortMultipartUpload`) deixa partes órfãs que geram custo de storage. Em sistemas com muitos uploads, esse overhead pode ser significativo. Configure sempre a regra `AbortIncompleteMultipartUpload`.

**Usar S3 Select para queries com agregações:** S3 Select não suporta `GROUP BY`, `COUNT()`, `SUM()`. Para essas queries, use Amazon Athena — que é construído sobre o mesmo princípio (query no S3) mas com SQL completo via Presto/Trino.

**Habilitar Transfer Acceleration para uploads de EC2 na mesma região:** o custo adicional ($0.04/GB) não tem benefício — instâncias EC2 na mesma região do bucket se comunicam via rede interna da AWS com latência < 1ms. Transfer Acceleration só ajuda clientes externos à AWS (internet pública).

## 🧩 Quiz de Fixação

1. Um upload de 50 GiB via PutObject falha após 47 GiB transferidos. Com Multipart Upload configurado com partes de 1 GiB, o mesmo upload falha na parte 47 de 50. Qual é o impacto da falha em cada cenário e qual é a vantagem concreta do Multipart?

2. Uma aplicação de analytics precisa calcular a soma de uma coluna numérica de um arquivo CSV de 8 GiB armazenado no S3. Por que S3 Select não resolve esse problema e qual serviço AWS usar no lugar?

3. Uma empresa brasileira faz upload de datasets de 2 GiB para um bucket em us-east-1. O tempo atual de upload é de 20 minutos via internet. Ao habilitar Transfer Acceleration, o tempo cai para 8 minutos. O custo adicional por upload é de $0.08 (2 GB × $0.04/GB). Em qual situação o Transfer Acceleration se paga financeiramente?

**Respostas:**

1) **PutObject (upload sequencial):** 47 GiB foram transferidos e perdidos — o upload precisa recomeçar do zero. O próximo upload envia os 50 GiB completos novamente. **Multipart Upload (partes de 1 GiB):** 47 partes foram concluídas com sucesso (cada uma com seu ETag armazenado no S3). Apenas a parte 47 (1 GiB) falhou. O próximo upload pode **reenviar apenas a parte 47** e depois chamar `CompleteMultipartUpload` com as 50 ETags. A vantagem concreta: em vez de re-transferir 50 GiB (ou 47 GiB desde o ponto de falha), apenas 1 GiB (2% do total) precisa ser reenviado. Isso é especialmente crítico em conexões instáveis ou com bandwidth cara (ex: uploads de filiais via link limitado).

2) S3 Select **não suporta funções de agregação** como `SUM()`, `COUNT()`, `AVG()`, `GROUP BY` — a linguagem SQL do S3 Select é muito limitada (essencialmente apenas `SELECT`, `WHERE` e `LIMIT`). Para calcular a soma de uma coluna, o S3 Select retornaria apenas os registros filtrados e a soma teria que ser calculada no cliente — baixando os dados relevantes, não a soma já calculada. A solução correta é **Amazon Athena**: suporta SQL completo (Presto/Trino), executa `SELECT SUM(coluna) FROM tabela WHERE condição` diretamente sobre arquivos S3 sem mover os dados, retorna apenas o resultado agregado, e cobra $5/TB escaneado. Para um CSV de 8 GiB com query de agregação, Athena retorna o resultado em segundos por $0.04 (8 GB × $5/TB).

3) O Transfer Acceleration se paga quando o **valor do tempo economizado supera $0.08**. Cálculo: o upload foi de 20 min → 8 min, economia de 12 minutos por upload. Se o custo de uma hora de engenheiro/analista que aguarda o upload é $50/hora, 12 minutos valem $10 — muito acima dos $0.08. Mesmo com custo de infraestrutura (ex: instância EC2 ou Glue job aguardando o dado): 12 minutos de compute de m5.large = $0.096/12min = ~$0.019 — ainda abaixo dos $0.08, então só pelo compute não compensa. **Quando compensa:** (a) quando o dado precisa chegar rapidamente para processos dependentes com SLA (12 min a menos = $X de SLA atendido); (b) quando múltiplos uploads paralelos aumentam o throughput total, não só a latência individual; (c) quando o tempo de engenheiro aguardando é o custo real (12 min × salário = >> $0.08). A análise deve considerar o custo total de espera, não apenas o custo de compute.
