### Segurança no S3 — Bucket Policies, ACLs, Block Public Access, Pre-signed URLs e Criptografia

Segurança no S3 opera em múltiplas camadas independentes. Um objeto pode ser bloqueado pela política do bucket, mesmo que o IAM do usuário permita; pode ser bloqueado pelo Block Public Access, mesmo que a política diga "Allow"; pode exigir que o acesso seja feito via URL temporária assinada. Entender como essas camadas se sobrepõem é fundamental para construir armazenamento seguro sem tornar dados inacessíveis acidentalmente.

---

## Hierarquia de controle de acesso

```
Para uma requisição chegar ao objeto, ela precisa passar por TODAS as camadas:

1. AWS IAM (identidade do caller)
   "Esta identidade tem permissão para acessar S3?"
   
2. Bucket Policy (política do recurso)
   "Este bucket permite essa operação desta identidade/IP/condição?"
   
3. Block Public Access (override de segurança)
   "Esta configuração bloqueia acesso público independente de qualquer política?"
   
4. ACL do objeto (legado — evitar em novos projetos)
   "Esta ACL específica do objeto permite?"
   
5. Object Lock / WORM
   "O objeto está bloqueado contra modificação/deleção?"

Lógica de avaliação:
  → Se QUALQUER camada negar explicitamente: acesso negado
  → Block Public Access tem precedência sobre tudo (exceto IAM de conta raiz)
  → Acesso público requer: Block Public Access desabilitado + Allow explícito
```

---

## Bucket Policies — controle de acesso baseado em recursos

Bucket Policies são documentos JSON anexados ao bucket que controlam acesso por identidade, IP, condições e operações específicas. São **resource-based policies** — aplicam-se ao bucket independente de quem está acessando.

### Estrutura de uma Bucket Policy

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "IdentificadorOpcional",
      "Effect": "Allow" | "Deny",
      "Principal": "quem",      // identidade que a regra se aplica
      "Action": "o quê",        // operação S3
      "Resource": "onde",       // bucket ou objeto
      "Condition": {}           // condições opcionais
    }
  ]
}
```

### Exemplos práticos de Bucket Policy

**1. Bucket privado — acesso apenas a uma role específica:**

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "AWS": "arn:aws:iam::123456789:role/AppBackendRole"
    },
    "Action": ["s3:GetObject", "s3:PutObject"],
    "Resource": "arn:aws:s3:::meu-bucket-dados/*"
  }]
}
```

**2. Bucket público para hosting de site estático (leitura pública):**

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": "*",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::meu-site-estatico/*"
  }]
}
```

**3. Forçar HTTPS — bloquear requisições HTTP:**

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyHTTP",
    "Effect": "Deny",
    "Principal": "*",
    "Action": "s3:*",
    "Resource": [
      "arn:aws:s3:::meu-bucket",
      "arn:aws:s3:::meu-bucket/*"
    ],
    "Condition": {
      "Bool": {
        "aws:SecureTransport": "false"
      }
    }
  }]
}
```

**4. Restringir acesso por VPC (via VPC Endpoint):**

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::meu-bucket-privado",
        "arn:aws:s3:::meu-bucket-privado/*"
      ]
    },
    {
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::meu-bucket-privado",
        "arn:aws:s3:::meu-bucket-privado/*"
      ],
      "Condition": {
        "StringNotEquals": {
          "aws:sourceVpce": "vpce-abc12345"
        }
      }
    }
  ]
}
```

**5. Restringir uploads sem criptografia KMS:**

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyUnencryptedObjectUploads",
    "Effect": "Deny",
    "Principal": "*",
    "Action": "s3:PutObject",
    "Resource": "arn:aws:s3:::meu-bucket-sensivel/*",
    "Condition": {
      "StringNotEquals": {
        "s3:x-amz-server-side-encryption": "aws:kms"
      }
    }
  }]
}
```

## Block Public Access — proteção global contra exposição acidental

**Block Public Access** é uma camada de segurança que **sobrepõe** qualquer política ou ACL que tentaria tornar objetos públicos. Existe no nível de conta e no nível de bucket.

```
4 configurações do Block Public Access:

BlockPublicAcls:
  → Impede adicionar ACLs que concedem acesso público
  → Ignora ACLs existentes que concedem acesso público

IgnorePublicAcls:
  → Ignora todas as ACLs públicas existentes e novas
  → O bucket não respeita nenhuma ACL que conceça acesso público

BlockPublicPolicy:
  → Impede bucket policies que concedam acesso público

RestrictPublicBuckets:
  → Restringe acesso público mesmo se existir uma policy pública
  → Apenas o dono da conta e usuários autorizados por IAM podem acessar
```

```bash
# Ver configuração atual
aws s3api get-public-access-block --bucket meu-bucket

# Habilitar todas as proteções (padrão recomendado para todos os buckets privados)
aws s3api put-public-access-block \
  --bucket meu-bucket \
  --public-access-block-configuration \
    "BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true"

# Habilitar Block Public Access no nível de conta (proteção global)
aws s3control put-public-access-block \
  --account-id 123456789 \
  --public-access-block-configuration \
    "BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true"
```

> **Desde abril de 2023:** a AWS habilitou Block Public Access por padrão para **todos os novos buckets**. Para hosting de site estático ou assets públicos, é necessário desabilitar explicitamente — o que é intencional por design.

## ACLs — legado (evitar em novos projetos)

ACLs (Access Control Lists) são o mecanismo original de controle de acesso do S3, anterior às Bucket Policies. Ainda existem mas são consideradas legado — a AWS recomenda desabilitar ACLs e usar apenas Bucket Policies + IAM.

```bash
# Desabilitar ACLs no bucket (recomendado para novos projetos)
aws s3api put-bucket-ownership-controls \
  --bucket meu-bucket \
  --ownership-controls Rules=[{ObjectOwnership=BucketOwnerEnforced}]
# Com BucketOwnerEnforced: ACLs são desabilitadas,
# o dono do bucket é dono de todos os objetos
```

```
ACLs predefinidas ainda usadas ocasionalmente:
  private:           apenas dono tem acesso (padrão)
  public-read:       qualquer um pode ler (evitar — use policy pública)
  bucket-owner-read: dono do bucket pode ler objetos de outras contas
  bucket-owner-full-control: dono do bucket tem controle total
```

## Pre-signed URLs — acesso temporário sem credenciais AWS

**Pre-signed URLs** permitem compartilhar acesso a um objeto específico por um tempo limitado, sem expor credenciais AWS e sem tornar o bucket público. O URL é assinado com as credenciais de quem o gerou — o acesso expira automaticamente.

```
Caso de uso típico:

1. Usuário clica "Download do relatório"
2. Backend (com credenciais AWS) gera uma pre-signed URL:
   → URL válida por 15 minutos
   → Para aquele objeto específico
   → Com a operação GET apenas
3. Backend retorna a URL para o cliente
4. Cliente baixa o arquivo diretamente do S3
   → Sem passar pelo backend (sem consumir banda do servidor)
   → Sem expor credenciais AWS
   → URL expira após 15 minutos — link compartilhado não funciona depois
```

```python
import boto3
from datetime import timedelta

s3 = boto3.client('s3', region_name='us-east-1')

# Gerar URL para download (GET)
url_download = s3.generate_presigned_url(
    'get_object',
    Params={
        'Bucket': 'meu-bucket',
        'Key': 'relatorios/relatorio-jan-2024.pdf',
        'ResponseContentDisposition': 'attachment; filename="relatorio.pdf"'
    },
    ExpiresIn=900  # 15 minutos (em segundos)
)

# Gerar URL para upload (PUT) — cliente faz upload direto para S3
url_upload = s3.generate_presigned_url(
    'put_object',
    Params={
        'Bucket': 'meu-bucket',
        'Key': f'uploads/{user_id}/foto-perfil.jpg',
        'ContentType': 'image/jpeg'
    },
    ExpiresIn=300  # 5 minutos
)
```

```bash
# Via CLI
aws s3 presign s3://meu-bucket/arquivo.pdf \
  --expires-in 3600  # 1 hora
```

### Limitações das Pre-signed URLs

```
Máxima duração:
  Com credenciais de IAM User: 7 dias (604.800 segundos)
  Com credenciais de IAM Role (STS token): mesmo tempo do token STS
    → Tokens STS expiram em até 12 horas por padrão
    → Se o token STS expirar antes da URL: URL inválida mesmo no prazo

Segurança:
  → Quem tiver a URL pode acessar — não há verificação de identidade
  → Não revogável (não há como invalidar antes do prazo)
  → Recomendado: prazos curtos (< 1 hora para downloads, < 15 min para uploads)
```

## Criptografia — dados em repouso

O S3 oferece criptografia em repouso com três modelos distintos, variando em quem controla as chaves.

### SSE-S3 — Server-Side Encryption com chave gerenciada pela AWS

```
SSE-S3:
  → AWS gerencia e rotaciona as chaves automaticamente
  → Criptografia AES-256
  → Sem custo adicional
  → Sem controle sobre as chaves (você não pode revogar ou auditar)
  → "Padrão" desde janeiro de 2023 (todos os novos objetos são criptografados)
```

```bash
# Upload com SSE-S3 (já é o padrão, mas pode ser explícito)
aws s3 cp arquivo.csv s3://meu-bucket/ \
  --sse AES256

# Configurar SSE-S3 como padrão do bucket
aws s3api put-bucket-encryption \
  --bucket meu-bucket \
  --server-side-encryption-configuration '{
    "Rules": [{
      "ApplyServerSideEncryptionByDefault": {
        "SSEAlgorithm": "AES256"
      }
    }]
  }'
```

### SSE-KMS — Server-Side Encryption com AWS KMS

```
SSE-KMS:
  → Chaves gerenciadas pelo AWS KMS (você controla)
  → Auditoria completa via CloudTrail (cada acesso a um objeto = chamada KMS logada)
  → Pode revogar acesso ao bucket revogando a chave KMS
  → Suporta Customer Managed Keys (CMK) para controle total
  → Custo adicional: $0.03 por 10.000 operações KMS
  → Limite de throughput do KMS pode ser gargalo em alto volume
```

```bash
# Upload com SSE-KMS usando CMK
aws s3 cp dados-sensiveis.csv s3://meu-bucket/ \
  --sse aws:kms \
  --sse-kms-key-id arn:aws:kms:us-east-1:123:key/mrk-abc123

# Configurar SSE-KMS como padrão do bucket
aws s3api put-bucket-encryption \
  --bucket meu-bucket \
  --server-side-encryption-configuration '{
    "Rules": [{
      "ApplyServerSideEncryptionByDefault": {
        "SSEAlgorithm": "aws:kms",
        "KMSMasterKeyID": "arn:aws:kms:us-east-1:123:key/mrk-abc123"
      },
      "BucketKeyEnabled": true
    }]
  }'
```

**`BucketKeyEnabled: true`** é importante para performance: sem ele, cada GetObject gera uma chamada KMS individual (custo e throughput). Com BucketKeyEnabled, o S3 usa uma chave de sessão do bucket, reduzindo chamadas KMS em até 99%.

### SSE-C — Server-Side Encryption com chave do cliente

```
SSE-C:
  → Você fornece a chave de criptografia em cada requisição
  → AWS usa a chave para criptografar/descriptografar e não a armazena
  → Máximo controle — a AWS nunca tem acesso permanente à chave
  → Responsabilidade total pela gestão e armazenamento das chaves
  → Não suportado via console AWS — apenas via API/CLI/SDK
  → Se você perder a chave: dados inacessíveis permanentemente
```

```python
import boto3
import os
import base64

# Gerar chave AES-256 (32 bytes)
chave = os.urandom(32)
chave_b64 = base64.b64encode(chave).decode()

s3 = boto3.client('s3')

# Upload com SSE-C
s3.put_object(
    Bucket='meu-bucket',
    Key='dados-ultra-sensiveis.enc',
    Body=data,
    SSECustomerAlgorithm='AES256',
    SSECustomerKey=chave,  # bytes de 32 caracteres
)

# Download com SSE-C (requer a mesma chave)
response = s3.get_object(
    Bucket='meu-bucket',
    Key='dados-ultra-sensiveis.enc',
    SSECustomerAlgorithm='AES256',
    SSECustomerKey=chave,
)
```

### Comparativo dos três modelos de criptografia

| Aspecto | SSE-S3 | SSE-KMS | SSE-C |
|---|---|---|---|
| Quem gerencia a chave | AWS | AWS KMS (você controla) | Você (completamente) |
| Auditoria de acesso | Não | Sim (CloudTrail) | Não (você audita) |
| Revogação de acesso | Não | Sim (desabilitar chave) | Sim (reter a chave) |
| Custo adicional | Nenhum | $0.03/10K ops | Nenhum |
| Compliance FIPS 140-2 | Não | Sim | Depende da impl. |
| Quando usar | Padrão geral | Dados regulatórios | Controle máximo |

## Criptografia em trânsito

Além da criptografia em repouso, dados em trânsito são protegidos via TLS:

```bash
# Bucket Policy para forçar HTTPS (já mostrado acima)
# Todos os SDKs AWS usam HTTPS por padrão
# Para verificar se um bucket exige TLS:
aws s3api get-bucket-policy --bucket meu-bucket | \
  jq '.Policy | fromjson | .Statement[] | select(.Condition.Bool."aws:SecureTransport" == "false")'
```

## Erros comuns e armadilhas

**"O bucket está público mas eu não quero":** verificar: (1) Block Public Access está habilitado? (2) A Bucket Policy tem `"Principal": "*"` com `"Effect": "Allow"`? (3) Alguma ACL no bucket ou objeto tem `public-read`? Todas as três precisam ser inspecionadas.

**Pre-signed URL gerada com IAM Role expira cedo:** se o token STS da role tiver 1 hora de validade e você gerar uma URL com `ExpiresIn=3600`, a URL pode expirar em 30 minutos se o token foi gerado há 30 minutos. Para URLs longas, use credenciais de IAM User (até 7 dias) ou gere a URL pouco antes de entregar ao cliente.

**Gargalo de KMS em alto throughput:** sem BucketKeyEnabled, cada GetObject faz uma chamada KMS. Para um bucket com 10.000 downloads/segundo, isso seria 10.000 chamadas KMS/segundo — acima do limite padrão (10.000/s por região, compartilhado). Habilitar `BucketKeyEnabled` é obrigatório em buckets de alto throughput com SSE-KMS.

## 🧩 Quiz de Fixação

1. Uma Bucket Policy tem `"Effect": "Allow", "Principal": "*", "Action": "s3:GetObject"`, mas Block Public Access está ativado com `RestrictPublicBuckets=true`. Um usuário anônimo tenta acessar um objeto. O que acontece e qual configuração prevalece?

2. Um desenvolvedor gerou uma Pre-signed URL com validade de 24 horas usando uma IAM Role com token STS de 8 horas de validade. O usuário tenta usar a URL às 10 horas após a geração. O que acontece e por quê?

3. Um banco precisa armazenar documentos de clientes no S3 com auditoria de cada acesso (quem acessou qual documento, quando). SSE-S3 ou SSE-KMS — qual é obrigatório para esse requisito e por quê SSE-S3 não atende?

**Respostas:**

1) O acesso é **negado**. `RestrictPublicBuckets=true` tem precedência sobre qualquer Bucket Policy — é um override de segurança que **ignora** políticas públicas, mesmo que digan `Allow`. A avaliação da camada Block Public Access ocorre antes da avaliação da Bucket Policy. Para tornar o bucket realmente público, seria necessário primeiro desabilitar o Block Public Access (`RestrictPublicBuckets=false` e `IgnorePublicAcls=false` no mínimo), e depois a Bucket Policy com `"Principal": "*"` funcionaria. Essa arquitetura em camadas é intencional — previne que uma Bucket Policy mal configurada acidentalmente exponha dados mesmo em contas onde Block Public Access está ativado no nível de conta.

2) A URL **não funciona mais** às 10 horas, mesmo que sua validade configurada seja 24 horas. O token STS da IAM Role tinha 8 horas de validade — após 8 horas, o token expirou. As credenciais usadas para assinar a URL (o token STS) são inválidas, então a assinatura da URL também é inválida. O S3 valida a assinatura contra as credenciais originais no momento do acesso — credenciais expiradas = URL inválida. Para URLs de longa duração (> horas), use credenciais de IAM User permanentes (máximo 7 dias de pré-signed URL) ou re-gere a URL pouco antes de entregá-la ao cliente.

3) **SSE-KMS é obrigatório** para esse requisito. SSE-S3 usa chaves gerenciadas internamente pela AWS — não há integração com CloudTrail para registrar "qual arquivo foi acessado por qual identidade". Com SSE-KMS, **cada operação de descriptografia** (ou seja, cada GetObject em um objeto criptografado) gera um evento no **AWS CloudTrail** com: identidade do caller (ARN do usuário/role), timestamp exato, ID do objeto (via bucket+key nos parâmetros), e o key ID KMS usado. Isso cria o trail de auditoria exigido: o auditor pode verificar no CloudTrail quais documentos foram acessados, por qual identidade, em qual data/hora — exatamente o que compliance bancário requer para dados de clientes. SSE-S3 oferece criptografia mas sem auditoria — não atende o requisito.
