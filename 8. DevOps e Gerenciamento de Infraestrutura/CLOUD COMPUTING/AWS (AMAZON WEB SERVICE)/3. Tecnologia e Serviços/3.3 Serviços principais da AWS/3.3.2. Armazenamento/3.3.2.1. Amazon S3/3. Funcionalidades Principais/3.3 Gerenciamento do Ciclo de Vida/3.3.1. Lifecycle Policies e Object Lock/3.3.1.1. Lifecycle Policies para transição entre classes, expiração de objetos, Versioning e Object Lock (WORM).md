### Lifecycle Policies, Versioning e Object Lock — gerenciamento do ciclo de vida no S3

Dados no S3 têm um ciclo de vida natural: são criados, acessados com frequência no início, ficam raramente acessados com o tempo, e eventualmente precisam ser arquivados ou deletados. Lifecycle Policies automatizam esse ciclo completamente — sem intervenção manual. Versioning preserva o histórico completo de mudanças. Object Lock garante imutabilidade absoluta para compliance regulatório.

---

## Versioning — histórico completo de objetos

**Versioning** preserva todas as versões de um objeto, incluindo deleções. É um pré-requisito para Object Lock e para proteção contra deleção acidental.

```
Bucket com Versioning habilitado:

PutObject "relatorio.pdf" (versão A)  → armazena version-id: "aaa111"
PutObject "relatorio.pdf" (versão B)  → armazena version-id: "bbb222" (nova current)
DeleteObject "relatorio.pdf"           → adiciona delete marker (version-id: "ccc333")
                                         versão B ainda existe, apenas marcada como deletada

Estado do bucket:
  relatorio.pdf (ccc333) = delete marker  ← "current version" — parece deletado
  relatorio.pdf (bbb222) = versão B       ← versão anterior acessível por version-id
  relatorio.pdf (aaa111) = versão A       ← versão mais antiga

Para acessar versão específica:
  aws s3api get-object --bucket meu-bucket --key relatorio.pdf --version-id bbb222 ./restaurado.pdf

Para "desfazer" deleção (remover delete marker):
  aws s3api delete-object --bucket meu-bucket --key relatorio.pdf --version-id ccc333
  → versão B volta a ser a current version
```

```bash
# Habilitar versioning
aws s3api put-bucket-versioning \
  --bucket meu-bucket \
  --versioning-configuration Status=Enabled

# Listar todas as versões de um objeto
aws s3api list-object-versions \
  --bucket meu-bucket \
  --prefix relatorio.pdf

# Restaurar versão anterior
aws s3api copy-object \
  --bucket meu-bucket \
  --copy-source "meu-bucket/relatorio.pdf?versionId=bbb222" \
  --key relatorio.pdf
  # copia a versão antiga como nova current version
```

### Estados do Versioning

```
Unversioned (padrão):  apenas a versão atual existe
Enabled:               todas as versões são preservadas
Suspended:             novas versões não são criadas, versões antigas preservadas
                       (usado para pausar sem deletar histórico)
```

### Custo do Versioning

Cada versão é armazenada e cobrada separadamente. Um bucket com versioning e alta frequência de modificações pode acumular muitas versões — use Lifecycle Policies para expirar versões antigas.

## Lifecycle Policies — automação do ciclo de vida

**Lifecycle Policies** são regras declarativas que instruem o S3 a **transicionar** objetos entre classes de armazenamento ou **expirar** (deletar) objetos automaticamente com base em critérios de tempo.

### Estrutura de uma Lifecycle Policy

```json
{
  "Rules": [
    {
      "ID": "nome-da-regra",
      "Status": "Enabled",
      "Filter": {
        "Prefix": "logs/",          // aplica apenas a objetos com este prefixo
        "ObjectSizeGreaterThan": 131072  // apenas objetos > 128 KB
      },
      "Transitions": [...],
      "Expiration": {...},
      "NoncurrentVersionTransitions": [...],
      "NoncurrentVersionExpiration": {...},
      "AbortIncompleteMultipartUpload": {...}
    }
  ]
}
```

### Regra completa — logs com ciclo de vida de 7 anos

```json
{
  "Rules": [{
    "ID": "ciclo-de-vida-logs-aplicacao",
    "Status": "Enabled",
    "Filter": {"Prefix": "logs/aplicacao/"},

    "Transitions": [
      {
        "Days": 30,
        "StorageClass": "STANDARD_IA"
      },
      {
        "Days": 90,
        "StorageClass": "GLACIER_IR"
      },
      {
        "Days": 365,
        "StorageClass": "DEEP_ARCHIVE"
      }
    ],

    "Expiration": {
      "Days": 2555
    },

    "NoncurrentVersionTransitions": [
      {
        "NoncurrentDays": 30,
        "StorageClass": "STANDARD_IA"
      },
      {
        "NoncurrentDays": 90,
        "StorageClass": "GLACIER_IR"
      }
    ],

    "NoncurrentVersionExpiration": {
      "NoncurrentDays": 365,
      "NewerNoncurrentVersions": 5
    },

    "AbortIncompleteMultipartUpload": {
      "DaysAfterInitiation": 7
    }
  }]
}
```

```
Linha do tempo de um objeto de log:

Dia 0:    Upload para STANDARD
Dia 30:   → STANDARD_IA (46% mais barato)
Dia 90:   → GLACIER_IR (83% mais barato que Standard)
Dia 365:  → DEEP_ARCHIVE (96% mais barato que Standard)
Dia 2555: → DELETADO (após ~7 anos)

Para versões não-atuais (com Versioning habilitado):
  Dia 30 após se tornar noncurrent:  → STANDARD_IA
  Dia 90 após se tornar noncurrent:  → GLACIER_IR
  Dia 365 após se tornar noncurrent: → DELETADO
  (ou quando existirem mais que 5 versões anteriores → deleta as mais antigas)
```

### Restrições nas transições

```
Ordem mínima de transições (dias desde a criação):

STANDARD → STANDARD_IA:     mínimo 30 dias
STANDARD → ONE_ZONE_IA:     mínimo 30 dias
STANDARD → INTELLIGENT_TIERING: mínimo 0 dias
STANDARD_IA → GLACIER_IR:   mínimo 30 dias
GLACIER_IR → GLACIER:       mínimo 0 dias
GLACIER → DEEP_ARCHIVE:     mínimo 0 dias

Restrição importante:
  Não é possível transicionar de GLACIER de volta para classes mais quentes
  via Lifecycle — somente restaurando o objeto (cópia temporária)
  
Transição mínima de objeto para IA: 128 KB
  Objetos menores que 128 KB NÃO são transicionados para Standard-IA ou One Zone-IA
  (cobrariam mais do que ficar no Standard)
```

```bash
# Aplicar lifecycle ao bucket
aws s3api put-bucket-lifecycle-configuration \
  --bucket meu-bucket \
  --lifecycle-configuration file://lifecycle.json

# Visualizar a configuração atual
aws s3api get-bucket-lifecycle-configuration --bucket meu-bucket

# Deletar toda a configuração de lifecycle
aws s3api delete-bucket-lifecycle --bucket meu-bucket
```

## Object Lock — imutabilidade WORM

**Object Lock** implementa o modelo **WORM (Write Once, Read Many)** no S3: objetos não podem ser sobrescritos ou deletados pelo período configurado. É a ferramenta para compliance regulatório que exige imutabilidade de dados.

```
WORM — Write Once, Read Many:
  → Gravar: sempre possível (apenas uma vez no mesmo key+version)
  → Ler: sempre possível
  → Modificar: IMPOSSÍVEL durante o período de retenção
  → Deletar: IMPOSSÍVEL durante o período de retenção
  
  NINGUÉM pode deletar — nem o root da conta AWS — até o período expirar.
  (exceto durante o período de cool-off de 24h após habilitar, para cancelar)
```

### Pré-requisitos

```bash
# Object Lock DEVE ser habilitado na CRIAÇÃO do bucket (não pode ser habilitado depois)
aws s3api create-bucket \
  --bucket meu-bucket-compliance \
  --region us-east-1

aws s3api put-object-lock-configuration \
  --bucket meu-bucket-compliance \
  --object-lock-configuration '{
    "ObjectLockEnabled": "Enabled",
    "Rule": {
      "DefaultRetention": {
        "Mode": "COMPLIANCE",
        "Years": 7
      }
    }
  }'

# Versioning é habilitado automaticamente ao ativar Object Lock
```

### Modos de retenção

```
COMPLIANCE (mais restritivo):
  → NENHUM usuário pode remover a proteção ou deletar o objeto antes do prazo
  → Nem o usuário root da conta AWS
  → Ideal para: regulação financeira (SOX, BACEN), saúde (HIPAA), jurídico

GOVERNANCE (moderadamente restritivo):
  → A maioria dos usuários não pode alterar ou deletar
  → Usuários com permissão especial s3:BypassGovernanceRetention PODEM remover
  → Ideal para: auditoria interna, proteção contra deleção acidental com escape hatch
  → Permite administradores corrigirem erros sem burocracia de regulação externa
```

### Configurando Object Lock por objeto

```bash
# Ao fazer upload, definir retenção específica
aws s3api put-object \
  --bucket meu-bucket-compliance \
  --key registros/contrato-2024-001.pdf \
  --body contrato.pdf \
  --object-lock-mode COMPLIANCE \
  --object-lock-retain-until-date "2031-01-15T00:00:00Z"

# Ver a configuração de retenção de um objeto
aws s3api get-object-retention \
  --bucket meu-bucket-compliance \
  --key registros/contrato-2024-001.pdf

# Estender o prazo (apenas para frente — nunca reduzir em COMPLIANCE)
aws s3api put-object-retention \
  --bucket meu-bucket-compliance \
  --key registros/contrato-2024-001.pdf \
  --retention '{
    "Mode": "COMPLIANCE",
    "RetainUntilDate": "2034-01-15T00:00:00Z"
  }'
```

### Legal Hold — bloqueio sem prazo definido

**Legal Hold** bloqueia um objeto indefinidamente (sem data de expiração), usado quando há litígio ou investigação em andamento:

```bash
# Aplicar Legal Hold (bloqueia independente de retenção configurada)
aws s3api put-object-legal-hold \
  --bucket meu-bucket-compliance \
  --key registros/email-investigacao.eml \
  --legal-hold Status=ON

# Remover Legal Hold (requer permissão s3:PutObjectLegalHold)
aws s3api put-object-legal-hold \
  --bucket meu-bucket-compliance \
  --key registros/email-investigacao.eml \
  --legal-hold Status=OFF
```

## Combinando Versioning + Lifecycle + Object Lock

```
Arquitetura de compliance para registros financeiros (7 anos):

Bucket: "registros-financeiros-prod"
  ├── Object Lock: COMPLIANCE mode, default 7 anos
  ├── Versioning: Enabled (obrigatório com Object Lock)
  └── Lifecycle Rules:
      ├── Versões atuais:
      │   ├── Dia 0-90:   STANDARD (acesso frequente no primeiro trimestre)
      │   ├── Dia 90-365: STANDARD_IA
      │   ├── Dia 365+:   GLACIER_IR
      │   └── Dia 2555:   EXPIRAR (após 7 anos — quando WORM já expirou)
      └── Versões não-atuais:
          ├── Dia 30:  GLACIER_IR
          └── Dia 90:  DEEP_ARCHIVE (versões antigas raramente acessadas)
```

## Replication — sincronização entre buckets

**S3 Replication** copia objetos automaticamente entre buckets em tempo real (assíncrona, geralmente < 15 minutos):

```
Cross-Region Replication (CRR):
  Bucket A (us-east-1) → Bucket B (sa-east-1)
  Casos de uso: DR multi-região, latência para usuários locais, compliance geográfico

Same-Region Replication (SRR):
  Bucket A (us-east-1) → Bucket B (us-east-1)
  Casos de uso: separação de ambientes, log aggregation, teste de transformação
```

```bash
# Configurar replicação
aws s3api put-bucket-replication \
  --bucket bucket-origem \
  --replication-configuration '{
    "Role": "arn:aws:iam::123:role/S3ReplicationRole",
    "Rules": [{
      "Status": "Enabled",
      "Filter": {"Prefix": "dados-criticos/"},
      "Destination": {
        "Bucket": "arn:aws:s3:::bucket-destino-dr",
        "StorageClass": "STANDARD_IA",
        "ReplicationTime": {
          "Status": "Enabled",
          "Time": {"Minutes": 15}
        },
        "Metrics": {
          "Status": "Enabled",
          "EventThreshold": {"Minutes": 15}
        }
      },
      "DeleteMarkerReplication": {"Status": "Enabled"}
    }]
  }'
```

**S3 Replication Time Control (RTC):** garante que 99.99% dos objetos serão replicados em 15 minutos, com SLA. Tem custo adicional mas é necessário para RPO < 15 minutos.

## Erros comuns e armadilhas

**Habilitar Object Lock depois da criação do bucket:** não é possível. O Object Lock deve ser configurado na criação. Para buckets existentes, a única opção é criar um novo bucket com Object Lock e migrar os dados.

**Confundir COMPLIANCE com GOVERNANCE:** em COMPLIANCE, nem o root da conta pode remover a proteção — isso é ideal para compliance externo mas problemático se houver erro (ex: upload de arquivo errado com retenção de 7 anos). Use GOVERNANCE quando precisar de um escape hatch administrativo.

**Não expirar versões antigas com versioning ativo:** sem `NoncurrentVersionExpiration` na lifecycle policy, versões antigas acumulam indefinidamente e geram custo crescente. Cada sobrescrita de objeto duplica o storage cobrado.

**Replicação não copia objetos existentes:** ao configurar replicação, apenas objetos criados DEPOIS da configuração são replicados. Para migrar objetos existentes, use S3 Batch Operations ou `aws s3 sync`.

## 🧩 Quiz de Fixação

1. Um bucket tem Versioning habilitado. Um usuário faz `DeleteObject` em `contrato.pdf` sem especificar version-id. O que acontece com o objeto e como o usuário pode desfazer a deleção?

2. Uma empresa configura Object Lock com `Mode: COMPLIANCE` e `RetainUntilDate: 2031-01-15` em um arquivo de contrato. Dois dias depois, percebe que fez upload do arquivo errado. Quais são as opções disponíveis?

3. Um bucket com Versioning habilitado acumula versões de 10.000 objetos modificados diariamente. Após 1 ano, quantas versões existem e como uma Lifecycle Policy com `NoncurrentVersionExpiration` com `NewerNoncurrentVersions: 5` e `NoncurrentDays: 30` reduziria esse número?

**Respostas:**

1) Sem especificar version-id, o S3 **não deleta o objeto** — ele adiciona um **delete marker** como nova "current version". O objeto original (com seu version-id) continua existindo no bucket. Para quem acessa o objeto sem version-id, ele parece deletado (recebe 404). Para **desfazer a deleção**: basta deletar o delete marker. Identificar o version-id do delete marker com `aws s3api list-object-versions --bucket meu-bucket --prefix contrato.pdf` (aparece em `DeleteMarkers`), e então `aws s3api delete-object --bucket meu-bucket --key contrato.pdf --version-id <id-do-delete-marker>`. A versão anterior volta a ser a current version automaticamente — sem nenhum dado perdido.

2) As opções são muito limitadas em modo COMPLIANCE: (a) **Não é possível deletar ou sobrescrever** o objeto até 2031-01-15 — nem mesmo o root da conta AWS pode. A proteção COMPLIANCE é absoluta por design regulatório; (b) É possível **adicionar** um novo objeto com o arquivo correto no mesmo key (uma nova versão será criada com seu próprio Object Lock), mas a versão errada permanecerá armazenada e protegida até 2031; (c) É possível **estender** o prazo de retenção (aumentar para 2035, por exemplo), mas não encurtar; (d) **Legal Hold** pode ser adicionado mas não ajuda — não é possível remover a proteção de retenção já existente. A lição é que COMPLIANCE deve ser usado somente quando a imutabilidade absoluta é um requisito regulatório — para proteção interna, use GOVERNANCE que permite que admins com permissão especial corrijam erros.

3) Sem Lifecycle Policy: após 1 ano, cada objeto foi modificado ~365 vezes → 10.000 objetos × 365 versões = ~3.650.000 versões totais armazenadas (incluindo current). Com `NoncurrentVersionExpiration: NoncurrentDays=30, NewerNoncurrentVersions=5`: (a) O S3 mantém no máximo as **5 versões mais recentes** não-atuais de cada objeto; (b) Versões com mais de 30 dias são elegíveis para expiração se houver mais de 5 versões; (c) Após 30 dias: cada objeto teria a current version + 5 versões não-atuais = 6 versões por objeto; (d) Total reduzido: 10.000 × 6 = **60.000 versões** (vs 3.650.000 sem a policy) — redução de 98.4%. O custo de storage cai proporcionalmente. Isso demonstra a importância crítica de configurar NoncurrentVersionExpiration em qualquer bucket com Versioning ativo em produção.
