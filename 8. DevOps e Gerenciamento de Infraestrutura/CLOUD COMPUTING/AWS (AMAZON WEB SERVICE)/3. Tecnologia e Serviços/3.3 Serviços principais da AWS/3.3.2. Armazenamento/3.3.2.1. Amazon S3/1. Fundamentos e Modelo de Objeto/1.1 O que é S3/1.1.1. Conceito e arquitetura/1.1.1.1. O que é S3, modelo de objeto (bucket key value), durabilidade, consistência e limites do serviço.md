### Amazon S3 — o que é, modelo de objeto, durabilidade e consistência

Amazon S3 (Simple Storage Service) é o serviço de **armazenamento de objetos** da AWS. Diferente de sistemas de arquivos (EFS, EBS) onde você navega por diretórios e modifica arquivos, o S3 armazena objetos imutáveis identificados por uma chave única — você os substitui inteiramente ou os versiona, mas não edita partes. Essa imutabilidade é o que permite a durabilidade extraordinária de 11 noves (99.999999999%) e a escala infinita.

---

## Armazenamento de objetos vs. outros modelos

```
Três modelos de armazenamento:

Block Storage (EBS):
  → Blocos de dados endereçados por offset
  → Sistema de arquivos montado na instância
  → Latência baixa, acesso aleatório eficiente
  → Ideal para: SO, banco de dados, aplicações que precisam de I/O rápido
  → Análogo a: HD interno do computador

File Storage (EFS):
  → Sistema de arquivos hierárquico (diretórios/subdiretórios)
  → Montado via NFS em múltiplas instâncias simultaneamente
  → Ideal para: compartilhamento de arquivos entre servidores
  → Análogo a: servidor de arquivos de rede (NAS)

Object Storage (S3):
  → Objetos planos identificados por chave única
  → Acesso via HTTP/S (API REST)
  → Sem hierarquia real — apenas simulada com prefixos
  → Ideal para: dados não estruturados, backups, mídia, data lakes
  → Análogo a: almoxarifado enorme onde cada item tem uma etiqueta única
```

## O modelo de objeto S3 — Bucket, Key, Value, Metadata

### Bucket

O **Bucket** é o contêiner de nível superior no S3. É globalmente único (o nome não pode existir em nenhuma outra conta AWS no mundo), pertence a uma região específica, e é o limite de configuração para políticas, versionamento, replicação e logging.

```
Regras de nomenclatura de buckets:
  ├── 3-63 caracteres
  ├── Apenas letras minúsculas, números e hífens
  ├── Deve começar com letra ou número
  ├── Não pode terminar com hífen
  ├── Não pode parecer um endereço IP (192.168.1.1)
  └── Globalmente único em todas as contas AWS do mundo
```

```bash
# Criar bucket
aws s3api create-bucket \
  --bucket meu-bucket-producao-2024 \
  --region us-east-1

# us-east-1 é a única região que não precisa de LocationConstraint
# Para outras regiões:
aws s3api create-bucket \
  --bucket meu-bucket-sa-east-1 \
  --region sa-east-1 \
  --create-bucket-configuration LocationConstraint=sa-east-1
```

### Key — a "chave" do objeto

A **Key** é o identificador único do objeto dentro do bucket. Parece um caminho de arquivo, mas tecnicamente é uma string plana — o S3 não tem diretórios reais:

```
Bucket: minha-empresa-dados
Key:    uploads/imagens/usuarios/2024/01/foto-user-123.jpg

Não existe a "pasta" uploads/imagens/usuarios/2024/01/
O S3 simula hierarquia usando o "/" como delimitador visual
O objeto existe diretamente no bucket com a key completa

URL de acesso:
  https://minha-empresa-dados.s3.amazonaws.com/uploads/imagens/usuarios/2024/01/foto-user-123.jpg
  ou via path-style (legado):
  https://s3.amazonaws.com/minha-empresa-dados/uploads/imagens/usuarios/2024/01/foto-user-123.jpg
```

### Value — o conteúdo do objeto

O **Value** é o conteúdo binário do objeto. Pode ser qualquer coisa: imagem, vídeo, JSON, CSV, Parquet, executável, ZIP. O S3 não interpreta o conteúdo — apenas armazena e retorna.

```
Limites de tamanho:
  Tamanho mínimo:  0 bytes (objeto vazio é válido)
  Tamanho máximo:  5 TB por objeto
  
  Upload em uma única requisição: até 5 GiB
  Acima de 5 GiB: obrigatório usar Multipart Upload
  Recomendado Multipart Upload acima de: 100 MiB
```

### Metadata — metadados do objeto

Cada objeto pode ter até **2 KB de metadados** no formato chave-valor:

```
Metadados do sistema (gerenciados pelo S3):
  Content-Type:     image/jpeg
  Content-Length:   204800
  Last-Modified:    2024-01-15T10:30:00Z
  ETag:             "abc123def456..."  (MD5 do conteúdo)

Metadados do usuário (prefixo x-amz-meta-):
  x-amz-meta-user-id:     "user-123"
  x-amz-meta-upload-date: "2024-01-15"
  x-amz-meta-processed:   "false"
```

## Durabilidade e disponibilidade

### 11 noves de durabilidade — o que significa na prática

```
Durabilidade 99.999999999% (11 noves):

Para 10.000.000 de objetos armazenados:
  → Perda esperada: 0.0000001 objetos por ano
  → Ou seja: estatisticamente, um objeto perdido a cada 10 milhões de anos

Como o S3 alcança isso:
  → Dados replicados em múltiplas instalações físicas dentro da região
  → Mínimo de 3 AZs para classes Standard
  → Checksums em todas as operações (detecta corrupção bit a bit)
  → Verificação e reparo contínuo dos dados armazenados

Durabilidade ≠ Disponibilidade:
  Durabilidade: probabilidade de não perder o objeto
  Disponibilidade: probabilidade de conseguir acessá-lo quando quiser

  S3 Standard:
    Durabilidade:    99.999999999%
    Disponibilidade: 99.99% (downtime máximo: ~52 min/ano)
```

### Arquitetura de redundância por classe

```
S3 Standard e Intelligent-Tiering:
  Dados replicados em ≥3 Availability Zones
  Uma AZ pode ser destruída completamente → dados preservados

S3 One Zone-IA:
  Dados em apenas 1 AZ
  Durabilidade: 99.999999999% (DENTRO dessa AZ)
  Se a AZ for destruída completamente: dados perdidos
  → Usar apenas para dados reproduzíveis ou com backup externo

S3 Glacier classes:
  Replicado em ≥3 AZs (mesma durabilidade do Standard)
```

## Consistência — como o S3 trata operações concorrentes

O S3 oferece **strong consistency** (consistência forte) para todas as operações desde dezembro de 2020:

```
Strong Consistency no S3:

PUT (upload de novo objeto):
  → Leitura imediatamente após o PUT retorna o novo objeto ✓
  → Sem janela de inconsistência

PUT (substituição de objeto existente):
  → Leitura imediatamente após retorna a nova versão ✓

DELETE:
  → Leitura imediatamente após retorna 404 ✓

LIST após PUT:
  → O objeto aparece imediatamente na listagem ✓

Antes de dez/2020 (eventual consistency — legado):
  → PUT de objeto novo: eventual consistency em LIST
  → Substituição/DELETE: eventual consistency na leitura
  → Isso causava bugs onde objetos recém-uploaded não apareciam
```

Essa mudança eliminou uma categoria inteira de bugs em aplicações que dependiam de ler um objeto logo após gravá-lo.

## Limites do serviço

| Recurso | Limite | Notas |
|---|---|---|
| Buckets por conta | 100 (padrão) / 1.000 (sob solicitação) | Soft limit — aumentável |
| Objetos por bucket | Ilimitado | Sem limite documentado |
| Tamanho máximo de objeto | 5 TB | Multipart obrigatório acima de 5 GiB |
| Chave máxima (key) | 1.024 bytes | UTF-8 encoded |
| Metadados por objeto | 2 KB | Chaves + valores |
| Tags por objeto | 10 | Chave até 128 chars, valor até 256 chars |
| Partes no Multipart Upload | 10.000 | Tamanho mínimo de parte: 5 MiB |
| Prefixos paralelos | Sem limite | Relevante para performance de throughput |

## Acesso ao S3 — URLs e métodos

### Path-style vs Virtual-hosted-style

```bash
# Virtual-hosted-style (padrão atual — recomendado)
https://meu-bucket.s3.amazonaws.com/pasta/arquivo.jpg
https://meu-bucket.s3.us-east-1.amazonaws.com/pasta/arquivo.jpg

# Path-style (legado — AWS está descontinuando)
https://s3.amazonaws.com/meu-bucket/pasta/arquivo.jpg
https://s3.us-east-1.amazonaws.com/meu-bucket/pasta/arquivo.jpg
```

### Operações básicas via AWS CLI

```bash
# Upload
aws s3 cp arquivo.jpg s3://meu-bucket/uploads/arquivo.jpg
aws s3 sync ./pasta-local/ s3://meu-bucket/pasta-remota/

# Download
aws s3 cp s3://meu-bucket/uploads/arquivo.jpg ./arquivo.jpg

# Listar objetos
aws s3 ls s3://meu-bucket/
aws s3 ls s3://meu-bucket/uploads/ --recursive

# Deletar
aws s3 rm s3://meu-bucket/uploads/arquivo.jpg
aws s3 rm s3://meu-bucket/uploads/ --recursive

# Informações de um objeto
aws s3api head-object \
  --bucket meu-bucket \
  --key uploads/arquivo.jpg
```

### S3 via SDK — upload com metadados

```python
import boto3

s3 = boto3.client('s3')

# Upload com metadados e content-type
s3.put_object(
    Bucket='meu-bucket',
    Key='uploads/imagens/foto.jpg',
    Body=open('foto.jpg', 'rb'),
    ContentType='image/jpeg',
    Metadata={
        'user-id': 'user-123',
        'upload-source': 'mobile-app'
    },
    StorageClass='STANDARD',
    ServerSideEncryption='aws:kms',
    SSEKMSKeyId='arn:aws:kms:us-east-1:123:key/abc'
)

# Download com streaming (eficiente para arquivos grandes)
response = s3.get_object(Bucket='meu-bucket', Key='uploads/imagens/foto.jpg')
content = response['Body'].read()
content_type = response['ContentType']
metadata = response['Metadata']  # {'user-id': 'user-123', ...}
```

## Prefixos e performance

O S3 distribui os dados internamente usando o prefixo da key como hash. Isso tem implicação direta em throughput:

```
Throughput por prefixo:
  Leitura:  5.500 requisições/segundo por prefixo
  Escrita:  3.500 requisições/segundo por prefixo

Com múltiplos prefixos, o throughput escala proporcionalmente:
  1 prefixo:   3.500 PUT/s e  5.500 GET/s
  4 prefixos: 14.000 PUT/s e 22.000 GET/s

Exemplo de organização com múltiplos prefixos:
  s3://bucket/2024/01/dados.parquet    ← prefixo "2024/01"
  s3://bucket/2024/02/dados.parquet    ← prefixo "2024/02"
  s3://bucket/2024/03/dados.parquet    ← prefixo "2024/03"

Anti-padrão — prefixo sequencial (gargalo):
  s3://bucket/log-0001.txt
  s3://bucket/log-0002.txt
  s3://bucket/log-0003.txt
  (todos no mesmo prefixo vazio → limitado a 3.500 PUT/s)

Padrão recomendado — prefixo com hash ou data:
  s3://bucket/a3f2/log-0001.txt
  s3://bucket/b1c9/log-0002.txt
  (prefixos diferentes → throughput distribuído)
```

## Erros comuns e armadilhas

**Nome de bucket já existe:** como os nomes são globais, nomes genéricos como `backup`, `assets`, `uploads` já estão tomados. Use prefixo com nome da empresa e sufixo único: `minha-empresa-assets-prod-2024`.

**Confundir durabilidade com disponibilidade:** um objeto pode ter 11 noves de durabilidade (nunca será perdido) mas ainda ter disponibilidade de 99.9% (pode ficar inacessível por horas/ano). Para dados críticos, considere replicação cross-region.

**Usar path-style URLs em novos projetos:** a AWS está descontinuando path-style access. Use sempre virtual-hosted-style no formato `bucket.s3.amazonaws.com`.

**Não configurar Block Public Access:** por padrão, o S3 bloqueia acesso público. Ao criar buckets de hosting de sites ou assets públicos, é necessário desabilitar explicitamente — o que é correto, mas deve ser feito conscientemente com entendimento das implicações.

## 🧩 Quiz de Fixação

1. Um bucket S3 tem um objeto com a key `dados/relatorios/2024/janeiro/relatorio-fiscal.pdf`. Um desenvolvedor diz que "deletou a pasta `dados/relatorios/2024/`". O que realmente aconteceu tecnicamente no S3, e como verificar se outros objetos com prefixo similar ainda existem?

2. Uma aplicação faz upload de um objeto e imediatamente tenta lê-lo, mas ocasionalmente recebe 404. O desenvolvedor alega "eventual consistency do S3". Essa explicação é válida para clusters criados após 2020? O que pode estar causando o 404?

3. Uma aplicação de IoT gera 100.000 objetos por segundo com keys sequenciais (`sensor-0000001.json`, `sensor-0000002.json`, etc.). Por que isso pode causar gargalo de throughput e como redesenhar as keys para distribuir a carga?

**Respostas:**

1) Tecnicamente, **nada aconteceu no nível de estrutura do S3** — não existem "pastas" reais. O que o desenvolvedor fez foi provavelmente deletar todos os objetos cujas keys começam com o prefixo `dados/relatorios/2024/`. O objeto `relatorio-fiscal.pdf` foi deletado pois sua key começa com esse prefixo. Para verificar se outros objetos similares ainda existem: `aws s3 ls s3://meu-bucket/dados/relatorios/ --recursive` — isso lista recursivamente todos os objetos com esse prefixo, independente de "subpastas". A ilusão de hierarquia no S3 existe apenas visualmente (o console e o CLI usam `/` como delimitador para exibição), mas na API cada objeto tem uma key plana completa.

2) A explicação de "eventual consistency" **não é válida para clusters AWS criados após dezembro de 2020** — o S3 implementou strong consistency para todas as operações nessa data. Um 404 imediatamente após um upload bem-sucedido hoje indica outro problema: (a) o upload pode ter falhado silenciosamente (verificar o response code do PUT — deve ser HTTP 200); (b) a aplicação pode estar lendo de um bucket diferente ou com uma key levemente diferente (diferença de maiúsculas/minúsculas — S3 é case-sensitive); (c) pode haver uma Race Condition na aplicação onde múltiplas threads sobrescrevem o objeto e o DELETE acontece antes da leitura; (d) pode ser um problema de IAM onde a role tem permissão de PUT mas não de GET para aquele prefixo específico.

3) Keys sequenciais como `sensor-0000001.json`, `sensor-0000002.json` criam um gargalo porque o S3 distribui internamente os dados usando um hash do prefixo da key — e prefixos lexicograficamente próximos e sequenciais tendem a cair no mesmo shard interno, limitando o throughput a ~3.500 PUTs/segundo por shard. **Solução:** adicionar um hash ou UUID no início da key para distribuir entre múltiplos prefixos: `a3f2c1/2024/01/15/sensor-0000001.json` (hash dos primeiros 4 caracteres da key original) ou usar timestamp no prefixo com granularidade de segundo/minuto: `2024/01/15/10/30/45/sensor-0000001.json`. Com 100.000 objetos/segundo, seriam necessários pelo menos `ceil(100.000 / 3.500) = 29` prefixos distintos para sustentar o throughput, o que qualquer esquema baseado em hash natural das keys provavelmente alcança.
