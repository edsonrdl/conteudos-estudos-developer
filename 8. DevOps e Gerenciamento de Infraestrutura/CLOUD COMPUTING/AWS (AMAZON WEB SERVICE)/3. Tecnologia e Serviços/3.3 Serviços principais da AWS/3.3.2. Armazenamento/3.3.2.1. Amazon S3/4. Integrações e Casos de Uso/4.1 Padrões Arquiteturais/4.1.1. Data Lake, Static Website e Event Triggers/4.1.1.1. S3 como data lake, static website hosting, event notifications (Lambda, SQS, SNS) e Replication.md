### S3 como data lake, static website, event notifications e Replication

O S3 vai muito além de armazenamento passivo de arquivos. Ele é o substrato de praticamente toda arquitetura de dados na AWS, o backend de sites estáticos de alta disponibilidade, o produtor de eventos que aciona Lambdas e filas, e a base de estratégias de DR multi-região. Este arquivo fecha o sub-glossário S3 com os padrões arquiteturais mais usados em produção.

---

## S3 como Data Lake

Um **data lake** é um repositório centralizado que armazena dados estruturados, semi-estruturados e não estruturados em formato bruto, sem transformação prévia. O S3 é o substrato de data lakes na AWS por três razões: custo, escala e integração.

```
Arquitetura de Data Lake no S3:

┌──────────────────────────────────────────────────────────────┐
│                    Data Lake no S3                          │
│                                                              │
│  s3://meu-datalake/                                         │
│  ├── raw/                     ← dados brutos, sem transformar│
│  │   ├── vendas/2024/01/      (CSV, JSON, XML como chegou)  │
│  │   └── logs/apache/2024/                                  │
│  │                                                           │
│  ├── processed/               ← dados limpos e tipados      │
│  │   ├── vendas/year=2024/    (Parquet particionado)        │
│  │   └── clientes/            (Delta Lake, Iceberg)         │
│  │                                                           │
│  └── curated/                 ← agregados prontos para BI   │
│      ├── kpis-diarios/        (Parquet pequenos, agregados) │
│      └── relatorios/          (resultado de jobs Glue/EMR)  │
│                                                              │
│  Serviços que consomem:                                     │
│  Amazon Athena  → SQL ad-hoc direto no S3                   │
│  AWS Glue       → ETL e catálogo de dados                   │
│  Amazon EMR     → Spark/Hadoop                              │
│  Amazon Redshift Spectrum → query S3 como tabelas externas  │
│  SageMaker      → treinar modelos com dados do S3           │
└──────────────────────────────────────────────────────────────┘
```

### Particionamento — fundamental para performance de queries

O particionamento organiza os dados em subdiretórios que os engines de query (Athena, Spark, Redshift Spectrum) usam para **evitar escanear arquivos desnecessários**:

```
Sem particionamento (scan completo):
  s3://datalake/vendas/vendas-todas.parquet  ← 500 GB
  
  Query: "Vendas de janeiro de 2024"
  Athena escaneia: 500 GB ($2.50 em custo de query)

Com particionamento por data:
  s3://datalake/vendas/year=2024/month=01/part-0001.parquet  ← 2 GB
  s3://datalake/vendas/year=2024/month=02/part-0001.parquet
  ...
  
  Query: "Vendas de janeiro de 2024 WHERE year=2024 AND month=01"
  Athena escaneia: 2 GB ($0.01 em custo de query) — 250x mais barato
```

```python
# Gerar dados particionados com Pandas + PyArrow
import pandas as pd
import pyarrow as pa
import pyarrow.parquet as pq
import boto3

df = pd.read_csv('vendas.csv')
df['year'] = pd.to_datetime(df['data']).dt.year
df['month'] = pd.to_datetime(df['data']).dt.month

# Escrever particionado direto para S3
table = pa.Table.from_pandas(df)
pq.write_to_dataset(
    table,
    root_path='s3://meu-datalake/vendas/',
    partition_cols=['year', 'month'],
    filesystem=pa.fs.S3FileSystem(region='us-east-1')
)
# Resultado: s3://meu-datalake/vendas/year=2024/month=1/part-0001.parquet
```

### Formatos de arquivo ideais para data lake

```
CSV / JSON: leitura linha por linha, sem schema — bom para raw layer
  → Scan completo sempre necessário
  → Sem compressão eficiente de colunas
  → Ideal apenas para ingestão (raw)

Parquet (colunar): compressão por coluna, leitura de colunas seletivas
  → Queries que usam poucos campos: 5-10x menos dados lidos
  → Compressão típica: 10:1 vs CSV
  → Ideal para processed/curated layers

Apache Iceberg / Delta Lake (table formats):
  → ACID transactions no S3 (commit atômico de múltiplos arquivos)
  → Time travel (query de dados como eram em um ponto no tempo)
  → Schema evolution (adicionar colunas sem reescrever tudo)
  → Compatível com Athena v3, Glue, Spark
  → Ideal para dados que precisam de updates/deletes (ex: LGPD)
```

## Static Website Hosting

O S3 pode servir arquivos HTML, CSS, JavaScript e imagens como um site estático — com alta disponibilidade automática, sem servidores para gerenciar, e com custo de centavos por mês para sites de médio porte.

```bash
# 1. Criar bucket com nome igual ao domínio (opcional mas convencional)
aws s3api create-bucket \
  --bucket www.meusite.com.br \
  --region us-east-1

# 2. Habilitar static website hosting
aws s3api put-bucket-website \
  --bucket www.meusite.com.br \
  --website-configuration '{
    "IndexDocument": {"Suffix": "index.html"},
    "ErrorDocument": {"Key": "404.html"},
    "RoutingRules": [{
      "Condition": {"KeyPrefixEquals": "blog/"},
      "Redirect": {
        "Protocol": "https",
        "HostName": "blog.meusite.com.br"
      }
    }]
  }'

# 3. Desabilitar Block Public Access (necessário para site público)
aws s3api put-public-access-block \
  --bucket www.meusite.com.br \
  --public-access-block-configuration \
    "BlockPublicAcls=false,IgnorePublicAcls=false,BlockPublicPolicy=false,RestrictPublicBuckets=false"

# 4. Adicionar Bucket Policy para leitura pública
aws s3api put-bucket-policy \
  --bucket www.meusite.com.br \
  --policy '{
    "Version": "2012-10-17",
    "Statement": [{
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::www.meusite.com.br/*"
    }]
  }'

# URL do site:
# http://www.meusite.com.br.s3-website-us-east-1.amazonaws.com
```

### Arquitetura com CloudFront (recomendada para produção)

S3 Website + CloudFront é o padrão de site estático em produção:

```
Usuário → CloudFront (HTTPS, cache, domínio customizado) → S3 (origem)

Vantagens do CloudFront sobre S3 direto:
  ✓ HTTPS com certificado ACM gratuito
  ✓ Domínio customizado (www.meusite.com.br)
  ✓ Cache nas edge locations — menor latência global
  ✓ Cache reduz custo de GET no S3
  ✓ WAF integration
  ✓ S3 permanece privado (acesso apenas via CloudFront OAC)
```

```bash
# Deploy de site React com pipeline completo
# 1. Build
npm run build

# 2. Sync para S3 (apenas arquivos modificados)
aws s3 sync ./build/ s3://www.meusite.com.br/ \
  --delete \
  --cache-control "max-age=31536000" \
  --exclude "index.html" \
  --exclude "*.json"

# index.html sem cache (sempre buscar versão nova)
aws s3 cp ./build/index.html s3://www.meusite.com.br/ \
  --cache-control "no-cache,no-store,must-revalidate"

# 3. Invalidar cache do CloudFront
aws cloudfront create-invalidation \
  --distribution-id EDFDVBD6EXAMPLE \
  --paths "/*"
```

## Event Notifications — S3 como produtor de eventos

O S3 pode publicar eventos (upload, deleção, restauração de Glacier) para **Lambda**, **SQS** e **SNS** automaticamente. Isso transforma o S3 em um produtor de eventos para pipelines event-driven.

```
Tipos de eventos disponíveis:
  s3:ObjectCreated:*          → qualquer criação (PUT, POST, COPY, multipart)
  s3:ObjectCreated:Put        → apenas PUT
  s3:ObjectRemoved:*          → deleção ou delete marker
  s3:ObjectRestore:*          → restauração de Glacier
  s3:Replication:*            → eventos de replicação
  s3:LifecycleExpiration:*    → expiração por lifecycle
  s3:ObjectTagging:*          → adição/remoção de tags
```

### Configurando Event Notifications

```bash
# Via AWS CLI — notificação para Lambda
aws s3api put-bucket-notification-configuration \
  --bucket meu-bucket-uploads \
  --notification-configuration '{
    "LambdaFunctionConfigurations": [{
      "LambdaFunctionArn": "arn:aws:lambda:us-east-1:123:function:processar-upload",
      "Events": ["s3:ObjectCreated:*"],
      "Filter": {
        "Key": {
          "FilterRules": [
            {"Name": "prefix", "Value": "uploads/imagens/"},
            {"Name": "suffix", "Value": ".jpg"}
          ]
        }
      }
    }],
    "QueueConfigurations": [{
      "QueueArn": "arn:aws:sqs:us-east-1:123:fila-processamento",
      "Events": ["s3:ObjectCreated:*"],
      "Filter": {
        "Key": {"FilterRules": [{"Name": "suffix", "Value": ".csv"}]}
      }
    }],
    "TopicConfigurations": [{
      "TopicArn": "arn:aws:sns:us-east-1:123:alertas-bucket",
      "Events": ["s3:ObjectRemoved:*"]
    }]
  }'
```

### Padrões event-driven com S3

**Pipeline de processamento de imagens:**
```
Upload foto  →  S3  →  Lambda  →  Redimensionar  →  S3 (processed/)
                   ↓
                  SQS  →  Lambda  →  Detectar faces (Rekognition)  →  DynamoDB
```

**Ingestão de dados em tempo real:**
```
Parceiro deposita CSV  →  S3 (raw/)  →  EventBridge  →  Glue Job
                                                       →  Lambda (validação)
                                                       →  SNS (notificação)
```

**EventBridge para roteamento avançado** (mais flexível que notificações diretas):
```bash
# Habilitar EventBridge notifications (suporta mais tipos de evento e filtros complexos)
aws s3api put-bucket-notification-configuration \
  --bucket meu-bucket \
  --notification-configuration '{"EventBridgeConfiguration": {}}'

# Criar regra EventBridge para filtrar e rotear
aws events put-rule \
  --name "s3-grandes-uploads" \
  --event-pattern '{
    "source": ["aws.s3"],
    "detail-type": ["Object Created"],
    "detail": {
      "bucket": {"name": ["meu-bucket"]},
      "object": {"size": [{"numeric": [">", 104857600]}]}
    }
  }'
```

## S3 Replication — sincronização entre buckets

Já introduzida no arquivo de Lifecycle, aqui o foco é nos padrões arquiteturais:

### Disaster Recovery multi-região

```
Região primária: us-east-1
  Bucket: dados-prod-primary
  ├── Object Lock: COMPLIANCE (7 anos)
  ├── Versioning: Enabled
  └── Lifecycle: Standard → IA → Glacier

         CRR (Cross-Region Replication)
                    ↓
Região de DR: sa-east-1
  Bucket: dados-prod-dr-brazil
  ├── Object Lock: COMPLIANCE (7 anos) → réplica também é imutável
  ├── Versioning: Enabled
  └── Lifecycle: Standard-IA (menos acesso esperado)

RPO (Recovery Point Objective): < 15 minutos com S3 RTC
RTO (Recovery Time Objective): minutos (apenas redirecionar DNS/endpoints)
```

### Separação de ambientes com SRR

```
Same-Region Replication — casos de uso:
  1. Logs → bucket de auditoria imutável (Object Lock no destino)
  2. Produção → staging (réplica para testes com dados reais)
  3. Centralizar logs de múltiplas contas em conta de segurança
  4. Replicar apenas subset de objetos (com filtros de prefixo/tag)
```

## S3 Object Lambda — transformar dados no acesso

**S3 Object Lambda** permite interceptar GetObject e transformar o objeto antes de entregá-lo ao cliente — sem criar cópias:

```
Sem Object Lambda:
  Cliente → S3 → recebe CSV bruto (10 MB)

Com Object Lambda:
  Cliente → S3 Object Lambda Access Point → Lambda (remove PII, filtra colunas)
           → Cliente recebe JSON filtrado (2 MB, sem dados sensíveis)

Casos de uso:
  ✓ Remover dados pessoais (LGPD/GDPR) antes de entregar para analytics
  ✓ Converter formato (CSV → JSON) sem armazenar cópia
  ✓ Redimensionar imagem sob demanda
  ✓ Watermark dinâmico em documentos
  ✓ Mascarar dados sensíveis para ambientes de dev/teste
```

## Erros comuns e armadilhas

**Loop infinito S3 → Lambda → S3:** uma função Lambda que escreve no mesmo bucket que a dispara pode criar um loop. Se o evento é `s3:ObjectCreated:*` e a Lambda faz PutObject no mesmo bucket, ela é acionada novamente. Use prefixos/sufixos diferentes para entrada e saída, ou buckets diferentes.

**Perder eventos durante configuração de notificações:** há uma janela entre criar o bucket e configurar as notificações onde eventos podem ser perdidos. Se o pipeline depende de não perder eventos, use SQS como destino (durável) em vez de Lambda direto (que pode perder se estiver throttled).

**Replicação não replica objetos existentes:** ao criar uma regra de replicação, apenas objetos criados após a configuração são replicados. Para objetos existentes, use **S3 Batch Replication** ou `aws s3 sync`.

**Custo de egress em replicação cross-region:** a replicação CRR transfere dados entre regiões — o custo de transferência é $0.02/GB (para a maioria das regiões). Para 10 TB de dados replicados: $200 de egress. Calcule o custo total de CRR antes de ativar para todos os dados.

## 🧩 Quiz de Fixação

1. Uma aplicação faz upload de imagens JPEG para `s3://meu-bucket/uploads/` e uma Lambda deve redimensioná-las, salvando em `s3://meu-bucket/processed/`. A Lambda é acionada por `s3:ObjectCreated:*` no bucket inteiro. Qual é o risco e como configurar corretamente para evitá-lo?

2. Um data lake Parquet no S3 tem os dados particionados por `year/month/day`. Uma query Athena busca todas as vendas de um cliente específico nos últimos 3 anos (sem filtro de data na query). O custo da query é alto ($50). Como o particionamento deveria ser reprojetado para esse padrão de query?

3. Uma empresa tem um bucket S3 em us-east-1 com 100 TB de dados e quer implementar DR em sa-east-1 via CRR. A política de retenção é mínima (dados deletados em produção devem ser deletados na réplica também). Qual é o custo mensal aproximado da replicação considerando que 1 TB de dados novos são adicionados por mês, e qual configuração é necessária para sincronizar as deleções?

**Respostas:**

1) O risco é um **loop infinito**: a Lambda salva em `processed/` (dentro do mesmo bucket `meu-bucket`) → o evento `s3:ObjectCreated:*` dispara a Lambda novamente para o arquivo em `processed/` → a Lambda tenta redimensionar um arquivo já processado → cria novo arquivo em `processed/` → loop. **Configuração correta:** adicionar um **filtro de prefixo** na notificação: `{"Name": "prefix", "Value": "uploads/"}`. Assim, apenas objetos criados em `uploads/` disparam a Lambda — objetos criados em `processed/` não geram notificação. Alternativamente (e mais seguro): usar **dois buckets separados** — `bucket-uploads` para entrada e `bucket-processados` para saída, eliminando qualquer possibilidade de loop por configuração.

2) O particionamento por `year/month/day` é **ineficiente** para queries por cliente, porque a query precisa escanear todos os arquivos de 3 anos para encontrar os registros de um cliente específico (nenhuma partição é eliminada). Para o padrão "buscar dados de um cliente específico", a solução é **repartir por `customer_id`**: `s3://datalake/vendas/customer_id=123/arquivo.parquet`. Com essa estrutura, a query filtra `WHERE customer_id = '123'` e Athena escaneia apenas a partição daquele cliente. Na prática, para dados com alta cardinalidade de customer_id, usa-se **particionamento com hash**: `customer_bucket=A3` (primeiros 2 chars do ID em hex) para manter no máximo ~256 partições e evitar criar milhões de diretórios com poucos arquivos cada. Uma outra abordagem é um índice invertido no DynamoDB: `customer_id → lista de arquivos S3`, e a Lambda/Athena consulta o DynamoDB antes para saber quais arquivos escanear.

3) **Custo mensal da CRR:** 1 TB de dados novos × $0.02/GB de transferência cross-region = 1.024 GB × $0.02 = **$20.48/mês** de egress. Mais o custo de armazenamento na região de destino (100 TB + crescimento): assumindo Standard-IA no destino para economizar: 100 TB × $0.0125/GB-mês ≈ **$1.280/mês**. Total: ~**$1.300/mês** para manter o DR. **Para sincronizar deleções:** na configuração de replicação, incluir `"DeleteMarkerReplication": {"Status": "Enabled"}` — isso replica os delete markers para o bucket destino, fazendo com que objetos deletados em produção também apareçam como deletados na réplica. **Atenção:** DeleteMarkerReplication só replica delete markers (deleções sem version-id). Deleções com version-id específico (deletar versão permanentemente) **não são replicadas** por padrão — isso é intencional para proteger a réplica de deleções acidentais ou maliciosas.
