### AWS Site-to-Site VPN — Virtual Private Gateway, Customer Gateway, túneis redundantes e limites

A AWS Site-to-Site VPN cria uma conexão criptografada entre a VPC AWS e a rede on-premises através da internet pública, usando o protocolo IPsec. É a forma mais rápida de estabelecer conectividade híbrida — configurável em minutos, sem necessidade de hardware dedicado ou circuito físico. Cada conexão VPN tem **dois túneis IPsec redundantes** em AZs diferentes para garantir disponibilidade.

---

## Componentes da Site-to-Site VPN

```
Arquitetura completa:

Rede On-premises                        AWS VPC
  ┌─────────────────┐                ┌──────────────────────┐
  │                 │                │                      │
  │  Roteador/      │  Túnel 1 (AZ-a)│ Virtual Private      │
  │  Firewall  ─────┼────IPsec───────┤ Gateway (VGW)        │
  │  (Customer│     │  Túnel 2 (AZ-b)│                      │
  │  Gateway) ─────┼────IPsec───────┤ ─── Route Table      │
  │                 │                │     (propagação BGP) │
  │  IP: 203.0.113.1│                │                      │
  └─────────────────┘                │  EC2, RDS, ECS...    │
                                     └──────────────────────┘

Customer Gateway (CGW):
  → Representa o dispositivo VPN on-premises na AWS
  → Objeto lógico com o IP público do roteador on-premises
  → AWS não gerencia — você configura o hardware/software

Virtual Private Gateway (VGW):
  → O lado AWS da VPN
  → Gerenciado pela AWS, altamente disponível
  → Anexado à VPC
  → Termina os túneis IPsec

Site-to-Site VPN Connection:
  → Une o CGW e o VGW
  → Contém 2 túneis IPsec (1 por AZ AWS)
  → Cada túnel tem IPs diferentes do lado AWS
```

## Criando a conexão VPN

```bash
# Passo 1: Criar Customer Gateway (representa o dispositivo on-premises)
aws ec2 create-customer-gateway \
  --bgp-asn 65000 \               # ASN do roteador on-premises (BGP)
  --public-ip 203.0.113.1 \       # IP público do roteador on-premises
  --type ipsec.1 \
  --tag-specifications 'ResourceType=customer-gateway,Tags=[{Key=Name,Value=cgw-datacenter-sp}]'

# Passo 2: Criar Virtual Private Gateway
aws ec2 create-vpn-gateway \
  --type ipsec.1 \
  --amazon-side-asn 64512 \       # ASN do lado AWS (para BGP)
  --tag-specifications 'ResourceType=vpn-gateway,Tags=[{Key=Name,Value=vgw-vpc-producao}]'

# Passo 3: Anexar VGW à VPC
aws ec2 attach-vpn-gateway \
  --vpn-gateway-id vgw-0abc123 \
  --vpc-id vpc-0abc123

# Passo 4: Criar a conexão VPN
aws ec2 create-vpn-connection \
  --type ipsec.1 \
  --customer-gateway-id cgw-0abc123 \
  --vpn-gateway-id vgw-0abc123 \
  --options '{
    "StaticRoutesOnly": false,
    "TunnelOptions": [
      {
        "TunnelInsideCidr": "169.254.10.0/30",
        "PreSharedKey": "chave-pre-compartilhada-1",
        "Phase1LifetimeSeconds": 28800,
        "Phase2LifetimeSeconds": 3600,
        "DPDTimeoutSeconds": 30
      },
      {
        "TunnelInsideCidr": "169.254.11.0/30",
        "PreSharedKey": "chave-pre-compartilhada-2"
      }
    ]
  }' \
  --tag-specifications 'ResourceType=vpn-connection,Tags=[{Key=Name,Value=vpn-producao-datacenter}]'

# Passo 5: Habilitar propagação de rotas BGP na Route Table
aws ec2 enable-vgw-route-propagation \
  --route-table-id rtb-privada-az-a \
  --gateway-id vgw-0abc123
# As rotas on-premises anunciadas via BGP aparecem automaticamente na Route Table
```

## Os dois túneis IPsec — redundância por design

Cada conexão VPN tem **dois túneis**, cada um terminando em um endpoint AWS diferente em AZs distintas:

```
Conexão VPN (uma conexão, dois túneis):

Túnel 1:
  AWS endpoint: 52.0.10.1 (us-east-1a)
  On-premises endpoint: 203.0.113.1
  Inside CIDR: 169.254.10.0/30
  Estado: UP ← ativo

Túnel 2:
  AWS endpoint: 52.0.10.2 (us-east-1b)
  On-premises endpoint: 203.0.113.1
  Inside CIDR: 169.254.11.0/30
  Estado: UP ← standby

Comportamento padrão (sem BGP):
  → Um túnel ativo, um em standby
  → Failover automático se o túnel ativo cair (segundos a minutos)

Com BGP (recomendado):
  → Ambos os túneis podem estar ativos simultaneamente
  → Tráfego distribui entre os dois (ECMP)
  → Failover mais rápido (BGP detecta imediatamente)
  → Configurar mesmo peso nas rotas BGP para distribuição igual

Por que dois túneis em AZs diferentes?
  → Se uma AZ AWS tiver problema: o outro túnel continua funcionando
  → A AWS faz manutenção nos túneis periodicamente (necessita ambos ativos)
```

## Roteamento: Estático vs Dinâmico (BGP)

### Roteamento Estático

```
StaticRoutesOnly: true

Você configura manualmente as rotas on-premises que o VGW deve conhecer:
  aws ec2 create-vpn-connection-route \
    --vpn-connection-id vpn-0abc123 \
    --destination-cidr-block 192.168.0.0/16

Na Route Table da VPC: rota manual para 192.168.0.0/16 via VGW
No roteador on-premises: rota manual para o CIDR da VPC

Vantagem: simples, sem necessidade de BGP no roteador
Desvantagem: nenhuma descoberta automática de rotas
             se adicionar nova subnet on-premises: atualizar manualmente
```

### Roteamento Dinâmico (BGP)

```
StaticRoutesOnly: false (padrão com BGP)

BGP (Border Gateway Protocol) troca rotas automaticamente:
  On-premises anuncia: 192.168.0.0/16, 10.100.0.0/8
  AWS anuncia: 10.0.0.0/16 (CIDR da VPC)
  
  Route Table da VPC recebe automaticamente:
    192.168.0.0/16 → vgw (propagada pelo BGP)
    10.100.0.0/8   → vgw (propagada pelo BGP)
  
  Novo escritório em São Paulo com 172.16.50.0/24?
  → Roteador SP anuncia para o BGP
  → Aparece automaticamente na Route Table da VPC
  
Vantagem: roteamento dinâmico, failover mais rápido,
          múltiplos sites conectados (hub-and-spoke)
Requisito: dispositivo on-premises deve suportar BGP (ASN configurado)
```

## Limitações e características de performance

```
Throughput máximo por túnel: 1.25 Gbps
  (cada conexão tem 2 túneis = 2.5 Gbps teórico com ECMP)

Latência adicional: depende da qualidade da internet
  → Rota pela internet pública: latência variável
  → Sem SLA de latência (diferente do Direct Connect)
  → Pode ter jitter em workloads sensíveis a latência

MTU (Maximum Transmission Unit):
  O encapsulamento IPsec reduz o MTU efetivo:
  → IP MTU padrão: 1500 bytes
  → VPN overhead (IPsec headers): ~73 bytes
  → MTU recomendado dentro do túnel: 1427 bytes
  
  Configurar TCP MSS Clamping no roteador on-premises:
    ip tcp adjust-mss 1379  ← Cisco IOS
  Sem isso: pacotes grandes são fragmentados → degradação de performance

PPS (Packets Per Second):
  Sem limite documentado explícito, mas alto volume
  de pacotes pequenos pode saturar antes de saturar o bandwidth

Encryption:
  IPsec com AES-256-GCM + SHA-256 (padrão moderno)
  Perfect Forward Secrecy por padrão
```

## Configuração do lado on-premises

A AWS fornece automaticamente um arquivo de configuração para os principais dispositivos:

```bash
# Baixar configuração para o dispositivo específico
aws ec2 get-vpn-connection-device-sample-configuration \
  --vpn-connection-id vpn-0abc123 \
  --vpn-connection-device-type-id "5fb390ba"  # ex: Cisco ASA 8.4+

# Listar tipos de dispositivos disponíveis
aws ec2 get-vpn-connection-device-types \
  --query 'VpnConnectionDeviceTypes[*].{Platform:Platform,Software:Software,Vendor:Vendor}'
# Cisco, Juniper, Palo Alto, FortiGate, pfSense, VyOS, strongSwan...
```

```bash
# Exemplo de configuração strongSwan (Linux) — Túnel 1
# /etc/ipsec.conf

conn vpn-aws-tunnel1
  authby=secret
  auto=start
  left=%defaultroute       ← IP local (on-premises)
  leftid=203.0.113.1       ← IP público on-premises
  leftsubnet=192.168.0.0/16 ← rede on-premises
  right=52.0.10.1          ← IP do túnel AWS (Tunnel 1)
  rightsubnet=10.0.0.0/16  ← CIDR da VPC (roteamento estático)
  ike=aes256-sha256-modp2048 ← algoritmos Phase 1
  esp=aes256-sha256         ← algoritmos Phase 2
  keyexchange=ikev2
  dpdaction=restart
  dpddelay=10
  dpdtimeout=30

# /etc/ipsec.secrets
203.0.113.1 52.0.10.1 : PSK "chave-pre-compartilhada-1"
```

## Monitorando a VPN

```bash
# Estado dos túneis
aws ec2 describe-vpn-connections \
  --vpn-connection-ids vpn-0abc123 \
  --query 'VpnConnections[0].VgwTelemetry[*].{
    OutsideIP:OutsideIpAddress,
    Status:Status,
    AcceptedRoutes:AcceptedRouteCount,
    LastChange:LastStatusChange
  }'

# CloudWatch métricas para a VPN
aws cloudwatch get-metric-statistics \
  --namespace AWS/VPN \
  --metric-name TunnelState \
  --dimensions Name=VpnId,Value=vpn-0abc123 \
  --statistic Average \
  --period 300 \
  --start-time $(date -d '1 hour ago' -Iseconds) \
  --end-time $(date -Iseconds)
# TunnelState: 1 = UP, 0 = DOWN

# Alarme para túnel DOWN
aws cloudwatch put-metric-alarm \
  --alarm-name "vpn-tunel-down" \
  --namespace AWS/VPN \
  --metric-name TunnelState \
  --dimensions Name=VpnId,Value=vpn-0abc123 \
  --statistic Minimum \
  --period 60 \
  --threshold 1 \
  --comparison-operator LessThanThreshold \
  --evaluation-periods 3 \
  --alarm-actions arn:aws:sns:...:alertas-rede
```

## VPN Accelerated — AWS Global Accelerator integrado

```
VPN acelerada (Accelerated Site-to-Site VPN):
  → Usa AWS Global Accelerator para rotear o tráfego VPN
  → Tráfego entra na rede AWS pelo edge location mais próximo
  → Reduz latência e jitter para conexões de longa distância
  
  Sem aceleração: Cliente → Internet → VPN endpoint AWS
  Com aceleração: Cliente → Edge Location → rede AWS backbone → VPN endpoint
  
  Custo adicional: ~$0.01/hora + custo de transferência Global Accelerator
  Quando vale: conexões internacionais onde a internet pública tem alta latência
```

## Erros comuns e armadilhas

**Apenas um túnel ativo sem monitorar o segundo:** a AWS pode colocar o segundo túnel em manutenção. Se o primeiro túnel cair durante a manutenção do segundo: sem conectividade. Monitorar ambos os túneis com alarmes CloudWatch.

**MTU sem MSS clamping:** pacotes grandes são fragmentados, degradando TCP throughput significativamente. Configurar `ip tcp adjust-mss` no roteador on-premises.

**Roteamento estático sem atualização após mudanças on-premises:** nova subnet adicionada on-premises? Sem BGP, você deve criar a rota VPN manualmente. Com BGP, seria anunciado automaticamente.

**Confundir VPN com solução de alta throughput:** VPN é limitada a 1.25 Gbps por túnel. Para cargas que precisam de mais throughput com latência consistente: AWS Direct Connect.

## 🧩 Quiz de Fixação

1. Uma conexão VPN tem dois túneis, ambos UP. Às 2h da manhã, o Túnel 1 cai (manutenção da AWS). O Túnel 2 também está DOWN (problema no roteador on-premises que não foi detectado). O que acontece com a conectividade e como essa situação poderia ter sido evitada?

2. Por que configurar `ip tcp adjust-mss 1379` no roteador on-premises melhora a performance da VPN, e o que acontece sem essa configuração?

3. Uma empresa tem VPN com roteamento estático. A equipe de rede on-premises adicionou uma nova subnet `172.20.50.0/24` que precisa se comunicar com servidores na VPC. O time AWS tentou o acesso mas falhou. Qual é a causa e como corrigir sem migrar para BGP?

**Respostas:**

1) **Conectividade é completamente perdida.** Com ambos os túneis DOWN, nenhum tráfego pode fluir entre on-premises e a VPC — instâncias EC2 ficam inacessíveis, aplicações que dependem de recursos on-premises param. **Como evitar:** (a) monitorar **ambos** os túneis com alarmes CloudWatch (`TunnelState < 1` para cada túnel separadamente); (b) configurar alertas no roteador on-premises também — a AWS monitorou o Túnel 2 como DOWN mas o roteador on-premises pode não ter detectado; (c) para alta disponibilidade real: considerar duas conexões VPN com dois Customer Gateways diferentes (roteadores on-premises diferentes), eliminando o single point of failure no lado on-premises; (d) para SLA mais robusto: Direct Connect como primário + VPN como backup.

2) O encapsulamento IPsec da VPN adiciona ~73 bytes de overhead a cada pacote. Com MTU padrão de 1500 bytes, um pacote de dados de 1427+ bytes + header IPsec excede 1500 bytes e precisa ser **fragmentado**. A fragmentação IP tem múltiplos impactos negativos: overhead de processamento em cada roteador, possibilidade de perda de fragmentos causando retransmissão TCP completa, redução de throughput. Com `ip tcp adjust-mss 1379`, o roteador instrui o TCP a usar segmentos menores (MSS = Maximum Segment Size), de forma que dados (1379) + headers TCP/IP + IPsec caibam em um único pacote de 1500 bytes — sem fragmentação. O resultado é throughput TCP significativamente maior, especialmente em transferências de grandes volumes.

3) **Causa:** com roteamento estático, as rotas on-premises são configuradas manualmente na conexão VPN e propagadas para a Route Table. A nova subnet `172.20.50.0/24` não tem rota criada na AWS — pacotes destinados a ela são descartados na VPC por falta de rota de retorno. **Correção:** adicionar a rota estática na conexão VPN:
```bash
aws ec2 create-vpn-connection-route \
  --vpn-connection-id vpn-0abc123 \
  --destination-cidr-block 172.20.50.0/24
```
Com propagação de rotas habilitada na Route Table (`enable-vgw-route-propagation`), a nova rota aparece automaticamente. Verificar também que o roteador on-premises tem rota para o CIDR da VPC via o túnel VPN — o problema pode estar em ambos os lados.
