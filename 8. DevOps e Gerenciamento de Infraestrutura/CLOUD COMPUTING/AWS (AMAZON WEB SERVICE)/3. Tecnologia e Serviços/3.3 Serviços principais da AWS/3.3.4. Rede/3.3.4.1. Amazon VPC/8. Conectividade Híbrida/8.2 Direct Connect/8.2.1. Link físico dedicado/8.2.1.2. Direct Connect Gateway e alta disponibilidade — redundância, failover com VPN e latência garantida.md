### Direct Connect Gateway e alta disponibilidade — redundância, failover com VPN e latência garantida

Uma única conexão Direct Connect é um ponto único de falha. Fibras são cortadas, equipamentos falham, DX Locations têm manutenção. Em produção, alta disponibilidade com Direct Connect exige múltiplas conexões físicas, estratégia de failover e — para a maioria dos cenários — uma VPN de backup. Este arquivo cobre os padrões de HA desde o mais simples até o mais robusto, e como garantir latência previsível independente das condições da rede.

---

## Modelos de alta disponibilidade — do mais simples ao mais robusto

### Nível 1 — Conexão única + VPN de backup (mínimo aceitável)

```
On-premises                     AWS
  │                              │
  ├── Direct Connect (primário) ─┤ VPC
  │   1 Gbps, latência < 5ms    │
  │                              │
  └── Site-to-Site VPN (backup) ─┤ VPC
      1.25 Gbps max, internet    │

BGP com Local Preference:
  DX:  local-preference = 200 (preferido)
  VPN: local-preference = 100 (backup)

Se DX cair: BGP detecta, tráfego migra para VPN (segundos)
Limitações: VPN suporta apenas 1.25 Gbps (se workload exige mais, VPN não escala)
            Latência aumenta muito no failover para VPN
Custo: baixo (apenas 1 DX + custos de VPN)
```

### Nível 2 — Duas conexões DX no mesmo DX Location

```
On-premises          DX Location A        AWS
  │                     │
  ├─ DX Connection 1 ───┤──────────────── VPC
  │   (ativa)            │
  └─ DX Connection 2 ───┤
      (standby/ECMP)     │

Protege contra:
  ✓ Falha de porta/equipamento no DX Location
  ✓ Falha de cross-connect físico
  
NÃO protege contra:
  ✗ Falha do DX Location inteiro (incêndio, desastre)
  ✗ Falha do cabo de last-mile (se compartilham o mesmo trajeto)
```

### Nível 3 — Conexões em dois DX Locations diferentes (máxima resiliência)

```
On-premises                    AWS
  │                             
  ├── DX Location A (SP) ─────────── VPC
  │   Connection 1 (ativa)
  │
  └── DX Location B (RJ) ─────────── VPC
      Connection 2 (standby/ECMP)

Protege contra:
  ✓ Falha do DX Location inteiro
  ✓ Desastres regionais (cabo oceânico cortado, datacenter inundado)
  ✓ Manutenção planejada de um dos locations
  
Isso é o que a AWS chama de "Maximum Resiliency"
Para high availability: recomendado para workloads críticos
Para development: desnecessário
```

### Nível 4 — Arquitetura "Maximum Resiliency" oficial da AWS

```
                    DX Location A (São Paulo)
On-premises    ────  Connection 1 (Router A)
Datacenter 1   ────  Connection 2 (Router B)
                         │
                    DX Location B (Rio de Janeiro)
On-premises    ────  Connection 3 (Router C)
Datacenter 2   ────  Connection 4 (Router D)
                         │
                      Direct Connect Gateway
                         │
                  Transit Gateway (TGW)
                  /      │      │      \
               VPC-1   VPC-2  VPC-3   VPC-N

Quatro conexões, dois locations, dois datacenters on-premises
→ Qualquer ponto único pode falhar sem impacto
→ Custo: 4x port hours + 4x last-mile connections
→ Justificado apenas para workloads mission-critical
```

## BGP para controle de failover

BGP é o protocolo que decide qual caminho usar quando há múltiplas conexões disponíveis.

### Preferência de rota com Local Preference

```
# Configuração no roteador on-premises (exemplo Cisco IOS)
# DX como primário, VPN como backup

# Aplicar local-preference alto para rotas recebidas via DX
route-map DX-PRIMARY permit 10
  set local-preference 200     ← mais alto = mais preferido

route-map VPN-BACKUP permit 10
  set local-preference 100     ← mais baixo = backup

# Aplicar nas vizinhanças BGP
router bgp 65000
  neighbor 169.254.0.1 remote-as 64512   ← BGP do Direct Connect
  neighbor 169.254.0.1 route-map DX-PRIMARY in
  
  neighbor 169.253.0.1 remote-as 64512   ← BGP da VPN
  neighbor 169.253.0.1 route-map VPN-BACKUP in
```

### AS Path Prepend — influenciar roteamento de entrada (AWS → on-premises)

```
# Para tráfego vindo da AWS para on-premises:
# As rotas on-premises anunciadas pela VPN devem ser menos preferidas

route-map ANNOUNCE-VIA-VPN permit 10
  set as-path prepend 65000 65000 65000
  # Adiciona 3 ASNs extras → caminho mais longo → menos preferido pela AWS

router bgp 65000
  neighbor 169.253.0.1 route-map ANNOUNCE-VIA-VPN out
```

### ECMP — dois túneis DX ativos simultaneamente

```
Com dois Direct Connects para o mesmo destino com mesmo custo BGP:

router bgp 65000
  maximum-paths 2              ← aceitar 2 rotas de igual custo
  
→ Tráfego distribuído entre as duas conexões (load balancing)
→ Throughput efetivo dobra (2 × 10 Gbps = 20 Gbps)
→ Se uma falha: tráfego migra para a outra instantaneamente

ECMP requer:
  BGP cost deve ser IGUAL em ambas as conexões
  Tanto o lado on-premises quanto o AWS devem suportar ECMP
```

## Bid Directional Failover — DX principal com VPN de backup ativo-passivo

```
Estado normal (DX ativo):
  On-premises → Direct Connect → VPC
  VPN: túneis UP mas sem tráfego (standby)

Detecção de falha do DX:
  1. BGP keepalive não recebido por X segundos (hold time: 30-90s padrão)
  2. BGP session torn down
  3. Rotas via DX removidas da tabela BGP
  4. Rotas via VPN assumem (local-preference mais baixa mas única opção)

Tempo de failover:
  BGP hold time: tipicamente 30s
  + BGP convergence: 5-30s
  Total: ~35-60 segundos de downtime durante o failover
  
Para failover mais rápido:
  BGP BFD (Bidirectional Forwarding Detection):
  → Detecta falha em milissegundos (não segundos)
  → aws directconnect update-virtual-interface-attributes \
       --virtual-interface-id dxvif-0abc123 \
       --enable-sfp-tx-discard
  → BFD hello interval: 300ms, multiplier: 3 = falha detectada em 900ms!
```

## Latência garantida e SLA

### Por que Direct Connect tem latência previsível

```
Tráfego via internet:
  On-premises → ISP → Backbone Internet → Múltiplos roteadores → AWS
  
  Cada roteador adiciona latência imprevisível:
  → Congestionamento em horário de pico: +50-500ms
  → Rerouting por falhas: latência aumenta abruptamente
  → BGP hijacking: rota subótima
  → Jitter (variação de latência): alta

Tráfego via Direct Connect:
  On-premises → DX Location → Backbone AWS privado → AWS
  
  Apenas 2-3 saltos fixos e conhecidos:
  → Backbone AWS não tem congestionamento público
  → Latência = distância física / velocidade da luz + processing overhead
  → São Paulo → us-east-1 (Virginia): ~130ms RTT (constante)
  → Jitter: < 1ms
  
  Cálculo de latência esperada:
  Distância SP → Virginia: ~7.800 km
  Velocidade da luz na fibra: ~200.000 km/s
  Propagação só de ida: 7.800/200.000 = ~39ms
  RTT (ida+volta): ~78ms mínimo físico
  Com processing: ~100-130ms RTT real
```

### SLA de disponibilidade

```
Direct Connect SLA (garantia da AWS):
  Dedicated Connection: 99.9% de disponibilidade do port
  
  Para 99.999% end-to-end:
  → Você precisa de múltiplas conexões DX em múltiplos locations
  → O SLA da AWS cobre apenas o port no DX Location
  → Last-mile (operadora) tem seu próprio SLA separado
  → Combinação de DX (99.9%) + VPN (99.95% internet) resulta em alta disponibilidade

Cálculo de disponibilidade combinada:
  Sistema com DX + VPN como backup independente:
  
  P(ambos falham) = P(DX falha) × P(VPN falha)
                  = 0.001 × 0.0005
                  = 0.0000005
  
  Disponibilidade combinada: 1 - 0.0000005 = 99.99995%
  (assumindo falhas independentes)
```

## Monitoramento de performance e alertas

```bash
# CloudWatch métricas do Direct Connect

# Throughput de entrada (on-premises → AWS)
aws cloudwatch get-metric-statistics \
  --namespace AWS/DX \
  --metric-name ConnectionBpsIngress \
  --dimensions Name=ConnectionId,Value=dxcon-0abc123 \
  --start-time $(date -d '1 hour ago' -Iseconds) \
  --end-time $(date -Iseconds) \
  --period 300 \
  --statistics Average

# Throughput de saída (AWS → on-premises)
# ConnectionBpsEgress

# Utilização da porta (%)
# ConnectionLightLevelTx / ConnectionLightLevelRx (nível óptico)

# Alarme: conexão DOWN (ConnectionState = 0)
aws cloudwatch put-metric-alarm \
  --alarm-name "dx-connection-down" \
  --namespace AWS/DX \
  --metric-name ConnectionState \
  --dimensions Name=ConnectionId,Value=dxcon-0abc123 \
  --statistic Minimum \
  --period 60 \
  --threshold 1 \
  --comparison-operator LessThanThreshold \
  --evaluation-periods 2 \
  --alarm-actions arn:aws:sns:...:alertas-rede \
  --treat-missing-data notBreaching

# Alarme: VIF BGP DOWN
aws cloudwatch put-metric-alarm \
  --alarm-name "dx-bgp-down" \
  --namespace AWS/DX \
  --metric-name VirtualInterfaceBpsIngress \
  --dimensions Name=VirtualInterfaceId,Value=dxvif-0abc123 \
  --statistic Sum \
  --period 60 \
  --threshold 0 \
  --comparison-operator LessThanOrEqualToThreshold \
  --evaluation-periods 3 \
  --alarm-actions arn:aws:sns:...:alertas-rede
```

  Uma VPN Site-to-Site

  Disponibilidade: 99.9%
  Latência: variável

  1 × Direct Connect 1 Gbps + VPN de backup

  Disponibilidade: 99.9% DX + VPN fallback

  2 × Direct Connect em DX Locations diferentes + VPN de backup

  Disponibilidade: 99.99%+
  Latência: sempre consistente (ambas DX)

Mission-critical (banco, saúde, governo):
  4 × Direct Connect (Maximum Resiliency: 2 locations × 2 connections)
  Custo: $2.000-8.000/mês (4 DX) + operadoras
  Disponibilidade: 99.999%+
  Latência: garantida sempre

## Erros comuns e armadilhas

**DX como única conexão sem VPN de backup:** uma fibra cortada, um equipamento com defeito ou manutenção da AWS pode deixar o ambiente sem conectividade por horas. Sempre manter VPN de backup ativa.

**BGP hold time alto (90s) sem BFD:** 90 segundos de downtime durante failover é inaceitável para muitas aplicações. Habilitar BFD para detecção em sub-segundo.

**Não testar o failover regularmente:** como o Direct Connect raramente falha, o failover para VPN não é testado. A VPN pode estar mal configurada, expirada ou com throughput insuficiente para o workload — só descoberto na hora da crise. Testar failover mensalmente em janela de manutenção.

**Subestimar o last-mile como ponto de falha:** o SLA da AWS cobre o port no DX Location. Se a operadora que fornece o last-mile tiver problema, a AWS não é responsável. Duas conexões DX na mesma operadora pelo mesmo caminho físico não são realmente redundantes.

## 🧩 Quiz de Fixação

1. Uma empresa tem DX (10 Gbps) + VPN (backup). Às 3h, o DX falha. O BGP hold time é de 90 segundos. O time de desenvolvimento relata que a aplicação ficou sem resposta por 2 minutos e depois voltou com latência 10x maior. Quais foram as duas fases desse evento e como reduzir o downtime de 2 minutos?

2. Uma empresa tem dois Direct Connects em dois DX Locations diferentes (SP e RJ), ambos para a mesma VPC com as mesmas rotas BGP. Por que o tráfego pode não ser distribuído igualmente entre os dois links, e como forçar distribuição balanceada?

3. O SLA da AWS para Dedicated Connection é 99.9%. A operadora de last-mile tem SLA de 99.95%. Qual é a disponibilidade combinada real do Direct Connect end-to-end, e qual arquitetura garantiria disponibilidade > 99.99%?

**Respostas:**

1) **Fase 1 — BGP convergence (0 a 90 segundos):** o DX falhou fisicamente mas o BGP ainda não sabe disso — os keepalives BGP têm hold time de 90 segundos. Durante esse período, as rotas ainda apontam para o DX (que não está mais disponível). Pacotes são enviados para o DX e descartados (black hole). A aplicação fica sem resposta. **Fase 2 — VPN ativa com maior latência (~90s em diante):** após 90s sem keepalives, o BGP detecta que a sessão DX caiu, remove as rotas DX, e as rotas de backup (VPN) entram em vigor. A conectividade é restaurada mas com latência da internet (~100-200ms RTT) vs latência do DX (~5-30ms RTT) — daí a latência 10x maior. **Como reduzir o downtime:** habilitar **BFD (Bidirectional Forwarding Detection)** com hello interval de 300ms e multiplier 3 = detecção em 900ms em vez de 90 segundos. O downtime cai de ~2 minutos para ~1-2 segundos (detecção 900ms + BGP convergence ~1s).

2) O tráfego pode não se distribuir igualmente por dois motivos: (a) **BGP prefere um caminho por tiebreaker:** quando as métricas BGP são idênticas (local-preference, AS-path length, MED), o BGP pode usar tiebreakers como router-ID ou origin do vizinho para preferir um caminho. O resultado é que todo o tráfego vai por um link; (b) **ECMP não configurado:** sem `maximum-paths 2` (ou equivalente) no roteador on-premises e no VGW/TGW AWS, o BGP seleciona apenas um caminho mesmo que dois sejam iguais. **Como forçar distribuição balanceada:** (a) configurar `maximum-paths 2` no roteador on-premises; (b) garantir que as métricas BGP sejam idênticas para ambos os caminhos (mesma local-preference, mesmo MED); (c) no TGW da AWS, verificar que ECMP está habilitado para o attachment do DXGW; (d) para distribuição ainda mais granular: usar ECMP por fluxo (5-tuple hashing) para distribuir diferentes conexões TCP entre os links.

3) **Disponibilidade combinada (sem redundância):** disponibilidade = SLA_AWS × SLA_operadora = 0.999 × 0.9995 = **0.9985 (99.85%)**. Isso é pior que qualquer componente isolado! Os dois SLAs se multiplicam porque ambos precisam estar disponíveis simultaneamente. **Arquitetura para > 99.99%:** duas conexões DX independentes (diferentes DX Locations) com duas operadoras de last-mile diferentes. Com redundância paralela: P(ambas indisponíveis) = P(falha DX 1 end-to-end) × P(falha DX 2 end-to-end) = (1 - 0.9985) × (1 - 0.9985) = 0.0015 × 0.0015 = 0.00000225. Disponibilidade = 1 - 0.00000225 = **99.9998%** — muito além dos 99.99% desejados. A chave é que as duas conexões precisam ser genuinamente independentes: diferentes DX Locations, diferentes operadoras de last-mile, diferentes trajetos físicos (não o mesmo duto subterrâneo).
