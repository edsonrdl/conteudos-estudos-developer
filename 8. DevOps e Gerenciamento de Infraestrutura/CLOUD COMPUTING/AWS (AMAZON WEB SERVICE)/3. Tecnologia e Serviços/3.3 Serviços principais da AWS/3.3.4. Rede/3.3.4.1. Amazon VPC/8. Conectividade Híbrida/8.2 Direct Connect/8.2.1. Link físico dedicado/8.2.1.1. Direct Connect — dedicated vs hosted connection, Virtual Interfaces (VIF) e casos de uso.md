### AWS Direct Connect — dedicated vs hosted connection, Virtual Interfaces e casos de uso

O AWS Direct Connect é uma conexão de rede física privada e dedicada entre a rede on-premises e a AWS — sem passar pela internet pública. Onde a VPN oferece conectividade rápida de configurar mas com latência variável e throughput limitado, o Direct Connect oferece largura de banda de 1 Gbps a 100 Gbps com latência consistente e previsível. É o padrão para workloads que exigem alta performance, compliance com requisitos de privacidade de dados ou migração de grandes volumes de dados.

---

## Por que Direct Connect em vez de VPN

```
VPN Site-to-Site:
  → Tráfego: internet pública (criptografado)
  → Throughput: até 1.25 Gbps por túnel
  → Latência: variável (depende da rota na internet)
  → Jitter: alto em horários de pico
  → SLA: nenhum de latência
  → Custo: baixo (sem hardware físico)
  → Setup: minutos

Direct Connect:
  → Tráfego: link físico dedicado (sem internet pública)
  → Throughput: 1 Gbps a 100 Gbps
  → Latência: consistente e previsível (sub-milissegundo a datacenter AWS)
  → Jitter: mínimo
  → SLA: SLA de disponibilidade da operadora
  → Custo: alto (port charges + operadora)
  → Setup: semanas a meses (instalação física)

Quando Direct Connect é obrigatório:
  → Migração de petabytes de dados (custo de transferência via internet proibitivo)
  → Workloads sensíveis a latência (trading, VDI, aplicações real-time)
  → Compliance que proíbe dados em internet pública
  → Throughput consistente > 1.25 Gbps
  → Custo de transferência de dados (Direct Connect tem preço menor que internet)
```

## Arquitetura do Direct Connect

```
On-premises (Datacenter/Escritório)
  │
  │ (cabo físico — fibra óptica)
  │
AWS Direct Connect Location (ponto de presença)
  → Locais físicos onde a AWS tem equipamentos (co-locations)
  → Ex: Equinix SP2 (São Paulo), Tivit (São Paulo), Ascenty
  │
  │ (cross-connect dentro do DX Location)
  │
AWS Direct Connect Router
  │
  │ (backbone AWS privado)
  │
AWS Region → VPC, S3, outros serviços AWS
```

### Como o cabo chega até o DX Location

```
Opção 1 — Você está no mesmo DX Location:
  Seu datacenter está fisicamente no Equinix SP2
  → Cross-connect direta: um cabo da sua gaiola para a gaiola AWS
  → Mais simples e barato

Opção 2 — Seu datacenter está em outra localização:
  Seu datacenter → (sua operadora de telecom) → DX Location → AWS
  → Last-mile connection: você contrata uma operadora para levar o cabo
  → Mais setup, envolve terceiros

Opção 3 — AWS Direct Connect Delivery Partners:
  Operadoras/parceiros que têm conexão no DX Location
  → Você contrata o parceiro (AT&T, Verizon, Cogent, Claro, Vivo...)
  → O parceiro provisiona a conectividade para você
  → Sem precisar estar físicamente no DX Location
```

## Dedicated Connection vs Hosted Connection

### Dedicated Connection

```
Capacidades:
  1 Gbps, 10 Gbps, 100 Gbps

Características:
  → Porta física dedicada para você no DX Location
  → Você tem o link exclusivo — sem compartilhamento
  → Você mesmo gerencia as VLANs (Virtual Interfaces)
  → Pode criar múltiplas VIFs (Private, Public, Transit) na mesma porta
  
Criação:
  1. Você solicita através do console AWS
  2. AWS provisiona a porta física no DX Location
  3. AWS fornece a Letter of Authorization (LOA/CFA) — documento com detalhes
     técnicos para o operador do DX Location conectar seu equipamento
  4. Operador do DX Location instala o cross-connect físico
  5. Semanas depois: porta disponível
  
Custo:
  Port hours: $0.30-$2.25/hora dependendo da velocidade
  Data transfer: menor que internet (~$0.02/GB vs $0.09/GB)
```

### Hosted Connection

```
Capacidades:
  50 Mbps, 100 Mbps, 200 Mbps, 300 Mbps, 400 Mbps, 500 Mbps,
  1 Gbps, 2 Gbps, 5 Gbps, 10 Gbps

Características:
  → Um AWS Direct Connect Partner já tem uma Dedicated Connection na AWS
  → Eles "fatiam" sua porta e vendem frações para múltiplos clientes
  → Você compartilha a infraestrutura física com outros clientes do parceiro
  → Mais rápido de provisionar (o parceiro já tem o link com a AWS)
  → Apenas 1 Virtual Interface por hosted connection
  
Quando usar Hosted:
  → Capacidade menor (50 Mbps - 500 Mbps — abaixo do mínimo Dedicated de 1 Gbps)
  → Provisioning mais rápido (parceiro já tem o link)
  → Menor comprometimento inicial
  → Não quer gerenciar a relação com o DX Location diretamente

Comparativo:
  Dedicated: você faz tudo, mais controle, mais complexo
  Hosted:    parceiro faz, menos controle, mais simples, mais rápido
```

## Virtual Interfaces (VIF) — tipos e uso

Uma **Virtual Interface** é uma interface lógica (VLAN + BGP session) sobre o link físico. A porta física pode ter múltiplas VIFs de diferentes tipos:

### Private VIF — acesso a VPC

```
Private VIF:
  → Conecta diretamente a uma VPC (via Virtual Private Gateway)
  → Acesso a recursos privados da VPC: EC2, RDS, ECS, etc.
  → IP privado no tunnel (RFC 1918)
  
Configuração:
  aws directconnect create-private-virtual-interface \
    --connection-id dxcon-0abc123 \
    --new-private-virtual-interface '{
      "virtualInterfaceName": "vif-vpc-producao",
      "vlan": 100,
      "asn": 65000,
      "authKey": "senha-bgp",
      "amazonAddress": "169.254.0.1/30",
      "customerAddress": "169.254.0.2/30",
      "virtualGatewayId": "vgw-0abc123"
    }'

VLAN: identifica qual tráfego pertence a essa VIF
BGP session: troca rotas entre on-premises e AWS
169.254.x.x: IPs de link-local para a sessão BGP

Limitação: uma Private VIF → uma VPC (via VGW)
Para múltiplas VPCs com uma Private VIF: usar Transit VIF + TGW
```

### Public VIF — acesso a serviços AWS públicos

```
Public VIF:
  → Acesso a endpoints públicos da AWS (S3, DynamoDB, SQS, etc.)
  → Sem passar pela internet pública
  → Recebe anúncio de todos os prefixos públicos da AWS na região
  
Uso típico:
  → Transferência de dados para S3 sem custo de internet
  → Acesso a serviços gerenciados AWS sem internet
  → Workloads que precisam de alta throughput para S3/DynamoDB

Observação:
  Public VIF não acessa recursos privados da VPC (IPs RFC 1918)
  Para isso: Private VIF
```

### Transit VIF — acesso a múltiplas VPCs via Transit Gateway

```
Transit VIF:
  → Conecta ao AWS Transit Gateway (TGW)
  → Uma única VIF pode acessar múltiplas VPCs via TGW
  → Solução para ambientes multi-VPC e multi-conta
  
Arquitetura:
  On-premises → Direct Connect → Transit VIF → TGW → VPC-1, VPC-2, VPC-3...
  
  Vs múltiplas Private VIFs:
    Antes: 1 Private VIF por VPC (complexo, muitas BGP sessions)
    Agora: 1 Transit VIF → TGW → N VPCs (muito mais escalável)
  
Requisito:
  AWS Direct Connect Gateway (DXGW) — conecta o DX ao TGW
  Necessário para cross-region também (uma DXGW pode ser global)
```

## Direct Connect Gateway — conexão cross-region

```
Problema sem Direct Connect Gateway:
  Uma Private VIF conecta a um VGW em uma região específica
  → On-premises → DX → Private VIF → VGW (us-east-1) → VPC (us-east-1)
  → Não pode acessar VPCs em eu-west-1 com o mesmo link

Com Direct Connect Gateway:
  → Um DXGW pode ser associado a VGWs em múltiplas regiões
  → Uma única conexão DX acessa VPCs globalmente
  
  aws directconnect create-direct-connect-gateway \
    --direct-connect-gateway-name "dxgw-global" \
    --amazon-side-asn 64512

  # Associar VGW de us-east-1
  aws directconnect create-direct-connect-gateway-association \
    --direct-connect-gateway-id dxgw-0abc123 \
    --gateway-id vgw-us-east-1

  # Associar VGW de eu-west-1
  aws directconnect create-direct-connect-gateway-association \
    --direct-connect-gateway-id dxgw-0abc123 \
    --gateway-id vgw-eu-west-1
  
  → On-premises pode alcançar VPCs em ambas as regiões pelo mesmo link DX
```

## Modelo de custo do Direct Connect

```
Componentes de custo:

1. Port Hours (AWS cobra):
   1 Gbps Dedicated:   $0.30/hora = $216/mês
   10 Gbps Dedicated:  $1.50/hora = $1.080/mês
   100 Gbps Dedicated: $2.25/hora = $1.620/mês
   Hosted (1 Gbps):    varia por parceiro (~$0.20-0.30/hora)

2. Data Transfer OUT (AWS cobra):
   us-east-1 → on-premises via DX: $0.02/GB (vs $0.09/GB pela internet)
   Economia em transferência:  78% menos que internet
   
   Para 100 TB/mês:
   Internet:      100.000 GB × $0.09 = $9.000/mês
   Direct Connect: 100.000 GB × $0.02 = $2.000/mês
   Economia:       $7.000/mês

3. Last-mile (operadora cobra separadamente):
   Custo do cabo entre seu DC e o DX Location
   Varia muito por localização e distância
   Tipicamente: $500-$5.000/mês adicionais

Análise de ROI:
  Para decidir entre VPN e Direct Connect, comparar:
  - Custo de port hours do DX
  - Custo de last-mile
  - Custo de transferência de dados (DX vs internet)
  - Valor da latência consistente (difícil de quantificar)
  - Requisitos de compliance (sem internet = valor intangível)
  
  Se o volume de dados for alto: DX frequentemente se paga em transferência
```

## Verificando o Direct Connect

```bash
# Listar conexões Direct Connect
aws directconnect describe-connections

# Verificar estado de uma conexão
aws directconnect describe-connections \
  --connection-id dxcon-0abc123 \
  --query 'connections[0].{State:connectionState,Bandwidth:bandwidth,Location:location}'

# Estados possíveis:
# ordering: pedido feito, aguardando aprovação AWS
# requested: aprovado, aguardando cross-connect físico
# pending: cross-connect instalado, aguardando LOA
# available: pronto para criar VIFs
# deleting/deleted: sendo removido

# Listar Virtual Interfaces
aws directconnect describe-virtual-interfaces \
  --connection-id dxcon-0abc123

# Verificar estado das BGP sessions
aws directconnect describe-virtual-interfaces \
  --query 'virtualInterfaces[*].{
    Name:virtualInterfaceName,
    State:virtualInterfaceState,
    BGPState:bgpPeers[0].bgpStatus,
    VLAN:vlan
  }'

# Estado UP = BGP estabelecido, rotas sendo trocadas
# Estado DOWN = BGP não estabelecido (verificar configuração BGP)
```

## Erros comuns e armadilhas

**Usar Direct Connect como única conexão sem backup:** Direct Connect pode ter falhas (manutenção, problemas físicos). Sempre manter uma VPN como backup. Configurar rotas com preferências: DX como primário, VPN como failover via BGP local-preference.

**VLAN mal configurada no switch on-premises:** o VLAN ID deve ser o mesmo configurado na VIF da AWS. Um mismatch silenciosamente impede o estabelecimento da sessão BGP.

**BGP session DOWN por MTU ou autenticação:** verificar que o MD5 auth key do BGP bate exatamente entre os dois lados, e que o MTU da interface on-premises permite os keepalives BGP.

**Tentar acessar recursos privados da VPC via Public VIF:** Public VIF só acessa endpoints públicos da AWS. Para EC2, RDS e outros recursos privados: Private VIF ou Transit VIF.

## 🧩 Quiz de Fixação

1. Uma empresa tem uma Dedicated Connection de 10 Gbps e precisa acessar 5 VPCs em us-east-1 e 3 VPCs em eu-west-1. Qual é a arquitetura mais escalável usando Direct Connect Gateway e Transit Gateway, e quantas VIFs são necessárias?

2. Uma empresa transfere 500 TB/mês de on-premises para S3 via internet (custo: $0.09/GB saída, mas os dados vão de on-premises para S3, portanto é transferência de entrada — custo $0). A empresa está considerando Direct Connect para reduzir custo. Qual é o erro de análise nesse raciocínio e qual é o custo real que o DX pode reduzir?

3. Uma Private VIF está com `bgpStatus: down`. A conexão física (layer 1) está OK e a VLAN está correta. Quais são as três causas mais prováveis de uma BGP session não estabelecer?

**Respostas:**

1) **Arquitetura recomendada:** uma única **Transit VIF** no Direct Connect → **Direct Connect Gateway (DXGW)** → **Transit Gateway (TGW)** em cada região (us-east-1 e eu-west-1). O TGW de cada região tem todos as VPCs como attachments. **VIFs necessárias: apenas 1 Transit VIF** na conexão DX. O DXGW atua como hub global, podendo associar TGWs de múltiplas regiões. Antes do DXGW + TGW, seriam necessárias 8 Private VIFs (1 por VPC) — inescalável. Com a arquitetura atual: 1 VIF → DXGW → TGW us-east-1 (5 VPCs) + TGW eu-west-1 (3 VPCs). A sessão BGP é estabelecida apenas uma vez com o DXGW.

2) O erro é que a transferência de **on-premises para S3** (upload/ingress) é **gratuita** na AWS — a AWS não cobra por dados entrando. O Direct Connect não reduz o custo de upload. O que o Direct Connect poderia reduzir é: (a) custo de **download** (S3 para on-premises), que custa $0.09/GB via internet vs $0.02/GB via DX; (b) custo de transferência entre regiões; (c) custo de **port hours** seria um custo adicional, não uma redução. Se a empresa só faz upload para S3, o Direct Connect não economiza em transferência de dados — o custo real seria apenas o de port hours (adicional), tornando a análise negativa financeiramente para esse caso específico. O DX ainda pode valer pelo throughput consistente (500 TB via internet seria lento) e pela latência.

3) **Três causas mais prováveis de BGP DOWN com layer 1 e VLAN corretos:** (a) **MD5 authentication key incorreta:** se a auth key configurada no roteador on-premises não bate exatamente (case-sensitive) com a configurada na VIF AWS, o BGP rejeita os pacotes. Verificar caracteres especiais, espaços em branco acidentais; (b) **ASN configurado incorretamente:** o BGP session usa o ASN como identificador. Se o ASN do lado on-premises não bate com o `asn` configurado na VIF AWS (campo `customerGatewayAsn`), a sessão não estabelece; (c) **MTU muito pequeno impedindo o BGP OPEN:** o BGP OPEN message pode ser grande o suficiente para ser fragmentado se o MTU da interface for menor que o necessário. Verificar que o MTU da interface on-premises é pelo menos 1500 bytes. Também verificar: firewall bloqueando TCP 179 (porta BGP), roteamento incorreto para o `amazonAddress` do link-local, ou interface on-premises com estado DOWN apesar do cabo físico OK.
