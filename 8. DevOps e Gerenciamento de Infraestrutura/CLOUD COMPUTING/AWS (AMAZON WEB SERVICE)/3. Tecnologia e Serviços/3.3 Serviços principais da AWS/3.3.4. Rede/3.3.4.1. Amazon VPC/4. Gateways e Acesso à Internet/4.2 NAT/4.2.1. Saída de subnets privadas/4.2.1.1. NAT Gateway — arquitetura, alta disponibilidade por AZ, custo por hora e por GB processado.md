### NAT Gateway — arquitetura, alta disponibilidade por AZ e modelo de custo

O NAT Gateway resolve um problema fundamental de arquitetura: instâncias em subnets privadas (sem IP público) precisam fazer chamadas de saída para a internet — baixar atualizações, chamar APIs externas, acessar serviços AWS — mas sem nunca expor um IP público que permita conexões de entrada. O NAT Gateway realiza a tradução de endereços de saída (SNAT — Source NAT) de forma gerenciada, com alta disponibilidade e escalabilidade automática.

---

## O que o NAT Gateway faz — SNAT

O NAT Gateway implementa **SNAT (Source Network Address Translation)**: quando uma instância privada envia um pacote para a internet, o NAT Gateway substitui o IP privado de origem pelo seu próprio IP público (Elastic IP), envia o pacote à internet, recebe a resposta e encaminha de volta à instância original.

```
Fluxo de um pacote via NAT Gateway:

Instância privada: 10.0.10.50 (sem IP público)
NAT Gateway:       Elastic IP 54.200.10.30, fica em subnet pública
Internet Gateway:  igw-0abc123

1. Instância envia:
   src=10.0.10.50 → dst=93.184.216.34 (servidor externo)

2. Route Table da subnet privada:
   0.0.0.0/0 → nat-gateway → pacote vai para o NAT GW

3. NAT Gateway realiza SNAT:
   src=54.200.10.30 → dst=93.184.216.34
   (IP privado substituído pelo Elastic IP do NAT)

4. NAT Gateway envia via IGW para a internet

5. Servidor externo responde:
   src=93.184.216.34 → dst=54.200.10.30

6. NAT Gateway recebe a resposta, consulta sua tabela de conexões:
   "54.200.10.30:porta X foi para 10.0.10.50:porta Y"

7. NAT Gateway realiza DNAT (Destination NAT) e entrega:
   src=93.184.216.34 → dst=10.0.10.50

8. Instância recebe a resposta como se tivesse chegado de 93.184.216.34
```

**Diferença fundamental do IGW:** o IGW faz NAT 1:1 (um IP privado ↔ um IP público fixo). O NAT Gateway faz NAT N:1 — muitas instâncias privadas compartilham um único IP público, diferenciadas pelo número de porta de origem (PAT — Port Address Translation).

---

## Onde o NAT Gateway deve ficar

O NAT Gateway deve estar em uma **subnet pública** — precisa de um IP público (Elastic IP) e de uma rota para o Internet Gateway para encaminhar os pacotes para a internet:

```
Arquitetura correta:

VPC: 10.0.0.0/16

Subnet Pública (10.0.1.0/24) — us-east-1a:
  ┌──────────────┐
  │ NAT Gateway  │ ← Elastic IP: 54.200.10.30
  │ nat-0abc123  │
  └──────────────┘
  Route Table:
    10.0.0.0/16 → local
    0.0.0.0/0   → igw-xxx

Subnet Privada (10.0.10.0/24) — us-east-1a:
  ┌──────────────┐
  │   EC2 App    │ ← IP: 10.0.10.50 (sem IP público)
  └──────────────┘
  Route Table:
    10.0.0.0/16 → local
    0.0.0.0/0   → nat-0abc123  ← tráfego de saída vai para o NAT

Fluxo: EC2 → NAT (subnet pública) → IGW → Internet
```

## Alta disponibilidade — 1 NAT Gateway por AZ

O NAT Gateway é um serviço **regional altamente disponível dentro de uma AZ**, mas **não é automaticamente multi-AZ**. Se você criar apenas um NAT Gateway em us-east-1a e direcionar instâncias de us-east-1b e us-east-1c para ele, uma falha na AZ-a derruba o acesso à internet de todas as instâncias privadas:

```
Configuração ERRADA (ponto único de falha):

us-east-1a: NAT Gateway (único)
us-east-1b: sem NAT Gateway
us-east-1c: sem NAT Gateway

Route Tables:
  rtb-privada-az-a: 0.0.0.0/0 → nat-az-a  (mesmo NAT)
  rtb-privada-az-b: 0.0.0.0/0 → nat-az-a  ← cross-AZ!
  rtb-privada-az-c: 0.0.0.0/0 → nat-az-a  ← cross-AZ!

Falha de us-east-1a:
  → NAT Gateway cai
  → Instâncias de us-east-1b e us-east-1c perdem acesso à internet
  → Tráfego cross-AZ (us-east-1b → nat-az-a) também gera custo extra

Configuração CORRETA (HA real):

us-east-1a: NAT Gateway A (nat-aaa)
us-east-1b: NAT Gateway B (nat-bbb)
us-east-1c: NAT Gateway C (nat-ccc)

Route Tables separadas por AZ:
  rtb-privada-az-a: 0.0.0.0/0 → nat-aaa  ← cada AZ usa seu próprio NAT
  rtb-privada-az-b: 0.0.0.0/0 → nat-bbb
  rtb-privada-az-c: 0.0.0.0/0 → nat-ccc

Falha de us-east-1a:
  → NAT Gateway A cai
  → Apenas instâncias de us-east-1a perdem acesso (aceitável com multi-AZ)
  → us-east-1b e us-east-1c continuam funcionando normalmente
```

```bash
# Criar NAT Gateway em cada AZ (3 AZs = 3 NAT Gateways)

# AZ-a: alocar EIP e criar NAT Gateway
EIP_A=$(aws ec2 allocate-address --domain vpc \
  --query 'AllocationId' --output text)
NAT_A=$(aws ec2 create-nat-gateway \
  --subnet-id subnet-publica-az-a \
  --allocation-id $EIP_A \
  --tag-specifications 'ResourceType=natgateway,Tags=[{Key=Name,Value=nat-producao-az-a}]' \
  --query 'NatGateway.NatGatewayId' --output text)

# AZ-b
EIP_B=$(aws ec2 allocate-address --domain vpc --query 'AllocationId' --output text)
NAT_B=$(aws ec2 create-nat-gateway \
  --subnet-id subnet-publica-az-b \
  --allocation-id $EIP_B \
  --tag-specifications 'ResourceType=natgateway,Tags=[{Key=Name,Value=nat-producao-az-b}]' \
  --query 'NatGateway.NatGatewayId' --output text)

# AZ-c
EIP_C=$(aws ec2 allocate-address --domain vpc --query 'AllocationId' --output text)
NAT_C=$(aws ec2 create-nat-gateway \
  --subnet-id subnet-publica-az-c \
  --allocation-id $EIP_C \
  --tag-specifications 'ResourceType=natgateway,Tags=[{Key=Name,Value=nat-producao-az-c}]' \
  --query 'NatGateway.NatGatewayId' --output text)

# Aguardar os NAT Gateways ficarem disponíveis
aws ec2 wait nat-gateway-available --nat-gateway-ids $NAT_A $NAT_B $NAT_C

# Adicionar rotas nas Route Tables de cada AZ
aws ec2 create-route --route-table-id rtb-privada-az-a \
  --destination-cidr-block 0.0.0.0/0 --nat-gateway-id $NAT_A
aws ec2 create-route --route-table-id rtb-privada-az-b \
  --destination-cidr-block 0.0.0.0/0 --nat-gateway-id $NAT_B
aws ec2 create-route --route-table-id rtb-privada-az-c \
  --destination-cidr-block 0.0.0.0/0 --nat-gateway-id $NAT_C
```

## Modelo de custo do NAT Gateway

O NAT Gateway tem **dois componentes de custo**:

```
Custo por hora de existência:
  $0.045/hora por NAT Gateway (us-east-1)
  
  3 NAT Gateways (1 por AZ) × $0.045 × 720h = $97.20/mês
  apenas pelo fato de existirem, sem processar nenhum byte

Custo por GB processado:
  $0.045/GB de dados processados pelo NAT Gateway
  
  Se suas instâncias baixam 1 TB/mês via NAT:
  1.024 GB × $0.045 = $46.08/mês em dados
  
  Total exemplo (3 NAT + 1 TB dados):
  $97.20 (existência) + $46.08 (dados) = $143.28/mês
```

### O custo de tráfego cross-AZ soma-se ao custo do NAT

Se você usa um único NAT Gateway e instâncias de outras AZs trafegam por ele, há custo adicional de transferência inter-AZ:

```
Instância em us-east-1b → NAT Gateway em us-east-1a:
  Custo NAT:         $0.045/GB (processado pelo NAT)
  Custo inter-AZ:    $0.01/GB  (tráfego entre AZs)
  Total efetivo:     $0.055/GB

Instância em us-east-1a → NAT Gateway em us-east-1a (mesma AZ):
  Custo NAT:         $0.045/GB (processado pelo NAT)
  Custo inter-AZ:    $0.00     (mesma AZ)
  Total efetivo:     $0.045/GB

→ Usar 1 NAT por AZ economiza em dados mas custa mais em existência
→ Para volumes altos de tráfego: 1 NAT por AZ é melhor
→ Para volumes baixos: considerar 1 NAT para economizar em existência
```

## Estratégias de otimização de custo

### Estratégia 1 — VPC Endpoints (eliminar tráfego ao S3/DynamoDB)

O custo mais evitável: tráfego de instâncias privadas para S3 e DynamoDB passa pelo NAT Gateway por padrão, gerando custo de processamento. Usando **VPC Gateway Endpoints**, esse tráfego vai pela rede privada da AWS — sem custo de NAT:

```
Sem VPC Endpoint (caro):
  EC2 privada → NAT Gateway ($0.045/GB) → IGW → S3

Com VPC Gateway Endpoint (gratuito):
  EC2 privada → VPC Endpoint → S3 (rede privada AWS)

Economia: todo acesso a S3 e DynamoDB via NAT é eliminado
Para clusters EKS com muitas imagens no ECR (que usa S3):
  Centenas de GB/mês podem ser eliminados do custo do NAT
```

```bash
# Criar VPC Gateway Endpoint para S3
aws ec2 create-vpc-endpoint \
  --vpc-id vpc-0abc123 \
  --service-name com.amazonaws.us-east-1.s3 \
  --route-table-ids rtb-privada-az-a rtb-privada-az-b rtb-privada-az-c
# Adiciona rota automaticamente nas Route Tables especificadas
```

### Estratégia 2 — NAT Gateway por schedule (dev/staging)

Para ambientes de desenvolvimento que funcionam apenas em horário comercial:

```bash
# Lambda para deletar NAT Gateways à noite e recriar de manhã
# (salva ~$97/mês por ambiente de dev com 3 AZs)

# Alternativa menos disruptiva: usar NAT Instance em dev
# (mais barata, mas requer gerenciamento manual)
```

### Estratégia 3 — Analisar destino do tráfego

```bash

# Verificar quais IPs de destino geram mais tráfego
# Se forem serviços AWS: criar Interface Endpoints para eliminá-los do NAT
```

## Limites do NAT Gateway

| Parâmetro | Limite |
|---|---|
| Largura de banda máxima | 100 Gbps por NAT Gateway |
| Conexões simultâneas TCP | 55.000 por destino único (IP+porta) |
| Conexões simultâneas totais | Sem limite documentado |
| Pacotes por segundo | 10 milhões |
| NAT Gateways por AZ por VPC | 5 (aumentável via suporte) |

**Limite de 55.000 conexões para o mesmo destino:** se muitas instâncias fazem muitas conexões para o mesmo endpoint externo (ex: uma API específica), o NAT Gateway pode esgotar as portas disponíveis. Sintoma: `ConnectionTimedOut` ou `ErrorPortAllocation`. Mitigação: diversificar IPs de destino ou usar múltiplos NAT Gateways com IPs diferentes.

## Monitorando o NAT Gateway

```bash
# Verificar métricas do NAT Gateway no CloudWatch
aws cloudwatch get-metric-statistics \
  --namespace AWS/NATGateway \
  --metric-name BytesOutToDestination \
  --dimensions Name=NatGatewayId,Value=nat-0abc123 \
  --start-time $(date -d '1 hour ago' -Iseconds) \
  --end-time $(date -Iseconds) \
  --period 300 \
  --statistics Sum

# Métricas disponíveis:
# BytesInFromDestination  → dados recebidos da internet
# BytesInFromSource       → dados de instâncias privadas
# BytesOutToDestination   → dados enviados para a internet
# BytesOutToSource        → dados devolvidos às instâncias
# ConnectionAttemptCount  → tentativas de conexão
# ConnectionEstablishedCount → conexões estabelecidas
# ErrorPortAllocation     → erros de esgotamento de porta (crítico)
# IdleTimeoutCount        → conexões encerradas por timeout

# Alarme para erros de porta
aws cloudwatch put-metric-alarm \
  --alarm-name "nat-gateway-erro-porta" \
  --namespace AWS/NATGateway \
  --metric-name ErrorPortAllocation \
  --dimensions Name=NatGatewayId,Value=nat-0abc123 \
  --statistic Sum \
  --period 60 \
  --threshold 0 \
  --comparison-operator GreaterThanThreshold \
  --evaluation-periods 1 \
  --alarm-actions arn:aws:sns:...:alertas-rede
```

## Erros comuns e armadilhas

**Esquecer de criar NAT Gateway por AZ:** o erro de infraestrutura mais comum em VPCs AWS. Uma falha de AZ derruba toda a conectividade de saída de instâncias privadas em outras AZs se há apenas um NAT centralizado.

**Não criar VPC Endpoints para S3/DynamoDB:** em arquiteturas com ECS/EKS, o tráfego para ECR (armazenado no S3) pode custar centenas de dólares por mês via NAT. VPC Endpoints eliminam esse custo completamente.

**Deleting the NAT Gateway sem liberar o Elastic IP:** ao deletar um NAT Gateway, o Elastic IP associado fica **em estado alocado sem estar associado** — gerando custo de $0.005/hora indefinidamente. Sempre verifique os EIPs após deletar NAT Gateways.

**Usar 1 NAT para dev/staging/prod na mesma VPC:** em arquiteturas com múltiplos ambientes na mesma VPC (não recomendado, mas comum), um único NAT serve todos os ambientes. Quando prod precisa escalar, o tráfego do NAT aumenta abruptamente — e o custo de dados aparece na conta consolidada sem associação clara ao ambiente.

## 🧩 Quiz de Fixação

1. Uma empresa tem 3 NAT Gateways (1 por AZ) e processa 500 GB de dados por mês em cada um. Calcule o custo mensal total dos NAT Gateways e identifique qual estratégia poderia reduzir o custo se 200 GB dos 500 GB são tráfego para o Amazon S3.

2. Uma instância EC2 privada faz 60.000 conexões TCP simultâneas para o mesmo servidor externo via NAT Gateway. Ela começa a receber erros `ErrorPortAllocation`. Por que isso acontece e quais são as opções para resolver?

3. A AZ us-east-1b falha. A empresa tem: 1 NAT Gateway em us-east-1a, instâncias em us-east-1b cujo Route Table aponta para o NAT de us-east-1a. As instâncias de us-east-1b ainda têm acesso à internet? O que acontece com o custo do tráfego cross-AZ durante o failover?

**Respostas:**

1) **Custo atual:**
- Existência: 3 × $0.045/h × 720h = **$97.20/mês**
- Dados: 3 × 500 GB × $0.045/GB = **$67.50/mês**
- **Total atual: $164.70/mês**

**Com VPC Gateway Endpoints para S3 (eliminar 200 GB por AZ):**
- Existência: 3 × $0.045/h × 720h = **$97.20/mês** (igual)
- Dados restantes: 3 × 300 GB × $0.045/GB = **$40.50/mês**
- VPC Endpoints para S3: **$0** (Gateway Endpoints são gratuitos)
- **Total com endpoints: $137.70/mês** — economia de **$27/mês (16%)** apenas com endpoints

Para maior economia: identificar outros serviços AWS nos 300 GB restantes que poderiam usar Interface Endpoints (ECR, Secrets Manager, STS, etc.).

2) O NAT Gateway suporta até **55.000 conexões simultâneas por destino único** (mesmo IP de destino + mesma porta de destino). Com 60.000 conexões para o mesmo servidor, esse limite é ultrapassado — o NAT Gateway não consegue alocar novas portas de origem para distinguir as conexões adicionais. **Opções para resolver:**
(a) **Múltiplos NAT Gateways com IPs diferentes**: distribuir as 60.000 conexões entre 2 NAT Gateways → 30.000 cada, dentro do limite;
(b) **Reduzir conexões via connection pooling**: a aplicação provavelmente está abrindo muitas conexões sem reutilizá-las. Implementar pooling de conexões HTTP (keep-alive) reduz drasticamente o número de conexões simultâneas;
(c) **Verificar se é um vazamento**: 60.000 conexões para um único destino é incomum — investigar se há um bug de leak de conexões;
(d) **Usar múltiplos destinos**: se possível, distribuir as requisições entre múltiplos endpoints (diferentes IPs de destino).

3) **Sim, as instâncias de us-east-1b ainda têm acesso à internet**, pois a Route Table delas aponta para o NAT Gateway de us-east-1a — que está em AZ diferente (us-east-1a não falhou, apenas us-east-1b falhou). As instâncias de us-east-1b continuam rodando (estão em us-east-1b, não afetadas pela falha de us-east-1b... aguarda — se us-east-1b falhou, as instâncias *nessa AZ* também estão fora. O cenário correto seria: instâncias de us-east-1b sobreviventes em outros recursos, mas em geral se a AZ cai, as instâncias EC2 também caem). **Custo durante operação normal (antes da falha):** tráfego de instâncias em us-east-1b passando pelo NAT em us-east-1a gera **custo inter-AZ de $0.01/GB** *além* do custo de NAT de $0.045/GB — totalizando $0.055/GB em vez de $0.045/GB. Esse é um dos motivos pelos quais criar 1 NAT por AZ é a prática correta — elimina o custo inter-AZ e também garante HA real em falha de AZ.
