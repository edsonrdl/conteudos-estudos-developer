### NAT Gateway vs NAT Instance — break-even de custo, bandwidth e quando cada um faz sentido

O NAT Gateway é o serviço gerenciado e recomendado pela AWS para NAT em produção. A NAT Instance é uma instância EC2 configurada manualmente para fazer NAT — um padrão mais antigo que ainda faz sentido em cenários específicos, principalmente quando o custo do NAT Gateway é alto em ambientes de desenvolvimento ou quando funcionalidades extras são necessárias.

---

## O que é uma NAT Instance

Uma NAT Instance é simplesmente uma instância EC2 com:
1. **Source/Destination Check desabilitado** (permite encaminhar pacotes de outros IPs)
2. **IP forwarding habilitado** no SO (`net.ipv4.ip_forward = 1`)
3. **Regras de iptables** para MASQUERADE (SNAT)
4. Localizada em uma **subnet pública** com rota para IGW

A AWS fornece AMIs otimizadas para NAT (`amzn-ami-vpc-nat`), mas você pode configurar qualquer instância Linux:

```bash
# Configuração manual de NAT Instance em Amazon Linux 2023

# 1. Desabilitar Source/Destination Check na instância
aws ec2 modify-instance-attribute \
  --instance-id i-nat-abc123 \
  --no-source-dest-check

# 2. Dentro da instância: habilitar IP forwarding
sudo sysctl -w net.ipv4.ip_forward=1
echo "net.ipv4.ip_forward = 1" | sudo tee -a /etc/sysctl.conf

# 3. Configurar iptables para MASQUERADE (SNAT)
# eth0 = interface com IP público/EIP
sudo iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE
sudo iptables -A FORWARD -i eth0 -o eth0 -m state \
  --state RELATED,ESTABLISHED -j ACCEPT
sudo iptables -A FORWARD -i eth1 -o eth0 -j ACCEPT

# Persistir regras após reboot
sudo service iptables save  # Amazon Linux 1
# Para AL2023: usar iptables-save e configurar systemd

# 4. Na Route Table das subnets privadas:
# 0.0.0.0/0 → ID da instância NAT (i-nat-abc123) ou sua ENI (eni-xxx)
aws ec2 create-route \
  --route-table-id rtb-privada \
  --destination-cidr-block 0.0.0.0/0 \
  --instance-id i-nat-abc123
```

```

│ Aspecto                 │ NAT Gateway             │ NAT Instance             │
├─────────────────────────┼─────────────────────────┼──────────────────────────┤
│ Gerenciamento           │ Totalmente gerenciado   │ Você gerencia tudo       │
│ Alta disponibilidade    │ Automático dentro da AZ │ Manual (HA com script)   │
│ Multi-AZ                │ 1 por AZ (recomendado)  │ 1 por AZ (manual)        │
│ Escalabilidade          │ Automática (até 100Gbps)│ Limitada pelo tipo EC2   │
│ Patches de SO           │ AWS cuida               │ Você cuida               │
│ Failover                │ Automático (AZ-level)   │ Manual ou script         │
│ Bandwidth máximo        │ 100 Gbps                │ Depende do tipo EC2      │
```

## Análise de custo — break-even

### Custo do NAT Gateway

```
NAT Gateway (us-east-1):
  Existência:    $0.045/hora × 720h = $32.40/mês por AZ
  Dados:         $0.045/GB
  
  1 AZ:  $32.40/mês base
  3 AZs: $97.20/mês base (HA completo)
```

### Custo da NAT Instance

```
NAT Instance (us-east-1, On-Demand):
  t4g.nano (ARM, 2 vCPU, 0.5 GiB):   $0.0042/h = $3.02/mês
  t4g.micro (ARM, 2 vCPU, 1 GiB):    $0.0084/h = $6.05/mês
  t4g.small (ARM, 2 vCPU, 2 GiB):    $0.0168/h = $12.10/mês
  t3.micro (Intel, 2 vCPU, 1 GiB):   $0.0104/h = $7.49/mês
  c6g.large (ARM, 2 vCPU, 4 GiB):    $0.0680/h = $48.96/mês
  
  Mais custo de EIP se estiver parada: $3.60/mês (idle EIP)
  Total t4g.nano + EIP: ~$3.02 + $0 (EIP gratuito quando associado) = $3.02/mês
  
  Para 3 AZs com t4g.nano: $3.02 × 3 = $9.06/mês base
  vs NAT Gateway: $97.20/mês base
  
  Diferença de existência: $88.14/mês
```

### Quando o NAT Gateway se paga vs NAT Instance

O ponto crítico é o **custo de dados**: o NAT Gateway cobra $0.045/GB, enquanto a NAT Instance cobra apenas o custo de transferência de dados EC2 ($0.09/GB de saída para a internet — mas esse custo existe também para o NAT Gateway, sendo cobrado pela AWS de qualquer forma como custo de dados de saída da VPC).

```
Análise de break-even para 1 AZ:

Diferença de custo base:
  NAT GW: $32.40/mês
  NAT Instance t4g.nano: $3.02/mês
  Diferença: $29.38/mês a favor da NAT Instance

O NAT Gateway cobra $0.045/GB de processamento
(além dos custos de egress normais da AWS)

A NAT Instance não cobra esse $0.045/GB extra de processamento

Break-even em GB processados:
  $29.38 (diferença base) ÷ $0.045/GB = 653 GB/mês

Se você processa MENOS de 653 GB/mês via NAT em uma AZ:
  → NAT Instance é mais barata

Se você processa MAIS de 653 GB/mês:
  → NAT Gateway se paga em relação à NAT Instance
  (pelo valor agregado: zero manutenção, HA automático, escalabilidade)

Para 3 AZs:
  Diferença base 3 AZs: $88.14/mês
  Break-even em dados: $88.14 ÷ $0.045 = 1.959 GB/mês total (≈ 2 TB)
  
  Abaixo de 2 TB/mês total: 3 NAT Instances são mais baratas
  Acima de 2 TB/mês: NAT Gateway começa a compensar
  (mas não inclui o custo operacional de gerenciar 3 instâncias)
```

## Bandwidth — limitação crucial da NAT Instance

A limitação de bandwidth da NAT Instance é determinada pelo tipo EC2. Instâncias pequenas saturarão rapidamente em workloads intensivos:

```
Bandwidth de rede por tipo EC2:

t4g.nano:   até 5 Gbps    → 625 MB/s teórico
t4g.small:  até 5 Gbps
t3.medium:  até 5 Gbps
m7g.large:  até 12.5 Gbps → 1.56 GB/s teórico
c7g.xlarge: até 12.5 Gbps
m7g.4xlarge:até 15 Gbps

NAT Gateway: 100 Gbps → 12.5 GB/s

Para workloads de produção com alto volume de dados:
  Uma NAT Instance t4g.nano a 5 Gbps saturaria com ~50 instâncias
  EC2 fazendo downloads simultâneos de ~100 Mbps cada.
  
  NAT Gateway aguenta 1.000x mais sem configuração adicional.
```

## Quando NAT Instance ainda faz sentido

```
Caso 1 — Ambientes de desenvolvimento com baixo tráfego:
  Dev/staging que roda apenas em horário comercial
  < 100 GB/mês de dados via NAT
  Tolerância a manutenção manual
  
  Economia: $29/mês por AZ (t4g.nano vs NAT GW)
  Para 3 ambientes de dev × 1 AZ cada: $87/mês de economia

Caso 2 — Port Forwarding necessário:
  NAT Gateway não suporta port forwarding (DNAT)
  NAT Instance com iptables suporta:
    iptables -t nat -A PREROUTING -p tcp --dport 2222 \
      -j DNAT --to-destination 10.0.10.50:22
  
  Use case: bastion host que também faz NAT, ou acesso específico
  a servidores internos sem VPN

Caso 3 — Funcionalidades extras integradas:
  NAT Instance pode rodar simultaneamente:
  ✓ Proxy HTTP/HTTPS (Squid) para filtragem de URLs
  ✓ VPN concentrador (OpenVPN, WireGuard)
  ✓ Bastion host para SSH
  ✓ Network monitoring (tcpdump, ntopng)
  ✓ Traffic shaping (tc/netem)
  
  Uma única instância medium pode substituir múltiplos serviços
  em ambientes pequenos

Caso 4 — Controle total de logs e tráfego:
  Em alguns cenários de compliance, é necessário inspecionar
  e logar todo pacote — possível com iptables LOG na NAT Instance
  Não é possível ter visibilidade de pacote individual no NAT Gateway
```

## Alta disponibilidade com NAT Instance — padrão com failover

Para produção com NAT Instance, é necessário implementar HA manualmente:

```bash
# Padrão de HA: Lambda + CloudWatch + SNS

# 1. CloudWatch Alarm monitorando a NAT Instance
aws cloudwatch put-metric-alarm \
  --alarm-name "nat-instance-down" \
  --metric-name StatusCheckFailed \
  --namespace AWS/EC2 \
  --dimensions Name=InstanceId,Value=i-nat-primary \
  --statistic Maximum \
  --period 60 \
  --threshold 1 \
  --comparison-operator GreaterThanOrEqualToThreshold \
  --evaluation-periods 2 \
  --alarm-actions arn:aws:lambda:...:function:failover-nat

# 2. Lambda para failover
# Quando primary falha: 
#   - Inicia NAT Instance secundária
#   - Atualiza Route Table para apontar para a nova instância
```

```python
# Lambda de failover para NAT Instance
import boto3

def lambda_handler(event, context):
    ec2 = boto3.client('ec2')
    
    # Iniciar instância de standby
    ec2.start_instances(InstanceIds=['i-nat-standby'])
    
    # Aguardar a instância ficar running
    waiter = ec2.get_waiter('instance_running')
    waiter.wait(InstanceIds=['i-nat-standby'])
    
    # Atualizar Route Table para apontar para a nova instância
    ec2.replace_route(
        RouteTableId='rtb-privada-az-a',
        DestinationCidrBlock='0.0.0.0/0',
        InstanceId='i-nat-standby'
    )
    
    print("Failover concluído: rtb-privada-az-a → i-nat-standby")
```

**Problema dessa abordagem:** o failover leva 2-3 minutos (detectar falha + iniciar instância + atualizar rota). Para produção com SLA estrito, o NAT Gateway é infinitamente mais adequado.

## Decisão — NAT Gateway ou NAT Instance

```
Use NAT GATEWAY quando:
  ✓ Ambiente de produção com SLA
  ✓ Volume > 500 GB/mês de dados via NAT
  ✓ Time sem experiência em Linux/iptables
  ✓ Necessidade de HA automática sem scripts
  ✓ Bandwidth > 5 Gbps necessário
  ✓ Escalabilidade imprevisível (picos de tráfego)

Use NAT INSTANCE quando:
  ✓ Ambiente de dev/staging com tráfego baixo (< 200 GB/mês)
  ✓ Orçamento muito restrito e aceitação de manutenção manual
  ✓ Precisa de port forwarding ou proxy HTTP
  ✓ Combinar NAT + bastion + outras funções em 1 instância
  ✓ Compliance com inspeção de pacote nível L7

Nunca use NAT Instance em produção sem:
  → Script de failover automatizado
  → Monitoramento com alarme de status check
  → Procedimento documentado de recuperação
  → Janela de manutenção planejada para patches
```

## Erros comuns e armadilhas

**NAT Instance sem Source/Destination Check desabilitado:** o erro mais comum ao configurar uma NAT Instance. Sem isso, a instância descarta pacotes que não têm seu próprio IP como origem ou destino — o NAT nunca funciona. Verificar com: `aws ec2 describe-instance-attribute --instance-id i-xxx --attribute sourceDestCheck`.

**Usar t2.nano ou t3.nano para NAT em dev e não monitorar CPU Credits:** instâncias burstable podem esgotar os créditos de CPU durante downloads intensos, causando throttling do processamento NAT. Em dev com picos de uso, usar t4g.small (com Unlimited mode) ou uma instância não-burstable pequena.

**Route Table apontando para a instância (i-xxx) em vez da ENI (eni-xxx):** ao fazer failover para uma nova instância, a Route Table precisa ser atualizada. Se você referenciar a ENI (mais estável), pode manter a mesma ENI entre instâncias e o failover é mais simples.

## 🧩 Quiz de Fixação

1. Um ambiente de desenvolvimento tem 3 VPCs (dev, staging, qa) em 1 AZ cada, com ~50 GB/mês de tráfego NAT por VPC. O time está pagando $32.40/mês por NAT Gateway em cada VPC = $97.20/mês total. Como calcular se vale a pena migrar para NAT Instances t4g.nano e qual seria a economia?

2. Uma NAT Instance está configurada corretamente (iptables, IP forwarding, Source/Dest Check desabilitado), mas instâncias privadas não conseguem acessar a internet. O Status Check da NAT Instance está verde. Quais são as 3 causas mais prováveis a investigar em ordem de probabilidade?

3. Por que o Port Forwarding é uma funcionalidade que o NAT Gateway não pode oferecer por design, e em qual cenário um arquiteto usaria uma NAT Instance especificamente por essa razão?

**Respostas:**

1) **Cálculo de break-even:**
- Custo atual (3 NAT Gateways): $97.20/mês (base) + 3 × 50 GB × $0.045 = $97.20 + $6.75 = **$103.95/mês**
- Custo com 3 NAT Instances t4g.nano: 3 × $3.02/mês (base) + dados (o $0.045/GB de processamento não é cobrado) = **$9.06/mês** (apenas existência)
- **Economia mensal: $94.89/mês (~91% de redução)**
- Custo operacional adicional: tempo de engenheiro para configurar e manter as 3 instâncias (~2-4h inicialmente + manutenção)
- Se o custo/hora do engenheiro é $50/h: $150-200 de setup amortizado em meses = break-even praticamente imediato

Para volumes de 50 GB/mês, a NAT Instance t4g.nano é claramente superior em custo. O único risco é a falta de HA automática — aceitável para dev/staging com SLA frouxo.

2) **Três causas mais prováveis em ordem:**

(1) **Route Table da subnet privada não aponta para a NAT Instance:** verificar com `aws ec2 describe-route-tables --filters Name=association.subnet-id,...`. A rota `0.0.0.0/0` deve apontar para o ID da instância NAT ou sua ENI — não para um IGW ou NAT Gateway.

(2) **Security Group da NAT Instance bloqueia o tráfego:** ao contrário do NAT Gateway (que não tem SG), a NAT Instance tem um SG. Verificar se o SG permite ingress das subnets privadas (CIDR `10.0.0.0/16` ou específico) em todas as portas, e se o egress para `0.0.0.0/0` está liberado.

(3) **Source/Destination Check ainda habilitado:** mesmo após executar o comando, verificar com `describe-instance-attribute --attribute sourceDestCheck` se o valor é `false`. Em alguns casos, o comando não é refletido imediatamente ou foi executado na ENI errada (instâncias com múltiplas ENIs precisam do check desabilitado na ENI correta).

3) O NAT Gateway opera como NAT de saída puro (SNAT) — ele traduz o IP de *origem* de pacotes saindo da VPC para seu IP público. Por design, ele não implementa DNAT (Destination NAT), que seria necessário para port forwarding — ou seja, redirecionar pacotes *entrando* de um IP/porta para outro IP/porta interno. **Cenário de uso:** uma empresa tem uma rede on-premises que precisa acessar um servidor de desenvolvimento interno na VPC (ex: servidor de banco na porta 5432) sem VPN ou Direct Connect. Usando uma NAT Instance na subnet pública com regra iptables DNAT: `iptables -t nat -A PREROUTING -p tcp --dport 15432 -j DNAT --to-destination 10.0.10.100:5432`, o servidor on-premises conecta-se ao Elastic IP da NAT Instance na porta 15432 e o tráfego é redirecionado para o banco interno. O NAT Gateway simplesmente não tem essa capacidade — é SNAT-only por design gerenciado.
