### Subnets públicas vs privadas — a route table é o que importa, não o nome

A distinção entre subnet pública e privada é um dos conceitos mais mal entendidos da AWS. O nome "pública" ou "privada" não existe como configuração técnica no console ou API — é apenas uma convenção humana. O que tecnicamente define se uma subnet é pública ou privada é exclusivamente a presença ou ausência de uma rota para um **Internet Gateway** na Route Table associada a ela.

---

## A definição técnica correta

```
Subnet "pública":
  → Route Table tem rota: 0.0.0.0/0 → igw-xxxxxxxx
  → Recursos com IP público podem se comunicar bidiretcionalmente com a internet
  → Exemplo: load balancer, NAT Gateway, bastion host

Subnet "privada":
  → Route Table NÃO tem rota para um Internet Gateway
  → Sem rota 0.0.0.0/0 → igw, ou rota 0.0.0.0/0 → nat-gateway/eigw
  → Recursos isolados da internet — não recebem conexões externas diretamente
  → Exemplo: EC2 de aplicação, RDS, ElastiCache, EKS workers
```

**Consequência direta:** se você criar uma subnet, chamá-la de "subnet-privada-app" no console, mas associá-la a uma Route Table com rota `0.0.0.0/0 → igw`, ela é **tecnicamente pública** — independente do nome.

---

## Demonstração prática — o nome não importa

```bash
# Criar duas subnets com nomes "enganosos"
aws ec2 create-subnet \
  --vpc-id vpc-0abc \
  --cidr-block 10.0.1.0/24 \
  --tag-specifications 'ResourceType=subnet,Tags=[{Key=Name,Value=subnet-privada-banco}]'

# Associar à Route Table que tem rota para IGW
aws ec2 associate-route-table \
  --subnet-id subnet-111 \
  --route-table-id rtb-com-igw

# Resultado: "subnet-privada-banco" é TECNICAMENTE PÚBLICA
# O nome é apenas uma tag — sem efeito no comportamento de rede

# Verificar o que realmente determina se é pública:
aws ec2 describe-route-tables \
  --route-table-ids rtb-com-igw \
  --query 'RouteTables[0].Routes[?DestinationCidrBlock==`0.0.0.0/0`]'
# Se retorna GatewayId com "igw-" = pública
# Se retorna NatGatewayId ou vazio = privada
```

## As três condições para acesso bidirecional com a internet

Uma subnet ser "pública" (ter rota para IGW) é necessário mas não suficiente para que uma instância acesse a internet bidirecionalmente. São necessárias **três condições simultâneas**:

```
Condição 1 — Route Table com rota para Internet Gateway:
  0.0.0.0/0 → igw-xxxxxxxx  ✓

Condição 2 — Instância com IP público (Elastic IP ou auto-assign):
  IP privado apenas: 10.0.1.50  ✗  (sem IP público → sem entrada da internet)
  IP privado + Elastic IP: 10.0.1.50 + 54.123.45.67  ✓

Condição 3 — Security Group permite o tráfego:
  Regra de ingresso: TCP 443 from 0.0.0.0/0  ✓

Se qualquer uma das três falhar:
  → Sem rota: pacote não sabe para onde ir (dropped)
  → Sem IP público: internet não tem como endereçar a instância
  → SG bloqueia: pacote chega mas é descartado pelo SG
```

### Por que a subnet da VPC Default é problemática

```
VPC Default — as três condições para toda instância:

Condição 1: ✓ Route Table tem 0.0.0.0/0 → igw (sempre)
Condição 2: ✓ MapPublicIpOnLaunch = true (sempre, por padrão)
Condição 3: ✓/✗ SG default permite all traffic from same SG

→ Qualquer EC2 lançada na VPC Default tem IP público e rota para internet
→ Está exposta à internet protegida apenas pelo SG default
```

## Anatomy de uma Route Table — lendo as rotas

Para determinar se uma subnet é pública ou privada, analise sua Route Table:

```
Route Table de subnet PÚBLICA:
  Destino           | Alvo               | Significado
  ──────────────────┼────────────────────┼──────────────────────────────
  10.0.0.0/16      | local              | Tráfego interno da VPC
  0.0.0.0/0        | igw-0abc12345      | Internet (entrada e saída)

Route Table de subnet PRIVADA com NAT:
  Destino           | Alvo               | Significado
  ──────────────────┼────────────────────┼──────────────────────────────
  10.0.0.0/16      | local              | Tráfego interno da VPC
  0.0.0.0/0        | nat-0abc12345      | Somente SAÍDA (NAT translates)
                                          Entrada da internet: IMPOSSÍVEL

Route Table de subnet PRIVADA isolada (sem saída para internet):
  Destino           | Alvo               | Significado
  ──────────────────┼────────────────────┼──────────────────────────────
  10.0.0.0/16      | local              | Apenas tráfego interno da VPC
  (sem 0.0.0.0/0)                        Sem saída nem entrada da internet
```

## Subnets isoladas — quando não há rota para nenhum gateway

Algumas subnets não precisam de saída para a internet nem para outros gateways. São usadas para recursos que devem se comunicar apenas dentro da VPC:

```
Casos de uso de subnets completamente isoladas:
  ✓ Bancos de dados (RDS, Aurora) em ambientes de alta segurança
  ✓ Serviços internos que só precisam de comunicação inter-serviços
  ✓ Ambientes de compliance que proibem qualquer saída de dados
  ✓ Clusters de processamento que leem/escrevem apenas em S3/DynamoDB
    (via VPC Gateway Endpoint — sem passar por NAT ou IGW)

Route Table de subnet isolada com VPC Endpoint:
  Destino           | Alvo               
  ──────────────────┼────────────────────
  10.0.0.0/16      | local              
  pl-xxxxxxxx      | vpce-xxxxxxxx      ← S3/DynamoDB via endpoint (sem internet)
```

## O papel do MapPublicIpOnLaunch

Além da Route Table, uma subnet tem o atributo `MapPublicIpOnLaunch` que controla se instâncias recebem IP público automaticamente:

```bash
# Ver o atributo atual de uma subnet
aws ec2 describe-subnets \
  --subnet-ids subnet-0abc \
  --query 'Subnets[0].MapPublicIpOnLaunch'

# Habilitar atribuição automática de IP público (subnet pública)
aws ec2 modify-subnet-attribute \
  --subnet-id subnet-0abc \
  --map-public-ip-on-launch

# Desabilitar (subnet privada — padrão para subnets criadas manualmente)
aws ec2 modify-subnet-attribute \
  --subnet-id subnet-0abc \
  --no-map-public-ip-on-launch
```

```
Combinações possíveis e comportamento resultante:

Route Table com IGW + MapPublicIpOnLaunch=true:
  → Subnet verdadeiramente pública. Instâncias recebem IP público automaticamente
  → Padrão para subnets de load balancer e bastion hosts

Route Table com IGW + MapPublicIpOnLaunch=false:
  → Subnet "semi-pública". Instâncias SEM IP público automático
  → Para acessar a internet, instância precisa de Elastic IP explícito
  → Útil quando você quer controle manual de quais instâncias têm IP público

Route Table sem IGW + MapPublicIpOnLaunch=false:
  → Subnet privada padrão.
  → Instâncias não têm IP público. Saída via NAT se configurado.

Route Table sem IGW + MapPublicIpOnLaunch=true:
  → Configuração inconsistente (IP público existe mas não há rota para usá-lo)
  → Desperdício — o IP público não serve para nada sem a rota IGW
```

## Verificando programaticamente se uma subnet é pública

```python
import boto3

ec2 = boto3.client('ec2', region_name='us-east-1')

def is_public_subnet(subnet_id: str) -> bool:
    """Determina se uma subnet é pública analisando sua Route Table."""
    
    # 1. Encontrar a Route Table associada à subnet
    response = ec2.describe_route_tables(
        Filters=[
            {'Name': 'association.subnet-id', 'Values': [subnet_id]}
        ]
    )
    
    route_tables = response['RouteTables']
    
    # Se não há associação explícita, usa a Main Route Table da VPC
    if not route_tables:
        subnet = ec2.describe_subnets(SubnetIds=[subnet_id])['Subnets'][0]
        vpc_id = subnet['VpcId']
        response = ec2.describe_route_tables(
            Filters=[
                {'Name': 'vpc-id', 'Values': [vpc_id]},
                {'Name': 'association.main', 'Values': ['true']}
            ]
        )
        route_tables = response['RouteTables']
    
    if not route_tables:
        return False
    
    # 2. Verificar se há rota 0.0.0.0/0 para um Internet Gateway
    for route in route_tables[0]['Routes']:
        if (route.get('DestinationCidrBlock') == '0.0.0.0/0' and
            route.get('GatewayId', '').startswith('igw-') and
            route.get('State') == 'active'):
            return True
    
    return False

# Uso
subnet_id = 'subnet-0abc123'
publico = is_public_subnet(subnet_id)
print(f"Subnet {subnet_id} é {'pública' if publico else 'privada'}")
```

## Armadilha clássica — Main Route Table

Quando uma subnet não tem uma Route Table explicitamente associada, ela herda a **Main Route Table** da VPC. A Main Route Table é criada automaticamente pela AWS e inicialmente tem apenas a rota local. **Mas** se alguém adicionar uma rota `0.0.0.0/0 → IGW` na Main Route Table, **todas as subnets sem associação explícita tornam-se publicas automaticamente**:

```
VPC com Main Route Table modificada:

Main Route Table:
  10.0.0.0/16  → local
  0.0.0.0/0    → igw-xxx  ← ALGUÉM ADICIONOU ISSO

Subnet-app-01: sem associação explícita → herda Main → É PÚBLICA (sem querer!)
Subnet-app-02: sem associação explícita → herda Main → É PÚBLICA (sem querer!)
Subnet-db-01:  sem associação explícita → herda Main → É PÚBLICA (sem querer!)

Boa prática:
  → NUNCA adicionar rota IGW na Main Route Table
  → Criar Route Tables separadas para subnets públicas e privadas
  → Associar cada subnet explicitamente à sua Route Table correta
  → Manter a Main Route Table com apenas a rota local
```

## 🧩 Quiz de Fixação

1. Uma subnet chamada "subnet-publica-web" tem uma Route Table com as rotas: `10.0.0.0/16 → local` e `0.0.0.0/0 → nat-0abc123`. Uma instância EC2 nessa subnet com Elastic IP tenta ser acessada da internet. O acesso funciona? Por quê?

2. Um DBA reclamou que o banco de dados RDS em "subnet-privada-db" está sendo alcançado de IPs externos. A subnet tem Route Table com `0.0.0.0/0 → igw-xxx`. O nome da subnet é suficiente para garantir privacidade?

3. Uma empresa quer que instâncias EC2 em uma subnet possam fazer download de atualizações da internet, mas nenhum host externo deve conseguir iniciar conexões com elas. Qual é a configuração correta de Route Table e qual gateway usar?

**Respostas:**

1) **Não funciona**. Embora a subnet tenha o nome "pública" e a instância tenha um Elastic IP, a Route Table aponta `0.0.0.0/0` para um **NAT Gateway** (`nat-0abc123`) — não para um Internet Gateway. O NAT Gateway é um dispositivo de saída unidirecional: permite que instâncias *internas* iniciem conexões para a internet, mas descarta qualquer pacote externo que tente entrar. O Elastic IP é inútil nesse contexto porque não há rota de entrada funcionando. Para a subnet ser verdadeiramente pública e aceitar conexões de entrada, a rota `0.0.0.0/0` deve apontar para um **Internet Gateway** (`igw-xxx`), não para um NAT Gateway.

2) **Absolutamente não**. O nome da subnet é apenas uma tag — sem nenhum efeito no comportamento de rede. O que determina o acesso é a Route Table, e essa subnet tem `0.0.0.0/0 → igw-xxx`, tornando-a tecnicamente pública independente do nome. Se o RDS tem um IP público (ou está acessível via Elastic IP) e o Security Group do RDS permite acesso externo, conexões de fora são possíveis. Para tornar a subnet verdadeiramente privada: remover a rota `0.0.0.0/0 → igw-xxx` da Route Table (ou substituir por `0.0.0.0/0 → nat-gateway` se saída é necessária). O nome "privada" é só documentação humana — a segurança está na Route Table e no Security Group.

3) A configuração correta é: Route Table com `0.0.0.0/0 → nat-gateway` e o NAT Gateway deve estar em uma **subnet pública** (com rota para Internet Gateway). O NAT Gateway permite que instâncias iniciem conexões de saída para a internet (downloads, atualizações), mas descarta qualquer tentativa de conexão de entrada iniciada por hosts externos. A combinação é: subnet privada (sem IGW na Route Table) + NAT Gateway em subnet pública = saída livre, entrada bloqueada no nível de rede. O Security Group adiciona uma segunda camada de controle, mas o NAT já garante a proteção primária por design.
