### Design multi-AZ — quantas subnets criar, distribuição e isolamento por camada

O design de subnets de uma VPC determina a resiliência, a segurança e a operabilidade de toda a infraestrutura. Uma VPC bem desenhada distribui os recursos entre múltiplas Availability Zones para alta disponibilidade e organiza as subnets em camadas funcionais para controle de tráfego e compliance. Este arquivo apresenta o modelo de referência e as decisões envolvidas.

---

## Por que múltiplas AZs são obrigatórias em produção

Cada Availability Zone é um datacenter fisicamente separado com energia, refrigeração e rede independentes. Falhas de AZ acontecem — a AWS documenta eventos como `us-east-1` em 2017, `ap-northeast-1` em 2019, entre outros. Sem distribuição multi-AZ, qualquer falha de AZ derruba toda a aplicação:

```
Aplicação em uma única AZ (us-east-1a):

Usuários → ALB → EC2 → RDS
                (us-east-1a)

Falha de us-east-1a às 03h:
  ALB, EC2 e RDS: todos indisponíveis
  RTO: horas (aguardar restauração da AZ ou rebuild manual)
  RPO: depende de backups

Aplicação multi-AZ (us-east-1a + us-east-1b):

Usuários → ALB (cross-AZ)
              ├── EC2 us-east-1a → RDS primary us-east-1a
              └── EC2 us-east-1b → RDS standby us-east-1b

Falha de us-east-1a às 03h:
  ALB redireciona para us-east-1b automaticamente
  RDS faz failover para us-east-1b em ~60s
  RTO: < 2 minutos (automático)
  RPO: segundos (replicação síncrona)
```

## O modelo de três camadas — a arquitetura de referência

O padrão mais adotado em produção AWS organiza as subnets em três camadas funcionais (tiers), cada uma com suas próprias subnets por AZ:

```
VPC: 10.0.0.0/16 — Arquitetura 3-tier em 3 AZs:

┌─────────────────────────────────────────────────────────────────────┐
│                          VPC 10.0.0.0/16                           │
│                                                                     │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐             │
│  │  AZ-a        │  │  AZ-b        │  │  AZ-c        │             │
│  │              │  │              │  │              │             │
│  │  ┌─────────┐ │  │  ┌─────────┐ │  │  ┌─────────┐ │             │
│  │  │ Pública │ │  │  │ Pública │ │  │  │ Pública │ │ ← Tier 1   │
│  │  │ /24     │ │  │  │ /24     │ │  │  │ /24     │ │   Internet │
│  │  └─────────┘ │  │  └─────────┘ │  │  └─────────┘ │   facing   │
│  │              │  │              │  │              │             │
│  │  ┌─────────┐ │  │  ┌─────────┐ │  │  ┌─────────┐ │             │
│  │  │  App    │ │  │  │  App    │ │  │  │  App    │ │ ← Tier 2   │
│  │  │  /22    │ │  │  │  /22    │ │  │  │  /22    │ │   Compute  │
│  │  └─────────┘ │  │  └─────────┘ │  │  └─────────┘ │             │
│  │              │  │              │  │              │             │
│  │  ┌─────────┐ │  │  ┌─────────┐ │  │  ┌─────────┐ │             │
│  │  │  Data   │ │  │  │  Data   │ │  │  │  Data   │ │ ← Tier 3   │
│  │  │  /24    │ │  │  │  /24    │ │  │  │  /24    │ │   Database │
│  │  └─────────┘ │  │  └─────────┘ │  │  └─────────┘ │             │
│  └──────────────┘  └──────────────┘  └──────────────┘             │
└─────────────────────────────────────────────────────────────────────┘

Total: 9 subnets para uma aplicação com 3 camadas em 3 AZs
```

## Tier 1 — Pública (Internet-facing)

**O que vai aqui:** recursos que precisam receber tráfego diretamente da internet.

```
Recursos típicos no Tier Público:
  ✓ Application Load Balancer (ALB)
  ✓ Network Load Balancer (NLB) com IP público
  ✓ NAT Gateway (1 por AZ — precisa de IP público)
  ✓ Bastion Host / Jump Server (se não usar SSM)
  ✓ API Gateway VPC Link endpoints

NÃO deve ter no Tier Público:
  ✗ EC2 de aplicação (expõe desnecessariamente)
  ✗ Banco de dados (jamais)
  ✗ Cache (ElastiCache)
  ✗ Workers assíncronos

Configuração da Route Table pública:
  10.0.0.0/16  → local
  0.0.0.0/0    → igw-xxxxxxxx

Tamanho sugerido: /27 ou /28 por AZ
  → ALB não consome IPs de subnet (é gerenciado pela AWS)
  → NAT Gateway consome 1 IP
  → Bastion host: 1 IP
  → /27 (27 IPs) é suficiente para a maioria dos casos
```

---

## Tier 2 — Privado — Aplicação (Compute)

**O que vai aqui:** instâncias de compute que processam a lógica de negócio.

```
Recursos típicos no Tier de Aplicação:
  ✓ EC2 instances (web servers, app servers)
  ✓ ECS Tasks / EKS Pods
  ✓ Lambda em VPC
  ✓ ElastiCache (Redis/Memcached) — alguns times colocam aqui
  ✓ Internal Load Balancers (entre microserviços)

Configuração da Route Table privada (com saída para internet):
  10.0.0.0/16  → local
  0.0.0.0/0    → nat-xxxxxxxx  (NAT Gateway na subnet pública da mesma AZ)

Tamanho sugerido: /22 por AZ (1.019 IPs)
  → ECS/EKS com VPC CNI: cada pod consome 1 IP
  → 20 nós × 29 IPs/nó = 580 IPs só para o cluster EKS
  → /22 garante espaço para crescimento
  → Para aplicações sem containers: /24 é suficiente
```

---

## Tier 3 — Privado — Dados

**O que vai aqui:** bancos de dados e armazenamento que nunca devem ter acesso externo.

```
Recursos típicos no Tier de Dados:
  ✓ RDS / Aurora (instâncias e clusters)
  ✓ ElastiCache (Redis/Memcached)
  ✓ Amazon Redshift
  ✓ OpenSearch / Elasticsearch
  ✓ DocumentDB
  ✓ Amazon Keyspaces

Configuração da Route Table de dados (sem saída para internet):
  10.0.0.0/16  → local
  (sem 0.0.0.0/0 — completamente isolado)

  OU, se precisar de saída para S3 sem internet:
  pl-xxxxxxxx  → vpce-s3  (S3 Gateway Endpoint — gratuito)

Tamanho sugerido: /26 por AZ (59 IPs)
  → RDS Multi-AZ: 2 IPs (primário + standby)
  → Aurora cluster: até 15 read replicas + writer
  → ElastiCache: depende do número de nós
  → /26 é generoso para a maioria das configurações de banco
```

## Quantas AZs usar

```
Mínimo para alta disponibilidade: 2 AZs
  → Tolera falha de 1 AZ (50% da capacidade fica disponível)
  → Custo menor (menos subnets, menos NAT Gateways)
  → Adequado para ambientes menores ou com orçamento restrito

Recomendado para produção: 3 AZs
  → Tolera falha de 1 AZ (66% da capacidade fica disponível)
  → Melhor distribuição de carga (evita "hot AZ" com 50/50)
  → Necessário para alguns serviços (Aurora requer 3 AZs por padrão)
  → Padrão para empresas com SLAs de 99.9%+

Considerações de custo:
  → NAT Gateway: 1 por AZ é necessário para HA
    3 AZs × $0.045/hora = $97.20/mês só em NAT Gateways (sem dados)
  → Tráfego inter-AZ: $0.01/GB (EC2 ↔ RDS entre AZs)
  → Para ambientes de dev/staging: 1 NAT Gateway em 1 AZ pode ser aceitável
```

```
  10.0.64.0/26  → Dados AZ-a  (59 IPs)

```

## Camadas adicionais — quando adicionar um quarto tier

Arquiteturas mais complexas frequentemente adicionam tiers específicos:

```
Tier de Gerenciamento (Intra-services):
  → VPC Endpoints (Interface)
  → Bastion hosts / Session Manager endpoints
  → Internal DNS resolvers
  → Monitoramento e observabilidade
  Subnet: /27 por AZ

Tier de Ingestão (para dados em tempo real):
  → Kafka/MSK (alto consumo de IPs)
  → Kinesis Enhanced Fan-Out endpoints
  Subnet: /22 por AZ (MSK com 3 brokers × 3 AZs = muitos IPs)

Tier de Egress centralizado (Security):
  → Network Firewall (AWS Network Firewall)
  → Proxy Egress (Squid, Zscaler)
  → Inspecionar todo tráfego de saída antes de sair pela internet
```

## Subnets de AZs diferentes mas mesmo tier devem ter o mesmo SG

Uma prática importante: instâncias nas subnets de app em us-east-1a e us-east-1b devem ter **o mesmo Security Group** — afinal, são o mesmo serviço em AZs diferentes. Isso simplifica as regras de firewall:

```
Correto:
  EC2 em app-us-east-1a → SG: sg-api-backend
  EC2 em app-us-east-1b → SG: sg-api-backend
  (mesmo SG, diferentes AZs — faz sentido: são o mesmo serviço)

Errado (excesso de complexidade):
  EC2 em app-us-east-1a → SG: sg-api-backend-az-a
  EC2 em app-us-east-1b → SG: sg-api-backend-az-b
  (SGs diferentes por AZ → nenhum benefício, apenas mais trabalho)
```

## Erros comuns e armadilhas

**Criar subnets de dados com saída para internet:** bancos de dados nunca devem ter rotas para NAT Gateway ou Internet Gateway. A subnet de dados deve ser completamente isolada — acesso ao banco é feito somente pela camada de aplicação na mesma VPC.

**Usar apenas 1 NAT Gateway para múltiplas AZs:** se o NAT Gateway fica em us-east-1a e a AZ us-east-1a cai, instâncias em us-east-1b e us-east-1c perdem o acesso à internet. Sempre 1 NAT Gateway por AZ para alta disponibilidade real.

**Criar todas as subnets com /24:** para aplicações com ECS/EKS, /24 esgota rapidamente. Para a camada de aplicação, use /22 ou /21 dependendo da escala esperada.

**Colocar RDS sem Multi-AZ:** criar subnets em múltiplas AZs não garante que o RDS use todas — você precisa configurar explicitamente `Multi-AZ = true` na criação do RDS. As subnets em múltiplas AZs formam o "DB Subnet Group", mas o RDS só usa as duas AZs se Multi-AZ estiver ativo.

## 🧩 Quiz de Fixação

1. Uma empresa tem uma aplicação com ALB, EC2, RDS e ElastiCache em 2 AZs. A AZ us-east-1a cai. Quais componentes continuam funcionando e quais ficam indisponíveis, assumindo que toda a infraestrutura está multi-AZ corretamente configurada?

2. Um arquiteto propõe criar subnets de aplicação com /24 (251 IPs) para um cluster EKS que deve chegar a 30 nós `m7g.large` (cada um consumindo até 29 IPs com VPC CNI). O arquiteto argumenta "30 × 29 = 870 IPs, vou usar 3 subnets /24 em 3 AZs = 753 IPs, é suficiente". Onde está o erro no raciocínio?

3. Por que um NAT Gateway no Tier Público é necessário para instâncias no Tier Privado de Aplicação, mas não é necessário para o Tier de Dados? O que o Tier de Dados usa para acessar o S3 sem internet?

**Respostas:**

1) **Componentes que continuam funcionando:**
- ALB: cross-AZ por padrão — redireciona todo o tráfego para us-east-1b automaticamente
- EC2 em us-east-1b: continua recebendo tráfego do ALB
- RDS standby em us-east-1b: promovido a primário em ~60s pelo Multi-AZ failover automático
- ElastiCache em us-east-1b: continua disponível se configurado com replicação entre AZs
- NAT Gateway em us-east-1b: instâncias de us-east-1b ainda têm acesso à internet

**Componentes indisponíveis:**
- EC2 em us-east-1a: fora de serviço (instâncias físicas na AZ falharam)
- RDS primário em us-east-1a: indisponível (será substituído pelo standby)
- NAT Gateway em us-east-1a: indisponível (instâncias de us-east-1a sem saída, mas elas também estão fora)
- ElastiCache em us-east-1a: shards/nós nessa AZ fora de serviço

**Resultado:** a aplicação continua servindo usuários com ~50% da capacidade de compute, RDS em failover automático, e cache parcialmente disponível.

2) O erro está em **distribuir os 30 nós igualmente entre 3 AZs (10 nós por AZ)** e calcular o total somando as 3 subnets. O problema real é que cada subnet `/24` individual tem apenas 251 IPs utilizáveis. Com VPC CNI, cada nó `m7g.large` reserva até 29 IPs **na mesma subnet onde o nó está**. 10 nós × 29 IPs = 290 IPs por AZ — **maior que os 251 disponíveis em uma /24**. O Kubernetes scheduler não pode colocar novos pods porque os IPs da subnet esgotam antes de todos os nós estarem completos. A solução correta é usar `/22` por AZ (1.019 IPs), que comporta facilmente 10+ nós com todos os pods sem problemas.

3) O **Tier de Aplicação precisa de NAT Gateway** porque as instâncias EC2/ECS/EKS precisam fazer chamadas de saída para a internet: baixar imagens Docker do ECR (via internet pública ou via endpoint), chamar APIs externas, baixar pacotes de sistemas, etc. O NAT Gateway traduz o IP privado da instância para o IP público do NAT, permitindo saída sem expor a instância diretamente. O **Tier de Dados não precisa de NAT** porque RDS, ElastiCache e outros bancos gerenciados não iniciam conexões para a internet — eles apenas respondem a conexões da camada de aplicação dentro da VPC. Para casos onde o banco precisa acessar o S3 (ex: exportar backups, importar dados), o **VPC Gateway Endpoint para S3** é usado: é uma rota na Route Table que direciona tráfego para o S3 via rede privada da AWS, sem sair para a internet e sem custo de transferência.
