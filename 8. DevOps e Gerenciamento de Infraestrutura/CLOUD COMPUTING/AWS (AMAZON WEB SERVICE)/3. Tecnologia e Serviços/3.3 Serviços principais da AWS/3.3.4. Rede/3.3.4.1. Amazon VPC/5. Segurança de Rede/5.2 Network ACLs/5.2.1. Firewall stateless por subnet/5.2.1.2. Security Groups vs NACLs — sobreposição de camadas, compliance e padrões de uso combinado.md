### Security Groups vs NACLs — sobreposição de camadas, compliance e padrões de uso combinado

Security Groups e NACLs não são concorrentes — são complementares. Operam em camadas diferentes da pilha de segurança de rede da VPC, com capacidades distintas que se reforçam mutuamente. Entender quando usar um, o outro, ou ambos juntos é o que separa uma arquitetura de segurança superficial de uma arquitetura de defesa em profundidade.

---

## Onde cada um opera — a diferença fundamental

```
Fluxo de um pacote TCP chegando à VPC:

Internet → IGW
             │
             ▼
        ┌─────────────────────────────────┐
        │         SUBNET                  │
        │  NACL avaliada AQUI             │ ← nível de subnet
        │  (antes do pacote chegar        │
        │   à instância)                  │
        └──────────────┬──────────────────┘
                       │
                       ▼
        ┌─────────────────────────────────┐
        │      INSTÂNCIA EC2 / RDS        │
        │  Security Group avaliado AQUI   │ ← nível de instância/ENI
        │  (associado à ENI da instância) │
        └─────────────────────────────────┘

Ordem de avaliação:
  Ingress: NACL da subnet → Security Group da instância
  Egress:  Security Group da instância → NACL da subnet

Para o pacote chegar à instância:
  AMBOS devem permitir — se qualquer um negar, o pacote é bloqueado
```

## Comparativo completo

```
┌─────────────────────────┬──────────────────────────┬──────────────────────────┐
│ Aspecto                 │ Security Group            │ NACL                     │
├─────────────────────────┼──────────────────────────┼──────────────────────────┤
│ Nível de operação       │ Instância (ENI)           │ Subnet                   │
│ Estado (stateful)       │ Sim — respostas automát.  │ Não — avaliar ida e volta│
│ Regras de DENY          │ Não (allow-only)          │ Sim (ALLOW e DENY)       │
│ Ordem de avaliação      │ Todas as regras (OR lógico)│ Numerada (para no match)│
│ Referência a SGs        │ Sim                       │ Não (CIDR apenas)        │
│ Escopo de proteção      │ Por instância/ENI         │ Por subnet inteira       │
│ Portas efêmeras         │ Não precisa configurar    │ Obrigatório configurar    │
│ Regras por recurso      │ Até 60 regras (5 SGs/ENI) │ Até 20 regras por NACL   │
│ Custo                   │ Sem custo adicional       │ Sem custo adicional       │
│ Latência de aplicação   │ Nanossegundos             │ Nanossegundos             │
│ Logs de avaliação       │ Via VPC Flow Logs         │ Via VPC Flow Logs         │
└─────────────────────────┴──────────────────────────┴──────────────────────────┘
```

## Quando cada camada é responsável

```
Use Security Groups para:
  ✓ Controle granular por instância (cada serviço com seu SG)
  ✓ Comunicação entre camadas (sg-app → sg-db)
  ✓ Ambientes dinâmicos (IPs efêmeros em ECS/EKS)
  ✓ Regras baseadas em identidade (qual serviço pode acessar qual serviço)
  ✓ Proteção dentro da mesma subnet (EC2-A vs EC2-B na mesma subnet)

Use NACLs para:
  ✓ Bloqueio de IPs específicos (DENY explícito)
  ✓ Proteção de subnet inteira como unidade (todos os recursos da subnet)
  ✓ Compliance que exige defesa em profundidade (PCI DSS, HIPAA)
  ✓ Barreira extra contra erros de configuração de SG
  ✓ Isolamento entre subnets da mesma VPC (ex: prod não fala com dev)
  ✓ Bloqueio emergencial de ataques (DDoS, port scanning)
```

---

## O modelo de defesa em profundidade

A principal razão para usar ambos juntos é a **defesa em profundidade**: se uma camada falhar ou for mal configurada, a outra ainda protege.

```
Cenário: engenheiro comete erro no SG

Configuração errada:
  sg-db inbound: TCP 5432 from 0.0.0.0/0 ← acidentalmente aberto para internet

Sem NACL customizada:
  Qualquer IP da internet pode tentar conectar no banco → VULNERABILIDADE

Com NACL customizada na subnet de dados:
  NACL inbound: apenas TCP 5432 from 10.0.0.0/16 ALLOW
               0.0.0.0/0 → DENY implícito
  
  → Mesmo com SG errado, a NACL bloqueia tráfego externo
  → Banco protegido pela segunda camada
  → Tempo para corrigir o SG sem exposição
```

## Padrões de uso combinado — exemplos práticos

### Padrão 1 — NACLs permissivas + SGs restritivos (mais comum)

```
Quando usar: ambientes onde os SGs já fornecem proteção suficiente
             e as NACLs são uma barreira adicional básica

NACL (permissiva — pouca complexidade):
  Inbound:
    #100  TCP  443    0.0.0.0/0  ALLOW  ← HTTPS
    #110  TCP  80     0.0.0.0/0  ALLOW  ← HTTP
    #120  TCP  1024-65535 0.0.0.0/0 ALLOW  ← portas efêmeras
    #*    All  0.0.0.0/0  DENY
  
  Outbound:
    #100  TCP  443    0.0.0.0/0  ALLOW
    #110  TCP  1024-65535 0.0.0.0/0 ALLOW
    #*    All  0.0.0.0/0  DENY

SGs (detalhados — proteção real):
  sg-alb:     inbound  TCP 443 from 0.0.0.0/0
  sg-app:     inbound  TCP 8080 from sg-alb
  sg-db:      inbound  TCP 5432 from sg-app
  sg-cache:   inbound  TCP 6379 from sg-app
```

### Padrão 2 — NACLs restritivas + SGs restritivos (compliance rigoroso)

```
Quando usar: PCI DSS, HIPAA, compliance financeiro — "defense in depth"

NACL da subnet de dados (muito restritiva):
  Inbound:
    #100  TCP  5432  10.0.10.0/24  ALLOW  ← apenas da subnet de app
    #110  TCP  6379  10.0.10.0/24  ALLOW  ← apenas da subnet de app
    #*    All  0.0.0.0/0           DENY   ← tudo mais bloqueado

  Outbound:
    #100  TCP  1024-65535  10.0.10.0/24  ALLOW  ← respostas para subnet app
    #*    All  0.0.0.0/0                 DENY   ← sem saída para internet

SG do RDS:
  inbound: TCP 5432 from sg-app
  outbound: All traffic (RDS gerenciado pela AWS — egress não costuma ser restrito)

Resultado:
  Atacante que comprometer instância em outra subnet:
  → NACL bloqueia tráfego de subnets não autorizadas
  → SG bloqueia tráfego sem sg-app
  → Duas barreiras independentes
```

### Padrão 3 — NACL como lista negra dinâmica

```
Uso: resposta a incidentes — bloquear IPs maliciosos rapidamente

Manter uma NACL de "blocklist" com regras numeradas de 1-900
para IPs a bloquear, e as regras de ALLOW normais a partir de 1000:

NACL com blocklist ativa:
  #10   All  203.0.113.50/32  DENY   ← IP atacante bloqueado hoje
  #20   All  198.51.100.0/24  DENY   ← range de bot network
  #30   All  192.0.2.100/32   DENY   ← IP de scraper abusivo
  ...
  #1000 TCP  443  0.0.0.0/0  ALLOW  ← HTTPS normal
  #1010 TCP  80   0.0.0.0/0  ALLOW  ← HTTP normal
  #1020 TCP  1024-65535 0.0.0.0/0 ALLOW ← efêmeras
  #*    All  0.0.0.0/0       DENY

Limitação: máximo de ~20 regras (aumentável para 40 com suporte)
Para blocklists maiores: AWS WAF (ilimitado) é mais adequado
```

## Compliance — onde NACLs são frequentemente exigidas

Regulações como **PCI DSS**, **HIPAA** e **ISO 27001** frequentemente exigem evidência de controles de rede em múltiplas camadas. NACLs fornecem essa segunda camada documenável:

```
PCI DSS Requirement 1 (Network Security Controls):
  "Install and maintain network security controls"
  
  Apenas SGs: uma camada de controle
  SGs + NACLs: duas camadas independentes
  
  Evidência para auditoria:
  → Screenshot/export das NACLs mostrando restrições
  → Demonstrar que mesmo com SG permissivo, NACL protege
  → Provar separação de redes: NACL nega tráfego entre prod e dev

HIPAA:
  Protected Health Information (PHI) requer controles técnicos de acesso
  NACLs documentam que apenas sistemas autorizados podem alcançar
  os servidores com PHI (subnet de dados isolada por NACL)
```

## Quando NACLs causam mais danos do que ajudam

```
Situações onde NACLs são contraproducentes:

1. Ambientes muito dinâmicos (ECS/EKS com muitas subnets):
   Manter NACLs sincronizadas com topologia de rede em constante mudança
   é operacionalmente custoso e propenso a erros que causam outages

2. Times sem experiência com stateless:
   NACLs mal configuradas (esquecer portas efêmeras) causam
   problemas intermitentes difíceis de diagnosticar

3. Poucas subnets com muitas instâncias diversas:
   NACL aplica para TODA a subnet — não há granularidade por instância
   Uma NACL que funciona para o EC2-A pode quebrar o EC2-B na mesma subnet

Regra prática:
  Ambientes simples:       SGs são suficientes
  Ambientes com compliance: SGs + NACLs nas subnets de dados
  Resposta a incidentes:   NACL para bloqueio emergencial de IPs
```

## Diagnosticando problemas causados por NACLs

```bash
# Identificar se o problema é SG ou NACL

# Passo 1: verificar se os SGs permitem
aws ec2 describe-security-groups --group-ids sg-0abc123 \
  --query 'SecurityGroups[0].IpPermissions'

# Passo 2: verificar a NACL da subnet de destino
SUBNET_ID=$(aws ec2 describe-instances --instance-ids i-0abc \
  --query 'Reservations[0].Instances[0].SubnetId' --output text)

NACL_ID=$(aws ec2 describe-network-acls \
  --filters Name=association.subnet-id,Values=$SUBNET_ID \
  --query 'NetworkAcls[0].NetworkAclId' --output text)

aws ec2 describe-network-acls --network-acl-ids $NACL_ID \
  --query 'NetworkAcls[0].{
    Inbound:Entries[?Egress==`false`],
    Outbound:Entries[?Egress==`true`]
  }'

# Passo 3: se SG permite mas ainda bloqueia → NACL é o culpado
# Sintoma clássico:
#   SG: TCP 5432 from sg-app → ALLOW
#   NACL inbound: #100 TCP 5432 from 10.0.0.0/16 → ALLOW (OK)
#   NACL outbound: apenas #* DENY (faltou a regra de portas efêmeras!)
#   Resultado: conexão inicia mas resposta nunca chega
```

## 🧩 Quiz de Fixação

1. Uma instância RDS tem SG com `Inbound: TCP 5432 from sg-app ALLOW`. A NACL da subnet do RDS tem apenas: `#100 All traffic from 0.0.0.0/0 ALLOW` (inbound) e `#100 All traffic to 0.0.0.0/0 ALLOW` (outbound). Uma instância de app (com sg-app) tenta conectar e falha. O SG está correto. Qual é o provável problema?

2. Um auditor de PCI DSS pede evidência de que a rede de servidores de cartão de crédito está isolada de outras redes. Você tem apenas Security Groups configurados. Por que isso pode não ser suficiente para o auditor e como NACLs completam a evidência?

3. Um time de segurança detecta um ataque DDoS vindo de um range de IPs `198.51.100.0/24`. Eles querem bloquear imediatamente. A subnet alvo tem uma NACL com 18 regras já configuradas (limite de 20). Quais são as opções disponíveis?

**Respostas:**

1) O problema provavelmente está na **NACL da subnet da instância de app** (origem), não na NACL do RDS. Para a conexão funcionar, AMBAS as NACLs precisam estar corretas: (a) NACL da subnet de origem (app): precisa de regra outbound para TCP 5432 destino subnet do RDS, e regra inbound para portas efêmeras (respostas do banco); (b) NACL da subnet do RDS: como tem `All traffic ALLOW`, isso está OK. O culpado é a subnet de app — se sua NACL não tem regra outbound para TCP 5432, o pacote é bloqueado antes de sair. Ou se não tem regra inbound para portas efêmeras, a resposta do banco é bloqueada quando volta. Verificar com `describe-network-acls` na subnet de app e procurar por regras que cubram TCP 5432 outbound e TCP 1024-65535 inbound.

2) **Por que SGs sozinhos podem não satisfazer o auditor PCI DSS:** Security Groups são controles no nível de instância — protegem o servidor específico, mas não demonstram isolamento de rede como uma unidade. Um auditor pode argumentar que: (a) se um SG for mal configurado, não há segunda barreira de rede; (b) SGs não documentam claramente a separação de segmento de rede (o que PCI DSS chama de "network segmentation"); (c) SGs são "soft controls" — baseados em software que pode ter bugs. **Como NACLs completam a evidência:** NACLs operam no nível de subnet e são avaliadas independentemente dos SGs. Com uma NACL na subnet de cardholder data que permite apenas tráfego de subnets autorizadas, você demonstra: (a) isolamento de rede declarativo e auditável; (b) duas camadas independentes de controle; (c) que mesmo com um SG mal configurado, a NACL garante que apenas sistemas do ambiente PCI podem alcançar os servidores com dados de cartão — evidência forte de "network segmentation" para o auditor.

3) Com 18 regras e limite de 20, restam apenas 2 slots disponíveis (a regra implícita `*` não conta no limite das 20). **Opção 1 — Usar as 2 regras restantes:** criar `#5 TCP 198.51.100.0/24 DENY` e `#6 UDP 198.51.100.0/24 DENY` para cobrir os principais vetores. Limitação: não cobre ICMP (possível flood de ping). **Opção 2 — Solicitar aumento do limite via AWS Support:** abrir um Support Case pedindo aumento para 40 regras por NACL — pode levar horas, não serve para bloqueio imediato. **Opção 3 — Usar AWS WAF:** se há um ALB ou CloudFront na frente, criar uma Web ACL rule bloqueando o range `198.51.100.0/24` — ilimitado, aplica imediatamente, mais adequado para listas negras grandes. WAF opera antes da VPC, então bloqueia antes mesmo de atingir a NACL. **Opção 4 — Substituir regras menos críticas:** avaliar se há regras menos urgentes que podem ser removidas para liberar slots para o DENY. Esta é a solução mais arriscada operacionalmente, pois pode remover proteções existentes.
