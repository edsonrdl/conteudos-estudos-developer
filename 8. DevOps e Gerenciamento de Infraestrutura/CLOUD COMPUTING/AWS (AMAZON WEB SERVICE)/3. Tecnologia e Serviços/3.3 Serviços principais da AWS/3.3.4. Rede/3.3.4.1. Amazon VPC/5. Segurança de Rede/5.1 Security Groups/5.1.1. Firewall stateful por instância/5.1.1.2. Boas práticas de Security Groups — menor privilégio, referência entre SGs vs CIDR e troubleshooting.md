### Boas práticas de Security Groups — menor privilégio, SG vs CIDR e troubleshooting

Configurar Security Groups corretamente vai além de "abrir as portas necessárias". Em ambientes de produção, SGs mal projetados são a causa mais comum de incidentes de segurança na AWS — seja por permissões excessivas, por regras que ficam abertas mais do que deveriam, ou por CIDRs largos onde SGs específicos seriam mais seguros. Este arquivo consolida as boas práticas e as técnicas de diagnóstico mais usadas no dia a dia.

---

## Princípio 1 — Menor privilégio (Least Privilege)

O princípio do menor privilégio aplicado a Security Groups significa: **cada serviço tem apenas as permissões mínimas necessárias para funcionar**, e nada mais.

```
Anti-padrão — permissão excessiva:

sg-api (instância de API):
  Inbound:  TCP 0-65535 from 0.0.0.0/0  ← todas as portas, de qualquer lugar
  Outbound: All traffic to 0.0.0.0/0    ← saída irrestrita

Riscos:
  → Atacante que descobre o IP pode tentar qualquer porta
  → Se comprometida, a instância pode exfiltrar dados para qualquer destino
  → Difícil auditar o que está realmente em uso

Padrão correto — menor privilégio:

sg-api (instância de API):
  Inbound:
    TCP 8080 from sg-alb          ← apenas do ALB, apenas na porta da app
  Outbound:
    TCP 5432 to sg-rds            ← apenas para o banco, apenas PostgreSQL
    TCP 6379 to sg-cache          ← apenas para o Redis
    TCP 443  to 0.0.0.0/0         ← HTTPS para APIs externas (necessário)
    TCP 53   to 10.0.0.2/32       ← DNS interno (resolver da VPC)
    UDP 53   to 10.0.0.2/32       ← DNS via UDP

Resultado:
  → Atacante que acessa a porta 8080 só consegue chegar no app server
  → Instância comprometida não consegue abrir SSH, RDP, ou outros vetores
  → Saída restrita ao necessário — exfiltração limitada a HTTPS externo
```

## Princípio 2 — Um SG por papel (role), não por instância

Não crie um SG diferente para cada instância. Crie SGs que representam **papéis funcionais** e associe múltiplas instâncias ao mesmo SG:

```
Anti-padrão — SG por instância:
  sg-ec2-i-001 → instância i-001
  sg-ec2-i-002 → instância i-002
  sg-ec2-i-003 → instância i-003
  
  Problema: 200 instâncias = 200 SGs para gerenciar
  Escalar: nova instância = novo SG = nova regra em todos os dependentes

Padrão correto — SG por papel:
  sg-api-backend:
    → instância i-001, i-002, i-003 (todas as instâncias do mesmo serviço)
    → Novas instâncias: simplesmente associar sg-api-backend
    → RDS permite acesso de sg-api-backend automaticamente
```

### Hierarquia de SGs por camada

```
Arquitetura típica com SGs por papel:

sg-alb          → Application Load Balancer
sg-api          → API servers (EC2/ECS)
sg-worker       → Workers assíncronos (SQS consumers)
sg-rds          → Banco de dados RDS
sg-cache        → ElastiCache Redis
sg-bastion      → Bastion host (acesso SSH)
sg-endpoints    → VPC Interface Endpoints

Regras resultantes:
  sg-api.inbound:    TCP 8080 from sg-alb
  sg-rds.inbound:    TCP 5432 from sg-api, TCP 5432 from sg-worker
  sg-cache.inbound:  TCP 6379 from sg-api, TCP 6379 from sg-worker
  sg-bastion.inbound: TCP 22 from <IP escritório>/32
  sg-api.inbound:    TCP 22 from sg-bastion (SSH via bastion)
```

## Princípio 3 — Preferir referência de SG a CIDR onde possível

```
Quando usar CIDR:
  ✓ Tráfego da internet (0.0.0.0/0 para serviços públicos)
  ✓ Acesso de um IP fixo específico (IP do escritório para bastion)
  ✓ Comunicação com redes on-premises (172.16.0.0/12)
  ✓ Acesso de serviços externos com IPs fixos conhecidos

Quando usar referência de SG:
  ✓ Comunicação entre camadas da aplicação (ALB → app → db)
  ✓ Qualquer comunicação onde os IPs são dinâmicos (EC2, ECS, EKS)
  ✓ Acesso de serviços internos da AWS que têm SG
  ✓ Ambientes com Auto Scaling (IPs mudam frequentemente)

Regra prática:
  Se a origem é "um conjunto de instâncias AWS" → use SG
  Se a origem é "um bloco de endereços fixo" → use CIDR
```

```bash
# Adicionar regra com descrição clara

  --group-id sg-api-0abc \
  --ip-permissions '[{
    "IpProtocol": "tcp",
    "FromPort": 8080,
    "ToPort": 8080,
    "UserIdGroupPairs": [{
      "GroupId": "sg-alb-0def",
      "Description": "Tráfego do ALB de produção — porta 8080 da API REST"

# Descrições ruins (evitar):
#   "HTTP"
#   "port 8080"
#   "teste"

# Descrições boas:
#   "Receber requisições do ALB producao na porta da API REST"
#   "SSH do bastion host para administração — só rede corporativa"
#   "PostgreSQL da camada de aplicação — sg-api-backend"
```

## Princípio 5 — Nunca usar 0.0.0.0/0 em portas administrativas

```
Regras que NUNCA devem existir em produção:
  TCP 22   from 0.0.0.0/0  ← SSH aberto para a internet inteira
  TCP 3389 from 0.0.0.0/0  ← RDP aberto para a internet inteira
  TCP 5432 from 0.0.0.0/0  ← PostgreSQL aberto
  TCP 3306 from 0.0.0.0/0  ← MySQL aberto
  TCP 27017 from 0.0.0.0/0 ← MongoDB aberto

Alternativas seguras:
  SSH/RDP: 
    Opção 1: TCP 22 from sg-bastion (via jump server)
    Opção 2: Usar AWS Systems Manager Session Manager (sem SSH!)
    Opção 3: TCP 22 from <IP VPN corporativa>/32 (se VPN ativa)
  
  Banco de dados:
    TCP 5432 from sg-app (referência ao SG da aplicação)
    Nunca expor banco de dados diretamente na internet
```

## Auditoria de SGs — encontrando permissões excessivas

```bash
# Encontrar Security Groups com SSH aberto para a internet
aws ec2 describe-security-groups \
  --query 'SecurityGroups[?IpPermissions[?
    FromPort==`22` && 
    IpRanges[?CidrIp==`0.0.0.0/0`]
  ]].{Name:GroupName,ID:GroupId,VPC:VpcId}' \
  --output table

# Encontrar SGs com RDP aberto
aws ec2 describe-security-groups \
  --query 'SecurityGroups[?IpPermissions[?
    FromPort==`3389` && 
    IpRanges[?CidrIp==`0.0.0.0/0`]
  ]].{Name:GroupName,ID:GroupId}' \
  --output table

# Encontrar SGs não utilizados (sem instâncias, ENIs ou serviços associados)
# (útil para limpeza)
USED_SGS=$(aws ec2 describe-network-interfaces \
  --query 'NetworkInterfaces[*].Groups[*].GroupId' \
  --output text | tr '\t' '\n' | sort -u)

ALL_SGS=$(aws ec2 describe-security-groups \
  --query 'SecurityGroups[*].GroupId' \
  --output text | tr '\t' '\n' | sort)

# SGs não utilizados:
comm -23 <(echo "$ALL_SGS") <(echo "$USED_SGS")
```

## Troubleshooting — diagnosticando problemas de conectividade

### Fluxo de diagnóstico sistemático

```
Problema: Instância A não consegue conectar na instância B

Passo 1 — Verificar o SG da instância B (destino):
  Tem regra inbound para a porta desejada?
  A origem é correta (CIDR ou SG)?
  
Passo 2 — Verificar o SG da instância A (origem):
  Tem regra outbound para a porta de destino?
  (Se outbound for All traffic to 0.0.0.0/0, este passo pode ser pulado)

Passo 3 — Verificar a NACL das subnets:
  NACL da subnet de A: tem regra outbound para a porta?
  NACL da subnet de B: tem regra inbound para a porta?
  NACLs são stateless — verificar AMBAS as direções!

Passo 4 — Verificar Route Tables:
  Há rota do CIDR de A para o CIDR de B?
  (Dentro da mesma VPC, a rota local cobre — mas em peering/TGW, verificar)

Passo 5 — Verificar se a instância B está ouvindo na porta:
  ssh ec2-user@10.0.10.50
  sudo ss -tlnp | grep :5432  # verificar se PostgreSQL está listening
  sudo netstat -tlnp | grep :5432

Passo 6 — VPC Reachability Analyzer (automatiza passos 1-4):
  aws ec2 start-network-insights-analysis \
    --network-insights-path-id nip-xxx
```

### Comandos de diagnóstico na instância

```bash
# Dentro da instância EC2 — testar conectividade

# 1. Testar conectividade TCP (sem estabelecer HTTP)
nc -zv 10.0.10.50 5432    # nc/netcat
telnet 10.0.10.50 5432    # telnet (se instalado)

# 2. Testar DNS e conectividade HTTPS
curl -v https://s3.amazonaws.com/  # deve funcionar via endpoint ou internet
curl -v http://169.254.169.254/latest/meta-data/  # metadata sempre funciona

# 3. Verificar a rota que o pacote tomará
ip route get 10.0.10.50    # mostra qual interface/gateway será usado
traceroute 10.0.10.50       # tracing de saltos

# 4. Capturar tráfego (requer sudo, instala tcpdump)
sudo tcpdump -i eth0 port 5432 -n
# Se aparecem SYN mas não SYN-ACK: SG ou NACL bloqueando a resposta

# 5. Verificar se há conexão TCP estabelecida
ss -tn | grep 5432          # conexões TCP ativas na porta 5432
```

### Interpretando VPC Flow Logs para troubleshooting

```
VPC Flow Logs — campos principais:
version account-id interface-id srcaddr dstaddr srcport dstport protocol packets bytes start end action log-status

Exemplo de log de conexão ACEITA:
2 123456789 eni-abc 10.0.1.50 10.0.10.100 52341 5432 6 5 840 1609459200 1609459260 ACCEPT OK

Exemplo de log de conexão REJEITADA (por SG ou NACL):
2 123456789 eni-abc 10.0.1.50 10.0.10.100 52341 5432 6 1 40 1609459200 1609459260 REJECT OK

Diagnóstico via Flow Logs:
  REJECT na ENI de destino → NACL da subnet de destino bloqueando
  REJECT na ENI de origem  → SG ou NACL da subnet de origem bloqueando
  ACCEPT mas sem resposta  → SG está ok, problema na aplicação (não está ouvindo)
  Sem log algum            → Pacote nem chegou na ENI → problema de roteamento
```

```bash
# Consultar Flow Logs no CloudWatch Logs Insights
# (substituir /vpc/flow-logs pelo seu log group)
aws logs start-query \
  --log-group-name /vpc/flow-logs \
  --start-time $(date -d '1 hour ago' +%s) \
  --end-time $(date +%s) \
  --query-string '
    fields @timestamp, srcAddr, dstAddr, srcPort, dstPort, action
    | filter dstAddr = "10.0.10.100" and dstPort = 5432
    | sort @timestamp desc
    | limit 50
  '
```

## Segurança adicional — SGs com AWS Security Hub e GuardDuty

```
AWS Security Hub detecta automaticamente:
  → SGs com SSH/RDP aberto para a internet
  → SGs com portas de banco expostas
  → Mudanças em SGs de recursos críticos

Amazon GuardDuty analisa VPC Flow Logs e detecta:
  → Port scanning de IPs na sua VPC
  → Conexões para IPs conhecidos como maliciosos
  → Padrões de exfiltração de dados (ex: alto volume de saída HTTPS)

AWS CloudTrail registra:
  → Toda alteração em Security Groups (AuthorizeSecurityGroupIngress, etc.)
  → Quem fez a mudança, quando, de qual IP
  → Base para auditoria e resposta a incidentes
```

## Template de Security Groups para arquitetura 3-tier

```bash
# Script completo para criar SGs de uma arquitetura 3-tier

VPC_ID="vpc-0abc123"
OFFICE_IP="203.0.113.10/32"  # IP do escritório para SSH

# ALB SG
aws ec2 create-security-group --vpc-id $VPC_ID \
  --group-name sg-alb --description "ALB: internet → porta 443/80"
SG_ALB=$(aws ec2 describe-security-groups \
  --filters Name=group-name,Values=sg-alb Name=vpc-id,Values=$VPC_ID \
  --query 'SecurityGroups[0].GroupId' --output text)
aws ec2 authorize-security-group-ingress --group-id $SG_ALB \
  --protocol tcp --port 443 --cidr 0.0.0.0/0 \
  --tag-specifications 'ResourceType=security-group-rule,Tags=[{Key=Description,Value="HTTPS da internet"}]'
aws ec2 authorize-security-group-ingress --group-id $SG_ALB \
  --protocol tcp --port 80 --cidr 0.0.0.0/0

# App SG
aws ec2 create-security-group --vpc-id $VPC_ID \
  --group-name sg-app --description "App tier: recebe do ALB, acessa DB e cache"
SG_APP=$(aws ec2 describe-security-groups \
  --filters Name=group-name,Values=sg-app Name=vpc-id,Values=$VPC_ID \
  --query 'SecurityGroups[0].GroupId' --output text)
aws ec2 authorize-security-group-ingress --group-id $SG_APP \
  --protocol tcp --port 8080 --source-group $SG_ALB

# DB SG
aws ec2 create-security-group --vpc-id $VPC_ID \
  --group-name sg-db --description "RDS PostgreSQL: apenas do tier app"
SG_DB=$(aws ec2 describe-security-groups \
  --filters Name=group-name,Values=sg-db Name=vpc-id,Values=$VPC_ID \
  --query 'SecurityGroups[0].GroupId' --output text)
aws ec2 authorize-security-group-ingress --group-id $SG_DB \
  --protocol tcp --port 5432 --source-group $SG_APP

# Bastion SG
aws ec2 create-security-group --vpc-id $VPC_ID \
  --group-name sg-bastion --description "Bastion: SSH apenas do escritório"
SG_BASTION=$(aws ec2 describe-security-groups \
  --filters Name=group-name,Values=sg-bastion Name=vpc-id,Values=$VPC_ID \
  --query 'SecurityGroups[0].GroupId' --output text)
aws ec2 authorize-security-group-ingress --group-id $SG_BASTION \
  --protocol tcp --port 22 --cidr $OFFICE_IP

# Permitir SSH do bastion para o app tier
aws ec2 authorize-security-group-ingress --group-id $SG_APP \
  --protocol tcp --port 22 --source-group $SG_BASTION

echo "SGs criados: ALB=$SG_ALB, App=$SG_APP, DB=$SG_DB, Bastion=$SG_BASTION"
```

## 🧩 Quiz de Fixação

1. Um time usa a regra `TCP 0-65535 from 10.0.0.0/16` no SG de um banco de dados RDS "para simplificar". Quais são os dois principais problemas de segurança dessa abordagem comparada com `TCP 5432 from sg-app`?

2. Um desenvolvedor reclamou que não consegue fazer SSH na instância EC2 de produção. A instância tem `sg-app` com regras: Inbound `TCP 8080 from sg-alb`. O bastion host tem `sg-bastion` com Inbound `TCP 22 from 0.0.0.0/0`. Usando o fluxo de diagnóstico, liste os 3 problemas nessa configuração.

3. Os VPC Flow Logs mostram `ACCEPT` para tráfego TCP da instância de app (10.0.1.50) para o banco RDS (10.0.10.100:5432), mas a aplicação continua retornando "Connection refused". O que isso indica sobre onde está o problema real, e como confirmar?

**Respostas:**

1) **Problema 1 — Escopo excessivo de portas:** `TCP 0-65535` permite que qualquer recurso na VPC tente conectar em *qualquer porta* do RDS — incluindo porta de administração (22/SSH se um agent estiver rodando), porta de métricas, porta de replicação, etc. Um atacante que comprometer qualquer instância na VPC (`10.0.0.0/16`) pode tentar explorar qualquer porta do banco. Com `TCP 5432 from sg-app`, apenas a porta PostgreSQL específica é acessível. **Problema 2 — Escopo excessivo de origem:** `10.0.0.0/16` autoriza *qualquer recurso da VPC* — incluindo servidores de outros times, instâncias de desenvolvimento, ferramentas de monitoramento, lambdas, etc. Se qualquer uma dessas instâncias for comprometida, o atacante tem acesso direto ao banco. Com `from sg-app`, apenas instâncias explicitamente no papel de "aplicação" têm acesso — um atacante comprometendo um servidor de dev não consegue alcançar o banco de produção.

2) **Problema 1 — `sg-app` não tem regra inbound para SSH do bastion:** a instância EC2 tem apenas `TCP 8080 from sg-alb`. Para o desenvolvedor fazer SSH via bastion, seria necessário adicionar `TCP 22 from sg-bastion` no `sg-app`. **Problema 2 — Bastion com SSH aberto para a internet inteira (`0.0.0.0/0`):** o bastion deveria ter `TCP 22 from <IP do escritório>/32` ou `from <IP da VPN>/32` — nunca `0.0.0.0/0` em portas administrativas. Isso expõe o bastion a ataques de força bruta de qualquer IP do mundo. **Problema 3 — Implicitamente: o desenvolvedor não tem como chegar à instância de app sem primeiro passar pelo bastion:** se o fluxo correto é Desenvolvedor → Bastion → App, então o bastion deve ter acesso SSH para a instância de app, e a instância de app deve ter `TCP 22 from sg-bastion`. Sem essa regra, o SSH do bastion para a app também não funciona.

3) O `ACCEPT` no Flow Log indica que o **Security Group e as NACLs estão permitindo o tráfego** — o pacote chega ao RDS. "Connection refused" na porta 5432 significa que o **processo PostgreSQL não está aceitando conexões**, não que o firewall está bloqueando. Causas possíveis: (a) o RDS está com status diferente de "available" — verificar no console/AWS CLI; (b) o PostgreSQL está configurado para aceitar conexões apenas de IPs específicos no `pg_hba.conf` — verificar configuração de autenticação; (c) o banco de dados específico não existe ou a credencial está errada (erro de aplicação, não de rede). **Como confirmar:** fazer `nc -zv 10.0.10.100 5432` de dentro da instância de app — se retornar `Connection refused` (não `Connection timed out`), confirma que o pacote chegou mas foi rejeitado pela aplicação. `Timed out` indicaria bloqueio de rede (SG/NACL/roteamento). Verificar também os logs do RDS no CloudWatch para ver se há tentativas de conexão chegando com erro de autenticação.
