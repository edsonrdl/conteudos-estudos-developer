### Security Groups — stateful, regras de ingresso e egresso, referência entre SGs e o default SG

O Security Group (SG) é o firewall virtual que controla o tráfego para e a partir de recursos AWS na VPC — instâncias EC2, interfaces de rede (ENIs), instâncias RDS, funções Lambda em VPC e outros. É o mecanismo de segurança de rede mais usado na AWS e opera no nível da instância (não da subnet — esse papel é das NACLs). Sua característica mais importante é ser **stateful**: respostas a conexões permitidas passam automaticamente, sem precisar de regra de retorno explícita.

---

## O que é "stateful" — a diferença que tudo muda

```
Firewall STATELESS (NACLs):
  Cada pacote é avaliado independentemente
  
  Conexão TCP: Client → EC2 na porta 443
  
  Pacote de ida:  Client:54321 → EC2:443  → avaliado pela regra inbound
  Pacote de volta: EC2:443 → Client:54321 → avaliado pela regra outbound
  
  Para funcionar: precisa de regra INBOUND permitindo 443
                  E regra OUTBOUND permitindo a porta efêmera do client

Firewall STATEFUL (Security Groups):
  O SG rastreia o estado das conexões
  
  Conexão TCP: Client → EC2 na porta 443
  
  Pacote de ida:  Client:54321 → EC2:443  → avaliado pela regra inbound ✓
  Pacote de volta: EC2:443 → Client:54321 → AUTOMATICAMENTE PERMITIDO
  
  Apenas a regra INBOUND é necessária — o retorno é implícito
  Não importa se há regra outbound bloqueando porta efêmera
```

**Consequência prática:** Security Groups são muito mais simples de configurar que NACLs — você só precisa pensar em "quem pode iniciar conexões", não em "quem pode responder".

## Estrutura de uma regra de Security Group

```
Componentes de uma regra:

Tipo:         Protocolo de aplicação (SSH, HTTP, HTTPS, etc.) ou Custom
Protocolo:    TCP, UDP, ICMP, All
Porta:        Porta única (22), range (8080-8090), ou All (0-65535)
Origem/Destino: Um de:
  → CIDR IPv4:     10.0.0.0/8, 0.0.0.0/0
  → CIDR IPv6:     ::/0, 2001:db8::/32
  → Security Group: sg-0abc123 (referência a outro SG)
  → Prefix List:   pl-xxxxxxxx (lista de CIDRs gerenciada)
Descrição:    Texto livre para documentar o propósito
```

## Regras de Ingresso (Inbound) vs Egresso (Outbound)

```
Inbound rules — quem pode ENTRAR:
  Controla conexões INICIADAS por fontes externas em direção ao recurso
  
  Exemplos:
  TCP 443 from 0.0.0.0/0    → qualquer cliente HTTPS pode conectar
  TCP 22  from 10.0.0.0/8   → SSH apenas da rede interna
  TCP 5432 from sg-app       → PostgreSQL apenas do SG da camada app

Outbound rules — quem pode SAIR:
  Controla conexões INICIADAS pelo recurso em direção a destinos externos
  
  Default: All traffic to 0.0.0.0/0 (egress totalmente livre)
  
  Exemplos de restrição:
  TCP 5432 to sg-db          → instância app só pode sair para o banco
  TCP 443 to 0.0.0.0/0       → apenas HTTPS para a internet
  All traffic to 10.0.0.0/16 → apenas tráfego interno à VPC

Stateful — como as regras inbound e outbound interagem:
  Conexão iniciada externamente (inbound):
    → Avaliada apenas pelo inbound rule
    → Resposta passa automaticamente (sem consultar outbound)
  
  Conexão iniciada pelo recurso (outbound):
    → Avaliada apenas pelo outbound rule
    → Resposta passa automaticamente (sem consultar inbound)
```

## Referência entre Security Groups — o recurso mais poderoso

Em vez de especificar um CIDR (IP fixo), você pode referenciar **outro Security Group** como origem ou destino de uma regra. Isso desacopla a segurança dos IPs — que são efêmeros em ambientes dinâmicos:

```
Por que referência entre SGs é superior a CIDR:

Cenário: camada app precisa acessar banco PostgreSQL

Opção CIDR (frágil):
  Inbound no SG-db:
  TCP 5432 from 10.0.10.0/24   ← CIDR da subnet de app
  
  Problema: novos pods/instâncias em outras subnets não têm acesso
            Escalar app para outra AZ requer atualizar a regra
            Qualquer recurso na subnet 10.0.10.0/24 acessa o banco

Opção referência de SG (robusta):
  Inbound no SG-db:
  TCP 5432 from sg-app           ← qualquer instância com sg-app
  
  Vantagem: funciona independente de qual IP ou subnet a instância está
            Scale out automático: novo pod com sg-app → acesso imediato
            Apenas recursos explicitamente com sg-app têm acesso
```

```bash
# Criando regras com referência entre SGs
# SG do banco: permitir PostgreSQL apenas do SG de aplicação
aws ec2 authorize-security-group-ingress \
  --group-id sg-db-0abc123 \
  --protocol tcp \
  --port 5432 \
  --source-group sg-app-0def456

# SG da aplicação: permitir HTTPS da internet
aws ec2 authorize-security-group-ingress \
  --group-id sg-app-0def456 \
  --protocol tcp \
  --port 443 \
  --cidr 0.0.0.0/0

# Ver todas as regras de um SG
aws ec2 describe-security-groups \
  --group-ids sg-db-0abc123 \
  --query 'SecurityGroups[0].{
    Name:GroupName,
    Ingress:IpPermissions,
    Egress:IpPermissionsEgress
  }'
```

### Self-reference — o SG referenciando a si mesmo

Um SG pode referenciar a si próprio nas regras, permitindo comunicação livre entre todos os recursos que compartilham aquele SG:

```yaml
# SG-cluster: permite comunicação livre entre membros do cluster
Inbound:
  All traffic from sg-cluster  ← o próprio SG como origem

Resultado:
  EC2-node-1 (sg-cluster) → EC2-node-2 (sg-cluster): PERMITIDO
  EC2-node-2 (sg-cluster) → EC2-node-3 (sg-cluster): PERMITIDO
  EC2-externo (sg-outro)  → EC2-node-1 (sg-cluster): NEGADO

Uso típico:
  → Clusters de banco de dados (nós Cassandra, Redis Cluster)
  → Clusters EKS/ECS (comunicação entre pods/tasks do mesmo serviço)
  → Grupos de instâncias que formam um "tier" e precisam se comunicar
```

## O Security Group default

Cada VPC tem um **Security Group default** criado automaticamente. Ele tem comportamento peculiar que frequentemente causa confusão:

```
Security Group default (comportamento padrão):

Inbound:
  All traffic | Source: sg-default (self-reference)
  → Apenas recursos no mesmo SG default podem iniciar conexões

Outbound:
  All traffic | Destination: 0.0.0.0/0
  → Saída totalmente livre para qualquer destino

Implicação:
  Instância A (sg-default) → Instância B (sg-default): PERMITIDO
  Instância A (sg-default) → Instância C (sg-outro):   NEGADO (sem regra inbound em C)
  Instância A (sg-default) → 8.8.8.8 (internet):       PERMITIDO (outbound livre)
```

### Por que NÃO usar o Security Group default em produção

```
Problemas do SG default:

1. Auto-referência inclusiva:
   Qualquer recurso "avulso" que alguém coloque no SG default
   automaticamente pode se comunicar com todos os outros no SG default.
   Sem consciência de quem está no mesmo SG.

2. Egress totalmente aberto:
   Recursos podem fazer chamadas para qualquer destino na internet.
   Dificulta auditoria de tráfego de saída.

3. Falta de granularidade e documentação:
   Sem descrições, sem separação por serviço, sem princípio do menor privilégio.

Boa prática:
  → Criar SGs específicos por serviço (sg-alb, sg-api, sg-db, sg-cache)
  → Documentar cada regra com descrição clara
  → Remover todas as regras do SG default (ou não usar)
  → Nunca usar o SG default como "SG temporário para testar"
```

## Criação e gerenciamento de Security Groups

```bash
# Criar Security Group
aws ec2 create-security-group \
  --group-name "sg-api-backend" \
  --description "API backend: recebe do ALB, acessa banco e cache" \
  --vpc-id vpc-0abc123 \
  --tag-specifications 'ResourceType=security-group,Tags=[
    {Key=Name,Value=sg-api-backend},
    {Key=Service,Value=api},
    {Key=Environment,Value=production}
  ]'

# Adicionar regra inbound
aws ec2 authorize-security-group-ingress \
  --group-id sg-api-0abc123 \
  --ip-permissions '[{
    "IpProtocol": "tcp",
    "FromPort": 8080,
    "ToPort": 8080,
    "UserIdGroupPairs": [{"GroupId": "sg-alb-0def456"}],
    "IpRanges": [],
    "Description": "Receber do ALB apenas"
  }]'

# Adicionar regra outbound restrita (remover o default All)
aws ec2 revoke-security-group-egress \
  --group-id sg-api-0abc123 \
  --ip-permissions '[{"IpProtocol": "-1", "IpRanges": [{"CidrIp": "0.0.0.0/0"}]}]'

aws ec2 authorize-security-group-egress \
  --group-id sg-api-0abc123 \
  --ip-permissions '[
    {
      "IpProtocol": "tcp",
      "FromPort": 5432,
      "ToPort": 5432,
      "UserIdGroupPairs": [{"GroupId": "sg-db-0ghi789"}]
    },
    {
      "IpProtocol": "tcp",
      "FromPort": 6379,
      "ToPort": 6379,
      "UserIdGroupPairs": [{"GroupId": "sg-cache-0jkl012"}]
    },
    {
      "IpProtocol": "tcp",
      "FromPort": 443,
      "ToPort": 443,
      "IpRanges": [{"CidrIp": "0.0.0.0/0", "Description": "HTTPS para APIs externas"}]
    }
  ]'
```

## Limites dos Security Groups

| Recurso | Limite padrão | Aumentável |
|---|---|---|
| SGs por VPC | 2.500 | Sim |
| Regras inbound por SG | 60 | Sim (até 1.000) |
| Regras outbound por SG | 60 | Sim (até 1.000) |
| SGs por interface de rede (ENI) | 5 | Sim (até 16) |
| Referências a SGs de outras contas | Apenas via VPC Peering ou Shared VPC | — |

**Limite de regras × SGs por ENI:** o número total de regras aplicadas a uma ENI = (número de SGs) × (regras por SG). AWS limita a 1.000 regras totais por ENI. Com 5 SGs e 200 regras cada = 1.000 regras — no limite.

## Erros comuns e armadilhas

**Confundir inbound com outbound para conexões TCP:** uma conexão HTTP do browser para a EC2 é **inbound** (chega na porta 80/443 da EC2). A resposta HTTP é **automaticamente permitida** pelo stateful — sem precisar de regra outbound para portas efêmeras. Muitos beginners adicionam regras outbound desnecessárias por não entender o stateful.

**Usar CIDR de subnet em vez de referência de SG:** `TCP 5432 from 10.0.10.0/24` autoriza qualquer recurso na subnet, incluindo instâncias que não deveriam ter acesso ao banco. `TCP 5432 from sg-app` autoriza apenas instâncias explicitamente no sg-app.

**Deixar o outbound default (All traffic 0.0.0.0/0):** adequado para simplificar, mas remove visibilidade sobre o que o serviço pode contactar. Para compliance e Zero Trust, restringir o outbound ao necessário.

**Acreditar que "sem regra inbound = seguro" sempre:** se há uma regra outbound permitindo tráfego para um destino, e esse destino inicia uma conexão de retorno (resposta), ela passa. Um serviço comprometido pode exfiltrar dados usando conexões de saída se o outbound não estiver restrito.

## 🧩 Quiz de Fixação

1. Uma instância EC2 tem 2 Security Groups: SG-A com `Inbound: TCP 443 from 0.0.0.0/0` e SG-B com `Inbound: Deny all` (sem regras). Um cliente tenta conectar na porta 443. O acesso é permitido? Por que Security Groups não têm regras de "Deny" explícitas?

2. Um banco RDS PostgreSQL tem a regra: `Inbound: TCP 5432 from sg-app`. O time escala a camada de aplicação para uma nova AZ com subnets /24 diferentes e novas instâncias com sg-app associado. As novas instâncias conseguem acessar o banco imediatamente, sem nenhuma mudança de configuração? Por que?

3. Uma instância EC2 (sg-servidor) tem apenas uma regra outbound: `TCP 443 to 0.0.0.0/0`. Um cliente externo tenta conectar SSH (porta 22) na instância. O SG do servidor não tem regra inbound para SSH. O cliente consegue conectar? E se o servidor tentar fazer SSH para outra instância?

**Respostas:**

1) O acesso na porta 443 é **permitido**. Security Groups usam **Allow-only** — não existe regra de Deny explícita. Quando múltiplos SGs estão associados a uma ENI, as regras de todos são **combinadas em uma união (OR lógico)**: se *qualquer* SG permite o tráfego, ele passa. SG-A permite TCP 443 → combinado com SG-B (sem regras inbound) → resultado: TCP 443 permitido. **Por que não há Deny explícito:** o modelo de Security Group é baseado em whitelist — tudo é negado por padrão, e você adiciona apenas o que quer permitir. Isso torna as regras mais simples e menos propensas a erros (sem conflito entre Allow e Deny). Para Deny explícito no nível de rede, use NACLs (que suportam regras numbered com Allow e Deny).

2) **Sim, imediatamente, sem nenhuma mudança.** Essa é exatamente a vantagem da referência entre Security Groups. A regra `from sg-app` significa "qualquer recurso que tenha o Security Group `sg-app` associado", independente de qual IP, subnet ou AZ esse recurso está. Quando as novas instâncias são lançadas com `sg-app` associado — mesmo em subnets /24 diferentes em outra AZ — elas imediatamente satisfazem a condição da regra do RDS. Se a regra fosse `from 10.0.10.0/24` (CIDR da subnet original), as novas instâncias em `10.0.15.0/24` não teriam acesso sem modificar a regra — demonstrando por que referência de SG é superior a CIDR em ambientes dinâmicos.

3) **Conexão SSH de fora (cliente → servidor, porta 22):** NÃO consegue. A instância não tem regra inbound para TCP 22. Security Groups são stateful — mas o stateful só se aplica à *resposta* de uma conexão que foi *permitida* na avaliação inicial. Como não há regra inbound para porta 22, a tentativa de conexão é bloqueada logo na avaliação inbound. A regra outbound `TCP 443` não tem relação com conexões de entrada. **SSH de saída (servidor → outra instância, porta 22):** SIM consegue iniciar, desde que a outra instância tenha uma regra inbound permitindo TCP 22 do SG do servidor. A regra outbound `TCP 443 to 0.0.0.0/0` *não* permite saída na porta 22 — mas o stateful significa que a *resposta* da conexão SSH saindo (porta 22 saindo) seria bloqueada pela ausência de regra outbound para porta 22. Para SSH de saída funcionar, precisaria de regra outbound `TCP 22 to destino`.
