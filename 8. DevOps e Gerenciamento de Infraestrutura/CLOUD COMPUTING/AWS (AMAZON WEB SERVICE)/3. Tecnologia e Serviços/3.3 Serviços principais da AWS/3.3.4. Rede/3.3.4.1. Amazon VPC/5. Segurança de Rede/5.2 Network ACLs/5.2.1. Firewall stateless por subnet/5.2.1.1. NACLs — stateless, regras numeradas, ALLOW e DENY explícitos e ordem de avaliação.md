### NACLs — stateless, regras numeradas, ALLOW e DENY e ordem de avaliação

As Network Access Control Lists (NACLs) são o firewall de rede que opera no nível da subnet, em contraste com os Security Groups que operam no nível da instância. Enquanto os SGs são stateful e só precisam de regras em uma direção, as NACLs são **stateless** — cada pacote, incluindo as respostas TCP, é avaliado independentemente contra as regras. Isso as torna mais complexas de configurar corretamente, mas também mais poderosas em cenários que requerem Deny explícito.

---

## O modelo stateless — por que muda tudo

```
Security Group (stateful):
  Regra inbound: TCP 443 from 0.0.0.0/0
  → Pacote de entrada na porta 443: ACEITO (match na regra)
  → Pacote de resposta (saída): ACEITO AUTOMATICAMENTE (estado rastreado)
  Você só precisa da regra inbound.

NACL (stateless):
  Regra inbound:  #100 TCP 443 from 0.0.0.0/0 → ALLOW
  → Pacote de entrada na porta 443: ACEITO (match na regra 100)
  → Pacote de resposta (saída): avaliado INDEPENDENTEMENTE nas regras outbound
  
  Se não houver regra outbound para a porta efêmera do cliente:
  → Resposta BLOQUEADA → conexão parece travar do lado do cliente

Implicação crítica:
  Para uma conexão TCP funcionar com NACLs, você precisa de:
  → Regra inbound permitindo a porta de serviço (ex: 443)
  → Regra outbound permitindo portas efêmeras (1024-65535)
    (ou a porta específica de retorno)
```

### Portas efêmeras — o conceito que mais confunde

```
Portas efêmeras (ephemeral ports):
  Quando um cliente inicia uma conexão TCP, o SO escolhe aleatoriamente
  uma porta de origem no range efêmero para aquela conexão.
  
  Linux:    32768-60999 (padrão moderno)
  Windows:  49152-65535
  AWS NACLs: recomenda usar 1024-65535 para cobrir todos os casos
  
  Exemplo: cliente web em 203.0.113.5:52341 → servidor em 10.0.1.50:443
  
  No servidor (porta 443):
    Inbound: TCP 443 from 0.0.0.0/0 → ALLOW ✓
    Outbound: TCP 52341 to 203.0.113.5 → precisa de regra para 1024-65535
  
  Na subnet do servidor:
    NACL inbound:  #100 TCP 443 from 0.0.0.0/0 → ALLOW
    NACL outbound: #100 TCP 1024-65535 to 0.0.0.0/0 → ALLOW
                            ^^^^^^^^^^^^^ range efêmero
```

## Estrutura de uma NACL

Cada VPC tem uma **NACL default** criada automaticamente. Você pode criar NACLs customizadas e associá-las a subnets específicas:

```
NACL — componentes:

Número da regra:  1-32766 (menor número = avaliado primeiro)
                  32767 = "*" (regra de negação implícita — não editável)
Tipo:             protocolo de aplicação (SSH, HTTP, etc.) ou Custom
Protocolo:        TCP, UDP, ICMP, All (número -1)
Porto range:      porta única ou range (ex: 1024-65535)
Origem/Destino:   CIDR apenas (0.0.0.0/0, 10.0.0.0/16, etc.)
                  NACLs NÃO suportam referência a Security Groups!
Ação:             ALLOW ou DENY
```

---

## A regra implícita de DENY ALL

Toda NACL tem uma **regra * (asterisco)** que nunca pode ser modificada ou removida:

```
Regra implícita (sempre presente, não visível no console como editável):
  #*   All traffic   All   0.0.0.0/0   DENY

Significado:
  Se um pacote não corresponde a NENHUMA regra numerada anterior,
  ele é NEGADO pela regra *.

A avaliação para na PRIMEIRA regra que corresponde ao pacote.
Uma vez que uma regra faz match, as regras subsequentes são ignoradas.
```

---

## NACL Default vs NACL Customizada

```
NACL Default (criada automaticamente com a VPC):
  Inbound:
    #100  All traffic  All  0.0.0.0/0  ALLOW
    #*    All traffic  All  0.0.0.0/0  DENY
    
  Outbound:
    #100  All traffic  All  0.0.0.0/0  ALLOW
    #*    All traffic  All  0.0.0.0/0  DENY
  
  Resultado: permite tudo — segurança delegada aos Security Groups
  
  Por que a AWS permite tudo por padrão?
  → Evitar que iniciantes travem instâncias inadvertidamente
  → SGs já fornecem proteção suficiente para a maioria dos casos

NACL Customizada (criada por você):
  Inbound:  apenas #* DENY (nada permitido inicialmente)
  Outbound: apenas #* DENY (nada permitido inicialmente)
  
  Você DEVE adicionar as regras necessárias explicitamente
```

## Criando e configurando NACLs

```bash
# Criar NACL customizada
aws ec2 create-network-acl \
  --vpc-id vpc-0abc123 \
  --tag-specifications 'ResourceType=network-acl,Tags=[{Key=Name,Value=nacl-subnet-publica}]'

# Adicionar regras inbound
# Regra 100: permitir HTTPS de qualquer IP
aws ec2 create-network-acl-entry \
  --network-acl-id acl-0abc123 \
  --ingress \
  --rule-number 100 \
  --protocol tcp \
  --rule-action allow \
  --cidr-block 0.0.0.0/0 \
  --port-range From=443,To=443

# Regra 110: permitir HTTP
aws ec2 create-network-acl-entry \
  --network-acl-id acl-0abc123 \
  --ingress \
  --rule-number 110 \
  --protocol tcp \
  --rule-action allow \
  --cidr-block 0.0.0.0/0 \
  --port-range From=80,To=80

# Regra 120: permitir portas efêmeras (respostas de saída iniciadas pela instância)
aws ec2 create-network-acl-entry \
  --network-acl-id acl-0abc123 \
  --ingress \
  --rule-number 120 \
  --protocol tcp \
  --rule-action allow \
  --cidr-block 0.0.0.0/0 \
  --port-range From=1024,To=65535

# Adicionar regras outbound
# Regra 100: permitir HTTPS de saída (para APIs externas)
aws ec2 create-network-acl-entry \
  --network-acl-id acl-0abc123 \
  --egress \
  --rule-number 100 \
  --protocol tcp \
  --rule-action allow \
  --cidr-block 0.0.0.0/0 \
  --port-range From=443,To=443

# Regra 110: permitir portas efêmeras de saída (respostas para clientes externos)
aws ec2 create-network-acl-entry \
  --network-acl-id acl-0abc123 \
  --egress \
  --rule-number 110 \
  --protocol tcp \
  --rule-action allow \
  --cidr-block 0.0.0.0/0 \
  --port-range From=1024,To=65535

# Associar a subnet à NACL customizada
aws ec2 replace-network-acl-association \
  --association-id aclassoc-0abc123 \
  --network-acl-id acl-0abc123
```

## DENY explícito — a vantagem das NACLs sobre SGs

A característica mais poderosa das NACLs é poder **bloquear explicitamente** tráfego, independente do que os Security Groups permitam. SGs são allow-only — se qualquer SG permite, o tráfego passa. NACLs podem negar antes mesmo do SG ser consultado:

```
Caso de uso de DENY explícito:

Cenário: IP 203.0.113.50 está fazendo ataques ou scraping abusivo.
Você quer bloqueá-lo imediatamente.

Com apenas Security Groups:
  Impossível! SGs não têm Deny explícito.
  Você teria que remover regras de ALLOW, o que afetaria outros IPs também.

Com NACL:
  aws ec2 create-network-acl-entry \
    --network-acl-id acl-0abc123 \
    --ingress \
    --rule-number 50 \  ← número menor que as regras ALLOW (avaliado primeiro)
    --protocol -1 \
    --rule-action deny \
    --cidr-block 203.0.113.50/32

  Resultado:
    #50   All  -1  203.0.113.50/32  DENY   ← bloqueia primeiro
    #100  TCP  443 0.0.0.0/0        ALLOW  ← outros IPs ainda passam
    #*    All  -1  0.0.0.0/0        DENY
```

## Exemplo completo — NACL para subnet pública

```
NACL da subnet pública (ALB + NAT Gateway):

Inbound rules:
  #100  TCP  80     0.0.0.0/0         ALLOW  ← HTTP público
  #110  TCP  443    0.0.0.0/0         ALLOW  ← HTTPS público
  #120  TCP  1024-65535  0.0.0.0/0   ALLOW  ← respostas efêmeras de saída
  #130  TCP  22     203.0.113.0/24   ALLOW  ← SSH da rede corporativa
  #999  All  -1     203.0.113.100/32 DENY   ← bloquear IP específico problemático
  #*    All  -1     0.0.0.0/0        DENY   ← tudo mais negado

Outbound rules:
  #100  TCP  80     0.0.0.0/0         ALLOW  ← HTTP para internet
  #110  TCP  443    0.0.0.0/0         ALLOW  ← HTTPS para internet
  #120  TCP  1024-65535  0.0.0.0/0   ALLOW  ← respostas efêmeras para clientes
  #130  TCP  8080   10.0.10.0/24     ALLOW  ← encaminhar para subnet privada
  #*    All  -1     0.0.0.0/0        DENY
```

## NACL para subnet privada

```
NACL da subnet privada (instâncias de aplicação):

Inbound rules:
  #100  TCP  8080   10.0.1.0/24     ALLOW  ← do ALB na subnet pública
  #110  TCP  22     10.0.0.0/24     ALLOW  ← SSH do bastion
  #120  TCP  1024-65535 0.0.0.0/0  ALLOW  ← respostas de saídas (NAT retorna)
  #*    All  -1     0.0.0.0/0       DENY

Outbound rules:
  #100  TCP  5432   10.0.20.0/24   ALLOW  ← PostgreSQL para subnet de dados
  #110  TCP  6379   10.0.20.0/24   ALLOW  ← Redis para subnet de dados
  #120  TCP  443    0.0.0.0/0      ALLOW  ← HTTPS via NAT para internet
  #130  TCP  1024-65535 10.0.0.0/16 ALLOW ← respostas efêmeras para ALB
  #*    All  -1     0.0.0.0/0       DENY
```

## Ordem de avaliação — exemplos práticos

```
NACL com regras conflitantes — qual vence?

Inbound:
  #50   TCP  22  10.0.5.0/24   DENY   ← nega SSH de uma subnet específica
  #100  TCP  22  10.0.0.0/16  ALLOW  ← permite SSH de toda a VPC

Pacote: SSH de 10.0.5.50 (que está em 10.0.5.0/24 E em 10.0.0.0/16):
  Avalia #50:  10.0.5.50 está em 10.0.5.0/24? SIM → DENY
  Regra #100 nunca é avaliada (parou no #50)
  Resultado: NEGADO

Pacote: SSH de 10.0.8.30 (que está em 10.0.0.0/16 mas NÃO em 10.0.5.0/24):
  Avalia #50:  10.0.8.30 está em 10.0.5.0/24? NÃO → continua
  Avalia #100: 10.0.8.30 está em 10.0.0.0/16? SIM → ALLOW
  Resultado: PERMITIDO
```

## Modificar regras vs substituir regras

Na NACL, **você não pode editar uma regra existente** — você deve deletar e recriar:

```bash
# Alterar uma regra: deletar e recriar com o mesmo número

# Deletar regra 100 inbound
aws ec2 delete-network-acl-entry \
  --network-acl-id acl-0abc123 \
  --ingress \
  --rule-number 100

# Recriar com a nova configuração
aws ec2 create-network-acl-entry \
  --network-acl-id acl-0abc123 \
  --ingress \
  --rule-number 100 \
  --protocol tcp \
  --rule-action allow \
  --cidr-block 10.0.0.0/16 \  ← novo CIDR
  --port-range From=443,To=443

# Boa prática: deixar gaps nos números para inserir regras depois
# #100, #200, #300 em vez de #100, #101, #102
# Permite inserir #150 entre #100 e #200 sem renumerar tudo
```

## Limites das NACLs

| Recurso | Limite |
|---|---|
| NACLs por VPC | 200 |
| Regras por NACL (inbound + outbound) | 20 (padrão) / 40 (máximo com suporte) |
| Subnets por NACL | Ilimitado |
| NACLs por subnet | 1 (apenas uma NACL por vez) |

O limite de **20 regras** é muito mais restritivo que os 60 dos Security Groups. Em NACLs complexas, planeje as regras cuidadosamente para não esgotar o limite.

## Erros comuns e armadilhas

**Esquecer as portas efêmeras:** o erro mais frequente com NACLs. Configurar regras inbound para as portas de serviço mas esquecer a regra outbound para 1024-65535 faz com que as respostas sejam bloqueadas — a conexão parece "travar" ou "timeout" sem motivo aparente.

**Usar números de regra sem gaps:** criar regras como #100, #101, #102 sem espaço. Quando precisar inserir uma regra de DENY para um IP específico com número menor (para executar antes), precisará renumerar todas as regras.

**NACLs são stateless mas SGs são stateful — confundir os dois:** ao debugar um problema de conectividade, lembre-se que NACLs exigem regras em AMBAS as direções (inbound E outbound) para uma conexão TCP funcionar. Um engenheiro que aplica lógica de SG (só precisa de uma direção) às NACLs vai sempre ter problemas.

**Regra de DENY depois de ALLOW para o mesmo CIDR:** se #100 tem ALLOW para 10.0.0.0/8 e #200 tem DENY para 10.0.5.0/24, o DENY nunca é avaliado para tráfego de 10.0.5.x — porque #100 já fez match. O DENY precisa ter número MENOR que o ALLOW para o CIDR mais específico.

## 🧩 Quiz de Fixação

1. Uma NACL de subnet pública tem: `#100 TCP 443 from 0.0.0.0/0 ALLOW` (inbound) e `#100 TCP 443 to 0.0.0.0/0 ALLOW` (outbound). Um usuário tenta acessar um site HTTPS hospedado na instância (porta 443) mas recebe timeout. O que está faltando e por quê?

2. Uma NACL tem as regras inbound: `#50 TCP 22 from 10.0.5.0/24 DENY` e `#100 All traffic from 0.0.0.0/0 ALLOW`. Um atacante de IP `10.0.5.100` tenta SSH. Qual regra se aplica? E um usuário legítimo de `10.0.8.50` tenta SSH — qual regra se aplica?

3. Você precisa bloquear emergencialmente o IP `45.33.32.156` que está fazendo port scanning na sua subnet pública, sem afetar outros usuários. Qual é a solução correta com NACL e por que Security Groups não são suficientes para isso?

**Respostas:**

1) **Falta a regra outbound para portas efêmeras**. O fluxo é: cliente (ex: 203.0.113.5:**52341**) → servidor (porta **443**). A NACL inbound permite pacotes chegando na porta 443 (regra #100). Mas a **resposta** sai da porta 443 do servidor para a **porta efêmera 52341** do cliente. A NACL outbound só permite `TCP 443` — não cobre a porta 52341 (que está no range efêmero 1024-65535). Resultado: o SYN-ACK e os dados de resposta são bloqueados pela NACL outbound, o cliente nunca recebe confirmação e o TCP sofre timeout. **Solução:** adicionar regra outbound `#110 TCP 1024-65535 to 0.0.0.0/0 ALLOW` para permitir as respostas às conexões iniciadas pelos clientes.

2) Para o atacante `10.0.5.100`: avalia regra **#50** — `10.0.5.100` está em `10.0.5.0/24`? **SIM** → **DENY**. A regra #100 nunca é avaliada. SSH bloqueado. Para o usuário `10.0.8.50`: avalia regra **#50** — `10.0.8.50` está em `10.0.5.0/24`? NÃO → continua. Avalia regra **#100** — `10.0.8.50` está em `0.0.0.0/0`? SIM → **ALLOW**. SSH permitido. Este é o padrão clássico de usar NACL para isolar uma subnet específica dentro de um CIDR maior: o DENY específico (#50) tem precedência para a subnet bloqueada, enquanto o ALLOW genérico (#100) cobre o resto.

3) **Solução com NACL:** criar uma regra DENY com número menor que qualquer regra ALLOW existente:
```bash
aws ec2 create-network-acl-entry \
  --network-acl-id acl-xxx --ingress \
  --rule-number 10 --protocol -1 \
  --rule-action deny \
  --cidr-block 45.33.32.156/32
```
Isso bloqueia **todo tráfego** desse IP antes que qualquer regra ALLOW seja avaliada. **Por que Security Groups não são suficientes:** SGs são **allow-only** — não têm regra de DENY explícita. Para bloquear um IP via SG, seria necessário remover as regras que permitem acesso de `0.0.0.0/0` e recriá-las com CIDRs específicos excluindo o IP atacante — o que quebraria o acesso de todos os outros usuários ou exigiria listar centenas de CIDRs legítimos. A NACL é a ferramenta correta para bloqueios de IP em produção: DENY explícito, avaliado antes dos SGs, aplicado a toda a subnet, e sem afetar nenhum outro usuário.
