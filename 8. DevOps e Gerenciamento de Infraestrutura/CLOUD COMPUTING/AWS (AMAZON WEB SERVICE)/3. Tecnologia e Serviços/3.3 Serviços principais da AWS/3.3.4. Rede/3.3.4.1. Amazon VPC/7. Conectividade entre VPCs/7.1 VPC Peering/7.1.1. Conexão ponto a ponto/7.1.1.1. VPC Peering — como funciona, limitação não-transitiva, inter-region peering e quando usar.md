### VPC Peering — como funciona, não-transitividade, inter-region e quando usar

O VPC Peering é uma conexão de rede direta entre duas VPCs que permite que os recursos de ambas se comuniquem usando endereços IP privados, como se estivessem na mesma rede. É a forma mais simples de conectar VPCs — sem gateways adicionais, sem criptografia extra (já está na backbone AWS), sem custo fixo por hora. A limitação fundamental é que não é transitivo: se A conecta com B e B conecta com C, A não pode falar com C pelo peering de B.

---

## Como o VPC Peering funciona

```
Antes do Peering:
  VPC-A (10.0.0.0/16) ←  sem conectividade  → VPC-B (10.1.0.0/16)
  EC2 em 10.0.1.50 tenta ping 10.1.1.50 → sem rota → descartado

Após criar o Peering e configurar as Route Tables:
  VPC-A (10.0.0.0/16) ←→ pcx-0abc123 ←→ VPC-B (10.1.0.0/16)
  
  Route Table de VPC-A: 10.1.0.0/16 → pcx-0abc123
  Route Table de VPC-B: 10.0.0.0/16 → pcx-0abc123
  
  EC2 em 10.0.1.50 → ping 10.1.1.50 → rota via pcx → chega em VPC-B

O peering usa a backbone privada da AWS — não passa pela internet.
A conexão é simétrica: ambos os lados precisam de rotas configuradas.
```

---

## Processo de criação — 4 passos

```bash
# Passo 1 — Solicitar o peering (do lado da VPC requester)
aws ec2 create-vpc-peering-connection \
  --vpc-id vpc-requester-0abc \
  --peer-vpc-id vpc-accepter-0def \
  --peer-owner-id 123456789012 \   # ID da conta AWS da VPC aceitante (pode ser a mesma)
  --peer-region us-east-1 \        # omitir se mesma região
  --tag-specifications 'ResourceType=vpc-peering-connection,Tags=[
    {Key=Name,Value=pcx-producao-servicos},
    {Key=Requester,Value=vpc-producao},
    {Key=Accepter,Value=vpc-servicos}
  ]'
# Retorna: {"VpcPeeringConnectionId": "pcx-0abc123"}

# Passo 2 — Aceitar o peering (do lado da VPC aceitante)
# (pode ser mesma conta ou conta diferente)
aws ec2 accept-vpc-peering-connection \
  --vpc-peering-connection-id pcx-0abc123

# Verificar estado: pending-acceptance → active
aws ec2 describe-vpc-peering-connections \
  --vpc-peering-connection-ids pcx-0abc123 \
  --query 'VpcPeeringConnections[0].Status'

# Passo 3 — Adicionar rotas na Route Table da VPC-A (requester)
aws ec2 create-route \
  --route-table-id rtb-vpc-a-privada \
  --destination-cidr-block 10.1.0.0/16 \  # CIDR da VPC-B
  --vpc-peering-connection-id pcx-0abc123

# Passo 4 — Adicionar rotas na Route Table da VPC-B (accepter)
aws ec2 create-route \
  --route-table-id rtb-vpc-b-privada \
  --destination-cidr-block 10.0.0.0/16 \  # CIDR da VPC-A
  --vpc-peering-connection-id pcx-0abc123
```

**Erro comum:** esquecer de configurar as rotas em AMBOS os lados. Um peering sem rotas em um dos lados = tráfego vai em uma direção mas não volta.

## A limitação não-transitiva — a mais importante das NACLs do Peering

O VPC Peering não é transitivo. Isso significa que um peering entre A↔B e um peering entre B↔C **não cria automaticamente** conectividade entre A e C, mesmo que B tenha peerings com ambos:

```
Topologia:
  VPC-A (10.0.0.0/16) ←→ pcx-AB ←→ VPC-B (10.1.0.0/16)
  VPC-B (10.1.0.0/16) ←→ pcx-BC ←→ VPC-C (10.2.0.0/16)

Pergunta: EC2 de VPC-A consegue falar com EC2 de VPC-C?
Resposta: NÃO

Por quê?
  VPC-A tem rota para VPC-B (via pcx-AB)
  VPC-B tem rota para VPC-C (via pcx-BC)
  
  Mas VPC-B NÃO PODE ser usada como "hop" para rotear entre VPC-A e VPC-C
  
  Para A falar com C:
  → Criar um terceiro peering direto: pcx-AC
  → Ou usar Transit Gateway (que é transitivo por design)

Topologia resultante para full mesh com 3 VPCs:
  A ←→ B (pcx-AB)
  B ←→ C (pcx-BC)
  A ←→ C (pcx-AC)  ← necessário para A e C se comunicarem

Full mesh com N VPCs: N × (N-1) / 2 conexões necessárias
  3 VPCs:  3 peerings
  5 VPCs:  10 peerings
  10 VPCs: 45 peerings
  20 VPCs: 190 peerings  ← ponto onde Transit Gateway é mais prático
```

### Restrição adicional — edge-to-edge routing não funciona

```
Cenários que NÃO funcionam via Peering:

1. VPN + Peering combinados:
   On-premises → VPN → VPC-A → Peering → VPC-B
   ✗ On-premises NÃO pode acessar VPC-B via VPC-A

2. Internet + Peering:
   Internet → IGW → VPC-A → Peering → VPC-B
   ✗ Recursos da internet não acessam VPC-B via VPC-A

3. NAT + Peering:
   VPC-A (privada) → NAT Gateway de VPC-B → Internet via peering
   ✗ VPC-A não pode usar o NAT de VPC-B para acessar a internet

Para todos esses cenários: Transit Gateway resolve.
```

## Restrições de CIDR para Peering

```
CIDRs NÃO podem se sobrepor:

VPC-A: 10.0.0.0/16
VPC-B: 10.0.0.0/16   ✗ Sobreposição exata — peering não pode ser criado
VPC-B: 10.0.100.0/24 ✗ Subconjunto de VPC-A — também não funciona
VPC-B: 10.1.0.0/16   ✓ Sem sobreposição
VPC-B: 172.16.0.0/16 ✓ Sem sobreposição

Por que é uma restrição crítica no planejamento:
  Se 10 VPCs precisam de peering entre si no futuro,
  nenhuma pode ter o mesmo CIDR.
  Planejar o espaço de endereçamento antes de criar as VPCs
  é fundamental para viabilizar o peering futuro.
```

## VPC Peering entre regiões (Inter-region Peering)

O VPC Peering funciona entre VPCs em regiões diferentes. O tráfego usa a backbone global da AWS — sem internet pública:

```bash
# Criar peering inter-region (da região us-east-1 para eu-west-1)
# Executado na região onde está a VPC requester (us-east-1)
aws ec2 create-vpc-peering-connection \
  --vpc-id vpc-us-east-1-0abc \
  --peer-vpc-id vpc-eu-west-1-0def \
  --peer-owner-id 123456789012 \
  --peer-region eu-west-1 \           # especificar a região destino
  --region us-east-1

# Aceitar na região da VPC aceitante (eu-west-1)
aws ec2 accept-vpc-peering-connection \
  --vpc-peering-connection-id pcx-0abc123 \
  --region eu-west-1
```

### Características do Inter-region Peering

```
Custo inter-region (diferente do intra-region):
  Intra-region peering:
    Mesma AZ:      $0.00/GB (gratuito)
    Cross-AZ:      $0.01/GB
  
  Inter-region peering (varia por par de regiões):
    us-east-1 ↔ eu-west-1: $0.02/GB
    us-east-1 ↔ ap-southeast-1: $0.09/GB
    (consultar pricing da AWS para pares específicos)

Latência:
  Intra-region: < 2ms
  Inter-region: 50-200ms (depende das regiões)

Criptografia:
  Todo tráfego inter-region via Peering é criptografado
  automaticamente pela AWS na backbone

DNS entre regiões:
  A resolução de DNS privado não funciona automaticamente cross-region
  Para resolver hostnames privados de VPCs em outras regiões:
  → Configurar Route 53 Resolver com endpoints e regras de forwarding
```

## Peering entre contas diferentes

```bash
# Conta A (111222333) cria o peering para VPC da Conta B (444555666)
aws ec2 create-vpc-peering-connection \
  --vpc-id vpc-conta-a \
  --peer-vpc-id vpc-conta-b \
  --peer-owner-id 444555666 \   # ID da conta B
  --peer-region us-east-1

# Conta B aceita (logada com credenciais da Conta B)
aws ec2 accept-vpc-peering-connection \
  --vpc-peering-connection-id pcx-0abc123

# Security Group cross-account: referenciar SG da outra conta
# Formato: account-id/sg-id
aws ec2 authorize-security-group-ingress \
  --group-id sg-conta-a \
  --protocol tcp \
  --port 5432 \
  --source-group 444555666/sg-conta-b-app
```

## Quando usar VPC Peering

```
VPC Peering É adequado quando:

✓ Poucas VPCs para conectar (2 a ~10)
✓ Conectividade ponto-a-ponto simples (A fala com B, não com C)
✓ Necessidade de acesso amplo entre duas VPCs (não apenas a um serviço)
✓ Ambientes diferentes mas relacionados:
   - VPC de produção ↔ VPC de monitoramento
   - VPC de app ↔ VPC de serviços compartilhados
   - VPC de dev ↔ VPC de build/CI
✓ Custo é fator importante (sem custo por hora, apenas por dados)
✓ VPCs em regiões diferentes precisam de comunicação de baixo volume

VPC Peering NÃO é adequado quando:

✗ Muitas VPCs (10+) — use Transit Gateway
✗ CIDRs sobrepostos (VPCs de times/empresas diferentes)
✗ Conectividade transitiva necessária (A→B→C)
✗ On-premises precisa acessar múltiplas VPCs via uma só conexão
✗ Acesso apenas a serviços específicos — use PrivateLink (mais seguro)
✗ Controle granular de roteamento entre VPCs — use TGW com route tables
```

## Erros comuns e armadilhas

**Configurar rotas em apenas um lado:** o peering fica em estado `active` mas o tráfego funciona apenas em uma direção. Sempre verificar rotas em AMBAS as VPCs após criar o peering.

**Assumir transitividade:** o erro arquitetural mais comum. "VPC-A tem peering com VPC-B, que tem peering com VPC-C, então A pode falar com C" — FALSO. Cada conexão precisa de peering direto.

**Não remover rotas ao deletar o peering:** rotas que apontam para um peering deletado ficam em estado `blackhole` — pacotes são silenciosamente descartados. Sempre limpar as Route Tables ao remover um peering.

**Usar peering onde PrivateLink seria mais seguro:** se VPC-A só precisa acessar um serviço de VPC-B, o peering expõe toda a VPC-B (protegida apenas por SGs). O PrivateLink expõe apenas o endpoint específico — mais seguro.

## 🧩 Quiz de Fixação

1. Uma empresa tem 4 VPCs: Prod (10.0.0.0/16), Staging (10.1.0.0/16), Dev (10.2.0.0/16) e Shared Services (10.3.0.0/16). Todas precisam acessar Shared Services. Prod e Staging não podem se comunicar. Dev pode se comunicar com Staging mas não com Prod. Desenhe o mapa de peerins necessários e explique por que Transit Gateway seria mais simples.

2. EC2 em VPC-A (10.0.1.50) faz `traceroute` para EC2 em VPC-B (10.1.1.50) via peering e vê apenas 1 salto. Em uma rede física tradicional entre dois datacenters, haveria muitos mais saltos. O que isso revela sobre a arquitetura de rede da AWS para peerins?

3. Uma empresa adquiriu outra empresa cujas VPCs usam `172.16.0.0/12` — o mesmo range que as VPCs da empresa compradora. VPC Peering é possível? Quais são as alternativas?

**Respostas:**

1) **Mapa de peerins necessários:**
- `pcx-prod-shared`: Prod ↔ Shared Services
- `pcx-staging-shared`: Staging ↔ Shared Services
- `pcx-dev-shared`: Dev ↔ Shared Services
- `pcx-dev-staging`: Dev ↔ Staging

Total: **4 peerings**. Não há peering Prod↔Staging (não podem comunicar) nem Prod↔Dev (não especificado como necessário). **Por que Transit Gateway seria mais simples:** com TGW, todas as 4 VPCs conectam ao mesmo hub. As restrições de "Prod não fala com Staging" são implementadas nas Route Tables do TGW: a route table de Prod não tem rota para Staging e vice-versa. Adicionar novas VPCs no futuro requer apenas 1 attachment ao TGW — não múltiplos peerins. Com 4 VPCs o ganho é pequeno, mas ao crescer para 10+ VPCs, o TGW se torna drasticamente mais simples.

2) O `traceroute` mostrando apenas 1 salto revela que o VPC Peering usa a **backbone privada da AWS** — não há roteadores intermediários, não há encapsulamento, não há tunelamento. Do ponto de vista da rede, as duas VPCs estão diretamente conectadas como se fossem a mesma rede lógica. A AWS implementa o peering no nível do hypervisor Nitro — o pacote vai diretamente da ENI de origem para a ENI de destino, com a tradução de roteamento acontecendo na camada de rede virtual da AWS, não em hardware físico intermediário. Isso também explica a latência extremamente baixa (sub-milissegundo intra-AZ, < 2ms inter-AZ) e por que o peering é gratuito na mesma AZ: não há infraestrutura adicional para cobrar.

3) **VPC Peering NÃO é possível** — `172.16.0.0/12` da empresa compradora inclui `172.16.0.0/12` da empresa adquirida (são o mesmo bloco ou blocos sobrepostos). Qualquer subconjunto do mesmo bloco cria sobreposição. **Alternativas:**
(a) **AWS PrivateLink:** para cada serviço específico que uma empresa precisa acessar da outra, criar um Endpoint Service (NLB + VPC Endpoint Service) e um Interface Endpoint do lado consumidor. Funciona com CIDRs sobrepostos — é a alternativa mais adequada para acesso a serviços específicos;
(b) **AWS Transit Gateway + NAT:** criar um TGW e usar NAT estático para traduzir os endereços IP antes do roteamento, separando os espaços de endereçamento — complexo de operar mas viabiliza comunicação ampla;
(c) **Renumerar as VPCs de uma das empresas:** a solução mais limpa a longo prazo, mas mais trabalhosa — exige recriar VPCs, migrar recursos e atualizar todas as configurações de rede;
(d) **Criar novas VPCs com CIDRs distintos** para os workloads que precisam se comunicar entre as empresas, e migrar gradualmente.
