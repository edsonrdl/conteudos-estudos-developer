### Transit Gateway — hub-and-spoke, route tables e uso em multi-conta

O Transit Gateway (TGW) é um hub de rede regional que centraliza a conectividade entre VPCs, redes on-premises (VPN e Direct Connect) e outras regiões AWS. Em vez de criar uma malha de VPC Peerings (N×(N-1)/2 conexões), todas as redes conectam ao mesmo TGW — e o TGW decide o roteamento entre elas usando suas próprias Route Tables. É o componente que viabiliza arquiteturas de rede AWS em escala enterprise.

---

## O modelo hub-and-spoke

```
VPC Peering (malha — N=5 VPCs → 10 conexões):

  VPC-A ←→ VPC-B
  VPC-A ←→ VPC-C
  VPC-A ←→ VPC-D
  VPC-A ←→ VPC-E
  VPC-B ←→ VPC-C
  VPC-B ←→ VPC-D
  ... (10 conexões no total)

Transit Gateway (hub — N=5 VPCs → 5 attachments):

  VPC-A ──┐
  VPC-B ──┤
  VPC-C ──┼── TGW (hub central)
  VPC-D ──┤
  VPC-E ──┘
  
  + On-premises via VPN ──┘
  + Outra região via TGW Peering ──┘

Adicionar VPC-F:
  Peering: 5 novas conexões (com cada VPC existente)
  TGW:     1 novo attachment
```

---

## Componentes do Transit Gateway

```
Transit Gateway possui:
  Attachments:      conexões com VPCs, VPNs, Direct Connect GW, outros TGWs
  Route Tables:     tabelas de roteamento que determinam para onde vai o tráfego
  Associations:     qual Route Table cada attachment usa para receber rotas
  Propagations:     quais rotas cada attachment anuncia para as Route Tables
```

### Criando um Transit Gateway

```bash
# Criar TGW
aws ec2 create-transit-gateway \
  --description "TGW central de producao" \
  --options '{
    "AmazonSideAsn": 64512,
    "AutoAcceptSharedAttachments": "disable",
    "DefaultRouteTableAssociation": "enable",
    "DefaultRouteTablePropagation": "enable",
    "VpnEcmpSupport": "enable",
    "DnsSupport": "enable",
    "MulticastSupport": "disable"
  }' \
  --tag-specifications 'ResourceType=transit-gateway,Tags=[{Key=Name,Value=tgw-producao}]'
# Retorna: {"TransitGatewayId": "tgw-0abc123"}

# Criar attachment de uma VPC ao TGW
aws ec2 create-transit-gateway-vpc-attachment \
  --transit-gateway-id tgw-0abc123 \
  --vpc-id vpc-producao \
  --subnet-ids subnet-tgw-az-a subnet-tgw-az-b \
  --tag-specifications 'ResourceType=transit-gateway-attachment,Tags=[{Key=Name,Value=att-vpc-producao}]'
```

**Subnets dedicadas para TGW:** o attachment precisa de subnets dedicadas (normalmente /28) em cada AZ onde o TGW precisa estar disponível. O TGW provisiona ENIs nessas subnets:

```
VPC com TGW attachment:
  Subnet TGW AZ-a (10.0.200.0/28):
    ENI: 10.0.200.4  ← provisioned pelo TGW
  Subnet TGW AZ-b (10.0.201.0/28):
    ENI: 10.0.201.4  ← provisioned pelo TGW
```

## Route Tables do Transit Gateway

O TGW tem suas próprias Route Tables, independentes das Route Tables das VPCs. É aqui que o controle de roteamento entre VPCs acontece:

```
Por padrão (DefaultRouteTableAssociation e DefaultRouteTablePropagation = enable):
  → Todos os attachments são associados à mesma Route Table padrão
  → Todos os attachments propagam suas rotas para essa Route Table
  → Resultado: todas as VPCs e redes se comunicam entre si (full mesh)

Para isolamento (múltiplas Route Tables):
  → Criar Route Tables separadas por "domínio de roteamento"
  → Associar attachments às Route Tables corretas
  → Propagar rotas seletivamente
```

### Exemplo — isolamento entre ambientes

```
Cenário: 3 ambientes (prod, staging, dev) não devem se comunicar
         mas todos precisam acessar shared-services

TGW Route Tables:

rtb-prod:
  Rotas: 10.0.0.0/16 (prod) → local (propagado)
         10.3.0.0/16 (shared) → att-shared (propagado)
  NÃO contém rotas para staging ou dev

rtb-staging:
  Rotas: 10.1.0.0/16 (staging) → local (propagado)
         10.3.0.0/16 (shared) → att-shared (propagado)

rtb-dev:
  Rotas: 10.2.0.0/16 (dev) → local (propagado)
         10.3.0.0/16 (shared) → att-shared (propagado)

rtb-shared:
  Rotas: 10.0.0.0/16 → att-prod    (propagado de prod)
         10.1.0.0/16 → att-staging (propagado de staging)
         10.2.0.0/16 → att-dev     (propagado de dev)
         10.3.0.0/16 → local       (próprio)

Associations (qual RT cada attachment usa para RECEBER):
  att-prod:    associado a rtb-prod
  att-staging: associado a rtb-staging
  att-dev:     associado a rtb-dev
  att-shared:  associado a rtb-shared

Resultado:
  prod → shared:    ✓ (rtb-prod tem rota para shared)
  staging → shared: ✓
  dev → shared:     ✓
  shared → prod:    ✓ (rtb-shared tem rota para prod)
  prod → staging:   ✗ (rtb-prod não tem rota para staging)
  prod → dev:       ✗
```

```bash
# Criar Route Tables customizadas no TGW
aws ec2 create-transit-gateway-route-table \
  --transit-gateway-id tgw-0abc123 \
  --tag-specifications 'ResourceType=transit-gateway-route-table,Tags=[{Key=Name,Value=rtb-tgw-prod}]'

# Associar attachment à Route Table
aws ec2 associate-transit-gateway-route-table \
  --transit-gateway-route-table-id tgw-rtb-prod \
  --transit-gateway-attachment-id tgw-attach-vpc-prod

# Habilitar propagação de rotas do attachment para a Route Table
aws ec2 enable-transit-gateway-route-table-propagation \
  --transit-gateway-route-table-id tgw-rtb-shared \
  --transit-gateway-attachment-id tgw-attach-vpc-prod

# Adicionar rota estática (para rotas que não se propagam automaticamente)
aws ec2 create-transit-gateway-route \
  --transit-gateway-route-table-id tgw-rtb-prod \
  --destination-cidr-block 0.0.0.0/0 \
  --transit-gateway-attachment-id tgw-attach-vpc-egress  # rota padrão para VPC de egress

# Rota de blackhole (bloquear explicitamente)
aws ec2 create-transit-gateway-route \
  --transit-gateway-route-table-id tgw-rtb-prod \
  --destination-cidr-block 10.2.0.0/16 \  # bloquear dev
  --blackhole
```

## Route Table das VPCs com TGW

As VPCs também precisam ter rotas apontando para o TGW attachment para que o tráfego chegue até o TGW:

```
VPC Prod Route Table (subnets privadas):
  10.0.0.0/16  → local          (tráfego interno da VPC)
  10.1.0.0/16  → tgw-0abc123   ← rota para VPC Staging (se permitido no TGW)
  10.3.0.0/16  → tgw-0abc123   ← rota para Shared Services
  0.0.0.0/0    → tgw-0abc123   ← rota padrão para VPC de Egress (opcional)

Nota: a rota na VPC aponta para o TGW ID, não para o attachment ID
```

```bash
# Adicionar rota para TGW na Route Table da VPC
aws ec2 create-route \
  --route-table-id rtb-vpc-prod-privada \
  --destination-cidr-block 10.3.0.0/16 \
  --transit-gateway-id tgw-0abc123
```

## TGW em ambientes multi-conta (AWS RAM)

Em organizações com múltiplas contas AWS, o Transit Gateway pode ser compartilhado entre contas usando o **AWS Resource Access Manager (RAM)**:

```bash
# Conta central (onde o TGW vive): compartilhar via RAM
aws ram create-resource-share \
  --name "tgw-compartilhado-org" \
  --resource-arns arn:aws:ec2:us-east-1:111222333:transit-gateway/tgw-0abc123 \
  --principals arn:aws:organizations::111222333:organization/o-abc123  # compartilhar com toda a org

# Ou compartilhar com contas específicas
aws ram create-resource-share \
  --name "tgw-compartilhado" \
  --resource-arns arn:aws:ec2:us-east-1:111222333:transit-gateway/tgw-0abc123 \
  --principals "444555666" "777888999"  # IDs das contas

# Na conta destino: aceitar o compartilhamento
aws ram accept-resource-share-invitation \
  --resource-share-invitation-arn arn:aws:ram:...:resource-share-invitation/abc123

# Na conta destino: criar attachment da VPC ao TGW compartilhado
aws ec2 create-transit-gateway-vpc-attachment \
  --transit-gateway-id tgw-0abc123 \        # TGW da conta central
  --vpc-id vpc-conta-destino \
  --subnet-ids subnet-tgw-az-a subnet-tgw-az-b

# Na conta do TGW: aprovar o attachment (se AutoAcceptSharedAttachments=disable)
aws ec2 accept-transit-gateway-vpc-attachment \
  --transit-gateway-attachment-id tgw-attach-0abc123
```

### Arquitetura hub central com AWS Organizations

```
Conta Network (hub de rede):
  TGW compartilhado via RAM para toda a organização
  Route Tables:
    - rtb-prod: rotas de VPCs de produção
    - rtb-dev: rotas de VPCs de desenvolvimento
    - rtb-shared: rotas de VPCs compartilhadas
    - rtb-on-premises: rotas via VPN/Direct Connect

Contas de Workload (spokes):
  Cada VPC conecta ao TGW compartilhado com 1 attachment
  A conta de Network controla o roteamento

Conta Network também gerencia:
  - VPN Site-to-Site para on-premises
  - Direct Connect Gateway attachment
  - TGW Peering para outras regiões
```

## TGW Peering — conectar regiões via TGW

```bash
# Criar peering entre TGW de duas regiões
# Da região us-east-1: solicitar peering com TGW de eu-west-1
aws ec2 create-transit-gateway-peering-attachment \
  --transit-gateway-id tgw-us-east-1-0abc \
  --peer-transit-gateway-id tgw-eu-west-1-0def \
  --peer-region eu-west-1 \
  --peer-account-id 111222333 \
  --region us-east-1

# Na região eu-west-1: aceitar
aws ec2 accept-transit-gateway-peering-attachment \
  --transit-gateway-attachment-id tgw-attach-peering-0abc \
  --region eu-west-1

# Adicionar rotas estáticas (peering TGW não propaga automaticamente)
aws ec2 create-transit-gateway-route \
  --transit-gateway-route-table-id tgw-rtb-us-east-1 \
  --destination-cidr-block 172.31.0.0/16 \  # CIDR das VPCs em eu-west-1
  --transit-gateway-attachment-id tgw-attach-peering-0abc \
  --region us-east-1
```

## Custo do Transit Gateway

```
Modelo de cobrança:
  Attachment:         $0.05/hora por attachment (VPC, VPN, DX GW)
  Dados processados:  $0.02/GB de dados transferidos via TGW

Exemplo (5 VPCs + 1 VPN + 500 GB/mês):
  Attachments: 6 × $0.05 × 720h = $216/mês
  Dados:       500 GB × $0.02 = $10/mês
  Total: $226/mês

Comparação com VPC Peering (5 VPCs em full mesh = 10 peerings):
  Peering: sem custo por hora, apenas $0.01/GB cross-AZ
  500 GB × $0.01 = $5/mês
  
  TGW é mais caro que peering para poucas VPCs e baixo volume!
  O valor do TGW está na escala, não no preço baixo:
  → 20 VPCs: TGW economiza em complexidade operacional
  → Transitividade: TGW viabiliza cenários impossíveis com peering
  → On-premises: 1 VPN/DX para TGW serve todas as VPCs
```

## Erros comuns e armadilhas

**DefaultRouteTableAssociation/Propagation = enable para ambientes que precisam de isolamento:** com os defaults ativados, todas as VPCs se comunicam — incluindo prod e dev. Para ambientes que precisam de isolamento desde o início, criar o TGW com `disable` e configurar Route Tables manualmente.

**Esquecer de adicionar rotas nas VPCs:** o attachment existe e as TGW Route Tables estão configuradas, mas as VPCs não têm rotas apontando para o TGW. O tráfego nunca chega ao TGW. Verificar Route Tables das VPCs E do TGW.

**Overlap de CIDRs entre VPCs conectadas ao TGW:** ao contrário do Peering, o TGW aceita múltiplas VPCs com CIDRs sobrepostos — mas o roteamento fica ambíguo. O TGW não sabe para qual das duas VPCs com `10.0.0.0/16` enviar o tráfego. Evitar CIDRs sobrepostos em VPCs que precisam se comunicar via TGW.

## 🧩 Quiz de Fixação

1. Uma empresa tem 15 VPCs (produção, staging, dev, shared-services, security, egress, etc.) e 2 conexões VPN on-premises. Por que Transit Gateway é claramente superior a VPC Peering nesse cenário? Calcule a diferença em número de conexões.

2. No TGW, qual é a diferença entre **Association** e **Propagation** de uma Route Table, e por que separar essas duas configurações permite controle granular de roteamento?

3. Uma VPC "Egress" centralizou o NAT Gateway para todas as outras VPCs via TGW. A rota `0.0.0.0/0 → tgw` nas VPCs internas funciona para atingir o NAT, mas o tráfego de retorno não volta. Qual é o problema e como corrigir?

**Respostas:**

1) **VPC Peering:** para conectar 15 VPCs em full mesh = `15 × 14 / 2 = 105 conexões` de peering. Mas full mesh não é necessário — mesmo com topologia seletiva, as 2 VPNs precisariam se conectar a cada VPC individualmente, impossível com Peering (VPN não é transitiva via Peering). **Transit Gateway:** 15 VPCs + 2 VPN = **17 attachments**. As VPNs se conectam ao TGW e automaticamente têm rota para todas as VPCs (conforme configurado nas Route Tables). Adicionar a 16ª VPC = 1 novo attachment. Com Peering, seria necessário criar até 15 novas conexões (uma com cada VPC existente). A diferença: 105 conexões de peering (sem os VPNs, que seriam inviáveis) vs 17 attachments de TGW. Em complexidade operacional, o TGW elimina o gerenciamento de 105 objetos de peering e suas Route Tables correspondentes.

2) **Association** define qual Route Table um attachment *consulta* para tomar decisões de roteamento — ou seja, qual tabela o TGW usa para saber para onde encaminhar pacotes que chegam daquele attachment. **Propagation** define quais Route Tables recebem automaticamente as rotas anunciadas pelo attachment (seus CIDRs). Separar permite: (a) um attachment pode *propagar* suas rotas para múltiplas Route Tables (ex: VPC-Shared anuncia suas rotas para a RT de Prod e para a RT de Staging simultaneamente); (b) um attachment é *associado* a apenas uma Route Table para consulta de destino. Exemplo concreto: VPC-Prod é **associada** à rtb-prod (consulta apenas essa tabela) mas tem suas rotas **propagadas** para rtb-shared (Shared Services consegue alcançar Prod). Sem essa separação, seria impossível ter um attachment que "recebe rotas de todos" mas "envia pacotes apenas para alguns".

3) O problema é **roteamento assimétrico**: o pacote de VPC-Interna → internet vai por VPC-Interna → TGW → VPC-Egress → NAT → internet. A resposta da internet chega no NAT com destino ao IP privado da VPC-Interna (ex: `10.0.10.50`). O NAT precisa enviar a resposta de volta para `10.0.10.50`. Na Route Table da VPC-Egress, deve existir uma rota `10.0.10.0/24 → tgw` (ou o CIDR completo de todas as VPCs internas). Se essa rota não existir, a resposta do NAT não sabe como chegar às VPCs internas — o NAT descarta ou o pacote vai pelo default route e tenta sair pela internet novamente. **Correção:** adicionar na Route Table da VPC-Egress (nas subnets onde o NAT está) rotas para todos os CIDRs das VPCs internas apontando para o TGW: `10.0.0.0/8 → tgw-0abc123` (ou CIDRs específicos de cada VPC interna). Isso garante que a resposta do NAT seja roteada de volta para as VPCs corretas via TGW.
