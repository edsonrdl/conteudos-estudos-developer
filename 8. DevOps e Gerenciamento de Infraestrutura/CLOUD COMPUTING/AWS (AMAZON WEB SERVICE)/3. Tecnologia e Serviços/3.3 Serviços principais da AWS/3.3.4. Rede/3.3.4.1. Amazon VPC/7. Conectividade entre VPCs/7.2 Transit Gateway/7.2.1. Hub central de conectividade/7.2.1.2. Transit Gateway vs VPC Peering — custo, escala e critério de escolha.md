### Transit Gateway vs VPC Peering — custo, escala e critério de escolha

VPC Peering e Transit Gateway resolvem o mesmo problema — conectar VPCs — mas com trade-offs opostos. O Peering é mais barato e simples para poucos casos de uso específicos; o TGW é mais caro mas viabiliza cenários impossíveis com Peering e escala sem limite prático. Escolher errado significa pagar a mais desnecessariamente ou criar uma arquitetura que não cresce.

---

## Comparativo direto em todas as dimensões

```
┌────────────────────────────┬──────────────────────────┬──────────────────────────┐
│ Dimensão                   │ VPC Peering              │ Transit Gateway          │
├────────────────────────────┼──────────────────────────┼──────────────────────────┤
│ Custo base (por hora)      │ $0.00                    │ $0.05/h por attachment   │
│ Custo por dados            │ $0.01/GB cross-AZ        │ $0.02/GB (qualquer AZ)   │
│ Custo inter-region         │ $0.02-$0.09/GB           │ $0.02-$0.09/GB + TGW     │
│ Transitividade             │ Não                      │ Sim                      │
│ CIDRs sobrepostos          │ Não funciona             │ Funciona (com cuidado)   │
│ On-premises via VPN/DX     │ Edge routing não funciona│ Nativo (1 attachment)    │
│ Escala de conexões         │ N×(N-1)/2                │ N (linear)               │
│ Controle de roteamento     │ Simples (por rota)       │ Avançado (route tables)  │
│ Isolamento entre VPCs      │ Por ausência de peering  │ Por Route Tables TGW     │
│ Multi-conta                │ Peering cross-account OK │ Compartilhado via RAM    │
│ Multi-região               │ Inter-region peering     │ TGW peering inter-region │
│ Blackhole routes           │ Não                      │ Sim                      │
│ Complexidade operacional   │ Baixa (poucos VPCs)      │ Média-Alta               │
│ DNS resolution cross-VPC   │ Configuração adicional   │ Habilitado no TGW        │
│ Latência adicional         │ Praticamente zero        │ Mínima (~1ms adicional)  │
└────────────────────────────┴──────────────────────────┴──────────────────────────┘
```

## Análise de custo — quando o TGW se paga

### Cenário 1 — 2 VPCs, 500 GB/mês, mesma região

```
VPC Peering:
  Custo base:  $0/mês
  Dados (cross-AZ, 50% do tráfego): 250 GB × $0.01 = $2.50/mês
  Total Peering: $2.50/mês

Transit Gateway:
  Attachments: 2 × $0.05/h × 720h = $72/mês
  Dados: 500 GB × $0.02 = $10/mês
  Total TGW: $82/mês

Veredicto: VPC Peering — 33x mais barato para 2 VPCs
```

### Cenário 2 — 10 VPCs em full mesh, 5 TB/mês total

```
VPC Peering (45 peerins):
  Custo base:  $0/mês (sem custo por peering)
  Dados (cross-AZ): 5.000 GB × $0.01 = $50/mês
  Operacional: 45 peerins × 2 RTs cada = 90 Route Tables para gerenciar
  Total Peering: $50/mês (mas alta complexidade operacional)

Transit Gateway:
  Attachments: 10 × $0.05/h × 720h = $360/mês
  Dados: 5.000 GB × $0.02 = $100/mês
  Total TGW: $460/mês

Veredicto financeiro: VPC Peering ainda é mais barato
Veredicto operacional: TGW vence em gerenciabilidade

→ Ponto de inflexão financeiro é difícil de calcular sem incluir
  o custo do tempo de engenheiro para manter 90 Route Tables.
  Se 1h/mês de engenheiro a $100/h = $100/mês: TGW é similar em custo total
```

### Cenário 3 — 10 VPCs + 2 conexões VPN on-premises

```
VPC Peering:
  → VPN conecta a 1 VPC (Virtual Private Gateway por VPC)
  → Para on-premises acessar todas as 10 VPCs: 10 VPNs separadas
    (ou 10 DX Virtual Interfaces)
  → Custo de 10 VPNs: $0.05/h × 10 × 720h = $360/mês apenas em VPNs
  → Impossível usar peering para fazer on-premises chegar em múltiplas VPCs

Transit Gateway:
  → 1 VPN attachment ao TGW → acessa todas as 10 VPCs via TGW
  → Custo: 12 attachments (10 VPCs + 2 VPNs) × $0.05 × 720h = $432/mês
  
Veredicto: TGW é a ÚNICA opção viável para on-premises + múltiplas VPCs
```

## Quando cada um é a escolha certa

### Use VPC Peering quando:

```
1. Poucas VPCs (2-5) com padrão de conectividade estável:
   → Não vai crescer para muitas VPCs
   → As conexões são fixas e bem conhecidas

2. Custo é a principal restrição:
   → Sem orçamento para TGW ($360+/mês para múltiplas VPCs)
   → Volume de dados baixo (< 1 TB/mês)

3. Acesso a serviços específicos entre POUCAS contas:
   → VPC de monitoramento que só precisa acessar VPCs de app
   → VPC de CI/CD que acessa repositórios

4. Sem necessidade de on-premises integrado:
   → Ambiente 100% AWS, sem VPN/Direct Connect

5. Sem requisito de transitividade:
   → Topologia simples: A fala com B, B fala com C, mas A não precisa de C

Regra prática: se cabe em um guardanapo (desenho simples) → Peering
```

### Use Transit Gateway quando:

```
1. Muitas VPCs (6+) ou expectativa de crescimento:
   → Adicionar VPCs futuras é trivial (1 attachment)
   → Evitar reconfiguração de N peerins a cada nova VPC

2. Conectividade on-premises (VPN ou Direct Connect):
   → 1 attachment centraliza o acesso de on-premises para todas as VPCs

3. Isolamento de ambientes como requisito:
   → Prod não pode falar com dev/staging
   → Diferentes BUs com restrições de comunicação
   → TGW Route Tables implementam isso limpamente

4. Arquitetura multi-conta (Landing Zone / Control Tower):
   → TGW compartilhado via RAM para toda a organização
   → Conta de Network centraliza o roteamento

5. Topologias de rede avançadas:
   → Egress centralizado (NAT Gateway em VPC dedicada)
   → Firewall centralizado (AWS Network Firewall em VPC de inspeção)
   → Conectividade multi-região

6. Equipe com experiência de rede:
   → TGW requer entendimento de BGP, Route Tables, propagação
   → Time sem essa experiência pode simplificar demais ou errar
```

## Árvore de decisão

```
Você precisa conectar VPCs?
│
├── Quantas VPCs?
│   ├── 2-3 VPCs → VPC Peering (mais barato e simples)
│   ├── 4-7 VPCs → Avaliar custo vs complexidade
│   └── 8+ VPCs → Transit Gateway (escala melhor)
│
├── Precisa conectar on-premises (VPN/Direct Connect)?
│   ├── SIM → Transit Gateway (obrigatório para múltiplas VPCs)
│   └── NÃO → continua ↓
│
├── Precisa de isolamento entre alguns grupos de VPCs?
│   ├── SIM → Transit Gateway (Route Tables de TGW)
│   └── NÃO → Peering pode funcionar
│
├── CIDRs se sobrepõem entre as VPCs?
│   ├── SIM → Transit Gateway (ou PrivateLink para serviços específicos)
│   └── NÃO → Peering é viável
│
├── Precisa de conectividade multi-região transitiva?
│   ├── SIM → Transit Gateway + TGW Peering
│   └── NÃO → Inter-region VPC Peering pode ser suficiente
│
└── Custo é a principal restrição?
    ├── SIM → VPC Peering (sem custo fixo por hora)
    └── NÃO → TGW pela operabilidade superior
```

## Migração de Peering para TGW

Em ambientes que começaram com Peering e cresceram além do ponto de gerenciabilidade, a migração para TGW é um processo gradual:

```bash
# Roteiro de migração gradual Peering → TGW

# Fase 1: criar TGW e attachments, sem remover peerins
aws ec2 create-transit-gateway ...
aws ec2 create-transit-gateway-vpc-attachment ... # para cada VPC

# Fase 2: adicionar rotas TGW em PARALELO com rotas Peering
# (tráfego ainda usa Peering — TGW é backup)
# VPC Route Tables: ambas as rotas existem
# Por longest prefix match, a mais específica vence

# Fase 3: validar conectividade via TGW (usar VPC Reachability Analyzer)

# Fase 4: mudar a rota na VPC para apontar para TGW (uma VPC por vez)
aws ec2 replace-route \
  --route-table-id rtb-vpc-a \
  --destination-cidr-block 10.1.0.0/16 \
  --transit-gateway-id tgw-0abc123
# (substituir a rota que antes apontava para pcx-peering)

# Fase 5: remover os peerins após validação completa
aws ec2 delete-vpc-peering-connection \
  --vpc-peering-connection-id pcx-0abc123
```

## Erros comuns e armadilhas

**Usar TGW para conectar apenas 2 VPCs:** custo 33x maior que Peering sem nenhuma vantagem funcional. TGW se justifica pelo hub — com apenas 2 conexões, não há hub, só custo.

**Manter Peering em paralelo com TGW por segurança:** dois caminhos para o mesmo destino criam ambiguidade de roteamento difícil de debugar. Após migrar para TGW, remover os peerins correspondentes.

**Não planejar o crescimento:** escolher Peering para "economizar" hoje e após 1 ano ter 15 VPCs com 105 conexões para gerenciar. Se o roadmap prevê mais de 10 VPCs, TGW desde o início é mais econômico a longo prazo (custo de migração + retrabalho supera o custo do TGW antecipado).

## 🧩 Quiz de Fixação

1. Uma startup tem 3 VPCs (app, banco, monitoring) totalmente dentro da AWS, sem VPN, com tráfego de ~100 GB/mês entre elas. O arquiteto propõe usar Transit Gateway. Calcule o custo mensal do TGW vs VPC Peering e justifique se a proposta faz sentido.

2. Uma empresa com 20 VPCs e 3 escritórios (conectados via VPN) está usando VPC Peering. O time de rede reclama de sobrecarga operacional. Qual é o número atual de peerins e de rotas para gerenciar, e como o TGW simplificaria?

3. Dois times compartilham a mesma conta AWS. O time A tem VPC com `10.0.0.0/16` e o time B tem VPC com `10.0.0.0/16` (CIDRs idênticos). Eles precisam se comunicar mas VPC Peering é impossível. Qual é a alternativa mais adequada considerando que o time B expõe apenas 2 APIs REST?

**Respostas:**

1) **Custo VPC Peering (3 peerins: app↔banco, app↔monitoring, banco↔monitoring):**
- Custo base: $0/mês
- Dados cross-AZ (assumindo 50% do tráfego): 50 GB × $0.01 = **$0.50/mês**
- **Total Peering: $0.50/mês**

**Custo Transit Gateway:**
- Attachments: 3 × $0.05/h × 720h = **$108/mês**
- Dados: 100 GB × $0.02 = **$2/mês**
- **Total TGW: $110/mês**

**Veredicto:** a proposta de TGW **não faz sentido** para esse cenário. O TGW custa 220× mais que o Peering sem nenhuma vantagem funcional: não há on-premises, não há isolamento necessário, não há crescimento planejado além de 3 VPCs, e o padrão de conectividade é fixo. VPC Peering com 3 conexões é a escolha correta — simples, barato e adequado.

2) **Estado atual com 20 VPCs em full mesh + 3 VPNs:**
- Peerins full mesh: `20 × 19 / 2 = 190 peerins`
- Cada peering requer 2 entradas de Route Table (uma em cada VPC): `190 × 2 = 380 entradas de Route`
- 3 VPNs, cada uma conectada a 1 VPC com Virtual Private Gateway
- Para on-premises acessar as outras 19 VPCs via cada VGW: 19 peerins × 3 = rotas adicionais ou VPNs separadas
- **Total aproximado de objetos a gerenciar: 190+ peerins, 380+ entradas de rota, 3 VGWs separados**

**Com Transit Gateway:**
- Attachments: 20 VPCs + 3 VPNs = **23 attachments**
- Route Tables TGW: 1 (ou algumas poucas para isolamento)
- VPCs: cada uma tem `10.x.0.0/16 → tgw-id` por CIDR destino (ou rota resumida)
- On-premises: 1 attachment por VPN, acessa todas as 20 VPCs via TGW
- **Redução de complexidade: de 190 conexões para 23 attachments**

3) A alternativa mais adequada é **AWS PrivateLink**. Como o time B expõe apenas 2 APIs REST (não precisa de acesso amplo à rede inteira), criar um VPC Endpoint Service para cada API (NLB + Endpoint Service) e Interface Endpoints do lado do time A. **Por que PrivateLink é melhor que TGW aqui:** (a) CIDRs sobrepostos não são problema com PrivateLink; (b) o time A acessa apenas as 2 APIs específicas — sem exposição da VPC do time B; (c) custo menor que TGW para 2 serviços específicos; (d) não requer renumeração de IPs em nenhuma das VPCs. **Por que não TGW:** o TGW também suporta CIDRs sobrepostos em teoria, mas o roteamento ficaria ambíguo — dois attachments com `10.0.0.0/16` no mesmo TGW criariam conflito na Route Table. PrivateLink resolve elegantemente sem nenhuma mudança de infraestrutura de rede.
