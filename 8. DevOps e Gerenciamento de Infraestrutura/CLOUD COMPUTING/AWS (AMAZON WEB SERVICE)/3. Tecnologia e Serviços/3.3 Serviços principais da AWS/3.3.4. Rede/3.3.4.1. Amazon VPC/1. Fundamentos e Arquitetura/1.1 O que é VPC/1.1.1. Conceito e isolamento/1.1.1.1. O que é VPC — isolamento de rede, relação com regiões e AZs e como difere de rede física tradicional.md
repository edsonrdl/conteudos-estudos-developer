### Amazon VPC — o que é, isolamento de rede e relação com regiões e AZs

Amazon VPC (Virtual Private Cloud) é uma rede virtual privada provisionada dentro da infraestrutura da AWS. É o componente de rede que envolve todos os seus recursos computacionais — EC2, RDS, ECS, Lambda (quando em VPC) — criando um espaço de rede isolado logicamente de todas as outras contas AWS e da internet pública, a menos que você configure o contrário explicitamente.

Entender a VPC é entender onde tudo roda na AWS. Sem VPC, não existe EC2, não existe RDS, não existe EKS. Ela é o pré-requisito silencioso de toda arquitetura AWS.

---

## O problema que a VPC resolve

Em um datacenter físico tradicional, o isolamento de rede vem do hardware: switches, VLANs, firewalls físicos. Para criar uma rede isolada para um novo projeto, você precisa de equipamentos, cabeamento, configuração de VLAN, tempo e um time de infraestrutura.

Na AWS, você compartilha a infraestrutura física com milhares de outros clientes. Sem isolamento lógico, qualquer instância EC2 poderia ver o tráfego de outro cliente na mesma máquina física.

```
Problema sem VPC:

Datacenter AWS (físico):
  ┌──────────────────────────────────────────────────────┐
  │  Servidor físico compartilhado                       │
  │  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐  │
  │  │  Conta AWS  │  │  Conta AWS  │  │  Conta AWS  │  │
  │  │  (sua)      │  │  (empresa B)│  │  (empresa C)│  │
  │  └─────────────┘  └─────────────┘  └─────────────┘  │
  └──────────────────────────────────────────────────────┘
  
  Sem isolamento: todas as contas na mesma "rede plana"
  → Sua instância poderia alcançar a instância do cliente B
  → Tráfego visível entre contas

Solução — VPC por conta:
  Conta AWS (sua):           Conta AWS (empresa B):
  ┌──────────────────┐       ┌──────────────────┐
  │  VPC: 10.0.0.0/16│       │  VPC: 10.0.0.0/16│
  │  ┌────┐  ┌────┐  │       │  ┌────┐  ┌────┐  │
  │  │ EC2│  │ RDS│  │       │  │ EC2│  │ RDS│  │
  │  └────┘  └────┘  │       │  └────┘  └────┘  │
  └──────────────────┘       └──────────────────┘
  Completamente isoladas — mesmo CIDRs sobrepostos não se comunicam
```

## O que é uma VPC — definição técnica

Uma VPC é um **espaço de endereçamento IP privado e isolado** dentro de uma região AWS, definido por um bloco CIDR (ex: `10.0.0.0/16`). Dentro desse espaço você cria subnets, define regras de roteamento, controla o acesso e lança recursos.

```
Anatomia de uma VPC:

VPC: 10.0.0.0/16 (us-east-1)
│
├── Subnet pública us-east-1a:  10.0.1.0/24
│     └── EC2 (10.0.1.10) — web server
│
├── Subnet pública us-east-1b:  10.0.2.0/24
│     └── EC2 (10.0.2.15) — web server (redundância)
│
├── Subnet privada us-east-1a:  10.0.10.0/24
│     └── EC2 (10.0.10.5)  — application server
│
├── Subnet privada us-east-1b:  10.0.11.0/24
│     └── EC2 (10.0.11.7)  — application server
│
├── Subnet de dados us-east-1a: 10.0.20.0/24
│     └── RDS (10.0.20.100) — banco de dados
│
└── Subnet de dados us-east-1b: 10.0.21.0/24
      └── RDS (10.0.21.101) — banco de dados (standby)
```

## Relação entre VPC, Região e Availability Zones

A VPC existe em uma **região** — ela não atravessa regiões. Dentro da região, ela pode (e deve) abranger múltiplas **Availability Zones** através de subnets:

```
Hierarquia geográfica na AWS:

Região (ex: us-east-1 — N. Virginia)
└── VPC: 10.0.0.0/16
      ├── AZ us-east-1a
      │     ├── Subnet pública:  10.0.1.0/24
      │     └── Subnet privada:  10.0.10.0/24
      ├── AZ us-east-1b
      │     ├── Subnet pública:  10.0.2.0/24
      │     └── Subnet privada:  10.0.11.0/24
      └── AZ us-east-1c
            ├── Subnet pública:  10.0.3.0/24
            └── Subnet privada:  10.0.12.0/24

Regras importantes:
  → 1 VPC pertence a exatamente 1 região
  → 1 subnet pertence a exatamente 1 AZ
  → 1 VPC pode ter subnets em todas as AZs da região
  → Recursos em subnets de AZs diferentes comunicam-se dentro da VPC
    via o roteamento local (sem passar pela internet)
```

### Por que multi-AZ importa

Cada AZ é um datacenter fisicamente separado. Um incêndio, falha de energia ou desastre em `us-east-1a` não afeta `us-east-1b`. Distribuir recursos entre AZs dentro da mesma VPC é como ter redundância geográfica sem a latência de uma segunda região:

```
Sem multi-AZ:
  Tudo em us-east-1a → falha da AZ → aplicação fora do ar

Com multi-AZ (mesma VPC):
  50% em us-east-1a, 50% em us-east-1b
  → Falha de us-east-1a → us-east-1b continua servindo
  → Latência entre AZs: < 2ms (rede privada da AWS)
  → Custo de tráfego inter-AZ: $0.01/GB
```

## Como o isolamento da VPC funciona tecnicamente

O isolamento não é por firewall — é por **construção do plano de dados**. A VPC usa o **hypervisor Nitro** da AWS para implementar regras de rede no nível mais baixo possível: cada pacote de rede é interceptado antes de sair da instância e verificado contra as políticas da VPC.

```
Camadas de isolamento na VPC:

Nível 1 — Endereçamento:
  Pacotes com endereço fora do CIDR da VPC → descartados pelo plano de dados
  (sem possibilidade de roteamento acidental para outra VPC)

Nível 2 — Security Groups:
  Firewall stateful aplicado no nível do hypervisor
  (antes do pacote entrar ou sair da instância virtual)

Nível 3 — NACLs:
  Firewall stateless aplicado no nível da subnet
  (segunda linha de defesa)

Nível 4 — Route Tables:
  Só existe rota para destinos explicitamente configurados
  (sem rota = sem comunicação, mesmo que o IP esteja alcançável fisicamente)
```

## Diferenças entre VPC e rede física tradicional

| Aspecto | Rede física tradicional | Amazon VPC |
|---|---|---|
| **Provisionamento** | Dias a semanas (hardware) | Segundos (API call) |
| **Isolamento** | VLANs, switches físicos | Hypervisor Nitro, software-defined |
| **Endereçamento** | Fixo ao hardware | Qualquer RFC 1918 (configurável) |
| **Roteamento** | Roteadores físicos com IOS/firmware | Route Tables (software, declarativo) |
| **Firewall** | Appliance físico (Cisco ASA, Palo Alto) | Security Groups + NACLs (API) |
| **Escalabilidade** | Limitada por hardware disponível | Virtualmente ilimitada |
| **Visibilidade de tráfego** | SPAN ports, TAPs físicos | VPC Flow Logs |
| **Mudança de topologia** | Recabeamento, reconfiguração manual | Atualizar Route Table via API |
| **Custo inicial** | Alto (hardware + licenças) | Zero (paga pelo uso) |
| **Redundância** | Dual-homed, HA manual | Multi-AZ nativo |

## Erros comuns e armadilhas

**Usar a VPC default em produção:** a VPC default da AWS tem todas as subnets públicas com IPs públicos atribuídos automaticamente às instâncias. Qualquer EC2 lançada sem configuração adicional tem um IP público diretamente exposto. Para produção, crie sempre uma VPC customizada com subnets privadas.

**Uma VPC por aplicação vs uma VPC para tudo:** times iniciantes colocam tudo em uma VPC. Times mais maduros percebem que uma VPC única para produção, staging e dev cria riscos de segurança e problemas de isolamento. O padrão recomendado é VPCs separadas por ambiente (prod, staging, dev) ou por domínio de negócio, conectadas via Transit Gateway quando necessário.

**Não planejar o CIDR antes de criar:** uma VPC criada com CIDR `10.0.0.0/16` não pode ter o range ampliado (você pode adicionar CIDRs secundários, mas não pode mudar o primário). Se você precisar de mais IPs no futuro, terá que criar uma nova VPC e migrar os recursos — processo complexo.

## 🧩 Quiz de Fixação

1. Uma empresa tem duas VPCs: VPC-A com CIDR `10.0.0.0/16` em us-east-1 e VPC-B com CIDR `10.0.0.0/16` em eu-west-1. Um engenheiro tenta criar VPC Peering entre elas para conectar os recursos. Por que isso não é possível e o que precisaria mudar?

2. Uma instância EC2 em `us-east-1a` precisa se comunicar com um banco RDS em `us-east-1b`, ambos na mesma VPC. Essa comunicação passa pela internet pública? Qual é a latência e o custo esperados?

3. Por que dizer que "a VPC é um firewall" é tecnicamente impreciso, mas dizer que "a VPC provê isolamento" é correto?

**Respostas:**

1) Não é possível porque **VPC Peering não permite CIDRs sobrepostos** — as duas VPCs têm o mesmo bloco `10.0.0.0/16`, o que impossibilita o roteamento: quando um recurso envia um pacote para `10.0.5.100`, o roteador não saberia se o destino é na VPC-A ou na VPC-B. Para o Peering funcionar, os CIDRs das VPCs não podem se sobrepor. A solução seria recriar uma das VPCs com um CIDR diferente (ex: VPC-B com `10.1.0.0/16`) — o que exige recriar toda a infraestrutura, reforçando a importância do planejamento de CIDR antes de criar qualquer VPC.

2) A comunicação **não passa pela internet pública**. Recursos na mesma VPC se comunicam via a **rede interna da AWS** — o tráfego nunca sai para a internet, mesmo que as instâncias estejam em AZs diferentes. A latência típica entre AZs na mesma região é **< 2 milissegundos**. O custo é **$0.01/GB** para tráfego inter-AZ (vs $0.09/GB para tráfego saindo para a internet). Para workloads com alto volume de tráfego entre camadas, é importante considerar esse custo inter-AZ no dimensionamento financeiro.

3) A VPC **não é um firewall** porque não inspeciona o conteúdo dos pacotes nem bloqueia tráfego por padrão — ela é fundamentalmente um **espaço de endereçamento isolado**. O isolamento vem do fato de que pacotes com destino fora do CIDR da VPC simplesmente não têm rota — não são bloqueados ativamente, são descartados por ausência de roteamento. O firewall dentro da VPC é o Security Group (e opcionalmente as NACLs), que são componentes separados. A VPC provê isolamento por construção de rede; os Security Groups proveem controle de acesso por regras. São mecanismos distintos que trabalham em camadas diferentes.
