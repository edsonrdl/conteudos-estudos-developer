Os conceitos de redes tradicionais que você já conhece se aplicam diretamente à VPC — mas a AWS introduz algumas diferenças importantes que mudam o comportamento esperado. Este arquivo mapeia cada conceito, explica o que é idêntico e o que é específico da AWS.

---

## RFC 1918 na VPC — as mesmas faixas, mas com restrições

A AWS exige que o CIDR de uma VPC use exclusivamente os blocos **RFC 1918** (endereços privados):

```
Faixas RFC 1918 e o que a AWS permite:

Faixa RFC 1918       Máscara mínima   Máscara máxima
──────────────────────────────────────────────────────
10.0.0.0/8           /16              /28
172.16.0.0/12        /16              /28
192.168.0.0/16       /16              /28

Exemplos válidos:
  10.0.0.0/16     ✓ (65.536 IPs)
  10.0.0.0/24     ✓ (256 IPs)
  172.16.0.0/16   ✓
  192.168.1.0/24  ✓

Exemplos inválidos:
  10.0.0.0/8      ✗ (bloco /8 não é permitido — muito grande)
  10.0.0.0/29     ✗ (bloco /29 não é permitido — menor que /28)
  8.8.8.0/24      ✗ (IP público — não permitido como CIDR de VPC)
  100.64.0.0/10   ✗ (Carrier-grade NAT — não é RFC 1918)
```

**Por que a AWS não permite /8?** Blocos gigantes como `10.0.0.0/8` (16 milhões de IPs) criariam problemas de roteamento interno na AWS e tornariam o planejamento multi-VPC inviável.

## Notação CIDR — idêntica ao que você já sabe

A notação CIDR funciona exatamente como no mundo tradicional. A única diferença é onde você a escreve (no console AWS ou CLI em vez de um roteador físico):

```
Tradução direta do conceito tradicional para AWS:

Rede tradicional:
  Endereço de rede: 10.0.0.0
  Máscara:          255.255.0.0 (/16)
  Hosts utilizáveis: 10.0.0.1 a 10.0.255.254 (65.534 hosts)
  Broadcast:        10.0.255.255

Na VPC AWS com CIDR 10.0.0.0/16:
  Endereço da VPC:  10.0.0.0
  Prefixo:          /16
  IPs disponíveis:  65.536 — mas NÃO todos utilizáveis (ver reservas abaixo)
  Broadcast:        AWS não usa broadcast (sem L2 broadcast na VPC)
```

**Diferença importante:** na rede tradicional, o broadcast (último IP) é reservado e funciona como L2 broadcast — todos os hosts na subnet recebem pacotes enviados para ele. Na VPC, não existe L2 broadcast. A AWS reserva o último IP por compatibilidade histórica, mas ele nunca é usado para broadcast real.

## Subnetting na VPC — igual ao tradicional, com 5 IPs reservados pela AWS

Subnetear uma VPC funciona exatamente como no mundo tradicional — você pega o bloco da VPC e divide em subnets menores. O que muda é que a AWS **reserva 5 endereços em cada subnet** (vs 2 no modelo tradicional):

```
Subnet tradicional 10.0.1.0/24 (256 endereços):
  10.0.1.0   → endereço de rede (reservado)
  10.0.1.1 a 10.0.1.254 → 254 hosts utilizáveis
  10.0.1.255 → broadcast (reservado)
  
  Total reservado: 2 endereços
  Total utilizável: 254 hosts

Subnet AWS 10.0.1.0/24 (256 endereços):
  10.0.1.0   → endereço de rede (reservado pela AWS)
  10.0.1.1   → reservado para o roteador da VPC (AWS gateway)
  10.0.1.2   → reservado para DNS da AWS (sempre .2 em qualquer subnet)
  10.0.1.3   → reservado para uso futuro da AWS
  10.0.1.4 a 10.0.1.254 → 251 hosts utilizáveis
  10.0.1.255 → broadcast (reservado, mas sem uso real)
  
  Total reservado: 5 endereços
  Total utilizável: 251 hosts
```

### O DNS resolver da AWS — sempre no .2

O endereço `.2` de qualquer subnet é sempre o **DNS resolver interno da AWS** (também chamado de Amazon Provided DNS ou Route 53 Resolver):

```
VPC com CIDR 10.0.0.0/16:
  DNS interno da AWS: 10.0.0.2
  (não importa qual subnet — o DNS é sempre o .2 do CIDR da VPC)

Subnet 10.0.1.0/24:
  DNS interno: 10.0.0.2 (não 10.0.1.2!)
  
Subnet 10.0.50.0/24:
  DNS interno: 10.0.0.2 (sempre o .2 do bloco da VPC)
```

Esse DNS resolve nomes de hosts da VPC (ex: `minha-instancia.us-east-1.compute.internal`) e consultas para serviços AWS privados.

## VLSM na VPC — design de subnets de tamanhos diferentes

O VLSM (Variable Length Subnet Mask) que você estudou em redes tradicionais aplica-se diretamente ao design de subnets da VPC. Você pode ter subnets de tamanhos diferentes dentro do mesmo bloco da VPC:

```
VPC 10.0.0.0/16 — exemplo com VLSM:

Subnets públicas (poucas instâncias, só load balancers):
  10.0.1.0/28  → 11 hosts utilizáveis (2 AZs × pequena)
  10.0.2.0/28  → 11 hosts utilizáveis

Subnets de aplicação (muitas instâncias EC2):
  10.0.10.0/22 → 1.019 hosts utilizáveis (2 AZs × grande)
  10.0.14.0/22 → 1.019 hosts utilizáveis

Subnets de banco de dados (poucos servidores RDS):
  10.0.20.0/26 → 59 hosts utilizáveis (2 AZs × médio)
  10.0.21.0/26 → 59 hosts utilizáveis

→ Cada camada recebe exatamente o espaço que precisa
→ Mesmo princípio do VLSM tradicional aplicado na AWS
```

**Restrição AWS:** a menor subnet possível é `/28` (16 IPs — 11 utilizáveis após as 5 reservas). Subnets menores que `/28` não são permitidas.

## Longest Prefix Match — o mesmo algoritmo de roteamento

O algoritmo de seleção de rota na VPC é **longest prefix match** — exatamente o mesmo usado em roteadores tradicionais. A rota mais específica (prefixo mais longo) sempre vence:

```
Route Table de uma subnet com múltiplas rotas:

Destino          Alvo
──────────────────────────────────────────
10.0.0.0/16     local           ← rota da VPC (mais específica para tráfego interno)
10.0.5.0/24     vpn-gateway     ← rota específica para subnet on-premises via VPN
0.0.0.0/0       nat-gateway     ← rota padrão (menos específica — internet)

Pacote para 10.0.5.100:
  Candidatos: 10.0.0.0/16 (match) e 10.0.5.0/24 (match mais longo)
  Vencedor:   10.0.5.0/24 → vai pelo VPN Gateway  ✓

Pacote para 10.0.7.200:
  Candidatos: 10.0.0.0/16 (match) e 0.0.0.0/0 (match)
  Vencedor:   10.0.0.0/16 → roteamento local dentro da VPC  ✓

Pacote para 8.8.8.8 (Google DNS):
  Candidatos: 0.0.0.0/0 (único match)
  Vencedor:   0.0.0.0/0 → vai pelo NAT Gateway  ✓
```

## O que NÃO existe na VPC (diferenças do mundo tradicional)

Algumas características da rede L2/L3 tradicional simplesmente não existem na VPC porque ela é uma rede **puramente L3 (camada de rede)**:

```
Não existe na VPC:
  ✗ ARP (Address Resolution Protocol)
    → A AWS mapeia IPs para instâncias internamente
    → Você nunca vê tabelas ARP em instâncias EC2 (ou vê mas são virtuais)

  ✗ L2 Broadcast (broadcast de subnet)
    → Pacotes para o IP de broadcast (.255) são descartados
    → Não existe comunicação "para todos na subnet" via broadcast

  ✗ Multicast
    → Protocolos que dependem de multicast (OSPF, PIM, VRRP) não funcionam nativamente
    → Para multicast, usar serviços gerenciados ou encapsulamento

  ✗ Spanning Tree Protocol (STP)
    → Sem loops de L2 para resolver — a VPC é L3 puro

  ✗ VLAN tags (802.1Q)
    → A segmentação é feita por subnets e route tables, não por VLANs

  ✗ Gratuitous ARP
    → Técnicas de HA baseadas em GARP (Keepalived, Corosync) não funcionam nativamente
    → Usar Elastic IP reassignment ou AWS load balancers para HA
```

### Implicação prática para softwares legados

Softwares que dependem de **broadcast ou multicast** para descoberta de serviços (ex: alguns clustering softwares, protocolos de descoberta automática) **não funcionam na VPC** sem adaptação. Para esses casos:

```
Alternativas na AWS:
  Broadcast/multicast para descoberta →  AWS Cloud Map (Service Discovery)
  GARP para failover de IP             →  Elastic IP + Lambda para reassignment
  OSPF/BGP internos à VPC              →  Route Tables da VPC + propagação
  Clustering via heartbeat broadcast   →  Amazon Route 53 Health Checks + failover
```

## Resumo — o que é igual e o que muda

```
┌────────────────────────────┬───────────────────────────┬──────────────────────────────┐
│ Conceito                   │ Rede tradicional          │ VPC AWS                      │
├────────────────────────────┼───────────────────────────┼──────────────────────────────┤
│ Notação CIDR               │ Idêntica                  │ Idêntica                     │
│ Faixas RFC 1918            │ 10/8, 172.16/12, 192.168  │ Mesmas, mas /16 a /28 apenas │
│ Subnetting (divisão)       │ Igual                     │ Igual (mínimo /28)           │
│ IPs reservados por subnet  │ 2 (rede + broadcast)      │ 5 (rede + 3 AWS + broadcast) │
│ Longest prefix match       │ Idêntico                  │ Idêntico                     │
│ VLSM                       │ Suportado                 │ Suportado                    │
│ L2 Broadcast               │ Existe                    │ Não existe                   │
│ ARP                        │ Existe                    │ Transparente (gerenciado AWS)│
│ Multicast                  │ Existe                    │ Não existe nativamente        │
│ VLANs                      │ Segmentação L2            │ Subnets e Route Tables       │
│ Roteamento                 │ Roteadores físicos        │ Route Tables (software)      │
│ Firewall                   │ Appliance físico/VLAN ACL │ Security Groups + NACLs      │
└────────────────────────────┴───────────────────────────┴──────────────────────────────┘
```

## 🧩 Quiz de Fixação

1. Uma subnet AWS tem o bloco `10.0.5.0/26`. Quantos hosts são utilizáveis nessa subnet e quais são os 5 endereços reservados pela AWS?

2. Uma empresa tenta migrar um software de clustering que usa **gratuitous ARP** para fazer failover de IP entre dois servidores. Na VPC, o failover para de funcionar. Por que, e qual é a alternativa AWS-native?

3. Uma Route Table tem duas entradas: `10.10.0.0/16 → VPN Gateway` e `10.10.5.0/24 → local`. Um pacote chega destinado a `10.10.5.50`. Qual rota é usada e por quê? O que acontece com um pacote para `10.10.8.100`?

**Respostas:**

1) `10.0.5.0/26` tem 64 endereços (2^6 = 64). Endereços reservados pela AWS:
- `10.0.5.0` → endereço de rede
- `10.0.5.1` → roteador interno da VPC
- `10.0.5.2` → DNS da AWS
- `10.0.5.3` → reservado para uso futuro da AWS
- `10.0.5.63` → broadcast (reservado, sem uso real)

**Hosts utilizáveis:** 64 - 5 = **59 hosts** (de `10.0.5.4` a `10.0.5.62`).

2) Gratuitous ARP funciona em redes L2 tradicionais: o servidor que assume o IP envia um ARP sem solicitação anunciando "eu sou o dono do IP X", atualizando as tabelas ARP de todos os hosts na subnet. Na VPC, **L2 ARP não existe** — a AWS mapeia IPs para instâncias de forma centralizada no plano de dados do Nitro Hypervisor. Nenhum pacote ARP "anunciado" pela instância tem efeito sobre o mapeamento IP→instância que a AWS mantém internamente. **Alternativa AWS-native:** usar um **Elastic IP** (IP estático) + uma função Lambda ou script que chama `aws ec2 associate-address` para reassociar o Elastic IP para a instância de failover quando detectar a falha. Outra opção é usar um **Application Load Balancer** ou **Network Load Balancer** como ponto de entrada, deixando o load balancer gerenciar o failover entre as instâncias sem depender de técnicas de IP.

3) **Pacote para `10.10.5.50`:** ambas as rotas têm match — `10.10.0.0/16` (prefixo /16) e `10.10.5.0/24` (prefixo /24). Pelo algoritmo **longest prefix match**, a rota `/24` é mais específica e vence: o pacote é roteado para **local** (dentro da VPC). **Pacote para `10.10.8.100`:** apenas `10.10.0.0/16` tem match (/24 não cobre `10.10.8.x`). O pacote é enviado pelo **VPN Gateway**. Esse é um padrão útil: criar uma rota `/24` específica para uma subnet da VPC que "sobrepõe" uma rota /16 para o VPN, fazendo com que o tráfego para essa subnet vá localmente enquanto o resto do /16 vai pelo VPN.
