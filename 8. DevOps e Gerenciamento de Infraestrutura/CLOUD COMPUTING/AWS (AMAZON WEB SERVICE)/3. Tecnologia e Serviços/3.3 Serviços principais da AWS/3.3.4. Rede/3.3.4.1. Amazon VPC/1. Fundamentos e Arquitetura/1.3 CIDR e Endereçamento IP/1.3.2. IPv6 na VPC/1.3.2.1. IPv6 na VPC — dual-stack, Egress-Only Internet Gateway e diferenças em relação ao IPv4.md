### IPv6 na VPC — dual-stack, Egress-Only Internet Gateway e diferenças do IPv4

IPv6 foi criado para resolver o esgotamento de endereços IPv4 — com 128 bits em vez de 32, oferece 340 undecilhões de endereços (3,4 × 10^38), essencialmente ilimitados. Na AWS, IPv6 é suportado nas VPCs em modo **dual-stack** — a VPC funciona simultaneamente com IPv4 e IPv6, e você controla quais recursos recebem endereços de cada protocolo. Este arquivo explica como o IPv6 se comporta na VPC, o que muda em relação ao IPv4 e quando faz sentido adotá-lo.

---

## IPv6 na AWS — o modelo é diferente do IPv4

A primeira grande diferença: **todos os endereços IPv6 na VPC são públicos por padrão**. Não existe o conceito de "faixa privada" em IPv6 como existe no IPv4 (RFC 1918). Na AWS, os blocos IPv6 atribuídos às VPCs são endereços globalmente únicos, roteáveis na internet:

```
IPv4 na VPC:
  Endereços:    privados (RFC 1918 — 10.x.x.x, 172.16.x.x, 192.168.x.x)
  Acesso à internet: requer NAT (NAT Gateway ou Internet Gateway com Elastic IP)
  Privacidade:  instâncias sem Elastic IP são não-roteáveis na internet

IPv6 na VPC:
  Endereços:    públicos e globalmente únicos (ex: 2600:1f18::/32)
  Acesso à internet: direto via Internet Gateway (sem NAT)
  Privacidade:  controlada por Security Groups e NACLs — não por ausência de IP público
  
Consequência importante:
  Uma instância com IPv6 + Internet Gateway tem um IP
  globalmente único e acessível da internet.
  O isolamento vem EXCLUSIVAMENTE do Security Group.
```

## Estrutura de endereços IPv6 na VPC

A AWS atribui um bloco `/56` de endereços IPv6 à VPC (fornecido pela AWS ou por você com BYOIP):

```
Hierarquia de endereços IPv6 na VPC:

AWS atribui à VPC: 2600:1f18:1234:5600::/56
  (um /56 = 256 subnets /64 disponíveis)
         │
         ├── Subnet A recebe: 2600:1f18:1234:5600::/64
         │     (18,4 quintilhões de endereços por subnet)
         │
         ├── Subnet B recebe: 2600:1f18:1234:5601::/64
         │
         └── Subnet C recebe: 2600:1f18:1234:5602::/64

Endereço de uma instância EC2:
  2600:1f18:1234:5600:abcd:1234:5678:90ab/128
  (único no mundo — sem NAT necessário)
```

### Diferenças na notação e estrutura

```
IPv4 (32 bits):          IPv6 (128 bits):
10.0.1.50/24             2600:1f18:1234:5600::50/64

Grupos:  4 × 8 bits      Grupos: 8 × 16 bits (hex)
Máscara: /24 típica      Máscara: /64 padrão para subnets
                                  /128 para hosts individuais

Abreviação IPv6:
  Zeros consecutivos → ::
  2600:1f18:0000:5600:0000:0000:0000:0050
  = 2600:1f18:0:5600::50  (abreviado)
```

## Habilitando IPv6 na VPC

```bash
# 1. Habilitar bloco IPv6 na VPC (AWS atribui automaticamente um /56)
aws ec2 associate-vpc-cidr-block \
  --vpc-id vpc-0abc123 \
  --amazon-provided-ipv6-cidr-block

# 2. Verificar o bloco IPv6 atribuído
aws ec2 describe-vpcs \
  --vpc-ids vpc-0abc123 \
  --query 'Vpcs[0].Ipv6CidrBlockAssociationSet'
# Saída: [{"Ipv6CidrBlock": "2600:1f18:1234:5600::/56", "State": "associated"}]

# 3. Atribuir bloco /64 a uma subnet
aws ec2 associate-subnet-cidr-block \
  --subnet-id subnet-0abc123 \
  --ipv6-cidr-block 2600:1f18:1234:5600::/64

# 4. Habilitar atribuição automática de IPv6 na subnet
aws ec2 modify-subnet-attribute \
  --subnet-id subnet-0abc123 \
  --assign-ipv6-address-on-creation

# 5. Adicionar rota IPv6 para Internet Gateway (subnet pública)
aws ec2 create-route \
  --route-table-id rtb-0abc123 \
  --destination-ipv6-cidr-block ::/0 \
  --gateway-id igw-0abc123
```

## Dual-stack — IPv4 e IPv6 simultaneamente

No modo dual-stack, uma instância tem **dois endereços**: um IPv4 privado (RFC 1918) e um IPv6 público. Ela pode se comunicar usando qualquer um dos dois, dependendo do que o destino suporta:

```
Instância EC2 dual-stack:
  IPv4: 10.0.1.50        (privado, RFC 1918)
  IPv6: 2600:1f18::50    (público, globalmente único)

Comunicação com a internet:
  → Conexão IPv6 de fora: 2600:1f18::50 → EC2 (direto, sem NAT)
  → Conexão IPv4 de fora: precisa de Elastic IP ou ALB

Comunicação interna na VPC:
  → Via IPv4: 10.0.1.50 (mais comum, sem alteração)
  → Via IPv6: 2600:1f18::50 (funciona, mas não usual internamente)

Preferência do sistema operacional (RFC 6724):
  → IPv6 é preferido quando ambos estão disponíveis
  → Pode causar comportamento inesperado se IPv6 não está
    completamente configurado (rota, SG, etc.)
```

## Egress-Only Internet Gateway — saída sem entrada

Para subnets **privadas** com IPv6, o problema é que todos os endereços IPv6 são globalmente acessíveis — não existe "IPv6 privado" como o RFC 1918 do IPv4. A solução da AWS é o **Egress-Only Internet Gateway (EIGW)**:

```
O problema sem EIGW:
  Subnet "privada" com IPv6 → instância tem IP público IPv6
  Internet Gateway na rota → qualquer host na internet pode se conectar
  → A subnet não é privada!

Solução — Egress-Only Internet Gateway:
  Subnet "privada" com IPv6 → instância tem IP público IPv6
  EIGW na rota → instância PODE iniciar conexões para a internet
              → internet NÃO PODE iniciar conexões para a instância
              → comportamento equivalente ao NAT Gateway para IPv4

Analogia:
  NAT Gateway IPv4:   saída SIM, entrada NÃO (para hosts sem Elastic IP)
  EIGW IPv6:          saída SIM, entrada NÃO (para instâncias em subnets privadas)
```

```bash
# Criar Egress-Only Internet Gateway
aws ec2 create-egress-only-internet-gateway \
  --vpc-id vpc-0abc123

# Adicionar rota IPv6 para EIGW (subnet privada)
aws ec2 create-route \
  --route-table-id rtb-privada-0abc123 \
  --destination-ipv6-cidr-block ::/0 \
  --egress-only-internet-gateway-id eigw-0abc123
```

```
Configuração de route tables para dual-stack:

Route Table — Subnet Pública:
  Destino          Alvo
  10.0.0.0/16     local
  ::/0            igw-0abc123     ← IPv6: acesso bidirecional pela internet
  0.0.0.0/0       igw-0abc123     ← IPv4: acesso bidirecional (com Elastic IP)

Route Table — Subnet Privada:
  Destino          Alvo
  10.0.0.0/16     local
  ::/0            eigw-0abc123    ← IPv6: apenas saída (sem entrada)
  0.0.0.0/0       nat-0abc123     ← IPv4: apenas saída via NAT Gateway
```

## Security Groups e NACLs com IPv6

Security Groups e NACLs precisam de regras explícitas para IPv6 — regras IPv4 **não se aplicam** automaticamente ao tráfego IPv6:

```bash
# Adicionar regra IPv6 em Security Group
aws ec2 authorize-security-group-ingress \
  --group-id sg-0abc123 \
  --protocol tcp \
  --port 443 \
  --cidr-ipv6 ::/0    ← todo tráfego HTTPS IPv6

# Regra IPv4 equivalente (separada):
aws ec2 authorize-security-group-ingress \
  --group-id sg-0abc123 \
  --protocol tcp \
  --port 443 \
  --cidr 0.0.0.0/0   ← todo tráfego HTTPS IPv4

# Verificar regras (ambas as versões)
aws ec2 describe-security-groups \
  --group-ids sg-0abc123 \
  --query 'SecurityGroups[0].IpPermissions'
```

**Erro comum:** habilitar IPv6 na VPC, adicionar rotas IPv6 no Internet Gateway, mas esquecer de adicionar regras IPv6 nos Security Groups → todo tráfego IPv6 é bloqueado silenciosamente.

## Quando usar IPv6 na VPC

```
Use IPv6 quando:
  ✓ Aplicações que precisam servir clientes com IPv6-only
    (ISPs móveis em alguns países já são majoritariamente IPv6)
  ✓ Eliminar custo de NAT Gateway para saída de subnets privadas
    (EIGW é gratuito vs $0.045/h do NAT Gateway)
  ✓ Clusters EKS/ECS com muitos pods que precisam de IPs únicos
    (IPv6 elimina o problema de esgotamento de IPs da VPC no CNI)
  ✓ Conectividade com parceiros ou serviços que já são IPv6-only

Não precisa de IPv6 quando:
  ✗ Stack completamente interno (sem exposição à internet)
  ✗ Todos os serviços AWS necessários já suportam IPv4
  ✗ Time sem experiência com IPv6 (curva de aprendizado adicional)
  ✗ Aplicações legadas que não suportam IPv6
```

## Erros comuns e armadilhas

**Confiar apenas no "endereço privado IPv6":** não existe. Todo IPv6 na AWS é público. Se você quer isolamento, o Security Group é obrigatório — não há "segurança por obscuridade" como existe com RFC 1918.

**Esquecer regras IPv6 nos Security Groups:** ao migrar uma aplicação para dual-stack, as regras IPv4 existentes (`0.0.0.0/0`) não cobrem IPv6. O tráfego IPv6 é silenciosamente bloqueado até que você adicione regras `::/0` explicitamente.

**Usar Internet Gateway em subnet "privada" com IPv6:** sem EIGW, uma subnet com rota `::/0 → IGW` é efetivamente pública para IPv6, mesmo que você a chame de privada. Use sempre EIGW para subnets que devem ser acessíveis apenas "de dentro para fora".

## 🧩 Quiz de Fixação

1. Uma instância EC2 em uma subnet privada tem endereço IPv6 `2600:1f18::50` e a subnet tem rota `::/0 → EIGW`. Um atacante na internet tenta conectar na porta 22 (SSH) diretamente via IPv6. O que acontece e por quê?

2. Uma empresa usa NAT Gateway para saída à internet de suas subnets privadas (IPv4). O custo mensal do NAT Gateway é $150 (horas + dados). Eles migram para dual-stack com EIGW para tráfego IPv6. Qual percentual do custo do NAT pode ser eliminado com essa migração, e qual parte do tráfego ainda exigirá NAT?

3. Um desenvolvedor adiciona uma regra no Security Group: `TCP 443 from 0.0.0.0/0 (Allow)`. A aplicação recebe conexões HTTPS de clientes IPv4, mas clientes IPv6 recebem timeout. Por que, e como corrigir?

**Respostas:**

1) A tentativa de conexão é **bloqueada pelo EIGW**. O Egress-Only Internet Gateway funciona como um dispositivo de estado unidirecional: permite que a instância *inicie* conexões para a internet, mas **descarta automaticamente qualquer pacote de entrada que não seja resposta a uma conexão iniciada pela instância**. Como o atacante está iniciando a conexão (SYN TCP), o EIGW descarta o pacote antes mesmo de chegar à instância. Mesmo que o EIGW não existisse, o Security Group da instância também bloquearia (assumindo que a porta 22 não está aberta). O EIGW é a primeira linha de defesa no nível de rede; o Security Group é a segunda.

2) A migração para EIGW elimina **o custo de NAT para todo o tráfego IPv6 de saída**. Se a aplicação se conecta a destinos que suportam IPv6 (ex: APIs modernas, CDNs como CloudFront, S3, muitos serviços AWS), esse tráfego passa pelo EIGW (gratuito) em vez do NAT Gateway. O **tráfego que ainda exigirá NAT**: (a) conexões com destinos que são **IPv4-only** (servidores antigos, APIs de terceiros sem IPv6) — esses pacotes ainda precisam sair via IPv4 pelo NAT Gateway; (b) o próprio endereço IPv4 privado da instância nunca usa EIGW — IPv4 sem Elastic IP sempre precisa do NAT. O percentual de economia depende de quanto do tráfego de saída vai para destinos com suporte IPv6 — em ambientes modernos com AWS APIs e CDNs, pode ser 40-70%.

3) A regra `0.0.0.0/0` em um Security Group **cobre apenas tráfego IPv4** — não é um wildcard para ambos os protocolos. IPv6 usa a notação `::/0` como equivalente de "qualquer origem IPv6". Para receber HTTPS de clientes IPv6, é necessário adicionar uma segunda regra: `TCP 443 from ::/0 (Allow)`. A ausência dessa regra faz com que o Security Group bloqueie todo o tráfego IPv6 de entrada, resultando em timeout para clientes IPv6. Após adicionar a regra `::/0`, os clientes IPv6 conseguirão conectar. Isso é um ponto frequente de confusão ao migrar para dual-stack — você precisa duplicar as regras de Security Group para ambos os protocolos.
