### CIDR da VPC — faixas RFC 1918, tamanhos válidos e os 5 endereços reservados pela AWS

O CIDR (Classless Inter-Domain Routing) é a linguagem com que você define o espaço de endereçamento da sua VPC e de cada subnet. Escolher bem o CIDR no início evita retrabalho custoso no futuro — uma VPC com CIDR pequeno demais não pode crescer, e um CIDR que conflita com on-premises bloqueia a integração híbrida. Este arquivo cobre as regras exatas que a AWS impõe e como calcular corretamente o espaço disponível.

---

## Faixas permitidas para o CIDR primário da VPC

A AWS restringe o CIDR primário da VPC a três faixas RFC 1918 com tamanhos mínimo e máximo:

```
Faixas RFC 1918 permitidas para VPC:

┌─────────────────┬──────────────────┬──────────────────┬───────────────────┐
│ Faixa           │ Prefixo mínimo   │ Prefixo máximo   │ Nº de IPs         │
│                 │ (VPC maior)      │ (VPC menor)      │ (min → max)       │
├─────────────────┼──────────────────┼──────────────────┼───────────────────┤
│ 10.0.0.0/8      │ /16              │ /28              │ 65.536 → 16       │
│ 172.16.0.0/12   │ /16              │ /28              │ 65.536 → 16       │
│ 192.168.0.0/16  │ /16              │ /28              │ 65.536 → 16       │
└─────────────────┴──────────────────┴──────────────────┴───────────────────┘

Exemplos válidos:
  10.0.0.0/16      ✓  65.536 IPs — padrão mais comum para VPCs de produção
  10.0.0.0/20      ✓   4.096 IPs — VPC pequena para um serviço específico
  10.0.0.0/24      ✓     256 IPs — VPC muito pequena (cuidado com crescimento)
  172.16.0.0/16    ✓  65.536 IPs
  192.168.0.0/24   ✓     256 IPs
  10.0.0.0/28      ✓      16 IPs — menor VPC possível (11 utilizáveis)

Exemplos inválidos:
  10.0.0.0/8       ✗  Bloco /8 é grande demais (não permitido)
  10.0.0.0/15      ✗  Prefixo entre /8 e /16 não permitido
  10.0.0.0/29      ✗  Menor que /28 não permitido
  8.8.8.0/24       ✗  IP público — não é RFC 1918
  100.64.0.0/10    ✗  Carrier-grade NAT — não é RFC 1918
  169.254.0.0/16   ✗  Link-local — reservado para uso interno da AWS
```

## CIDRs secundários — expandir uma VPC existente

Uma VPC pode ter até **5 CIDRs associados** (1 primário + 4 secundários). Isso permite expandir o espaço de endereçamento sem recriar a VPC — mas com restrições:

```bash
# Adicionar CIDR secundário a uma VPC existente
aws ec2 associate-vpc-cidr-block \
  --vpc-id vpc-0abc123 \
  --cidr-block 10.1.0.0/16

# Listar os CIDRs de uma VPC
aws ec2 describe-vpcs \
  --vpc-ids vpc-0abc123 \
  --query 'Vpcs[0].CidrBlockAssociationSet'
```

```
Restrições dos CIDRs secundários:

1. Não podem se sobrepor com o CIDR primário
   10.0.0.0/16 (primário) + 10.0.128.0/17 (secundário) ✗ — sobreposição

2. Não podem se sobrepor com outros CIDRs secundários

3. Se o primário é 172.16.0.0/12, os secundários devem ser
   da mesma faixa (/16 a /28 dentro de 172.16.0.0/12)
   OU de faixas RFC 1918 diferentes

4. Máximo de 5 CIDRs por VPC (aumentável via support)

Cenário prático:
  VPC original:    10.0.0.0/16 (65.536 IPs — usados completamente)
  CIDR secundário: 10.2.0.0/16 (65.536 IPs adicionais)
  Novo total:      131.072 IPs na mesma VPC
```

## CIDR das subnets — regras específicas

Cada subnet tem seu próprio CIDR, que deve ser um **subconjunto do CIDR da VPC**:

```
VPC: 10.0.0.0/16

Subnets válidas (subconjuntos do /16):
  10.0.1.0/24    ✓  dentro de 10.0.0.0/16
  10.0.100.0/22  ✓  dentro de 10.0.0.0/16
  10.0.255.0/28  ✓  dentro de 10.0.0.0/16

Subnets inválidas:
  10.1.0.0/24    ✗  fora do bloco da VPC (10.1.x.x não está em 10.0.0.0/16)
  10.0.0.0/15    ✗  maior que o bloco da VPC (/15 contém o /16)

Regras adicionais:
  → Subnets dentro da mesma VPC não podem se sobrepor
  → Tamanho mínimo de subnet: /28 (16 IPs — 11 utilizáveis)
  → Tamanho máximo de subnet: igual ao CIDR da VPC
```

## Os 5 endereços reservados pela AWS por subnet

Em **cada subnet**, a AWS reserva 5 endereços que não podem ser atribuídos a instâncias:

```
Subnet 10.0.1.0/24 — 256 endereços totais:

┌─────────────┬──────────────────────────────────────────────────────────────┐
│ IP          │ Reserva / Função                                            │
├─────────────┼──────────────────────────────────────────────────────────────┤
│ 10.0.1.0    │ Endereço de rede — identifica a subnet (padrão TCP/IP)      │
├─────────────┼──────────────────────────────────────────────────────────────┤
│ 10.0.1.1    │ Roteador VPC — gateway padrão de todas as instâncias        │
│             │ (o "default gateway" que você configuraria num router físico) │
├─────────────┼──────────────────────────────────────────────────────────────┤
│ 10.0.1.2    │ DNS da AWS — Amazon Route 53 Resolver                       │
│             │ (resolve nomes internos e externos para instâncias na VPC)   │
├─────────────┼──────────────────────────────────────────────────────────────┤
│ 10.0.1.3    │ Reservado para uso futuro da AWS                            │
│             │ (nenhuma função atual — AWS mantém para expansões futuras)   │
├─────────────┼──────────────────────────────────────────────────────────────┤
│ 10.0.1.255  │ Endereço de broadcast — reservado por compatibilidade       │
│             │ (sem uso real na VPC — não existe L2 broadcast)              │
└─────────────┴──────────────────────────────────────────────────────────────┘

IPs utilizáveis: 10.0.1.4 a 10.0.1.254 = 251 hosts
```

### Como calcular hosts utilizáveis com as 5 reservas

```
Fórmula: hosts_utilizáveis = 2^(32 - prefixo) - 5

Exemplos práticos:

/28  →  2^4  - 5 = 16  - 5 = 11 hosts
/27  →  2^5  - 5 = 32  - 5 = 27 hosts
/26  →  2^6  - 5 = 64  - 5 = 59 hosts
/25  →  2^7  - 5 = 128 - 5 = 123 hosts
/24  →  2^8  - 5 = 256 - 5 = 251 hosts
/23  →  2^9  - 5 = 512 - 5 = 507 hosts
/22  →  2^10 - 5 = 1.024 - 5 = 1.019 hosts
/21  →  2^11 - 5 = 2.048 - 5 = 2.043 hosts
/20  →  2^12 - 5 = 4.096 - 5 = 4.091 hosts
/19  →  2^13 - 5 = 8.192 - 5 = 8.187 hosts
/18  →  2^14 - 5 = 16.384 - 5 = 16.379 hosts
/17  →  2^15 - 5 = 32.768 - 5 = 32.763 hosts
/16  →  2^16 - 5 = 65.536 - 5 = 65.531 hosts
```

## O .2 é sempre do CIDR da VPC, não da subnet

Uma confusão muito comum: o DNS interno da AWS (`.2`) é sempre o segundo IP do **CIDR primário da VPC**, não da subnet:

```
VPC CIDR: 10.0.0.0/16
DNS da AWS: 10.0.0.2  ← sempre .2 do bloco /16 da VPC

Subnet A: 10.0.5.0/24
  Default gateway: 10.0.5.1  ← .1 da subnet
  DNS da AWS:      10.0.0.2  ← .2 da VPC (não da subnet!)

Subnet B: 10.0.50.0/24
  Default gateway: 10.0.50.1  ← .1 da subnet
  DNS da AWS:      10.0.0.2   ← mesmo endereço de DNS

VPC com CIDR 192.168.0.0/16:
  DNS da AWS: 192.168.0.2

VPC com CIDR 172.31.0.0/16 (VPC Default):
  DNS da AWS: 172.31.0.2
```

Esse DNS é também conhecido como **169.254.169.253** — um alias de link-local que funciona em qualquer subnet, independente do CIDR da VPC.

## DHCP Options Sets — como instâncias obtêm seus IPs e DNS

A VPC usa DHCP para atribuir endereços automaticamente às instâncias. O **DHCP Options Set** configura:

```bash
# Ver o DHCP Options Set da VPC
aws ec2 describe-dhcp-options \
  --dhcp-options-ids $(aws ec2 describe-vpcs \
    --vpc-ids vpc-0abc123 \
    --query 'Vpcs[0].DhcpOptionsId' \
    --output text)

# Saída típica:
# {
#   "DhcpConfigurations": [
#     {"Key": "domain-name",         "Values": ["us-east-1.compute.internal"]},
#     {"Key": "domain-name-servers", "Values": ["AmazonProvidedDNS"]}
#   ]
# }
```

```
DHCP Options Set padrão:
  domain-name:         ec2.internal (us-east-1) ou <region>.compute.internal
  domain-name-servers: AmazonProvidedDNS (aponta para o .2 da VPC)
  
Personalização possível:
  → Apontar domain-name-servers para seus próprios servidores DNS
  → Útil quando você tem AD (Active Directory) ou BIND customizado
  → Após modificar, precisa renovar o DHCP nas instâncias (reboot ou dhclient)
```

## Verificando configurações de rede de uma instância EC2

```bash
# Dentro da instância Linux — verificar IP, gateway e DNS
ip addr show eth0
ip route show
cat /etc/resolv.conf

# Saída esperada para instância em 10.0.1.50/24:
# ip addr: inet 10.0.1.50/24
# ip route: default via 10.0.1.1 (gateway reservado pela AWS)
# resolv.conf: nameserver 10.0.0.2 (DNS da VPC)

# Verificar via Instance Metadata (sem precisar entrar na instância)
TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/local-ipv4
# Retorna: 10.0.1.50
```

## Erros comuns e armadilhas

**Escolher CIDR /24 para uma VPC inteira:** com uma VPC /24 (251 hosts utilizáveis), uma única subnet /24 ocupa toda a VPC — impossível criar subnets em múltiplas AZs. O mínimo recomendado para uma VPC de produção é /20 (4.091 IPs), mas /16 é o mais comum.

**Esquecer as 5 reservas ao dimensionar subnets:** planejar uma subnet /28 esperando 14 hosts disponíveis (como no modelo tradicional com 2 reservas) resulta em apenas 11 hosts utilizáveis com as 5 reservas da AWS. Para serviços como EKS com VPC CNI, onde cada pod consome um IP, esse detalhe é crítico.

**Criar subnets com CIDRs que se sobrepõem:** a AWS permite criar subnets em faixas diferentes dentro da VPC, mas blocos sobrepostos causam falha na criação. Sempre verifique antes de criar: `aws ec2 describe-subnets --filters Name=vpc-id,Values=<vpc-id>`.

**Usar 192.168.0.0/16 em VPCs que precisam de VPN com rede corporativa:** redes corporativas frequentemente usam `192.168.x.x` para Wi-Fi de escritório ou redes de laboratório. Um conflito de CIDR bloqueia completamente a conectividade VPN.

## 🧩 Quiz de Fixação

1. Uma VPC tem CIDR `10.0.0.0/20`. O arquiteto precisa criar 6 subnets — 2 públicas, 2 privadas de aplicação e 2 de banco de dados — em 2 AZs, com subnets de banco menores. Como dividir o /20 usando VLSM, e qual o número de hosts utilizáveis por subnet?

2. Uma instância EC2 em `10.0.5.0/24` tenta resolver `banco.interno.empresa.com` e falha. O comando `cat /etc/resolv.conf` mostra `nameserver 10.0.5.2`. Por que o DNS está falhando e qual é o endereço DNS correto?

3. Uma VPC tem CIDR primário `10.0.0.0/16` completamente esgotado (todas as subnets criadas). A equipe precisa adicionar mais capacidade sem recriar a VPC. Quais são as opções e qual é a limitação principal de cada uma?

**Respostas:**

1) VPC `10.0.0.0/20` tem 4.096 IPs (10.0.0.0 a 10.0.15.255). Proposta de divisão com VLSM:
```
Subnets públicas (pequenas — apenas LBs):
  10.0.0.0/26   → 59 hosts (AZ-a)
  10.0.0.64/26  → 59 hosts (AZ-b)

Subnets de aplicação (médias — EC2, containers):
  10.0.1.0/24   → 251 hosts (AZ-a)
  10.0.2.0/24   → 251 hosts (AZ-b)

Subnets de banco (pequenas — apenas RDS):
  10.0.3.0/27   → 27 hosts (AZ-a)
  10.0.3.32/27  → 27 hosts (AZ-b)

Espaço restante: 10.0.3.64 a 10.0.15.255 — disponível para crescimento futuro
```
Total alocado: ~2 × 59 + 2 × 251 + 2 × 27 = 724 IPs alocados, ~3.370 IPs reservados para crescimento.

2) O DNS está com o endereço **errado**. O `resolv.conf` aponta para `10.0.5.2` — que seria o segundo IP da subnet `10.0.5.0/24`. Mas o DNS da AWS não está no `.2` da subnet — está no **`.2` do CIDR da VPC**. Se a VPC tem CIDR `10.0.0.0/16`, o DNS correto é `10.0.0.2`. O endereço `10.0.5.2` não existe como serviço DNS — simplesmente não responde. Isso indica que o DHCP Options Set foi modificado manualmente ou o `resolv.conf` foi editado incorretamente dentro da instância. Para corrigir: editar `/etc/resolv.conf` para `nameserver 10.0.0.2`, ou corrigir o DHCP Options Set e renovar o lease com `sudo dhclient -r && sudo dhclient`.

3) **Opção 1 — CIDR secundário:** adicionar até 4 CIDRs secundários (ex: `10.1.0.0/16`). Limitação: os novos CIDRs não podem se sobrepor ao primário nem entre si; subnets criadas em CIDRs secundários são funcionalmente idênticas, mas rotas e políticas precisam ser atualizadas para cobrir os novos blocos. **Opção 2 — Solicitar aumento via Support:** é possível solicitar mais de 5 CIDRs associados via AWS Support. Limitação: o processo leva dias úteis e não é garantido. **Limitação principal de ambas:** o CIDR *primário* não pode ser modificado ou expandido — se `10.0.0.0/16` está esgotado, ele continuará sendo `/16`. Os CIDRs secundários são adicionados como blocos separados, e subnets existentes no primário não são automaticamente expandidas. Para uma expansão limpa a longo prazo, a melhor prática é criar uma nova VPC com CIDR bem dimensionado e migrar gradualmente.
