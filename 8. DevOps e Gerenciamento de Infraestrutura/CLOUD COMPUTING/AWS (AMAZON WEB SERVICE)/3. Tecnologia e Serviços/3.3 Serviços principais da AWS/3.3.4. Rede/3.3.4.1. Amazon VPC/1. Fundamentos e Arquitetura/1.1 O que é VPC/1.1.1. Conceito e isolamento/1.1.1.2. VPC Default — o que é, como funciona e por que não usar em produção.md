### VPC Default — o que é, como funciona e por que não usar em produção

A VPC Default é criada automaticamente pela AWS em cada região quando você cria uma conta. Ela existe para que você possa começar a usar EC2 e outros serviços imediatamente, sem precisar configurar rede. É conveniente para testes e aprendizado — mas tem características que a tornam inadequada e potencialmente perigosa para cargas de trabalho de produção.

---

## O que a AWS cria automaticamente na VPC Default

Ao criar uma conta AWS, a AWS provisiona automaticamente em cada região:

```
VPC Default (us-east-1 — exemplo):

VPC: 172.31.0.0/16
  │
  ├── Subnet Default us-east-1a: 172.31.0.0/20   (4.091 hosts)
  ├── Subnet Default us-east-1b: 172.31.16.0/20  (4.091 hosts)
  ├── Subnet Default us-east-1c: 172.31.32.0/20  (4.091 hosts)
  ├── Subnet Default us-east-1d: 172.31.48.0/20  (4.091 hosts)
  │
  ├── Internet Gateway (anexado à VPC)
  │
  ├── Route Table principal:
  │     10.0.0.0/8   → local
  │     172.31.0.0/16 → local
  │     0.0.0.0/0    → Internet Gateway  ← TODA subnet tem rota para internet
  │
  ├── Security Group default:
  │     Ingress: All traffic FROM sg-default (apenas de si mesmo)
  │     Egress:  All traffic to 0.0.0.0/0 (saída livre para qualquer lugar)
  │
  └── DHCP Options Set padrão
```

A AWS usa o bloco `172.31.0.0/16` — faixa RFC 1918 — para todas as VPCs default em todas as regiões de todas as contas.

## Características problemáticas da VPC Default

### 1. Todas as subnets são efetivamente públicas

A route table principal da VPC Default tem uma rota `0.0.0.0/0 → Internet Gateway` associada a **todas as subnets**. Isso significa que qualquer recurso lançado na VPC Default está em uma subnet com rota para a internet — não existe subnet verdadeiramente privada na VPC Default sem reconfiguração manual.

```
VPC Default — todas as subnets têm rota para internet:

Subnet A (172.31.0.0/20):
  Route: 0.0.0.0/0 → IGW  ← exposta à internet

Subnet B (172.31.16.0/20):
  Route: 0.0.0.0/0 → IGW  ← exposta à internet

Subnet C (172.31.32.0/20):
  Route: 0.0.0.0/0 → IGW  ← exposta à internet

→ Não existe camada de rede "privada" por padrão
```

### 2. IPs públicos atribuídos automaticamente

Por padrão, toda instância EC2 lançada em qualquer subnet da VPC Default recebe um **IP público automaticamente** (`MapPublicIpOnLaunch = true`). Isso significa que um banco de dados, um servidor de aplicação ou qualquer EC2 lançada sem configuração adicional tem um IP público diretamente acessível da internet — protegido apenas pelo Security Group.

```bash
# Verificar a configuração de IP público automático em subnets
aws ec2 describe-subnets \
  --filters Name=defaultForAz,Values=true \
  --query 'Subnets[*].{ID:SubnetId,AZ:AvailabilityZone,AutoPublicIP:MapPublicIpOnLaunch}'

# Saída típica da VPC Default:
# [
#   {"ID": "subnet-abc", "AZ": "us-east-1a", "AutoPublicIP": true},
#   {"ID": "subnet-def", "AZ": "us-east-1b", "AutoPublicIP": true},
#   ...
# ]
```

### 3. CIDR `172.31.0.0/16` igual em todas as contas

Todas as VPCs Default de todas as contas AWS do mundo usam o mesmo bloco `172.31.0.0/16`. Isso cria dois problemas práticos:

```
Problema 1 — Conflito ao conectar contas:
  Conta A (produção): VPC Default 172.31.0.0/16
  Conta B (staging):  VPC Default 172.31.0.0/16
  
  Tentar criar VPC Peering entre as duas: IMPOSSÍVEL
  (CIDRs sobrepostos não podem fazer peering)

Problema 2 — Conflito com rede on-premises:
  Rede corporativa: 172.16.0.0/12 (inclui 172.31.x.x)
  VPC Default: 172.31.0.0/16
  
  Tentar criar VPN site-to-site: conflito de roteamento
  (rotas ambíguas para o mesmo range de IPs)
```

### 4. Security Group default permissivo

O Security Group default permite **todo o tráfego de entrada de instâncias no mesmo SG** e **todo o tráfego de saída**. Em um ambiente onde múltiplos projetos e times compartilham a VPC Default, qualquer recurso no mesmo SG pode se comunicar livremente com qualquer outro — sem segregação.

```
Security Group "default" na VPC Default:

Ingress rules:
  All traffic | All ports | Source: sg-default (self-reference)
  → Todos os recursos no SG default se comunicam entre si sem restrição

Egress rules:
  All traffic | All ports | Destination: 0.0.0.0/0
  → Saída irrestrita para a internet
```

## Por que a VPC Default existe — o caso legítimo de uso

A VPC Default não é um erro de design — ela é intencional para reduzir a fricção de novos usuários:

```
Casos de uso legítimos da VPC Default:
  ✓ Aprendizado e experimentação (criar uma EC2 rapidamente para testar)
  ✓ Protótipos de curta duração onde segurança não é preocupação
  ✓ Scripts de CI/CD simples em ambientes de desenvolvimento pessoal
  ✓ Testes de conectividade e ferramentas de diagnóstico
  
Casos onde NÃO usar:
  ✗ Qualquer ambiente de produção
  ✗ Dados sensíveis (banco de dados, storage com PII)
  ✗ Ambientes compartilhados entre times
  ✗ Qualquer coisa que precise se conectar a on-premises
  ✗ Multi-conta com peering entre contas
```

## O que acontece se você deletar a VPC Default

A VPC Default pode ser deletada, e serviços como EC2 ainda funcionarão — desde que você use uma VPC customizada. Contudo, **uma vez deletada, a AWS não a recria automaticamente**. Para recriar manualmente:

```bash
# Verificar se a VPC Default existe
aws ec2 describe-vpcs \
  --filters Name=isDefault,Values=true \
  --query 'Vpcs[*].{VpcId:VpcId,CIDR:CidrBlock}'

# Recriar a VPC Default (se deletada acidentalmente)
aws ec2 create-default-vpc

# Recriar uma subnet default em uma AZ específica
aws ec2 create-default-subnet \
  --availability-zone us-east-1a
```

## VPC Default vs VPC Customizada — comparativo

```
┌───────────────────────────┬─────────────────────┬──────────────────────────┐
│ Aspecto                   │ VPC Default         │ VPC Customizada          │
├───────────────────────────┼─────────────────────┼──────────────────────────┤
│ CIDR                      │ 172.31.0.0/16 fixo  │ Qualquer RFC 1918        │
│ Subnets                   │ Todas públicas      │ Você decide              │
│ IP público automático     │ Sim (sempre)        │ Não (padrão)             │
│ Internet Gateway          │ Já anexado          │ Você cria e anexa        │
│ Subnets privadas          │ Não por padrão      │ Sim, criadas por você    │
│ NAT Gateway               │ Não existe          │ Você cria se necessário  │
│ Isolamento entre projetos │ Nenhum              │ Por VPC, subnet ou SG    │
│ Compatível com Peering    │ Frequentemente não  │ Sim (se CIDRs não batem) │
│ Compatível com VPN        │ Frequentemente não  │ Sim (com planejamento)   │
│ Adequada para produção    │ Não                 │ Sim                      │
└───────────────────────────┴─────────────────────┴──────────────────────────┘
```

## Boa prática — desabilitar IP público automático nas subnets Default

Se por algum motivo você precisa usar temporariamente a VPC Default, ao menos desabilite a atribuição automática de IPs públicos:

```bash
# Desabilitar IP público automático em todas as subnets default
aws ec2 describe-subnets \
  --filters Name=defaultForAz,Values=true \
  --query 'Subnets[*].SubnetId' \
  --output text | tr '\t' '\n' | while read subnet_id; do
    aws ec2 modify-subnet-attribute \
      --subnet-id "$subnet_id" \
      --no-map-public-ip-on-launch
    echo "Desabilitado IP público automático em $subnet_id"
done
```

## 🧩 Quiz de Fixação

1. Um desenvolvedor lança um banco de dados PostgreSQL em uma EC2 na VPC Default sem alterar nenhuma configuração. O Security Group default está aplicado. O banco tem um IP público. O DBA afirma "está seguro porque o Security Group bloqueia tudo". Avalie essa afirmação — ela está correta?

2. Uma empresa com 5 contas AWS (produção, staging, dev, sandbox, segurança) quer criar VPC Peering entre todas elas para comunicação interna. Todas usam a VPC Default. Por que essa arquitetura é inviável e qual é a solução?

3. Um time deletou a VPC Default de us-east-1 sem querer. Eles precisam lançar uma EC2 urgentemente para um teste. Quais são as duas opções disponíveis?

**Respostas:**

1) A afirmação está **parcialmente correta, mas insuficiente**. O Security Group default permite ingress apenas de outras instâncias no mesmo SG (`sg-default`), o que bloqueia acesso externo arbitrário. Porém há dois riscos sérios: (a) **qualquer instância adicionada ao mesmo Security Group default pode acessar o banco PostgreSQL na porta 5432** — em ambientes compartilhados, isso cria acesso lateral não intencional entre projetos; (b) **o Egress é completamente aberto** (`0.0.0.0/0`) — se o banco for comprometido via alguma vulnerabilidade de aplicação que permita execução de código, o atacante pode exfiltrar dados para qualquer destino na internet. Um banco de dados de produção deve estar em uma **subnet privada** (sem rota para internet), com Security Group que permite acesso **somente da camada de aplicação** na porta 5432 — nunca em uma subnet pública com IP público.

2) A arquitetura é inviável porque **todas as 5 contas usam o mesmo CIDR `172.31.0.0/16`** da VPC Default, e VPC Peering não funciona com CIDRs sobrepostos. Tentativas de criar peering entre qualquer par de contas resultariam em erro imediato. **Solução:** criar VPCs customizadas em cada conta com CIDRs únicos planejados (ex: produção `10.0.0.0/16`, staging `10.1.0.0/16`, dev `10.2.0.0/16`, etc.) e usar **AWS Transit Gateway** como hub central para conectar todas elas — muito mais escalável que múltiplos pares de peering para 5 contas.

3) **Opção 1:** recriar a VPC Default com `aws ec2 create-default-vpc` — a AWS recria automaticamente com todas as configurações padrão (subnets por AZ, Internet Gateway, route tables). Leva menos de 1 minuto. **Opção 2:** criar uma VPC customizada manualmente com os recursos mínimos necessários para o teste (VPC + subnet + Internet Gateway + route table + Security Group). Mais trabalhoso mas resulta em uma VPC mais segura. Para um teste urgente, a opção 1 é mais rápida; para qualquer coisa que possa se tornar permanente, a opção 2 é sempre preferível.
