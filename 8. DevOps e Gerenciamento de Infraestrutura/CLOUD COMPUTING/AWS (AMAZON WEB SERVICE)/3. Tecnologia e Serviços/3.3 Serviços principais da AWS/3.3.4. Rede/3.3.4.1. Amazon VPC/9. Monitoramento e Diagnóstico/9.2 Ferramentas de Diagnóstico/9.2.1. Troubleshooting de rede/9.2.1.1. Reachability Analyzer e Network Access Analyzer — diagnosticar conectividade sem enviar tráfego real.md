### VPC Reachability Analyzer e Network Access Analyzer — diagnóstico de conectividade sem tráfego

Quando uma instância EC2 não consegue se conectar a outra, o troubleshooting manual envolve verificar Security Groups, NACLs, Route Tables, VPC Peerings e Transit Gateways — um por um, em cada hop do caminho. O **VPC Reachability Analyzer** automatiza esse processo: analisa a configuração de rede logicamente e determina se um pacote conseguiria chegar de A a B, e se não consegue, exatamente onde seria bloqueado. O **Network Access Analyzer** vai além: varre toda a sua rede identificando caminhos de acesso não intencionais e problemas de compliance.

---

## VPC Reachability Analyzer

### O que faz

```
Reachability Analyzer:
  → Analisa CONFIGURAÇÃO de rede (não envia tráfego real)
  → Verifica: Security Groups, NACLs, Route Tables, VPC Peering,
              Transit Gateway, Internet Gateway, NAT Gateway,
              Load Balancers, VPN Connections
  → Resultado: REACHABLE ou NOT_REACHABLE
  → Se não alcançável: identifica exatamente qual componente bloqueia
  → Custo: $0.10 por análise executada

Analogia:
  Sem Reachability Analyzer: verificar manualmente cada porta, regra, tabela
  Com Reachability Analyzer: "AWS, verifica por mim se A consegue falar com B"
```

### Criando uma análise

```bash
# Criar Network Insights Path (origem e destino)
aws ec2 create-network-insights-path \
  --source eni-origem-0abc123 \
  --destination eni-destino-0def456 \
  --protocol tcp \
  --destination-port 5432 \
  --tag-specifications 'ResourceType=network-insights-path,Tags=[{Key=Name,Value=path-app-rds}]'
# Retorna: {"NetworkInsightsPathId": "nip-0abc123"}

# Iniciar a análise
aws ec2 start-network-insights-analysis \
  --network-insights-path-id nip-0abc123
# Retorna: {"NetworkInsightsAnalysisId": "nia-0abc123"}

# Aguardar o resultado (segundos)
aws ec2 describe-network-insights-analyses \
  --network-insights-analysis-ids nia-0abc123 \
  --query 'NetworkInsightsAnalyses[0].{
    Status:Status,
    NetworkPathFound:NetworkPathFound,
    ExplanationCode:Explanations[0].ExplanationCode,
    Component:Explanations[0].Component.Id,
    Direction:Explanations[0].Direction
  }'
```

### Interpretando os resultados

```
NetworkPathFound: true
  → Caminho é alcançável — conectividade existe
  → Exibe o path hop a hop: ENI → SG → NACL → Route Table → ENI destino

NetworkPathFound: false
  → Caminho NÃO é alcançável
  → ExplanationCode indica o motivo:

Explanation Codes mais comuns:
  SECURITY_GROUP_RULE_BLOCKED
    → Um Security Group bloqueia o tráfego
    → O resultado mostra: qual SG, qual regra (ou ausência de regra)

  NETWORK_ACL_RULE_BLOCKED
    → Uma NACL bloqueia o tráfego
    → O resultado mostra: qual NACL, qual regra de DENY

  NO_ROUTE_TO_DESTINATION
    → Nenhuma rota na Route Table leva ao destino
    → O resultado mostra: qual Route Table, qual CIDR não tem rota

  ROUTE_TABLE_NOT_FOUND
    → Subnet sem Route Table associada
    
  MISSING_TARGET_CONFIGURATION
    → Target Group do Load Balancer não tem instâncias saudáveis

  VPC_PEERING_CONNECTION_NOT_ACTIVE
    → VPC Peering em estado incorreto (pending, failed, etc.)

  TRANSIT_GATEWAY_ATTACHMENT_NOT_FOUND
    → Attachment de TGW não existe ou não está ativo
```

### Exemplo completo de troubleshooting

```python
# Python — análise automatizada
import boto3
import time

ec2 = boto3.client('ec2', region_name='us-east-1')

def verificar_conectividade(
    origem_eni: str,
    destino_eni: str,
    porta: int,
    protocolo: str = 'tcp'
) -> dict:
    """Verifica se a origem consegue alcançar o destino na porta especificada."""
    
    # Criar path
    path = ec2.create_network_insights_path(
        Source=origem_eni,
        Destination=destino_eni,
        Protocol=protocolo,
        DestinationPort=porta
    )
    path_id = path['NetworkInsightsPath']['NetworkInsightsPathId']
    
    # Iniciar análise
    analysis = ec2.start_network_insights_analysis(
        NetworkInsightsPathId=path_id
    )
    analysis_id = analysis['NetworkInsightsAnalysis']['NetworkInsightsAnalysisId']
    
    # Aguardar resultado (polling)
    for _ in range(30):  # timeout de 60 segundos
        time.sleep(2)
        result = ec2.describe_network_insights_analyses(
            NetworkInsightsAnalysisIds=[analysis_id]
        )
        analysis_data = result['NetworkInsightsAnalyses'][0]
        
        if analysis_data['Status'] == 'succeeded':
            reachable = analysis_data.get('NetworkPathFound', False)
            explanations = analysis_data.get('Explanations', [])
            
            return {
                'reachable': reachable,
                'path_id': path_id,
                'analysis_id': analysis_id,
                'explanation': explanations[0] if explanations else None
            }
    
    return {'error': 'Timeout aguardando análise'}

# Uso
resultado = verificar_conectividade(
    origem_eni='eni-app-0abc123',
    destino_eni='eni-rds-0def456',
    porta=5432
)

if resultado['reachable']:
    print("✓ Conectividade OK — app consegue alcançar o RDS na porta 5432")
else:
    exp = resultado['explanation']
    if exp:
        print(f"✗ Bloqueado por: {exp.get('ExplanationCode')}")
        print(f"  Componente: {exp.get('Component', {}).get('Id')}")
    else:
        print("✗ Não alcançável — sem explicação detalhada")
```

## Network Access Analyzer

### O que faz — diferença do Reachability Analyzer

```
Reachability Analyzer:
  "Consigo ir de A até B?"
  → Analisa um path específico sob demanda
  → Ponto a ponto, dirigido pelo usuário

Network Access Analyzer:
  "Quais paths de acesso INESPERADOS existem na minha rede?"
  → Varre toda a rede automaticamente
  → Identifica violações de política (compliance as code)
  → "Alguma instância de dev consegue alcançar o banco de produção?"
  → "Alguma EC2 tem acesso direto à internet sem passar pelo firewall?"
  → Custo: $0.002 por hora de análise por recurso analisado
```

### Network Access Scope — definindo o que analisar

```
Um Network Access Scope define:
  1. Source: de onde o tráfego pode vir (ou não deveria vir)
  2. Destination: para onde vai (ou não deveria ir)
  3. Condições: protocolos, portas, serviços AWS

Exemplo — detectar instâncias com acesso direto à internet:
  Source: Internet Gateway
  Destination: EC2 instances com tags Environment=production
  → Qualquer EC2 de produção diretamente acessível da internet
     sem passar por Load Balancer? → violação!
```

```bash
# Criar Network Access Scope
aws ec2-instance-connect create-network-insights-access-scope \
  --match-paths '[{
    "Source": {
      "ResourceStatement": {
        "ResourceTypes": ["AWS::EC2::InternetGateway"]
      }
    },
    "Destination": {
      "ResourceStatement": {
        "ResourceTypes": ["AWS::EC2::Instance"],
        "Tags": [{"Key": "Environment", "Value": "production"}]
      }
    }
  }]' \
  --exclude-paths '[{
    "Source": {
      "ResourceStatement": {
        "ResourceTypes": ["AWS::ElasticLoadBalancingV2::LoadBalancer"]
      }
    }
  }]'
```

### Casos de uso do Network Access Analyzer

```
1. Compliance — verificar isolamento de ambientes:
   "Nenhuma instância de Dev tem acesso ao banco de Produção"
   
   Scope: source=dev-subnet, destination=prod-rds
   → Se encontrar paths: violação de isolamento

2. Auditoria de segurança — instâncias expostas à internet:
   "Todas as instâncias de produção só recebem tráfego do ALB"
   
   Scope: source=internet-gateway, destination=prod-instances
   Exclusão: paths que passam pelo ALB
   → Instâncias com IP público direto = não conformes

3. Verificação de Zero Trust:
   "Todo acesso entre serviços usa endpoints privados (não internet)"
   
   Scope: source=VPC, destination=AWS Services
   → Tráfego indo para endpoints públicos = usar VPC endpoints

4. Detecção de shadow IT:
   "Nenhum recurso tem conectividade com IPs fora do nosso espaço"
   
   Scope: source=VPC-resources, destination=external-ips
   → Conexões para IPs não corporativos = investigar
```

## Quando usar cada ferramenta

```
Para troubleshooting de conectividade específica:
  → VPC Reachability Analyzer
  → "Por que a instância A não consegue se conectar ao banco B?"
  → Resultado em segundos, identifica o problema exato

Para auditoria de segurança e compliance:
  → Network Access Analyzer
  → "Existe algum caminho de acesso não autorizado na minha rede?"
  → Varre a rede inteira procurando violações de política

Para análise de tráfego real (o que JÁ passou):
  → VPC Flow Logs
  → "Quem se conectou a quem nas últimas 24 horas?"
  → Dados históricos do tráfego real

Combinação poderosa:
  1. Flow Logs identificam tráfego suspeito (ex: IP inesperado acessando banco)
  2. Reachability Analyzer confirma se a rota existe (ou se já foi corrigida)
  3. Network Access Analyzer verifica se há outras rotas similares na rede
```

## Custo e boas práticas

```
VPC Reachability Analyzer:
  $0.10 por análise executada
  → 100 análises/mês = $10
  → Razoável para debugging pontual
  → Evitar em pipelines CI/CD com muitas execuções

Network Access Analyzer:
  $0.002/hora por recurso analisado
  → Análise de 1000 recursos por 1 hora = $2
  → Executar periodicamente (diário/semanal) para compliance
  → Não deixar rodando continuamente sem necessidade

Boas práticas:
  → Salvar Network Insights Paths para reutilizar (não recriar a cada análise)
  → Nomear paths com tags descritivas (app→rds, bastion→app, etc.)
  → Integrar Network Access Analyzer com AWS Security Hub para alertas automáticos
  → Executar após cada mudança de infraestrutura como teste de regressão
```

## Integração com CI/CD — testes de conectividade automatizados

```python
# Executar verificação de conectividade após deploy
import boto3
import sys

CONNECTIVITY_TESTS = [
    {
        "name": "App → RDS PostgreSQL",
        "source": "eni-app-0abc123",
        "destination": "eni-rds-0def456",
        "port": 5432
    },
    {
        "name": "ALB → App",
        "source": "eni-alb-0ghi789",
        "destination": "eni-app-0abc123",
        "port": 8080
    },
    {
        "name": "App NÃO deve acessar internet diretamente",
        "source": "eni-app-0abc123",
        "destination": "igw-0jkl012",
        "port": 443,
        "expected_reachable": False  # DEVE falhar!
    }
]

def run_connectivity_tests():
    falhas = []
    
    for test in CONNECTIVITY_TESTS:
        resultado = verificar_conectividade(
            test["source"], test["destination"], test["port"]
        )
        
        esperado = test.get("expected_reachable", True)
        atual = resultado.get("reachable", False)
        
        if atual != esperado:
            falhas.append({
                "test": test["name"],
                "esperado": "REACHABLE" if esperado else "NOT_REACHABLE",
                "atual": "REACHABLE" if atual else "NOT_REACHABLE",
                "explicacao": resultado.get("explanation")
            })
    
    if falhas:
        print("❌ Testes de conectividade FALHARAM:")
        for f in falhas:
            print(f"  {f['test']}: esperado {f['esperado']}, obtido {f['atual']}")
        sys.exit(1)
    else:
        print("✓ Todos os testes de conectividade PASSARAM")

run_connectivity_tests()
```

## Erros comuns e armadilhas

**Achar que Reachability Analyzer é um teste de conectividade em tempo real:** a ferramenta analisa a **configuração** atual da rede — não envia pacotes reais. Se a configuração está correta mas há um problema em camadas superiores (aplicação, sistema operacional, firewall interno da instância), o Reachability Analyzer retorna "REACHABLE" mesmo com o problema real. Complementar sempre com testes reais (`nc`, `telnet`, `curl`).

**Não reutilizar Network Insights Paths:** criar um novo path a cada análise gasta $0.10 por vez e acumula objetos não utilizados. Criar paths nomeados para cada teste recorrente e reutilizá-los.

**Esperar que Network Access Analyzer verifique estados dinâmicos:** a ferramenta analisa configuração estática (Security Groups, Route Tables, etc.). Não detecta problemas como "NAT Gateway está com erro" ou "instância está fora de serviço" — apenas verifica se a configuração permitiria o acesso.

## 🧩 Quiz de Fixação

1. O Reachability Analyzer retorna `NetworkPathFound: true` para a análise `app-instance → rds-instance:5432`. Mas a aplicação continua recebendo timeout ao tentar conectar ao banco. Quais são as causas possíveis que o Reachability Analyzer NÃO detecta?

2. Uma empresa quer usar Network Access Analyzer para garantir que nenhuma instância EC2 de produção pode ser alcançada diretamente pela internet (apenas via ALB). Como definir o scope e a exclusão corretamente?

3. Por que integrar o VPC Reachability Analyzer em pipelines de CI/CD como "teste de regressão de rede" é uma boa prática, e qual limitação deve ser considerada para não criar falsos negativos?

**Respostas:**

1) O Reachability Analyzer verifica apenas a **configuração de rede** (layer 3/4). Problemas que ele NÃO detecta: (a) **Firewall interno da instância (iptables/nftables):** a instância EC2 pode ter regras de firewall no SO que bloqueiam o tráfego mesmo que a rede permita; (b) **Serviço não está ouvindo:** o PostgreSQL pode não estar rodando ou pode estar ouvindo apenas em `127.0.0.1` (localhost) em vez de `0.0.0.0`; (c) **Autenticação/autorização no banco:** o PostgreSQL pode estar rodando mas rejeitando a conexão por credenciais incorretas ou `pg_hba.conf` restritivo; (d) **Problema de DNS:** a aplicação pode estar resolvendo para o IP errado; (e) **Instância sobrecarregada:** timeout por CPU/memória, não por rede; (f) **Conexão esgotada:** limite de `max_connections` do banco atingido. **Diagnóstico complementar necessário:** `nc -zv rds-host 5432` dentro da instância EC2, verificar logs do PostgreSQL, `ss -tlnp` para confirmar que o serviço está ouvindo.

2) **Scope correto para detectar EC2 diretamente acessível da internet:** Source: `Internet Gateway` (recurso AWS tipo `AWS::EC2::InternetGateway`), Destination: instâncias EC2 com tag `Environment=production`. **Exclusão:** paths que **passam por** um Load Balancer (`AWS::ElasticLoadBalancingV2::LoadBalancer`). A lógica é: "quero ver todos os caminhos de IGW até EC2 de produção que NÃO passam pelo ALB". Se o Network Access Analyzer encontrar algum path que vai diretamente do IGW para uma EC2 de produção sem passar pelo ALB, isso é uma violação — a instância tem IP público ou está em subnet pública diretamente acessível. O resultado mostraria exatamente quais instâncias violam a política, permitindo corrigir (remover IP público, mover para subnet privada, ou corrigir Security Group).

3) **Por que é boa prática:** após cada deploy de infraestrutura (Terraform, CloudFormation), a configuração de rede pode mudar inadvertidamente — uma Security Group rule removida, uma Route Table incorreta, um NACL com nova regra de DENY. O Reachability Analyzer como teste de regressão valida que as conexões necessárias ainda existem e as conexões proibidas ainda estão bloqueadas (`expected_reachable: false`). É como um smoke test de rede que roda em segundos sem enviar tráfego real, custando apenas $0.10 por análise. **Limitação — falsos negativos:** o Reachability Analyzer testa a **configuração atual** no momento da análise. Se a infraestrutura muda **depois** do teste (ex: alguém abre uma Security Group rule manualmente no console horas depois do deploy), o teste passou mas a vulnerabilidade existe. Para contínua validação, combinar com o **Network Access Analyzer** rodando periodicamente (diário/horário) que varre toda a rede procurando violações — não apenas testa os paths conhecidos, mas também descobre paths inesperados que ninguém pensou em testar.
