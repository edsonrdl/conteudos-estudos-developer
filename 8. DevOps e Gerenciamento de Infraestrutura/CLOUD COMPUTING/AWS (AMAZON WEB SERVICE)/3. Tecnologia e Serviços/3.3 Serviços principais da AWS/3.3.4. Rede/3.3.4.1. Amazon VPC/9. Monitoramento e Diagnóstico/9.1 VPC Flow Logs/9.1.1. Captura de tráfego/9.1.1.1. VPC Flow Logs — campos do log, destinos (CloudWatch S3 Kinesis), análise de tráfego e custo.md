### VPC Flow Logs — campos do log, destinos, análise de tráfego e custo

VPC Flow Logs capturam informações sobre o tráfego de rede que entra e sai das interfaces de rede (ENIs) na VPC. Não é uma captura de pacotes completa — é um registro de metadados de fluxo (source IP, destination IP, ports, protocol, bytes, action). É a ferramenta primária para debugging de conectividade, análise de segurança, detecção de anomalias e troubleshooting de Security Groups e NACLs.

---

## O que o Flow Log captura

```
Flow Log NÃO é:
  ✗ Captura de pacotes (não vê o conteúdo)
  ✗ Dados em tempo real (há atraso de segundos a minutos)

Flow Log É:
  ✓ Metadados de cada fluxo TCP/UDP/ICMP
  ✓ Endereços IP de origem e destino
  ✓ Portas de origem e destino
  ✓ Protocolo
  ✓ Quantidade de bytes e pacotes
  ✓ Ação (ACCEPT ou REJECT pelo Security Group/NACL)
  ✓ Direção do tráfego (INGRESS/EGRESS)
```

---

## Campos do VPC Flow Log — v2 (padrão)

```
version account-id interface-id srcaddr dstaddr srcport dstport protocol packets bytes windowstart windowend action log-status

Exemplo de linha de log (v2):
2 123456789012 eni-abc12345 10.0.1.50 10.0.2.100 52341 5432 6 15 2048 1705312800 1705312860 ACCEPT OK

Campos:
  version:       2 (versão do formato)
  account-id:    123456789012 (conta AWS)
  interface-id:  eni-abc12345 (ENI capturada)
  srcaddr:       10.0.1.50 (IP de origem)
  dstaddr:       10.0.2.100 (IP de destino)
  srcport:       52341 (porta de origem)
  dstport:       5432 (porta de destino — PostgreSQL)
  protocol:      6 (TCP=6, UDP=17, ICMP=1)
  packets:       15 (pacotes no fluxo)
  bytes:         2048 (bytes no fluxo)
  windowstart:   1705312800 (início — Unix timestamp)
  windowend:     1705312860 (fim — Unix timestamp)
  action:        ACCEPT (permitido) ou REJECT (bloqueado)
  log-status:    OK | NODATA | SKIPDATA
```

### Campos adicionais — v3, v4 e v5

```
# Versão 3 adiciona:
vpc-id            → ID da VPC (útil em ambientes multi-VPC)
subnet-id         → Subnet da ENI
instance-id       → ID da instância EC2 (se aplicável)
tcp-flags         → Flags TCP: SYN(2), FIN(1), RST(4), SYN-ACK(18)
type              → IPv4 ou IPv6
pkt-srcaddr       → IP real do pacote (vs IP do NAT)
pkt-dstaddr       → IP real de destino
region            → Região AWS

# Versão 4 adiciona:
pkt-src-aws-service  → serviço AWS de origem (S3, EC2, etc.)
pkt-dst-aws-service  → serviço AWS de destino
flow-direction       → ingress ou egress (perspectiva da ENI)
traffic-path         → como o pacote viajou (through IGW, VPN, etc.)

# Versão 5 adiciona:
ecs-cluster-name     → cluster ECS (se aplicável)
ecs-cluster-arn
ecs-container-instance-arn
ecs-task-arn
ecs-task-definition-arn
ecs-service-name
```

## Criando Flow Logs

```bash
# Flow Log para toda a VPC → CloudWatch Logs
aws ec2 create-flow-logs \
  --resource-type VPC \
  --resource-ids vpc-0abc123 \
  --traffic-type ALL \              # ALL | ACCEPT | REJECT
  --log-destination-type cloud-watch-logs \
  --log-group-name /vpc/flow-logs/producao \
  --deliver-logs-permission-arn arn:aws:iam::123:role/FlowLogsRole \
  --log-format '${version} ${account-id} ${interface-id} ${srcaddr} ${dstaddr} ${srcport} ${dstport} ${protocol} ${packets} ${bytes} ${start} ${end} ${action} ${log-status} ${vpc-id} ${subnet-id} ${instance-id} ${flow-direction}'

# Flow Log para uma subnet específica → S3 (mais barato para retenção longa)
aws ec2 create-flow-logs \
  --resource-type Subnet \
  --resource-ids subnet-0abc123 \
  --traffic-type ALL \
  --log-destination-type s3 \
  --log-destination arn:aws:s3:::meu-bucket-logs/flow-logs/ \
  --log-format '${version} ${account-id} ${interface-id} ${srcaddr} ${dstaddr} ${srcport} ${dstport} ${protocol} ${packets} ${bytes} ${start} ${end} ${action} ${log-status}'

# Flow Log para uma ENI específica → Kinesis Data Firehose (streaming)
aws ec2 create-flow-logs \
  --resource-type NetworkInterface \
  --resource-ids eni-0abc123 \
  --traffic-type REJECT \           # apenas tráfego rejeitado
  --log-destination-type kinesis-data-firehose \
  --log-destination arn:aws:firehose:...:deliverystream/vpc-flow-logs
```

## Destinos dos Flow Logs — comparativo

```
CloudWatch Logs:
  → Log streams criados por ENI
  → Busca com CloudWatch Logs Insights
  → Alertas em tempo real com CloudWatch Alarms
  → Retenção configurável (7 dias, 30 dias, 1 ano...)
  → Custo: $0.50/GB ingestão + $0.03/GB armazenamento/mês
  → Melhor para: alertas em tempo real, debugging ativo

S3:
  → Arquivos Parquet ou texto delimitado
  → Consultas via Amazon Athena (SQL barato)
  → Retenção via S3 Lifecycle Policies
  → Custo: $0.023/GB armazenamento + custo de Athena ($5/TB scaneado)
  → Melhor para: análise histórica, compliance, grandes volumes, custo

Kinesis Data Firehose:
  → Streaming em tempo real
  → Pode enviar para S3, Elasticsearch, Redshift, Splunk
  → Transformação com Lambda antes de armazenar
  → Custo: $0.029/GB processado
  → Melhor para: SIEM, análise em tempo real, integração com terceiros
```

## Analisando Flow Logs

### CloudWatch Logs Insights

```sql
-- Buscar conexões rejeitadas na última hora
fields @timestamp, srcaddr, dstaddr, dstport, action
| filter action = "REJECT"
| filter @timestamp > ago(1h)
| sort @timestamp desc
| limit 100

-- Top 10 IPs que mais tentaram conectar (possível port scanning)
fields srcaddr
| filter action = "REJECT"
| stats count(*) as tentativas by srcaddr
| sort tentativas desc
| limit 10

-- Tráfego para porta específica (ex: buscar acesso ao banco 5432)
fields @timestamp, srcaddr, dstaddr, dstport, action, bytes
| filter dstport = 5432
| sort bytes desc

-- Fluxos grandes (possível exfiltração de dados)
fields srcaddr, dstaddr, dstport, bytes, action
| filter bytes > 10000000  -- maior que 10 MB
| sort bytes desc
| limit 50

-- Conexões de um IP específico
fields @timestamp, dstaddr, dstport, action, bytes
| filter srcaddr = "10.0.1.50"
| stats sum(bytes) as total_bytes by dstaddr, dstport
| sort total_bytes desc
```

### Athena para análise de Flow Logs no S3

```sql
-- Criar tabela Athena para Flow Logs (formato padrão v2)
CREATE EXTERNAL TABLE vpc_flow_logs (
  version INT,
  account_id STRING,
  interface_id STRING,
  srcaddr STRING,
  dstaddr STRING,
  srcport INT,
  dstport INT,
  protocol INT,
  packets BIGINT,
  bytes BIGINT,
  windowstart BIGINT,
  windowend BIGINT,
  action STRING,
  log_status STRING
)
PARTITIONED BY (dt STRING)
ROW FORMAT DELIMITED
FIELDS TERMINATED BY ' '
LOCATION 's3://meu-bucket-logs/flow-logs/'
TBLPROPERTIES ("skip.header.line.count"="1");

-- Top talkers — quais IPs geram mais tráfego
SELECT srcaddr, SUM(bytes) as total_bytes
FROM vpc_flow_logs
WHERE dt = '2024-01-15'
  AND action = 'ACCEPT'
GROUP BY srcaddr
ORDER BY total_bytes DESC
LIMIT 10;

-- Conexões rejeitadas por Security Group
SELECT srcaddr, dstaddr, dstport, COUNT(*) as rejeicoes
FROM vpc_flow_logs
WHERE dt = '2024-01-15'
  AND action = 'REJECT'
GROUP BY srcaddr, dstaddr, dstport
ORDER BY rejeicoes DESC;

-- Análise de protocolo
SELECT 
  CASE protocol
    WHEN 6  THEN 'TCP'
    WHEN 17 THEN 'UDP'
    WHEN 1  THEN 'ICMP'
    ELSE CAST(protocol AS VARCHAR)
  END AS protocolo,
  SUM(bytes) as total_bytes,
  COUNT(*) as fluxos
FROM vpc_flow_logs
WHERE dt = '2024-01-15'
GROUP BY protocol
ORDER BY total_bytes DESC;
```

## Interpretando o campo `action`

```
ACCEPT: tráfego foi permitido pelo Security Group E pela NACL
REJECT: tráfego foi bloqueado pelo Security Group OU pela NACL

Para distinguir se o REJECT foi pelo SG ou pela NACL:
  Verificar a NACL da subnet
  Verificar o Security Group da instância
  
  Dica: REJECT na ENI de destino → SG ou NACL de destino
        REJECT na ENI de origem → NACL de origem (para tráfego de saída)

log-status:
  OK:       dados capturados normalmente
  NODATA:   nenhum tráfego na janela de aggregação (normal em interfaces ociosas)
  SKIPDATA: alguns logs pulados por limite de capacidade
            (cuidado: você está perdendo dados de captura!)
```

## Flow Logs e custo — estimativas

```
Fatores de custo:
  1. Volume de tráfego na VPC
  2. Destino escolhido (CloudWatch é mais caro que S3)
  3. Versão do formato (mais campos = mais dados = mais custo)
  4. Filtro (ALL vs REJECT — capturar apenas rejeições é muito mais barato)

Exemplo de estimativa para VPC com 10 instâncias EC2:
  Tráfego médio: 1 GB/hora = 720 GB/mês
  
  Flow Logs para CloudWatch (tráfego gerado ~20% do original):
    ~144 GB/mês de logs
    Ingestão: 144 × $0.50 = $72/mês
    Armazenamento (30 dias): 144 × $0.03 = $4.32/mês
    Total: ~$76/mês
  
  Flow Logs para S3 (Parquet — 10x compressão):
    ~14 GB/mês
    S3 storage: 14 × $0.023 = $0.32/mês
    Athena queries (sob demanda): $5/TB scaneado
    Total: ~$1-5/mês dependendo de queries
  
  Estratégia de custo:
    → S3 para retenção histórica e análise
    → CloudWatch para alertas em tempo real (apenas REJECT)
    → Filtrar: REJECT only reduz ~90% do volume vs ALL
```

## Erros comuns e armadilhas

**Não criar IAM role correta para Flow Logs:** o serviço de Flow Logs precisa de permissão para criar log groups e streams no CloudWatch. Sem a role correta, os logs são silenciosamente não enviados — sem erro visível.

**`log-status: SKIPDATA`:** indica que o sistema de captura está sobrecarregado e pulando registros. Em redes com altíssimo volume de tráfego, Flow Logs pode não capturar 100% dos fluxos. Monitorar essa métrica.

**Usar versão v2 e perder campos úteis:** a versão padrão (v2) não inclui `vpc-id`, `subnet-id`, `flow-direction`. Em ambientes com múltiplas VPCs e subnets, esses campos são essenciais para debugging. Sempre usar formato customizado com os campos relevantes.

**Flow Logs em CloudWatch sem configurar retenção:** sem configurar retenção no Log Group, logs ficam armazenados indefinidamente — custo crescendo sem limite. Configurar retenção de 30-90 dias para CloudWatch e mover histórico para S3.

## 🧩 Quiz de Fixação

1. Um log de Flow Logs mostra: `srcaddr=10.0.1.50 dstaddr=10.0.2.100 dstport=5432 action=REJECT`. O Security Group do RDS em `10.0.2.100` tem a regra `TCP 5432 from sg-app`. A instância em `10.0.1.50` tem `sg-app`. Por que o tráfego ainda foi rejeitado e onde investigar?

2. Uma equipe quer usar Flow Logs para detectar em tempo real quando qualquer IP desconhecido tenta conectar na porta 22 (SSH) de qualquer instância. Qual destino de Flow Logs, qual filtro e qual serviço AWS para alertas seria a combinação mais adequada?

3. Uma análise de Flow Logs no Athena retorna `log_status = SKIPDATA` para 5% dos registros em horário de pico. O que isso significa e quais são as implicações para uma análise de segurança?

**Respostas:**

1) O Security Group permite o acesso (sg-app está autorizado para porta 5432), mas o Flow Log mostra REJECT. A causa mais provável é a **NACL da subnet** onde o RDS está localizado. NACLs são stateless e operam no nível de subnet — uma regra DENY na NACL supera o ALLOW do Security Group. **Como investigar:** verificar a NACL associada à subnet do RDS com `describe-network-acls`. Verificar se há uma regra com número baixo (avaliada primeiro) que bloqueia TCP da subnet `10.0.1.0/24` ou do IP `10.0.1.50` na porta 5432. Também verificar as regras de EGRESS da NACL da subnet do cliente — NACLs são stateless, então também precisam de regra de saída para portas efêmeras (1024-65535) para permitir a resposta.

2) Combinação ideal: (a) **Destino: CloudWatch Logs** — permite consultas em tempo quase real e integração com alarmes; (b) **Filtro: `--traffic-type REJECT`** — capturar apenas tráfego rejeitado reduz 90%+ do volume e é justamente o que queremos monitorar (tráfego bloqueado na porta 22 indica tentativas de invasão); (c) **CloudWatch Logs Insights + CloudWatch Alarm** — criar uma métrica de filtro no Log Group para padrão `dstport=22 action=REJECT` e configurar alarme quando o count superar um threshold (ex: 5 tentativas em 1 minuto); (d) **Alternativa mais avançada:** enviar para **Kinesis Data Firehose → Lambda** para enriquecimento em tempo real e enviar alerta via SNS com contexto completo. O filtro REJECT é crucial — sem ele, cada conexão SSH legítima também geraria alertas.

3) `SKIPDATA` significa que o sistema de captura de Flow Logs **estava sobrecarregado** e precisou descartar registros para não afetar a performance da rede. 5% dos registros no horário de pico foram perdidos e simplesmente **não existem nos logs**. **Implicações para análise de segurança:** (a) você não pode afirmar com certeza que "nenhum tráfego suspeito ocorreu" baseado nesses logs — os 5% descartados podem conter exatamente os eventos de segurança que você estava procurando; (b) análises de baseline ("tráfego normal é X GB/hora") ficam imprecisas; (c) investigações forenses após incidentes podem ter lacunas; (d) compliance que exige log completo pode estar violado. **Mitigações:** (a) usar versão mais enxuta do formato para reduzir volume por fluxo; (b) filtrar para `REJECT` only se o objetivo é segurança; (c) usar Kinesis Data Firehose como destino (processa com maior throughput que CloudWatch); (d) criar alarme para monitorar a métrica `log_status = SKIPDATA` para detectar o problema antes de se tornar crítico.
