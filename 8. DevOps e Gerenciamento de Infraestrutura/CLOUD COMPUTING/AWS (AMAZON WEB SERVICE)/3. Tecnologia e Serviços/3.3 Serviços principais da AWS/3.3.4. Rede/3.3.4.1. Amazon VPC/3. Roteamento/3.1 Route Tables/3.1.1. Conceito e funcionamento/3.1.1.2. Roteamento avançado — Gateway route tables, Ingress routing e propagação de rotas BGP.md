### Roteamento avançado — Gateway Route Tables, Ingress Routing e propagação de rotas BGP

Além das Route Tables de subnet, a VPC suporta cenários de roteamento mais sofisticados: **Gateway Route Tables** permitem inspecionar o tráfego antes que ele entre ou saia da VPC (essencial para firewalls e IDS); **Ingress Routing** direciona tráfego de entrada para appliances de segurança; **propagação de rotas BGP** sincroniza automaticamente as rotas de uma VPN ou Direct Connect com as Route Tables. Esses recursos são o que separa arquiteturas de rede básicas de arquiteturas de segurança de nível enterprise.

---

## Gateway Route Tables — inspecionar tráfego na borda

Por padrão, o Internet Gateway simplesmente entrega o tráfego da internet diretamente para a instância destino. Em arquiteturas com firewalls ou IDS/IPS, você quer **interceptar esse tráfego** antes que chegue à instância — para inspecionar, filtrar ou registrar. É para isso que serve a **Gateway Route Table**.

```
Sem Gateway Route Table (fluxo padrão):
  Internet → IGW → EC2 (direto)
  
  Problema: tráfego não inspecionado

Com Gateway Route Table (fluxo inspecionado):
  Internet → IGW → [Route Table do IGW] → Firewall Appliance → EC2
  
  O IGW consulta sua própria Route Table antes de encaminhar
  o pacote — e você pode direcionar para um firewall primeiro
```

### Como configurar uma Gateway Route Table

```bash
# 1. Criar a Route Table que será associada ao IGW
aws ec2 create-route-table \
  --vpc-id vpc-0abc123 \
  --tag-specifications 'ResourceType=route-table,Tags=[{Key=Name,Value=rtb-igw-inspection}]'

# 2. Adicionar rota: tráfego para subnet pública vai para o firewall primeiro
# (o firewall tem IP 10.0.0.4 na subnet de firewall)
aws ec2 create-route \
  --route-table-id rtb-igw-123 \
  --destination-cidr-block 10.0.1.0/24 \   # subnet pública de destino
  --network-interface-id eni-firewall-123   # ENI do firewall

# 3. Associar a Route Table ao Internet Gateway
aws ec2 associate-route-table \
  --gateway-id igw-0abc123 \
  --route-table-id rtb-igw-123
```

```
Arquitetura com Inspection (AWS Network Firewall ou appliance):

Internet
  │
  ▼
Internet Gateway
  │  consulta sua Gateway Route Table
  │  Destination: 10.0.1.0/24 → eni-firewall (na subnet de firewall)
  │
  ▼
AWS Network Firewall / Palo Alto / Fortinet
  │  inspeciona, filtra, loga
  │
  ▼
EC2 na subnet pública (10.0.1.x)

Fluxo de retorno (reply):
EC2 → subnet route table → firewall → IGW → internet
```

### Regras para Gateway Route Tables

```
Restrições:
  → Só pode ser associada a IGW ou VGW (Virtual Private Gateway)
  → Destinos devem ser CIDRs de subnets dentro da mesma VPC
  → Target deve ser uma ENI ou VPC Endpoint (não pode ser igw, nat, etc.)
  → A rota local (10.0.0.0/16 → local) ainda existe e tem precedência
    para tráfego intra-VPC
```

## Ingress Routing — forçar tráfego de entrada por um appliance

**Ingress Routing** é o nome dado ao padrão de arquitetura que usa Gateway Route Tables para fazer todo tráfego entrante da internet passar por uma appliance de segurança antes de chegar às instâncias. É o equivalente AWS de um firewall perimetral em datacenter físico:

```
Arquitetura de Ingress Routing com 3 subnets:

VPC: 10.0.0.0/16
  ├── Subnet Firewall (10.0.0.0/28) — us-east-1a
  │     Firewall Appliance: ENI 10.0.0.4
  │     Route Table: 0.0.0.0/0 → igw (firewall sai pela internet)
  │
  ├── Subnet Pública (10.0.1.0/24) — us-east-1a
  │     EC2 Web Servers (10.0.1.x)
  │     Route Table: 0.0.0.0/0 → eni-firewall (saída pelo firewall)
  │
  └── IGW Route Table (associada ao IGW):
        10.0.1.0/24 → eni-firewall  ← entrada da internet vai para firewall
        (tráfego para EC2 não vai direto — passa pelo firewall primeiro)

Fluxo completo:
  1. Usuário na internet → IGW
  2. IGW consulta sua Route Table: 10.0.1.50 → eni-firewall
  3. Firewall recebe, inspeciona, encaminha para 10.0.1.50
  4. EC2 10.0.1.50 responde → Route Table da subnet pública → eni-firewall
  5. Firewall verifica estado da conexão e encaminha → IGW → internet
```

## Propagação de rotas BGP via VGW

Quando você conecta uma rede on-premises via **VPN Site-to-Site** ou **Direct Connect** e habilita BGP, o roteador on-premises anuncia suas rotas para o **Virtual Private Gateway (VGW)**. A AWS pode **propagar automaticamente** essas rotas para as Route Tables das subnets, evitando que você configure manualmente cada rota.

```
Sem propagação (manual):
  On-premises anuncia via BGP: 192.168.0.0/16, 172.20.0.0/14
  
  Você deve adicionar manualmente nas Route Tables:
  aws ec2 create-route --destination-cidr-block 192.168.0.0/16 --gateway-id vgw-xxx
  aws ec2 create-route --destination-cidr-block 172.20.0.0/14 --gateway-id vgw-xxx
  
  Se o on-premises adicionar novas subredes: você atualiza manualmente

Com propagação habilitada (automático):
  VGW aprende rotas via BGP → propaga automaticamente para as Route Tables
  → Novas rotas on-premises aparecem automaticamente nas Route Tables
  → Sem intervenção manual para mudanças de roteamento
```

### Habilitando propagação de rotas

```bash
# Habilitar propagação em uma Route Table específica
aws ec2 enable-vgw-route-propagation \
  --route-table-id rtb-0abc123 \
  --gateway-id vgw-0abc123

# Verificar rotas propagadas (aparecem com "propagated: true")
aws ec2 describe-route-tables \
  --route-table-ids rtb-0abc123 \
  --query 'RouteTables[0].Routes[?Origin==`EnableVgwRoutePropagation`]'

# Desabilitar propagação
aws ec2 disable-vgw-route-propagation \
  --route-table-id rtb-0abc123 \
  --gateway-id vgw-0abc123
```

### Rotas propagadas vs rotas estáticas — precedência

```
Quando há conflito entre rota propagada e rota estática:

Rota estática (configurada manualmente): SEMPRE vence
Rota propagada (via BGP): perde para rota estática com mesmo prefixo

Exemplo:
  Rota estática:  10.20.5.0/24 → vpce-endpoint (mais específica que propagada)
  Rota propagada: 10.20.0.0/16 → vgw-vpn

  Pacote para 10.20.5.100:
  → Tanto estática (match /24) quanto propagada (match /16) têm match
  → Estática vence por ser mais específica (/24 > /16)
  → E mesmo se fossem igual prefixo, estática vence sobre propagada
```

## Transit Gateway Route Tables — roteamento entre VPCs

O **Transit Gateway (TGW)** tem suas próprias Route Tables, separadas das Route Tables das VPCs. Cada attachment (VPC, VPN, Direct Connect) pode ser associado a uma TGW Route Table diferente, criando segmentação de roteamento entre VPCs:

```
Transit Gateway com múltiplas Route Tables:

TGW Route Table "producao":
  Destination    Target
  10.0.0.0/16   → attachment VPC-Prod
  10.1.0.0/16   → attachment VPC-Servicos
  0.0.0.0/0     → attachment VPC-Egress (firewall centralizado)

TGW Route Table "staging":
  Destination    Target
  10.10.0.0/16  → attachment VPC-Staging
  10.1.0.0/16   → attachment VPC-Servicos (compartilhado com prod)
  (sem rota 0.0.0.0/0 → staging não tem egress para internet)

Resultado:
  VPC-Prod pode falar com VPC-Servicos e VPC-Egress
  VPC-Staging pode falar com VPC-Servicos mas não com VPC-Prod
  VPC-Staging não tem saída para internet
```

### Blackhole routes no Transit Gateway

O TGW suporta rotas de blackhole — tráfego para esse destino é **descartado explicitamente**:

```bash
# Criar rota de blackhole no TGW (bloquear VPC de falar com outra)
aws ec2 create-transit-gateway-route \
  --destination-cidr-block 10.20.0.0/16 \
  --transit-gateway-route-table-id tgw-rtb-0abc123 \
  --blackhole

# Útil para:
# → Isolar ambientes (dev não pode falar com prod via TGW)
# → Compliance: bloquear explicitamente certos destinos
# → Substituir regras de SG complexas por roteamento
```

## Policy-based routing — roteamento por identidade da instância

A AWS não suporta policy-based routing nativo (roteamento por source IP ou campos L4) nas Route Tables de subnet. Mas é possível simular com **source/destination check desabilitado** em appliances:

```
Source/Destination Check (padrão):
  Uma ENI só aceita/envia tráfego com seu próprio IP como src/dst
  
  Necessário desabilitar para:
  ✓ NAT Instance (precisa encaminhar tráfego de outros IPs)
  ✓ Firewall Appliances
  ✓ VPN Concentrators customizados
  ✓ Qualquer instância que age como roteador/proxy

aws ec2 modify-network-interface-attribute \
  --network-interface-id eni-0abc123 \
  --no-source-dest-check
```

## Diagnóstico avançado com VPC Reachability Analyzer

O **VPC Reachability Analyzer** analisa o caminho lógico entre dois recursos sem enviar tráfego real, verificando Route Tables, Security Groups, NACLs e configurações de rede:

```bash
# Criar análise de alcançabilidade
aws ec2-instance-connect create-network-insights-path \
  --source i-0abc123 \       # instância de origem
  --destination i-0def456 \ # instância de destino
  --protocol TCP \
  --destination-port 443

# Iniciar análise
aws ec2 start-network-insights-analysis \
  --network-insights-path-id nip-0abc123

# Ver resultado
aws ec2 describe-network-insights-analyses \
  --network-insights-analysis-ids nia-0abc123 \
  --query 'NetworkInsightsAnalyses[0].{
    Status:Status,
    Reachable:NetworkPathFound,
    ExplanationCode:Explanations[0].ExplanationCode
  }'

# Saída quando há problema:
# ExplanationCode: "NO_ROUTE_TO_DESTINATION"
# ExplanationCode: "SECURITY_GROUP_RULE"
# ExplanationCode: "NETWORK_ACL_RULE"
```

## Erros comuns e armadilhas

**Rota de retorno assimétrica:** em arquiteturas com firewalls, o tráfego de ida passa pelo firewall mas o tráfego de volta não — o firewall não consegue associar a resposta à conexão original (sem estado) e descarta. Toda arquitetura com appliances deve garantir que tanto a rota de ida quanto a de retorno passem pelo mesmo appliance.

**Propagação de rotas em Route Tables que não deveriam ter:** habilitar propagação em todas as Route Tables de uma VPC com conectividade híbrida pode resultar em rotas on-premises sendo propagadas para subnets de dados que deveriam ser completamente isoladas. Habilite propagação apenas nas Route Tables de subnets que precisam da conectividade.

**Conflito silencioso entre rota propagada e esperada:** se uma rota propagada via BGP usa um prefixo mais específico que sua rota estática, ela **sobrescreve** o comportamento esperado. Monitore as rotas propagadas regularmente para detectar anúncios BGP inesperados do equipamento on-premises.

## 🧩 Quiz de Fixação

1. Uma empresa quer que todo o tráfego de entrada da internet para suas instâncias EC2 passe por um AWS Network Firewall antes de chegar às instâncias. Descreva os componentes e as Route Tables necessárias para implementar esse padrão.

2. Uma VPN Site-to-Site com BGP está configurada. O roteador on-premises anuncia `10.100.0.0/16` via BGP. A Route Table da subnet app tem propagação habilitada e também tem uma rota estática `10.100.5.0/24 → vpce-endpoint`. Um pacote chega para `10.100.5.50`. Qual rota é usada e por quê?

3. Por que rotas de blackhole no Transit Gateway são mais eficientes para isolamento entre VPCs do que apenas não criar as rotas correspondentes?

**Respostas:**

1) **Componentes necessários:**
- **Subnet de Firewall** (ex: `10.0.0.0/28`) em cada AZ, com o AWS Network Firewall
- **Subnet Pública** (ex: `10.0.1.0/24`) com as instâncias EC2
- **Internet Gateway** com uma **Gateway Route Table** associada

**Route Tables:**
- *Gateway Route Table (associada ao IGW):* `10.0.1.0/24 → vpce-firewall-endpoint` (ENI do Firewall)
- *Route Table da Subnet de Firewall:* `0.0.0.0/0 → igw` (firewall precisa de saída para internet para encaminhar respostas)
- *Route Table da Subnet Pública:* `0.0.0.0/0 → vpce-firewall-endpoint` (saída também passa pelo firewall)

**Fluxo:** Internet → IGW → [Gateway RT: para subnet pública → Firewall] → Firewall inspeciona → EC2. Retorno: EC2 → [RT subnet pública: saída → Firewall] → Firewall verifica estado → IGW → Internet.

2) A rota estática `10.100.5.0/24 → vpce-endpoint` **vence**, por dois motivos: (a) é mais específica (/24 > /16 pelo Longest Prefix Match) — mesmo que a rota propagada fosse estática; (b) no caso de prefixos iguais, rotas estáticas têm precedência sobre rotas propagadas por BGP na AWS. Portanto: pacote para `10.100.5.50` usa a rota `/24` e vai para o VPC Endpoint. Pacotes para outros IPs em `10.100.0.0/16` (ex: `10.100.10.50`) não têm match na estática `/24` e usam a rota propagada `/16` → VPN Gateway.

3) Apenas não criar a rota no TGW cria **isolamento implícito** — funciona enquanto ninguém adiciona a rota. Uma rota de blackhole cria **isolamento explícito e auditável**: (a) fica documentada nas Route Tables do TGW como intenção deliberada; (b) no dia que alguém quiser adicionar a rota de comunicação, precisará remover explicitamente o blackhole — um passo adicional que gera log e requer revisão; (c) é mais difícil de "acidentalmente habilitar" a comunicação; (d) é visível em auditoria (AWS Config, CloudTrail) como controle de segurança ativo. Para compliance, a existência de uma rota de blackhole explícita é mais forte como evidência de segregação do que a simples ausência de uma rota.
