### Route Tables — rota local, longest prefix match, main route table e associação com subnets

A Route Table é o componente que determina para onde vai cada pacote de rede dentro da VPC. Ela funciona como uma tabela de roteamento de qualquer roteador IP — mas em vez de hardware físico, é um objeto de software que você associa a subnets. Entender como o roteamento funciona na VPC é fundamental para diagnosticar problemas de conectividade e projetar arquiteturas de rede corretas.

---

## O que é uma Route Table

Uma Route Table é uma lista de **rotas** — cada rota define: "pacotes com destino **X** devem ser enviados para **Y**". Na VPC, X é um bloco CIDR (destino) e Y é um alvo (target) que pode ser um Internet Gateway, NAT Gateway, instância EC2, VPC Peering, etc.

```
Estrutura de uma Route Table:

Route Table ID: rtb-0abc123
Associada às subnets: subnet-111 (us-east-1a), subnet-222 (us-east-1b)

Rotas:
┌─────────────────────┬──────────────────────────┬────────────┐
│ Destination         │ Target                   │ Status     │
├─────────────────────┼──────────────────────────┼────────────┤
│ 10.0.0.0/16         │ local                    │ active     │
│ 10.1.0.0/16         │ pcx-0abc123 (VPC Peering)│ active     │
│ 10.10.5.0/24        │ vgw-0abc123 (VPN GW)     │ active     │
│ pl-63a5400a (S3)    │ vpce-0abc123 (Endpoint)  │ active     │
│ 0.0.0.0/0           │ nat-0abc123 (NAT GW)     │ active     │
└─────────────────────┴──────────────────────────┴────────────┘
```

## A rota local — a rota que nunca some

Toda Route Table tem **obrigatoriamente** uma rota para o bloco CIDR da própria VPC com target `local`. Essa rota é criada automaticamente pela AWS quando você cria a VPC e **não pode ser deletada ou modificada**:

```
VPC CIDR: 10.0.0.0/16
Rota local obrigatória em toda Route Table desta VPC:
  Destination: 10.0.0.0/16  |  Target: local

Significado:
  Todo tráfego destinado a qualquer IP dentro de 10.0.0.0/16
  é roteado localmente dentro da VPC — sem sair para nenhum gateway.
  
  EC2 em 10.0.1.50 → EC2 em 10.0.8.20:
  Route Table consulta 10.0.8.20 → match em 10.0.0.0/16 → target: local
  Pacote vai diretamente para 10.0.8.20 via rede interna da VPC
  (mesmo que 10.0.8.20 esteja em AZ diferente)

O target "local" significa:
  → A AWS roteia o pacote internamente na VPC
  → Sem passar por nenhum gateway físico
  → Sem custo (tráfego intra-VPC dentro da mesma AZ é gratuito)
  → Tráfego entre AZs da mesma VPC: $0.01/GB
```

### CIDRs secundários também ganham rota local

Se a VPC tem CIDRs secundários, cada um ganha sua própria rota local:

```
VPC com CIDRs:
  Primário:   10.0.0.0/16
  Secundário: 10.2.0.0/16

Route Table (gerada automaticamente):
  10.0.0.0/16  → local  ← criada com o CIDR primário
  10.2.0.0/16  → local  ← adicionada ao associar o CIDR secundário
  0.0.0.0/0    → igw-xxx ← você adiciona manualmente
```

## Longest Prefix Match — qual rota vence quando há múltiplas

Quando um pacote tem múltiplas rotas candidatas, a **rota com o prefixo mais longo** (mais específica) vence. É o mesmo algoritmo usado em qualquer roteador IP do mundo:

```
Route Table com múltiplas rotas:
  10.0.0.0/16  → local
  10.0.5.0/24  → vgw-vpn (VPN Gateway — subnet on-premises específica)
  10.0.5.10/32 → eni-0abc (instância específica — rota host)
  0.0.0.0/0    → nat-xxx  (internet via NAT)

Pacote destinado a 10.0.5.10:
  Candidatos:
    10.0.0.0/16  → match (/16)
    10.0.5.0/24  → match (/24) — mais específico
    10.0.5.10/32 → match (/32) — MAIS específico de todos
  Vencedor: 10.0.5.10/32 → eni-0abc (rota host /32)

Pacote destinado a 10.0.5.50:
  Candidatos:
    10.0.0.0/16  → match (/16)
    10.0.5.0/24  → match (/24) — mais específico
    10.0.5.10/32 → NÃO match (10.0.5.50 ≠ 10.0.5.10)
  Vencedor: 10.0.5.0/24 → vgw-vpn (VPN Gateway)

Pacote destinado a 10.0.8.100:
  Candidatos:
    10.0.0.0/16  → match (/16)
  Vencedor: 10.0.0.0/16 → local (roteamento interno da VPC)

Pacote destinado a 8.8.8.8:
  Candidatos:
    0.0.0.0/0    → match (/0) — único candidato
  Vencedor: 0.0.0.0/0 → nat-xxx (internet via NAT)
```

## Main Route Table — a Route Table padrão da VPC

Cada VPC tem uma **Main Route Table** — criada automaticamente e que serve como padrão para subnets sem associação explícita:

```
Comportamento da Main Route Table:

VPC com 5 subnets:
  subnet-A → associada explicitamente à rtb-publica
  subnet-B → associada explicitamente à rtb-privada
  subnet-C → SEM associação explícita → usa Main Route Table
  subnet-D → SEM associação explícita → usa Main Route Table
  subnet-E → SEM associação explícita → usa Main Route Table

Se alguém adicionar 0.0.0.0/0 → igw na Main Route Table:
  subnet-C, subnet-D, subnet-E → tornam-se públicas SEM QUERER
```

### Identificando a Main Route Table

```bash
# Identificar a Main Route Table da VPC
aws ec2 describe-route-tables \
  --filters \
    Name=vpc-id,Values=vpc-0abc123 \
    Name=association.main,Values=true \
  --query 'RouteTables[0].{ID:RouteTableId,Routes:Routes}'

# Listar todas as Route Tables e suas associações
aws ec2 describe-route-tables \
  --filters Name=vpc-id,Values=vpc-0abc123 \
  --query 'RouteTables[*].{
    ID:RouteTableId,
    Main:Associations[?Main==`true`]|[0].Main,
    Subnets:Associations[?SubnetId!=null]|[*].SubnetId,
    Routes:Routes[*].{Dest:DestinationCidrBlock,Target:GatewayId}
  }'
```

### Boa prática com Main Route Table

```
NUNCA adicionar rota 0.0.0.0/0 → IGW na Main Route Table

Motivo: qualquer subnet criada sem associação explícita se torna pública

Prática correta:
  1. Manter a Main Route Table com apenas a rota local:
     10.0.0.0/16 → local
  
  2. Criar Route Tables separadas:
     rtb-publica:  10.0.0.0/16 → local | 0.0.0.0/0 → igw
     rtb-privada:  10.0.0.0/16 → local | 0.0.0.0/0 → nat
     rtb-isolada:  10.0.0.0/16 → local

  3. Associar EXPLICITAMENTE cada subnet à Route Table correta

Mudar qual Route Table é a "Main" (se necessário):
  aws ec2 replace-route-table-association \
    --association-id <id-da-associação-main-atual> \
    --route-table-id rtb-nova-main
```

## Criando e gerenciando Route Tables

```bash
# Criar Route Table
aws ec2 create-route-table \
  --vpc-id vpc-0abc123 \
  --tag-specifications 'ResourceType=route-table,Tags=[{Key=Name,Value=prod-rtb-privada-az-a}]'

# Adicionar rota para NAT Gateway
aws ec2 create-route \
  --route-table-id rtb-0abc123 \
  --destination-cidr-block 0.0.0.0/0 \
  --nat-gateway-id nat-0abc123

# Adicionar rota para VPC Peering
aws ec2 create-route \
  --route-table-id rtb-0abc123 \
  --destination-cidr-block 10.1.0.0/16 \
  --vpc-peering-connection-id pcx-0abc123

# Associar subnet à Route Table
aws ec2 associate-route-table \
  --subnet-id subnet-0abc123 \
  --route-table-id rtb-0abc123

# Substituir uma rota existente (ex: failover de NAT Gateway)
aws ec2 replace-route \
  --route-table-id rtb-0abc123 \
  --destination-cidr-block 0.0.0.0/0 \
  --nat-gateway-id nat-nova-az  # trocar para NAT Gateway de outra AZ

# Deletar uma rota
aws ec2 delete-route \
  --route-table-id rtb-0abc123 \
  --destination-cidr-block 10.1.0.0/16

# Desassociar subnet de uma Route Table
aws ec2 disassociate-route-table \
  --association-id assoc-0abc123
```

## Targets disponíveis em uma rota

```
Targets possíveis em uma rota:

local               → Roteamento interno da VPC (automático, não configurável)
igw-xxx             → Internet Gateway (subnet pública)
nat-xxx             → NAT Gateway (subnet privada com saída)
eigw-xxx            → Egress-Only Internet Gateway (IPv6 privado)
vgw-xxx             → Virtual Private Gateway (VPN Site-to-Site)
tgw-xxx             → Transit Gateway (hub multi-VPC)
pcx-xxx             → VPC Peering Connection
vpce-xxx            → VPC Endpoint (Gateway type: S3 ou DynamoDB)
eni-xxx             → Network Interface (rota para instância específica)
i-xxx               → Instância EC2 (rota via instância — legado)
```

## Route Tables por subnet vs Route Table compartilhada

Você pode ter uma Route Table por subnet ou compartilhar uma Route Table entre várias subnets. Cada abordagem tem prós e contras:

```
Uma Route Table por subnet:
  Prós:
    → Controle granular por subnet
    → Facilita failover (trocar apenas a rota de uma subnet)
    → Auditoria precisa (qual subnet usa qual gateway)
  Contras:
    → Mais objetos para gerenciar
    → Mudanças precisam ser aplicadas em cada Route Table

Route Table compartilhada entre subnets da mesma camada:
  Prós:
    → Menor número de objetos
    → Mudança em uma Route Table afeta todas as subnets associadas
  Contras:
    → Menos controle por subnet
    → Risco: mudança acidental afeta todas as subnets do grupo

Recomendação por tier:
  Tier Público:    1 Route Table (compartilhada entre AZs públicas)
  Tier Privado:    1 Route Table POR AZ
    → Cada AZ aponta para o NAT Gateway da própria AZ
    → Se usar 1 Route Table compartilhada, todas as AZs privadas
      usariam o mesmo NAT Gateway → ponto único de falha
  Tier Dados:      1 Route Table (compartilhada — sem NAT, só rota local)
```

## Diagnóstico de rotas — identificando problemas

```bash
# Verificar por que um pacote não está chegando ao destino
# 1. Identificar a subnet da instância
aws ec2 describe-instances \
  --instance-ids i-0abc123 \
  --query 'Reservations[0].Instances[0].SubnetId'

# 2. Identificar a Route Table da subnet
aws ec2 describe-route-tables \
  --filters Name=association.subnet-id,Values=subnet-0abc \
  --query 'RouteTables[0].Routes'

# 3. Verificar se há rota para o destino
# Se não há rota: pacote descartado (sem roteamento disponível)
# Se há rota para igw mas sem Elastic IP na instância: sem conectividade de entrada
# Se há rota para NAT: apenas saída, sem entrada

# Usar VPC Reachability Analyzer para análise automática
aws ec2-instance-connect start-ssm-session # via SSM sem necessidade de bastion
```

## Erros comuns e armadilhas

**Esquecer de adicionar rota em ambos os lados do Peering:** ao criar VPC Peering entre VPC-A e VPC-B, é necessário adicionar a rota para o CIDR da VPC-B na Route Table de VPC-A **e** a rota para o CIDR de VPC-A na Route Table de VPC-B. Apenas um lado configurado = sem comunicação.

**Uma Route Table de subnet privada apontando NAT Gateway de outra AZ:** se todas as subnets privadas compartilham uma Route Table com `0.0.0.0/0 → nat-az-a`, e a AZ-a cai, as instâncias em AZ-b e AZ-c perdem acesso à internet — mesmo que estejam rodando. Use Route Tables separadas por AZ, cada uma apontando para o NAT Gateway da própria AZ.

**Rota em blackhole:** quando o target de uma rota (ex: um NAT Gateway ou instância EC2) é deletado mas a rota permanece, o status da rota fica como `blackhole` — pacotes são silenciosamente descartados sem nenhum erro visível no cliente.

```bash
# Verificar rotas em blackhole
aws ec2 describe-route-tables \
  --filters Name=vpc-id,Values=vpc-0abc \
  --query 'RouteTables[*].Routes[?State==`blackhole`]'
```

## 🧩 Quiz de Fixação

1. Uma Route Table tem as rotas: `10.0.0.0/16 → local`, `10.0.10.0/24 → pcx-peering`, `0.0.0.0/0 → nat-abc`. Uma instância na subnet associada a essa Route Table envia um pacote para `10.0.10.50`. Qual rota é usada e por que a rota local não vence, mesmo que `10.0.10.50` esteja dentro de `10.0.0.0/16`?

2. Um engenheiro cria uma nova VPC com 4 subnets e não associa nenhuma delas explicitamente a uma Route Table. Ele então adiciona a rota `0.0.0.0/0 → igw-xxx` na Main Route Table para testar a conectividade de uma subnet. Ele percebe que TODAS as 4 subnets ficaram com acesso à internet. Por que isso aconteceu e como corrigir para que apenas a subnet de teste seja pública?

3. Um cluster EKS tem instâncias em us-east-1a e us-east-1b, ambas usando a mesma Route Table privada com `0.0.0.0/0 → nat-az-a`. O NAT Gateway na AZ-a falha. Descreva exatamente o que acontece com as instâncias nas duas AZs e qual é a solução correta.

**Respostas:**

1) A rota `10.0.10.0/24 → pcx-peering` vence pelo **algoritmo de Longest Prefix Match**. Embora `10.0.10.50` esteja contido em `10.0.0.0/16` (match de /16), também está contido em `10.0.10.0/24` (match de /24). O prefixo /24 é **mais longo (mais específico)** que o /16, portanto vence. O pacote é enviado para a VPC Peering connection, não roteado localmente. Isso demonstra por que é possível "sobrescrever" a rota local para um subconjunto do CIDR da VPC — basta criar uma rota mais específica (/24, /25, /32) com target diferente.

2) Isso aconteceu porque **todas as 4 subnets sem associação explícita herdam automaticamente a Main Route Table**. Ao modificar a Main Route Table, todas as subnets que dependem dela são afetadas simultaneamente. **Como corrigir:** (a) remover a rota `0.0.0.0/0 → igw-xxx` da Main Route Table — isso restaura o isolamento de todas as 4 subnets; (b) criar uma Route Table separada `rtb-teste` com `0.0.0.0/0 → igw-xxx`; (c) associar **explicitamente** apenas a subnet de teste à `rtb-teste`; (d) as outras 3 subnets continuam sem associação explícita, herdando a Main Route Table (sem IGW). Lição: nunca modificar a Main Route Table para acesso à internet — sempre criar Route Tables dedicadas.

3) **O que acontece:** quando o NAT Gateway na AZ-a falha, a rota `0.0.0.0/0 → nat-az-a` fica com status **blackhole** — pacotes destinados à internet são silenciosamente descartados. Instâncias em us-east-1a: completamente sem acesso à internet (o NAT delas falhou e a rota está em blackhole). Instâncias em us-east-1b: também perdem acesso à internet, pois a Route Table compartilhada aponta para o NAT da AZ-a (que está fora). As instâncias continuam rodando — apenas a conectividade de saída é perdida — mas qualquer serviço que dependa de chamadas externas (ECR para pull de imagens, Secrets Manager, APIs externas) para de funcionar. **Solução correta:** criar Route Tables separadas por AZ:
- `rtb-privada-az-a`: `0.0.0.0/0 → nat-az-a` → associada apenas a subnets de us-east-1a
- `rtb-privada-az-b`: `0.0.0.0/0 → nat-az-b` → associada apenas a subnets de us-east-1b

Com esse design, a falha do NAT na AZ-a afeta apenas as instâncias de us-east-1a. As instâncias de us-east-1b continuam com saída via o NAT da própria AZ.
