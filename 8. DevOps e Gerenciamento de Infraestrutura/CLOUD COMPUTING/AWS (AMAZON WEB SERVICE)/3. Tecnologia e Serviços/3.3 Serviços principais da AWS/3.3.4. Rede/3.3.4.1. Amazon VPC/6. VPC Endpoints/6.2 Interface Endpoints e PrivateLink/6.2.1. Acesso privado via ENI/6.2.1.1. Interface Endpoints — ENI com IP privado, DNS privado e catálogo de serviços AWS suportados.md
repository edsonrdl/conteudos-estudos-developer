### Interface Endpoints — ENI com IP privado, DNS privado e serviços AWS suportados

Enquanto os Gateway Endpoints funcionam apenas para S3 e DynamoDB via rotas em Route Tables, os **Interface Endpoints** cobrem centenas de serviços AWS usando um mecanismo diferente: uma **Elastic Network Interface (ENI)** com IP privado é provisionada dentro da sua VPC, e o serviço AWS fica acessível através desse IP como se fosse um recurso interno. É a tecnologia central do **AWS PrivateLink**.

---

## Como Interface Endpoints funcionam

```
Sem Interface Endpoint:
  EC2 privada → NAT Gateway → Internet → api.ecr.amazonaws.com
  (tráfego sai pela internet pública, mesmo que HTTPS)

Com Interface Endpoint:
  EC2 privada → ENI do endpoint (10.0.10.200) → rede privada AWS → ECR
  (tráfego nunca sai para internet — IP privado dentro da VPC)

O que a AWS provisiona ao criar um Interface Endpoint:
  ┌───────────────────────────────────────────────────────┐
  │  Subnet privada us-east-1a                            │
  │                                                       │
  │  ┌──────────────────────────────────────────────┐    │
  │  │  Interface Endpoint ENI                      │    │
  │  │  IP: 10.0.10.200 (IP da subnet)              │    │
  │  │  DNS: vpce-0abc123-xyz.ecr.api.us-east-1.    │    │
  │  │       vpce.amazonaws.com                     │    │
  │  └──────────────────────────────────────────────┘    │
  │                                                       │
  └───────────────────────────────────────────────────────┘
  ↑ 1 ENI por AZ onde o endpoint é criado
```

A ENI do endpoint é um recurso real na sua VPC — aparece no console, tem Security Group, consome um IP da subnet.

---

## DNS privado — o mecanismo que torna o endpoint transparente

Por padrão, ao criar um Interface Endpoint, o serviço continua sendo acessado pelo nome DNS público (`ecr.amazonaws.com`). O **DNS privado** muda isso: quando habilitado, a AWS cria entradas no Route 53 Resolver da VPC para que o nome DNS público do serviço resolva para o IP da ENI do endpoint, em vez de para o IP público da AWS.

```
Sem DNS privado (endpoint criado, sem DNS privado):
  nslookup ecr.amazonaws.com (de dentro da VPC):
  → 52.119.x.x  ← IP PÚBLICO da AWS
  → Tráfego vai para IP público, mas a Route Table não tem
    rota para esse IP específico via endpoint
  → O tráfego vai pelo NAT ou IGW normalmente

Com DNS privado habilitado:
  nslookup ecr.amazonaws.com (de dentro da VPC):
  → 10.0.10.200  ← IP PRIVADO da ENI do endpoint
  → Tráfego vai direto para a ENI, sem NAT, sem internet
  → Aplicações não precisam mudar nenhuma configuração!

A mágica do DNS privado:
  A aplicação usa o mesmo URL de sempre:
  "https://ecr.amazonaws.com/..."
  Dentro da VPC com DNS privado: resolve para IP privado → endpoint
  Fora da VPC: resolve para IP público → internet normal
```

```bash
# Criar Interface Endpoint com DNS privado habilitado
aws ec2 create-vpc-endpoint \
  --vpc-id vpc-0abc123 \
  --vpc-endpoint-type Interface \
  --service-name com.amazonaws.us-east-1.ecr.api \
  --subnet-ids subnet-privada-az-a subnet-privada-az-b \
  --security-group-ids sg-endpoints-0abc123 \
  --private-dns-enabled \
  --tag-specifications 'ResourceType=vpc-endpoint,Tags=[{Key=Name,Value=vpce-ecr-api}]'
```

**Pré-requisito para DNS privado:** a VPC deve ter `enableDnsHostnames` e `enableDnsSupport` habilitados:

```bash
# Verificar configurações de DNS da VPC
aws ec2 describe-vpc-attribute \
  --vpc-id vpc-0abc123 \
  --attribute enableDnsHostnames

aws ec2 describe-vpc-attribute \
  --vpc-id vpc-0abc123 \
  --attribute enableDnsSupport

# Habilitar se necessário
aws ec2 modify-vpc-attribute \
  --vpc-id vpc-0abc123 \
  --enable-dns-hostnames
aws ec2 modify-vpc-attribute \
  --vpc-id vpc-0abc123 \
  --enable-dns-support
```

## Security Group do Interface Endpoint

Diferente do Gateway Endpoint (sem SG), o Interface Endpoint tem uma ENI e portanto precisa de um Security Group. O SG deve permitir o tráfego das instâncias que usarão o endpoint:

```bash
# Criar Security Group para Interface Endpoints
aws ec2 create-security-group \
  --group-name sg-vpc-endpoints \
  --description "Permite tráfego HTTPS para Interface Endpoints" \
  --vpc-id vpc-0abc123

# Regra: aceitar HTTPS da VPC inteira (ou das subnets específicas)
aws ec2 authorize-security-group-ingress \
  --group-id sg-endpoints-0abc123 \
  --protocol tcp \
  --port 443 \
  --cidr 10.0.0.0/16  # CIDR da VPC

# Sem regra de outbound específica necessária
# (default all outbound é suficiente para endpoints)
```

## Modelo de custo dos Interface Endpoints

```
Custo por Interface Endpoint:
  $0.01/hora por AZ onde o endpoint está provisionado
  $0.01/GB de dados processados

Exemplo — Endpoint ECR em 3 AZs:
  Existência: 3 AZs × $0.01/h × 720h = $21.60/mês
  Dados:      200 GB/mês × $0.01/GB = $2.00/mês
  Total:      $23.60/mês por endpoint

Comparação com NAT Gateway (200 GB/mês de ECR via NAT):
  NAT existência: $32.40/mês (1 AZ) ou $97.20 (3 AZs)
  NAT dados:      200 GB × $0.045 = $9.00/mês
  Total NAT:      $41.40 (1 AZ) ou $106.20 (3 AZs)

Break-even por endpoint individual:
  Interface Endpoint: $21.60 + $2.00 = $23.60/mês
  NAT (1 AZ): $41.40/mês → Interface Endpoint já economiza
  
  Mas atenção: um endpoint é por SERVIÇO
  10 serviços × $21.60 = $216/mês só em endpoints
  vs NAT Gateway (3 AZs): $97.20 + dados de todos os serviços
  
  Para muitos serviços: avaliar se os endpoints valem o custo
```

## Endpoints essenciais para ECS/EKS em subnet privada sem internet

Para clusters completamente privados (sem NAT Gateway, sem IGW), esses endpoints são necessários:

```bash
# Script para criar todos os endpoints necessários para ECS Fargate em VPC privada

SERVICES=(
  "com.amazonaws.us-east-1.ecr.api"
  "com.amazonaws.us-east-1.ecr.dkr"
  "com.amazonaws.us-east-1.s3"           # imagens ECR são armazenadas em S3
  "com.amazonaws.us-east-1.ecs"
  "com.amazonaws.us-east-1.ecs-agent"
  "com.amazonaws.us-east-1.ecs-telemetry"
  "com.amazonaws.us-east-1.logs"         # CloudWatch Logs
  "com.amazonaws.us-east-1.secretsmanager"
  "com.amazonaws.us-east-1.ssm"
  "com.amazonaws.us-east-1.ssmmessages"
  "com.amazonaws.us-east-1.ec2messages"
)

for SERVICE in "${SERVICES[@]}"; do
  echo "Criando endpoint para: $SERVICE"
  aws ec2 create-vpc-endpoint \
    --vpc-id vpc-0abc123 \
    --vpc-endpoint-type Interface \
    --service-name $SERVICE \
    --subnet-ids subnet-privada-az-a subnet-privada-az-b \
    --security-group-ids sg-endpoints-0abc123 \
    --private-dns-enabled \
    --no-cli-pager
done

# S3 deve ser Gateway Endpoint (gratuito) em vez de Interface
aws ec2 create-vpc-endpoint \
  --vpc-id vpc-0abc123 \
  --service-name com.amazonaws.us-east-1.s3 \
  --vpc-endpoint-type Gateway \
  --route-table-ids rtb-privada-az-a rtb-privada-az-b
```

**Custo de uma VPC totalmente privada com todos os endpoints vs NAT Gateway:**

```
10 Interface Endpoints × 2 AZs × $0.01/h × 720h = $144/mês
Gateway Endpoint S3: $0
Total endpoints: $144/mês

vs NAT Gateway (2 AZs) + dados:
  $0.045/h × 2 × 720 = $64.80/mês (existência)
  + dados processados (depende do volume)

Break-even: se os dados processados via NAT excedem ~$79.20/mês
então endpoints ficam mais baratos. Para clusters grandes: endpoints
frequentemente ganham.
```

## Alta disponibilidade — 1 ENI por AZ

Para HA, é necessário criar o endpoint em múltiplas AZs. Se o endpoint está apenas em us-east-1a e essa AZ cai, instâncias em us-east-1b não conseguem acessar o serviço via endpoint:

```bash
# Criar endpoint em 2 AZs (subnet em cada AZ)
aws ec2 create-vpc-endpoint \
  --vpc-id vpc-0abc123 \
  --vpc-endpoint-type Interface \
  --service-name com.amazonaws.us-east-1.ecr.api \
  --subnet-ids subnet-privada-az-a subnet-privada-az-b  # 2 subnets = 2 AZs
  --security-group-ids sg-endpoints-0abc123 \
  --private-dns-enabled

# O DNS privado do endpoint distribui automaticamente entre as ENIs das AZs
# usando latência de rede para selecionar a ENI mais próxima
```

## Erros comuns e armadilhas

**Criar endpoint sem DNS privado:** o endpoint existe mas as aplicações ainda usam os IPs públicos. Sem DNS privado, a aplicação precisa usar explicitamente o endpoint-specific DNS name (muito longo e diferente do URL padrão). Sempre habilitar DNS privado.

**Security Group do endpoint muito restritivo:** se o SG do endpoint não permite HTTPS (443) das instâncias que precisam acessá-lo, as chamadas de API falham com timeout — exatamente como se o endpoint não existisse. Verificar que o SG do endpoint permite `TCP 443 from <CIDR da VPC>` ou do SG das instâncias.

**Criar endpoint apenas em 1 AZ para economizar:** a ENI do endpoint em us-east-1a não serve instâncias em us-east-1b sem latência extra (tráfego cross-AZ). Para HA e performance, criar ENIs em todas as AZs onde há workload.

**Não considerar o custo total de múltiplos endpoints:** 10 serviços × 3 AZs × $0.01/h = $216/mês. Para cenários com poucos serviços e alto volume de dados, o NAT Gateway pode ser mais econômico. Calcule antes de criar.

## 🧩 Quiz de Fixação

1. Uma tarefa ECS Fargate em subnet privada falha ao iniciar com erro `CannotPullContainerError: failed to pull image`. A subnet não tem NAT Gateway. Quais Interface Endpoints são necessários para que o Fargate consiga fazer pull da imagem do ECR?

2. Um cluster EKS tem instâncias em us-east-1a e us-east-1b. Um Interface Endpoint para Secrets Manager foi criado apenas em us-east-1a. Uma instância em us-east-1b falha ao acessar o Secrets Manager. Qual é o custo adicional e o problema de performance se a instância de us-east-1b usar o endpoint de us-east-1a?

3. Por que habilitar o DNS privado de um Interface Endpoint é considerado a configuração "transparente" — e o que o desenvolvedor precisaria fazer se não houvesse DNS privado disponível?

**Respostas:**

1) Para o ECS Fargate fazer pull de imagem do ECR em subnet privada sem NAT, são necessários **3 endpoints**:
- **`ecr.api`** — para autenticação e operações da API do ECR (`GetAuthorizationToken`, `DescribeImages`)
- **`ecr.dkr`** — para o protocolo Docker Registry (download das camadas da imagem)
- **`s3` (Gateway Endpoint, gratuito)** — as camadas das imagens ECR são armazenadas no S3; sem esse endpoint, o download vai tentar acessar o S3 publicamente e falhar sem NAT

Além desses, para que a task consiga enviar logs e funcionar corretamente:
- **`logs`** — para CloudWatch Logs (se configurado como driver de log)
- **`ecr-telemetry`** e **`ecs-agent`** — para o agente ECS reportar status

2) **Custo adicional:** tráfego cross-AZ de us-east-1b para o endpoint em us-east-1a gera **$0.01/GB** de custo inter-AZ. Cada chamada ao Secrets Manager que cruza a AZ paga esse overhead. Para clusters com muitas chamadas frequentes, isso soma. **Problema de performance:** latência adicional de ~1-2ms por chamada (latência inter-AZ) comparado a um endpoint local. Para aplicações que fazem chamadas frequentes ao Secrets Manager (ex: a cada refresh de credencial), isso pode impactar a latência percebida. **Solução:** criar o endpoint também em us-east-1b — custo de $0.01/h × 720h = $7.20/mês, que para qualquer volume razoável de dados processados é menor que o custo cross-AZ acumulado.

3) **Com DNS privado:** a aplicação faz `https://secretsmanager.us-east-1.amazonaws.com/...` (URL padrão) — o DNS da VPC resolve automaticamente para o IP da ENI do endpoint. Zero mudança de código, zero configuração adicional. É "transparente" porque a aplicação não sabe que está usando um endpoint — apenas que o serviço está "aí dentro". **Sem DNS privado:** o desenvolvedor teria duas opções: (a) usar o endpoint-specific DNS name, que tem formato como `vpce-0abc123-xyz.secretsmanager.us-east-1.vpce.amazonaws.com` — diferente do URL padrão, exige mudança de configuração em toda aplicação; (b) usar o alias regional do endpoint como `https://secretsmanager.us-east-1.amazonaws.com` mas manualmente configurar um registro DNS privado no Route 53 Private Hosted Zone para sobrescrever a resolução. Ambas as opções adicionam complexidade operacional significativa — por isso DNS privado é considerado essencial e deve ser sempre habilitado.
