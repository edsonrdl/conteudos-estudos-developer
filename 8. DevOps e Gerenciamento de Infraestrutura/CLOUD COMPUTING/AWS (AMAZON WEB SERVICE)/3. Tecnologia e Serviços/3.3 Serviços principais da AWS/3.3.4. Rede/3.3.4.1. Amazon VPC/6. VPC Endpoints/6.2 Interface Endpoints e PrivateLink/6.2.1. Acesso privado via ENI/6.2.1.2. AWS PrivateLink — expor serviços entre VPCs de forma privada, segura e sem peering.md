### AWS PrivateLink — expor serviços entre VPCs de forma privada e sem peering

AWS PrivateLink é a tecnologia que permite consumir serviços hospedados em outras VPCs — ou em outras contas AWS — através de um Interface Endpoint, sem que o tráfego atravesse a internet e sem precisar de VPC Peering. É o mecanismo que a própria AWS usa por baixo dos panos para os Interface Endpoints de seus serviços, e que você pode usar para criar serviços SaaS privados ou plataformas internas compartilhadas entre contas.

---

## O problema que PrivateLink resolve

Imagine que você tem dois cenários onde VPCs diferentes precisam se comunicar:

```
Cenário 1 — VPC Peering (modelo tradicional):
  VPC-A (10.0.0.0/16) ←→ VPC-B (10.1.0.0/16)
  
  Problemas:
  → Tráfego é BIDIRECIONAL — VPC-A pode acessar qualquer recurso de VPC-B
  → CIDRs não podem se sobrepor
  → Não transitivo (A pode falar com B e C, mas B não pode falar com C via A)
  → Para 100 VPCs: 4.950 conexões de peering necessárias

Cenário 2 — PrivateLink (acesso direcionado):
  VPC-A (consumidora) → Interface Endpoint → VPC-B (provedora)
  
  Vantagens:
  → Acesso UNIDIRECIONAL e controlado — consumidor acessa apenas o serviço específico
  → CIDRs PODEM se sobrepor
  → Transitivo não é necessário — cada consumidor tem seu endpoint direto
  → Para 100 VPCs consumindo 1 serviço: 100 endpoints (não 4.950 peerins)
  → Sem exposição da rede inteira — apenas o serviço é acessível
```

## Arquitetura do PrivateLink — dois lados

```
LADO DO PROVEDOR (quem expõe o serviço):

VPC Provedora
  ├── Network Load Balancer (NLB)
  │     └── Target Group com as instâncias/containers do serviço
  │
  └── VPC Endpoint Service
        ├── Configuração: aceitar apenas contas específicas
        ├── DNS name: com.amazonaws.vpce.us-east-1.vpce-svc-0abc123
        └── Estado: aceita/rejeita requisições de endpoints

LADO DO CONSUMIDOR (quem acessa o serviço):

VPC Consumidora
  └── Interface Endpoint (vpce-0def456)
        ├── ENI com IP privado (10.0.5.100)
        ├── DNS name privado: serv.company.com (opcional)
        └── Conecta ao VPC Endpoint Service da provedora
```

## Configurando o lado do Provedor

### Passo 1 — Criar o Network Load Balancer

O PrivateLink requer um **NLB** como frontend do serviço (não ALB — o PrivateLink opera em Layer 4):

```bash
# Criar NLB interno para o PrivateLink
aws elbv2 create-load-balancer \
  --name nlb-meu-servico \
  --type network \
  --scheme internal \
  --subnets subnet-privada-az-a subnet-privada-az-b \
  --tag-specifications 'ResourceType=load-balancer,Tags=[{Key=Name,Value=nlb-servico-interno}]'

# Criar Target Group
aws elbv2 create-target-group \
  --name tg-meu-servico \
  --protocol TCP \
  --port 8080 \
  --vpc-id vpc-provedora \
  --target-type ip  # ou instance

# Registrar targets (instâncias ou IPs do serviço)
aws elbv2 register-targets \
  --target-group-arn arn:aws:elasticloadbalancing:...:targetgroup/tg-meu-servico/abc \
  --targets Id=10.0.10.50,Port=8080 Id=10.0.11.50,Port=8080

# Criar Listener no NLB
aws elbv2 create-listener \
  --load-balancer-arn arn:aws:elasticloadbalancing:...:loadbalancer/net/nlb-meu-servico/abc \
  --protocol TCP \
  --port 443 \
  --default-actions Type=forward,TargetGroupArn=arn:...:targetgroup/tg-meu-servico/abc
```

### Passo 2 — Criar o VPC Endpoint Service

```bash
# Criar o Endpoint Service (o que os consumidores vão acessar)
aws ec2 create-vpc-endpoint-service-configuration \
  --network-load-balancer-arns arn:aws:elasticloadbalancing:...:loadbalancer/net/nlb-meu-servico/abc \
  --acceptance-required \  # requer aprovação manual de cada consumidor
  --private-dns-name "api.empresa.com" \  # nome DNS customizado (opcional)
  --tag-specifications 'ResourceType=vpc-endpoint-service,Tags=[{Key=Name,Value=svc-api-interna}]'

# Retorna: {"ServiceId": "vpce-svc-0abc123", "ServiceName": "com.amazonaws.vpce.us-east-1.vpce-svc-0abc123"}

# Permitir que uma conta específica crie endpoints para este serviço
aws ec2 modify-vpc-endpoint-service-permissions \
  --service-id vpce-svc-0abc123 \
  --add-allowed-principals arn:aws:iam::999888777:root  # conta consumidora

# Ver requisições pendentes de conexão
aws ec2 describe-vpc-endpoint-connections \
  --filters Name=vpc-endpoint-service-id,Values=vpce-svc-0abc123

# Aceitar uma conexão pendente
aws ec2 accept-vpc-endpoint-connections \
  --service-id vpce-svc-0abc123 \
  --vpc-endpoint-ids vpce-0def456
```

## Configurando o lado do Consumidor

```bash
# Na conta consumidora: criar Interface Endpoint apontando para o serviço do provedor
aws ec2 create-vpc-endpoint \
  --vpc-id vpc-consumidora \
  --vpc-endpoint-type Interface \
  --service-name com.amazonaws.vpce.us-east-1.vpce-svc-0abc123 \
  --subnet-ids subnet-consumidora-az-a subnet-consumidora-az-b \
  --security-group-ids sg-consumidora-endpoints \
  --tag-specifications 'ResourceType=vpc-endpoint,Tags=[{Key=Name,Value=vpce-servico-empresa}]'

# Verificar estado do endpoint
aws ec2 describe-vpc-endpoints \
  --filters Name=vpc-endpoint-id,Values=vpce-0def456 \
  --query 'VpcEndpoints[0].State'
# "pendingAcceptance" → aguardando aprovação do provedor
# "available" → pronto para usar
```

## Fluxo completo de uma requisição via PrivateLink

```
Consumidor (VPC-B: 10.1.0.0/16)
  EC2: 10.1.5.50

  1. Aplicação chama: https://api.empresa.com/v1/dados
  
  2. DNS resolve api.empresa.com → 10.1.5.100
     (IP da ENI do Interface Endpoint na VPC consumidora)
  
  3. Pacote: src=10.1.5.50 → dst=10.1.5.100:443
  
  4. Interface Endpoint recebe e encaminha via PrivateLink
     (rede privada da AWS — sem internet, sem NAT)
  
  5. Chega ao NLB da VPC provedora (10.0.0.0/16)
     NLB encaminha para o target: 10.0.10.50:8080
  
  6. Instância do serviço (10.0.10.50) processa e responde
  
  7. Resposta volta pelo mesmo caminho privado

Nenhum pacote saiu para a internet.
VPC-B não tem visibilidade de 10.0.10.50 — só vê 10.1.5.100.
VPC-A não tem visibilidade de 10.1.5.50 — é completamente opaca.
```

## Casos de uso principais

### 1. Plataformas internas entre contas (multi-account architecture)

```
Conta Platform (000111222):
  VPC Platform: 10.0.0.0/16
  Serviços: auth-service, notification-service, audit-service
  
  Cada serviço exposto como Endpoint Service via PrivateLink

Conta Produto A (333444555):
  VPC Produto A: 10.10.0.0/16
  Interface Endpoints → auth-service, notification-service

Conta Produto B (666777888):
  VPC Produto B: 192.168.0.0/16  ← CIDR pode se sobrepor!
  Interface Endpoints → auth-service, audit-service

Resultado:
  → CIDRs sobrepostos não são problema (PrivateLink funciona)
  → Produto A não pode acessar recursos de Produto B
  → Platform não pode acessar Produto A ou B diretamente
  → Cada produto acessa apenas os serviços específicos autorizados
```

### 2. SaaS via AWS Marketplace

```
Fornecedor SaaS (ex: Datadog, Splunk, New Relic):
  Expõe seu serviço como Endpoint Service no AWS Marketplace
  
  Cliente AWS:
  Cria Interface Endpoint → tráfego vai diretamente para o SaaS
  via rede privada da AWS, sem atravessar a internet
  
  Vantagem: dados sensíveis nunca saem da rede AWS
```

### 3. Microserviços com CIDRs sobrepostos

```
Aquisição de empresa: empresa adquirida usa 10.0.0.0/8 (igual à empresa mãe)
  → VPC Peering impossível
  → PrivateLink funciona independente de CIDRs sobrepostos
  → Acesso apenas aos serviços específicos necessários
```

## DNS personalizado para Endpoint Services

Você pode configurar um nome DNS amigável para o Endpoint Service, em vez de usar o nome gerado pela AWS:

```bash
# Configurar nome DNS privado para o Endpoint Service
aws ec2 modify-vpc-endpoint-service-configuration \
  --service-id vpce-svc-0abc123 \
  --private-dns-name "api.minha-empresa.com"

# A AWS verifica a posse do domínio via registro TXT no Route 53
# Após verificação, consumidores veem "api.minha-empresa.com" como DNS do endpoint

# Verificar status da verificação de domínio
aws ec2 describe-vpc-endpoint-service-configurations \
  --service-ids vpce-svc-0abc123 \
  --query 'ServiceConfigurations[0].PrivateDnsNameConfiguration'
```

## PrivateLink vs VPC Peering — quando usar cada um

```
┌─────────────────────────┬─────────────────────────┬──────────────────────────┐
│ Critério                │ VPC Peering             │ PrivateLink              │
├─────────────────────────┼─────────────────────────┼──────────────────────────┤
│ CIDRs sobrepostos       │ Não funciona            │ Funciona                 │
│ Acesso bidirecional     │ Sim (todas as subnets)  │ Não (apenas o serviço)   │
│ Exposição de rede       │ Total (ambas as VPCs)   │ Apenas o endpoint        │
│ Escala (N VPCs)         │ N² conexões             │ N endpoints (linear)     │
│ Transitivo              │ Não                     │ Não necessário           │
│ Custo (dados)           │ $0.01/GB cross-AZ       │ $0.01/GB + $0.01/h/AZ    │
│ Configuração            │ Simples                 │ Requer NLB + svc config  │
│ Serviços específicos    │ Acesso a tudo           │ Acesso controlado        │
│ Isolamento de blast     │ Baixo                   │ Alto                     │
│ Quando usar             │ Acesso amplo necessário │ Serviço específico       │
└─────────────────────────┴─────────────────────────┴──────────────────────────┘
```

## Erros comuns e armadilhas

**`acceptance-required: true` sem monitorar requisições pendentes:** se o provedor configura aceitação obrigatória mas não monitora as requisições, consumidores ficam com endpoint em `pendingAcceptance` indefinidamente. Configurar um CloudWatch Event para notificar quando há novas conexões pendentes.

**NLB sem cross-zone load balancing em múltiplas AZs:** por padrão, o NLB roteia para targets na mesma AZ da ENI de entrada. Se o NLB tem targets em us-east-1a mas o consumidor conecta via ENI em us-east-1b, pode ter load balancing assimétrico. Habilitar cross-zone para NLBs de PrivateLink.

**IP de origem no serviço é o IP do NLB, não do consumidor:** o serviço recebe pacotes com IP de origem sendo o do NLB (ou do endpoint), não do cliente real. Se o serviço precisa do IP do cliente (para rate limiting ou logs), habilitar **Proxy Protocol** no NLB:

```bash
aws elbv2 modify-target-group-attributes \
  --target-group-arn arn:...:targetgroup/tg-meu-servico/abc \
  --attributes Key=proxy_protocol_v2.enabled,Value=true
```

## 🧩 Quiz de Fixação

1. Uma empresa tem 50 VPCs de produtos e 1 VPC de plataforma com serviços compartilhados (auth, notificações, billing). Calcule quantas conexões VPC Peering seriam necessárias para conectar todas as 50 VPCs à plataforma vs a quantidade de Endpoints de PrivateLink.

2. Dois times usam CIDRs sobrepostos: VPC-A `10.0.0.0/16` e VPC-B `10.0.0.0/16`. O time de VPC-A precisa consumir uma API REST do time de VPC-B. VPC Peering não é possível. Como o PrivateLink resolve, e quais são os componentes que o time de VPC-B precisa criar?

3. O serviço exposto via PrivateLink precisa de rate limiting por cliente. O desenvolvedor nota que todos os requests chegam com o mesmo IP de origem (o IP do NLB). Como obter o IP real do cliente consumidor?

**Respostas:**

1) **VPC Peering:** para conectar 50 VPCs de produto à VPC de plataforma, seria necessário criar **50 conexões de peering** (1 entre cada VPC de produto e a VPC de plataforma). Além disso, se as VPCs de produto precisassem se comunicar entre si, seriam `50 × 49 / 2 = 1.225` conexões adicionais. **PrivateLink:** para cada serviço da plataforma (ex: auth, notificações, billing = 3 serviços), cada uma das 50 VPCs de produto precisa de 1 Interface Endpoint por serviço = `50 × 3 = 150 endpoints`. O total de Endpoint Services no provedor é apenas 3. A diferença de escala é dramática: 50 conexões de peering (ponto-a-ponto) vs 150 endpoints (independentes, sem malha). Com PrivateLink, adicionar uma 51ª VPC requer apenas 3 novos endpoints — sem nenhuma mudança na plataforma.

2) O PrivateLink funciona porque **não requer roteamento entre os CIDRs das VPCs** — ele usa uma ENI com IP privado dentro da VPC consumidora, e o tráfego nunca precisa "chegar" ao CIDR de VPC-B. Da perspectiva do consumidor, o serviço está em `10.0.5.100` (IP da ENI na VPC-A), não em nenhum IP de VPC-B. **Componentes que o time de VPC-B precisa criar:** (a) **Network Load Balancer** interno na VPC-B, apontando para as instâncias/containers da API REST; (b) **VPC Endpoint Service** associado ao NLB, com permissão para a conta de VPC-A criar endpoints; (c) Opcionalmente, configurar `acceptance-required: false` para aprovação automática ou `true` para aprovação manual. O time de VPC-A cria apenas 1 Interface Endpoint apontando para o Endpoint Service de VPC-B.

3) O IP de origem que chega ao serviço é o IP do NLB porque o NLB realiza SNAT (Source NAT) ao encaminhar para os targets. Para obter o IP real do cliente consumidor, é necessário habilitar **Proxy Protocol v2** no Target Group do NLB. Com o Proxy Protocol habilitado, o NLB insere um **header de Proxy Protocol** no início da conexão TCP com os metadados do cliente original (IP, porta, família de protocolo). O serviço deve ser configurado para ler e interpretar esse header (a maioria dos servidores web como Nginx, HAProxy e muitos frameworks suportam natively). Após habilitar, o log do serviço mostrará o IP real da ENI do consumidor — que pode ser usado para rate limiting, auditoria e identificação de clientes.
