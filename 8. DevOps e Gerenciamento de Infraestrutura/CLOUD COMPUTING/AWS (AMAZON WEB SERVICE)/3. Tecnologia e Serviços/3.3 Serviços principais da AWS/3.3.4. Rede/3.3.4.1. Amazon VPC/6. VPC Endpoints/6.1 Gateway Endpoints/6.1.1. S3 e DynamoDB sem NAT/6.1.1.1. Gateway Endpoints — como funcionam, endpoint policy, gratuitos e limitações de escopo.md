### Gateway Endpoints — acesso privado a S3 e DynamoDB sem NAT Gateway

O Gateway Endpoint é uma forma de acessar o Amazon S3 e o Amazon DynamoDB diretamente a partir de recursos dentro de uma VPC, sem que o tráfego passe pela internet pública ou por um NAT Gateway. É gratuito, de baixa latência e melhora a segurança ao manter o tráfego para esses serviços dentro da rede da AWS.

---

## O problema que Gateway Endpoints resolvem

Instâncias EC2, pods EKS e tasks ECS em subnets privadas normalmente precisam do NAT Gateway para acessar qualquer serviço AWS (como S3 e DynamoDB). Mas isso tem três problemas:

```
Sem Gateway Endpoint:
  EC2 privada (10.0.10.50)
       │
       ▼ rota: 0.0.0.0/0 → NAT Gateway
  NAT Gateway (subnet pública, Elastic IP)
       │
       ▼ sai pela internet pública
  Internet Gateway
       │
       ▼
  S3 endpoint público (s3.amazonaws.com)

Problemas:
  1. Custo: $0.045/GB processado pelo NAT + custo de dados de saída
  2. Latência: pacote sai pela internet pública e volta
  3. Segurança: tráfego passa pela internet (mesmo que criptografado via HTTPS)

Com Gateway Endpoint:
  EC2 privada (10.0.10.50)
       │
       ▼ rota: pl-xxxxxxxx (prefix list do S3) → vpce-xxxxxxxxx
  VPC Endpoint (Gateway)
       │
       ▼ rede privada da AWS — nunca sai para a internet
  S3

Resultado:
  ✓ Sem custo de NAT Gateway para S3/DynamoDB
  ✓ Menor latência (rede interna da AWS)
  ✓ Tráfego nunca toca a internet pública
  ✓ Funciona mesmo sem NAT Gateway ou Internet Gateway
```

---

## Como o Gateway Endpoint funciona tecnicamente

O Gateway Endpoint adiciona uma **rota especial** às Route Tables que você especificar. Essa rota usa um **Prefix List** — uma lista gerenciada pela AWS contendo todos os CIDRs dos IPs do serviço (S3 ou DynamoDB) para aquela região:

```bash
# Verificar o Prefix List do S3 em us-east-1
aws ec2 describe-managed-prefix-lists \
  --filters Name=prefix-list-name,Values=com.amazonaws.us-east-1.s3 \
  --query 'PrefixLists[0].{ID:PrefixListId,Name:PrefixListName,MaxEntries:MaxEntries}'

# Saída: {"ID": "pl-63a5400a", "Name": "com.amazonaws.us-east-1.s3", ...}

# Ver os CIDRs dentro do prefix list
aws ec2 get-managed-prefix-list-entries \
  --prefix-list-id pl-63a5400a \
  --query 'Entries[*].Cidr'
# Retorna lista de CIDRs dos IPs da AWS para o S3 nessa região
```

Quando um pacote tem destino dentro desse Prefix List, a Route Table desvia para o endpoint em vez de seguir para o NAT ou IGW.

## Criando um Gateway Endpoint

```bash
# Criar Gateway Endpoint para S3 e associar às Route Tables das subnets privadas
aws ec2 create-vpc-endpoint \
  --vpc-id vpc-0abc123 \
  --service-name com.amazonaws.us-east-1.s3 \
  --vpc-endpoint-type Gateway \
  --route-table-ids rtb-privada-az-a rtb-privada-az-b rtb-privada-az-c \
  --tag-specifications 'ResourceType=vpc-endpoint,Tags=[{Key=Name,Value=vpce-s3-producao}]'

# Criar Gateway Endpoint para DynamoDB
aws ec2 create-vpc-endpoint \
  --vpc-id vpc-0abc123 \
  --service-name com.amazonaws.us-east-1.dynamodb \
  --vpc-endpoint-type Gateway \
  --route-table-ids rtb-privada-az-a rtb-privada-az-b rtb-privada-az-c

# Verificar o endpoint criado e as rotas adicionadas
aws ec2 describe-vpc-endpoints \
  --filters Name=vpc-id,Values=vpc-0abc123 \
  --query 'VpcEndpoints[*].{ID:VpcEndpointId,Service:ServiceName,State:State,RTBs:RouteTableIds}'
```

Após criar o endpoint, a Route Table recebe automaticamente uma nova entrada:

```
Route Table (antes):
  10.0.0.0/16   → local
  0.0.0.0/0     → nat-gateway

Route Table (depois do Gateway Endpoint):
  10.0.0.0/16   → local
  pl-63a5400a   → vpce-s3-endpoint  ← adicionada automaticamente
  0.0.0.0/0     → nat-gateway
```

O tráfego para S3 agora usa a rota do prefix list — mais específica que `0.0.0.0/0` (longest prefix match) — e nunca chega ao NAT Gateway.

## Endpoint Policy — controle de acesso ao endpoint

Por padrão, o Gateway Endpoint permite acesso a qualquer bucket S3 ou tabela DynamoDB de qualquer conta. A **Endpoint Policy** permite restringir isso:

```json
// Endpoint Policy — permitir apenas buckets da própria conta
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": "*",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::meu-bucket-producao",
        "arn:aws:s3:::meu-bucket-producao/*"
      ]
    },
    {
      "Effect": "Allow",
      "Principal": "*",
      "Action": ["s3:GetObject"],
      "Resource": [
        "arn:aws:s3:::amazonlinux.us-east-1",
        "arn:aws:s3:::amazonlinux.us-east-1/*",
        "arn:aws:s3:::amazonlinux-2-repos-us-east-1",
        "arn:aws:s3:::amazonlinux-2-repos-us-east-1/*"
      ]
    }
  ]
}
```

```bash
# Aplicar endpoint policy
aws ec2 modify-vpc-endpoint \
  --vpc-endpoint-id vpce-0abc123 \
  --policy-document file://endpoint-policy.json
```

### Usos da Endpoint Policy

```
Caso 1 — Evitar exfiltração de dados (data exfiltration prevention):
  Restringir o endpoint para apenas buckets da própria organização
  → Mesmo que um atacante comprometa uma instância e tente exfiltrar
    dados para um bucket de outra conta via S3, a Endpoint Policy bloqueia

Caso 2 — Compliance de localidade de dados:
  Permitir apenas buckets na mesma região
  → Dados não saem acidentalmente para buckets em outras regiões

Caso 3 — Separação de ambientes:
  Endpoint de staging só acessa buckets de staging
  → Um bug no código de staging não afeta buckets de produção
```

## Serviços suportados — apenas S3 e DynamoDB

```
Gateway Endpoints suportam APENAS:
  ✓ Amazon S3
  ✓ Amazon DynamoDB

Para outros serviços AWS (ECR, Secrets Manager, STS, etc.):
  → Usar Interface Endpoints (com custo, cobrado por hora + GB)

Por que apenas S3 e DynamoDB?
  Gateway Endpoints funcionam adicionando rotas às Route Tables
  e são gratuitos porque a AWS consegue otimizá-los como serviços
  de alto volume. Outros serviços usam o modelo de Interface Endpoint
  (ENI com IP privado), que tem custo de infraestrutura adicional.
```

## Limitações do Gateway Endpoint

```
Limitação 1 — Escopo regional:
  Um Gateway Endpoint acessa apenas S3/DynamoDB na MESMA região da VPC
  → ec2 em us-east-1 → endpoint → S3 em us-east-1 ✓
  → ec2 em us-east-1 → endpoint → S3 em eu-west-1 ✗ (vai pelo NAT/internet)

Limitação 2 — Apenas para recursos DENTRO da VPC:
  Gateway Endpoints não funcionam via:
  ✗ VPN Site-to-Site
  ✗ Direct Connect
  ✗ VPC Peering (de outras VPCs)
  ✗ Transit Gateway
  
  Recursos on-premises que acessam a VPC via VPN/DX não se beneficiam
  do Gateway Endpoint — o tráfego deles vai pelo caminho normal

Limitação 3 — DNS público do S3 ainda resolve para IPs públicos:
  O endpoint não muda a resolução DNS
  → O nome s3.amazonaws.com ainda resolve para IPs públicos
  → O que muda é a ROTA para esses IPs (passa pelo endpoint, não pelo NAT)
  → Aplicações não precisam mudar nada — a rota é transparente

Limitação 4 — Sem suporte a IPv6 (apenas IPv4):
  Gateway Endpoints funcionam apenas com tráfego IPv4
  Para IPv6 com S3: usar Interface Endpoints ou rota IPv6 direta
```

## Gateway Endpoint vs Interface Endpoint para S3

```
┌─────────────────────┬─────────────────────────┬──────────────────────────┐
│ Aspecto             │ Gateway Endpoint (S3)   │ Interface Endpoint (S3)  │
├─────────────────────┼─────────────────────────┼──────────────────────────┤
│ Custo               │ Gratuito                │ $0.01/h por AZ + $0.01/GB│
│ Implementação       │ Rota na Route Table     │ ENI com IP privado        │
│ DNS                 │ Sem mudança             │ DNS privado opcional      │
│ Escopo              │ Dentro da VPC           │ On-premises via VPN/DX   │
│ IPv6                │ Não                     │ Sim                       │
│ Endpoint Policy     │ Sim                     │ Sim (Bucket Policy)       │
│ Alta disponibilidade│ Automática (AWS)        │ 1 ENI por AZ             │
│ Quando usar         │ Padrão para EC2/ECS/EKS │ On-premises ou IPv6      │
└─────────────────────┴─────────────────────────┴──────────────────────────┘

Recomendação: sempre criar Gateway Endpoints para S3 e DynamoDB.
É gratuito e elimina o custo de NAT para acesso a esses serviços.
```

## Verificando que o tráfego usa o endpoint

```bash
# Dentro de uma instância EC2 privada (sem IGW, sem NAT):
# Testar se S3 é acessível via endpoint
aws s3 ls s3://meu-bucket --region us-east-1

# Verificar a rota que o pacote toma para S3
# Primeiro, obter o IP atual do S3:
nslookup s3.amazonaws.com
# Resultado: um IP público da AWS (ex: 52.216.0.0)

# Verificar a rota para esse IP
ip route get 52.216.0.0
# Se o endpoint estiver funcionando:
# 52.216.0.0 via 10.0.1.1 dev eth0 src 10.0.10.50
# (vai pelo gateway local, não pelo NAT)

# Monitorar custo: verificar se BytesOutToDestination do NAT diminuiu
# após criar o endpoint (métrica CloudWatch do NAT Gateway)
aws cloudwatch get-metric-statistics \
  --namespace AWS/NATGateway \
  --metric-name BytesOutToDestination \
  --dimensions Name=NatGatewayId,Value=nat-0abc123 \
  --start-time $(date -d '1 day ago' -Iseconds) \
  --end-time $(date -Iseconds) \
  --period 3600 --statistics Sum
```

## Erros comuns e armadilhas

**Criar o endpoint mas não associar às Route Tables corretas:** o endpoint existe mas as instâncias ainda usam o NAT. Verificar com `describe-vpc-endpoints` que as Route Tables das subnets privadas estão na lista `RouteTableIds`.

**Esquecer de adicionar buckets do Amazon Linux nas Endpoint Policies restritivas:** ao criar uma Endpoint Policy que limita acesso a buckets específicos, o `yum`/`dnf` na instância para de funcionar — porque ele acessa `amazonlinux.us-east-1` e repositórios similares. Sempre incluir os buckets de repositório do Amazon Linux na policy.

**Assumir que o endpoint cobre tráfego de VPN/Direct Connect:** recursos on-premises não se beneficiam do Gateway Endpoint. Para eles, o tráfego S3 ainda vai pelo seu link de rede normal. Use Interface Endpoints com DNS privado para cobrir o on-premises.

## 🧩 Quiz de Fixação

1. Uma empresa tem 10 instâncias EC2 em subnets privadas que fazem download de 500 GB/mês de objetos do S3 via NAT Gateway. Calcule a economia mensal de criar um Gateway Endpoint para S3 (considere custo de NAT de $0.045/GB e que o download de dados do S3 em si tem custo separado).

2. Uma Endpoint Policy restringe o Gateway Endpoint para `arn:aws:s3:::empresa-dados-producao/*`. Uma instância EC2 privada tenta fazer `yum update` e falha. Por que, e como corrigir sem remover a restrição de segurança?

3. Uma empresa tem instâncias on-premises conectadas via Direct Connect à VPC. Elas precisam acessar o S3 sem passar pela internet pública. Um Gateway Endpoint resolve esse problema? O que usar no lugar?

**Respostas:**

1) **Economia com Gateway Endpoint:**
- Custo atual de NAT para S3: 500 GB × $0.045/GB = **$22.50/mês** por instância × 10 instâncias = **$225/mês**

Porém, o custo de NAT é por **dados processados pelo NAT Gateway** — se as 10 instâncias *juntas* processam 500 GB/mês via NAT para S3:
- Custo eliminado: 500 GB × $0.045/GB = **$22.50/mês**

Com o Gateway Endpoint, esse tráfego não passa mais pelo NAT Gateway:
- **Economia: $22.50/mês** (ou mais, se o volume for maior)
- O custo de dados S3 em si (egress/ingress de objetos) continua existindo separadamente
- O Gateway Endpoint é gratuito — zero custo adicional
- Para um cluster EKS com muitas imagens ECR (armazenadas em S3): a economia pode ser de centenas de dólares por mês

2) O `yum update` falha porque a Endpoint Policy bloqueia acesso a qualquer bucket que não seja `empresa-dados-producao/*`. Os repositórios do Amazon Linux estão em buckets como `amazonlinux.us-east-1` e `amazonlinux-2-repos-us-east-1`, que não correspondem ao padrão permitido. **Correção:** adicionar os buckets de repositório do Amazon Linux à Endpoint Policy:
```json
{
  "Effect": "Allow",
  "Principal": "*",
  "Action": ["s3:GetObject"],
  "Resource": [
    "arn:aws:s3:::amazonlinux.us-east-1/*",
    "arn:aws:s3:::amazonlinux-2-repos-us-east-1/*",
    "arn:aws:s3:::amazonlinux-2023-repos-us-east-1/*",
    "arn:aws:s3:::packages.us-east-1.amazonaws.com/*"
  ]
}
```
Isso mantém a restrição nos buckets de dados de negócio enquanto permite que o gerenciador de pacotes funcione normalmente.

3) **Não, um Gateway Endpoint NÃO resolve para on-premises.** A limitação fundamental é que Gateway Endpoints funcionam apenas para tráfego originado de recursos dentro da VPC. Tráfego de Direct Connect chega à VPC via Virtual Private Gateway ou Transit Gateway, mas as rotas do Gateway Endpoint não são propagadas para esses recursos on-premises. **Solução:** criar um **Interface Endpoint para S3** com DNS privado habilitado. Com o Interface Endpoint: (a) uma ENI com IP privado da VPC é criada; (b) com DNS privado ativado, o nome `s3.amazonaws.com` resolve para o IP da ENI dentro da VPC; (c) o tráfego on-premises que chega via Direct Connect, ao tentar resolver `s3.amazonaws.com`, recebe o IP da ENI; (d) o pacote vai pelo Direct Connect → VPC → Interface Endpoint → S3, sem toque na internet pública. O Interface Endpoint tem custo ($0.01/hora/AZ + $0.01/GB), mas é a única opção para on-premises acessar S3 privadamente via Direct Connect.
