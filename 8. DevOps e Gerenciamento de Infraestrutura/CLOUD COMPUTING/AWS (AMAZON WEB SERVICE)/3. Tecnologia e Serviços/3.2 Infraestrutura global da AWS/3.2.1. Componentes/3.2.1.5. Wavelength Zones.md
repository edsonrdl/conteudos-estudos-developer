### AWS Wavelength Zones — computação AWS dentro das redes 5G

AWS Wavelength Zones são infraestruturas AWS embarcadas diretamente nos data centers das operadoras de telecomunicações 5G. Enquanto Local Zones aproximam a computação de cidades específicas, as Wavelength Zones vão além — colocam os servidores AWS literalmente dentro das instalações das operadoras de rede, na mesma infraestrutura que processa o tráfego 5G. O resultado é latência de um único dígito de milissegundos (< 10ms) para dispositivos móveis 5G, sem que o tráfego precise sair da rede da operadora para chegar aos servidores de aplicação.

---

## O conceito fundamental: computação na borda da rede móvel

```
Problema sem Wavelength:
  Dispositivo 5G (smartphone, veículo autônomo, robô)
       ↓ rede 5G
  Torre 5G (Radio Access Network — RAN)
       ↓ backbone da operadora
  Ponto de Presença da Operadora (PoP)
       ↓ internet ou backbone AWS
  Região AWS (us-east-1, sa-east-1, etc.)
  
  Latência total: 50-100ms (backbone da operadora + internet + AWS)
  Para aplicações de tempo real: inaceitável

Com Wavelength Zone:
  Dispositivo 5G
       ↓ rede 5G
  Torre 5G (RAN)
       ↓ backbone 5G da operadora
  Data Center da Operadora → [Wavelength Zone AWS aqui]
  
  Latência total: < 10ms (o tráfego nunca sai da rede da operadora)
  
Onde está a Wavelength Zone:
  → Dentro do Mobile Edge Computing (MEC) da operadora
  → Na mesma localização que o User Plane Function (UPF) 5G
  → O pacote do dispositivo 5G chega à Wavelength Zone
    sem passar pela internet ou pela Região AWS
```

## Como as Wavelength Zones funcionam tecnicamente

```
Arquitetura 5G com Wavelength:

[Dispositivo 5G]
     |
     | Protocolo 5G (NR - New Radio)
     |
[gNB - Torre 5G]
     |
     | Backhaul 5G
     |
[5G Core Network - da operadora]
  ├── Control Plane (AMF, SMF) → pode estar na nuvem da operadora
  └── User Plane (UPF)
         |
         | Tráfego de dados (N6 interface)
         |
[Wavelength Zone AWS]
  ├── Carrier Gateway (gateway de conectividade com a operadora)
  ├── EC2 instances (compute)
  ├── EBS volumes (storage)
  └── VPC subnet (estende a VPC da Região)
         |
         | Backbone AWS (para Região pai)
         |
[Região AWS - serviços restantes]
  ├── S3, RDS, Lambda, etc.
  └── IAM, CloudTrail, CloudWatch

Carrier Gateway:
  → Componente único das Wavelength Zones
  → Permite que dispositivos 5G acessem instâncias EC2 na Wavelength
  → Os IPs das instâncias são "carrier IPs" (espaço de endereços da operadora)
  → Tráfego nunca vai para internet pública
```

## Casos de uso

### Veículos autônomos

```
Por que precisam de Wavelength:

Veículo autônomo em alta velocidade:
  Velocidade: 120 km/h = 33 metros/segundo
  Latência de 100ms: o carro percorre 3,3 metros "cego"
  Latência de 10ms: o carro percorre 33 cm "cego"
  
  Para decisões de segurança: 33 cm vs. 3,3 metros é a diferença
  entre um freio emergencial bem-executado e uma colisão

Arquitetura com Wavelength:
  [Carro com câmeras, LiDAR, sensores]
     ↓ 5G, < 10ms
  [Wavelength Zone - processamento de visão computacional]
     → Detecta obstáculos, sinalização, pedestres em tempo real
     → Envia decisões de controle de volta ao carro em < 10ms
     ↓ backbone AWS
  [Região AWS - analytics, mapeamento, atualizações de modelo ML]

Watchdog local (safety net):
  O carro tem processamento local para casos de conectividade perdida
  Wavelength complementa — não substitui — a autonomia onboard
```

### Realidade aumentada e mixta (AR/MR)

```
Microsoft HoloLens 2, Apple Vision Pro, etc. via 5G:

Sem Wavelength:
  Óculos AR renderiza localmente (limitado pela bateria e processamento)
  → Gráficos simples, bateria dura pouco
  → Experiência limitada

Com Wavelength:
  Óculos AR captura o ambiente e envia via 5G
  Wavelength processa e renderiza os objetos virtuais em < 10ms
  Envia os frames renderizados de volta ao dispositivo
  
  → Processamento pesado na nuvem (sem limites de CPU/GPU)
  → Óculos mais leve (menos processamento local)
  → Gráficos mais ricos
  → Latência < 10ms: imperceptível para o olho humano (< 20ms é o threshold)

Cloud rendering para jogos (xCloud, GeForce NOW):
  → Jogo renderizado na Wavelength Zone
  → Stream de vídeo H.264/H.265 ao dispositivo móvel em < 10ms
  → Controles do jogador voltam em < 10ms
  → Total round-trip < 20ms: jogável como jogo local
```

### IoT industrial e manufatura

```
Fábrica 5G com robôs colaborativos:

[Robô industrial]
     ↓ 5G privado da fábrica (5G private network)
[Wavelength Zone - dentro da fábrica ou PoP próximo]
     → Visão computacional para controle de qualidade
     → Coordenação de múltiplos robôs em tempo real
     → Detecção de anomalias nos processos

Vantagem sobre 5G privado on-premises puro:
  → Usa serviços AWS nativamente (S3 para imagens, SageMaker para ML)
  → Sem gerenciar hardware de edge computing próprio
  → Escala com workloads — não compra hardware para o pico

Telemedicina e cirurgia remota:
  → Médico controla robô cirúrgico remotamente
  → Feedback tátil e visual via 5G + Wavelength
  → Latência < 10ms permite feedback háptico em tempo real
```

## Wavelength Zones vs. Local Zones vs. Edge Locations

```
                  WAVELENGTH ZONES   LOCAL ZONES         EDGE LOCATIONS
Onde está         Rede da operadora  Data center em      PoPs AWS globais
                  5G (MEC)           cidade específica
Conectividade     Via rede 5G        Via internet ou     Via internet
principal         (sem internet)     Direct Connect
Latência          < 10ms para 5G     < 5ms para cidade   < 5ms para HTTP
Serviços          EC2, EBS, VPC      EC2, ECS, RDS,      CloudFront,
                  (limitado)         ElastiCache, ALB    Lambda@Edge
Acesso sem 5G     Não (carrier GW)   Sim (internet)      Sim (internet)
Caso de uso       Devices 5G         Apps low-latency    Cache CDN,
principal         (veículos, AR/MR)  em cidade           computação edge
Disponibilidade   Verizon, KDDI,     30+ cidades EUA     300+ global
                  SK Telecom, etc.   + internacional
Brasil            Não confirmado      Não confirmado      Sim (SP, RJ, FOR)
```

## Habilitando e usando Wavelength Zones

```
Habilitação (similar a Local Zones):
  Console → EC2 → Settings → Zones → Enable Wavelength Zone

Criar subnet na Wavelength Zone:
  aws ec2 create-subnet \
    --vpc-id vpc-xxx \
    --cidr-block 10.0.10.0/24 \
    --availability-zone-id use1-wl1-bos-wlz-1  ← Boston Wavelength

Criar Carrier Gateway (específico de Wavelength):
  aws ec2 create-carrier-gateway \
    --vpc-id vpc-xxx
  
  # Adicionar rota na subnet Wavelength
  # 0.0.0.0/0 → carrier-gateway (para dispositivos 5G chegarem)

EC2 com Carrier IP:
  aws ec2 allocate-address --domain vpc --network-border-group us-east-1-wl1-bos-wlz-1
  
  → Retorna um "carrier IP" (espaço de endereços da Verizon, por ex.)
  → Dispositivo 5G acessa a instância por esse carrier IP
  → Sem passar pela internet pública

Comunicação com Região pai:
  Wavelength Zone ↔ Região us-east-1:
  → Via backbone AWS (não internet)
  → S3, RDS e outros serviços da Região acessíveis normalmente
  → Latência adicional: ~15-20ms (aceitável para dados não-críticos)
```

## Limitações das Wavelength Zones

```
1. Serviços limitados:
   Apenas EC2 e EBS basicamente — muito menos que uma Região
   Sem Lambda, sem RDS, sem S3 localmente
   → Serviços avançados devem ficar na Região pai

2. Dependência da operadora:
   → Só funciona com dispositivos na rede da operadora parceira
   → Usuário em roaming ou em WiFi: não se beneficia
   → A operadora precisa ter parceria com a AWS

3. Disponibilidade geográfica restrita:
   → Muito menos Wavelength Zones que Local Zones ou Edge Locations
   → Disponível principalmente em grandes cidades dos EUA e Ásia

4. Custo premium:
   Instâncias EC2 em Wavelength custam mais que na Região
   Carrier Gateway tem custo adicional
   → Justificado apenas quando < 10ms é genuinamente necessário

5. Casos de uso de nicho:
   A maioria das aplicações não precisa de < 10ms
   → Para web apps, APIs, e-commerce: Local Zones ou CloudFront são suficientes
   → Wavelength é especializado para 5G edge computing real
```

## 🧩 Quiz de Fixação

1. Por que a Wavelength Zone consegue oferecer latência menor que uma Local Zone para dispositivos 5G, se ambas são infraestruturas físicas próximas ao usuário?
2. Uma empresa de jogos quer lançar cloud gaming para usuários de smartphones 5G no Japão. Por que Wavelength com KDDI é superior a usar uma Local Zone próxima às cidades japonesas para esse caso de uso específico?
3. Um arquiteto propõe usar Wavelength Zone para hospedar toda a stack de backend de um aplicativo móvel (incluindo banco de dados, filas, e APIs), argumentando que "todos os usuários terão latência mínima". Quais são as limitações técnicas dessa proposta e qual arquitetura híbrida seria mais adequada?

**Respostas:**
1) A diferença está em onde o tráfego é processado dentro da rede. Uma Local Zone é uma extensão da AWS posicionada em uma cidade, mas o tráfego do dispositivo 5G ainda precisa: sair do aparelho → passar pela RAN (radio access network) → percorrer o backbone da operadora até um ponto de interconexão → atravessar a internet ou uma conexão privada → chegar à Local Zone. Esse percurso adiciona 10-30ms extras de backbone de operadora + troca de rede. A Wavelength Zone fica dentro da infraestrutura da própria operadora 5G, no mesmo local onde o User Plane Function (UPF) processa o tráfego 5G. O pacote do dispositivo vai da torre 5G pelo backhaul curto até o MEC da operadora — e lá encontra os servidores AWS. O tráfego nunca sai da rede da operadora para chegar à Wavelength. Resultado: a Wavelength elimina o trecho de internet e o hop adicional de interconexão, reduzindo a latência de 30-50ms (Local Zone via 5G) para < 10ms.
2) Para cloud gaming via smartphones 5G, a Wavelength com KDDI é superior à Local Zone por três razões específicas: (1) O tráfego de jogo (frames renderizados + inputs do jogador) nunca precisa sair da rede KDDI — menor jitter (variação de latência), que é tão importante quanto a latência absoluta para jogabilidade; (2) O custo de data transfer é menor — o tráfego entre dispositivo e Wavelength não gera custo de egress pois permanece dentro da rede da operadora; (3) A latência < 10ms via Wavelength permite controle de jogo reativo — com uma Local Zone o melhor esperado seria ~15-20ms via 5G + backbone + internet, que pode causar input lag perceptível em jogos competitivos. A Local Zone seria suficiente para usuários de WiFi ou outros tipos de conexão, enquanto Wavelength é otimizada especificamente para o canal 5G direto.
3) Limitações técnicas: (1) Wavelength Zones oferecem apenas EC2 e EBS — sem Lambda, sem RDS, sem SQS, sem S3. Hospedar banco de dados exigiria EC2 com banco auto-gerenciado (sem RDS gerenciado), perdendo benefícios de backup automático, Multi-AZ e failover; (2) Wavelength só serve dispositivos na rede 5G da operadora parceira — usuários em WiFi, usuários com outras operadoras, e integrações B2B (APIs chamadas de servidores) teriam latência maior pois não se beneficiam do carrier gateway; (3) O armazenamento é muito mais caro e limitado na Wavelength; (4) Alta disponibilidade é difícil — Wavelength Zones não têm o equivalente de Multi-AZ e há muito menos redundância. Arquitetura híbrida adequada: Wavelength Zone → apenas as partes que genuinamente precisam de < 10ms: processamento de frames de vídeo em tempo real, recebimento de inputs de controle, e lógica de estado de sessão (ElastiCache básico); Região AWS (us-east-1) → banco de dados (RDS Aurora), fila de mensagens (SQS), armazenamento (S3), APIs administrativas, analytics, autenticação (Cognito); CloudFront → assets estáticos do jogo (sprites, assets, downloads). Os dois ambientes se comunicam via backbone AWS com latência adicional de ~20ms aceitável para operações não-críticas de tempo real.
