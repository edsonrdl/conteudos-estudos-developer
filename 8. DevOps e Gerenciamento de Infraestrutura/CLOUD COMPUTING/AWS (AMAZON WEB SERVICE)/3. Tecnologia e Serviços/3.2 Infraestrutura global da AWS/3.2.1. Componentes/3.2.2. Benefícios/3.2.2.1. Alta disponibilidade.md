### Alta disponibilidade — como a AWS garante que sistemas funcionem mesmo com falhas

Alta disponibilidade (HA — High Availability) é a capacidade de um sistema continuar operando mesmo quando componentes individuais falham. Na infraestrutura global da AWS, HA não é um recurso opcional — é a consequência natural de usar múltiplas AZs, Regiões e serviços gerenciados projetados com redundância desde o início. Entender como a AWS implementa HA em diferentes camadas e como projetar workloads que aproveitam essa infraestrutura é fundamental para construir sistemas confiáveis.

---

## SLAs dos principais serviços AWS

```
SLA (Service Level Agreement): compromisso de disponibilidade da AWS

Serviços com SLA de 99.99% (quatro noves = ~52 min/ano de downtime):
  ├── Amazon EC2 (com múltiplas instâncias em múltiplas AZs)
  ├── Amazon S3 (99.99% de disponibilidade, 11 noves de durabilidade)
  ├── Amazon RDS Multi-AZ
  ├── Amazon DynamoDB
  ├── Amazon ELB (Elastic Load Balancing)
  └── Amazon CloudFront

Serviços com SLA de 99.9% (três noves = ~8.7h/ano de downtime):
  ├── Amazon EC2 (instância única)
  ├── Amazon RDS Single-AZ
  └── Outros serviços gerenciados básicos

Disponibilidade por configuração:
  Instância única (Single AZ):      99.9%   (~8.7h/ano)
  Multi-AZ (2 AZs):                 99.99%  (~52min/ano)
  Multi-Region Active-Passive:       99.999% (~5.25min/ano)
  Multi-Region Active-Active:        99.9999% (~31seg/ano)

Custo de disponibilidade:
  Cada "nove" adicional aumenta complexidade e custo
  Avalie o custo do downtime vs. custo de HA:
  Se 1h de downtime custa $10.000:
  → 99.9%: ~8.7h/ano = risco de $87.000/ano em perda
  → 99.99%: ~52min/ano = risco de $8.700/ano
  → Custo de Multi-AZ RDS: ~2x o preço do Single-AZ
  → ROI: se custo de downtime > custo de Multi-AZ, vale a pena
```

## Como a AWS implementa HA em cada camada

### Camada 1: Hardware e infraestrutura física

```
AWS projetou a infraestrutura física para isolamento de falhas:

Energia redundante por AZ:
  Cada AZ tem múltiplas subestações elétricas independentes
  + geradores diesel de backup
  + UPS (Uninterruptible Power Supply) de alta capacidade
  
  Falha em uma subestação → sem impacto para a AZ
  Falha de energia da cidade (Blackout) → geradores assumem automaticamente

Rede redundante:
  Múltiplos provedores de fibra por AZ (não uma única operadora)
  Redundância de uplinks entre AZs
  
  "Se um cabo for cortado (obra na rua, sabotagem), 
   o tráfego rerouted automaticamente via outro caminho"

Cooling (resfriamento) redundante:
  Sistemas HVAC independentes com failover automático
  Hot/Cold aisle containment para eficiência e redundância

Servidores com hardware redundante:
  RAID para storage
  Dual power supply em cada servidor
  Redundância de NICs (Network Interface Cards)
```

### Camada 2: Serviços gerenciados com HA nativo

```
Serviços que têm HA sem configuração adicional:

Amazon S3:
  → Dados replicados em múltiplas AZs AUTOMATICAMENTE
  → 11 noves de durabilidade (99.999999999%)
  → Probabilidade de perder um objeto: 0.000000001%
  → Você só faz PUT — AWS cuida da replicação
  
  Como a AWS calcula 11 noves:
  "Você pode armazenar 10 milhões de objetos e
   esperar perder 1 objeto a cada 10.000 anos"

Amazon DynamoDB:
  → Replicado em 3 AZs por padrão
  → Sem configuração de Multi-AZ necessária
  → Failover automático transparente

Amazon SQS, SNS:
  → Mensagens replicadas em múltiplas AZs
  → Sem fila única que pode cair
  → Alta durabilidade nativa

AWS Lambda:
  → Executa em múltiplas AZs automaticamente
  → Se uma AZ tiver problema: invocações vão para outras AZs
  → Sem configuração necessária

Amazon Route 53:
  → DNS distribuído globalmente em múltiplos pontos
  → Sem SPOF de DNS
  → 100% de SLA (único serviço com SLA de 100%)
```

### Camada 3: Serviços que exigem configuração de HA

```
Serviços onde VOCÊ precisa configurar HA:

Amazon RDS:
  Single-AZ (padrão): um banco, uma AZ = SPOF
  → Se a AZ falhar: banco inacessível
  
  Multi-AZ (recomendado para produção):
  aws rds create-db-instance \
    --multi-az  ← uma flag habilita HA completa
  → Primary em uma AZ, Standby em outra
  → Replicação síncrona
  → Failover automático em 30-60 segundos
  → SLA: 99.95% (em vez de 99.9% do Single-AZ)

Amazon EC2:
  Instância única = SPOF
  → Configurar Auto Scaling Group com múltiplas AZs
  → ALB distribui tráfego
  → Se instância falha: ASG lança nova automaticamente

Amazon ElastiCache:
  Single node = SPOF
  → Habilitar Multi-AZ com failover automático
  → Primary + Replica(s) em AZs diferentes
```

## Padrões de arquitetura de alta disponibilidade

### Padrão fundamental: Stateless + ALB + Multi-AZ ASG

```
A arquitetura mais comum para web applications:

Internet
    │
[Route 53] → health checks + DNS failover
    │
[CloudFront] → cache de conteúdo estático + WAF + Shield
    │
[ALB] → distribuído entre AZs automaticamente
  ├─────────────────────────────────┐
  ▼                                 ▼
[EC2/ECS em AZ-a]           [EC2/ECS em AZ-b]
  └──────────────────────────────────┘
              ↓
    [RDS Aurora Multi-AZ]
    Primary: AZ-a ←replicação síncrona→ Replica: AZ-b
    
    [ElastiCache Redis Multi-AZ]
    Primary: AZ-a ←replicação→ Replica: AZ-b

Cenário de falha na AZ-a:
  t=0:    AZ-a falha
  t=10s:  ALB health check detecta EC2 em AZ-a como unhealthy
  t=10s:  ALB para de rotear para AZ-a
  t=30s:  RDS Multi-AZ detecta falha do Primary
  t=60s:  RDS Multi-AZ promove Replica (AZ-b) para Primary
  t=60s:  DNS do RDS atualizado
  t=90s:  ASG lança novas EC2 em AZ-b para compensar
  
  Downtime percebido pelo usuário: ~10-60 segundos
  (ALB redireciona em 10s; RDS failover em 60s = gargalo)
```

### Padrão avançado: Stateless com sessão externalizada

```
Para zero perda de sessão durante failover:

PROBLEMA com sessão na memória do EC2:
  Usuário → EC2-1 (sessão na memória)
  EC2-1 falha → ALB roteia para EC2-2
  EC2-2 não tem a sessão → usuário deslogado
  → Péssima experiência do usuário

SOLUÇÃO com sessão no ElastiCache:
  Usuário → EC2-1 → salva sessão no ElastiCache (AZ-a ou AZ-b)
  EC2-1 falha → ALB roteia para EC2-2
  EC2-2 → busca sessão no ElastiCache → encontra → usuário continua logado
  
  Código:
  # Python Django com Redis para sessão
  SESSION_ENGINE = 'django.contrib.sessions.backends.cache'
  CACHES = {
      'default': {
          'BACKEND': 'django_redis.cache.RedisCache',
          'LOCATION': 'redis://my-elasticache-cluster:6379/1',
      }
  }
  
  Resultado: failover de qualquer EC2 = zero impacto na sessão do usuário
```

### Padrão de alta disponibilidade para bancos de dados

```
Estratégia em camadas para diferentes cargas:

WRITES (sempre para o Primary):
  Application → ElastiCache (verificar cache miss)
              → RDS Primary (para writes e cache miss reads críticos)

READS (distribuir entre Replicas):
  Application → ElastiCache (verificar cache primeiro)
  Cache hit: < 1ms → resposta imediata, sem ir ao banco
  Cache miss:
    → Read Replica 1 (analytics queries, relatórios)
    → Read Replica 2 (reads da aplicação não-críticos)
    → RDS Primary (apenas writes e reads que EXIGEM consistência)

Aurora Multi-AZ (6 cópias em 3 AZs):
  Aurora mantém 6 cópias dos dados em 3 AZs:
  AZ-a: 2 cópias
  AZ-b: 2 cópias
  AZ-c: 2 cópias
  
  Pode perder 2 cópias sem impacto nos writes
  Pode perder 3 cópias sem impacto nos reads
  → Muito mais resiliente que RDS Multi-AZ tradicional
  → Failover em < 30 segundos (vs. 60s do RDS)
```

## Health Checks — detectar falhas rapidamente

```
Health Checks são o mecanismo de detecção de falhas:

ALB Health Check:
  Path: /health (endpoint que você implementa)
  Interval: 30 segundos
  Healthy threshold: 2 checks consecutivos OK → saudável
  Unhealthy threshold: 3 checks falhos → remove do pool
  
  Timeout total para detectar instância doente:
  3 checks × 30s = 90 segundos no pior caso
  
  Para detectar mais rápido (critical workloads):
  Interval: 10 segundos
  Unhealthy threshold: 2 checks
  → Detecta em 20 segundos (vs. 90s)

Route 53 Health Check:
  Monitora endpoints periodicamente
  → Se primary falhar: DNS redireciona para secondary
  → Interval: 10 ou 30 segundos
  → Failover multi-region automático
  
  Calculadora de RTO com Route 53:
  Health check interval: 30s
  TTL do DNS: 60s
  
  Tempo total de failover:
  30s (detectar) + 60s (TTL expira) + 30s (clientes atualizarem) = ~2 minutos
  
  Para minimizar RTO:
  → TTL baixo (60s) + Health check rápido (10s) = ~1 minuto de failover

Auto Scaling Health Check:
  EC2 Health Check: verifica se a instância EC2 está rodando (básico)
  ELB Health Check: verifica se a aplicação está respondendo (melhor)
  
  Configurar ASG para usar ELB Health Check:
  aws autoscaling update-auto-scaling-group \
    --auto-scaling-group-name my-asg \
    --health-check-type ELB \
    --health-check-grace-period 300
```

## Availability vs. Durability — conceitos distintos

```
DISPONIBILIDADE (Availability):
  "O serviço está acessível?"
  Medida em % de uptime
  
  S3 Standard: 99.99% de disponibilidade
  → Em 0.01% do tempo, o S3 pode não estar acessível
  → ~52 minutos/ano de possível indisponibilidade
  
DURABILIDADE (Durability):
  "Os dados ainda existem?"
  Medida em probabilidade de perda de dados
  
  S3 Standard: 99.999999999% de durabilidade (11 noves)
  → Probabilidade de perder um objeto: 0.000000001%
  → Um objeto pode estar temporariamente inacessível (disponibilidade)
  → Mas os bytes existem e serão recuperáveis quando o serviço voltar

Confundir os dois é perigoso:
  "S3 tem 11 noves então meus dados estão sempre disponíveis" ← ERRADO
  
  Correto:
  → 11 noves de DURABILIDADE: os dados não serão perdidos
  → 99.99% de DISPONIBILIDADE: o serviço pode ficar indisponível por 52 min/ano
  → Para disponibilidade adicional: use S3 Multi-Region Access Points
    ou replicação cross-region
```

## Monitorando disponibilidade

```
CloudWatch métricas de disponibilidade:

Para ALB:
  HealthyHostCount: instâncias saudáveis no target group
  UnHealthyHostCount: instâncias não saudáveis
  
  Alarm: UnHealthyHostCount > 0
  → Notifica quando qualquer instância vai para unhealthy

Para RDS:
  DatabaseConnections: conexões ativas
  ReplicaLag: atraso de replicação (Multi-AZ)
  
  Alarm: ReplicaLag > 30 segundos
  → Indica problema de replicação antes do failover

Para Route 53:
  Metric: HealthCheckPercentageHealthy
  
  Alarm: < 100% (qualquer endpoint com problema)

SLA próprio (como calcular o seu):
  Disponibilidade = (total_minutos - downtime_minutos) / total_minutos × 100
  
  Se você teve 10 minutos de downtime no mês:
  (43.800 - 10) / 43.800 × 100 = 99.977%
  
  Para 99.99% você pode ter no máximo 4.38 minutos/mês de downtime
```

## 🧩 Quiz de Fixação

1. Uma aplicação tem SLA de 99.9% com o cliente, mas o sistema usa EC2 Single-AZ e RDS Single-AZ. Por que essa arquitetura não atinge o SLA e quais mudanças mínimas seriam necessárias para atingir 99.99%?
2. Qual é a diferença entre disponibilidade e durabilidade no contexto do Amazon S3, e por que um backup em S3 não garante que os dados estarão disponíveis quando você mais precisar?
3. O ALB está com `HealthyHostCount = 1` (de 3 instâncias esperadas) às 3h da manhã. O On-Call recebe o alerta. Descreva o diagnóstico inicial e as ações de recuperação que o sistema deveria executar automaticamente vs. as que requerem intervenção humana.

**Respostas:**
1) EC2 Single-AZ tem SLA de 99.9% (~8.7h/ano de downtime potencial); RDS Single-AZ tem SLA de 99.9%. Combinados em série: 0.999 × 0.999 = 99.8% de disponibilidade do sistema — abaixo do 99.9% prometido ao cliente, e longe dos 99.99% almejados. Mudanças mínimas para 99.99%: (1) EC2 → Auto Scaling Group com mínimo 2 instâncias em 2 AZs diferentes + ALB distribuído entre as AZs. O ALB + ASG multi-AZ eleva a disponibilidade do tier de compute para 99.99% (SLA do ALB); (2) RDS Single-AZ → RDS Multi-AZ (adicionar `--multi-az` na criação ou modificar a instância existente). O RDS Multi-AZ tem SLA de 99.95%. Com ambos configurados: a disponibilidade do sistema sobe para ~99.94% (limitada pelo RDS Multi-AZ), muito mais próxima do 99.99%. Para atingir o 99.99% completo seria necessário Aurora Multi-AZ (SLA de 99.99%) e monitoramento com health checks otimizados.
2) Disponibilidade (99.99%): a capacidade de acessar objetos no S3 — em 0.01% do tempo (52 minutos/ano), o S3 pode retornar erros temporariamente; os dados existem mas não são acessíveis momentaneamente. Durabilidade (11 noves): a probabilidade de os dados não serem destruídos permanentemente — 99.999999999% garantia de que os bytes não são perdidos. A diferença prática: um backup em S3 não garante que os dados estarão disponíveis no momento exato de uma crise porque: (1) durante as janelas de indisponibilidade do S3 (raras mas existentes), o restore falharia; (2) se a Região inteira onde o S3 está sofrer um evento catastrófico, mesmo com 11 noves de durabilidade na mesma Região, o acesso seria impactado; (3) para garantia de disponibilidade de backup em cenários críticos, é necessário S3 Cross-Region Replication (dados em outra Região) + S3 Intelligent-Tiering ou S3 Multi-Region Access Points, que adicionam disponibilidade cross-region.
3) Diagnóstico automático (deve acontecer sem intervenção): o Auto Scaling Group, ao detectar apenas 1 instância healthy via ELB Health Check, já deve ter iniciado o processo de substituição das 2 instâncias unhealthy. O ASG termina as instâncias unhealthy e lança 2 novas na capacidade desejada. Se estiver configurado com múltiplas AZs e uma AZ estiver problemática, o ASG lança as novas instâncias em AZs saudáveis. O ALB continua servindo tráfego pela instância saudável restante durante esse processo. Ações que requerem intervenção humana: (1) Verificar por que as 2 instâncias ficaram unhealthy simultaneamente — isso é incomum e sugere um problema sistêmico (deploy defeituoso que está falhando nas novas instâncias também, problema de configuração, dependência compartilhada como banco de dados inacessível) que o Auto Scaling não consegue resolver sozinho; (2) Se o ASG está lançando e terminando instâncias em loop (thrashing), significa que o health check falha consistentemente nas novas instâncias — o engenheiro precisa verificar os logs da aplicação, o endpoint /health, e o status do RDS; (3) Se o problema for um deploy defeituoso, a ação correta é fazer rollback via CodeDeploy ou revertendo a task definition do ECS.
