### Recuperação de desastres — estratégias para sobreviver ao impensável

Recuperação de desastres (DR — Disaster Recovery) é o conjunto de processos e tecnologias que permitem a uma organização restaurar suas operações após um evento catastrófico — falha de Região inteira, erro humano crítico, ransomware, desastre natural. Na AWS, a disponibilidade de múltiplas Regiões geograficamente separadas transforma o DR de um projeto de $millions em on-premises para algo mensurável, testável e acessível. O segredo está em escolher a estratégia certa para o RPO e RTO que o negócio realmente exige — e testar regularmente se ela funciona.

---

## Os dois parâmetros fundamentais do DR

```
RPO — Recovery Point Objective:
  "Quanto de dado posso perder?"
  Mede a janela máxima de dados que pode ser perdida
  
  Backup diário: RPO = 24h
  → Se desastre ocorre às 23h, você perde 23h de dados (desde o último backup)
  
  Replicação em tempo real: RPO = segundos
  → Você perde no máximo os últimos segundos de transações

RTO — Recovery Time Objective:
  "Quanto tempo posso ficar fora do ar?"
  Mede o tempo máximo aceitável de indisponibilidade
  
  "Restaurar manualmente": RTO = horas a dias
  "Failover automático": RTO = minutos
  "Active-Active": RTO ≈ zero

Relação custo × proteção:
  
  RPO/RTO alto ────────────────────────► RPO/RTO baixo
  (aceita mais perda/tempo)              (quer perder menos)
  
  Custo: Baixo ─────────────────────────────────► Alto
  
  Backup &    Pilot     Warm       Active-
  Restore     Light     Standby    Active
  
Regra geral: cada ordem de magnitude de melhoria em RPO/RTO
             aumenta significativamente o custo de infraestrutura
```

## Estratégia 1: Backup and Restore

```
O mais simples e barato. RPO: horas. RTO: horas a dias.

Como funciona:
  Região A (produção, sempre ativa)
  → Backups periódicos replicados para Região B (via S3 Cross-Region)
  
  Em caso de desastre na Região A:
  1. Equipe percebe o desastre (pode levar minutos a horas)
  2. Provisiona infraestrutura na Região B (via IaC)
  3. Restaura dados do backup mais recente
  4. Atualiza DNS para apontar para Região B
  5. Valida que tudo funciona
  6. Serviço restaurado
  
  Total: horas a dias (manual)

Implementação na AWS:

  AWS Backup (backup centralizado):
  → Faz backup de EC2, EBS, RDS, DynamoDB, EFS, S3
  → Cross-Region Copy: replica backups para Região B automaticamente
  → Retention policies: define por quanto tempo manter
  
  aws backup create-backup-plan --backup-plan '{
    "BackupPlanName": "DR-Plan",
    "Rules": [{
      "RuleName": "Daily-Backup-with-CrossRegion",
      "TargetBackupVaultName": "primary-vault",
      "ScheduleExpression": "cron(0 2 * * ? *)",
      "StartWindowMinutes": 60,
      "CompletionWindowMinutes": 180,
      "Lifecycle": {"DeleteAfterDays": 30},
      "CopyActions": [{
        "DestinationBackupVaultArn": "arn:aws:backup:us-east-1:123:backup-vault:dr-vault",
        "Lifecycle": {"DeleteAfterDays": 90}
      }]
    }]
  }'

  S3 Cross-Region Replication (para dados em S3):
  → Objetos copiados para bucket em outra Região automaticamente
  → Pode ser assíncrona (replicação não é imediata)
  
  RDS Automated Backups:
  → Snapshot automático diário + logs de transação (Point-in-Time Recovery)
  → PITR: restaurar banco para qualquer ponto nos últimos 35 dias
  → Exportar snapshots para outra Região para DR

Quando usar:
  → Sistemas não-críticos (sites institucionais, ferramentas internas)
  → Quando o negócio tolera horas/dias de inatividade
  → Quando o custo de infraestrutura de DR precisa ser minimizado
  → Bom ponto de partida para empresas sem DR formal

RPO real: depende da frequência de backup
  Backup diário: RPO = 24h
  Backup horário: RPO = 1h
  Replicação de logs contínua: RPO = minutos
```

## Estratégia 2: Pilot Light

```
Segunda estratégia. RPO: minutos. RTO: 10-60 minutos.

Como funciona:
  Região A (produção): stack completo ativo
  Região B (DR): apenas dados replicados + componentes mínimos
  
  "Pilot light" = a chama piloto de um fogão a gás
  → Sempre acesa (mínimo ligado), pronta para inflamar rapidamente
  
  O que fica sempre rodando na Região B:
  ├── Banco de dados em replicação contínua (menor instância possível)
  ├── Container images no ECR (para deploy rápido)
  └── IaC (Terraform/CloudFormation) pronto para executar
  
  O que NÃO fica rodando (até precisar):
  ├── EC2/ECS (compute) → desligados ou mínimo
  ├── ALB → não provisionado
  └── Auto Scaling → configurado mas sem instâncias

Em caso de desastre na Região A:
  1. Alertas disparam (automático)
  2. Equipe ativa o plano de DR
  3. Executa Terraform/CloudFormation na Região B:
     → Levanta EC2/ECS com instâncias maiores
     → Provisiona ALB
     → Configura Auto Scaling
  4. Banco de dados na Região B promovido a primary
  5. DNS atualizado para Região B
  
  Total: 10-60 minutos (parcialmente manual)

Implementação:

  Aurora Global Database (banco sempre replicado):
  → Primary em us-east-1 (replicação para sa-east-1 com < 1s de lag)
  → RPO: segundos (dados quase em tempo real na Região B)
  → Em caso de DR: promote replica → vira primary em < 1 minuto
  
  DynamoDB Global Tables:
  → Replicação automática entre Regiões
  → Operações de escrita aceitas em qualquer Região replicada
  → RPO: segundos

  Custo do Pilot Light:
  Região B: apenas banco rodando (ex: db.r6g.large)
  + custo de replicação de dados
  Custo típico: 10-20% do custo da Região de produção
```

## Estratégia 3: Warm Standby

```
Terceira estratégia. RPO: segundos. RTO: 1-15 minutos.

Como funciona:
  Região A (produção): stack completo, capacidade total
  Região B (DR): stack reduzido mas FUNCIONANDO (ex: 20-30% da capacidade)
  
  "Warm" = já está aquecido e processando
  → Aceita tráfego real em volume reduzido
  → Em desastre: escalar rapidamente para capacidade total
  
  Região B sempre ativa com:
  ├── 2-3 instâncias EC2/ECS (vs. 10+ na Região A)
  ├── ALB ativo
  ├── Banco de dados replicado (como no Pilot Light)
  └── Auto Scaling configurado com max capacity disponível

Em caso de desastre:
  1. Route 53 detecta falha de health check na Região A
  2. DNS redireciona para Região B (automático, ~1 minuto)
  3. Auto Scaling na Região B escala para capacidade total
  4. Banco promovido a primary
  
  Total: 1-15 minutos (pode ser automático)

Implementação com Route 53 Failover:
  Route 53 Failover Routing:
  Record: api.empresa.com (Primary)  → ALB Região A, Health Check ON
  Record: api.empresa.com (Secondary) → ALB Região B
  
  Health Check: 
  → Monitora: /health na Região A
  → Interval: 10 segundos
  → Failure threshold: 3 checks consecutivos
  
  Failover automático:
  Região A falha → Health Check falha (3 × 10s = 30s)
  → Route 53 automaticamente serve o Secondary record (Região B)
  → TTL baixo (60s): todos os clientes migraram em ~90s total

Custo do Warm Standby:
  Região B: 20-30% da capacidade de produção sempre rodando
  Custo típico: 30-50% do custo da Região de produção

Quando usar:
  → Sistemas onde horas de downtime não são toleráveis
  → Quando RTO de 15 min é aceitável
  → Custo de DR ≈ 30-50% da produção é justificável
```

## Estratégia 4: Multi-Site Active-Active

```
Estratégia mais sofisticada. RPO: zero. RTO: zero (imperceptível).

Como funciona:
  Região A e Região B: ambas 100% ativas, recebendo tráfego
  Route 53 distribui tráfego entre as duas Regiões continuamente
  
  Em caso de falha de uma Região:
  → Route 53 detecta e remove a Região do balanceamento
  → Todo tráfego vai para a Região restante
  → Usuários percebem latência levemente maior, mas zero downtime

Topologias de Active-Active:
  
  Todas as Regiões iguais (pesos iguais):
  Route 53 Weighted: 50% us-east-1, 50% sa-east-1
  → Simples mas exige dados sincronizados em tempo real
  
  Latency-based com ativo-ativo:
  Route 53 Latency: usuário vai para a Região mais próxima
  → Usa múltiplas Regiões simultaneamente (cada um serve localmente)
  
  Geolocation ativo-ativo:
  Route 53 Geolocation: usuários BR → sa-east-1, US → us-east-1
  → Compliance + performance

O desafio: consistência de dados com escrita em múltiplas Regiões

  Problema clássico:
  Usuário compra produto em sa-east-1 (estoque: 10)
  Mesmo tempo: outro usuário compra em us-east-1 (também vê estoque: 10)
  Ambos confirmam → estoque vai para -1 (overselling!)
  
  Soluções:
  
  1. DynamoDB Global Tables (para dados com escrita distribuída):
     → Replicação entre Regiões em < 1 segundo
     → Conditional writes (optimistic locking) para evitar conflitos
     → Ideal para: dados de sessão, perfis, estado de usuário
  
  2. CRDTs (Conflict-free Replicated Data Types):
     → Estruturas de dados que se "mesclam" corretamente
     → Counters, sets, maps distribuídos sem conflitos
  
  3. Write to one, read from all (leitor universal):
     → Escreve APENAS em uma Região (a do usuário)
     → Replica assincronamente para outras
     → Leitura aceita eventual consistency
  
  4. Sharding geográfico (particionamento por usuário):
     → Usuários BR: seus dados VIVEM em sa-east-1
     → Usuários US: seus dados VIVEM em us-east-1
     → Sem conflito (cada usuário tem uma "home Region")
     → Em DR: home Region inativa → failover para outra Região
```

## Serviços AWS que facilitam DR

```
REPLICAÇÃO DE DADOS:
  Aurora Global Database:
  → Réplicas de leitura em até 5 Regiões
  → Lag de replicação: < 1 segundo
  → Failover para outra Região: < 1 minuto
  → RPO: segundos | RTO: < 1 minuto

  DynamoDB Global Tables:
  → Replicação automática em N Regiões
  → Escritas aceitas em qualquer Região
  → Resolução de conflito: "last write wins" (timestamp)
  → RPO: segundos | RTO: segundos (automático)

  S3 Cross-Region Replication:
  → Replicação assíncrona (não em tempo real)
  → S3 Replication Time Control (RTC): garante 99.99% dos objetos em 15 minutos
  → Útil para: dados de aplicação, backups, artefatos

ROTEAMENTO E FAILOVER:
  Route 53 Health Checks:
  → Monitora endpoints em múltiplas Regiões
  → Failover automático quando health check falha
  → TTL baixo + health check frequente = RTO mínimo

  Global Accelerator:
  → Failover de endpoint em < 30 segundos (sem depender de DNS TTL)
  → IPs estáticos que roteiam automaticamente para o endpoint saudável
  → Melhor que Route 53 para RTO muito baixo (sem problema de DNS caching)

INFRASTRUCTURE AS CODE (fundamental para DR):
  Terraform / CloudFormation:
  → Infraestrutura da Região B descrita como código
  → Em DR: terraform apply na Região B = ambiente completo em minutos
  → SEM IaC: reconstruir manualmente levaria horas/dias
  → Versionado no Git: você sabe exatamente o estado da infra

AWS Elastic Disaster Recovery (DRS):
  → Serviço gerenciado para DR de servidores (on-prem ou outras clouds)
  → Replicação contínua de discos para AWS (via agente)
  → Em DR: lança instâncias EC2 com dados mais recentes em minutos
  → RPO: segundos | RTO: minutos
```

## Testando o plano de DR — a parte mais negligenciada

```
"Um plano de DR não testado não é um plano de DR — é uma esperança."

Por que testar é crítico:
  → A maioria das falhas de DR em produção são descobertas
    DURANTE o desastre real, não antes
  → IaC pode ter drift (código ≠ realidade atual)
  → Credenciais podem ter expirado
  → Dados replicados podem estar corrompidos
  → Equipe pode não saber o procedimento sob pressão

Tipos de testes de DR:

1. TABLETOP EXERCISE (documentação apenas):
   → Reunião da equipe: "Se Região A cair agora, o que fazemos?"
   → Revisar o runbook passo a passo
   → Identificar gaps sem executar nada
   → Frequência: trimestral
   → Custo: horas de reunião

2. FAILOVER TEST (ambiente separado):
   → Provisionar ambiente de DR em staging/test
   → Simular failover completo
   → Medir RTO e RPO reais
   → Sem impacto na produção
   → Frequência: semestral

3. PILOT TEST EM PRODUÇÃO (impacto controlado):
   → Redirecionar % pequeno do tráfego para Região B
   → Ex: Route 53 Weighted: 95% Região A, 5% Região B
   → Validar que Região B funciona com tráfego real
   → Sem downtime para a maioria dos usuários
   → Frequência: anual para apps críticas

4. FULL FAILOVER (teste completo):
   → Migrar 100% do tráfego para Região B durante janela planejada
   → Validar todas as funcionalidades
   → Medir RTO real sob condições reais
   → Planejar rollback se algo der errado
   → Frequência: anual (custo e risco significativos)

Checklist de teste de DR:
  ✓ Provisionar infraestrutura na Região B via IaC: funciona?
  ✓ Banco de dados de DR tem dados recentes: sim? Quão recentes?
  ✓ Restore de backup: quanto tempo levou? Dados corretos?
  ✓ DNS failover: quanto tempo o Route 53 levou para redirecionar?
  ✓ Aplicação na Região B: todas as dependências funcionam?
  ✓ Credenciais e secrets: disponíveis na Região B?
  ✓ Certificados TLS: válidos na Região B?
  ✓ Equipe: todos sabem seus papéis no runbook?
  ✓ Comunicação: canal de comunicação de emergência funciona?
  ✓ Rollback: como retornar para Região A quando restaurada?
```

## Comparativo final das estratégias

```
                Backup &    Pilot      Warm       Active-
                Restore     Light      Standby    Active
                ─────────   ────────   ────────   ───────────
RPO             Horas       Minutos    Segundos   Zero
RTO             Horas/Dias  10-60 min  1-15 min   Zero
Infraestrutura  Zero em B   Dados+min  Stack red.  Stack completo
                            na B       na B        em ambas
Custo B         Quase zero  10-20% A   30-50% A   ~100% A (2x total)
Complexidade    Baixa       Média      Alta       Muito Alta
Automação DR    Manual      Parcial    Automático  Automático
Testes          Restore     Failover   Failover   Canary traffic
Ideal para      Não-crítico Importante Crítico    Missão crítica
```

## 🧩 Quiz de Fixação

1. Uma fintech processa R$ 5 milhões/hora em transações. O CTO define RPO de 30 segundos e RTO de 5 minutos. Qual estratégia de DR é a única que atende esses requisitos e quais serviços AWS específicos implementariam a replicação de dados com RPO de 30 segundos?
2. Um time implementou Pilot Light com Aurora Global Database em sa-east-1 (produção) e us-east-1 (DR). O desastre ocorre e a equipe precisa realizar o failover. Descreva os passos técnicos em ordem e o que pode dar errado em cada passo.
3. Por que um plano de DR nunca testado é potencialmente mais perigoso do que não ter plano de DR, e qual é o tipo de teste mínimo que deve ser feito regularmente sem impactar a produção?

**Respostas:**
1) Apenas Warm Standby ou Active-Active atendem RPO de 30 segundos + RTO de 5 minutos. Pilot Light pode ter RTO de 10-60 minutos (provisionamento necessário), que viola o requisito de 5 minutos. A recomendação é Warm Standby com stack reduzido sempre ativo em us-east-1 para failover automático. Serviços para RPO de 30 segundos: (1) Aurora Global Database — replica escritas para us-east-1 com lag < 1 segundo (muito abaixo dos 30s exigidos); em DR, o promote da réplica para primary leva < 1 minuto; (2) DynamoDB Global Tables — para dados de sessão, estado de transação temporária; replicação em < 1 segundo; escritas aceitas em ambas as Regiões; (3) S3 com Replication Time Control (RTC) — para documentos e artefatos; garante 99.99% dos objetos replicados em 15 minutos (adequado para dados não transacionais); (4) ElastiCache com replicação cross-region — para cache de tokens e sessões. O RTO de 5 minutos é garantido com Route 53 Failover Routing + health check de 10 segundos + TTL de 60 segundos + Warm Standby já rodando (sem necessidade de provisionar compute).
2) Passos técnicos do failover Pilot Light e o que pode dar errado: (1) Detectar o desastre — pode demorar minutos sem monitoramento automatizado; um CloudWatch Alarm + Route 53 Health Check automático evita dependência humana; risco: demora humana aumenta o tempo de downtime; (2) Promover a réplica Aurora Global Database em us-east-1 para primary via Console ou CLI (`aws rds promote-read-replica-db-cluster`) — risco: se a réplica teve replicação interrompida antes do desastre, pode haver lag maior que o RPO esperado; verificar `AuroraGlobalDBReplicationLag` antes; (3) Provisionar compute na Região de DR (EC2/ECS) via IaC — risco: o código Terraform pode estar desatualizado (drift) se a infra de produção evoluiu sem atualizar o IaC de DR; ou variáveis de ambiente e secrets do Secrets Manager podem não estar disponíveis em us-east-1 (se esqueceram de replicar); (4) Atualizar DNS Route 53 para apontar para us-east-1 — risco: TTL alto deixado por acidente (ex: 3600s) faz clientes continuarem indo para sa-east-1 inoperante por até 1 hora; solução: manter TTL baixo (60s) permanentemente; (5) Validar que a aplicação está funcionando em us-east-1 — risco: dependências de terceiros (pagamentos, APIs externas) podem ter configuração diferente na Região de DR; testar checklist completo de funcionalidades críticas antes de comunicar retorno ao ar.
3) Um plano de DR não testado é potencialmente mais perigoso porque cria uma falsa sensação de segurança. O time de liderança acredita que tem um plano, o que pode levar a menor vigilância e menor investimento em HA preventiva ("não precisamos de Multi-AZ, temos o plano de DR"). Quando o desastre real ocorre, a equipe descobre em tempo real os problemas: IaC desatualizado, secrets que não foram replicados, banco com dados inconsistentes, equipe que não sabe executar o runbook sob pressão, DNS com TTL alto — cada problema adiciona horas ao RTO real. Sem plano, a equipe pelo menos sabe que precisa construir o ambiente do zero e tem expectativas realistas. O tipo mínimo de teste regular sem impactar produção é o **Tabletop Exercise combinado com Restore Test**: trimestralmente, a equipe realiza um walkthrough do runbook de DR (tabletop), identifica gaps, e o time executa um restore completo de backup em ambiente de staging (não produção) para verificar que o processo de restore funciona, que os dados são consistentes, e medir quanto tempo leva. Esse teste custa apenas horas de trabalho e não afeta nenhum usuário, mas valida que os dados de backup são recuperáveis — a parte mais crítica de qualquer estratégia de DR.
