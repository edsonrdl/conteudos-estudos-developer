### Baixa latência — como a infraestrutura global da AWS minimiza o tempo de resposta

Latência é o tempo entre o envio de uma requisição e o recebimento da resposta. Na AWS, a baixa latência é resultado de uma combinação de infraestrutura física estrategicamente posicionada, backbone de rede privado de alta velocidade, e serviços de roteamento inteligente que direcionam usuários ao recurso mais próximo. Entender como cada camada contribui para a latência permite tomar decisões arquiteturais que otimizam a experiência do usuário globalmente.

---

## Os fatores físicos da latência

```
Latência de rede tem um limite físico:
  Velocidade da luz no fibra óptica: ~200.000 km/segundo
  
  Cálculo simples:
  São Paulo → us-east-1 (Virgínia, ~7.600 km):
  Mínimo teórico: 7.600 / 200.000 × 1.000ms = 38ms (one-way)
  Round-trip mínimo: ~76ms
  
  Na prática: ~120-150ms round-trip (roteiros BGP, overhead de protocolo)

  São Paulo → sa-east-1 (mesma cidade):
  Mínimo: < 1ms one-way
  Round-trip: 1-5ms

Componentes que somam latência:
  ├── Latência de propagação: física (velocidade da luz)
  ├── Latência de transmissão: tamanho do pacote / largura de banda
  ├── Latência de processamento: switches/roteadores no caminho
  └── Latência de fila: congestionamento na rede

O que a AWS controla:
  ├── Backbone privado (elimina hops de internet pública)
  ├── Edge Locations (aproxima o processamento ao usuário)
  ├── Otimização de protocolos (QUIC/HTTP3 no CloudFront)
  └── Roteamento inteligente (Route 53 Latency-based Routing)

O que você controla:
  ├── Escolha de Região (dados próximos dos usuários)
  ├── Cache strategy (CloudFront, ElastiCache)
  ├── Tamanho de payload (compressão, paginação)
  └── Conexões persistentes (keep-alive, connection pooling)
```

## O backbone privado da AWS

```
A AWS opera uma rede global privada separada da internet pública:

Topologia:
  Região us-east-1 ──── fibra privada ──── Região us-west-2
  Região sa-east-1 ──── fibra privada ──── Região us-east-1
  Edge Locations ────── fibra privada ──── Regiões

Vantagens vs. internet pública:

Internet pública (sem backbone):
  São Paulo → Virgínia:
  SP → Operadora Brasil → IXP BR → cabos submarinos → IXP EUA
  → Carrier americano → data center Virgínia
  Hops: 15-25 roteadores
  Latência: variável (120-200ms dependendo do congestionamento)

Backbone AWS (com Global Accelerator ou recursos na Edge):
  São Paulo → Edge Location SP (< 5ms)
  → Backbone privado AWS → us-east-1 (< 50ms total)
  Hops: 3-5 (controlados pela AWS)
  Latência: determinística (~50-70ms total)

Resultado: 30-40% menos latência + muito menos jitter
```

## Route 53 — roteamento por latência

### Latency-based Routing

```
Route 53 redireciona usuários para a Região com menor latência:

Configuração:
  DNS: api.empresa.com
  
  Record 1: api.empresa.com → 1.2.3.4 (us-east-1), Region: us-east-1
  Record 2: api.empresa.com → 5.6.7.8 (sa-east-1), Region: sa-east-1
  Record 3: api.empresa.com → 9.10.11.12 (eu-west-1), Region: eu-west-1

Funcionamento:
  Usuário em São Paulo resolve api.empresa.com:
  → Route 53 mede latência esperada para cada Record
  → sa-east-1: ~10ms (mais próximo)
  → us-east-1: ~120ms
  → eu-west-1: ~200ms
  → Route 53 retorna: 5.6.7.8 (sa-east-1)
  
  Usuário em Frankfurt resolve api.empresa.com:
  → eu-west-1: ~15ms (mais próximo)
  → Route 53 retorna: 9.10.11.12 (eu-west-1)

Como Route 53 mede latência:
  → Não faz ping em tempo real para cada usuário
  → Mantém banco de dados histórico de latência por IP prefix → Região
  → Atualizado periodicamente com dados reais de latência
  → Decisão baseada em dados históricos (não medição em tempo real)

Health Check integration:
  Se sa-east-1 ficar doente:
  → Route 53 detecta via Health Check
  → Remove sa-east-1 dos resultados
  → Usuários de SP passam a receber us-east-1
  → Latência aumenta, mas serviço continua disponível
```

### Geolocation Routing

```
Diferente de Latency-based: baseia-se em ONDE o usuário está
(não em qual Região é mais rápida):

Configuração:
  Record 1: api.empresa.com → us-east-1, Location: US
  Record 2: api.empresa.com → eu-west-1, Location: Europe
  Record 3: api.empresa.com → sa-east-1, Location: South America
  Record 4: api.empresa.com → sa-east-1, Default (qualquer lugar)

Casos de uso do Geolocation (diferente de Latency):
  ├── Compliance: dados de europeus DEVEM ir para eu-west-1 (GDPR)
  ├── Conteúdo geo-restrito: usuários brasileiros veem catálogo BR
  ├── Idioma: usuários japoneses veem interface em japonês
  └── Preços regionais: usuários veem preços em moeda local

Vs. Latency-based:
  Latency: otimiza performance (escolhe o mais rápido)
  Geolocation: impõe regra de onde o tráfego VAI (independente de latência)
  
  Pode ser menos performático:
  "Usuário no México vai para us-east-1 (regra: América = us-east-1)"
  Mesmo que sa-east-1 tenha latência similar por cabo submarino

Geoproximity (Route 53 Traffic Flow):
  Variação avançada: roteia baseado em distância geográfica
  com bias configurável:
  "Envie um pouco mais de tráfego para us-east-1
   mesmo para usuários que estão ligeiramente mais próximos de sa-east-1"
  → Útil para balancear carga entre regiões
```

## CloudFront — reduzindo latência de conteúdo

```
Para conteúdo estático e APIs cacheáveis:
  Sem CloudFront: usuário → Região (120ms+ para usuários distantes)
  Com CloudFront: usuário → Edge Location (< 10ms para cache hit)

Configuração de cache por tipo de conteúdo:

Conteúdo estático (imagens, CSS, JS, fontes):
  Cache-Control: public, max-age=31536000, immutable
  → CloudFront cacheia indefinidamente (ou até invalidação)
  → 100% de cache hit para arquivos que nunca mudam

HTML (pages):
  Cache-Control: no-cache
  → CloudFront revalida com origin a cada request
  → Mas pode usar stale-while-revalidate para resposta imediata

APIs REST:
  Cache-Control: public, max-age=60
  → CloudFront cacheia por 60 segundos
  → Múltiplos usuários solicitando o mesmo endpoint compartilham cache
  → Reduz carga no backend e latência para usuários subsequentes

Quando NOT usar CloudFront:
  → APIs altamente personalizadas (cada response é único por usuário)
  → Dados em tempo real que mudam a cada segundo
  → Websockets (CloudFront suporta mas com limitações)
  → Operações que modificam estado (POST, PUT, DELETE com payload único)
```

## ElastiCache — latência de acesso a dados

```
Hierarquia de latência de dados:

EC2 local memory (Python dict): < 0.001ms
ElastiCache Redis (mesma AZ): 0.1-1ms
RDS (mesma AZ): 1-10ms
RDS (cross-AZ): 2-15ms
S3 (mesma Região): 10-100ms
S3 (cross-Region): 50-200ms

Estratégia de cache:

Cache-aside (mais comum):
  def get_produto(produto_id):
      # Tentar do cache
      cached = redis.get(f"produto:{produto_id}")
      if cached:
          return json.loads(cached)  # < 1ms
      
      # Cache miss: buscar do banco
      produto = db.query("SELECT * FROM produtos WHERE id = ?", produto_id)
      
      # Salvar no cache para próximas requisições
      redis.setex(f"produto:{produto_id}", 3600, json.dumps(produto))
      
      return produto  # ~5-10ms na primeira vez

Write-through (dados sempre frescos no cache):
  def update_produto(produto_id, dados):
      db.update(produto_id, dados)  # escreve no banco
      redis.setex(f"produto:{produto_id}", 3600, json.dumps(dados))  # e no cache
      # Próximas leituras: sempre do cache (frescos)

Cache para resultados de queries caras:
  # Consulta que demora 500ms no banco
  def get_relatorio_vendas():
      cached = redis.get("relatorio:vendas:hoje")
      if cached:
          return json.loads(cached)  # 0.5ms em vez de 500ms
      
      resultado = db.query("""
          SELECT produto, SUM(valor) FROM vendas 
          WHERE data = CURRENT_DATE 
          GROUP BY produto
      """)  # 500ms
      
      redis.setex("relatorio:vendas:hoje", 300, json.dumps(resultado))
      return resultado
```

## Medindo latência — ferramentas e métricas

```
Ferramentas de medição:

CloudWatch Metrics:
  ALB → TargetResponseTime: latência do backend (p50, p90, p99)
  CloudFront → OriginLatency: latência para a origem
  API Gateway → IntegrationLatency: latência do backend integrado
  
  ATENÇÃO: sempre analise percentis p99, não média:
  Média de 50ms pode esconder que 1% dos usuários espera 5 segundos
  
  Alarm: p99 de latência > 2000ms → alertar time de produto

X-Ray (tracing distribuído):
  Identifica qual componente da stack está adicionando latência:
  
  Request: 350ms total
  Breakdown:
  ├── ALB → EC2: 2ms
  ├── EC2 (processamento): 5ms
  ├── EC2 → RDS: 10ms
  ├── RDS (query): 330ms ← GARGALO
  └── RDS → EC2 → usuário: 3ms
  
  → 94% da latência é da query no banco
  → Adicionar índice ou cache resolve o problema

Synthetic Monitoring (CloudWatch Synthetics):
  Canary que roda de várias regiões e mede latência end-to-end:
  → Roda script de browser simulado do usuário real
  → Mede latência de Frankfurt, Tokyo, São Paulo para sua aplicação
  → Alerta se latência de qualquer região exceder threshold

Tools externos:
  cloudping.info → latência para cada Região AWS
  ping.canary.tools → latência de múltiplos pontos para seu endpoint
  GTmetrix, WebPageTest → performance completa (incluindo CDN)
```

## Otimizações de latência por camada

```
CAMADA DNS (Route 53):
  ├── TTL baixo para registros que mudam: 60-300s
  ├── TTL alto para registros estáticos: 86400s
  ├── Latency-based routing para múltiplas Regiões
  └── Route 53 Resolver for DNS in VPCs (evita resolução externa)

CAMADA DE REDE:
  ├── Usuários → CloudFront (< 10ms para cache hit)
  ├── VPC Endpoints para serviços AWS (sem egress para internet)
  ├── Placement Groups para instâncias que se comunicam muito
  │   → Cluster Placement Group: instâncias no mesmo rack (~10μs)
  └── Enhanced Networking (ENA): throughput maior, latência menor por instância

CAMADA DE APLICAÇÃO:
  ├── Connection pooling para banco de dados
  ├── HTTP/2 multiplexing (múltiplas requests em uma conexão)
  ├── Compressão gzip/brotli (payload menor = menos tempo de transmissão)
  ├── Lazy loading (carregar apenas o necessário)
  └── Async operations (não bloquear thread esperando I/O)

CAMADA DE DADOS:
  ├── Índices adequados (query de 500ms → 5ms com índice)
  ├── Read Replicas para distribuir reads
  ├── ElastiCache para dados frequentemente acessados
  ├── DynamoDB on-demand (< 10ms para qualquer throughput)
  └── S3 Intelligent-Tiering + Transfer Acceleration para uploads

CAMADA GLOBAL:
  ├── Global Accelerator para tráfego TCP/UDP (backbone privado)
  ├── Multi-Region deployments com Route 53 Latency routing
  ├── CloudFront para CDN global
  └── S3 Multi-Region Access Points para acesso global a dados
```

## Latência de rede interna AWS — dicas práticas

```
Ordem de latência crescente (recursos na mesma Região):

Mesma instância EC2 (loopback): < 0.1ms
Mesma AZ, via IP privado: 0.1-0.5ms
Diferente AZ, mesma Região, via IP privado: 1-3ms
Mesma Região, via Endpoint (S3, DynamoDB): 1-20ms
Serviços managed na mesma Região (SQS, SNS): 2-20ms
Cross-Region, via backbone AWS: 30-200ms

Implicação para microserviços:
  Se você tem Serviço A chamando Serviço B síncronamente:
  
  Mesma AZ: +0.5ms por chamada
  Diferente AZ: +2ms por chamada
  
  10 calls síncronos em chain na mesma AZ: +5ms total
  10 calls síncronos em chain em AZs diferentes: +20ms total
  
  → Para chains síncronos: colocar serviços na mesma AZ
  → Para independência: tolerar o custo de cross-AZ
  → Para performance crítica: desacoplar (async com SQS)
```

## 🧩 Quiz de Fixação

1. Uma aplicação tem usuários em São Paulo, Nova York e Frankfurt. O backend está apenas em us-east-1. Usuários em SP e Frankfurt relatam latência de 150-200ms, enquanto usuários em NY têm 20ms. Como o Route 53 Latency-based Routing e múltiplas Regiões resolveriam isso, e quais são os desafios de manter dados consistentes em múltiplas Regiões?
2. O time de produto observa que o p99 de latência da API é 2.5 segundos, mas a média é 80ms. O que essa discrepância indica e como o AWS X-Ray ajudaria a identificar e resolver o problema?
3. Por que o Global Accelerator reduz latência para APIs dinâmicas (não cacheáveis), onde o CloudFront não ajudaria, e em que cenário você usaria cada um?

**Respostas:**
1) Route 53 Latency-based Routing com deployments em 3 Regiões: criar registros DNS para api.empresa.com apontando para us-east-1 (NY), sa-east-1 (SP) e eu-west-1 (Frankfurt) com routing policy Latency. Route 53 redireciona cada usuário para a Região com menor latência medida historicamente — usuários de SP iriam para sa-east-1 (~10ms), Frankfurt para eu-west-1 (~15ms), NY para us-east-1 (~20ms). Desafios de consistência de dados: (1) Banco de dados: usar Aurora Global Database (replicação de us-east-1 para sa-east-1 e eu-west-1 com lag < 1 segundo) ou DynamoDB Global Tables (replicação automática entre Regiões) — mas escritas feitas em sa-east-1 levam ~100ms para aparecer em us-east-1; (2) Writes: para dados que precisam de consistência imediata (pagamentos, inventário), considerar routing para uma única Região de escrita enquanto reads distribuem; (3) Session state: usar DynamoDB Global Tables ou ElastiCache com replicação para que sessões criadas em SP sejam visíveis em outras Regiões; (4) Cache invalidação cross-region: quando dado muda em uma Região, o cache de outras Regiões precisa ser invalidado ou ter TTL baixo o suficiente.
2) A discrepância p99=2.5s vs média=80ms indica que a maioria das requisições é rápida, mas uma pequena fração (1%) experimenta degradação severa — padrão típico de: (1) slow queries no banco de dados sem índice adequado (a query executa rápido quando usa cache/plano otimizado, mas ocasionalmente faz full table scan); (2) cold start de Lambda ou EC2 (instâncias novas recém-lançadas pelo Auto Scaling); (3) conexão de banco sendo restabelecida (connection pool esgotado, timeout, reconexão); (4) garbage collection em JVM/Node.js causando pausa. AWS X-Ray resolve isso: instrumentando a aplicação com o SDK X-Ray, cada request gera um trace com breakdown temporal de cada componente. Filtrando traces com duração > 2 segundos, X-Ray mostra o mapa de serviços do request lento — por exemplo, "EC2 processamento: 15ms, EC2→RDS: 8ms, RDS query: 2.450ms" — identificando exatamente que a query RDS é o gargalo no p99. Com essa informação, o time executa EXPLAIN ANALYZE na query problemática, descobre o full table scan, e adiciona o índice correto — resolvendo os 2.5s sem tocar no código.
3) CloudFront serve principalmente conteúdo cacheável — para APIs dinâmicas onde cada response é único por usuário (conta, saldo, histórico), o CloudFront apenas faz proxy sem cache, mas ainda usa o backbone AWS do Edge Location para a Região de origem. O Global Accelerator é superior para APIs dinâmicas porque: (1) roteia qualquer protocolo TCP/UDP (não só HTTP); (2) usa anycast routing — o IP do Global Accelerator é alcançado pelo edge mais próximo e o pacote entra na rede privada AWS imediatamente, percorrendo o backbone de alta velocidade até a Região; (3) sem overhead de processamento de cache (CloudFront processa headers, verifica cache rules mesmo para misses). Use CloudFront quando: o conteúdo tem componentes cacheáveis (assets estáticos, respostas de API com TTL), você precisa de WAF integrado na edge, ou está servindo conteúdo de S3. Use Global Accelerator quando: tráfego puramente dinâmico sem cache possível, protocolos além de HTTP (jogos, VoIP, IoT), necessidade de IPs estáticos globais, ou failover ultra-rápido entre Regiões sem depender de TTL de DNS.
