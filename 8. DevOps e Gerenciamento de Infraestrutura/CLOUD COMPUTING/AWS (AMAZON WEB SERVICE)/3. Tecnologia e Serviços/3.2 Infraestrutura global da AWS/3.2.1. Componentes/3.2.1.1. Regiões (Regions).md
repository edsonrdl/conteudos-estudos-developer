### Regiões AWS — a unidade geográfica fundamental da infraestrutura global

Uma Região AWS é um conjunto de data centers fisicamente separados e geograficamente agrupados em uma área específica do mundo. Cada Região é completamente independente das outras — dados não se movem entre Regiões a menos que você explicitamente configure isso. Com mais de 30 Regiões disponíveis, a AWS oferece cobertura global que permite servir usuários com baixa latência, atender requisitos de soberania de dados e implementar estratégias de disaster recovery geograficamente distribuídas.

---

## O que define uma Região AWS

```
Uma Região é:
  ├── Um nome geográfico: us-east-1 (Norte da Virgínia)
  ├── Múltiplas Zonas de Disponibilidade (mínimo 3, geralmente 3-6)
  ├── Cada AZ: um ou mais data centers físicos separados
  ├── Completamente isolada: falha de uma Região não afeta outras
  └── Independente de IAM, billing (parcialmente), e dados

Regiões mais importantes:
  us-east-1   → Norte da Virgínia, EUA (a maior, maioria dos serviços)
  us-west-2   → Oregon, EUA
  eu-west-1   → Irlanda
  eu-central-1→ Frankfurt, Alemanha
  ap-southeast-1 → Singapura
  ap-northeast-1 → Tóquio
  sa-east-1   → São Paulo, Brasil
  
Total: 33+ Regiões (crescendo continuamente)

Nomenclatura:
  [continente/país]-[direção]-[número]
  sa-east-1: South America, East, número 1
  eu-central-1: Europe, Central, número 1
  ap-southeast-2: Asia Pacific, Southeast, número 2 (Sydney)
```

## Como escolher a Região certa

### Critério 1: Latência para os usuários finais

```
Regra fundamental: colocar os recursos próximos aos usuários

Medição de latência por região: cloudping.info, awsspeedtest.com

Exemplo de latência aproximada do Brasil (sa-east-1 vs. outros):
  sa-east-1 (São Paulo):    ~10ms   ← usuários brasileiros
  us-east-1 (Virgínia):     ~120ms  ← aceitável para APIs
  eu-west-1 (Irlanda):      ~200ms  ← alto para usuário BR
  ap-southeast-1 (Singapura):~330ms ← inaceitável para usuário BR

Impacto na experiência do usuário:
  < 50ms:  imperceptível (excelente)
  50-100ms: levemente perceptível
  100-200ms: perceptível, aceitável para algumas apps
  > 200ms: claramente lento, impacta conversão em e-commerce

Para aplicação com usuários majoritariamente brasileiros:
  → sa-east-1 (São Paulo) é a escolha óbvia
  → CloudFront para conteúdo estático (edge locations globais)
  → API e banco: sa-east-1
```

### Critério 2: Conformidade e soberania de dados

```
Alguns dados não podem sair de certas jurisdições:

LGPD (Brasil):
  → Dados pessoais de brasileiros podem ser processados em sa-east-1
  → Transferência internacional: permitida com mecanismos adequados (DPA)
  → Setores regulados (financeiro, saúde): verificar regulação setorial

GDPR (Europa):
  → Dados de europeus: eu-west-1, eu-central-1, eu-west-2, eu-north-1, etc.
  → Standard Contractual Clauses (SCCs) para transferências para fora da UE
  → Dados podem ser processados em outras regiões com SCCs adequadas

China:
  → Regiões cn-north-1 (Beijing) e cn-northwest-1 (Ningxia)
  → Operadas por parceiros locais (Sinnet, NWCD) — não pela AWS diretamente
  → Conta AWS separada necessária
  → Regulação específica de internet na China

Governo americano:
  → us-gov-east-1, us-gov-west-1 (AWS GovCloud)
  → Para dados ITAR, FedRAMP High, dados sigilosos
  → Apenas para cidadãos americanos

Escolha de Região para compliance:
  → Mapear jurisdições dos usuários/dados
  → Identificar regulações aplicáveis
  → Confirmar que a Região tem os serviços necessários
  → Usar SCPs para garantir que dados não saiam da Região correta
```

### Critério 3: Disponibilidade de serviços

```
Nem todos os serviços AWS estão disponíveis em todas as Regiões:

us-east-1 (Norte da Virgínia): primeiro a receber novos serviços
sa-east-1 (São Paulo): cobertura menor, alguns serviços indisponíveis

Verificar disponibilidade: aws.amazon.com/about-aws/global-infrastructure/regional-product-services

Serviços tipicamente disponíveis em todas as Regiões:
  ├── EC2, ECS, EKS, Lambda
  ├── S3, EBS, EFS
  ├── RDS, DynamoDB, Aurora
  ├── VPC, CloudFront, Route 53
  ├── IAM, CloudTrail, CloudWatch
  └── SQS, SNS, EventBridge

Serviços que podem não estar em sa-east-1:
  → Alguns modelos específicos do Bedrock (AI generativa)
  → Alguns tipos de instância EC2 mais novos
  → Alguns serviços de ML especializados
  
Estratégia para serviço ausente na Região principal:
  → Lambda em sa-east-1 chama API em us-east-1 (latência aceitável para async)
  → CloudFront com origem em outra Região
  → Avaliar se a latência cross-region é aceitável para o caso de uso
```

### Critério 4: Preço

```
Preços variam entre Regiões para o mesmo serviço:

Exemplos de diferença de preço (EC2 m6i.xlarge, On-Demand):
  us-east-1 (Virgínia):  $0.192/hora  ← mais barato (baseline)
  eu-west-1 (Irlanda):   $0.214/hora  (+11%)
  ap-northeast-1 (Tóquio): $0.248/hora (+29%)
  sa-east-1 (São Paulo): $0.326/hora  (+70%)

Por que sa-east-1 é mais caro:
  → Menor escala (menos clientes) → menos economia de escala
  → Infraestrutura de telecomunicações mais cara no Brasil
  → Impostos e custos operacionais locais

Estratégia de custo por Região:
  Workloads sem requisito de localidade (ex: batch jobs de ML):
  → us-east-1 ou us-west-2 (mais baratos)
  → Desde que latência não seja crítica para o workload

  Workloads com usuários brasileiros ou dados LGPD:
  → sa-east-1 é necessário (custo maior é justificado)

  Análise de custo:
  Processar 1 TB de dados em sa-east-1 vs. us-east-1:
  → Custo de compute: 70% mais caro em sa-east-1
  → Data transfer para Brasil de us-east-1: $120/TB de egress
  → Dependendo do volume, manter em sa-east-1 pode ser mais barato
     mesmo com compute mais caro (evita data transfer cross-region)
```

## Regiões e Disaster Recovery

```
Estratégias de DR entre Regiões:

1. BACKUP AND RESTORE (RPO: horas, RTO: horas):
   Região primária → backups replicados → Região secundária
   Se primária falhar: restaurar da Região secundária
   
   Custo: baixo (apenas armazenamento de backup)
   Exemplo: S3 Cross-Region Replication para buckets de backup
   
2. PILOT LIGHT (RPO: minutos, RTO: 10-60 min):
   Região primária: stack completo ativo
   Região secundária: dados replicados + infra mínima (banco rodando)
   Se primária falhar: expandir a infra secundária (EC2, ECS, etc.)
   
   Custo: moderado (banco rodando, compute desligado)
   Implementação: Aurora Global Database para dados, EC2 desligadas

3. WARM STANDBY (RPO: segundos, RTO: minutos):
   Região primária: stack completo em capacidade total
   Região secundária: stack reduzido mas funcionando (ex: 20% da capacidade)
   Se primária falhar: escalar a secundária para capacidade total
   
   Custo: médio-alto (segunda região ativa com custo contínuo)

4. MULTI-SITE ACTIVE-ACTIVE (RPO: zero, RTO: zero):
   Ambas as regiões ativas 100% do tempo
   Route 53 distribui tráfego entre ambas
   Se uma falhar: Route 53 detecta e redireciona tudo para a outra
   
   Custo: alto (2x a infra de produção)
   Serviços que facilitam: Aurora Global, DynamoDB Global Tables,
   S3 Cross-Region Replication, Route 53 Health Checks

Escolha de Região secundária:
  sa-east-1 (primária) + us-east-1 (secundária):
  → Latência entre regiões: ~120ms (replicação aceitável)
  → Separação geográfica: adequada para desastre natural
  
  Evitar: usar duas regiões muito próximas geograficamente
  → Desastre natural poderia afetar ambas
```

## Regiões e o modelo de responsabilidade

```
A Região é um limite importante no modelo de responsabilidade:

Dentro de uma Região:
  → Dados nunca saem da Região por padrão
  → AWS garante isolamento físico entre clientes
  → Mesmo workload em us-east-1 e sa-east-1 são ambientes completamente separados

Global (transcende Regiões):
  → IAM: global (usuários/roles valem em todas as Regiões)
  → Route 53: global (DNS é global)
  → CloudFront: global (edge locations em todo o mundo)
  → Billing: global (fatura consolidada, mas custo por Região visível)

Regional (específico por Região):
  → EC2, RDS, S3 (com raras exceções como S3 global endpoints)
  → VPC: regional
  → Security Groups, EBS, AMIs: regionais
  → Lambda: regional

Implicação prática:
  Um IAM Role criado funciona em qualquer Região
  Uma AMI criada em us-east-1 não está disponível em sa-east-1
  → aws ec2 copy-image para copiar AMI entre Regiões
```

## SCPs para garantir residência de dados

```
Service Control Policy para forçar uso de Região específica:

{
  "Effect": "Deny",
  "Action": "*",
  "Resource": "*",
  "Condition": {
    "StringNotEquals": {
      "aws:RequestedRegion": [
        "sa-east-1",   ← única Região permitida (dados brasileiros)
        "us-east-1"    ← Região secundária para DR
      ]
    },
    "ArnNotLike": {
      "aws:PrincipalARN": "arn:aws:iam::*:role/GlobalAdminRole"
    }
  }
}

Efeito:
  → Nenhum recurso pode ser criado fora de sa-east-1 ou us-east-1
  → Proteção contra configurações acidentais em outras Regiões
  → Garante residência de dados para LGPD
  → Exceção para GlobalAdminRole (emergências e configuração global)
```

## 🧩 Quiz de Fixação

1. Uma startup brasileira está escolhendo entre sa-east-1 e us-east-1 para hospedar sua aplicação SaaS voltada para empresas brasileiras. Quais são os três critérios mais importantes para essa decisão e qual seria a recomendação final?
2. Uma empresa global tem dados de clientes europeus e brasileiros. Ela quer garantir que dados europeus nunca saiam da Europa e dados brasileiros nunca saiam do Brasil. Como implementar essa garantia técnica usando AWS Organizations e SCPs?
3. A Região sa-east-1 não tem um serviço de ML específico que a aplicação precisa. O time propõe usar us-east-1 para o processamento de ML e sa-east-1 para os dados dos usuários. Quais são os riscos de compliance desta arquitetura e como mitigá-los?

**Respostas:**
1) Os três critérios mais importantes: (1) Latência para usuários — empresas brasileiras acessando de São Paulo ou outras cidades terão ~10ms para sa-east-1 vs. ~120ms para us-east-1; para uma aplicação SaaS usada durante o dia de trabalho, 120ms é perceptível e pode afetar a experiência; (2) Conformidade LGPD — dados de clientes brasileiros (funcionários, leads, informações financeiras) estão sujeitos à LGPD; manter em sa-east-1 simplifica demonstrar conformidade e evita complexidade de adequações para transferência internacional; (3) Custo vs. experiência do cliente — sa-east-1 é ~70% mais caro em compute, mas o custo de data transfer de us-east-1 para os usuários no Brasil ($0.09/GB) pode compensar a diferença dependendo do volume. Recomendação: sa-east-1 para o stack principal (banco, aplicação, dados dos clientes) para menor latência e conformidade LGPD simplificada; CloudFront para conteúdo estático (edge locations globais, incluindo Brasil); considerar us-east-1 apenas para workloads assíncronos de processamento (ML, analytics) que não afetam latência do usuário diretamente.
2) Implementação com SCPs por OU: (1) Criar duas OUs na organização: `OU-Europe` (contas que processam dados europeus) e `OU-Brazil` (contas que processam dados brasileiros); (2) SCP para `OU-Europe`: Deny em todas as actions com Condition `aws:RequestedRegion` NOT IN `[eu-west-1, eu-central-1, eu-west-2, eu-north-1, eu-south-1]` — bloqueia criação de qualquer recurso fora da Europa; (3) SCP para `OU-Brazil`: Deny com Condition `aws:RequestedRegion` NOT IN `[sa-east-1]` — bloqueia criação fora de São Paulo; (4) Adicionar ao DPA/contratos com usuários: cláusula de que dados são processados nas respectivas regiões geográficas; (5) Monitoramento: Config Rule + CloudTrail para detectar e alertar se qualquer tentativa de criar recurso em Região não autorizada for feita (mesmo que o SCP a bloqueie, o log é importante para auditoria).
3) Riscos de compliance: (1) LGPD — ao enviar dados de usuários brasileiros para us-east-1 para processamento de ML (mesmo que temporariamente), ocorre transferência internacional de dados pessoais; a LGPD (Art. 33) permite isso com mecanismos adequados, mas exige base legal explícita (consentimento ou contrato com cláusulas de proteção); (2) Exposição de dados sensíveis — dados de treinamento/inferência em ML frequentemente contêm PII; em us-east-1 sob diferentes jurisdições americanas (incluindo CLOUD Act), pode haver exigências de acesso governamental que não se aplicam em sa-east-1; (3) Custo de egress — enviar dados para us-east-1 e resultados de volta: $0.02/GB cross-region. Mitigações: (1) Implementar anonimização/pseudoanonimização antes de enviar para us-east-1 (dados processados não seriam pessoais sob LGPD); (2) Usar Lambda@Edge ou CloudFront Functions para processamento simples na edge sem mover dados de sa-east-1; (3) Verificar se o serviço de ML tem equivalente em sa-east-1 ou se pode ser solicitado à AWS (account team pode acelerar disponibilidade de serviços); (4) Formalizar o mecanismo de transferência no DPA/política de privacidade caso a transferência seja necessária.
