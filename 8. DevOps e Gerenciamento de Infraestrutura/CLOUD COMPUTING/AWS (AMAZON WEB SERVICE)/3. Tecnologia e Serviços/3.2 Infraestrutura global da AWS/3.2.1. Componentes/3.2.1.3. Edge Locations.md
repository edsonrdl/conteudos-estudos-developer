### Edge Locations — a rede global de pontos de presença da AWS

Edge Locations são pontos de presença (PoPs — Points of Presence) da AWS distribuídos pelo mundo, separados das Regiões principais. Enquanto Regiões são grandes complexos de data centers com todos os serviços AWS, Edge Locations são instalações menores e mais numerosas (300+ no mundo) focadas em entregar conteúdo e processar requisições com a menor latência possível para o usuário final. São a infraestrutura que possibilita o CloudFront, Lambda@Edge, Global Accelerator e Route 53 operarem com performance global.

---

## Região vs. Edge Location — a diferença fundamental

```
REGIÃO (ex: sa-east-1 São Paulo):
  ├── Complexo completo de data centers
  ├── Executa todos os serviços AWS (EC2, RDS, Lambda, etc.)
  ├── ~33 Regiões no mundo
  ├── Você escolhe a Região para cada recurso
  └── Distância do usuário: pode ser centenas de km

EDGE LOCATION (ex: Fortaleza, Brasil):
  ├── Instalação menor, focada em caching e proximity
  ├── Executa: CloudFront, Lambda@Edge, CloudFront Functions, Route 53
  ├── 300+ locais no mundo
  ├── AWS escolhe automaticamente o mais próximo do usuário
  └── Distância do usuário: geralmente < 50-100 km

Analogia:
  Região = fábrica central (produz tudo)
  Edge Location = loja de distribuição local (entrega rapidamente o que já está pronto)
  
  Usuário em Fortaleza:
  Sem Edge: Fortaleza → São Paulo (sa-east-1) → resposta (~20ms)
  Com Edge: Fortaleza → Edge Location Fortaleza → resposta (~2ms)
  → 10x mais rápido para conteúdo cacheado
```

## CloudFront — o serviço principal das Edge Locations

### Como o CloudFront usa Edge Locations

```
Fluxo sem CloudFront:
  Usuário em Frankfurt → sua origem em us-east-1 → conteúdo
  Latência: ~120ms por requisição × 1.000 usuários = 120 segundos totais

Fluxo com CloudFront:
  Usuário em Frankfurt
    ↓
  Edge Location Frankfurt (< 5ms de distância)
    ├── Cache HIT? → resposta imediata em < 5ms (99% dos casos para conteúdo estático)
    └── Cache MISS? → busca na origem (us-east-1, ~120ms) → cacheia → responde
  
  Nas próximas requisições do mesmo conteúdo: sempre < 5ms

O cache nas Edge Locations:
  ├── TTL (Time to Live): definido pelos headers do conteúdo (Cache-Control)
  ├── Objetos cacheados: imagens, CSS, JS, vídeos, APIs com cache habilitado
  ├── Invalidação: você pode invalidar o cache programaticamente
  └── Cache por Edge Location: cada PoP tem cache independente

Hit ratio:
  Alta taxa de cache = a maioria das requisições não vai à origem
  → Menos carga na origem (EC2, S3, ALB)
  → Menor custo (egress de S3 para CloudFront: GRATUITO)
  → Menor latência para o usuário
```

### Configuração básica de CloudFront

```
Distribuição CloudFront:
  Origem: 
  ├── S3 bucket (conteúdo estático)
  ├── ALB (aplicação dinâmica)
  ├── API Gateway
  └── Qualquer HTTP endpoint

  Behaviors (comportamentos por path):
  /images/*  → cachear por 24h (conteúdo estático)
  /api/*     → não cachear (conteúdo dinâmico)
  /          → cachear por 1h (HTML pode mudar)
  
  Headers de cache:
  Cache-Control: max-age=86400    → CloudFront cacheia por 24h
  Cache-Control: no-cache         → CloudFront consulta origem a cada req
  Cache-Control: no-store         → CloudFront nunca cacheia

Domínio customizado + certificado:
  → Route 53 CNAME: www.empresa.com → d123abc.cloudfront.net
  → Certificado ACM em us-east-1 (obrigatório para CloudFront)
  → HTTPS transparente para o usuário
```

## Lambda@Edge — computação nas Edge Locations

```
Lambda@Edge executa código em cada Edge Location, não em Regiões:

Casos de uso:
  ├── Personalização de conteúdo por usuário (sem ir ao origin)
  ├── Redirecionamentos A/B testing na edge
  ├── Autenticação/autorização antes de chegar ao backend
  ├── Reescrita de URLs
  └── Adição de headers de segurança

Os quatro gatilhos do CloudFront:

  Usuário → [Viewer Request] → CloudFront Cache
                                  ├── Cache HIT → [Viewer Response] → Usuário
                                  └── Cache MISS → [Origin Request] → Origem
                                                                          ↓
                                            Origem → [Origin Response] → Cache

  1. Viewer Request: executa antes de verificar o cache
     → Modificar a requisição do usuário
     → Autenticar (verificar JWT antes de qualquer coisa)
     → Redirecionar baseado em user-agent, geolocalização

  2. Origin Request: executa quando vai à origem (cache miss)
     → Modificar request para a origem
     → Adicionar headers de autenticação para a origem
     → Cachear baseado em headers personalizados

  3. Origin Response: executa quando a origem responde
     → Modificar resposta da origem antes de cachear
     → Adicionar headers de cache dinamicamente

  4. Viewer Response: executa antes de devolver ao usuário
     → Adicionar headers de segurança (HSTS, CSP, X-Frame-Options)
     → Modificar resposta antes de chegar ao browser

Exemplo — Adicionar headers de segurança com Lambda@Edge:

exports.handler = async (event) => {
    const response = event.Records[0].cf.response;
    const headers = response.headers;
    
    headers['strict-transport-security'] = [{
        key: 'Strict-Transport-Security',
        value: 'max-age=31536000; includeSubDomains; preload'
    }];
    
    headers['x-content-type-options'] = [{
        key: 'X-Content-Type-Options',
        value: 'nosniff'
    }];
    
    headers['x-frame-options'] = [{
        key: 'X-Frame-Options',
        value: 'DENY'
    }];
    
    return response;
};
// Executado em cada Edge Location — usuário recebe headers sem latência extra
```

## CloudFront Functions — alternativa mais leve a Lambda@Edge

```
CloudFront Functions são mais simples e mais baratas que Lambda@Edge:

Comparação:
                    CloudFront Functions   Lambda@Edge
Latência            Sub-milissegundo       Milissegundos
Gatilhos            Viewer Request/Response Todos os 4 gatilhos
Tempo máximo execução 1ms                  5s (viewer), 30s (origin)
Memória             2MB                    128MB-10GB
Linguagem           JavaScript (ES 5.1)    Node.js, Python
Acesso à internet   Não                    Sim (origin request/response)
Acesso a rede VPC   Não                    Sim (origin request/response)
Custo               $0.10/M invocações     $0.60/M + compute
Regiões             Global (Edge Locations) us-east-1 (replicado)

Quando usar CloudFront Functions:
  → Operações simples e rápidas: URL rewrite, header manipulation
  → Cache key customization
  → Redirects simples
  → Validação básica de token (sem chamadas externas)

Quando usar Lambda@Edge:
  → Lógica complexa com múltiplas chamadas
  → Acesso a banco de dados ou APIs externas
  → Processamento que leva mais de 1ms
  → Autenticação com OAuth/JWT validation completa

Exemplo CloudFront Function — URL rewrite:
function handler(event) {
    var request = event.request;
    var uri = request.uri;
    
    // Redireciona /old-path para /new-path
    if (uri.startsWith('/old-path')) {
        request.uri = uri.replace('/old-path', '/new-path');
    }
    
    return request;
}
```

## Regional Edge Caches — a camada intermediária

```
Hierarquia de cache do CloudFront:

Usuário → Edge Location (cidade) → Regional Edge Cache (país/continente) → Origem

Regional Edge Caches:
  → Maior capacidade de armazenamento que Edge Locations
  → Mantêm objetos por mais tempo (cache de segundo nível)
  → Se Edge Location não tem o objeto: vai ao Regional Cache (não à Origem)
  → Reduz ainda mais as requisições que chegam à origem
  
Localização dos Regional Edge Caches:
  São Paulo, São Francisco, Virginia, Irlanda, Frankfurt, 
  Singapura, Tóquio, Mumbai, Sydney, etc.

Benefício:
  Usuário em Fortaleza → Edge Location Fortaleza
  → Cache miss → Regional Edge Cache São Paulo (< 10ms)
  → Cache hit no Regional Cache → responde ao Fortaleza Edge Location
  → 99% dos objetos populares nunca chegam à origem
```

## Global Accelerator — aceleração de tráfego dinâmico

```
Enquanto CloudFront é para conteúdo (HTTP/HTTPS),
Global Accelerator acelera QUALQUER tráfego TCP/UDP:

Como funciona:
  Usuário → Edge Location mais próximo
           → Backbone privado da AWS (não internet)
           → Endpoint na Região de destino

Benefício:
  Sem Global Accelerator:
  Cliente em São Paulo → internet → us-east-1 (roteamento BGP público)
  → Latência variável, muitos hops
  
  Com Global Accelerator:
  Cliente em São Paulo → Edge Location SP
  → Backbone privado AWS (baixa latência, determinística)
  → us-east-1
  → Latência 20-40% menor, muito mais consistente

Casos de uso:
  ├── Aplicações que não são HTTP (VoIP, jogos, IoT)
  ├── APIs com requisito de baixa latência global
  ├── Failover multi-região transparente (troca de endpoint sem DNS TTL)
  └── Client VPN com melhor performance (via edge)

Dois IPs Anycast estáticos:
  Global Accelerator fornece 2 IPs globais
  → Tráfego para esses IPs vai ao Edge Location mais próximo
  → Funciona com failover automático entre Regiões
```

```
  ├── São Paulo (múltiplos PoPs)

  ├── Fortaleza
  ├── Porto Alegre

  cloudping.info → mede latência para cada Edge Location
  dig +short myip.opendns.com → seu IP
  traceroute para d123.cloudfront.net → mostra o PoP utilizado

Impacto para aplicações brasileiras:
  Usuário em Manaus (sem edge próxima):
  → Latência até São Paulo (1.700 km): ~30ms
  → CloudFront serve da edge mais próxima disponível

  Usuário em São Paulo:
  → Latência para Edge Location SP: ~2-5ms
  → Conteúdo estático cacheado: resposta quase instantânea
```

## 🧩 Quiz de Fixação

1. Um usuário em Fortaleza acessa um site hospedado em S3 (us-east-1) através do CloudFront. A primeira requisição para `/images/logo.png` demora 150ms. A segunda requisição para o mesmo arquivo demora 3ms. Explique o que aconteceu em cada requisição.
2. Qual é a diferença entre usar Lambda@Edge e CloudFront Functions para adicionar headers de segurança HTTP a todas as respostas, e qual é a escolha mais adequada para esse caso de uso específico?
3. Uma aplicação de jogos multiplayer precisa de latência mínima global para jogadores no Brasil, Europa e Ásia conectando ao servidor de jogo em us-east-1. Por que CloudFront não é a solução ideal aqui e como o Global Accelerator resolve o problema?

**Respostas:**
1) Primeira requisição (150ms): foi um cache MISS. A requisição chegou ao Edge Location mais próximo de Fortaleza, que não tinha o arquivo em cache. O Edge Location foi buscar o objeto na origem (S3 em us-east-1/São Paulo), o que levou ~150ms (latência de rede Fortaleza→S3 + processamento). O objeto foi armazenado no cache do Edge Location com o TTL definido pelo header `Cache-Control`. Segunda requisição (3ms): foi um cache HIT. O arquivo já estava cacheado no Edge Location de Fortaleza. A requisição foi processada inteiramente dentro do PoP local, sem precisar ir à origem. Os 3ms representam a latência de rede entre o usuário e o Edge Location (~2ms) mais o tempo de busca no cache local (~1ms). Enquanto o objeto permanecer em cache (conforme o TTL configurado), todas as requisições subsequentes terão a mesma performance de ~3ms.
2) CloudFront Functions são a escolha correta para adicionar headers de segurança. Comparação: a operação de adicionar headers de segurança (`Strict-Transport-Security`, `X-Content-Type-Options`, `X-Frame-Options`) é extremamente simples — lê a resposta e adiciona campos fixos ao objeto de headers. Isso não requer chamadas externas, não precisa de internet, não tem lógica complexa, e executa em < 1ms. CloudFront Functions custam $0.10/M invocações vs. Lambda@Edge $0.60/M + custo de compute — 6x mais baratas. Além disso, CloudFront Functions executam em sub-milissegundo (sem latência perceptível), enquanto Lambda@Edge adiciona alguns milissegundos. Lambda@Edge seria necessário apenas se a lógica fosse complexa (ex: validar um JWT contra uma lista negra em DynamoDB, fazer uma chamada a uma API de autorização externa) — nesses casos a latência maior e o custo maior se justificam pela capacidade adicional.
3) CloudFront não é ideal para jogos multiplayer porque: (1) CloudFront é otimizado para HTTP/HTTPS — jogos multiplayer frequentemente usam UDP ou protocolos TCP customizados de baixa latência que o CloudFront não suporta; (2) CloudFront cacheia conteúdo — em jogos, cada pacote é único (posição de jogador, ação em tempo real), não há o que cachear; (3) A latência do CloudFront para conteúdo não-cacheável ainda passa pela internet pública entre o Edge e a Região. Global Accelerator resolve: (1) Suporta TCP e UDP — compatível com protocolos de jogos; (2) Sem cache — cada pacote chega diretamente ao servidor; (3) O jogador conecta ao Edge Location mais próximo e o tráfego percorre o backbone privado da AWS (não internet pública) até us-east-1 — latência 20-40% menor e muito mais consistente (jitter reduzido, crucial para jogos); (4) Dois IPs Anycast estáticos — jogadores de qualquer lugar do mundo conectam nos mesmos IPs, que roteiam automaticamente ao PoP mais próximo. Para um jogador no Brasil: basta o tráfego chegar ao Edge Location de São Paulo em ~5ms e o backbone faz o resto com latência previsível até us-east-1.
