### Zonas de Disponibilidade — o bloco fundamental de resiliência dentro de uma Região

Uma Zona de Disponibilidade (Availability Zone — AZ) é um ou mais data centers fisicamente separados dentro de uma Região AWS, conectados entre si por fibra de altíssima velocidade e baixíssima latência. As AZs são a unidade de isolamento de falhas dentro de uma Região — enquanto uma Região protege contra desastres geográficos (furacão, terremoto), múltiplas AZs protegem contra falhas de data center (incêndio, falha de energia, falha de hardware). A maioria dos serviços gerenciados da AWS distribui dados e computação entre AZs automaticamente.

---

## O que é uma AZ fisicamente

```
Região: us-east-1 (Norte da Virgínia)
  ├── AZ: us-east-1a → data center(s) em Loudoun County, VA
  ├── AZ: us-east-1b → data center(s) em Prince William County, VA
  ├── AZ: us-east-1c → data center(s) em Manassas, VA
  ├── AZ: us-east-1d → data center(s) em outro local
  ├── AZ: us-east-1e → data center(s) em outro local
  └── AZ: us-east-1f → data center(s) em outro local

Características físicas de cada AZ:
  ├── Localização: km a dezenas de km de distância das outras AZs
  ├── Energia: subestação elétrica independente (falha em uma não afeta outra)
  ├── Conectividade: múltiplos provedores de fibra independentes
  ├── Resfriamento: sistema de HVAC independente
  └── Latência entre AZs: < 2ms (fibra de alta velocidade da AWS)

Isolamento de falhas:
  Enchente em us-east-1a → apenas us-east-1a afetada
  Falha de energia em us-east-1b → apenas us-east-1b afetada
  Incêndio em us-east-1c → apenas us-east-1c afetada
  
  Probabilidade de múltiplas AZs falharem simultaneamente: muito baixa
  → A AWS projeta para que falhas em AZs sejam independentes
```

---

## AZ vs. Região — entendendo a hierarquia

```
REGIÃO (proteção geográfica):
  → Escopo: cidade/estado/país
  → Falha protegida: desastre natural regional, regulatory event
  → Latência entre Regiões: 100-300ms
  → Custo de tráfego: $0.02/GB entre Regiões
  → Dados: NÃO replicam entre Regiões por padrão

ZONA DE DISPONIBILIDADE (proteção de data center):
  → Escopo: data center individual ou cluster de DCs
  → Falha protegida: falha de hardware, energia, incêndio, falha de rede
  → Latência entre AZs: < 2ms (mesma Região)
  → Custo de tráfego: $0.01/GB entre AZs (por lado)
  → Dados: serviços gerenciados replicam entre AZs automaticamente

Analogia de resiliência:
  Uma única AZ = um único data center = SPOF de data center
  Múltiplas AZs = múltiplos data centers = sem SPOF de data center
  Múltiplas Regiões = múltiplos locais geográficos = sem SPOF regional
```

## Como distribuir recursos entre AZs

### Instâncias EC2 com Auto Scaling Group

```
Auto Scaling Group distribuído em múltiplas AZs:

ASG configurado:
  Availability Zones: ["us-east-1a", "us-east-1b", "us-east-1c"]
  min: 3, desired: 6, max: 12

Distribuição automática:
  us-east-1a: 2 instâncias
  us-east-1b: 2 instâncias
  us-east-1c: 2 instâncias
  
  AWS Auto Scaling distribui igualmente entre as AZs configuradas

Rebalancing (reequilíbrio):
  Se us-east-1a falhar e as 2 instâncias terminam:
  → ASG detecta: us-east-1b e us-east-1c com 2 cada (4 total)
  → ASG inicia 2 novas instâncias em us-east-1b ou us-east-1c
  → Tráfego redistribuído pelo ALB automaticamente
  
  Quando us-east-1a voltar:
  → ASG pode "rebalancear": termina instância em AZ sobrecarregada
  → Inicia nova instância em us-east-1a
  → Mantém distribuição equilibrada

Subnets e AZs (relação 1:1):
  Cada subnet existe em apenas uma AZ
  → Subnet A (10.0.1.0/24) → apenas us-east-1a
  → Subnet B (10.0.2.0/24) → apenas us-east-1b
  → Subnet C (10.0.3.0/24) → apenas us-east-1c
  
  Para distribuir EC2 em múltiplas AZs:
  → Criar subnet em cada AZ
  → ASG distribui instâncias entre as subnets
```

### RDS Multi-AZ — banco de dados resiliente

```
RDS Multi-AZ:
  Primary: us-east-1a (ativo, recebe leituras e escritas)
  Standby: us-east-1b (passivo, replicação síncrona)
  
  Replicação síncrona:
  → Write no Primary → replicado ANTES de confirmar ao cliente
  → Zero lag (RPO ≈ 0 segundos)
  
  Failover automático (se Primary falhar):
  1. RDS detecta falha (~30-60 segundos)
  2. Standby promovido a Primary automaticamente
  3. DNS do endpoint RDS atualizado
  4. Aplicação conecta ao novo Primary via DNS
  
  Por que usar endpoint DNS e não IP:
  → IP do Primary muda no failover
  → DNS é atualizado → aplicação reconecta automaticamente
  → SEM código de failover na aplicação
  
  RDS Multi-AZ NÃO é para read scaling:
  → Standby é passivo (não atende reads)
  → Para reads: usar Read Replicas (diferente de Multi-AZ)
```

### ElastiCache com replicação entre AZs

```
ElastiCache Redis com replicação multi-AZ:

Cluster mode disabled (replicação simples):
  Primary: us-east-1a
  Replica 1: us-east-1b
  Replica 2: us-east-1c
  
  Failover: se primary cair, uma replica é promovida (~30s)
  
Cluster mode enabled (sharding + replicação):
  Shard 1: Primary AZ-a + Replica AZ-b
  Shard 2: Primary AZ-b + Replica AZ-c
  Shard 3: Primary AZ-c + Replica AZ-a
  
  → Cada shard tem primary em AZ diferente (balanceia a carga)
  → Replica em AZ diferente do primary (HA garantida)
  → Se AZ-a cair: apenas shard 1 faz failover (shards 2 e 3 ok)
```

## O custo do tráfego cross-AZ — a armadilha frequente

```
Tráfego entre AZs (mesma Região): $0.01/GB por lado

Exemplo que gera custo invisível:

Microserviço A em AZ-a chama Microserviço B em AZ-b:
  → 100 GB/mês de tráfego entre serviços
  → Custo: 100 GB × $0.01 (saída de AZ-a) + 100 GB × $0.01 (entrada em AZ-b)
  → = $2.00/mês
  
  Parece barato, mas escala:
  100 microserviços × 100 GB de comunicação cross-AZ = $200/mês
  Arquitetura maior: pode chegar a milhares de dólares/mês

TRÁFEGO GRATUITO (entre instâncias na mesma AZ):
  EC2 em AZ-a → EC2 em AZ-a (via IP privado): GRATUITO
  EC2 em AZ-a → RDS em AZ-a (via IP privado): GRATUITO

Estratégias para minimizar custo cross-AZ:
  1. Colocation de serviços interdependentes:
     Serviço A e Banco de Dados B comunicam-se muito?
     → Colocar na mesma AZ quando possível
     → Trade-off: menor HA (ambos caem se AZ cair)
     → Aceitável para: cache, banco secundário de analytics
  
  2. Sticky sessions com ALB:
     ALB tem "Stickiness": conexão do mesmo usuário vai à mesma EC2
     → Se EC2 está na AZ-a, e o banco está na AZ-a: sem cross-AZ
     → Mas: quebra balanceamento perfeito
  
  3. Replicar dados localmente:
     Cache local em cada AZ (ElastiCache por AZ)
     → EC2 em AZ-a → ElastiCache em AZ-a (gratuito)
     → Ao invés de → ElastiCache em AZ-b (cross-AZ)
  
  4. Serviços gerenciados (ignoram custo cross-AZ):
     ALB, RDS Multi-AZ, EFS: tráfego interno entre AZs é gerenciado
     pela AWS → você não paga pelo tráfego de replicação interna
     Apenas tráfego da sua aplicação gera custo

Tráfego DENTRO da mesma AZ (via IP público): COBRA
  EC2 em AZ-a → S3 via IP público (mesmo que S3 seja "regional")
  → $0.01/GB cada lado
  Solução: VPC Gateway Endpoint para S3 (gratuito, sem cross-AZ)
```

## O conceito de AZ ID — mapeamento entre contas

```
Problema: "AZ names são diferentes entre contas"

Na conta A: us-east-1a pode mapear fisicamente para Data Center X
Na conta B: us-east-1a pode mapear para Data Center Y

A AWS randomiza o mapeamento de AZ name → AZ física por conta
(para distribuir carga entre DCs automaticamente)

AZ ID resolve isso:
  AZ ID é consistente entre contas:
  use1-az1, use1-az2, use1-az3...
  
  Conta A: us-east-1a = use1-az1
  Conta B: us-east-1a = use1-az3  ← mesma letra, AZ física diferente!
  Conta B: us-east-1c = use1-az1  ← mesma AZ física que AZ-a da conta A
  
  Quando usar AZ IDs:
  → Arquitetura multi-conta onde você precisa garantir co-location
    (ex: compartilhar dados sem custo de cross-AZ entre contas)
  → AWS Resource Access Manager (RAM) para recursos compartilhados
  
  Consultar AZ ID:
  aws ec2 describe-availability-zones \
    --query 'AvailabilityZones[*].{Name:ZoneName,ID:ZoneId}'
  
  Resultado:
  [
    {"Name": "us-east-1a", "ID": "use1-az1"},
    {"Name": "us-east-1b", "ID": "use1-az6"},
    {"Name": "us-east-1c", "ID": "use1-az2"}
  ]
```

## Quantas AZs usar?

```
Mínimo recomendado: 2 AZs
  → Proteção contra falha de um data center
  → Maioria das aplicações de produção usa 2-3 AZs

3 AZs (padrão para aplicações críticas):
  → Tolerante a falha de qualquer AZ sem perda de mais de 33% da capacidade
  → ECS/EKS Fargate, RDS Multi-AZ: usa 3 AZs automaticamente
  → ALB: distribui entre 3 AZs automaticamente
  → Auto Scaling Group: configurar 3 subnets = 3 AZs

Regra de distribuição (Auto Scaling com 3 AZs):
  desired capacity = 6 instâncias
  → 2 instâncias por AZ
  Se AZ-a falha:
  → 2 instâncias perdidas, 4 sobrevivem
  → Capacidade reduz para 67% — sistema continua funcionando
  → ASG lança 2 novas em AZ-b e AZ-c para restaurar
  
  desired capacity = 3 instâncias
  → 1 instância por AZ
  Se AZ-a falha:
  → 1 instância perdida, 2 sobrevivem
  → Capacidade reduz para 67% — sistema continua funcionando
  → ASG lança 1 nova para restaurar para 3

Local Zones e Wavelength Zones:
  Extensões de AZs para casos específicos:
  Local Zones: latência ultra-baixa para cidades específicas
  Wavelength: latência ultra-baixa para usuários de rede 5G
  (ver 3.2.1.4 e 3.2.1.5 para detalhes)
```

## 🧩 Quiz de Fixação

1. Uma aplicação tem ALB + 3 EC2 + RDS Multi-AZ, com todos os recursos distribuídos em us-east-1a, us-east-1b e us-east-1c. A AZ us-east-1b fica completamente offline. Descreva o que acontece com cada componente (ALB, EC2, RDS) e qual é o impacto no usuário final.
2. Um arquiteto percebe que os microserviços da aplicação estão gerando $800/mês em tráfego cross-AZ. Quais são as duas estratégias arquiteturais principais para reduzir esse custo e qual é o trade-off de cada uma?
3. O time de DevOps de uma empresa usa a conta A e precisa garantir co-location com recursos de um parceiro na conta B para evitar custo de cross-AZ. Eles assumem que "us-east-1a da conta A = us-east-1a da conta B". Por que essa suposição está errada e como verificar se realmente estão na mesma AZ física?

**Respostas:**
1) O que acontece com us-east-1b offline: **ALB** — o Application Load Balancer é um serviço gerenciado distribuído entre as AZs configuradas. Ele detecta via health checks que as instâncias EC2 em us-east-1b não respondem e para de rotear tráfego para elas automaticamente. As AZs us-east-1a e us-east-1c continuam recebendo tráfego normalmente — o ALB redistribui. **EC2** — as duas instâncias em us-east-1b ficam inacessíveis. O Auto Scaling Group detecta que estão unhealthy (via health check), as termina, e lança duas novas instâncias em us-east-1a e us-east-1c para restaurar a capacidade desejada. **RDS Multi-AZ** — se o primary estava em us-east-1b, o RDS detecta a falha em ~30-60 segundos e promove automaticamente o standby (em outra AZ) a primary. O endpoint DNS do RDS é atualizado. Aplicação reconecta via DNS. **Impacto no usuário final** — breve degradação de ~1-2 minutos (tempo de detecção do health check + failover do RDS). Após a recuperação, o sistema opera normalmente com capacidade reduzida até as novas EC2 ficarem saudáveis (~3-5 minutos total). Usuário pode ver alguns erros ou latência elevada brevemente, mas o serviço não fica completamente fora do ar.
2) Duas estratégias para reduzir custo cross-AZ: (1) **Afinidade de AZ (co-location)** — identificar quais microserviços comunicam-se intensamente e colocá-los na mesma AZ. Implementação: usar topology spread constraints no Kubernetes com `topologyKey: topology.kubernetes.io/zone` para agrupar pods relacionados, ou Auto Scaling Groups com preferred placement. Trade-off: se a AZ falhar, ambos os serviços caem juntos — reduz HA para essas comunicações. Aceitável para: serviços não-críticos, caches locais, componentes de analytics. (2) **Cache local por AZ** — em vez de compartilhar um cluster de cache central (cross-AZ), criar instâncias de cache em cada AZ. EC2 em AZ-a usa ElastiCache em AZ-a (gratuito). Trade-off: dados podem ficar levemente inconsistentes entre caches de AZs diferentes (eventual consistency); gerenciamento de múltiplos clusters aumenta complexidade operacional. Aceitável para: dados de sessão, dados de configuração, resultados de queries caras com tolerância a inconsistência eventual.
3) A AWS randomiza o mapeamento de AZ name para AZ física por conta — o objetivo é distribuir automaticamente a carga dos clientes entre os data centers físicos. Portanto, us-east-1a na conta A e us-east-1a na conta B provavelmente mapeiam para data centers físicos diferentes. A forma correta de verificar co-location é usar **AZ IDs**, que são consistentes entre contas. Passos: (1) Na conta A: `aws ec2 describe-availability-zones --query 'AvailabilityZones[*].{Name:ZoneName,ID:ZoneId}'` — anota qual AZ ID corresponde à AZ desejada (ex: us-east-1a = use1-az1); (2) Na conta B: mesmo comando — identifica qual AZ name corresponde ao mesmo AZ ID use1-az1 (pode ser us-east-1c na conta B, por exemplo); (3) Para garantir co-location: recursos na conta A em use1-az1 e recursos na conta B também em use1-az1 — mesmo data center físico. Ferramentas como AWS Resource Access Manager (RAM) para compartilhar subnets ou recursos entre contas usam AZ IDs internamente para garantir esse alinhamento.
